v2 보완 안내 · SAP Flight 통합 실습 시험 패키지 v2 - 단계형

Flight 통합 실습을 단계별 문제로 풀 수 있도록 구성한 하루 코스형 자료입니다.

Flight단계형시험v2
학습 목표
  • Flight 통합 실습을 단계적으로 진행할 수 있다.
  • 각 단계별 산출물과 검증 포인트를 이해할 수 있다.
  • 최신 v4 실습으로 확장하기 전 기본 흐름을 익힐 수 있다.
검수 후 보완 포인트
  • 단계형 학습 자료로 좋지만 최신 v4와 어떤 관계인지 안내가 필요합니다.
  • v2 보완본에서는 단계형 학습용이라는 위치를 명확히 표시합니다.
  • 처음 학습자는 이 자료로 흐름을 잡고 v4로 넘어가도록 안내합니다.

SAP Flight 통합 실습 시험 패키지 (단계형, 하루 코스)

대상: D75AW / GW100 / S4D400 / S4D401 / S4D437

목표: “한 시나리오”를 끝까지 완성하면서, 시험을 풀며 동시에 학습이 되도록 문제별 세부 단계를 제공합니다.

데이터: SCARR, SPFLI, SFLIGHT, SBOOK, SAIRPLANE, SCUSTOM, STRAVELAG (표준 Flight 모델)

0. 공통 시나리오

항공 운영팀은 (1) 운항/좌석/매출 KPI를 빠르게 보고, (2) 외부 채널(UI/API)로 제공하고, (3) 이상 징후(Alert)를 등록해 추적하려 합니다.

당신은 이를 위해 다음 5개 산출물을 순차적으로 완성해야 합니다.

  1. D75AW: ABAP 클래스 1개로 “KPI 리포트” 구현
  2. S4D400: KPI 리포트를 “Pushdown 중심”으로 리팩토링
  3. S4D401: KPI를 “CDS (ZI/ZC + Metadata Extension)”로 표준 레이어링
  4. GW100: KPI/상세 조회 OData V2 서비스 구현
  5. S4D437: KPI 기반 “Alert 관리” RAP BO 구현

공통 규칙(채점 공통)

  • 반복 SELECT, LOOP 안 SELECT 금지(예외는 근거/대안 필수)
  • 가능하면 집계/계산은 DB에서 수행 (SQL GROUP BY 또는 CDS)
  • 필요 컬럼만 SELECT (SELECT * 지양)
  • 레이어 분리: 조회/가공/출력(또는 노출) 분리

1. D75AW – “운항 KPI 리포트 클래스” (단계형 10문항)

산출물: 실행 클래스 1개 권장(예: ZCL_FLT_KPI_REPORT, IF_OO_ADT_CLASSRUN). 리포트로 구현해도 무방합니다.

문제 1. 프로젝트 뼈대(클래스 구조) 만들기

목표: 시험 전체의 기준 프레임을 먼저 고정합니다.

  1. 클래스 생성: ZCL_FLT_KPI_REPORT
  2. 퍼블릭 메소드 구성(권장):
    • run( ) 또는 if_oo_adt_classrun~main
    • read_input( ) – SSCR/파라미터 수집
    • select_raw( ) – 원천 조회(Flight/Booking)
    • build_kpi( ) – KPI 계산/집계
    • build_exceptions( ) – 이상치 추출
    • render( ) – 출력(ALV 또는 out)
  3. 예외 처리 전략을 결정합니다(예: CX_STATIC_CHECK 또는 메시지 테이블).

검증: 실행 시 “입력값 없음”에서도 기본 범위로 정상 동작(예: 최근 30일).

문제 2. 선택화면(SSCR) 설계 + 기본값 전략

목표: 사용자가 KPI를 안정적으로 조회할 수 있는 입력 UX를 설계합니다.

  1. 입력 요소:
    • SO_CARR (SCARR-CARRID) 다중 선택
    • SO_CONN (SPFLI-CONNID) 선택
    • SO_DATE (SFLIGHT-FLDATE) 범위
    • P_MODE (SUMMARY/DETAIL) 라디오
    • P_PAGE, P_SIZE (기본 1, 50)
  2. 기본값:
    • SO_DATE 비어 있으면 “오늘-30 ~ 오늘”
    • P_SIZE 비어 있으면 50
  3. 입력 검증:
    • P_PAGE >= 1, 1 <= P_SIZE <= 500
    • SO_DATE-high >= low

학습 포인트: SSCR은 “데이터 범위를 강제”해 성능사고를 유도합니다.

문제 3. 원천 조회 ①: 운항(SFLIGHT) + 노선(SPFLI) + 항공사(SCARR)

목표: KPI 계산에 필요한 최소 데이터만 “한 번”에 가져옵니다.

  1. 조회 전략을 정의합니다:
    • 기본: SFLIGHT 중심 + SPFLI/SCARR 조인
    • 조건: carrid/connid/date 범위 반영
    • 필요 컬럼만 선택(예: carrid, connid, fldate, seatsmax, seatsocc, price, currency 등)
  2. 정렬 기준을 결정합니다(페이징용): carrid, connid, fldate, flightno(가능하면)
  3. 결과 ITAB 타입을 선택합니다:
    • 대량 조회/정렬 필요: STANDARD + SORT
    • 키 조회 빈번: HASHED/SORTED (선택 이유 주석)

검증: 동일 조건으로 2회 실행 시 결과 건수 동일, 정렬 일관성 유지.

문제 4. 원천 조회 ②: 예약(SBOOK) 매출 집계용 조회 설계

목표: “예약 매출”을 KPI에 연결할 수 있도록 데이터를 준비합니다.

  1. 집계 단위를 먼저 결정합니다:
    • Carrier KPI: carrid 기준 합계
    • Route KPI: carrid+connid 기준 합계
    • 필요하면 Date 단위까지 확장(carrid+connid+fldate)
  2. SBOOK에서 필요한 컬럼을 선택합니다:
    • carrid, connid, fldate, loccuram(또는 유사 금액), forcuram/환산 여부는 선택
  3. 가능하면 DB에서 GROUP BY 집계하여 가져옵니다(가산점).

학습 포인트: “원천 테이블을 그대로 가져오는 것”과 “집계 형태로 가져오는 것”의 성능 차이를 체감합니다.

문제 5. KPI 계산 ①: 좌석 점유율(%) 정의 + 안전한 계산

목표: 비율 계산에서 0 나누기/정밀도 문제를 안전하게 처리합니다.

  1. 정의:
    • Occupancy% = SUM(seatsocc) / SUM(seatsmax) * 100
  2. 처리 규칙:
    • SUM(seatsmax)=0이면 occupancy는 NULL 또는 0으로 처리하고, 예외 목록으로 이동
    • 고정소수점/반올림 규칙 결정(예: 소수 1자리 반올림)
  3. ABAP 계산 vs DB 계산 중 선택하고, 선택 이유를 서술합니다.

문제 6. KPI 계산 ②: 매출(Revenue) 집계 + 통화 취급 전략

목표: 금액 집계는 “통화 문제”가 항상 따라옵니다.

  1. 기본(필수): 동일 통화 기준으로 합산 가능한 범위에서 Revenue를 산출합니다.
  2. 확장(선택/가산점):
    • 통화가 다를 수 있음을 감지해 “통화별 합계”로 분리 출력
    • 또는 “기준 통화” 파라미터를 받아 환산 후 합산(가능한 경우)
  3. 통화 취급에 대한 제한/가정이 있으면 출력에 명시합니다.

문제 7. 결과 데이터셋 설계: Carrier KPI / Route KPI / Exception

목표: 출력 요구를 만족하는 결과 구조를 설계합니다.

  1. Carrier KPI 구조 필드 예:
    • carrid, carrname, flights_cnt, seatsmax_sum, seatsocc_sum, occupancy_pct, revenue_sum, currency
  2. Route KPI 구조 필드 예:
    • carrid, connid, cityfrom, cityto, flights_cnt, occupancy_pct, revenue_sum
  3. Exception 구조:
    • reason_code, carrid, connid, fldate, details(문자열)
  4. 키 설계와 ITAB 타입 선택을 명시합니다(왜 HASHED가 필요한지 등).

문제 8. 페이징 구현: DB 페이징 우선, 대안 제시

목표: UI/사용자 관점에서 “페이지 단위 조회”가 가능해야 합니다.

  1. 정렬 기준 고정(필수): carrid, connid, fldate (그리고 가능하면 flightno)
  2. OFFSET 기반:
    • offset = (page-1) * size
    • up to size rows
  3. 만약 OFFSET 사용이 제약되는 환경/요건이 있다면:
    • 대안 ① “Seek 방식”: 마지막 키(carrid/connid/fldate)를 다음 페이지 입력으로 받음
    • 대안 ② “상위 N+정렬 후 잘라내기”: 단, 비효율 근거와 제한 명시

문제 9. 출력: SUMMARY/DETAIL 모드 구현

목표: 동일 프로그램이 요약/상세를 모두 제공하도록 설계합니다.

  1. SUMMARY: Carrier KPI + Route KPI + Exception을 3개 블록으로 출력
  2. DETAIL: Flight 상세 리스트를 추가로 출력(페이징 적용)
  3. 출력 형식:
    • 가능하면 ALV(가산점)
    • 또는 out->write로 구조적 출력

문제 10. 품질 점검: 성능/가독성/재사용성 리팩토링

목표: “돌아간다”에서 끝내지 않고, 실무 품질 기준으로 정리합니다.

  1. 중복 코드 제거(예: 조건 조립, 공통 SELECT 옵션)
  2. SELECT 호출 횟수와 근거를 표 형태로 주석에 남기기
  3. 예외 처리: 사용자 입력 오류 vs 데이터 이상치 분리
  4. 테스트 케이스 5개를 문서화(입력값/기대 결과/검증 방법)

2. S4D400 – “Pushdown 리팩토링” (단계형 10문항)

산출물: D75AW 산출물의 V2 (예: ZCL_FLT_KPI_REPORT_V2) 또는 동일 클래스 내 리팩토링.

문제 1. 병목 진단 체크리스트 작성

  1. “DB 호출 횟수”, “가져온 컬럼 수”, “ABAP 후처리량” 3가지를 수치/정성으로 기록
  2. 병목 후보 3개를 선정하고 개선 우선순위를 부여

문제 2. KPI 집계를 DB GROUP BY로 이동

  1. Carrier KPI를 SQL로 집계하는 SELECT를 분리 구현
  2. Route KPI도 동일하게 집계
  3. ABAP에서 수행하던 합계/카운트를 제거

문제 3. “한 번의 조회”로 끝내기(가능한 범위)

  1. JOIN/집계/CASE를 활용해 KPI를 단일 SQL로 계산 가능한지 검토
  2. 불가하면 “왜 불가한지”와 “최소 2회 조회로 나누는 기준”을 명시

문제 4. 필드 최소화 + WHERE 푸시다운 강화

  1. SELECT * 제거, 필요한 컬럼 목록 선언
  2. 필터 조건을 ABAP 후처리로 두지 말고 WHERE로 내리기

문제 5. 페이징 최적화(Seek 방식 설계)

  1. OFFSET 방식이 부담되는 대량 데이터 시나리오를 가정
  2. 마지막 키(last_key)를 기반으로 다음 페이지를 조회하는 Seek SQL을 설계
  3. Seek 방식의 장단점을 문서화

문제 6. 정렬/집계 정확성 회귀 테스트

  1. 리팩토링 전/후 동일 입력으로 “총합/점유율/건수”가 일치하는지 비교
  2. 오차가 있으면 원인 분석(정렬 기준, 그룹키, 통화 분리 등)

문제 7. New Open SQL 기능 2개 이상 적용

  • CASE, CAST, COALESCE, UNION, SUBQUERY 중 2개 이상 사용
  • 왜 사용했는지(가독성/성능/정확성) 근거 작성

문제 8. ITAB 타입 재선정

  1. 리팩토링 후 ITAB 접근 패턴을 다시 평가
  2. HASHED/SORTED로 바꾸거나 유지 결정 및 이유 명시

문제 9. 운영 관점 로그/메트릭 추가(가산점)

  1. 실행 시간(초), 결과 건수, DB 조회 건수를 출력에 포함
  2. 현업 장애 분석에 도움이 되는 최소 정보만 남기기

문제 10. 리팩토링 리포트 제출

  • 개선 전/후 아키텍처(텍스트 다이어그램)
  • 핵심 SQL 2~3개와 선택 근거
  • 남은 리스크(통화/대량 데이터/잠금 등)

3. S4D401 – “CDS 레이어링 + UI Annotation” (단계형 10문항)

산출물: ZI_* (Interface) 1개 + ZC_* (Projection) 1개 + Metadata Extension 1개

문제 1. KPI 데이터 모델(필드/키) 설계서 작성

  1. Carrier KPI / Route KPI 각각의 키와 필드 목록 정의
  2. 집계 단위(그룹키)를 명확히 선언
  3. 통화 필드와 amount 필드의 짝(semantics) 정의

문제 2. ZI_FlightKpi (Interface View) 생성

  1. 데이터 소스 조합을 결정(SFLIGHT + SPFLI + SCARR + (가능하면) SBOOK)
  2. JOIN과 WHERE 조건을 정의
  3. 집계 필드(SUM/COUNT) 구현 + GROUP BY 작성

문제 3. 계산 필드 추가: 점유율/상태/파생 지표

  1. 점유율 계산(0 나누기 방지 포함)
  2. CASE로 상태 필드 예: occupancy_pct >= 85 → 'HIGH', 50~84 → 'MID', else 'LOW'
  3. 산술식 1개 이상(예: seatsfree = seatsmax - seatsocc)

문제 4. 금액/통화 Annotation 적용

  1. @Semantics.amount.currencyCode 적용(금액 필드)
  2. @Semantics.currencyCode 적용(통화 필드)
  3. 노출 계층(ZI vs ZC) 배치 이유를 명시

문제 5. 파라미터 CDS 적용(선택/가산점)

  1. 기간(from/to) 또는 기준통화 파라미터 정의
  2. WHERE에 파라미터 적용
  3. 파라미터 없는 호출 대비 장단점 서술

문제 6. ZC_FlightKpi (Projection View) 생성

  1. ZI를 기반으로 Projection 작성
  2. UI/Consumption 관련 Annotation은 Projection에 집중 배치

문제 7. 검색(Search) 설계

  1. Searchable 필드 2~3개 선정(예: carrname, cityfrom, cityto)
  2. 기본 검색과 필드 검색의 차이를 간단히 설명

문제 8. Metadata Extension으로 Object Page 구조 설계

  1. Facet 3개 Section 구성:
    • Section 1: Key + Description
    • Section 2: 기간/카운트/상태 등 핵심 정보
    • Section 3: 감사필드/추가 KPI
  2. 각 Section에 fieldGroup(또는 identification)을 매핑

문제 9. List Report 컬럼/정렬/프리셋 설계

  1. List에 보여줄 핵심 컬럼 6~10개 선정
  2. 기본 정렬(orderby) 의도 정의(예: revenue desc)
  3. 사용자가 자주 쓰는 필터(예: carrid, 기간) 노출

문제 10. GW100/RAP과의 연결성 문서화

  • Gateway에서 CDS를 어떻게 소비할지(또는 왜 직접조회인지)
  • RAP에서 KPI를 “읽기”로 재사용할 수 있는지(제약 포함)

4. GW100 – “Flight KPI OData V2 서비스” (단계형 10문항)

산출물: SEGW 프로젝트 1개(예: ZGW_FLT_KPI)

문제 1. 서비스 경계 정의(읽기 전용 vs 일부 변경)

  1. 이번 서비스는 KPI 조회가 핵심이므로 기본은 읽기 전용으로 설계
  2. 변경이 필요하면 “Alert”는 RAP로 분리한다는 아키텍처 결정을 기록

문제 2. Entity 설계: CarrierKpi, RouteKpi, FlightDetail

  1. 각 Entity의 Key 설계를 문서화
  2. 필드 목록을 “CDS 결과 필드”에 최대한 맞춘다(재사용)

문제 3. GET_ENTITYSET 기본 구현(필터 없이)

  1. 최소 1개 EntitySet은 정상 조회 가능해야 함
  2. 고정된 기본 기간(최근 30일 등)을 적용

문제 4. $filter 적용(필수)

  1. 지원 필터: carrid, connid, fldate
  2. 파싱 방법을 선택: 기술적 필터 테이블 해석 또는 helper 활용
  3. 지원하지 않는 필터가 오면 “명확한 메시지”로 거절(400 처리 설계)

문제 5. $orderby 적용(필수)

  1. revenue, occupancy_pct 정렬 지원
  2. 정렬이 DB에서 수행되도록 SQL에 반영

문제 6. $top/$skip 페이징 적용(필수)

  1. top/skip 값을 추출
  2. DB 페이징(가능하면)으로 적용
  3. 불가하면 “대안(Seek)”과 제한을 문서화

문제 7. $count / inlinecount 적용(필수)

  1. 동일 filter 조건을 사용해 count를 계산
  2. count와 데이터 조회의 조건 불일치가 없도록 구성

문제 8. $select(가산점)

  1. 요청된 프로퍼티만 읽도록 select list를 조정(가능 범위)
  2. 불가 시 이유(프레임워크 제약/맵핑 비용)와 대안을 제시

문제 9. Navigation(가산점): Carrier → Routes

  1. Association/Navigation을 정의
  2. GET_EXPANDED_ENTITYSET 또는 관련 메소드를 활용

문제 10. 성능/운영 체크리스트 제출

  • 지원 Query Option 목록
  • DB 호출 횟수
  • 대량 조회 제한(최대 top 등) 정책

5. S4D437 – “Flight Alert 관리 RAP BO” (단계형 10문항)

산출물: ZI_Alert + ZC_Alert + Behavior + Service Definition/Binding

문제 1. Clean Core 기반 설계 결정문 작성(필수)

  1. 왜 표준 Flight 테이블을 직접 업데이트하지 않는지
  2. 왜 Alert는 커스텀 테이블에 저장해야 하는지
  3. Gateway(OData V2)와 RAP(OData V4)의 역할 분리 이유

문제 2. 커스텀 테이블 ZFLT_ALERT 설계

  1. 키 전략 선택: UUID 또는 (carrid, connid, period)
  2. 필수 필드: severity, reason, status, owner, created/changed audit
  3. KPI 스냅샷 필드: revenue, occupancy_pct(선택)

문제 3. ZI_Alert Interface View 생성

  1. 테이블 기반 Interface View 작성
  2. 필드 의미/라벨을 정리

문제 4. Behavior Definition (Managed) 작성

  1. create/update/delete 허용
  2. 필드 제어: created_at/by는 읽기전용

문제 5. Determination 구현

  1. create 시 created_at/by 자동 세팅
  2. update 시 changed_at/by 자동 세팅

문제 6. Validation 구현

  1. severity 값 검증(LOW/MED/HIGH)
  2. OPEN 상태에서만 수정 가능 등 비즈니스 규칙 1개 이상 추가

문제 7. Action 구현: CloseAlert

  1. OPEN → CLOSED 전환
  2. 이미 CLOSED인 경우 오류 메시지 반환

문제 8. Projection Layer(ZC_Alert + projection behavior)

  1. 외부 노출 필드만 선택적으로 제공
  2. UI Annotation(최소) 적용(리스트/오브젝트 페이지)

문제 9. Service Definition/Binding 생성

  1. Expose ZC_Alert
  2. 권한/접근 제어 전략을 간단히 기술(예: role 기반)

문제 10. KPI와 Alert 연결(통합 시나리오 완성)

  1. KPI 조회 결과에서 특정 조건(예: occupancy HIGH + revenue 급락 등)을 “Alert 후보”로 제시
  2. 사용자가 해당 후보를 Alert로 생성/Close 할 수 있는 사용 흐름을 문서화

6. 제출물 패키지(최종)

  • D75AW: KPI 리포트 클래스(소스 + 실행 로그/ALV 캡처)
  • S4D400: 리팩토링 버전 + 개선 리포트(전/후 비교)
  • S4D401: ZI/ZC + Metadata Extension + 설계서(필드/키/Annotation 이유)
  • GW100: SEGW 프로젝트 + 지원 Query Option 문서
  • S4D437: RAP BO 전체(Behavior/Service) + Clean Core 결정문
