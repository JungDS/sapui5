SAP Flight 통합 실습 시험 패키지 v3

대상: D75AW / GW100 / S4D400 / S4D401 / S4D437

형태: “하나의 시나리오”를 끝까지 완성하는 통합형 실습 시험. 본 문서는 해설본/답안지 수준으로 작성되어, 출제자가 그대로 문서화/재작성할 수 있게 구성합니다.

0. 중요 정정(오류 수정): 클래스(ClassRun)와 SSCR(Selection Screen)

정정: ABAP 클래스(특히 IF_OO_ADT_CLASSRUN 기반 실행 클래스) 단독으로는 전통적인 Selection Screen(SSCR)을 만들 수 없습니다.

  • Selection Screen은 리포트 프로그램(Report)에서 제공되는 런타임(UI)입니다.
  • 따라서 “클래스 + SSCR”을 함께 요구하려면, 리포트(SSCR 담당) → 클래스(로직 담당) 구조로 분리해야 합니다.

권장 표준 구조(시험 산출물 기준)

  1. Report (예: ZR_FLT_KPI): SSCR 정의 + 입력 검증 + 클래스 호출
  2. Class (예: ZCL_FLT_KPI_REPORT): 조회/집계/출력 데이터 생성(순수 로직)
  3. Interface/DTO(선택): 입력 파라미터 구조(ty_selection)와 결과 구조(ty_kpi_carrier 등)

채점 관점: SSCR/UI는 Report에, 핵심 로직은 Class에 두는 것이 유지보수/테스트/재사용 관점에서 가장 합리적입니다.

1. 공통 Flight 시나리오

항공 운영팀은 (1) 운항/좌석/매출 KPI를 빠르게 보고, (2) 외부 채널(UI/API)로 제공하고, (3) 이상 징후(Alert)를 등록해 추적하려 합니다.

사용 테이블: SCARR, SPFLI, SFLIGHT, SBOOK, SAIRPLANE, SCUSTOM, STRAVELAG

공통 규칙(채점 공통)

  • LOOP 안 SELECT 금지(예외 시 근거 + 대안 필수)
  • 가능하면 집계/계산은 DB에서 수행(SQL GROUP BY 또는 CDS)
  • 필요 컬럼만 SELECT
  • 레이어 분리: 입력(Report) / 로직(Class) / 노출(GW/RAP)

2. D75AW – “KPI 리포트(Report + Class)” (단계형 12문항)

산출물:

  • Report: ZR_FLT_KPI (Selection Screen + 실행 진입점)
  • Class: ZCL_FLT_KPI_REPORT (순수 로직: 조회/집계/예외/출력 데이터 생성)

공통 데이터 정의(답안 가이드)

아래는 “정답 설계”의 최소 기준입니다. 필드명은 시스템 표준에 맞추고, 출력/집계 목적에 맞게 조정 가능합니다.

  • ty_selection: carrid range, connid range/param, fldate range, mode, page, size, (옵션) currency handling
  • ty_raw_flight: carrid, connid, fldate, seatsmax, seatsocc, (가능하면) planetype/price/currency, cityfrom/cityto, carrname
  • ty_raw_book_agg: group key(예: carrid/connid/fldate) + revenue_sum + currency
  • ty_kpi_carrier: carrid, carrname, flights_cnt, seatsmax_sum, seatsocc_sum, occupancy_pct, revenue_sum, currency, status
  • ty_kpi_route: carrid, connid, cityfrom, cityto, flights_cnt, occupancy_pct, revenue_sum, currency, status
  • ty_exception: reason_code, severity, carrid, connid, fldate, details

문제 1. Report 뼈대 + SSCR 구성(정답지 수준)

목표: 사용자의 입력을 안정적으로 수집하고, 클래스에 전달할 “표준 입력 구조(ty_selection)”로 변환합니다.

정답 구조:

  1. Report 생성: ZR_FLT_KPI
  2. Selection Screen 정의:
    • SELECT-OPTIONS: so_carr FOR scarr-carrid
    • SELECT-OPTIONS 또는 PARAMETERS: so_conn(또는 p_conn) for spfli-connid
    • SELECT-OPTIONS: so_date FOR sflight-fldate
    • PARAMETERS: p_mode RADIOBUTTON GROUP g1 (SUMMARY/DETAIL)
    • PARAMETERS: p_page TYPE i DEFAULT 1, p_size TYPE i DEFAULT 50
  3. AT SELECTION-SCREEN 또는 START-OF-SELECTION에서 입력 검증
  4. 입력값을 ty_selection에 매핑 후 클래스 호출

검증 체크(정답 기준):

  • p_page >= 1
  • 1 <= p_size <= 500
  • so_date가 비어있으면 기본값(오늘-30~오늘) 자동 설정

왜 이렇게 하는가(해설): SSCR은 Report가 담당하고, Class는 UI에 의존하지 않게 만들어야 재사용(ADT 실행, 배치, 테스트)이 가능합니다.

문제 2. Class API 설계(입력/출력 계약 정의)

목표: Report가 호출할 “단일 진입 메소드”와 결과 반환 형태를 고정합니다.

정답 설계 예:

  • PUBLIC METHOD run
    • IMPORTING is_sel TYPE ty_selection
    • EXPORTING et_carrier TYPE tt_kpi_carrier et_route TYPE tt_kpi_route et_detail TYPE tt_raw_flight et_ex TYPE tt_exception

해설: run( )은 “Use-case 단위”로 설계합니다. 여러 getter를 외부에 노출하면 결합도가 올라가고 시험 채점도 어려워집니다.

문제 3. 원천 조회 ① Flight Raw (JOIN + 최소 컬럼 + 필터)

목표: KPI 계산의 기반이 되는 운항 데이터를 한 번에 수집합니다.

정답 접근:

  1. 조회 중심 테이블: SFLIGHT
  2. JOIN:
    • SFLIGHT.carrid = SCARR.carrid
    • SFLIGHT.carrid/connid = SPFLI.carrid/connid (노선의 cityfrom/cityto 얻기 위함)
  3. WHERE:
    • carrid IN so_carr
    • connid IN so_conn(또는 = p_conn)
    • fldate IN so_date
  4. SELECT 컬럼(예시, 최소):
    • carrid, connid, fldate, seatsmax, seatsocc
    • carrname, cityfrom, cityto

정답 품질 기준: SELECT * 사용하지 않음. JOIN/WHERE는 DB에서 수행. 결과는 정렬 기준(키) 일관.

문제 4. 원천 조회 ② Booking Revenue (집계 형태로 가져오기)

목표: SBOOK의 금액을 “필요한 집계 단위”로 DB에서 미리 집계합니다.

정답 설계(권장):

  • Carrier KPI용: GROUP BY carrid, (가능하면) currency
  • Route KPI용: GROUP BY carrid, connid, (가능하면) currency
  • 상세/일자까지 필요하면: GROUP BY carrid, connid, fldate, currency

통화 처리(정답 기준):

  • 최소 정답: currency가 섞이면 합산을 분리(통화별)하거나, “단일 통화만 지원”을 명시하고 예외로 분류
  • 가산점: 기준통화 파라미터를 받아 환산 후 합산(시스템 기능/제약이 있으면 설명 포함)

문제 5. KPI 집계 ① Carrier KPI 생성(집계 + 상태 분류)

목표: 항공사 단위 KPI 테이블을 생성합니다.

정답 계산식:

  • flights_cnt = 항공편 건수
  • seatsmax_sum = SUM(seatsmax)
  • seatsocc_sum = SUM(seatsocc)
  • occupancy_pct = (seatsocc_sum / seatsmax_sum) * 100

0 나누기 방지(정답 처리): seatsmax_sum = 0이면 occupancy_pct는 0 또는 initial 처리 + 예외 목록(reason=SEATSMAX_ZERO)로 이동.

상태(status) 분류(정답 예):

  • occupancy_pct >= 85 → 'HIGH'
  • 50~84 → 'MID'
  • 그 외 → 'LOW'

문제 6. KPI 집계 ② Route KPI 생성(노선 단위)

목표: carrid+connid 단위로 KPI를 생성하고, cityfrom/cityto를 포함합니다.

정답 포인트:

  • Group key가 route 기준(carrid+connid)으로 일관되어야 합니다.
  • cityfrom/cityto는 SPFLI에서 확보되며, 조인/매핑이 정확해야 합니다.

문제 7. 매출(Revenue) 결합 로직(정답: 키 기반 매핑)

목표: Booking 집계 결과를 KPI 테이블에 결합합니다.

정답 구현 원칙:

  • ITAB을 HASHED(키=그룹키)로 만들고 READ TABLE로 결합
  • 또는 SQL 단계에서 조인하여 KPI를 완성(성능/가산점)

실격 패턴: KPI LOOP 안에서 SBOOK을 다시 SELECT하는 구조.

문제 8. 예외/이상치 목록(Exception) 설계 및 생성

목표: 운영 관점에서 “데이터 품질/경보” 정보를 제공할 수 있어야 합니다.

정답 예외 규칙(최소 4개 이상):

  • SEATSMAX=0
  • SEATSOCC > SEATSMAX
  • 필터 범위 밖(입력 검증 실패 포함)
  • 통화 혼합으로 합산 불가

정답 출력: reason_code + severity + key(carrid/connid/fldate) + 설명(details)을 명확히 남김.

문제 9. 페이징: DB 페이징 우선 + 대안 제시(정답지)

정답 설계:

  • 정렬 기준 고정: carrid, connid, fldate (가능하면 추가 키)
  • offset = (page-1) * size
  • DB에서 OFFSET/UP TO 적용 가능하면 그대로 적용

대안(Seek 방식) 정답 설명: offset이 커질수록 비용이 증가할 수 있으므로, 마지막 키를 기준으로 “그 이후”를 조회하는 방식도 제시할 수 있습니다. 단, 이 방식은 UI가 last_key를 기억해야 하므로 계약이 바뀝니다.

문제 10. 출력(Report에서) – SUMMARY/DETAIL 분기(정답 기준)

정답 구조: 출력은 Report가 담당합니다(클래스는 결과만 반환).

  • SUMMARY: Carrier KPI / Route KPI / Exception 3블록 출력
  • DETAIL: SUMMARY + Flight Detail(페이징 적용) 추가 출력

채점 기준: 데이터가 많아도 UI/출력이 깨지지 않으며, 모드 전환이 명확합니다.

문제 11 (추가). 입력/출력 계약 문서화(“API 계약서” 제출)

목표: 학습자가 “프로그램 인터페이스를 문서화”하도록 유도합니다(실무 필수 역량).

정답 제출물:

  • 입력: ty_selection 필드 정의 + 기본값 + 유효범위
  • 출력: Carrier/Route/Detail/Exception 필드 정의 + 의미
  • 정렬 기준/페이징 규칙

문제 12 (추가). 회귀 테스트 시나리오 8개 설계(테스트 케이스 표)

목표: “정확성”을 스스로 검증하는 방법을 문제로 학습합니다.

정답 기준(최소 8개):

  • 기본 실행(최근 30일) – 정상 출력
  • 특정 carrid만 – 건수 감소 확인
  • date 범위 1일 – 결과 일관성
  • p_size=1, p_page=2 – 페이징 정확성
  • SEATSMAX=0 존재 시 – Exception 생성 확인
  • 통화 혼합 시 – 분리/예외 처리 확인
  • DETAIL 모드 – 상세 + 요약 동시 출력
  • 입력 오류(p_page=0) – 사용자 오류 처리

문제 10. GW100/RAP 재사용 연결성 문서

CDS를 Gateway에서 직접 소비할지, 또는 DPC_EXT에서 직접 SQL로 조회할지 선택 근거를 작성합니다.

5. GW100 – “Flight KPI OData V2 서비스” (정답지 수준 10문항)

핵심: Query Option을 “정확하게” 반영하고, $count/inlinecount의 조건 불일치가 없도록 구현합니다.

문제 1. 서비스 경계(정답)

KPI는 읽기 전용. 변경은 RAP Alert로 분리. 이유: 표준 테이블 변경 회피 + Clean Core.

문제 2. Entity/Key 설계(정답)

  • CarrierKpi: Key=carrid (+currency가 섞이면 currency도 키 고려)
  • RouteKpi: Key=carrid+connid (+currency)
  • FlightDetail: Key=carrid+connid+fldate(+flightno)

문제 3. GET_ENTITYSET 기본

기본 기간(최근 30일) 적용. 필터 없으면 제한을 강제(대량 방지).

문제 4. $filter

지원 필드만 허용. 미지원 필터는 400으로 명확히 거절.

문제 5. $orderby

revenue/occupancy 정렬을 DB 쪽 ORDER BY로 반영.

문제 6. $top/$skip

DB 페이징 적용. max top 제한 정책(예: 500) 제시.

문제 7. $count/inlinecount

count는 동일한 WHERE/필터/조인 조건으로 계산되어야 합니다.

문제 8. $select(가산점)

요청된 property만 가져오도록 select list 조정 가능 범위를 문서화.

문제 9. Navigation(가산점)

Carrier → Routes 확장. 구현 난이도가 높으면 “왜 생략하는지”와 대안을 제시.

문제 10. 운영 체크리스트

지원 옵션, 최대 top, 기본 기간 제한, DB 호출 수를 문서화.

6. S4D437 – “Flight Alert RAP BO” (정답지 수준 10문항)

핵심: 표준 데이터는 건드리지 않고, Alert를 커스텀 테이블에 저장하여 확장합니다.

문제 1. Clean Core 결정문(정답)

표준 Flight 테이블 직접 업데이트 금지 → 업그레이드 안정성/표준 무결성/지원 정책.

문제 2. ZFLT_ALERT 테이블 설계

Key는 UUID 권장. 필수 필드(severity/status/reason/audit) 포함. KPI snapshot은 선택.

문제 3. ZI_Alert

테이블 기반 Interface View 생성 + 의미 라벨 정리.

문제 4. Managed Behavior

Create/Update/Delete 허용, audit 필드 read-only.

문제 5. Determination

created/changed 자동 세팅.

문제 6. Validation

severity 값 검증, OPEN에서만 close 가능 등 규칙.

문제 7. Action: CloseAlert

OPEN→CLOSED 전환 + 이미 CLOSED면 오류.

문제 8. Projection Layer

외부 노출 필드 최소화 + UI annotation 최소 적용.

문제 9. Service Definition/Binding

ZC_Alert expose. 접근제어 전략 간단 기술.

문제 10. KPI↔Alert 통합 흐름 문서화

KPI 결과에서 Alert 후보를 뽑는 규칙(예: occupancy HIGH + revenue 하락)을 정의하고, Alert 생성/해제 사용자 흐름을 설명합니다.
