SAPUI5 1.120 기준 · 실무 확장 v4.4

Messaging과 Input Validation 실무 입문

초심자가 가장 먼저 헷갈리는 Input 화면 값과 Model 값의 차이에서 출발해, 저장 전 Guard, MessageModel, OData/RAP 백엔드 메시지 디버깅까지 연결하는 교육용 가이드입니다.

기준: SAPUI5 1.120.23 권장 접근: sap/ui/core/Messaging 심화: OData/RAP Server Message
01 · 먼저 해보는 검증 실습

입력할 때마다 즉시 검증되는 흐름을 확인합니다

아래 실습은 UI5 런타임을 흉내 낸 개념 실습용 시뮬레이터입니다. 버튼을 눌러 검증하는 방식이 아니라, 값이 바뀔 때마다 즉시 parse와 validate가 실행되는 흐름을 보여줍니다. 실제 UI5에서는 sap.m.Input의 valueLiveUpdate="true"를 사용하면 사용자가 입력할 때마다 바인딩 갱신이 시도됩니다.

실제 UI5 기준 valueLiveUpdate="true"이면 입력 중에도 value 바인딩 갱신이 시도됩니다. 기본값인 false에서는 보통 Enter 또는 focus out 시점에 갱신되므로, 초심자 실습에서는 즉시 검증을 보여주기 위해 true를 명시하는 편이 좋습니다.

파란 점선 밑줄이 있는 용어는 클릭하면 초급자용 설명 팝업이 열립니다. 어려운 단어를 먼저 확인한 뒤 실습을 진행해도 좋습니다.
수업 진행 권장 이 문서는 개념 설명보다 실습을 먼저 배치했습니다. 학생에게 abc, 999, 30을 먼저 입력하게 한 뒤, “왜 화면 값과 값이 달라지는가?”라는 질문으로 학습 목표에 진입하면 집중도가 높아집니다.

실습 입력창

조건은 Integer, minimum: 1, maximum: 120입니다. 초기 값은 20입니다. 값을 입력하거나 버튼으로 값을 바꾸면 즉시 검증됩니다.

아직 오류가 없습니다. 값을 바꾸면 즉시 검증됩니다. 현재 값은 20입니다.

현재 상태

화면 값
20
확정값
20

상태

메시지 없음 — 저장 통과 가능
입력값발생 단계예상 결과초심자에게 설명할 문장
abc parseError 에는 남지만 은 20 유지 숫자로 해석할 수 없어 진입 전 차단됩니다.
999 validationError 에는 남지만 은 이전 정상값 유지 숫자는 맞지만 1~120 규칙을 위반해 거부됩니다.
30 validationSuccess 값도 30으로 변경 검증을 통과한 값만 확정 데이터가 됩니다.
valueLiveUpdate 사용 기준 valueLiveUpdate="true"를 사용하면 입력할 때마다 바인딩 갱신이 시도되어 parse/validation 결과를 즉시 확인할 수 있습니다. 다만 서버 요청, 무거운 , 복잡한 계산이 연결된 필드에는 입력마다 비용이 발생할 수 있으므로 실무에서는 필드 성격에 따라 선택해야 합니다.
강의 운영 팁 먼저 abc를 입력해 를 보여주고, 다음으로 999를 입력해 를 보여준 뒤, 마지막으로 30을 입력해 Model 값이 즉시 변경되는 순간을 보여주면 이해가 빠릅니다. 이때 valueLiveUpdate="true"가 없으면 실제 UI5에서는 입력 즉시가 아니라 Enter 또는 focus out 시점에 검증될 수 있음을 함께 설명하세요.
02 · 학습 목표

이 문서가 해결하려는 오해

초심자는 에 값이 보이면 경로의 Model 값도 이미 바뀌었다고 생각하기 쉽습니다. 하지만 UI5에서는 화면에 보이는 후보값과 Model에 기록된 확정값이 다를 수 있습니다.

Input 화면 값

"abc"

사용자가 방금 입력한 값입니다. 아직 Type 변환과 Validation을 통과하지 못했을 수 있습니다.

Model 실제 값

20

마지막으로 검증을 통과해 경로에 기록된 값입니다. 저장 로직이 신뢰해야 할 기준입니다.

강사용 핵심 문장 Input은 사용자가 적는 임시 입력칸이고, Model은 UI5가 인정한 확정 데이터 저장소입니다. 오류가 있으면 값은 Input에 남아도 Model에는 들어가지 않습니다.
03 · 용어를 먼저 정리

어려운 단어는 접어서 설명합니다

Messaging

UI5의 중앙 메시지 처리 모듈입니다. 최신 코드에서는 sap/ui/core/Messaging을 import해서 validation error, warning, information message 등을 조회하거나 처리합니다.

MessageManager

기존 문서와 레거시 코드에서 자주 보이는 이름입니다. 1.120에서도 개념 이해에는 필요하지만, 새 예제 코드는 sap.ui.getCore().getMessageManager() 대신 Messaging 모듈 중심으로 작성합니다.

Binding Type과 Constraints

sap.ui.model.type.Integer 같은 은 입력값을 숫자·날짜·문자 등으로 해석하는 검문소입니다. constraints는 minimum, maximum처럼 통과 규칙을 선언하는 영역입니다.

parseError와 validationError

parseError는 값의 형식을 해석하지 못할 때 발생합니다. 예를 들어 숫자 Input에 abc를 입력한 경우입니다. validationError는 형식은 맞지만 규칙을 통과하지 못할 때 발생합니다. 예를 들어 1~120 범위에 999를 입력한 경우입니다.

OData/RAP Server Message

브라우저에서 만든 validation message가 아니라, 백엔드 서비스가 응답으로 돌려준 메시지입니다. 이 메시지가 특정 Input에 연결되려면 서버 메시지의 target과 UI5 바인딩 경로가 맞아야 합니다.

04 · 데이터 흐름

Input 값이 Model까지 가는 검문소

1

사용자가 Input에 값을 입력

이 단계의 값은 화면에 보이는 후보값입니다. 아직 Model 데이터라고 단정하면 안 됩니다.

2

의 단계

Integer 타입에 abc가 들어오면 숫자로 해석할 수 없어 parseError가 발생합니다.

3

의 단계

숫자 형식은 맞아도 maximum: 120을 넘는 999라면 validationError가 발생합니다.

4

성공하면 Model 반영, 실패하면 으로 메시지 표시

검증 실패 시 Input에는 값이 남지만 Model은 이전 정상값을 유지합니다.

정확한 의미 빨간 테두리는 “Model에 잘못된 값이 들어갔다”가 아니라, “이 값을 Model에 넣으려 했지만 UI5가 거부했다”는 표시입니다.
05 · 1.120과 최신 흐름

1.120 기준으로도 중심 예제가 맞습니다

항목1.120 기준교육자료에서의 처리
handleValidation 사용 가능 앱 전체 validation message 처리는 manifest.json에서 선언
sap/ui/core/Messaging 사용 가능 신규 예제의 기본 접근 방식으로 사용
sap.ui.getCore().getMessageManager() 기존 코드에서 볼 수 있음 레거시 코드 이해용으로만 설명하고, 새 예제에서는 사용하지 않음
OData/RAP Server Message Model별 처리 차이 존재 심화 장에서 V2/V4 차이를 구분해 설명
버전 주의 이 문서는 교육 서버 기준을 1.120.23으로 두고 작성했습니다. 공개 OpenUI5 릴리스는 계속 갱신되므로 최신 버전 자체는 하단 공식 링크에서 확인합니다.
06 · 프론트엔드 검증 기본 코드

초심자에게 보여줄 최소 코드

HTML 문서에서는 핵심만 보여줍니다. 실제 실행용 앱에는 index.html, Component.js, 라우팅 설정 등이 더 필요할 수 있습니다.

manifest.json — handleValidation 핵심만 표시
{
  "sap.ui5": {
    "...": "...",
    "handleValidation": true
  }
}
Main.view.xml — Input Binding Type + constraints
<Input
    id="idAgeInput"
    valueLiveUpdate="true"
    value="{
        path: 'view>/Age',
        type: 'sap.ui.model.type.Integer',
        constraints: {
            minimum: 1,
            maximum: 120
        }
    }" />

<Button
    text="Input 값과 Model 값 비교"
    press=".onCompareValue" />

<Button
    text="저장 전 오류 검사"
    type="Emphasized"
    press=".onSave" />
Main.controller.js — Messaging 중심 예제
sap.ui.define([
    "sap/ui/core/mvc/Controller",
    "sap/ui/model/json/JSONModel",
    "sap/ui/core/Messaging",
    "sap/ui/core/library",
    "sap/m/MessageBox",
    "sap/m/MessageToast"
], function (
    Controller,
    JSONModel,
    Messaging,
    coreLibrary,
    MessageBox,
    MessageToast
) {
    "use strict";

    var MessageType = coreLibrary.MessageType;

    return Controller.extend("demo.mm.controller.Main", {
        onInit: function () {
            this.getView().setModel(new JSONModel({
                Age: 20
            }), "view");
        },

        onCompareValue: function () {
            var sInputValue = this.byId("idAgeInput").getValue();
            var vModelValue = this.getView()
                .getModel("view")
                .getProperty("/Age");

            MessageBox.information(
                "Input 화면 값: " + sInputValue + "\n" +
                "Model 값: " + vModelValue
            );
        },

        onSave: function () {
            var aMessages = Messaging
                .getMessageModel()
                .getData();

            var bHasError = aMessages.some(function (oMessage) {
                return oMessage.type === MessageType.Error;
            });

            if (bHasError) {
                MessageBox.error(
                    "입력 오류를 먼저 수정해 주세요."
                );
                return;
            }

            var vAge = this.getView()
                .getModel("view")
                .getProperty("/Age");

            MessageToast.show(
                "저장 가능한 Model 값: " + vAge
            );
        }
    });
});
보조 설명 this.getView().setModel(Messaging.getMessageModel(), "message")는 처럼 메시지 목록을 화면에 바인딩할 때 필요합니다. Input의 valueState 자동 연결 자체는 handleValidation 또는 Messaging.registerObject(..., true)가 담당합니다.
07 · 저장 전

화면 오류를 저장 로직 앞에서 차단해야 합니다

validation error가 화면에 표시되는 것과 저장 로직이 자동으로 중단되는 것은 별개입니다. 저장 버튼에서는 을 확인해 Error가 있으면 서버 요청을 보내지 않는 를 두는 것이 안전합니다.

저장 전 Error Guard 패턴
var aMessages = Messaging
    .getMessageModel()
    .getData();

var bHasError = aMessages.some(function (oMessage) {
    return oMessage.type === MessageType.Error;
});

if (bHasError) {
    MessageBox.error(
        "입력 오류를 먼저 수정해 주세요."
    );
    return;
}

// 여기부터 실제 저장 또는 submitBatch 로직

위험한 방식

this.byId("idAgeInput").getValue()만 읽고 저장하면, 검증을 통과하지 못한 화면 후보값을 기준으로 판단할 수 있습니다.

안전한 방식

먼저 MessageModel의 Error를 검사하고, 오류가 없을 때 Model 경로의 확정값을 읽습니다.

08 · 실무 확장

브라우저 검증과 백엔드 메시지는 다릅니다

지금까지의 예제는 Input Type과 가 만드는 프론트엔드 validation message입니다. 실무 RAP/OData 앱에서는 백엔드가 저장 시점에 메시지를 내려주는 경우가 많습니다. 이 메시지는 UI5 Model의 message parser와 중앙 흐름을 통해 MessageModel에 들어올 수 있습니다.

구분발생 위치대표 예실무 체크포인트
프론트엔드 validation 브라우저 Integer, minimum, maximum Type과 constraints가 정확한지 확인
OData/RAP server message ABAP 백엔드 validation, determination, action 에러 서버 메시지 target과 UI5 매칭 확인
Application message 코드 개발자가 직접 만든 오류/경고 target, processor를 어떻게 줄지 명확히 결정
V2와 V4를 구분하세요 V2는 sap-message 헤더와 error response를 파싱하는 흐름이 중요하고, V4는 error response, sap-messages 헤더, entity의 message property 등 메시지 채널이 다릅니다. 같은 “서버 메시지”라도 모델 종류와 서비스 구현 방식에 따라 디버깅 기준이 달라집니다.
09 · 디버깅 수첩

MessageModel에는 있는데 화면에 안 붙는 이유

백엔드 메시지가 탭에는 보이는데 특정 Input에 빨간 테두리가 생기지 않는다면, 가장 먼저 서버 메시지의 target과 의 실제 를 비교해야 합니다.

지뢰 01

type 선언이 없어서 검증이 아예 안 됨

value="{view>/Age}"처럼 단순 경로만 쓰면 UI5가 어떤 형식으로 검증해야 하는지 알 수 없습니다.

수정 전 / 수정 후
<!-- 수정 전: 검증 기준 없음 -->
<Input value="{view>/Age}" />

<!-- 수정 후: Type과 constraints 선언 -->
<Input value="{
    path: 'view>/Age',
    type: 'sap.ui.model.type.Integer',
    constraints: {
        minimum: 1,
        maximum: 120
    }
}" />
지뢰 02

정상값으로 고쳐도 오류가 갱신되지 않음

입력값이 Model로 다시 전달되지 않는 구조라면 validation이 재실행되지 않을 수 있습니다. 기본 흐름은 보통 이지만, OData Model이나 개별 설정에서 mode가 달라질 수 있습니다.

특정 바인딩에서 mode를 명시하는 예
<Input value="{
    path: 'view>/Age',
    mode: 'TwoWay',
    type: 'sap.ui.model.type.Integer',
    constraints: {
        minimum: 1,
        maximum: 120
    }
}" />
지뢰 03

백엔드 target과 UI5 binding path가 안 맞음

OData V4 기준으로 Input highlighting은 resolved message target과 의 binding path가 일치해야 작동합니다. 따라서 Response의 target과 실제 Control binding path를 함께 봐야 합니다.

Network 탭에서 볼 것 error response 또는 sap-messages 헤더의 target, message, code, numericSeverity
UI5 Control에서 볼 것 Control의 binding context path와 value binding path를 조합한 실제 경로
Controller 내부에서 binding path 확인
var oControl = this.byId("idAgeInput");
var oBinding = oControl.getBinding("value");
var oContext = oBinding.getContext();

var sFullBindingPath =
    (oContext ? oContext.getPath() + "/" : "") +
    oBinding.getPath();

console.log(sFullBindingPath);
브라우저 콘솔에서 MessageModel 확인
sap.ui.require([
    "sap/ui/core/Messaging"
], function (Messaging) {
    console.table(
        Messaging.getMessageModel().getData().map(function (m) {
            return {
                type: m.type,
                message: m.message,
                target: m.target,
                technical: m.technical
            };
        })
    );
});
콘솔 디버깅 주의 브라우저 콘솔에서 sap.ui.getCore().byId(...)를 쓰는 것은 임시 디버깅 수단입니다. XML 의 local ID와 런타임 ID는 다를 수 있으므로, 실제 전체 ID를 확인해야 합니다. 정식 앱 코드는 안에서 this.byId(...)를 우선 사용하세요.
10 · 체크리스트

문제가 생겼을 때 순서대로 확인

증상우선 확인조치
오류값을 넣어도 빨간 테두리가 없음 handleValidation, type manifest와 XML binding을 먼저 확인
저장 버튼이 그대로 실행됨 저장 전 유무 Messaging.getMessageModel().getData()로 Error 검사
정상값으로 수정해도 오류가 남음 Binding mode, 수동 valueState 설정 여부와 직접 setValueState 코드 확인
서버 메시지는 있는데 Control에 안 붙음 server target과 binding path Network Response와 Control binding path 비교
메시지 목록이 화면에 안 나옴 MessageModel 바인딩 여부 나 MessageView에 Messaging.getMessageModel() 연결
