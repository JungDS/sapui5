## 4. INNER JOIN이란 무엇인가?

`INNER JOIN`은 두 테이블에서 **연결 조건이 서로 맞는 데이터만** 결과로 가져오는 Join 방식이다.

예를 들어 항공사 테이블 `SCARR`와 항공편 연결 테이블 `SPFLI`가 있다고 하자.

| 테이블 | 역할 |
|---|---|
| SCARR | 항공사 마스터. 항공사 코드와 항공사명을 가짐 |
| SPFLI | 항공편 연결 정보. 항공사 코드, 연결번호, 출발/도착 도시 등을 가짐 |

두 테이블은 보통 `CARRID` 필드로 연결된다.

```text
SCARR-CARRID = SPFLI-CARRID
```

`INNER JOIN`은 이 조건을 만족하는 행만 결과에 포함한다.

```text
SCARR에 항공사 코드가 있고
SPFLI에도 같은 항공사 코드가 있는 경우
→ 결과에 포함
```

반대로 어느 한쪽에만 존재하는 데이터는 `INNER JOIN` 결과에서 제외된다.

## 5. 왜 INNER JOIN이 필요한가?

단일 테이블 조회만으로는 업무적으로 충분한 정보를 얻기 어려운 경우가 많다.

예를 들어 `SPFLI`에서 항공편 연결 정보를 조회하면 항공사 코드 `CARRID`는 확인할 수 있다. 그러나 사용자가 보기 좋은 항공사명은 `SCARR-CARRNAME`에 있을 수 있다.

단일 테이블 조회 예:

```abap
SELECT carrid,
       connid,
       cityfrom,
       cityto
  FROM spfli
  INTO TABLE @DATA(lt_spfli).
```

이 결과는 다음처럼 코드 중심이다.

| CARRID | CONNID | CITYFROM | CITYTO |
|---|---|---|---|
| AA | 0017 | NEW YORK | SAN FRANCISCO |

업무 사용자는 `AA`만 보고 항공사명을 바로 알기 어려울 수 있다.  
이때 `SCARR`와 Join하면 항공사명을 함께 가져올 수 있다.

Join 조회 결과 예:

| CARRID | CARRNAME | CONNID | CITYFROM | CITYTO |
|---|---|---|---|---|
| AA | American Airlines | 0017 | NEW YORK | SAN FRANCISCO |

즉, `INNER JOIN`은 코드 테이블, 마스터 테이블, 트랜잭션 테이블을 연결해 더 의미 있는 조회 결과를 만들기 위한 핵심 도구이다.

## 6. INNER JOIN 기본 문법

ABAP Open SQL의 기본적인 `INNER JOIN` 형태는 다음과 같다.

```abap
SELECT a~field1,
       b~field2
  FROM table_a AS a
  INNER JOIN table_b AS b
    ON a~key_field = b~key_field
  INTO TABLE @DATA(lt_result).
```

각 부분의 의미는 다음과 같다.

| 구문 | 의미 |
|---|---|
| `FROM table_a AS a` | 첫 번째 테이블과 Alias 지정 |
| `INNER JOIN table_b AS b` | 두 번째 테이블과 Inner Join 수행 |
| `ON a~key = b~key` | 두 테이블을 연결하는 조건 |
| `a~field`, `b~field` | 어떤 테이블의 필드인지 명확히 지정 |
| `INTO TABLE @DATA(...)` | 조회 결과를 Internal Table로 받음 |

## 7. Table Alias

### 7.1 Alias가 필요한 이유

Join에서는 여러 테이블의 필드를 동시에 사용한다.  
이때 같은 이름의 필드가 여러 테이블에 존재할 수 있다.

예를 들어 `SCARR`와 `SPFLI`에는 모두 `CARRID`가 있다.  
따라서 `CARRID`라고만 쓰면 어느 테이블의 필드인지 불명확해질 수 있다.

Alias를 사용하면 다음처럼 필드 출처를 명확히 할 수 있다.

```abap
FROM scarr AS c
INNER JOIN spfli AS p
  ON c~carrid = p~carrid
```

여기서 Alias의 의미는 다음과 같다.

| Alias | 테이블 | 의미 |
|---|---|---|
| `c` | `SCARR` | Carrier |
| `p` | `SPFLI` | Flight connection |

이후 필드는 다음처럼 작성한다.

```abap
c~carrid
c~carrname
p~connid
p~cityfrom
p~cityto
```

### 7.2 Alias 명명 기준

실무에서는 Alias를 너무 짧거나 의미 없게 쓰면 가독성이 떨어진다.

| Alias | 평가 |
|---|---|
| `a`, `b`, `c` | 간단하지만 의미가 약함 |
| `sc`, `sp` | 테이블명을 연상할 수 있어 무난 |
| `carrier`, `conn` | 의미가 명확하지만 길어질 수 있음 |

교육용 예제에서는 `c`, `p`처럼 짧은 Alias를 사용하되, 설명에서는 의미를 명확히 붙인다.

## 8. ON Condition

### 8.1 ON Condition의 목적

`ON`은 두 테이블을 어떤 조건으로 연결할지 정의하는 부분이다.

```abap
ON c~carrid = p~carrid
```

이 조건은 다음 의미를 가진다.

```text
SCARR의 항공사 코드와
SPFLI의 항공사 코드가 같은 행만
하나의 결과 행으로 연결한다.
```

### 8.2 ON 조건이 잘못되면?

`ON` 조건이 잘못되면 결과가 아예 없거나, 반대로 너무 많이 늘어날 수 있다.

예를 들어 다음처럼 잘못 연결했다고 하자.

```abap
ON c~carrid = p~connid
```

`CARRID`는 항공사 코드이고 `CONNID`는 연결번호이다. 의미가 다른 필드이므로 정상적인 Join 조건이 아니다.  
이런 조건은 Syntax상 가능하더라도 업무적으로 잘못된 결과를 만들 수 있다.

초급자는 다음 원칙을 기억한다.

```text
ON 조건은 필드 이름이 비슷해서 정하는 것이 아니라,
테이블 사이의 업무적 관계와 Key 관계를 기준으로 정한다.
```

## 9. WHERE 조건과 ON 조건의 차이

Join을 처음 배울 때 `ON`과 `WHERE`를 혼동하기 쉽다.

| 구분 | 역할 |
|---|---|
| `ON` | 테이블과 테이블을 연결하는 조건 |
| `WHERE` | 연결된 결과 중 필요한 데이터를 제한하는 조건 |

예:

```abap
SELECT c~carrid,
       c~carrname,
       p~connid,
       p~cityfrom,
       p~cityto
  FROM scarr AS c
  INNER JOIN spfli AS p
    ON c~carrid = p~carrid
  WHERE p~countryfr = 'US'
  INTO TABLE @DATA(lt_result).
```

해석은 다음과 같다.

```text
ON: SCARR와 SPFLI를 CARRID 기준으로 연결한다.
WHERE: 연결된 결과 중 출발 국가가 US인 데이터만 가져온다.
```

초급자는 다음 문장을 기억하면 된다.

```text
ON은 관계를 정의하고, WHERE는 결과를 필터링한다.
```

## 10. 최소 예제: SCARR + SPFLI INNER JOIN

### 10.1 예제 목적

항공사 마스터 `SCARR`와 항공편 연결 정보 `SPFLI`를 `CARRID` 기준으로 Join하여, 항공사명과 연결 정보를 함께 출력한다.

> [추정] 대부분의 SAP 교육 시스템에는 Flight Model 테이블 `SCARR`, `SPFLI`, `SFLIGHT`가 존재한다. 단, 일부 S/4HANA 학습 시스템에서는 샘플 데이터가 없거나 클라이언트별로 데이터가 다를 수 있다.

### 10.2 예제 코드

```abap
REPORT zjhy_join_inner_01.

SELECT c~carrid,
       c~carrname,
       p~connid,
       p~cityfrom,
       p~cityto
  FROM scarr AS c
  INNER JOIN spfli AS p
    ON c~carrid = p~carrid
  INTO TABLE @DATA(lt_join_result).

IF sy-subrc = 0.
  WRITE: / 'INNER JOIN result count:', lines( lt_join_result ).
  ULINE.

  LOOP AT lt_join_result INTO DATA(ls_result).
    WRITE: / ls_result-carrid,
             ls_result-carrname,
             ls_result-connid,
             ls_result-cityfrom,
             ls_result-cityto.
  ENDLOOP.
ELSE.
  WRITE: / 'No data found.'.
ENDIF.
```

### 10.3 코드 해설

| 코드 | 설명 |
|---|---|
| `FROM scarr AS c` | 항공사 테이블을 `c`라는 Alias로 사용 |
| `INNER JOIN spfli AS p` | 항공편 연결 테이블을 `p`라는 Alias로 Join |
| `ON c~carrid = p~carrid` | 항공사 코드가 같은 행끼리 연결 |
| `c~carrname` | 항공사명 |
| `p~connid` | 항공편 연결번호 |
| `INTO TABLE @DATA(...)` | 결과 Internal Table을 인라인 선언 |
| `sy-subrc = 0` | 조회 결과가 존재함 |
| `lines( lt_join_result )` | 결과 건수 확인 |

## 11. 조회 결과 이해

Join 결과에서 가장 중요한 점은 결과 행의 기준이 무엇인지 이해하는 것이다.

`SCARR`는 항공사 1건당 1행이다.  
`SPFLI`는 항공사별로 여러 연결편을 가질 수 있다.

따라서 `SCARR`와 `SPFLI`를 Join하면 결과는 보통 `SPFLI`의 항공편 연결 건수 기준으로 나온다.

예를 들어 다음 데이터가 있다고 하자.

### SCARR

| CARRID | CARRNAME |
|---|---|
| AA | American Airlines |
| LH | Lufthansa |

### SPFLI

| CARRID | CONNID | CITYFROM | CITYTO |
|---|---|---|---|
| AA | 0017 | NEW YORK | SAN FRANCISCO |
| AA | 0064 | SAN FRANCISCO | NEW YORK |
| LH | 0400 | FRANKFURT | NEW YORK |

### Join 결과

| CARRID | CARRNAME | CONNID | CITYFROM | CITYTO |
|---|---|---|---|---|
| AA | American Airlines | 0017 | NEW YORK | SAN FRANCISCO |
| AA | American Airlines | 0064 | SAN FRANCISCO | NEW YORK |
| LH | Lufthansa | 0400 | FRANKFURT | NEW YORK |

`AA` 항공사는 `SCARR`에는 1건이지만, `SPFLI`에 2건이 있으므로 Join 결과에서는 2행으로 나타난다.

이것이 Join에서 매우 중요한 **행 증가** 감각이다.

## 12. Join Cardinality 감각

초급 단계에서 Cardinality를 수학적으로 깊게 다룰 필요는 없다.  
다만 Join 결과 행 수를 이해하기 위해 다음 감각은 필요하다.

| 관계 | 의미 | 결과 특성 |
|---|---|---|
| 1:1 | 한쪽 1건이 다른 쪽 1건과 연결 | 행 수가 크게 늘지 않음 |
| 1:N | 한쪽 1건이 다른 쪽 여러 건과 연결 | 결과 행이 N만큼 늘 수 있음 |
| N:M | 양쪽이 여러 건과 연결 | 결과가 크게 폭증할 수 있음 |

`SCARR`와 `SPFLI`는 대체로 다음 관계로 이해할 수 있다.

```text
SCARR 1건 : SPFLI 여러 건
```

즉, 항공사 하나에 여러 항공편 연결이 있을 수 있다.

실무에서 Join 결과가 예상보다 많다면 다음을 의심해야 한다.

```text
1. ON 조건이 부족하다.
2. 1:N 관계를 1:1로 착각했다.
3. 중복 가능한 필드로 Join했다.
4. WHERE 조건이 너무 넓다.
5. 필요한 필드보다 더 상세한 테이블을 Join했다.
```

---

## 13. ON 조건이 부족한 예

예를 들어 `SFLIGHT`는 항공편 날짜별 데이터를 가진다.  
`SPFLI`와 `SFLIGHT`를 Join하려면 보통 `CARRID`, `CONNID`가 함께 필요하다.

좋은 예:

```abap
ON p~carrid = f~carrid
AND p~connid = f~connid
```

부족한 예:

```abap
ON p~carrid = f~carrid
```

`CARRID`만으로 Join하면 같은 항공사 안의 여러 연결번호가 서로 섞이면서 결과가 크게 늘어날 수 있다.

초급자는 다음 원칙을 기억한다.

```text
Join 조건은 테이블 사이의 관계를 유일하게 설명할 수 있을 만큼 충분해야 한다.
```

이 내용은 후속 Join/FAE 선택 기준에서도 다시 중요하게 다룬다.

## 14. 조건을 추가한 INNER JOIN 예제

이번에는 특정 항공사만 조회하도록 조건을 추가한다.

```abap
REPORT zjhy_join_inner_02.

PARAMETERS p_carrid TYPE scarr-carrid DEFAULT 'AA'.

SELECT c~carrid,
       c~carrname,
       p~connid,
       p~cityfrom,
       p~cityto
  FROM scarr AS c
  INNER JOIN spfli AS p
    ON c~carrid = p~carrid
  WHERE c~carrid = @p_carrid
  INTO TABLE @DATA(lt_join_result).

IF lt_join_result IS INITIAL.
  WRITE: / 'No data found for carrier:', p_carrid.
  RETURN.
ENDIF.

WRITE: / 'Carrier:', p_carrid,
       / 'Rows   :', lines( lt_join_result ).
ULINE.

LOOP AT lt_join_result INTO DATA(ls_result).
  WRITE: / ls_result-carrid,
           ls_result-carrname,
           ls_result-connid,
           ls_result-cityfrom,
           ls_result-cityto.
ENDLOOP.
```

### 설명

| 구문 | 설명 |
|---|---|
| `PARAMETERS p_carrid TYPE scarr-carrid` | 항공사 코드를 입력받음 |
| `WHERE c~carrid = @p_carrid` | 입력한 항공사만 조회 |
| `@p_carrid` | Open SQL에서 ABAP 변수 사용을 명시 |
| `lt_join_result IS INITIAL` | 결과가 없는지 확인 |

ABAP 7.40 이후의 Open SQL 문법에서는 ABAP 변수 앞에 `@`를 붙이는 방식이 일반적이다.

## 15. 필요한 필드만 조회하기

초급자가 자주 하는 실수는 다음과 같다.

```abap
SELECT *
  FROM scarr AS c
  INNER JOIN spfli AS p
    ON c~carrid = p~carrid
  INTO TABLE @DATA(lt_result).

이 방식은 학습 초기에 편해 보이지만 실무에서는 권장하기 어렵다.

### SELECT *를 피해야 하는 이유

| 이유 | 설명 |
|---|---|
| 불필요한 데이터 전송 | 사용하지 않는 필드까지 DB에서 가져온다. |

| Join 결과 혼란 | 여러 테이블에 같은 필드명이 있을 때 결과 구조가 복잡해진다. |

실무 기준으로는 필요한 필드만 명시하는 습관이 좋다.

SELECT c~carrid,
       c~carrname,
       p~connid,
       p~cityfrom,
       p~cityto
```

## 16. 결과 구조를 명시적으로 정의하는 방식

인라인 선언은 학습에 편리하지만, 실무 교육에서는 결과 구조를 명시하는 방식도 중요하다.

```abap
REPORT zjhy_join_inner_03.

TYPES: BEGIN OF ty_join_result,
         carrid   TYPE scarr-carrid,
         carrname TYPE scarr-carrname,
         connid   TYPE spfli-connid,
         cityfrom TYPE spfli-cityfrom,
         cityto   TYPE spfli-cityto,
       END OF ty_join_result.

DATA lt_join_result TYPE STANDARD TABLE OF ty_join_result.

PARAMETERS p_carrid TYPE scarr-carrid DEFAULT 'AA'.

SELECT c~carrid,
       c~carrname,
       p~connid,
       p~cityfrom,
       p~cityto
  FROM scarr AS c
  INNER JOIN spfli AS p
    ON c~carrid = p~carrid
  WHERE c~carrid = @p_carrid
  INTO TABLE @lt_join_result.

LOOP AT lt_join_result INTO DATA(ls_result).
  WRITE: / ls_result-carrid,
           ls_result-carrname,
           ls_result-connid,
           ls_result-cityfrom,
           ls_result-cityto.
ENDLOOP.
```

명시적 타입 방식의 장점은 다음과 같다.

| 장점 | 설명 |
|---|---|
| 결과 구조 명확 | 어떤 필드를 받을지 명시적으로 보임 |
| 유지보수 용이 | ALV, Method 파라미터, 테스트 코드와 연결하기 쉬움 |
| 교육 효과 | Open SQL 결과와 Internal Table 구조의 관계를 이해하기 좋음 |
| 호환성 | 인라인 선언을 제한적으로 사용하는 조직에서도 설명 가능 |

## 19. 자주 발생하는 오류와 해결

### 19.1 Alias 누락 또는 필드 출처 불명확

#### 증상

```text
Field CARRID is ambiguous
```

또는 유사한 의미의 Syntax 오류가 발생할 수 있다.

#### 원인

Join 대상 테이블 여러 개에 같은 이름의 필드가 있는데 Alias 없이 필드를 사용했다.

#### 해결

필드 앞에 Alias를 붙인다.

```abap
c~carrid
p~carrid
```

---

### 19.2 ON 조건 오타

#### 증상

Syntax 오류 또는 결과 없음.

#### 원인

필드명을 잘못 입력했거나 의미가 다른 필드를 연결했다.

#### 해결

SE11에서 두 테이블의 필드를 확인하고, 관계 필드를 기준으로 ON 조건을 작성한다.

```abap
ON c~carrid = p~carrid
```

---

### 19.3 Host Variable `@` 누락

#### 증상

ABAP 7.40 이후 문법에서 Open SQL Syntax 오류가 발생할 수 있다.

#### 원인

`WHERE` 조건에서 ABAP 변수를 사용할 때 `@`를 빠뜨렸다.

잘못된 예:

```abap
WHERE c~carrid = p_carrid
```

좋은 예:

```abap
WHERE c~carrid = @p_carrid
```

---

### 19.4 조회 결과가 없음

#### 가능한 원인

| 원인 | 설명 |
|---|---|
| 샘플 데이터 없음 | 교육 시스템에 `SCARR`, `SPFLI` 데이터가 없을 수 있음 |
| 입력값 부정확 | 존재하지 않는 항공사 코드 입력 |
| Client 차이 | 샘플 데이터가 현재 Client에 없을 수 있음 |
| ON 조건 오류 | 테이블 관계를 잘못 연결 |

#### 해결 순서

```text
1. SE16N에서 SCARR 데이터 확인
2. SE16N에서 SPFLI 데이터 확인
3. 동일 CARRID가 양쪽에 존재하는지 확인
4. WHERE 조건 제거 후 전체 조회
5. ON 조건 재확인
```

---

### 19.5 결과 건수가 예상보다 많음

#### 가능한 원인

```text
1:N 관계를 1:1로 착각했다.
ON 조건이 부족하다.
WHERE 조건이 너무 넓다.
테이블 관계를 잘못 이해했다.
```

#### 해결

- 먼저 각 테이블을 단독 조회한다.
- 연결 필드의 중복 여부를 확인한다.
- 필요한 경우 ON 조건을 추가한다.
- 결과 건수의 기준이 어느 테이블인지 확인한다.

## 20. 성능 관점 주의사항

초급 단계에서 성능을 지나치게 깊게 다루지는 않지만, Join은 DB에 직접 영향을 주는 조회이므로 최소한의 주의는 필요하다.

### 20.1 필요한 필드만 조회

```abap
SELECT *
```

보다는 필요한 필드만 명시한다.

```abap
SELECT c~carrid,
       c~carrname,
       p~connid,
       p~cityfrom,
       p~cityto
```

### 20.2 조건 없이 대량 Join하지 않기

조건 없는 Join은 데이터가 많은 테이블에서 큰 부하를 만들 수 있다.

교육용 샘플 테이블은 작지만, 실무 테이블은 수백만 건 이상일 수 있다.

### 20.3 Index와 Key 관계 이해

Join 조건이 Key 또는 Index와 잘 맞으면 DB가 더 효율적으로 처리할 가능성이 높다.  
초급 단계에서는 세부 실행 계획보다 다음 원칙을 기억하면 된다.

```text
Join 조건은 업무 관계와 테이블 Key를 함께 고려한다.
```

### 20.4 DB에서 할 일과 ABAP에서 할 일 구분

Join은 DB에서 데이터를 연결하는 기능이다.  
모든 로직을 ABAP Internal Table로 가져와서 직접 조합하는 방식은 데이터량이 많을 때 비효율적일 수 있다.

이 비교는 `THEORY-11-M07 — JOIN / FAE / ABAP 처리 선택 기준`에서 더 자세히 다룬다.

## 21. 유지보수 관점 주의사항

### 21.1 Alias는 일관되게 사용한다

나쁜 예:

```abap
FROM scarr AS a
INNER JOIN spfli AS b
```

실습에서는 가능하지만, 복잡한 Join에서는 의미 파악이 어려울 수 있다.

좋은 예:

```abap
FROM scarr AS carrier
INNER JOIN spfli AS connection
```

또는 짧지만 의미를 알 수 있는 기준을 프로젝트에서 정한다.

```abap
FROM scarr AS c
INNER JOIN spfli AS p
```

### 21.2 Join 조건은 주석으로 보조할 수 있다

교육용이나 복잡한 업무 테이블에서는 Join 조건의 의미를 간단히 주석으로 남기는 것이 좋다.

```abap
" Carrier master and flight connection are linked by carrier ID.
ON c~carrid = p~carrid
```

### 21.3 업무 의미가 다른 필드끼리 Join하지 않는다

필드 타입과 길이가 같다고 해서 Join 조건으로 적절한 것은 아니다.

예:

```text
BUKRS와 WERKS가 모두 CHAR4라고 해서 서로 Join하면 안 된다.
```

Join은 기술 타입이 아니라 업무 의미와 관계를 기준으로 작성해야 한다.

## 22. 운영 안정성 관점

실무 운영 시스템에서는 Join 조회가 사용자 응답 속도와 DB 부하에 직접 영향을 줄 수 있다.

다음 상황은 특히 주의해야 한다.

| 상황 | 위험 |
|---|---|
| 대량 테이블 간 조건 없는 Join | DB 부하 증가 |
| 잘못된 ON 조건 | 결과 폭증 또는 잘못된 업무 결과 |
| `SELECT *` 남발 | 불필요한 네트워크/메모리 사용 |
| UI 요청마다 무거운 Join 반복 | 사용자 응답 지연 |
| 권한 체크 없는 조회 | 민감 데이터 노출 가능 |

초급 과정에서는 권한 체크 구현까지 깊게 들어가지는 않지만, 조회 대상 테이블과 업무 데이터의 민감도는 항상 고려해야 한다.

## 23. 실습 리뷰 기준

강사는 학습자 실습 결과를 다음 기준으로 검토할 수 있다.

| 검토 기준 | 좋은 결과 |
|---|---|
| Join 목적 설명 | 항공사명과 연결 정보를 함께 보기 위해 Join한다고 설명 |

| 오류 기록 | 결과 없음 또는 Syntax 오류 케이스 1개 기록 |

## 24. 자기 점검 문제

### 24.1 객관식

#### Q1. INNER JOIN의 결과에 포함되는 데이터는?

A. 왼쪽 테이블의 모든 데이터  
B. 오른쪽 테이블의 모든 데이터  
C. 양쪽 테이블의 연결 조건이 일치하는 데이터  
D. 조건과 무관하게 모든 조합 데이터

정답: C

#### Q2. `ON` 조건의 역할은?

A. 조회 결과를 화면에 정렬한다.  
B. 두 테이블을 어떤 필드로 연결할지 정의한다.  
C. Internal Table을 선언한다.  
D. ABAP 변수에 기본값을 넣는다.

정답: B

#### Q3. Join에서 Alias를 사용하는 가장 큰 이유는?

A. 프로그램 실행 속도를 무조건 높이기 위해  
B. 필드 출처를 명확히 하고 같은 필드명 충돌을 피하기 위해  
C. 테이블 데이터를 자동으로 변경하기 위해  
D. SELECT 결과를 자동 정렬하기 위해

정답: B

### 24.2 단답형

#### Q1. `ON`과 `WHERE`의 차이를 설명하시오.

모범 답안:  
`ON`은 Join 대상 테이블 사이의 연결 조건을 정의하고, `WHERE`는 연결된 결과 중 필요한 행을 필터링한다.

#### Q2. `SCARR`와 `SPFLI`를 Join할 때 기본 연결 필드는 무엇인가?

모범 답안:  
두 테이블의 항공사 코드인 `CARRID`를 기준으로 연결한다. 예: `ON c~carrid = p~carrid`.

#### Q3. Join 결과 건수가 예상보다 많을 때 확인해야 할 항목은?

모범 답안:  
ON 조건이 충분한지, 1:N 관계를 1:1로 착각하지 않았는지, WHERE 조건이 너무 넓지 않은지, 중복 가능한 필드로 Join하지 않았는지 확인한다.

## 26. 후속 모듈 연결

이번 모듈에서는 `INNER JOIN`을 배웠다.  
다음 모듈인 `THEORY-11-M02 — LEFT OUTER JOIN 기본 개념과 NULL 처리`에서는 연결 조건이 맞지 않는 데이터도 보존해야 하는 상황을 다룬다.

이번 모듈과 다음 모듈의 차이는 다음과 같다.

| 모듈 | 핵심 질문 |
|---|---|
| THEORY-11-M01 INNER JOIN | 양쪽에 모두 존재하는 데이터만 필요할 때 어떻게 조회하는가? |
| THEORY-11-M02 LEFT OUTER JOIN | 왼쪽 테이블의 데이터는 보존하면서 오른쪽 데이터를 붙이려면 어떻게 하는가? |

이후에는 Join 결과를 집계하는 `GROUP BY`, 집계 조건인 `HAVING`, 정렬인 `ORDER BY`, 그리고 Join과 `FOR ALL ENTRIES` 선택 기준으로 확장된다.

## 27. 핵심 요약

```text
INNER JOIN은 연결 조건이 양쪽 테이블에서 일치하는 데이터만 가져온다.
ON은 테이블 사이의 연결 조건이다.
WHERE는 연결된 결과를 필터링하는 조건이다.
Alias는 필드 출처를 명확히 하기 위해 사용한다.
Join 결과 행 수는 테이블 사이의 관계, 특히 1:N 관계에 따라 늘어날 수 있다.
SELECT *보다 필요한 필드를 명시하는 방식이 실무적으로 안전하다.
ON 조건은 필드 이름이 아니라 업무 관계와 Key 관계를 기준으로 작성한다.
```
