## 3. 세 가지 선택지의 큰 그림

실무에서 여러 테이블 데이터를 결합하거나 필터링할 때 대표 선택지는 다음 세 가지이다.

| 선택지 | 핵심 생각 | 대표 사용 상황 |
|---|---|---|
| JOIN | DB에서 관계를 기준으로 결합한다. | 테이블 관계가 명확하고 한 SQL로 표현 가능 |
| FOR ALL ENTRIES | ABAP 내부 테이블의 값 목록을 조건으로 후속 조회한다. | 선행 조회 결과가 후속 조회 조건이 될 때 |
| ABAP 내부 처리 | DB에서 원자료를 가져와 ABAP에서 LOOP/READ/SORT 등으로 조합한다. | 복잡한 업무 로직, 단순 SQL로 표현 어려움 |

중요한 것은 세 방식 중 하나가 절대적으로 항상 우월하지 않다는 점이다.  
하지만 S/4HANA와 HANA DB 기반의 현대 ABAP에서는 가능한 한 데이터베이스가 잘할 수 있는 작업은 DB에서 처리하는 방향을 우선 검토한다.

```text
필터링, 조인, 집계, 정렬은 DB가 잘하는 영역이다.
복잡한 예외 처리, 상태 전이, 다단계 업무 판단은 ABAP 로직이 필요한 영역이다.
```

## 4. JOIN을 선택하는 기준

### 4.1 JOIN이 적합한 경우

`JOIN`은 여러 테이블 간의 관계가 명확하고, 조건이 SQL로 표현 가능할 때 적합하다.

| 적합한 상황 | 설명 |
|---|---|
| 헤더-아이템 관계가 명확함 | 예: 주문 헤더와 주문 품목 |
| 마스터-텍스트 관계가 명확함 | 예: 코드와 코드명 |
| Check Table 관계가 명확함 | 외래키 관계나 의미상 관계가 뚜렷함 |
| 필터 조건을 DB에서 줄일 수 있음 | WHERE 조건으로 대상 데이터를 작게 만들 수 있음 |
| 결과가 한 SQL로 표현 가능함 | 조인, 필터, 집계가 한 문장에 자연스럽게 표현됨 |
| 대량 데이터 처리 가능성이 있음 | DB 최적화와 인덱스 활용을 기대할 수 있음 |

### 4.2 JOIN 예시

[추정] 아래 예시는 교육용으로 SAP Flight Model의 `SCARR`, `SPFLI` 테이블이 존재한다고 가정한다. 실습 시스템에 해당 테이블이 없으면 고객 시스템의 교육용 Z 테이블로 대체한다.

```abap
SELECT c~carrid,
       c~carrname,
       p~connid,
       p~cityfrom,
       p~cityto
  FROM scarr AS c
  INNER JOIN spfli AS p
    ON p~carrid = c~carrid
  WHERE c~carrid = @p_carrid
  INTO TABLE @DATA(lt_result).
```

이 코드는 항공사와 연결 정보를 DB에서 직접 결합한다.  
항공사 ID를 기준으로 관계가 명확하고, WHERE 조건으로 대상 항공사를 줄일 수 있으므로 JOIN이 자연스럽다.

### 4.3 JOIN을 피해야 하거나 신중해야 하는 경우

| 상황 | 이유 |
|---|---|
| 조인 조건이 명확하지 않음 | 잘못된 Cartesian Product 또는 중복 폭증 가능 |
| 선택 관계가 복잡함 | LEFT OUTER JOIN 결과 해석이 어려울 수 있음 |
| 조인 대상이 너무 많음 | SQL 가독성과 유지보수성이 낮아질 수 있음 |
| ABAP 후처리가 핵심임 | SQL로 억지 표현하면 오히려 위험 |
| 권한/클라이언트/조직 조건이 복잡함 | 표준 API나 CDS 권한 모델 검토 필요 |

초급자는 JOIN을 사용할 때 반드시 다음을 점검해야 한다.

```text
ON 조건이 업무적으로 맞는가?
WHERE 조건이 조인 전후 결과를 의도대로 제한하는가?
결과 건수가 예상보다 폭증하지 않는가?
INNER JOIN인지 LEFT OUTER JOIN인지 이유를 설명할 수 있는가?
```

## 5. FOR ALL ENTRIES를 선택하는 기준

### 5.1 FAE가 적합한 경우

`FOR ALL ENTRIES`는 선행 조회 결과 Internal Table의 값 목록을 기준으로 후속 테이블을 조회할 때 사용한다.

| 적합한 상황 | 설명 |
|---|---|
| 선행 결과가 후속 조회 조건이 됨 | 먼저 고객/문서 목록을 얻고 상세를 조회 |
| SQL JOIN으로 표현하기 애매한 단계적 조회 | 중간 로직 결과가 후속 조회 조건 |
| 여러 조건 목록을 기반으로 조회 | Internal Table의 여러 값이 조건으로 사용됨 |
| 기존 코드 패턴 유지보수가 필요 | 레거시 ABAP에서 많이 사용됨 |
| 후속 조회 대상이 선행 결과에 의해 크게 줄어듦 | 전체 테이블 조회를 피할 수 있음 |

### 5.2 FAE 예시

```abap
SELECT carrid,
       carrname
  FROM scarr
  WHERE carrid IN @s_carrid
  INTO TABLE @DATA(lt_carrier).

IF lt_carrier IS NOT INITIAL.
  SELECT carrid,
         connid,
         cityfrom,
         cityto
    FROM spfli
    FOR ALL ENTRIES IN @lt_carrier
    WHERE carrid = @lt_carrier-carrid
    INTO TABLE @DATA(lt_connection).
ENDIF.
```

이 예제의 핵심은 `lt_carrier`가 비어 있는지 먼저 확인한다는 점이다.

### 5.3 FAE의 필수 점검: Empty Table Check

`FOR ALL ENTRIES`에서 가장 대표적인 실수는 내부 테이블이 비어 있는 상태로 실행하는 것이다.

```abap
IF lt_carrier IS NOT INITIAL.
  SELECT ...
    FOR ALL ENTRIES IN @lt_carrier
    WHERE carrid = @lt_carrier-carrid
    INTO TABLE @lt_connection.
ENDIF.
```

초급자는 다음 원칙을 강하게 기억해야 한다.

```text
FOR ALL ENTRIES를 쓰기 전에는 반드시 기준 Internal Table이 비어 있지 않은지 확인한다.
```

### 5.4 FAE의 중복 위험

FAE 기준 테이블에 같은 키가 반복되어 있으면 불필요한 조건이 늘어나고, 결과 해석이 복잡해질 수 있다.  
따라서 기준 Internal Table은 조회 전 정리하는 것이 좋다.

```abap
SORT lt_carrier BY carrid.
DELETE ADJACENT DUPLICATES FROM lt_carrier COMPARING carrid.
```

실무에서는 기준 필드가 여러 개인 경우 `COMPARING` 필드를 정확히 지정해야 한다.

### 5.5 FAE를 신중하게 써야 하는 경우

| 상황 | 이유 |
|---|---|
| 기준 Internal Table이 매우 큼 | 조건 목록이 과도하게 커질 수 있음 |
| Empty Check가 없음 | 전체 조회 위험 |
| 중복 제거가 없음 | 불필요한 DB 조건과 결과 혼선 |
| JOIN으로 간단히 표현 가능 | JOIN이 더 명확하고 유지보수성이 높을 수 있음 |
| 후속 로직이 단순 결합뿐임 | DB에서 JOIN하는 것이 더 자연스러울 수 있음 |

## 6. ABAP 내부 처리를 선택하는 기준

### 6.1 ABAP 내부 처리가 필요한 경우

DB가 잘하는 일은 DB에서 하는 것이 좋지만, 모든 업무 로직을 SQL로 밀어 넣는 것이 정답은 아니다.  
다음과 같은 경우에는 ABAP 내부 처리가 필요하거나 더 명확할 수 있다.

| 상황 | 설명 |
|---|---|
| 복잡한 업무 분기 | 여러 상태와 예외를 순차적으로 판단 |
| 외부 함수/클래스 호출 필요 | DB SQL로 표현 불가 |
| 사용자 권한/조직 로직이 코드에 포함 | 표준 권한 함수나 API 필요 |
| 다단계 계산 | 중간 결과를 검증하며 처리해야 함 |
| 메시지 수집 필요 | 오류별 메시지를 테이블로 모아야 함 |
| 화면/ALV 표시용 후처리 | 색상, 아이콘, 텍스트 구성 등 |

### 6.2 ABAP 내부 조합 예시

```abap
SELECT carrid,
       carrname
  FROM scarr
  INTO TABLE @DATA(lt_carrier).

SELECT carrid,
       connid,
       cityfrom,
       cityto
  FROM spfli
  INTO TABLE @DATA(lt_connection).

SORT lt_carrier BY carrid.

LOOP AT lt_connection INTO DATA(ls_connection).
  READ TABLE lt_carrier INTO DATA(ls_carrier)
       WITH KEY carrid = ls_connection-carrid
       BINARY SEARCH.

  IF sy-subrc = 0.
    "표시용 결과 구성
  ENDIF.
ENDLOOP.
```

이 방식은 교육적으로 Internal Table 조합을 설명하기 쉽다.  
하지만 실무에서 단순 관계 결합만 한다면 JOIN이 더 적절할 가능성이 높다.

### 6.3 ABAP 내부 처리를 피해야 하는 경우

| 상황 | 이유 |
|---|---|
| DB에서 WHERE로 줄일 수 있는 데이터를 전부 가져옴 | 네트워크/메모리 낭비 |
| DB에서 GROUP BY 가능한 집계를 ABAP LOOP로 처리 | DB 최적화 포기 |
| 단순 JOIN을 ABAP LOOP/READ로 구현 | 코드량 증가와 성능 위험 |
| 대량 데이터를 SORT 없이 READ 반복 | 성능 저하 |
| Nested LOOP로 대량 데이터를 조합 | O(n*m) 문제 |

| 중복 기준 정리가 필요한가? | 보통 ON/WHERE 설계 | 필요할 수 있음 | 필요할 수 있음 |

```text
10. 코드 리뷰 시 선택 근거를 문서화한다.
```

이 흐름을 문장으로 바꾸면 다음과 같다.

```text
관계가 명확하고 SQL로 자연스럽게 표현되면 JOIN을 우선 검토한다.
선행 결과 집합을 기준으로 후속 조회가 필요하면 FAE를 검토한다.
복잡한 업무 판단, 메시지 처리, 표시 가공은 ABAP 내부 처리로 분리한다.
```

## 9. 성능 관점의 선택 기준

### 9.1 DB에서 처리하는 것이 유리한 작업

| 작업 | 이유 |
|---|---|
| WHERE 필터 | 불필요한 데이터 전송 감소 |
| JOIN | DB 옵티마이저가 관계 결합 최적화 가능 |
| GROUP BY | DB 집계 처리에 적합 |
| HAVING | 집계 결과 필터링 가능 |
| ORDER BY | 결과 정렬을 DB에서 일관되게 수행 |
| Projection | 필요한 필드만 선택하여 전송량 감소 |

초급자는 `SELECT *`를 습관적으로 쓰지 않도록 주의해야 한다.

```abap
"비권장
SELECT *
  FROM sflight
  INTO TABLE @DATA(lt_sflight).

"권장
SELECT carrid,
       connid,
       fldate,
       price,
       currency
  FROM sflight
  INTO TABLE @DATA(lt_sflight).
```

### 9.2 ABAP에서 처리해도 되는 작업

| 작업 | 이유 |
|---|---|
| 소량 결과의 표시용 텍스트 구성 | DB보다 ABAP이 명확 |
| ALV 아이콘/색상/상태 텍스트 구성 | 화면 출력 목적 |
| 복잡한 예외 메시지 수집 | 업무 메시지 처리 |
| 사용자별 후처리 | 권한/개인화 로직 |
| 이미 조회된 소량 데이터의 단순 정리 | 추가 DB 접근보다 효율적일 수 있음 |

## 10. 유지보수성 관점의 선택 기준

성능만큼 중요한 것이 유지보수성이다.

### 10.1 JOIN의 유지보수성

JOIN은 관계가 명확할 때 유지보수성이 좋다.  
하지만 JOIN이 너무 길어지고, Alias가 혼란스럽고, OUTER JOIN이 여러 개 섞이면 초급 개발자가 이해하기 어려운 SQL이 된다.

좋은 JOIN의 특징은 다음과 같다.

```text
Alias가 명확하다.
ON 조건이 업무 관계를 그대로 표현한다.
WHERE 조건이 명확하다.
필요한 필드만 SELECT한다.
결과 구조가 후속 로직에 맞다.
```

### 10.2 FAE의 유지보수성

FAE는 단계별 조회 흐름이 눈에 잘 보인다.  
하지만 Empty Check, 중복 제거, 기준 필드 정리가 누락되면 위험하다.

좋은 FAE 코드의 특징은 다음과 같다.

```text
기준 Internal Table이 비어 있는지 확인한다.
기준 키 중복을 제거한다.
FAE 조건 필드가 명확하다.
후속 결과를 어떻게 매칭할지 명확하다.
대량 데이터 가능성을 검토한다.
```

### 10.3 ABAP 내부 처리의 유지보수성

ABAP 내부 처리는 업무 로직을 자세히 표현할 수 있다.  
하지만 DB가 할 수 있는 일을 지나치게 ABAP으로 가져오면 코드가 길어지고 성능도 떨어질 수 있다.

좋은 ABAP 내부 처리의 특징은 다음과 같다.

```text
DB 조회 범위가 충분히 좁혀져 있다.
Internal Table 종류와 Key가 의도에 맞다.
SORT/READ 또는 HASHED TABLE 사용 기준이 명확하다.
Nested LOOP를 피한다.
업무 예외 처리와 메시지 수집이 읽기 쉽다.
```

## 11. 오류 상황과 예방 기준

### 11.1 JOIN 오류: 결과 건수 폭증

#### 상황

조인 조건이 부족하여 예상보다 많은 결과가 나온다.

#### 원인

```text
ON 조건에 필요한 Key 필드가 빠짐
Client 조건 또는 조직 조건 고려 부족
다대다 관계를 단순 JOIN으로 처리
```

#### 예방

```text
ON 조건을 테이블 Key와 업무 관계 기준으로 검토한다.
결과 건수를 먼저 COUNT로 확인한다.
소량 조건으로 테스트한다.
```

### 11.2 LEFT OUTER JOIN 오류: 초기값 해석 실수

#### 상황

오른쪽 테이블 데이터가 없는 경우 결과 필드가 초기값으로 보이는데, 실제 값과 구분하지 못한다.

#### 예방

```text
LEFT OUTER JOIN 결과의 누락 데이터를 별도 상태로 판단한다.
필요하면 CASE 표현식이나 후처리로 누락 여부를 명확히 한다.
```

### 11.3 FAE 오류: 기준 테이블 Empty

#### 상황

`FOR ALL ENTRIES` 기준 Internal Table이 비어 있음에도 SELECT 실행.

#### 예방

```abap
IF lt_key IS NOT INITIAL.
  SELECT ...
    FOR ALL ENTRIES IN @lt_key
    WHERE ...
    INTO TABLE @lt_result.
ENDIF.
```

### 11.4 FAE 오류: 기준 키 중복

#### 상황

기준 Internal Table에 중복 키가 많아 불필요한 조건이 생성된다.

#### 예방

```abap
SORT lt_key BY carrid connid.
DELETE ADJACENT DUPLICATES FROM lt_key COMPARING carrid connid.
```

### 11.5 ABAP 처리 오류: Nested LOOP 성능 저하

#### 상황

대량 테이블 두 개를 이중 LOOP로 비교한다.

```abap
LOOP AT lt_header INTO DATA(ls_header).
  LOOP AT lt_item INTO DATA(ls_item)
       WHERE vbeln = ls_header-vbeln.
  ENDLOOP.
ENDLOOP.
```

#### 예방

정렬 후 READ, SORTED TABLE, HASHED TABLE, GROUP BY, 또는 JOIN을 검토한다.

## 12. 실습 시나리오

### 12.1 실습 목표

같은 요구사항을 세 가지 방식으로 설계하고, 어떤 방식이 더 적절한지 판단한다.

### 12.2 요구사항

[추정] SAP Flight Model이 존재한다고 가정한다.

```text
항공사별 연결 노선 수를 조회한다.
항공사명과 노선 수를 함께 출력한다.
특정 항공사 조건을 입력할 수 있다.
결과는 항공사 ID 기준으로 정렬한다.
```

### 12.3 방법 A: JOIN + GROUP BY

```abap
SELECT c~carrid,
       c~carrname,
       COUNT( p~connid ) AS connection_count
  FROM scarr AS c
  INNER JOIN spfli AS p
    ON p~carrid = c~carrid
  WHERE c~carrid IN @s_carrid
  GROUP BY c~carrid,
           c~carrname
  ORDER BY c~carrid
  INTO TABLE @DATA(lt_join_result).
```

판단:

```text
관계가 명확하다.
집계가 필요하다.
DB가 GROUP BY를 처리할 수 있다.
따라서 이 요구사항에는 JOIN + GROUP BY가 자연스럽다.
```

### 12.4 방법 B: FAE

```abap
SELECT carrid,
       carrname
  FROM scarr
  WHERE carrid IN @s_carrid
  INTO TABLE @DATA(lt_carrier).

IF lt_carrier IS NOT INITIAL.

  SORT lt_carrier BY carrid.
  DELETE ADJACENT DUPLICATES FROM lt_carrier COMPARING carrid.

  SELECT carrid,
         connid
    FROM spfli
    FOR ALL ENTRIES IN @lt_carrier
    WHERE carrid = @lt_carrier-carrid
    INTO TABLE @DATA(lt_connection).

ENDIF.
```

이후 ABAP에서 항공사별 건수를 계산해야 한다.  
이 방식은 가능하지만, 집계를 DB에서 하지 않고 ABAP으로 가져오므로 요구사항에는 JOIN + GROUP BY보다 덜 직접적이다.

### 12.5 방법 C: ABAP 내부 처리

```abap
SELECT carrid,
       carrname
  FROM scarr
  WHERE carrid IN @s_carrid
  INTO TABLE @DATA(lt_carrier).

SELECT carrid,
       connid
  FROM spfli
  INTO TABLE @DATA(lt_connection).

LOOP AT lt_carrier INTO DATA(ls_carrier).
  DATA(lv_count) = 0.

  LOOP AT lt_connection INTO DATA(ls_connection)
       WHERE carrid = ls_carrier-carrid.
    lv_count += 1.
  ENDLOOP.

  "결과 구성
ENDLOOP.
```

이 방식은 교육용으로 이해는 쉽지만, 전체 `SPFLI`를 가져와 ABAP에서 조합하므로 실무에서는 비효율적일 가능성이 높다.

### 12.6 실습 결론

이 요구사항의 권장 선택은 다음이다.

```text
1순위: JOIN + GROUP BY
2순위: FAE + ABAP 집계
3순위: 전체 조회 후 ABAP 내부 처리
```

단, 실제 운영 데이터량, 인덱스, 권한, 테이블 관계, 시스템 버전에 따라 최종 판단은 테스트 결과와 코드 리뷰를 통해 확정해야 한다.

## 15. 후속 CDS/RAP 관점으로 확장

이번 모듈은 단순히 Open SQL 선택 기준만 다루는 것이 아니다.  
이 사고방식은 후속 CDS와 RAP에서도 그대로 확장된다.

### 15.1 CDS로의 연결

CDS View Entity에서는 데이터 모델을 DB 레벨에서 의미 있게 표현한다.  
JOIN, Association, Projection, Aggregation을 CDS에서 정의할 수 있다.

이번 모듈의 판단 기준은 CDS 학습에서 다음 질문으로 바뀐다.

```text
이 관계를 Open SQL JOIN으로 매번 작성할 것인가?
CDS Association으로 의미 있는 관계를 모델링할 것인가?
집계를 ABAP에서 할 것인가, CDS에서 View로 제공할 것인가?
```

### 15.2 RAP로의 연결

RAP에서는 CDS View Entity 위에 Behavior를 구성한다.  
따라서 데이터 접근을 어떻게 모델링할 것인지는 RAP의 서비스 품질과도 연결된다.

```text
좋은 Open SQL 판단
→ 좋은 CDS 모델링 감각
→ 좋은 RAP 비즈니스 객체 설계
```

### 15.3 Clean Core 관점

S/4HANA에서는 표준 테이블을 직접 읽는 방식, 확장 방식, API 사용 여부를 신중하게 판단해야 한다.  
모든 데이터를 직접 JOIN으로 읽는 방식이 항상 바람직한 것은 아니다.

실무에서는 다음 순서도 고려한다.

```text
표준 API가 있는가?
Released CDS View가 있는가?
표준 Extension Point가 있는가?
직접 테이블 접근이 허용되는가?
성능과 유지보수 책임은 누가 지는가?
```

이 모듈은 초급 과정이므로 직접 테이블 접근 예제로 설명하지만, 이후 Clean Core와 RAP 단계에서는 표준 API/Released Object 관점으로 확장해야 한다.

## 16. 평가 문제

### 16.1 객관식

#### Q1. 테이블 관계가 명확하고 한 SQL로 자연스럽게 표현 가능한 경우 우선 검토할 방식은?

A. Nested LOOP  
B. JOIN  
C. WRITE  
D. MESSAGE

정답: B

#### Q2. FOR ALL ENTRIES 사용 전 반드시 확인해야 하는 것은?

A. WRITE 문 존재 여부  
B. 기준 Internal Table이 비어 있지 않은지 여부  
C. 프로그램명이 Z로 시작하는지 여부  
D. ALV Field Catalog 존재 여부

정답: B

#### Q3. 단순 합계와 건수 계산에 일반적으로 적합한 방식은?

A. DB의 GROUP BY / Aggregate  
B. 모든 데이터를 SELECT * 후 ABAP LOOP  
C. WRITE 반복 출력  
D. SCREEN LOOP

정답: A

### 16.2 서술형

#### Q1. JOIN과 FAE의 선택 기준을 설명하시오.

모범 답안:  
테이블 관계가 명확하고 SQL로 자연스럽게 표현 가능하며 DB에서 필터와 조인을 처리할 수 있으면 JOIN을 우선 검토한다. 반면 선행 조회 결과 Internal Table의 값 목록을 기준으로 후속 조회가 필요한 경우에는 FAE를 검토한다. FAE 사용 시에는 기준 Internal Table Empty Check와 중복 제거가 중요하다.

#### Q2. DB에서 처리하는 것이 유리한 작업과 ABAP에서 처리하는 것이 적합한 작업을 구분하시오.

모범 답안:  
WHERE 필터, JOIN, GROUP BY, HAVING, ORDER BY처럼 데이터량을 줄이거나 집합 기반으로 처리하는 작업은 DB에서 처리하는 것이 유리하다. 반면 복잡한 업무 예외 처리, 메시지 수집, 화면 표시용 아이콘/색상 구성, 외부 함수 호출 등이 필요한 경우는 ABAP 내부 처리가 적합할 수 있다.

#### Q3. Nested LOOP가 대량 데이터에서 위험한 이유를 설명하시오.

모범 답안:  
대량 데이터 두 개를 중첩 반복하면 반복 횟수가 두 테이블 건수의 곱에 가까워져 성능이 급격히 저하될 수 있다. 따라서 JOIN, SORT 후 READ, HASHED TABLE, GROUP BY 등 대안을 검토해야 한다.

## 17. 실습 과제

### 17.1 기본 과제

다음 요구사항을 세 가지 방식으로 설계해본다.

```text
항공사별 연결 노선 수를 조회하고 항공사명과 함께 출력한다.
```

작성할 방식:

```text
1. JOIN + GROUP BY
2. FAE + ABAP 집계
```

```abap
  FROM spfli
  INTO TABLE @DATA(lt_spfli).
```

## 18. 핵심 요약

이번 모듈의 핵심은 다음이다.

```text
JOIN은 관계가 명확하고 DB에서 결합·필터·집계가 가능한 경우 우선 검토한다.
FOR ALL ENTRIES는 선행 Internal Table 결과를 기준으로 후속 조회가 필요할 때 사용한다.
FAE 사용 전에는 Empty Table Check와 중복 제거를 반드시 고려한다.
ABAP 내부 처리는 복잡한 업무 판단, 메시지 처리, 표시 가공에 적합하다.
대량 데이터의 필터링, 조인, 집계, 정렬은 가능하면 DB에서 처리하는 방향을 우선 검토한다.
성능뿐 아니라 유지보수성, 권한, 표준 API 사용 가능성도 함께 판단해야 한다.
```
