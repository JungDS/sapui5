## 3. INNER JOIN 복습

`INNER JOIN`은 두 테이블 사이에서 조건이 일치하는 데이터만 결과에 포함한다.

예를 들어 항공사 테이블 `SCARR`와 항공편 연결 테이블 `SPFLI`를 생각한다.

```text
SCARR  = 항공사 마스터
SPFLI  = 항공사별 연결 노선
```

두 테이블의 연결 기준은 보통 `CARRID`이다.

```text
SCARR-CARRID = SPFLI-CARRID
```

`INNER JOIN`은 다음과 같은 의미이다.

```text
항공사도 있고, 해당 항공사의 연결 노선도 있는 데이터만 조회한다.
```

즉, `SCARR`에는 항공사가 존재하지만 `SPFLI`에 연결 노선이 하나도 없다면 그 항공사는 결과에서 제외된다.

이 특성은 “연결 데이터가 있는 건만 보고 싶다”는 요구사항에서는 적절하다. 그러나 “연결 데이터가 없어도 기준 마스터는 모두 보고 싶다”는 요구사항에서는 적절하지 않다.

## 4. LEFT OUTER JOIN의 핵심 개념

### 4.1 쉬운 정의

`LEFT OUTER JOIN`은 왼쪽 테이블의 데이터를 기준으로 결과를 유지하고, 오른쪽 테이블에 매칭되는 데이터가 있으면 붙여서 조회하는 JOIN이다.

```text
왼쪽 테이블 데이터는 최대한 살린다.
오른쪽 테이블 데이터는 있으면 붙인다.
오른쪽에 데이터가 없으면 오른쪽 필드는 비어 있는 값처럼 보인다.
```

### 4.2 구조 그림

```text
SCARR AS c
LEFT OUTER JOIN SPFLI AS p
ON p~carrid = c~carrid
```

이 구조에서 왼쪽 테이블은 `SCARR`이고, 오른쪽 테이블은 `SPFLI`이다.

```text
왼쪽 기준: SCARR
오른쪽 추가 정보: SPFLI
연결 조건: CARRID
```

결과적으로 `SCARR`의 항공사는 조회 결과에 유지된다. `SPFLI`에 해당 항공사의 노선이 있으면 노선 정보가 붙고, 없으면 오른쪽 필드가 DB 관점에서 NULL이 된다.

### 4.3 INNER JOIN과 비교

| 구분 | INNER JOIN | LEFT OUTER JOIN |
|---|---|---|
| 기준 데이터 보존 | 양쪽 모두 매칭될 때만 | 왼쪽 데이터는 보존 |
| 오른쪽 데이터 미존재 시 | 결과에서 제외 | 결과에 남음 |
| 누락 데이터 탐지 | 부적합할 수 있음 | 적합 |
| 대표 용도 | 매칭된 업무 데이터 조회 | 기준 데이터 + 선택적 상세 데이터 조회 |
| 초급자 기억법 | 둘 다 있어야 나온다 | 왼쪽은 일단 나온다 |

## 5. LEFT OUTER JOIN이 필요한 업무 상황

실무에서는 “기준 데이터는 모두 보고 싶고, 관련 데이터가 있으면 함께 보고 싶다”는 요구가 자주 나온다.

### 5.1 마스터 데이터와 상세 데이터

예를 들어 고객 마스터는 모두 조회하되, 최근 주문이 있으면 주문 정보도 함께 보고 싶을 수 있다.

```text
고객은 모두 보여준다.
주문이 있으면 주문번호를 보여준다.
주문이 없으면 주문번호는 비어 있어도 된다.
```

이 경우 고객 테이블을 왼쪽에 두고 주문 테이블을 오른쪽에 두는 `LEFT OUTER JOIN`을 검토할 수 있다.

### 5.2 누락 데이터 점검

예를 들어 항공사 마스터에는 존재하지만 연결 노선이 없는 항공사를 찾고 싶다고 하자.

```text
SCARR에는 있는데 SPFLI에는 없는 CARRID를 찾는다.
```

이런 경우도 `LEFT OUTER JOIN`이 유용하다.

### 5.3 설정 데이터와 사용 데이터

예를 들어 상태 코드 설정은 모두 보고 싶고, 해당 상태를 실제로 사용하는 데이터가 있으면 건수나 예시를 보고 싶을 수 있다.

```text
상태 코드 기준표는 모두 출력한다.
사용 중인 데이터가 있으면 함께 표시한다.
사용되지 않는 코드는 별도로 확인한다.
```

이처럼 기준표 또는 마스터 데이터를 왼쪽에 두고, 선택적 관계 데이터를 오른쪽에 붙이는 방식이 OUTER JOIN의 대표적인 활용이다.

## 6. ABAP SQL 기본 문법

### 6.1 기본 형태

ABAP SQL의 기본적인 LEFT OUTER JOIN 형태는 다음과 같다.

```abap
SELECT c~carrid,
       c~carrname,
       p~connid,
       p~cityfrom,
       p~cityto
  FROM scarr AS c
  LEFT OUTER JOIN spfli AS p
    ON p~carrid = c~carrid
  INTO TABLE @DATA(lt_result).
```

위 코드는 다음 의미를 가진다.

| 코드 | 의미 |
|---|---|
| `scarr AS c` | 항공사 마스터를 왼쪽 기준 테이블로 사용 |
| `LEFT OUTER JOIN spfli AS p` | 연결 노선 테이블을 오른쪽 테이블로 조인 |
| `ON p~carrid = c~carrid` | 항공사 ID 기준으로 연결 |
| `c~carrid`, `c~carrname` | 왼쪽 테이블 필드 |
| `p~connid`, `p~cityfrom`, `p~cityto` | 오른쪽 테이블 필드 |
| `INTO TABLE @DATA(lt_result)` | 결과를 Internal Table에 저장 |

### 6.2 왜 Alias를 사용하는가?

JOIN에서는 여러 테이블에 같은 이름의 필드가 존재할 수 있다. 예를 들어 `SCARR`와 `SPFLI`는 모두 `CARRID`를 가진다.

Alias를 사용하지 않으면 어느 테이블의 필드인지 읽기 어렵다.

```abap
FROM scarr AS c
LEFT OUTER JOIN spfli AS p
```

이렇게 Alias를 두면 다음처럼 필드 출처를 명확히 표현할 수 있다.

```abap
c~carrid
p~carrid
```

초급자는 JOIN 학습 단계에서 Alias를 습관화하는 것이 좋다.

## 7. NULL과 ABAP Initial Value

### 7.1 DB NULL이란?

DB 관점에서 `NULL`은 “값이 없음”을 의미한다. 숫자 0이나 빈 문자열과는 다르다.

```text
0        = 숫자 값 0이 존재한다.
''       = 빈 문자 값이 존재한다.
NULL     = 값 자체가 없다.
```

LEFT OUTER JOIN에서 오른쪽 테이블에 매칭 데이터가 없으면 오른쪽 테이블 필드는 DB 관점에서 NULL이 된다.

### 7.2 ABAP에서는 어떻게 보이는가?

ABAP의 일반 변수는 DB NULL을 그대로 담는 방식이 아니라, 결과를 ABAP 타입의 Initial Value로 받는 경우가 많다.

예를 들어 오른쪽 테이블 필드가 매칭되지 않았다면 ABAP 결과에서는 다음처럼 보일 수 있다.

| DB 결과 | ABAP에서 보이는 값 예시 |
|---|---|
| NULL 문자 필드 | 공백 또는 Initial 문자값 |
| NULL 숫자 필드 | 0 |
| NULL 날짜 필드 | `00000000` |
| NULL 시간 필드 | `000000` |

즉, OUTER JOIN에서 오른쪽 데이터가 없을 때 ABAP 결과는 “비어 보이는 값”으로 나타날 수 있다.

### 7.3 왜 위험한가?

Initial Value는 두 가지 의미를 가질 수 있다.

```text
1. 실제 데이터가 Initial 값이다.
2. OUTER JOIN에서 매칭 데이터가 없어 NULL이 Initial로 변환된 것이다.
```

이 둘을 무조건 같은 의미로 해석하면 오류가 생긴다.

예를 들어 `p~connid`가 Initial로 보인다고 해서 항상 “연결 번호가 공백인 데이터가 있다”라고 말하면 안 된다. 실제로는 오른쪽 `SPFLI` 행이 없어서 발생한 결과일 수 있다.

초급자는 다음 문장을 반드시 기억해야 한다.

```text
LEFT OUTER JOIN 결과에서 오른쪽 필드의 Initial 값은 실제 값일 수도 있고, 매칭 실패의 결과일 수도 있다.
```

## 8. 매칭 여부를 구분하는 기본 전략

### 8.1 오른쪽 테이블의 Key 필드를 함께 조회한다

매칭 여부를 판단하려면 오른쪽 테이블의 Key 필드를 결과에 포함하는 것이 좋다.

```abap
SELECT c~carrid      AS carrid,
       c~carrname    AS carrname,
       p~carrid      AS spfli_carrid,
       p~connid      AS connid,
       p~cityfrom    AS cityfrom,
       p~cityto      AS cityto
  FROM scarr AS c
  LEFT OUTER JOIN spfli AS p
    ON p~carrid = c~carrid
  INTO TABLE @DATA(lt_result).
```

이때 `p~carrid`는 오른쪽 테이블에 매칭 데이터가 있는지 확인하는 힌트가 된다.

```text
p~carrid가 Initial이면 오른쪽 테이블 매칭 실패 가능성이 높다.
p~carrid가 값이 있으면 오른쪽 테이블 매칭 성공이다.
```

다만 이 판단도 오른쪽 Key 필드가 실제로 Initial이 될 수 없는 구조라는 전제가 있을 때 안전하다.

### 8.2 COALESCE 사용

ABAP SQL에서는 릴리스와 문법 범위에 따라 SQL Expression을 사용할 수 있다. 그중 `COALESCE`는 NULL일 때 대체값을 지정하는 데 유용하다.

예시는 다음과 같다.

```abap
SELECT c~carrid,
       c~carrname,
       coalesce( p~connid, '----' ) AS connid_display,
       p~cityfrom,
       p~cityto
  FROM scarr AS c
  LEFT OUTER JOIN spfli AS p
    ON p~carrid = c~carrid
  INTO TABLE @DATA(lt_result).
```

위 예제는 `p~connid`가 NULL이면 `'----'`를 표시값으로 사용하겠다는 의미이다.

> [추정] 교육 시스템의 ABAP 릴리스나 SQL 표현식 지원 범위에 따라 `COALESCE` 사용 가능 여부와 타입 추론 방식이 다를 수 있다. 사용 중인 S/4HANA 시스템에서 Syntax Check로 확인하는 것이 안전하다.

### 8.3 후처리에서 Initial만으로 단정하지 않는다

다음 코드는 단순하지만 위험할 수 있다.

```abap
IF ls_result-connid IS INITIAL.
  WRITE: / 'No connection'.
ENDIF.
```

이 코드는 `CONNID`가 실제 Initial인 경우와, OUTER JOIN 매칭 실패로 Initial처럼 들어온 경우를 구분하지 못한다.

더 안전한 방식은 매칭 판단용 필드를 함께 조회하거나, SQL 레벨에서 대체값 또는 상태값을 명확히 만드는 것이다.

## 9. WHERE 조건 위치의 중요성

LEFT OUTER JOIN에서 초급자가 가장 많이 실수하는 부분은 `WHERE` 조건을 오른쪽 테이블 필드에 걸어 OUTER JOIN 의미를 깨뜨리는 것이다.

### 9.1 위험한 예

다음 코드를 보자.

```abap
SELECT c~carrid,
       c~carrname,
       p~connid,
       p~cityfrom,
       p~cityto
  FROM scarr AS c
  LEFT OUTER JOIN spfli AS p
    ON p~carrid = c~carrid
  WHERE p~countryfr = 'US'
  INTO TABLE @DATA(lt_result).
```

이 코드는 겉으로는 LEFT OUTER JOIN이지만, `WHERE p~countryfr = 'US'` 조건 때문에 오른쪽 테이블이 매칭되지 않은 행은 결과에서 제외될 수 있다.

왜냐하면 오른쪽 테이블이 매칭되지 않은 행에서는 `p~countryfr`가 NULL이기 때문이다. NULL은 일반 비교 조건에서 `'US'`와 같지 않다.

결과적으로 LEFT OUTER JOIN을 사용했지만 INNER JOIN처럼 동작하는 결과가 나올 수 있다.

### 9.2 의도에 따른 조건 위치

오른쪽 테이블에 대한 제한 조건이 “조인 대상 자체를 제한”하는 의미라면 `ON` 조건에 넣는 방식을 검토한다.

예시:

```abap
SELECT c~carrid,
       c~carrname,
       p~connid,
       p~cityfrom,
       p~cityto
  FROM scarr AS c
  LEFT OUTER JOIN spfli AS p
    ON  p~carrid    = c~carrid
    AND p~countryfr = 'US'
  INTO TABLE @DATA(lt_result).
```

이 코드는 다음 의미에 가깝다.

```text
SCARR 항공사는 모두 유지한다.
단, 붙일 SPFLI 데이터는 출발 국가가 US인 것만 붙인다.
```

오른쪽에 US 출발 노선이 없으면 항공사 행은 남고, 오른쪽 필드는 NULL/Initial처럼 보일 수 있다.

### 9.3 판단 기준

| 조건 위치 | 의미 |
|---|---|
| `ON` 조건 | 어떤 오른쪽 데이터를 붙일 것인지 결정 |
| `WHERE` 조건 | JOIN 결과 전체에서 어떤 행을 남길지 결정 |

초급자는 다음 문장을 기억해야 한다.

```text
LEFT OUTER JOIN에서 오른쪽 테이블 필드를 WHERE에 직접 조건으로 걸면, 왼쪽 보존 효과가 사라질 수 있다.
```

## 10. 실습 시나리오

### 10.1 실습 목표

항공사 마스터 `SCARR`를 기준으로 연결 노선 `SPFLI`를 붙여 조회한다. 이때 연결 노선이 없는 항공사도 결과에서 빠지지 않는다는 점을 확인한다.

> [추정] 교육용 Flight Model 데이터(`SCARR`, `SPFLI`, `SFLIGHT`)는 많은 SAP 교육 시스템에 존재하지만, 시스템 구성에 따라 데이터가 없거나 일부 테이블이 제공되지 않을 수 있다. 데이터가 없으면 강사가 준비한 Z 테이블 또는 시스템 표준 샘플 테이블로 대체한다.

### 10.2 기본 실습 코드

```abap
REPORT zopen_sql_left_join_01.

SELECT c~carrid      AS carrid,
       c~carrname    AS carrname,
       p~carrid      AS spfli_carrid,
       p~connid      AS connid,
       p~cityfrom    AS cityfrom,
       p~cityto      AS cityto
  FROM scarr AS c
  LEFT OUTER JOIN spfli AS p
    ON p~carrid = c~carrid
  INTO TABLE @DATA(lt_result).

IF sy-subrc = 0.
  LOOP AT lt_result INTO DATA(ls_result).
    WRITE: / ls_result-carrid,
             ls_result-carrname,
             ls_result-spfli_carrid,
             ls_result-connid,
             ls_result-cityfrom,
             ls_result-cityto.
  ENDLOOP.
ELSE.
  WRITE: / 'No data found.'.
ENDIF.
```

### 10.3 관찰 포인트

실행 후 다음을 확인한다.

| 관찰 항목 | 확인 내용 |
|---|---|
| 전체 행 수 | INNER JOIN과 비교했을 때 행 수가 같은지, 더 많은지 확인 |
| `c~carrid` | 왼쪽 테이블 항공사 ID가 유지되는지 확인 |
| `p~carrid` | 오른쪽 테이블 매칭 여부 확인용 |
| `connid` | 연결 노선이 없을 때 Initial처럼 보이는지 확인 |
| 중복 행 | 항공사 하나에 여러 노선이 있으면 여러 행으로 펼쳐지는지 확인 |

## 11. INNER JOIN과 LEFT OUTER JOIN 결과 비교 실습

### 11.1 INNER JOIN 코드

```abap
REPORT zopen_sql_join_compare_01.

SELECT c~carrid,
       c~carrname,
       p~connid
  FROM scarr AS c
  INNER JOIN spfli AS p
    ON p~carrid = c~carrid
  INTO TABLE @DATA(lt_inner).

WRITE: / 'INNER JOIN rows:', lines( lt_inner ).
```

### 11.2 LEFT OUTER JOIN 코드

```abap
SELECT c~carrid,
       c~carrname,
       p~connid
  FROM scarr AS c
  LEFT OUTER JOIN spfli AS p
    ON p~carrid = c~carrid
  INTO TABLE @DATA(lt_left).

WRITE: / 'LEFT OUTER JOIN rows:', lines( lt_left ).
```

### 11.3 결과 해석

일반적으로 LEFT OUTER JOIN 결과는 INNER JOIN보다 행 수가 작지 않다. 다만 오른쪽 테이블이 1:N 관계이면 왼쪽 한 건이 여러 건으로 확장될 수 있다.

예를 들어 항공사 하나에 노선 5개가 있으면 해당 항공사는 5행으로 출력될 수 있다.

```text
SCARR 1건
SPFLI 5건
LEFT OUTER JOIN 결과 5건
```

오른쪽에 노선이 하나도 없으면 다음처럼 된다.

```text
SCARR 1건
SPFLI 0건
LEFT OUTER JOIN 결과 1건
오른쪽 필드는 NULL/Initial
```

## 12. 결과 중복과 1:N 관계

LEFT OUTER JOIN은 왼쪽 데이터를 “한 번만” 보여주는 기능이 아니다. 오른쪽 테이블에 매칭되는 데이터가 여러 건이면 왼쪽 행은 그 개수만큼 반복된다.

예시:

| SCARR-CARRID | SPFLI-CONNID |
|---|---|
| AA | 0017 |
| AA | 0064 |
| AA | 1984 |

이 결과는 정상이다. `LEFT OUTER JOIN`은 왼쪽 행을 보존하지만, 오른쪽에 여러 건이 있으면 결과가 늘어나는 것이 표준적인 관계형 데이터 처리 방식이다.

초급자는 다음을 혼동하지 말아야 한다.

```text
LEFT OUTER JOIN = 왼쪽 테이블 행 수와 결과 행 수가 항상 같다
```

이 문장은 틀렸다.

더 정확한 표현은 다음이다.

```text
LEFT OUTER JOIN = 오른쪽 매칭이 없어도 왼쪽 행이 결과에서 사라지지 않는다.
```

## 13. 오류 상황과 디버깅 포인트

### 13.1 오류 1: ON 조건 누락 또는 잘못된 연결

#### 증상

결과 행 수가 지나치게 많거나, 업무적으로 말이 안 되는 조합이 나온다.

#### 원인

`ON` 조건이 잘못되었거나, 필요한 Key 조건이 빠졌을 수 있다.

#### 해결

다음 순서로 점검한다.

```text
1. 두 테이블의 관계 필드를 확인한다.
2. Alias가 올바른지 확인한다.
3. ON 조건에 필요한 모든 연결 필드가 들어갔는지 확인한다.
4. 결과 행 수를 INNER JOIN 결과와 비교한다.
```

### 13.2 오류 2: WHERE 조건으로 OUTER JOIN이 무력화됨

#### 증상

LEFT OUTER JOIN을 사용했는데도 오른쪽 데이터가 없는 왼쪽 행이 사라진다.

#### 원인

오른쪽 테이블 필드를 `WHERE` 조건에서 직접 제한했을 가능성이 있다.

#### 해결

조건의 의도를 확인하고, 오른쪽 테이블 필터를 `ON` 조건으로 이동할 수 있는지 검토한다.

### 13.3 오류 3: Initial 값을 잘못 해석함

#### 증상

오른쪽 필드가 비어 있는 것을 실제 빈 값 데이터로 오해한다.

#### 원인

OUTER JOIN의 NULL이 ABAP Initial Value로 전달되는 특성을 고려하지 않았다.

#### 해결

오른쪽 Key 필드 또는 매칭 여부를 판단할 수 있는 보조 필드를 함께 조회한다.

### 13.4 오류 4: 너무 많은 필드를 SELECT함

#### 증상

조회가 느려지거나 결과 구조가 불필요하게 복잡해진다.

#### 원인

`SELECT *` 또는 불필요한 필드 조회를 사용했다.

#### 해결

필요한 필드만 명시한다.

```abap
SELECT c~carrid,
       c~carrname,
       p~connid
  FROM scarr AS c
  LEFT OUTER JOIN spfli AS p
    ON p~carrid = c~carrid
  INTO TABLE @DATA(lt_result).
```

## 14. 성능 관점 주의사항

LEFT OUTER JOIN은 강력하지만 무조건 사용하면 안 된다.

### 14.1 성능에 영향을 주는 요소

| 요소 | 설명 |
|---|---|
| JOIN 대상 테이블 크기 | 큰 테이블끼리 JOIN하면 비용이 커질 수 있다. |
| ON 조건 품질 | Key 기반 조건이 아니면 결과가 폭증할 수 있다. |
| WHERE 조건 | 왼쪽 테이블을 먼저 줄일 수 있는 조건이 있으면 유리하다. |
| SELECT 필드 수 | 필요한 필드만 조회해야 한다. |
| 결과 행 수 | 1:N 관계로 결과가 크게 늘 수 있다. |

### 14.2 WHERE 조건은 왼쪽 테이블 기준으로 먼저 줄인다

가능하다면 왼쪽 테이블을 제한하는 조건을 명확히 둔다.

```abap
SELECT c~carrid,
       c~carrname,
       p~connid
  FROM scarr AS c
  LEFT OUTER JOIN spfli AS p
    ON p~carrid = c~carrid
  WHERE c~carrid IN @s_carrid
  INTO TABLE @DATA(lt_result).
```

이 예제는 사용자가 입력한 항공사 범위에 대해 LEFT OUTER JOIN을 수행한다.

### 14.3 OUTER JOIN이 정말 필요한지 확인한다

오른쪽 데이터가 없는 경우를 결과에 포함할 필요가 없다면 `INNER JOIN`이 더 명확할 수 있다.

판단 질문:

```text
오른쪽 데이터가 없어도 왼쪽 데이터를 반드시 보여줘야 하는가?
```

답이 “예”이면 LEFT OUTER JOIN을 검토한다. 답이 “아니오”이면 INNER JOIN이 더 적절할 수 있다.

## 15. 실무 적용 기준

### 15.1 LEFT OUTER JOIN을 사용하기 좋은 경우

| 상황 | 예시 |
|---|---|
| 기준 마스터를 모두 표시해야 함 | 모든 고객 + 최근 주문 정보 |
| 누락 데이터를 찾고 싶음 | 제품은 있는데 가격 조건이 없는 데이터 |
| 선택적 상세 데이터를 붙이고 싶음 | 항공사 + 노선 정보 |
| 설정값 사용 여부를 확인하고 싶음 | 코드 테이블 + 실제 사용 데이터 |

### 15.2 사용을 신중히 해야 하는 경우

| 상황 | 이유 |
|---|---|
| 오른쪽 데이터가 반드시 있어야 하는 업무 | INNER JOIN이 더 명확할 수 있음 |
| 결과 행 수가 폭증하는 1:N 관계 | 성능과 중복 해석 문제 발생 |
| WHERE 조건이 복잡한 경우 | OUTER JOIN 의미가 깨질 수 있음 |
| Initial 값 자체가 업무적으로 의미 있는 경우 | NULL 변환 결과와 구분 필요 |

### 15.3 실무 리뷰 질문

LEFT OUTER JOIN 코드를 리뷰할 때 다음을 확인한다.

```text
왼쪽 기준 테이블이 정말 기준 데이터인가?
오른쪽 데이터가 없어도 결과에 남아야 하는가?
ON 조건은 업무 관계를 정확히 표현하는가?
오른쪽 테이블 조건이 WHERE에 들어가 OUTER JOIN을 깨지 않는가?
Initial 값 해석 기준이 명확한가?
필요한 필드만 SELECT하고 있는가?
```

## 17. 자가 진단 문제

### 17.1 객관식

#### Q1. LEFT OUTER JOIN의 설명으로 가장 적절한 것은?

A. 양쪽 테이블 모두에 매칭되는 데이터만 조회한다.  
B. 왼쪽 테이블의 데이터는 유지하고, 오른쪽 매칭 데이터가 있으면 붙인다.  
C. 오른쪽 테이블의 데이터만 유지한다.  
D. JOIN 조건 없이 모든 조합을 만든다.

정답: B

#### Q2. LEFT OUTER JOIN 결과에서 오른쪽 테이블 필드가 Initial로 보일 수 있는 이유는?

A. ABAP SQL은 JOIN을 지원하지 않기 때문이다.  
B. 오른쪽 테이블에 매칭 데이터가 없어 DB NULL이 ABAP Initial Value로 전달될 수 있기 때문이다.  
C. 왼쪽 테이블의 Key가 항상 비어 있기 때문이다.  
D. WHERE 조건이 항상 무시되기 때문이다.

정답: B

#### Q3. LEFT OUTER JOIN에서 오른쪽 테이블 필드를 WHERE 조건으로 제한할 때 주의해야 하는 이유는?

A. WHERE 조건은 항상 Syntax Error를 만든다.  
B. 오른쪽 매칭이 없는 행이 제외되어 OUTER JOIN 의미가 깨질 수 있다.  
C. 모든 결과가 자동으로 중복 제거된다.  
D. SELECT 결과가 항상 1건만 나온다.

정답: B

### 17.2 단답형

#### Q1. INNER JOIN과 LEFT OUTER JOIN의 가장 큰 차이를 설명하시오.

모범 답안:  
INNER JOIN은 양쪽 테이블에 모두 매칭되는 데이터만 결과에 포함한다. LEFT OUTER JOIN은 오른쪽 테이블에 매칭 데이터가 없어도 왼쪽 테이블의 데이터는 결과에 남긴다.

#### Q2. LEFT OUTER JOIN 결과에서 Initial 값을 해석할 때 왜 조심해야 하는가?

모범 답안:  
오른쪽 테이블의 실제 값이 Initial일 수도 있고, 오른쪽 테이블에 매칭 데이터가 없어 DB NULL이 ABAP Initial Value로 전달된 것일 수도 있기 때문이다.

#### Q3. 오른쪽 테이블 조건을 ON 조건에 넣는 경우와 WHERE 조건에 넣는 경우의 차이를 설명하시오.

모범 답안:  
ON 조건은 어떤 오른쪽 데이터를 붙일지 결정하는 조건이고, WHERE 조건은 JOIN 결과 전체에서 어떤 행을 남길지 결정하는 조건이다. LEFT OUTER JOIN에서 오른쪽 테이블 필드를 WHERE로 제한하면 오른쪽 매칭이 없는 왼쪽 행이 제외될 수 있다.

## 18. 강사용 설명 포인트

강의 시 다음 흐름으로 설명하면 초급자가 이해하기 쉽다.

```text
1. INNER JOIN 복습: 둘 다 있어야 나온다.

6. WHERE 조건 실수: OUTER JOIN이 INNER JOIN처럼 바뀔 수 있음.
```

```text
LEFT OUTER JOIN은 왼쪽 기준 데이터가 사라지지 않게 하기 위한 JOIN이다.
```

그리고 다음 문장도 함께 강조한다.

```text
하지만 오른쪽 조건을 WHERE에 잘못 걸면 왼쪽 보존 효과가 깨질 수 있다.
```

## 20. 후속 모듈 연결

이번 모듈에서는 LEFT OUTER JOIN을 통해 “기준 데이터 보존”과 “매칭되지 않은 오른쪽 데이터 처리”를 학습했다.

다음 모듈인 `THEORY-11-M03 — GROUP BY와 Aggregate`에서는 여러 행을 그룹화하고 합계, 건수, 평균 같은 집계 값을 구하는 방법을 다룬다.

연결 관계는 다음과 같다.

```text
THEORY-11-M01 INNER JOIN
  → 매칭되는 데이터만 연결

THEORY-11-M02 LEFT OUTER JOIN
  → 기준 데이터 보존 + 선택적 연결 데이터

THEORY-11-M03 GROUP BY와 Aggregate
  → 여러 행을 기준별로 묶어 집계
```

실무에서는 LEFT OUTER JOIN과 GROUP BY가 함께 사용되는 경우도 많다. 예를 들어 “모든 고객을 기준으로 주문 건수를 집계하되, 주문이 없는 고객도 0건으로 표시”하는 요구사항이 대표적이다. 다만 이 복합 패턴은 다음 모듈 이후에 더 자연스럽게 다룬다.

## 21. 핵심 요약

```text
LEFT OUTER JOIN은 왼쪽 테이블 데이터를 보존하는 JOIN이다.
오른쪽 테이블에 매칭 데이터가 있으면 붙이고, 없으면 오른쪽 필드는 DB NULL이 된다.
ABAP 결과에서는 NULL이 타입별 Initial Value처럼 보일 수 있다.
Initial 값은 실제 값일 수도 있고 매칭 실패 결과일 수도 있으므로 조심해야 한다.
오른쪽 테이블 필드를 WHERE 조건으로 제한하면 OUTER JOIN 의미가 깨질 수 있다.
ON 조건은 붙일 데이터를 결정하고, WHERE 조건은 최종 결과 행을 제한한다.
실무에서는 기준 데이터 보존, 누락 데이터 탐지, 선택적 상세 데이터 조회에 자주 사용한다.
```
