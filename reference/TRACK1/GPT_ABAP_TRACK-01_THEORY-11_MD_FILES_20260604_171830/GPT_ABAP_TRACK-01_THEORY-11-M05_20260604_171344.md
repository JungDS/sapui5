## 3. ORDER BY란 무엇인가?

`ORDER BY`는 Open SQL 조회 결과의 정렬 순서를 지정하는 구문이다.

기본 형태는 다음과 같다.

```abap
SELECT carrid,
       connid,
       cityfrom,
       cityto
  FROM spfli
  WHERE carrid = 'LH'
  ORDER BY connid
  INTO TABLE @DATA(lt_spfli).
```

위 예제는 `SPFLI`에서 항공사 `LH`의 연결 정보를 조회하되, 결과를 `CONNID` 기준으로 정렬한다.

정렬 방향을 명시하면 다음과 같다.

```abap
SELECT carrid,
       connid,
       cityfrom,
       cityto
  FROM spfli
  WHERE carrid = 'LH'
  ORDER BY connid ASCENDING
  INTO TABLE @DATA(lt_spfli).
```

내림차순은 다음과 같다.

```abap
SELECT carrid,
       connid,
       cityfrom,
       cityto
  FROM spfli
  WHERE carrid = 'LH'
  ORDER BY connid DESCENDING
  INTO TABLE @DATA(lt_spfli).
```

초급자는 다음처럼 이해하면 된다.

```text
ORDER BY = 데이터베이스에서 조회 결과를 어떤 순서로 줄지 명시하는 약속
```

## 4. ORDER BY가 필요한 이유

### 4.1 결과 순서 보장

`ORDER BY`가 없는 SQL 결과는 특정 순서를 보장하지 않는다고 이해해야 한다. 실제 시스템에서 같은 조회를 반복했을 때 같은 순서로 보일 수 있지만, 그것은 우연일 수 있다.

나쁜 예는 다음과 같다.

```abap
SELECT carrid, connid, cityfrom, cityto
  FROM spfli
  INTO TABLE @DATA(lt_spfli).

READ TABLE lt_spfli INTO DATA(ls_first) INDEX 1.
```

이 코드는 첫 번째 행이 어떤 의미 있는 데이터라고 가정할 수 없다. `ORDER BY`가 없으므로 첫 번째 행은 업무적으로 보장된 첫 번째가 아니다.

개선된 예는 다음과 같다.

```abap
SELECT carrid, connid, cityfrom, cityto
  FROM spfli
  ORDER BY carrid, connid
  INTO TABLE @DATA(lt_spfli).

READ TABLE lt_spfli INTO DATA(ls_first) INDEX 1.
```

이제 첫 번째 행은 `CARRID`, `CONNID` 오름차순 기준으로 가장 앞에 오는 행이다.

### 4.2 사용자 출력 안정성

리스트 출력이나 ALV에서 사용자가 보기 쉬운 순서가 필요하다. 예를 들어 항공편 목록은 항공사, 연결번호, 비행일자 순으로 보는 것이 자연스럽다.

```abap
SELECT carrid, connid, fldate, price, currency
  FROM sflight
  WHERE carrid = 'LH'
  ORDER BY carrid, connid, fldate
  INTO TABLE @DATA(lt_flight).
```

### 4.3 테스트 검증 안정성

교육과 테스트에서는 결과 순서가 중요하다. 같은 프로그램을 실행했는데 결과 순서가 매번 달라지면 학습자가 로직 오류인지 정렬 누락인지 혼동할 수 있다.

따라서 실습 예제에서는 `ORDER BY`를 명시하는 습관을 들이는 것이 좋다.

### 4.4 후속 처리 안정성

ABAP 프로그램에서 조회 결과를 순서 기반으로 처리하는 경우 `ORDER BY`는 더 중요하다. 예를 들어 이전 행과 현재 행을 비교하거나, 그룹이 바뀌는 순간을 감지하는 로직은 정렬 순서에 의존한다.

```text
정렬 순서에 의존하는 로직이 있다면,
SELECT의 ORDER BY 또는 Internal Table의 SORT를 명시해야 한다.
```

## 5. 기본 문법

### 5.1 단일 필드 정렬

```abap
SELECT carrid, connid, cityfrom, cityto
  FROM spfli
  ORDER BY carrid
  INTO TABLE @DATA(lt_spfli).
```

`CARRID` 기준 오름차순 정렬이다.

### 5.2 오름차순 명시

```abap
SELECT carrid, connid, cityfrom, cityto
  FROM spfli
  ORDER BY carrid ASCENDING
  INTO TABLE @DATA(lt_spfli).
```

`ASCENDING`은 오름차순이다. 많은 경우 기본 정렬 방향은 오름차순으로 이해할 수 있지만, 교육용 문서에서는 의도를 명확히 하기 위해 필요 시 명시하는 편이 좋다.

### 5.3 내림차순 정렬

```abap
SELECT carrid, connid, cityfrom, cityto
  FROM spfli
  ORDER BY carrid DESCENDING
  INTO TABLE @DATA(lt_spfli).
```

`DESCENDING`은 내림차순이다. 최신일자, 최대금액, 높은 수량을 먼저 보여줄 때 자주 사용한다.

### 5.4 복수 필드 정렬

```abap
SELECT carrid, connid, fldate, price, currency
  FROM sflight
  ORDER BY carrid ASCENDING,
           connid ASCENDING,
           fldate DESCENDING
  INTO TABLE @DATA(lt_flight).
```

정렬 순서는 왼쪽부터 적용된다.

```text
1순위: CARRID 오름차순
2순위: CONNID 오름차순
3순위: FLDATE 내림차순
```

즉 같은 항공사 안에서 연결번호를 정렬하고, 같은 연결번호 안에서는 비행일자를 최신순으로 보여준다.

## 7. ORDER BY와 Primary Key

### 7.1 PRIMARY KEY 기준 정렬

Open SQL에서는 테이블의 Primary Key 기준으로 정렬하는 방식을 사용할 수 있다. 초급 단계에서는 “테이블의 기본 Key 순서대로 정렬하고 싶을 때 사용할 수 있는 표현” 정도로 이해한다.

예시는 다음과 같다.

```abap
SELECT *
  FROM sflight
  ORDER BY PRIMARY KEY
  INTO TABLE @DATA(lt_sflight).
```

다만 실무 교육에서는 다음을 함께 강조해야 한다.

```text
업무적으로 어떤 순서가 필요한지 명확하다면,
ORDER BY PRIMARY KEY보다 필드명을 직접 쓰는 편이 의도를 드러내기 쉽다.
```

예를 들어 사용자에게 항공편을 항공사, 연결번호, 일자 순으로 보여주려면 다음이 더 명확하다.

```abap
SELECT carrid, connid, fldate, price, currency
  FROM sflight
  ORDER BY carrid, connid, fldate
  INTO TABLE @DATA(lt_sflight).
```

### 7.2 Key 순서와 업무 출력 순서는 다를 수 있다

Primary Key는 데이터 식별을 위한 기준이다. 사용자 출력 순서와 항상 같지는 않다.

예를 들어 테이블 Key가 다음과 같다고 하자.

```text
MANDT + CARRID + CONNID + FLDATE
```

하지만 사용자는 최신 일자부터 보고 싶을 수 있다. 이때는 다음처럼 업무 출력 순서를 별도로 지정해야 한다.

```abap
SELECT carrid, connid, fldate, price, currency
  FROM sflight
  WHERE carrid = 'LH'
  ORDER BY fldate DESCENDING
  INTO TABLE @DATA(lt_sflight).
```

## 8. JOIN 결과 정렬

### 8.1 INNER JOIN 결과 정렬

JOIN 조회에서도 `ORDER BY`를 사용할 수 있다.

```abap
SELECT a~carrid,
       a~carrname,
       b~connid,
       b~cityfrom,
       b~cityto
  FROM scarr AS a
  INNER JOIN spfli AS b
    ON a~carrid = b~carrid
  ORDER BY a~carrid, b~connid
  INTO TABLE @DATA(lt_result).
```

여기서 정렬 기준은 다음이다.

```text
1순위: 항공사 ID
2순위: 연결번호
```

JOIN에서는 같은 필드명이 여러 테이블에 존재할 수 있으므로 Alias를 사용하는 습관이 중요하다.

```abap
ORDER BY a~carrid, b~connid
```

### 8.2 LEFT OUTER JOIN 결과 정렬

LEFT OUTER JOIN에서는 오른쪽 테이블에 매칭 데이터가 없을 때 오른쪽 필드가 초기값으로 채워질 수 있다. 이 경우 정렬 결과에서 초기값이 어디에 위치하는지 확인해야 한다.

```abap
SELECT a~carrid,
       a~carrname,
       b~connid,
       b~cityfrom,
       b~cityto
  FROM scarr AS a
  LEFT OUTER JOIN spfli AS b
    ON a~carrid = b~carrid
  ORDER BY a~carrid, b~connid
  INTO TABLE @DATA(lt_result).
```

초급자에게 중요한 포인트는 다음이다.

```text
LEFT OUTER JOIN 결과는 매칭되지 않은 오른쪽 테이블 필드가 초기값으로 보일 수 있다.
그 필드를 정렬 기준으로 삼으면 초기값 데이터의 위치를 함께 확인해야 한다.
```

## 9. GROUP BY 결과 정렬

### 9.1 그룹별 집계 결과 정렬

집계 결과도 `ORDER BY`로 정렬할 수 있다.

```abap
SELECT carrid,
       COUNT( * ) AS flight_count,
       SUM( price ) AS total_price
  FROM sflight
  GROUP BY carrid
  ORDER BY carrid
  INTO TABLE @DATA(lt_summary).
```

이 예제는 항공사별 항공편 수와 총 금액을 집계한 뒤 항공사 ID 기준으로 정렬한다.

### 9.2 집계값 기준 정렬

업무에서는 그룹명보다 집계값 기준 정렬이 더 중요할 때가 많다. 예를 들어 항공편 수가 많은 항공사부터 보고 싶다면 다음처럼 작성한다.

```abap
SELECT carrid,
       COUNT( * ) AS flight_count
  FROM sflight
  GROUP BY carrid
  ORDER BY flight_count DESCENDING
  INTO TABLE @DATA(lt_summary).
```

이때 `flight_count`는 집계 결과 컬럼의 별칭이다.

> [추정] 시스템 릴리스와 Open SQL 문법 수준에 따라 SELECT list alias를 `ORDER BY`에서 사용하는 방식에 제약이 있을 수 있다. 교육 시스템에서 오류가 발생하면 `ORDER BY COUNT( * ) DESCENDING` 방식 또는 ABAP 정렬 대안으로 확인한다.

### 9.3 HAVING 이후 정렬

`HAVING`으로 집계 그룹을 필터링한 뒤 정렬할 수도 있다.

```abap
SELECT carrid,
       COUNT( * ) AS flight_count
  FROM sflight
  GROUP BY carrid
  HAVING COUNT( * ) >= 5
  ORDER BY flight_count DESCENDING
  INTO TABLE @DATA(lt_summary).
```

논리 흐름은 다음처럼 이해하면 된다.

```text
FROM / WHERE
→ GROUP BY
→ HAVING
→ SELECT 결과 구성
→ ORDER BY
→ INTO TABLE
```

초급자는 실제 DB 내부 처리 순서와 최적화 방식을 깊게 이해할 필요는 없다. 다만 학습 단계에서는 “조회하고, 그룹화하고, 그룹을 걸러낸 뒤, 최종 결과를 정렬한다”라는 논리 흐름으로 이해하면 된다.

## 10. ORDER BY와 INTO TABLE 위치 감각

ABAP Open SQL은 문법 버전과 작성 스타일에 따라 구문 배치가 다소 달라 보일 수 있다. 최신 ABAP 문법에서는 `INTO` 절의 위치가 뒤쪽으로 오는 예제를 자주 볼 수 있다.

교육용으로는 다음 형태를 기준으로 통일한다.

```abap
SELECT carrid, connid, fldate
  FROM sflight
  WHERE carrid = 'LH'
  ORDER BY carrid, connid, fldate
  INTO TABLE @DATA(lt_flight).
```

중요한 것은 키워드 순서를 기계적으로 외우는 것이 아니라, 각 절의 역할을 이해하는 것이다.

| 절 | 역할 |
|---|---|
| SELECT | 가져올 필드 정의 |
| FROM | 조회할 테이블 정의 |
| WHERE | 행 필터링 |
| GROUP BY | 그룹 기준 정의 |
| HAVING | 그룹 결과 필터링 |
| ORDER BY | 최종 결과 정렬 |
| INTO TABLE | ABAP Internal Table에 저장 |

## 11. DB 정렬과 ABAP 정렬의 선택 기준

조회 결과를 정렬하는 방법은 크게 두 가지이다.

```text
1. DB에서 ORDER BY로 정렬한다.
2. ABAP Internal Table에서 SORT로 정렬한다.
```

### 11.1 DB에서 정렬하는 것이 적합한 경우

| 상황 | 이유 |
|---|---|
| 화면 출력 순서가 조회 시점부터 명확함 | DB에서 필요한 순서로 바로 받으면 된다. |
| 상위 N건 조회와 정렬이 결합됨 | DB에서 정렬 후 제한하는 것이 자연스럽다. |
| 집계 결과를 정렬해야 함 | GROUP BY 결과를 DB에서 바로 정렬할 수 있다. |
| 후속 ABAP 처리 전에 순서가 보장되어야 함 | SELECT 결과를 안정적으로 받을 수 있다. |

### 11.2 ABAP에서 SORT가 적합한 경우

| 상황 | 이유 |
|---|---|
| 조회 후 계산 필드를 추가한 뒤 정렬 | DB에는 없는 값으로 정렬해야 한다. |
| 사용자가 ALV에서 동적으로 정렬 | UI 레벨 정렬이 더 적합하다. |
| 같은 데이터셋을 여러 기준으로 반복 정렬 | Internal Table 정렬을 여러 번 적용할 수 있다. |
| 조회 결과가 이미 작고 ABAP 로직 중심 | DB 정렬의 이점이 제한적일 수 있다. |

### 11.3 기본 실무 기준

```text
DB에서 정렬해야 의미가 있는 결과라면 ORDER BY를 사용한다.
ABAP에서 가공한 후의 결과를 정렬해야 한다면 SORT를 사용한다.
불필요한 정렬은 하지 않는다.
```

## 12. 성능 관점의 주의사항

### 12.1 ORDER BY는 비용이 있다

`ORDER BY`는 결과를 정렬해야 하므로 비용이 발생한다. 데이터량이 작을 때는 체감되지 않지만, 대량 데이터에서는 성능에 영향을 줄 수 있다.

따라서 다음처럼 모든 조회에 습관적으로 `ORDER BY`를 붙이는 것은 좋은 방식이 아니다.

```abap
SELECT *
  FROM zt_jhy_big_log
  ORDER BY created_on
  INTO TABLE @DATA(lt_log).
```

정렬이 정말 필요한지 먼저 판단해야 한다.

### 12.2 인덱스와 정렬

정렬 필드가 테이블의 Key 또는 적절한 인덱스와 관련될 때 DB가 더 효율적으로 처리할 수 있다. 반대로 인덱스와 무관한 대량 정렬은 비용이 커질 수 있다.

초급 단계에서는 인덱스 설계까지 깊게 다루지 않는다. 다만 다음 기준은 기억한다.

```text
대량 테이블에서 ORDER BY를 사용할 때는 WHERE 조건, 정렬 필드, 인덱스 가능성을 함께 생각해야 한다.
```

### 12.3 SELECT *와 ORDER BY의 조합 주의

필요 없는 필드까지 모두 가져오면서 정렬하면 네트워크, 메모리, DB 처리량이 함께 증가할 수 있다.

나쁜 예:

```abap
SELECT *
  FROM sflight
  ORDER BY carrid, connid, fldate
  INTO TABLE @DATA(lt_sflight).
```

개선 예:

```abap
SELECT carrid, connid, fldate, price, currency
  FROM sflight
  ORDER BY carrid, connid, fldate
  INTO TABLE @DATA(lt_sflight).
```

필요한 필드만 조회하는 습관은 정렬 여부와 관계없이 중요하다.

## 13. 실무 안티패턴

### 13.1 ORDER BY 없이 첫 번째 행을 신뢰

```abap
SELECT carrid, connid, fldate
  FROM sflight
  INTO TABLE @DATA(lt_flight).

READ TABLE lt_flight INTO DATA(ls_first) INDEX 1.
```

문제는 첫 번째 행의 의미가 보장되지 않는다는 점이다.

개선:

```abap
SELECT carrid, connid, fldate
  FROM sflight
  ORDER BY carrid, connid, fldate
  INTO TABLE @DATA(lt_flight).
```

### 13.2 화면에서만 정렬되면 된다고 생각

ALV에서 사용자가 정렬할 수 있다고 해서 DB 조회 정렬이 항상 불필요한 것은 아니다. 프로그램 내부 로직이 정렬 순서에 의존한다면 조회 결과나 Internal Table 정렬을 명시해야 한다.

### 13.3 불필요한 대량 정렬

정렬이 필요 없는 배치 처리에서 대량 데이터를 굳이 `ORDER BY`로 정렬하면 성능 부담이 생긴다.

### 13.4 업무 정렬 기준이 아닌 기술 Key 기준 정렬

`ORDER BY PRIMARY KEY`는 편리하지만, 사용자에게 필요한 출력 순서가 최신순, 금액순, 상태순이라면 명시적인 업무 기준으로 정렬해야 한다.

### 13.5 LEFT OUTER JOIN의 초기값 정렬을 고려하지 않음

LEFT OUTER JOIN 결과에서 오른쪽 테이블 필드를 기준으로 정렬하면 매칭되지 않은 데이터가 초기값 기준으로 앞이나 뒤에 모일 수 있다. 이 결과가 업무적으로 적절한지 확인해야 한다.

## 14. 단계별 실습

### 14.1 실습 1 — 단일 필드 정렬

목표: 항공사 정보를 항공사 ID 기준으로 정렬한다.

```abap
REPORT zsql_order_01.

SELECT carrid,
       carrname,
       currcode
  FROM scarr
  ORDER BY carrid
  INTO TABLE @DATA(lt_scarr).

LOOP AT lt_scarr INTO DATA(ls_scarr).
  WRITE: / ls_scarr-carrid,
           ls_scarr-carrname,
           ls_scarr-currcode.
ENDLOOP.
```

확인 포인트:

| 항목 | 확인 |
|---|---|
| 정렬 기준 | CARRID |
| 정렬 방향 | 오름차순 |
| 결과 확인 | CARRID 순서가 안정적인가 |

### 14.2 실습 2 — 복수 필드 정렬

목표: 항공편 데이터를 항공사, 연결번호, 일자 기준으로 정렬한다.

```abap
REPORT zsql_order_02.

SELECT carrid,
       connid,
       fldate,
       price,
       currency
  FROM sflight
  ORDER BY carrid ASCENDING,
           connid ASCENDING,
           fldate DESCENDING
  INTO TABLE @DATA(lt_flight).

LOOP AT lt_flight INTO DATA(ls_flight).
  WRITE: / ls_flight-carrid,
           ls_flight-connid,
           ls_flight-fldate,
           ls_flight-price,
           ls_flight-currency.
ENDLOOP.
```

확인 포인트:

```text
같은 CARRID 안에서 CONNID가 정렬되는가?
같은 CARRID + CONNID 안에서 FLDATE가 최신순으로 보이는가?
```

### 14.3 실습 3 — JOIN 결과 정렬

목표: 항공사와 연결 정보를 JOIN하고 결과를 항공사/연결번호 기준으로 정렬한다.

```abap
REPORT zsql_order_03.

SELECT a~carrid,
       a~carrname,
       b~connid,
       b~cityfrom,
       b~cityto
  FROM scarr AS a
  INNER JOIN spfli AS b
    ON a~carrid = b~carrid
  ORDER BY a~carrid, b~connid
  INTO TABLE @DATA(lt_result).

LOOP AT lt_result INTO DATA(ls_result).
  WRITE: / ls_result-carrid,
           ls_result-carrname,
           ls_result-connid,
           ls_result-cityfrom,
           ls_result-cityto.
ENDLOOP.
```

확인 포인트:

| 항목 | 설명 |
|---|---|
| Alias 사용 | `a~`, `b~`로 정렬 필드 출처가 명확한가 |
| JOIN 결과 | 항공사명과 연결정보가 함께 표시되는가 |
| 정렬 결과 | 항공사 ID, 연결번호 순서인가 |

### 14.4 실습 4 — 집계 결과 정렬

목표: 항공사별 항공편 수를 구하고 많은 순서대로 정렬한다.

```abap
REPORT zsql_order_04.

SELECT carrid,
       COUNT( * ) AS flight_count
  FROM sflight
  GROUP BY carrid
  ORDER BY flight_count DESCENDING
  INTO TABLE @DATA(lt_summary).

LOOP AT lt_summary INTO DATA(ls_summary).
  WRITE: / ls_summary-carrid,
           ls_summary-flight_count.
ENDLOOP.
```

오류가 발생하는 시스템에서는 다음 대안을 사용할 수 있다.

```abap
REPORT zsql_order_04_alt.

SELECT carrid,
       COUNT( * ) AS flight_count
  FROM sflight
  GROUP BY carrid
  INTO TABLE @DATA(lt_summary).

SORT lt_summary BY flight_count DESCENDING.

LOOP AT lt_summary INTO DATA(ls_summary).
  WRITE: / ls_summary-carrid,
           ls_summary-flight_count.
ENDLOOP.
```

이 대안은 집계는 DB에서 수행하고, 정렬은 ABAP Internal Table에서 수행한다.

## 15. 오류 상황과 해결

### 15.1 정렬 필드가 SELECT 결과와 맞지 않음

상황:

```abap
SELECT carrid, carrname
  FROM scarr
  ORDER BY currcode
  INTO TABLE @DATA(lt_scarr).
```

일부 문법 수준이나 DB 처리 규칙에서는 SELECT list와 ORDER BY 필드 관계에 대한 제약이 있을 수 있다. 교육용으로는 정렬 기준 필드를 SELECT list에도 포함하는 방식이 안전하다.

개선:

```abap
SELECT carrid, carrname, currcode
  FROM scarr
  ORDER BY currcode
  INTO TABLE @DATA(lt_scarr).
```

### 15.2 Alias 누락 또는 모호성

JOIN에서 같은 필드명이 여러 테이블에 존재할 수 있다.

나쁜 예:

```abap
ORDER BY carrid
```

개선:

```abap
ORDER BY a~carrid
```

### 15.3 내림차순 의도 누락

최신 데이터부터 보여주고 싶은데 `DESCENDING`을 빼면 오래된 순서가 먼저 나올 수 있다.

```abap
ORDER BY fldate DESCENDING
```

### 15.4 정렬 기준과 후속 처리 기준 불일치

예를 들어 ABAP에서 그룹 변경 로직을 `CARRID`, `CONNID` 기준으로 처리하는데 SELECT는 `FLDATE`만 정렬했다면 로직이 틀어질 수 있다.

해결 기준:

```text
후속 ABAP 로직이 어떤 순서를 전제로 하는지 먼저 확인하고,
그 순서를 SELECT ORDER BY 또는 SORT에 정확히 반영한다.
```

## 16. 디버깅과 검증 포인트

정렬 결과를 검증할 때는 단순히 화면을 훑어보지 말고 다음을 확인한다.

| 검증 항목 | 확인 방법 |
|---|---|
| 첫 번째 정렬 필드 | 이전 행보다 작아지지 않는지 확인 |
| 두 번째 정렬 필드 | 첫 번째 필드가 같을 때 순서 확인 |
| DESCENDING 필드 | 값이 감소하는지 확인 |
| JOIN Alias | 정렬 기준 필드가 어느 테이블의 필드인지 확인 |
| 집계 정렬 | 집계값이 의도한 방향으로 정렬되는지 확인 |

디버깅 시에는 Internal Table `lt_result` 또는 `lt_summary`를 열어 정렬 순서를 직접 확인한다.

## 17. 실무 적용 기준

### 17.1 화면 출력용 정렬

사용자에게 보여주는 리스트는 업무적으로 자연스러운 순서를 제공해야 한다.

예:

```text
회사코드 → 전표번호 → 회계연도
플랜트 → 자재번호
판매조직 → 고객 → 판매오더
항공사 → 연결번호 → 비행일자
```

### 17.2 배치 처리용 정렬

배치 프로그램에서는 정렬이 필요 없는 경우도 많다. 단순 전체 처리라면 불필요한 정렬은 제거한다. 다만 로그 출력, 순차 처리, 그룹 변경 감지, 파일 생성 순서가 중요하면 정렬을 명시한다.

### 17.3 인터페이스 파일 생성

외부 시스템에 파일을 전달할 때 정렬 순서는 인터페이스 사양의 일부가 될 수 있다. 이 경우 `ORDER BY` 또는 `SORT` 누락은 품질 결함이 될 수 있다.

### 17.4 테스트 케이스

테스트 검증에서는 기대 결과 순서가 명확해야 한다. Unit Test 또는 수동 테스트에서 행 순서를 비교한다면 정렬 기준을 반드시 고정한다.

## 18. 자가 점검 문제

### Q1. `ORDER BY`를 사용하지 않은 SELECT 결과 순서를 신뢰하면 안 되는 이유는 무엇인가?

**모범 답안:**
`ORDER BY`가 없으면 데이터베이스가 어떤 순서로 결과를 반환할지 보장되지 않는다. 결과 순서는 실행 계획, 인덱스, 조건, DB 최적화 방식에 따라 달라질 수 있으므로 업무 로직이나 테스트 기준으로 삼으면 안 된다.

### Q2. 최신 비행일자부터 조회하려면 어떤 정렬 방향을 사용해야 하는가?

**모범 답안:**
`ORDER BY fldate DESCENDING`을 사용한다.

### Q3. JOIN 결과에서 `ORDER BY carrid`보다 `ORDER BY a~carrid`가 좋은 이유는 무엇인가?

**모범 답안:**
JOIN에서는 같은 필드명이 여러 테이블에 존재할 수 있으므로 Alias를 사용하면 정렬 기준 필드의 출처가 명확해지고 모호성을 줄일 수 있다.

### Q4. 집계 결과를 항공편 수가 많은 순서로 정렬하려면 어떤 방식이 가능한가?

**모범 답안:**
`COUNT( * ) AS flight_count`로 집계한 뒤 `ORDER BY flight_count DESCENDING`을 사용할 수 있다. 시스템 문법 제약이 있으면 집계 결과를 Internal Table에 담은 뒤 `SORT lt_summary BY flight_count DESCENDING`으로 정렬할 수 있다.

### Q5. DB의 `ORDER BY`와 ABAP의 `SORT` 중 무엇을 선택해야 하는가?

**모범 답안:**
조회 시점부터 필요한 순서가 명확하고 DB 결과 자체를 정렬해야 하면 `ORDER BY`를 사용한다. 조회 후 ABAP에서 계산 필드를 추가하거나 여러 기준으로 반복 정렬해야 하면 Internal Table의 `SORT`가 적합할 수 있다. 불필요한 정렬은 피한다.

## 20. 강사용 설명 포인트

강의에서는 `ORDER BY`를 단순 문법이 아니라 **결과 순서에 대한 명시적 계약**으로 설명해야 한다.

추천 질문:

```text
ORDER BY가 없는데 지금 결과가 정렬되어 보이면 믿어도 될까요?
사용자 화면 정렬과 프로그램 내부 처리 정렬은 같은 문제일까요?
대량 데이터에서 무조건 ORDER BY를 붙이면 좋은 코드일까요?
JOIN 결과에서 정렬 필드는 어느 테이블 기준인지 어떻게 명확히 할까요?
집계값 기준 정렬은 DB에서 해야 할까요, ABAP에서 해야 할까요?
```

초급자는 정렬을 “보기 좋게 만드는 기능”으로만 이해하기 쉽다. 그러나 실무에서는 정렬이 테스트 안정성, 인터페이스 사양, 그룹 처리, 성능에 모두 영향을 준다.

---

## 21. 핵심 요약

```text
ORDER BY는 SELECT 결과의 정렬 순서를 명시한다.
ORDER BY가 없으면 결과 순서를 보장하지 않는다고 생각해야 한다.
ASCENDING은 오름차순, DESCENDING은 내림차순이다.
복수 필드 정렬은 왼쪽부터 1순위, 2순위, 3순위로 적용된다.
JOIN에서는 Alias를 사용해 정렬 필드 출처를 명확히 한다.
GROUP BY 결과도 ORDER BY로 정렬할 수 있다.
불필요한 ORDER BY는 성능 부담이 될 수 있다.
DB 정렬과 ABAP SORT 중 어느 쪽이 적합한지 업무 흐름에 따라 판단한다.
```

## 22. 다음 모듈 연결

다음 모듈은 `THEORY-11-M06 — FOR ALL ENTRIES 사용 기준`이다.

이번 모듈에서 학습한 `ORDER BY`는 다음 모듈과도 연결된다. `FOR ALL ENTRIES`는 입력 Internal Table을 기준으로 DB를 조회하는 패턴이며, 결과 중복, 입력 테이블 초기값, 정렬 필요성 등을 함께 고려해야 한다. 특히 FAE 결과가 업무적으로 특정 순서를 가져야 한다면 조회 후 정렬 기준을 별도로 설계해야 한다.

연결 흐름은 다음과 같다.

```text
JOIN 결과 정렬
→ GROUP BY / HAVING 결과 정렬
→ ORDER BY 기준 확립
→ FOR ALL ENTRIES 조회 결과의 중복/정렬/후처리 판단
→ JOIN / FAE / ABAP 처리 선택 기준
```
