## 0. 이 문서의 학습 범위

이 문서는 `THEORY-11-M03 — GROUP BY와 Aggregate`만 다룬다.

이번 모듈의 핵심 키워드는 다음 네 가지이다.

| 키워드 | 의미 |
|---|---|
| `GROUP BY` | 조회 결과를 특정 필드 조합별로 묶는 Open SQL 구문 |
| `SUM` | 그룹별 합계를 계산하는 집계 함수 |
| `COUNT` | 그룹별 건수 또는 전체 건수를 계산하는 집계 함수 |
| `AVG` | 그룹별 평균값을 계산하는 집계 함수 |

> 핵심 문장:  
> **`GROUP BY`는 “여러 행을 기준 필드별로 묶고, Aggregate 함수는 묶인 행들을 하나의 요약값으로 계산한다.”**

## 1. 왜 GROUP BY와 Aggregate가 필요한가?

실무에서 데이터 조회는 항상 상세 목록만 필요한 것이 아니다.  
오히려 업무 담당자가 원하는 것은 다음처럼 요약된 정보인 경우가 많다.

```text
항공사별 예약 건수
고객별 총 주문금액
월별 매출 합계
제품별 평균 단가
회사코드별 전표 건수
플랜트별 재고 수량 합계
```

이런 요약 데이터를 ABAP 내부 테이블로 모두 가져와서 `LOOP AT`으로 계산할 수도 있다.  
하지만 대량 데이터에서는 비효율적이다.

비교하면 다음과 같다.

| 방식 | 설명 | 장점 | 위험 |
|---|---|---|---|
| ABAP에서 계산 | DB에서 상세 데이터를 모두 가져온 뒤 ABAP LOOP로 합산 | 코드 흐름이 직관적 | 대량 데이터 전송, 메모리 사용, 성능 저하 |
| DB에서 집계 | Open SQL의 `GROUP BY`, `SUM`, `COUNT`, `AVG` 사용 | DB 레벨에서 요약 후 필요한 결과만 전송 | SQL 문법과 그룹 기준 이해 필요 |

S/4HANA 환경에서는 가능한 계산을 데이터베이스에 내려보내는 **Code Pushdown** 관점이 중요하다.  
초급 단계에서 CDS나 AMDP까지 확장하지 않더라도, Open SQL의 집계 조회를 이해하는 것은 Code Pushdown의 첫 번째 실전 감각이다.

## 3. Aggregate 함수의 기본 개념

Aggregate 함수는 여러 행을 하나의 값으로 계산하는 함수이다.

대표 함수는 다음과 같다.

| 함수 | 의미 | 예 |
|---|---|---|
| `COUNT( * )` | 그룹의 전체 행 수 | 항공사별 항공편 건수 |
| `COUNT( field )` | 특정 필드 값 기준 건수 | 예약번호 건수 |
| `SUM( field )` | 숫자 필드 합계 | 좌석 수 합계, 금액 합계 |
| `AVG( field )` | 숫자 필드 평균 | 평균 가격 |
| `MIN( field )` | 최솟값 | 가장 이른 날짜 |
| `MAX( field )` | 최댓값 | 가장 늦은 날짜 |

이번 모듈의 핵심 함수는 `SUM`, `COUNT`, `AVG`이다.  
`MIN`, `MAX`는 함께 알아두면 좋지만 심화 설명은 후속 SQL 응용에서 다룬다.

## 4. GROUP BY의 기본 구조

`GROUP BY`는 특정 필드별로 데이터를 묶는다.

기본 형태는 다음과 같다.

```abap
SELECT group_field,
       aggregate_function( numeric_field ) AS result_field
  FROM db_table
  GROUP BY group_field
  INTO TABLE @DATA(lt_result).
```

예를 들어 항공사별 항공편 수를 구하려면 다음과 같이 작성할 수 있다.

```abap
SELECT carrid,
       COUNT( * ) AS flight_count
  FROM sflight
  GROUP BY carrid
  INTO TABLE @DATA(lt_result).
```

이 코드는 다음 의미이다.

```text
SFLIGHT 전체 데이터를 CARRID별로 묶는다.
각 CARRID 그룹 안에 몇 건의 항공편 행이 있는지 COUNT한다.
결과는 항공사별 한 줄씩 반환한다.
```

상세 데이터가 10,000건이어도 항공사가 10개라면 결과는 10건 수준으로 줄어들 수 있다.

## 5. GROUP BY의 가장 중요한 규칙

`GROUP BY`를 처음 배울 때 가장 중요한 규칙은 이것이다.

```text
SELECT 목록에 집계 함수 없이 표시되는 필드는 GROUP BY에 포함되어야 한다.
```

예를 들어 다음 코드는 올바른 방향이다.

```abap
SELECT carrid,
       COUNT( * ) AS flight_count
  FROM sflight
  GROUP BY carrid
  INTO TABLE @DATA(lt_result).
```

`SELECT`에 집계 함수 없이 나온 필드는 `CARRID` 하나이고, `GROUP BY`에도 `CARRID`가 있다.

반대로 다음 코드는 문제가 된다.

```abap
SELECT carrid,
       connid,
       COUNT( * ) AS flight_count
  FROM sflight
  GROUP BY carrid
  INTO TABLE @DATA(lt_result).
```

`CONNID`가 `SELECT`에 있지만 `GROUP BY`에 없다.  
이 경우 시스템은 “CARRID 그룹 안에 여러 CONNID가 있을 수 있는데 어떤 CONNID를 보여줘야 하는가?”를 결정할 수 없다.

수정하려면 다음처럼 `CONNID`도 그룹 기준에 포함해야 한다.

```abap
SELECT carrid,
       connid,
       COUNT( * ) AS flight_count
  FROM sflight
  GROUP BY carrid, connid
  INTO TABLE @DATA(lt_result).
```

## 6. GROUP BY 결과를 읽는 방법

다음 조회를 보자.

```abap
SELECT carrid,
       connid,
       COUNT( * ) AS flight_count
  FROM sflight
  GROUP BY carrid, connid
  INTO TABLE @DATA(lt_result).
```

이 결과는 “항공사 + 연결번호” 조합별로 한 줄씩 나온다.

| CARRID | CONNID | FLIGHT_COUNT |
|---|---:|---:|
| AA | 0017 | 12 |
| AA | 0064 | 8 |
| LH | 0400 | 15 |
| LH | 0401 | 15 |

여기서 `COUNT`는 전체 `SFLIGHT` 행 수가 아니라, 각 그룹 안의 행 수이다.

초급자는 다음을 구분해야 한다.

| 구분 | 의미 |
|---|---|
| 원본 행 | `SFLIGHT`에 저장된 상세 항공편 일자별 데이터 |
| 그룹 기준 | `CARRID`, `CONNID` |
| 집계 결과 | 각 그룹별 `COUNT` 결과 |
| 결과 행 수 | 그룹 개수 |

## 7. COUNT 사용법

### 7.1 COUNT( * )

`COUNT( * )`는 그룹에 속한 전체 행 수를 계산한다.

```abap
SELECT carrid,
       COUNT( * ) AS flight_count
  FROM sflight
  GROUP BY carrid
  INTO TABLE @DATA(lt_count).
```

결과 의미:

```text
항공사별 항공편 행 수
```

### 7.2 단일 전체 건수 조회

그룹 없이 전체 건수만 알고 싶다면 다음처럼 쓸 수 있다.

```abap
SELECT COUNT( * )
  FROM sflight
  INTO @DATA(lv_flight_count).
```

이 경우 `GROUP BY`가 필요 없다.  
결과는 단일 값이다.

### 7.3 COUNT와 sy-subrc

`SELECT COUNT( * )`는 일반 상세 조회와 다르게 이해해야 한다.

```abap
SELECT COUNT( * )
  FROM sflight
  WHERE carrid = 'XX'
  INTO @DATA(lv_count).
```

조건에 맞는 행이 없어도 `lv_count`는 `0`이 될 수 있다.  
초급자는 COUNT 결과를 판단할 때 `sy-subrc`만 보지 말고, 실제 Count 값도 함께 확인하는 습관이 필요하다.

```abap
IF lv_count = 0.
  WRITE: / '조건에 맞는 데이터가 없습니다.'.
ENDIF.
```

## 8. SUM 사용법

`SUM`은 숫자 필드의 합계를 계산한다.

예를 들어 항공사별 가용 좌석 수 합계를 구한다고 가정한다.

```abap
SELECT carrid,
       SUM( seatsmax ) AS total_seats
  FROM sflight
  GROUP BY carrid
  INTO TABLE @DATA(lt_seats).
```

의미:

```text
SFLIGHT 데이터를 CARRID별로 묶고,
각 항공사의 SEATSMAX 값을 모두 더한다.
```

### 8.1 SUM 대상 필드

`SUM`은 숫자 성격의 필드에 사용하는 것이 적절하다.

| 적합한 필드 | 부적합한 필드 |
|---|---|
| 수량 | 이름 |
| 금액 | 설명 텍스트 |
| 좌석 수 | 코드성 문자 |
| 개수 | 날짜를 의미 없이 합산 |

날짜나 문자 코드를 합산하는 것은 업무적으로 의미가 없다.

### 8.2 금액 합계 시 주의

금액 필드를 합산할 때는 통화 단위가 섞이지 않았는지 주의해야 한다.

예를 들어 `PRICE`를 단순 합계할 때 여러 통화가 섞여 있다면 결과는 업무적으로 잘못될 수 있다.

나쁜 예:

```abap
SELECT carrid,
       SUM( price ) AS total_price
  FROM sflight
  GROUP BY carrid
  INTO TABLE @DATA(lt_price).
```

이 조회는 통화가 다른 가격을 무조건 더할 위험이 있다.

더 안전한 방향은 통화도 그룹 기준에 포함하는 것이다.

```abap
SELECT carrid,
       currency,
       SUM( price ) AS total_price
  FROM sflight
  GROUP BY carrid, currency
  INTO TABLE @DATA(lt_price).
```

의미:

```text
항공사 + 통화별 가격 합계
```

실무에서는 통화 변환이 필요한 경우 별도 기준 환율, 통화 변환 함수, CDS Annotation, 통화 키 참조 등을 함께 검토해야 한다.  
이번 모듈에서는 최소한 “금액 합계에는 통화 기준이 필요하다”는 점을 기억한다.

## 9. AVG 사용법

`AVG`는 평균값을 계산한다.

예를 들어 항공사별 평균 가격을 계산할 수 있다.

```abap
SELECT carrid,
       currency,
       AVG( price ) AS avg_price
  FROM sflight
  GROUP BY carrid, currency
  INTO TABLE @DATA(lt_avg_price).
```

여기서도 `CURRENCY`를 그룹 기준에 포함했다.  
평균 가격 역시 통화가 섞이면 의미가 없기 때문이다.

### 9.1 AVG 결과 해석

평균은 편리하지만 업무적으로 오해가 생기기 쉽다.

예를 들어 항공사별 평균 가격이 다음과 같이 나왔다고 하자.

| CARRID | CURRENCY | AVG_PRICE |
|---|---|---:|
| AA | USD | 450.00 |
| LH | EUR | 390.00 |

이 결과만 보고 AA가 LH보다 비싸다고 단정하면 안 된다.  
통화가 다르고, 노선 길이, 좌석 등급, 기간이 다를 수 있기 때문이다.

초급자는 평균을 쓸 때 다음 질문을 해야 한다.

```text
평균을 낼 기준 그룹이 적절한가?
서로 비교 가능한 값인가?
통화나 단위가 섞이지 않았는가?
극단값이 평균을 왜곡하지 않는가?
```

## 10. WHERE와 GROUP BY의 처리 순서 감각

다음 SQL을 보자.

```abap
SELECT carrid,
       COUNT( * ) AS flight_count
  FROM sflight
  WHERE fldate >= @sy-datum
  GROUP BY carrid
  INTO TABLE @DATA(lt_future_flights).
```

이 코드는 다음 순서로 이해하면 된다.

```text
1. SFLIGHT에서 FLDATE >= 오늘 조건에 맞는 상세 행을 먼저 고른다.
2. 남은 행을 CARRID별로 묶는다.
3. 각 그룹의 건수를 계산한다.
4. 결과를 ABAP 내부 테이블로 가져온다.
```

즉, `WHERE`는 그룹을 만들기 전에 상세 행을 필터링한다.

중요한 구분:

| 구문 | 적용 시점 | 역할 |
|---|---|---|
| `WHERE` | 그룹화 전 | 상세 행 필터 |
| `GROUP BY` | 필터링 후 | 그룹 생성 |
| Aggregate 함수 | 그룹 생성 후 | 그룹별 계산 |
| `HAVING` | 그룹 생성 후 | 집계 결과 필터 |

`HAVING`은 다음 모듈인 `THEORY-11-M04`에서 다룬다.  
이번 모듈에서는 `WHERE`가 그룹화 전 필터라는 점까지만 확실히 이해한다.

## 11. JOIN과 GROUP BY 함께 사용하기

이전 모듈에서 JOIN을 학습했으므로, 이번에는 JOIN 결과를 집계해본다.

예: 항공사 이름별 항공편 수

```abap
SELECT c~carrid,
       c~carrname,
       COUNT( * ) AS flight_count
  FROM scarr AS c
  INNER JOIN sflight AS f
    ON f~carrid = c~carrid
  GROUP BY c~carrid, c~carrname
  INTO TABLE @DATA(lt_result).
```

의미:

```text
SCARR와 SFLIGHT를 항공사 코드로 연결한다.
항공사 코드와 항공사명별로 그룹화한다.
각 항공사의 항공편 수를 계산한다.
```

여기서 `CARRNAME`도 `GROUP BY`에 들어간다.  
왜냐하면 `SELECT` 목록에 집계 함수 없이 표시되기 때문이다.

### 11.1 Alias와 GROUP BY

JOIN이 들어가면 필드 출처가 헷갈릴 수 있으므로 Alias를 사용하는 것이 좋다.

```abap
FROM scarr AS c
INNER JOIN sflight AS f
```

그리고 필드를 명시한다.

```abap
c~carrid
c~carrname
f~price
```

이는 실무에서 가독성과 오류 방지에 중요하다.

## 12. INTO TABLE 결과 타입

집계 조회 결과는 원본 테이블 구조와 다르다.

예를 들어 다음 SQL의 결과 구조는 `SFLIGHT`와 같지 않다.

```abap
SELECT carrid,
       COUNT( * ) AS flight_count
  FROM sflight
  GROUP BY carrid
  INTO TABLE @DATA(lt_result).
```

결과는 다음 두 필드만 가진다.

```text
CARRID
FLIGHT_COUNT
```

따라서 원본 테이블 타입 `SFLIGHT`로 받을 수 없다.  
인라인 선언 `@DATA(lt_result)`를 사용하면 ABAP가 SELECT 목록에 맞는 익명 구조를 추론해준다.

초급 학습에서는 인라인 선언이 편리하다.

하지만 실무에서 명확한 타입이 필요하면 별도 TYPES를 정의할 수 있다.

```abap
TYPES: BEGIN OF ty_flight_count,
         carrid       TYPE sflight-carrid,
         flight_count TYPE i,
       END OF ty_flight_count.

DATA lt_result TYPE STANDARD TABLE OF ty_flight_count.

SELECT carrid,
       COUNT( * ) AS flight_count
  FROM sflight
  GROUP BY carrid
  INTO TABLE @lt_result.
```

> [추정] 시스템 릴리스와 COUNT 결과 타입에 따라 정확한 타입은 달라질 수 있다. 실무에서는 인라인 선언으로 실제 타입을 확인하거나, 필요한 경우 충분한 범위의 정수 타입을 사용한다.

## 13. GROUP BY와 ABAP LOOP 집계 비교

같은 작업을 ABAP에서 직접 할 수도 있다.

### 13.1 ABAP LOOP 방식

```abap
SELECT carrid
  FROM sflight
  INTO TABLE @DATA(lt_flights).

SORT lt_flights BY carrid.

LOOP AT lt_flights INTO DATA(ls_flight).
  " 여기에서 carrid별 건수를 직접 계산
ENDLOOP.
```

초급자에게는 흐름이 눈에 보이지만, 데이터가 많아지면 비효율적이다.

### 13.2 Open SQL GROUP BY 방식

```abap
SELECT carrid,
       COUNT( * ) AS flight_count
  FROM sflight
  GROUP BY carrid
  INTO TABLE @DATA(lt_result).
```

DB가 그룹화와 건수 계산을 수행하고, ABAP에는 요약 결과만 전달한다.

### 13.3 선택 기준

| 상황 | 권장 |
|---|---|
| 단순 합계/건수/평균 | Open SQL 집계 우선 검토 |
| 복잡한 ABAP 전용 로직 필요 | ABAP 처리 검토 |
| 대량 데이터를 모두 가져와야 하는 이유 없음 | DB 집계 사용 |
| 사용자별 후처리 로직이 핵심 | ABAP 후처리 가능 |

실무 원칙:

```text
DB에서 정확하게 처리할 수 있는 단순 집계는 DB에 맡긴다.
ABAP에서만 표현 가능한 복잡한 업무 로직은 ABAP에서 처리한다.
```

## 14. 자주 발생하는 오류와 해결

### 14.1 SELECT 필드가 GROUP BY에 없음

문제 코드:

```abap
SELECT carrid,
       connid,
       COUNT( * ) AS flight_count
  FROM sflight
  GROUP BY carrid
  INTO TABLE @DATA(lt_result).
```

원인:

```text
CONNID가 SELECT 목록에 있지만 GROUP BY에 없다.
```

해결:

```abap
SELECT carrid,
       connid,
       COUNT( * ) AS flight_count
  FROM sflight
  GROUP BY carrid, connid
  INTO TABLE @DATA(lt_result).
```

### 14.2 금액을 통화 없이 합산

문제 코드:

```abap
SELECT carrid,
       SUM( price ) AS total_price
  FROM sflight
  GROUP BY carrid
  INTO TABLE @DATA(lt_result).
```

원인:

```text
통화가 섞일 가능성이 있다.
```

해결:

```abap
SELECT carrid,
       currency,
       SUM( price ) AS total_price
  FROM sflight
  GROUP BY carrid, currency
  INTO TABLE @DATA(lt_result).
```

### 14.3 집계 결과 타입을 원본 테이블 타입으로 받음

문제 코드:

```abap
DATA lt_sflight TYPE STANDARD TABLE OF sflight.

SELECT carrid,
       COUNT( * ) AS flight_count
  FROM sflight
  GROUP BY carrid
  INTO TABLE @lt_sflight.
```

원인:

```text
SELECT 결과 구조와 SFLIGHT 구조가 다르다.
```

해결:

```abap
SELECT carrid,
       COUNT( * ) AS flight_count
  FROM sflight
  GROUP BY carrid
  INTO TABLE @DATA(lt_result).
```

또는 결과 전용 타입을 정의한다.

### 14.4 WHERE와 HAVING을 혼동

문제 방향:

```text
집계 결과가 10건 이상인 그룹만 조회하고 싶은데 WHERE로 COUNT 조건을 쓰려고 함
```

해결 방향:

```text
집계 결과 조건은 HAVING에서 다룬다.
```

`HAVING`은 다음 모듈에서 학습한다.

## 15. 실습 1 — 항공사별 항공편 수

### 15.1 요구사항

`SFLIGHT`에서 항공사별 항공편 수를 조회한다.

### 15.2 예제 코드

```abap
REPORT zgpt_theory11_m03_01.

SELECT carrid,
       COUNT( * ) AS flight_count
  FROM sflight
  GROUP BY carrid
  INTO TABLE @DATA(lt_result).

LOOP AT lt_result INTO DATA(ls_result).
  WRITE: / ls_result-carrid,
           ls_result-flight_count.
ENDLOOP.
```

### 15.3 확인 포인트

| 확인 항목 | 설명 |
|---|---|
| 결과 행 수 | 항공사 수만큼 출력되는가 |
| `COUNT` 값 | 각 항공사의 상세 행 수인가 |
| `GROUP BY` | `CARRID`가 포함되어 있는가 |
| 결과 타입 | 원본 SFLIGHT 타입이 아닌 집계 결과 구조인가 |

## 16. 실습 2 — 항공사/통화별 가격 합계와 평균

### 16.1 요구사항

`SFLIGHT`에서 항공사와 통화별 가격 합계 및 평균 가격을 조회한다.

### 16.2 예제 코드

```abap
REPORT zgpt_theory11_m03_02.

SELECT carrid,
       currency,
       SUM( price ) AS total_price,
       AVG( price ) AS avg_price
  FROM sflight
  GROUP BY carrid, currency
  INTO TABLE @DATA(lt_result).

LOOP AT lt_result INTO DATA(ls_result).
  WRITE: / ls_result-carrid,
           ls_result-currency,
           ls_result-total_price,
           ls_result-avg_price.
ENDLOOP.
```

### 16.3 왜 CURRENCY를 GROUP BY에 넣는가?

가격은 통화와 함께 해석해야 한다.  
통화가 다른 금액을 단순 합산하거나 평균내면 의미가 왜곡된다.

따라서 다음 기준이 안전하다.

```text
금액 집계: 금액 필드 + 통화 필드 함께 고려
수량 집계: 수량 필드 + 단위 필드 함께 고려
```

## 17. 실습 3 — JOIN 결과 집계

### 17.1 요구사항

항공사 코드와 항공사명별 항공편 수를 조회한다.

### 17.2 예제 코드

```abap
REPORT zgpt_theory11_m03_03.

SELECT c~carrid,
       c~carrname,
       COUNT( * ) AS flight_count
  FROM scarr AS c
  INNER JOIN sflight AS f
    ON f~carrid = c~carrid
  GROUP BY c~carrid, c~carrname
  INTO TABLE @DATA(lt_result).

LOOP AT lt_result INTO DATA(ls_result).
  WRITE: / ls_result-carrid,
           ls_result-carrname,
           ls_result-flight_count.
ENDLOOP.
```

### 17.3 실무적 의미

이 예제는 “마스터 테이블의 설명 필드와 트랜잭션성 데이터의 건수”를 함께 보여주는 전형적인 패턴이다.

실무 예시로 바꾸면 다음과 같다.

| 마스터 | 상세/거래 | 집계 |
|---|---|---|
| 고객 마스터 | 판매오더 | 고객별 오더 건수 |
| 자재 마스터 | 재고/출고 이력 | 자재별 수량 합계 |
| 회사코드 | 회계전표 | 회사코드별 전표 건수 |
| 플랜트 | 생산오더 | 플랜트별 생산 건수 |

## 18. 성능과 운영 관점

### 18.1 GROUP BY는 데이터 전송량을 줄일 수 있다

상세 데이터 1,000,000건을 ABAP으로 가져와서 집계하는 것보다, DB에서 100건의 요약 결과로 줄여 가져오는 방식이 일반적으로 유리하다.

```text
상세 데이터 전체 전송
→ ABAP 메모리 사용 증가
→ LOOP 처리 증가
→ 네트워크/DB 전송량 증가

DB 집계 후 요약 전송
→ 결과 건수 감소
→ ABAP 처리량 감소
→ Code Pushdown 관점에 부합
```

### 18.2 그래도 무조건 GROUP BY가 정답은 아니다

다음 경우에는 별도 검토가 필요하다.

| 상황 | 검토 |
|---|---|
| 집계 기준이 너무 많아 결과가 거의 상세와 동일 | 이득이 작을 수 있음 |
| WHERE 조건이 부실해 대량 전체 스캔 발생 | 조건 최적화 필요 |
| 복잡한 업무 로직이 ABAP 함수/클래스에 있음 | ABAP 후처리 검토 |
| 금액/수량 단위 변환 필요 | 통화/단위 처리 설계 필요 |
| 권한 필터가 ABAP에서만 구현됨 | 권한 적용 위치 검토 필요 |

### 18.3 WHERE 조건을 먼저 생각한다

집계 조회에서도 `WHERE` 조건은 중요하다.

좋은 방향:

```abap
SELECT carrid,
       COUNT( * ) AS flight_count
  FROM sflight
  WHERE fldate BETWEEN @lv_from AND @lv_to
  GROUP BY carrid
  INTO TABLE @DATA(lt_result).
```

부족한 방향:

```abap
SELECT carrid,
       COUNT( * ) AS flight_count
  FROM sflight
  GROUP BY carrid
  INTO TABLE @DATA(lt_result).
```

기간, 조직, 회사코드, 플랜트 등 기본 조건 없이 전체 데이터를 집계하면 운영 시스템에서 부담이 될 수 있다.

## 19. 권한과 검증 관점

Open SQL 집계는 데이터를 직접 조회한다.  
따라서 실제 업무 프로그램에서는 권한 검사가 중요하다.

초급자는 다음 정도의 원칙을 기억한다.

```text
집계 결과도 업무 데이터이다.
상세 조회가 제한되어야 하는 사용자는 집계 조회도 제한되어야 할 수 있다.
권한 조건을 WHERE에 반영하거나, 조회 전 권한 검사를 수행해야 한다.
```

예를 들어 회사코드별 매출 집계 프로그램이라면 사용자가 조회 가능한 회사코드만 집계해야 한다.  
권한이 없는 회사코드의 상세 데이터를 숨기면서 집계값만 보여주는 것도 정보 유출이 될 수 있다.

## 20. 실무 안티패턴

### 20.1 전체 데이터를 가져온 뒤 ABAP에서 합계

```abap
SELECT *
  FROM sflight
  INTO TABLE @DATA(lt_sflight).

LOOP AT lt_sflight INTO DATA(ls_sflight).
  " ABAP에서 합계 계산
ENDLOOP.
```

단순 합계라면 DB에서 처리하는 것이 더 적절할 가능성이 높다.

### 20.2 SELECT *와 GROUP BY를 같이 이해하지 못함

`GROUP BY` 조회에서는 상세 행 전체 구조가 아니라 그룹별 요약 결과가 나온다.  
따라서 `SELECT *` 관점으로 접근하면 혼란이 생긴다.

### 20.3 통화/단위 무시

금액과 수량 집계에서 가장 위험한 실수이다.

```text
KRW + USD + EUR를 그대로 SUM
KG + EA + L를 그대로 SUM
```

업무적으로 의미 없는 숫자가 된다.

### 20.4 GROUP BY 기준 과다

너무 많은 필드를 그룹 기준으로 넣으면 집계의 의미가 사라진다.

예:

```text
CARRID + CONNID + FLDATE + PRICE + CURRENCY ...
```

이렇게 하면 거의 상세 행과 비슷한 결과가 나올 수 있다.

### 20.5 집계 결과를 상세 데이터처럼 후속 처리

집계 결과는 원본 테이블과 구조가 다르다.  
집계 결과를 후속 로직에서 상세 행처럼 취급하면 필드 누락, 의미 오류, 타입 오류가 발생한다.

---

## 21. 디버깅과 검증 포인트

집계 조회는 ABAP 디버거에서 DB 내부의 그룹화 과정을 직접 한 줄씩 볼 수 없다.  
따라서 검증 방식이 중요하다.

### 21.1 검증 방법

| 검증 방법 | 설명 |
|---|---|
| SE16N에서 원본 데이터 확인 | 특정 그룹의 상세 건수를 직접 확인 |
| 조건을 좁혀 테스트 | CARRID 하나만 조회해 결과 검증 |
| COUNT와 상세 조회 비교 | COUNT 결과와 SELECT 상세 건수 비교 |
| 통화/단위별 그룹 확인 | 금액/수량 집계의 의미 검증 |
| 작은 데이터셋으로 테스트 | 먼저 결과를 눈으로 검증 가능한 수준으로 제한 |

### 21.2 비교 검증 예

```abap
SELECT COUNT( * )
  FROM sflight
  WHERE carrid = 'LH'
  INTO @DATA(lv_count_lh).

SELECT carrid,
       COUNT( * ) AS flight_count
  FROM sflight
  WHERE carrid = 'LH'
  GROUP BY carrid
  INTO TABLE @DATA(lt_group_count).
```

두 결과가 같은지 비교하면 `GROUP BY` 이해가 쉬워진다.

## 22. 후속 모듈과의 연결

이번 모듈에서는 `GROUP BY`와 Aggregate 함수로 요약 데이터를 만들었다.  
다음 모듈 `THEORY-11-M04 — HAVING과 집계 조건`에서는 “집계 결과에 조건을 거는 방법”을 배운다.

관계는 다음과 같다.

```text
WHERE  : 상세 행을 먼저 필터링
GROUP BY : 필터링된 행을 그룹화
SUM/COUNT/AVG : 그룹별 계산
HAVING : 계산된 그룹 결과를 다시 필터링
```

예를 들어 다음 요구사항은 HAVING이 필요하다.

```text
항공편 수가 10건 이상인 항공사만 조회
총 매출이 1,000,000 이상인 고객만 조회
예약 건수가 5건 이상인 노선만 조회
```

이번 모듈에서는 HAVING을 깊게 다루지 않고, 다음 모듈의 필요성을 이해하는 수준으로 연결한다.

## 23. 자가 진단 문제

### 23.1 객관식

#### Q1. `GROUP BY`의 목적은 무엇인가?

A. 상세 행을 무조건 정렬한다.  
B. 특정 필드 기준으로 행을 묶어 집계할 수 있게 한다.  
C. 테이블을 물리적으로 병합한다.  
D. 화면에 자동으로 ALV를 생성한다.

정답: B

#### Q2. 다음 중 금액 합계 시 가장 주의해야 할 것은?

A. 통화 기준이 섞이지 않았는지 확인한다.  
B. 필드명을 반드시 소문자로 쓴다.  
C. `COUNT`를 반드시 같이 써야 한다.  
D. `GROUP BY`에는 숫자 필드만 넣을 수 있다.

정답: A

#### Q3. `SELECT carrid, connid, COUNT( * ) ... GROUP BY carrid`가 문제가 되는 이유는?

A. `COUNT`는 사용할 수 없기 때문이다.  
B. `CONNID`가 집계 함수 없이 SELECT 목록에 있지만 GROUP BY에 없기 때문이다.  
C. `CARRID`는 문자 필드라 GROUP BY가 불가능하기 때문이다.  
D. `GROUP BY`는 JOIN에서만 사용할 수 있기 때문이다.

정답: B

### 23.2 서술형

#### Q1. `WHERE`와 `HAVING`의 차이를 간단히 설명하시오.

모범 답안:  
`WHERE`는 그룹화 전에 상세 행을 필터링한다. `HAVING`은 `GROUP BY`와 집계 함수가 적용된 후 그룹 결과를 필터링한다. 이번 모듈에서는 `WHERE`를 중심으로 다루고, `HAVING`은 다음 모듈에서 학습한다.

#### Q2. ABAP LOOP로 집계하는 방식보다 Open SQL `GROUP BY`가 유리할 수 있는 이유를 설명하시오.

모범 답안:  
DB에서 그룹화와 집계를 먼저 수행하면 ABAP으로 전송되는 데이터량이 줄어들고, ABAP 내부 테이블 메모리와 LOOP 처리량을 줄일 수 있다. 단순 합계, 건수, 평균은 DB에서 처리하는 것이 Code Pushdown 관점에 부합한다.

#### Q3. `SUM( price )`를 사용할 때 `currency`를 함께 고려해야 하는 이유를 설명하시오.

모범 답안:  
금액은 통화 단위와 함께 해석해야 한다. 서로 다른 통화의 금액을 단순 합산하면 업무적으로 의미 없는 값이 될 수 있다. 따라서 통화별로 그룹화하거나 별도 통화 변환 로직을 고려해야 한다.

## 25. 핵심 요약

이번 모듈의 핵심은 다음이다.

```text
GROUP BY는 상세 행을 특정 기준별로 묶는다.
SUM, COUNT, AVG는 그룹 안의 여러 행을 하나의 값으로 계산한다.
SELECT 목록의 비집계 필드는 GROUP BY에 포함되어야 한다.
WHERE는 그룹화 전에 상세 행을 필터링한다.
금액과 수량 집계는 통화와 단위를 반드시 고려해야 한다.
JOIN 결과도 GROUP BY로 집계할 수 있다.
단순 집계는 ABAP LOOP보다 DB 집계를 우선 검토한다.
```

초급자는 이번 모듈을 통해 “DB에서 요약해서 가져온다”는 감각을 익혀야 한다.  
이 감각은 이후 CDS View, Analytical Query, RAP List Report, Fiori Elements로 확장될 때 매우 중요해진다.
