## 1. 이 문서의 목적

이 문서는 ABAP Open SQL에서 `FOR ALL ENTRIES`를 언제, 어떻게 사용해야 하는지 초급자도 실무 기준으로 이해할 수 있도록 구성한 학습 문서이다.

`FOR ALL ENTRIES`는 ABAP 개발에서 오래전부터 많이 사용된 조회 패턴이다.  
하지만 잘못 사용하면 **전체 테이블 조회**, **불필요한 중복 조건**, **예상과 다른 결과**, **성능 저하**를 만들 수 있다.

이번 모듈의 핵심은 다음 한 문장으로 요약할 수 있다.

```text
FOR ALL ENTRIES는 내부 테이블의 값 목록을 기준으로 DB를 조회하는 기능이지만,
사용 전 반드시 내부 테이블이 비어 있지 않은지 확인하고,
중복 키를 제거한 뒤 사용해야 한다.
```

이번 모듈은 `FOR ALL ENTRIES`와 관련된 기본 규칙에 집중한다.  
`JOIN`, `FOR ALL ENTRIES`, ABAP 내부 처리 중 무엇을 선택해야 하는지는 다음 모듈인 `THEORY-11-M07`에서 종합적으로 판단한다.

## 2. 선수 지식

이 모듈을 이해하려면 다음 내용을 알고 있어야 한다.

| 선수 지식 | 필요한 이유 |
|---|---|
| Internal Table | `FOR ALL ENTRIES`는 내부 테이블을 기준으로 조회한다. |
| Open SQL 기본 SELECT | DB 테이블에서 데이터를 읽는 기본 문법이 필요하다. |
| WHERE 조건 | 내부 테이블 값과 DB 컬럼을 조건으로 연결한다. |
| INNER JOIN / LEFT OUTER JOIN | `FOR ALL ENTRIES`와 비교되는 대표 조회 방식이다. |
| SORT / DELETE ADJACENT DUPLICATES | 중복 키 제거에 필요하다. |

## 3. FOR ALL ENTRIES란 무엇인가?

`FOR ALL ENTRIES`는 내부 테이블에 들어 있는 여러 값을 기준으로 데이터베이스 테이블을 조회하는 Open SQL 문법이다.

예를 들어 항공편 연결 정보 `SPFLI`에서 특정 노선 목록을 먼저 구하고, 그 노선에 해당하는 실제 운항 데이터 `SFLIGHT`를 조회한다고 가정한다.

```text
1단계: SPFLI에서 조회 대상 노선 목록을 가져온다.
2단계: 그 노선 목록을 기준으로 SFLIGHT를 조회한다.
```

이때 2단계에서 `FOR ALL ENTRIES`를 사용할 수 있다.

개념적으로는 다음과 비슷하다.

```text
SFLIGHT에서
  (CARRID = 첫 번째 노선-CARRID AND CONNID = 첫 번째 노선-CONNID)
또는
  (CARRID = 두 번째 노선-CARRID AND CONNID = 두 번째 노선-CONNID)
또는
  ...
조건을 만족하는 데이터를 조회한다.
```

초급자 관점에서는 다음처럼 이해하면 된다.

```text
FOR ALL ENTRIES = 내부 테이블에 들어 있는 키 목록을 DB 조회 조건으로 사용하는 방식
```

## 4. 기본 사용 형태

기본 형태는 다음과 같다.

```abap
SELECT field1,
       field2,
       field3
  FROM db_table
  FOR ALL ENTRIES IN @lt_key
  WHERE key_field1 = @lt_key-key_field1
    AND key_field2 = @lt_key-key_field2
  INTO TABLE @DATA(lt_result).
```

여기서 각 요소의 의미는 다음과 같다.

| 요소 | 의미 |
|---|---|
| `lt_key` | 조회 조건으로 사용할 내부 테이블 |
| `lt_key-key_field1` | 내부 테이블의 비교 필드 |
| `db_table-key_field1` | DB 테이블의 비교 컬럼 |
| `WHERE` | 내부 테이블 값과 DB 컬럼을 연결하는 조건 |
| `lt_result` | 조회 결과를 담을 내부 테이블 |

## 5. 가장 중요한 규칙: Empty Table Check

`FOR ALL ENTRIES`에서 가장 중요한 규칙은 **내부 테이블이 비어 있는지 먼저 확인하는 것**이다.

### 5.1 위험한 코드

다음 코드는 매우 위험하다.

```abap
SELECT carrid,
       connid,
       fldate,
       price
  FROM sflight
  FOR ALL ENTRIES IN @lt_spfli
  WHERE carrid = @lt_spfli-carrid
    AND connid = @lt_spfli-connid
  INTO TABLE @DATA(lt_sflight).
```

문제는 `lt_spfli`가 비어 있을 때 발생한다.

`FOR ALL ENTRIES`의 기준 내부 테이블이 비어 있으면, 의도한 조건이 적용되지 않아 매우 많은 데이터가 조회될 수 있다.  
실무에서는 이를 “실수로 전체 테이블을 읽었다”라고 표현하는 경우가 많다.

### 5.2 안전한 코드

항상 다음처럼 내부 테이블이 비어 있지 않을 때만 실행한다.

```abap
IF lt_spfli IS NOT INITIAL.

  SELECT carrid,
         connid,
         fldate,
         price
    FROM sflight
    FOR ALL ENTRIES IN @lt_spfli
    WHERE carrid = @lt_spfli-carrid
      AND connid = @lt_spfli-connid
    INTO TABLE @DATA(lt_sflight).

ENDIF.
```

이 패턴은 반드시 습관화해야 한다.

```text
FOR ALL ENTRIES 사용 전:
IF lt_key IS NOT INITIAL.
```

## 6. 두 번째 핵심 규칙: 중복 키 제거

`FOR ALL ENTRIES`의 기준 내부 테이블에 중복 값이 많으면 불필요한 조건이 많이 생성될 수 있다.  
이는 DB 처리량과 네트워크/SQL 처리 효율에 악영향을 줄 수 있다.

### 6.1 중복이 있는 내부 테이블 예시

| CARRID | CONNID |
|---|---|
| AA | 0017 |
| AA | 0017 |
| AA | 0017 |
| LH | 0400 |

이 상태로 `FOR ALL ENTRIES`를 실행하면 같은 조건이 반복적으로 포함될 수 있다.  
결과 데이터가 중복되어 보이는 문제보다 더 중요한 것은 **불필요한 조회 조건이 많아지는 성능 문제**이다.

### 6.2 중복 제거 패턴

사용 전에 기준 키만 남기고 정렬한 뒤 중복을 제거한다.

```abap
SORT lt_spfli BY carrid connid.
DELETE ADJACENT DUPLICATES FROM lt_spfli COMPARING carrid connid.
```

그리고 나서 `FOR ALL ENTRIES`를 실행한다.

```abap
IF lt_spfli IS NOT INITIAL.

  SELECT carrid,
         connid,
         fldate,
         price
    FROM sflight
    FOR ALL ENTRIES IN @lt_spfli
    WHERE carrid = @lt_spfli-carrid
      AND connid = @lt_spfli-connid
    INTO TABLE @DATA(lt_sflight).

ENDIF.
```

## 7. 표준 권장 패턴

초급 단계에서 반드시 외워야 할 안전한 패턴은 다음이다.

```abap
" 1. 기준 데이터 조회
SELECT carrid,
       connid
  FROM spfli
  WHERE carrid = @p_carrid
  INTO TABLE @DATA(lt_spfli).

" 2. 중복 제거
SORT lt_spfli BY carrid connid.
DELETE ADJACENT DUPLICATES FROM lt_spfli COMPARING carrid connid.

" 3. Empty Table Check 후 FAE 실행
IF lt_spfli IS NOT INITIAL.

  SELECT carrid,
         connid,
         fldate,
         price,
         currency
    FROM sflight
    FOR ALL ENTRIES IN @lt_spfli
    WHERE carrid = @lt_spfli-carrid
      AND connid = @lt_spfli-connid
    INTO TABLE @DATA(lt_flight).

ENDIF.
```

이 예제에서 핵심은 SELECT 문 자체보다 그 앞의 준비 단계이다.

```text
기준 데이터 조회
→ 기준 키 정렬
→ 중복 제거
→ 비어 있는지 확인
→ FOR ALL ENTRIES 실행
```

## 8. FOR ALL ENTRIES가 필요한 대표 상황

`FOR ALL ENTRIES`는 다음과 같은 상황에서 자주 등장한다.

### 8.1 1차 조회 결과를 기준으로 2차 조회가 필요할 때

예를 들어 먼저 조건에 맞는 주문번호 목록을 찾고, 그 주문번호 목록을 기준으로 상세 데이터를 조회할 수 있다.

```text
1차 조회: 주문 헤더에서 대상 주문번호 목록 추출
2차 조회: 주문번호 목록 기준으로 주문 아이템 조회
```

### 8.2 조인하기 어려운 단계적 조회가 필요할 때

일부 상황에서는 프로그램 로직상 먼저 대상 집합을 ABAP 내부 테이블로 구성한 뒤, 그 결과를 기준으로 DB를 다시 조회해야 한다.

예:

```text
사용자 입력
→ 권한/필터/비즈니스 로직으로 대상 키 목록 구성
→ 대상 키 목록 기준으로 DB 조회
```

### 8.3 내부 테이블의 키 목록이 조회 조건이 될 때

DB 테이블이 아니라 ABAP 내부 처리 결과가 조회 기준이 되는 경우 `FOR ALL ENTRIES`가 사용될 수 있다.

## 9. 사용을 피해야 하는 대표 상황

`FOR ALL ENTRIES`가 항상 좋은 선택은 아니다.

### 9.1 단순 JOIN으로 해결되는 경우

두 테이블이 명확한 키 관계를 가지고 있고, DB에서 한 번에 처리하는 것이 자연스럽다면 `JOIN`이 더 적절할 수 있다.

```abap
SELECT a~carrid,
       a~connid,
       b~fldate,
       b~price
  FROM spfli AS a
  INNER JOIN sflight AS b
    ON  b~carrid = a~carrid
    AND b~connid = a~connid
  WHERE a~carrid = @p_carrid
  INTO TABLE @DATA(lt_result).
```

이 모듈에서는 `JOIN`과 `FOR ALL ENTRIES`의 최종 선택 기준을 깊게 다루지 않는다.  
다만 단순 관계 조회를 무조건 `FOR ALL ENTRIES`로 처리하는 습관은 피해야 한다.

### 9.2 기준 내부 테이블이 너무 큰 경우

기준 내부 테이블에 매우 많은 행이 들어 있으면 `FOR ALL ENTRIES` 조건이 과도하게 커질 수 있다.

이 경우에는 다음을 검토해야 한다.

```text
정말 필요한 키만 남겼는가?
중복을 제거했는가?
DB JOIN으로 처리할 수 없는가?
조회 조건을 더 좁힐 수 없는가?
패키지 단위 처리가 필요한가?
```

### 9.3 기준 테이블이 비어 있을 수 있는데 체크하지 않는 경우

이것은 사용을 피해야 하는 수준이 아니라 명확한 오류 패턴이다.

```abap
" 위험: Empty Table Check 없음
SELECT ...
  FROM ...
  FOR ALL ENTRIES IN @lt_key
  WHERE ...
```

반드시 `IF lt_key IS NOT INITIAL.`을 사용한다.

## 10. 결과 중복과 Duplicate Risk 이해

`FOR ALL ENTRIES`에서 중복과 관련해 초급자가 혼동하는 지점은 두 가지이다.

### 10.1 기준 내부 테이블의 중복

기준 내부 테이블에 같은 키가 반복되는 경우이다.

```text
lt_key에 같은 CARRID/CONNID가 여러 번 있음
```

이 경우 불필요한 조건이 늘어나 성능에 악영향을 줄 수 있다.  
따라서 사전에 `SORT`와 `DELETE ADJACENT DUPLICATES`로 정리한다.

### 10.2 결과 데이터의 중복처럼 보이는 현상

조회 결과에 비슷한 데이터가 여러 건 나오는 것은 실제 DB에 여러 행이 있기 때문일 수 있다.  
예를 들어 `SFLIGHT`에는 같은 항공사/노선에 대해 여러 비행일자가 존재할 수 있다.

| CARRID | CONNID | FLDATE |
|---|---|---|
| AA | 0017 | 2026-06-01 |
| AA | 0017 | 2026-06-02 |
| AA | 0017 | 2026-06-03 |

이는 중복 오류가 아니라 정상 데이터일 수 있다.  
따라서 결과 중복을 판단할 때는 업무 Key를 먼저 확인해야 한다.

## 11. 실무에서 자주 하는 실수

### 11.1 Empty Table Check 누락

가장 위험한 실수이다.

```abap
SELECT ...
  FROM sflight
  FOR ALL ENTRIES IN @lt_key
  WHERE carrid = @lt_key-carrid
  INTO TABLE @DATA(lt_result).
```

개선:

```abap
IF lt_key IS NOT INITIAL.
  SELECT ...
    FROM sflight
    FOR ALL ENTRIES IN @lt_key
    WHERE carrid = @lt_key-carrid
    INTO TABLE @DATA(lt_result).
ENDIF.
```

### 11.2 중복 제거 누락

위험한 패턴:

```abap
IF lt_key IS NOT INITIAL.
  SELECT ...
    FOR ALL ENTRIES IN @lt_key
    ...
ENDIF.
```

더 좋은 패턴:

```abap
SORT lt_key BY carrid connid.
DELETE ADJACENT DUPLICATES FROM lt_key COMPARING carrid connid.

IF lt_key IS NOT INITIAL.
  SELECT ...
    FOR ALL ENTRIES IN @lt_key
    ...
ENDIF.
```

### 11.3 비교 필드 부족

예를 들어 `SFLIGHT`를 조회하면서 `CARRID`만 비교하면 너무 많은 데이터가 조회될 수 있다.

```abap
WHERE carrid = @lt_spfli-carrid
```

노선 단위로 조회하려면 보통 `CARRID`와 `CONNID`를 함께 비교해야 한다.

```abap
WHERE carrid = @lt_spfli-carrid
  AND connid = @lt_spfli-connid
```

### 11.4 필요 없는 전체 필드 조회

`SELECT *`를 무조건 사용하는 것도 좋지 않다.

비권장:

```abap
SELECT *
  FROM sflight
  FOR ALL ENTRIES IN @lt_spfli
  WHERE carrid = @lt_spfli-carrid
    AND connid = @lt_spfli-connid
  INTO TABLE @DATA(lt_sflight).
```

권장:

```abap
SELECT carrid,
       connid,
       fldate,
       price,
       currency
  FROM sflight
  FOR ALL ENTRIES IN @lt_spfli
  WHERE carrid = @lt_spfli-carrid
    AND connid = @lt_spfli-connid
  INTO TABLE @DATA(lt_sflight).
```

조회 필드는 실제로 필요한 컬럼만 선택하는 습관이 좋다.

## 12. 실습 시나리오

### 12.1 실습 목표

`SPFLI`에서 특정 항공사의 노선 목록을 조회한 뒤, 해당 노선에 대한 `SFLIGHT` 데이터를 `FOR ALL ENTRIES`로 조회한다.

> [추정] `SCARR`, `SPFLI`, `SFLIGHT`는 많은 ABAP 교육 시스템에서 제공되는 Flight Model 테이블이지만, 모든 S/4HANA 실습 시스템에 동일하게 준비되어 있다고 보장할 수는 없다. 없는 경우 교육용 Z 테이블 또는 시스템의 표준 예제 테이블로 대체한다.

### 12.2 예제 프로그램

```abap
REPORT ztheory11_m06_fae_basic.

PARAMETERS p_carrid TYPE s_carr_id DEFAULT 'AA'.

" 1. 기준 노선 목록 조회
SELECT carrid,
       connid
  FROM spfli
  WHERE carrid = @p_carrid
  INTO TABLE @DATA(lt_spfli).

" 2. 중복 제거
SORT lt_spfli BY carrid connid.
DELETE ADJACENT DUPLICATES FROM lt_spfli COMPARING carrid connid.

" 3. 기준 테이블이 비어 있지 않을 때만 FAE 실행
IF lt_spfli IS NOT INITIAL.

  SELECT carrid,
         connid,
         fldate,
         price,
         currency
    FROM sflight
    FOR ALL ENTRIES IN @lt_spfli
    WHERE carrid = @lt_spfli-carrid
      AND connid = @lt_spfli-connid
    INTO TABLE @DATA(lt_flight).

  WRITE: / '조회된 항공편 수:', lines( lt_flight ).

  LOOP AT lt_flight INTO DATA(ls_flight).
    WRITE: / ls_flight-carrid,
             ls_flight-connid,
             ls_flight-fldate,
             ls_flight-price,
             ls_flight-currency.
  ENDLOOP.

ELSE.
  WRITE: / '조회 대상 노선이 없습니다.'.
ENDIF.
```

## 13. 실습 검증 포인트

실습 후 다음을 확인한다.

| 검증 항목 | 확인 내용 |
|---|---|
| 기준 테이블 조회 | `lt_spfli`에 데이터가 들어오는가 |
| Empty Table Check | `IF lt_spfli IS NOT INITIAL`이 있는가 |
| 중복 제거 | `SORT`, `DELETE ADJACENT DUPLICATES`를 수행했는가 |
| 비교 필드 | `CARRID`, `CONNID`를 함께 비교하는가 |
| 결과 건수 | 예상 범위의 데이터가 조회되는가 |
| 조회 필드 | 필요한 필드만 SELECT하는가 |
| 오류 케이스 | 기준 테이블이 비어 있을 때 전체 조회를 막는가 |

## 14. 오류 케이스 실습

### 14.1 기준 데이터가 없는 항공사 입력

`p_carrid`에 존재하지 않는 값을 입력한다.

```text
ZZ
```

예상 결과:

```text
조회 대상 노선이 없습니다.
```

이 결과가 나와야 한다.  
만약 많은 항공편 데이터가 조회된다면 Empty Table Check가 누락되었을 가능성이 높다.

### 14.2 Empty Table Check 제거 후 비교

교육 목적상 개발/실습 시스템에서만 Empty Table Check를 잠시 제거해 결과 차이를 관찰할 수 있다.

주의:

```text
운영 시스템이나 대량 데이터 테이블에서는 절대 실험하지 않는다.
```

이 실험의 목적은 다음이다.

```text
FOR ALL ENTRIES 기준 내부 테이블이 비었을 때 왜 위험한지 체감한다.
```

## 16. ATC와 코드 리뷰 관점

실무 코드 리뷰에서 `FOR ALL ENTRIES`가 보이면 리뷰어는 보통 다음을 확인한다.

```text
기준 내부 테이블 Empty Check가 있는가?
중복 제거가 되어 있는가?
기준 키 필드가 충분한가?
조회 필드가 과도하지 않은가?
JOIN으로 더 단순하게 처리할 수 없는가?
대량 데이터에서 위험하지 않은가?
```

특히 다음 코드는 리뷰에서 지적될 가능성이 높다.

```abap
SELECT *
  FROM zlarge_table
  FOR ALL ENTRIES IN @lt_key
  WHERE key1 = @lt_key-key1
  INTO TABLE @DATA(lt_result).
```

지적 이유:

```text
SELECT * 사용
Empty Check 여부 불명확
기준 키 부족 가능성
대량 테이블 성능 위험
중복 제거 여부 불명확
```

## 17. FOR ALL ENTRIES와 JOIN의 관계

이번 모듈에서는 `FOR ALL ENTRIES` 자체의 안전한 사용 기준을 다룬다.  
하지만 실무에서는 항상 다음 질문이 함께 따라온다.

```text
이 조회는 JOIN으로 처리하는 것이 더 좋은가?
아니면 FOR ALL ENTRIES가 더 적절한가?
```

간단히 보면 다음과 같다.

| 상황 | 우선 검토 |
|---|---|
| DB 테이블 간 명확한 관계 조회 | JOIN |
| ABAP 내부 처리 결과가 조회 조건 | FOR ALL ENTRIES 가능 |
| 기준 데이터가 매우 작고 명확함 | FOR ALL ENTRIES 가능 |
| 기준 데이터가 크고 단순 테이블 관계 | JOIN 또는 다른 방식 검토 |
| 조회 후 복잡한 Application Logic 필요 | 상황별 판단 |

최종 선택 기준은 다음 모듈에서 더 자세히 다룬다.

## 19. 평가 문제

### 19.1 객관식

#### Q1. `FOR ALL ENTRIES` 사용 전 반드시 확인해야 하는 것은?

A. 화면 타이틀  
B. 기준 내부 테이블이 비어 있지 않은지  
C. 프로그램 이름이 8자리인지  
D. ALV Layout이 저장되었는지  

**정답:** B

#### Q2. 기준 내부 테이블의 중복 키를 줄이기 위해 사용하는 대표 구문은?

A. `SORT`와 `DELETE ADJACENT DUPLICATES`  
B. `WRITE`와 `ULINE`  
C. `PARAMETERS`와 `SELECT-OPTIONS`  
D. `MESSAGE`와 `LEAVE PROGRAM`  

**정답:** A

#### Q3. `FOR ALL ENTRIES`와 함께 무조건 권장되는 조회 방식은?

A. 항상 `SELECT *` 사용  
B. 필요한 컬럼만 명시적으로 선택  
C. WHERE 조건 생략  
D. Empty Table Check 생략  

**정답:** B

### 19.2 서술형

#### Q1. `FOR ALL ENTRIES` 기준 내부 테이블이 비어 있을 때 왜 위험한지 설명하시오.

**모범 답안:**  
기준 내부 테이블이 비어 있으면 의도한 조건이 적용되지 않아 매우 많은 데이터가 조회될 수 있다. 실무에서는 전체 테이블 조회로 이어질 수 있으므로 반드시 `IF lt_key IS NOT INITIAL`로 실행 여부를 제어해야 한다.

#### Q2. `FOR ALL ENTRIES` 전에 중복 제거가 필요한 이유를 설명하시오.

**모범 답안:**  
기준 내부 테이블에 같은 키가 여러 번 있으면 불필요한 조회 조건이 반복되어 SQL 처리량과 성능에 악영향을 줄 수 있다. 따라서 기준 키 기준으로 정렬한 뒤 `DELETE ADJACENT DUPLICATES`로 중복을 제거하는 것이 좋다.

#### Q3. `JOIN`과 `FOR ALL ENTRIES`의 관계를 간단히 설명하시오.

**모범 답안:**  
두 방식 모두 여러 데이터 집합을 연결하거나 기준 집합을 사용해 조회하는 데 쓰일 수 있다. 단순한 DB 테이블 간 관계 조회는 JOIN이 더 자연스러울 수 있고, ABAP 내부 처리 결과를 기준으로 DB를 다시 조회해야 하는 경우에는 `FOR ALL ENTRIES`를 검토할 수 있다.

## 20. 실무 체크리스트

`FOR ALL ENTRIES`를 작성하거나 리뷰할 때 다음 체크리스트를 사용한다.

| 체크 | 항목 |
|---|---|
| [ ] | 기준 내부 테이블이 명확한가 |
| [ ] | 기준 내부 테이블 Empty Check가 있는가 |
| [ ] | 기준 키 기준으로 중복 제거를 했는가 |
| [ ] | WHERE 조건이 충분히 구체적인가 |
| [ ] | 불필요한 `SELECT *`를 피했는가 |
| [ ] | 결과 건수가 예상 범위인지 확인했는가 |
| [ ] | JOIN으로 대체 가능한 단순 조회는 아닌지 검토했는가 |
| [ ] | 대량 데이터에서 위험하지 않은지 검토했는가 |

## 21. 핵심 요약

```text
FOR ALL ENTRIES는 내부 테이블 값을 기준으로 DB 테이블을 조회하는 Open SQL 기능이다.
기준 내부 테이블이 비어 있으면 전체 조회 위험이 있으므로 반드시 Empty Table Check를 한다.
기준 내부 테이블의 중복 키는 SORT와 DELETE ADJACENT DUPLICATES로 제거한다.
WHERE 조건에는 충분한 비교 필드를 넣어 조회 범위를 명확히 한다.
SELECT * 대신 필요한 컬럼만 조회한다.
JOIN으로 단순하게 해결되는 조회는 JOIN을 먼저 검토한다.
```
