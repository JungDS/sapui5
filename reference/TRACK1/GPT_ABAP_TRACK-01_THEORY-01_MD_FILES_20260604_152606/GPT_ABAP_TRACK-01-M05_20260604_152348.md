## 3. Transparent Table이란 무엇인가?

### 3.1 쉬운 정의

Transparent Table은 ABAP Dictionary에서 정의하는 데이터베이스 테이블이다.  
개발자는 SAP GUI의 `SE11` 또는 ADT를 통해 테이블 필드, Key, 데이터 타입, 설명 등을 정의한다.  
활성화가 완료되면 ABAP 프로그램에서 Open SQL을 사용해 해당 테이블의 데이터를 조회하거나 저장할 수 있다.

간단히 말하면 다음과 같다.

```text
Transparent Table = SAP 시스템에서 업무 데이터를 실제로 저장하기 위한 DDIC 테이블 객체
```

예를 들어 교육용 사용자 정보를 저장하는 테이블을 만든다고 가정하자.

| 필드 | 의미 | 예시 값 |
|---|---|---|
| MANDT | Client | 100 |
| USER_ID | 사용자 ID | U0001 |
| USER_NAME | 사용자명 | Kim Developer |
| STATUS | 사용자 상태 | A |

이런 데이터를 실제로 저장하려면 Structure만으로는 부족하다.  
Structure는 타입 정의일 뿐이고, 실제 데이터 저장 공간은 아니다.  
데이터를 DB에 저장하려면 Transparent Table 같은 데이터베이스 테이블 객체가 필요하다.

---

## 4. Structure와 Transparent Table의 차이

앞선 모듈에서 배운 Structure와 이번 모듈의 Transparent Table은 겉으로 보면 둘 다 필드 목록을 가진다.  
하지만 목적은 완전히 다르다.

| 구분 | Structure | Transparent Table |
|---|---|---|
| 객체 성격 | 데이터 타입 | 데이터베이스 테이블 |
| 실제 DB 저장 | 하지 않음 | 함 |
| Key Field | 일반적으로 없음 | 반드시 설계 필요 |
| Client Field | 보통 없음 | 업무 테이블에서는 일반적으로 사용 |
| 사용 위치 | 프로그램 변수, Internal Table Line Type, ALV 출력 구조 등 | Open SQL 조회, INSERT, UPDATE, DELETE 대상 |
| 데이터 지속성 | 프로그램 실행 중 메모리 | DB에 저장되어 프로그램 종료 후에도 유지 |

### 4.1 Structure가 적합한 경우

Structure는 다음과 같은 경우 적합하다.

```text
ALV 출력용 필드 묶음
Function Module 파라미터 구조
Method 입출력 구조
Screen 입출력 구조
Internal Table의 Line Type
```

### 4.2 Transparent Table이 적합한 경우

Transparent Table은 다음과 같은 경우 적합하다.

```text
업무 데이터를 저장해야 할 때
프로그램 종료 후에도 데이터가 남아야 할 때
여러 사용자가 같은 데이터를 조회하거나 변경해야 할 때
Open SQL로 조회할 대상이 필요할 때
```

### 4.3 초급자 판단 기준

초급자는 다음 질문으로 판단하면 된다.

```text
이 데이터가 프로그램 실행 중에만 필요하다면? → Structure 또는 Internal Table
이 데이터가 DB에 저장되어 계속 남아야 한다면? → Transparent Table
```

## 5. Transparent Table의 기본 구성 요소

Transparent Table은 최소한 다음 요소를 가진다.

| 구성 요소 | 설명 |
|---|---|
| Table Name | 테이블 객체명. 고객 개발 객체는 보통 `Z` 또는 `Y`로 시작한다. |
| Short Description | 테이블의 목적을 설명하는 짧은 텍스트 |

이번 모듈에서는 특히 다음 두 가지를 집중적으로 본다.

```text
Key Field
Client Field
```

## 6. Key Field란 무엇인가?

### 6.1 쉬운 정의

Key Field는 테이블에서 한 건의 데이터를 식별하기 위해 사용하는 필드이다.

예를 들어 다음 데이터가 있다고 하자.

| USER_ID | USER_NAME | STATUS |
|---|---|---|
| U0001 | Kim Developer | A |
| U0002 | Lee Consultant | I |
| U0003 | Park Admin | A |

여기서 `USER_ID`가 중복되지 않는다면, `USER_ID`만으로 한 사용자를 구분할 수 있다.  
이때 `USER_ID`는 Key Field 후보가 된다.

SAP의 Client-dependent 업무 테이블에서는 보통 `MANDT`와 업무 식별 필드를 함께 Key로 사용한다.

```text
MANDT + USER_ID
```

### 6.2 Key Field가 필요한 이유

Key Field가 필요한 이유는 다음과 같다.

| 이유 | 설명 |
|---|---|
| 유일성 보장 | 같은 Key 값을 가진 데이터가 중복 저장되는 것을 방지한다. |
| 조회 기준 제공 | 특정 데이터를 빠르게 찾을 수 있는 기준이 된다. |
| 변경 기준 제공 | UPDATE, DELETE 시 어떤 행을 변경할지 판단하는 기준이 된다. |
| 업무 의미 명확화 | 데이터 한 건의 식별 기준을 모델링 단계에서 명확히 한다. |

### 6.3 Key 설계의 기본 원칙

초급 단계에서는 다음 원칙을 기억한다.

1. Key는 한 건의 데이터를 유일하게 식별해야 한다.
2. Key는 너무 많아지면 안 된다.
3. Key는 자주 바뀌지 않는 값을 사용해야 한다.
4. Client-dependent 테이블에서는 일반적으로 `MANDT`가 첫 번째 Key Field가 된다.
5. 이름이나 설명처럼 바뀔 수 있는 필드는 Key로 두지 않는 것이 일반적이다.

### 6.4 나쁜 Key 설계 예

```text
MANDT + USER_ID + USER_NAME + STATUS
```

위 설계는 초급자가 종종 하는 실수이다.  
모든 필드를 Key로 지정하면 데이터 변경이 어려워지고, 한 건의 식별 기준이 불명확해진다.

더 적절한 설계는 다음과 같다.

```text
MANDT + USER_ID
```

그리고 `USER_NAME`, `STATUS`는 일반 필드로 둔다.

## 7. Client Field란 무엇인가?

### 7.1 Client의 의미

SAP 시스템은 하나의 시스템 안에서 여러 논리 영역을 Client로 분리할 수 있다.  
예를 들어 같은 개발 서버 안에도 `100`, `200`, `300` 같은 Client가 존재할 수 있다.

초급자는 Client를 다음처럼 이해하면 된다.

```text
Client = SAP 시스템 안에서 데이터를 논리적으로 분리하는 단위
```

일반적인 업무 테이블은 Client별로 데이터가 분리되어야 한다.  
그래서 많은 업무 테이블의 첫 번째 필드는 `MANDT`이다.

### 7.2 MANDT 필드

`MANDT`는 Client를 저장하는 표준 필드이다.

| 항목 | 일반적 값 |
|---|---|
| Field Name | MANDT |
| Data Element | MANDT |
| Data Type | CLNT |
| Length | 3 |
| Key 여부 | Yes |
| 위치 | 일반적으로 첫 번째 필드 |

`MANDT`는 직접 업무 사용자가 입력하는 값이라기보다, SAP 시스템의 Client 처리와 관련된 필드이다.

### 7.3 Client-dependent Table

`MANDT` 필드를 가진 테이블은 일반적으로 Client-dependent Table로 이해할 수 있다.  
Client-dependent Table은 Client별로 데이터가 분리된다.

예를 들어 같은 `USER_ID = U0001`이라도 Client가 다르면 별개의 데이터로 취급될 수 있다.

| MANDT | USER_ID | USER_NAME |
|---|---|---|
| 100 | U0001 | Kim Developer |
| 200 | U0001 | Kim Developer Test |

### 7.4 Open SQL에서의 Client 처리 기본 감각

ABAP Open SQL은 Client-dependent Table에 대해 일반적으로 현재 Client 기준의 처리를 제공한다.  
초급자는 이 단계에서 다음 정도만 이해하면 충분하다.

```text
MANDT가 있는 테이블은 Client별 데이터 분리를 고려해야 한다.
일반적인 조회에서는 현재 로그인 Client의 데이터만 다루는 흐름으로 이해한다.
Client를 임의로 넘나드는 처리는 초급 단계에서 다루지 않는다.
```

Client를 명시적으로 다루는 고급 문법이나 운영 이슈는 후속 학습에서 다루는 것이 적절하다.

## 8. 실습 시나리오

### 8.1 업무 가정

교육용으로 간단한 사용자 마스터 테이블을 만든다.  
이 테이블은 사용자 ID, 사용자명, 상태를 저장한다.

업무 요구사항은 다음과 같다.

```text
사용자 ID는 Client 안에서 중복되면 안 된다.
사용자명은 변경될 수 있다.
사용자 상태는 A, I, B 중 하나를 사용한다.
생성자와 생성일은 기록한다.
```

### 8.2 생성할 테이블

```text
Table Name: ZT_JHY_USER
Short Description: Training User Master Table
```

### 8.3 사용할 기존 DDIC 객체

앞선 모듈에서 생성했다고 가정하는 객체는 다음과 같다.

| 객체 | 목적 |
|---|---|
| `ZD_JHY_STATUS` | 사용자 상태의 기술 속성 정의 |
| `ZDE_JHY_STATUS` | 사용자 상태의 업무 의미 정의 |
| `ZDE_JHY_USER_ID` | 사용자 ID의 업무 의미 정의 |
| `ZDE_JHY_USER_NAME` | 사용자명의 업무 의미 정의 |
| `ZS_JHY_USER_INFO` | 사용자 정보 Structure |

[추정] 실제 실습 시스템의 명명 규칙이 다르면 강사 또는 프로젝트 규칙에 맞게 `JHY` 부분을 변경해도 된다.

## 9. 테이블 필드 설계

이번 실습 테이블의 필드는 다음과 같이 설계한다.

| 순서 | Field | Key | Data Element | 설명 |
|---:|---|---|---|---|
| 1 | MANDT | X | MANDT | Client |
| 2 | USER_ID | X | ZDE_JHY_USER_ID | 사용자 ID |
| 3 | USER_NAME |  | ZDE_JHY_USER_NAME | 사용자명 |
| 4 | STATUS |  | ZDE_JHY_STATUS | 사용자 상태 |
| 5 | CREATED_BY |  | SYUNAME | 생성자 |
| 6 | CREATED_ON |  | DATS | 생성일 |

### 9.1 왜 `MANDT`와 `USER_ID`가 Key인가?

이 테이블에서는 같은 Client 안에서 `USER_ID`가 한 사용자를 식별한다.  
따라서 Client까지 포함하면 다음 조합이 한 건을 식별하는 Key가 된다.

```text
MANDT + USER_ID
```

### 9.2 왜 `USER_NAME`은 Key가 아닌가?

사용자명은 바뀔 수 있다.  
예를 들어 이름 표기 방식이 바뀌거나, 설명명이 변경될 수 있다.  
바뀔 수 있는 필드를 Key로 사용하면 데이터 변경과 연관 처리에 불필요한 제약이 생긴다.

### 9.3 왜 `STATUS`는 Key가 아닌가?

상태는 사용자의 현재 상태를 나타내는 속성이다.  
사용자를 식별하는 기준이 아니라 사용자의 현재 값을 설명하는 필드이다.  
따라서 일반 필드로 두는 것이 적절하다.

## 10. SE11에서 Transparent Table 생성 절차

### 10.1 SE11 실행

SAP GUI에서 다음 트랜잭션을 실행한다.

```text
SE11
```

`Database Table` 영역에 테이블명을 입력한다.

```text
ZT_JHY_USER
```

이후 `Create`를 선택한다.

### 10.2 Short Description 입력

다음과 같이 테이블 설명을 입력한다.

```text
Training User Master Table
```

Short Description은 단순 장식이 아니다.  
SE11, Repository 검색, 개발자 간 커뮤니케이션에서 객체의 목적을 빠르게 파악하는 기준이 된다.

### 10.3 Delivery Class 설정

교육용 실습에서는 시스템 상황에 따라 다음 중 하나를 사용할 수 있다.

| Delivery Class | 의미 | 교육용 사용 관점 |
|---|---|---|
| A | Application Table | 일반 업무 데이터 테이블로 설명하기 쉬움 |
| C | Customizing Table | 설정성 데이터 예제에 적합 |

이번 실습은 사용자 마스터 성격의 교육용 테이블이므로 `A`를 기준 예시로 둔다.

```text
Delivery Class: A
```

단, 실제 프로젝트에서는 Delivery Class가 CTS, 운영 데이터 관리, 테이블 유지보수 정책과 연결되므로 프로젝트 기준을 따라야 한다.

### 10.4 Data Browser/Table View Maint. 설정

초급 실습에서는 화면에 보이는 옵션의 의미를 다음 수준으로만 이해한다.

| 설정 항목 | 의미 |
|---|---|
| Display/Maintenance Allowed | Data Browser 또는 Table Maintenance 관련 허용 여부에 영향을 준다. |
| Display/Maintenance Not Allowed | 직접 조회/유지보수를 제한한다. |

이번 모듈의 핵심은 Table 구조 생성이므로, 데이터 입력과 조회는 다음 모듈에서 별도로 확인한다.

### 10.5 Fields 탭으로 이동

Fields 탭에서 필드를 순서대로 입력한다.

| Field | Key | Data Element |
|---|---|---|
| MANDT | X | MANDT |
| USER_ID | X | ZDE_JHY_USER_ID |
| USER_NAME |  | ZDE_JHY_USER_NAME |
| STATUS |  | ZDE_JHY_STATUS |
| CREATED_BY |  | SYUNAME |
| CREATED_ON |  | DATS |

`MANDT`는 일반적으로 첫 번째 필드에 둔다.  
`MANDT`와 `USER_ID`는 Key 체크를 한다.

### 10.6 Currency/Quantity 필드가 있을 때의 주의

이번 실습 테이블에는 금액이나 수량 필드가 없다.  
하지만 실무 테이블에는 `CURR`, `QUAN` 타입 필드가 자주 등장한다.

이런 필드는 일반적으로 통화 키 또는 단위 필드와 연결되어야 한다.  
초급 단계에서는 다음 정도만 기억한다.

```text
금액 필드만 단독으로 두지 않는다.
수량 필드만 단독으로 두지 않는다.
통화/단위 참조 필드가 필요할 수 있다.
```

이 주제는 DDIC 심화나 실제 업무 테이블 설계에서 다시 다루는 것이 적절하다.

### 10.7 저장

객체를 저장한다.

교육용 시스템에서는 보통 다음 중 하나를 선택한다.

| 저장 위치 | 의미 |
|---|---|
| Local Object `$TMP` | Transport 없이 로컬 실습용으로 사용 |
| Package `Z...` | Transport 가능한 개발 객체로 관리 |

초급 실습에서는 시스템 정책에 따라 강사가 지정한 방식을 따른다.

### 10.8 Enhancement Category 설정

Transparent Table 활성화 과정에서 Enhancement Category 설정을 요구받을 수 있다.  
실습에서는 다음과 같은 의미로 이해하면 된다.

```text
이 테이블 구조가 향후 Append Structure 등으로 확장될 수 있는지에 대한 분류
```

교육용 단순 테이블에서는 시스템에서 요구하는 기본 선택지를 사용하되, 실제 프로젝트에서는 확장 가능성과 운영 정책을 고려해야 한다.

### 10.9 Technical Settings 입력

Transparent Table은 활성화 전에 Technical Settings가 필요할 수 있다.  
그러나 이 주제는 다음 모듈 `THEORY-01-M06`의 핵심 주제이다.

이번 모듈에서는 다음 정도만 이해한다.

```text
Technical Settings는 DB 저장 방식과 성능/크기 관련 설정이다.
Transparent Table 생성 과정에서 필요한 필수 설정일 수 있다.
상세 의미와 검증은 다음 모듈에서 다룬다.
```

실습 시스템에서 활성화를 위해 최소 입력이 필요하다면 다음 예시를 사용할 수 있다.

| 항목 | 교육용 예시 |
|---|---|
| Data Class | APPL0 또는 시스템 교육 기준값 |
| Size Category | 0 |
| Buffering | Buffering not allowed 또는 비활성 |

[추정] 교육 시스템마다 기본값, 권장값, 권한 정책이 다를 수 있으므로 강사 또는 시스템 관리자 기준을 우선한다.

### 10.10 Activate

모든 필수 항목을 입력한 뒤 Activate한다.

활성화는 다음 의미를 가진다.

```text
ABAP Dictionary 정의를 런타임과 데이터베이스 사용 가능 상태로 반영하는 과정
```

활성화가 성공해야 ABAP 프로그램에서 다음과 같이 테이블을 참조할 수 있다.

```abap
SELECT *
  FROM zt_jhy_user
  INTO TABLE @DATA(lt_user).
```

Open SQL 자체는 후속 모듈에서 자세히 학습하므로, 여기서는 “Transparent Table은 ABAP SQL의 대상이 될 수 있다”는 정도만 이해한다.

## 11. 테이블 생성 후 확인할 항목

Transparent Table을 생성한 뒤에는 최소한 다음을 확인한다.

| 확인 항목 | 확인 내용 |
|---|---|
| Object Active 여부 | 테이블이 활성화되었는가? |
| Field 순서 | `MANDT`가 첫 번째 필드인가? |
| Key 지정 | `MANDT`, `USER_ID`가 Key인가? |
| Data Element 연결 | 각 필드가 의도한 Data Element를 참조하는가? |
| Short Description | 테이블 목적이 설명되어 있는가? |
| Enhancement Category | 설정 누락 경고가 없는가? |
| Technical Settings | 활성화에 필요한 최소 설정이 되었는가? |

초급자는 활성화 성공만 보고 끝내지 말고, 필드와 Key가 의도대로 들어갔는지 반드시 다시 확인해야 한다.

## 12. 정상 흐름과 오류 흐름

### 12.1 정상 흐름

정상적인 Transparent Table 생성 흐름은 다음과 같다.

```text
1. 테이블명 입력
2. Short Description 입력
3. Delivery Class 설정
4. Fields 탭에서 필드 입력
5. Key Field 지정
6. MANDT를 첫 번째 Key Field로 입력
7. Enhancement Category 설정
8. Technical Settings 최소 입력
9. Save
10. Activate
11. 활성화 결과 확인
```

### 12.2 오류 흐름 1: Key Field를 지정하지 않음

#### 상황

테이블 필드를 입력했지만 Key 체크를 하지 않았다.

#### 문제

Transparent Table은 데이터 한 건을 식별할 기준이 필요하다.  
Key가 없으면 테이블 설계 의도가 불명확해지고 활성화 과정에서 오류 또는 경고가 발생할 수 있다.

#### 해결

데이터 한 건을 유일하게 식별하는 필드를 Key로 지정한다.

이번 실습에서는 다음 조합을 Key로 둔다.

```text
MANDT + USER_ID
```

### 12.3 오류 흐름 2: MANDT를 누락함

#### 상황

업무 데이터 테이블을 만들면서 `MANDT` 필드를 넣지 않았다.

#### 문제

Client별 데이터 분리가 필요한 테이블인데 `MANDT`가 없으면 Cross-client 성격의 테이블이 된다.  
교육용 단순 실습에서는 지나칠 수 있지만, 실무 업무 테이블에서는 큰 설계 문제가 될 수 있다.

#### 해결

Client-dependent 업무 테이블이라면 일반적으로 첫 번째 필드에 다음을 추가한다.

```text
Field: MANDT
Key: X
Data Element: MANDT
```

### 12.4 오류 흐름 3: MANDT 위치가 부적절함

#### 상황

`MANDT`를 넣었지만 첫 번째 필드가 아니라 중간이나 마지막에 넣었다.

#### 문제

SAP 표준 관행상 Client Field는 일반적으로 첫 번째 Key Field로 설계한다.  
초급 교육에서는 이 관행을 따라야 이후 표준 테이블을 읽을 때 혼란이 줄어든다.

#### 해결

필드 순서를 조정한다.

```text
1. MANDT
2. 업무 Key Field
3. 일반 속성 필드
```

### 12.5 오류 흐름 4: 존재하지 않는 Data Element를 입력함

#### 상황

`ZDE_JHY_USER_ID`를 입력했지만 아직 생성하지 않았거나 활성화하지 않았다.

#### 문제

Table Field가 참조할 타입 정보를 찾을 수 없다.

#### 해결

다음 순서를 확인한다.

```text
1. Domain 생성 및 Activate
2. Data Element 생성 및 Activate
3. Transparent Table에서 Data Element 참조
4. Transparent Table Activate
```

### 12.6 오류 흐름 5: 모든 필드를 Key로 지정함

#### 상황

초급자가 중복을 막기 위해 모든 필드에 Key를 체크했다.

#### 문제

`USER_NAME`, `STATUS`, `CREATED_BY`, `CREATED_ON`까지 Key가 되면 한 건의 식별 기준이 과도하게 넓어진다.  
또한 상태나 이름 변경이 어려워질 수 있다.

#### 해결

Key는 최소 식별 기준만 둔다.

```text
좋은 예: MANDT + USER_ID
나쁜 예: MANDT + USER_ID + USER_NAME + STATUS + CREATED_BY + CREATED_ON
```

### 12.7 오류 흐름 6: Technical Settings 누락

#### 상황

테이블 필드를 모두 입력했지만 활성화 시 Technical Settings 관련 메시지가 발생한다.

#### 문제

Transparent Table은 DB에 생성되는 객체이므로 기술 설정이 필요할 수 있다.

#### 해결

교육용 최소 설정을 입력하되, 상세 의미는 다음 모듈에서 학습한다.

```text
Data Class
Size Category
Buffering
```

## 13. 실무 설계 기준

### 13.1 Z Table을 만들기 전에 먼저 질문해야 할 것

실무에서 개발자가 바로 Z Table을 만드는 것은 바람직하지 않을 수 있다.  
먼저 다음 질문을 해야 한다.

```text
이미 SAP 표준 테이블에 저장되는 데이터인가?
표준 Extension이나 Customizing으로 해결 가능한가?
임시 데이터라면 DB 테이블이 아니라 Internal Table로 충분한가?
여러 프로그램에서 영구 저장해야 하는 데이터인가?
운영 중 누가 생성/변경/삭제할 데이터인가?
권한, 감사, 이력 관리가 필요한가?
```

초급자는 Z Table 생성 방법을 배워야 하지만, 실무자는 Z Table이 정말 필요한지도 판단해야 한다.

### 13.2 테이블명은 목적을 드러내야 한다

나쁜 예:

```text
ZT_TEST
ZT_TEMP
ZT_DATA
ZT_001
```

좋은 예:

```text
ZT_JHY_USER
ZT_JHY_USER_LOG
ZT_JHY_CARR_CFG
```

교육용 이름은 단순해도 되지만, 실무에서는 이름만 보고도 데이터 성격을 추정할 수 있어야 한다.

### 13.3 필드명은 업무 의미를 드러내야 한다

나쁜 예:

```text
FIELD1
FIELD2
CODE
TEXT
VALUE
```

좋은 예:

```text
USER_ID
USER_NAME
STATUS
CREATED_BY
CREATED_ON
```

필드명은 ABAP 코드와 SQL 조회에서 계속 사용되므로, 처음부터 명확하게 설계하는 것이 중요하다.

### 13.4 Key는 업무 식별 기준이다

Key는 단순히 “중복을 막기 위한 체크박스”가 아니다.  
업무적으로 데이터 한 건을 무엇으로 식별할 것인지 결정하는 설계 행위이다.

따라서 Key 설계에는 다음 관점이 필요하다.

| 관점 | 질문 |
|---|---|
| 유일성 | 이 조합으로 한 건이 유일하게 식별되는가? |
| 안정성 | 이 값은 자주 바뀌지 않는가? |
| 최소성 | 불필요한 필드가 Key에 포함되지 않았는가? |
| 업무성 | 업무 사용자가 이해할 수 있는 식별 기준인가? |

### 13.5 Client Field를 무의식적으로 빼지 않는다

실무 업무 데이터는 대부분 Client 종속성을 가진다.  
따라서 교육 초기에는 다음을 기본 관행으로 익히는 것이 좋다.

```text
업무 데이터 Z Table을 만들 때는 먼저 MANDT가 필요한지 검토한다.
필요하다면 MANDT를 첫 번째 Key Field로 둔다.
```

단, 모든 테이블이 반드시 Client-dependent인 것은 아니다.  
Cross-client 설정이나 시스템 공통 데이터처럼 특수한 경우도 있지만, 초급 과정에서는 예외를 일반화하지 않는다.

### 13.6 표준 테이블을 직접 변경하지 않는다

SAP 표준 테이블은 고객 개발자가 마음대로 필드를 추가하거나 변경하는 대상이 아니다.  
확장이 필요하면 표준 Enhancement, Append Structure, Extension Framework 등 적절한 방식을 검토해야 한다.

이번 모듈에서는 고객 개발용 Z Table을 만드는 방법만 학습한다.

## 14. 최소 ABAP 사용 예고

Transparent Table을 만들면 ABAP 프로그램에서 Open SQL의 대상이 될 수 있다.  
다음 코드는 이번 모듈의 이해를 돕기 위한 예고 수준의 예제이다.

```abap
REPORT zjhy_read_user.

SELECT user_id,
       user_name,
       status
  FROM zt_jhy_user
  INTO TABLE @DATA(lt_user).

LOOP AT lt_user INTO DATA(ls_user).
  WRITE: / ls_user-user_id,
           ls_user-user_name,
           ls_user-status.
ENDLOOP.
```

이 예제에서 중요한 점은 SQL 문법 자체가 아니다.  
이번 모듈에서는 다음 사실만 이해하면 된다.

```text
Transparent Table은 ABAP 프로그램에서 조회할 수 있는 실제 데이터 저장 객체이다.
```

Open SQL의 상세 문법, WHERE 조건, 성능, JOIN, 집계는 후속 Section에서 단계적으로 다룬다.

## 16. 강사용 설명 포인트

강사는 이번 모듈에서 다음 메시지를 반복해서 강조하면 좋다.

### 16.1 “테이블 생성”은 단순 화면 조작이 아니다

초급자는 SE11 화면에서 필드를 입력하는 행위만 기억하기 쉽다.  
하지만 실무에서 중요한 것은 다음 판단이다.

```text
무엇을 Key로 둘 것인가?
Client별로 분리해야 하는가?
어떤 Data Element를 재사용할 것인가?
이 데이터는 정말 DB에 저장해야 하는가?
```

### 16.2 `MANDT`는 외워서 넣는 필드가 아니다

`MANDT`는 단순히 “첫 번째 줄에 넣는 필드”가 아니다.  
Client별 데이터 분리와 연결된 중요한 설계 요소이다.

### 16.3 모든 Z Table이 좋은 설계는 아니다

초급 실습에서는 Z Table을 만들어야 학습이 가능하지만, 실무에서는 Z Table 남발이 유지보수 부담이 될 수 있다.

### 16.4 후속 학습과 연결한다

이번 모듈에서 만든 Transparent Table은 이후 다음 주제와 연결된다.

| 후속 주제 | 연결 방식 |
|---|---|
| Technical Settings | 테이블 저장/성능 설정을 이해한다. |
| Data Browser | 생성한 테이블의 데이터를 조회한다. |
| Open SQL | 테이블 데이터를 ABAP 프로그램에서 읽는다. |
| Internal Table | DB 조회 결과를 메모리에서 가공한다. |
| ALV | 테이블 데이터를 화면에 리스트로 보여준다. |
| CDS | DB 테이블 위에 의미 있는 View를 만든다. |
| RAP | 테이블과 CDS를 기반으로 비즈니스 객체를 만든다. |

## 18. 평가 문제

### 18.1 객관식

#### Q1. Transparent Table에 대한 설명으로 가장 적절한 것은?

A. 프로그램 실행 중에만 존재하는 로컬 변수이다.  
B. ABAP Dictionary에서 정의되고 실제 데이터 저장과 연결되는 테이블 객체이다.  
C. 화면 출력 전용 라벨 모음이다.  
D. 검색 도움말만 제공하는 객체이다.

**정답:** B

#### Q2. Client-dependent 업무 테이블에서 일반적으로 첫 번째 Key Field로 사용하는 필드는?

A. USER_ID  
B. STATUS  
C. MANDT  
D. CREATED_ON

**정답:** C

#### Q3. Key Field 설계 기준으로 적절하지 않은 것은?

A. 한 건을 유일하게 식별해야 한다.  
B. 가능하면 모든 필드를 Key로 지정해야 한다.  
C. 자주 바뀌지 않는 값이 적합하다.  
D. Client-dependent 테이블에서는 MANDT를 고려해야 한다.

**정답:** B

### 18.2 서술형

#### Q1. Structure와 Transparent Table의 차이를 설명하시오.

**모범 답안:**  
Structure는 여러 필드를 묶은 데이터 타입이며 실제 DB에 데이터를 저장하지 않는다. Transparent Table은 ABAP Dictionary에 정의되는 데이터베이스 테이블 객체로, 활성화 후 실제 데이터 저장과 Open SQL 조회 대상이 될 수 있다.

#### Q2. `MANDT + USER_ID`를 Key로 설계하는 이유를 설명하시오.

**모범 답안:**  
`MANDT`는 Client별 데이터 분리를 위한 필드이고, `USER_ID`는 해당 Client 안에서 사용자를 식별하는 업무 Key이다. 두 필드를 함께 사용하면 Client별로 사용자 데이터를 유일하게 식별할 수 있다.

#### Q3. 모든 필드를 Key로 지정하면 왜 문제가 되는가?

**모범 답안:**  
Key는 데이터 한 건을 식별하는 최소 기준이어야 한다. 모든 필드를 Key로 지정하면 변경 가능한 속성까지 식별 기준에 포함되어 데이터 변경이 어려워지고, 테이블의 업무 식별 의미가 불명확해진다.

## 20. 핵심 요약

이번 모듈의 핵심은 다음과 같다.

```text
Transparent Table은 실제 데이터를 저장할 수 있는 ABAP Dictionary 테이블 객체이다.
Structure는 타입이고, Transparent Table은 저장 객체이다.
Key Field는 데이터 한 건의 식별 기준이다.
Client-dependent 업무 테이블에서는 일반적으로 MANDT가 첫 번째 Key Field가 된다.
Z Table을 만들 때는 이름, Key, Client, Data Element, 활성화 오류를 함께 고려해야 한다.
```

초급자는 이번 모듈을 통해 “테이블을 만든다”는 표현이 단순 화면 조작이 아니라 데이터 모델링의 출발점이라는 점을 이해해야 한다.
