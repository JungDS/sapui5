## 4. Data Element란 무엇인가?

Data Element는 ABAP Dictionary에서 **데이터 필드의 업무적 의미를 정의하는 객체**이다.

Domain이 “값이 어떤 기술적 형식을 가지는가?”에 답한다면, Data Element는 “그 값이 업무적으로 무엇을 의미하는가?”에 답한다.

예를 들어 `CHAR 1`이라는 기술 타입만 놓고 보면 다음 필드들은 모두 같은 형태일 수 있다.

| 기술 타입 | 가능한 업무 의미 |
|---|---|
| CHAR 1 | 사용자 상태 |
| CHAR 1 | 삭제 여부 |
| CHAR 1 | 승인 상태 |
| CHAR 1 | 사용 여부 |
| CHAR 1 | 잠금 여부 |

기술 타입은 같지만, 업무 의미는 다르다.  
따라서 이들을 모두 같은 Data Element로 처리하면 화면 라벨, 문서화, 유지보수 기준이 섞이게 된다.

Data Element는 다음 정보를 제공한다.

| 정보 | 설명 |
|---|---|
| Short Description | Data Element 자체의 간단한 설명 |
| Domain 또는 Built-in Type | 기술 타입의 기반 |
| Field Label | 화면, 리스트, ALV 등에서 사용할 표시명 |
| Documentation | F1 Help 등에서 사용할 설명 문서 |
| Search Help 연결 | 입력 도움말 연결 가능 |

초급 단계에서는 우선 **Domain 연결 + Field Label 작성**을 핵심으로 이해하면 된다.

## 5. Domain과 Data Element의 차이

Domain과 Data Element는 함께 사용되지만 목적이 다르다.

| 구분 | Domain | Data Element |
|---|---|---|
| 주된 역할 | 기술적 속성 정의 | 업무 의미 정의 |
| 대표 질문 | 어떤 타입인가? 몇 자리인가? 어떤 값을 허용하는가? | 이 필드는 무엇을 의미하는가? 화면에 어떻게 표시할 것인가? |
| 예시 | `CHAR 1`, Fixed Value `A/I/B` | 사용자 상태, 승인 상태, 삭제 여부 |
| 포함 정보 | Data Type, Length, Decimal, Fixed Value, Lowercase | Field Label, Short Description, Documentation |
| 재사용 기준 | 기술 형식이 같을 때 | 업무 의미가 같을 때 |
| 후속 사용 | Data Element의 기술 기반 | Table Field, Structure Component, Program Type 등에서 참조 |

같은 Domain을 여러 Data Element가 공유할 수 있다.

예를 들어 다음처럼 설계할 수 있다.

| Domain | Data Element | 업무 의미 |
|---|---|---|
| `ZD_JHY_FLAG` | `ZDE_JHY_DELETE_FLAG` | 삭제 여부 |
| `ZD_JHY_FLAG` | `ZDE_JHY_ACTIVE_FLAG` | 활성 여부 |
| `ZD_JHY_FLAG` | `ZDE_JHY_APPROVAL_FLAG` | 승인 여부 |

세 Data Element가 모두 `CHAR 1`과 `X/space` 같은 기술 규칙을 공유하더라도, 업무 의미는 서로 다르다. 이때 Data Element를 분리하면 화면 라벨과 문서화를 의미에 맞게 관리할 수 있다.

## 6. Data Element가 필요한 이유

### 6.1 화면 표시명 일관성

SAP 화면, Selection Screen, ALV, Table Maintenance, F1 Help 등에서는 필드의 표시명이 필요하다. Data Element의 Field Label은 이러한 표시명의 표준 기반이 된다.

예를 들어 `ZDE_JHY_STATUS`에 다음 Field Label을 정의했다고 가정한다.

| Label 유형 | 값 |
|---|---|
| Short | Status |
| Medium | User Status |
| Long | User Account Status |
| Heading | Status |

이 Data Element를 여러 테이블과 구조에서 사용하면, 화면 표시명을 매번 새로 정하지 않아도 동일한 의미와 라벨을 재사용할 수 있다.

### 6.2 업무 의미의 중앙 관리

Data Element는 “이 필드가 어떤 업무 의미를 가지는가?”를 중앙에서 관리한다.

예를 들어 사용자 상태라는 의미가 여러 곳에서 사용된다고 가정한다.

```text
ZT_JHY_USER-STATUS
ZS_JHY_USER_INFO-STATUS
ABAP 변수 GV_STATUS
Selection Screen Parameter P_STATUS
```

모두 `ZDE_JHY_STATUS`를 참조하면 “사용자 상태”라는 의미가 일관되게 유지된다.

### 6.3 문서화와 F1 Help 기반

Data Element에는 Documentation을 작성할 수 있다. 이 Documentation은 사용자가 F1 Help를 통해 필드 의미를 확인할 때 활용될 수 있다.

초급 실습에서는 Documentation을 생략하기 쉽지만, 실무에서는 중요한 필드일수록 Data Element Documentation을 작성하는 것이 좋다.

예를 들어 `사용자 상태` 필드라면 다음과 같은 설명을 남길 수 있다.

```text
사용자 계정의 현재 상태를 나타낸다.
A = Active, I = Inactive, B = Blocked.
Blocked 상태의 사용자는 후속 업무 처리 대상에서 제외될 수 있다.
```

### 6.4 유지보수성과 영향 분석

Data Element를 사용하면 Where-Used List를 통해 이 의미 객체가 어디에서 사용되는지 확인할 수 있다.

예를 들어 `ZDE_JHY_STATUS`를 변경하려는 경우, 다음 항목들을 영향 분석할 수 있다.

| 사용 위치 | 예시 |
|---|---|
| Table Field | `ZT_JHY_USER-STATUS` |
| Structure Component | `ZS_JHY_USER_INFO-STATUS` |
| Program Variable | `DATA gv_status TYPE zde_jhy_status` |
| Search Help 연결 | 후속 DDIC 2차 Section에서 학습 |
| Screen Field | Dynpro 또는 Selection Screen |

SAP 개발에서는 필드 길이나 의미 변경이 여러 프로그램과 화면에 영향을 줄 수 있다. Data Element는 이런 영향을 추적하는 중요한 단위이다.

## 7. Field Label의 의미

Data Element의 가장 중요한 학습 포인트 중 하나는 Field Label이다.

Field Label은 SAP 화면이나 리스트에서 필드를 표시할 때 사용되는 텍스트이다. SAP GUI 800 기준 SE11의 Data Element 화면에서 Field Label 탭을 통해 입력할 수 있다.

| Field Label | 일반 길이 | 용도 |
|---|---:|---|
| Short | 10 | 짧은 화면 필드명, 공간이 좁은 화면 |
| Medium | 20 | 일반 화면 필드명 |
| Long | 40 | 상세 화면 또는 설명형 필드명 |
| Heading | 55 | 리스트/테이블 헤더용 텍스트 |

예시:

| Label 유형 | 값 |
|---|---|
| Short | Status |
| Medium | User Status |
| Long | User Account Status |
| Heading | Status |

### 7.1 라벨 작성 기준

Field Label은 개발자 약어보다 사용자가 이해할 수 있는 표현을 우선해야 한다.

| 나쁜 예 | 좋은 예 | 이유 |
|---|---|---|
| Stat | Status | 약어보다 명확한 단어 사용 |
| UStat | User Status | 의미가 명확함 |
| UsrActSts | User Account Status | 과도한 축약 방지 |
| DelFg | Deletion Flag | 업무 의미가 분명함 |

라벨은 화면에 노출될 수 있으므로, 초급자라도 처음부터 사용자 관점의 이름을 작성하는 습관을 들이는 것이 좋다.

### 7.2 라벨이 항상 그대로 표시되는 것은 아니다

Data Element의 Field Label은 기본 표시명의 원천이지만, 모든 화면에서 항상 그대로 표시된다고 단정하면 안 된다.

예를 들어 다음 경우에는 다른 텍스트가 표시될 수 있다.

| 상황 | 설명 |
|---|---|
| ALV Field Catalog에서 별도 텍스트 지정 | Data Element 라벨보다 Field Catalog 텍스트가 우선될 수 있음 |
| Dynpro Screen Painter에서 텍스트 직접 지정 | 화면 요소의 고정 텍스트가 사용될 수 있음 |
| CDS Annotation에서 라벨 지정 | UI Annotation의 라벨이 사용될 수 있음 |
| 다국어 번역 미관리 | 로그온 언어에 따라 텍스트가 다르게 보이거나 비어 보일 수 있음 |

따라서 Field Label은 “표준 표시명의 기준”이지, 모든 UI 텍스트를 강제로 결정하는 절대 규칙은 아니다.

## 8. Data Element의 기술 구조

Data Element는 보통 다음 구조로 이해할 수 있다.

```text
Data Element
  ├─ Short Description
  ├─ Elementary Type
  │    └─ Domain 또는 Built-in Type
  ├─ Field Label
  ├─ Documentation
  └─ Optional: Search Help 등 부가 설정
```

초급 실습에서는 다음 두 가지를 반드시 확인한다.

1. Data Element가 어떤 Domain을 참조하는가?
2. Field Label이 의미에 맞게 작성되었는가?

이번 실습에서는 다음 구조를 만든다.

```text
Domain:       ZD_JHY_STATUS
                 ↓
Data Element: ZDE_JHY_STATUS
                 ↓
향후 사용처:    Structure Component / Table Field / Program Variable
```

## 10. SE11에서 Data Element 생성 절차

### 10.1 Data Element 생성 화면 진입

1. SAP GUI에 로그인한다.
2. T-Code 입력창에 `SE11`을 입력한다.
3. `Data Type`을 선택한다.
4. 객체명에 `ZDE_JHY_STATUS`를 입력한다.
5. `Create` 버튼을 선택한다.
6. 생성 유형 선택 화면에서 `Data Element`를 선택한다.

### 10.2 기본 정보 입력

Data Element 화면에서 다음 값을 입력한다.

| 항목 | 값 |
|---|---|
| Short Description | `User Status` |
| Elementary Type | Domain 기준 |
| Domain | `ZD_JHY_STATUS` |

여기서 Domain을 입력하면 Data Element는 `ZD_JHY_STATUS`의 기술 속성을 상속받는다.

즉, `ZDE_JHY_STATUS`는 다음 기술 규칙을 갖게 된다.

| 속성 | 출처 | 값 |
|---|---|---|
| Data Type | Domain | CHAR |
| Length | Domain | 1 |
| Fixed Value | Domain | A/I/B |
| 업무 의미 | Data Element | User Status |
| Field Label | Data Element | Status / User Status 등 |

### 10.3 Field Label 입력

Field Label 탭으로 이동하여 다음 값을 입력한다.

| Label 유형 | 입력값 | 설명 |
|---|---|---|
| Short | `Status` | 공간이 좁은 화면용 |
| Medium | `User Status` | 일반 화면용 |
| Long | `User Account Status` | 상세 화면용 |
| Heading | `Status` | 리스트 헤더용 |

라벨을 입력할 때는 “개발자가 편한 이름”보다 “사용자가 이해할 수 있는 이름”을 우선한다.

### 10.4 저장과 패키지 지정

1. Save 버튼을 선택한다.
2. 패키지를 지정한다.
3. 교육용 로컬 실습이면 `$TMP`를 사용할 수 있다.
4. Transport 대상 실습이면 교육용 패키지 예: `ZEDU_ABAP_TRACK1`을 사용할 수 있다.

[추정] 실제 교육 시스템에서 패키지와 Transport Request 정책은 운영 환경과 강의용 시스템 설정에 따라 다를 수 있다. 로컬 실습에서는 `$TMP`가 가장 단순하다.

### 10.5 활성화

1. Activate 버튼을 선택한다.
2. 오류 메시지가 없으면 활성화 완료 상태를 확인한다.
3. 활성화 후 Data Element가 다른 DDIC 객체와 ABAP 프로그램에서 타입으로 참조 가능한 상태가 된다.

## 11. 활성화 후 검증

Data Element 생성 후에는 단순히 “저장되었다”로 끝내면 안 된다. 다음 기준으로 검증해야 한다.

| 검증 항목 | 확인 방법 | 정상 기준 |
|---|---|---|
| 객체 활성화 | SE11 상단 상태 또는 Activate 재실행 | 오류 없이 Active 상태 |
| Domain 연결 | Data Element의 Domain 필드 확인 | `ZD_JHY_STATUS` 연결 |
| Field Label | Field Label 탭 확인 | Short/Medium/Long/Heading 입력됨 |
| Where-Used 가능성 | Utilities 또는 Where-Used | 이후 사용처 확인 가능 |
| ABAP 타입 참조 | 간단한 프로그램에서 TYPE 참조 | Syntax Check 통과 |

### 11.1 간단한 ABAP 검증 예제

다음 코드는 Data Element가 ABAP 프로그램에서 타입으로 참조되는지 확인하기 위한 최소 예제이다.

```abap
REPORT zjhy_check_data_element.

DATA gv_status TYPE zde_jhy_status.

gv_status = 'A'.

WRITE: / 'User Status:', gv_status.
```

이 예제의 목적은 출력 품질이 아니라, `ZDE_JHY_STATUS`가 ABAP 타입으로 정상 인식되는지 확인하는 것이다.

### 11.2 PARAMETERS와의 연결 예고

Data Element는 Selection Screen 입력 필드에서도 사용될 수 있다.

```abap
REPORT zjhy_param_status.

PARAMETERS p_status TYPE zde_jhy_status.

WRITE: / 'Input Status:', p_status.
```

다만 PARAMETERS와 Selection Screen의 흐름은 후속 Section에서 별도로 다룬다. 여기서는 “Data Element가 화면 입력 필드의 의미와 라벨에도 영향을 줄 수 있다”는 정도만 이해하면 충분하다.

## 12. 정상 흐름과 오류 흐름

### 12.1 정상 흐름

```text
1. Domain ZD_JHY_STATUS가 Active 상태인지 확인
2. SE11에서 Data Type ZDE_JHY_STATUS 생성
3. Data Element 선택
4. Short Description 입력
5. Domain ZD_JHY_STATUS 연결
6. Field Label 입력
7. 저장
8. 활성화
9. ABAP 프로그램에서 TYPE 참조로 검증
```

### 12.2 오류 흐름 1: Domain이 존재하지 않음

| 항목 | 내용 |
|---|---|
| 증상 | Domain 입력 후 활성화 오류 발생 |
| 원인 | `ZD_JHY_STATUS`가 생성되지 않았거나 Active 상태가 아님 |
| 해결 | Domain을 먼저 생성하고 활성화한 뒤 Data Element를 다시 활성화 |

초급자가 가장 자주 만나는 오류이다. DDIC 객체는 선후수 관계가 있다. Data Element가 Domain을 참조한다면 Domain이 먼저 활성화되어야 한다.

### 12.3 오류 흐름 2: Field Label 누락

| 항목 | 내용 |
|---|---|
| 증상 | 활성화는 될 수 있으나 화면 표시명이 부실함 |
| 원인 | Short/Medium/Long/Heading 라벨을 입력하지 않음 |
| 해결 | Field Label 탭에서 의미 있는 라벨 입력 |

라벨 누락은 기술적으로 즉시 오류가 아닐 수 있다. 하지만 교육 문서와 실무 기준에서는 품질 오류로 본다.

### 12.4 오류 흐름 3: Data Element 이름이 의미를 담지 못함

| 나쁜 이름 | 문제 | 개선 이름 |
|---|---|---|
| `ZDE_JHY_CHAR1` | 기술 타입만 표현 | `ZDE_JHY_STATUS` |
| `ZDE_JHY_FLAG1` | 업무 의미 불명확 | `ZDE_JHY_DELETE_FLAG` |
| `ZDE_JHY_FIELD01` | 재사용과 유지보수 어려움 | `ZDE_JHY_USER_STATUS` |

Data Element는 의미 계층이므로, 이름에도 가능한 한 의미가 드러나야 한다.

### 12.5 오류 흐름 4: 같은 Data Element를 무리하게 재사용

하나의 Data Element를 여러 의미에 무리하게 재사용하면 문제가 생긴다.

예를 들어 `ZDE_JHY_STATUS`를 사용자 상태, 주문 상태, 승인 상태에 모두 사용하면 화면 라벨과 문서화가 맞지 않게 된다.

| 사용처 | 실제 의미 | 동일 Data Element 사용 문제 |
|---|---|---|
| 사용자 마스터 | 사용자 상태 | 적합 |
| 주문 헤더 | 주문 상태 | 라벨과 문서 의미 불일치 가능 |
| 승인 문서 | 승인 상태 | 업무 규칙 혼동 |

기술 타입이 같아도 업무 의미가 다르면 Data Element를 분리하는 것이 일반적으로 더 안전하다.

## 13. 실무 설계 기준

### 13.1 Data Element는 의미 단위로 설계한다

Data Element는 단순히 “타입 재사용”을 위한 객체가 아니다.  
따라서 Data Element를 설계할 때는 다음 질문을 먼저 해야 한다.

```text
이 필드는 업무적으로 무엇을 의미하는가?
이 의미는 다른 테이블이나 화면에서도 동일하게 사용되는가?
화면 표시명은 무엇이 적절한가?
사용자가 F1 Help를 봤을 때 어떤 설명이 필요할까?
```

### 13.2 같은 Domain, 다른 Data Element가 가능하다

Domain은 기술 속성 재사용 단위이고 Data Element는 의미 재사용 단위이다. 따라서 하나의 Domain을 여러 Data Element가 사용할 수 있다.

예시:

| Domain | Data Element | 의미 |
|---|---|---|
| `ZD_JHY_STATUS` | `ZDE_JHY_USER_STATUS` | 사용자 상태 |
| `ZD_JHY_STATUS` | `ZDE_JHY_ACCOUNT_STATUS` | 계정 상태 |
| `ZD_JHY_STATUS` | `ZDE_JHY_PROCESS_STATUS` | 처리 상태 |

이 설계가 항상 정답은 아니다. 하지만 “기술 속성이 같기 때문에 무조건 같은 Data Element를 써야 한다”는 생각은 피해야 한다.

### 13.3 표준 Data Element 사용 가능성을 검토한다

SAP 표준 업무 의미와 완전히 동일한 필드라면 표준 Data Element를 사용하는 것이 적절할 수 있다.

예시:

| 업무 의미 | 대표 표준 Data Element 예시 | 설명 |
|---|---|---|
| Client | `MANDT` | Client 필드 |
| Company Code | `BUKRS` | 회사 코드 |
| Currency Key | `WAERS` | 통화 키 |
| Language Key | `SPRAS` | 언어 키 |
| User Name | `SYUNAME` 또는 관련 표준 타입 | 사용자명 성격 |

다만 고객 전용 업무 의미라면 `ZDE_*` 형태의 고객 Data Element를 설계하는 것이 일반적이다.

[추정] 실제 프로젝트에서는 고객사 개발 표준에 따라 표준 Data Element 재사용 범위와 Z Data Element 생성 기준이 별도로 정해져 있을 수 있다.

### 13.4 SAP 표준 Data Element를 직접 수정하지 않는다

표준 SAP Data Element는 고객이 임의로 수정하면 안 된다. 표준 객체 변경은 업그레이드, 노트 적용, 운영 안정성에 영향을 줄 수 있다.

고객 요구사항으로 추가 의미가 필요하면 다음 방식이 일반적이다.

```text
표준 객체 직접 수정 금지
→ Z Data Element 생성
→ Z Table / Append Structure / Extension 영역에서 사용
```

이 원칙은 Clean Core 관점에서도 중요하다.

## 14. Data Element와 후속 객체의 연결

이번 모듈에서 만든 `ZDE_JHY_STATUS`는 이후 모듈에서 계속 사용된다.

| 후속 모듈 | 연결 방식 |
|---|---|
| THEORY-01-M04 Structure 기본 생성 | Structure Component의 타입으로 사용 |
| THEORY-01-M05 Transparent Table 기본 생성 | Table Field의 Data Element로 사용 |
| THEORY-01-M06 Technical Settings와 데이터 확인 | 테이블 데이터 입력 및 조회 시 필드 의미 확인 |
| DDIC 2차 Section | Search Help, Foreign Key와 연결 가능 |
| ABAP 기본 문법 Section | 변수 타입, PARAMETERS 타입으로 사용 가능 |
| ALV Section | Field Label이 컬럼 텍스트의 기본 후보로 활용 가능 |

즉, Data Element는 단독으로 끝나는 객체가 아니다. ABAP 프로그램과 화면, 테이블, ALV, CDS로 이어지는 의미 정의의 연결점이다.

## 16. 실습 코드: Data Element 타입 참조

다음 코드는 Data Element를 ABAP 타입으로 참조하는 최소 예제이다.

```abap
REPORT zjhy_m03_data_element.

DATA gv_status TYPE zde_jhy_status.

gv_status = 'A'.

WRITE: / 'Data Element:', 'ZDE_JHY_STATUS',
       / 'Status Value:', gv_status.
```

### 16.1 코드 설명

| 코드 | 설명 |
|---|---|
| `DATA gv_status TYPE zde_jhy_status` | 변수의 타입을 Data Element 기준으로 선언 |
| `gv_status = 'A'` | Domain Fixed Value 중 하나를 대입 |
| `WRITE` | 값이 정상적으로 사용되는지 출력 |

이 예제에서 `ZDE_JHY_STATUS`는 단순히 길이 1짜리 문자 타입처럼 보일 수 있다. 그러나 시스템 관점에서는 `ZD_JHY_STATUS` Domain의 기술 규칙과 `ZDE_JHY_STATUS` Data Element의 의미 정보를 함께 가진 타입으로 관리된다.

### 16.2 오류 테스트

다음과 같이 Domain Fixed Value에 없는 값을 넣어볼 수 있다.

```abap
gv_status = 'X'.
```

주의할 점은 ABAP 변수에 직접 값을 대입하는 것과 화면/테이블 입력 검증은 항상 동일하게 동작하지 않을 수 있다는 것이다. Domain Fixed Value는 DDIC 기반 입력 도움말, 화면 검증, 테이블 필드 검증 등과 결합될 때 더 명확하게 체감된다.

따라서 이 단계에서는 `X` 대입 여부보다, Data Element가 타입으로 인식되고 후속 객체에서 의미 계층으로 사용된다는 점을 이해하는 것이 중요하다.

## 17. 초급자가 자주 하는 질문

### Q1. Data Element 없이 Domain만으로 테이블 필드를 만들 수 있나요?

기술적으로 일부 상황에서 직접 타입을 지정하는 방식이 가능할 수 있지만, SAP DDIC 설계 관점에서는 Data Element를 통해 업무 의미와 Field Label을 제공하는 방식이 일반적으로 더 적절하다.

초급 학습에서는 다음 원칙을 기억하면 된다.

```text
Domain = 기술 속성
Data Element = 업무 의미와 라벨
Table Field = 실제 저장 필드
```

### Q2. 같은 Domain을 쓰면 같은 Data Element를 써야 하나요?

아니다. 기술 속성이 같아도 업무 의미가 다르면 다른 Data Element를 사용하는 것이 좋다.

예를 들어 `CHAR 1` 기반 상태값이라도 사용자 상태와 승인 상태는 다른 의미이다. 이 경우 Data Element를 분리하면 화면 라벨과 문서화가 더 명확해진다.

### Q3. Field Label은 꼭 입력해야 하나요?

실무 품질 기준에서는 입력하는 것이 좋다. Field Label이 없으면 화면, 리스트, ALV 등에서 필드 의미가 불명확해질 수 있다.

### Q4. Data Element 이름은 어떻게 정하나요?

고객 개발 객체는 일반적으로 `Z` 또는 `Y` 네임스페이스를 사용한다. 교육용 예시는 다음 규칙을 사용한다.

```text
ZDE_ + 교육 Prefix + 의미
```

예:

```text
ZDE_JHY_STATUS
ZDE_JHY_USER_ID
ZDE_JHY_USER_NAME
```

### Q5. 표준 Data Element를 사용해도 되나요?

업무 의미가 표준 필드와 동일하다면 사용할 수 있다. 예를 들어 회사 코드라면 `BUKRS`, 통화 키라면 `WAERS` 같은 표준 Data Element를 검토할 수 있다. 단, 고객 고유 의미라면 Z Data Element를 사용하는 것이 더 명확하다.

## 18. 실무 안티패턴

### 18.1 기술 타입만 표현하는 Data Element

```text
나쁜 예: ZDE_CHAR1
좋은 예: ZDE_JHY_USER_STATUS
```

Data Element는 의미 객체이므로 이름이 기술 타입만 표현하면 좋지 않다.

### 18.2 모든 상태값을 하나의 Data Element로 통합

```text
나쁜 예:
ZDE_STATUS 하나를 사용자 상태, 주문 상태, 승인 상태에 모두 사용
```

문제점:

| 문제 | 설명 |
|---|---|
| 라벨 불일치 | User Status가 주문 상태 화면에 표시될 수 있음 |
| 문서화 혼선 | F1 Help 내용이 특정 업무에 맞지 않음 |
| 변경 영향 과다 | 한 업무 요구 변경이 다른 업무 객체에 영향 |
| 유지보수 난이도 증가 | Where-Used 결과가 의미별로 분리되지 않음 |

### 18.3 Field Label을 개발자 약어로 작성

```text
나쁜 예: UStat, UsrSt, StsCd
좋은 예: User Status, User Account Status
```

사용자는 개발자 약어를 이해하지 못할 수 있다. Field Label은 가능한 한 업무 사용자 관점으로 작성한다.

### 18.4 표준 객체 직접 수정

SAP 표준 Data Element의 라벨이나 Domain을 직접 수정하는 것은 위험하다. 표준 객체 변경은 업그레이드와 유지보수에 영향을 줄 수 있다.

## 19. 강사용 설명 포인트

강의에서는 다음 비유를 사용하면 초급자가 쉽게 이해한다.

```text
Domain은 그릇의 크기와 재질이다.
Data Element는 그 그릇에 붙은 이름표와 사용 목적이다.
Table Field는 실제로 그 그릇을 어디에 놓고 데이터를 담을지 정하는 것이다.
```

예를 들어 `CHAR 1`이라는 그릇은 여러 곳에 쓰일 수 있다. 하지만 그 그릇이 “사용자 상태”를 담는지, “승인 여부”를 담는지, “삭제 여부”를 담는지는 Data Element가 설명한다.

또 다른 설명 방식은 다음과 같다.

```text
Domain: 값의 기술 규칙
Data Element: 값의 업무 의미
Field Label: 사용자에게 보이는 이름
Documentation: 사용자가 F1으로 확인할 수 있는 설명
```

초급자는 Domain과 Data Element를 자주 혼동하므로, 강의 중에는 반드시 둘을 나란히 비교하는 표를 반복해서 보여주는 것이 좋다.

## 21. 평가 문제

### 21.1 객관식

#### Q1. Data Element의 가장 핵심적인 역할은 무엇인가?

A. 실제 데이터를 저장한다.  
B. 데이터베이스 인덱스를 생성한다.  
C. 데이터 필드의 업무 의미와 Field Label을 정의한다.  
D. 프로그램의 실행 순서를 제어한다.  

**정답:** C

#### Q2. Domain과 Data Element의 설명으로 올바른 것은?

A. Domain은 업무 의미, Data Element는 기술 속성을 정의한다.  
B. Domain은 기술 속성, Data Element는 업무 의미를 정의한다.  
C. 둘은 완전히 같은 객체이다.  
D. Data Element는 Transparent Table에서만 사용된다.  

**정답:** B

#### Q3. Field Label 중 일반 화면 필드명으로 가장 자주 사용되는 것은?

A. Short  
B. Medium  
C. Package  
D. Transport  

**정답:** B

### 21.2 서술형

#### Q1. 같은 Domain을 여러 Data Element가 사용할 수 있는 이유를 설명하시오.

**모범 답안:**  
Domain은 데이터 타입, 길이, Fixed Value 같은 기술 속성을 정의한다. 여러 필드가 같은 기술 속성을 가질 수 있지만 업무 의미는 다를 수 있다. 따라서 같은 Domain을 사용하더라도 사용자 상태, 승인 상태, 삭제 여부처럼 의미가 다르면 별도의 Data Element를 만들어 Field Label과 문서화를 분리할 수 있다.

#### Q2. Field Label을 작성하지 않으면 어떤 문제가 발생할 수 있는가?

**모범 답안:**  
화면, 리스트, ALV 등에서 필드 의미가 명확하게 표시되지 않을 수 있다. 또한 사용자 관점의 설명이 부족해지고, 개발자가 별도 텍스트를 반복 지정해야 하므로 유지보수성이 낮아진다.

#### Q3. Data Element 이름을 `ZDE_CHAR1`처럼 짓는 것이 좋지 않은 이유를 설명하시오.

**모범 답안:**  
Data Element는 기술 타입이 아니라 업무 의미를 표현하는 객체이다. `ZDE_CHAR1`은 기술 형식만 나타내고 업무 의미를 설명하지 못하므로, Where-Used 분석이나 화면 라벨 관리, 문서화 측면에서 유지보수성이 낮다.

## 22. 미니 과제

### 과제 1: Data Element 생성

다음 Data Element를 생성하시오.

| 항목 | 값 |
|---|---|
| Data Element | `ZDE_JHY_STATUS` |
| Domain | `ZD_JHY_STATUS` |

| Long Label | `User Account Status` |
| Heading | `Status` |

### 과제 2: ABAP 타입 참조

다음 조건을 만족하는 프로그램을 작성하시오.

| 조건 | 내용 |
|---|---|
| Program | `ZJHY_M03_CHECK_DE` |
| 변수 | `GV_STATUS` |
| 변수 타입 | `ZDE_JHY_STATUS` |
| 대입 값 | `A` |
| 출력 | Data Element명과 상태값 |

예시 출력:

```text
Data Element: ZDE_JHY_STATUS
Status Value: A
```

### 과제 3: 설계 판단

다음 세 필드를 하나의 Data Element로 통합해도 되는지 판단하시오.

| 필드 | 기술 타입 | 업무 의미 |
|---|---|---|
| USER_STATUS | CHAR 1 | 사용자 상태 |
| ORDER_STATUS | CHAR 1 | 주문 상태 |

**기대 답안:**

## 23. 이번 모듈의 핵심 정리

이번 모듈에서 반드시 기억해야 할 내용은 다음과 같다.

```text
Domain은 기술 속성을 정의한다.
Data Element는 업무 의미를 정의한다.
Field Label은 사용자에게 보이는 표시명의 기준이다.
같은 Domain을 여러 Data Element가 사용할 수 있다.
업무 의미가 다르면 Data Element를 분리하는 것이 좋다.
Data Element는 Structure, Table, Program, Screen, ALV로 이어지는 의미 계층이다.
```

초급자는 처음에 Domain과 Data Element를 모두 “타입”으로만 이해하기 쉽다. 그러나 SAP DDIC의 설계 의도는 단순 타입 선언보다 더 크다.  
SAP는 데이터의 기술 속성과 업무 의미를 분리함으로써, 대규모 엔터프라이즈 시스템에서 데이터 정의를 중앙화하고 재사용성과 유지보수성을 높인다.
