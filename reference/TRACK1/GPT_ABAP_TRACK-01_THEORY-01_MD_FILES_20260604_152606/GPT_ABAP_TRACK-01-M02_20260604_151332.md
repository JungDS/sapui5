## 3. Domain이란 무엇인가?

Domain은 ABAP Dictionary에서 데이터의 **기술적 속성**을 정의하는 객체이다.

쉽게 말하면 Domain은 다음 질문에 답한다.

```text
이 값은 어떤 데이터 타입인가?
몇 자리까지 입력할 수 있는가?
소수점은 몇 자리인가?
소문자를 허용할 것인가?
입력 가능한 값이 정해져 있는가?
```

예를 들어 사용자 상태를 `A`, `I`, `B` 세 가지 값으로 관리한다고 가정하자.

| 상태 코드 | 의미 |
|---|---|
| A | Active |
| I | Inactive |
| B | Blocked |

이 경우 Domain은 다음과 같이 정의할 수 있다.

| Domain 속성 | 값 |
|---|---|
| Domain Name | `ZD_JHY_STATUS` |
| Data Type | `CHAR` |
| Length | `1` |
| Fixed Value | `A`, `I`, `B` |
| Lowercase | 미허용 |

이 Domain은 “상태값은 한 자리 문자이며, 허용 값은 A/I/B이다”라는 기술적 규칙을 시스템에 알려준다.

## 4. Domain의 위치: DDIC 객체 계층에서의 역할

SAP Dictionary의 기본 데이터 모델은 보통 다음 흐름으로 이해하면 된다.

```text
Domain
  ↓
Data Element
  ↓
Structure / Transparent Table Field
  ↓
ABAP Program / Screen / ALV / CDS / Interface
```

각 계층의 역할은 다르다.

| 계층 | 역할 | 예시 |
|---|---|---|
| Domain | 기술적 속성 정의 | CHAR 1, NUMC 10, DEC 15.2 |
| Data Element | 업무 의미 정의 | 사용자 상태, 고객 번호, 주문일자 |
| Table Field | 실제 저장 필드 정의 | `ZT_USER-STATUS` |
| Program Field | 프로그램에서 사용하는 변수 | `DATA gv_status TYPE zde_jhy_status` |

Domain은 가장 아래쪽에 위치한 기술 기반이다.  
Data Element는 Domain을 참조하여 업무 의미와 라벨을 제공한다.  
테이블 필드는 일반적으로 Data Element를 참조하여 기술 속성과 업무 의미를 함께 사용한다.

> 초급자 핵심:  
> **Domain은 “형식”을 정의하고, Data Element는 “의미”를 정의한다.**

## 5. Domain과 Data Element의 차이

Domain과 Data Element는 처음 배울 때 가장 많이 혼동되는 개념이다.

### 5.1 비교표

| 구분 | Domain | Data Element |
|---|---|---|
| 핵심 역할 | 기술적 속성 정의 | 업무적 의미 정의 |
| 주요 속성 | Data Type, Length, Decimal, Fixed Value | Field Label, Documentation, Domain 참조 |
| 예시 | CHAR 1 | 사용자 상태 |
| 재사용 기준 | 같은 기술 형식 | 같은 업무 의미 |
| 화면 라벨 제공 | 직접 제공하지 않음 | 제공함 |
| 필드 설명 제공 | 제한적 | 가능 |
| 초급자 이해 방식 | “그릇의 크기와 형태” | “그릇에 담긴 업무 의미” |

### 5.2 예시로 이해하기

`CHAR 1`이라는 기술 형식은 여러 업무 의미에 사용될 수 있다.

| 업무 의미 | 가능한 값 | 기술 형식 |
|---|---|---|
| 사용자 상태 | A/I/B | CHAR 1 |
| 삭제 여부 | X/blank | CHAR 1 |
| 승인 여부 | Y/N | CHAR 1 |
| 성별 코드 | M/F | CHAR 1 |

이들은 모두 `CHAR 1`일 수 있지만 같은 의미는 아니다.  
따라서 같은 Domain을 무조건 재사용하는 것이 항상 좋은 설계는 아니다.

### 5.3 실무적 판단 기준

| 상황 | 권장 판단 |
|---|---|
| 기술 형식만 같고 업무 의미가 다름 | Data Element는 분리 |
| 허용 값 체계도 같고 의미도 유사함 | Domain 재사용 검토 |
| 코드값이 완전히 다른 의미를 가짐 | Domain도 분리 권장 |
| 단순 CHAR 길이만 같음 | 무조건 같은 Domain으로 묶지 않음 |

> [추정] 교육 환경에서는 Domain 재사용을 단순화하여 설명할 수 있지만, 실제 프로젝트에서는 “기술 형식이 같다”보다 “업무 의미와 값 체계가 같은가”를 더 중요하게 판단해야 한다.

## 6. Domain의 주요 속성

SE11에서 Domain을 생성하면 여러 속성을 입력한다. 초급 단계에서는 다음 항목을 반드시 이해해야 한다.

## 6.1 Short Description

Domain의 간단한 설명이다.

예시:

```text
User Status Domain
Customer Classification Domain
Document Type Domain
```

설명은 시스템 유지보수 시 매우 중요하다.  
객체명만으로 의미가 명확하지 않을 수 있으므로, Short Description에는 업무적 맥락을 간단히 적는 것이 좋다.

나쁜 예:

```text
Status
Code
Test
```

좋은 예:

```text
User Account Status Domain
Training User Status Code Domain
Customer Grade Code Domain
```

---

## 6.2 Data Type

Domain에서 가장 중요한 속성이다.  
값의 기본 기술 형식을 결정한다.

초급 단계에서 자주 사용하는 타입은 다음과 같다.

| Data Type | 의미 | 사용 예 |
|---|---|---|
| CHAR | 일반 문자 | 이름, 코드, 상태 |
| NUMC | 숫자 형태 문자 | 문서번호, 순번, 사업자번호 일부 |
| DATS | 날짜 | 생성일, 전기일, 납기일 |
| TIMS | 시간 | 생성시간, 처리시간 |
| DEC | 소수점 포함 숫자 | 비율, 일반 수치 |
| CURR | 통화 금액 | 금액 |
| QUAN | 수량 | 수량 |
| CLNT | Client | `MANDT` |

### CHAR와 NUMC의 차이

초급자가 자주 헷갈리는 타입이 `CHAR`와 `NUMC`이다.

| 구분 | CHAR | NUMC |
|---|---|---|
| 저장 형태 | 문자 | 숫자 문자 |
| 허용 문자 | 문자/숫자 가능 | 숫자 형태 중심 |
| 예시 | `A001`, `KR01` | `000001`, `202406` |
| 사용 목적 | 코드, 이름, 상태 | 숫자로 구성된 고정 길이 식별자 |
| 정렬 느낌 | 문자 정렬 | 숫자 문자열 정렬 |

주의할 점은 `NUMC`가 계산용 숫자 타입이 아니라는 점이다.  
`NUMC`는 “숫자로 보이는 문자”에 가깝다. 문서번호처럼 앞의 0이 의미 있는 경우에 적합하다.

---

## 6.3 Length

Length는 입력 가능한 자릿수 또는 문자 길이를 의미한다.

예시:

| 의미 | Data Type | Length |
|---|---:|---:|
| 상태 코드 | CHAR | 1 |
| 사용자 ID | CHAR | 12 |
| 회사 코드 | CHAR | 4 |
| 순번 | NUMC | 6 |
| 우편번호 | CHAR 또는 NUMC | 5 |

길이를 정할 때는 현재 데이터만 보지 말고, 확장 가능성과 표준 SAP 관행을 함께 고려해야 한다.

### 길이를 너무 짧게 잡으면?

- 나중에 코드 체계가 확장될 때 변경이 어렵다.
- 테이블 필드, 프로그램, 인터페이스, 화면에 영향이 생긴다.
- 운영 데이터가 이미 존재하면 변경 리스크가 커진다.

### 길이를 너무 길게 잡으면?

- 의미 없는 여유 길이가 생긴다.
- 화면, ALV, 인터페이스에서 불필요한 공간을 차지한다.
- 정렬·검증 기준이 느슨해질 수 있다.

초급 실습에서는 상태 코드처럼 명확한 값 체계는 `CHAR 1`부터 시작하는 것이 좋다.

---

## 6.4 Decimal Places

`DEC`, `CURR`, `QUAN` 같은 숫자 타입에서 사용하는 소수 자릿수이다.

예시:

| 의미 | Data Type | Length | Decimal |
|---|---:|---:|---:|
| 비율 | DEC | 5 | 2 |
| 금액 | CURR | 15 | 2 |
| 수량 | QUAN | 13 | 3 |

이번 모듈의 실습은 상태 코드 Domain이므로 Decimal은 사용하지 않는다.  
다만 금액과 수량을 다룰 때는 Decimal 설정이 매우 중요하다.

> 주의: 금액(`CURR`)과 수량(`QUAN`) 필드는 일반적으로 통화키 또는 단위 필드와의 관계를 고려해야 한다. 이 내용은 후속 DDIC/테이블 설계 단계에서 더 자세히 다룬다.

---

## 6.5 Lowercase

Lowercase는 소문자 입력 허용 여부를 결정한다.

| 설정 | 의미 |
|---|---|
| 체크 | 소문자 허용 |
| 미체크 | 대문자 변환 또는 대문자 중심 처리 |

코드성 값은 보통 소문자를 허용하지 않는다.

예시:

| 필드 | Lowercase 권장 |
|---|---|
| 상태 코드 | 미체크 |
| 회사 코드 | 미체크 |
| 사용자 이름 | 체크 가능 |
| 설명 텍스트 | 체크 가능 |

실습 Domain인 `ZD_JHY_STATUS`는 상태 코드이므로 Lowercase를 체크하지 않는다.

## 7. Fixed Value

Fixed Value는 Domain 수준에서 입력 가능한 값을 제한하는 기능이다.

예를 들어 상태 Domain을 다음과 같이 정의할 수 있다.

| Fixed Value | Description |
|---|---|
| A | Active |
| I | Inactive |
| B | Blocked |

이렇게 설정하면 이 Domain을 참조하는 필드에서는 허용 값 체계를 명확히 표현할 수 있다.

## 7.1 Fixed Value의 장점

| 장점 | 설명 |
|---|---|
| 값 체계 명확화 | 어떤 값이 허용되는지 Domain에서 확인 가능 |
| 입력 오류 감소 | 허용되지 않는 코드 입력을 줄일 수 있음 |
| 재사용성 | 동일 값 체계를 여러 Data Element/Field에서 재사용 가능 |
| 문서화 효과 | 코드와 설명이 함께 관리됨 |
| F4 도움말 기초 | 고정 값 기반 선택 도움말처럼 활용 가능 |

## 7.2 Fixed Value가 적합한 경우

Fixed Value는 값의 종류가 작고, 자주 변하지 않는 경우에 적합하다.

| 적합한 예 | 이유 |
|---|---|
| 상태 코드 A/I/B | 값이 적고 안정적 |
| 사용 여부 Y/N | 값 체계 단순 |
| 승인 단계 1/2/3 | 단계가 명확 |
| 성별 코드 M/F | 값이 제한적 |

## 7.3 Fixed Value가 부적합한 경우

| 부적합한 예 | 이유 |
|---|---|
| 고객 번호 | 데이터가 계속 증가 |
| 자재 번호 | 마스터 테이블로 관리 필요 |
| 플랜트 코드 | 조직 구조와 연계 필요 |
| 국가 코드 | 표준 테이블/검증 체계 활용 필요 |
| 사용자 ID | 시스템 사용자 마스터와 연계 가능 |

Fixed Value는 “간단한 코드값”에는 유용하지만, 업무 데이터가 계속 증가하거나 추가 속성이 필요한 경우에는 별도 테이블과 관계 설정을 고려해야 한다.  
이 내용은 후속 모듈인 DDIC 관계, Foreign Key, Search Help에서 더 깊게 다룬다.

## 8. Domain 설계 절차

Domain을 설계할 때는 바로 SE11에 들어가서 값을 입력하기보다, 먼저 설계 질문에 답하는 것이 좋다.

### 8.1 설계 질문

```text
1. 이 값은 무엇을 표현하는가?
2. 값의 기술 타입은 무엇인가?
3. 최대 길이는 몇 자리인가?
4. 소수점이 필요한가?
5. 소문자를 허용해야 하는가?
6. 허용 가능한 값 목록이 고정되어 있는가?
7. 이 Domain을 다른 필드에서도 재사용할 수 있는가?
8. 나중에 값 체계가 확장될 가능성이 있는가?
```

### 8.2 상태 코드 Domain 설계 예시

| 설계 질문 | 답변 |
|---|---|
| 무엇을 표현하는가? | 사용자 계정 상태 |
| 기술 타입은? | CHAR |
| 길이는? | 1 |
| 소수점은? | 없음 |
| 소문자 허용? | 불필요 |
| 값 목록은? | A/I/B |
| 재사용 가능성은? | 사용자 상태 관련 필드에서 재사용 가능 |
| 확장 가능성은? | 낮음. 필요 시 C, D 등 추가 가능 |

## 9. Naming Convention

고객 개발 객체는 일반적으로 `Z` 또는 `Y` 네임스페이스를 사용한다.  
교육용으로는 다음과 같은 Prefix를 사용할 수 있다.

| 객체 유형 | Prefix 예시 |
|---|---|
| Domain | `ZD_` |
| Data Element | `ZDE_` |
| Structure | `ZS_` |
| Transparent Table | `ZT_` |
| Table Type | `ZTT_` |

이번 실습에서는 다음 Domain을 사용한다.

```text
ZD_JHY_STATUS
```

이름을 해석하면 다음과 같다.

| 부분 | 의미 |
|---|---|
| ZD | Z Domain |
| JHY | 작성자 또는 교육용 식별자 |
| STATUS | 상태 코드 |

> 실무에서는 프로젝트별 Naming Rule이 존재하는 경우가 많으므로 반드시 고객사/프로젝트 규칙을 우선한다.

Domain: ZD_JHY_STATUS

## 10.3 설계 속성

|---|---|

### 11.4 저장

저장 시 패키지를 지정해야 할 수 있다.

| 상황 | 선택 |
|---|---|
| 교육용 임시 객체 | `$TMP` Local Object |

초급 실습에서는 `$TMP`를 사용해도 된다.

```text

```

## 12. 활성화 후 확인 방법

Domain을 생성하고 활성화한 뒤에는 다음을 확인한다.

| 확인 항목 | 확인 방법 |
|---|---|
| Domain 존재 여부 | SE11에서 `ZD_JHY_STATUS` 조회 |
| 활성화 상태 | Object 상태 확인 |
| Data Type | CHAR인지 확인 |
| Length | 1인지 확인 |
| Fixed Value | A/I/B가 입력되었는지 확인 |
| Description | 설명이 충분한지 확인 |

초급자는 “저장”과 “활성화”를 혼동하기 쉽다.  
저장은 객체 정의를 보관하는 것이고, 활성화는 실제 사용 가능한 상태로 반영하는 것이다.

## 13. 오류 상황과 해결 방법

## 13.1 객체 이름 오류

### 증상

```text
Object name is not in the customer namespace
```

### 원인

SAP 표준 네임스페이스에 해당하는 이름을 사용했을 가능성이 있다.

### 해결

고객 개발 객체는 `Z` 또는 `Y`로 시작하는 이름을 사용한다.

```text
잘못된 예: D_USER_STATUS
좋은 예: ZD_JHY_STATUS
```

---

## 13.2 Data Type 누락

### 증상

활성화 시 필수 속성이 없다는 오류가 발생한다.

### 원인

Data Type 또는 Length를 입력하지 않았다.

### 해결

Definition 탭에서 Data Type과 No. Characters를 입력한다.

---

## 13.3 Fixed Value 길이 오류

### 증상

Fixed Value를 입력했는데 길이 관련 오류가 발생한다.

### 원인

Domain 길이보다 긴 값을 입력했다.

예를 들어 Length가 1인데 Fixed Value에 `ACT`를 입력하면 맞지 않는다.

### 해결

둘 중 하나를 선택해야 한다.

| 선택 | 설명 |
|---|---|
| Fixed Value를 한 자리로 조정 | A/I/B |
| Domain Length를 늘림 | ACT/INA/BLK 같은 코드 사용 시 |

초급 실습에서는 `CHAR 1`에 `A/I/B`를 사용한다.

---

## 13.4 Lowercase 설정 오류

### 증상

소문자 입력이 기대와 다르게 처리된다.

### 원인

Lowercase 허용 여부를 잘못 설정했다.

### 해결

상태 코드처럼 대문자 코드값만 허용하려면 Lowercase를 체크하지 않는다.  
이름, 설명처럼 소문자가 필요한 값에는 Lowercase를 허용할 수 있다.

---

## 14. 실무 설계 기준

Domain은 초급 실습에서는 단순해 보이지만, 실제 프로젝트에서는 변경 파급효과가 크다.

## 14.1 Domain 변경의 파급효과

Domain은 여러 Data Element에서 참조될 수 있고, 그 Data Element는 여러 테이블 필드와 프로그램에서 사용될 수 있다.

```text
Domain 변경
  → Data Element 영향
  → Table Field 영향
  → DB Table 변환 가능성
  → Program/Screen/Interface 영향
```

특히 Length 변경은 매우 민감하다.  
운영 테이블에 데이터가 들어간 뒤 길이를 줄이면 데이터 손실 또는 변환 오류가 발생할 수 있다.

## 14.2 처음부터 신중히 정해야 하는 항목

| 항목 | 이유 |
|---|---|
| Data Type | 필드의 본질을 결정 |
| Length | DB 구조와 프로그램 타입에 영향 |
| Decimal | 금액/수량 계산 정확도 영향 |
| Fixed Value | 입력 검증과 코드 체계 영향 |
| Lowercase | 사용자 입력과 표시 방식 영향 |

## 14.3 실무에서 피해야 할 설계

| 나쁜 설계 | 문제 |
|---|---|
| 모든 코드를 CHAR10으로 통일 | 의미 없는 길이 증가 |
| Fixed Value를 과도하게 사용 | 운영 중 코드 추가가 어려움 |
| 업무 의미가 다른 필드에 같은 Domain 강제 | 유지보수 혼란 |
| 설명 없는 Domain 생성 | 영향 분석 어려움 |
| 테스트 객체를 운영 Package에 생성 | 객체 관리 혼선 |

## 15. Domain 재사용 판단

Domain은 재사용 가능한 객체이지만, 무조건 많이 재사용하는 것이 좋은 것은 아니다.

## 15.1 재사용해도 좋은 경우

| 조건 | 예 |
|---|---|
| 기술 타입이 같음 | CHAR 1 |
| 허용 값 체계가 같음 | A/I/B |
| 업무 의미가 유사함 | 사용자 상태, 계정 상태 |
| 변경 시 함께 바뀌어도 됨 | 동일 상태 체계 공유 |

## 15.2 분리하는 것이 좋은 경우

| 조건 | 예 |
|---|---|
| 기술 타입만 같고 의미가 다름 | 삭제 여부와 승인 여부 |
| 값 체계가 다름 | A/I/B vs Y/N |
| 변경 주기가 다름 | 고정 코드 vs 운영 변경 코드 |
| 소유 부서가 다름 | HR 코드 vs SD 코드 |

> 핵심 판단:  
> **같이 바뀌어도 되는 값 체계인가?**  
> 이 질문에 “아니오”라면 Domain을 분리하는 것이 안전하다.

## 16. 초급자 관점의 이해 비유

Domain을 “그릇의 형태”라고 생각할 수 있다.

| 개념 | 비유 |
|---|---|
| Domain | 그릇의 크기와 형태 |
| Data Element | 그릇의 이름과 용도 |
| Table Field | 실제 식탁 위에 놓인 그릇 |
| 값 | 그릇에 담기는 내용 |

예를 들어 `CHAR 1`이라는 Domain은 “한 글자짜리 작은 그릇”이다.  
하지만 그 그릇이 “상태 코드”를 담는지, “삭제 여부”를 담는지는 Data Element가 설명한다.

## 17. ABAP 코드에서 Domain은 어떻게 보이는가?

ABAP 프로그램에서 보통 Domain을 직접 타입으로 사용하기보다는 Data Element를 통해 사용한다.

예를 들어 후속 모듈에서 `ZDE_JHY_STATUS`라는 Data Element를 만들면 다음처럼 사용할 수 있다.

```abap
DATA gv_status TYPE zde_jhy_status.

gv_status = 'A'.
WRITE gv_status.
```

이때 `ZDE_JHY_STATUS`가 `ZD_JHY_STATUS` Domain을 참조하고 있다면, `gv_status`는 Domain의 기술 속성을 간접적으로 따른다.

초급 단계에서는 다음 원칙만 기억하면 된다.

```text
Domain은 기술 속성의 원천이다.
ABAP 변수나 테이블 필드는 보통 Data Element를 통해 Domain의 속성을 사용한다.
```

## 18. 미니 점검 문제

### Q1. Domain의 가장 중요한 역할은 무엇인가?

A. 화면 제목을 정의한다.  
B. 데이터의 기술적 타입과 길이를 정의한다.  
C. 프로그램 이벤트를 제어한다.  
D. DB 데이터를 직접 저장한다.

**정답:** B

---

### Q2. 상태 코드 `A`, `I`, `B`를 한 자리 값으로 관리하려면 적절한 Domain 설정은?

A. CHAR 1  
B. CHAR 40  
C. DATS 8  
D. DEC 15.2

**정답:** A

---

### Q3. Fixed Value가 가장 적합한 경우는?

A. 고객 번호처럼 계속 증가하는 값  
B. 자재 번호처럼 마스터 테이블로 관리되는 값  
C. Y/N처럼 값 종류가 작고 안정적인 값  
D. 판매오더 번호처럼 매일 생성되는 값

**정답:** C

---

### Q4. Domain과 Data Element의 차이를 설명하시오.

**모범 답안:**  
Domain은 데이터 타입, 길이, 소수점, Fixed Value 같은 기술적 속성을 정의한다. Data Element는 그 기술 속성에 업무 의미와 Field Label, Documentation을 부여한다.

---

### Q5. Domain Length를 운영 중에 변경할 때 주의해야 하는 이유는?

**모범 답안:**  
Domain은 여러 Data Element와 Table Field에서 참조될 수 있으므로 Length 변경이 DB 테이블 구조, 프로그램 변수, 화면, 인터페이스에 영향을 줄 수 있다. 특히 길이를 줄이는 변경은 기존 데이터 손실이나 변환 오류를 유발할 수 있다.

## 19. 실습 과제

## 19.1 기본 과제

다음 Domain을 생성한다.

```text
Domain: ZD_JHY_STATUS
Description: User Account Status Domain
Data Type: CHAR
Length: 1
Fixed Values:
  A Active
  I Inactive
  B Blocked
```

완료 후 다음을 확인한다.

```text
1. Domain이 저장되었는가?
2. Domain이 활성화되었는가?
3. Fixed Value 3개가 정상 입력되었는가?
4. Length가 1로 설정되었는가?
5. Lowercase가 체크되지 않았는가?
```

## 19.2 확장 과제

다음 두 Domain을 추가로 설계해본다.

| Domain | 의미 | 권장 타입 |
|---|---|---|
| `ZD_JHY_YN` | Yes/No 코드 | CHAR 1 |
| `ZD_JHY_GRADE` | 등급 코드 | CHAR 1 또는 CHAR 2 |

각 Domain에 대해 다음을 작성한다.

```text
1. Data Type
2. Length
3. Fixed Value
4. Lowercase 여부
5. 재사용 가능성
```

## 20. 강사용 설명 포인트

이 모듈을 강의할 때는 “Domain을 왜 굳이 만드는가?”를 반드시 설명해야 한다.

초급자는 테이블 필드에 `CHAR 1`을 직접 넣어도 화면상으로는 동작한다고 느낄 수 있다.  
따라서 다음 메시지가 중요하다.

```text
SAP 개발은 단순히 실행되는 코드를 만드는 것이 아니라,
업무 의미와 기술 속성을 시스템 전체에서 재사용 가능하게 정의하는 작업이다.
```

강의 중 추천 질문:

```text
상태 코드와 삭제 여부가 모두 CHAR 1이라면 같은 Domain을 써도 될까요?
값이 A/I/B에서 A/I/B/S로 늘어나면 어떤 영향이 있을까요?
Fixed Value와 별도 코드 테이블은 언제 구분해야 할까요?
```

이 질문을 통해 학습자가 단순 입력 절차를 넘어 설계 관점으로 사고하도록 유도한다.

## 21. 후속 모듈 연결

이번 모듈에서는 Domain을 통해 데이터의 기술적 속성을 정의했다.  
다음 모듈인 `THEORY-01-M03 Data Element 기본 설계`에서는 이 Domain을 참조하여 업무 의미와 Field Label을 정의한다.

연결 흐름은 다음과 같다.

```text
THEORY-01-M02 Domain 기본 설계
  → 기술 타입, 길이, Fixed Value 정의

THEORY-01-M03 Data Element 기본 설계
  → Domain에 업무 의미와 화면 라벨 부여

THEORY-01-M04 Structure 기본 생성
  → 여러 Data Element를 Component로 조합

THEORY-01-M05 Transparent Table 기본 생성
  → 실제 DB 테이블 필드로 구성
```

따라서 이번 모듈의 결과물인 `ZD_JHY_STATUS`는 다음 모듈에서 `ZDE_JHY_STATUS`를 만들 때 사용된다.

## 22. 핵심 요약

```text
Domain은 ABAP Dictionary에서 데이터의 기술적 속성을 정의하는 객체이다.
Domain은 Data Type, Length, Decimal, Fixed Value, Lowercase 여부를 가진다.
Domain은 업무 의미보다 기술 형식에 집중한다.
Data Element는 Domain을 참조하여 업무 의미와 Field Label을 제공한다.
Fixed Value는 값 종류가 작고 안정적인 코드성 필드에 적합하다.
Domain 변경은 여러 객체에 영향을 줄 수 있으므로 신중해야 한다.
```
