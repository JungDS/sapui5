## 3. 초급자가 먼저 이해해야 할 전제

### 3.1 SAP 시스템은 단순한 코드 실행 환경이 아니다

일반적인 프로그래밍 입문에서는 먼저 변수, 조건문, 반복문을 배운다. 예를 들어 Java나 Python에서는 코드 파일 안에서 변수를 선언하고 바로 실행할 수 있다.

하지만 SAP ABAP은 기업 업무 데이터를 다루는 엔터프라이즈 플랫폼 위에서 동작한다. 그래서 프로그램이 다루는 데이터의 의미, 타입, 화면 표시명, 데이터베이스 저장 구조가 시스템 전체에 걸쳐 일관되게 관리되어야 한다.

이 역할을 담당하는 대표 영역이 SAP Dictionary이다.

### 3.2 SAP 개발은 Repository 중심이다

ABAP 개발 객체는 단순히 로컬 PC의 파일이 아니다. 개발 객체는 SAP 시스템 내부의 ABAP Repository에 저장되고, 활성화되고, 전송 요청을 통해 다른 시스템으로 이동한다.

예를 들어 다음과 같은 객체들이 Repository Object이다.

| 객체 유형 | 예시 | 설명 |
|---|---|---|
| ABAP Program | `ZREPORT_...` | 실행 가능한 프로그램 |
| Class | `ZCL_...` | OO ABAP 클래스 |
| Function Module | `ZFM_...` | Function Builder 기반 재사용 로직 |
| Domain | `ZD_...` | 기술적 데이터 속성 |
| Data Element | `ZDE_...` | 비즈니스 의미와 필드 라벨 |
| Structure | `ZS_...` | 재사용 가능한 구조 타입 |
| Transparent Table | `ZT_...` | 데이터베이스 테이블 정의 |
| Search Help | `ZSH_...` | F4 입력 도움말 |
| Lock Object | `ZE_...` | 동시성 제어 객체 |

초급자는 “ABAP 개발은 코드만 작성하는 것이 아니라 Repository Object를 설계하고 연결하는 일”이라는 관점을 먼저 가져야 한다.

## 4. SAP Dictionary란 무엇인가

### 4.1 기본 정의

SAP Dictionary는 ABAP 시스템에서 데이터 정의를 중앙 관리하는 영역이다. 흔히 DDIC라고 부른다.

DDIC는 다음과 같은 질문에 답하는 시스템 영역이다.

```text
이 필드는 어떤 타입인가?
이 필드는 몇 자리인가?
이 필드는 어떤 업무 의미인가?
화면에는 어떤 라벨로 보여야 하는가?
이 구조는 여러 프로그램에서 재사용 가능한가?
이 테이블은 실제 데이터베이스에 저장되는가?
이 필드는 어떤 값만 허용해야 하는가?
```

즉, DDIC는 단순한 테이블 생성 도구가 아니라, ABAP 애플리케이션의 데이터 의미와 기술 구조를 연결하는 중심 계층이다.

### 4.2 DDIC의 핵심 역할

| 역할 | 설명 | 초급자 관점 예시 |
|---|---|---|
| 기술 타입 정의 | 문자, 숫자, 날짜, 금액, 수량 등의 타입과 길이를 정의 | 사용자 ID는 CHAR 10 |
| 의미 정의 | 필드가 업무적으로 무엇을 의미하는지 정의 | `USER_ID`는 사용자 식별자 |
| 화면 라벨 제공 | 화면, ALV, 입력 필드 등에 표시될 텍스트 제공 | User ID, 사용자 ID |
| DB 구조 정의 | 실제 데이터베이스 테이블 구조 정의 | `ZT_USER` |
| 재사용성 제공 | 여러 프로그램에서 같은 타입과 의미를 공유 | 여러 프로그램이 같은 Data Element 사용 |
| 검증 기반 제공 | 입력 가능한 값, Foreign Key, Search Help 등과 연결 | 상태값 A/I/B |
| 영향 분석 기반 제공 | 객체 변경 시 참조 관계를 추적 | Where-Used List |

### 4.3 왜 코드 안에서만 타입을 만들면 안 되는가

ABAP 코드 안에서도 타입을 직접 정의할 수 있다.

```abap
TYPES: BEGIN OF ty_user,
         user_id   TYPE c LENGTH 10,
         user_name TYPE c LENGTH 40,
       END OF ty_user.
```

이 방식은 작은 예제에서는 충분하다. 그러나 기업 시스템에서는 같은 의미의 필드를 수십 개 프로그램에서 사용한다.

만약 모든 프로그램이 각자 `USER_ID`의 길이를 다르게 정의하면 다음 문제가 생긴다.

| 문제 | 설명 |
|---|---|
| 데이터 불일치 | 어떤 프로그램은 10자리, 어떤 프로그램은 12자리로 처리 |
| 화면 라벨 불일치 | 어떤 화면은 User, 어떤 화면은 User ID로 표시 |
| 유지보수 어려움 | 필드 길이 변경 시 모든 프로그램을 직접 찾아야 함 |
| 인터페이스 오류 | 외부 시스템과 주고받는 필드 길이가 불일치 |
| DB 저장 오류 | 프로그램 타입과 테이블 필드 타입이 맞지 않음 |

DDIC를 사용하면 같은 의미의 필드를 중앙에서 정의하고 재사용할 수 있다.

## 5. DDIC 객체의 기본 계층

이번 모듈에서는 객체를 깊게 생성하지 않고 전체 구조만 이해한다.

```text
Domain
  → Data Element
    → Structure
    → Transparent Table
      → Program / Screen / ALV / CDS / RAP
```

### 5.1 Domain

Domain은 데이터의 기술적 속성을 정의한다.

예를 들어 `CHAR 10`, `NUMC 8`, `DATS`, `DEC 15.2` 같은 형식을 정의한다.

Domain은 “무엇을 의미하는가?”보다 “어떤 형태인가?”에 가깝다.

### 5.2 Data Element

Data Element는 Domain에 업무 의미를 부여한다.

예를 들어 같은 `CHAR 10`이라도 다음처럼 의미가 다를 수 있다.

| 기술 타입 | Data Element 의미 |
|---|---|
| CHAR 10 | 고객 번호 |
| CHAR 10 | 사용자 ID |
| CHAR 10 | 자재 그룹 |
| CHAR 10 | 승인 코드 |

Data Element는 Field Label과 Documentation을 통해 화면과 문서에서 사용할 의미 정보를 제공한다.

### 5.3 Structure

Structure는 여러 필드를 묶은 재사용 가능한 구조 타입이다. 실제 DB 테이블은 아니며, 프로그램 내부 타입, 화면 입출력 구조, ALV 출력 구조 등에 자주 사용된다.

### 5.4 Transparent Table

Transparent Table은 ABAP Dictionary에서 정의되며 실제 데이터베이스 테이블로 생성되는 객체이다.

초급자는 다음 차이를 명확히 기억해야 한다.

| 구분 | Structure | Transparent Table |
|---|---|---|
| 실제 DB 저장 | 없음 | 있음 |
| 데이터 보관 | Runtime Memory | Database |
| Key 필요 여부 | 일반적으로 없음 | 필요 |
| 주요 사용처 | 프로그램 타입, 화면 구조, ALV 구조 | 업무 데이터 저장 |

## 6. SE11과 ADT의 역할

### 6.1 SE11

SE11은 SAP GUI에서 SAP Dictionary 객체를 생성하고 조회하는 대표 트랜잭션이다.

```text
T-Code: SE11
```

SE11에서 다루는 대표 객체는 다음과 같다.

| 영역 | 객체 |
|---|---|
| Database Table | Transparent Table, Pooled/Cluster Table의 역사적 개념 포함 |
| View | Database View, Projection View, Help View, Maintenance View 등 |
| Data Type | Structure, Table Type, Data Element |
| Domain | Domain |
| Search Help | Elementary Search Help, Collective Search Help |
| Lock Object | Lock Object |

초급 교육에서는 SE11이 DDIC 개념을 시각적으로 이해하기 좋다. 객체 간 연결 관계를 화면에서 직접 확인할 수 있기 때문이다.

### 6.2 ADT

ADT는 Eclipse 기반 ABAP Development Tools이다.

S/4HANA와 최신 ABAP 개발에서는 ADT의 중요성이 높다. 특히 CDS View Entity, RAP, ABAP Cloud, ClassRun 기반 개발은 ADT 중심으로 진행되는 경우가 많다.

다만 DDIC의 기본 계층을 처음 배우는 단계에서는 SE11을 통해 Domain, Data Element, Table 등의 관계를 먼저 체감하는 것이 효과적이다.

### 6.3 SE11과 ADT 비교

| 항목 | SE11 | ADT |
|---|---|---|
| 실행 환경 | SAP GUI | Eclipse |
| 초급 DDIC 이해 | 매우 직관적 | 다소 개발자 도구 중심 |
| Classic DDIC 객체 확인 | 강함 | 가능 |
| CDS/RAP 개발 | 제한적 | 강함 |
| 최신 개발 흐름 | 보조적 | 중심 도구 |
| 교육 초반 추천도 | 높음 | 보조 병행 |

[추정] 실제 고객사 프로젝트에서는 여전히 SE11, SE80, SE38, SE24 같은 SAP GUI 도구와 ADT를 병행하는 경우가 많다. 다만 S/4HANA 신규 개발, RAP, ABAP Cloud 방향으로 갈수록 ADT 활용 비중이 커진다.

## 7. Repository Object와 Activation

### 7.1 Repository Object란 무엇인가

Repository Object는 SAP 시스템 안에서 개발 객체로 관리되는 단위이다.

DDIC 객체도 Repository Object이다. 즉, Domain, Data Element, Structure, Table은 단순 설정값이 아니라 시스템이 관리하는 개발 객체이다.

이 관점이 중요한 이유는 다음과 같다.

| 이유 | 설명 |
|---|---|
| 버전과 변경 이력 | 객체 변경은 시스템에 기록되고 관리된다 |
| 활성화 필요 | 저장만으로는 런타임에 반영되지 않을 수 있다 |
| 참조 관계 | 다른 객체가 해당 객체를 참조할 수 있다 |
| 전송 관리 | 개발 시스템에서 품질/운영 시스템으로 이동한다 |
| 권한 통제 | 객체 생성/변경 권한이 필요하다 |

### 7.2 저장과 활성화의 차이

초급자가 자주 혼동하는 개념이 Save와 Activate이다.

| 구분 | 의미 | 결과 |
|---|---|---|
| Save | 개발 객체의 현재 내용을 저장 | 비활성 상태일 수 있음 |
| Activate | 시스템이 사용할 수 있는 런타임 객체로 반영 | 다른 객체나 프로그램에서 사용 가능 |

예를 들어 Data Element를 만들고 저장만 했지만 활성화하지 않으면, Table에서 참조할 때 오류가 발생하거나 사용할 수 없는 상태가 될 수 있다.

### 7.3 활성화가 실패하는 대표 원인

| 원인 | 예시 | 해결 방향 |
|---|---|---|
| 필수 속성 누락 | Domain의 Data Type 미입력 | 필수 필드 입력 |
| 참조 객체 미활성 | Data Element가 비활성 Domain 참조 | 선행 객체 활성화 |
| 이름 규칙 위반 | 고객 네임스페이스 미사용 | `Z` 또는 `Y` Prefix 사용 |
| 타입 불일치 | 길이, 소수점, 타입 충돌 | 설계값 재검토 |
| 권한 부족 | 개발 객체 변경 권한 없음 | 권한 요청 |
| 패키지/전송 문제 | Local Object 여부 혼동 | Package와 Transport 확인 |

## 8. DDIC 개발의 일반적인 흐름

이번 Section 전체에서 배우게 될 흐름은 다음과 같다.

```text
1. 업무적으로 필요한 데이터 구조를 파악한다.
2. 필드의 기술적 속성을 Domain으로 설계한다.
3. 필드의 업무 의미를 Data Element로 설계한다.
4. 재사용이 필요한 필드 묶음은 Structure로 설계한다.
5. 실제 저장이 필요한 경우 Transparent Table을 설계한다.
6. Technical Settings를 설정한다.
7. 객체를 저장하고 활성화한다.
8. 테스트 데이터를 입력하거나 조회한다.
9. 프로그램, 화면, ALV, CDS 등에서 재사용한다.
```

M01에서는 이 흐름을 개념적으로 이해하고, M02부터 실제 객체 생성으로 들어간다.

## 9. 표준 SAP 동작과 고객사 관행 구분

SAP 교육에서 매우 중요한 태도는 “표준 동작”과 “고객사 관행”을 구분하는 것이다.

예를 들어 어떤 고객사에서는 다음과 같은 규칙을 사용할 수 있다.

```text
Domain Prefix: ZDM_
Data Element Prefix: ZDE_
Table Prefix: ZT_
Structure Prefix: ZS_
```

그러나 다른 고객사는 다른 네이밍 규칙을 사용할 수 있다.

이때 중요한 것은 특정 Prefix 자체가 표준이라는 뜻이 아니다. 표준 관점에서 중요한 것은 다음이다.

| 기준 | 설명 |
|---|---|
| 고객 네임스페이스 사용 | 커스텀 객체는 보통 Z/Y 네임스페이스 사용 |
| 의미 있는 이름 | 객체 이름만 보고 역할을 추정 가능해야 함 |
| 일관성 | 프로젝트 전체에서 동일 규칙 적용 |
| 충돌 회피 | SAP 표준 객체명과 충돌하지 않도록 설계 |
| 유지보수성 | 후속 개발자가 객체 목적을 이해할 수 있어야 함 |

## 10. 초급자용 개발 흐름 예시

교육용 사용자 정보를 저장하고 싶다.

## 11. SE11 탐색 실습

### 11.1 실습 목적

이번 실습은 객체를 새로 생성하기보다 SE11에서 DDIC 객체가 어떻게 연결되어 있는지 확인하는 데 목적이 있다.

### 11.2 준비 사항

| 항목 | 내용 |
|---|---|
| 시스템 | SAP S/4HANA 또는 ABAP 학습 시스템 |
| 접속 도구 | SAP GUI 800 |
| 권한 | SE11 조회 권한 |
| 변경 작업 | 수행하지 않음 |
| 권장 테이블 | `T000`, `T005`, 또는 교육 시스템의 Demo Table |

[추정] 일부 교육 시스템에는 `SCARR`, `SPFLI`, `SFLIGHT` 같은 Demo Table이 제공될 수 있다. 시스템에 없을 경우 표준 조회 가능한 테이블을 사용한다.

### 11.3 실습 절차: SE11에서 테이블 구조 확인

1. SAP GUI에 로그인한다.
2. 명령창에 `SE11`을 입력한다.
3. Database Table을 선택한다.
4. 조회 가능한 표준 테이블명을 입력한다.
   - 예: `T000`
   - 또는 교육 시스템에서 제공하는 Demo Table
5. Display를 선택한다.
6. Fields 탭을 확인한다.
7. 각 필드가 어떤 Data Element를 사용하는지 확인한다.
8. Data Element를 더블클릭해 상세 화면으로 이동한다.
9. Data Element가 어떤 Domain을 참조하는지 확인한다.
10. 뒤로 돌아와 전체 연결 관계를 정리한다.

### 11.4 실습 중 기록할 내용

| 기록 항목 | 예시 |
|---|---|
| 확인한 테이블 | T000 |
| 확인한 필드 | MANDT |
| Data Element | MANDT |
| Domain | MANDT |
| 느낀 점 | 필드가 직접 타입만 가지는 것이 아니라 Data Element와 Domain 계층으로 연결됨 |

### 11.5 실습 결과 정리 예시

```text
SE11에서 테이블 필드를 확인해 보니, 각 필드는 단순히 CHAR, NUMC 같은 타입만 가지는 것이 아니라 Data Element를 참조하고 있었다.
Data Element를 따라가면 다시 Domain으로 연결되었다.
이를 통해 SAP Dictionary는 기술 타입과 업무 의미를 계층적으로 분리한다는 점을 확인했다.
```

## 13. 오류 상황과 검증 포인트

### 13.1 오류 상황 1: 객체가 조회되지 않음

| 항목 | 내용 |
|---|---|
| 증상 | SE11에서 테이블 또는 DDIC 객체를 입력했지만 존재하지 않음 |
| 원인 | 객체명 오타, 시스템에 해당 Demo Object 없음, 권한 부족 |
| 해결 | 이름 재확인, 다른 표준 테이블 사용, 권한 확인 |

### 13.2 오류 상황 2: Display는 가능하지만 Change가 불가능함

| 항목 | 내용 |
|---|---|
| 증상 | 객체 조회는 가능하지만 변경 버튼 사용 불가 |
| 원인 | 권한 부족, SAP 표준 객체 변경 제한, 객체 Lock 상태 |
| 해결 | 표준 객체는 변경하지 않음, Z/Y 객체에서만 실습, 권한 요청 |

### 13.3 오류 상황 3: 객체가 비활성 상태임

| 항목 | 내용 |

| 원인 | 저장만 하고 Activate하지 않음, 참조 객체 오류 |
| 해결 | 선행 객체부터 순서대로 활성화 |

### 13.4 오류 상황 4: Transport Request 선택 요구

| 항목 | 내용 |
|---|---|
| 증상 | 객체 저장 시 전송 요청을 선택하라는 팝업 발생 |

| 해결 | 교육 시스템 정책에 따라 Local Object 또는 지정 Transport 사용 |

### 13.5 오류 상황 5: 표준 객체를 변경하려고 함

| 항목 | 내용 |
|---|---|
| 증상 | SAP 표준 테이블이나 Data Element를 변경하려고 시도 |

| 해결 | 표준 객체는 조회만 하고, 실습은 Z/Y 객체로 수행 |

## 14. 실무 관점의 주의사항

### 14.1 DDIC 변경은 파급효과가 크다

DDIC 객체는 여러 프로그램, 화면, 인터페이스, CDS View, ALV 출력에서 참조될 수 있다.

Data Element 하나의 필드 라벨을 바꾸는 것은 단순해 보이지만, 해당 Data Element를 사용하는 여러 화면의 표시 텍스트에 영향을 줄 수 있다.

Domain의 길이를 변경하면 그 Domain을 참조하는 Data Element, Table Field, Program Type에 영향을 줄 수 있다.

따라서 실무에서는 DDIC 변경 전 다음을 확인한다.

| 확인 항목 | 설명 |
|---|---|
| Where-Used List | 어떤 객체가 참조하는지 확인 |
| 데이터 보존 영향 | 기존 DB 데이터가 잘리는지 확인 |
| 인터페이스 영향 | 외부 연동 필드 길이와 타입 확인 |
| 화면 영향 | 라벨, 입력 길이, F4 Help 영향 확인 |
| 성능 영향 | 테이블 구조 변경, 인덱스, 버퍼링 영향 확인 |
| 운영 반영 영향 | Transport 순서, 다운타임 필요 여부 확인 |

### 14.2 DDIC 설계는 후속 개발 품질을 좌우한다

초급자는 DDIC를 “ABAP 전에 잠깐 배우는 설정” 정도로 생각하기 쉽다.

하지만 실무에서는 DDIC 설계가 나쁘면 이후 프로그램이 복잡해진다.

| 나쁜 DDIC 설계 | 후속 문제 |
|---|---|
| 필드 의미가 불명확함 | 프로그램마다 해석이 달라짐 |
| 라벨이 비어 있음 | ALV/화면 품질 저하 |
| 타입 길이가 부적절함 | 데이터 잘림 또는 불필요한 공간 사용 |
| 모든 값을 CHAR로 처리 | 날짜, 금액, 수량 처리 오류 |
| 재사용 기준 없이 객체 난립 | 유지보수 비용 증가 |

### 14.3 초급 단계에서 기억할 원칙

```text
기술 타입은 Domain에서 생각한다.
업무 의미는 Data Element에서 생각한다.
필드 묶음은 Structure에서 생각한다.
데이터 저장은 Transparent Table에서 생각한다.
개발 객체는 저장 후 Activate해야 한다.
표준 객체는 조회하고, 실습은 Z/Y 객체로 한다.
```

| 3 | SE11에서 표준 테이블 탐색 | 15분 |
| 4 | Data Element와 Domain 연결 확인 | 10분 |
| 5 | ADT에서 동일 객체 검색 | 10분 |
| 6 | 오류 케이스와 실무 주의사항 정리 | 10분 |
| 7 | 퀴즈 및 질의응답 | 5분 |

### 17.2 강의 중 강조할 문장

```text
DDIC는 테이블을 만드는 화면이 아니라 SAP 데이터 의미를 중앙에서 관리하는 계층입니다.
ABAP 프로그램은 DDIC 위에서 데이터를 읽고, 처리하고, 출력합니다.
저장과 활성화는 다릅니다.
표준 객체는 조회하고, 실습은 Z/Y 객체로 진행합니다.
```

### 17.3 초급자에게 피해야 할 설명 방식

| 피해야 할 방식 | 이유 |
|---|---|
| 처음부터 Technical Settings 깊게 설명 | M06에서 다룰 내용이며 초급자에게 부담 |

## 19. 용어 정리

| 용어 | 설명 |
|---|---|
| DDIC | SAP Dictionary의 약어. ABAP 시스템의 데이터 정의를 중앙에서 관리하는 영역 |
| SAP Dictionary | Domain, Data Element, Structure, Table 등 데이터 정의 객체를 관리하는 SAP 영역 |
| SE11 | SAP GUI에서 DDIC 객체를 조회하고 관리하는 대표 트랜잭션 |
| ADT | Eclipse 기반 ABAP Development Tools |
| Repository Object | ABAP Repository에서 관리되는 개발 객체 |
| Domain | 데이터의 기술적 속성을 정의하는 DDIC 객체 |
| Data Element | 데이터의 업무 의미와 필드 라벨을 정의하는 DDIC 객체 |
| Structure | 여러 필드를 묶은 재사용 가능한 구조 타입 |
| Transparent Table | 실제 데이터베이스에 저장되는 테이블 정의 |
| Activation | 저장된 개발 객체를 시스템에서 사용할 수 있는 런타임 객체로 반영하는 과정 |
| Transport Request | 개발 객체 변경 사항을 다른 시스템으로 이동하기 위한 전송 단위 |
| Where-Used List | 특정 객체가 어디에서 사용되는지 확인하는 기능 |
