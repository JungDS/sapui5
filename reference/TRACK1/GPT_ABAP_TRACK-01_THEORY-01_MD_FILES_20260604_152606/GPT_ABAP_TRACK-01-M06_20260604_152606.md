```text
→ 생성한 테이블이 실제로 사용할 수 있는 상태인지 확인한다.
```

## 3. Technical Settings란 무엇인가?

Technical Settings는 Transparent Table이 데이터베이스에 생성될 때 필요한 기술적 저장 속성을 정의하는 설정이다.

ABAP Dictionary에서 Transparent Table을 만들 때 개발자는 필드를 정의한다. 예를 들어 다음과 같은 테이블을 생각할 수 있다.

| Field | Key | Data Element | 설명 |
|---|---:|---|---|
| MANDT | X | MANDT | Client |
| USER_ID | X | ZDE_JHY_USER_ID | 사용자 ID |
| USER_NAME |  | ZDE_JHY_USER_NAME | 사용자명 |
| STATUS |  | ZDE_JHY_STATUS | 상태 |
| CREATED_BY |  | SYUNAME | 생성자 |
| CREATED_ON |  | DATS | 생성일 |

이 필드 정의는 “테이블이 어떤 컬럼을 가지는가”를 말한다.  
하지만 데이터베이스 관점에서는 추가 질문이 남는다.

```text
이 테이블은 어떤 종류의 데이터를 저장하는가?
데이터가 얼마나 커질 것으로 예상하는가?
Application Server Buffer를 사용할 것인가?
변경 로그를 고려해야 하는가?
```

이런 질문에 답하는 영역이 Technical Settings이다.

---

## 4. 왜 Technical Settings를 배워야 하는가?

초급자는 처음에 “필드만 만들고 활성화하면 끝 아닌가?”라고 생각하기 쉽다.  
하지만 SAP 시스템에서 테이블은 단순한 개발자 개인 객체가 아니라 여러 계층이 함께 사용하는 Repository 객체이다.

Technical Settings가 중요한 이유는 다음과 같다.

| 관점 | 의미 |
|---|---|
| 데이터베이스 저장 | 테이블이 DB에 생성될 때 저장 특성에 영향을 준다. |
| 운영 안정성 | 테이블의 성격을 잘못 정의하면 운영 관리 기준이 흔들릴 수 있다. |
| 성능 | Buffering 설정은 읽기 성능과 데이터 정합성에 영향을 준다. |
| 유지보수 | 테이블이 마스터성인지, 트랜잭션성인지 구분하는 데 도움을 준다. |
| 활성화 | 일부 시스템에서는 Technical Settings 미설정 또는 부적절한 설정이 활성화 오류나 경고로 이어질 수 있다. |

초급 단계에서는 모든 기술 세부 사항을 암기할 필요는 없다.  
다만 “테이블 생성은 필드 정의 + 기술 설정 + 활성화 + 데이터 확인까지가 한 흐름”이라는 감각을 가져야 한다.

## 5. Technical Settings의 주요 구성요소

대표적인 Technical Settings 항목은 다음과 같다.

| 항목 | 초급자 설명 |
|---|---|
| Data Class | 테이블에 저장되는 데이터의 성격 |
| Size Category | 예상 데이터 크기 범주 |
| Buffering | Application Server Buffer 사용 여부 |
| Logging | 변경 로그 기록 관련 설정 |
| Storage 관련 옵션 | DB 저장 방식과 관련된 기술 설정 |

이 모듈에서는 DDIC 초급 단계에 맞춰 Data Class, Size Category, Buffering, 데이터 확인 흐름을 중심으로 다룬다.

## 6. Data Class

### 6.1 Data Class의 의미

Data Class는 테이블에 저장되는 데이터가 어떤 성격을 가지는지 분류하는 설정이다.

SAP 시스템에서 데이터는 일반적으로 다음과 같이 구분할 수 있다.

| 데이터 유형 | 설명 | 예시 |
|---|---|---|
| 마스터 데이터 | 비교적 안정적으로 유지되는 기준 데이터 | 고객, 자재, 공급업체 |
| 트랜잭션 데이터 | 업무 처리 과정에서 계속 발생하는 거래 데이터 | 판매오더, 구매오더, 전표 |
| 조직/커스터마이징 데이터 | 시스템 설정이나 조직 구조 관련 데이터 | 회사코드 설정, 플랜트 설정 |

Data Class는 이런 데이터 성격을 기술적으로 구분하는 데 사용된다.

### 6.2 대표 Data Class 예시

시스템과 릴리스에 따라 표시 방식은 다를 수 있지만, 전통적인 DDIC 학습에서 자주 설명하는 분류는 다음과 같다.

| Data Class | 일반적 의미 | 초급자 해석 |
|---|---|---|
| APPL0 | Master Data | 기준정보 성격의 데이터 |
| APPL1 | Transaction Data | 업무 처리 결과로 계속 쌓이는 데이터 |
| APPL2 | Organizational / Customizing Data | 조직 구조나 설정 성격의 데이터 |

> [추정] 교육용 Z 테이블에서는 실습 목적상 APPL0 또는 APPL1을 선택해도 학습 진행에는 큰 문제가 없을 수 있다. 다만 실제 프로젝트에서는 데이터 성격, 운영 정책, 저장소 관리 기준에 맞춰 결정해야 한다.

### 6.3 교육용 테이블에서의 선택 기준

이번 Section의 예제 테이블이 `ZT_JHY_USER`와 같은 사용자 정보성 테이블이라면 학습 목적상 다음처럼 판단할 수 있다.

| 테이블 성격 | 권장 Data Class 판단 |
|---|---|
| 사용자 기본정보처럼 기준정보 성격 | APPL0 |
| 로그나 이력처럼 계속 쌓이는 거래성 데이터 | APPL1 |
| 설정값이나 코드값 관리 목적 | APPL2 또는 커스터마이징 성격 검토 |

초급 과정에서는 “무조건 APPL0”처럼 외우기보다, 다음 질문을 스스로 던지는 것이 좋다.

```text
이 테이블은 기준정보인가?
업무 처리마다 계속 증가하는 데이터인가?
시스템 설정값인가?
운영 중 사용자가 자주 변경하는가?
데이터가 대량으로 쌓일 가능성이 있는가?
```

## 7. Size Category

### 7.1 Size Category의 의미

Size Category는 테이블에 저장될 것으로 예상되는 데이터량을 나타내는 설정이다.

초급자 관점에서는 다음 정도로 이해하면 된다.

```text
Size Category = 이 테이블이 어느 정도 크기로 커질 것인지에 대한 예상 범주
```

교육용 실습 테이블은 데이터가 많아야 몇 건에서 수십 건 정도이므로 가장 작은 범주를 사용해도 충분하다.

### 7.2 왜 필요한가?

Size Category는 데이터베이스 저장 영역과 관련된 기술적 판단에 사용된다.  
과거 SAP 시스템에서는 테이블 생성 시 저장 공간 산정과 관련하여 중요한 의미를 가졌고, 현재도 DDIC의 기술적 속성으로 남아 있다.

초급자가 기억할 포인트는 다음이다.

| 포인트 | 설명 |
|---|---|
| 정확한 건수 예측이 어렵다 | 실무에서는 예상 증가량을 기준으로 대략 판단한다. |
| 교육용 테이블은 작게 설정한다 | 실습 테이블은 대량 데이터가 아니므로 작은 값이 적절하다. |
| 운영 테이블은 임의 설정 금지 | 실제 프로젝트에서는 Basis/DB 운영 기준과 연계될 수 있다. |

### 7.3 예시 판단

| 테이블 | 예상 데이터량 | Size Category 관점 |
|---|---:|---|
| ZT_JHY_USER | 수십 건 | 가장 작은 범주 |
| ZT_SALES_LOG | 수십만 건 이상 가능 | 운영 기준 검토 필요 |
| ZT_CODE_STATUS | 몇 건 또는 수십 건 | 작은 범주 |

## 8. Buffering

### 8.1 Buffering이란?

Buffering은 데이터베이스 테이블의 데이터를 Application Server 메모리에 보관하여 읽기 성능을 높이는 기능이다.

쉽게 표현하면 다음과 같다.

```text
매번 DB에 직접 물어보지 않고,
자주 읽는 데이터를 Application Server 쪽에 임시로 보관해 빠르게 읽는 방식
```

하지만 Buffering은 항상 좋은 기능이 아니다.  
읽기 성능은 좋아질 수 있지만, 데이터 변경이 잦거나 정합성이 중요한 테이블에서는 문제가 될 수 있다.

### 8.2 Buffering을 조심해야 하는 이유

| 이유 | 설명 |
|---|---|
| 데이터 정합성 | 버퍼에 오래된 데이터가 남아 있을 수 있다. |
| 변경 빈도 | 자주 변경되는 테이블은 버퍼 이점보다 위험이 커질 수 있다. |
| 대량 데이터 | 큰 테이블을 버퍼링하면 메모리 부담이 생길 수 있다. |
| 실무 판단 필요 | Basis, 성능, 업무 특성을 함께 고려해야 한다. |

### 8.3 초급 과정의 권장 관점

초급 교육용 테이블에서는 Buffering을 먼저 켜기보다, 기본적으로 꺼둔 상태로 학습하는 것이 안전하다.

| 테이블 유형 | Buffering 판단 |
|---|---|
| 자주 읽고 거의 변하지 않는 작은 코드 테이블 | 검토 가능 |
| 자주 변경되는 트랜잭션 테이블 | 일반적으로 비권장 |
| 대량 테이블 | 신중 검토 |
| 교육용 기본 실습 테이블 | 꺼두고 진행 권장 |

> [추정] 교육용 Z 테이블에서 Buffering을 꺼두는 방식은 초급 학습자가 데이터 정합성 혼란 없이 DDIC 생성 흐름을 익히기에 적합하다.

## 9. Logging

Logging은 테이블 데이터 변경에 대한 로그 기록과 관련된 설정이다.

초급 단계에서는 다음 정도로만 이해한다.

```text
Logging은 누가, 언제, 어떤 데이터를 변경했는지 추적할 필요가 있는 테이블에서 검토하는 설정이다.
```

하지만 실제 로그 기록 여부는 시스템 설정, 클라이언트 설정, 테이블 속성, 운영 정책과 연결될 수 있으므로 단순히 체크박스 하나로만 판단하면 안 된다.

초급 학습에서 중요한 점은 다음이다.

| 관점 | 설명 |
|---|---|
| 감사 추적 | 변경 이력 확인이 필요한 데이터인지 판단 |
| 운영 정책 | 고객사 또는 프로젝트 정책을 따른다 |
| 성능 영향 | 변경 로그 기록은 운영 부하와도 연결될 수 있다 |
| 교육 단계 | 개념만 이해하고 심화 설정은 후속 과정에서 다룬다 |

## 10. Technical Settings 설정 절차

### 10.1 SE11에서 설정하는 흐름

Transparent Table을 생성한 후 Technical Settings는 다음 흐름으로 접근한다.

```text
SE11
→ Database Table 입력
→ Change 또는 Create
→ Fields 정의
→ Technical Settings 버튼
→ Data Class 선택
→ Size Category 선택
→ Buffering 설정 확인
→ Save
→ Activate
```

### 10.2 예제 설정

교육용 테이블 `ZT_JHY_USER` 기준 예시이다.

| 항목 | 예시 값 | 설명 |
|---|---|---|
| Data Class | APPL0 | 사용자 기본정보 성격으로 가정 |
| Size Category | 0 또는 가장 작은 범주 | 교육용 소량 데이터 |
| Buffering | Buffering not allowed 또는 비활성 | 초급 실습에서는 정합성 우선 |
| Logging | 필요 시 검토 | 기본 실습에서는 심화 제외 |

> [추정] 실제 SAP GUI 화면의 선택값 명칭은 시스템 릴리스, 언어, 설정에 따라 약간 다르게 표시될 수 있다.

## 11. 테이블 활성화 전 점검

Technical Settings를 설정한 뒤 바로 Activate하기 전에 다음 항목을 확인한다.

| 점검 항목 | 확인 내용 |
|---|---|
| Short Description | 테이블 설명이 비어 있지 않은가 |
| Delivery Class | 테이블 성격에 맞게 설정했는가 |
| MANDT | Client-dependent 테이블이면 첫 번째 Key로 있는가 |
| Key Field | 최소한의 유일 식별 키가 정의되었는가 |
| Field Type | 각 필드가 적절한 Data Element를 참조하는가 |
| Technical Settings | Data Class, Size Category가 설정되었는가 |
| Enhancement Category | Structure/Table 확장 관련 설정이 필요한가 |
| Activation Error | 오류 메시지를 확인했는가 |

초급자가 자주 놓치는 점은 “활성화 버튼을 눌렀다”와 “오류 없이 정상 활성화되었다”를 구분하지 않는 것이다.  
반드시 시스템 메시지와 상태 표시를 확인해야 한다.

## 14. SE16과 SE16N

### 14.1 SE16

SE16은 전통적인 Data Browser 트랜잭션이다.

```text
T-Code: SE16
Table Name: ZT_JHY_USER
```

조건을 입력하고 Execute하면 테이블 데이터를 조회할 수 있다.

### 14.2 SE16N

SE16N은 General Table Display 트랜잭션으로, 실무에서 데이터 확인용으로 자주 사용된다.

```text
T-Code: SE16N
Table: ZT_JHY_USER
```

초급 교육에서는 SE16N을 통해 다음을 확인한다.

| 확인 항목 | 설명 |
|---|---|
| 필드 목록 | DDIC에서 만든 필드가 조회 화면에 보이는가 |
| 선택 조건 | 특정 USER_ID나 STATUS로 조회 가능한가 |
| 결과 리스트 | 입력한 테스트 데이터가 정상 표시되는가 |
| Field Label | Data Element의 라벨이 화면에 반영되는지 확인 가능 |

### 14.3 주의점

SE16N은 시스템 권한과 설정에 따라 데이터 변경이 제한될 수 있다.  
또한 운영 시스템에서 직접 테이블 데이터를 변경하는 것은 매우 위험할 수 있다.

초급자에게 반드시 강조해야 하는 원칙은 다음이다.

```text
Data Browser는 기본적으로 조회 도구로 이해한다.
운영 데이터 변경은 표준 트랜잭션, 유지보수 뷰, 프로그램, 승인된 절차를 사용한다.
비공식적인 SE16N 편집 방식은 교육하지 않는다.
```

## 17. ABAP 프로그램에서 확인하는 최소 예제

후속 Section에서 ABAP 기본 문법과 Open SQL을 더 자세히 다루지만, DDIC 테이블이 프로그램에서 사용된다는 감각을 위해 최소 예제를 확인한다.

```abap
REPORT zjhy_check_user_table.

SELECT user_id,
       user_name,
       status,
       created_by,
       created_on
  FROM zt_jhy_user
  INTO TABLE @DATA(lt_user).

IF sy-subrc = 0.
  LOOP AT lt_user INTO DATA(ls_user).
    WRITE: / ls_user-user_id,
             ls_user-user_name,
             ls_user-status,
             ls_user-created_by,
             ls_user-created_on.
  ENDLOOP.
ELSE.
  WRITE: / 'No data found.'.
ENDIF.
```

초급자는 이 코드의 모든 문법을 완벽히 이해하지 않아도 된다.  
현재 단계에서 이해할 포인트는 다음이다.

```text
DDIC에서 만든 Transparent Table은 ABAP Open SQL의 FROM 대상이 될 수 있다.
테이블 필드는 SELECT 문에서 조회 대상이 된다.
조회 결과는 ABAP 프로그램 안에서 출력하거나 가공할 수 있다.
```

## 18. 자주 발생하는 오류와 해결

### 18.1 Technical Settings 누락

| 항목 | 내용 |
|---|---|
| 현상 | 활성화 시 Technical Settings 관련 경고 또는 오류 발생 |
| 원인 | Data Class 또는 Size Category 설정 누락 |
| 해결 | Technical Settings 화면에서 필수 항목 설정 후 재활성화 |

### 18.2 테이블이 활성화되지 않음

| 항목 | 내용 |
|---|---|
| 현상 | SE16N에서 테이블 조회 불가 |
| 원인 | DDIC 객체가 비활성 상태 |
| 해결 | SE11에서 Activate 수행 및 오류 메시지 확인 |

### 18.3 필드 타입 오류

| 항목 | 내용 |
|---|---|
| 현상 | 테이블 활성화 실패 |
| 원인 | 존재하지 않는 Data Element 또는 비활성 Data Element 참조 |
| 해결 | 참조 객체를 먼저 활성화한 후 테이블 재활성화 |

### 18.4 테스트 데이터 입력 실패

| 항목 | 내용 |
|---|---|
| 현상 | 데이터 저장이 되지 않음 |
| 원인 | Key 중복, Fixed Value 위반, 권한 부족, 클라이언트 설정 |
| 해결 | Key 값 확인, Domain Fixed Value 확인, 권한 및 시스템 설정 확인 |

### 18.5 조회 결과 없음

| 항목 | 내용 |
|---|---|
| 현상 | SE16N 또는 ABAP SELECT 결과가 비어 있음 |
| 원인 | 데이터 미입력, 다른 Client에 입력, 조회 조건 오류 |
| 해결 | MANDT/Client 확인, 조건 제거 후 전체 조회, 테스트 데이터 재확인 |

## 22. 평가 문제

### 22.1 객관식

#### Q1. Technical Settings의 주요 목적은 무엇인가?

A. ABAP 프로그램의 실행 순서를 정의한다.  
B. 테이블의 필드 라벨을 정의한다.  
C. Transparent Table의 기술적 저장 속성을 정의한다.  
D. 사용자의 로그인 권한을 정의한다.

정답: C

#### Q2. Data Class가 주로 나타내는 것은 무엇인가?

A. 필드 출력 길이  
B. 테이블 데이터의 성격  
C. 프로그램 주석 여부  
D. Selection Screen 입력 조건

정답: B

#### Q3. Buffering을 무조건 켜면 안 되는 이유로 가장 적절한 것은?

A. 테이블 이름이 길어지기 때문이다.  
B. 모든 필드가 Key가 되기 때문이다.  
C. 오래된 데이터가 버퍼에 남아 정합성 문제가 생길 수 있기 때문이다.  
D. ABAP 프로그램을 작성할 수 없기 때문이다.

정답: C

### 22.2 서술형

#### Q1. Size Category를 교육용 테이블에서 작게 설정해도 되는 이유를 설명하시오.

모범 답안:  
교육용 테이블은 일반적으로 테스트 데이터가 소량이며, 운영 환경처럼 대량 데이터가 장기간 누적되는 목적이 아니기 때문이다. 따라서 가장 작은 범주로 설정해도 학습 목적에는 충분하다.

#### Q2. SE16N에서 데이터가 조회되지 않을 때 확인할 항목을 세 가지 쓰시오.

모범 답안:  
테이블이 활성화되었는지, 테스트 데이터가 실제로 입력되었는지, 현재 Client와 데이터의 MANDT가 일치하는지, 조회 조건이 너무 제한적이지 않은지 등을 확인한다.

#### Q3. Buffering을 켜기 전에 고려해야 할 기준을 설명하시오.

모범 답안:  
테이블의 데이터 변경 빈도, 읽기 빈도, 데이터 정합성 요구 수준, 테이블 크기, 운영 정책을 고려해야 한다. 자주 변경되는 트랜잭션성 테이블은 Buffering이 적합하지 않을 수 있다.

## 25. 마무리

Technical Settings와 데이터 확인은 초급자가 DDIC 객체를 “만들었다”에서 “실제로 사용할 수 있다”로 넘어가는 마지막 확인 단계이다.

이 단계에서 중요한 것은 복잡한 DB 옵션을 모두 암기하는 것이 아니다.  
중요한 것은 다음의 실무 감각이다.

```text
테이블은 업무 의미와 기술 속성을 함께 가진다.
필드 정의와 Technical Settings는 서로 보완 관계이다.
활성화와 데이터 확인은 개발 완료의 기본 검증 절차이다.
조회 결과가 없을 때는 테이블, 데이터, Client, 조건을 차례로 확인한다.
```

이 감각이 잡히면 이후 ABAP 프로그램, Open SQL, Internal Table, ALV 학습에서 DDIC 객체를 훨씬 자연스럽게 사용할 수 있다.
