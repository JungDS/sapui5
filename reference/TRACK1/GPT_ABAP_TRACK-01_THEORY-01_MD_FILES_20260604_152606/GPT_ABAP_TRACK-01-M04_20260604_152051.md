## 3. Structure란 무엇인가?

### 3.1 쉬운 정의

Structure는 여러 개의 필드를 하나의 이름 있는 타입으로 묶은 ABAP Dictionary 객체이다.

예를 들어 사용자 정보를 프로그램에서 다루려면 다음과 같은 필드들이 필요할 수 있다.

| 필드 | 의미 |
|---|---|
| USER_ID | 사용자 ID |
| USER_NAME | 사용자 이름 |
| STATUS | 사용자 상태 |
| CREATED_BY | 생성자 |
| CREATED_ON | 생성일 |

이 필드들을 매 프로그램마다 따로 정의하면 반복이 많아지고, 필드 길이나 의미가 서로 달라질 수 있다.  
이때 DDIC Structure로 한 번 정의해두면 여러 프로그램에서 동일한 구조를 재사용할 수 있다.

```text
ZS_GPT_USER_BASIC
 ├─ USER_ID
 ├─ USER_NAME
 ├─ STATUS
 ├─ CREATED_BY
 └─ CREATED_ON
```

### 3.2 표준 SAP 관점의 의미

SAP Dictionary의 Structure는 시스템 Repository에 저장되는 전역 타입이다.  
즉, 특정 ABAP 프로그램 안에서만 존재하는 로컬 `TYPES`와 달리, 시스템 내 여러 개발 객체에서 공통으로 참조할 수 있다.

Structure는 다음과 같은 곳에서 자주 사용된다.

- ABAP 프로그램의 Work Area
- Internal Table의 Line Type
- Function Module의 파라미터
- Class Method의 Importing/Exporting/Changing 파라미터
- Screen/Dynpro의 입출력 구조
- ALV 출력 구조
- BAPI 또는 RFC 인터페이스 구조
- CDS/RAP 학습 전 데이터 구조 이해용 기초 모델

## 4. Structure와 Transparent Table의 차이

초급자가 가장 많이 혼동하는 지점은 Structure와 Transparent Table이다.

둘 다 필드 목록을 가진다.  
하지만 목적은 완전히 다르다.

| 구분 | Structure | Transparent Table |
|---|---|---|
| 주 목적 | 데이터 타입 정의 | 실제 데이터 저장 |
| DB 테이블 생성 여부 | 생성되지 않음 | 생성됨 |
| 데이터 보관 위치 | 런타임 메모리 | 데이터베이스 |
| Key 필드 필수 여부 | 필수 아님 | 일반적으로 필요 |
| Technical Settings 필요 여부 | 필요 없음 | 필요 |
| SE16N 조회 가능 여부 | 불가 | 가능 |
| 예시 | `ZS_GPT_USER_BASIC` | `ZT_GPT_USER` |
| 학습 시점 | 현재 모듈 | 다음 모듈 |

초급자 관점에서 다음처럼 이해하면 쉽다.

```text
Structure = 데이터 모양을 정의하는 설계도
Transparent Table = 그 모양으로 실제 데이터를 저장하는 DB 테이블
```

Structure는 설계도이므로 자체적으로 데이터를 저장하지 않는다.  
프로그램이 실행될 때 Structure 타입의 변수나 Internal Table을 만들면, 그때 메모리 안에 데이터가 담긴다.

## 5. Component란 무엇인가?

Structure를 구성하는 각각의 필드를 Component라고 한다.

예를 들어 다음 Structure가 있다고 하자.

```text
Structure: ZS_GPT_USER_BASIC
```

| Component | Component Type | 설명 |
|---|---|---|
| USER_ID | ZDE_GPT_USER_ID | 사용자 ID |
| USER_NAME | ZDE_GPT_USER_NAME | 사용자 이름 |
| STATUS | ZDE_GPT_STATUS | 사용자 상태 |
| CREATED_BY | SYUNAME | 생성자 |
| CREATED_ON | DATS | 생성일 |

여기서 `USER_ID`, `USER_NAME`, `STATUS` 등이 Component이다.

### 5.1 Component 이름

Component 이름은 Structure 안에서 유일해야 한다.  
같은 Structure 안에 동일한 Component 이름을 두 번 정의할 수 없다.

권장 사항은 다음과 같다.

| 기준 | 설명 |
|---|---|
| 대문자 사용 | SAP GUI SE11에서는 일반적으로 대문자 객체명이 사용된다. |
| 의미 있는 이름 | `FIELD1`, `FIELD2`보다 `USER_ID`, `STATUS`가 좋다. |
| 약어 남발 금지 | 초급 학습과 유지보수성을 위해 의미를 읽을 수 있어야 한다. |
| 업무 의미 기준 | 기술 타입보다 업무 의미가 드러나야 한다. |

### 5.2 Component Type

Component Type에는 일반적으로 Data Element를 사용한다.

예를 들어 `USER_ID` 필드에는 `CHAR10`을 직접 입력할 수도 있지만, 더 좋은 방식은 `ZDE_GPT_USER_ID` 같은 Data Element를 사용하는 것이다.

```text
권장:
USER_ID TYPE ZDE_GPT_USER_ID

비권장:
USER_ID TYPE CHAR10
```

Data Element를 사용하면 다음 장점이 있다.

| 장점 | 설명 |
|---|---|
| 의미 재사용 | 같은 업무 의미를 여러 객체에서 공유할 수 있다. |
| 라벨 재사용 | Field Label이 화면, ALV 등에서 활용될 수 있다. |
| 변경 관리 | 길이나 의미 변경 시 영향 분석이 가능하다. |
| 표준 설계 흐름 | Domain → Data Element → Structure 흐름이 유지된다. |

## 6. Structure가 필요한 이유

### 6.1 반복 정의 방지

ABAP 프로그램마다 같은 필드를 매번 로컬로 정의하면 다음 문제가 생긴다.

```abap
TYPES: BEGIN OF ty_user,
         user_id   TYPE c LENGTH 10,
         user_name TYPE c LENGTH 40,
         status    TYPE c LENGTH 1,
       END OF ty_user.
```

이 코드를 여러 프로그램에 반복하면, 어떤 프로그램은 `USER_ID`를 10자리로 만들고, 다른 프로그램은 12자리로 만들 수 있다.  
이런 차이는 나중에 인터페이스, ALV, DB 저장, 데이터 변환에서 오류를 만든다.

DDIC Structure를 사용하면 다음처럼 중앙 타입을 참조할 수 있다.

```abap
DATA ls_user TYPE zs_gpt_user_basic.
```

### 6.2 의미 일관성 유지

Structure는 단순히 필드를 묶는 것이 아니라, 시스템 전체에서 같은 데이터 모양을 공유하게 해준다.

예를 들어 사용자 기본 정보가 여러 프로그램에서 쓰인다면, 하나의 Structure를 참조하는 편이 좋다.

```text
ZREPT_USER_LIST
ZREPT_USER_DETAIL
ZCL_USER_SERVICE
ZFM_USER_GET_DETAIL
```

위 객체들이 모두 `ZS_GPT_USER_BASIC`을 참조하면, 사용자 기본 정보의 구조를 일관되게 유지할 수 있다.

### 6.3 인터페이스 안정성 확보

Function Module, Class Method, RFC, BAPI에서는 파라미터 구조가 중요하다.  
Structure를 사용하면 입출력 데이터 형식을 명확하게 정의할 수 있다.

예:

```abap
METHODS get_user
  IMPORTING iv_user_id TYPE zde_gpt_user_id
  EXPORTING es_user    TYPE zs_gpt_user_basic.
```

이처럼 Structure는 프로그램 사이의 약속 역할을 한다.

## 7. SE11에서 Structure 생성하기

### 7.1 생성 대상

이번 실습에서 생성할 Structure는 다음과 같다.

```text
Structure Name: ZS_GPT_USER_BASIC
Short Description: User Basic Information Structure
```

> [추정] 앞선 모듈에서 `ZDE_GPT_USER_ID`, `ZDE_GPT_USER_NAME`, `ZDE_GPT_STATUS`를 생성했다고 가정한다. 실제 시스템에서 다른 이름을 사용했다면 본인의 Data Element 이름으로 대체한다.

### 7.2 Component 설계

| 순서 | Component | Component Type | 설명 |
|---:|---|---|---|
| 1 | USER_ID | ZDE_GPT_USER_ID | 사용자 ID |
| 2 | USER_NAME | ZDE_GPT_USER_NAME | 사용자 이름 |
| 3 | STATUS | ZDE_GPT_STATUS | 사용자 상태 |
| 4 | CREATED_BY | SYUNAME | 생성자 |
| 5 | CREATED_ON | DATS | 생성일 |

이 실습에서는 아직 DB Table을 만들지 않으므로 `MANDT`는 넣지 않는다.  
`MANDT`는 Client-dependent Transparent Table을 만들 때 중요하며, 다음 모듈에서 다룬다.

### 7.3 생성 절차

SAP GUI 800 기준 절차는 다음과 같다.

```text
1. SAP GUI 실행
2. Transaction Code 입력: SE11
3. Data Type 선택
4. Object Name에 ZS_GPT_USER_BASIC 입력
5. Create 선택
6. 팝업에서 Structure 선택
7. Short Description 입력
8. Components 탭에서 Component와 Component Type 입력
9. Save
10. Package 또는 Local Object 선택
11. Activate
```

교육용 시스템에서는 보통 `$TMP` Local Object로 저장해도 된다.  
실무 프로젝트에서는 고객사 네이밍 규칙과 패키지 정책에 따라 저장해야 한다.

## 8. 각 입력 항목의 의미

### 8.1 Data Type 선택

SE11의 첫 화면에서 `Data Type`을 선택하는 이유는 Structure가 DDIC 데이터 타입의 한 종류이기 때문이다.

Data Type 안에는 다음 유형이 포함될 수 있다.

| 유형 | 설명 |
|---|---|
| Data Element | 단일 필드 의미 정의 |
| Structure | 여러 필드의 묶음 |
| Table Type | Internal Table 타입 정의 |

초급자는 SE11에서 `Data Type`을 선택한다고 해서 모두 같은 객체가 만들어지는 것이 아니라, 생성 팝업에서 어떤 종류를 선택하느냐가 중요하다는 점을 기억해야 한다.

### 8.2 Short Description

Short Description은 Repository 객체를 설명하는 짧은 문장이다.

좋은 예:

```text
User Basic Information Structure
```

나쁜 예:

```text
test
abc
user
```

Short Description은 개발자 검색과 유지보수에 영향을 준다.  
운영 시스템에서는 수백, 수천 개의 Z 객체가 있을 수 있으므로 설명을 명확히 작성하는 습관이 중요하다.

### 8.3 Component Type

Component Type은 각 Component가 어떤 타입을 가질지 지정한다.

가능한 방식은 여러 가지가 있지만 초급 단계에서는 다음 우선순위를 권장한다.

| 우선순위 | 방식 | 설명 |
|---:|---|---|
| 1 | Data Element 사용 | 가장 권장되는 기본 방식 |
| 2 | 표준 Data Element 사용 | `SYUNAME`, `DATS` 등 |
| 3 | Built-in Type 직접 사용 | 교육용 임시 구조에서만 제한적으로 사용 |

## 9. ABAP 프로그램에서 Structure 사용하기

DDIC Structure를 생성하고 활성화하면 ABAP 프로그램에서 타입으로 사용할 수 있다.

### 9.1 단일 Work Area로 사용

```abap
REPORT zgpt_use_structure_01.

DATA ls_user TYPE zs_gpt_user_basic.

ls_user-user_id    = 'U000000001'.
ls_user-user_name  = 'Kim Beginner'.
ls_user-status     = 'A'.
ls_user-created_by = sy-uname.
ls_user-created_on = sy-datum.

WRITE: / 'User ID   :', ls_user-user_id,
       / 'User Name :', ls_user-user_name,
       / 'Status    :', ls_user-status,
       / 'Created By:', ls_user-created_by,
       / 'Created On:', ls_user-created_on.
```

이 코드는 `ZS_GPT_USER_BASIC`이라는 DDIC Structure를 기준으로 변수 `LS_USER`를 만든다.  
프로그램 실행 중 `LS_USER`는 메모리 안에 존재한다.

### 9.2 Internal Table의 Line Type으로 사용

Structure는 Internal Table의 한 줄 구조로도 사용할 수 있다.

```abap
REPORT zgpt_use_structure_02.

DATA lt_user TYPE STANDARD TABLE OF zs_gpt_user_basic.
DATA ls_user TYPE zs_gpt_user_basic.

ls_user-user_id    = 'U000000001'.
ls_user-user_name  = 'Kim Beginner'.
ls_user-status     = 'A'.
ls_user-created_by = sy-uname.
ls_user-created_on = sy-datum.
APPEND ls_user TO lt_user.

CLEAR ls_user.

ls_user-user_id    = 'U000000002'.
ls_user-user_name  = 'Lee Trainee'.
ls_user-status     = 'I'.
ls_user-created_by = sy-uname.
ls_user-created_on = sy-datum.
APPEND ls_user TO lt_user.

LOOP AT lt_user INTO ls_user.
  WRITE: / ls_user-user_id,
           ls_user-user_name,
           ls_user-status.
ENDLOOP.
```

이 예제는 Internal Table의 상세 문법을 깊게 설명하기 위한 것이 아니다.  
핵심은 DDIC Structure가 프로그램의 데이터 타입으로 재사용될 수 있다는 점이다.

Internal Table은 이후 Section에서 별도로 자세히 학습한다.

## 10. Activation의 의미

Structure를 저장한 것만으로는 충분하지 않다.  
ABAP 프로그램이나 다른 DDIC 객체에서 참조하려면 Activate가 필요하다.

### 10.1 저장과 활성화의 차이

| 구분 | 의미 |
|---|---|
| Save | Repository에 변경 내용을 저장 |
| Activate | 런타임에서 사용할 수 있는 활성 버전 생성 |

초급자가 자주 겪는 상황은 다음과 같다.

```text
Structure를 만들고 저장했는데 ABAP 프로그램에서 TYPE으로 인식되지 않는다.
```

이 경우 대부분 Structure가 Activate되지 않았거나, 참조한 Component Type 중 일부가 아직 Activate되지 않은 상태이다.

### 10.2 활성화 순서

Structure는 내부에서 Data Element를 참조한다.  
따라서 참조 대상이 먼저 활성화되어 있어야 한다.

권장 순서:

```text
1. Domain Activate
2. Data Element Activate
3. Structure Activate
4. ABAP Program Syntax Check
```

---

## 11. 정상 흐름과 오류 흐름

### 11.1 정상 흐름

```text
Data Element 준비
 → Structure 생성
 → Component 입력
 → Save
 → Activate
 → ABAP 프로그램에서 TYPE으로 참조
 → Syntax Check 성공
```

### 11.2 오류 흐름 1: Component Type이 존재하지 않음

상황:

```text
Component Type에 ZDE_GPT_USER_ID를 입력했는데 해당 Data Element가 존재하지 않음
```

가능한 원인:

- Data Element 이름 오타
- Data Element 미생성
- Data Element 미활성화
- 다른 패키지/시스템에만 존재하는 객체명 사용

해결:

```text
1. SE11에서 Data Element 존재 여부 확인
2. 이름 오타 확인
3. Data Element Activate 여부 확인
4. 다시 Structure Activate
```

### 11.3 오류 흐름 2: Component 이름 중복

상황:

```text
USER_ID Component를 두 번 입력
```

문제:

Structure 안에서 Component 이름은 유일해야 한다.

해결:

- 중복 Component 삭제
- 의미에 맞는 다른 이름 사용
- 같은 의미의 필드를 여러 번 넣어야 한다면 접미어를 명확히 부여

예:

```text
CREATED_BY
CHANGED_BY
```

### 11.4 오류 흐름 3: Built-in Type 직접 사용 남발

상황:

```text
USER_ID TYPE CHAR10
USER_NAME TYPE CHAR40
STATUS TYPE CHAR1
```

문제:

- Field Label 재사용 어려움
- 의미 계층 부재
- 다른 객체와 타입 불일치 가능
- 향후 테이블, ALV, 화면과 연결 시 유지보수성 저하

해결:

가능하면 Data Element를 먼저 정의하고 Structure에서 참조한다.

## 12. 실무 적용 기준

### 12.1 Structure를 사용하면 좋은 경우

| 상황 | 이유 |
|---|---|
| 여러 프로그램이 같은 데이터 묶음을 사용 | 중앙 정의로 일관성 확보 |
| Function Module 또는 Method 파라미터가 여러 필드로 구성 | 인터페이스 의미가 명확해짐 |
| ALV 출력 구조가 필요 | 출력 필드 묶음을 명확히 정의 가능 |
| 화면 입출력 구조가 필요 | Dynpro/Screen과 연결하기 쉬움 |
| 임시 계산 결과를 여러 곳에서 사용 | 재사용 가능한 타입으로 관리 가능 |

### 12.2 Structure를 굳이 만들지 않아도 되는 경우

| 상황 | 이유 |
|---|---|
| 한 프로그램 안에서만 일회성으로 사용 | 로컬 TYPES가 더 단순할 수 있음 |
| 필드가 1개뿐인 단순 값 | Data Element로 충분할 수 있음 |
| 실제 DB 저장이 목적 | Transparent Table이 필요 |
| 인터페이스로 공개할 필요가 없음 | 로컬 타입으로 충분할 수 있음 |

### 12.3 실무 판단 질문

Structure를 만들지 말지 고민될 때 다음 질문을 던진다.

```text
이 필드 묶음이 여러 프로그램에서 재사용되는가?
이 구조가 인터페이스의 입출력 형식으로 사용되는가?
이 구조의 의미를 중앙에서 관리할 필요가 있는가?
이 구조가 향후 ALV, 화면, API 출력으로 확장될 수 있는가?
이 데이터는 실제 DB에 저장되어야 하는가?
```

마지막 질문에 대한 답이 “예”라면 Structure만으로는 부족하고 Transparent Table을 검토해야 한다.

## 13. Structure 네이밍 기준

교육용 예제에서는 다음 규칙을 사용한다.

| 객체 유형 | Prefix | 예시 |
|---|---|---|
| Domain | ZD_ | ZD_GPT_STATUS |
| Data Element | ZDE_ | ZDE_GPT_STATUS |
| Structure | ZS_ | ZS_GPT_USER_BASIC |
| Transparent Table | ZT_ | ZT_GPT_USER |
| Table Type | ZTT_ | ZTT_GPT_USER |

Structure 이름은 보통 `ZS_`로 시작하도록 정의한다.

좋은 이름:

```text
ZS_GPT_USER_BASIC
ZS_GPT_ORDER_HEADER
ZS_GPT_FLIGHT_INFO
```

나쁜 이름:

```text
ZS_TEST
ZS_TEMP
ZS_DATA
ZS_ABC
```

이름만 보고 구조의 의미를 추측할 수 있어야 한다.

## 14. 실습: 사용자 기본 정보 Structure 생성

### 14.1 실습 목표

SE11에서 `ZS_GPT_USER_BASIC` Structure를 생성하고 ABAP 프로그램에서 타입으로 사용하는 흐름을 경험한다.

### 14.2 준비물

앞선 모듈에서 다음 Data Element가 준비되어 있다고 가정한다.

| Data Element | 의미 |
|---|---|
| ZDE_GPT_USER_ID | 사용자 ID |
| ZDE_GPT_USER_NAME | 사용자 이름 |
| ZDE_GPT_STATUS | 사용자 상태 |

해당 Data Element가 없다면 시스템에 존재하는 본인의 교육용 Data Element 이름으로 대체한다.

### 14.3 Step 1 — SE11 실행

```text
Transaction Code: SE11
```

`Data Type`을 선택하고 이름에 다음을 입력한다.

```text
ZS_GPT_USER_BASIC
```

### 14.4 Step 2 — Structure 선택

Create 버튼을 누르면 객체 유형 선택 팝업이 표시된다.  
여기서 `Structure`를 선택한다.

### 14.5 Step 3 — Short Description 입력

```text
User Basic Information Structure
```

### 14.6 Step 4 — Component 입력

| Component | Component Type |
|---|---|
| USER_ID | ZDE_GPT_USER_ID |
| USER_NAME | ZDE_GPT_USER_NAME |
| STATUS | ZDE_GPT_STATUS |
| CREATED_BY | SYUNAME |
| CREATED_ON | DATS |

### 14.7 Step 5 — 저장

교육 시스템에서는 Local Object로 저장할 수 있다.

```text
Local Object: $TMP
```

실무 시스템에서는 반드시 프로젝트 Package와 Transport 정책을 따른다.

### 14.8 Step 6 — 활성화

Activate 버튼을 눌러 Structure를 활성화한다.

정상적으로 활성화되면 하단 상태 메시지에 활성화 완료 메시지가 표시된다.

### 14.9 Step 7 — 프로그램에서 확인

다음 간단한 Report를 생성하여 Structure가 타입으로 인식되는지 확인한다.

```abap
REPORT zgpt_check_structure.

DATA ls_user TYPE zs_gpt_user_basic.

ls_user-user_id    = 'U000000001'.
ls_user-user_name  = 'Kim Beginner'.
ls_user-status     = 'A'.
ls_user-created_by = sy-uname.
ls_user-created_on = sy-datum.

WRITE: / 'Structure check:',
       / ls_user-user_id,
       / ls_user-user_name,
       / ls_user-status.
```

Syntax Check가 성공하면 Structure가 정상적으로 활성화되어 프로그램에서 참조 가능하다는 의미이다.

## 16. 초급자 오해 정리

### 오해 1. Structure를 만들면 DB 테이블도 생긴다

아니다.  
Structure는 DB 테이블이 아니다.  
데이터베이스에 실제 저장 공간을 만들지 않는다.

### 오해 2. Structure에는 Key가 필요하다

일반적인 DDIC Structure에는 DB Table처럼 Primary Key를 설정하지 않는다.  
Key 개념은 주로 Transparent Table이나 Internal Table의 접근 방식에서 중요해진다.

### 오해 3. Structure는 SE16N에서 조회할 수 있다

아니다.  
Structure는 데이터 저장소가 아니므로 SE16N으로 데이터를 조회할 수 없다.

### 오해 4. Component Type은 아무거나 입력해도 된다

아니다.  
Component Type은 존재하는 Data Element, Dictionary Type, Built-in Type 등을 기준으로 올바르게 지정해야 한다.

### 오해 5. 모든 필드 묶음은 DDIC Structure로 만들어야 한다

아니다.  
한 프로그램 안에서만 임시로 쓰는 구조라면 로컬 `TYPES`가 더 단순하고 적절할 수 있다.

## 17. 후속 모듈과의 연결

이번 모듈에서 Structure는 “필드 묶음 타입”이라는 관점으로 학습했다.

다음 모듈 `THEORY-01-M05 — Transparent Table 기본 생성`에서는 이와 유사하게 필드를 정의하지만, 실제 데이터베이스에 저장되는 테이블을 만든다.

연결 관계는 다음과 같다.

```text
THEORY-01-M02 Domain 기본 설계
 → THEORY-01-M03 Data Element 기본 설계
 → THEORY-01-M04 Structure 기본 생성
 → THEORY-01-M05 Transparent Table 기본 생성
```

이 흐름에서 M04의 핵심은 다음이다.

```text
Data Element를 이용하여 재사용 가능한 필드 묶음 타입을 만든다.
```

## 18. 평가 문제

### 18.1 객관식

#### Q1. DDIC Structure의 가장 적절한 설명은?

A. 실제 데이터를 저장하는 DB 테이블이다.  
B. 여러 필드를 묶은 재사용 가능한 데이터 타입이다.  
C. 입력값을 검증하는 프로그램 이벤트이다.  
D. SAP Client를 구분하는 시스템 필드이다.

정답: B

#### Q2. Structure와 Transparent Table의 차이로 올바른 것은?

A. Structure는 DB에 데이터를 저장하고 Transparent Table은 저장하지 않는다.  
B. 둘 다 반드시 Technical Settings가 필요하다.  
C. Structure는 타입 정의이고 Transparent Table은 실제 DB 저장 객체이다.  
D. Structure는 SE16N에서 직접 데이터 조회가 가능하다.

정답: C

#### Q3. Structure Component Type으로 가장 권장되는 것은?

A. 의미 없는 Built-in Type 직접 입력  
B. 가능한 경우 Data Element 사용  
C. 항상 CHAR 타입 사용  
D. 항상 NUMC 타입 사용

정답: B

### 18.2 단답형

#### Q1. Structure의 Component란 무엇인가?

모범 답안:  
Structure를 구성하는 개별 필드이다. 예를 들어 `ZS_GPT_USER_BASIC` 안의 `USER_ID`, `USER_NAME`, `STATUS` 등이 Component이다.

#### Q2. Structure를 Activate해야 하는 이유는 무엇인가?

모범 답안:  
ABAP 프로그램이나 다른 DDIC 객체에서 사용할 수 있는 활성 버전을 생성하기 위해서이다. 저장만 된 비활성 객체는 참조 시 오류가 발생할 수 있다.

#### Q3. Structure가 SE16N에서 조회되지 않는 이유는 무엇인가?

모범 답안:  
Structure는 실제 데이터를 저장하는 DB 테이블이 아니라 데이터 타입 정의이기 때문이다.

### 18.3 실습 리뷰 문제

다음 Structure 설계의 문제점을 설명하시오.

| Component | Component Type |
|---|---|
| FIELD1 | CHAR10 |
| FIELD2 | CHAR40 |
| FIELD3 | CHAR1 |

모범 답안:  
Component 이름이 업무 의미를 표현하지 못하고, Component Type도 Data Element를 사용하지 않아 의미와 라벨 재사용이 어렵다. 유지보수성과 영향 분석 측면에서 좋지 않다. `USER_ID`, `USER_NAME`, `STATUS`처럼 의미 있는 Component 이름을 사용하고, 가능하면 `ZDE_GPT_USER_ID`, `ZDE_GPT_USER_NAME`, `ZDE_GPT_STATUS` 같은 Data Element를 사용하는 것이 좋다.

## 19. 실무 관점 요약

Structure는 ABAP Dictionary에서 재사용 가능한 데이터 모양을 정의하는 객체이다.  
실제 데이터를 저장하지는 않지만, 프로그램과 인터페이스에서 데이터 구조를 일관되게 유지하는 데 매우 중요하다.

실무에서 Structure를 잘 설계하면 다음 효과를 얻을 수 있다.

```text
반복 타입 정의 감소
프로그램 간 데이터 형식 일관성 확보
Function/Method 인터페이스 명확화
ALV, 화면, API 출력 구조 재사용
유지보수성과 영향 분석 용이성 향상
```

반대로 의미 없는 Structure를 남발하면 오히려 Repository 객체가 불필요하게 늘어나고 관리가 어려워진다.  
따라서 Structure는 “여러 곳에서 재사용할 가치가 있는 필드 묶음”일 때 만드는 것이 좋다.

## 20. 핵심 문장 암기

```text
Structure는 데이터를 저장하는 객체가 아니라, 여러 필드를 묶어 재사용하기 위한 DDIC 데이터 타입이다.
```

```text
Structure의 Component Type은 가능하면 Data Element를 사용하여 기술 속성과 업무 의미를 함께 재사용한다.
```

```text
Structure는 Transparent Table의 전 단계처럼 보일 수 있지만, 저장 목적이 아니라 타입 정의 목적이라는 점이 다르다.
```
