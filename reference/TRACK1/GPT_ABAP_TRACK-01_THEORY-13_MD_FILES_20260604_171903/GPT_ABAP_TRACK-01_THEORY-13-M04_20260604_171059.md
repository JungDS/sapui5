```text
START-OF-SELECTION은 검증을 통과한 뒤 실제 조회/처리를 수행한다.
```

## 3. 왜 입력 검증이 필요한가?

Report 프로그램은 사용자의 입력값을 기준으로 데이터를 조회하거나 처리한다.  
입력값이 잘못되면 다음 문제가 발생할 수 있다.

| 문제 | 예시 |
|---|---|
| 의미 없는 조회 | 날짜 From이 To보다 큰 상태로 조회 |
| 성능 문제 | 필수 조건 없이 대량 테이블 전체 조회 |
| 업무 오류 | 허용되지 않는 상태값으로 처리 |
| 사용자 혼란 | 아무 결과가 나오지 않지만 이유를 알 수 없음 |
| 운영 리스크 | 잘못된 조건으로 대량 변경 프로그램 실행 |

예를 들어 사용자가 다음처럼 입력했다고 가정한다.

```text
시작일: 2026-12-31
종료일: 2026-01-01
```

이 입력은 기술적으로는 날짜 형식이 맞을 수 있다.  
하지만 업무적으로는 시작일이 종료일보다 늦기 때문에 올바른 조회 조건이라고 보기 어렵다.

이런 경우 `START-OF-SELECTION`에서 조회를 실행하기 전에 `AT SELECTION-SCREEN`에서 막아야 한다.

```text
잘못된 입력
→ AT SELECTION-SCREEN에서 검증
→ 오류 메시지 표시
→ Selection Screen으로 복귀
→ 사용자가 값 수정
→ 다시 실행
```

## 4. Report 실행 흐름 속 위치

Classic Report의 대표적인 이벤트 흐름은 다음과 같이 이해할 수 있다.

```text
LOAD-OF-PROGRAM
  ↓
INITIALIZATION
  ↓
AT SELECTION-SCREEN OUTPUT
  ↓
Selection Screen 표시
  ↓
사용자 입력
  ↓
AT SELECTION-SCREEN
  ↓
START-OF-SELECTION
  ↓
END-OF-SELECTION
```

이번 모듈의 위치는 사용자가 입력을 마친 뒤, 실제 본문 실행 전에 해당한다.

```text
사용자 입력
  ↓
AT SELECTION-SCREEN 입력 검증
  ↓
검증 성공 시 START-OF-SELECTION
```

### 4.1 중요한 실행 감각

`AT SELECTION-SCREEN`은 사용자가 Selection Screen에서 실행 버튼을 누르거나 Enter 등의 사용자 액션이 발생했을 때 입력값을 검증하는 데 사용된다.

초급자가 이해해야 할 핵심은 다음이다.

```text
AT SELECTION-SCREEN은 Report 본문 실행 전에 입력값을 막을 수 있는 마지막 관문이다.
```

잘못된 입력을 여기서 잡지 않으면 `START-OF-SELECTION`에서 불필요한 조회나 오류 처리가 발생할 수 있다.

## 5. `AT SELECTION-SCREEN`의 기본 형태

가장 기본적인 형태는 다음과 같다.

```abap
AT SELECTION-SCREEN.
  " 전체 Selection Screen 입력값 검증
```

예제:

```abap
REPORT ztr13_m04_basic_validation.

PARAMETERS: p_from TYPE d,
            p_to   TYPE d.

AT SELECTION-SCREEN.
  IF p_from IS NOT INITIAL
     AND p_to IS NOT INITIAL
     AND p_from > p_to.
    MESSAGE '시작일은 종료일보다 늦을 수 없습니다.' TYPE 'E'.
  ENDIF.

START-OF-SELECTION.
  WRITE: / '검증 통과',
         / '시작일:', p_from,
         / '종료일:', p_to.
```

이 예제에서 사용자가 시작일을 종료일보다 크게 입력하면 오류 메시지가 표시되고, 프로그램 본문인 `START-OF-SELECTION`은 실행되지 않는다.

## 6. `MESSAGE TYPE 'E'`의 의미

Selection Screen 검증에서 가장 자주 사용하는 메시지 유형은 `E`이다.

```abap
MESSAGE '오류 메시지' TYPE 'E'.
```

`TYPE 'E'`는 오류 메시지를 의미한다.  
`AT SELECTION-SCREEN`에서 오류 메시지가 발생하면 사용자는 Selection Screen으로 돌아가 값을 수정해야 한다.

| 메시지 유형 | 초급자 관점 설명 | Selection Screen 검증에서의 사용 |
|---|---|---|
| `E` | 오류 | 잘못된 입력을 막을 때 사용 |
| `W` | 경고 | 주의는 주되 계속 진행 가능할 수 있음 |
| `I` | 정보 | 단순 안내 |
| `S` | 성공 | 처리 성공 안내 |
| `A` | 종료성 오류 | 일반 검증 로직에서는 부적절 |
| `X` | Runtime Error 유발 | 검증 로직에서는 사용 금지 |

실무 입력 검증에서는 대부분 `E` 메시지를 사용한다.  
다만 운영 프로그램에서 무조건 `E`만 사용하는 것이 좋은 것은 아니다. 사용자가 판단 후 진행할 수 있는 조건이라면 `W` 또는 확인 팝업이 더 적절할 수도 있다. 초급 과정에서는 먼저 `E` 메시지로 실행을 막는 흐름을 확실히 익힌다.

## 7. Inline Text Message와 Message Class

초급 실습에서는 다음처럼 문자열 메시지를 바로 사용할 수 있다.

```abap
MESSAGE '조회 건수는 1 이상이어야 합니다.' TYPE 'E'.
```

하지만 실무에서는 보통 Message Class를 사용한다.

```abap
MESSAGE e001(zmsg_abap_train) WITH p_max.
```

### 7.1 실무에서 Message Class가 유리한 이유

| 이유 | 설명 |
|---|---|
| 다국어 관리 | 한국어, 영어 등 언어별 메시지 관리 가능 |
| 재사용성 | 여러 프로그램에서 같은 메시지 재사용 가능 |
| 유지보수성 | 메시지 문구 변경을 중앙에서 관리 가능 |
| 표준 관행 | SAP 표준 프로그램도 Message Class 기반이 많음 |

### 7.2 초급 단계의 기준

이번 모듈에서는 메시지 동작 자체를 이해하는 것이 중요하므로 Inline Text Message를 사용해도 된다.  
다만 실무 코딩 기준에서는 Message Class를 사용하는 방향으로 확장해야 한다.

> [추정] 교육용 시스템에서 Message Class 생성 권한이 없을 수 있으므로, 초급 실습에서는 Inline Text Message를 사용하고 개념만 Message Class로 연결하는 방식이 적절하다.

## 8. 전체 검증과 필드별 검증

`AT SELECTION-SCREEN`에는 여러 형태가 있다.

| 형태 | 용도 |
|---|---|
| `AT SELECTION-SCREEN.` | 전체 입력값 간 관계 검증 |
| `AT SELECTION-SCREEN ON p_field.` | 특정 Parameter 값 검증 |
| `AT SELECTION-SCREEN ON s_range.` | 특정 Select-Option 전체 검증 |
| `AT SELECTION-SCREEN ON BLOCK b1.` | 특정 Block 단위 검증 |
| `AT SELECTION-SCREEN ON VALUE-REQUEST FOR p_field.` | F4 Help 직접 구현 |
| `AT SELECTION-SCREEN ON HELP-REQUEST FOR p_field.` | F1 Help 직접 구현 |

이번 모듈에서는 입력 검증 중심으로 다음 세 가지를 중점적으로 다룬다.

```text
AT SELECTION-SCREEN.
AT SELECTION-SCREEN ON p_field.
AT SELECTION-SCREEN ON s_range.
```

F4/F1 Help 이벤트는 DDIC Search Help 및 후속 Selection Screen 주제와 연결하여 별도로 다루는 것이 좋다.

## 9. 필드별 검증: `AT SELECTION-SCREEN ON <parameter>`

특정 Parameter 하나만 검증할 때는 다음 형태를 사용할 수 있다.

```abap
AT SELECTION-SCREEN ON p_max.
  IF p_max <= 0.
    MESSAGE '조회 건수는 1 이상이어야 합니다.' TYPE 'E'.
  ENDIF.
```

전체 검증과 비교하면 장점이 있다.

| 구분 | 특징 |
|---|---|
| 전체 검증 | 여러 필드 간 관계를 보기 좋다. |
| 필드별 검증 | 특정 필드의 단독 규칙을 명확히 표현하기 좋다. |

예제:

```abap
REPORT ztr13_m04_on_parameter.

PARAMETERS p_max TYPE i DEFAULT 100.

AT SELECTION-SCREEN ON p_max.
  IF p_max <= 0.
    MESSAGE '조회 건수는 1 이상이어야 합니다.' TYPE 'E'.
  ELSEIF p_max > 500.
    MESSAGE '조회 건수는 500을 초과할 수 없습니다.' TYPE 'E'.
  ENDIF.

START-OF-SELECTION.
  WRITE: / '조회 건수 제한:', p_max.
```

이 예제는 `p_max` 하나에 대한 규칙을 검증한다.

```text
p_max는 1 이상이어야 한다.
p_max는 500 이하이어야 한다.
```

## 10. 여러 필드 관계 검증

두 개 이상의 입력값 사이의 관계를 검증할 때는 일반 `AT SELECTION-SCREEN.`이 적합하다.

대표적인 예가 날짜 범위 검증이다.

```abap
REPORT ztr13_m04_date_relation.

PARAMETERS: p_from TYPE d,
            p_to   TYPE d.

AT SELECTION-SCREEN.
  IF p_from IS NOT INITIAL
     AND p_to IS NOT INITIAL
     AND p_from > p_to.
    MESSAGE '시작일은 종료일보다 늦을 수 없습니다.' TYPE 'E'.
  ENDIF.

START-OF-SELECTION.
  WRITE: / '조회 시작일:', p_from,
         / '조회 종료일:', p_to.
```

이 검증은 `p_from` 하나만 보고 판단할 수 없다.  
`p_from`과 `p_to`의 관계를 함께 봐야 한다. 따라서 전체 검증 블록이 적합하다.

### 10.1 관계 검증의 대표 사례

| 검증 유형 | 예 |
|---|---|
| 날짜 From/To 검증 | 시작일 <= 종료일 |
| 금액 From/To 검증 | 최소금액 <= 최대금액 |
| 상호 배타 조건 | 전체 선택과 개별 선택을 동시에 허용하지 않음 |
| 필수 조합 검증 | 특정 체크박스 선택 시 추가 입력 필수 |
| 옵션 조합 검증 | 출력 모드에 따라 허용되는 조건 다름 |

## 11. `SELECT-OPTIONS` 입력 검증

`SELECT-OPTIONS`는 단일 값이 아니라 Range Table 형태의 값을 가진다.  
따라서 검증 방식도 `PARAMETERS`보다 조금 더 신중해야 한다.

예제:

```abap
REPORT ztr13_m04_select_options.

TABLES sflight.

SELECT-OPTIONS s_carrid FOR sflight-carrid.

AT SELECTION-SCREEN ON s_carrid.
  LOOP AT s_carrid ASSIGNING FIELD-SYMBOL(<ls_carrid>).
    IF <ls_carrid>-sign = 'I'
       AND <ls_carrid>-option = 'BT'
       AND <ls_carrid>-low > <ls_carrid>-high.
      MESSAGE '항공사 코드 범위의 시작값이 종료값보다 클 수 없습니다.' TYPE 'E'.
    ENDIF.
  ENDLOOP.

START-OF-SELECTION.
  WRITE: / '항공사 조건 입력 완료'.
```

### 11.1 `SELECT-OPTIONS` 내부 구조 기초

`SELECT-OPTIONS`는 내부적으로 다음과 같은 필드를 가진 Range Table이다.

| 필드 | 의미 |
|---|---|
| `SIGN` | Include 또는 Exclude |
| `OPTION` | EQ, BT, CP 등 조건 연산자 |
| `LOW` | 단일값 또는 시작값 |
| `HIGH` | 종료값 |
| `LOW`/`HIGH` | 조건 형태에 따라 의미가 달라짐 |

따라서 검증할 때는 단순히 `LOW`만 보면 안 된다.  
`SIGN`, `OPTION`, `LOW`, `HIGH`를 함께 고려해야 한다.

### 11.2 실무 주의

모든 `SELECT-OPTIONS` 조건을 개발자가 직접 검증하려고 하면 복잡도가 급격히 올라간다.  
가능하면 다음 기준으로 검증 범위를 정리한다.

| 검증 대상 | 권장 방식 |
|---|---|
| 날짜 From/To 기본 관계 | 직접 검증 가능 |
| 필수 입력 여부 | `OBLIGATORY` 또는 이벤트 검증 |
| 존재 여부 | 후속 M07에서 DB 조회 기반 검증 |
| 권한 여부 | `AUTHORITY-CHECK` 기반 검증 |
| 복잡한 Range 조합 | 업무 요구사항에 따라 별도 설계 |

---

## 12. `OBLIGATORY`와 이벤트 검증의 차이

`PARAMETERS`나 `SELECT-OPTIONS`에 `OBLIGATORY`를 붙이면 필수 입력을 강제할 수 있다.

```abap
PARAMETERS p_carrid TYPE sflight-carrid OBLIGATORY.
```

하지만 `OBLIGATORY`는 단순히 “비어 있으면 안 된다”에 가깝다.  
다음과 같은 복합 검증은 이벤트 로직이 필요하다.

```text
시작일은 종료일보다 늦을 수 없다.
체크박스를 선택하면 추가 입력 필드가 필수다.
조회 건수는 1 이상 500 이하여야 한다.
상세 출력과 요약 출력은 동시에 선택할 수 없다.
```

### 12.1 비교표

| 구분 | `OBLIGATORY` | `AT SELECTION-SCREEN` 검증 |
|---|---|---|
| 목적 | 필수 입력 여부 | 업무 규칙 검증 |
| 복잡한 조건 | 부적합 | 적합 |
| 여러 필드 관계 | 부적합 | 적합 |
| 코드 필요성 | 낮음 | 필요 |
| 유지보수성 | 단순 | 설계 필요 |

초급자는 이렇게 정리하면 된다.

```text
비어 있으면 안 되는 입력은 OBLIGATORY로 처리한다.
값 사이의 관계나 업무 규칙은 AT SELECTION-SCREEN에서 처리한다.
```

## 13. 동적 화면 제어와 입력 검증의 연결

이전 모듈에서 `MODIF ID`와 `AT SELECTION-SCREEN OUTPUT`을 사용해 특정 조건에서 필드를 활성화하거나 숨길 수 있었다.

이번 모듈의 입력 검증은 그 결과와 연결되어야 한다.

예를 들어 체크박스를 선택했을 때만 고급 조건을 입력하게 한다고 가정하자.

```abap
REPORT ztr13_m04_dynamic_validation.

PARAMETERS p_adv AS CHECKBOX USER-COMMAND adv.
PARAMETERS p_limit TYPE i MODIF ID adv.

AT SELECTION-SCREEN OUTPUT.
  LOOP AT SCREEN.
    IF screen-group1 = 'ADV'.
      IF p_adv = abap_true.
        screen-active = 1.
      ELSE.
        screen-active = 0.
      ENDIF.
      MODIFY SCREEN.
    ENDIF.
  ENDLOOP.

AT SELECTION-SCREEN.
  IF p_adv = abap_true AND p_limit <= 0.
    MESSAGE '고급 옵션 사용 시 제한 건수는 1 이상이어야 합니다.' TYPE 'E'.
  ENDIF.

START-OF-SELECTION.
  WRITE: / 'Advanced:', p_adv,
         / 'Limit   :', p_limit.
```

### 13.1 핵심 해석

이 예제는 두 이벤트가 역할을 나눈다.

| 이벤트 | 역할 |
|---|---|
| `AT SELECTION-SCREEN OUTPUT` | `p_adv`에 따라 `p_limit` 필드를 보이거나 숨김 |
| `AT SELECTION-SCREEN` | `p_adv` 선택 시 `p_limit` 값이 유효한지 검증 |

화면에서 숨겨진 필드를 무조건 검증하면 사용자가 수정할 수 없는 필드 때문에 오류가 발생할 수 있다.  
따라서 동적 화면 제어와 입력 검증은 같은 조건 체계를 공유해야 한다.

## 14. `MESSAGE` 처리 시 사용자 경험

입력 검증은 단순히 오류를 막는 것이 아니라 사용자가 어떤 값을 수정해야 하는지 알 수 있도록 안내해야 한다.

나쁜 메시지:

```text
오류
잘못된 값
입력 확인
```

좋은 메시지:

```text
시작일은 종료일보다 늦을 수 없습니다.
조회 건수는 1 이상 500 이하로 입력하세요.
상세 출력 선택 시 항공사 코드는 필수입니다.
```

### 14.1 좋은 메시지의 조건

| 조건 | 설명 |
|---|---|
| 원인 명확 | 어떤 값이 문제인지 알려준다. |
| 수정 방향 제시 | 어떤 범위로 입력해야 하는지 알려준다. |
| 업무 용어 사용 | 사용자가 이해하는 용어로 안내한다. |
| 짧고 구체적 | 너무 긴 문장보다 핵심을 전달한다. |

### 14.2 메시지 설계 예

| 상황 | 권장 메시지 |
|---|---|
| 날짜 역전 | 시작일은 종료일보다 늦을 수 없습니다. |
| 조회 건수 초과 | 조회 건수는 500 이하로 입력하세요. |
| 필수 조합 누락 | 상세 출력 선택 시 항공사 코드는 필수입니다. |
| 허용되지 않는 상태 | 상태는 A, I, B 중 하나만 입력할 수 있습니다. |

## 15. 검증 로직 위치 설계

초급자는 모든 검증을 하나의 `AT SELECTION-SCREEN` 블록에 넣는 경우가 많다.  
작은 예제에서는 가능하지만, 실무에서는 유지보수성이 떨어질 수 있다.

### 15.1 작은 프로그램

작은 Report에서는 다음 정도도 허용된다.

```abap
AT SELECTION-SCREEN.
  PERFORM validate_date.
  PERFORM validate_limit.
  PERFORM validate_mode.
```

### 15.2 조금 더 구조화된 프로그램

검증 로직이 많아지면 Form Routine이나 Method로 분리하는 것이 좋다.

```abap
AT SELECTION-SCREEN.
  PERFORM validate_selection_screen.

FORM validate_selection_screen.
  PERFORM validate_date_range.
  PERFORM validate_display_mode.
  PERFORM validate_limit.
ENDFORM.
```

OO 기반 프로그램에서는 Local Class의 검증 Method로 분리할 수 있다.

```abap
AT SELECTION-SCREEN.
  lcl_validator=>validate_selection(
    iv_from = p_from
    iv_to   = p_to
    iv_max  = p_max ).
```

다만 이 모듈은 Classic Report Event 학습 단계이므로, Method 분리 자체를 깊게 다루지는 않는다.  
핵심은 **검증 로직도 유지보수 대상이므로 구조화해야 한다**는 점이다.

## 16. 정상 흐름과 오류 흐름

### 16.1 정상 흐름

```text
사용자가 Selection Screen 입력
→ 실행 버튼 클릭
→ AT SELECTION-SCREEN 실행
→ 검증 조건 통과
→ START-OF-SELECTION 실행
→ 조회/출력 수행
```

### 16.2 오류 흐름

```text
사용자가 잘못된 값 입력
→ 실행 버튼 클릭
→ AT SELECTION-SCREEN 실행
→ MESSAGE TYPE 'E' 발생
→ START-OF-SELECTION 실행되지 않음
→ Selection Screen으로 복귀
→ 사용자가 값 수정
```

### 16.3 디버깅 포인트

디버깅할 때는 다음 위치에 Breakpoint를 걸어 확인한다.

| 위치 | 확인 내용 |
|---|---|
| `AT SELECTION-SCREEN OUTPUT` | 화면 제어가 먼저 실행되는지 확인 |
| `AT SELECTION-SCREEN ON p_field` | 필드별 검증이 실행되는지 확인 |
| `AT SELECTION-SCREEN` | 전체 검증이 실행되는지 확인 |
| `START-OF-SELECTION` | 검증 성공 후에만 들어오는지 확인 |

초급자는 특히 `MESSAGE TYPE 'E'`가 발생하면 `START-OF-SELECTION`으로 가지 않는다는 점을 직접 확인해야 한다.

## 17. 실습 예제: 항공편 조회 조건 검증

### 17.1 요구사항

표준 교육용 항공편 테이블을 조회한다고 가정한다.  
사용자는 항공사 코드, 날짜 범위, 최대 조회 건수를 입력한다.

검증 규칙은 다음과 같다.

| 규칙 | 설명 |
|---|---|
| 최대 조회 건수 | 1 이상 500 이하 |
| 날짜 범위 | 시작일은 종료일보다 늦을 수 없음 |
| 상세 출력 | 상세 출력 선택 시 항공사 코드는 필수 |
| 상태 메시지 | 오류 발생 시 사용자가 수정 방향을 알 수 있어야 함 |

### 17.2 예제 코드

```abap
REPORT ztr13_m04_flight_validation.

TABLES sflight.

SELECTION-SCREEN BEGIN OF BLOCK b01 WITH FRAME TITLE TEXT-t01.
  PARAMETERS p_detail AS CHECKBOX USER-COMMAND det.
  PARAMETERS p_max    TYPE i DEFAULT 100.
  SELECT-OPTIONS s_carrid FOR sflight-carrid.
  PARAMETERS: p_from TYPE d,
              p_to   TYPE d.
SELECTION-SCREEN END OF BLOCK b01.

INITIALIZATION.
  TEXT-t01 = 'Flight Search Condition'.

AT SELECTION-SCREEN ON p_max.
  IF p_max <= 0.
    MESSAGE '최대 조회 건수는 1 이상이어야 합니다.' TYPE 'E'.
  ELSEIF p_max > 500.
    MESSAGE '최대 조회 건수는 500 이하로 입력하세요.' TYPE 'E'.
  ENDIF.

AT SELECTION-SCREEN.
  IF p_from IS NOT INITIAL
     AND p_to IS NOT INITIAL
     AND p_from > p_to.
    MESSAGE '시작일은 종료일보다 늦을 수 없습니다.' TYPE 'E'.
  ENDIF.

  IF p_detail = abap_true AND s_carrid[] IS INITIAL.
    MESSAGE '상세 출력 선택 시 항공사 코드는 필수입니다.' TYPE 'E'.
  ENDIF.

START-OF-SELECTION.
  WRITE: / '입력 검증을 통과했습니다.',
         / '상세 출력:', p_detail,
         / '최대 건수:', p_max,
         / '시작일:', p_from,
         / '종료일:', p_to.
```

### 17.3 코드 해설

| 코드 영역 | 역할 |
|---|---|
| `PARAMETERS p_detail` | 상세 출력 여부 입력 |
| `PARAMETERS p_max` | 최대 조회 건수 입력 |
| `SELECT-OPTIONS s_carrid` | 항공사 코드 조건 입력 |
| `AT SELECTION-SCREEN ON p_max` | `p_max` 단일 필드 검증 |
| `AT SELECTION-SCREEN` | 여러 입력값 간 관계 검증 |
| `MESSAGE TYPE 'E'` | 오류 발생 시 실행 중단 및 Selection Screen 복귀 |
| `START-OF-SELECTION` | 검증 통과 후 본문 실행 |

## 20. 실무 적용 기준

### 20.1 검증은 어디까지 해야 하는가?

입력 검증은 너무 적어도 문제이고, 너무 많아도 문제가 된다.

| 부족한 검증 | 과도한 검증 |
|---|---|
| 잘못된 입력으로 성능/업무 오류 발생 | Selection Screen이 복잡하고 답답해짐 |
| 불필요한 DB 조회 발생 | 사용자가 합리적 예외를 입력하지 못함 |
| 오류 원인 파악 어려움 | 유지보수 난이도 증가 |
| 운영 리스크 증가 | 검증 로직이 비즈니스 로직과 뒤섞임 |

좋은 검증은 다음 기준을 따른다.

```text
실행하면 명백히 잘못되는 조건은 Selection Screen에서 막는다.
데이터 존재 여부와 권한처럼 DB/권한 의존 검증은 별도 기준으로 분리한다.
복잡한 업무 규칙은 Selection Screen에 과도하게 몰아넣지 않는다.
오류 메시지는 수정 방향을 알려준다.
```

### 20.2 입력 검증과 본문 로직 분리

나쁜 예:

```abap
START-OF-SELECTION.
  IF p_max <= 0.
    MESSAGE '최대 건수 오류' TYPE 'E'.
  ENDIF.

  SELECT ...
```

이 방식도 동작할 수 있지만, Selection Screen 입력 검증이라는 목적이 흐려진다.  
입력값 자체의 문제는 가능하면 `AT SELECTION-SCREEN`에서 처리하는 것이 더 명확하다.

좋은 예:

```abap
AT SELECTION-SCREEN.
  PERFORM validate_input.

START-OF-SELECTION.
  PERFORM select_data.
  PERFORM display_data.
```

## 21. 성능 관점 주의사항

`AT SELECTION-SCREEN`은 사용자가 실행을 시도할 때 호출된다.  
여기서 지나치게 무거운 DB 조회를 수행하면 사용자 경험이 나빠질 수 있다.

### 21.1 가벼운 검증에 적합한 것

| 검증 | 예 |
|---|---|
| 초기값 여부 | 필수 입력 확인 |
| 범위 관계 | From <= To |
| 숫자 범위 | 1 <= P_MAX <= 500 |
| 옵션 조합 | 상세 출력 선택 시 추가 조건 필수 |
| 단순 값 목록 | A/I/B 중 하나인지 확인 |

### 21.2 신중해야 하는 것

| 검증 | 주의 |
|---|---|
| 대량 테이블 조회 | Selection Screen 반응이 느려질 수 있음 |
| 복잡한 Join | 실행 전 검증 단계가 무거워짐 |
| 외부 RFC/API 호출 | 대기 시간과 장애 전파 가능 |
| 권한 검증 남발 | 기준 없이 반복하면 유지보수 어려움 |

존재 여부와 권한 검증은 중요하지만, 이번 모듈에서는 개념만 언급하고 M07에서 더 체계적으로 다룬다.

## 22. 권한/존재 여부 검증과의 경계

이번 모듈의 Validation은 주로 **입력 형식과 입력 조합의 타당성**에 집중한다.

| 검증 종류 | 이번 모듈에서 다루는 정도 |
|---|---|
| 날짜 From/To 관계 | 직접 구현 |
| 숫자 범위 | 직접 구현 |
| 필수 조합 | 직접 구현 |
| 코드값 존재 여부 | 개념만 언급 |
| 마스터 데이터 존재 여부 | M07에서 확장 |
| `AUTHORITY-CHECK` | M07에서 확장 |

예를 들어 항공사 코드가 실제 `SCARR`에 존재하는지 확인하는 검증은 이번 모듈의 중심이 아니다.  
이번 모듈에서는 항공사 코드를 입력해야 하는 조건인지, Range 입력이 말이 되는지를 검증한다.

```text
기본값 설정: INITIALIZATION

```

## 25. 자가 진단 문제

### 25.1 객관식

#### Q1. `AT SELECTION-SCREEN`의 가장 적절한 용도는?

A. Report 프로그램이 메모리에 로드될 때 초기화한다.  
B. Selection Screen이 표시되기 직전 화면 속성을 바꾼다.  
C. 사용자가 입력한 Selection Screen 값을 검증한다.  
D. 최종 출력 리스트를 꾸민다.

**정답:** C

#### Q2. 날짜 From/To 관계 검증에 적합한 이벤트는?

A. `LOAD-OF-PROGRAM`  
B. `AT SELECTION-SCREEN`  
C. `END-OF-SELECTION`  
D. `TOP-OF-PAGE`

**정답:** B

#### Q3. 입력 오류를 표시하고 Selection Screen으로 돌아가게 할 때 가장 일반적으로 사용하는 메시지 타입은?

A. `S`  
B. `I`  
C. `E`  
D. `X`

**정답:** C

### 25.2 단답형

#### Q1. `OBLIGATORY`와 `AT SELECTION-SCREEN` 검증의 차이를 설명하시오.

**모범 답안:**  
`OBLIGATORY`는 입력 필드가 비어 있지 않도록 하는 단순 필수 입력 검증에 적합하다. `AT SELECTION-SCREEN`은 여러 필드 간 관계, 값 범위, 조건부 필수 입력 등 업무 규칙을 코드로 검증할 때 사용한다.

#### Q2. 숨겨진 필드를 무조건 검증하면 왜 문제가 되는가?

**모범 답안:**  
사용자가 화면에서 볼 수 없거나 수정할 수 없는 필드 때문에 오류가 발생할 수 있다. 따라서 `AT SELECTION-SCREEN OUTPUT`에서 필드를 숨기거나 비활성화한 조건과 `AT SELECTION-SCREEN`의 검증 조건을 일치시켜야 한다.

#### Q3. 입력 검증을 `START-OF-SELECTION`보다 `AT SELECTION-SCREEN`에서 처리하는 것이 좋은 이유는?

**모범 답안:**  
`AT SELECTION-SCREEN`은 Report 본문 실행 전에 Selection Screen 입력값을 검증할 수 있는 이벤트이므로, 잘못된 입력을 조기에 차단하고 불필요한 DB 조회나 업무 처리를 막을 수 있다.

## 27. 핵심 요약

이번 모듈의 핵심은 다음이다.

```text
AT SELECTION-SCREEN은 사용자가 Selection Screen에 입력한 값을 검증하는 이벤트이다.
잘못된 입력은 MESSAGE TYPE 'E'로 막고 Selection Screen으로 돌려보낼 수 있다.
단일 필드 검증은 AT SELECTION-SCREEN ON <field>에 두면 명확하다.
여러 필드 간 관계 검증은 일반 AT SELECTION-SCREEN에서 처리하기 좋다.
OBLIGATORY는 단순 필수 입력이고, 복합 업무 규칙은 이벤트 검증이 필요하다.
동적 화면 제어와 입력 검증은 같은 조건 기준을 사용해야 한다.
입력 검증은 가볍고 명확해야 하며, 무거운 조회/처리는 본문 로직과 분리한다.
```

## 28. 다음 모듈 연결

다음 모듈은 `THEORY-13-M05 — START-OF-SELECTION 조회 실행`이다.

이번 모듈에서 입력값을 검증했다면, 다음 모듈에서는 검증을 통과한 입력값을 기준으로 실제 조회 로직을 실행한다.

연결 흐름은 다음과 같다.

```text
THEORY-13-M03
AT SELECTION-SCREEN OUTPUT으로 화면 제어
  ↓
THEORY-13-M04
AT SELECTION-SCREEN으로 입력 검증
  ↓
THEORY-13-M05
START-OF-SELECTION에서 본문 조회 실행
```

즉, `THEORY-13-M04`는 사용자가 입력한 조건이 실행 가능한지 확인하는 관문이고, `THEORY-13-M05`는 그 조건을 바탕으로 실제 데이터를 조회하는 단계이다.
