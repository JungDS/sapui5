## 3. 왜 Selection Screen에서 검증해야 하는가?

Report 프로그램은 사용자가 입력한 조건을 기준으로 데이터를 조회하고 출력한다.  
입력 조건이 잘못되었거나 권한이 없는 상태에서 조회 로직이 실행되면 여러 문제가 발생한다.

### 3.1 잘못된 입력값의 문제

예를 들어 항공사 코드 `CARRID`를 입력받는 프로그램이 있다고 하자.

```abap
PARAMETERS p_carrid TYPE scarr-carrid.
```

사용자가 존재하지 않는 코드 `ZZ`를 입력했는데 프로그램이 그대로 실행되면 다음 문제가 생긴다.

| 문제 | 설명 |
|---|---|
| 조회 결과 없음 | 사용자는 프로그램 오류인지 데이터 없음인지 혼동할 수 있다. |
| 불필요한 DB 접근 | 의미 없는 조건으로 조회가 수행된다. |
| 메시지 품질 저하 | 원인을 명확히 알려주지 못한다. |
| 후속 로직 오류 | 이후 로직이 데이터 존재를 전제로 작성되어 있으면 오류 가능성이 있다. |

### 3.2 권한 없는 입력값의 문제

사용자가 조회할 수 없는 회사코드, 플랜트, 영업조직, 고객 등을 입력할 수도 있다.  
이때 프로그램이 권한 검증 없이 데이터를 조회하면 보안상 문제가 생길 수 있다.

| 문제 | 설명 |
|---|---|
| 정보 노출 | 권한 없는 데이터가 조회될 수 있다. |
| 감사 리스크 | 승인되지 않은 데이터 접근이 발생할 수 있다. |
| 운영 위험 | 민감 데이터 접근 통제가 무력화될 수 있다. |
| 프로그램 신뢰도 저하 | 표준 권한 체계와 맞지 않는 프로그램이 된다. |

## 4. 검증을 수행하는 대표 위치

Selection Screen 검증은 보통 `AT SELECTION-SCREEN` 이벤트에서 수행한다.

```abap
AT SELECTION-SCREEN.
  " 전체 입력값 검증
```

특정 필드에 대한 검증은 다음처럼 작성할 수 있다.

```abap
AT SELECTION-SCREEN ON p_carrid.
  " p_carrid 필드 전용 검증
```

초급 단계에서는 다음 기준으로 이해하면 충분하다.

| 이벤트 | 사용 목적 |
|---|---|
| `AT SELECTION-SCREEN` | 전체 입력값 간 관계 검증, 전체 실행 전 검증 |
| `AT SELECTION-SCREEN ON <field>` | 특정 필드 단위 검증 |
| `AT SELECTION-SCREEN OUTPUT` | 화면 표시 전 속성 제어. 권한 검증 자체를 대체하지 않음 |
| `START-OF-SELECTION` | 검증 통과 후 실제 조회/처리 실행 |

이번 모듈에서는 `AT SELECTION-SCREEN`과 `AT SELECTION-SCREEN ON <field>`를 중심으로 다룬다.

## 5. 존재 여부 검증

### 5.1 존재 여부 검증의 의미

존재 여부 검증은 사용자가 입력한 값이 기준 테이블에 실제로 존재하는지 확인하는 것이다.

예를 들어 항공사 코드가 존재하는지 확인하려면 표준 교육 테이블 `SCARR`를 조회할 수 있다.

```text
사용자 입력: P_CARRID = 'AA'
검증 대상: SCARR-CARRID
판단: SCARR에 'AA'가 있으면 통과, 없으면 오류
```

> [추정] 교육 시스템에 `SCARR` 테이블 데이터가 없거나 비활성화되어 있다면, 해당 시스템에서 사용하는 교육용 마스터 테이블 또는 고객 개발 Z 테이블로 대체한다.

### 5.2 최소 존재 여부 검증 예제

```abap
REPORT zgpt_sel_check_01.

PARAMETERS p_carrid TYPE scarr-carrid OBLIGATORY.

AT SELECTION-SCREEN ON p_carrid.

  SELECT SINGLE carrid
    FROM scarr
    WHERE carrid = @p_carrid
    INTO @DATA(lv_carrid).

  IF sy-subrc <> 0.
    MESSAGE '존재하지 않는 항공사 코드입니다.' TYPE 'E'.
  ENDIF.

START-OF-SELECTION.

  WRITE: / '검증된 항공사 코드:', p_carrid.
```

이 예제의 핵심은 다음이다.

| 코드 | 의미 |
|---|---|
| `PARAMETERS p_carrid` | 사용자가 항공사 코드를 입력한다. |
| `AT SELECTION-SCREEN ON p_carrid` | 해당 필드에 대한 입력 검증을 수행한다. |
| `SELECT SINGLE` | 입력값이 마스터 테이블에 존재하는지 확인한다. |
| `sy-subrc <> 0` | 데이터가 없음을 의미한다. |
| `MESSAGE TYPE 'E'` | 오류 메시지를 표시하고 Selection Screen에 머문다. |

---

## 6. `MESSAGE TYPE 'E'`의 의미

Selection Screen 이벤트에서 `MESSAGE TYPE 'E'`를 사용하면 사용자는 오류 메시지를 확인하고 다시 입력 화면에 머문다.

```abap
MESSAGE '존재하지 않는 항공사 코드입니다.' TYPE 'E'.
```

초급자는 다음 흐름을 기억해야 한다.

```text
AT SELECTION-SCREEN에서 오류 메시지 발생
→ START-OF-SELECTION으로 넘어가지 않음
→ 사용자가 입력값 수정
→ 다시 실행
```

이는 잘못된 조건으로 메인 조회 로직이 실행되는 것을 막는 중요한 패턴이다.

### 6.1 메시지 작성 기준

좋은 메시지는 사용자가 무엇을 고쳐야 하는지 알려준다.

| 나쁜 메시지 | 좋은 메시지 |
|---|---|
| Error | 존재하지 않는 항공사 코드입니다. |
| Invalid | 회사코드가 존재하지 않습니다. 입력값을 확인하세요. |
| No data | 조회 권한이 없거나 존재하지 않는 값입니다. |
| Check input | 플랜트 코드를 입력하세요. |

실무에서는 하드코딩 메시지보다 Message Class를 사용하는 것이 유지보수에 좋다.  
그러나 초급 실습에서는 문법 이해를 위해 문자열 메시지를 먼저 사용할 수 있다.

## 7. 권한 검증의 기본 개념

### 7.1 `AUTHORITY-CHECK`란?

`AUTHORITY-CHECK`는 현재 사용자가 특정 권한 객체와 필드 조합에 대해 권한을 가지고 있는지 확인하는 ABAP 문이다.

기본 형태는 다음과 같다.

```abap
AUTHORITY-CHECK OBJECT '권한객체'
  ID '필드1' FIELD 값1
  ID '필드2' FIELD 값2.
```

실행 후 결과는 `sy-subrc`에 저장된다.

| `sy-subrc` | 의미 |
|---:|---|
| 0 | 권한 있음 |
| 0 아님 | 권한 없음 또는 검증 실패 |

초급자는 다음처럼 이해하면 된다.

```text
AUTHORITY-CHECK는 현재 사용자의 접근 자격을 프로그램에서 확인하는 표준 ABAP 구문이다.
```

### 7.2 권한 검증은 화면 제어가 아니다

`AT SELECTION-SCREEN OUTPUT`에서 `SCREEN-INPUT = 0`으로 필드를 비활성화하는 것은 화면 제어이다.  
이것은 보안 검증이 아니다.

예를 들어 어떤 필드를 숨기거나 입력 불가능하게 만들었다고 해서 사용자가 해당 데이터에 접근할 권한이 있다고 판단할 수는 없다.

| 구분 | 목적 |
|---|---|
| 화면 제어 | 사용자 입력 편의와 UI 제어 |
| 권한 검증 | 사용자의 데이터 접근 자격 확인 |

실무에서는 반드시 서버 측 로직에서 권한 검증을 수행해야 한다.  
Selection Screen 화면 제어는 보조 수단일 뿐이다.

## 8. 권한 검증 기본 예제

권한 객체는 고객사, 업무 영역, SAP 표준 권한 설계에 따라 다르다.  
따라서 아래 예제는 구조를 이해하기 위한 최소 패턴이다.

```abap
REPORT zgpt_sel_auth_01.

PARAMETERS p_tcode TYPE sy-tcode DEFAULT 'SE38'.

AT SELECTION-SCREEN.

  AUTHORITY-CHECK OBJECT 'S_TCODE'
    ID 'TCD' FIELD p_tcode.

  IF sy-subrc <> 0.
    MESSAGE '해당 트랜잭션 실행 권한이 없습니다.' TYPE 'E'.
  ENDIF.

START-OF-SELECTION.

  WRITE: / '권한 검증 통과:', p_tcode.
```

이 예제의 목적은 `AUTHORITY-CHECK` 문법 구조를 이해하는 것이다.  
실제 업무 데이터 권한 검증은 회사코드, 플랜트, 영업조직, 구매조직 등 업무 필드와 연결된 권한 객체를 사용한다.

> [추정] 고객사 프로젝트에서는 `Z_`로 시작하는 고객 권한 객체나 표준 업무 권한 객체를 사용할 수 있다. 실제 적용 시에는 권한 담당자 또는 보안 설계 문서를 기준으로 한다.

## 9. 업무 데이터 권한 검증 패턴

예를 들어 회사코드 입력값에 대한 권한을 검증한다고 가정하자.

```abap
PARAMETERS p_bukrs TYPE bukrs OBLIGATORY.
```

실무에서는 다음 질문이 필요하다.

```text
사용자가 이 회사코드 데이터를 조회할 수 있는가?
조회인지 변경인지 어떤 Activity인가?
권한 객체는 무엇인가?
회사코드 필드는 어떤 Authorization Field에 매핑되는가?
```

권한 검증은 단순히 “필드값이 존재하는가”와 다르다.

| 검증 | 질문 |
|---|---|
| 존재 여부 검증 | 이 회사코드가 시스템에 존재하는가? |
| 권한 검증 | 현재 사용자가 이 회사코드 데이터를 조회할 수 있는가? |

## 10. 존재 여부 검증과 권한 검증의 순서

### 10.1 일반 교육용 흐름

초급 교육에서는 다음 순서로 설명하는 것이 이해하기 쉽다.

```text
1. 입력값이 비어 있지 않은지 확인
2. 마스터 데이터 존재 여부 확인
3. 권한 검증
4. 조회 실행
```

이 순서는 사용자가 잘못 입력한 값을 먼저 수정하게 해주므로 학습에 적합하다.

### 10.2 보안이 중요한 업무의 흐름

민감한 데이터에서는 존재 여부를 먼저 알려주는 것 자체가 정보 노출이 될 수 있다.  
예를 들어 사용자가 권한 없는 고객번호를 입력했을 때 “존재하는 고객이지만 권한 없음”이라고 알려주는 것은 민감할 수 있다.

이 경우 다음처럼 처리할 수 있다.

```text
1. 권한 검증
2. 존재 여부 검증
3. 메시지는 모호하게 처리
```

또는 다음처럼 메시지를 일반화할 수 있다.

```text
입력값을 확인할 수 없거나 조회 권한이 없습니다.
```

초급 단계에서는 이런 보안 관점을 깊게 구현하지 않아도 되지만, 실무에서는 매우 중요하다.

## 11. 존재 여부 + 권한 검증 통합 예제

아래 예제는 항공사 코드 입력값에 대해 존재 여부를 확인하고, 이후 간단한 권한 검증 구조를 보여준다.

> [추정] `SCARR`는 교육 시스템에서 자주 사용하는 항공사 마스터 예제 테이블이다. 시스템에 따라 데이터가 없을 수 있다.

```abap
REPORT zgpt_sel_check_auth.

PARAMETERS p_carrid TYPE scarr-carrid OBLIGATORY.

AT SELECTION-SCREEN ON p_carrid.

  PERFORM check_carrid_exists.
  PERFORM check_carrid_authority.

START-OF-SELECTION.

  WRITE: / '검증 완료 후 조회를 시작합니다.',
         / '항공사 코드:', p_carrid.

FORM check_carrid_exists.

  SELECT SINGLE carrid
    FROM scarr
    WHERE carrid = @p_carrid
    INTO @DATA(lv_carrid).

  IF sy-subrc <> 0.
    MESSAGE '존재하지 않는 항공사 코드입니다.' TYPE 'E'.
  ENDIF.

ENDFORM.

FORM check_carrid_authority.

  " 교육용 예시:
  " 실제 권한 객체는 시스템/프로젝트 권한 설계에 따라 달라진다.
  AUTHORITY-CHECK OBJECT 'S_CARRID'
    ID 'CARRID' FIELD p_carrid
    ID 'ACTVT'  FIELD '03'.

  IF sy-subrc <> 0.
    MESSAGE '해당 항공사 코드에 대한 조회 권한이 없습니다.' TYPE 'E'.
  ENDIF.

ENDFORM.
```

### 11.1 예제 해석

| 구문 | 의미 |
|---|---|
| `PERFORM check_carrid_exists` | 존재 여부 검증을 별도 루틴으로 분리 |
| `PERFORM check_carrid_authority` | 권한 검증을 별도 루틴으로 분리 |
| `ACTVT = '03'` | 일반적으로 조회(Display) Activity 의미로 사용되는 값 |
| `MESSAGE TYPE 'E'` | 실패 시 Selection Screen에서 실행 중단 |

> [추정] `S_CARRID` 권한 객체는 교육용 예시 이름이다. 실제 시스템에 존재하지 않을 수 있다. 실무에서는 반드시 SU21, PFCG 역할, 권한 설계 문서, 보안 담당자 기준에 맞는 권한 객체를 사용한다.

## 12. `AUTHORITY-CHECK` 결과 확인

권한 검증 후에는 반드시 `sy-subrc`를 확인해야 한다.

```abap
AUTHORITY-CHECK OBJECT 'S_TCODE'
  ID 'TCD' FIELD 'SE38'.

IF sy-subrc = 0.
  WRITE: / '권한 있음'.
ELSE.
  WRITE: / '권한 없음'.
ENDIF.
```

초급자가 자주 하는 실수는 `AUTHORITY-CHECK`만 작성하고 결과를 확인하지 않는 것이다.

```abap
" 나쁜 예
AUTHORITY-CHECK OBJECT 'S_TCODE'
  ID 'TCD' FIELD 'SE38'.

" sy-subrc 확인 없이 계속 실행
```

`AUTHORITY-CHECK`는 검사를 수행할 뿐이다.  
그 결과에 따라 프로그램 흐름을 제어하는 코드는 개발자가 작성해야 한다.

## 13. 검증 로직 분리

초급 예제에서는 `AT SELECTION-SCREEN` 안에 모든 코드를 직접 작성할 수 있다.  
하지만 실무에서는 검증 로직이 길어지므로 별도 FORM, Method, Function으로 분리하는 것이 좋다.

### 13.1 단순 직접 작성

```abap
AT SELECTION-SCREEN.

  SELECT SINGLE carrid
    FROM scarr
    WHERE carrid = @p_carrid
    INTO @DATA(lv_carrid).

  IF sy-subrc <> 0.
    MESSAGE '존재하지 않는 항공사 코드입니다.' TYPE 'E'.
  ENDIF.
```

장점:

```text
초급자가 흐름을 이해하기 쉽다.
```

단점:

```text
검증이 많아지면 이벤트 블록이 복잡해진다.
재사용이 어렵다.
테스트와 유지보수가 불편하다.
```

### 13.2 FORM으로 분리

```abap
AT SELECTION-SCREEN.
  PERFORM validate_selection_screen.

FORM validate_selection_screen.

  PERFORM check_carrid_exists.
  PERFORM check_carrid_authority.

ENDFORM.
```

장점:

```text
이벤트 흐름이 명확해진다.
검증 항목을 분리해서 읽기 쉽다.
후속 OO ABAP Method 분리로 확장하기 쉽다.
```

## 14. 성능 관점 주의사항

Selection Screen 검증은 사용자가 실행 버튼을 누를 때마다 수행된다.  
따라서 검증 로직이 너무 무겁거나 대량 조회를 수행하면 사용자 경험과 시스템 부하에 영향을 줄 수 있다.

### 14.1 존재 여부 확인 시 권장 패턴

존재 여부만 확인한다면 필요한 컬럼 하나만 조회한다.

```abap
SELECT SINGLE carrid
  FROM scarr
  WHERE carrid = @p_carrid
  INTO @DATA(lv_carrid).
```

좋지 않은 예:

```abap
SELECT *
  FROM scarr
  WHERE carrid = @p_carrid
  INTO @DATA(ls_scarr).
ENDSELECT.
```

문제:

| 문제 | 설명 |
|---|---|
| 불필요한 컬럼 조회 | 존재 여부만 필요한데 모든 컬럼을 읽는다. |
| 구문 의도 불명확 | 존재 확인인지 데이터 처리인지 헷갈린다. |
| 유지보수성 저하 | 후속 개발자가 로직 목적을 오해할 수 있다. |

### 14.2 반복 권한 검증 주의

`SELECT-OPTIONS`처럼 여러 범위 값을 입력받는 경우 각 값마다 권한 검증을 반복할 수 있다.  
이 경우 입력 건수가 많으면 성능과 사용자 경험에 영향을 줄 수 있다.

이번 모듈에서는 단일 `PARAMETERS` 기준으로만 다룬다.  
범위 조건의 대량 검증은 후속 Selection Screen 또는 Open SQL 심화에서 다루는 것이 적절하다.

## 15. 권한 검증 디버깅과 운영 확인

### 15.1 초급자 확인 포인트

권한 검증이 예상대로 동작하지 않으면 다음을 확인한다.

| 확인 항목 | 설명 |
|---|---|
| 권한 객체명 | 실제 시스템에 존재하는 권한 객체인가 |
| Authorization Field | ID로 지정한 필드명이 맞는가 |
| Activity | 조회는 보통 `03`, 변경은 보통 `02` 등 업무 기준에 맞는가 |
| 입력값 | 권한 필드에 전달한 값이 올바른가 |
| `sy-subrc` | 권한 검증 결과를 확인했는가 |
| 사용자 역할 | PFCG Role에 해당 권한이 포함되어 있는가 |

### 15.2 SU53

권한 오류가 발생했을 때 사용자는 `SU53`을 통해 마지막 권한 실패 정보를 확인할 수 있다.

초급자에게는 다음 정도로 설명하면 된다.

```text
권한 오류가 발생하면 SU53에서 최근 실패한 권한 체크 정보를 확인할 수 있다.
```

단, `SU53`은 “마지막 권한 오류”를 보여주는 도구이므로, 여러 권한 검증이 연속으로 수행되면 해석에 주의가 필요하다.  
실무에서는 Basis/보안 담당자와 함께 확인해야 한다.

### 15.3 STAUTHTRACE

`STAUTHTRACE`는 권한 추적에 더 강력한 도구이다.  
초급 과정에서는 이름만 소개하고, 상세 사용은 보안/운영 심화 과정에서 다루는 것이 적절하다.

## 16. 실무 적용 기준

### 16.1 Selection Screen 검증에 넣어도 좋은 것

| 검증 항목 | 설명 |
|---|---|
| 필수값 누락 | `OBLIGATORY` 또는 이벤트 검증 |
| 입력값 형식 | 날짜 범위, 코드 패턴 등 |
| 마스터 존재 여부 | 회사코드, 플랜트, 고객, 자재 등 |
| 사용자 권한 | 회사코드/조직/업무영역 접근 권한 |
| 상호 관계 | 시작일 <= 종료일, From <= To 등 |

### 16.2 Selection Screen 검증에 넣기 애매한 것

| 항목 | 이유 |
|---|---|
| 대량 데이터 상세 검증 | 실행 전 검증 단계가 너무 무거워질 수 있다. |
| 복잡한 비즈니스 계산 | START-OF-SELECTION 또는 서비스 계층이 더 적절할 수 있다. |
| DB 전체 스캔이 필요한 검증 | 성능 문제가 생길 수 있다. |
| 출력 전용 가공 로직 | 검증이 아니라 메인 처리 로직에 가깝다. |

### 16.3 실무 판단 기준

검증 로직을 넣기 전에 다음 질문을 한다.

```text
이 검증은 실행 전에 반드시 막아야 하는가?
검증 실패 시 사용자가 바로 수정할 수 있는가?
검증 로직이 너무 무겁지는 않은가?
권한 없는 사용자에게 민감 정보를 노출하지 않는가?
메시지가 사용자가 조치할 수 있는 형태인가?
```

## 17. 전체 예제: Selection Screen 검증 통합 Report

아래 예제는 이번 Section에서 배운 Event 흐름을 하나로 연결한 교육용 예제이다.

```abap
REPORT zgpt_report_event_check.

TABLES scarr.

PARAMETERS p_carrid TYPE scarr-carrid OBLIGATORY.

INITIALIZATION.
  p_carrid = 'AA'.

AT SELECTION-SCREEN OUTPUT.
  " 화면 속성 제어가 필요한 경우 여기에 작성한다.
  " 권한 검증 자체는 여기서 끝내지 않는다.

AT SELECTION-SCREEN ON p_carrid.
  PERFORM check_carrid_exists.
  PERFORM check_carrid_authority.

START-OF-SELECTION.

  SELECT carrid,
         carrname,
         currcode
    FROM scarr
    WHERE carrid = @p_carrid
    INTO TABLE @DATA(lt_scarr).

END-OF-SELECTION.

  IF lt_scarr IS INITIAL.
    WRITE: / '출력할 데이터가 없습니다.'.
  ELSE.
    LOOP AT lt_scarr INTO DATA(ls_scarr).
      WRITE: / ls_scarr-carrid,
               ls_scarr-carrname,
               ls_scarr-currcode.
    ENDLOOP.
  ENDIF.

FORM check_carrid_exists.

  SELECT SINGLE carrid
    FROM scarr
    WHERE carrid = @p_carrid
    INTO @DATA(lv_carrid).

  IF sy-subrc <> 0.
    MESSAGE '존재하지 않는 항공사 코드입니다.' TYPE 'E'.
  ENDIF.

ENDFORM.

FORM check_carrid_authority.

  " 실제 권한 객체는 시스템별 권한 설계를 따른다.
  " 아래 권한 객체명은 교육용 예시이다.
  AUTHORITY-CHECK OBJECT 'S_CARRID'
    ID 'CARRID' FIELD p_carrid
    ID 'ACTVT'  FIELD '03'.

  IF sy-subrc <> 0.
    MESSAGE '해당 항공사 코드에 대한 조회 권한이 없습니다.' TYPE 'E'.
  ENDIF.

ENDFORM.
```

### 17.1 이벤트 흐름 해석

| 이벤트 | 역할 |
|---|---|
| `INITIALIZATION` | 기본값 설정 |
| `AT SELECTION-SCREEN OUTPUT` | 화면 표시 전 속성 제어 |
| `AT SELECTION-SCREEN ON p_carrid` | 입력값 검증 |
| `START-OF-SELECTION` | 검증 통과 후 조회 |
| `END-OF-SELECTION` | 출력 마무리 |

이 예제를 통해 `THEORY-13` Section의 전체 흐름을 하나로 복습할 수 있다.

## 18. 자주 발생하는 오류와 해결

### 18.1 `AUTHORITY-CHECK` 후 `sy-subrc`를 확인하지 않음

| 구분 | 내용 |
|---|---|
| 증상 | 권한이 없어도 프로그램이 계속 실행된다. |
| 원인 | `AUTHORITY-CHECK` 결과를 확인하지 않았다. |
| 해결 | `IF sy-subrc <> 0.` 조건으로 오류 처리한다. |

### 18.2 존재하지 않는 권한 객체 사용

| 구분 | 내용 |
|---|---|
| 증상 | 권한 체크가 의도대로 동작하지 않거나 문법/런타임 문제가 발생한다. |
| 원인 | 시스템에 없는 권한 객체명을 사용했다. |
| 해결 | SU21, 권한 설계 문서, 보안 담당자 기준으로 실제 객체명을 확인한다. |

### 18.3 존재 여부 검증에서 대량 조회 사용

| 구분 | 내용 |
|---|---|
| 증상 | Selection Screen 실행 전 검증이 느려진다. |
| 원인 | 존재 확인만 필요한데 전체 데이터를 조회했다. |
| 해결 | `SELECT SINGLE`로 필요한 Key 필드만 조회한다. |

### 18.4 권한 검증을 화면 제어로 대체함

| 구분 | 내용 |
|---|---|
| 증상 | 특정 필드를 숨겼지만 데이터 접근은 여전히 가능하다. |
| 원인 | UI 제어를 보안 검증으로 오해했다. |
| 해결 | 반드시 서버 측 ABAP 로직에서 `AUTHORITY-CHECK`를 수행한다. |

### 18.5 오류 메시지가 모호함

| 구분 | 내용 |
|---|---|
| 증상 | 사용자가 무엇을 수정해야 하는지 모른다. |
| 원인 | 메시지가 너무 짧거나 원인을 설명하지 않는다. |
| 해결 | 사용자가 조치할 수 있는 형태로 메시지를 작성한다. 단, 민감 정보 노출은 피한다. |

## 20. 평가 문제

### 20.1 객관식

#### Q1. Selection Screen 입력값 검증을 수행하기에 가장 적절한 이벤트는?

A. `INITIALIZATION`  
B. `AT SELECTION-SCREEN`  
C. `END-OF-SELECTION`  
D. `TOP-OF-PAGE`

**정답:** B

#### Q2. `AUTHORITY-CHECK` 후 반드시 확인해야 하는 시스템 필드는?

A. `sy-datum`  
B. `sy-uname`  
C. `sy-subrc`  
D. `sy-index`

**정답:** C

#### Q3. 존재 여부만 확인할 때 적절한 SQL 패턴은?

A. `SELECT * ... ENDSELECT`  
B. `SELECT SINGLE key_field ...`  
C. 모든 데이터를 Internal Table로 조회  
D. `WRITE`로 화면에 출력 후 확인

**정답:** B

#### Q4. 화면 필드를 비활성화하는 것만으로 권한 검증을 대체할 수 있는가?

A. 가능하다. 화면에 보이지 않으면 접근 권한도 없는 것이다.  
B. 가능하다. `LOOP AT SCREEN`은 권한 검증 구문이다.  
C. 불가능하다. 화면 제어와 권한 검증은 목적이 다르다.  
D. 불가능하지만 `WRITE`를 쓰면 대체 가능하다.

**정답:** C

### 20.2 단답형

#### Q1. `MESSAGE TYPE 'E'`를 Selection Screen 검증에서 사용하는 이유는 무엇인가?

**모범 답안:**  
검증 실패 시 프로그램이 `START-OF-SELECTION`으로 넘어가지 않도록 막고, 사용자가 Selection Screen에서 입력값을 수정할 수 있게 하기 위해 사용한다.

#### Q2. 존재 여부 검증과 권한 검증의 차이를 설명하시오.

**모범 답안:**  
존재 여부 검증은 사용자가 입력한 코드나 마스터 데이터가 시스템에 실제로 존재하는지 확인하는 것이다. 권한 검증은 현재 사용자가 해당 데이터에 접근하거나 조회할 권한이 있는지 확인하는 것이다.

#### Q3. 권한 검증 순서를 보안 관점에서 조정해야 할 수 있는 이유는 무엇인가?

**모범 답안:**  
권한 없는 사용자에게 특정 데이터가 존재한다는 사실 자체를 알려주는 것이 정보 노출이 될 수 있기 때문이다. 민감 데이터에서는 권한 검증을 먼저 하거나 메시지를 일반화하는 방식이 필요할 수 있다.

## 22. Section 전체 요약

`THEORY-13`에서는 Classic ABAP Report Event와 Selection Screen 심화 흐름을 학습했다.

```text
M01: ABAP Report Event 전체 흐름
M02: INITIALIZATION 기본값 설정
M03: AT SELECTION-SCREEN OUTPUT 동적 화면 제어
M04: AT SELECTION-SCREEN 입력 검증
M05: START-OF-SELECTION 조회 실행
M06: END-OF-SELECTION 출력 마무리
M07: Selection Screen 권한/존재 여부 검증 기초
```

이번 마지막 모듈을 통해 Selection Screen은 단순 입력 화면이 아니라, 실행 전 데이터 품질과 보안을 통제하는 중요한 지점임을 이해해야 한다.

핵심 문장은 다음이다.

```text
Selection Screen 검증은 잘못된 입력과 권한 없는 실행을 START-OF-SELECTION 전에 차단하는 표준 방어선이다.
```

## 24. 마무리

초급 단계에서 Selection Screen 검증은 문법처럼 보이지만, 실무에서는 프로그램 안정성과 보안의 출발점이다.

다음 세 가지를 반드시 기억한다.

```text
1. 존재하지 않는 입력값은 메인 로직으로 넘기지 않는다.
2. 권한 없는 입력값은 조회나 변경 로직으로 넘기지 않는다.
3. 검증 실패 시 사용자가 수정 가능한 메시지를 제공한다.
```

이 기준을 지키면 Report 프로그램의 품질이 크게 높아진다.
