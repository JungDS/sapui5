## 3. ABAP Report 이벤트 흐름에서 END-OF-SELECTION의 위치

Classic Report의 대표 실행 흐름을 단순화하면 다음과 같다.

```text
LOAD-OF-PROGRAM
  ↓
INITIALIZATION
  ↓
AT SELECTION-SCREEN OUTPUT
  ↓
사용자 입력
  ↓
AT SELECTION-SCREEN
  ↓
START-OF-SELECTION
  ↓
END-OF-SELECTION
```

`END-OF-SELECTION`은 이름 그대로 선택 처리가 끝난 후의 이벤트이다. 여기서 말하는 “선택”은 Selection Screen에서 사용자가 값을 선택했다는 의미만이 아니라, Report의 주 데이터 선택과 처리 흐름이 끝난 뒤의 후속 단계를 포함하는 의미로 이해하면 된다.

초급자 관점에서는 다음처럼 이해하는 것이 가장 안전하다.

```text
START-OF-SELECTION: 데이터를 조회하고 주요 비즈니스 로직을 수행한다.
END-OF-SELECTION: 조회 결과를 출력하거나 마무리 메시지를 정리한다.
```

## 4. START-OF-SELECTION과 END-OF-SELECTION의 역할 분리

### 4.1 역할 비교

| 구분 | START-OF-SELECTION | END-OF-SELECTION |
|---|---|---|
| 주 역할 | 메인 처리 시작 | 메인 처리 이후 출력·마무리 |
| 대표 작업 | DB 조회, 데이터 가공, 주요 로직 실행 | 결과 출력, 요약 표시, 후속 정리 |
| 초급 예제 | `SELECT ... INTO TABLE` | `LOOP AT ... WRITE` |
| 실무 관점 | 프로그램의 핵심 처리 위치 | 출력 계층 또는 마무리 계층으로 활용 가능 |
| 필수 여부 | 일반 Report에서 자주 사용 | 항상 필수는 아님 |

### 4.2 간단한 구조 예시

```abap
REPORT zjhy_report_event_m06.

TYPES: BEGIN OF ty_user,
         user_id   TYPE c LENGTH 10,
         user_name TYPE c LENGTH 30,
         status    TYPE c LENGTH 1,
       END OF ty_user.

DATA gt_user TYPE STANDARD TABLE OF ty_user.
DATA gs_user TYPE ty_user.

START-OF-SELECTION.
  gs_user-user_id   = 'U0001'.
  gs_user-user_name = 'Kim Developer'.
  gs_user-status    = 'A'.
  APPEND gs_user TO gt_user.

  CLEAR gs_user.
  gs_user-user_id   = 'U0002'.
  gs_user-user_name = 'Lee Consultant'.
  gs_user-status    = 'I'.
  APPEND gs_user TO gt_user.

END-OF-SELECTION.
  WRITE: / 'User List'.
  ULINE.

  LOOP AT gt_user INTO gs_user.
    WRITE: / gs_user-user_id,
             gs_user-user_name,
             gs_user-status.
  ENDLOOP.
```

이 예제에서 `START-OF-SELECTION`은 데이터를 준비하고, `END-OF-SELECTION`은 준비된 데이터를 출력한다.

실제 실무 Report에서는 데이터 조회와 가공이 더 복잡해질 수 있다. 그러나 기본 설계 원칙은 동일하다.

## 5. END-OF-SELECTION은 반드시 필요한가?

결론부터 말하면, 모든 Report에서 `END-OF-SELECTION`을 반드시 사용할 필요는 없다.

다음과 같이 `START-OF-SELECTION` 안에서 조회와 출력까지 모두 처리할 수도 있다.

```abap
REPORT zjhy_report_no_end.

START-OF-SELECTION.
  WRITE: / 'Hello ABAP Report'.
```

이 코드는 정상적으로 실행된다. 따라서 초급자가 다음처럼 오해하면 안 된다.

```text
오해: Report에는 START-OF-SELECTION과 END-OF-SELECTION이 항상 둘 다 있어야 한다.
정답: 필요에 따라 사용할 수 있다. END-OF-SELECTION은 출력과 마무리 단계를 분리하고 싶을 때 유용하다.
```

### 5.1 사용하면 좋은 경우

| 상황 | 이유 |
|---|---|
| 조회와 출력을 분리하고 싶을 때 | 코드 구조가 명확해진다. |
| START-OF-SELECTION에 메인 로직이 많을 때 | 출력 로직을 후단으로 분리할 수 있다. |
| 조회 결과를 요약해서 출력해야 할 때 | 처리 후 전체 건수, 합계, 메시지를 정리하기 좋다. |
| 교육용으로 이벤트 흐름을 보여주고 싶을 때 | Report 이벤트 순서를 체계적으로 설명할 수 있다. |

### 5.2 사용하지 않아도 되는 경우

| 상황 | 이유 |
|---|---|
| 매우 단순한 Report | 이벤트 블록이 오히려 과해질 수 있다. |
| 출력이 SALV/ALV 메서드 호출 하나로 끝나는 경우 | 별도 이벤트 분리가 필수는 아니다. |
| OO 구조로 Controller/Service/View를 분리한 경우 | 이벤트 블록보다 메서드 분리가 더 명확할 수 있다. |
| RAP/CDS 기반 UI 흐름 | Classic Report 이벤트 자체가 중심이 아니다. |

## 6. END-OF-SELECTION에 적합한 로직

`END-OF-SELECTION`에는 일반적으로 “주 처리 이후 결과를 정리하는 로직”을 둔다.

### 6.1 적합한 예

| 로직 | 설명 |
|---|---|
| 결과 리스트 출력 | 조회된 Internal Table을 `WRITE`로 출력 |
| 요약 건수 출력 | `LINES( gt_data )` 또는 처리 건수 표시 |
| 결과 없음 메시지 | 조회 결과가 없을 때 사용자에게 안내 |
| 합계/소계 출력 | 이미 계산된 결과를 마무리 단계에서 표시 |
| 로그성 메시지 출력 | 처리 완료 상태를 사용자에게 보여줌 |

예시:

```abap
END-OF-SELECTION.
  IF gt_user IS INITIAL.
    WRITE: / 'No user data found.'.
    RETURN.
  ENDIF.

  WRITE: / 'Total users:', lines( gt_user ).
  ULINE.

  LOOP AT gt_user INTO gs_user.
    WRITE: / gs_user-user_id,
             gs_user-user_name,
             gs_user-status.
  ENDLOOP.
```

### 6.2 피하는 것이 좋은 예

| 로직 | 피해야 하는 이유 |
|---|---|
| 핵심 DB 조회를 모두 END-OF-SELECTION에 배치 | 이벤트 역할이 불명확해진다. |
| 입력값 검증 | 이미 `AT SELECTION-SCREEN`에서 처리하는 것이 자연스럽다. |
| 화면 동적 제어 | `AT SELECTION-SCREEN OUTPUT`의 역할이다. |
| 복잡한 비즈니스 처리 | `START-OF-SELECTION` 또는 별도 메서드에서 분리하는 편이 명확하다. |
| 권한 검증 전체 | 위치에 따라 다르지만 보통 메인 처리 전후 명확한 기준을 둬야 한다. |

## 7. 데이터 없음 처리

Report 출력 단계에서 매우 중요한 것은 데이터가 없을 때의 처리이다.

초급자는 조회 결과가 있을 때만 생각하고 다음처럼 작성하기 쉽다.

```abap
END-OF-SELECTION.
  LOOP AT gt_user INTO gs_user.
    WRITE: / gs_user-user_id, gs_user-user_name.
  ENDLOOP.
```

이 경우 `gt_user`가 비어 있으면 화면에 아무것도 출력되지 않는다. 사용자는 프로그램이 실행된 것인지, 오류가 난 것인지 알기 어렵다.

더 좋은 방식은 다음과 같다.

```abap
END-OF-SELECTION.
  IF gt_user IS INITIAL.
    WRITE: / 'No data found for the selected condition.'.
    RETURN.
  ENDIF.

  LOOP AT gt_user INTO gs_user.
    WRITE: / gs_user-user_id, gs_user-user_name.
  ENDLOOP.
```

### 7.1 실무적 의미

데이터 없음은 오류가 아닐 수 있다. 하지만 사용자는 결과가 없는 이유를 알아야 한다.

| 상황 | 출력 메시지 예 |
|---|---|
| 조건에 맞는 데이터 없음 | `No data found for the selected condition.` |
| 입력값이 너무 제한적임 | `No records match the current filter.` |
| 권한으로 인해 결과 없음 | `[추정] Authorization may restrict visible data.` |
| 테스트 데이터 미생성 | `Please create test data before running this report.` |

권한이나 시스템 설정이 원인인지 확실하지 않다면 `[추정]`으로 구분해야 한다.

## 8. 출력 헤더와 구분선 구성

Classic List 출력에서 `END-OF-SELECTION`은 결과 헤더와 리스트를 구성하기 좋은 위치이다.

```abap
END-OF-SELECTION.
  WRITE: / 'User Report Result'.
  WRITE: / 'Executed by:', sy-uname.
  WRITE: / 'Executed on:', sy-datum.
  ULINE.

  WRITE: / 'User ID', 15 'User Name', 50 'Status'.
  ULINE.

  LOOP AT gt_user INTO gs_user.
    WRITE: / gs_user-user_id,
             15 gs_user-user_name,
             50 gs_user-status.
  ENDLOOP.
```

이 예제는 단순하지만, 교육용으로 다음을 보여주기에 좋다.

| 요소 | 의미 |
|---|---|
| `sy-uname` | 실행 사용자 |
| `sy-datum` | 실행일 |
| `ULINE` | 구분선 출력 |
| 위치 지정 | `15`, `50` 같은 출력 위치 제어 |
| LOOP 출력 | Internal Table 데이터를 한 줄씩 표시 |

다만 실제 실무에서는 단순 `WRITE` 리스트보다 SALV, Grid ALV, Fiori, CDS/RAP 기반 UI를 사용하는 경우가 많다. 이 모듈은 Classic Report Event의 이해를 위한 기본 단계로 본다.

## 9. 예제: 조회와 출력 분리 Report

다음 예제는 `START-OF-SELECTION`에서 표준 항공사 테이블 `SCARR`를 조회하고, `END-OF-SELECTION`에서 결과를 출력하는 기본 구조이다.

> [추정] 교육 시스템에 `SCARR` 데이터가 없거나 Flight Model 테이블이 비활성인 경우 결과가 없을 수 있다. 이 경우 시스템에 존재하는 다른 표준 테이블 또는 교육용 Z 테이블로 대체한다.

```abap
REPORT zjhy_end_of_selection_01.

DATA gt_scarr TYPE STANDARD TABLE OF scarr.
DATA gs_scarr TYPE scarr.

START-OF-SELECTION.
  SELECT *
    FROM scarr
    INTO TABLE gt_scarr.

END-OF-SELECTION.
  IF gt_scarr IS INITIAL.
    WRITE: / 'No carrier data found.'.
    RETURN.
  ENDIF.

  WRITE: / 'Carrier List'.
  WRITE: / 'Total Count:', lines( gt_scarr ).
  ULINE.

  LOOP AT gt_scarr INTO gs_scarr.
    WRITE: / gs_scarr-carrid,
             gs_scarr-carrname,
             gs_scarr-currcode.
  ENDLOOP.
```

### 9.1 코드 해설

| 코드 | 설명 |
|---|---|
| `DATA gt_scarr TYPE STANDARD TABLE OF scarr` | `SCARR` 구조를 가진 Internal Table 선언 |
| `START-OF-SELECTION` | 메인 조회 위치 |
| `SELECT * FROM scarr INTO TABLE gt_scarr` | 항공사 데이터를 조회 |
| `END-OF-SELECTION` | 조회 후 출력 단계 |
| `IF gt_scarr IS INITIAL` | 결과 없음 처리 |
| `lines( gt_scarr )` | 결과 건수 계산 |
| `LOOP AT gt_scarr` | 결과 출력 |

### 9.2 초급자 확인 포인트

실행 후 다음을 확인한다.

```text
1. 조회 결과가 있을 때 헤더와 데이터가 출력되는가?
2. 결과 건수가 표시되는가?
3. gt_scarr가 비어 있을 때 메시지가 출력되는가?
4. START-OF-SELECTION과 END-OF-SELECTION의 역할이 분리되어 보이는가?
```

## 10. 예제: 선택 조건과 연결

이전 모듈과 연결하여 Selection Screen 입력값을 기준으로 데이터를 조회하고, `END-OF-SELECTION`에서 출력할 수 있다.

```abap
REPORT zjhy_end_of_selection_02.

PARAMETERS p_carrid TYPE scarr-carrid.

DATA gt_scarr TYPE STANDARD TABLE OF scarr.
DATA gs_scarr TYPE scarr.

START-OF-SELECTION.
  SELECT *
    FROM scarr
    WHERE carrid = p_carrid
    INTO TABLE gt_scarr.

END-OF-SELECTION.
  IF gt_scarr IS INITIAL.
    WRITE: / 'No data found for carrier:', p_carrid.
    RETURN.
  ENDIF.

  WRITE: / 'Selected Carrier:', p_carrid.
  ULINE.

  LOOP AT gt_scarr INTO gs_scarr.
    WRITE: / gs_scarr-carrid,
             gs_scarr-carrname,
             gs_scarr-currcode.
  ENDLOOP.
```

이 예제에서 `PARAMETERS`는 입력을 받고, `START-OF-SELECTION`은 입력값을 이용해 조회하며, `END-OF-SELECTION`은 결과를 출력한다.

## 11. SY-SUBRC와 END-OF-SELECTION

초급자는 `SELECT` 직후 `sy-subrc`만 보고 출력 여부를 판단하려고 한다.

```abap
START-OF-SELECTION.
  SELECT *
    FROM scarr
    WHERE carrid = p_carrid
    INTO TABLE gt_scarr.

  IF sy-subrc <> 0.
    WRITE: / 'No data found.'.
  ENDIF.
```

이 방식 자체가 항상 틀린 것은 아니다. 하지만 출력 단계가 `END-OF-SELECTION`으로 분리되어 있다면, 출력 여부는 Internal Table의 상태를 기준으로 판단하는 편이 읽기 쉽다.

```abap
END-OF-SELECTION.
  IF gt_scarr IS INITIAL.
    WRITE: / 'No data found.'.
    RETURN.
  ENDIF.
```

### 11.1 실무 권장 감각

| 판단 기준 | 설명 |
|---|---|
| DB 조회 직후 오류성 판단 | `sy-subrc` 확인 가능 |
| 출력 단계의 데이터 존재 여부 | Internal Table `IS INITIAL` 확인이 직관적 |
| 여러 조회 결과를 종합하는 경우 | 별도 상태 변수 또는 메시지 테이블 사용 권장 |
| 예외 처리 필요한 경우 | 메시지, 로그, 예외 클래스를 설계 기준에 따라 사용 |

초급 단계에서는 `sy-subrc`와 Internal Table 상태를 함께 관찰하면서 차이를 이해하는 것이 좋다.

## 12. END-OF-SELECTION과 ALV/SALV의 관계

이 모듈은 `WRITE` 기반의 Classic List 출력으로 설명하지만, 실무에서는 SALV나 Grid ALV를 사용하는 경우가 많다.

예를 들어 SALV 출력 호출도 `END-OF-SELECTION`에 배치할 수 있다.

```abap
END-OF-SELECTION.
  IF gt_scarr IS INITIAL.
    MESSAGE 'No data found.' TYPE 'S'.
    RETURN.
  ENDIF.

  cl_salv_table=>factory(
    IMPORTING
      r_salv_table = DATA(lo_alv)
    CHANGING
      t_table      = gt_scarr ).

  lo_alv->display( ).
```

그러나 이 코드는 후속 SALV/ALV 학습 내용을 포함하므로, 이번 모듈에서는 개념 연결만 한다.

핵심은 다음이다.

```text
END-OF-SELECTION은 WRITE 출력뿐 아니라 결과 표시 단계로도 활용될 수 있다.
다만 현대적 설계에서는 이벤트 블록 안에 모든 로직을 몰아넣기보다 메서드로 분리하는 것이 유지보수에 유리하다.
```

## 13. 디버깅 포인트

`END-OF-SELECTION`의 실행 시점을 이해하려면 디버깅이 효과적이다.

### 13.1 추천 Breakpoint 위치

| 위치 | 확인할 내용 |
|---|---|
| `START-OF-SELECTION` 첫 줄 | Selection Screen 이후 메인 이벤트 진입 확인 |
| `SELECT` 직후 | 조회 결과와 `sy-subrc` 확인 |
| `END-OF-SELECTION` 첫 줄 | 주 처리 이후 출력 이벤트 진입 확인 |
| `LOOP AT gt_scarr` 내부 | 한 줄씩 출력되는 데이터 확인 |

### 13.2 디버깅 중 확인할 변수

| 변수 | 확인 의미 |
|---|---|
| `p_carrid` | 사용자가 입력한 Selection Screen 값 |
| `gt_scarr` | 조회 결과 Internal Table |
| `sy-subrc` | 직전 명령의 처리 결과 |
| `sy-dbcnt` | DB 처리 건수 확인에 활용 가능 |
| `sy-uname` | 실행 사용자 |
| `sy-datum` | 실행일 |

## 14. 자주 발생하는 오류와 해결

### 14.1 END-OF-SELECTION이 실행되지 않는다고 오해

#### 증상

학습자가 `END-OF-SELECTION`에 Breakpoint를 걸었는데 흐름을 잘못 이해한다.

#### 원인

Selection Screen 단계에서 입력 검증 오류가 발생하면 `START-OF-SELECTION`까지 가지 않을 수 있다. 또는 프로그램 실행 흐름을 잘못 관찰했을 수 있다.

#### 해결

다음 위치에 순서대로 Breakpoint를 둔다.

```text
AT SELECTION-SCREEN
START-OF-SELECTION
END-OF-SELECTION
```

실행 흐름을 단계별로 확인한다.

### 14.2 데이터가 없는데 화면이 비어 있음

#### 원인

Internal Table이 비어 있는데 결과 없음 메시지를 출력하지 않았다.

#### 해결

```abap
IF gt_data IS INITIAL.
  WRITE: / 'No data found.'.
  RETURN.
ENDIF.
```

### 14.3 START와 END 역할이 뒤섞임

#### 원인

조회, 검증, 출력, 메시지를 모든 이벤트에 섞어서 작성했다.

#### 해결

초급 실습에서는 다음 기준으로 분리한다.

```text
AT SELECTION-SCREEN: 입력 검증
START-OF-SELECTION: 조회와 메인 처리
END-OF-SELECTION: 출력과 마무리
```

### 14.4 END-OF-SELECTION에 DB 조회를 모두 작성함

#### 원인

이벤트 이름만 보고 마지막에 모든 로직을 몰아넣었다.

#### 해결

주 조회 로직은 `START-OF-SELECTION`에 두고, END에는 결과 출력 중심 로직을 둔다.

### 14.5 WRITE 위치가 맞지 않음

#### 원인

Classic List 출력 위치를 지정하지 않아 컬럼이 뒤섞였다.

#### 해결

기초 단계에서는 `WRITE` 위치 지정과 `ULINE`을 사용해 최소한의 가독성을 확보한다.

```abap
WRITE: / 'CARRID', 10 'CARRNAME', 40 'CURRCODE'.
ULINE.
```

## 15. 실무 적용 기준

### 15.1 교육용 Report와 실무 Report의 차이

| 구분 | 교육용 | 실무 |
|---|---|---|
| 목적 | 이벤트 흐름 이해 | 유지보수 가능한 처리 구조 |
| 출력 | WRITE 중심 | SALV, Grid ALV, Fiori, Excel 등 다양 |
| 로직 위치 | 이벤트 블록에 직접 작성 가능 | 메서드/클래스 분리 권장 |
| 데이터량 | 소량 | 대량 가능 |
| 오류 처리 | 단순 메시지 | 로그, 예외, 권한, 감사 고려 |

### 15.2 실무에서의 권장 구조

Classic Report라도 실무에서는 다음처럼 이벤트 블록을 얇게 유지하는 것이 좋다.

```abap
START-OF-SELECTION.
  PERFORM get_data.
  PERFORM process_data.

END-OF-SELECTION.
  PERFORM display_result.
```

또는 OO 방식으로는 다음처럼 구성할 수 있다.

```abap
START-OF-SELECTION.
  lcl_app=>run( ).
```

이 경우 `END-OF-SELECTION`을 쓰지 않을 수도 있다. 중요한 것은 이벤트를 외우는 것이 아니라, **입력 검증, 조회, 처리, 출력의 책임을 명확히 분리하는 것**이다.

## 16. 미니 실습

### 16.1 실습 목표

`START-OF-SELECTION`에서 데이터를 준비하고, `END-OF-SELECTION`에서 출력하는 Report를 작성한다.

### 16.2 실습 요구사항

```text
1. PARAMETERS p_carrid TYPE scarr-carrid 선언
2. START-OF-SELECTION에서 SCARR 조회
3. END-OF-SELECTION에서 결과 없음 처리
4. 결과가 있으면 헤더, 건수, 데이터 출력
5. Breakpoint를 걸어 이벤트 실행 순서 확인
```

### 16.3 예시 코드

```abap
REPORT zjhy_m06_end_selection.

PARAMETERS p_carrid TYPE scarr-carrid DEFAULT 'AA'.

DATA gt_scarr TYPE STANDARD TABLE OF scarr.
DATA gs_scarr TYPE scarr.

START-OF-SELECTION.
  SELECT *
    FROM scarr
    WHERE carrid = p_carrid
    INTO TABLE gt_scarr.

END-OF-SELECTION.
  IF gt_scarr IS INITIAL.
    WRITE: / 'No data found for carrier:', p_carrid.
    RETURN.
  ENDIF.

  WRITE: / 'Carrier Report'.
  WRITE: / 'Selected Carrier:', p_carrid.
  WRITE: / 'Total Count:', lines( gt_scarr ).
  ULINE.

  WRITE: / 'ID', 10 'Name', 50 'Currency'.
  ULINE.

  LOOP AT gt_scarr INTO gs_scarr.
    WRITE: / gs_scarr-carrid,
             10 gs_scarr-carrname,
             50 gs_scarr-currcode.
  ENDLOOP.
```

## 18. 평가 문제

### 18.1 객관식

#### Q1. `END-OF-SELECTION`의 가장 적절한 사용 목적은?

A. Selection Screen 필드의 동적 비활성화  
B. 입력값 검증 메시지 처리  
C. 주 처리 이후 결과 출력 또는 마무리 처리  
D. 프로그램 로드 시 전역 변수 초기화  

정답: C

#### Q2. 입력값 검증에 가장 적합한 이벤트는?

A. INITIALIZATION  
B. AT SELECTION-SCREEN  
C. END-OF-SELECTION  
D. TOP-OF-PAGE  

정답: B

#### Q3. 조회 결과가 없을 때 좋은 처리 방식은?

A. 아무것도 출력하지 않는다.  
B. 프로그램을 강제로 덤프낸다.  
C. 결과 없음 메시지를 출력하고 종료한다.  
D. 모든 조건을 무시하고 전체 데이터를 출력한다.  

정답: C

### 18.2 서술형

#### Q1. `START-OF-SELECTION`과 `END-OF-SELECTION`의 역할 차이를 설명하시오.

모범 답안:  
`START-OF-SELECTION`은 사용자의 Selection Screen 입력과 검증 이후 메인 조회와 처리 로직을 실행하는 위치로 사용된다. `END-OF-SELECTION`은 그 주 처리 이후 조회 결과를 출력하거나 요약 메시지, 결과 없음 처리 등 마무리 단계를 구성하는 위치로 사용할 수 있다.

#### Q2. `END-OF-SELECTION`이 항상 필수는 아닌 이유를 설명하시오.

모범 답안:  
단순 Report에서는 `START-OF-SELECTION` 안에서 조회와 출력까지 모두 처리할 수 있으며, OO 방식이나 SALV 호출 구조에서는 별도 메서드로 출력 책임을 분리할 수도 있다. 따라서 `END-OF-SELECTION`은 이벤트 흐름을 명확히 분리하고 싶을 때 유용하지만 모든 Report에서 필수는 아니다.

#### Q3. 데이터 없음 처리를 `END-OF-SELECTION`에서 구현할 때의 장점을 설명하시오.

모범 답안:  
조회 결과가 모두 준비된 후 Internal Table 상태를 기준으로 출력 여부를 판단할 수 있다. 따라서 결과가 없을 때 사용자에게 명확한 메시지를 제공하고, 결과가 있을 때만 헤더와 데이터를 출력하는 구조를 만들 수 있다.

## 19. 안티패턴과 개선 방향

| 안티패턴 | 문제 | 개선 방향 |
|---|---|---|
| 모든 로직을 `END-OF-SELECTION`에 작성 | 이벤트 역할이 불명확해진다. | 조회는 START, 출력은 END로 분리한다. |
| 데이터가 없을 때 아무 출력도 하지 않음 | 사용자가 실행 결과를 판단하기 어렵다. | 결과 없음 메시지를 출력한다. |
| 입력 검증을 END에서 수행 | 검증 시점이 늦고 흐름이 부자연스럽다. | `AT SELECTION-SCREEN`에서 검증한다. |
| `WRITE` 위치 지정 없이 난잡한 리스트 출력 | 결과 가독성이 떨어진다. | 헤더, `ULINE`, 위치 지정을 사용한다. |
| 이벤트 블록에 복잡한 실무 로직을 모두 작성 | 유지보수성이 떨어진다. | FORM, 메서드, 클래스 등으로 책임을 분리한다. |
