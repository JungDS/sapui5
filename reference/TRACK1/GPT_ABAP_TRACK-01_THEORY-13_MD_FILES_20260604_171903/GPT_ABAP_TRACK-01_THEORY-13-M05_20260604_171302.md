## 1. 이 문서의 목적

이 문서는 Classic ABAP Report에서 `START-OF-SELECTION` 이벤트가 어떤 역할을 하며, Selection Screen에서 입력·검증된 조건을 바탕으로 Open SQL 조회를 실행하는 표준 흐름을 이해하도록 돕기 위한 학습 자료이다.

앞선 모듈에서는 다음을 학습했다.

```text
THEORY-13-M01  ABAP Report Event 전체 흐름
THEORY-13-M02  INITIALIZATION 기본값 설정
THEORY-13-M03  AT SELECTION-SCREEN OUTPUT 동적 화면 제어
THEORY-13-M04  AT SELECTION-SCREEN 입력 검증
```

이번 모듈은 그 다음 단계이다.  
즉, 사용자가 Selection Screen에 값을 입력하고, 시스템이 검증을 통과한 뒤, 실제 조회 또는 주요 처리 로직을 실행하는 시점이 `START-OF-SELECTION`이다.

초급자는 이번 모듈에서 다음 한 문장을 반드시 기억해야 한다.

> `START-OF-SELECTION`은 Classic Report에서 사용자의 입력값이 확정된 뒤 본격적인 조회와 메인 로직을 실행하는 대표 이벤트이다.

## 4. Report Event 흐름에서의 위치

Classic Report의 대표 흐름은 다음처럼 이해할 수 있다.

```text
LOAD-OF-PROGRAM
  ↓
INITIALIZATION
  ↓
AT SELECTION-SCREEN OUTPUT
  ↓
Selection Screen 표시
  ↓
사용자 입력
  ↓
AT SELECTION-SCREEN
  ↓
START-OF-SELECTION
  ↓
END-OF-SELECTION
```

이번 모듈의 핵심은 `START-OF-SELECTION`이다.

각 이벤트의 책임을 비교하면 다음과 같다.

| 이벤트 | 대표 역할 |
|---|---|
| `INITIALIZATION` | Selection Screen 초기값 설정 |
| `AT SELECTION-SCREEN OUTPUT` | Selection Screen 표시 직전 동적 속성 제어 |
| `AT SELECTION-SCREEN` | 사용자 입력값 검증 |
| `START-OF-SELECTION` | 검증 완료 후 조회와 메인 처리 실행 |
| `END-OF-SELECTION` | 조회 이후 출력 또는 마무리 처리 |

즉, `START-OF-SELECTION`은 “입력을 받는 시점”이 아니라 “입력값을 바탕으로 실제 업무 처리를 시작하는 시점”이다.

## 5. START-OF-SELECTION의 표준적 역할

### 5.1 기본 정의

`START-OF-SELECTION`은 Classic Executable Program에서 주 처리 로직을 작성하는 대표 이벤트 블록이다.

예시는 다음과 같다.

```abap
START-OF-SELECTION.
  " Main logic starts here
```

이 블록 안에는 보통 다음 작업이 들어간다.

```text
1. Selection Screen 입력값 기반 조회 조건 구성
2. Open SQL 실행
3. 조회 결과 존재 여부 확인
4. 후속 처리 로직 호출
5. 출력 또는 다음 이벤트로 넘길 데이터 준비
```

### 5.2 조회 실행 이벤트로 이해하기

Selection Screen이 있는 Report에서 사용자는 조건을 입력한다.

예를 들어 다음과 같은 입력값이 있을 수 있다.

```abap
PARAMETERS p_carrid TYPE s_carr_id.
```

사용자가 `AA`를 입력하고 실행하면, `AT SELECTION-SCREEN`에서 검증을 마친 뒤 `START-OF-SELECTION`에서 실제 조회를 실행한다.

```abap
START-OF-SELECTION.

  SELECT carrid,
         carrname,
         currcode
    FROM scarr
    WHERE carrid = @p_carrid
    INTO TABLE @DATA(lt_scarr).
```

이 예제에서 `p_carrid`는 Selection Screen에서 확정된 입력값이고, `START-OF-SELECTION`은 그 값을 이용해 실제 DB 조회를 수행한다.

## 6. 이벤트별 책임 분리

초급자가 가장 자주 하는 실수는 모든 로직을 아무 이벤트에나 작성하는 것이다.

좋은 Report는 이벤트별 책임이 분리되어 있다.

| 처리 내용 | 권장 위치 |
|---|---|
| 기본값 설정 | `INITIALIZATION` |
| 화면 필드 활성/비활성 | `AT SELECTION-SCREEN OUTPUT` |
| 필수 관계 검증 | `AT SELECTION-SCREEN` |
| DB 조회 실행 | `START-OF-SELECTION` |
| 결과 출력 마무리 | `END-OF-SELECTION` 또는 출력 전용 FORM/Method |

### 6.1 잘못된 예

다음은 검증 이벤트에서 DB 조회까지 수행하는 나쁜 예이다.

```abap
AT SELECTION-SCREEN.
  SELECT *
    FROM scarr
    WHERE carrid = @p_carrid
    INTO TABLE @DATA(lt_scarr).
```

문법적으로 가능해 보일 수 있지만, 이벤트 책임이 섞인다.  
`AT SELECTION-SCREEN`은 입력 검증이 중심이고, 메인 조회 실행은 `START-OF-SELECTION`이 더 적절하다.

### 6.2 권장 예

```abap
AT SELECTION-SCREEN.
  IF p_carrid IS INITIAL.
    MESSAGE e001(zmsg) WITH '항공사 코드는 필수입니다.'.
  ENDIF.

START-OF-SELECTION.
  SELECT *
    FROM scarr
    WHERE carrid = @p_carrid
    INTO TABLE @DATA(lt_scarr).
```

이렇게 분리하면 코드의 의도가 명확하다.

```text
AT SELECTION-SCREEN  = 입력값이 실행 가능한 조건인지 확인
START-OF-SELECTION   = 검증된 조건으로 조회 실행
```

## 7. 최소 예제: START-OF-SELECTION에서 조회 실행

다음은 가장 단순한 형태의 예제이다.

> [추정] `SCARR`는 많은 ABAP 교육 시스템에서 사용되는 항공사 데모 테이블이지만, 시스템에 따라 데이터가 없거나 테이블이 제공되지 않을 수 있다. 해당 시스템에 `SCARR`가 없으면 이전 DDIC 실습에서 만든 `ZT_JHY_USER` 같은 교육용 Z 테이블로 대체한다.

```abap
REPORT ztr13_m05_start_select_01.

PARAMETERS p_carrid TYPE s_carr_id OBLIGATORY.

START-OF-SELECTION.

  SELECT carrid,
         carrname,
         currcode
    FROM scarr
    WHERE carrid = @p_carrid
    INTO TABLE @DATA(lt_scarr).

  IF sy-subrc <> 0.
    WRITE: / '조회된 데이터가 없습니다.'.
    RETURN.
  ENDIF.

  LOOP AT lt_scarr INTO DATA(ls_scarr).
    WRITE: / ls_scarr-carrid,
             ls_scarr-carrname,
             ls_scarr-currcode.
  ENDLOOP.
```

### 7.1 코드 해설

| 코드 | 의미 |
|---|---|
| `PARAMETERS p_carrid` | 사용자가 항공사 코드를 입력한다. |
| `START-OF-SELECTION` | 입력값 확정 후 메인 조회를 시작한다. |
| `SELECT ... FROM scarr` | DB 테이블에서 데이터를 조회한다. |
| `@p_carrid` | ABAP 변수 또는 파라미터를 SQL 호스트 변수로 사용한다. |
| `INTO TABLE @DATA(lt_scarr)` | 조회 결과를 Internal Table에 담는다. |
| `sy-subrc <> 0` | 조회 결과가 없거나 SQL 처리 결과가 성공이 아님을 확인한다. |
| `RETURN` | 더 이상 출력할 데이터가 없으므로 이벤트 블록 처리를 종료한다. |
| `LOOP AT` | 조회된 Internal Table을 순회한다. |

## 8. Selection Screen 검증과 조회 실행 연결

실무적인 Report에서는 입력 검증과 조회 실행을 함께 구성해야 한다.

### 8.1 입력 검증 예제

```abap
REPORT ztr13_m05_start_select_02.

PARAMETERS p_carrid TYPE s_carr_id OBLIGATORY.

AT SELECTION-SCREEN.

  IF p_carrid IS INITIAL.
    MESSAGE e001(zmsg) WITH '항공사 코드를 입력하세요.'.
  ENDIF.

START-OF-SELECTION.

  SELECT carrid,
         carrname,
         currcode
    FROM scarr
    WHERE carrid = @p_carrid
    INTO TABLE @DATA(lt_scarr).

  IF lt_scarr IS INITIAL.
    WRITE: / '조건에 해당하는 항공사 데이터가 없습니다.'.
    RETURN.
  ENDIF.

  LOOP AT lt_scarr INTO DATA(ls_scarr).
    WRITE: / ls_scarr-carrid,
             ls_scarr-carrname,
             ls_scarr-currcode.
  ENDLOOP.
```

### 8.2 흐름 설명

이 프로그램은 다음 순서로 동작한다.

```text
1. 사용자가 p_carrid 입력
2. 실행 버튼 선택
3. AT SELECTION-SCREEN에서 입력값 검증
4. 검증 통과 시 START-OF-SELECTION으로 진행
5. SCARR 조회
6. 조회 결과가 없으면 메시지성 출력 후 종료
7. 조회 결과가 있으면 리스트 출력
```

여기서 중요한 점은 다음이다.

```text
검증 실패는 Selection Screen 단계에서 막는다.
검증 성공 후에만 START-OF-SELECTION에서 조회한다.
```

## 9. SELECT-OPTIONS와 함께 사용하는 예제

Report에서는 단일 값보다 범위 조건을 받을 때가 많다.  
이 경우 `SELECT-OPTIONS`를 사용한다.

```abap
REPORT ztr13_m05_start_select_03.

SELECT-OPTIONS s_carrid FOR scarr-carrid.

START-OF-SELECTION.

  SELECT carrid,
         carrname,
         currcode
    FROM scarr
    WHERE carrid IN @s_carrid
    INTO TABLE @DATA(lt_scarr).

  IF lt_scarr IS INITIAL.
    WRITE: / '조회 조건에 해당하는 데이터가 없습니다.'.
    RETURN.
  ENDIF.

  LOOP AT lt_scarr INTO DATA(ls_scarr).
    WRITE: / ls_scarr-carrid,
             ls_scarr-carrname,
             ls_scarr-currcode.
  ENDLOOP.
```

### 9.1 주의점

`SELECT-OPTIONS`는 내부적으로 Range Table 구조를 가진다.  
따라서 Open SQL에서 사용할 때 다음처럼 작성한다.

```abap
WHERE carrid IN @s_carrid
```

단일 `PARAMETERS`와는 다르다.

```abap
WHERE carrid = @p_carrid
```

이 차이를 구분하는 것이 중요하다.

## 10. 조회 결과가 없을 때의 처리

조회 결과가 없을 수 있다.  
이것은 항상 오류가 아니다.

예를 들어 사용자가 존재하지 않는 항공사 코드를 입력하면 결과가 없을 수 있다.

### 10.1 `sy-subrc` 방식

```abap
SELECT carrid,
       carrname,
       currcode
  FROM scarr
  WHERE carrid = @p_carrid
  INTO TABLE @DATA(lt_scarr).

IF sy-subrc <> 0.
  WRITE: / '조회 결과가 없습니다.'.
  RETURN.
ENDIF.
```

### 10.2 Internal Table 초기값 확인 방식

```abap
IF lt_scarr IS INITIAL.
  WRITE: / '조회 결과가 없습니다.'.
  RETURN.
ENDIF.
```

두 방식 모두 초급 단계에서 이해할 수 있다.  
다만 실제 코드에서는 조회 결과 테이블 자체를 확인하는 방식이 더 직관적인 경우가 많다.

### 10.3 실무 메시지 판단

조회 결과 없음은 업무적으로 세 가지 의미를 가질 수 있다.

| 상황 | 처리 |
|---|---|
| 사용자가 조건을 좁게 입력 | 안내 메시지 또는 빈 결과 |
| 필수 데이터가 존재해야 하는 업무 | 오류 또는 경고 |
| 권한 때문에 결과가 제한됨 | 권한 메시지 또는 별도 로그 |

초급 단계에서는 단순히 “No data found”를 출력하지만, 실무에서는 업무 의미를 판단해야 한다.

## 11. Main Logic을 직접 작성할 것인가, 분리할 것인가

작은 예제에서는 `START-OF-SELECTION` 안에 조회와 출력을 모두 작성해도 된다.  
하지만 실무 Report에서는 로직이 길어지므로 분리하는 것이 좋다.

### 11.1 초급 예제 수준

```abap
START-OF-SELECTION.
  SELECT ...
  LOOP AT ...
```

학습 초기에는 이 방식이 이해하기 쉽다.

### 11.2 실무형 구조

```abap
START-OF-SELECTION.
  PERFORM get_data.
  PERFORM display_data.
```

또는 OO 방식으로 다음처럼 구성할 수 있다.

```abap
START-OF-SELECTION.
  lcl_app=>run( ).
```

이번 모듈에서는 Classic Report Event를 학습하는 단계이므로 FORM 기반 예제를 먼저 본다.

```abap
REPORT ztr13_m05_start_select_04.

SELECT-OPTIONS s_carrid FOR scarr-carrid.

DATA gt_scarr TYPE STANDARD TABLE OF scarr.

START-OF-SELECTION.
  PERFORM get_data.
  PERFORM display_data.

FORM get_data.
  SELECT *
    FROM scarr
    WHERE carrid IN @s_carrid
    INTO TABLE @gt_scarr.
ENDFORM.

FORM display_data.
  IF gt_scarr IS INITIAL.
    WRITE: / '조회 결과가 없습니다.'.
    RETURN.
  ENDIF.

  LOOP AT gt_scarr INTO DATA(ls_scarr).
    WRITE: / ls_scarr-carrid,
             ls_scarr-carrname,
             ls_scarr-currcode.
  ENDLOOP.
ENDFORM.
```

### 11.3 책임 분리의 장점

| 장점 | 설명 |
|---|---|
| 가독성 | 이벤트 블록에서 전체 흐름이 보인다. |
| 유지보수성 | 조회 로직과 출력 로직을 따로 수정할 수 있다. |
| 테스트 용이성 | 후속 OO/ABAP Unit 학습으로 확장하기 쉽다. |
| 확장성 | ALV, 파일 다운로드, 메시지 처리로 확장하기 쉽다. |

## 12. START-OF-SELECTION에서 피해야 할 코드

### 12.1 모든 로직을 한 블록에 몰아넣기

나쁜 예:

```abap
START-OF-SELECTION.
  " 300줄 이상의 조회, 변환, 출력, 메시지, 권한 체크가 모두 섞임
```

문제점:

- 읽기 어렵다.
- 오류 위치를 찾기 어렵다.
- 유지보수 시 영향 범위 파악이 어렵다.
- 동일 로직 재사용이 어렵다.

### 12.2 Selection Screen 검증을 늦게 하기

나쁜 예:

```abap
START-OF-SELECTION.
  IF p_carrid IS INITIAL.
    WRITE: / '항공사 코드를 입력하세요.'.
    RETURN.
  ENDIF.
```

이 방식도 동작할 수 있지만, 입력 검증 책임은 보통 `AT SELECTION-SCREEN`에 두는 것이 명확하다.  
사용자 입력 오류는 Selection Screen 단계에서 막고, `START-OF-SELECTION`은 실행 가능한 조건을 전제로 처리하는 편이 좋다.

### 12.3 조건 없는 전체 테이블 조회

나쁜 예:

```abap
START-OF-SELECTION.
  SELECT *
    FROM zt_jhy_large_log
    INTO TABLE @DATA(lt_log).
```

대량 테이블에서 조건 없는 전체 조회는 성능 문제를 일으킬 수 있다.  
실무에서는 Selection Screen 조건, 최대 건수 제한, 인덱스 활용, 권한 체크 등을 고려해야 한다.

## 13. 성능 관점의 주의사항

`START-OF-SELECTION`은 사용자가 실행 버튼을 누른 뒤 실제 로직이 시작되는 지점이다.  
따라서 성능 이슈는 사용자가 직접 체감한다.

### 13.1 WHERE 조건을 명확히 작성한다

좋은 예:

```abap
SELECT carrid,
       connid,
       fldate
  FROM sflight
  WHERE carrid IN @s_carrid
    AND fldate IN @s_fldate
  INTO TABLE @DATA(lt_flight).
```

나쁜 예:

```abap
SELECT *
  FROM sflight
  INTO TABLE @DATA(lt_flight).
```

### 13.2 필요한 필드만 조회한다

초급자는 `SELECT *`를 자주 사용하지만, 실무에서는 필요한 필드만 조회하는 습관이 중요하다.

```abap
SELECT carrid,
       carrname,
       currcode
  FROM scarr
  INTO TABLE @DATA(lt_scarr).
```

필요하지 않은 필드를 모두 가져오면 네트워크, 메모리, 후속 처리 비용이 증가할 수 있다.

### 13.3 Internal Table 후처리를 고려한다

조회 후 Internal Table에서 정렬, 필터, LOOP 처리를 수행할 경우 데이터 건수가 많으면 프로그램 성능에 영향을 준다.  
따라서 가능한 필터링은 DB WHERE 조건에서 먼저 수행하는 것이 일반적으로 좋다.

## 14. 권한 관점의 주의사항

실무 Report에서는 데이터 조회 전에 권한을 확인해야 하는 경우가 많다.  
이번 모듈의 핵심은 `START-OF-SELECTION` 조회 실행이므로 권한 검증을 깊게 다루지는 않지만, 기본 위치 감각은 가져야 한다.

예를 들어 회사코드나 플랜트 기준으로 데이터를 조회하는 Report라면, 사용자가 해당 조직 데이터에 접근할 권한이 있는지 확인해야 한다.

일반적인 흐름은 다음과 같다.

```text
AT SELECTION-SCREEN
  → 입력 형식과 필수값 검증

START-OF-SELECTION
  → 권한 확인
  → 권한 통과 시 조회 실행
```

또는 입력 단계에서 조직값 권한까지 검사하는 설계도 가능하다.  
권한 검증은 고객사 보안 정책과 표준 Authorization Object에 따라 달라진다.

## 15. 디버깅 포인트

`START-OF-SELECTION`을 학습할 때 디버깅하면 이벤트 흐름을 매우 잘 이해할 수 있다.

### 15.1 권장 Breakpoint 위치

| 위치 | 확인할 내용 |
|---|---|
| `AT SELECTION-SCREEN` 시작 | 사용자가 입력한 값이 들어왔는지 확인 |
| `START-OF-SELECTION` 첫 줄 | 검증 통과 후 이벤트가 실행되는지 확인 |
| `SELECT` 직후 | 조회 결과와 `sy-subrc` 확인 |
| `LOOP AT` 내부 | 출력 대상 데이터 한 줄 확인 |
| `RETURN` 직전 | 결과 없음 또는 중단 조건 확인 |

### 15.2 확인할 변수

| 변수 | 확인 내용 |
|---|---|
| `p_carrid` | 단일 입력 파라미터 값 |
| `s_carrid[]` | SELECT-OPTIONS Range Table 내용 |
| `lt_scarr` | 조회 결과 Internal Table |
| `sy-subrc` | SELECT 결과 상태 |
| `sy-dbcnt` | DB 처리 건수 확인이 필요한 경우 참고 |

## 16. 실습: 조건 입력 후 START-OF-SELECTION에서 조회

### 16.1 실습 목표

Selection Screen에서 항공사 코드를 입력받고, `START-OF-SELECTION`에서 항공사 데이터를 조회하여 출력한다.

### 16.2 실습 코드

```abap
REPORT ztr13_m05_lab_start_select.

PARAMETERS p_carrid TYPE s_carr_id OBLIGATORY.

AT SELECTION-SCREEN.
  IF p_carrid IS INITIAL.
    MESSAGE e001(zmsg) WITH '항공사 코드를 입력하세요.'.
  ENDIF.

START-OF-SELECTION.

  SELECT carrid,
         carrname,
         currcode
    FROM scarr
    WHERE carrid = @p_carrid
    INTO TABLE @DATA(lt_scarr).

  IF lt_scarr IS INITIAL.
    WRITE: / '조회 결과가 없습니다. 입력값:', p_carrid.
    RETURN.
  ENDIF.

  WRITE: / '조회 조건:', p_carrid.
  ULINE.

  LOOP AT lt_scarr INTO DATA(ls_scarr).
    WRITE: / ls_scarr-carrid,
             ls_scarr-carrname,
             ls_scarr-currcode.
  ENDLOOP.
```

### 16.3 실행 절차

```text
1. SE38 또는 ADT에서 프로그램 생성
2. 코드 입력
3. Syntax Check
4. Activate
5. Execute
6. Selection Screen에서 항공사 코드 입력
7. 실행
8. 결과 리스트 확인
```

### 16.4 테스트 케이스

| 케이스 | 입력값 | 기대 결과 |
|---|---|---|
| 정상 조회 | 시스템에 존재하는 항공사 코드 | 항공사 정보 출력 |
| 결과 없음 | 존재하지 않는 코드 | 조회 결과 없음 메시지 |
| 미입력 | 공백 | OBLIGATORY 또는 검증 메시지 |
| 소문자 입력 | aa | 시스템/타입 설정에 따라 대문자 변환 또는 결과 없음 |

> [추정] Demo 테이블의 실제 데이터는 교육 시스템마다 다를 수 있으므로, 정상 조회 케이스는 `SE16N` 또는 ADT Data Preview에서 먼저 존재하는 값을 확인한 뒤 테스트한다.

## 17. 오류 상황과 해결

### 17.1 `START-OF-SELECTION`이 실행되지 않는 것처럼 보이는 경우

가능한 원인:

| 원인 | 설명 |
|---|---|
| Selection Screen 검증 오류 | `AT SELECTION-SCREEN`에서 E 메시지가 발생하면 진행되지 않는다. |
| 필수 입력 누락 | `OBLIGATORY` 필드가 비어 있으면 실행 전 막힌다. |
| 프로그램 미활성화 | 최신 코드가 활성화되지 않았을 수 있다. |
| Breakpoint 위치 오류 | 이벤트 흐름을 잘못 예상했을 수 있다. |

해결:

```text
1. Selection Screen 메시지 확인
2. AT SELECTION-SCREEN 로직 확인
3. 프로그램 Activate 확인
4. START-OF-SELECTION 첫 줄에 Breakpoint 설정
```

### 17.2 조회 결과가 없는 경우

가능한 원인:

| 원인 | 설명 |
|---|---|
| 입력 조건이 실제 데이터와 불일치 | 존재하지 않는 코드 입력 |
| Client 차이 | 다른 Client에 데이터 존재 |
| 조건이 너무 좁음 | 여러 조건이 함께 적용되어 결과 없음 |
| 권한 제한 | 사용자가 조회 가능한 데이터가 제한됨 |
| 테이블 자체에 데이터 없음 | Demo 또는 교육용 테이블 데이터 미준비 |

해결:

```text
1. SE16N에서 테이블 데이터 존재 확인
2. 조건을 줄여서 조회
3. Client 확인
4. 권한 오류 메시지 또는 Trace 확인
5. 테스트 데이터 입력 여부 확인
```

### 17.3 SQL 문법 오류

예:

```abap
WHERE carrid = p_carrid
```

최신 Open SQL 문법에서는 ABAP 변수 사용 시 `@`를 붙이는 방식이 일반적이다.

권장:

```abap
WHERE carrid = @p_carrid
```

시스템 릴리스와 구문 모드에 따라 허용 범위가 다를 수 있으므로, 교육에서는 최신 Open SQL 스타일을 기준으로 익히는 것이 좋다.

## 18. 실무 적용 기준

### 18.1 START-OF-SELECTION에 둘 수 있는 것

| 가능 | 설명 |
|---|---|
| 메인 흐름 제어 | 조회, 변환, 출력 호출 순서 |
| 주요 데이터 조회 | Open SQL 호출 |
| 권한 체크 호출 | 조회 전 권한 검증 |
| FORM/Method 호출 | 로직 분리 |
| 실행 로그 시작 | 필요 시 처리 시작 기록 |

### 18.2 START-OF-SELECTION에 과도하게 두지 말아야 할 것

| 비권장 | 이유 |
|---|---|
| 모든 DB 조회와 변환과 출력을 한 블록에 작성 | 유지보수성 저하 |
| Selection Screen UI 제어 | `AT SELECTION-SCREEN OUTPUT` 책임 |
| 입력 형식 검증 | `AT SELECTION-SCREEN` 책임 |
| 대량 데이터 무조건 전체 조회 | 성능 문제 |
| 권한 체크 생략 | 운영 보안 문제 |

### 18.3 실무형 구조 예

```abap
START-OF-SELECTION.
  PERFORM check_authority.
  PERFORM get_data.
  PERFORM process_data.
  PERFORM display_data.
```

이 구조는 이벤트 블록을 “목차”처럼 만들어준다.  
실제 상세 로직은 각 FORM 또는 Class Method에 위임한다.

## 19. 후속 모듈과의 연결

이번 모듈에서 `START-OF-SELECTION`은 조회 실행의 중심 이벤트로 다루었다.  
다음 모듈인 `THEORY-13-M06 END-OF-SELECTION 출력 마무리`에서는 조회 이후 결과를 마무리하거나 출력 단계로 정리하는 흐름을 다룬다.

연결 관계는 다음과 같다.

```text
AT SELECTION-SCREEN
  → 입력값 검증

START-OF-SELECTION
  → 조회 실행과 메인 로직

END-OF-SELECTION
  → 결과 출력 및 마무리
```

이 흐름을 이해하면 Classic Report의 이벤트 기반 구조를 훨씬 명확하게 설계할 수 있다.

## 20. 평가 문제

### 20.1 객관식

#### Q1. `START-OF-SELECTION`의 가장 적절한 역할은 무엇인가?

A. 프로그램 로드 시 전역 변수를 생성한다.  
B. Selection Screen 필드의 화면 속성을 동적으로 변경한다.  
C. 입력값 검증 후 본격적인 조회와 메인 로직을 실행한다.  
D. 출력 리스트가 모두 끝난 뒤 화면을 닫는다.

**정답:** C

#### Q2. Selection Screen 입력값 검증에 가장 적절한 이벤트는?

A. `INITIALIZATION`  
B. `AT SELECTION-SCREEN`  
C. `START-OF-SELECTION`  
D. `END-OF-SELECTION`

**정답:** B

#### Q3. `SELECT-OPTIONS s_carrid`를 Open SQL 조건에 사용하는 올바른 예는?

A. `WHERE carrid = @s_carrid`  
B. `WHERE carrid IN @s_carrid`  
C. `WHERE s_carrid = @carrid`  
D. `WHERE carrid LIKE @s_carrid`

**정답:** B

### 20.2 서술형

#### Q1. `AT SELECTION-SCREEN`과 `START-OF-SELECTION`의 책임 차이를 설명하시오.

**모범 답안:**  
`AT SELECTION-SCREEN`은 사용자가 입력한 값을 실행 전에 검증하는 이벤트이고, `START-OF-SELECTION`은 검증이 통과된 뒤 조회와 메인 업무 로직을 실행하는 이벤트이다.

#### Q2. `START-OF-SELECTION` 안에 모든 로직을 작성하면 왜 문제가 되는가?

**모범 답안:**  
코드가 길어지고 조회, 변환, 출력, 권한 체크가 섞여 가독성과 유지보수성이 떨어진다. 실무에서는 이벤트 블록에서 전체 흐름만 제어하고 상세 로직은 FORM이나 Method로 분리하는 것이 좋다.

#### Q3. 조회 결과가 없을 때 확인할 항목을 세 가지 이상 쓰시오.

**모범 답안:**  
입력 조건이 실제 데이터와 일치하는지, 테이블에 데이터가 존재하는지, Client가 맞는지, 조건이 너무 좁지 않은지, 권한 제한이 있는지 확인한다.
