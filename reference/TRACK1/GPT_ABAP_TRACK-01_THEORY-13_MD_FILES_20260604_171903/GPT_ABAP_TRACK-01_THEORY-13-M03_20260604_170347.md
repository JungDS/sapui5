## 3. 왜 동적 Selection Screen이 필요한가?

실무 Report는 사용자의 입력 조건에 따라 조회 방식이 달라지는 경우가 많다.

예를 들어 다음과 같은 요구사항을 생각해보자.

```text
사용자가 “고객 기준 조회”를 선택하면 고객번호 입력 필드를 보여준다.
사용자가 “자재 기준 조회”를 선택하면 자재번호 입력 필드를 보여준다.
사용자가 “상세 옵션 사용”을 체크하면 추가 조건 필드를 입력 가능하게 한다.
일반 사용자는 특정 고급 옵션을 수정하지 못하게 한다.
```

이런 경우 모든 필드를 항상 열어두면 화면이 복잡해진다.  
사용자가 잘못된 조합으로 입력할 가능성도 커진다.

동적 Selection Screen 제어를 사용하면 다음 효과를 얻을 수 있다.

| 효과 | 설명 |
|---|---|
| 화면 단순화 | 현재 선택에 필요한 필드만 보이게 하거나 입력 가능하게 한다. |
| 입력 오류 감소 | 불필요하거나 충돌하는 필드를 비활성화한다. |
| 사용자 경험 개선 | 업무 흐름에 맞는 화면을 제공한다. |
| 프로그램 의도 명확화 | 어떤 조건이 어떤 모드에서 사용되는지 화면 수준에서 표현한다. |

하지만 화면 제어는 어디까지나 **사용자 편의와 입력 흐름 안내**를 위한 것이다.  
정말 중요한 검증은 `AT SELECTION-SCREEN` 이벤트에서 별도로 수행해야 한다.

## 4. Selection Screen 이벤트 흐름 속 위치

Classic ABAP Report의 대표 흐름을 단순화하면 다음과 같다.

```text
LOAD-OF-PROGRAM
  ↓
INITIALIZATION
  ↓
AT SELECTION-SCREEN OUTPUT
  ↓
Selection Screen 표시
  ↓
사용자 입력
  ↓
AT SELECTION-SCREEN
  ↓
START-OF-SELECTION
  ↓
END-OF-SELECTION
```

이번 모듈의 위치는 다음이다.

```text
화면이 사용자에게 보이기 직전
```

즉, `AT SELECTION-SCREEN OUTPUT`은 Selection Screen의 **PBO(Process Before Output) 성격**으로 이해할 수 있다.

> 주의: `AT SELECTION-SCREEN OUTPUT`은 한 번만 실행된다고 단정하면 안 된다. 사용자가 Enter를 누르거나 화면이 다시 그려지는 상황에서 반복 실행될 수 있다. 따라서 이 이벤트 안의 로직은 반복 실행되어도 안정적으로 동작해야 한다.

## 5. `INITIALIZATION`과의 차이

초급자가 가장 많이 혼동하는 지점은 `INITIALIZATION`과 `AT SELECTION-SCREEN OUTPUT`이다.

| 구분 | `INITIALIZATION` | `AT SELECTION-SCREEN OUTPUT` |
|---|---|---|
| 주요 목적 | Selection Screen 기본값 설정 | Selection Screen 필드 속성 동적 변경 |
| 대표 작업 | Parameter 기본값 입력 | 필드 활성/비활성, 숨김, 필수 표시 |
| 실행 시점 | Selection Screen 최초 표시 전 | 화면 출력 직전 |
| 반복 실행 가능성 | 일반적으로 초기화 목적 중심 | 화면 출력 전마다 반복 가능 |
| 주로 다루는 대상 | 변수 값 | `SCREEN` 속성 |
| 예시 | `p_bukrs = '1000'.` | `screen-input = 0.` |

간단히 구분하면 다음과 같다.

```text
값을 넣고 싶다 → INITIALIZATION
화면 속성을 바꾸고 싶다 → AT SELECTION-SCREEN OUTPUT
입력값을 검증하고 싶다 → AT SELECTION-SCREEN
실제 조회를 실행하고 싶다 → START-OF-SELECTION
```

## 6. `AT SELECTION-SCREEN OUTPUT` 기본 구조

가장 기본적인 구조는 다음과 같다.

```abap
AT SELECTION-SCREEN OUTPUT.

  LOOP AT SCREEN.
    " screen 속성 변경
    MODIFY SCREEN.
  ENDLOOP.
```

여기서 핵심은 `SCREEN`이라는 시스템 구조이다.  
`LOOP AT SCREEN`을 수행하면 현재 Selection Screen에 배치된 화면 요소들이 하나씩 `SCREEN` 구조에 들어온다.

개발자는 각 화면 요소의 이름이나 그룹을 확인하여 속성을 변경하고, `MODIFY SCREEN`으로 변경 내용을 반영한다.

---

## 7. `SCREEN` 구조의 주요 필드

초급 단계에서 반드시 알아야 할 필드는 다음이다.

| `SCREEN` 필드 | 의미 | 대표 사용 |
|---|---|---|
| `SCREEN-NAME` | 화면 요소 이름 | 특정 필드 직접 식별 |
| `SCREEN-GROUP1` | `MODIF ID` 값 | 필드 그룹별 제어 |
| `SCREEN-ACTIVE` | 화면 요소 활성 여부 | 필드 숨김/비활성 처리 |
| `SCREEN-INPUT` | 입력 가능 여부 | Read-only 처리 |
| `SCREEN-INVISIBLE` | 보이지 않게 표시 | 숨김 처리 |
| `SCREEN-REQUIRED` | 필수 입력 표시 | 동적 필수 표시 |
| `SCREEN-INTENSIFIED` | 강조 표시 | 필드 강조 |

### 7.1 `SCREEN-NAME`

`SCREEN-NAME`은 화면 요소의 이름이다.  
Parameter 이름을 기준으로 제어할 때 사용할 수 있다.

예:

```abap
IF screen-name = 'P_CARRID'.
  screen-input = 0.
  MODIFY SCREEN.
ENDIF.
```

단, `SELECT-OPTIONS`는 내부적으로 여러 화면 요소를 생성하므로 단순히 하나의 이름만 생각하면 안 된다.  
초급 실습에서는 `MODIF ID` 기반 제어를 우선 권장한다.

### 7.2 `SCREEN-GROUP1`

`SCREEN-GROUP1`은 Selection Screen 필드에 지정한 `MODIF ID` 값이 들어가는 영역이다.

예:

```abap
PARAMETERS p_date TYPE sy-datum MODIF ID adv.
```

이 경우 `LOOP AT SCREEN` 중 해당 필드는 보통 `SCREEN-GROUP1 = 'ADV'` 기준으로 식별할 수 있다.

> `MODIF ID`는 Selection Screen 필드 그룹 제어에 매우 유용하다. 실무에서는 개별 필드명을 일일이 비교하기보다 MODIF ID로 그룹화하는 방식이 유지보수에 유리하다.

### 7.3 `SCREEN-ACTIVE`

`SCREEN-ACTIVE = 0`으로 설정하면 해당 화면 요소를 비활성화한다.  
상황에 따라 화면에서 보이지 않거나 입력 대상에서 제외되는 효과로 이해하면 된다.

초급자에게는 다음처럼 설명할 수 있다.

```text
이 필드를 현재 화면 흐름에서 사용하지 않도록 한다.
```

### 7.4 `SCREEN-INPUT`

`SCREEN-INPUT = 0`은 필드를 화면에는 보이게 하되 사용자가 입력하지 못하게 만드는 데 사용한다.

예:

```text
보여주기는 하지만 수정은 못하게 하는 필드
```

### 7.5 `SCREEN-INVISIBLE`

`SCREEN-INVISIBLE = 1`은 필드를 보이지 않게 만드는 목적에 사용한다.  
입력 가능 여부와 함께 고려해야 한다.

### 7.6 `SCREEN-REQUIRED`

`SCREEN-REQUIRED = 1`은 필수 입력 표시를 동적으로 제어할 때 사용한다.

다만 초급자가 주의할 점이 있다.  
화면에서 필수 표시를 한다고 해서 모든 업무 검증이 끝나는 것은 아니다.  
중요한 입력 검증은 다음 모듈의 `AT SELECTION-SCREEN`에서 반드시 수행해야 한다.

## 8. `MODIF ID`의 목적

`MODIF ID`는 Selection Screen 필드를 그룹화하기 위한 식별자이다.

예를 들어 고급 옵션 필드를 하나의 그룹으로 묶고 싶다면 다음처럼 선언할 수 있다.

```abap
PARAMETERS p_adv1 TYPE c LENGTH 10 MODIF ID adv.
PARAMETERS p_adv2 TYPE c LENGTH 10 MODIF ID adv.
```

이후 `AT SELECTION-SCREEN OUTPUT`에서 다음처럼 제어한다.

```abap
LOOP AT SCREEN.
  IF screen-group1 = 'ADV'.
    screen-active = 0.
    MODIFY SCREEN.
  ENDIF.
ENDLOOP.
```

이 방식의 장점은 명확하다.

| 장점 | 설명 |
|---|---|
| 유지보수 쉬움 | 필드가 늘어나도 같은 MODIF ID만 부여하면 된다. |
| 의미 단위 제어 | 고객조회 필드, 자재조회 필드, 고급옵션 필드처럼 그룹화 가능 |
| 코드 단순화 | `SCREEN-NAME`을 여러 개 비교하지 않아도 된다. |
| 실무 확장성 | 화면 조건이 복잡해질수록 그룹 제어가 유리하다. |

## 9. 기본 예제 1: 체크박스로 고급 옵션 활성화

### 9.1 요구사항

```text
기본 조건은 항상 입력 가능하다.
“고급 옵션 사용” 체크박스를 선택한 경우에만 고급 조건 필드를 입력할 수 있다.
체크하지 않으면 고급 조건 필드는 입력 불가능하게 한다.
```

### 9.2 예제 코드

```abap
REPORT zgpt_sel_screen_output_01.

PARAMETERS p_carrid TYPE s_carr_id.

PARAMETERS p_adv AS CHECKBOX USER-COMMAND adv.

PARAMETERS p_max TYPE i MODIF ID adv.
PARAMETERS p_sort TYPE c LENGTH 1 MODIF ID adv.

INITIALIZATION.
  p_carrid = 'AA'.
  p_max    = 100.
  p_sort   = 'A'.

AT SELECTION-SCREEN OUTPUT.

  LOOP AT SCREEN.
    IF screen-group1 = 'ADV'.
      IF p_adv = abap_true.
        screen-input = 1.
        screen-active = 1.
      ELSE.
        screen-input = 0.
        screen-active = 1.
      ENDIF.

      MODIFY SCREEN.
    ENDIF.
  ENDLOOP.

START-OF-SELECTION.

  WRITE: / 'Carrier:', p_carrid,
         / 'Advanced:', p_adv,
         / 'Max Rows:', p_max,
         / 'Sort Type:', p_sort.
```

### 9.3 코드 해설

| 코드 | 의미 |
|---|---|
| `p_adv AS CHECKBOX` | 고급 옵션 사용 여부를 입력받는다. |
| `USER-COMMAND adv` | 체크박스 변경 시 화면이 다시 처리되도록 한다. |
| `MODIF ID adv` | 고급 옵션 필드를 ADV 그룹으로 묶는다. |
| `AT SELECTION-SCREEN OUTPUT` | 화면 표시 직전에 실행된다. |
| `LOOP AT SCREEN` | 화면 요소를 하나씩 순회한다. |
| `screen-group1 = 'ADV'` | ADV 그룹의 필드만 제어한다. |
| `screen-input = 0` | 필드를 보이지만 입력 불가능하게 한다. |
| `MODIFY SCREEN` | 변경한 화면 속성을 반영한다. |

> 참고: `abap_true` 사용을 위해 시스템/문맥에 따라 `TYPE abap_bool` 또는 `abap_true` 사용 가능 여부가 다를 수 있다. 초급 교육 시스템에서 `abap_true`가 바로 인식되지 않으면 체크박스 값 `'X'`를 사용해도 된다.

## 10. 기본 예제 2: Radio Button으로 입력 그룹 전환

### 10.1 요구사항

```text
항공사 기준 조회를 선택하면 CARRID 입력 필드를 활성화한다.
연결번호 기준 조회를 선택하면 CONNID 입력 필드를 활성화한다.
선택되지 않은 그룹은 입력 불가능하게 한다.
```

### 10.2 예제 코드

```abap
REPORT zgpt_sel_screen_output_02.

PARAMETERS r_car RADIOBUTTON GROUP g1 DEFAULT 'X' USER-COMMAND mode.
PARAMETERS r_con RADIOBUTTON GROUP g1.

PARAMETERS p_carrid TYPE s_carr_id MODIF ID car.
PARAMETERS p_connid TYPE s_conn_id MODIF ID con.

AT SELECTION-SCREEN OUTPUT.

  LOOP AT SCREEN.

    CASE screen-group1.
      WHEN 'CAR'.
        IF r_car = abap_true.
          screen-input = 1.
          screen-active = 1.
        ELSE.
          screen-input = 0.
          screen-active = 1.
        ENDIF.
        MODIFY SCREEN.

      WHEN 'CON'.
        IF r_con = abap_true.
          screen-input = 1.
          screen-active = 1.
        ELSE.
          screen-input = 0.
          screen-active = 1.
        ENDIF.
        MODIFY SCREEN.
    ENDCASE.

  ENDLOOP.

START-OF-SELECTION.

  IF r_car = abap_true.
    WRITE: / 'Mode: Carrier',
           / 'Carrier:', p_carrid.
  ELSE.
    WRITE: / 'Mode: Connection',
           / 'Connection:', p_connid.
  ENDIF.
```

### 10.3 실무적 의미

이 패턴은 실무 Report에서 매우 자주 사용된다.

예:

| 선택 모드 | 활성화 필드 |
|---|---|
| 고객 기준 조회 | 고객 번호 |
| 자재 기준 조회 | 자재 번호 |
| 전표 기준 조회 | 회사코드, 전표번호, 회계연도 |
| 기간 기준 조회 | 시작일, 종료일 |

동적 화면 제어를 사용하면 사용자가 현재 모드에 맞는 조건만 입력하도록 유도할 수 있다.

## 11. 숨김과 비활성의 차이

화면 필드를 제어할 때 가장 중요한 실무 판단 중 하나는 “숨길 것인가, 보이되 입력만 막을 것인가”이다.

| 방식 | 대표 속성 | 사용자 경험 | 적합한 경우 |
|---|---|---|---|
| 입력만 비활성 | `screen-input = 0` | 필드는 보이지만 수정 불가 | 값은 참고해야 하지만 변경하면 안 되는 경우 |
| 화면에서 숨김 | `screen-active = 0` 또는 `screen-invisible = 1` 조합 | 사용자가 필드를 보지 않음 | 현재 모드에서 완전히 불필요한 경우 |
| 필수 표시 | `screen-required = 1` | 입력 필요성을 시각적으로 안내 | 조건부 필수값 안내 |

초급자에게는 다음 기준을 권장한다.

```text
사용자가 필드 존재를 알아야 한다 → 비활성화
사용자가 해당 필드를 신경 쓸 필요가 없다 → 숨김
업무적으로 반드시 입력해야 한다 → 화면 표시 + AT SELECTION-SCREEN 검증
```

---

## 12. 동적 필수 입력 처리

### 12.1 요구사항

```text
상세 조회 모드를 선택하면 상세 기준일을 필수로 입력하게 한다.
기본 조회 모드에서는 상세 기준일이 필수가 아니다.
```

### 12.2 예제

```abap
REPORT zgpt_sel_screen_output_03.

PARAMETERS r_basic RADIOBUTTON GROUP g1 DEFAULT 'X' USER-COMMAND mode.
PARAMETERS r_det   RADIOBUTTON GROUP g1.

PARAMETERS p_date TYPE sy-datum MODIF ID det.

AT SELECTION-SCREEN OUTPUT.

  LOOP AT SCREEN.
    IF screen-group1 = 'DET'.
      IF r_det = abap_true.
        screen-input    = 1.
        screen-required = 1.
      ELSE.
        screen-input    = 0.
        screen-required = 0.
      ENDIF.

      MODIFY SCREEN.
    ENDIF.
  ENDLOOP.

AT SELECTION-SCREEN.

  IF r_det = abap_true AND p_date IS INITIAL.
    MESSAGE '상세 조회 모드에서는 기준일을 입력해야 합니다.' TYPE 'E'.
  ENDIF.

START-OF-SELECTION.

  WRITE: / 'Basic Mode:', r_basic,
         / 'Detail Mode:', r_det,
         / 'Date:', p_date.
```

### 12.3 중요한 포인트

여기서 `screen-required = 1`은 사용자에게 필수 입력처럼 보이게 하는 화면 제어이다.  
하지만 실제 업무 검증은 `AT SELECTION-SCREEN`에서 `MESSAGE TYPE 'E'`로 수행한다.

즉, 역할을 다음처럼 분리해야 한다.

```text
AT SELECTION-SCREEN OUTPUT
→ 화면 안내와 입력 편의 제공

AT SELECTION-SCREEN
→ 실제 입력값 검증과 오류 차단
```

이 분리는 실무에서 매우 중요하다.

---

## 13. `USER-COMMAND`의 역할

Checkbox나 Radio Button을 변경했을 때 Selection Screen이 즉시 다시 그려져야 한다면 `USER-COMMAND`가 필요하다.

예:

```abap
PARAMETERS p_adv AS CHECKBOX USER-COMMAND adv.
```

또는

```abap
PARAMETERS r_car RADIOBUTTON GROUP g1 DEFAULT 'X' USER-COMMAND mode.
PARAMETERS r_con RADIOBUTTON GROUP g1.
```

`USER-COMMAND`를 지정하면 사용자가 해당 필드를 조작했을 때 화면 처리가 다시 발생하고, 그 과정에서 `AT SELECTION-SCREEN OUTPUT` 로직이 다시 반영될 수 있다.

초급자가 겪는 대표 문제는 다음이다.

```text
체크박스를 눌렀는데 화면 필드가 바로 바뀌지 않는다.
```

이 경우 `USER-COMMAND` 지정 여부를 먼저 확인한다.

## 14. `LOOP AT SCREEN` 작성 패턴

실무적으로는 다음 패턴을 권장한다.

### 14.1 좋은 패턴

```abap
AT SELECTION-SCREEN OUTPUT.

  LOOP AT SCREEN.
    CASE screen-group1.
      WHEN 'ADV'.
        PERFORM set_advanced_screen.
      WHEN 'CAR'.
        PERFORM set_carrier_screen.
      WHEN 'CON'.
        PERFORM set_connection_screen.
    ENDCASE.

    MODIFY SCREEN.
  ENDLOOP.
```

다만 초급 실습에서는 `FORM`을 아직 배우지 않았거나 OO 모듈 전이라면, 한 블록 안에서 명확하게 작성해도 된다.

### 14.2 너무 복잡한 패턴

```abap
IF screen-name = 'P_A' OR screen-name = 'P_B' OR screen-name = 'P_C'
   OR screen-name = 'P_D' OR screen-name = 'P_E'.
```

이런 코드는 필드가 늘어날수록 유지보수가 어려워진다.  
가능하면 `MODIF ID`를 사용하여 의미 단위로 묶는다.

## 15. 실습: 조회 모드에 따른 Selection Screen 제어

### 15.1 실습 목표

Radio Button 선택에 따라 조회 조건 필드를 동적으로 활성화한다.

### 15.2 요구사항

```text
1. 항공사 기준 조회 모드와 날짜 기준 조회 모드를 만든다.
2. 항공사 기준 조회 모드에서는 CARRID 필드만 입력 가능하게 한다.
3. 날짜 기준 조회 모드에서는 FLDATE 필드만 입력 가능하게 한다.
4. 비활성화된 필드는 화면에 보이지만 입력하지 못하게 한다.
5. 실행 시 선택 모드와 입력값을 WRITE로 출력한다.
```

### 15.3 예제 코드

```abap
REPORT ztra_theory_13_m03.

PARAMETERS r_car  RADIOBUTTON GROUP g1 DEFAULT 'X' USER-COMMAND mode.
PARAMETERS r_date RADIOBUTTON GROUP g1.

PARAMETERS p_carr TYPE s_carr_id MODIF ID car.
PARAMETERS p_date TYPE s_date    MODIF ID dat.

INITIALIZATION.
  p_carr = 'AA'.
  p_date = sy-datum.

AT SELECTION-SCREEN OUTPUT.

  LOOP AT SCREEN.

    CASE screen-group1.
      WHEN 'CAR'.
        IF r_car = abap_true.
          screen-input = 1.
        ELSE.
          screen-input = 0.
        ENDIF.
        MODIFY SCREEN.

      WHEN 'DAT'.
        IF r_date = abap_true.
          screen-input = 1.
        ELSE.
          screen-input = 0.
        ENDIF.
        MODIFY SCREEN.
    ENDCASE.

  ENDLOOP.

START-OF-SELECTION.

  IF r_car = abap_true.
    WRITE: / '조회 모드: 항공사 기준',
           / '항공사:', p_carr.
  ELSE.
    WRITE: / '조회 모드: 날짜 기준',
           / '비행일:', p_date.
  ENDIF.
```

### 15.4 실습 관찰 포인트

실행 후 다음을 확인한다.

| 관찰 항목 | 확인 내용 |
|---|---|
| 최초 화면 | 항공사 기준 Radio Button이 기본 선택되어 있는가 |
| 항공사 모드 | `P_CARR`는 입력 가능하고 `P_DATE`는 입력 불가능한가 |
| 날짜 모드 | `P_DATE`는 입력 가능하고 `P_CARR`는 입력 불가능한가 |
| Radio Button 변경 | 선택 변경 시 화면 속성이 즉시 반영되는가 |
| 실행 결과 | 선택한 모드와 입력값이 WRITE로 출력되는가 |

## 16. 오류 상황과 해결 방법

### 16.1 화면이 동적으로 바뀌지 않음

| 항목 | 내용 |
|---|---|
| 증상 | 체크박스나 Radio Button을 바꿔도 필드 상태가 바로 바뀌지 않음 |
| 원인 | `USER-COMMAND` 누락 가능성 |
| 해결 | 화면 제어를 유발할 Checkbox 또는 Radio Button에 `USER-COMMAND` 추가 |

### 16.2 `MODIF ID`를 지정했는데 제어가 안 됨

| 항목 | 내용 |
|---|---|
| 증상 | `screen-group1 = 'ADV'` 조건이 타지 않음 |
| 원인 | `MODIF ID` 오타, 대소문자 혼동, 다른 그룹 필드에 지정 |
| 해결 | Parameter 선언의 `MODIF ID`와 `screen-group1` 비교값 확인 |

### 16.3 `MODIFY SCREEN`을 빼먹음

| 항목 | 내용 |
|---|---|
| 증상 | `screen-input` 값을 변경했지만 화면에 반영되지 않음 |
| 원인 | `MODIFY SCREEN` 누락 |
| 해결 | `SCREEN` 속성 변경 후 반드시 `MODIFY SCREEN` 실행 |

### 16.4 입력 검증을 화면 제어로만 처리함

| 항목 | 내용 |
|---|---|
| 증상 | 필수값이 비어 있어도 프로그램이 실행됨 |
| 원인 | `screen-required` 표시만 하고 실제 검증을 하지 않음 |
| 해결 | `AT SELECTION-SCREEN`에서 `MESSAGE TYPE 'E'`로 검증 추가 |

### 16.5 숨긴 필드 값이 내부에 남아 있음

| 항목 | 내용 |
|---|---|
| 증상 | 화면에서 보이지 않는 필드의 기존 값이 실행 로직에 영향을 줌 |
| 원인 | 필드를 숨겼지만 변수 값 자체는 초기화하지 않음 |
| 해결 | 실행 로직에서 선택 모드에 맞는 필드만 사용하거나, 필요 시 값을 명시적으로 초기화 |

## 17. 동적 화면 제어와 입력 검증의 역할 분리

실무에서 매우 중요한 원칙은 다음이다.

```text
화면 제어는 사용자 편의 기능이다.
입력 검증은 업무 정합성 보장 기능이다.
```

### 17.1 화면 제어에 적합한 것

| 작업 | 위치 |
|---|---|
| 현재 모드와 무관한 필드 비활성화 | `AT SELECTION-SCREEN OUTPUT` |
| 특정 옵션 선택 시 추가 필드 표시 | `AT SELECTION-SCREEN OUTPUT` |
| 필드 필수 표시 | `AT SELECTION-SCREEN OUTPUT` |
| 필드 강조 | `AT SELECTION-SCREEN OUTPUT` |

### 17.2 입력 검증에 적합한 것

| 작업 | 위치 |
|---|---|
| 필수 입력 누락 차단 | `AT SELECTION-SCREEN` |
| 존재하지 않는 고객/자재/항공사 입력 차단 | `AT SELECTION-SCREEN` |
| 시작일이 종료일보다 늦은 경우 차단 | `AT SELECTION-SCREEN` |
| 권한 없는 조건 입력 차단 | `AT SELECTION-SCREEN` 또는 후속 권한 검증 로직 |

다음 모듈 `THEORY-13-M04`에서는 이 입력 검증을 본격적으로 다룬다.

## 18. 실무 적용 기준

### 18.1 동적 화면 제어가 적합한 경우

| 상황 | 판단 |
|---|---|
| 조회 모드가 여러 개인 Report | 적합 |
| 고급 옵션을 선택적으로 보여주고 싶음 | 적합 |
| 사용자 권한에 따라 특정 필드 입력을 제한하고 싶음 | 가능하나 실제 권한 검증 별도 필요 |
| 단순한 기본값 설정만 필요 | `INITIALIZATION`이 더 적합 |
| 입력값 오류를 차단해야 함 | `AT SELECTION-SCREEN` 검증이 필요 |

### 18.2 남용하면 안 되는 이유

동적 Selection Screen은 편리하지만 과도하게 사용하면 화면 로직이 복잡해진다.

문제점은 다음과 같다.

| 문제 | 설명 |
|---|---|
| 유지보수 어려움 | 화면 상태 조건이 많아지면 추적이 어렵다. |
| 테스트 케이스 증가 | 모드 조합별 화면 상태를 모두 확인해야 한다. |
| 숨겨진 값 문제 | 숨긴 필드의 기존 값이 실행 로직에 남아 영향을 줄 수 있다. |
| 권한 검증 착각 | 화면에서 막았다고 보안 검증이 끝난 것은 아니다. |
| 사용자 혼란 | 필드가 너무 자주 바뀌면 화면 예측성이 떨어진다. |

실무 기준으로는 다음 원칙이 좋다.

```text
화면 제어 조건은 단순하게 유지한다.
업무 검증은 반드시 별도 이벤트에서 수행한다.
MODIF ID로 의미 단위 그룹화를 사용한다.
숨긴 필드의 값이 실행 로직에 영향을 주지 않도록 한다.
```

## 19. 코드 리뷰 체크리스트

`AT SELECTION-SCREEN OUTPUT` 로직을 리뷰할 때는 다음을 확인한다.

| 체크 항목 | 질문 |
|---|---|
| 이벤트 위치 | 화면 제어 로직이 `AT SELECTION-SCREEN OUTPUT`에 있는가 |
| 그룹화 | `MODIF ID`를 사용해 의미 단위로 그룹화했는가 |
| 반영 | `MODIFY SCREEN`을 누락하지 않았는가 |
| 반복 실행 안정성 | 이벤트가 여러 번 실행되어도 값이 꼬이지 않는가 |
| 검증 분리 | 입력값 검증을 `AT SELECTION-SCREEN`에서 수행하는가 |
| 숨김 필드 값 | 숨긴 필드 값이 실행 로직에 잘못 사용되지 않는가 |
| 가독성 | 화면 상태 조건이 지나치게 복잡하지 않은가 |
| 사용자 경험 | 필드가 갑자기 사라져도 사용자가 이해할 수 있는가 |

## 20. 강사용 설명 포인트

강의에서는 다음 순서로 설명하면 좋다.

```text
1. Selection Screen 이벤트 흐름 복습
2. INITIALIZATION과 OUTPUT 이벤트 차이 설명
3. 화면 요소를 SCREEN 구조로 제어한다는 개념 소개
4. LOOP AT SCREEN 기본 패턴 시연
5. MODIF ID 없이 SCREEN-NAME으로 제어하는 방식의 한계 설명
6. MODIF ID 기반 그룹 제어 예제 구현
7. USER-COMMAND 누락 시 화면이 즉시 바뀌지 않는 문제 시연
8. AT SELECTION-SCREEN 검증과 역할 분리 강조
```

초급자에게는 `SCREEN` 구조의 모든 필드를 암기시키기보다, 다음 네 가지를 먼저 확실히 익히게 하는 것이 좋다.

```text
SCREEN-GROUP1
SCREEN-ACTIVE
SCREEN-INPUT
MODIFY SCREEN
```

### 21.2 단답형

#### Q1. `INITIALIZATION`과 `AT SELECTION-SCREEN OUTPUT`의 차이를 설명하시오.

**모범 답안:**  
`INITIALIZATION`은 Selection Screen이 처음 표시되기 전에 기본값을 설정하는 데 주로 사용한다. `AT SELECTION-SCREEN OUTPUT`은 Selection Screen이 표시되기 직전에 화면 요소의 표시 여부, 입력 가능 여부, 필수 표시 등을 동적으로 제어하는 데 사용한다.

#### Q2. `USER-COMMAND`가 필요한 대표 상황을 설명하시오.

**모범 답안:**  
Checkbox나 Radio Button을 변경했을 때 Selection Screen이 즉시 다시 처리되어 화면 필드 활성/비활성 상태가 바뀌어야 하는 경우 `USER-COMMAND`가 필요하다.

#### Q3. 화면 제어와 입력 검증을 분리해야 하는 이유는?

**모범 답안:**  
화면 제어는 사용자 편의와 안내를 위한 것이고, 업무 정합성을 보장하는 실제 검증은 별도로 수행해야 한다. 화면에서 필드를 비활성화하거나 필수 표시를 했다고 해서 모든 입력 오류가 차단되는 것은 아니므로 `AT SELECTION-SCREEN`에서 검증해야 한다.

## 22. 실습 과제

### 22.1 기본 과제

다음 요구사항을 만족하는 Report를 작성한다.

```text
1. Radio Button으로 “항공사 기준”, “날짜 기준” 모드를 선택한다.
2. 항공사 기준이면 CARRID 필드만 입력 가능하게 한다.
3. 날짜 기준이면 날짜 필드만 입력 가능하게 한다.
4. 선택되지 않은 그룹은 입력 불가능하게 한다.
5. 실행 시 현재 선택 모드와 입력값을 WRITE로 출력한다.
```

### 22.2 확장 과제

다음 기능을 추가한다.

```text
1. “상세 옵션 사용” 체크박스를 추가한다.
2. 체크박스가 선택된 경우에만 최대 조회 건수 필드를 입력 가능하게 한다.
3. 최대 조회 건수가 Initial이면 다음 모듈에서 배울 AT SELECTION-SCREEN 검증 대상으로 남겨둔다.
4. 필드를 숨기는 방식과 입력만 막는 방식을 각각 테스트해본다.
```

### 22.3 오류 기록 과제

실습 중 일부러 다음 오류를 만들어보고 결과를 기록한다.

| 오류 상황 | 관찰할 결과 |
|---|---|
| `USER-COMMAND` 제거 | Radio Button 변경 시 화면 반영 시점 확인 |
| `MODIFY SCREEN` 제거 | 화면 속성 변경 미반영 확인 |
| `MODIF ID` 오타 | 그룹 제어 실패 확인 |
| `screen-input = 0` 대신 `screen-active = 0` 사용 | 필드 표시 방식 차이 확인 |

## 23. 후속 모듈 연결

이번 모듈에서는 Selection Screen의 화면 속성을 동적으로 제어했다.  
다음 모듈 `THEORY-13-M04 — AT SELECTION-SCREEN 입력 검증`에서는 사용자가 입력한 값이 업무적으로 올바른지 검증하는 방법을 다룬다.

연결 관계는 다음과 같다.

```text
THEORY-13-M02 INITIALIZATION 기본값 설정
  → 기본값을 제공한다.

THEORY-13-M03 AT SELECTION-SCREEN OUTPUT 동적 화면 제어
  → 화면 요소를 동적으로 제어한다.

THEORY-13-M04 AT SELECTION-SCREEN 입력 검증
  → 입력값을 검증하고 오류를 차단한다.

THEORY-13-M05 START-OF-SELECTION 조회 실행
  → 검증이 끝난 입력값으로 실제 조회를 수행한다.
```

## 24. 핵심 요약

```text
AT SELECTION-SCREEN OUTPUT은 Selection Screen 출력 직전에 실행되는 화면 제어 이벤트이다.
LOOP AT SCREEN을 사용하면 현재 화면 요소를 순회하며 속성을 바꿀 수 있다.
MODIF ID는 Selection Screen 필드를 그룹 단위로 제어하는 데 유용하다.
SCREEN-INPUT은 입력 가능 여부, SCREEN-ACTIVE/INVISIBLE은 표시 여부 제어에 사용된다.
화면 속성을 변경한 뒤에는 MODIFY SCREEN이 필요하다.
Checkbox나 Radio Button 변경에 따른 즉시 반영에는 USER-COMMAND가 필요할 수 있다.
화면 제어와 입력 검증은 분리해야 한다.
```
