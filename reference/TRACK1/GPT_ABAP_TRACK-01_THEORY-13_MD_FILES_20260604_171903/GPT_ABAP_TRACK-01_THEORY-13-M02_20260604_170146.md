## 1. 이 문서의 목적

이 문서는 ABAP Report의 Selection Screen 처리 흐름 중 **`INITIALIZATION` 이벤트에서 기본값을 설정하는 방법**을 초급자가 정확히 이해하도록 돕기 위한 학습 자료이다.

`INITIALIZATION`은 단순히 값을 한 번 넣는 문법이 아니다.  
Report 프로그램이 실행되어 Selection Screen이 사용자에게 표시되기 전에, 입력 필드에 **초기 제안값**을 구성하는 이벤트이다.

초급자가 이 주제를 정확히 배워야 하는 이유는 다음과 같다.

```text
사용자 입력 화면을 보여주기 전에 기본값을 준비할 수 있다.
오늘 날짜, 로그인 사용자, 기본 회사코드, 기본 상태값 등을 제안할 수 있다.
PARAMETERS와 SELECT-OPTIONS의 기본값 설정 위치를 구분할 수 있다.
DEFAULT 옵션과 INITIALIZATION 이벤트의 차이를 이해할 수 있다.
후속 이벤트인 AT SELECTION-SCREEN OUTPUT, AT SELECTION-SCREEN, START-OF-SELECTION과 역할을 분리할 수 있다.
```

이번 모듈에서는 기본값 설정에 집중한다.  
동적 화면 제어는 다음 모듈인 `THEORY-13-M03 AT SELECTION-SCREEN OUTPUT 동적 화면 제어`에서 다루고, 입력 검증은 `THEORY-13-M04 AT SELECTION-SCREEN 입력 검증`에서 다룬다.

## 4. INITIALIZATION 이벤트의 위치

ABAP Report의 기본 흐름을 간단히 정리하면 다음과 같다.

```text
프로그램 로드
  ↓
LOAD-OF-PROGRAM
  ↓
INITIALIZATION
  ↓
Selection Screen 표시 전 처리
  ↓
Selection Screen 표시
  ↓
사용자 입력
  ↓
AT SELECTION-SCREEN 계열 이벤트
  ↓
START-OF-SELECTION
  ↓
조회/처리 로직 실행
```

`INITIALIZATION`은 Selection Screen이 사용자에게 표시되기 전에 실행된다.  
따라서 이 이벤트의 대표 목적은 다음과 같다.

```text
사용자에게 보여줄 입력 필드의 초기값을 준비한다.
```

### 4.1 이벤트 선언 위치

문법적으로는 다음처럼 작성한다.

```abap
INITIALIZATION.
  p_bukrs = '1000'.
```

Report 프로그램 안에서 이벤트 블록은 일반적으로 선언부 뒤에 배치한다.

```abap
REPORT zedu_initialization_01.

PARAMETERS p_bukrs TYPE bukrs.

INITIALIZATION.
  p_bukrs = '1000'.

START-OF-SELECTION.
  WRITE: / 'Company Code:', p_bukrs.
```

## 5. DEFAULT 옵션과 INITIALIZATION의 차이

초급자가 가장 먼저 구분해야 하는 것은 `DEFAULT`와 `INITIALIZATION`이다.

### 5.1 PARAMETERS DEFAULT

`PARAMETERS` 선언문에서 바로 기본값을 줄 수 있다.

```abap
PARAMETERS p_bukrs TYPE bukrs DEFAULT '1000'.
```

이 방식은 가장 단순하다.  
항상 같은 고정값을 기본값으로 제안할 때 적합하다.

### 5.2 INITIALIZATION

`INITIALIZATION` 이벤트에서는 ABAP 로직을 사용해 기본값을 설정할 수 있다.

```abap
PARAMETERS p_date TYPE sy-datum.

INITIALIZATION.
  p_date = sy-datum.
```

이 방식은 동적인 기본값을 구성할 때 적합하다.

### 5.3 비교표

| 구분 | DEFAULT 옵션 | INITIALIZATION 이벤트 |
|---|---|---|
| 설정 위치 | `PARAMETERS` 선언문 안 | 별도 이벤트 블록 |
| 적합한 값 | 고정 기본값 | 동적 기본값 |
| 로직 사용 | 거의 불가 | 가능 |
| 예시 | 회사코드 `1000` | 오늘 날짜 `sy-datum` |
| 가독성 | 단순 | 로직이 늘면 관리 필요 |
| 초급자 권장 | 고정값이면 우선 고려 | 계산/조건이 필요하면 사용 |

### 5.4 판단 기준

```text
항상 같은 값이면 DEFAULT를 먼저 고려한다.
시스템 날짜, 로그인 사용자, 조건 계산이 필요하면 INITIALIZATION을 사용한다.
사용자 입력을 검사하는 목적이면 INITIALIZATION이 아니라 AT SELECTION-SCREEN 계열 이벤트를 사용한다.
화면 필드를 보이거나 숨기는 목적이면 INITIALIZATION이 아니라 AT SELECTION-SCREEN OUTPUT을 사용한다.
```

## 6. PARAMETERS 기본값 설정

### 6.1 가장 단순한 예제

```abap
REPORT zedu_init_param_01.

PARAMETERS p_stat TYPE c LENGTH 1.

INITIALIZATION.
  p_stat = 'A'.

START-OF-SELECTION.
  WRITE: / 'Status:', p_stat.
```

이 프로그램을 실행하면 Selection Screen의 `P_STAT` 필드에 `A`가 기본값으로 표시된다.

### 6.2 시스템 날짜를 기본값으로 설정

```abap
REPORT zedu_init_param_02.

PARAMETERS p_date TYPE sy-datum.

INITIALIZATION.
  p_date = sy-datum.

START-OF-SELECTION.
  WRITE: / 'Input Date:', p_date.
```

`sy-datum`은 현재 SAP 시스템 날짜이다.  
따라서 프로그램 실행일에 따라 기본값이 달라진다.

### 6.3 로그인 사용자를 기본값으로 설정

```abap
REPORT zedu_init_param_03.

PARAMETERS p_user TYPE sy-uname.

INITIALIZATION.
  p_user = sy-uname.

START-OF-SELECTION.
  WRITE: / 'User:', p_user.
```

이 예제는 현재 로그인 사용자를 입력 필드에 기본값으로 제안한다.  
실무에서는 “내가 생성한 데이터만 기본 조회” 같은 화면에서 유용하다.

## 7. SELECT-OPTIONS 기본값 설정

`SELECT-OPTIONS`는 단일 값이 아니라 범위 조건을 담는 내부 테이블 형태의 입력 조건이다.  
따라서 `PARAMETERS`처럼 단순 대입만으로 모든 조건을 표현하지 않는다.

### 7.1 SELECT-OPTIONS 구조 감각

다음 선언을 보자.

```abap
SELECT-OPTIONS s_date FOR sy-datum.
```

`S_DATE`는 내부적으로 다음과 유사한 구조를 가진다.

| 필드 | 의미 |
|---|---|
| SIGN | 포함/제외 |
| OPTION | 조건 연산자 |
| LOW | 하한값 또는 단일값 |
| HIGH | 상한값 |

예를 들어 오늘 날짜 하나만 기본 조건으로 넣으려면 다음처럼 작성할 수 있다.

```abap
INITIALIZATION.
  s_date-sign   = 'I'.
  s_date-option = 'EQ'.
  s_date-low    = sy-datum.
  APPEND s_date.
```

### 7.2 오늘부터 7일 범위 설정

```abap
REPORT zedu_init_seltab_01.

TABLES sflight.

SELECT-OPTIONS s_date FOR sflight-fldate.

INITIALIZATION.
  s_date-sign   = 'I'.
  s_date-option = 'BT'.
  s_date-low    = sy-datum.
  s_date-high   = sy-datum + 7.
  APPEND s_date.

START-OF-SELECTION.
  WRITE: / 'Date Low :', s_date-low,
         / 'Date High:', s_date-high.
```

여기서 `BT`는 Between 조건이다.  
즉, `LOW`와 `HIGH` 사이의 범위를 의미한다.

### 7.3 여러 조건 추가

```abap
REPORT zedu_init_seltab_02.

TABLES scarr.

SELECT-OPTIONS s_carrid FOR scarr-carrid.

INITIALIZATION.
  CLEAR s_carrid.
  s_carrid-sign   = 'I'.
  s_carrid-option = 'EQ'.
  s_carrid-low    = 'AA'.
  APPEND s_carrid.

  CLEAR s_carrid.
  s_carrid-sign   = 'I'.
  s_carrid-option = 'EQ'.
  s_carrid-low    = 'LH'.
  APPEND s_carrid.

START-OF-SELECTION.
  LOOP AT s_carrid.
    WRITE: / s_carrid-sign, s_carrid-option, s_carrid-low.
  ENDLOOP.
```

이 예제는 항공사 코드 `AA`, `LH`를 기본 조건으로 제안한다.

### 7.4 실무적 주의

`SELECT-OPTIONS` 기본값을 여러 개 넣을 때는 `CLEAR` 후 `APPEND`하는 습관이 중요하다.

나쁜 예:

```abap
s_carrid-sign = 'I'.
s_carrid-option = 'EQ'.
s_carrid-low = 'AA'.
APPEND s_carrid.

s_carrid-low = 'LH'.
APPEND s_carrid.
```

이 코드도 단순 예제에서는 동작할 수 있지만, `HIGH` 같은 이전 값이 남아 있으면 예상치 못한 조건이 만들어질 수 있다.

좋은 예:

```abap
CLEAR s_carrid.
s_carrid-sign = 'I'.
s_carrid-option = 'EQ'.
s_carrid-low = 'AA'.
APPEND s_carrid.

CLEAR s_carrid.
s_carrid-sign = 'I'.
s_carrid-option = 'EQ'.
s_carrid-low = 'LH'.
APPEND s_carrid.
```

## 8. INITIALIZATION에서 하지 말아야 할 일

`INITIALIZATION`은 기본값 설정 이벤트이다.  
다음 작업을 이 이벤트에 넣는 것은 권장하지 않는다.

| 작업 | 왜 부적절한가 |
|---|---|
| 대량 DB 조회 | 화면 표시 전부터 불필요하게 느려질 수 있다. |
| 사용자 입력 검증 | 아직 사용자가 입력하기 전이다. |
| MESSAGE 오류 처리 | 화면 진입 자체를 방해할 수 있다. |
| 권한 검증 전체 수행 | 사용자가 조건을 바꾸기 전이라 시점이 부적절할 수 있다. |
| 동적 화면 숨김/비활성화 | `AT SELECTION-SCREEN OUTPUT`의 역할이다. |
| 실제 비즈니스 처리 | `START-OF-SELECTION` 이후 처리하는 것이 일반적이다. |

### 8.1 기본값 제안과 강제값 설정의 차이

`INITIALIZATION`은 보통 기본값을 **제안**하는 용도로 사용한다.  
사용자가 화면에서 값을 바꿀 수 있다면, INITIALIZATION 값은 강제값이 아니다.

예를 들어 다음은 기본값 제안이다.

```abap
INITIALIZATION.
  p_stat = 'A'.
```

사용자는 Selection Screen에서 `A`를 다른 값으로 바꿀 수 있다.  
만약 특정 값을 반드시 강제해야 한다면 단순 기본값 설정이 아니라 권한, 입력 검증, 화면 제어 등 별도 설계를 검토해야 한다.

## 9. INITIALIZATION과 Variant

Report 프로그램에서는 Selection Variant를 사용하여 입력 조건을 저장하고 재사용할 수 있다.  
따라서 기본값 로직을 설계할 때 Variant와의 관계를 고려해야 한다.

초급자는 다음 정도를 기억하면 충분하다.

```text
INITIALIZATION은 프로그램이 제안하는 기본값이다.
Variant는 사용자가 저장하거나 운영에서 지정한 실행 조건이다.
운영 프로그램에서는 Variant 값을 무시하도록 INITIALIZATION 로직을 과도하게 강제하면 안 된다.
```

실무적으로는 다음 원칙이 안전하다.

| 원칙 | 설명 |
|---|---|
| 고정 기본값은 DEFAULT 사용 | 단순한 경우 불필요한 로직을 줄인다. |
| 동적 제안값은 INITIALIZATION 사용 | 오늘 날짜, 현재 사용자 등 |
| 운영 Variant를 존중 | 배치 잡이나 정기 실행 조건을 방해하지 않는다. |
| 강제 검증은 별도 이벤트에서 처리 | 입력 검증은 `AT SELECTION-SCREEN` 계열 이벤트에서 수행한다. |
| 화면 동적 제어는 다음 이벤트에서 처리 | 필드 숨김/비활성화는 `AT SELECTION-SCREEN OUTPUT`에서 다룬다. |

> [추정] 시스템 릴리스, 실행 방식, Variant 적용 방식에 따라 화면에 표시되는 최종 기본값 체감이 다를 수 있으므로, 운영 프로그램에서는 반드시 실제 실행 방식과 Variant 적용 결과를 테스트해야 한다.

## 10. 실습 1: 오늘 날짜 기본값 설정

### 10.1 요구사항

사용자가 프로그램을 실행하면 `P_DATE`에 오늘 날짜가 기본값으로 표시되어야 한다.  
사용자는 필요하면 날짜를 변경할 수 있다.

### 10.2 예제 코드

```abap
REPORT zedu_t13_m02_01.

PARAMETERS p_date TYPE sy-datum.

INITIALIZATION.
  p_date = sy-datum.

START-OF-SELECTION.
  WRITE: / 'Selected Date:', p_date.
```

### 10.3 확인 포인트

| 확인 항목 | 설명 |
|---|---|
| Selection Screen 표시 전 기본값 | `P_DATE`에 오늘 날짜가 보이는가 |
| 사용자 변경 가능 여부 | 화면에서 다른 날짜로 변경 가능한가 |
| 출력 결과 | 변경한 값이 WRITE로 출력되는가 |
| 이벤트 역할 | INITIALIZATION은 실행 로직이 아니라 기본값 설정임을 이해했는가 |

## 11. 실습 2: 날짜 범위 기본값 설정

### 11.1 요구사항

항공편 일자 조건 `S_FLDATE`에 오늘부터 7일 뒤까지의 범위를 기본값으로 넣는다.

### 11.2 예제 코드

```abap
REPORT zedu_t13_m02_02.

TABLES sflight.

SELECT-OPTIONS s_fldate FOR sflight-fldate.

INITIALIZATION.
  CLEAR s_fldate.
  s_fldate-sign   = 'I'.
  s_fldate-option = 'BT'.
  s_fldate-low    = sy-datum.
  s_fldate-high   = sy-datum + 7.
  APPEND s_fldate.

START-OF-SELECTION.
  WRITE: / 'From:', s_fldate-low,
         / 'To  :', s_fldate-high.
```

### 11.3 확인 포인트

| 확인 항목 | 설명 |
|---|---|
| LOW | 오늘 날짜가 들어갔는가 |
| HIGH | 오늘 + 7일이 들어갔는가 |
| OPTION | `BT` 조건이 설정되었는가 |
| SIGN | `I` 포함 조건이 설정되었는가 |
| 사용자 변경 | 화면에서 범위를 수정할 수 있는가 |

## 12. 실습 3: 기본 사용자와 상태값 설정

### 12.1 요구사항

현재 로그인 사용자와 기본 상태값을 Selection Screen에 표시한다.

### 12.2 예제 코드

```abap
REPORT zedu_t13_m02_03.

PARAMETERS: p_user TYPE sy-uname,
            p_stat TYPE c LENGTH 1.

INITIALIZATION.
  p_user = sy-uname.
  p_stat = 'A'.

START-OF-SELECTION.
  WRITE: / 'User  :', p_user,
         / 'Status:', p_stat.
```

### 12.3 교육 포인트

이 예제는 실제 프로그램에서 자주 등장하는 기본값 패턴이다.

```text
현재 사용자
현재 날짜
기본 상태
기본 회사코드
기본 플랜트
기본 언어
```

다만 회사코드, 플랜트, 영업조직처럼 조직 구조와 연결된 값은 사용자 권한이나 사용자 파라미터, 테이블 설정과 연결될 수 있으므로 단순 하드코딩을 피해야 한다.

## 13. 오류 상황과 해결

### 13.1 이벤트 위치 오류

#### 잘못된 예

```abap
START-OF-SELECTION.
  INITIALIZATION.
    p_date = sy-datum.
```

`INITIALIZATION`은 다른 이벤트 블록 안에 중첩해서 쓰는 구조가 아니다.

#### 해결

이벤트 블록을 독립적으로 작성한다.

```abap
INITIALIZATION.
  p_date = sy-datum.

START-OF-SELECTION.
  WRITE p_date.
```

### 13.2 선언되지 않은 필드에 값 대입

#### 잘못된 예

```abap
INITIALIZATION.
  p_date = sy-datum.
```

그런데 `PARAMETERS p_date`가 선언되어 있지 않다면 문법 오류가 발생한다.

#### 해결

선언부에서 입력 필드를 먼저 정의한다.

```abap
PARAMETERS p_date TYPE sy-datum.

INITIALIZATION.
  p_date = sy-datum.
```

### 13.3 SELECT-OPTIONS에 APPEND 누락

#### 잘못된 예

```abap
s_date-sign   = 'I'.
s_date-option = 'EQ'.
s_date-low    = sy-datum.
```

이렇게 하면 Header Line처럼 보이는 작업 영역에만 값이 들어가고, 실제 선택 조건 라인으로 추가되지 않을 수 있다.

#### 해결

조건 라인을 구성한 뒤 `APPEND`한다.

```abap
CLEAR s_date.
s_date-sign   = 'I'.
s_date-option = 'EQ'.
s_date-low    = sy-datum.
APPEND s_date.
```

### 13.4 기본값과 입력 검증 혼동

#### 잘못된 방향

```abap
INITIALIZATION.
  IF p_date IS INITIAL.
    MESSAGE e001(zmsg).
  ENDIF.
```

아직 사용자가 입력하기 전이므로, 입력값 검증 시점으로 적절하지 않다.

#### 해결

입력 검증은 `AT SELECTION-SCREEN`에서 다룬다.  
이 내용은 `THEORY-13-M04`에서 학습한다.

## 14. 실무 적용 기준

### 14.1 기본값은 사용자를 돕기 위한 장치이다

기본값은 사용자의 입력 부담을 줄이는 데 도움을 준다.  
그러나 잘못 설정하면 오히려 사고를 유발할 수 있다.

예를 들어 조회 조건에 오늘 날짜를 넣는 것은 편리하지만, 사용자가 과거 데이터까지 조회해야 하는데 기본값을 못 보고 실행하면 결과가 누락될 수 있다.

따라서 기본값은 다음 기준으로 설계한다.

| 기준 | 설명 |
|---|---|
| 예측 가능성 | 사용자가 왜 이 값이 들어왔는지 이해할 수 있어야 한다. |
| 변경 가능성 | 사용자가 필요하면 바꿀 수 있어야 한다. |
| 업무 안전성 | 기본값 때문에 데이터 누락이나 오처리가 발생하지 않아야 한다. |
| 성능 | 지나치게 넓은 기본 조회 조건을 넣지 않는다. |
| 운영 Variant | 배치나 정기 실행 Variant를 방해하지 않는다. |

### 14.2 하드코딩 기본값 주의

다음 코드는 교육용으로는 단순하지만, 실무에서는 주의가 필요하다.

```abap
INITIALIZATION.
  p_bukrs = '1000'.
```

회사코드 `1000`은 특정 고객사에서는 맞을 수 있지만, 다른 고객사나 다른 Client에서는 맞지 않을 수 있다.

실무에서는 다음 대안을 검토한다.

```text
사용자 파라미터 ID
사용자별 설정 테이블
권한 기반 기본 조직
커스터마이징 테이블
Variant
```

이 주제는 운영 프로그램 설계와 권한 검증 단계에서 더 깊게 다룬다.

### 14.3 무거운 로직 금지

`INITIALIZATION`에서 대량 DB 조회나 복잡한 계산을 수행하면 Selection Screen이 뜨기 전부터 프로그램이 느려진다.

나쁜 예:

```abap
INITIALIZATION.
  SELECT * FROM zt_large_log INTO TABLE @DATA(lt_log).
```

좋은 방향:

```text
초기값 계산에 필요한 최소 로직만 수행한다.
실제 조회는 START-OF-SELECTION에서 수행한다.
화면 표시 제어는 AT SELECTION-SCREEN OUTPUT에서 수행한다.
```

## 16. 후속 모듈과의 연결

이번 모듈은 Selection Screen이 표시되기 전에 값을 준비하는 단계이다.  
후속 모듈과의 역할 분리를 반드시 기억해야 한다.

| 모듈 | 이벤트/주제 | 역할 |
|---|---|---|
| THEORY-13-M02 | INITIALIZATION | 기본값 제안 |
| THEORY-13-M03 | AT SELECTION-SCREEN OUTPUT | 화면 필드 동적 제어 |
| THEORY-13-M04 | AT SELECTION-SCREEN | 사용자 입력 검증 |
| THEORY-13-M05 | START-OF-SELECTION | 실제 조회/처리 실행 |
| THEORY-13-M06 | END-OF-SELECTION | 출력 마무리 |
| THEORY-13-M07 | 권한/존재 여부 검증 | 실행 전 안전성 확보 |

이 역할을 분리하지 못하면 Selection Screen 프로그램이 복잡해지고, 유지보수가 어려워진다.

## 17. 자가 평가 문제

### Q1. INITIALIZATION 이벤트의 주요 목적은 무엇인가?

A. 사용자가 입력한 값을 검증한다.  
B. Selection Screen이 표시되기 전에 기본값을 설정한다.  
C. 실제 데이터 조회를 수행한다.  
D. ALV를 출력한다.

**정답:** B

### Q2. 오늘 날짜를 기본값으로 설정할 때 가장 적절한 코드는?

```abap
PARAMETERS p_date TYPE sy-datum.

INITIALIZATION.
  p_date = sy-datum.
```

**해설:** `sy-datum`은 실행 시점의 시스템 날짜이므로 동적 기본값에 적합하다.

### Q3. `SELECT-OPTIONS`에 기본 조건을 넣을 때 필요한 작업은?

**모범 답안:**  
`SIGN`, `OPTION`, `LOW`, 필요 시 `HIGH` 값을 설정하고, 조건 라인을 `APPEND`해야 한다.

### Q4. INITIALIZATION에서 입력 검증을 하면 안 되는 이유는?

**모범 답안:**  
`INITIALIZATION`은 사용자가 Selection Screen에 값을 입력하기 전에 실행되는 이벤트이므로 입력 검증 시점으로 적절하지 않다. 입력 검증은 `AT SELECTION-SCREEN` 계열 이벤트에서 수행하는 것이 적절하다.

### Q5. DEFAULT 옵션과 INITIALIZATION의 차이를 설명하시오.

**모범 답안:**  
`DEFAULT`는 선언 시 고정 기본값을 간단히 지정하는 방식이고, `INITIALIZATION`은 이벤트 블록 안에서 시스템 필드나 조건 로직을 사용해 동적인 기본값을 설정할 수 있는 방식이다.

## 19. 핵심 요약

```text
INITIALIZATION은 Selection Screen 표시 전에 기본값을 설정하는 이벤트이다.
고정 기본값은 DEFAULT로도 충분할 수 있다.
동적 기본값은 INITIALIZATION에서 설정한다.
PARAMETERS는 단순 대입으로 기본값을 설정할 수 있다.
SELECT-OPTIONS는 SIGN, OPTION, LOW, HIGH를 구성한 뒤 APPEND해야 한다.
입력 검증은 INITIALIZATION이 아니라 AT SELECTION-SCREEN에서 처리한다.
화면 제어는 INITIALIZATION이 아니라 AT SELECTION-SCREEN OUTPUT에서 처리한다.
실무에서는 Variant, 권한, 조직값, 성능을 고려해 기본값을 설계해야 한다.
```
