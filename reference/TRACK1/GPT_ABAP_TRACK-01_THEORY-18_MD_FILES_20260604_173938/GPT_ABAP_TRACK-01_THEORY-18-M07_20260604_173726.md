## 3. 상속이란 무엇인가?

상속은 한 클래스가 다른 클래스의 속성과 동작을 이어받는 OO 개념이다.

ABAP Objects에서는 상속받는 클래스를 **Subclass**, 상속을 제공하는 클래스를 **Superclass**라고 이해하면 된다.

```text
Superclass
  ↓
Subclass
```

예를 들어 “일반 문서”와 “판매 문서”를 생각해보자.

```text
일반 문서
  - 문서번호
  - 생성자
  - 생성일
  - 문서 설명 반환

판매 문서
  - 일반 문서의 공통 속성을 사용
  - 판매조직
  - 고객
  - 판매 문서 설명 반환
```

이때 판매 문서는 일반 문서의 특수한 형태로 볼 수 있다.  
이런 관계가 자연스럽다면 상속을 고려할 수 있다.

초급자 관점에서 상속은 다음 문장으로 이해하면 된다.

```text
Subclass는 Superclass의 일반적인 성격을 이어받고, 필요한 부분을 추가하거나 바꾼다.
```

## 4. ABAP에서 상속을 선언하는 기본 문법

ABAP Objects에서 Subclass는 다음 문법으로 Superclass를 상속한다.

```abap
CLASS lcl_subclass DEFINITION INHERITING FROM lcl_superclass.
  PUBLIC SECTION.
    " 추가 또는 재정의할 구성요소 선언
ENDCLASS.
```

예를 들어 다음과 같이 선언할 수 있다.

```abap
CLASS lcl_document DEFINITION.
  PUBLIC SECTION.
    METHODS get_text
      RETURNING VALUE(rv_text) TYPE string.
ENDCLASS.

CLASS lcl_sales_document DEFINITION INHERITING FROM lcl_document.
  PUBLIC SECTION.
    METHODS get_text REDEFINITION.
ENDCLASS.
```

여기서 중요한 부분은 다음이다.

| 구문 | 의미 |
|---|---|
| `INHERITING FROM lcl_document` | `lcl_sales_document`가 `lcl_document`를 상속한다. |
| `METHODS get_text REDEFINITION` | 상속받은 `get_text` 메서드의 구현을 Subclass에서 다시 정의한다. |

## 5. Superclass와 Subclass

### 5.1 Superclass

Superclass는 더 일반적인 개념을 표현하는 클래스이다.

예시:

```text
LCL_DOCUMENT
LCL_VEHICLE
LCL_EMPLOYEE
LCL_PAYMENT
```

Superclass에는 여러 Subclass가 공통으로 가져야 하는 속성과 메서드를 둔다.

예를 들어 `LCL_DOCUMENT`에는 모든 문서가 공통으로 가지는 속성을 둘 수 있다.

```text
문서번호
생성자
생성일
공통 설명 반환 메서드
```

### 5.2 Subclass

Subclass는 Superclass의 특수한 형태이다.

예시:

```text
LCL_SALES_DOCUMENT
LCL_PURCHASE_DOCUMENT
LCL_CAR
LCL_MANAGER
LCL_CREDIT_CARD_PAYMENT
```

Subclass는 Superclass의 속성과 메서드를 이어받고, 필요하면 다음 작업을 수행한다.

| 작업 | 설명 |
|---|---|
| 속성 추가 | Subclass에만 필요한 Attribute 추가 |
| 메서드 추가 | Subclass에만 필요한 Method 추가 |
| 메서드 재정의 | Superclass 메서드의 동작을 Subclass에 맞게 변경 |

## 6. Redefinition이란 무엇인가?

Redefinition은 Superclass에서 정의된 메서드를 Subclass에서 다시 구현하는 것이다.

예를 들어 Superclass의 `get_text`가 다음처럼 일반 설명을 반환한다고 하자.

```abap
METHOD get_text.
  rv_text = 'Generic document'.
ENDMETHOD.
```

Subclass인 `lcl_sales_document`에서는 같은 메서드 이름을 사용하되, 판매 문서에 맞게 동작을 바꿀 수 있다.

```abap
METHOD get_text.
  rv_text = 'Sales document'.
ENDMETHOD.
```

이것이 Method Redefinition이다.

### 6.1 Redefinition의 핵심

Redefinition은 다음 조건을 전제로 한다.

1. Superclass에 이미 메서드가 존재해야 한다.
2. Subclass에서 같은 메서드를 `REDEFINITION`으로 선언한다.
3. 구현부에서 Subclass에 맞는 로직을 작성한다.
4. 외부 호출자는 같은 메서드 이름을 호출하지만, 실제 객체 타입에 따라 다른 결과를 얻을 수 있다.

## 7. 전체 예제: 문서 클래스와 판매 문서 클래스

다음 예제는 Local Class를 사용한다.  
Global Class를 만들기 전에도 ABAP Editor 또는 ADT에서 상속 개념을 빠르게 확인할 수 있기 때문이다.

> [추정] 교육 시스템의 ABAP 릴리스에 따라 `NEW`, 인라인 선언, 문자열 템플릿 사용 가능 여부가 다를 수 있다. S/4HANA 기준에서는 일반적으로 사용 가능하지만, 구형 시스템에서는 `CREATE OBJECT`와 명시적 DATA 선언으로 바꿔 실습한다.

```abap
REPORT zedu_inheritance_demo.

CLASS lcl_document DEFINITION.
  PUBLIC SECTION.
    METHODS get_text
      RETURNING VALUE(rv_text) TYPE string.
ENDCLASS.

CLASS lcl_document IMPLEMENTATION.
  METHOD get_text.
    rv_text = 'Generic document'.
  ENDMETHOD.
ENDCLASS.

CLASS lcl_sales_document DEFINITION INHERITING FROM lcl_document.
  PUBLIC SECTION.
    METHODS get_text REDEFINITION.
ENDCLASS.

CLASS lcl_sales_document IMPLEMENTATION.
  METHOD get_text.
    rv_text = 'Sales document'.
  ENDMETHOD.
ENDCLASS.

START-OF-SELECTION.

  DATA(lo_document) = NEW lcl_document( ).
  DATA(lo_sales)    = NEW lcl_sales_document( ).

  WRITE: / lo_document->get_text( ).
  WRITE: / lo_sales->get_text( ).
```

### 7.1 실행 결과

예상 출력은 다음과 같다.

```text
Generic document
Sales document
```

이 결과는 `lcl_sales_document`가 `lcl_document`를 상속했지만, `get_text` 메서드를 자기 방식으로 다시 구현했기 때문에 발생한다.

## 8. `super->method( )`의 의미

Subclass에서 Redefinition을 할 때, Superclass의 기존 로직을 완전히 버리는 대신 일부 재사용하고 싶을 수 있다.  
이때 `super->method( )`를 사용할 수 있다.

다음 예제를 보자.

```abap
REPORT zedu_super_call_demo.

CLASS lcl_document DEFINITION.
  PUBLIC SECTION.
    METHODS get_text
      RETURNING VALUE(rv_text) TYPE string.
ENDCLASS.

CLASS lcl_document IMPLEMENTATION.
  METHOD get_text.
    rv_text = 'Generic document'.
  ENDMETHOD.
ENDCLASS.

CLASS lcl_sales_document DEFINITION INHERITING FROM lcl_document.
  PUBLIC SECTION.
    METHODS get_text REDEFINITION.
ENDCLASS.

CLASS lcl_sales_document IMPLEMENTATION.
  METHOD get_text.
    DATA(lv_parent_text) = super->get_text( ).
    rv_text = |Sales document based on: { lv_parent_text }|.
  ENDMETHOD.
ENDCLASS.

START-OF-SELECTION.

  DATA(lo_sales) = NEW lcl_sales_document( ).

  WRITE: / lo_sales->get_text( ).
```

### 8.1 실행 결과

```text
Sales document based on: Generic document
```

### 8.2 해석

`super->get_text( )`는 Subclass 안에서 Superclass의 `get_text` 구현을 호출한다.  
즉, 부모 클래스의 기본 처리 결과를 가져와서 Subclass 로직에 덧붙일 수 있다.

실무적으로 이 방식은 다음 상황에 유용하다.

| 상황 | 설명 |
|---|---|
| 공통 검증 로직 유지 | Superclass의 기본 검증을 먼저 수행 |
| 공통 로그 처리 유지 | 공통 로그 생성 후 Subclass별 추가 처리 |
| 기본 반환값 확장 | 기본 텍스트 또는 기본 계산값에 추가 정보 부여 |
| 표준 흐름 보존 | 공통 처리 순서를 깨지 않고 일부만 확장 |

## 9. Reference Type과 실제 객체 타입

상속에서 중요한 개념은 “참조 변수의 타입”과 “실제 객체의 타입”이 다를 수 있다는 점이다.

다음 코드를 보자.

```abap
REPORT zedu_dynamic_dispatch_demo.

CLASS lcl_document DEFINITION.
  PUBLIC SECTION.
    METHODS get_text
      RETURNING VALUE(rv_text) TYPE string.
ENDCLASS.

CLASS lcl_document IMPLEMENTATION.
  METHOD get_text.
    rv_text = 'Generic document'.
  ENDMETHOD.
ENDCLASS.

CLASS lcl_sales_document DEFINITION INHERITING FROM lcl_document.
  PUBLIC SECTION.
    METHODS get_text REDEFINITION.
ENDCLASS.

CLASS lcl_sales_document IMPLEMENTATION.
  METHOD get_text.
    rv_text = 'Sales document'.
  ENDMETHOD.
ENDCLASS.

START-OF-SELECTION.

  DATA lo_document TYPE REF TO lcl_document.

  lo_document = NEW lcl_sales_document( ).

  WRITE: / lo_document->get_text( ).
```

출력은 다음과 같다.

```text
Sales document
```

참조 변수 `lo_document`의 선언 타입은 `lcl_document`이다.  
하지만 실제 객체는 `lcl_sales_document`이다.  
호출된 `get_text`는 실제 객체 타입인 `lcl_sales_document`의 재정의된 메서드이다.

이 동작을 초급자 관점에서는 다음처럼 이해하면 된다.

```text
참조 변수는 부모 타입으로 선언될 수 있지만,
실제 객체가 자식 클래스라면 재정의된 메서드가 실행될 수 있다.
```

이것이 OO의 다형성(Polymorphism)과 연결된다.  
다만 다형성의 심화 설계는 Interface와 함께 더 깊게 다루는 것이 좋다.

## 10. Visibility와 상속

상속을 이해하려면 Visibility가 중요하다.

| Visibility | Subclass에서 접근 가능 여부 | 설명 |
|---|---:|---|
| PUBLIC | 가능 | 외부와 Subclass 모두 접근 가능 |
| PROTECTED | 가능 | 외부에서는 접근 불가, Subclass에서는 접근 가능 |
| PRIVATE | 불가 | 해당 클래스 내부에서만 접근 가능 |

### 10.1 Protected의 의미

`PROTECTED`는 상속 관계에서 매우 중요하다.  
Superclass의 내부 구현을 외부에는 숨기고 싶지만, Subclass에는 허용하고 싶을 때 사용한다.

```abap
CLASS lcl_document DEFINITION.
  PROTECTED SECTION.
    DATA mv_document_type TYPE string.
ENDCLASS.
```

Subclass는 `mv_document_type`에 접근할 수 있다.  
하지만 클래스 외부의 일반 프로그램에서는 접근할 수 없다.

### 10.2 Private은 상속되지 않는가?

초급자들이 자주 묻는 질문이다.

정확히는 Subclass가 Superclass의 일부로서 객체 구조를 이어받더라도, `PRIVATE` 구성요소는 Subclass 코드에서 직접 접근할 수 없다.  
따라서 Superclass가 Subclass에게 제공할 필요가 있는 내부 정보는 `PROTECTED` 또는 `PUBLIC` 메서드를 통해 노출해야 한다.

## 11. Constructor와 상속

상속 구조에서 Constructor는 초급자에게 다소 복잡할 수 있다.  
이번 모듈에서는 최소 수준만 다룬다.

Subclass 객체를 생성하면 Superclass의 생성 흐름도 고려된다.  
Subclass Constructor를 작성할 때는 Superclass Constructor 호출이 필요한 경우가 있다.

예시:

```abap
CLASS lcl_document DEFINITION.
  PUBLIC SECTION.
    METHODS constructor
      IMPORTING iv_doc_id TYPE string.
  PROTECTED SECTION.
    DATA mv_doc_id TYPE string.
ENDCLASS.

CLASS lcl_document IMPLEMENTATION.
  METHOD constructor.
    mv_doc_id = iv_doc_id.
  ENDMETHOD.
ENDCLASS.

CLASS lcl_sales_document DEFINITION INHERITING FROM lcl_document.
  PUBLIC SECTION.
    METHODS constructor
      IMPORTING
        iv_doc_id TYPE string
        iv_sales_org TYPE string.
  PRIVATE SECTION.
    DATA mv_sales_org TYPE string.
ENDCLASS.

CLASS lcl_sales_document IMPLEMENTATION.
  METHOD constructor.
    super->constructor( iv_doc_id = iv_doc_id ).
    mv_sales_org = iv_sales_org.
  ENDMETHOD.
ENDCLASS.
```

여기서 `super->constructor( )`는 Superclass의 Constructor를 호출한다.

초급자는 다음 원칙만 기억해도 충분하다.

```text
Subclass 생성 시 Superclass 초기화도 중요하다.
Superclass Constructor가 필요한 값을 받는다면 Subclass Constructor에서 super->constructor( ) 호출을 고려해야 한다.
```

## 12. 상속을 사용할 때 적합한 경우

상속은 “A는 B의 한 종류이다”라는 관계가 자연스러울 때 적합하다.

```text
Sales Document is a Document.
Manager is an Employee.
Car is a Vehicle.
Credit Card Payment is a Payment.
```

이런 관계를 흔히 **is-a 관계**라고 설명한다.

### 12.1 적합한 설계 예

| Superclass | Subclass | 관계 |
|---|---|---|
| Document | Sales Document | 판매 문서는 문서의 한 종류 |
| Payment | Card Payment | 카드 결제는 결제의 한 종류 |
| Employee | Manager | 관리자는 직원의 한 종류 |
| Animal | Dog | 개는 동물의 한 종류 |

### 12.2 ABAP 실무 예시 감각

실무 ABAP에서는 다음과 같은 영역에서 상속을 볼 수 있다.

| 영역 | 설명 |
|---|---|
| Exception Class | 공통 Exception 계층을 만들고 세부 예외를 구분 |
| Framework 확장 | 특정 Framework가 상속 기반 Extension Point를 제공하는 경우 |
| 공통 처리 Template | 공통 처리 흐름을 Superclass에 두고 일부 단계만 Subclass가 재정의 |
| 테스트 Double 또는 Mock | 테스트 목적의 대체 구현 구성 |

단, 모든 실무 개발에서 상속이 최우선 선택인 것은 아니다.

## 13. 상속을 피해야 할 수 있는 경우

상속은 강한 결합을 만들 수 있다.  
Superclass가 바뀌면 Subclass에 영향을 줄 수 있고, 계층이 깊어질수록 동작을 추적하기 어려워질 수 있다.

### 13.1 피해야 할 설계 예

| 나쁜 상황 | 문제 |
|---|---|
| 단순 코드 재사용만을 위해 상속 | 의미 없는 is-a 관계가 만들어진다. |
| Superclass가 너무 많은 책임을 가짐 | Subclass가 불필요한 기능까지 떠안는다. |
| 상속 계층이 4~5단계 이상 깊어짐 | 디버깅과 영향 분석이 어려워진다. |
| Private 내부 구현에 우회적으로 의존 | 변경에 취약해진다. |
| Interface로 충분한데 상속 사용 | 구현 결합이 강해진다. |

### 13.2 단순 재사용에는 Composition 검토

단순히 다른 클래스의 기능을 사용하고 싶은 것이라면 상속보다 Composition이 더 적합할 수 있다.

```text
상속: A is a B
Composition: A has a B
```

예를 들어 `Report`가 `Logger` 기능을 쓰고 싶다고 해서 `Report`가 `Logger`를 상속하는 것은 어색하다.

더 자연스러운 설계는 다음과 같다.

```text
Report has a Logger.
```

ABAP 코드 감각으로는 다음과 같다.

```abap
CLASS lcl_report DEFINITION.
  PRIVATE SECTION.
    DATA mo_logger TYPE REF TO lcl_logger.
ENDCLASS.
```

## 14. Interface와 상속의 차이

이전 모듈에서 Interface를 학습했다.  
상속과 Interface는 모두 다형성과 연결되지만 설계 의미가 다르다.

| 구분 | Class Inheritance | Interface |
|---|---|---|
| 의미 | 한 클래스가 다른 클래스의 특수 형태 | 어떤 기능 계약을 구현 |
| 관계 | is-a | can-do 또는 role |
| 구현 재사용 | 가능 | Interface 자체는 구현을 강제하지 않음 |
| 결합도 | 상대적으로 강함 | 상대적으로 약함 |
| 다중 적용 | 클래스 상속은 일반적으로 단일 계층 | 여러 Interface 구현 가능 |
| 사용 예 | 공통 기본 클래스와 특수 클래스 | 저장 가능, 출력 가능, 검증 가능 같은 역할 |

초급자는 다음 기준으로 판단하면 된다.

```text
정말 “A는 B의 한 종류”라면 상속을 검토한다.
“이 기능을 수행할 수 있다”라면 Interface를 먼저 검토한다.
```

예시:

```text
SalesDocument is a Document.        → 상속 가능성 있음
SalesDocument can be printed.       → Interface가 더 자연스러움
SalesDocument can be approved.      → Interface가 더 자연스러움
```

## 15. 실습 1: 기본 상속과 Redefinition 확인

### 15.1 실습 목표

문서 Superclass와 판매 문서 Subclass를 만들고, 같은 메서드 호출이 다른 결과를 반환하는 것을 확인한다.

### 15.2 실습 코드

```abap
REPORT zedu_theory18_m07_01.

CLASS lcl_document DEFINITION.
  PUBLIC SECTION.
    METHODS get_text
      RETURNING VALUE(rv_text) TYPE string.
ENDCLASS.

CLASS lcl_document IMPLEMENTATION.
  METHOD get_text.
    rv_text = 'Generic document'.
  ENDMETHOD.
ENDCLASS.

CLASS lcl_sales_document DEFINITION INHERITING FROM lcl_document.
  PUBLIC SECTION.
    METHODS get_text REDEFINITION.
ENDCLASS.

CLASS lcl_sales_document IMPLEMENTATION.
  METHOD get_text.
    rv_text = 'Sales document'.
  ENDMETHOD.
ENDCLASS.

START-OF-SELECTION.

  DATA(lo_document) = NEW lcl_document( ).
  DATA(lo_sales)    = NEW lcl_sales_document( ).

  WRITE: / lo_document->get_text( ).
  WRITE: / lo_sales->get_text( ).
```

### 15.3 확인 포인트

| 확인 항목 | 기대 결과 |
|---|---|
| Superclass 객체 호출 | `Generic document` 출력 |
| Subclass 객체 호출 | `Sales document` 출력 |
| `REDEFINITION` 제거 후 활성화 | 재정의 구현과 선언 불일치 오류 가능 |
| `INHERITING FROM` 제거 후 활성화 | `REDEFINITION` 대상이 없어 오류 가능 |

## 17. 실습 3: `super->` 호출로 기본 로직 재사용

### 17.1 실습 목표

Subclass가 Superclass의 기본 메서드 로직을 호출한 뒤 자신의 로직을 추가하는 흐름을 확인한다.

### 17.2 실습 코드

```abap
REPORT zedu_theory18_m07_03.

CLASS lcl_document DEFINITION.
  PUBLIC SECTION.
    METHODS get_text
      RETURNING VALUE(rv_text) TYPE string.
ENDCLASS.

CLASS lcl_document IMPLEMENTATION.
  METHOD get_text.
    rv_text = 'Generic document'.
  ENDMETHOD.
ENDCLASS.

CLASS lcl_sales_document DEFINITION INHERITING FROM lcl_document.
  PUBLIC SECTION.
    METHODS get_text REDEFINITION.
ENDCLASS.

CLASS lcl_sales_document IMPLEMENTATION.

ENDCLASS.

  DATA(lo_sales) = NEW lcl_sales_document( ).

  WRITE: / lo_sales->get_text( ).
```

### 17.3 확인 포인트

예상 출력:

```text
Sales document based on: Generic document
```

이 실습을 통해 Subclass가 Superclass의 로직을 완전히 버리지 않고 확장할 수 있음을 확인한다.

## 18. 자주 발생하는 오류와 해결

### 18.1 `REDEFINITION` 대상 메서드가 없음

#### 상황

Subclass에서 다음처럼 선언했다.

```abap
METHODS get_text REDEFINITION.
```

하지만 Superclass에 `get_text` 메서드가 없다.

#### 원인

재정의하려면 Superclass에 같은 메서드가 먼저 있어야 한다.

#### 해결

Superclass에 해당 메서드를 선언하거나, 재정의가 아니라 신규 메서드라면 `REDEFINITION`을 제거한다.

---

### 18.2 Method Signature 불일치

#### 상황

Superclass의 메서드와 Subclass의 재정의 메서드 파라미터가 다르다.

#### 원인

Redefinition은 기존 메서드 계약을 유지해야 한다.  
입출력 파라미터를 임의로 바꾸면 같은 메서드라고 볼 수 없다.

#### 해결

Superclass 메서드의 Signature를 기준으로 동일하게 유지한다.

---

### 18.3 Private Attribute 직접 접근 오류

#### 상황

Subclass에서 Superclass의 Private Attribute에 접근하려고 한다.

```abap
mv_private_value = 'X'.
```

#### 원인

Superclass의 `PRIVATE SECTION` 구성요소는 Subclass에서 직접 접근할 수 없다.

#### 해결

다음 중 하나를 사용한다.

| 해결 방법 | 설명 |
|---|---|
| `PROTECTED SECTION` 사용 | Subclass 접근을 허용해야 하는 내부 상태 |
| Public/Protected Getter Method 제공 | 직접 접근 대신 메서드로 읽기 |
| 설계 재검토 | Subclass가 Superclass 내부 상태에 의존하지 않도록 조정 |

---

### 18.4 상속 계층이 너무 깊어짐

#### 상황

```text
A → B → C → D → E
```

처럼 상속 계층이 깊어졌다.

#### 문제

어떤 메서드가 어디서 정의되고 어디서 재정의되는지 추적하기 어렵다.  
디버깅, 영향 분석, 테스트가 복잡해진다.

#### 해결

상속 계층을 줄이고 Interface 또는 Composition을 검토한다.

---

### 18.5 상속을 코드 재사용 수단으로만 사용

#### 상황

두 클래스가 비슷한 코드를 공유한다는 이유만으로 상속 관계를 만들었다.

#### 문제

업무 의미상 is-a 관계가 아니면 설계가 어색해진다.  
나중에 한쪽 클래스가 변경될 때 다른 클래스까지 불필요하게 영향을 받을 수 있다.

#### 해결

공통 기능을 별도 Helper 또는 Service Class로 분리하고 Composition으로 사용하는 방식을 검토한다.

---

## 19. 실무 설계 기준

상속을 사용할지 판단할 때는 다음 질문을 사용한다.

| 질문 | 상속 검토 가능 여부 |
|---|---|
| Subclass가 Superclass의 한 종류인가? | 예라면 검토 가능 |
| Superclass의 공통 로직이 여러 Subclass에 자연스럽게 적용되는가? | 예라면 검토 가능 |
| Subclass가 Superclass의 일부 동작만 바꾸면 되는가? | 예라면 Redefinition 검토 |
| 단순 기능 재사용이 목적일 뿐인가? | Composition 우선 검토 |
| 여러 역할을 동시에 표현해야 하는가? | Interface 우선 검토 |
| 변경 영향이 넓게 퍼질 가능성이 큰가? | 상속 신중 검토 |

초급자에게 가장 중요한 문장은 다음이다.

```text
상속은 강력하지만 결합도가 높은 도구이다.
```

따라서 문법을 아는 것보다 언제 쓰지 말아야 하는지를 아는 것이 더 중요하다.

## 20. ABAP OO 실무에서의 권장 관점

### 20.1 상속보다 Interface가 적합한 경우

다음처럼 “역할”을 표현하는 경우 Interface가 더 적합하다.

```text
출력 가능하다
검증 가능하다
저장 가능하다
변환 가능하다
로그 기록 가능하다
```

예시 Interface 이름:

```abap
zif_gpt_printable
zif_gpt_validatable
zif_gpt_persistable
zif_gpt_converter
```

### 20.2 상속이 적합한 경우

다음처럼 분명한 계층이 있는 경우 상속을 검토할 수 있다.

```text
공통 Exception Class와 세부 Exception Class
공통 추상 처리 클래스와 구체 처리 클래스
Framework에서 요구하는 Base Class 확장
```

### 20.3 상속 계층은 얕게 유지

일반적인 실무 권장 방향은 다음이다.

```text
깊은 상속 계층보다 얕은 상속 + 명확한 Interface + Composition을 선호한다.
```

다만 프로젝트, 표준 Framework, 기존 고객사 아키텍처에 따라 기준은 달라질 수 있다.

## 21. 강사용 설명 포인트

강의에서는 다음 포인트를 강조한다.

### 21.1 “상속은 재사용이 아니라 분류 모델이다”

초급자는 상속을 코드 재사용 문법으로 이해하기 쉽다.  
하지만 상속의 핵심은 “공통 부모와 특수 자식”이라는 의미 모델이다.

### 21.2 Redefinition은 같은 이름의 다른 동작이다

같은 메서드 이름을 호출하지만 실제 객체 타입에 따라 다른 구현이 실행될 수 있다.  
이것이 다형성으로 이어진다.

### 21.3 `super->`는 부모 로직을 보존하는 도구이다

Subclass에서 부모 로직을 완전히 무시하면 공통 흐름이 깨질 수 있다.  
필요할 때 `super->method( )`로 기본 처리를 재사용한다.

### 21.4 Protected와 Private을 구분한다

Subclass에서 필요한 내부 상태는 `PROTECTED`로 설계할 수 있다.  
하지만 무분별하게 Protected를 늘리면 Superclass 내부 구조에 Subclass가 과도하게 의존하게 된다.

## 22. 자가 점검 문제

### Q1. ABAP에서 Class 상속을 선언할 때 사용하는 핵심 구문은 무엇인가?

정답 예시:

```abap
CLASS lcl_sub DEFINITION INHERITING FROM lcl_super.
```

---

### Q2. Redefinition이란 무엇인가?

정답 예시:

Superclass에 정의된 메서드를 Subclass에서 다시 구현하여 Subclass에 맞는 동작을 제공하는 것이다.

---

### Q3. `super->get_text( )`는 어떤 의미인가?

정답 예시:

Subclass 내부에서 Superclass의 `get_text` 구현을 호출한다는 의미이다.

---

### Q4. `PRIVATE SECTION`의 Attribute를 Subclass에서 직접 접근할 수 있는가?

정답 예시:

직접 접근할 수 없다. Subclass 접근이 필요하면 `PROTECTED SECTION` 또는 적절한 Getter/Setter Method를 검토해야 한다.

---

### Q5. 상속보다 Interface가 더 적합한 경우는 언제인가?

정답 예시:

“한 종류이다” 관계가 아니라 “어떤 기능을 수행할 수 있다”라는 역할을 표현할 때 Interface가 더 적합하다.

## 24. 평가 루브릭

| 평가 항목 | 우수 | 보통 | 보완 필요 |
|---|---|---|---|
| 상속 개념 설명 | Superclass/Subclass/is-a 관계를 명확히 설명 | 기본 정의만 설명 | 단순 코드 재사용으로만 이해 |
| Redefinition 구현 | 선언과 구현을 정확히 작성 | 일부 문법 오류 있으나 개념 이해 | Superclass 메서드 없이 재정의 시도 |
| `super->` 이해 | 부모 로직 재사용 목적을 설명 | 호출 문법만 이해 | `me->`와 혼동 |
| Visibility 이해 | Public/Protected/Private 차이 설명 | Public/Private만 구분 | Subclass에서 Private 접근 가능하다고 오해 |
| 실무 판단 | Interface/Composition과 비교 가능 | 상속 장단점 일부 이해 | 상속을 항상 좋은 설계로 오해 |

## 25. 핵심 요약

```text
Inheritance는 한 클래스가 다른 클래스의 특수한 형태일 때 사용하는 OO 개념이다.
ABAP에서는 INHERITING FROM으로 상속을 선언한다.
Subclass는 Superclass의 메서드를 REDEFINITION으로 다시 구현할 수 있다.
super->method( )는 Subclass에서 Superclass의 기존 구현을 호출할 때 사용한다.
Superclass 타입 참조 변수가 Subclass 객체를 가리키면, 재정의된 Instance Method가 실행될 수 있다.
PRIVATE 구성요소는 Subclass에서 직접 접근할 수 없고, PROTECTED는 접근 가능하다.
상속은 강력하지만 결합도가 높으므로 Interface와 Composition을 함께 비교해야 한다.
```
