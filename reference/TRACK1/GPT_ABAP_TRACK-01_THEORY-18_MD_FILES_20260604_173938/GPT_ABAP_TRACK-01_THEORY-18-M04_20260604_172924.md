## 1. 이 문서의 목적

이 문서는 OO ABAP 기본 설계 과정에서 **Static Method와 Instance Method의 차이**를 명확히 이해하도록 돕기 위한 학습 문서이다.

ABAP에서 클래스는 속성(Attribute)과 메서드(Method)를 가진다.  
하지만 모든 메서드가 같은 방식으로 호출되는 것은 아니다.

메서드는 크게 다음 두 가지로 나눌 수 있다.

```text
Instance Method
Static Method, 즉 Class Method
```

초급자는 처음에 다음과 같은 질문을 자주 한다.

```text
언제 객체를 생성해야 하는가?
언제 클래스 이름으로 바로 호출할 수 있는가?
CLASS-METHODS와 METHODS는 무엇이 다른가?
Static Method만 쓰면 더 편한 것 아닌가?
Instance Method는 왜 필요한가?
```

이 문서는 위 질문에 답하기 위해 작성되었다.

## 2. 선행 지식

이 모듈을 학습하기 전에 다음 내용을 알고 있어야 한다.

| 선행 주제 | 필요한 이유 |
|---|---|
| Global Class 생성 | Static/Instance Method는 Class 내부 구성 요소이기 때문이다. |
| Attribute / Method / Visibility | Method 선언 위치와 접근 범위를 이해해야 한다. |
| Constructor와 객체 초기화 | Instance Method는 객체 생성 이후 호출하는 경우가 많기 때문이다. |
| `CREATE OBJECT` / `NEW` | Instance를 만드는 기본 방법을 알아야 한다. |

이전 모듈인 `THEORY-18-M03`에서는 Constructor와 객체 초기화를 다루었다.  
이번 모듈에서는 객체 생성이 필요한 메서드와 필요하지 않은 메서드를 구분한다.

## 3. 핵심 결론 먼저 보기

초급자는 다음 문장부터 기억하면 된다.

```text
Instance Method는 객체의 상태를 사용하거나 변경할 때 사용한다.
Static Method는 특정 객체 상태와 무관한 공통 기능을 제공할 때 사용한다.
```

조금 더 ABAP 문법적으로 말하면 다음과 같다.

| 구분 | 선언 | 호출 |
|---|---|---|
| Instance Method | `METHODS` | `lo_object->method( )` |
| Static Method | `CLASS-METHODS` | `lcl_class=>method( )` |

호출 연산자가 다르다.

```abap
" Instance Method 호출
lo_calculator->add( ).

" Static Method 호출
lcl_calculator=>add_static( ).
```

`->`는 객체 참조를 통한 Instance 호출이다.  
`=>`는 클래스 자체를 통한 Static 호출이다.

## 4. Instance Method란 무엇인가?

Instance Method는 객체 인스턴스에 속한 메서드이다.

객체를 먼저 생성한 뒤, 그 객체를 통해 호출한다.

```abap
DATA(lo_user) = NEW zcl_gpt_user( ).
lo_user->set_name( 'Kim' ).
lo_user->get_name( ).
```

여기서 `set_name`과 `get_name`이 Instance Method라면, 이 메서드들은 특정 객체 `lo_user`의 상태를 다룬다.

### 4.1 Instance Method의 특징

| 특징 | 설명 |
|---|---|
| 객체 생성 필요 | 호출 전에 `NEW` 또는 `CREATE OBJECT`가 필요하다. |
| 객체 상태 사용 가능 | Instance Attribute를 읽고 변경할 수 있다. |
| 객체마다 값이 다를 수 있음 | 같은 클래스라도 객체별로 다른 상태를 가진다. |
| `->`로 호출 | 참조 변수와 Instance Method 사이에 `->`를 사용한다. |

### 4.2 Instance Method가 적합한 경우

다음 상황에서는 Instance Method가 적합하다.

| 상황 | 예 |
|---|---|
| 객체마다 다른 상태가 필요한 경우 | 고객 객체마다 이름, 등급, 상태가 다름 |
| Constructor로 초기화한 값을 계속 사용할 경우 | 환율 계산 객체가 특정 통화 기준을 가짐 |
| 여러 메서드가 같은 내부 상태를 공유할 경우 | `set_amount`, `calculate_tax`, `get_total` |
| 테스트와 확장성을 고려해야 하는 경우 | Interface/Polymorphism으로 대체 가능 |

---

## 5. Static Method란 무엇인가?

Static Method는 특정 객체 인스턴스에 종속되지 않는 메서드이다.  
ABAP에서는 `CLASS-METHODS`로 선언한다.

```abap
CLASS-METHODS get_today
  RETURNING VALUE(rv_date) TYPE d.
```

호출할 때는 객체를 만들지 않고 클래스 이름으로 직접 호출한다.

```abap
DATA(lv_today) = zcl_gpt_date_util=>get_today( ).
```

### 5.1 Static Method의 특징

| 특징 | 설명 |
|---|---|
| 객체 생성 불필요 | `NEW` 없이 호출 가능 |
| 클래스 수준 기능 | 특정 인스턴스가 아니라 클래스 자체에 속함 |
| `=>`로 호출 | 클래스명과 Static Method 사이에 `=>` 사용 |
| 공통 유틸리티에 적합 | 변환, 포맷, 단순 계산, 상수 제공 등 |
| Instance Attribute 직접 접근 불가 | 객체별 상태를 전제로 하지 않음 |

### 5.2 Static Method가 적합한 경우

| 상황 | 예 |
|---|---|
| 상태가 필요 없는 단순 계산 | 두 숫자 합계 계산 |
| 공통 포맷 변환 | 날짜 문자열 변환 |
| 코드값 텍스트 변환 | 상태 코드 `A` → `Active` |
| Factory Method | 객체 생성을 통제하는 클래스 메서드 |
| 테스트용 작은 유틸리티 | 입력값만으로 결과가 결정되는 함수 |

## 6. 문법 비교

### 6.1 Instance Method 선언

```abap
CLASS zcl_gpt_counter DEFINITION
  PUBLIC
  FINAL
  CREATE PUBLIC.

  PUBLIC SECTION.
    METHODS:
      increment,
      get_count RETURNING VALUE(rv_count) TYPE i.

  PRIVATE SECTION.
    DATA mv_count TYPE i.
ENDCLASS.
```

구현부는 다음과 같다.

```abap
CLASS zcl_gpt_counter IMPLEMENTATION.

  METHOD increment.
    mv_count = mv_count + 1.
  ENDMETHOD.

  METHOD get_count.
    rv_count = mv_count.
  ENDMETHOD.

ENDCLASS.
```

호출 예:

```abap
DATA(lo_counter) = NEW zcl_gpt_counter( ).

lo_counter->increment( ).
lo_counter->increment( ).

DATA(lv_count) = lo_counter->get_count( ).
```

여기서 `mv_count`는 객체별 상태이다.  
객체를 두 개 만들면 각 객체는 서로 다른 `mv_count` 값을 가진다.

### 6.2 Static Method 선언

```abap
CLASS zcl_gpt_math DEFINITION
  PUBLIC
  FINAL
  CREATE PUBLIC.

  PUBLIC SECTION.
    CLASS-METHODS:
      add
        IMPORTING
          iv_a TYPE i
          iv_b TYPE i
        RETURNING VALUE(rv_result) TYPE i.
ENDCLASS.
```

구현부는 다음과 같다.

```abap
CLASS zcl_gpt_math IMPLEMENTATION.

  METHOD add.
    rv_result = iv_a + iv_b.
  ENDMETHOD.

ENDCLASS.
```

호출 예:

```abap
DATA(lv_sum) = zcl_gpt_math=>add(
  iv_a = 10
  iv_b = 20
).
```

이 예제에서는 객체 상태가 필요 없다.  
입력값 `10`, `20`만으로 결과가 결정되므로 Static Method가 적합하다.

## 7. 호출 연산자 `->`와 `=>`

OO ABAP에서 호출 연산자는 매우 중요하다.

| 연산자 | 의미 | 사용 예 |
|---|---|---|
| `->` | 객체 참조를 통한 Instance Component 접근 | `lo_obj->method( )` |
| `=>` | 클래스 이름을 통한 Static Component 접근 | `zcl_util=>method( )` |

### 7.1 `->` 예시

```abap
DATA(lo_user) = NEW zcl_gpt_user( ).
lo_user->set_name( 'Kim' ).
```

`lo_user`라는 객체 참조가 있어야 한다.  
따라서 객체가 생성되지 않으면 호출할 수 없다.

### 7.2 `=>` 예시

```abap
DATA(lv_text) = zcl_gpt_status_util=>get_text( 'A' ).
```

객체 참조가 필요 없다.  
클래스 이름만으로 호출한다.

### 7.3 초급자 오류

다음은 자주 발생하는 오류이다.

```abap
" 잘못된 예: Instance Method를 클래스명으로 호출
zcl_gpt_user=>set_name( 'Kim' ).
```

`set_name`이 `METHODS`로 선언된 Instance Method라면 위 호출은 맞지 않다.

반대로 다음도 오류이다.

```abap
DATA(lo_util) = NEW zcl_gpt_status_util( ).
lo_util->get_text( 'A' ).
```

`get_text`가 `CLASS-METHODS`로 선언된 Static Method라면 일반적으로 클래스명으로 호출해야 한다.

## 8. Instance Attribute와 Static Attribute

Static Method와 Instance Method의 차이는 Attribute와 함께 이해해야 한다.

| 구분 | Instance Attribute | Static Attribute |
|---|---|---|
| 선언 | `DATA` | `CLASS-DATA` |
| 소속 | 객체별 | 클래스 전체 |
| 접근 | `lo_obj->mv_value` | `zcl_class=>gv_value` |
| 값의 범위 | 객체마다 다름 | 클래스 로드 단위에서 공유 |
| 대표 사용 | 객체 상태 | 전역적 공통 상태, 캐시, 상수성 값 |

### 8.1 Instance Attribute 예시

```abap
PRIVATE SECTION.
  DATA mv_name TYPE string.
```

객체마다 `mv_name`이 다를 수 있다.

```abap
DATA(lo_user1) = NEW zcl_gpt_user( ).
DATA(lo_user2) = NEW zcl_gpt_user( ).

lo_user1->set_name( 'Kim' ).
lo_user2->set_name( 'Lee' ).
```

`lo_user1`과 `lo_user2`는 서로 다른 이름을 가진다.

### 8.2 Static Attribute 예시

```abap
PRIVATE SECTION.
  CLASS-DATA gv_call_count TYPE i.
```

`gv_call_count`는 클래스 수준에서 공유된다.  
모든 호출자가 같은 값을 보게 될 수 있다.

이 때문에 Static Attribute는 신중히 사용해야 한다.  
특히 상태를 저장하는 Static Attribute는 테스트, 병렬 처리, 사용자별 데이터 분리 측면에서 혼란을 만들 수 있다.

## 9. 실습 예제 1 — Instance Method로 카운터 만들기

### 9.1 목적

객체마다 독립적인 상태를 가지는 Instance Method를 이해한다.

### 9.2 클래스 정의

```abap
CLASS zcl_gpt_counter DEFINITION
  PUBLIC
  FINAL
  CREATE PUBLIC.

  PUBLIC SECTION.
    METHODS:
      increment,
      get_count RETURNING VALUE(rv_count) TYPE i.

  PRIVATE SECTION.
    DATA mv_count TYPE i.
ENDCLASS.
```

### 9.3 클래스 구현

```abap
CLASS zcl_gpt_counter IMPLEMENTATION.

  METHOD increment.
    mv_count = mv_count + 1.
  ENDMETHOD.

  METHOD get_count.
    rv_count = mv_count.
  ENDMETHOD.

ENDCLASS.
```

### 9.4 테스트 코드

```abap
DATA(lo_counter1) = NEW zcl_gpt_counter( ).
DATA(lo_counter2) = NEW zcl_gpt_counter( ).

lo_counter1->increment( ).
lo_counter1->increment( ).

lo_counter2->increment( ).

WRITE: / 'Counter1:', lo_counter1->get_count( ).
WRITE: / 'Counter2:', lo_counter2->get_count( ).
```

예상 결과:

```text
Counter1: 2
Counter2: 1
```

### 9.5 학습 포인트

같은 클래스에서 만든 객체라도 Instance Attribute는 객체별로 다르다.  
따라서 객체 상태를 다루는 기능에는 Instance Method가 적합하다.

## 10. 실습 예제 2 — Static Method로 상태 텍스트 변환하기

### 10.1 목적

객체 상태가 필요 없는 공통 변환 로직을 Static Method로 작성한다.

### 10.2 클래스 정의

```abap
CLASS zcl_gpt_status_text DEFINITION
  PUBLIC
  FINAL
  CREATE PUBLIC.

  PUBLIC SECTION.
    CLASS-METHODS:
      get_text
        IMPORTING iv_status TYPE c LENGTH 1
        RETURNING VALUE(rv_text) TYPE string.
ENDCLASS.
```

### 10.3 클래스 구현

```abap
CLASS zcl_gpt_status_text IMPLEMENTATION.

  METHOD get_text.
    CASE iv_status.
      WHEN 'A'.
        rv_text = 'Active'.
      WHEN 'I'.
        rv_text = 'Inactive'.
      WHEN 'B'.
        rv_text = 'Blocked'.
      WHEN OTHERS.
        rv_text = 'Unknown'.
    ENDCASE.
  ENDMETHOD.

ENDCLASS.
```

### 10.4 호출 예

```abap
DATA(lv_text) = zcl_gpt_status_text=>get_text( 'A' ).

WRITE: / lv_text.
```

예상 결과:

```text
Active
```

### 10.5 학습 포인트

`get_text`는 객체별 상태가 필요 없다.  
입력값만 있으면 결과를 만들 수 있으므로 Static Method가 적합하다.

## 11. 실습 예제 3 — 잘못된 Static 남용

초급자는 Static Method가 편하다는 이유로 모든 기능을 Static으로 만들고 싶어질 수 있다.

예를 들어 다음 클래스를 보자.

```abap
CLASS zcl_gpt_bad_cart DEFINITION
  PUBLIC
  FINAL
  CREATE PUBLIC.

  PUBLIC SECTION.
    CLASS-METHODS:
      add_amount IMPORTING iv_amount TYPE p LENGTH 10 DECIMALS 2,
      get_total RETURNING VALUE(rv_total) TYPE p LENGTH 10 DECIMALS 2.

  PRIVATE SECTION.
    CLASS-DATA gv_total TYPE p LENGTH 10 DECIMALS 2.
ENDCLASS.
```

이 클래스는 장바구니 총액을 Static Attribute에 저장한다.  
여러 사용자가 동시에 사용하거나 여러 테스트가 실행될 때 값이 공유되어 예측하기 어려운 결과가 나올 수 있다.

더 적절한 설계는 장바구니 객체를 Instance로 만들고, 총액을 Instance Attribute로 두는 것이다.

```abap
CLASS zcl_gpt_cart DEFINITION
  PUBLIC
  FINAL
  CREATE PUBLIC.

  PUBLIC SECTION.
    METHODS:
      add_amount IMPORTING iv_amount TYPE p LENGTH 10 DECIMALS 2,
      get_total RETURNING VALUE(rv_total) TYPE p LENGTH 10 DECIMALS 2.

  PRIVATE SECTION.
    DATA mv_total TYPE p LENGTH 10 DECIMALS 2.
ENDCLASS.
```

학습 포인트는 다음이다.

```text
Static은 편리하지만 상태 저장에 남용하면 위험하다.
객체별로 달라져야 하는 값은 Instance Attribute와 Instance Method가 적합하다.
```

## 12. 설계 판단 기준

### 12.1 Instance Method를 선택해야 하는 질문

다음 질문 중 하나라도 “예”라면 Instance Method를 먼저 검토한다.

```text
이 기능이 객체의 현재 상태를 읽는가?
이 기능이 객체의 현재 상태를 변경하는가?
객체마다 다른 결과가 나와야 하는가?
Constructor로 받은 값이 이후 메서드에서 계속 사용되는가?
다형성, Interface, Mocking, Unit Test 확장이 필요한가?
```

예:

```text
주문 객체의 총액 계산
사용자 객체의 상태 변경
장바구니 객체의 품목 추가
서비스 객체의 내부 설정 기반 처리
```

### 12.2 Static Method를 선택해도 좋은 질문

다음 질문에 모두 가깝다면 Static Method가 적합할 수 있다.

```text
입력값만으로 결과가 결정되는가?
객체 상태가 전혀 필요 없는가?
공통 유틸리티인가?
객체를 만들 이유가 없는 단순 변환인가?
공유 상태를 저장하지 않는가?
```

예:

```text
날짜 포맷 변환
상태 코드 텍스트 변환
문자열 정규화
단순 계산 함수
Factory Method
```

## 13. Static Method와 테스트 가능성

Static Method는 간단한 유틸리티에는 편리하지만, 테스트와 대체 가능성 측면에서는 주의가 필요하다.

### 13.1 Static Method의 장점

| 장점 | 설명 |
|---|---|
| 호출이 간단함 | 객체 생성 없이 바로 호출 |
| 순수 함수 형태에 적합 | 입력값만으로 결과가 정해지는 경우 명확함 |
| 공통 유틸리티 작성이 쉬움 | 날짜, 문자열, 코드 변환 등에 적합 |

### 13.2 Static Method의 단점

| 단점 | 설명 |
|---|---|
| 대체가 어려울 수 있음 | Interface 기반 Mocking이 어렵다. |
| 공유 상태 사용 시 위험 | `CLASS-DATA`가 예기치 않게 공유된다. |
| 의존성 숨김 | 내부에서 DB나 외부 기능을 직접 호출하면 테스트가 어려워진다. |
| 절차적 코드로 회귀 가능 | 모든 로직을 Static Utility로 몰아넣으면 OO 설계 장점이 약해진다. |

### 13.3 실무 권장

상태 없는 작은 Utility는 Static으로 둘 수 있다.  
하지만 업무 서비스 로직은 Instance Method와 Interface 기반 설계를 우선 검토하는 것이 좋다.

## 14. ABAP에서 Static Constructor 참고

ABAP Class에는 Static Constructor 개념도 있다.

```abap
CLASS-METHODS class_constructor.
```

또는 클래스의 Static Constructor는 클래스가 처음 사용될 때 실행되는 초기화 로직으로 이해할 수 있다.

초급 단계에서는 다음 정도만 기억한다.

```text
Instance Constructor는 객체 생성 시 실행된다.
Static Constructor는 클래스 사용 시점의 클래스 수준 초기화에 사용된다.
```

Static Constructor는 강력하지만, 실행 시점을 초급자가 예측하기 어렵고 숨은 부작용을 만들 수 있으므로 이번 모듈에서는 깊게 다루지 않는다.

## 15. 정상 흐름과 오류 흐름

### 15.1 정상 흐름 — Instance Method

```text
1. Class에 METHODS 선언
2. Instance Attribute 정의
3. METHOD 구현
4. NEW 또는 CREATE OBJECT로 객체 생성
5. 참조 변수->method( )로 호출
6. 객체별 상태가 의도대로 유지되는지 확인
```

### 15.2 정상 흐름 — Static Method

```text
1. Class에 CLASS-METHODS 선언
2. 필요한 Importing/Returning Parameter 정의
3. METHOD 구현
4. 클래스명=>method( )로 호출
5. 입력값과 결과가 일관적인지 확인
```

### 15.3 오류 흐름 — 호출 연산자 오류

| 현상 | 원인 | 해결 |
|---|---|---|
| Static Method를 `->`로 호출 | 클래스 메서드를 객체 메서드처럼 호출 | `=>` 사용 |
| Instance Method를 `=>`로 호출 | 객체 메서드를 클래스 메서드처럼 호출 | 객체 생성 후 `->` 사용 |
| 객체 참조가 Initial | `NEW` 또는 `CREATE OBJECT` 누락 | 객체 생성 후 호출 |
| Instance Attribute를 Static Method에서 직접 사용 | 객체 상태가 없기 때문 | Instance Method로 전환 또는 설계 변경 |

### 15.4 오류 흐름 — Static Attribute 공유 문제

| 현상 | 원인 | 해결 |
|---|---|---|
| 테스트마다 결과가 달라짐 | Static Attribute에 상태 누적 | Instance Attribute 사용 |
| 사용자별 값이 섞임 | 클래스 수준 공유 상태 사용 | 객체별 상태로 분리 |
| 초기화 타이밍이 불명확 | Static Constructor/CLASS-DATA 남용 | 명시적 객체 초기화 구조 사용 |

## 16. 미니 실습 과제

### 16.1 과제 A — Static Method 만들기

다음 기능을 가진 클래스를 만든다.

```text
Class: ZCL_GPT_TEXT_UTIL
Static Method: TO_UPPER
입력: IV_TEXT TYPE STRING
출력: RV_TEXT TYPE STRING
기능: 입력 문자열을 대문자로 변환
```

예상 호출:

```abap
DATA(lv_result) = zcl_gpt_text_util=>to_upper( 'sap abap' ).
WRITE lv_result.
```

예상 결과:

```text
SAP ABAP
```

### 16.2 과제 B — Instance Method 만들기

다음 기능을 가진 클래스를 만든다.

```text
Class: ZCL_GPT_SCORE
Instance Attribute: MV_SCORE TYPE I
Constructor: 초기 점수 입력
Instance Method: ADD_SCORE
Instance Method: GET_SCORE
```

예상 호출:

```abap
DATA(lo_score) = NEW zcl_gpt_score( iv_score = 70 ).

lo_score->add_score( 10 ).

WRITE lo_score->get_score( ).
```

예상 결과:

```text
80
```

### 16.3 과제 C — 판단 문제

다음 기능이 Static Method인지 Instance Method인지 판단한다.

| 기능 | 권장 방식 | 이유 |
|---|---|---|
| 날짜를 `YYYY-MM-DD` 문자열로 변환 | Static | 입력값만으로 결과 결정 |
| 고객 객체의 등급을 변경 | Instance | 고객 객체 상태 변경 |
| 두 숫자의 평균 계산 | Static | 상태 불필요 |
| 장바구니에 상품 추가 | Instance | 장바구니별 상태 필요 |
| 상태 코드 텍스트 변환 | Static | 코드값만으로 결과 결정 |

## 17. 실무 안티패턴

### 17.1 모든 Method를 Static으로 만드는 설계

초급자나 절차적 프로그래밍에 익숙한 개발자는 다음처럼 설계할 수 있다.

```text
모든 로직을 ZCL_XXX_UTIL의 CLASS-METHODS로 작성
모든 값은 CLASS-DATA로 공유
객체 생성은 사용하지 않음
```

이 방식은 처음에는 간단해 보이지만, 규모가 커지면 다음 문제가 생긴다.

| 문제 | 설명 |
|---|---|
| 상태 추적 어려움 | 값이 어디서 변경되었는지 찾기 어렵다. |
| 테스트 어려움 | 의존성을 대체하기 어렵다. |
| 확장성 저하 | Interface, Inheritance 활용이 제한된다. |
| 동시성 위험 | 공유 상태가 의도치 않게 섞일 수 있다. |
| OO 설계 이점 상실 | 클래스가 단순 함수 묶음이 된다. |

### 17.2 무조건 Instance로만 만드는 설계

반대로 모든 기능을 Instance Method로만 만드는 것도 항상 좋은 것은 아니다.

```abap
DATA(lo_util) = NEW zcl_gpt_string_util( ).
DATA(lv_result) = lo_util->to_upper( 'abap' ).
```

상태가 전혀 없는 단순 문자열 변환이라면 객체 생성은 불필요한 복잡도를 추가할 수 있다.

### 17.3 실무 균형

```text
상태가 필요하면 Instance
상태가 필요 없고 순수 변환이면 Static
업무 서비스는 Instance 우선
작은 Utility는 Static 허용
공유 상태 CLASS-DATA는 신중히 사용
```

## 18. 자가 점검 문제

### Q1. `METHODS`와 `CLASS-METHODS`의 차이는 무엇인가?

**모범 답안:**  
`METHODS`는 Instance Method를 선언하며 객체를 생성한 뒤 `->`로 호출한다. `CLASS-METHODS`는 Static Method를 선언하며 객체 생성 없이 클래스명과 `=>`를 사용해 호출한다.

### Q2. 객체별로 다른 상태를 가져야 하는 로직에는 어떤 Method가 적합한가?

**모범 답안:**  
Instance Method가 적합하다. 객체별 Instance Attribute를 사용할 수 있기 때문이다.

### Q3. Static Method를 남용하면 어떤 문제가 생길 수 있는가?

**모범 답안:**  
공유 상태가 생기면 테스트가 어려워지고, 사용자별 값이 섞일 수 있으며, Interface 기반 대체나 확장이 어려워질 수 있다. 모든 로직이 Utility Class로 몰리면 OO 설계의 장점도 약해진다.

### Q4. 다음 호출에서 사용된 연산자는 무엇을 의미하는가?

```abap
zcl_gpt_math=>add( ).
```

**모범 답안:**  
`=>`는 클래스 수준의 Static Component를 호출할 때 사용하는 연산자이다.

### Q5. 다음 호출에서 사용된 연산자는 무엇을 의미하는가?

```abap
lo_cart->add_item( ).
```

**모범 답안:**  
`->`는 객체 참조를 통해 Instance Component를 호출할 때 사용하는 연산자이다.

## 21. 핵심 요약

```text
Instance Method는 METHODS로 선언하고 객체 참조->메서드 형태로 호출한다.
Static Method는 CLASS-METHODS로 선언하고 클래스명=>메서드 형태로 호출한다.
객체별 상태가 필요하면 Instance Method가 적합하다.
입력값만으로 결과가 결정되는 공통 Utility는 Static Method가 적합하다.
CLASS-DATA와 Static Method를 남용하면 테스트와 유지보수가 어려워질 수 있다.
OO ABAP 설계에서는 편의성보다 상태, 책임, 테스트 가능성을 기준으로 선택해야 한다.
```
