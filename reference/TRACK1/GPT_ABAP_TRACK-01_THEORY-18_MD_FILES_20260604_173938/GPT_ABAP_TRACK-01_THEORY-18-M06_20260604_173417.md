## 3. 왜 Exception Class가 필요한가?

### 3.1 오류는 프로그램 흐름의 일부이다

실무 프로그램은 항상 정상 데이터만 처리하지 않는다.

예를 들어 사용자 정보를 조회하는 Method가 있다고 하자.

```abap
lo_service->get_user( iv_user_id = 'U0001' ).
```

이 Method 안에서는 여러 문제가 생길 수 있다.

| 오류 상황 | 예시 |
|---|---|
| 입력값 누락 | `iv_user_id`가 Initial |
| 데이터 없음 | 해당 사용자 ID가 테이블에 없음 |
| 권한 없음 | 현재 사용자가 조회 권한이 없음 |
| 외부 호출 실패 | RFC, HTTP, DB 접근 실패 |
| 업무 규칙 위반 | 비활성 사용자에 대한 처리 요청 |

초급 단계에서는 보통 `IF`, `MESSAGE`, `sy-subrc`로 처리하기 쉽다.  
하지만 OO ABAP에서는 Method 내부에서 오류를 발견했을 때, 호출자에게 오류의 의미를 명확히 전달해야 한다.

이때 Exception Class가 필요하다.

## 4. 전통적 오류 처리와 OO 예외 처리 비교

### 4.1 `sy-subrc` 기반 처리

전통적인 ABAP에서는 많은 구문이 실행 결과를 `sy-subrc`에 담는다.

예:

```abap
READ TABLE lt_user INTO ls_user WITH KEY user_id = iv_user_id.

IF sy-subrc <> 0.
  WRITE: / 'User not found'.
ENDIF.
```

이 방식은 간단하지만 다음 한계가 있다.

| 한계 | 설명 |
|---|---|
| 의미 부족 | `sy-subrc = 4`만으로는 구체적인 업무 오류를 알기 어렵다. |
| 누락 위험 | 개발자가 `sy-subrc` 확인을 잊으면 오류가 조용히 지나갈 수 있다. |
| 호출자 전달 어려움 | Method 내부 오류를 바깥 계층에 구조적으로 전달하기 어렵다. |
| 오류 정보 부족 | 어떤 입력값에서 왜 실패했는지 담기 어렵다. |

### 4.2 Class-based Exception 처리

OO ABAP에서는 오류 상황을 Exception Class의 객체로 표현할 수 있다.

```abap
RAISE EXCEPTION TYPE zcx_gpt_user_not_found.
```

호출자는 다음처럼 처리한다.

```abap
TRY.
    lo_service->get_user( iv_user_id = 'U9999' ).

  CATCH zcx_gpt_user_not_found INTO DATA(lx_user).
    WRITE: / lx_user->get_text( ).
ENDTRY.
```

이 방식의 장점은 다음과 같다.

| 장점 | 설명 |
|---|---|
| 의미 명확 | 오류 종류를 클래스 이름으로 표현할 수 있다. |
| 구조적 처리 | `TRY ... CATCH` 블록으로 정상 흐름과 오류 흐름을 분리한다. |
| 정보 전달 | 예외 객체에 메시지, 입력값, 원인 정보를 담을 수 있다. |
| 유지보수성 | 어떤 오류가 발생할 수 있는지 Method Signature에서 드러난다. |
| 테스트 용이성 | ABAP Unit에서 특정 예외 발생 여부를 검증하기 쉽다. |

## 5. Exception Class의 기본 개념

### 5.1 Exception Class란?

Exception Class는 오류 상황을 표현하기 위해 사용하는 ABAP Class이다.

일반 Class와 마찬가지로 이름, 속성, Method를 가질 수 있지만, 목적이 다르다.

| 구분 | 일반 Class | Exception Class |
|---|---|---|
| 목적 | 업무 로직이나 상태 표현 | 오류 상황 표현 |
| 사용 흐름 | 생성 후 Method 호출 | 오류 발생 시 Raise |
| 호출자 처리 | 일반 메서드 호출 | `TRY ... CATCH`로 처리 |
| 대표 상위 클래스 | 일반 Object 계층 | `CX_ROOT` 계열 |

ABAP의 Class-based Exception은 일반적으로 `CX_ROOT` 계열의 예외 클래스 구조를 따른다.  
Custom Exception Class를 만들 때도 시스템이 제공하는 예외 기반 클래스를 상속하는 방식으로 설계된다.

## 6. Checked Exception과 Unchecked Exception

ABAP Objects에는 Class-based Exception의 주요 종류가 있다.

초급 단계에서는 다음 세 가지 이름을 기억하면 된다.

| 예외 계열 | 초급 설명 |
|---|---|
| `CX_STATIC_CHECK` | 호출자가 선언 또는 처리해야 하는 Checked Exception |
| `CX_DYNAMIC_CHECK` | 런타임에서 발생 가능하며 정적 선언 강제가 약한 Checked 성격의 예외 |
| `CX_NO_CHECK` | 선언하지 않아도 전파될 수 있는 Unchecked Exception |

### 6.1 `CX_STATIC_CHECK`

`CX_STATIC_CHECK` 계열은 호출자에게 예외 처리를 명확히 요구하는 성격이 강하다.

예를 들어 Method가 `ZCX_GPT_USER_NOT_FOUND`를 발생시킬 수 있다면, Method Signature에 예외가 드러나야 한다.

개념적으로는 다음과 같다.

```abap
METHODS get_user
  IMPORTING iv_user_id TYPE zde_gpt_user_id
  RAISING   zcx_gpt_user_not_found.
```

호출자는 다음 중 하나를 선택해야 한다.

```text
1. TRY ... CATCH로 직접 처리한다.
2. 자신의 Method Signature에 다시 RAISING으로 전파한다.
```

초급 실습에서는 `CX_STATIC_CHECK` 기반 Custom Exception을 먼저 권장한다.  
이유는 “이 Method는 이런 예외를 발생시킬 수 있다”는 계약이 분명해지기 때문이다.

### 6.2 `CX_DYNAMIC_CHECK`

`CX_DYNAMIC_CHECK`는 초급 단계에서 깊게 다루지 않는다.  
다만 Runtime 상황에서 발생할 수 있는 예외 계열이며, 선언·처리 방식이 `CX_STATIC_CHECK`와 다소 다르게 느껴질 수 있다는 정도만 이해한다.

### 6.3 `CX_NO_CHECK`

`CX_NO_CHECK` 계열은 호출자가 반드시 Signature에 선언하거나 CATCH하지 않아도 전파될 수 있다.

이 방식은 편리할 수 있지만, 초급자가 남용하면 다음 문제가 생긴다.

| 문제 | 설명 |
|---|---|
| 호출자가 오류 가능성을 모름 | Method Signature에 예외가 명확히 보이지 않을 수 있다. |
| 예외 흐름 추적 어려움 | 어디서 잡아야 하는지 모호해질 수 있다. |
| 업무 오류 남용 위험 | 예상 가능한 업무 오류까지 Unchecked로 처리할 수 있다. |

따라서 초급 실무 감각에서는 다음 기준을 추천한다.

```text
예상 가능한 업무 예외는 CX_STATIC_CHECK 기반으로 명확히 설계한다.
시스템적이고 복구가 어려운 예외는 별도 기준으로 판단한다.
```

> [추정] 프로젝트에 따라 Exception Class 설계 규칙은 다를 수 있다. 일부 조직은 checked exception 남용을 피하고, 일부 조직은 명확한 RAISING 선언을 선호한다. 본 문서는 초급 학습과 명시적 오류 계약을 우선한다.

## 7. `TRY ... CATCH ... ENDTRY` 기본 구조

### 7.1 기본 문법

```abap
TRY.
    " 정상 처리 로직

  CATCH zcx_gpt_user_not_found INTO DATA(lx_user_not_found).
    " 예외 처리 로직

ENDTRY.
```

`TRY` 블록에는 예외가 발생할 수 있는 코드를 작성한다.  
`CATCH` 블록에는 특정 예외가 발생했을 때의 처리 로직을 작성한다.

### 7.2 여러 예외 처리

여러 예외를 처리할 수도 있다.

```abap
TRY.
    lo_service->get_user( iv_user_id = lv_user_id ).

  CATCH zcx_gpt_user_not_found INTO DATA(lx_not_found).
    WRITE: / lx_not_found->get_text( ).

  CATCH zcx_gpt_invalid_input INTO DATA(lx_invalid).
    WRITE: / lx_invalid->get_text( ).

ENDTRY.
```

### 7.3 CATCH 순서

예외 클래스에는 상속 관계가 있을 수 있다.  
일반적으로 더 구체적인 예외를 먼저 CATCH하고, 더 일반적인 예외를 나중에 CATCH한다.

초급자는 다음 원칙을 기억하면 된다.

```text
구체적인 예외부터 잡고,
일반적인 예외는 마지막에 잡는다.
```

나쁜 예:

```abap
TRY.
    lo_service->get_user( iv_user_id = lv_user_id ).

  CATCH cx_root INTO DATA(lx_root).
    WRITE: / lx_root->get_text( ).

  CATCH zcx_gpt_user_not_found INTO DATA(lx_not_found).
    WRITE: / lx_not_found->get_text( ).

ENDTRY.
```

위 구조에서는 `cx_root`가 너무 일반적이어서 구체적인 CATCH가 의미 없어질 수 있다.  
실제 활성화 또는 문법 검사에서 도달 불가능한 CATCH와 관련된 문제가 발생할 수 있다.

좋은 예:

```abap
TRY.
    lo_service->get_user( iv_user_id = lv_user_id ).

  CATCH zcx_gpt_user_not_found INTO DATA(lx_not_found).
    WRITE: / lx_not_found->get_text( ).

  CATCH cx_root INTO DATA(lx_root).
    WRITE: / lx_root->get_text( ).

ENDTRY.
```

## 8. `RAISE EXCEPTION` 기본 구조

### 8.1 예외 발생시키기

Method 내부에서 처리할 수 없는 오류가 발생하면 예외를 발생시킨다.

```abap
IF iv_user_id IS INITIAL.
  RAISE EXCEPTION TYPE zcx_gpt_invalid_input.
ENDIF.
```

이 코드는 “입력값이 비어 있으므로 이 Method는 정상 결과를 만들 수 없다”는 의미이다.

### 8.2 예외를 호출자에게 전달한다는 의미

`RAISE EXCEPTION`은 단순히 메시지를 출력하는 것이 아니다.  
현재 처리 흐름을 중단하고, 해당 예외를 처리할 수 있는 호출자 쪽 `CATCH` 블록으로 흐름을 넘긴다.

개념 흐름은 다음과 같다.

```text
Caller
  → Method 호출
    → Method 내부 오류 발견
    → RAISE EXCEPTION
  → Caller의 CATCH 블록으로 이동
```

### 8.3 `RAISE EXCEPTION NEW`와 최신 문법

S/4HANA 기반 최신 ABAP에서는 다음과 같은 형태도 자주 사용한다.

```abap
RAISE EXCEPTION NEW zcx_gpt_invalid_input( ).
```

다만 초급 단계에서는 시스템 릴리스, 문법 레벨, 프로젝트 코딩 규칙에 따라 전통적 문법과 최신 문법이 함께 보일 수 있다는 점을 이해하면 된다.

```abap
RAISE EXCEPTION TYPE zcx_gpt_invalid_input.
```

```abap
RAISE EXCEPTION NEW zcx_gpt_invalid_input( ).
```

두 문법의 세부 차이는 Modern ABAP Syntax와 Exception Handling 심화에서 더 깊게 다루는 것이 적절하다.

## 9. Custom Exception Class 설계 예시

### 9.1 실습 시나리오

사용자 조회 서비스 Class가 있다고 가정한다.

```text
Class: ZCL_GPT_USER_SERVICE
Method: GET_USER
Exception: ZCX_GPT_USER_NOT_FOUND
```

`GET_USER` Method는 사용자 ID를 받아 사용자 정보를 조회한다.  
사용자가 없으면 `ZCX_GPT_USER_NOT_FOUND` 예외를 발생시킨다.

### 9.2 Exception Class 이름

교육용 Naming은 다음처럼 사용한다.

| 객체 | 예시 |
|---|---|
| Exception Class | `ZCX_GPT_USER_NOT_FOUND` |
| 일반 Service Class | `ZCL_GPT_USER_SERVICE` |
| Interface | `ZIF_GPT_USER_PROVIDER` |

Exception Class는 보통 `ZCX_` Prefix를 사용하면 의미가 명확하다.

나쁜 예:

```text
ZCL_ERROR
ZCL_TEST_EXCEPTION
ZCX_001
ZCX_TEMP
```

좋은 예:

```text
ZCX_GPT_USER_NOT_FOUND
ZCX_GPT_INVALID_INPUT
ZCX_GPT_AUTH_FAILED
```

이름만 보고도 어떤 오류인지 예상 가능해야 한다.

## 10. SE24 또는 ADT에서 Exception Class 생성

### 10.1 SE24 기준 생성 흐름

SAP GUI 800에서 전통적인 방식으로 Exception Class를 만들 수 있다.

```text
1. Transaction Code: SE24
2. Class 이름 입력: ZCX_GPT_USER_NOT_FOUND
3. Create
4. Exception Class 선택
5. Superclass 지정 또는 시스템 제안 확인
6. Description 입력
7. Save
8. Activate
```

### 10.2 상위 클래스 선택

교육용으로는 `CX_STATIC_CHECK` 기반 예외를 먼저 권장한다.

```text

```

## 11. Method Signature에 예외 선언하기

Exception Class를 만들었다면, 예외를 발생시킬 Method의 Signature에 선언해야 한다.

예:

```abap
CLASS zcl_gpt_user_service DEFINITION
  PUBLIC
  FINAL
  CREATE PUBLIC.

  PUBLIC SECTION.
    TYPES:
      BEGIN OF ty_user,
        user_id   TYPE c LENGTH 10,
        user_name TYPE c LENGTH 40,
        status    TYPE c LENGTH 1,
      END OF ty_user.

    METHODS get_user
      IMPORTING
        iv_user_id TYPE c LENGTH 10
      RETURNING
        VALUE(rs_user) TYPE ty_user
      RAISING
        zcx_gpt_user_not_found.
ENDCLASS.
```

여기서 중요한 부분은 다음이다.

```abap
RAISING zcx_gpt_user_not_found
```

이 선언은 Method의 계약이다.

```text
이 Method는 정상적으로 User를 반환할 수 있다.
하지만 사용자가 없으면 ZCX_GPT_USER_NOT_FOUND를 발생시킬 수 있다.
```

호출자는 이 계약을 보고 예외 처리를 준비할 수 있다.

---

## 12. Method 구현 예시

아래 코드는 교육용 단순 예제이다.  
실무에서는 DB 조회, 권한 체크, 메시지 클래스, 로깅 등을 함께 고려해야 한다.

```abap
CLASS zcl_gpt_user_service IMPLEMENTATION.

  METHOD get_user.

    IF iv_user_id IS INITIAL.
      RAISE EXCEPTION TYPE zcx_gpt_user_not_found.
    ENDIF.

    CASE iv_user_id.
      WHEN 'U000000001'.
        rs_user-user_id   = iv_user_id.
        rs_user-user_name = 'Kim Developer'.
        rs_user-status    = 'A'.

      WHEN OTHERS.
        RAISE EXCEPTION TYPE zcx_gpt_user_not_found.
    ENDCASE.

  ENDMETHOD.

ENDCLASS.
```

이 예제의 핵심은 다음이다.

| 상황 | 처리 |
|---|---|
| `iv_user_id`가 `U000000001` | 정상 사용자 반환 |
| 그 외 값 | `ZCX_GPT_USER_NOT_FOUND` 예외 발생 |
| Initial 입력 | 예외 발생 |

실무에서는 Initial 입력과 Not Found를 서로 다른 예외로 나누는 것이 더 명확할 수 있다.

예:

```text
ZCX_GPT_INVALID_INPUT
ZCX_GPT_USER_NOT_FOUND
```

다만 이번 모듈에서는 예외 처리 기본 구조를 익히는 것이 목표이므로 하나의 예외로 단순화한다.

## 13. 호출자에서 TRY CATCH 처리하기

호출자는 예외가 발생할 수 있는 Method를 `TRY` 블록 안에서 호출한다.

```abap
START-OF-SELECTION.

  DATA(lo_service) = NEW zcl_gpt_user_service( ).

  TRY.
      DATA(ls_user) = lo_service->get_user( iv_user_id = 'U999999999' ).

      WRITE: / 'User ID  :', ls_user-user_id,
             / 'User Name:', ls_user-user_name,
             / 'Status   :', ls_user-status.

    CATCH zcx_gpt_user_not_found INTO DATA(lx_not_found).
      WRITE: / 'User not found.'.
      WRITE: / lx_not_found->get_text( ).

  ENDTRY.
```

초급자는 `TRY`와 `CATCH`를 다음처럼 읽으면 된다.

```text
TRY:
  예외가 발생할 수 있는 정상 처리 시도

CATCH:
  특정 예외가 발생했을 때의 대체 처리
```

## 14. `get_text( )`의 의미

예외 객체는 일반적으로 메시지 텍스트를 반환할 수 있다.

```abap
lx_not_found->get_text( )
```

초급 단계에서는 다음 정도로 이해하면 충분하다.

```text
get_text( )는 예외 객체가 가지고 있는 사람이 읽을 수 있는 오류 설명을 반환하는 메서드이다.
```

고급 과정에서는 메시지 클래스, T100 메시지, IF_T100_MESSAGE, Placeholder, Previous Exception 등으로 확장할 수 있다.  
이번 모듈에서는 과도하게 확장하지 않는다.

## 15. 정상 흐름과 예외 흐름 비교

### 15.1 정상 흐름

```text
프로그램 시작
→ Service 객체 생성
→ get_user 호출
→ 사용자 존재
→ 사용자 구조 반환
→ WRITE 출력
→ ENDTRY 이후 계속 진행
```

### 15.2 예외 흐름

```text
프로그램 시작
→ Service 객체 생성
→ get_user 호출
→ 사용자 없음
→ RAISE EXCEPTION
→ TRY 블록의 남은 코드는 건너뜀
→ CATCH zcx_gpt_user_not_found 실행
→ 오류 메시지 출력
→ ENDTRY 이후 계속 진행
```

이 비교가 중요하다.  
예외가 발생하면 `TRY` 블록 안에서 예외 발생 지점 이후의 정상 코드는 실행되지 않는다.  
대신 해당 예외를 처리할 수 있는 `CATCH` 블록으로 이동한다.

## 17. 자주 발생하는 오류와 해결

### 17.1 Method에서 예외를 Raise했는데 Signature에 선언하지 않음

#### 증상

`CX_STATIC_CHECK` 기반 예외를 발생시킬 때 문법 오류가 발생하거나, 호출자가 처리해야 한다는 메시지가 나타난다.

#### 원인

Method Signature에 `RAISING zcx_gpt_user_not_found`를 선언하지 않았다.

#### 해결

Method Definition에 RAISING 구문을 추가한다.

```abap
METHODS get_user
  IMPORTING iv_user_id TYPE c LENGTH 10
  RETURNING VALUE(rs_user) TYPE ty_user
  RAISING zcx_gpt_user_not_found.
```

### 17.2 호출자에서 TRY CATCH를 작성하지 않음

#### 증상

Checked Exception을 처리하지 않았다는 문법 또는 활성화 오류가 발생한다.

#### 원인

호출자가 예외를 직접 처리하지도 않고, 자신의 Signature에 전파하지도 않았다.

#### 해결

Report에서는 보통 `TRY ... CATCH`를 작성한다.

```abap
TRY.
    lo_service->get_user( iv_user_id = lv_user_id ).
  CATCH zcx_gpt_user_not_found INTO DATA(lx_error).
    WRITE lx_error->get_text( ).
ENDTRY.
```

### 17.3 CATCH 순서 오류

#### 증상

구체적인 예외 CATCH가 실행되지 않거나, 문법적으로 도달 불가능한 CATCH가 된다.

#### 원인

상위 예외 클래스인 `cx_root`를 먼저 CATCH했다.

#### 해결

구체적인 예외를 먼저 CATCH하고, 일반 예외는 마지막에 둔다.

```abap
CATCH zcx_gpt_user_not_found INTO DATA(lx_not_found).
CATCH cx_root INTO DATA(lx_root).
```

### 17.4 예외를 메시지처럼 오해함

#### 증상

`RAISE EXCEPTION` 후에도 같은 Method 안에서 다음 코드가 계속 실행될 것으로 생각한다.

#### 원인

예외 흐름을 단순 메시지 출력으로 오해했다.

#### 해결

예외가 발생하면 현재 정상 흐름은 중단되고 CATCH 가능한 호출자 쪽으로 제어가 이동한다는 점을 이해한다.

### 17.5 모든 오류를 하나의 Exception Class로 처리함

#### 증상

`ZCX_ERROR` 하나로 모든 오류를 처리한다.

#### 문제

오류 의미가 불명확해지고, 호출자가 어떤 후속 조치를 해야 하는지 알기 어렵다.

#### 해결

업무적으로 후속 처리가 다른 오류는 별도 Exception Class 또는 명확한 오류 코드/텍스트로 구분한다.

예:

```text
ZCX_GPT_INVALID_INPUT
ZCX_GPT_USER_NOT_FOUND
ZCX_GPT_AUTH_FAILED
```

## 18. 실무 적용 기준

### 18.1 Exception Class가 적합한 경우

| 상황 | 이유 |
|---|---|
| Method가 정상 결과를 만들 수 없는 경우 | 호출자에게 실패를 명확히 알릴 수 있다. |
| 오류 원인별 후속 처리가 필요한 경우 | CATCH를 분리할 수 있다. |
| 여러 계층을 거쳐 오류를 전달해야 하는 경우 | 객체 기반으로 전파할 수 있다. |
| ABAP Unit에서 오류 상황을 검증해야 하는 경우 | 특정 예외 발생 여부를 테스트할 수 있다. |
| 메시지 이상의 오류 정보가 필요한 경우 | 예외 객체에 속성을 둘 수 있다. |

### 18.2 Exception Class를 남용하면 안 되는 경우

| 상황 | 설명 |
|---|---|
| 단순 조건 분기 | `IF`로 충분한 정상 업무 분기일 수 있다. |
| 루프 안의 정상 Skip | `CONTINUE`나 조건 필터가 더 적절할 수 있다. |
| 사용자 안내 메시지만 필요한 경우 | Selection Screen 입력 검증 메시지로 충분할 수 있다. |
| 성능 민감 대량 반복 | 예외를 일반 제어 흐름으로 남용하면 가독성과 성능 측면에서 좋지 않다. |

중요한 원칙은 다음이다.

```text
Exception은 예외 상황을 표현하기 위한 것이지,
일반적인 조건 분기를 대체하기 위한 도구가 아니다.
```

### 18.3 `MESSAGE`와 Exception의 역할 구분

| 구분 | MESSAGE | Exception Class |
|---|---|---|
| 주 목적 | 사용자에게 메시지 표시 | 호출자에게 오류 상황 전달 |
| 사용 위치 | Report, Screen, Selection Screen 등 UI 흐름 | Class/Method 내부 오류 전달 |
| 처리 방식 | 메시지 타입에 따라 화면 흐름 영향 | TRY CATCH로 구조적 처리 |
| 재사용성 | UI에 가까움 | 로직 계층에서 재사용 가능 |

실무적으로 Service Class 안에서 바로 `MESSAGE`를 출력하면 재사용성이 떨어질 수 있다.  
Class는 예외를 발생시키고, Report나 UI 계층이 메시지를 표시하는 방식이 더 깔끔할 때가 많다.

## 19. 계층별 예외 처리 감각

초급자가 실무 구조를 이해하기 쉽도록 단순 계층을 생각해보자.

```text
Report / UI Layer
  → Service Class
    → Repository Class / DB Access
```

각 계층의 역할은 다음처럼 나눌 수 있다.

| 계층 | 역할 |
|---|---|
| Repository | DB 조회 실패, 데이터 없음 등을 예외로 전달 |
| Service | 업무 규칙 위반을 예외로 전달하거나 하위 예외를 변환 |
| Report/UI | 예외를 사용자 메시지로 표시하거나 후속 화면 흐름 처리 |

이 구조를 따르면 Class 내부 로직과 사용자 출력 로직이 분리된다.

## 20. ABAP Unit과의 연결

Exception Class는 ABAP Unit 테스트와 잘 연결된다.

예를 들어 “존재하지 않는 사용자 ID를 조회하면 예외가 발생해야 한다”는 테스트를 만들 수 있다.

개념 예시:

```abap
TRY.
    lo_service->get_user( iv_user_id = 'UNKNOWN' ).
    cl_abap_unit_assert=>fail( 'Expected exception was not raised.' ).

  CATCH zcx_gpt_user_not_found.
    cl_abap_unit_assert=>assert_true( abap_true ).
ENDTRY.
```

이번 모듈에서는 ABAP Unit 자체를 깊게 다루지 않는다.  
다만 Exception Class를 사용하면 오류 상황을 테스트 가능한 형태로 만들 수 있다는 점을 기억한다.

## 21. 강사용 설명 포인트

강의할 때는 다음 흐름으로 설명하면 좋다.

```text
1. sy-subrc 방식의 한계 제시
2. OO Method 내부 오류 상황 제시
3. Exception Class가 오류를 객체로 표현한다고 설명
4. RAISING은 Method의 예외 계약이라고 설명
5. TRY CATCH는 호출자의 안전 처리 구간이라고 설명
6. 예외는 일반 분기가 아니라 예외 상황에 사용한다고 강조
```

### 21.1 초급자에게 유용한 비유

Exception Class는 “오류 보고서”와 같다.

```text
일반 메시지:
  지금 오류가 났다고 말만 한다.

Exception 객체:
  어떤 종류의 오류인지,
  어디서 발생했는지,
  호출자가 어떻게 처리할 수 있는지를 구조적으로 전달한다.
```

### 21.2 실습 중 반드시 확인할 것

| 확인 항목 | 이유 |
|---|---|
| Exception Class가 Active 상태인가 | 비활성 객체는 참조 불가 |
| Superclass가 적절한가 | Checked/Unchecked 성격에 영향 |
| Method Signature에 RAISING이 있는가 | 호출자 계약 표시 |
| TRY CATCH가 호출자에 있는가 | 예외 처리 흐름 확인 |
| 정상 입력과 오류 입력을 모두 테스트했는가 | 정상/오류 흐름 분리 이해 |

### 22.2 단답형

#### Q1. `RAISING zcx_gpt_user_not_found`는 어떤 의미인가?

모범 답안:  
해당 Method가 실행 중 `ZCX_GPT_USER_NOT_FOUND` 예외를 발생시킬 수 있음을 Method Signature에 명시하는 것이다. 호출자는 이 예외를 처리하거나 다시 전파해야 한다.

#### Q2. `RAISE EXCEPTION`과 `MESSAGE`의 차이를 설명하시오.

모범 답안:  
`MESSAGE`는 주로 사용자에게 메시지를 표시하는 UI 흐름에 가깝고, `RAISE EXCEPTION`은 Method 내부 오류 상황을 호출자에게 구조적으로 전달하는 예외 처리 흐름이다.

#### Q3. CATCH 순서에서 구체적인 예외를 먼저 두어야 하는 이유는?

모범 답안:  
상위 예외를 먼저 CATCH하면 하위의 구체적인 예외 CATCH가 실행될 수 없거나 의미가 없어질 수 있기 때문이다. 따라서 구체적인 예외를 먼저 처리하고 일반 예외를 마지막에 처리한다.

## 24. 핵심 요약

이번 모듈의 핵심은 다음이다.

```text
Exception Class는 OO ABAP에서 오류 상황을 객체로 표현하는 방식이다.
RAISE EXCEPTION은 현재 정상 흐름을 중단하고 예외를 호출자에게 전달한다.
TRY CATCH는 예외가 발생할 수 있는 코드를 안전하게 감싸고 처리한다.
CX_STATIC_CHECK 기반 예외는 호출자에게 처리 또는 전파를 명확히 요구한다.
예외는 일반 조건 분기가 아니라 비정상 또는 처리 불가 상황을 표현할 때 사용한다.
```
