## 3. Interface란 무엇인가?

### 3.1 쉬운 정의

Interface는 Class가 제공해야 하는 Method의 약속을 정의하는 ABAP Repository Object이다.

예를 들어 여러 종류의 메시지 출력 클래스가 있다고 가정한다.

```text
ZCL_GPT_CONSOLE_LOGGER
ZCL_GPT_MEMORY_LOGGER
ZCL_GPT_TEST_LOGGER
```

세 클래스는 내부 구현은 다를 수 있지만 모두 “메시지를 출력한다”는 공통 기능을 제공할 수 있다.  
이때 공통 약속을 Interface로 정의할 수 있다.

```text
ZIF_GPT_LOGGER
  METHOD write_log
```

그러면 이 Interface를 구현하는 Class는 반드시 `WRITE_LOG` Method를 제공해야 한다.

### 3.2 Interface의 핵심 의미

Interface의 핵심은 다음이다.

| 관점 | 설명 |
|---|---|
| 계약 | 구현 Class가 제공해야 하는 Method Signature를 정의한다. |
| 분리 | 사용하는 쪽은 구체 Class보다 Interface에 의존할 수 있다. |
| 다형성 | 여러 Class를 같은 Interface 타입으로 다룰 수 있다. |
| 확장성 | 새로운 구현 Class를 추가해도 호출 측 코드를 덜 변경할 수 있다. |
| 테스트 용이성 | 실제 구현 대신 테스트용 구현체를 주입할 수 있다. |

## 4. Class와 Interface의 차이

Class와 Interface는 모두 ABAP Objects의 중요한 요소이지만 역할이 다르다.

| 구분 | Class | Interface |
|---|---|---|
| 핵심 역할 | 실제 동작 구현 | 공통 사용 계약 정의 |
| 객체 생성 | 가능 | 직접 객체 생성 불가 |
| Method Body | 가짐 | 일반적으로 구현 Body 없음 |
| Attribute | 인스턴스 상태를 가질 수 있음 | 상태 저장용 객체가 아님 |
| Constructor | 가질 수 있음 | 일반 객체 초기화 구조가 아님 |
| 사용 목적 | 기능 구현 | 구현체 간 공통 규격 |
| 예시 | `ZCL_GPT_CONSOLE_LOGGER` | `ZIF_GPT_LOGGER` |

초급자 관점에서 다음 비유가 유용하다.

```text
Interface = 콘센트 규격
Class = 콘센트 규격에 맞춰 실제로 전기를 공급하는 장치
```

어떤 장치가 내부에서 어떻게 동작하는지는 다를 수 있다.  
하지만 정해진 규격을 지키면 같은 방식으로 사용할 수 있다.

## 5. Interface가 필요한 이유

### 5.1 구체 Class에 직접 의존할 때의 문제

다음과 같은 클래스가 있다고 가정한다.

```abap
DATA(lo_logger) = NEW zcl_gpt_console_logger( ).
lo_logger->write_log( 'Created successfully' ).
```

이 코드는 `ZCL_GPT_CONSOLE_LOGGER`라는 구체 Class에 직접 의존한다.  
처음에는 문제가 없어 보이지만, 나중에 로그 방식을 바꾸고 싶으면 호출 코드도 바뀔 가능성이 크다.

예를 들어 Console 출력 대신 Memory 저장 방식으로 바꾸려면 다음처럼 변경해야 할 수 있다.

```abap
DATA(lo_logger) = NEW zcl_gpt_memory_logger( ).
lo_logger->write_log( 'Created successfully' ).
```

구현 Class가 곳곳에 직접 사용되면 변경 범위가 넓어진다.

### 5.2 Interface에 의존하는 방식

Interface를 사용하면 호출 측은 구체 Class 대신 Interface 타입에 의존할 수 있다.

```abap
DATA lo_logger TYPE REF TO zif_gpt_logger.

lo_logger = NEW zcl_gpt_console_logger( ).
lo_logger->write_log( 'Created successfully' ).
```

나중에 구현체를 바꾸더라도 변수 타입은 그대로 유지할 수 있다.

```abap
lo_logger = NEW zcl_gpt_memory_logger( ).
lo_logger->write_log( 'Created successfully' ).
```

호출 측은 `WRITE_LOG`라는 계약만 알고 있으면 된다.  
실제로 Console에 쓰는지, 메모리에 저장하는지, 테스트 로그로 기록하는지는 구현 Class가 결정한다.

## 6. Interface의 기본 구성

### 6.1 Interface 이름

고객 개발 Interface는 일반적으로 `ZIF_` 또는 `YIF_` Prefix를 사용한다.

교육용 예시는 다음을 사용한다.

```text
ZIF_GPT_LOGGER
```

| Prefix | 의미 |
|---|---|
| Z | 고객 개발 네임스페이스 |
| IF | Interface |
| GPT_LOGGER | 로그 기록 계약 |

좋은 이름은 다음 특징을 가진다.

```text
역할을 나타낸다.
구현 방식이 아니라 계약을 나타낸다.
너무 광범위하지 않다.
```

좋은 예:

```text
ZIF_GPT_LOGGER
ZIF_GPT_PRICING_RULE
ZIF_GPT_VALIDATOR
ZIF_GPT_EXPORTER
```

나쁜 예:

```text
ZIF_UTIL
ZIF_COMMON
ZIF_PROCESS
ZIF_TEST
```

### 6.2 Interface Method

Interface에는 구현 Class가 반드시 제공해야 하는 Method Signature를 정의한다.

예:

```abap
INTERFACE zif_gpt_logger PUBLIC.

  METHODS write_log
    IMPORTING
      iv_message TYPE string.

ENDINTERFACE.
```

이 코드는 다음 약속을 뜻한다.

```text
이 Interface를 구현하는 Class는 WRITE_LOG라는 Instance Method를 제공해야 한다.
WRITE_LOG는 문자열 메시지 IV_MESSAGE를 입력받아야 한다.
```

Interface 자체에는 일반적으로 “어떻게 로그를 쓸 것인가”를 적지 않는다.  
그 구현은 Class가 담당한다.

## 9. Class에서 Interface 구현하기

### 9.1 구현 Class 생성

Interface를 구현할 Class를 만든다.

```text
Class Name: ZCL_GPT_CONSOLE_LOGGER
Description: Console Logger Implementation
```

이 Class는 `ZIF_GPT_LOGGER` Interface를 구현한다.

### 9.2 ADT Class Source 예시

```abap
CLASS zcl_gpt_console_logger DEFINITION
  PUBLIC
  FINAL
  CREATE PUBLIC.

  PUBLIC SECTION.
    INTERFACES zif_gpt_logger.

ENDCLASS.

CLASS zcl_gpt_console_logger IMPLEMENTATION.

  METHOD zif_gpt_logger~write_log.
    WRITE: / iv_message.
  ENDMETHOD.

ENDCLASS.
```

여기서 중요한 문법은 두 가지이다.

| 문법 | 의미 |
|---|---|
| `INTERFACES zif_gpt_logger.` | 이 Class가 해당 Interface를 구현한다는 선언 |
| `METHOD zif_gpt_logger~write_log.` | Interface Method의 실제 구현 |

### 9.3 왜 `~`가 사용되는가?

ABAP에서 Interface Method를 구현할 때는 다음처럼 Interface 이름과 Method 이름을 `~`로 연결한다.

```abap
zif_gpt_logger~write_log
```

이는 “이 Method는 Class 자체의 일반 Method가 아니라, Interface에서 온 Method를 구현한 것”이라는 의미를 명확히 한다.

## 10. Interface Reference Variable

Interface의 강력한 활용은 Reference Variable에서 드러난다.

```abap
DATA lo_logger TYPE REF TO zif_gpt_logger.

lo_logger = NEW zcl_gpt_console_logger( ).
lo_logger->write_log( 'Hello Interface' ).
```

여기서 변수 타입은 `ZIF_GPT_LOGGER`이다.  
하지만 실제 객체는 `ZCL_GPT_CONSOLE_LOGGER`이다.

이 구조가 가능한 이유는 `ZCL_GPT_CONSOLE_LOGGER`가 `ZIF_GPT_LOGGER`를 구현했기 때문이다.

```text
참조 변수 타입: ZIF_GPT_LOGGER
실제 객체 타입: ZCL_GPT_CONSOLE_LOGGER
호출 가능한 Method: Interface에 정의된 Method
```

초급자는 다음 문장을 반드시 기억해야 한다.

```text
Interface Reference는 해당 Interface가 약속한 Method만 안정적으로 호출하게 해준다.
```

## 11. 다형성(Polymorphism)의 기초

### 11.1 다형성이란?

다형성은 같은 호출 코드가 서로 다른 구현체에서 다르게 동작할 수 있는 성질이다.

예를 들어 두 개의 Logger Class가 있다고 하자.

```text
ZCL_GPT_CONSOLE_LOGGER
ZCL_GPT_MEMORY_LOGGER
```

둘 다 `ZIF_GPT_LOGGER`를 구현한다.

```abap
DATA lo_logger TYPE REF TO zif_gpt_logger.

lo_logger = NEW zcl_gpt_console_logger( ).
lo_logger->write_log( 'A' ).

lo_logger = NEW zcl_gpt_memory_logger( ).
lo_logger->write_log( 'B' ).
```

호출 코드는 동일하다.

```abap
lo_logger->write_log( ... )
```

하지만 실제 실행되는 구현은 객체가 어떤 Class인지에 따라 달라진다.

### 11.2 다형성의 실무적 의미

다형성이 중요한 이유는 다음과 같다.

| 효과 | 설명 |
|---|---|
| 구현 교체 용이 | 호출 코드를 크게 바꾸지 않고 구현체를 바꿀 수 있다. |
| 테스트 용이 | 실제 구현 대신 테스트용 구현체를 사용할 수 있다. |
| 확장성 | 새로운 Class를 추가해도 Interface 계약을 지키면 사용 가능하다. |
| 의존성 감소 | 호출 측이 구체 Class의 세부 구현에 덜 의존한다. |

## 12. 전체 실습 예제

이번 실습에서는 다음 세 가지 객체를 만든다.

| 객체 | 역할 |
|---|---|
| `ZIF_GPT_LOGGER` | 로그 기록 Interface |
| `ZCL_GPT_CONSOLE_LOGGER` | WRITE로 메시지를 출력하는 구현 Class |
| `ZCL_GPT_LOGGER_DEMO` 또는 Report | Interface Reference로 호출하는 데모 |

### 12.1 Interface 생성

```abap
INTERFACE zif_gpt_logger
  PUBLIC.

  METHODS write_log
    IMPORTING
      iv_message TYPE string.

ENDINTERFACE.
```

### 12.2 구현 Class 생성

```abap
CLASS zcl_gpt_console_logger DEFINITION
  PUBLIC
  FINAL
  CREATE PUBLIC.

  PUBLIC SECTION.
    INTERFACES zif_gpt_logger.

ENDCLASS.

CLASS zcl_gpt_console_logger IMPLEMENTATION.

  METHOD zif_gpt_logger~write_log.
    WRITE: / |[LOG] { iv_message }|.
  ENDMETHOD.

ENDCLASS.
```

### 12.3 ClassRun 데모 예시

ADT 환경에서는 `IF_OO_ADT_CLASSRUN`을 구현한 Class로 테스트할 수 있다.

```abap
CLASS zcl_gpt_interface_demo DEFINITION
  PUBLIC
  FINAL
  CREATE PUBLIC.

  PUBLIC SECTION.
    INTERFACES if_oo_adt_classrun.

ENDCLASS.

CLASS zcl_gpt_interface_demo IMPLEMENTATION.

  METHOD if_oo_adt_classrun~main.

    DATA lo_logger TYPE REF TO zif_gpt_logger.

    lo_logger = NEW zcl_gpt_console_logger( ).

    lo_logger->write_log( iv_message = 'Interface demo started' ).
    lo_logger->write_log( iv_message = 'Message written by implementation class' ).

    out->write( 'Interface reference call completed.' ).

  ENDMETHOD.

ENDCLASS.
```

위 예제에서 `OUT->WRITE`와 `WRITE` 출력 방식은 실행 환경에 따라 표시 위치가 다를 수 있다.  
ClassRun 중심 실습에서는 `OUT->WRITE`를 주 출력으로 사용하는 것이 좋다.

> [추정] 일부 교육 시스템에서는 Console List Output보다 ADT Console의 `OUT->WRITE` 출력 흐름이 더 명확할 수 있다. 강의 환경에 맞춰 출력 방식을 하나로 통일해도 된다.

## 13. ClassRun에 맞춘 구현 개선

ClassRun 실습에서는 Interface Method 안에서 `WRITE`를 직접 사용하는 대신, 메시지를 문자열로 반환하는 설계도 가능하다.

### 13.1 Interface 변경 예시

```abap
INTERFACE zif_gpt_logger
  PUBLIC.

  METHODS build_log_message
    IMPORTING
      iv_message       TYPE string
    RETURNING
      VALUE(rv_result) TYPE string.

ENDINTERFACE.
```

### 13.2 구현 Class 예시

```abap
CLASS zcl_gpt_console_logger DEFINITION
  PUBLIC
  FINAL
  CREATE PUBLIC.

  PUBLIC SECTION.
    INTERFACES zif_gpt_logger.

ENDCLASS.

CLASS zcl_gpt_console_logger IMPLEMENTATION.

  METHOD zif_gpt_logger~build_log_message.
    rv_result = |[LOG] { iv_message }|.
  ENDMETHOD.

ENDCLASS.
```

### 13.3 실행 Class 예시

```abap
CLASS zcl_gpt_interface_demo DEFINITION
  PUBLIC
  FINAL
  CREATE PUBLIC.

  PUBLIC SECTION.
    INTERFACES if_oo_adt_classrun.

ENDCLASS.

CLASS zcl_gpt_interface_demo IMPLEMENTATION.

  METHOD if_oo_adt_classrun~main.

    DATA lo_logger TYPE REF TO zif_gpt_logger.

    lo_logger = NEW zcl_gpt_console_logger( ).

    out->write(
      lo_logger->build_log_message(
        iv_message = 'Interface with returning value' ) ).

  ENDMETHOD.

ENDCLASS.
```

이 방식은 Interface Method가 출력 장치에 직접 의존하지 않도록 만들어준다.  
초급 단계에서는 `WRITE_LOG` 방식이 직관적이고, 실무 설계 관점에서는 `BUILD_LOG_MESSAGE`처럼 결과를 반환하는 방식이 더 테스트하기 쉬울 수 있다.

## 14. Interface 설계 기준

### 14.1 좋은 Interface의 특징

좋은 Interface는 다음 특징을 가진다.

| 특징 | 설명 |
|---|---|
| 목적이 명확하다 | Interface 이름만 봐도 역할을 추정할 수 있다. |
| Method 수가 과도하지 않다 | 하나의 책임에 집중한다. |
| 구현 세부사항을 강요하지 않는다 | 무엇을 해야 하는지만 정의한다. |
| 호출 측 관점에서 안정적이다 | 자주 바뀌지 않는 계약을 제공한다. |
| 테스트 가능성을 높인다 | Mock 또는 Test Double 구현이 가능하다. |

### 14.2 나쁜 Interface의 예

```abap
INTERFACE zif_gpt_common
  PUBLIC.

  METHODS do_something.
  METHODS process.
  METHODS save.
  METHODS check.
  METHODS display.
  METHODS calculate.
  METHODS send.
  METHODS convert.

ENDINTERFACE.
```

이 Interface는 무엇을 위한 계약인지 알기 어렵다.  
역할이 너무 많고 이름도 추상적이다.

더 나은 방식은 책임별로 분리하는 것이다.

```text
ZIF_GPT_VALIDATOR
ZIF_GPT_LOGGER
ZIF_GPT_PRICING_RULE
ZIF_GPT_EXPORTER
```

### 14.3 Interface를 만들기 전 질문

Interface를 만들기 전에 다음 질문을 던진다.

```text
이 기능을 여러 구현체가 가질 가능성이 있는가?
호출 측이 구체 Class에 직접 의존하지 않아야 하는가?
테스트용 대체 구현이 필요한가?
이 계약이 쉽게 바뀌지 않을 만큼 안정적인가?
Method 이름만 보고 사용 의도를 알 수 있는가?
```

질문에 대부분 “아니오”라면 Interface 없이 Class만으로 충분할 수 있다.

## 15. 자주 발생하는 오류와 해결

### 15.1 Interface Method 구현 누락

#### 현상

Class가 Interface를 선언했지만, Interface Method의 구현이 누락되어 활성화 오류가 발생한다.

#### 원인

```abap
INTERFACES zif_gpt_logger.
```

만 선언하고 아래 구현을 작성하지 않은 경우이다.

```abap
METHOD zif_gpt_logger~write_log.
  ...
ENDMETHOD.
```

#### 해결

Interface에 정의된 모든 Method를 구현한다.

---

### 15.2 Method 이름을 잘못 구현함

#### 잘못된 예

```abap
METHOD write_log.
  WRITE: / iv_message.
ENDMETHOD.
```

Interface Method는 보통 Interface Prefix를 포함해 구현해야 한다.

#### 올바른 예

```abap
METHOD zif_gpt_logger~write_log.
  WRITE: / iv_message.
ENDMETHOD.
```

---

### 15.3 Interface Reference로 Class 전용 Method 호출 시도

#### 상황

```abap
DATA lo_logger TYPE REF TO zif_gpt_logger.

lo_logger = NEW zcl_gpt_console_logger( ).
lo_logger->display_internal_state( ).
```

#### 문제

`DISPLAY_INTERNAL_STATE`가 Interface에 정의되어 있지 않다면 Interface Reference로는 호출할 수 없다.

#### 해결

호출 측이 반드시 알아야 하는 기능이면 Interface에 Method를 정의한다.  
구현 Class 내부 전용 기능이면 Interface Reference로 호출하지 않는다.

---

### 15.4 너무 큰 Interface 설계

#### 현상

Interface에 Method가 너무 많고 여러 책임이 섞인다.

#### 문제

구현 Class가 실제로 필요하지 않은 Method까지 억지로 구현해야 한다.  
이는 유지보수성과 테스트성을 떨어뜨린다.

#### 해결

역할 단위로 Interface를 분리한다.

```text
ZIF_GPT_LOGGER
ZIF_GPT_VALIDATOR
ZIF_GPT_REPOSITORY
```

## 16. 실무 적용 기준

### 16.1 Interface가 특히 유용한 상황

| 상황 | 이유 |
|---|---|
| 같은 기능을 여러 방식으로 구현해야 함 | 다형성 활용 |
| Unit Test에서 실제 구현을 대체해야 함 | 테스트 가능성 향상 |
| 외부 호출자가 구현 Class를 몰라도 되어야 함 | 의존성 감소 |
| 프레임워크가 특정 Method 계약을 요구함 | 표준 계약 구현 |
| Strategy Pattern처럼 동작을 교체해야 함 | 확장성 향상 |

### 16.2 Interface가 과한 상황

| 상황 | 설명 |
|---|---|
| 구현체가 하나뿐이고 확장 가능성도 낮음 | Class 직접 사용이 더 단순할 수 있음 |
| Method가 1회성 유틸리티 수준임 | Static Method 또는 일반 Class로 충분할 수 있음 |
| 계약이 자주 바뀜 | Interface 변경이 구현체 전체에 영향을 줌 |
| 역할이 불명확함 | 추상화가 오히려 이해를 방해함 |

초급자는 “Interface는 좋은 것이므로 항상 만들어야 한다”가 아니라 다음처럼 이해해야 한다.

```text
변경 가능성과 구현 교체 가능성이 있는 안정적 계약에 Interface를 사용한다.
```

## 17. Visibility와 Interface

Interface에 선언된 Method는 구현 Class의 Public 계약으로 노출되는 성격이 강하다.  
따라서 Interface는 외부 사용자가 호출해도 되는 기능만 담는 것이 좋다.

예를 들어 다음 Method는 Interface에 적합할 수 있다.

```text
VALIDATE
CALCULATE_PRICE
WRITE_LOG
EXPORT
```

반면 다음 Method는 구현 내부 보조 기능일 가능성이 높다.

```text
BUILD_TEMP_BUFFER
READ_PRIVATE_FLAG
CONVERT_INTERNAL_FORMAT
```

내부 보조 기능은 Class의 Private Method로 두는 편이 적절하다.

## 18. 강사용 설명 포인트

강의에서는 Interface를 “객체지향의 어려운 추상 개념”으로 시작하기보다, 다음 순서로 설명하면 이해가 쉽다.

```text
1. 여러 Class가 같은 Method 이름을 가져야 하는 상황 제시
2. 호출 측이 구체 Class를 몰라도 되게 하고 싶다는 문제 제기
3. Interface를 공통 계약으로 소개
4. Class가 Interface를 구현하게 함
5. Interface Reference로 호출
6. 실제 객체를 바꾸어도 호출 코드가 같다는 점 확인
```

특히 초급자에게는 다음 질문을 던지는 것이 좋다.

```text
로그를 화면에 출력하는 Class와 파일에 저장하는 Class가 있다면,
호출 프로그램은 두 Class를 모두 자세히 알아야 할까요?
아니면 WRITE_LOG라는 공통 약속만 알면 될까요?
```

이 질문을 통해 Interface의 필요성을 자연스럽게 설명할 수 있다.

## 20. 평가 문제

### 20.1 객관식

#### Q1. Interface의 가장 적절한 설명은?

A. 실제 객체 상태를 저장하는 테이블이다.  
B. Class가 따라야 하는 공통 Method 계약을 정의한다.  
C. Constructor만 모아두는 객체이다.  
D. Database Table을 조회하는 SQL 문이다.

**정답:** B

#### Q2. Interface를 구현하는 Class에서 Interface Method를 구현할 때 일반적으로 사용하는 표기는?

A. `METHOD write_log.`  
B. `METHOD zif_gpt_logger~write_log.`  
C. `FORM write_log.`  
D. `CALL METHOD write_log.`

**정답:** B

#### Q3. Interface Reference Variable의 장점으로 적절한 것은?

A. 구체 Class에 대한 의존성을 줄이고 다형성을 사용할 수 있다.  
B. 모든 Method를 Private으로 숨길 수 있다.  
C. 객체 생성 없이 Instance Attribute를 사용할 수 있다.  
D. Database Table의 Primary Key를 자동 생성한다.

**정답:** A

### 20.2 단답형

#### Q1. Interface와 Class의 차이를 설명하시오.

**모범 답안:**  
Interface는 구현 Class가 제공해야 하는 Method의 계약을 정의한다. Class는 실제 속성과 Method 구현을 가진 객체 생성 가능한 구현체이다.

#### Q2. Interface Reference로 Class 전용 Method를 호출할 수 없는 이유는 무엇인가?

**모범 답안:**  
Interface Reference는 해당 Interface에 정의된 계약만 알고 있기 때문이다. 구체 Class에만 존재하는 Method는 Interface 타입 변수로는 호출할 수 없다.

#### Q3. Interface를 너무 크게 설계하면 어떤 문제가 생기는가?

**모범 답안:**  
구현 Class가 필요하지 않은 Method까지 억지로 구현해야 하며, Interface 변경 시 모든 구현체에 영향이 발생한다. 역할이 불명확해져 유지보수성이 떨어진다.

## 22. 핵심 요약

```text
Interface는 Class가 지켜야 할 공통 사용 계약이다.
Class는 Interface를 구현하여 실제 동작을 제공한다.
Interface Method 구현은 일반적으로 zif_name~method_name 형태로 작성한다.
Interface Reference를 사용하면 구체 Class가 달라도 같은 Method 호출 구조를 유지할 수 있다.
이 구조가 OO ABAP의 다형성 기초이다.
Interface는 변경 가능성과 구현 교체 가능성이 있는 안정적 계약에 사용하는 것이 좋다.
```

## 23. 다음 모듈 연결

다음 모듈은 `THEORY-18-M06 — Exception Class 기초`이다.

Interface는 객체 간 계약을 정의한다.  
Exception Class는 객체지향 방식으로 오류를 표현하고 전달하는 구조이다.

연결 흐름은 다음과 같다.

```text
Interface로 객체가 제공할 기능 계약을 정의한다.
→ 구현 Class에서 실제 동작을 작성한다.
→ 동작 중 오류가 발생하면 Exception Class로 명확히 표현한다.
```

따라서 Interface와 Exception Class는 실무 OO ABAP 설계에서 함께 자주 등장한다.
