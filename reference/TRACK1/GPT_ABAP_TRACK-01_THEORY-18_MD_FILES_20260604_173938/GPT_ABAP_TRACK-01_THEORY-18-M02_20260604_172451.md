## 0. 이 문서의 학습 범위

이 문서는 `THEORY-18-M02 — Attribute / Method / Visibility`만 다룬다.

이번 모듈의 핵심은 **Class 내부에서 데이터와 동작을 어떻게 나누고, 외부에 무엇을 공개하며, 무엇을 감출 것인가**를 이해하는 것이다.

OO ABAP에서 Class는 단순히 코드를 모아두는 상자가 아니다. Class는 상태를 보관하는 **Attribute**, 동작을 수행하는 **Method**, 접근 범위를 제어하는 **Visibility Section**으로 구성된다. 이 세 가지를 이해해야 Constructor, Static/Instance Method, Interface, Exception, Inheritance 같은 후속 OO 개념을 안정적으로 배울 수 있다.

이번 모듈에서는 다음을 깊게 다룬다.

| 주제 | 학습 범위 |
|---|---|
| Attribute | Class 내부의 상태 또는 값을 보관하는 멤버 변수 |
| Method | Class가 수행하는 동작 또는 기능 단위 |
| Visibility | Public / Protected / Private 접근 제어 |
| Encapsulation | 내부 상태를 직접 노출하지 않고 Method를 통해 제어하는 설계 원칙 |
| 실습 | 간단한 Global Class에 Attribute와 Method를 만들고 접근 가능 범위를 확인 |

아직 다음 주제들은 깊게 다루지 않는다.

| 후속 모듈 | 이 문서에서의 처리 수준 |
|---|---|
| Constructor | 객체 초기화가 필요한 이유만 예고 |
| Static / Instance Method | 차이를 간단히 예고하되 구현 심화는 M04로 위임 |
| Interface | Public Method 계약의 확장 개념으로만 예고 |
| Exception Class | Method 오류 처리의 필요성만 언급 |
| Inheritance | Protected Section이 왜 존재하는지 예고 수준으로만 설명 |

## 3. Attribute란 무엇인가?

### 3.1 쉬운 정의

Attribute는 Class 내부에 선언되는 변수이다.  
객체가 보관해야 하는 상태, 기준값, 처리 결과, 설정값 등을 저장한다.

예를 들어 계산기 Class를 만든다고 가정하면, 현재 금액이나 할인율을 Attribute로 둘 수 있다.

```abap
PRIVATE SECTION.
  DATA mv_amount        TYPE p LENGTH 10 DECIMALS 2.
  DATA mv_discount_rate TYPE p LENGTH 5 DECIMALS 2.
```

여기서 `MV_AMOUNT`, `MV_DISCOUNT_RATE`는 Class 내부의 Attribute이다.

### 3.2 Attribute와 일반 변수의 차이

ABAP Report 안에서 선언한 `DATA gv_amount TYPE p DECIMALS 2.`는 해당 프로그램 안에서만 사용하는 변수이다.  
반면 Class Attribute는 Class 또는 Object의 상태로 관리된다.

| 구분 | 일반 변수 | Attribute |
|---|---|---|
| 선언 위치 | Program, Method, FORM 등 | Class Definition 내부 |
| 생명주기 | 선언 위치와 실행 흐름에 따라 다름 | Object 또는 Class 생명주기와 연결 |
| 역할 | 임시 계산, 지역 처리 | 객체 상태, 설정, 누적값 보관 |
| 접근 제어 | 보통 블록 또는 프로그램 범위 | Public / Protected / Private로 제어 |

### 3.3 Attribute Naming Convention

교육용 문서에서는 다음 Prefix를 사용한다.

| Prefix | 의미 | 예시 |
|---|---|---|
| MV_ | Member Variable, Instance Attribute | `mv_amount` |
| MS_ | Member Structure | `ms_header` |
| MT_ | Member Table | `mt_items` |
| GV_ | Global Variable, Report 전역 변수 | `gv_amount` |
| LV_ | Local Variable | `lv_total` |

실무에서는 프로젝트별 규칙을 우선한다. 다만 초급자는 Prefix를 통해 변수의 범위와 성격을 읽는 훈련을 하는 것이 좋다.

## 4. Method란 무엇인가?

### 4.1 쉬운 정의

Method는 Class 내부에 정의되는 기능 단위이다.  
Report에서 FORM이 절차적 재사용 단위였다면, OO ABAP에서는 Method가 Class의 책임을 수행하는 기본 단위이다.

예를 들어 할인 금액을 계산하는 Method는 다음처럼 설계할 수 있다.

```abap
PUBLIC SECTION.
  METHODS calculate_discount
    IMPORTING iv_amount          TYPE p LENGTH 10 DECIMALS 2
              iv_discount_rate   TYPE p LENGTH 5 DECIMALS 2
    RETURNING VALUE(rv_discount) TYPE p LENGTH 10 DECIMALS 2.
```

이 선언은 다음 의미를 가진다.

| 요소 | 의미 |
|---|---|
| `calculate_discount` | Method 이름 |
| `IMPORTING` | Method 호출자가 전달하는 입력값 |
| `RETURNING` | Method가 돌려주는 결과값 |
| `iv_amount` | 입력 금액 |
| `rv_discount` | 계산 결과 |

### 4.2 Method가 필요한 이유

Method는 단순히 코드를 줄이는 도구가 아니다. Method는 Class의 책임을 명확하게 나누는 단위이다.

| 이유 | 설명 |
|---|---|
| 책임 분리 | 한 Method는 한 가지 업무 기능에 집중한다. |
| 재사용 | 같은 기능을 여러 곳에서 호출할 수 있다. |
| 테스트 용이성 | Method 단위로 입력과 결과를 검증하기 쉽다. |
| 캡슐화 | 내부 Attribute를 직접 만지지 않고 Method를 통해 제어한다. |
| 유지보수 | 변경 영향 범위를 Method 단위로 좁힐 수 있다. |

### 4.3 Method Naming Convention

Method 이름은 동사 또는 동사구로 작성하는 것이 좋다.

좋은 예:

```text
calculate_total
get_status_text
set_discount_rate
validate_input
load_flights
```

나쁜 예:

```text
method1
process
run
check
abc
```

`process`, `run`, `check` 같은 이름은 너무 넓다. 무엇을 처리하고 무엇을 확인하는지 드러나지 않는다.

## 5. Attribute와 Method의 관계

Attribute와 Method는 함께 설계해야 한다.

```text
Attribute = 객체가 기억하는 상태
Method    = 그 상태를 읽거나 변경하거나 활용하는 행동
```

예를 들어 주문 금액을 보관하고 할인 금액을 계산하는 Class를 생각해보자.

```abap
CLASS zcl_gpt_price_calculator DEFINITION PUBLIC CREATE PUBLIC.
  PUBLIC SECTION.
    METHODS set_amount
      IMPORTING iv_amount TYPE p LENGTH 10 DECIMALS 2.

    METHODS calculate_discount
      RETURNING VALUE(rv_discount) TYPE p LENGTH 10 DECIMALS 2.

  PRIVATE SECTION.
    DATA mv_amount        TYPE p LENGTH 10 DECIMALS 2.
    DATA mv_discount_rate TYPE p LENGTH 5 DECIMALS 2 VALUE '10.00'.
ENDCLASS.
```

이 구조에서 외부 호출자는 `MV_AMOUNT`를 직접 변경하지 않는다.  
대신 `SET_AMOUNT` Method를 호출하여 값을 넣는다. 이렇게 하면 입력값 검증, 초기값 처리, 오류 메시지 등을 Method 안에 넣을 수 있다.

## 6. Visibility란 무엇인가?

Visibility는 Class의 구성요소가 어디에서 접근 가능한지를 정하는 규칙이다.

ABAP Objects의 대표 Visibility Section은 다음 세 가지이다.

| Section | 접근 범위 | 초급자 이해 |
|---|---|---|
| Public Section | 외부 객체와 프로그램에서 접근 가능 | 외부에 공개하는 인터페이스 |
| Protected Section | 해당 Class와 Subclass에서 접근 가능 | 상속 확장을 위한 내부 공개 영역 |
| Private Section | 해당 Class 내부에서만 접근 가능 | 외부에 감추는 구현 세부사항 |

초급자는 다음 원칙부터 기억한다.

```text
가능하면 Attribute는 Private으로 감춘다.
외부에서 필요한 기능은 Public Method로 제공한다.
Protected는 상속 설계가 필요한 경우에만 신중히 사용한다.
```

## 7. Public Section

Public Section에 선언한 Attribute와 Method는 외부 프로그램 또는 다른 Class에서 접근할 수 있다.

```abap
PUBLIC SECTION.
  METHODS get_status_text
    RETURNING VALUE(rv_text) TYPE string.
```

외부 호출 예시는 다음과 같다.

```abap
DATA(lo_object) = NEW zcl_gpt_demo( ).
DATA(lv_text) = lo_object->get_status_text( ).
```

Public Section은 Class의 외부 계약에 해당한다.  
따라서 Public Method 이름, Parameter, Return Type은 신중히 설계해야 한다.

### 7.1 Public Attribute를 조심해야 하는 이유

Public Attribute는 외부에서 직접 읽고 쓸 수 있기 때문에 통제력이 떨어진다.

```abap
lo_object->mv_status = 'X'.
```

이런 방식은 간단해 보이지만 다음 문제가 있다.

| 문제 | 설명 |
|---|---|
| 검증 불가 | 허용되지 않는 값이 직접 들어올 수 있다. |
| 변경 추적 어려움 | 어느 코드가 값을 바꿨는지 찾기 어렵다. |
| 캡슐화 약화 | Class 내부 규칙이 외부로 새어 나간다. |
| 유지보수 위험 | Attribute 이름 변경 시 외부 호출 코드가 모두 깨진다. |

따라서 실무에서는 Public Attribute보다 Private Attribute + Public Method를 우선 검토한다.

---

## 8. Private Section

Private Section은 해당 Class 내부에서만 접근 가능한 영역이다.

```abap
PRIVATE SECTION.
  DATA mv_status TYPE c LENGTH 1.
```

외부 프로그램에서 다음처럼 접근하면 오류가 발생한다.

```abap
lo_object->mv_status = 'A'. " 접근 불가
```

Private Section은 Class 내부 구현을 감추기 위한 핵심 장치이다.  
외부는 `SET_STATUS`, `GET_STATUS_TEXT` 같은 Public Method만 사용하고, 실제 저장 방식은 Class 내부에서 관리한다.

### 8.1 Private Attribute의 장점

| 장점 | 설명 |
|---|---|
| 데이터 보호 | 외부에서 임의 변경을 막을 수 있다. |
| 검증 집중 | Setter Method에서 입력 검증을 수행할 수 있다. |
| 구현 변경 용이 | 내부 Attribute 구조를 바꿔도 Public Method가 유지되면 외부 영향이 줄어든다. |
| 책임 명확화 | 상태 변경 책임이 Class 내부로 집중된다. |

---

## 9. Protected Section

Protected Section은 현재 Class와 이를 상속받은 Subclass에서 접근 가능한 영역이다.

초급 단계에서는 Protected를 깊게 사용하지 않는다. 다만 후속 모듈인 Inheritance / Redefinition에서 중요해진다.

```abap
PROTECTED SECTION.
  METHODS build_default_text
    RETURNING VALUE(rv_text) TYPE string.
```

Protected는 다음 경우에 검토한다.

| 상황 | 설명 |
|---|---|
| Subclass가 확장해야 하는 내부 로직 | 부모 Class의 일부 기능을 자식 Class가 활용해야 함 |
| Redefinition 대상의 보조 기능 | 자식 Class에서 재사용할 수 있는 내부 Method 제공 |
| Framework 설계 | 상속 기반 확장 지점을 설계할 때 사용 |

초급 실무 원칙은 다음이다.

```text
상속 설계 의도가 없다면 Protected보다 Private을 먼저 고려한다.
```

## 10. Encapsulation: 캡슐화

OO 설계에서 Visibility를 배우는 이유는 캡슐화 때문이다.

캡슐화는 Class 내부 상태와 구현 세부사항을 외부에서 직접 만지지 못하게 하고, 정해진 Method를 통해서만 사용하게 만드는 원칙이다.

### 10.1 나쁜 설계

```abap
PUBLIC SECTION.
  DATA mv_status TYPE c LENGTH 1.
```

외부에서 아무 값이나 넣을 수 있다.

```abap
lo_user->mv_status = '?'.
```

### 10.2 개선된 설계

```abap
PUBLIC SECTION.
  METHODS set_status
    IMPORTING iv_status TYPE c LENGTH 1.

  METHODS get_status_text
    RETURNING VALUE(rv_text) TYPE string.

PRIVATE SECTION.
  DATA mv_status TYPE c LENGTH 1.
```

`SET_STATUS` 안에서 허용 값을 검증할 수 있다.

```abap
METHOD set_status.
  CASE iv_status.
    WHEN 'A' OR 'I' OR 'B'.
      mv_status = iv_status.
    WHEN OTHERS.
      mv_status = 'I'.
  ENDCASE.
ENDMETHOD.
```

이 방식은 상태 변경 규칙을 Class 내부로 모은다.

## 11. Method Parameter 설계

Method는 외부와 데이터를 주고받기 위해 Parameter를 사용한다.

대표 Parameter 방향은 다음과 같다.

| 구분 | 의미 | 예시 |
|---|---|---|
| IMPORTING | 호출자가 Method에 전달하는 입력값 | `iv_user_id` |
| EXPORTING | Method가 호출자에게 전달하는 출력값 | `ev_status` |
| CHANGING | 입력과 출력이 모두 필요한 값 | `ct_items` |
| RETURNING | 하나의 주 결과값 | `rv_text` |

초급 단계에서는 다음 기준을 권장한다.

```text
하나의 주 결과값만 있으면 RETURNING을 우선 사용한다.
여러 결과값이 필요하면 EXPORTING을 사용한다.
입력값을 직접 바꿔야 하는 특별한 경우에만 CHANGING을 사용한다.
```

### 11.1 좋은 Method Signature 예시

```abap
METHODS get_status_text
  IMPORTING iv_status      TYPE c LENGTH 1
  RETURNING VALUE(rv_text) TYPE string.
```

이 Method는 입력 1개와 결과 1개가 명확하다.

### 11.2 모호한 Method Signature 예시

```abap
METHODS process
  CHANGING cs_data TYPE any.
```

문제점:

| 문제 | 설명 |
|---|---|
| 이름이 모호함 | 무엇을 처리하는지 알 수 없다. |
| 타입이 모호함 | `ANY` 사용은 초급 설계에서 피하는 것이 좋다. |
| 변경 범위 불명확 | `CHANGING`은 호출자 데이터가 바뀔 수 있어 주의 필요 |

## 12. 실습: Private Attribute와 Public Method 만들기

### 12.1 실습 목표

Global Class에 Private Attribute를 만들고 Public Method로 값을 설정·조회한다.

### 12.2 생성할 Class

```text
Class Name: ZCL_GPT_USER_STATUS
Description: User Status Demo Class
```

[추정] 앞선 모듈에서 이미 만든 Class가 있다면 같은 Class에 Method를 추가해도 된다. 다만 교육 자료의 독립성을 위해 여기서는 별도 Class 이름을 사용한다.

### 12.3 Class Definition 예시

```abap
CLASS zcl_gpt_user_status DEFINITION
  PUBLIC
  FINAL
  CREATE PUBLIC.

  PUBLIC SECTION.
    METHODS set_status
      IMPORTING iv_status TYPE c LENGTH 1.

    METHODS get_status
      RETURNING VALUE(rv_status) TYPE c LENGTH 1.

    METHODS get_status_text
      RETURNING VALUE(rv_text) TYPE string.

  PRIVATE SECTION.
    DATA mv_status TYPE c LENGTH 1.
ENDCLASS.
```

### 12.4 Class Implementation 예시

```abap
CLASS zcl_gpt_user_status IMPLEMENTATION.

  METHOD set_status.
    CASE iv_status.
      WHEN 'A' OR 'I' OR 'B'.
        mv_status = iv_status.
      WHEN OTHERS.
        mv_status = 'I'.
    ENDCASE.
  ENDMETHOD.

  METHOD get_status.
    rv_status = mv_status.
  ENDMETHOD.

  METHOD get_status_text.
    CASE mv_status.
      WHEN 'A'.
        rv_text = 'Active'.
      WHEN 'I'.
        rv_text = 'Inactive'.
      WHEN 'B'.
        rv_text = 'Blocked'.
      WHEN OTHERS.
        rv_text = 'Unknown'.
    ENDCASE.
  ENDMETHOD.

ENDCLASS.
```

### 12.5 ADT ClassRun 테스트 예시

실행 가능한 테스트용 Class를 별도로 만들거나, `IF_OO_ADT_CLASSRUN`을 구현한 Class에서 다음처럼 확인할 수 있다.

```abap
CLASS zcl_gpt_run_user_status DEFINITION
  PUBLIC
  FINAL
  CREATE PUBLIC.

  PUBLIC SECTION.
    INTERFACES if_oo_adt_classrun.
ENDCLASS.

CLASS zcl_gpt_run_user_status IMPLEMENTATION.

  METHOD if_oo_adt_classrun~main.
    DATA(lo_status) = NEW zcl_gpt_user_status( ).

    lo_status->set_status( 'A' ).

    out->write( |Status: { lo_status->get_status( ) }| ).
    out->write( |Text  : { lo_status->get_status_text( ) }| ).
  ENDMETHOD.

ENDCLASS.
```

예상 출력:

```text
Status: A
Text  : Active
```

## 15. 정상 흐름과 오류 흐름

### 15.1 정상 흐름

```text
Class 생성
→ Private Attribute 선언
→ Public Method 선언
→ Method Parameter 정의
→ Method Implementation 작성
→ Syntax Check
→ Activate
→ 테스트 Class 또는 Report에서 호출
→ 결과 확인
```

### 15.2 오류 흐름 1: Private Attribute를 외부에서 직접 접근

오류 예:

```abap
DATA(lo_status) = NEW zcl_gpt_user_status( ).
lo_status->mv_status = 'A'.
```

원인:

```text
MV_STATUS가 PRIVATE SECTION에 선언되어 외부 접근이 불가능하다.
```

해결:

```abap
lo_status->set_status( 'A' ).
```

### 15.3 오류 흐름 2: Method 선언만 하고 구현하지 않음

증상:

```text
Method implementation missing
```

해결:

```abap
METHOD get_status_text.
  rv_text = 'Active'.
ENDMETHOD.
```

### 15.4 오류 흐름 3: Parameter 이름 불일치

선언:

```abap
METHODS set_status
  IMPORTING iv_status TYPE c LENGTH 1.
```

구현에서 잘못 사용:

```abap
METHOD set_status.
  mv_status = lv_status. " lv_status는 존재하지 않음
ENDMETHOD.
```

해결:

```abap
METHOD set_status.
  mv_status = iv_status.
ENDMETHOD.
```

### 15.5 오류 흐름 4: Public Method가 너무 많은 책임을 가짐

나쁜 예:

```abap
METHODS process_all.
```

문제:

- 상태 설정
- DB 조회
- 검증
- 출력
- 로그 저장

위 기능이 한 Method에 섞일 수 있다.

개선:

```text
set_status
validate_status
get_status_text
save_status_log
```

한 Method는 가능한 한 하나의 책임을 가지도록 설계한다.

## 16. Getter와 Setter

Getter는 Attribute 값을 읽는 Method이고, Setter는 Attribute 값을 변경하는 Method이다.

```abap
METHODS set_status
  IMPORTING iv_status TYPE c LENGTH 1.

METHODS get_status
  RETURNING VALUE(rv_status) TYPE c LENGTH 1.
```

### 16.1 장점

| 장점 | 설명 |
|---|---|
| 검증 가능 | Setter에서 값 검증 가능 |
| 내부 변경 보호 | Attribute 이름이나 구조가 바뀌어도 Public Method 유지 가능 |
| 의미 명확화 | 단순 대입보다 업무 동작을 이름으로 표현 가능 |

### 16.2 남용 위험

모든 Attribute에 무조건 Getter/Setter를 만들면 Class가 단순 데이터 컨테이너가 될 수 있다.

나쁜 방향:

```text
get_field1 / set_field1
get_field2 / set_field2
get_field3 / set_field3
```

더 좋은 방향:

```text
activate_user
block_user
is_active
get_display_text
```

즉, Method는 가능하면 단순 필드 접근보다 업무 행동을 표현하는 것이 좋다.

## 17. 실무 설계 기준

### 17.1 Attribute 설계 기준

| 기준 | 설명 |
|---|---|
| 기본은 Private | 외부 직접 접근을 줄인다. |
| 상태 최소화 | 불필요한 Attribute를 늘리지 않는다. |
| 의미 있는 이름 | `mv_flag`보다 `mv_is_active`가 명확하다. |
| 타입 명확화 | DDIC Type 또는 명확한 ABAP Type을 사용한다. |
| 초기값 고려 | Constructor 또는 Setter에서 초기화 정책을 정한다. |

### 17.2 Method 설계 기준

| 기준 | 설명 |
|---|---|
| 하나의 책임 | 한 Method는 한 가지 목적을 가진다. |
| 이름으로 의도 표현 | `calculate_net_amount`, `validate_status`처럼 작성한다. |
| Signature 단순화 | 불필요한 CHANGING, EXPORTING 남용을 피한다. |
| 예외 처리 고려 | 잘못된 입력을 무시할지, 기본값 처리할지, 예외를 던질지 결정한다. |
| 테스트 가능성 | 입력과 결과가 명확해야 검증하기 쉽다. |

### 17.3 Visibility 설계 기준

| 대상 | 기본 권장 |
|---|---|
| Attribute | Private |
| 외부에서 호출할 기능 | Public Method |
| 내부 보조 기능 | Private Method |
| 상속 확장 기능 | Protected Method |
| 상속 의도 없는 Class | Protected 최소화 |

## 18. Clean ABAP 관점

Clean ABAP 관점에서 Attribute / Method / Visibility 설계는 가독성과 유지보수성에 직접 영향을 준다.

중요한 원칙은 다음이다.

```text
Public 영역은 작게 유지한다.
내부 구현은 Private으로 감춘다.
Method 이름은 의도를 드러낸다.
Method는 짧고 한 가지 일을 하게 만든다.
불필요한 상태를 Attribute로 보관하지 않는다.
```

초급자는 “작동하는 코드”를 먼저 만들 수 있어야 하지만, OO ABAP에서는 작동 여부만큼 구조도 중요하다. RAP, Gateway, ALV Service Class, Application Class를 만들 때 Public Method와 Private 구현 분리는 실무 품질을 좌우한다.

## 20. 평가 문제

### 20.1 객관식

#### Q1. Attribute의 가장 적절한 설명은?

A. Class가 수행하는 동작이다.  
B. Class 내부에 선언되는 상태 또는 값이다.  
C. 프로그램 실행을 시작하는 이벤트이다.  
D. Transport Request의 한 종류이다.

정답: B

#### Q2. Private Section의 의미로 올바른 것은?

A. 모든 프로그램에서 직접 접근 가능하다.  
B. 해당 Class 내부에서만 접근 가능하다.  
C. SAP 표준 Class에서만 사용 가능하다.  
D. 데이터베이스 테이블에만 적용된다.

정답: B

#### Q3. Public Attribute를 남발하면 안 되는 이유는?

A. ABAP에서는 Public Attribute가 문법적으로 금지되어 있기 때문이다.  
B. 외부에서 임의로 값을 변경할 수 있어 검증과 캡슐화가 약해지기 때문이다.  
C. Public Attribute는 항상 성능이 느리기 때문이다.  
D. Public Attribute는 Transport가 불가능하기 때문이다.

정답: B

### 20.2 서술형

#### Q1. Attribute와 Method의 차이를 설명하시오.

모범 답안:  
Attribute는 Class 내부의 상태나 값을 보관하는 멤버 변수이고, Method는 그 상태를 읽거나 변경하거나 업무 동작을 수행하는 기능 단위이다.

#### Q2. Public Method와 Private Attribute를 함께 사용하는 이유를 설명하시오.

모범 답안:  
외부에서 Attribute를 직접 변경하지 못하게 하고, Public Method를 통해 검증과 처리 규칙을 적용하기 위해서이다. 이를 통해 캡슐화와 유지보수성이 좋아진다.

#### Q3. Protected Section은 언제 검토하는가?

모범 답안:  
상속 구조에서 Subclass가 부모 Class의 일부 기능이나 상태에 접근해야 할 때 검토한다. 상속 설계 의도가 없다면 Private을 우선 사용하는 것이 일반적으로 안전하다.

## 22. 핵심 요약

```text
Attribute는 Class가 기억하는 값이다.
Method는 Class가 수행하는 행동이다.
Visibility는 Attribute와 Method의 접근 범위를 정한다.
Public은 외부 계약, Private은 내부 구현, Protected는 상속 확장 영역이다.
실무에서는 Attribute를 Private으로 두고 Public Method를 통해 제어하는 설계를 우선 검토한다.
Method 이름과 Parameter는 Class의 책임을 드러내야 한다.
```
