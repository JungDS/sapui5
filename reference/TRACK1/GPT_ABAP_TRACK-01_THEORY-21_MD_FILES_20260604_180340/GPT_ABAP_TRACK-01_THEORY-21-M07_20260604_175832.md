## 3. 전체 구조에서의 위치

RAP Business Object의 단순 구조는 다음과 같다.

```text
Database Table
   ↓
Interface View Entity  ZI_*
   ↓
Projection View Entity ZC_*
   ↓
Behavior Definition
   ↓
Behavior Implementation
   ↓
Service Definition
   ↓
Service Binding
   ↓
Fiori Elements / OData V4 Consumer
```

Validation, Determination, Action은 Behavior Definition과 Behavior Implementation 사이에 위치한다.

```text
Behavior Definition
  - validation 선언
  - determination 선언
  - action 선언

Behavior Implementation Class
  - validation 메서드 구현
  - determination 메서드 구현
  - action 메서드 구현
```

즉, BDEF는 “어떤 동작이 있는가”를 선언하고, Behavior Implementation Class는 “그 동작이 실제로 무엇을 하는가”를 구현한다.

## 4. Validation, Determination, Action 한눈에 비교

| 구분 | Validation | Determination | Action |
|---|---|---|---|
| 핵심 목적 | 입력값 검증 | 파생값/기본값 자동 계산 | 명시적 업무 동작 실행 |
| 대표 예 | 종료일이 시작일보다 빠르면 오류 | 생성 시 상태값을 `N`으로 자동 설정 | 승인, 반려, 복사 |
| 호출 방식 | RAP Framework가 저장/수정 흐름에서 호출 | RAP Framework가 생성/수정 흐름에서 호출 | 사용자가 버튼/API로 호출 |
| 데이터 변경 | 일반적으로 오류 보고 중심 | 값 변경 가능 | 값 변경 또는 결과 반환 가능 |
| 메시지 | `reported`에 메시지 추가 | 필요 시 `reported` 가능 | 성공/오류 메시지 가능 |
| 실패 처리 | `failed`에 실패 Key 추가 | 실패보다는 값 보정이 중심 | 실패/성공 모두 가능 |
| UI 노출 | 보통 버튼으로 노출되지 않음 | 보통 버튼으로 노출되지 않음 | 버튼으로 노출 가능 |
| 초급 이해 | “저장하면 안 되는 값 차단” | “자동으로 채울 값 계산” | “사용자가 누르는 업무 버튼” |

이 표는 초급자가 반드시 암기해야 할 핵심 구분이다.

## 5. Validation

## 5.1 Validation의 목적

Validation은 RAP Business Object의 비즈니스 규칙을 검사하는 동작이다.  
잘못된 데이터가 저장되거나 처리되지 않도록 막는 역할을 한다.

예를 들어 출장 신청 BO가 있다고 가정하자.

| 필드 | 의미 |
|---|---|
| TravelId | 출장 ID |
| BeginDate | 시작일 |
| EndDate | 종료일 |
| Status | 상태 |
| TotalAmount | 총 금액 |

이때 다음 규칙이 있을 수 있다.

```text
종료일은 시작일보다 빠를 수 없다.
상태값은 허용된 값만 사용할 수 있다.
금액은 음수가 될 수 없다.
승인 완료 상태에서는 일부 필드를 수정할 수 없다.
```

이런 규칙을 RAP에서는 Validation으로 구현할 수 있다.

---

## 5.2 Validation의 실행 시점

Validation은 Behavior Definition에서 선언한 Trigger에 따라 실행된다.

대표적인 선언 형태는 다음과 같다.

```abap
validation validate_dates on save { create; update; field BeginDate, EndDate; }
```

이 선언을 초급자용으로 해석하면 다음과 같다.

```text
validate_dates라는 Validation은 저장 시점(on save)에 실행된다.
Create와 Update 상황에서 실행된다.
BeginDate 또는 EndDate 필드와 관련된 검증이다.
```

Validation은 보통 `on save` 시점에 많이 사용한다.  
이유는 저장 직전에 최종 상태를 확인하고, 문제가 있으면 저장을 막는 것이 자연스럽기 때문이다.

---

## 5.3 Validation에서 하지 말아야 할 일

Validation은 “검증”을 위한 동작이다.  
따라서 초급 과정에서는 다음 원칙을 지키는 것이 좋다.

| 피해야 할 일 | 이유 |
|---|---|
| Validation 안에서 값을 무리하게 변경 | Validation의 목적은 값 보정보다 오류 판단이다. |
| 순서에 의존한 복잡한 로직 작성 | RAP Framework의 실행 순서를 과도하게 가정하면 유지보수가 어려워진다. |
| 외부 시스템을 무조건 호출 | 저장 성능과 안정성 문제가 생길 수 있다. |
| 모든 업무 로직을 Validation에 몰아넣기 | Action, Determination, Authorization과 역할 분리가 무너진다. |

초급자는 다음 원칙을 기억한다.

```text
Validation은 데이터를 바꾸는 곳이 아니라, 저장 가능 여부를 판단하는 곳이다.
```

## 6. Determination

## 6.1 Determination의 목적

Determination은 RAP Business Object의 값을 자동으로 결정하는 동작이다.

대표적인 예는 다음과 같다.

| 상황 | Determination 예 |
|---|---|
| 새 Travel 생성 | 상태값을 `N`으로 자동 설정 |
| 시작일/종료일 변경 | 기간 일수를 자동 계산 |
| 금액 변경 | 총액 또는 세액 자동 계산 |
| 생성자 기록 | 생성 사용자 또는 생성일 자동 설정 |
| 코드 입력 | 설명 텍스트 또는 파생 코드 자동 설정 |

Determination은 초급자가 “자동 입력” 또는 “자동 계산”으로 이해하면 쉽다.

---

## 6.2 Determination의 실행 시점

Determination은 보통 `on modify` 또는 `on save` 시점에 선언한다.

예:

```abap
determination set_initial_status on modify { create; }
determination calculate_days on modify { create; update; field BeginDate, EndDate; }
```

해석은 다음과 같다.

```text
set_initial_status는 생성 시점에 기본 상태값을 채운다.
calculate_days는 BeginDate나 EndDate가 변경될 때 기간을 계산한다.
```

초급자는 다음 기준으로 이해하면 된다.

| 시점 | 사용 감각 |
|---|---|
| on modify | 사용자가 필드를 바꿀 때 바로 파생값을 계산하는 느낌 |
| on save | 저장 직전에 최종 값을 보정하는 느낌 |

실제 사용 시점은 BO 설계, Draft 여부, UI 반응성, 데이터 정합성 요구에 따라 달라질 수 있다.

---

## 6.3 Determination에서 주의할 점

Determination은 값 변경을 수행할 수 있으므로 Validation보다 더 신중해야 한다.

| 주의점 | 설명 |
|---|---|
| 멱등성 | 같은 Determination이 여러 번 실행되어도 결과가 안정적이어야 한다. |
| 과도한 변경 금지 | 사용자가 입력한 값을 예상치 못하게 덮어쓰지 않아야 한다. |
| Trigger 명확화 | 어떤 필드 변경에 반응하는지 BDEF에 명확히 선언한다. |
| 성능 고려 | 대량 데이터에 대해 불필요한 Read/Modify를 반복하지 않는다. |
| 메시지 처리 | 자동 보정이 실패하면 reported/failed 흐름을 고려한다. |

중요한 실무 감각은 다음이다.

```text
Determination은 편리하지만, 사용자가 모르게 값을 바꾸므로 설계 의도가 명확해야 한다.
```

## 7. Action

## 7.1 Action의 목적

Action은 사용자가 명시적으로 실행하는 비즈니스 동작이다.  
Fiori Elements에서는 Action이 버튼으로 노출될 수 있다.

대표적인 Action 예는 다음과 같다.

| Action | 의미 |
|---|---|
| approve | 승인 |
| reject | 반려 |
| cancel | 취소 |
| submit | 제출 |
| copy | 복사 |
| recalculate | 재계산 |
| close | 마감 |
| reopen | 재오픈 |

CRUD는 기본적인 생성/조회/수정/삭제이다.  
Action은 그보다 더 업무적인 의미를 가진다.

예를 들어 `Status = 'A'`로 직접 수정하는 것과 `Approve` 버튼을 누르는 것은 다르다.

```text
단순 필드 수정: Status 값을 A로 바꿈
Action: 승인 권한, 현재 상태, 필수값, 메시지, 이력 등을 포함한 업무 처리
```

---

## 7.2 Action의 종류

초급 단계에서는 다음 구분만 이해하면 충분하다.

| 구분 | 의미 |
|---|---|
| Instance Action | 특정 Entity 인스턴스 한 건 또는 여러 건에 대해 실행 |
| Static Action | 특정 인스턴스 없이 Entity 수준에서 실행 |
| Action with Parameter | Action 실행 시 추가 입력값을 받음 |
| Action with Result | 실행 후 결과 Entity 또는 값을 반환 |

예를 들어 특정 Travel 한 건을 승인하는 것은 Instance Action이다.

```abap
action approve result [1] $self;
```

반려 사유를 입력받는 Action은 Parameter가 필요할 수 있다.

```abap
action reject parameter ZS_JHY_REJECT_REASON result [1] $self;
```

## 9. Interface View 예시: ZI_*

RAP 예제를 만들 때는 항상 Interface View와 Projection View를 분리하는 습관이 중요하다.  
Interface View는 BO의 내부 모델에 가까운 계층이다.

```abap
@EndUserText.label: 'Travel Interface View'
@AccessControl.authorizationCheck: #CHECK
define root view entity ZI_JHY_Travel
  as select from ztjhy_travel
{
  key travel_uuid             as TravelUUID,
      travel_id               as TravelId,
      agency_id               as AgencyId,
      customer_id             as CustomerId,
      begin_date              as BeginDate,
      end_date                as EndDate,
      duration_days           as DurationDays,
      status                  as Status,
      total_price             as TotalPrice,
      currency_code           as CurrencyCode,
      created_by              as CreatedBy,
      created_at              as CreatedAt,
      last_changed_by         as LastChangedBy,
      last_changed_at         as LastChangedAt,
      local_last_changed_at   as LocalLastChangedAt
}
```

초급자는 이 예제에서 다음을 확인한다.

| 요소 | 의미 |
|---|---|
| `define root view entity` | RAP Root Entity 정의 |
| `key travel_uuid` | BO 인스턴스의 기술 Key |
| `as TravelUUID` | CDS Element 이름 |
| `LocalLastChangedAt` | ETag 또는 변경 추적에 사용 가능 |
| `@AccessControl.authorizationCheck: #CHECK` | 권한 제어를 고려하는 표준 흐름 |

## 10. Projection View 예시: ZC_*

Projection View는 외부 노출 계층에 가깝다.  
Fiori Elements 또는 OData Service에 노출할 필드를 선별하고 UI Annotation을 추가할 수 있다.

```abap
@EndUserText.label: 'Travel Projection View'

@Metadata.allowExtensions: true
define root view entity ZC_JHY_Travel
  as projection on ZI_JHY_Travel
{

      CustomerId,

      DurationDays,
      Status,
      TotalPrice,
      CurrencyCode,
      CreatedBy,
      CreatedAt,
      LastChangedBy,
      LastChangedAt,
      LocalLastChangedAt
```

Projection View를 별도로 두는 이유는 다음과 같다.

| 이유 | 설명 |
|---|---|
| 내부 모델과 외부 노출 모델 분리 | Interface View 변경이 외부 API에 직접 노출되지 않도록 조절 |
| UI Annotation 분리 | Metadata Extension으로 UI 표현을 관리하기 쉬움 |
| 서비스 안정성 | 외부 소비자에게 필요한 필드만 노출 가능 |
| RAP 표준 흐름 | Interface Behavior와 Projection Behavior 분리 가능 |

## 11. Interface Behavior Definition 예시

다음은 Validation, Determination, Action을 선언한 Interface Behavior Definition 예시이다.

```abap
managed implementation in class ZBP_I_JHY_Travel unique;
strict ( 2 );

define behavior for ZI_JHY_Travel alias Travel
persistent table ztjhy_travel
lock master
authorization master ( instance )
etag master LocalLastChangedAt
{
  create;
  update;
  delete;

  field ( readonly ) TravelUUID;
  field ( readonly ) CreatedBy, CreatedAt, LastChangedBy, LastChangedAt, LocalLastChangedAt;
  field ( readonly ) DurationDays;

  validation validate_dates on save
  { create; update; field BeginDate, EndDate; }

  validation validate_status on save
  { create; update; field Status; }

  determination set_initial_status on modify
  { create; }

  determination calculate_duration on modify
  { create; update; field BeginDate, EndDate; }

  action approve result [1] $self;
  action reject parameter ZS_JHY_RejectReason result [1] $self;

  mapping for ztjhy_travel
  {
    TravelUUID          = travel_uuid;
    TravelId            = travel_id;
    AgencyId            = agency_id;
    CustomerId          = customer_id;
    BeginDate           = begin_date;
    EndDate             = end_date;
    DurationDays        = duration_days;
    Status              = status;
    TotalPrice          = total_price;
    CurrencyCode        = currency_code;
    CreatedBy           = created_by;
    CreatedAt           = created_at;
    LastChangedBy       = last_changed_by;
    LastChangedAt       = last_changed_at;
    LocalLastChangedAt  = local_last_changed_at;
  }
}
```

### 11.1 BDEF에서 확인할 포인트

| 선언 | 의미 |
|---|---|
| `managed implementation` | Managed Scenario 기준 구현 |
| `strict ( 2 )` | 엄격한 RAP 문법/계약 준수 |
| `validation ... on save` | 저장 시점 검증 |
| `determination ... on modify` | 생성/수정 시점 자동 값 결정 |
| `action approve` | 명시적 승인 동작 |
| `result [1] $self` | Action 후 자기 자신 Entity 결과 반환 |
| `mapping` | CDS Element와 DB Table Column 연결 |

## 12. Projection Behavior Definition 예시

Projection Behavior에서는 Interface Behavior에서 정의한 동작을 외부 소비 계층에 노출할지 결정한다.

```abap
projection;
strict ( 2 );

define behavior for ZC_JHY_Travel alias Travel
{
  use create;
  use update;
  use delete;

  use action approve;
  use action reject;
}
```

이 예제에서 `approve`, `reject`를 `use action`으로 노출했기 때문에, Service Binding과 UI Annotation이 적절하면 Fiori Elements 화면에서 버튼으로 보일 수 있다.

```text

Projection BDEF에서 use action을 하지 않으면
외부 서비스 계층에서 보이지 않을 수 있다.
```

## 13. Behavior Implementation Class 구조

Behavior Implementation Class에는 BDEF에서 선언한 Validation, Determination, Action 메서드가 구현된다.

예시 구조는 다음과 같다.

```abap
CLASS lhc_Travel DEFINITION INHERITING FROM cl_abap_behavior_handler.
  PRIVATE SECTION.

    METHODS validate_dates FOR VALIDATE ON SAVE
      IMPORTING keys FOR Travel~validate_dates.

    METHODS validate_status FOR VALIDATE ON SAVE
      IMPORTING keys FOR Travel~validate_status.

    METHODS set_initial_status FOR DETERMINE ON MODIFY
      IMPORTING keys FOR Travel~set_initial_status.

    METHODS calculate_duration FOR DETERMINE ON MODIFY
      IMPORTING keys FOR Travel~calculate_duration.

    METHODS approve FOR MODIFY
      IMPORTING keys FOR ACTION Travel~approve RESULT result.

    METHODS reject FOR MODIFY
      IMPORTING keys FOR ACTION Travel~reject RESULT result.

ENDCLASS.
```

이 구조에서 중요한 점은 메서드 이름과 BDEF 선언이 연결된다는 점이다.  
ADT의 Quick Fix 또는 Behavior Implementation 생성 기능을 사용하면 메서드 스텁을 자동으로 만들 수 있다.

## 14. Validation 구현 예시: 날짜 검증

다음 예제는 종료일이 시작일보다 빠른 경우 저장을 막는 Validation이다.

```abap
METHOD validate_dates.

  READ ENTITIES OF ZI_JHY_Travel IN LOCAL MODE
    ENTITY Travel
      FIELDS ( BeginDate EndDate )
      WITH CORRESPONDING #( keys )
    RESULT DATA(lt_travel).

  LOOP AT lt_travel INTO DATA(ls_travel).

    IF ls_travel-BeginDate IS NOT INITIAL
       AND ls_travel-EndDate IS NOT INITIAL
       AND ls_travel-EndDate < ls_travel-BeginDate.

      APPEND VALUE #( %tky = ls_travel-%tky ) TO failed-Travel.

      APPEND VALUE #(
        %tky = ls_travel-%tky
        %msg = new_message_with_text(
                 severity = if_abap_behv_message=>severity-error
                 text     = '종료일은 시작일보다 빠를 수 없습니다.' )
        %element-BeginDate = if_abap_behv=>mk-on
        %element-EndDate   = if_abap_behv=>mk-on
      ) TO reported-Travel.

    ENDIF.

  ENDLOOP.

ENDMETHOD.
```

### 14.1 코드 해설

| 코드 | 설명 |
|---|---|
| `READ ENTITIES ... IN LOCAL MODE` | 현재 RAP Transaction Buffer 기준으로 Entity 값을 읽는다. |
| `WITH CORRESPONDING #( keys )` | Validation 대상 Key에 해당하는 데이터를 읽는다. |
| `failed-Travel` | 실패한 Entity를 Framework에 알려 저장을 막는다. |
| `reported-Travel` | 사용자에게 표시할 메시지를 전달한다. |
| `%element-BeginDate` | 메시지와 관련된 필드를 UI에 표시할 수 있게 한다. |

초급자가 가장 중요하게 이해해야 할 부분은 `failed`와 `reported`이다.

```text
failed  = 이 인스턴스는 처리 실패이다.
reported = 사용자에게 보여줄 메시지이다.
```

## 15. Validation 구현 예시: 상태값 검증

상태값이 허용 범위를 벗어나면 오류를 발생시키는 Validation이다.

```abap
METHOD validate_status.

  READ ENTITIES OF ZI_JHY_Travel IN LOCAL MODE
    ENTITY Travel
      FIELDS ( Status )
      WITH CORRESPONDING #( keys )
    RESULT DATA(lt_travel).

  LOOP AT lt_travel INTO DATA(ls_travel).

    IF ls_travel-Status <> 'N'
       AND ls_travel-Status <> 'A'
       AND ls_travel-Status <> 'R'.

      APPEND VALUE #( %tky = ls_travel-%tky ) TO failed-Travel.

      APPEND VALUE #(
        %tky = ls_travel-%tky
        %msg = new_message_with_text(
                 severity = if_abap_behv_message=>severity-error
                 text     = '허용되지 않는 상태값입니다. N, A, R만 사용할 수 있습니다.' )
        %element-Status = if_abap_behv=>mk-on
      ) TO reported-Travel.

    ENDIF.

  ENDLOOP.

ENDMETHOD.
```

실무적으로는 상태값이 Domain Fixed Value, Check Table, CDS Value Help, Configuration Table 등과 연결될 수 있다.  
하지만 이번 모듈의 핵심은 “Validation이 잘못된 상태값을 막는 역할”이라는 점이다.

## 16. Determination 구현 예시: 초기 상태 설정

신규 Travel을 생성할 때 기본 상태를 `N`으로 설정하는 예제이다.

```abap
METHOD set_initial_status.

  READ ENTITIES OF ZI_JHY_Travel IN LOCAL MODE
    ENTITY Travel
      FIELDS ( Status )
      WITH CORRESPONDING #( keys )
    RESULT DATA(lt_travel).

  DATA lt_update TYPE TABLE FOR UPDATE ZI_JHY_Travel.

  LOOP AT lt_travel INTO DATA(ls_travel).

    IF ls_travel-Status IS INITIAL.
      APPEND VALUE #(
        %tky   = ls_travel-%tky
        Status = 'N'
      ) TO lt_update.
    ENDIF.

  ENDLOOP.

  IF lt_update IS NOT INITIAL.
    MODIFY ENTITIES OF ZI_JHY_Travel IN LOCAL MODE
      ENTITY Travel
        UPDATE FIELDS ( Status )
        WITH lt_update
      REPORTED DATA(lt_reported).

    reported = CORRESPONDING #( DEEP lt_reported ).
  ENDIF.

ENDMETHOD.
```

### 16.1 코드 해설

| 코드 | 설명 |
|---|---|
| `FIELDS ( Status )` | 상태 필드만 읽어 불필요한 데이터 로드를 줄인다. |
| `IF ls_travel-Status IS INITIAL` | 사용자가 이미 값을 넣었다면 덮어쓰지 않는다. |
| `MODIFY ENTITIES ... IN LOCAL MODE` | RAP Transaction Buffer 안에서 값을 갱신한다. |
| `reported = CORRESPONDING #( DEEP lt_reported )` | 하위 MODIFY에서 발생한 Reported 메시지를 상위로 전달한다. |

중요한 설계 포인트는 다음이다.

```text
Determination은 사용자가 입력한 값을 무조건 덮어쓰지 않도록 조심해야 한다.
```

## 17. Determination 구현 예시: 기간 계산

시작일과 종료일을 기준으로 기간 일수를 계산하는 Determination이다.

```abap
METHOD calculate_duration.

  READ ENTITIES OF ZI_JHY_Travel IN LOCAL MODE
    ENTITY Travel
      FIELDS ( BeginDate EndDate DurationDays )
      WITH CORRESPONDING #( keys )
    RESULT DATA(lt_travel).

  DATA lt_update TYPE TABLE FOR UPDATE ZI_JHY_Travel.

  LOOP AT lt_travel INTO DATA(ls_travel).

    IF ls_travel-BeginDate IS NOT INITIAL
       AND ls_travel-EndDate IS NOT INITIAL
       AND ls_travel-EndDate >= ls_travel-BeginDate.

      DATA(lv_days) = ls_travel-EndDate - ls_travel-BeginDate + 1.

      IF ls_travel-DurationDays <> lv_days.
        APPEND VALUE #(
          %tky         = ls_travel-%tky
          DurationDays = lv_days
        ) TO lt_update.
      ENDIF.

    ENDIF.

  ENDLOOP.

  IF lt_update IS NOT INITIAL.
    MODIFY ENTITIES OF ZI_JHY_Travel IN LOCAL MODE
      ENTITY Travel
        UPDATE FIELDS ( DurationDays )
        WITH lt_update
      REPORTED DATA(lt_reported).

    reported = CORRESPONDING #( DEEP lt_reported ).
  ENDIF.

ENDMETHOD.
```

### 17.1 Determination 설계 포인트

이 예제는 다음 원칙을 보여준다.

| 원칙 | 적용 |
|---|---|
| 필요한 필드만 읽기 | `FIELDS ( BeginDate EndDate DurationDays )` |
| 조건이 맞을 때만 계산 | 날짜가 모두 있고 종료일이 시작일 이상일 때 |
| 값이 다를 때만 Update | 불필요한 Modify 방지 |
| Validation과 역할 분리 | 잘못된 날짜 오류는 `validate_dates`가 담당 |

날짜가 잘못된 경우 `calculate_duration`에서 오류를 내기보다 `validate_dates`에서 막는 방식이 역할 분리에 더 명확하다.

## 18. Action 구현 예시: 승인

Travel을 승인 상태로 바꾸는 Action 예제이다.

```abap
METHOD approve.

  READ ENTITIES OF ZI_JHY_Travel IN LOCAL MODE
    ENTITY Travel
      FIELDS ( Status )
      WITH CORRESPONDING #( keys )
    RESULT DATA(lt_travel).

  DATA lt_update TYPE TABLE FOR UPDATE ZI_JHY_Travel.

  LOOP AT lt_travel INTO DATA(ls_travel).

    IF ls_travel-Status = 'A'.
      APPEND VALUE #(
        %tky = ls_travel-%tky
        %msg = new_message_with_text(
                 severity = if_abap_behv_message=>severity-warning
                 text     = '이미 승인된 Travel입니다.' )
      ) TO reported-Travel.
      CONTINUE.
    ENDIF.

    APPEND VALUE #(
      %tky   = ls_travel-%tky
      Status = 'A'
    ) TO lt_update.

  ENDLOOP.

  IF lt_update IS NOT INITIAL.
    MODIFY ENTITIES OF ZI_JHY_Travel IN LOCAL MODE
      ENTITY Travel
        UPDATE FIELDS ( Status )
        WITH lt_update
      FAILED DATA(lt_failed)
      REPORTED DATA(lt_reported).

    failed   = CORRESPONDING #( DEEP lt_failed ).
    reported = CORRESPONDING #( DEEP lt_reported ).
  ENDIF.

  READ ENTITIES OF ZI_JHY_Travel IN LOCAL MODE
    ENTITY Travel
      ALL FIELDS WITH CORRESPONDING #( keys )
    RESULT DATA(lt_result).

  result = VALUE #(
    FOR ls_result IN lt_result
    ( %tky   = ls_result-%tky
      %param = ls_result )
  ).

ENDMETHOD.
```

### 18.1 Action 해설

| 코드 | 설명 |
|---|---|
| `FOR ACTION Travel~approve` | BDEF의 Action과 연결 |
| `Status = 'A'` | 승인 상태로 변경 |
| `result [1] $self` | 변경된 자기 자신 Entity를 결과로 반환 |
| `reported-Travel` | 이미 승인된 경우 경고 메시지 |
| `FAILED DATA(...)` | 하위 Modify 실패를 수집 |

Action은 사용자가 버튼으로 실행할 수 있으므로, 성공/실패 메시지의 품질이 중요하다.

## 19. Action 구현 예시: 반려

반려 Action은 반려 사유를 받을 수 있다.  
BDEF에서 다음처럼 Parameter Structure를 지정했다고 가정한다.

```abap
action reject parameter ZS_JHY_RejectReason result [1] $self;
```

Parameter Structure 예시는 다음과 같다.

```text
ZS_JHY_RejectReason
  - ReasonCode
  - ReasonText
```

Action 구현의 기본 흐름은 다음과 같다.

```abap
METHOD reject.

  DATA lt_update TYPE TABLE FOR UPDATE ZI_JHY_Travel.

  LOOP AT keys INTO DATA(ls_key).

    IF ls_key-%param-ReasonText IS INITIAL.

      APPEND VALUE #( %tky = ls_key-%tky ) TO failed-Travel.

      APPEND VALUE #(
        %tky = ls_key-%tky
        %msg = new_message_with_text(
                 severity = if_abap_behv_message=>severity-error
                 text     = '반려 사유를 입력해야 합니다.' )
      ) TO reported-Travel.

      CONTINUE.

    ENDIF.

    APPEND VALUE #(
      %tky   = ls_key-%tky
      Status = 'R'
    ) TO lt_update.

  ENDLOOP.

  IF lt_update IS NOT INITIAL.
    MODIFY ENTITIES OF ZI_JHY_Travel IN LOCAL MODE
      ENTITY Travel
        UPDATE FIELDS ( Status )
        WITH lt_update
      FAILED DATA(lt_failed)
      REPORTED DATA(lt_reported).

    failed   = CORRESPONDING #( DEEP lt_failed ).
    reported = CORRESPONDING #( DEEP lt_reported ).
  ENDIF.

  READ ENTITIES OF ZI_JHY_Travel IN LOCAL MODE
    ENTITY Travel
      ALL FIELDS WITH CORRESPONDING #( keys )
    RESULT DATA(lt_result).

  result = VALUE #(
    FOR ls_result IN lt_result
    ( %tky   = ls_result-%tky
      %param = ls_result )
  ).

ENDMETHOD.
```

### 19.1 반려 Action에서 배울 점

| 포인트 | 설명 |
|---|---|
| Action Parameter | 사용자의 추가 입력값을 받을 수 있다. |
| Parameter 검증 | Action 내부에서도 입력값 검증이 필요할 수 있다. |
| `failed` 처리 | 반려 사유가 없으면 해당 Entity 처리 실패 |
| 결과 반환 | 처리 후 변경된 Entity를 UI에 돌려줄 수 있다. |

## 20. Fiori Elements에서의 확인 흐름

Service Binding까지 만들어져 있다면 Fiori Elements Preview에서 Action 버튼을 확인할 수 있다.

기본 흐름은 다음과 같다.

```text
1. ADT에서 Service Binding 열기
2. Publish 상태 확인
3. Entity Set 선택
4. Preview 실행
5. Object Page 또는 List Report에서 Action 버튼 확인
6. Approve 또는 Reject 실행
7. 메시지와 상태값 변경 확인
```

Action 버튼이 보이지 않는 경우 다음을 확인한다.

| 확인 항목 | 설명 |
|---|---|
| Interface BDEF | Action이 선언되어 있는가 |
| Projection BDEF | `use action`으로 노출했는가 |
| Service Binding | 최신 상태로 Publish 되었는가 |
| UI Annotation | Action 표시 위치가 적절한가 |
| Authorization | 버튼 실행 권한 또는 Feature Control 영향이 있는가 |
| Draft 여부 | Draft 상태에서 Action 노출 조건이 다른가 |

이번 모듈에서는 UI Annotation 세부 구현보다 “Action이 RAP BO의 명시적 업무 동작이며 UI 버튼으로 연결될 수 있다”는 흐름을 이해하는 것이 중요하다.

## 21. 정상 흐름과 오류 흐름

## 21.1 정상 흐름

```text
1. ZI_* Interface View 준비
2. ZC_* Projection View 준비
3. Interface BDEF에 Validation / Determination / Action 선언
4. Behavior Implementation Class에 메서드 구현
5. Projection BDEF에 Action 노출
6. Service Definition / Binding Publish
7. Fiori Elements Preview 실행
8. 잘못된 입력값 저장 시 Validation 메시지 확인
9. 생성 시 Determination으로 기본값 자동 설정 확인
10. Action 버튼 실행 후 상태 변경 확인
```

## 21.2 오류 흐름 1: Validation 메시지가 나오지 않음

| 원인 | 해결 |
|---|---|
| BDEF에 Validation 선언이 없음 | `validation ... on save` 선언 확인 |
| Trigger 필드가 누락됨 | `{ create; update; field ...; }` 확인 |
| Behavior Implementation 메서드가 비어 있음 | 메서드 구현 확인 |
| `failed`에 Key를 넣지 않음 | 실패 Entity를 `failed-Entity`에 추가 |
| `reported` 메시지만 있고 `failed`가 없음 | 오류 저장 차단이 필요한 경우 `failed`도 추가 |

### 핵심

```text
오류 메시지를 보여주는 것과 저장을 막는 것은 다르다.
저장을 막으려면 failed 처리가 필요하다.
```

## 21.3 오류 흐름 2: Determination이 실행되지 않음

| 원인 | 해결 |
|---|---|
| Trigger 선언 누락 | `on modify { create; update; field ...; }` 확인 |
| 관련 필드 변경이 발생하지 않음 | Trigger 필드와 UI 입력 필드 확인 |
| 메서드 스텁만 있고 구현 없음 | Behavior Implementation 작성 |
| 값을 Update하지 않음 | `MODIFY ENTITIES ... UPDATE FIELDS` 확인 |
| 무한 재호출성 설계 | 값이 바뀔 때만 Update하도록 조건 추가 |

### 핵심

```text
Determination은 Trigger와 구현이 모두 맞아야 실행 결과가 보인다.
```

## 21.4 오류 흐름 3: Action 버튼이 보이지 않음

| 원인 | 해결 |
|---|---|
| Projection BDEF에서 `use action` 누락 | `use action approve;` 추가 |
| Service Binding 미갱신 | Publish 또는 Refresh |
| UI Annotation 누락 | Object Page/List Report Action 노출 설정 확인 |
| 권한/Feature Control 영향 | Authorization과 Instance Feature 확인 |
| Draft 상태 조건 | Draft Action 노출 조건 확인 |

### 핵심

```text
Action은 Interface BDEF 선언만으로 UI에 자동 표시된다고 단정하면 안 된다.
Projection, Service, UI, 권한 흐름을 함께 확인해야 한다.
```

## 21.5 오류 흐름 4: Action 실행 후 화면 값이 갱신되지 않음

| 원인 | 해결 |
|---|---|
| Action Result 미반환 | `result [1] $self`와 `result` 채움 확인 |
| 변경 후 READ 누락 | Modify 후 최신 Entity를 읽어 반환 |
| UI Refresh 문제 | Preview 재실행 또는 화면 Refresh |
| Service Metadata 갱신 필요 | Service Binding 최신화 |

## 22. 실무 설계 기준

## 22.1 Validation 설계 기준

Validation은 다음 기준으로 설계한다.

| 기준 | 설명 |
|---|---|
| 데이터 무결성 | 저장되어서는 안 되는 값인지 판단 |
| 사용자 피드백 | 어떤 필드가 왜 잘못되었는지 명확히 보고 |
| 중복 방지 | 같은 검증을 UI, BO, DB에 흩뿌리지 않도록 설계 |
| 성능 | 대량 저장 시 검증 비용을 고려 |
| 권한 분리 | 권한 검사는 Authorization 역할과 혼동하지 않음 |

## 22.2 Determination 설계 기준

Determination은 다음 기준으로 설계한다.

| 기준 | 설명 |
|---|---|
| 자동 계산 | 사용자가 직접 입력할 필요 없는 값인지 판단 |
| 명확성 | 자동 변경 사실이 사용자에게 예측 가능해야 함 |
| 멱등성 | 여러 번 실행되어도 동일 결과가 되어야 함 |
| 최소 변경 | 필요한 필드만 Update |
| 역할 분리 | 오류 차단은 Validation, 업무 버튼은 Action과 분리 |

## 22.3 Action 설계 기준

Action은 다음 기준으로 설계한다.

| 기준 | 설명 |
|---|---|
| 업무 의미 | 단순 필드 변경보다 명확한 업무 동작인지 확인 |
| 명시성 | 사용자가 실행 의도를 가진 버튼/API인지 확인 |
| 권한 | 누가 실행할 수 있는지 고려 |
| 상태 전이 | 어떤 상태에서 어떤 상태로 바뀔 수 있는지 명확화 |
| 결과 반환 | UI가 갱신될 수 있도록 결과 설계 |
| 메시지 품질 | 성공/실패 사유를 명확히 전달 |

## 23. Clean Core / ABAP Cloud 관점

RAP의 Validation, Determination, Action은 Clean Core 개발에서 중요한 확장 지점이다.

기존 방식에서는 다음처럼 구현이 흩어질 수 있다.

```text
화면 PAI 모듈에서 검증
Report 안에서 임의로 값 보정
Function Module에서 상태 변경
User Exit/BAdI에서 별도 로직 추가
테이블 직접 UPDATE
```

RAP에서는 Business Object의 Behavior 안에 업무 규칙을 모을 수 있다.

```text
Business Object
  - Validation: 저장 가능 여부 판단
  - Determination: 파생값 자동 결정
  - Action: 명시적 업무 동작
  - Authorization: 실행 권한 판단
  - Locking: 동시성 제어
```

이 구조는 다음 장점을 가진다.

| 장점 | 설명 |
|---|---|
| 규칙 집중 | BO Behavior 안에 업무 규칙이 모인다. |
| 서비스 일관성 | UI와 API가 같은 Behavior를 사용한다. |
| 테스트 가능성 | 동작 단위로 검증하기 쉽다. |
| Clean Core 적합성 | 표준 객체 직접 수정 대신 확장 가능한 모델을 사용한다. |
| 유지보수성 | 역할별로 Validation, Determination, Action을 구분할 수 있다. |

## 24. 초급자 오해 정리

## 24.1 “Validation에서 값을 고치면 되지 않나요?”

초급 단계에서는 권장하지 않는다.  
Validation은 오류를 감지하고 보고하는 역할로 이해하는 것이 좋다.  
값을 자동으로 보정해야 한다면 Determination을 먼저 검토한다.

## 24.2 “Determination으로 모든 값을 자동 변경하면 편하지 않나요?”

과도한 자동 변경은 사용자를 혼란스럽게 만든다.  
사용자가 입력한 값이 예상치 못하게 바뀌면 신뢰성이 떨어진다.  
자동 변경은 명확하고 예측 가능한 값에만 적용하는 것이 좋다.

## 24.3 “Action은 그냥 Update랑 같은 것 아닌가요?”

아니다.  
Action은 업무 의미를 가진 명시적 동작이다.  
승인은 단순히 `Status = 'A'`로 바꾸는 것이 아니라, 권한, 상태 전이, 메시지, 이력, 후속 처리까지 포함할 수 있다.

## 24.4 “Interface BDEF에 Action을 선언하면 UI에 바로 보이나요?”

항상 그렇지는 않다.  
Projection BDEF, Service Binding, UI Annotation, 권한, Feature Control 조건을 함께 확인해야 한다.

## 24.5 “failed 없이 reported 메시지만 넣어도 저장이 막히나요?”

저장을 확실히 막아야 하는 Validation에서는 실패 대상 Entity를 `failed`에 넣어야 한다.  
`reported`는 사용자 메시지 전달 역할이고, `failed`는 처리 실패를 Framework에 알리는 역할이다.

## 26. 평가 문제

### 26.1 객관식

#### Q1. RAP Validation의 가장 적절한 목적은 무엇인가?

A. 사용자가 누르는 버튼을 만드는 것이다.  
B. 생성 시 기본값을 자동으로 채우는 것이다.  
C. 저장 가능한 데이터인지 비즈니스 규칙을 검사하는 것이다.  
D. OData Service Binding을 Publish하는 것이다.

**정답:** C

#### Q2. Determination에 가장 적합한 예는 무엇인가?

A. 종료일이 시작일보다 빠르면 저장을 막는다.  
B. 신규 생성 시 상태값을 기본값으로 자동 설정한다.  
C. 사용자가 승인 버튼을 눌러 상태를 승인으로 바꾼다.  
D. Field Label 정의

**정답:** B

#### Q3. Action에 가장 적합한 예는 무엇인가?

A. BeginDate와 EndDate의 입력값 검증  
B. 생성 시 CreatedBy 자동 입력  
C. Approve 버튼을 눌러 승인 처리  
D. Field Label 정의

**정답:** C

#### Q4. Validation에서 저장을 막기 위해 중요한 것은?

A. `reported`만 채우면 충분하다.  
B. 실패 Entity를 `failed`에 추가해야 한다.  
C. Projection View를 삭제해야 한다.  
D. Service Definition을 다시 만들 필요가 없다.

**정답:** B

### 26.2 서술형

#### Q1. Validation, Determination, Action의 차이를 설명하시오.

**모범 답안:**  
Validation은 입력값이나 상태가 저장 가능한지 검증하고 오류를 보고하는 동작이다. Determination은 생성·수정 시점에 기본값이나 파생값을 자동으로 계산하는 동작이다. Action은 사용자가 버튼 또는 API 호출로 명시적으로 실행하는 업무 동작이다.

#### Q2. `failed`와 `reported`의 역할을 설명하시오.

**모범 답안:**  
`failed`는 특정 Entity 인스턴스의 처리가 실패했음을 RAP Framework에 알리는 역할을 한다. `reported`는 사용자 또는 소비자에게 전달할 메시지를 담는다. Validation에서 저장을 막으려면 일반적으로 오류 대상 Entity를 `failed`에 추가하고, 오류 사유를 `reported`에 담는다.

#### Q3. Projection BDEF에서 `use action`이 필요한 이유를 설명하시오.

**모범 답안:**  
Interface BDEF에 Action을 정의하더라도 외부 서비스 소비 계층에 노출하려면 Projection Behavior에서 해당 Action을 사용할 수 있도록 선언해야 한다. 이를 누락하면 Fiori Elements 또는 OData 소비 계층에서 Action이 보이지 않거나 사용할 수 없을 수 있다.

## 28. 핵심 요약

이번 모듈의 핵심은 다음이다.

```text
Validation은 잘못된 데이터를 막는다.
Determination은 기본값과 파생값을 자동으로 채운다.
Action은 사용자가 명시적으로 실행하는 업무 동작이다.
BDEF는 동작을 선언하고, Behavior Implementation Class는 동작을 구현한다.
오류를 막으려면 reported 메시지뿐 아니라 failed 처리도 중요하다.
Action을 UI/Service에 노출하려면 Projection BDEF와 Service Binding 흐름을 함께 확인해야 한다.
```

초급자는 특히 다음 문장을 반드시 기억한다.

```text
막는 것은 Validation, 채우는 것은 Determination, 누르는 것은 Action이다.
```
