## 3. ABAP Cloud란 무엇인가?

### 3.1 쉬운 정의

ABAP Cloud는 클라우드와 온프레미스 S/4HANA 확장을 위해 SAP가 제시하는 현대적 ABAP 개발 모델이다.  
핵심은 다음 세 가지로 요약할 수 있다.

```text
1. 안정적으로 공개된 API만 사용한다.
2. 업그레이드에 강한 확장을 만든다.
3. RAP, CDS, ADT, ABAP 언어 버전 제약을 기반으로 개발한다.
```

ABAP Cloud는 단순히 “BTP에서만 쓰는 ABAP”을 의미하지 않는다.  
S/4HANA Cloud에서는 기본 개발 모델에 가깝고, S/4HANA On-Premise 또는 Private Cloud에서도 Clean Core와 업그레이드 안정성을 위해 점점 더 중요해지는 개발 원칙이다.

### 3.2 Classic ABAP와의 차이

| 구분 | Classic ABAP 개발 | ABAP Cloud 개발 |
|---|---|---|
| 개발 도구 | SAP GUI, SE80, SE38, SE11 중심 | ADT 중심 |
| 표준 객체 접근 | 많은 표준 테이블/함수/클래스 직접 참조 가능 | Released API 중심 |
| 언어 사용 | 전통 ABAP 문법 폭넓게 사용 | ABAP for Cloud Development 제약 적용 |
| 확장 방식 | User Exit, BAdI, Enhancement, Z Report 등 다양 | RAP, CDS, Released API, 명시적 Extension 중심 |
| 업그레이드 안정성 | 개발자 통제에 크게 의존 | 플랫폼 규칙으로 안정성 강화 |
| Clean Core 적합성 | 개발 방식에 따라 편차 큼 | Clean Core 지향 |

초급자는 다음 문장으로 이해하면 된다.

```text
Classic ABAP는 “가능한 것을 개발자가 잘 골라 써야 하는 방식”에 가깝고,
ABAP Cloud는 “사용 가능한 것만 명시적으로 허용해서 안정성을 높이는 방식”에 가깝다.
```

## 4. Clean Core란 무엇인가?

Clean Core는 SAP 표준 코어를 가능한 깨끗하게 유지하고, 확장은 명시적이고 업그레이드 가능한 방식으로 수행하자는 원칙이다.

### 4.1 Clean Core의 핵심 의도

Clean Core의 목적은 “Z 개발을 하지 말라”가 아니다.  
오히려 필요한 확장은 하되, 다음과 같은 방식으로 하라는 의미에 가깝다.

```text
표준 소스를 직접 수정하지 않는다.
SAP 내부 객체에 무분별하게 의존하지 않는다.
확장 지점과 공개 API를 사용한다.
업그레이드 시 깨질 가능성이 낮은 구조로 만든다.
테스트와 영향 분석이 가능한 구조로 만든다.
```

### 4.2 Clean Core가 필요한 이유

| 이유 | 설명 |
|---|---|
| 업그레이드 안정성 | SAP 표준 내부 구현이 바뀌어도 고객 개발이 덜 깨지도록 한다. |
| 유지보수성 | 표준과 고객 확장의 경계를 명확히 한다. |
| 전환 가능성 | Cloud 전환 또는 Private Cloud 전환 시 개발 부채를 줄인다. |
| 감사/품질 | 허용된 API와 확장 지점을 사용했는지 점검하기 쉽다. |
| 장기 운영 | 5년, 10년 뒤에도 이해 가능한 확장 구조를 만든다. |

### 4.3 Clean Core를 해치는 예

다음은 실무에서 흔히 발생하는 위험한 패턴이다.

```abap
SELECT *
  FROM mara
  INTO TABLE @DATA(lt_mara).
```

위 코드는 Classic ABAP 교육에서는 자주 보이는 예제일 수 있다.  
하지만 ABAP Cloud 원칙에서는 표준 테이블을 직접 참조하는 것이 허용되지 않을 수 있다.  
해당 데이터가 필요하다면 SAP가 외부 사용을 허용한 CDS View, Business Object, Class API, OData API 등 Released API를 먼저 찾아야 한다.

> [추정] 특정 표준 테이블이나 CDS View의 Release 상태는 시스템 릴리스와 제품 영역에 따라 달라질 수 있다. 따라서 실제 프로젝트에서는 ADT의 API 상태, SAP Business Accelerator Hub, 시스템 내 Repository 정보, 프로젝트 가이드를 기준으로 확인해야 한다.

## 5. Released API란 무엇인가?

### 5.1 쉬운 정의

Released API는 SAP 또는 개발 조직이 외부 소비자가 사용해도 된다고 명시적으로 공개한 API이다.

여기서 API는 단순히 REST API만 의미하지 않는다. ABAP Cloud 관점에서 API는 여러 형태일 수 있다.

| API 유형 | 예시 |
|---|---|
| CDS View / CDS View Entity | 공개 조회용 Interface View |
| ABAP Class / Interface | 공개 메서드를 가진 Released Class |
| Behavior Definition / RAP BO | 공개된 비즈니스 객체 동작 |
| OData Service | 외부 소비용 서비스 |
| Data Element / Type | 공개 타입 |
| BAdI / Extension Point | 확장 지점 |

중요한 것은 “존재한다”가 아니라 “사용하도록 Release되어 있다”이다.

### 5.2 Released와 Public의 차이

초급자가 자주 혼동하는 지점이다.

| 표현 | 의미 |
|---|---|
| Public Method | 클래스 내부 접근 제어자 관점에서 public |
| Released API | 다른 개발 객체/소비자가 안정적으로 사용하도록 공개된 API |
| 존재하는 객체 | 시스템에 있지만 외부 사용이 보장되지 않을 수 있음 |
| 검색되는 객체 | ADT/SE11에서 보이더라도 사용 가능하다는 뜻은 아님 |

즉, 어떤 클래스의 메서드가 `PUBLIC`이라고 해서 ABAP Cloud 개발에서 사용 가능한 Released API라는 뜻은 아니다.

### 5.3 왜 Released API만 사용해야 하는가?

SAP 내부 객체는 릴리스마다 구조나 의미가 바뀔 수 있다.  
하지만 Released API는 외부 사용을 전제로 안정성을 더 강하게 고려한다.

| 구분 | Released API 사용 | Unreleased Object 직접 사용 |
|---|---|---|
| 업그레이드 안정성 | 상대적으로 높음 | 낮음 |
| 호환성 약속 | 있음 | 없음 또는 제한적 |
| Clean Core 적합성 | 높음 | 낮음 |
| ATC/Cloud Readiness | 통과 가능성 높음 | 오류/경고 가능성 높음 |
| 장기 유지보수 | 유리 | 리스크 큼 |

## 6. Unreleased Object 직접 참조의 위험

### 6.1 동작은 하지만 위험한 코드

Classic ABAP 시스템에서는 다음 코드가 문법적으로 동작할 수 있다.

```abap
SELECT *
  FROM some_sap_internal_table
  INTO TABLE @DATA(lt_result).
```

문제는 “오늘 동작한다”는 사실이 “앞으로도 사용해도 된다”를 의미하지 않는다는 점이다.

### 6.2 위험 요소

| 위험 | 설명 |
|---|---|
| 업그레이드 파손 | SAP 내부 테이블 구조가 바뀌면 코드가 깨질 수 있다. |
| 의미 변경 | 같은 필드라도 업무 의미가 릴리스에 따라 바뀔 수 있다. |
| 권한/보안 | 표준 API가 제공하는 권한 검사를 우회할 수 있다. |
| 데이터 정합성 | 내부 테이블 조합을 잘못 이해하면 잘못된 결과를 만들 수 있다. |
| Cloud 전환 장애 | ABAP Cloud 언어 버전에서 사용할 수 없을 수 있다. |
| ATC 오류 | Cloud Readiness 또는 Clean Core 점검에서 걸릴 수 있다. |

### 6.3 실무 예시

사용자가 판매오더 정보를 조회해야 한다고 가정한다.

나쁜 접근:

```text
표준 테이블을 직접 찾아서 JOIN한다.
내부 함수 모듈을 찾아 호출한다.
업그레이드 후에도 유지될지 확인하지 않는다.
```

좋은 접근:

```text
1. SAP가 제공하는 Released CDS View 또는 API를 먼저 찾는다.
2. 필요한 데이터가 API에 있는지 확인한다.
3. 없으면 확장 지점이나 공개 BO/Service를 검토한다.
4. 그래도 부족하면 프로젝트 아키텍처 기준에 따라 예외 승인 또는 Wrapper 전략을 검토한다.
```

## 7. ABAP Cloud 언어 버전

ABAP Cloud 개발에서는 ABAP 언어 버전이 중요하다.  
언어 버전은 단순 문법 설정이 아니라, 어떤 명령과 객체 참조가 허용되는지를 제한하는 개발 계약에 가깝다.

### 7.1 언어 버전이 필요한 이유

| 이유 | 설명 |
|---|---|
| 안정성 | 위험하거나 오래된 문법 사용을 제한한다. |
| Cloud 적합성 | 클라우드 환경에서 허용되는 개발 범위를 명확히 한다. |
| API 통제 | Released API 중심으로 의존성을 제한한다. |
| 품질 검사 | ATC와 연계해 잘못된 참조를 조기에 발견한다. |

### 7.2 초급자 이해 포인트

초급자는 다음 정도를 이해하면 충분하다.

```text
ABAP Cloud 개발에서는 “문법적으로 가능하다”보다
“해당 언어 버전에서 허용되는가”가 더 중요하다.
```

즉, SE38에서 만들던 전통 Report 방식이나 특정 Function Module 호출이 Classic 시스템에서는 가능해도 ABAP Cloud 개발에서는 허용되지 않을 수 있다.

## 8. RAP와 Released API의 연결

RAP Business Object를 설계할 때 Released API 원칙은 여러 지점에 적용된다.

```text
Persistence Table
→ Interface View ZI_*
→ Projection View ZC_*
→ Behavior Definition
→ Behavior Implementation
→ Service Definition
→ Service Binding
```

### 8.1 Persistence Table

고객 개발 테이블은 보통 고객 네임스페이스 `Z*` 또는 `Y*`에 생성한다.  
하지만 표준 SAP 업무 데이터와 연결하려면 표준 테이블을 직접 참조하지 말고, Released API를 먼저 찾는다.

### 8.2 Interface View `ZI_*`

Interface View는 RAP BO의 의미적 중심이다.  
여기에서 표준 데이터와 Join 또는 Association을 만들 때 Released CDS View를 우선 사용해야 한다.

예시 설계 원칙:

```text
좋은 방향:
ZI_GPT_SalesOrderRoot
  association to released interface view or released value help view

위험한 방향:
ZI_GPT_SalesOrderRoot
  직접 표준 내부 테이블과 강한 결합
```

[추정] 실제 시스템에서 어떤 `I_*` View가 Released 상태인지는 릴리스, 스코프, 소프트웨어 컴포넌트에 따라 달라질 수 있다.

### 8.3 Projection View `ZC_*`

Projection View는 소비자에게 노출할 필드와 행위를 정리하는 계층이다.  
이 계층에서도 내부 구현 세부사항을 그대로 노출하지 않는 것이 좋다.

좋은 설계 방향:

```text
ZI_*에서는 BO 내부 모델과 의미를 정리한다.
ZC_*에서는 UI/API 소비 관점의 필드를 선별한다.
표준 내부 필드명을 그대로 노출하지 않고 의미 있는 이름과 주석을 사용한다.
```

### 8.4 Behavior Implementation

Behavior Implementation에서는 표준 데이터 조회, 검증, 후속 처리 등이 필요할 수 있다.  
이때도 내부 Function Module이나 미공개 Class를 호출하기보다 Released Class, RAP BO API, 공개 Service, Released CDS View를 우선 검토한다.

위험한 예:

```abap
"예시 목적의 위험 패턴
CALL FUNCTION 'SOME_INTERNAL_FUNCTION'.
```

좋은 방향:

```text
1. Released Class 또는 Interface 검색
2. 공개 CDS View 또는 RAP BO 사용
3. 공식 Business API 검토
4. 없으면 아키텍처 예외 처리 기준 수립
```

## 9. API 상태 확인 방법

### 9.1 ADT에서 확인

ABAP Cloud 개발에서는 ADT를 통해 객체의 API 상태, 언어 버전, 사용 가능 여부를 확인하는 흐름이 중요하다.

초급자 관점의 확인 절차는 다음과 같다.

```text
1. ADT에서 사용할 표준 객체를 검색한다.
2. 객체의 Release State 또는 API 상태를 확인한다.
3. 현재 패키지/언어 버전에서 사용 가능한지 확인한다.
4. ATC 또는 Syntax Check를 실행한다.
5. Cloud Development 제약 위반 메시지가 있는지 확인한다.
```

### 9.2 ATC와 Cloud Readiness

ATC는 ABAP Test Cockpit이다.  
ABAP Cloud나 Clean Core 전환에서는 ATC를 통해 미공개 객체 참조, 금지 문법, 위험한 의존성을 조기에 발견할 수 있다.

확인해야 할 대표 항목은 다음과 같다.

| 점검 항목 | 의미 |
|---|---|
| Unreleased API 사용 | 공개되지 않은 표준 객체를 참조했는가 |
| 금지 문법 | Cloud 언어 버전에서 허용되지 않는 문법인가 |
| 직접 DB 접근 | 표준 내부 테이블 직접 접근이 있는가 |
| 패키지 의존성 | 허용되지 않은 패키지 객체를 참조했는가 |
| 확장 방식 | 표준 확장 지점을 우회하고 있는가 |

## 10. 실무 판단 흐름

Released API 사용 여부를 판단할 때는 다음 순서로 생각한다.

```text
1. 내가 필요한 업무 데이터나 기능은 무엇인가?
2. SAP가 해당 기능을 Released API로 제공하는가?
3. Released CDS View, Class, RAP BO, OData API 중 무엇이 적합한가?
4. API가 제공하는 필드와 동작이 요구사항을 충족하는가?
5. 부족한 경우 확장 지점이 있는가?
6. 그래도 부족하면 예외 승인이 필요한가?
7. 예외를 쓰는 경우 업그레이드 리스크와 대체 계획을 문서화했는가?
```

### 10.1 판단표

| 상황 | 권장 판단 |
|---|---|
| Released API가 요구사항을 충족 | 해당 API 사용 |
| Released API가 있으나 일부 필드 부족 | 확장 필드, Projection, Extension 검토 |
| Released API가 없고 내부 테이블만 존재 | 직접 참조 전 아키텍처 검토 필요 |
| 기존 Z 프로그램이 표준 테이블 직접 참조 | 리팩토링 후보 |
| Cloud 전환 예정 | Unreleased 참조 제거 우선순위 높음 |

## 11. 교육용 RAP 예제 설계 원칙

이번 Section 전체에서 사용한 RAP 흐름을 ABAP Cloud 관점으로 다시 정리한다.

### 11.1 Interface View `ZI_*`

교육용 Root Interface View 예시는 다음 명명 규칙을 사용한다.

```text
ZI_GPT_TravelRoot
ZI_GPT_BookingRoot
ZI_GPT_ProductRoot
```

Interface View에서는 다음을 고려한다.

| 항목 | 원칙 |
|---|---|
| Root Entity | BO의 루트 의미를 명확히 한다. |
| Key | 안정적인 업무 Key 또는 UUID 기반 Key를 사용한다. |
| Association | 표준 내부 테이블 직접 참조보다 Released View를 우선한다. |
| Composition | BO 내부 생명주기 관계에 사용한다. |
| Annotation | 소비 계층과 혼동하지 않도록 필요한 수준만 사용한다. |

### 11.2 Projection View `ZC_*`

Projection View 예시는 다음과 같다.

```text
ZC_GPT_Travel
ZC_GPT_Booking
ZC_GPT_Product
```

Projection View에서는 다음을 고려한다.

| 항목 | 원칙 |
|---|---|
| 소비자 관점 | UI/API에 필요한 필드만 노출한다. |
| 행위 노출 | Create/Update/Delete/Action을 소비 시나리오에 맞게 공개한다. |
| 민감 필드 | 내부 처리용 필드를 무조건 노출하지 않는다. |
| 표준 연계 | 표준 데이터 의미를 노출할 때 Released API 기반인지 확인한다. |

### 11.3 Behavior Definition

Behavior Definition에서는 다음 원칙을 둔다.

```text
strict(2)를 기준으로 학습한다.
CRUD 가능 여부를 명확히 선언한다.
Validation, Determination, Action은 업무 의미가 있을 때만 둔다.
표준 내부 객체 호출은 Behavior Implementation에서 신중히 검토한다.
```

### 11.4 Service Definition / Binding

Service로 외부 노출할 때는 다음을 고려한다.

| 항목 | 원칙 |
|---|---|
| 공개 범위 | 필요한 Projection Entity만 expose한다. |
| OData V4 | RAP 기본 서비스 노출 방식으로 이해한다. |
| 권한 | 단순 노출이 곧 안전한 API가 아님을 이해한다. |
| 안정성 | 외부 소비자가 의존할 계약이므로 필드 변경에 주의한다. |

## 13. 미니 설계 예시

아래 예시는 개념 전달용이다. 실제 시스템의 Released API 상태는 반드시 확인해야 한다.

### 13.1 Root Interface View 예시

```abap
@EndUserText.label: 'Travel Root Interface View'
define root view entity ZI_GPT_TravelRoot
  as select from zgpt_travel
  association [0..1] to I_Currency as _Currency
    on $projection.CurrencyCode = _Currency.Currency
{
  key travel_uuid     as TravelUUID,
      travel_id       as TravelID,
      agency_id       as AgencyID,
      customer_id     as CustomerID,
      currency_code   as CurrencyCode,
      total_price     as TotalPrice,
      overall_status  as OverallStatus,

      _Currency
}
```

> [추정] `I_Currency`의 실제 사용 가능 여부와 필드명은 시스템 릴리스와 API Release 상태에 따라 다를 수 있다. 교육 환경에서는 시스템에서 Released 상태로 확인 가능한 View로 대체한다.

### 13.2 Projection View 예시

```abap
@EndUserText.label: 'Travel Projection View'
@AccessControl.authorizationCheck: #CHECK
define root view entity ZC_GPT_Travel
  as projection on ZI_GPT_TravelRoot
{
  key TravelUUID,
      TravelID,
      AgencyID,
      CustomerID,
      CurrencyCode,
      TotalPrice,
      OverallStatus,

      _Currency
}
```

### 13.3 핵심 해석

이 예시의 핵심은 문법보다 원칙이다.

```text
Z 테이블은 고객 개발 영역의 Persistence로 사용한다.
ZI_*는 BO의 안정적인 Interface 계층을 만든다.
ZC_*는 소비자에게 필요한 필드만 노출한다.
표준 데이터와 연결할 때는 Released API인지 확인한다.
```

## 14. 자주 하는 실수

### 14.1 “ADT에서 보이면 써도 된다”라고 생각

ADT에서 객체가 검색된다고 해서 ABAP Cloud에서 사용할 수 있다는 뜻은 아니다.  
Release 상태와 언어 버전 제약을 반드시 확인해야 한다.

### 14.2 표준 테이블 직접 SELECT

Classic ABAP에서 자주 쓰던 방식이지만 Clean Core 관점에서는 위험할 수 있다.

```abap
SELECT *
  FROM some_standard_table
  INTO TABLE @DATA(lt_data).
```

대신 다음 순서로 검토한다.

```text
Released CDS View
Released Class / Interface
Business API
RAP BO
Extensibility Point
```

### 14.3 내부 Function Module 호출

오래된 Function Module은 Classic 시스템에서 잘 동작할 수 있지만 ABAP Cloud에서 허용되지 않을 수 있다.  
특히 이름만 보고 표준 내부 API를 호출하는 습관은 위험하다.

### 14.4 Projection View에 내부 필드를 과도하게 노출

`ZC_*`는 소비 계층이다. 내부 관리용 필드, 기술 필드, 임시 상태값을 무조건 외부에 공개하면 API 계약이 불안정해진다.

### 14.5 Clean Core를 “개발 금지”로 오해

Clean Core는 개발을 하지 말라는 뜻이 아니다.  
표준과 고객 확장의 경계를 명확히 하고, 공개 API와 확장 포인트를 사용하라는 뜻이다.

## 15. 오류 상황과 검증 포인트

### 15.1 Syntax Check 오류

| 현상 | 가능 원인 | 해결 |
|---|---|---|
| 객체를 사용할 수 없다는 오류 | 언어 버전에서 허용되지 않음 | Released API 대체 객체 검색 |
| 패키지 접근 오류 | 패키지 의존성 미허용 | Package Interface 또는 공개 API 확인 |
| Cloud readiness 오류 | Unreleased API 참조 | ATC 결과 기준으로 리팩토링 |

### 15.2 ATC 오류

ATC에서 다음 메시지 유형이 나오면 주의한다.

```text
Use of unreleased object
Use of restricted ABAP statement
Direct access to non-released database table
Package check violation
```

해결 접근은 다음이다.

```text
1. 오류 객체 확인
2. Release 상태 확인
3. 대체 Released API 검색
4. 설계 계층에서 참조 위치 변경
5. 필요 시 아키텍처 예외 승인 문서화
```

### 15.3 런타임 오류

Released API 원칙을 지키지 않으면 문법 오류뿐 아니라 런타임 오류나 권한 오류도 발생할 수 있다.  
특히 표준 내부 테이블 직접 접근은 권한 모델을 우회하거나 잘못된 데이터 의미를 가져올 위험이 있다.

## 18. 평가 문제

### 18.1 객관식

#### Q1. ABAP Cloud 개발에서 Released API를 우선 사용하는 가장 중요한 이유는?

A. 코드 줄 수를 줄이기 위해  
B. 업그레이드 안정성과 Clean Core를 확보하기 위해  
C. SAP GUI 화면 색상을 바꾸기 위해  
D. 모든 테이블을 Buffering하기 위해  

**정답:** B

#### Q2. 다음 중 Released API라고 단정할 수 없는 것은?

A. SAP가 외부 사용을 허용한 CDS View  
B. Release 상태가 명시된 Class API  
C. ADT에서 검색되는 모든 표준 테이블  
D. 공개된 RAP Business Object API  

**정답:** C

#### Q3. Clean Core의 의미로 가장 적절한 것은?

A. 모든 Z 개발을 금지한다.  
B. 표준 객체를 직접 수정하고 빠르게 개발한다.  
C. 표준 코어를 안정적으로 유지하면서 공개 API와 확장 지점을 통해 확장한다.  
D. 모든 개발을 SE38 Report로만 작성한다.  

**정답:** C

### 18.2 단답형

#### Q1. Released API와 Public Method의 차이를 설명하시오.

**모범 답안:**  
Public Method는 클래스 접근 제어자 관점에서 외부 호출이 가능한 메서드라는 뜻이다. Released API는 특정 소비자가 안정적으로 사용해도 된다고 공개 상태가 명시된 API이다. Public Method라고 해서 반드시 ABAP Cloud에서 사용 가능한 Released API인 것은 아니다.

#### Q2. 표준 테이블을 직접 SELECT하는 방식이 ABAP Cloud 관점에서 위험한 이유를 설명하시오.

**모범 답안:**  
표준 내부 테이블은 외부 사용을 위한 안정적 계약이 아닐 수 있다. 릴리스 변경 시 구조나 의미가 바뀔 수 있고, 권한/정합성 로직을 우회할 수 있으며, Clean Core 또는 Cloud Readiness 점검에서 오류가 발생할 수 있다.

#### Q3. RAP에서 `ZI_*`와 `ZC_*`를 둘 다 설계하는 이유를 설명하시오.

**모범 답안:**  
`ZI_*`는 Business Object의 내부 Interface 계층으로 핵심 데이터 모델과 관계를 정의하고, `ZC_*`는 소비자 관점에서 노출할 필드와 행위를 정리한다. 두 계층을 분리하면 내부 모델과 외부 API 계약을 안정적으로 관리할 수 있다.

```text
3. Persistence Table 이름: Z*
4. 외부 표준 데이터 참조 지점
5. 해당 표준 데이터의 Released API 후보
6. Released API가 없을 때의 대체 전략
```

### 19.3 리뷰 과제

다음 코드를 보고 문제점을 설명한다.

```abap
SELECT *
  FROM some_sap_standard_table
  INTO TABLE @DATA(lt_data).

CALL FUNCTION 'SOME_SAP_INTERNAL_FM'
  TABLES
    et_data = lt_data.
```

리뷰 관점:

```text
1. 표준 테이블 직접 접근 여부
2. 내부 Function Module 호출 여부
3. Released API 확인 여부
4. Clean Core 위반 가능성
5. 대체 API 또는 RAP/CDS 설계 방향
```

## 20. 강사용 설명 포인트

강의에서는 다음 포인트를 강조한다.

### 20.1 초급자에게는 “금지 목록”보다 “판단 순서”가 중요하다

ABAP Cloud를 처음 배우는 학습자에게 모든 허용/금지 규칙을 한 번에 설명하면 혼란스럽다.  
따라서 다음 순서를 반복적으로 훈련한다.

```text
필요한 데이터/기능 정의
→ Released API 검색
→ ZI_* / ZC_* 설계 반영
→ Behavior Implementation에서 의존성 최소화
→ ATC로 검증
```

### 20.2 Clean Core는 기술 규칙이면서 아키텍처 규칙이다

Clean Core는 단순 문법 문제가 아니다.  
표준과 고객 개발의 경계를 어디에 둘 것인지에 대한 아키텍처 문제이다.

### 20.3 RAP 입문 마지막 모듈로서의 의미

이 모듈은 RAP의 모든 고급 기능을 끝내는 자리가 아니다.  
RAP 입문 후 Track 2 실무 응용으로 넘어가기 전에, “어떤 방식으로 개발해야 장기적으로 안전한가”를 잡아주는 마무리 모듈이다.

## 21. 핵심 요약

```text
ABAP Cloud는 Released API와 제한된 ABAP 언어 버전을 기반으로 업그레이드 가능한 확장을 지향한다.
Released API는 외부 소비자가 사용해도 된다고 명시적으로 공개된 API이다.
ADT에서 객체가 보인다고 해서 사용 가능한 API라는 뜻은 아니다.
Clean Core는 Z 개발 금지가 아니라 표준 코어를 안정적으로 유지하는 확장 원칙이다.
RAP 개발에서도 ZI_*, ZC_*, Behavior, Service 계층 전체에서 Released API 의존성을 검토해야 한다.
Unreleased Object 직접 참조는 업그레이드, 권한, 정합성, Cloud 전환 측면에서 위험하다.
```
