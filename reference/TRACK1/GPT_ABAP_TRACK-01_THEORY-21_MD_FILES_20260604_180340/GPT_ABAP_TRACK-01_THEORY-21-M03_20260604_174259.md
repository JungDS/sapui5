## 0. 이 문서의 학습 범위

이 문서는 `THEORY-21-M03 — Projection View ZC_* 설계`만 다룬다.

이전 모듈 `THEORY-21-M02`에서는 RAP Business Object의 내부 데이터 모델 계층인 **Interface View `ZI_*`**를 학습했다. 이번 모듈에서는 그 Interface View를 서비스 소비 관점으로 노출하기 위한 **Projection View `ZC_*`**를 설계한다.

이번 모듈에서 다루는 핵심 흐름은 다음과 같다.

```text
ZI_* Interface View 확인
→ Projection View ZC_*의 목적 이해
→ Root Projection View 작성
→ Child Projection View 작성
→ Composition/Parent Association Redirection
→ Consumption 관점의 필드 선별
→ Activation 및 오류 확인
→ 후속 Behavior Definition / Service Definition으로 연결
```

이번 모듈에서는 `Behavior Definition`, `Service Definition`, `Service Binding`, `OData V4`를 깊게 구현하지 않는다.  
이들은 후속 모듈에서 순서대로 다룬다. 여기서는 `ZC_*` Projection View가 왜 필요한지, `ZI_*`와 어떻게 연결되는지, 그리고 RAP BO 노출 계층에서 어떤 설계 판단이 필요한지에 집중한다.

## 2. 선수 지식

Projection View는 단독으로 설계하는 객체가 아니다.  
항상 기반이 되는 Interface View가 먼저 필요하다.

| 선수 지식 | 필요한 이유 |
|---|---|
| RAP 아키텍처 개요 | Projection View가 어느 계층에 위치하는지 이해해야 한다. |
| CDS View Entity | `define view entity`, `define root view entity`, `as projection on` 문법을 이해해야 한다. |
| Interface View `ZI_*` | Projection View는 `ZI_*`를 기반으로 노출 계층을 만든다. |
| Association / Composition | Root-Child 구조를 Projection 계층에서도 이어야 한다. |
| Business Object 개념 | Projection View가 BO의 외부 소비 모델이 되는 이유를 이해해야 한다. |

초급자는 다음 문장을 기억하면 된다.

> Interface View `ZI_*`는 내부 데이터 모델이고, Projection View `ZC_*`는 외부 소비 모델이다.

---

## 3. Projection View란 무엇인가?

Projection View는 RAP Business Object의 소비 계층을 정의하는 CDS View Entity이다.  
일반적으로 객체명은 `ZC_*` 형태를 사용한다.

예를 들어 교육용 주문 비즈니스 객체가 다음 Interface View를 가진다고 가정한다.

```text
ZI_GPT_Order
ZI_GPT_OrderItem
```

이를 서비스나 UI 소비 관점으로 노출하기 위해 다음 Projection View를 만든다.

```text
ZC_GPT_Order
ZC_GPT_OrderItem
```

이름만 보면 단순 복사처럼 보이지만, 역할은 다르다.

```text
ZI_GPT_Order      = 내부 데이터 모델
ZC_GPT_Order      = 외부 소비 모델
ZI_GPT_OrderItem  = 내부 Item 데이터 모델
ZC_GPT_OrderItem  = 외부 Item 소비 모델
```

Projection View는 Interface View의 모든 필드를 무조건 외부에 노출하는 객체가 아니다.  
소비자에게 필요한 필드와 관계만 선별하여 노출하고, 서비스 또는 UI 소비에 맞는 의미를 부여하는 계층이다.

---

## 4. RAP 계층에서 Projection View의 위치

RAP Managed Scenario의 기본 흐름은 다음과 같이 이해할 수 있다.

```text
Database Table
  ↓
Interface View ZI_*
  ↓
Projection View ZC_*
  ↓
Behavior Definition
  ↓
Service Definition
  ↓
Service Binding
  ↓
OData V4 / Fiori Elements / External Consumer
```

조금 더 역할 중심으로 정리하면 다음과 같다.

| 계층 | 대표 객체 | 역할 |
|---|---|---|
| Persistence | `ZT_*` | 실제 데이터 저장 |
| Interface View | `ZI_*` | BO 내부 데이터 모델 정의 |
| Projection View | `ZC_*` | 소비자에게 노출할 모델 정의 |
| Behavior | `BDEF`, `BIMP` | CRUD, Action, Validation, Determination 정의 |
| Service | `SRVD`, Binding | OData 서비스 노출 |

Projection View는 `ZI_*`와 외부 서비스 사이의 경계에 위치한다.  
따라서 설계 관점에서는 다음 질문이 중요하다.

```text
내부 모델의 어떤 필드를 외부에 보여줄 것인가?
내부 Association 중 어떤 관계를 외부 소비 모델에 유지할 것인가?
외부 소비자가 사용하면 안 되는 기술 필드는 숨길 것인가?
UI 또는 API 소비에 필요한 Annotation을 어디까지 둘 것인가?
```

## 5. Interface View와 Projection View의 차이

### 5.1 기본 비교

| 구분 | Interface View `ZI_*` | Projection View `ZC_*` |
|---|---|---|
| 계층 | 내부 데이터 모델 | 소비자 노출 모델 |
| 주요 목적 | BO 구조와 영속성 기반 모델링 | 서비스/UI/API 소비 모델링 |
| Naming | `ZI_*` | `ZC_*` |
| 기반 | DB Table 또는 다른 CDS | Interface View |
| 문법 | `as select from` | `as projection on` |
| 관계 정의 | Association, Composition 원천 정의 | Association Redirection |
| 소비자 노출 | 직접 노출하지 않는 것이 일반적 | 서비스 노출 대상으로 사용 |
| 설계 관점 | 데이터 모델 정확성 | 노출 범위와 소비 편의성 |

### 5.2 핵심 차이 문장

```text
ZI_*는 "이 Business Object는 내부적으로 어떤 데이터 구조인가?"에 답한다.
ZC_*는 "이 Business Object를 외부 소비자에게 어떤 형태로 보여줄 것인가?"에 답한다.
```

### 5.3 초급자가 자주 하는 오해

초급자는 Projection View를 단순히 Interface View를 한 번 더 복사하는 객체로 이해하기 쉽다.  
하지만 Projection View는 복사가 아니라 **노출 정책을 정의하는 계층**이다.

예를 들어 Interface View에는 다음 필드가 있을 수 있다.

```text
OrderUUID
OrderID
Buyer
OrderDate
Status
LocalCreatedBy
LocalCreatedAt
LocalLastChangedBy
LocalLastChangedAt
LastChangedAt
```

이 중 외부 화면이나 API에서 전부 보여줄 필요는 없을 수 있다.  
Projection View에서는 소비자에게 필요한 필드를 선별한다.

## 6. Projection View의 Naming Convention

교육용 RAP 객체는 다음 규칙을 사용한다.

| 객체 유형 | Prefix | 예시 |
|---|---|---|
| Interface View | `ZI_` | `ZI_GPT_Order` |
| Projection View | `ZC_` | `ZC_GPT_Order` |
| Root Projection View | `ZC_*` | `ZC_GPT_Order` |
| Child Projection View | `ZC_*` | `ZC_GPT_OrderItem` |
| Behavior Definition | 대상 View 기준 | `ZI_GPT_Order`, `ZC_GPT_Order` |
| Service Definition | `ZUI_*`, `ZSRV_*` 등 프로젝트 규칙 | 후속 모듈에서 다룸 |

이번 모듈에서는 다음 객체를 기준으로 설명한다.

```text
Interface View:
  ZI_GPT_Order
  ZI_GPT_OrderItem

Projection View:
  ZC_GPT_Order
  ZC_GPT_OrderItem
```

> [추정] 실제 프로젝트에서는 고객사 Naming Rule에 따라 `ZI_`, `ZC_` 대신 다른 Prefix를 사용할 수 있다. 다만 SAP RAP 학습 자료와 예제에서는 Interface/Projection을 구분하기 위해 `I`와 `C` 계층을 명확히 나누는 방식이 널리 사용된다.

## 7. Projection View의 기본 문법

Projection View의 핵심 문법은 다음과 같다.

```abap
define root view entity ZC_GPT_Order
  provider contract transactional_query
  as projection on ZI_GPT_Order
{
  key OrderUUID,
      OrderID,
      Buyer,
      OrderDate,
      Status
}
```

### 7.1 문법 요소 해석

| 문법 요소 | 의미 |
|---|---|
| `define root view entity` | Root Projection View를 정의한다. |
| `ZC_GPT_Order` | 생성할 Projection View 이름이다. |
| `provider contract transactional_query` | RAP 트랜잭션 소비 시나리오의 Projection 계약을 나타낸다. |
| `as projection on ZI_GPT_Order` | `ZI_GPT_Order` Interface View를 기반으로 Projection을 만든다. |
| `{ ... }` | 외부에 노출할 필드와 Association을 정의한다. |
| `key OrderUUID` | 기반 View의 Key를 Projection에서도 Key로 노출한다. |

### 7.2 `as select from`과의 차이

Interface View에서는 보통 다음 형태를 사용한다.

```abap
define root view entity ZI_GPT_Order
  as select from zgpt_order
{
  key order_uuid as OrderUUID,
      order_id   as OrderID
}
```

Projection View에서는 다음 형태를 사용한다.

```abap
define root view entity ZC_GPT_Order
  as projection on ZI_GPT_Order
{
  key OrderUUID,
      OrderID
}
```

핵심 차이는 다음이다.

| 문법 | 사용 계층 | 의미 |
|---|---|---|
| `as select from` | Interface View | DB Table 또는 Data Source에서 새 모델을 정의 |
| `as projection on` | Projection View | 기존 Interface View를 소비 모델로 투영 |

## 8. 예제 전제: Interface View `ZI_*`

Projection View를 만들기 위해서는 기반 Interface View가 필요하다.  
이전 모듈에서 다음과 같은 Interface View를 작성했다고 가정한다.

### 8.1 Root Interface View 예시

```abap
@EndUserText.label: 'Order Root Interface View'
define root view entity ZI_GPT_Order
  as select from zgpt_order
  composition [0..*] of ZI_GPT_OrderItem as _Item
{
  key order_uuid      as OrderUUID,
      order_id        as OrderID,
      buyer           as Buyer,
      order_date      as OrderDate,
      status          as Status,
      local_created_by      as LocalCreatedBy,
      local_created_at      as LocalCreatedAt,
      local_last_changed_by as LocalLastChangedBy,
      local_last_changed_at as LocalLastChangedAt,
      last_changed_at       as LastChangedAt,

      _Item
}
```

### 8.2 Child Interface View 예시

```abap
@EndUserText.label: 'Order Item Interface View'
define view entity ZI_GPT_OrderItem
  as select from zgpt_order_i
  association to parent ZI_GPT_Order as _Order
    on $projection.OrderUUID = _Order.OrderUUID
{
  key item_uuid       as ItemUUID,
      order_uuid      as OrderUUID,
      item_no         as ItemNo,
      product_id      as ProductID,
      quantity        as Quantity,
      unit            as Unit,
      price_amount    as PriceAmount,
      currency_code   as CurrencyCode,

      _Order
}
```

이번 모듈의 목표는 위 `ZI_*`를 기반으로 다음 `ZC_*` Projection View를 작성하는 것이다.

```text
ZI_GPT_Order      → ZC_GPT_Order
ZI_GPT_OrderItem  → ZC_GPT_OrderItem
```

## 9. Root Projection View 설계

### 9.1 최소 Root Projection View

가장 단순한 Root Projection View는 다음과 같다.

```abap
@EndUserText.label: 'Order Consumption Projection'
define root view entity ZC_GPT_Order
  provider contract transactional_query
  as projection on ZI_GPT_Order
{
  key OrderUUID,
      OrderID,
      Buyer,
      OrderDate,
      Status
}
```

이 예제는 `ZI_GPT_Order`에서 필요한 필드만 골라 `ZC_GPT_Order`로 노출한다.

### 9.2 필드 선택 기준

Projection View에서는 Interface View의 필드를 모두 가져오지 않아도 된다.  
다음 기준으로 선별한다.

| 필드 유형 | Projection 노출 판단 |
|---|---|
| Business Key | 일반적으로 노출 |
| 사용자 화면에 필요한 설명 필드 | 노출 |
| 상태 필드 | 노출 가능 |
| 기술 키 | RAP 동작에 필요하므로 유지하는 경우 많음 |
| 생성자/생성일 | 화면 요구사항에 따라 노출 |
| 변경 타임스탬프 | ETag/동시성 설계와 연결되므로 후속 모듈에서 검토 |
| 내부 처리 전용 필드 | 숨김 검토 |

초급 단계에서는 다음처럼 단순화할 수 있다.

```text
처음에는 RAP 동작에 필요한 Key와 화면에 보여줄 업무 필드를 노출한다.
내부 감사 필드는 필요할 때만 단계적으로 추가한다.
```

## 10. Root Projection View의 확장 예

서비스 또는 Fiori Elements 화면에서 더 많은 필드가 필요하다면 다음처럼 Projection에 포함할 수 있다.

```abap
@EndUserText.label: 'Order Consumption Projection'
define root view entity ZC_GPT_Order
  provider contract transactional_query
  as projection on ZI_GPT_Order
{
  key OrderUUID,
      OrderID,
      Buyer,
      OrderDate,
      Status,
      LocalCreatedBy,
      LocalCreatedAt,
      LocalLastChangedBy,
      LocalLastChangedAt,
      LastChangedAt
}
```

하지만 모든 필드를 습관적으로 노출하는 것은 좋지 않다.  
Projection View는 소비자에게 보여줄 모델이므로, 노출 범위는 의도적으로 설계해야 한다.

## 11. Child Projection View 설계

Root에 Child가 있는 RAP BO라면 Child View도 Projection 계층에서 정의해야 한다.

```abap
@EndUserText.label: 'Order Item Consumption Projection'
define view entity ZC_GPT_OrderItem
  provider contract transactional_query
  as projection on ZI_GPT_OrderItem
{
  key ItemUUID,
      OrderUUID,
      ItemNo,
      ProductID,
      Quantity,
      Unit,
      PriceAmount,
      CurrencyCode
}
```

이 View는 `ZI_GPT_OrderItem`을 기반으로 Item 소비 모델을 정의한다.

### 11.1 Child Projection View의 역할

| 역할 | 설명 |
|---|---|
| Item 필드 노출 | 주문 품목의 소비자용 필드 목록을 정의한다. |
| Parent 연결 유지 | Root Projection View와 관계를 이어야 한다. |
| 서비스 노출 준비 | Service Definition에서 Root와 함께 노출될 수 있다. |
| Behavior 연결 준비 | 후속 Behavior Projection과 연결될 수 있다. |

Child Projection View도 단순히 필드를 나열하는 것에서 끝나지 않는다.  
Root/Child 관계를 Projection 계층에서도 이어야 하므로 Association Redirection을 이해해야 한다.

---

## 12. Association Redirection이란 무엇인가?

Interface View에서 Root와 Child는 다음처럼 연결되어 있었다.

```text
ZI_GPT_Order
  └─ composition [0..*] of ZI_GPT_OrderItem as _Item

ZI_GPT_OrderItem
  └─ association to parent ZI_GPT_Order as _Order
```

Projection View에서는 기반 Interface View의 Association을 그대로 외부에 노출하지 않는다.  
소비 계층에서는 `ZC_*`끼리 연결되도록 Association을 **Redirect**해야 한다.

즉, 다음처럼 연결 관계를 바꿔준다.

```text
ZI_GPT_Order      → ZI_GPT_OrderItem
     ↓ Projection       ↓ Projection
ZC_GPT_Order      → ZC_GPT_OrderItem
```

이를 Association Redirection이라고 이해하면 된다.

## 13. Composition Child Redirection

Root Projection View에서 Child Composition을 노출하려면 다음 문법을 사용한다.

```abap
@EndUserText.label: 'Order Consumption Projection'
define root view entity ZC_GPT_Order
  provider contract transactional_query
  as projection on ZI_GPT_Order
{
  key OrderUUID,
      OrderID,
      Buyer,
      OrderDate,
      Status,

      _Item : redirected to composition child ZC_GPT_OrderItem
}
```

### 13.1 문법 해석

| 문법 | 의미 |
|---|---|
| `_Item` | 기반 Interface View `ZI_GPT_Order`에 존재하는 Composition Association |
| `redirected to composition child` | Projection 계층의 Child Projection으로 관계를 재지정 |
| `ZC_GPT_OrderItem` | 소비 계층에서 연결할 Child Projection View |

### 13.2 왜 필요한가?

만약 Root Projection View에서 `_Item`을 그냥 노출하면 소비 모델이 내부 Interface View의 Child를 참조하는 형태가 될 수 있다.  
RAP Projection 계층에서는 소비자에게 `ZC_*` 모델을 보여주는 것이 목적이므로, Root의 Child Association도 `ZC_*`로 연결되어야 한다.

즉, 다음 구조가 되어야 한다.

```text
좋은 구조:
ZC_GPT_Order → ZC_GPT_OrderItem

피해야 할 구조:
ZC_GPT_Order → ZI_GPT_OrderItem
```

## 14. Parent Redirection

Child Projection View에서는 Parent Association을 Projection Root로 Redirect한다.

```abap
@EndUserText.label: 'Order Item Consumption Projection'
define view entity ZC_GPT_OrderItem
  provider contract transactional_query
  as projection on ZI_GPT_OrderItem
{
  key ItemUUID,
      OrderUUID,
      ItemNo,
      ProductID,
      Quantity,
      Unit,
      PriceAmount,
      CurrencyCode,

      _Order : redirected to parent ZC_GPT_Order
}
```

### 14.1 문법 해석

| 문법 | 의미 |
|---|---|
| `_Order` | 기반 Interface View `ZI_GPT_OrderItem`의 Parent Association |
| `redirected to parent` | Projection 계층의 Parent Projection View로 관계를 재지정 |
| `ZC_GPT_Order` | 소비 계층의 Root Projection View |

### 14.2 Root와 Child 양쪽 Redirection

Root와 Child가 모두 Projection 계층에서 연결되려면 다음 두 가지가 함께 필요하다.

```text
Root Projection:
  _Item : redirected to composition child ZC_GPT_OrderItem

Child Projection:
  _Order : redirected to parent ZC_GPT_Order
```

이 두 가지를 함께 정의해야 소비 계층의 BO 구조가 일관된다.

## 17. Projection View에서 필드를 선별하는 기준

Projection View 설계에서 가장 중요한 판단은 “무엇을 노출할 것인가”이다.

### 17.1 노출할 가능성이 높은 필드

| 필드 유형 | 예시 | 이유 |
|---|---|---|
| Key | `OrderUUID`, `ItemUUID` | RAP 동작과 식별에 필요 |
| Business ID | `OrderID`, `ItemNo` | 사용자와 외부 소비자가 인식 |
| 상태 | `Status` | 화면/업무 흐름에 필요 |
| 날짜 | `OrderDate` | 검색/정렬/표시에 필요 |
| 금액/수량 | `PriceAmount`, `Quantity` | 업무 핵심 정보 |
| Association | `_Item`, `_Order` | Navigation과 Composition 표현 |

### 17.2 신중히 노출할 필드

| 필드 유형 | 예시 | 주의 이유 |
|---|---|---|
| 내부 기술 필드 | 내부 처리용 Flag | 외부 소비자에게 의미가 없을 수 있음 |
| 감사 필드 | Created/Changed 정보 | UI 요구사항에 따라 결정 |
| 동시성 필드 | ETag 관련 Timestamp | Behavior 설계와 함께 검토 |
| 민감 정보 | 개인정보, 권한 관련 값 | 권한과 마스킹 검토 필요 |

### 17.3 노출 판단 질문

Projection View를 설계할 때 다음 질문을 사용한다.

```text
이 필드는 화면 또는 API 소비자에게 필요한가?
이 필드가 외부에 노출되어도 보안상 문제가 없는가?
이 필드는 내부 처리용인가?
이 필드는 RAP Behavior 동작에 필요한가?
이 Association은 외부 Navigation에 필요한가?
```

## 18. Projection View와 UI Annotation

Projection View는 소비 계층이므로 UI Annotation과 가까운 위치에 있다.  
다만 이 모듈에서는 Fiori Elements Annotation을 깊게 다루지 않는다.

초급 단계에서는 다음 정도만 이해하면 된다.

```text
Projection View는 UI/API 소비 모델이므로,
화면에 어떻게 보일지와 관련된 Annotation을 붙이거나
Metadata Extension으로 분리할 수 있다.
```

예를 들어 다음 Annotation은 UI에서 필드 표시나 Header 정보를 구성할 때 사용될 수 있다.

```abap
@Metadata.allowExtensions: true
```

이 설정이 있으면 별도 Metadata Extension 객체에서 UI Annotation을 관리할 수 있다.  
이 방식은 View 본문과 UI 표현 메타데이터를 분리하는 데 도움이 된다.

> UI Annotation, Metadata Extension, Fiori Elements Object Page/List Report 구성은 후속 Fiori/RAP UI 학습에서 더 자세히 다룬다.

## 19. Projection View와 Behavior Definition의 연결

Projection View는 후속 Behavior Definition과 연결된다.  
RAP에서는 Interface View 기반 Behavior와 Projection View 기반 Behavior가 구분될 수 있다.

초급 단계에서는 다음 흐름만 기억한다.

```text
Interface View ZI_*
  → 내부 BO 구조와 기본 Behavior의 기준

Projection View ZC_*
  → 소비자에게 노출할 Behavior의 기준
```

예를 들어 후속 모듈에서는 다음과 같은 Behavior Definition 개념을 만나게 된다.

```abap
define behavior for ZI_GPT_Order alias Order
  persistent table zgpt_order
  lock master
  authorization master ( instance )
{
  create;
  update;
  delete;
}
```

그리고 Projection 계층에서도 소비자에게 노출할 동작을 제한하거나 공개하는 설계를 하게 된다.

이번 모듈에서는 Behavior 문법을 작성하지 않아도 된다.  
다만 Projection View가 후속 Behavior Projection과 Service Definition의 기준 모델이 된다는 점을 이해해야 한다.

## 20. Projection View와 Service Definition의 연결

Service Definition은 어떤 CDS View를 서비스로 노출할지 결정한다.  
일반적으로 외부 서비스에는 Interface View보다 Projection View를 노출하는 방식이 적절하다.

예를 들어 후속 모듈에서 다음과 같은 Service Definition을 만들 수 있다.

```abap
@EndUserText.label: 'Order Service Definition'
define service ZUI_GPT_ORDER {
  expose ZC_GPT_Order as Order;
  expose ZC_GPT_OrderItem as OrderItem;
}
```

이 구조에서 핵심은 다음이다.

```text
Service Definition은 ZI_*가 아니라 ZC_*를 노출한다.
```

왜냐하면 `ZC_*`가 외부 소비를 위해 설계된 모델이기 때문이다.

## 21. 정상 흐름

Projection View 생성의 정상 흐름은 다음과 같다.

```text
1. ZI_* Interface View가 Active 상태인지 확인한다.
2. Root Projection View ZC_*를 생성한다.
3. provider contract transactional_query를 지정한다.
4. as projection on ZI_*를 작성한다.
5. 노출할 필드를 선별한다.
6. Root의 Composition Association을 Child Projection으로 Redirect한다.
7. Child Projection View ZC_*를 생성한다.
8. Child의 Parent Association을 Root Projection으로 Redirect한다.
9. Syntax Check를 수행한다.
10. Activate한다.
11. Activation 오류가 없으면 후속 Behavior Definition으로 이동한다.
```

## 22. 자주 발생하는 오류와 해결

### 22.1 기반 Interface View가 활성화되어 있지 않음

| 항목 | 내용 |
|---|---|
| 현상 | `as projection on ZI_GPT_Order`에서 대상 View를 찾지 못하거나 활성화 실패 |
| 원인 | `ZI_GPT_Order`가 미생성 또는 비활성 상태 |
| 해결 | 먼저 `ZI_GPT_Order`, `ZI_GPT_OrderItem`을 활성화한다. |

### 22.2 Projection 대상 이름 오타

| 항목 | 내용 |
|---|---|
| 현상 | 대상 CDS View Entity를 찾을 수 없음 |
| 원인 | `ZI_GPT_Order` 대신 `Zl_GPT_Order`, `ZI_GTP_Order` 등 오타 |
| 해결 | ADT Repository 검색 또는 Project Explorer에서 정확한 객체명을 확인한다. |

### 22.3 Key 누락

| 항목 | 내용 |
|---|---|
| 현상 | Projection View 활성화 오류 또는 RAP 후속 단계에서 식별 문제 |
| 원인 | 기반 View의 Key를 Projection에서 누락 |
| 해결 | Root와 Child Projection에서 필요한 Key 필드를 명확히 노출한다. |

### 22.4 Association Redirection 누락

| 항목 | 내용 |
|---|---|
| 현상 | Composition Navigation이 소비 계층에서 제대로 연결되지 않음 |
| 원인 | `_Item : redirected to composition child ...` 또는 `_Order : redirected to parent ...` 누락 |
| 해결 | Root/Child 양쪽 Projection View에서 Redirection을 정의한다. |

### 22.5 Association Alias 불일치

| 항목 | 내용 |
|---|---|
| 현상 | `_Item` 또는 `_Order`를 찾을 수 없음 |
| 원인 | Interface View에서 정의한 Association Alias와 Projection에서 사용한 이름이 다름 |
| 해결 | Interface View의 Association Alias를 확인하고 동일한 이름을 사용한다. |

### 22.6 Provider Contract 누락 또는 부적절

| 항목 | 내용 |
|---|---|
| 현상 | RAP Projection View로 사용하기에 적합하지 않은 설정 또는 활성화 오류 |
| 원인 | Transactional Projection View에서 필요한 Provider Contract 누락 |
| 해결 | RAP Managed Scenario의 소비 Projection으로 사용할 경우 `provider contract transactional_query`를 적용한다. |

### 22.7 너무 많은 필드 노출

| 항목 | 내용 |
|---|---|
| 현상 | 기술 필드와 내부 필드가 외부 API/UI에 그대로 노출 |
| 원인 | Interface View의 필드를 무비판적으로 모두 Projection에 포함 |
| 해결 | 소비자 관점에서 필요한 필드만 선별하고, 민감/내부 필드는 제외한다. |

## 23. 실무 설계 기준

### 23.1 Projection View는 API 계약에 가깝다

Projection View는 단순한 조회 View가 아니라 외부 소비 모델이다.  
서비스로 노출되면 외부 소비자는 이 모델을 기준으로 개발하게 된다.

따라서 다음을 신중히 판단해야 한다.

```text
필드명을 나중에 바꿔도 되는가?
이 필드를 외부 소비자가 의존하게 해도 되는가?
기술 필드를 외부 API 계약에 포함해도 되는가?
Association을 공개하면 외부 Navigation 계약이 생기는가?
```

### 23.2 내부 모델과 외부 모델을 분리한다

`ZI_*`를 직접 서비스에 노출하면 내부 모델 변경이 외부 소비자에게 바로 영향을 줄 수 있다.  
Projection View는 이 영향을 완충하는 역할을 한다.

```text
내부 모델 변경
  → ZI_* 수정
  → ZC_*에서 외부 계약 유지 여부 판단
  → 서비스 소비자 영향 최소화
```

### 23.3 Projection View에 모든 Annotation을 몰아넣지 않는다

UI Annotation을 Projection View 본문에 직접 작성할 수도 있지만, 규모가 커지면 View가 복잡해질 수 있다.  
실무에서는 Metadata Extension을 활용해 UI 표현 Annotation을 분리하는 방식을 검토한다.

초급 단계에서는 다음 원칙만 기억한다.

```text
Projection View는 소비 계층이다.
UI Annotation과 가까운 계층이지만, UI 표현은 Metadata Extension으로 분리할 수 있다.
```

### 23.4 권한 설계를 교육용 설정으로 일반화하지 않는다

교육용 예제에서는 `@AccessControl.authorizationCheck: #NOT_REQUIRED`를 사용할 수 있다.  
그러나 운영 시스템에서는 권한 설계가 필수일 수 있다.

```text
교육용:
  #NOT_REQUIRED로 단순화 가능

실무:
  Access Control, Authorization, CDS Role, RAP Authorization을 검토
```

| 필드 노출 범위 | 불필요한 내부 필드가 과도하게 노출되지 않았는지 확인 |
| 후속 준비 | `ZC_*`가 Service Definition에서 노출 가능하도록 준비되었는지 확인 |

## 27. 평가 문제

### 27.1 객관식

#### Q1. Projection View `ZC_*`의 가장 적절한 역할은?

A. DB Table의 물리 저장소를 생성한다.  
B. Interface View를 기반으로 외부 소비 모델을 정의한다.  
C. ABAP Class의 Method 구현을 담당한다.  
D. Transport Request를 자동 생성한다.

정답: B

#### Q2. Projection View에서 주로 사용하는 문법은?

A. `as select from`  
B. `as projection on`  
C. `insert into`  
D. `call function`

정답: B

#### Q3. Root Projection View에서 Child Projection으로 Composition을 연결할 때 사용하는 표현은?

A. `redirected to composition child`  
B. `association to database table`  
C. `select-options for child`  
D. `lock master`

정답: A

#### Q4. Service Definition에서 일반적으로 노출하기 적절한 View는?

A. 내부 Interface View `ZI_*`  
B. 외부 소비 Projection View `ZC_*`  
C. DB Table `ZT_*`  
D. Behavior Implementation Class

정답: B

### 27.2 단답형

#### Q1. Interface View와 Projection View의 차이를 한 문장으로 설명하시오.

모범 답안:  
Interface View는 RAP Business Object의 내부 데이터 모델을 정의하고, Projection View는 그 내부 모델을 외부 소비자에게 노출할 형태로 선별·투영한다.

#### Q2. Association Redirection이 필요한 이유를 설명하시오.

모범 답안:  
Projection 계층에서는 외부 소비자가 `ZC_*` 모델을 기준으로 탐색해야 하므로, Interface View의 Association을 그대로 노출하지 않고 Projection View 간 관계로 다시 연결해야 한다.

#### Q3. Projection View에서 모든 필드를 무조건 노출하지 않는 이유는 무엇인가?

모범 답안:  
Projection View는 외부 소비 모델이므로 내부 기술 필드, 민감 정보, 소비자에게 불필요한 필드를 노출하면 API 계약이 불필요하게 커지고 보안·유지보수 문제가 생길 수 있기 때문이다.

## 28. 초급자 핵심 요약

이번 모듈에서 반드시 기억할 내용은 다음이다.

```text
Projection View ZC_*는 RAP의 소비 계층 View이다.
Projection View는 Interface View ZI_*를 기반으로 만든다.
ZI_*는 내부 데이터 모델이고, ZC_*는 외부 소비 모델이다.
Projection View에서는 필요한 필드와 Association만 선별해 노출한다.
Root/Child 관계는 Projection 계층에서 Redirection으로 다시 연결해야 한다.
Service Definition에는 일반적으로 ZC_* Projection View를 노출한다.
```
