## 2. 선수 지식

RAP는 Track 1의 후반부에 배치되어 있다. 이유는 RAP가 단일 문법이 아니라 여러 ABAP 기술의 조합이기 때문이다.

이번 모듈을 제대로 이해하려면 다음 선행 지식이 필요하다.

| 선수 지식 | 필요한 이유 |
|---|---|
| DDIC 기본 | RAP의 영속 테이블과 데이터 타입 기반을 이해하기 위해 필요하다. |
| ABAP 기본 문법 | 클래스, 메서드, 데이터 선언, SQL 결과 처리를 이해하기 위해 필요하다. |
| Open SQL | RAP의 데이터 조회와 영속성 계층을 이해하기 위해 필요하다. |
| Internal Table | 데이터 처리 흐름과 결과 구조를 이해하기 위해 필요하다. |
| OO ABAP | Behavior Implementation이 ABAP Class 기반으로 동작하기 때문에 필요하다. |
| CDS View Entity | RAP의 데이터 모델이 CDS View Entity를 중심으로 구성되기 때문에 필요하다. |

초급자는 다음 문장을 기억하면 된다.

> RAP는 CDS, OO ABAP, OData, 서비스 노출, 트랜잭션 처리 개념이 결합된 현대식 ABAP 애플리케이션 개발 모델이다.

## 3. RAP란 무엇인가?

RAP는 **ABAP RESTful Application Programming Model**의 약자이다.  
SAP가 ABAP 기반 비즈니스 애플리케이션을 현대적인 방식으로 만들기 위해 제공하는 개발 모델이다.

초급자 관점에서는 다음처럼 정의할 수 있다.

```text
RAP = ABAP에서 비즈니스 객체를 모델링하고,
      CRUD 동작과 검증 로직을 정의하며,
      OData 서비스로 노출할 수 있게 해주는 표준 개발 모델
```

과거 ABAP 개발에서는 화면, 데이터 조회, 저장 로직, 검증 로직, 서비스 노출 로직이 여러 기술로 분산되어 있었다. 예를 들어 다음과 같은 조합이 흔했다.

```text
Transparent Table
+ Function Module
+ Module Pool 또는 Report
+ BAPI
+ Gateway SEGW
+ 별도 검증 로직
+ 별도 권한 로직
```

이 방식은 강력하지만, 신규 서비스 기반 애플리케이션을 만들 때 구조가 복잡해지기 쉽다. RAP는 이 흐름을 더 명확한 계층으로 나누어 관리한다.

---

## 4. RAP가 필요한 이유

### 4.1 Fiori / OData 중심 개발 흐름

현대 SAP 애플리케이션은 SAP GUI 화면만을 대상으로 하지 않는다. Fiori Elements, SAPUI5, 외부 시스템, 모바일 앱 등 다양한 소비자가 백엔드 서비스를 사용한다.

따라서 백엔드 개발자는 단순히 Report 화면을 만드는 것이 아니라, 다음을 고려해야 한다.

| 요구 | 설명 |
|---|---|
| 서비스 노출 | 데이터를 OData 서비스로 제공해야 한다. |
| 표준 CRUD | 조회, 생성, 수정, 삭제가 일관된 방식으로 동작해야 한다. |
| 트랜잭션 처리 | 저장 시점, 검증, 메시지 처리가 안정적이어야 한다. |
| UI 메타데이터 | Fiori Elements가 사용할 수 있는 의미 정보가 필요하다. |
| 확장성 | Clean Core 방향에 맞게 표준과 커스텀을 분리해야 한다. |

RAP는 이 요구를 ABAP Platform 안에서 표준 구조로 처리하기 위한 모델이다.

### 4.2 개발 객체 간 역할 분리

RAP는 객체 역할을 비교적 명확하게 분리한다.

| 역할 | RAP 객체 |
|---|---|
| 데이터 모델 | CDS View Entity, Root View, Association, Composition |
| 동작 모델 | Behavior Definition, Behavior Implementation |
| 서비스 노출 | Service Definition, Service Binding |
| UI 의미 | CDS Annotation, Metadata Extension |
| 영속성 | Database Table 또는 기존 API/Legacy Logic |

초급자가 RAP를 어렵게 느끼는 이유는 객체가 많기 때문이다. 하지만 객체가 많은 이유는 “복잡한 것을 복잡하게 만들기 위해서”가 아니라, **역할을 분리해 유지보수성을 높이기 위해서**이다.

## 5. RAP 전체 아키텍처 큰 그림

RAP를 처음 볼 때는 아래 흐름을 먼저 이해해야 한다.

```text
[Database Table]
      ↓
[CDS Interface View: ZI_*]
      ↓
[CDS Projection View: ZC_*]
      ↓
[Behavior Definition: BDEF]
      ↓
[Behavior Implementation: ABAP Class]
      ↓
[Service Definition]
      ↓
[Service Binding]
      ↓
[OData V4 Service / Fiori Elements]
```

이 흐름을 계층별로 다시 정리하면 다음과 같다.

| 계층 | 대표 객체 | 역할 |
|---|---|---|
| Persistence Layer | DB Table | 실제 데이터 저장 |
| Data Model Layer | Interface View `ZI_*` | 비즈니스 객체의 핵심 데이터 모델 |
| Consumption Layer | Projection View `ZC_*` | 외부 소비자에게 노출할 모델 정리 |
| Behavior Layer | Behavior Definition / Implementation | CRUD, Validation, Determination, Action 등 동작 정의 |
| Service Layer | Service Definition / Binding | OData 서비스로 노출 |
| UI Layer | Fiori Elements / SAPUI5 | 사용자가 보는 화면 |

초급자는 이 표를 반복해서 봐야 한다. RAP는 단일 객체를 만드는 기술이 아니라 **계층형 애플리케이션 모델**이다.

## 6. Business Object란 무엇인가?

RAP에서 가장 중요한 개념은 **Business Object**이다.

Business Object는 단순 테이블이 아니다.  
업무적으로 의미 있는 데이터를 구조화하고, 그 데이터에 대해 허용되는 동작을 함께 정의한 모델이다.

예를 들어 “여행 예약”이라는 업무 객체가 있다고 하자.

```text
Travel
 ├─ Booking
 └─ Supplement
```

이때 Travel은 단순히 DB 테이블 하나가 아니라 다음을 포함할 수 있다.

| 구성 | 설명 |
|---|---|
| Root Entity | Business Object의 중심 엔티티 |
| Child Entity | Root에 종속되는 하위 엔티티 |
| Association | 엔티티 간 탐색 관계 |
| Composition | 생명주기를 공유하는 포함 관계 |
| Behavior | 생성, 수정, 삭제, 검증, 액션 등 |
| Service Exposure | 외부 소비자에게 노출되는 방식 |

초급자에게는 다음 비유가 유용하다.

```text
DB Table = 데이터를 담는 표
Business Object = 데이터 + 관계 + 동작 + 서비스 노출의 업무 단위
```

---

## 7. Business Object와 Entity

RAP Business Object는 보통 하나 이상의 Entity로 구성된다.

| 용어 | 의미 |
|---|---|
| Entity | CDS View Entity 기반의 데이터 단위 |
| Root Entity | Business Object의 시작점이 되는 중심 Entity |
| Child Entity | Root Entity에 종속되거나 연관된 하위 Entity |
| Association | 한 Entity에서 다른 Entity로 탐색하는 관계 |
| Composition | 부모-자식 생명주기를 함께 관리하는 강한 관계 |

예를 들어 교육용 주문 객체를 생각해보자.

```text
Sales Order BO
 ├─ Sales Order Header   (Root Entity)
 └─ Sales Order Item     (Child Entity)
```

Header가 삭제되면 Item도 함께 의미를 잃는다. 이런 경우에는 Composition 관계로 모델링할 수 있다.

이번 M01에서는 Association과 Composition을 깊게 구현하지 않는다.  
다만 RAP Business Object는 보통 Root와 Child의 구조를 가질 수 있다는 점만 이해하면 된다.

## 8. Interface View `ZI_*`의 위치

RAP에서 `ZI_*`는 보통 Interface View를 의미하는 이름 규칙으로 사용한다.

Interface View는 Business Object의 핵심 데이터 모델을 정의한다.  
즉, DB 테이블을 직접 서비스로 노출하지 않고, CDS View Entity를 통해 의미 있는 모델로 감싼다.

예시 이름:

```text
ZI_GPT_TRAVEL
ZI_GPT_BOOKING
```

Interface View는 다음 역할을 가진다.

| 역할 | 설명 |
|---|---|
| DB Table 추상화 | 실제 테이블 구조를 그대로 외부에 노출하지 않는다. |
| Key 정의 | Business Object의 식별 기준을 명확히 한다. |
| Association / Composition | 엔티티 관계를 모델링한다. |
| Semantic Annotation | 금액, 통화, 단위, 텍스트 등 의미를 부여한다. |
| Behavior 대상 | Root View가 Behavior Definition의 대상이 된다. |

중요한 점은 `ZI_*`가 “내부 모델”에 가깝다는 것이다. 외부 소비자에게 직접 노출하기보다, Projection View를 통해 필요한 형태로 정리하는 것이 일반적이다.

---

## 9. Projection View `ZC_*`의 위치

`ZC_*`는 보통 Projection View 또는 Consumption View 성격의 객체 이름으로 사용한다.

Projection View는 Interface View를 외부 소비자에게 노출하기 적합한 형태로 정리한다.

예시 이름:

```text
ZC_GPT_TRAVEL
ZC_GPT_BOOKING
```

Projection View의 역할은 다음과 같다.

| 역할 | 설명 |
|---|---|
| 외부 노출 모델 | UI나 OData 서비스에서 소비할 모델을 정리한다. |
| 필드 선택 | 외부에 필요한 필드만 노출할 수 있다. |
| Annotation 분리 | UI 관련 Annotation을 별도 계층으로 둘 수 있다. |
| 보안/확장성 | 내부 모델과 외부 소비 모델을 분리한다. |

초급자가 기억해야 할 구조는 다음이다.

```text
ZI_* = 핵심 비즈니스 모델
ZC_* = 소비자에게 보여줄 노출 모델
```

> 이 프로젝트의 RAP 예제에서는 Interface View는 `ZI_*`, Projection View는 `ZC_*` 형태로 함께 제공하는 것을 기본 원칙으로 한다.

## 10. Behavior Definition이란 무엇인가?

RAP의 Behavior Definition은 Business Object가 어떤 동작을 지원하는지 선언하는 객체이다.

예를 들어 다음 질문에 답한다.

```text
이 객체는 생성 가능한가?
수정 가능한가?
삭제 가능한가?
Draft를 지원하는가?
Validation이 있는가?
Determination이 있는가?
Action이 있는가?
Lock 처리 방식은 무엇인가?
```

초급자는 Behavior Definition을 다음처럼 이해하면 된다.

```text
Behavior Definition = Business Object의 사용 가능한 동작 계약서
```

예시 개념:

```abap
managed implementation in class zbp_i_gpt_travel unique;
strict ( 2 );

define behavior for ZI_GPT_TRAVEL alias Travel
persistent table zt_gpt_travel
lock master
authorization master ( instance )
{
  create;
  update;
  delete;
}
```

위 예시는 전체 구현을 설명하기 위한 것이 아니라, Behavior Definition이 “CRUD와 동작 규칙을 선언한다”는 감각을 주기 위한 예시이다.

`strict(2)`와 세부 문법은 `THEORY-21-M04`에서 다룬다.

---

## 11. Behavior Implementation이란 무엇인가?

Behavior Definition이 동작을 “선언”한다면, Behavior Implementation은 필요한 로직을 ABAP Class로 “구현”한다.

예를 들어 다음과 같은 로직이 있을 수 있다.

| 로직 | 설명 |
|---|---|
| Validation | 저장 전 입력값을 검증한다. |
| Determination | 특정 필드 값을 자동 계산하거나 채운다. |
| Action | 사용자가 명시적으로 실행하는 업무 동작이다. |
| Feature Control | 상황에 따라 버튼이나 필드 동작을 제어한다. |
| Authorization | 인스턴스 단위 권한 판단을 구현할 수 있다. |

초급자는 다음 구분을 기억하면 된다.

```text
Behavior Definition = 무엇을 할 수 있는지 선언
Behavior Implementation = 필요한 경우 그 동작의 세부 로직 구현
```

Managed Scenario에서는 기본 CRUD 저장 처리의 많은 부분을 RAP Framework가 처리한다. 개발자는 필요한 검증, 자동계산, 액션 등을 구현한다.

## 12. Service Definition과 Service Binding

RAP Business Object를 외부에서 사용하려면 서비스로 노출해야 한다.

이때 사용하는 객체가 Service Definition과 Service Binding이다.

### 12.1 Service Definition

Service Definition은 어떤 CDS Projection View를 서비스에 포함할지 정의한다.

예시 개념:

```abap
define service ZUI_GPT_TRAVEL {
  expose ZC_GPT_TRAVEL as Travel;
  expose ZC_GPT_BOOKING as Booking;
}
```

초급자는 다음처럼 이해하면 된다.

```text
Service Definition = 어떤 엔티티를 서비스로 노출할지 선언하는 목록
```

### 12.2 Service Binding

Service Binding은 Service Definition을 실제 프로토콜 형태로 바인딩한다.  
RAP에서는 보통 OData V4 기반으로 서비스를 노출한다.

```text
Service Definition
  → Service Binding
  → OData V4 Endpoint
  → Fiori Elements Preview / 외부 소비자
```

초급자는 다음처럼 기억하면 된다.

```text
Service Binding = 선언된 서비스를 실제로 실행 가능한 OData 서비스로 만드는 단계
```

Service Definition과 Service Binding은 `THEORY-21-M06`에서 자세히 다룬다.

## 13. Managed Scenario란 무엇인가?

RAP에서 자주 만나는 용어가 Managed Scenario이다.

Managed Scenario는 RAP Framework가 기본 영속성 처리와 트랜잭션 처리의 많은 부분을 관리하는 개발 방식이다.

초급자 관점에서는 다음처럼 정의할 수 있다.

```text
Managed Scenario = CRUD와 저장 흐름의 많은 부분을 RAP Framework가 관리하는 방식
```

Managed Scenario에서는 일반적으로 다음 구성이 사용된다.

| 구성 | 설명 |
|---|---|
| Persistent Table | 실제 데이터를 저장하는 DB 테이블 |
| CDS Root View | Business Object의 Root Entity |
| Behavior Definition | Managed 방식의 CRUD 동작 선언 |
| Behavior Pool Class | 필요한 확장 로직 구현 |
| Service Binding | OData 서비스 노출 |

Managed Scenario의 장점은 다음과 같다.

| 장점 | 설명 |
|---|---|
| 표준화 | RAP Framework가 일관된 트랜잭션 흐름을 제공한다. |
| 생산성 | 기본 CRUD 처리를 직접 모두 작성하지 않아도 된다. |
| Fiori 연계 | Fiori Elements와 잘 연결된다. |
| 학습 적합성 | 초급자가 RAP 구조를 익히기에 상대적으로 적합하다. |

---

## 14. Managed와 Unmanaged의 큰 차이

RAP에는 Managed Scenario와 Unmanaged Scenario가 있다.

| 구분 | Managed Scenario | Unmanaged Scenario |
|---|---|---|
| 기본 CRUD 처리 | Framework가 많이 담당 | 개발자가 직접 구현해야 하는 비중이 큼 |
| 영속성 | 보통 Persistent Table 기반 | 기존 API, Legacy Logic, 복잡한 저장 로직 가능 |
| 초급 학습 적합성 | 높음 | 낮음 |
| 사용 목적 | 신규 RAP BO 개발에 적합 | 기존 로직 재사용 또는 특수 저장 시나리오에 적합 |
| 구현 난이도 | 상대적으로 낮음 | 상대적으로 높음 |

초급자는 RAP를 처음 배울 때 Managed Scenario부터 시작하는 것이 좋다.

Unmanaged Scenario는 기존 BAPI, Function Module, Legacy 저장 로직을 감싸야 하는 경우에 유용하지만, 초급 단계에서는 동작 구조가 복잡해질 수 있다.

> [추정] 교육 과정에서는 첫 RAP 실습을 Managed Scenario로 시작하고, Unmanaged Scenario는 Track 2 또는 실무 응용 영역에서 다루는 편이 학습 부담을 줄인다.

## 15. RAP 객체 생성 순서

RAP는 객체가 많기 때문에 순서를 지키는 것이 중요하다.

```text
1. Persistent Table 준비
2. Interface Root View ZI_* 생성

5. Behavior Definition 생성
6. Behavior Implementation 생성
7. Service Definition 생성
8. Service Binding 생성
```

| M03 | Projection View `ZC_*` 설계 | 소비 모델 |

## 16. RAP와 ABAP Cloud

RAP는 ABAP Cloud와 밀접하게 연결된다.

ABAP Cloud는 Clean Core, Released API, Cloud-ready 개발 원칙을 강조한다. RAP는 이런 방향에 맞는 현대 ABAP 애플리케이션 개발 모델이다.

초급자는 다음 정도로 이해하면 충분하다.

| 개념 | 의미 |
|---|---|
| RAP | ABAP 기반 비즈니스 객체와 서비스를 만드는 개발 모델 |
| ABAP Cloud | 클라우드 친화적이고 업그레이드 안정적인 ABAP 개발 모델 |
| Released API | 사용이 허용된 안정적인 SAP API |
| Clean Core | 표준 코어를 직접 수정하지 않고 확장과 API 중심으로 개발하는 원칙 |

RAP를 배운다는 것은 단순히 새로운 문법을 배우는 것이 아니라, SAP가 권장하는 미래형 ABAP 개발 흐름에 익숙해지는 것이다.

## 17. 초급자가 가장 많이 혼동하는 지점

### 17.1 CDS View와 RAP는 같은가?

아니다.  
CDS View는 RAP의 데이터 모델을 구성하는 중요한 요소이지만, RAP 전체는 CDS만으로 끝나지 않는다.

```text
CDS View Entity = 데이터 모델
RAP = 데이터 모델 + 동작 모델 + 서비스 노출 + 트랜잭션 처리
```

### 17.2 Projection View만 만들면 서비스가 되는가?

아니다.  
Projection View는 외부 소비 모델을 정의하지만, 실제 서비스 노출을 위해서는 Service Definition과 Service Binding이 필요하다.

### 17.3 Behavior Definition만 만들면 로직이 실행되는가?

부분적으로만 맞다.  
Behavior Definition은 동작을 선언한다. 검증, 자동 계산, 액션 같은 커스텀 로직은 Behavior Implementation에서 구현해야 한다.

### 17.4 Managed Scenario는 코딩이 전혀 필요 없는가?

아니다.  
기본 CRUD 흐름은 Framework가 많이 처리하지만, 업무 검증, 자동 값 채움, 액션, 권한 로직 등은 여전히 개발자가 구현할 수 있다.

### 17.5 RAP는 SAP GUI 개발을 완전히 대체하는가?

아니다.  
RAP는 현대 서비스 기반 개발에 적합하지만, 기존 SAP GUI Report, Dynpro, ALV 개발은 여전히 많은 시스템에서 사용된다. 다만 신규 Fiori/OData 중심 개발에서는 RAP의 중요성이 커진다.

## 20. 정상 흐름과 오류 흐름

### 20.1 정상 흐름

```text
DB Table 준비
→ ZI_* Root View 생성
→ ZC_* Projection View 생성
→ Behavior Definition 생성
→ Behavior Implementation 필요한 로직 작성
→ Service Definition 생성
→ Service Binding 생성
→ Preview 또는 OData 호출 확인
```

### 20.2 오류 흐름

| 단계 | 대표 오류 | 초급자 확인 포인트 |
|---|---|---|
| CDS View 생성 | Syntax Error | 필드명, Key, Association 문법 확인 |
| Projection View 생성 | Source View 참조 오류 | ZI_*가 활성화되었는지 확인 |
| Behavior Definition | Entity 이름 불일치 | Root Entity와 Alias 확인 |
| Behavior Implementation | Method 시그니처 불일치 | ADT Quick Fix와 생성된 메서드 확인 |
| Service Definition | Expose 대상 오류 | ZC_* Projection View가 활성화되었는지 확인 |
| Service Binding | Activation 실패 | 서비스 타입, 권한, Gateway/OData 상태 확인 |

초급자는 오류가 발생했을 때 “RAP 전체가 어렵다”고 생각하기보다, 어느 계층에서 오류가 났는지를 먼저 분리해야 한다.

## 22. 평가 문제

### 22.1 객관식

#### Q1. RAP의 가장 적절한 설명은?

A. SAP GUI 화면 색상을 설정하는 도구이다.  
B. ABAP에서 비즈니스 객체와 서비스를 만들기 위한 현대적 개발 모델이다.  
C. 데이터베이스 백업 전용 트랜잭션이다.  
D. 오직 Report 출력만을 위한 문법이다.

정답: B

#### Q2. RAP Business Object에 대한 설명으로 올바른 것은?

A. 단순히 DB 테이블 하나만 의미한다.  
B. 데이터 모델과 동작 모델을 함께 포함할 수 있는 업무 단위이다.  
C. 반드시 SAP GUI Dynpro만으로 실행된다.  
D. Behavior Definition 없이 항상 완성된다.

정답: B

#### Q3. Managed Scenario의 특징으로 가장 적절한 것은?

A. 모든 저장 로직을 개발자가 직접 처음부터 구현해야 한다.  
B. RAP Framework가 기본 CRUD와 트랜잭션 처리의 많은 부분을 관리한다.  
C. OData 서비스로 노출할 수 없다.  
D. CDS View Entity를 사용할 수 없다.

정답: B

### 22.2 서술형

#### Q1. `ZI_*`와 `ZC_*`의 역할 차이를 설명하시오.

모범 답안:  
`ZI_*`는 Business Object의 핵심 데이터 모델을 정의하는 Interface View 성격이며, DB 테이블과 비즈니스 의미를 연결한다. `ZC_*`는 외부 소비자에게 노출할 형태를 정리하는 Projection View 성격이며, UI나 OData 서비스에서 사용할 소비 모델을 구성한다.

#### Q2. Behavior Definition과 Behavior Implementation의 차이를 설명하시오.

모범 답안:  
Behavior Definition은 Business Object가 지원하는 create, update, delete, validation, action 등의 동작 계약을 선언한다. Behavior Implementation은 필요한 경우 이 동작의 세부 로직을 ABAP Class로 구현한다.

#### Q3. RAP를 처음 배울 때 객체 생성 순서를 이해해야 하는 이유를 설명하시오.

모범 답안:  
RAP는 DB Table, CDS Interface View, Projection View, Behavior Definition, Implementation, Service Definition, Service Binding 등 여러 객체가 계층적으로 연결된다. 선행 객체가 활성화되지 않거나 이름이 맞지 않으면 후속 객체 생성과 활성화가 실패할 수 있으므로 생성 순서를 이해해야 한다.
