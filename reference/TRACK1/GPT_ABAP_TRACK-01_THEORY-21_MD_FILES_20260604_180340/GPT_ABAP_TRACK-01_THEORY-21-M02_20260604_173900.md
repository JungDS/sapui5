## 2. 선수 지식

RAP Interface View는 CDS View Entity 기반으로 작성된다. 따라서 다음 선행 지식이 필요하다.

| 선수 지식 | 필요한 이유 |
|---|---|
| DDIC Transparent Table | Interface View는 영속 테이블 또는 기존 데이터 소스를 기반으로 한다. |
| CDS View Entity | `define root view entity`, `association`, `composition` 문법을 이해해야 한다. |
| Open SQL 기본 | CDS 결과가 ABAP SQL 관점에서 어떻게 소비되는지 이해하는 데 도움이 된다. |
| OO ABAP 기본 | 후속 Behavior Implementation이 ABAP Class 기반으로 구현된다. |
| RAP 아키텍처 개요 | Interface View가 RAP 계층 중 어디에 위치하는지 알아야 한다. |

초급자는 다음 문장을 기억하면 된다.

> RAP Interface View는 Business Object의 내부 데이터 모델을 정의하는 CDS View Entity 계층이다.

## 3. Interface View란 무엇인가?

Interface View는 RAP Business Object의 기본 데이터 모델을 정의하는 CDS View Entity이다. 일반적으로 객체명은 `ZI_*` 형태를 사용한다.

예를 들어 교육용 주문 비즈니스 객체를 만든다면 다음과 같은 객체명을 사용할 수 있다.

```text
ZI_GPT_ORDER      Root Interface View
ZI_GPT_ORDERITEM  Child Interface View
```

여기서 `ZI_`는 Interface View를 의미하는 교육용 네이밍 Prefix이다. 실제 프로젝트에서는 고객사 또는 프로젝트 네이밍 규칙을 우선해야 한다.

Interface View의 역할은 다음과 같다.

| 역할 | 설명 |
|---|---|
| 내부 데이터 모델 정의 | RAP Business Object가 어떤 필드와 관계를 가지는지 정의한다. |
| 영속 테이블 추상화 | DB 테이블을 직접 노출하지 않고 CDS 계층으로 감싼다. |
| Root/Child 노드 구성 | Business Object의 노드 구조를 정의한다. |
| Composition 관계 표현 | Header-Item 같은 생명주기 종속 관계를 모델링한다. |
| Behavior Definition의 기반 | 후속 BDEF가 어떤 CDS View를 기준으로 동작할지 결정한다. |
| Projection View의 원천 | `ZC_*` Projection View가 Interface View를 소비한다. |

---

## 4. Interface View와 Projection View의 차이

RAP 학습 초급자가 가장 자주 혼동하는 부분은 `ZI_*`와 `ZC_*`의 차이이다.

| 구분 | Interface View `ZI_*` | Projection View `ZC_*` |
|---|---|---|
| 주 목적 | 내부 데이터 모델 정의 | 외부 소비 모델 정의 |
| 위치 | Business Object 내부 계층 | Service/UI 노출 계층 |
| 일반 Prefix | `ZI_` | `ZC_` |
| Root 여부 | Root/Child 노드의 원본 | Interface View를 Projection |
| Composition | 실제 BO 구조 표현 | 소비자에게 노출할 구조 선택 |
| Behavior 연결 | Interface Behavior Definition의 기반 | Projection Behavior Definition 또는 서비스 노출 기반 |
| 설계 관점 | 안정적, 내부적, 재사용 가능 | 소비자 친화적, UI/API 지향 |

초급자는 다음처럼 이해하면 된다.

```text
ZI_* = 내부 모델, BO의 뼈대
ZC_* = 외부 소비 모델, 서비스/UI에 보여줄 모양
```

이번 모듈에서는 `ZI_*`만 만든다. `ZC_*`는 다음 모듈에서 다룬다.

## 5. 왜 DB 테이블을 바로 노출하지 않는가?

초급자는 “DB 테이블이 이미 있는데 왜 CDS Interface View를 다시 만드는가?”라고 질문할 수 있다.

RAP에서 DB 테이블을 바로 서비스로 노출하지 않고 Interface View를 두는 이유는 다음과 같다.

| 이유 | 설명 |
|---|---|
| 추상화 | DB 구조를 직접 외부에 노출하지 않는다. |
| 의미 부여 | 필드 Alias, Semantic Annotation, Association으로 업무 의미를 표현한다. |
| 안정성 | DB 테이블 변경과 외부 서비스 구조를 분리할 수 있다. |
| 재사용성 | 같은 Interface View를 여러 Projection이나 서비스에서 사용할 수 있다. |
| RAP Behavior 기반 | Behavior Definition이 CDS View Entity를 기준으로 연결된다. |
| Clean Core | 표준 확장과 고객 개발 객체를 명확히 분리하는 데 유리하다. |

실무 관점에서 Interface View는 DB 테이블과 서비스 사이의 완충 계층이다. 이 계층을 잘 설계하면 후속 UI, API, Behavior 확장이 훨씬 안정적이다.

## 6. RAP Business Object와 Root View

### 6.1 Root View의 의미

Root View는 RAP Business Object의 최상위 노드를 나타내는 Interface View이다.

예를 들어 주문 객체는 일반적으로 Header와 Item으로 구성된다.

```text
Order Header
 └─ Order Item
```

이 구조에서 Header가 Root이다.

```text
Root View:  ZI_GPT_ORDER
Child View: ZI_GPT_ORDERITEM
```

Root View는 Business Object의 대표 노드로서 다음 역할을 가진다.

| 역할 | 설명 |
|---|---|
| 객체 식별 | Business Object의 시작점이다. |
| Composition 소유 | 하위 Child Node를 포함한다. |
| Behavior 기준 | Managed Scenario에서 Root Behavior의 중심이 된다. |
| Service 진입점 | 후속 Projection/Service 노출의 기준이 된다. |

### 6.2 Root View 선언 문법

CDS View Entity에서 Root View는 다음처럼 선언한다.

```abap
@AccessControl.authorizationCheck: #NOT_REQUIRED
@EndUserText.label: 'Order Root Interface View'
define root view entity ZI_GPT_Order
  as select from zgpt_order
{
  key order_uuid        as OrderUUID,
      order_id          as OrderID,
      customer_id       as CustomerID,
      order_date        as OrderDate,
      currency_code     as CurrencyCode,
      gross_amount      as GrossAmount,
      created_by        as CreatedBy,
      created_at        as CreatedAt,
      last_changed_by   as LastChangedBy,
      last_changed_at   as LastChangedAt
}
```

이 예시는 가장 기본 형태이다. 아직 Composition은 없다. Composition은 Child View를 만든 뒤 Root View에 추가한다.

## 7. Root View 설계 시 Key 판단

RAP Interface View에서 Key 설계는 매우 중요하다.

### 7.1 Technical Key와 Semantic Key

실무 RAP 모델에서는 기술적으로 안정적인 Key와 업무적으로 읽기 쉬운 Key를 구분하는 것이 좋다.

| 구분 | 예시 | 설명 |
|---|---|---|
| Technical Key | `OrderUUID` | 시스템 내부 식별용. 변경되지 않는 고유 키. |
| Semantic Key | `OrderID` | 사용자가 인식하는 업무 번호. |

초급자는 처음에 `OrderID`만 Key로 쓰고 싶어질 수 있다. 그러나 RAP Managed Scenario에서는 UUID 기반 기술 키를 사용하는 설계가 자주 사용된다.

[추정] 교육용 단순 시스템에서는 `OrderID`를 Key로 사용해도 개념 설명은 가능하다. 다만 RAP Managed Scenario의 표준적인 학습 흐름을 고려하면 `UUID` 또는 `RAW(16)` 기반 키를 사용하는 예제를 익히는 것이 좋다.

### 7.2 Root View Key 예시

```abap
key order_uuid as OrderUUID,
    order_id   as OrderID,
```

여기서 `OrderUUID`는 CDS View Entity의 Key이다. `OrderID`는 Semantic Key로 사용할 수 있지만, 실제 Behavior Definition과 Numbering 전략은 후속 모듈에서 다룬다.

## 8. Composition이란 무엇인가?

Composition은 Parent와 Child 사이의 생명주기 종속 관계를 표현한다.

주문 Header와 Item을 예로 들면 다음과 같다.

```text
Order Header가 삭제되면 해당 Order Item도 함께 영향을 받는다.
Order Item은 독립적으로 존재하기보다 Order Header에 종속된다.
```

이처럼 Child가 Parent에 종속되는 관계를 RAP Interface View에서는 Composition으로 표현한다.

| 관계 | 설명 |
|---|---|
| Association | 일반 참조 관계 |
| Composition | 생명주기 종속 관계 |

초급자는 다음처럼 기억하면 된다.

```text
Association = 연결되어 있다.
Composition = 포함되어 있고 생명주기가 종속된다.
```

---

## 9. Composition 설계 구조

Header-Item 구조의 RAP Interface View는 보통 다음 구조가 된다.

```text
ZI_GPT_Order
  composition [0..*] of ZI_GPT_OrderItem as _Item

ZI_GPT_OrderItem
  association to parent ZI_GPT_Order as _Order
```

Root View는 Child를 Composition으로 가진다. Child View는 Parent를 `association to parent`로 참조한다.

이 양방향 설계가 맞아야 RAP 모델이 안정적으로 활성화된다.

## 11. Root Interface View 구현 예제

### 11.1 기본 Root View

다음은 주문 Header를 Root Interface View로 정의하는 예제이다.

```abap
@AccessControl.authorizationCheck: #NOT_REQUIRED
@EndUserText.label: 'Order Root Interface View'
define root view entity ZI_GPT_Order
  as select from zgpt_order
{
  key order_uuid      as OrderUUID,
      order_id        as OrderID,
      customer_id     as CustomerID,
      order_date      as OrderDate,
      currency_code   as CurrencyCode,
      gross_amount    as GrossAmount,
      created_by      as CreatedBy,
      created_at      as CreatedAt,
      last_changed_by as LastChangedBy,
      last_changed_at as LastChangedAt
}
```

### 11.2 코드 해설

| 코드 | 의미 |
|---|---|
| `define root view entity` | RAP Root Node로 사용할 CDS View Entity를 정의한다. |
| `ZI_GPT_Order` | Interface View 객체명이다. |
| `as select from zgpt_order` | 영속 테이블을 데이터 소스로 사용한다. |
| `key order_uuid as OrderUUID` | 기술 키를 CDS Key로 노출한다. |
| `as OrderID` | DB 필드명을 외부 CDS 요소명으로 Alias 처리한다. |
| `@AccessControl.authorizationCheck` | DCL 권한 체크 정책을 지정한다. |
| `@EndUserText.label` | 객체 설명 라벨을 제공한다. |

### 11.3 Alias를 쓰는 이유

영속 테이블 필드는 보통 `snake_case` 또는 기술적 명칭으로 되어 있을 수 있다. Interface View에서는 CDS 요소명을 더 읽기 쉬운 형태로 노출할 수 있다.

예:

```text
order_uuid      → OrderUUID
customer_id     → CustomerID
last_changed_at → LastChangedAt
```

이렇게 Alias를 정리하면 후속 Projection View와 OData 메타데이터에서도 의미가 더 명확해진다.

## 12. Child Interface View 구현 예제

Child View는 Root View에 종속되는 하위 노드를 표현한다. 주문 품목을 예로 들면 다음과 같다.

```abap
@AccessControl.authorizationCheck: #NOT_REQUIRED
@EndUserText.label: 'Order Item Interface View'
define view entity ZI_GPT_OrderItem
  as select from zgpt_orderitem
  association to parent ZI_GPT_Order as _Order
    on $projection.OrderUUID = _Order.OrderUUID
{
  key item_uuid     as ItemUUID,
      order_uuid    as OrderUUID,
      item_no       as ItemNo,
      product_id    as ProductID,
      quantity      as Quantity,
      quantity_unit as QuantityUnit,
      net_amount    as NetAmount,
      currency_code as CurrencyCode,

      _Order
}
```

Child View에서는 `define root view entity`가 아니라 일반 `define view entity`를 사용한다. Root는 하나이고, Child는 Root에 종속되는 노드이기 때문이다.

### 12.1 `association to parent`의 의미

```abap
association to parent ZI_GPT_Order as _Order
  on $projection.OrderUUID = _Order.OrderUUID
```

이 문장은 Child View가 자신의 Parent Root View를 참조한다는 의미이다.

| 요소 | 설명 |
|---|---|
| `association to parent` | RAP Composition 모델의 Parent Association을 정의한다. |
| `ZI_GPT_Order` | Parent Root View이다. |
| `_Order` | Association Alias이다. |
| `$projection.OrderUUID` | 현재 Child View의 노출 필드이다. |
| `_Order.OrderUUID` | Parent View의 Key 필드이다. |

## 13. Root View에 Composition 추가

Child View를 만들었다면 Root View에 Composition Association을 추가한다.

```abap
@AccessControl.authorizationCheck: #NOT_REQUIRED
@EndUserText.label: 'Order Root Interface View'
define root view entity ZI_GPT_Order
  as select from zgpt_order
  composition [0..*] of ZI_GPT_OrderItem as _Item
{
  key order_uuid      as OrderUUID,
      order_id        as OrderID,
      customer_id     as CustomerID,
      order_date      as OrderDate,
      currency_code   as CurrencyCode,
      gross_amount    as GrossAmount,
      created_by      as CreatedBy,
      created_at      as CreatedAt,
      last_changed_by as LastChangedBy,
      last_changed_at as LastChangedAt,

      _Item
}
```

### 13.1 Composition Cardinality

```abap
composition [0..*] of ZI_GPT_OrderItem as _Item
```

이 표현은 Root Order 하나가 0개 이상의 Item을 가질 수 있다는 의미이다.

| Cardinality | 의미 |
|---|---|
| `[0..1]` | 없거나 하나 |
| `[1..1]` | 반드시 하나 |
| `[0..*]` | 없거나 여러 개 |
| `[1..*]` | 하나 이상 |

주문 Header와 Item 관계에서는 일반적으로 `[0..*]` 또는 `[1..*]`를 검토할 수 있다. 교육용 예제에서는 생성 초기 상태나 임시 저장 가능성을 고려하여 `[0..*]`를 사용하는 것이 설명하기 쉽다.

## 14. Root View와 Child View의 완성 구조

최종적으로 Interface View 계층은 다음처럼 정리된다.

```text
ZI_GPT_Order
  - Root Interface View
  - Source: zgpt_order
  - Key: OrderUUID
  - Composition: _Item

ZI_GPT_OrderItem
  - Child Interface View
  - Source: zgpt_orderitem
  - Key: ItemUUID
  - Parent Association: _Order
```

시각적으로 표현하면 다음과 같다.

```text
                 ZI_GPT_Order
              Root View Entity
                    │
                    │ composition [0..*]
                    ▼
              ZI_GPT_OrderItem
              Child View Entity
                    │
                    │ association to parent
                    ▲
                 _Order
```

이 구조는 후속 Behavior Definition에서 다음과 같이 확장된다.

```text
managed implementation in class ...
define behavior for ZI_GPT_Order alias Order
  persistent table zgpt_order
  lock master
{
  create;
  update;
  delete;

  association _Item { create; }
}
```

위 BDEF는 다음 모듈 이후에 자세히 다룰 내용이므로, 이번 모듈에서는 “Interface View 구조가 BDEF의 기반이 된다”는 정도만 이해한다.

## 15. Interface View에 자주 사용하는 Annotation

Interface View에는 여러 Annotation을 사용할 수 있다. 초급 단계에서는 다음 정도를 먼저 이해하면 충분하다.

| Annotation | 역할 |
|---|---|
| `@EndUserText.label` | 객체의 설명 텍스트를 제공한다. |
| `@AccessControl.authorizationCheck` | DCL 권한 체크 방식을 지정한다. |
| `@Metadata.ignorePropagatedAnnotations` | 하위 소스에서 전달되는 Annotation 제어에 사용될 수 있다. |
| `@Semantics.amount.currencyCode` | 금액 필드와 통화 필드의 의미 관계를 표현한다. |
| `@Semantics.quantity.unitOfMeasure` | 수량 필드와 단위 필드의 의미 관계를 표현한다. |

### 15.1 금액과 통화 Annotation 예시

```abap
@Semantics.amount.currencyCode: 'CurrencyCode'
gross_amount as GrossAmount,

currency_code as CurrencyCode,
```

금액 필드는 통화 코드와 연결되어야 의미가 명확하다.

### 15.2 수량과 단위 Annotation 예시

```abap
@Semantics.quantity.unitOfMeasure: 'QuantityUnit'
quantity as Quantity,

quantity_unit as QuantityUnit,
```

수량 필드는 단위와 함께 해석되어야 한다.

### 15.3 적용 예시

```abap
@AccessControl.authorizationCheck: #NOT_REQUIRED
@EndUserText.label: 'Order Item Interface View'
define view entity ZI_GPT_OrderItem
  as select from zgpt_orderitem
  association to parent ZI_GPT_Order as _Order
    on $projection.OrderUUID = _Order.OrderUUID
{
  key item_uuid as ItemUUID,
      order_uuid as OrderUUID,
      item_no    as ItemNo,
      product_id as ProductID,

      @Semantics.quantity.unitOfMeasure: 'QuantityUnit'
      quantity as Quantity,
      quantity_unit as QuantityUnit,

      @Semantics.amount.currencyCode: 'CurrencyCode'
      net_amount as NetAmount,
      currency_code as CurrencyCode,

      _Order
}
```

## 16. `ZI_*` 네이밍 설계 기준

교육용 네이밍 기준은 다음과 같다.

| 객체 유형 | Prefix | 예시 |
|---|---|---|
| Interface View | `ZI_` | `ZI_GPT_Order` |
| Projection View | `ZC_` | `ZC_GPT_Order` |
| Behavior Definition | View와 동일명 기반 | `ZI_GPT_Order`에 대한 BDEF |
| Service Definition | `ZUI_` 또는 프로젝트 규칙 | `ZUI_GPT_ORDER` |
| Service Binding | `ZUI_..._O4` 등 | `ZUI_GPT_ORDER_O4` |

실무에서 중요한 점은 “Prefix를 외우는 것”보다 “객체의 계층과 책임이 이름에 드러나는 것”이다.

좋은 이름:

```text
ZI_GPT_Order
ZI_GPT_OrderItem
ZI_GPT_Travel
ZI_GPT_Booking
```

나쁜 이름:

```text
ZI_TEST
ZI_TEMP
ZI_DATA
ZI_VIEW1
```

이름만 보고 어떤 Business Object의 어느 노드인지 알 수 있어야 한다.

## 17. 실습: Order Root Interface View 만들기

### 17.1 실습 목표

ADT에서 `ZI_GPT_Order`와 `ZI_GPT_OrderItem` Interface View를 만들고, Root-Child Composition 구조를 활성화한다.

### 17.2 선행 조건

다음 영속 테이블이 존재한다고 가정한다.

```text
zgpt_order
zgpt_orderitem
```

필드명은 예제와 동일하다고 가정한다. 실제 시스템에서 필드명이 다르면 코드의 필드명을 조정해야 한다.

### 17.3 생성 순서

권장 순서는 다음과 같다.

```text
1. Root View를 Composition 없이 먼저 생성
2. Child View를 Parent Association과 함께 생성
3. Root View에 Composition Association 추가
4. Root View와 Child View 모두 Activate
5. Data Preview 또는 Dependency 확인
```

이 순서를 권장하는 이유는 활성화 오류를 단계적으로 줄일 수 있기 때문이다. 처음부터 Root와 Child를 모두 서로 참조하도록 작성하면 참조 대상이 아직 활성화되지 않아 오류 원인을 파악하기 어려울 수 있다.

### 17.4 Step 1 — Root View 1차 생성

```abap
@AccessControl.authorizationCheck: #NOT_REQUIRED
@EndUserText.label: 'Order Root Interface View'
define root view entity ZI_GPT_Order
  as select from zgpt_order
{
  key order_uuid      as OrderUUID,
      order_id        as OrderID,
      customer_id     as CustomerID,
      order_date      as OrderDate,
      currency_code   as CurrencyCode,
      gross_amount    as GrossAmount,
      created_by      as CreatedBy,
      created_at      as CreatedAt,
      last_changed_by as LastChangedBy,
      last_changed_at as LastChangedAt
}
```

이 단계에서는 `_Item` Composition을 아직 넣지 않는다.

### 17.5 Step 2 — Child View 생성

```abap
@AccessControl.authorizationCheck: #NOT_REQUIRED
@EndUserText.label: 'Order Item Interface View'
define view entity ZI_GPT_OrderItem
  as select from zgpt_orderitem
  association to parent ZI_GPT_Order as _Order
    on $projection.OrderUUID = _Order.OrderUUID
{
  key item_uuid     as ItemUUID,
      order_uuid    as OrderUUID,
      item_no       as ItemNo,
      product_id    as ProductID,
      quantity      as Quantity,
      quantity_unit as QuantityUnit,
      net_amount    as NetAmount,
      currency_code as CurrencyCode,

      _Order
}
```

### 17.6 Step 3 — Root View에 Composition 추가

Root View를 다시 열고 다음 구문을 추가한다.

```abap
composition [0..*] of ZI_GPT_OrderItem as _Item
```

그리고 select list 마지막에 Association을 노출한다.

```abap
_Item
```

최종 Root View는 다음과 같다.

```abap
@AccessControl.authorizationCheck: #NOT_REQUIRED
@EndUserText.label: 'Order Root Interface View'
define root view entity ZI_GPT_Order
  as select from zgpt_order
  composition [0..*] of ZI_GPT_OrderItem as _Item
{
  key order_uuid      as OrderUUID,
      order_id        as OrderID,
      customer_id     as CustomerID,
      order_date      as OrderDate,
      currency_code   as CurrencyCode,
      gross_amount    as GrossAmount,
      created_by      as CreatedBy,
      created_at      as CreatedAt,
      last_changed_by as LastChangedBy,
      last_changed_at as LastChangedAt,

      _Item
}
```

## 19. 자주 발생하는 오류와 해결

### 19.1 Root View에 `root` 키워드를 누락함

#### 증상

후속 Behavior Definition 또는 RAP 객체 생성 시 Root View로 인식되지 않거나 모델 구성이 맞지 않는다.

#### 원인

Root Interface View를 다음처럼 일반 View로 선언했다.

```abap
define view entity ZI_GPT_Order
```

#### 해결

Root View는 다음처럼 선언한다.

```abap
define root view entity ZI_GPT_Order
```

---

### 19.2 Child View에서 `association to parent`를 누락함

#### 증상

Composition 관계가 맞지 않거나 Parent-Child 관계를 RAP가 제대로 해석하지 못한다.

#### 원인

Child View가 일반 Association만 가지고 있거나 Parent Association이 없다.

#### 해결

Child View에 다음 형태를 추가한다.

```abap
association to parent ZI_GPT_Order as _Order
  on $projection.OrderUUID = _Order.OrderUUID
```

---

### 19.3 Root View에서 `_Item`을 노출하지 않음

#### 증상

Composition을 정의했지만 하위 노드 탐색이 기대대로 보이지 않는다.

#### 원인

Composition Association을 선언했지만 select list에 `_Item`을 포함하지 않았다.

#### 해결

Root View의 select list에 다음을 포함한다.

```abap
_Item
```

---

### 19.4 Association 조건 필드명이 맞지 않음

#### 증상

Activation 오류가 발생하거나 Association이 의미적으로 잘못 연결된다.

#### 원인

Child의 `OrderUUID`와 Parent의 `OrderUUID`가 같은 의미가 아닌데 연결했거나 Alias 전후 명칭을 혼동했다.

#### 해결

다음을 확인한다.

```text
Child View에서 노출한 필드명
Parent View에서 노출한 Key 필드명
DB 테이블 원본 필드명
Alias 적용 후 CDS 요소명
```

CDS Association에서는 `$projection`을 사용할 때 노출된 CDS 요소명을 기준으로 생각해야 한다.

---

### 19.5 Key가 불안정함

#### 증상

후속 CRUD 처리나 Draft/Lock 설계에서 어려움이 생긴다.

#### 원인

업무상 변경될 수 있는 필드를 CDS Key로 사용했다.

#### 해결

가능하면 변경되지 않는 Technical Key를 사용한다.

```text
권장: UUID 기반 Key
주의: 설명, 상태, 이름, 날짜처럼 변경 가능한 필드 Key 사용
```

---

### 19.6 Access Control Annotation에 대한 오해

#### 증상

`@AccessControl.authorizationCheck: #NOT_REQUIRED`를 사용했기 때문에 운영에서도 권한 체크가 필요 없다고 오해한다.

#### 원인

교육용 단순화를 운영 설계로 착각했다.

#### 해결

초급 실습에서는 권한 모델을 단순화하기 위해 `#NOT_REQUIRED`를 사용할 수 있다. 그러나 실제 프로젝트에서는 DCL, 권한 객체, RAP 권한 제어를 반드시 검토해야 한다.

## 20. 실무 설계 기준

### 20.1 Interface View는 내부 안정성을 우선한다

Interface View는 외부 UI가 보기 좋은 구조를 만드는 계층이 아니다. 그것은 Projection View의 역할이다.

Interface View에서는 다음을 우선한다.

| 우선순위 | 설명 |
|---|---|
| 내부 모델 안정성 | DB 구조와 BO 구조를 안정적으로 연결한다. |
| Key 안정성 | 변경되지 않는 식별자를 사용한다. |
| 관계 명확성 | Composition과 Association을 명확히 설계한다. |
| 재사용성 | 여러 Projection에서 사용할 수 있는 내부 모델을 만든다. |
| 후속 Behavior 호환성 | BDEF, Lock, CRUD, Determination 설계를 고려한다. |

### 20.2 Projection View 역할을 Interface View에 섞지 않는다

나쁜 설계 예:

```text
ZI_*에서 UI 전용 필드명, 소비자별 필드 숨김, 화면 전용 Annotation을 과도하게 처리
```

Interface View는 BO 내부 모델이다. 외부 소비자별 필드 선택, UI 친화적 노출, 서비스 전용 조정은 `ZC_*` Projection View에서 처리하는 것이 더 적절하다.

### 20.3 Composition을 남용하지 않는다

모든 Association이 Composition은 아니다.

| 관계 | 적절한 모델 |
|---|---|
| Order Header - Order Item | Composition 가능 |
| Sales Order - Customer | 일반 Association |
| Booking - Carrier | 일반 Association |
| Header - Long Text가 Header에 완전히 종속 | Composition 검토 |

Composition은 생명주기 종속성이 있을 때 사용한다. 단순 조회 참조 관계에는 일반 Association이 적합하다.

### 20.4 Root는 Business Object의 업무 시작점이다

Root View는 “그냥 가장 위에 있는 View”가 아니다. Business Object의 생성, 수정, 삭제, Lock, Authorization, Draft 흐름의 중심이다.

따라서 Root를 정할 때는 다음 질문을 한다.

```text
사용자가 생성하는 가장 큰 업무 단위는 무엇인가?
하위 데이터가 이 Root 없이 독립적으로 의미가 있는가?
삭제 또는 저장 흐름에서 생명주기 주체는 무엇인가?
후속 서비스에서 진입점이 될 객체는 무엇인가?
```

## 21. 성능과 운영 관점 주의사항

### 21.1 CDS View는 단순 문서가 아니라 실행 가능한 DB 모델이다

CDS View Entity는 Activation 후 DB 질의 모델로 사용된다. 따라서 Association을 많이 만든다고 항상 좋은 것은 아니다.

초급 단계에서는 다음을 주의한다.

| 주의 항목 | 설명 |
|---|---|
| 불필요한 Association 남발 | 조회 복잡도와 이해 난이도를 높일 수 있다. |
| 계산 필드 남발 | 성능과 책임 분리가 흐려질 수 있다. |
| 대량 데이터 Preview | 개발 시스템에서도 무분별한 전체 조회를 피한다. |
| 권한 체크 무시 | 교육용 설정을 운영 설정으로 가져가지 않는다. |

### 21.2 Interface View의 변경 파급효과

Interface View는 후속 객체의 기반이다. 변경 시 다음 객체에 영향을 줄 수 있다.

```text
ZI_* Interface View 변경
→ ZC_* Projection View 영향
→ Behavior Definition 영향
→ Service Definition 영향
→ Service Binding Metadata 영향
→ Fiori Elements/UI 영향
→ 테스트 코드 영향
```

따라서 필드명, Key, Association Alias는 초기에 신중하게 설계한다.

## 22. 강사용 설명 포인트

이 모듈은 초급자에게 어렵게 느껴질 수 있다. 강의 시 다음 순서로 설명하면 이해가 쉽다.

### 22.1 먼저 비유로 설명한다

```text
DB Table = 실제 저장소
ZI_* Interface View = 내부 업무 모델
ZC_* Projection View = 외부 소비자에게 보여줄 모델
Behavior Definition = 이 모델이 할 수 있는 행동 규칙
Service Binding = 외부에 서비스를 열어주는 출입구
```

### 22.2 Root와 Child를 업무 예제로 설명한다

주문 Header와 Item이 가장 설명하기 쉽다.

```text
주문 Header는 주문 자체를 의미한다.
주문 Item은 주문에 포함된 개별 품목이다.
Item은 Header 없이 독립적으로 존재하기 어렵다.
따라서 Header는 Root, Item은 Child가 된다.
```

### 22.3 Composition과 Association을 비교한다

```text
Order - Item = Composition
Order - Customer = Association
```

이 비교만 명확히 해도 RAP 모델링 오류가 크게 줄어든다.

| 확인 항목 | 결과 기록 |
|---|---|
| Root View 활성화 성공 여부 |  |
| Child View 활성화 성공 여부 |  |
| `_Item` Composition 존재 여부 |  |
| `_Order` Parent Association 존재 여부 |  |
| Key 필드가 안정적인지 |  |
| Data Preview 가능 여부 |  |
| 오류 메시지 발생 여부 |  |

### 23.3 오류 분석 과제

일부러 Root View의 `root` 키워드를 제거한 뒤 어떤 오류 또는 후속 제약이 발생하는지 확인한다. 이후 다시 `define root view entity`로 수정하고 정상 활성화한다.

이 과제의 목적은 “RAP에서 Root View 선언이 단순 문법이 아니라 모델 의미를 가진다”는 점을 체감하는 것이다.

### 24.1 객관식

### 24.2 서술형

#### Q1. RAP에서 `ZI_*` Interface View를 두는 이유를 설명하시오.

**모범 답안:**  
`ZI_*` Interface View는 DB 테이블을 직접 외부에 노출하지 않고, RAP Business Object의 내부 데이터 모델을 정의하기 위한 계층이다. 필드 Alias, Key, Association, Composition을 통해 업무 의미와 관계를 표현하고, 후속 Projection View와 Behavior Definition의 기반이 된다.

#### Q2. `association to parent`와 `composition`의 관계를 설명하시오.

**모범 답안:**  
Root View는 Child View를 Composition으로 포함하고, Child View는 Parent Root View를 `association to parent`로 참조한다. 이 양쪽 정의를 통해 RAP는 Parent-Child 생명주기 종속 관계를 이해할 수 있다.

#### Q3. 모든 Association을 Composition으로 만들면 안 되는 이유를 설명하시오.

**모범 답안:**  
Composition은 생명주기 종속 관계를 의미한다. 단순 참조 관계까지 Composition으로 만들면 데이터 모델의 의미가 왜곡되고, 삭제·저장·동작 처리에서 잘못된 설계가 될 수 있다. 생명주기가 독립적인 참조 대상은 일반 Association으로 표현하는 것이 적절하다.

## 26. 핵심 요약

이번 모듈의 핵심은 다음이다.

```text
Interface View ZI_*는 RAP Business Object의 내부 데이터 모델이다.
Root View는 Business Object의 최상위 노드이다.
Child View는 Parent Root View에 association to parent로 연결된다.
Root View는 Child View를 composition으로 포함한다.
Composition은 단순 연결이 아니라 생명주기 종속 관계이다.
ZI_*는 후속 ZC_*, BDEF, Service Definition, Service Binding의 기반이 된다.
```

초급자는 이 모듈에서 모든 RAP 문법을 완벽히 암기할 필요는 없다. 그러나 다음 문장만은 정확히 이해해야 한다.

> `ZI_*` Interface View를 잘못 설계하면 후속 Projection, Behavior, Service 계층 전체가 흔들린다.
