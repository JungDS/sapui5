## 3. RAP 서비스 노출 흐름 전체 그림

RAP에서 서비스 노출은 대략 다음 계층을 가진다.

```text
Database Table
   ↓
CDS Interface View Entity     ZI_*
   ↓
CDS Projection View Entity    ZC_*
   ↓
Behavior Definition / Implementation
   ↓
Service Definition            ZUI_*, ZSD_*, ZSRV_*
   ↓
Service Binding               OData V4 UI / Web API
   ↓
Preview / Fiori Elements / 외부 소비자
```

이 중 이번 모듈에서 다루는 부분은 아래이다.

```text
Projection View ZC_*
   ↓ expose
Service Definition
   ↓ bind + publish
Service Binding
   ↓ preview / consume
OData V4 Service
```

핵심은 다음이다.

```text
Service Definition은 “무엇을 서비스로 공개할 것인가”를 정의한다.
Service Binding은 “어떤 프로토콜과 런타임 방식으로 공개할 것인가”를 정의한다.
```

## 4. Service Definition이란 무엇인가?

### 4.1 쉬운 정의

Service Definition은 RAP/CDS 기반 모델 중 어떤 Entity를 서비스로 노출할지 선언하는 객체이다.

예를 들어 `ZC_JHY_TRAVEL` Projection View를 외부로 공개하려면 Service Definition에서 다음처럼 expose한다.

```abap
@EndUserText.label: 'Travel Service Definition'
define service ZUI_JHY_TRAVEL {
  expose ZC_JHY_TRAVEL as Travel;
}
```

이 코드가 의미하는 바는 다음이다.

| 코드 요소 | 의미 |
|---|---|
| `define service` | 서비스 정의 객체를 선언한다. |
| `ZUI_JHY_TRAVEL` | Service Definition 이름이다. |
| `expose ZC_JHY_TRAVEL` | Projection View를 서비스 대상으로 공개한다. |
| `as Travel` | 서비스 안에서 사용할 Entity 이름을 지정한다. |

### 4.2 Service Definition의 책임

Service Definition의 책임은 다음과 같다.

| 책임 | 설명 |
|---|---|
| 노출 대상 결정 | 어떤 CDS Entity를 서비스에 포함할지 결정한다. |
| 외부 이름 부여 | `as Travel`처럼 서비스 Entity 이름을 지정한다. |
| 서비스 범위 제한 | 내부 모델 전체가 아니라 공개할 모델만 노출한다. |
| 소비 계층 분리 | 내부 Interface View와 외부 Consumption View 사이의 경계를 유지한다. |

Service Definition은 서비스의 프로토콜을 직접 결정하지 않는다. OData V4인지, UI용인지, Web API용인지는 Service Binding에서 결정한다.

---

## 5. Service Binding이란 무엇인가?

### 5.1 쉬운 정의

Service Binding은 Service Definition을 실제 런타임 서비스로 연결하는 객체이다.

Service Definition이 “무엇을 공개할 것인가”라면, Service Binding은 “어떻게 공개할 것인가”이다.

예를 들어 같은 Service Definition이라도 다음과 같은 Binding 방식이 있을 수 있다.

| Binding 성격 | 설명 |
|---|---|
| OData V4 - UI | Fiori Elements Preview와 UI 소비에 적합한 Binding |
| OData V4 - Web API | 외부 API 소비 관점의 Binding |

[추정] 실제 ADT 화면의 Binding Type 명칭은 ABAP Platform/S/4HANA 릴리스와 시스템 설정에 따라 다소 다르게 표시될 수 있다.

### 5.2 Service Binding의 책임

Service Binding의 책임은 다음과 같다.

| 책임 | 설명 |
|---|---|
| 프로토콜 결정 | OData V4 등 노출 방식을 선택한다. |
| 런타임 엔드포인트 생성 | 실제 호출 가능한 서비스 경로를 제공한다. |
| Publish 관리 | 서비스가 외부에서 사용할 수 있도록 게시한다. |
| Preview 지원 | ADT에서 서비스 또는 Fiori Elements Preview를 실행할 수 있게 한다. |
| 소비자 연결 | UI, API Client, 테스트 도구가 접근할 수 있는 접점을 만든다. |

## 6. Service Definition과 Service Binding의 차이

초급자가 가장 많이 혼동하는 부분이다.

| 구분 | Service Definition | Service Binding |
|---|---|---|
| 핵심 질문 | 무엇을 공개할 것인가? | 어떻게 공개할 것인가? |
| 주요 대상 | CDS Entity, Projection View | Service Definition |
| 주요 문법/행위 | `define service`, `expose` | Binding Type 선택, Publish |
| 프로토콜 결정 | 하지 않음 | 수행 |
| 예시 이름 | `ZUI_JHY_TRAVEL` | `ZUI_JHY_TRAVEL_O4` |
| 결과 | 서비스에 포함될 Entity 목록 | 호출 가능한 OData 서비스 |

비유하면 다음과 같다.

```text
Service Definition = 메뉴판에 올릴 음식 목록
Service Binding    = 그 메뉴를 매장, 배달앱, 키오스크 중 어디로 판매할지 정하는 방식
```

## 7. 왜 Projection View `ZC_*`를 노출하는가?

RAP에서는 보통 Interface View `ZI_*`를 직접 외부에 노출하지 않고, Projection View `ZC_*`를 통해 노출한다.

### 7.1 Interface View의 역할

`ZI_*`는 내부 데이터 모델에 가깝다.

```text
ZI_* = Business Object의 내부 중심 모델
```

여기에는 Root, Composition, Association, Persistence, Internal Behavior와 밀접한 설계가 들어간다.

### 7.2 Projection View의 역할

`ZC_*`는 외부 소비자에게 보여줄 모델이다.

```text
ZC_* = UI/API 소비를 위한 외부 노출 모델
```

Projection View에서는 다음을 제어할 수 있다.

| 제어 항목 | 설명 |
|---|---|
| 노출 필드 | 외부에 보여줄 필드만 선택한다. |
| Annotation | UI 또는 소비 계층에 필요한 Annotation을 둔다. |
| Association 노출 | 필요한 Association만 공개한다. |
| Behavior Projection | 외부에서 허용할 동작 범위를 조정한다. |

### 7.3 Clean Core 관점

Clean Core 관점에서 중요한 원칙은 내부 모델과 외부 소비 모델을 분리하는 것이다.

```text
내부 모델이 변경되어도 외부 서비스 계약은 안정적으로 유지해야 한다.
```

따라서 Service Definition에는 보통 `ZC_*` Projection View를 expose한다.

## 10. 여러 Entity를 expose하는 경우

RAP Business Object가 Root와 Child Composition을 가진다면 Service Definition에서 여러 Entity를 expose할 수 있다.

예:

```abap
@EndUserText.label: 'Travel Service Definition'
define service ZUI_JHY_TRAVEL {
  expose ZC_JHY_TRAVEL        as Travel;
  expose ZC_JHY_BOOKING       as Booking;
  expose ZC_JHY_BOOKING_SUPPL as BookingSupplement;
}
```

초급 단계에서는 Root Entity 하나만 노출해도 충분하다. 다만 Composition 구조를 가진 RAP Business Object에서는 Root와 Child를 함께 노출해야 Preview나 Navigation이 자연스럽게 동작할 수 있다.

주의할 점은 다음이다.

```text
Service Definition에 expose하지 않은 Entity는 해당 서비스의 외부 소비자가 직접 접근할 수 없다.
```

## 11. Service Binding 생성 절차

### 11.1 ADT에서 생성

Service Definition이 활성화되었다면 Service Binding을 생성한다.

```text
1. Package 선택
2. New → Other ABAP Repository Object
3. 검색창에 Service Binding 입력
4. Service Binding 선택
5. 이름 입력: ZUI_JHY_TRAVEL_O4
6. Description 입력
7. Binding Type 선택: OData V4 - UI 또는 시스템 제공 OData V4 유형
8. Service Definition 선택: ZUI_JHY_TRAVEL
9. Finish
```

### 11.2 이름 예시

| 객체 | 예시 이름 | 설명 |
|---|---|---|
| Service Definition | `ZUI_JHY_TRAVEL` | 공개할 Entity 목록 |
| Service Binding | `ZUI_JHY_TRAVEL_O4` | OData V4 Binding |

이름에 `_O4`를 붙이는 것은 OData V4 Binding임을 구분하기 위한 교육용 규칙이다. 실제 프로젝트에서는 프로젝트 Naming Rule을 따른다.

### 11.3 Binding Type 선택

RAP 입문 과정에서는 OData V4 Binding을 기준으로 설명한다.

| Binding Type | 사용 관점 |
|---|---|
| OData V4 - UI | Fiori Elements 기반 Preview 또는 UI 소비에 적합 |
| OData V4 - Web API | 외부 API 소비 관점에 적합 |

[추정] 특정 시스템에서는 UI/WEB API 명칭이 다르거나 사용 가능한 Binding Type이 제한될 수 있다. 이 경우 시스템 릴리스와 권한 정책을 확인해야 한다.

## 12. Publish의 의미

Service Binding을 생성하고 활성화했다고 해서 바로 서비스가 사용할 수 있는 상태가 아닐 수 있다. 일반적으로 Service Binding에서는 **Publish**가 필요하다.

### 12.1 Activate와 Publish의 차이

| 구분 | 의미 |
|---|---|
| Activate | Repository 객체를 활성 상태로 만든다. |
| Publish | 런타임에서 서비스 엔드포인트를 사용할 수 있도록 게시한다. |

초급자는 다음처럼 기억하면 된다.

```text
Activate = 개발 객체가 문법적으로 유효하고 사용할 수 있는 상태
Publish  = 서비스가 실제 호출 가능한 상태
```

### 12.2 Publish 절차

ADT Service Binding Editor에서 다음 흐름으로 진행한다.

```text
1. Service Binding 열기
2. Activate 상태 확인
3. Publish 버튼 클릭
4. Publish 성공 메시지 확인
5. Service URL 또는 Preview 사용 가능 여부 확인
```

Publish가 실패하면 오류 메시지를 확인해야 한다. 단순히 버튼을 다시 누르는 것보다 원인을 분류하는 것이 중요하다.

## 13. Preview와 테스트

Service Binding이 Publish되면 ADT에서 Preview를 실행할 수 있다.

### 13.1 Preview의 목적

Preview는 서비스가 실제로 노출되었는지, Entity가 Metadata에 포함되었는지, 기본 List/Object Page가 표시되는지 확인하는 단계이다.

| 확인 항목 | 의미 |
|---|---|
| Entity Set 표시 | Service Definition의 expose가 정상 반영되었는지 확인 |
| Metadata 로딩 | OData V4 서비스가 게시되었는지 확인 |
| List Page 표시 | UI Annotation과 Projection View 노출 상태 확인 |
| Create/Update/Delete 가능 여부 | Behavior Definition과 Binding 유형 확인 |
| 오류 메시지 | 권한, Annotation, Behavior, Publish 상태 점검 |

### 13.2 초급자 확인 절차

```text
1. Service Binding 열기
2. Entity 목록 확인
3. Preview 실행
4. Browser 또는 ADT Preview 화면 확인
5. List 화면이 열리는지 확인
6. 데이터가 조회되는지 확인
7. Create/Update/Delete 버튼 표시 여부 확인
8. 오류 발생 시 메시지 기록
```

### 13.3 Preview에서 데이터가 보이지 않는 경우

데이터가 보이지 않는다고 해서 서비스가 실패한 것은 아닐 수 있다.

가능한 원인은 다음과 같다.

| 원인 | 확인 방법 |
|---|---|
| DB 테이블에 데이터 없음 | SE16N 또는 ADT Data Preview로 Persistent Table 확인 |
| CDS View 조건 때문에 필터링됨 | CDS View Preview 확인 |
| Authorization 문제 | SU53, ST01, Gateway/Error Log 등 시스템별 확인 |
| Service Binding 미게시 | Publish 상태 확인 |
| Projection View에 필드 미노출 | `ZC_*` 정의 확인 |

## 14. OData V4 기본 감각

RAP Service Binding은 OData V4 서비스 노출과 연결된다.

초급 단계에서는 OData V4를 다음 정도로 이해하면 된다.

```text
OData V4는 웹 기반으로 데이터를 조회/생성/변경/삭제할 수 있게 하는 표준 서비스 프로토콜이다.
RAP는 CDS와 Behavior를 기반으로 OData V4 서비스를 생성하고 노출한다.
```

### 14.1 Metadata

OData 서비스에는 Metadata가 있다. Metadata는 서비스가 어떤 Entity, 필드, Association, 동작을 제공하는지 설명한다.

예를 들어 `Travel` Entity가 있다면 Metadata에는 다음 정보가 포함될 수 있다.

| Metadata 요소 | 의미 |
|---|---|
| EntityType | Entity의 필드 구조 |
| EntitySet | 호출 가능한 Entity 집합 |
| Navigation Property | Association/Composition 기반 이동 |
| Action/Function | 서비스에서 실행 가능한 동작 |

### 14.2 Entity Set

Service Definition에서 `expose ZC_JHY_TRAVEL as Travel;`라고 작성하면, 서비스 소비자는 일반적으로 `Travel`이라는 이름으로 Entity에 접근하게 된다.

이름을 정할 때는 다음을 고려한다.

| 기준 | 설명 |
|---|---|
| 의미 명확성 | 소비자가 이해하기 쉬운 이름 사용 |
| 과도한 약어 지양 | 내부 개발자만 아는 약어는 피한다 |
| API 안정성 | 외부 계약 이름이므로 자주 바꾸지 않는다 |

## 15. 권한과 노출 범위 주의

Service Definition과 Service Binding은 외부 소비 경계를 만드는 단계이다. 따라서 “잘 보이면 성공”만으로 끝내면 안 된다.

### 15.1 노출 범위 최소화

외부 서비스에는 필요한 Entity와 필드만 노출해야 한다.

나쁜 방향:

```text
내부 Interface View 전체를 그대로 노출한다.
사용하지 않는 Child Entity까지 모두 expose한다.
민감한 관리 필드를 그대로 노출한다.
```

좋은 방향:

```text
Projection View에서 외부 소비에 필요한 필드만 선별한다.
Service Definition에는 실제 서비스 대상 Entity만 expose한다.
권한과 UI 요구사항을 분리해서 검토한다.
```

### 15.2 권한 체크

RAP 서비스는 사용자 권한과 연결된다. 초급 단계에서는 다음 정도를 기억한다.

```text
Preview 오류가 항상 코드 오류는 아니다.
권한 부족, 서비스 미게시, 인증 문제, Entity 노출 누락이 모두 원인이 될 수 있다.
```

실무에서는 CDS Access Control, Authorization Default, Business Role, Service Authorization 등을 함께 확인해야 한다. 이 내용은 후속 과정에서 심화로 다룬다.

## 16. 정상 흐름과 오류 흐름

### 16.1 정상 흐름

정상적인 Service Definition/Binding 흐름은 다음과 같다.

```text
1. Projection View ZC_* 활성화
2. Projection Behavior Definition 활성화
3. Service Definition 생성
4. Service Definition에서 ZC_* expose
5. Service Definition 활성화
6. Service Binding 생성
7. Binding Type 선택
8. Service Definition 연결
9. Service Binding 활성화
10. Publish
11. Preview 실행
12. Metadata와 Entity 표시 확인
```

### 16.2 오류 흐름 1: Service Definition에서 Entity를 찾지 못함

| 항목 | 내용 |
|---|---|
| 증상 | `ZC_*`를 expose하려는데 인식되지 않음 |
| 원인 | Projection View 이름 오타, 비활성 상태, 패키지/권한 문제 |
| 해결 | ADT에서 `ZC_*` 활성화 상태와 이름 확인 |

### 16.3 오류 흐름 2: Service Binding에서 Service Definition 선택 불가

| 항목 | 내용 |
|---|---|
| 증상 | Binding 생성 시 Service Definition이 목록에 보이지 않음 |
| 원인 | Service Definition 미활성화, 이름 오타, 객체 저장 문제 |
| 해결 | Service Definition Activate 후 다시 Binding 생성 |

### 16.4 오류 흐름 3: Publish 실패

| 항목 | 내용 |
|---|---|
| 증상 | Publish 버튼 실행 후 오류 발생 |
| 원인 | 하위 객체 비활성, Binding Type 부적합, 서비스 등록 권한 부족, Runtime 오류 |
| 해결 | Problems View, Error Log, 하위 객체 Activate 상태 확인 |

### 16.5 오류 흐름 4: Preview에서 Metadata 오류

| 항목 | 내용 |
|---|---|
| 증상 | Preview 실행 시 Metadata 로딩 실패 |
| 원인 | 서비스 미게시, Annotation 오류, Behavior/Projection 불일치, 권한 문제 |
| 해결 | Publish 상태, ADT Problems, 브라우저 오류 메시지 확인 |

### 16.6 오류 흐름 5: Create 버튼이 보이지 않음

| 항목 | 내용 |
|---|---|
| 증상 | Preview 화면에 생성 기능이 표시되지 않음 |
| 원인 | Behavior Definition에서 create 미허용, Projection Behavior에서 use create 누락, UI Annotation 부족 |
| 해결 | Interface/Projection BDEF의 CRUD 선언과 Projection 설정 확인 |

### 16.7 오류 흐름 6: 데이터 조회는 되지만 수정이 실패함

| 항목 | 내용 |
|---|---|
| 증상 | List는 보이지만 저장 또는 수정 시 오류 발생 |
| 원인 | Behavior Implementation 오류, Lock/Authorization 문제, Validation 실패, Draft 설정 문제 |
| 해결 | ST22, ADT Console, Behavior Method 로직, reported/failed 메시지 확인 |

## 19. 실무 적용 기준

### 19.1 서비스 노출은 계약이다

Service Definition과 Service Binding은 단순 테스트 도구가 아니다. 외부 소비자에게 공개되는 서비스 계약을 만드는 단계이다.

따라서 다음을 신중히 결정해야 한다.

```text
Entity 이름을 무엇으로 공개할 것인가?
어떤 필드를 외부에 보여줄 것인가?
어떤 Association/Composition을 노출할 것인가?
CRUD를 어디까지 허용할 것인가?
UI용 서비스와 API용 서비스를 분리할 것인가?
```

### 19.2 UI용과 API용을 구분한다

Fiori Elements UI를 위한 서비스와 외부 시스템 연계를 위한 API 서비스는 요구사항이 다를 수 있다.

| 구분 | UI용 서비스 | API용 서비스 |
|---|---|---|
| 주요 소비자 | Fiori Elements | 외부 시스템, Integration |
| 관심사 | 화면 구성, Annotation, 사용자 흐름 | 계약 안정성, Payload, 버전 관리 |
| 변경 영향 | UI 동작 영향 | 외부 연계 장애 가능 |
| 설계 기준 | 사용자 업무 흐름 | API 소비 계약 |

초급 과정에서는 하나의 OData V4 UI Binding으로 실습해도 충분하지만, 실무에서는 서비스 목적을 구분하는 습관이 필요하다.

### 19.3 내부 이름과 외부 이름을 구분한다

`ZC_JHY_TRAVEL`은 내부 개발 객체명이고, `Travel`은 서비스 소비자에게 보일 수 있는 Entity 이름이다.

외부 이름은 API 계약의 일부가 될 수 있으므로 자주 바꾸지 않는 것이 좋다.

### 19.4 노출 최소화 원칙

Service Definition에서는 필요한 Entity만 expose한다. Projection View에서도 외부에 필요한 필드만 제공한다.

```text
내부 모델 전체를 외부로 그대로 공개하지 않는다.
필요한 소비 모델을 Projection View로 정리한 뒤 Service Definition에서 expose한다.
```

## 20. 강사용 설명 포인트

강의 시 다음 순서로 설명하면 초급자가 이해하기 쉽다.

### 20.1 첫 번째 비유

```text
CDS View = 데이터 모델
Behavior = 가능한 동작
Service Definition = 공개 메뉴
Service Binding = 실제 매장 오픈
Preview = 손님 입장에서 접속 테스트
```

### 20.2 두 번째 강조점

Service Binding을 생성했지만 Publish하지 않으면 초급자는 “왜 Preview가 안 되지?”라고 혼동한다. Activate와 Publish를 반드시 분리해서 설명한다.

### 20.3 세 번째 강조점

`ZI_*`를 직접 노출하는 것이 아니라 `ZC_*`를 노출하는 이유를 Clean Core 관점으로 설명한다.

```text
내부 모델은 변경될 수 있다.
외부 서비스 계약은 안정적으로 관리되어야 한다.
그래서 Projection View가 소비 계층의 완충 역할을 한다.
```

## 21. 평가 문제

### 21.1 객관식

#### Q1. Service Definition의 가장 적절한 역할은 무엇인가?

A. 데이터베이스 테이블을 생성한다.  
B. 어떤 CDS Entity를 서비스로 노출할지 정의한다.  
C. ABAP Class의 메서드를 구현한다.  
D. 사용자의 SAP GUI 메뉴 권한을 설정한다.

**정답:** B

#### Q2. Service Binding의 가장 적절한 역할은 무엇인가?

A. Service Definition을 특정 프로토콜과 런타임 방식으로 게시한다.  
B. CDS View의 Association을 정의한다.  
C. Transparent Table의 Key를 설정한다.  
D. ABAP Report의 Selection Screen을 만든다.

**정답:** A

#### Q3. RAP에서 보통 서비스로 노출하는 View는 무엇인가?

A. Database Table  
B. Interface View `ZI_*`  
C. Projection View `ZC_*`  
D. Domain

**정답:** C

#### Q4. Activate와 Publish의 차이로 올바른 것은?

A. 둘은 완전히 같은 의미이다.  
B. Activate는 Repository 객체 활성화이고, Publish는 런타임 서비스 게시에 가깝다.  
C. Publish는 DDIC Domain에서만 사용한다.  
D. Activate는 OData V4에서만 사용하는 용어이다.

**정답:** B

### 21.2 서술형

#### Q1. Service Definition과 Service Binding의 차이를 설명하시오.

**모범 답안:**  
Service Definition은 어떤 CDS Entity를 서비스로 공개할지 정의하는 객체이다. Service Binding은 해당 Service Definition을 OData V4 같은 구체적인 프로토콜과 런타임 방식으로 연결하고 Publish하여 실제 소비 가능한 서비스로 만드는 객체이다.

#### Q2. 왜 `ZI_*`가 아니라 `ZC_*` Projection View를 서비스로 노출하는 것이 일반적인가?

**모범 답안:**  
`ZI_*`는 Business Object의 내부 Interface 모델에 가깝고, `ZC_*`는 UI/API 소비를 위한 Projection 모델이다. Projection View를 통해 외부에 노출할 필드, Association, Annotation, 동작 범위를 조정할 수 있으므로 내부 모델과 외부 서비스 계약을 분리할 수 있다.

#### Q3. Preview에서 Entity가 보이지만 데이터가 표시되지 않을 때 확인할 항목을 쓰시오.

**모범 답안:**  
Persistent Table에 테스트 데이터가 있는지, CDS View의 WHERE 조건이나 Filter로 데이터가 제외되지 않았는지, 현재 Client가 맞는지, 권한 문제가 없는지, Projection View에서 필요한 필드를 노출했는지 확인한다.

```text
Service Binding은 어떻게 공개할지 정의하고 Publish한다.
RAP 서비스 노출은 보통 Projection View ZC_*를 기준으로 한다.
Activate와 Publish는 다른 단계이다.
OData V4 Preview는 서비스 노출 결과를 빠르게 검증하는 수단이다.
서비스 노출은 외부 계약이므로 필드, Entity, 권한, 이름을 신중히 설계해야 한다.
```
