## 3. Behavior Implementation이란 무엇인가?

Behavior Implementation은 RAP Business Object의 동작 로직을 구현하는 ABAP Class 기반 객체이다.

RAP에서는 데이터 모델과 동작 모델이 분리된다.

```text
CDS Interface View ZI_*
  → 데이터 모델의 핵심 구조

Behavior Definition
  → 이 Business Object가 어떤 동작을 지원하는지 선언

Behavior Implementation
  → 선언된 동작 중 개발자 로직이 필요한 부분을 ABAP Method로 구현

Projection View ZC_*
  → 소비 계층에 노출할 모델

Service Definition / Service Binding
  → OData V4 서비스 노출
```

즉, Behavior Definition이 “무엇을 할 수 있는가”를 선언한다면, Behavior Implementation은 “그 동작이 실제로 어떻게 수행되는가”를 구현한다.

## 4. BDEF와 BIMP의 역할 차이

RAP 초급자가 가장 먼저 구분해야 하는 것은 BDEF와 BIMP의 역할이다.

| 구분 | Behavior Definition | Behavior Implementation |
|---|---|---|
| 약칭 | BDEF | BIMP 또는 Behavior Pool 구현 |
| 성격 | 선언 | 구현 |
| 주요 내용 | create/update/delete, lock, authorization, action, validation, determination 선언 | 선언된 동작의 ABAP Method 구현 |
| 작성 방식 | RAP Behavior Definition 문법 | ABAP Class/Method 문법 |
| 대표 객체 | `ZI_JHY_ORDER`에 대한 behavior definition | `ZBP_I_JHY_ORDER` behavior pool class |
| 초급자 이해 | Business Object의 동작 계약 | 동작 계약을 수행하는 로직 |

예를 들어 BDEF에서 다음과 같이 선언했다고 하자.

```abap
define behavior for ZI_JHY_RAP_ORDER alias Order
persistent table ztjhy_rap_ord
lock master
authorization master ( instance )
{
  create;
  update;
  delete;

  action set_completed result [1] $self;
}
```

위 선언은 다음 의미를 가진다.

```text
이 Business Object는 create/update/delete를 지원한다.
이 Business Object에는 set_completed라는 Action이 있다.
set_completed Action은 실행 후 자신의 결과를 반환할 수 있다.
```

하지만 `set_completed`가 실제로 상태값을 어떻게 변경할지는 BDEF만으로 알 수 없다. 이 부분을 구현하는 위치가 Behavior Implementation이다.

## 5. Managed Scenario에서 개발자가 구현하는 것

RAP Managed Scenario에서는 표준 CRUD의 많은 부분을 RAP Framework가 처리한다.

| 동작 | Managed Scenario 기본 감각 |
|---|---|
| create | Persistent Table에 신규 데이터 저장 흐름을 Framework가 처리 |
| update | 변경 데이터 반영 흐름을 Framework가 처리 |
| delete | 삭제 흐름을 Framework가 처리 |
| lock | BDEF 선언에 따라 Lock 흐름이 연결 |
| draft | Draft 사용 시 Framework가 초안 흐름을 관리 |
| action | 개발자가 Method로 구현해야 함 |
| validation | 선언 후 개발자가 Method로 구현 |
| determination | 선언 후 개발자가 Method로 구현 |
| authorization | 선언 수준에 따라 구현 Method 필요 가능 |

초급자는 다음을 기억하면 된다.

```text
Managed Scenario라고 해서 구현 클래스가 필요 없는 것은 아니다.
표준 CRUD 저장 흐름은 Framework가 처리하지만,
업무 규칙, 상태 변경, 검증, 자동값 세팅, 권한 판단 등은 구현 클래스에서 작성한다.
```

## 6. Behavior Pool Class

Behavior Implementation의 대표 객체는 **Behavior Pool Class**이다.

일반적인 네이밍 예시는 다음과 같다.

| 대상 Interface View | Behavior Pool Class 예시 |
|---|---|
| `ZI_JHY_RAP_ORDER` | `ZBP_I_JHY_RAP_ORDER` |
| `ZI_JHY_TRAVEL` | `ZBP_I_JHY_TRAVEL` |
| `ZI_JHY_BOOKING` | `ZBP_I_JHY_BOOKING` |

`ZBP_*`는 교육용 예시 Prefix이다. 실제 프로젝트에서는 네이밍 규칙을 따른다.

Behavior Pool Class는 보통 ADT에서 Behavior Definition을 생성하거나 Quick Fix를 사용할 때 함께 생성된다.

### 6.1 Behavior Pool의 성격

Behavior Pool은 일반적인 Utility Class와 다르다.

| 구분 | 일반 ABAP Class | Behavior Pool Class |
|---|---|---|
| 목적 | 범용 로직, 서비스, 유틸리티 구현 | RAP Business Object 동작 구현 |
| 호출 방식 | 프로그램이나 다른 클래스에서 직접 호출 가능 | RAP Framework가 동작 시점에 호출 |
| Method 정의 | 개발자가 자유롭게 설계 | BDEF 선언에 의해 Method 시그니처가 정해짐 |
| 상태 관리 | 일반 OO 설계 기준 | RAP Transactional Buffer와 LUW 흐름 고려 |

Behavior Pool은 개발자가 직접 `CREATE OBJECT`하거나 일반 프로그램에서 마음대로 호출하는 대상이 아니다. RAP Framework가 요청 처리 중 필요한 시점에 호출한다.

## 7. Local Handler Class

Behavior Pool 내부에는 보통 Entity별 Local Handler Class가 생성된다.

예를 들어 `ZI_JHY_RAP_ORDER` 엔티티의 alias가 `Order`라면 다음과 같은 Local Handler Class가 생길 수 있다.

```abap
CLASS lhc_Order DEFINITION INHERITING FROM cl_abap_behavior_handler.
  PRIVATE SECTION.
    METHODS set_completed FOR MODIFY
      IMPORTING keys FOR ACTION Order~set_completed RESULT result.
ENDCLASS.
```

이 코드는 다음 의미를 가진다.

| 요소 | 의미 |
|---|---|
| `lhc_Order` | Local Handler Class. 특정 RAP Entity의 Behavior 로직 담당 |
| `cl_abap_behavior_handler` | RAP Behavior Handler의 상위 클래스 |
| `set_completed` | BDEF에 선언한 Action 구현 Method |
| `FOR MODIFY` | Modify Phase에서 실행되는 Method |
| `keys` | Action 실행 대상 인스턴스의 Key 정보 |
| `RESULT result` | Action 실행 후 반환할 결과 구조 |

초급자는 Local Handler Class를 다음처럼 이해하면 된다.

```text
Behavior Pool Class 내부에서 특정 Entity의 RAP 동작을 담당하는 로컬 구현 클래스
```

## 9. Interface View `ZI_*` 예시

Behavior Implementation을 이해하려면 최소한 Root View의 필드를 알고 있어야 한다.

```abap
@AccessControl.authorizationCheck: #NOT_REQUIRED
@EndUserText.label: 'RAP Order Root Interface View'
define root view entity ZI_JHY_RAP_ORDER
  as select from ztjhy_rap_ord
{
  key order_uuid       as OrderUUID,
      order_id         as OrderID,
      customer_id      as CustomerID,
      order_status     as OrderStatus,
      gross_amount     as GrossAmount,
      currency_code    as CurrencyCode,
      created_by       as CreatedBy,
      created_at       as CreatedAt,
      last_changed_by  as LastChangedBy,
      last_changed_at  as LastChangedAt
}
```

이 View는 RAP Business Object의 Root Entity가 된다.

중요한 점은 `Behavior Implementation`이 일반적으로 이 `ZI_*` Interface View를 대상으로 하는 Behavior Definition과 연결된다는 것이다.

## 10. Projection View `ZC_*` 예시

Projection View는 소비 계층에 노출할 모델이다.

```abap
@AccessControl.authorizationCheck: #NOT_REQUIRED
@EndUserText.label: 'RAP Order Projection View'

{

      OrderID,
      CustomerID,
      OrderStatus,
      GrossAmount,
      CurrencyCode,
```

## 11. Behavior Definition 예시

이번 모듈에서 사용할 BDEF 예시는 다음과 같다.

```abap
managed implementation in class zbp_i_jhy_rap_order unique;
strict ( 2 );

define behavior for ZI_JHY_RAP_ORDER alias Order
persistent table ztjhy_rap_ord
lock master
authorization master ( instance )
{
  create;
  update;
  delete;

  field ( readonly ) OrderUUID;
  field ( readonly ) CreatedBy, CreatedAt, LastChangedBy, LastChangedAt;

  action set_completed result [1] $self;
}
```

여기서 `set_completed`는 주문 상태를 완료 상태로 바꾸는 단순 Action이다.

> 주의: Action의 개념과 UI 노출, Projection Behavior에서의 노출 방식은 후속 모듈에서 더 깊게 다룬다. 여기서는 Behavior Implementation Method 구조를 설명하기 위한 최소 예제로 사용한다.

## 12. Behavior Implementation Class 기본 구조

ADT에서 Behavior Implementation을 생성하면 Behavior Pool Class 내부에 다음과 유사한 구조가 만들어진다.

```abap
CLASS lhc_Order DEFINITION INHERITING FROM cl_abap_behavior_handler.
  PRIVATE SECTION.

    METHODS set_completed FOR MODIFY
      IMPORTING keys FOR ACTION Order~set_completed RESULT result.

ENDCLASS.

CLASS lhc_Order IMPLEMENTATION.

  METHOD set_completed.
    " 구현 로직 작성 위치
  ENDMETHOD.

ENDCLASS.
```

이 구조에서 초급자가 봐야 할 포인트는 세 가지이다.

```text
1. Method 이름은 BDEF 선언과 연결된다.
2. Method 시그니처는 RAP Framework가 요구하는 형태로 정해진다.
3. Method 내부에서는 RAP Entity 조작을 위해 EML을 사용할 수 있다.
```

## 13. Minimal Action 구현 예시

다음 코드는 `set_completed` Action을 실행하면 주문 상태를 `C`로 변경하고, 변경된 인스턴스를 결과로 반환하는 최소 예시이다.

```abap
CLASS lhc_Order IMPLEMENTATION.

  METHOD set_completed.

    MODIFY ENTITIES OF zi_jhy_rap_order IN LOCAL MODE
      ENTITY Order
        UPDATE FIELDS ( OrderStatus )
        WITH VALUE #(
          FOR key IN keys
          ( %tky        = key-%tky
            OrderStatus = 'C' ) )
      FAILED failed
      REPORTED reported.

    READ ENTITIES OF zi_jhy_rap_order IN LOCAL MODE
      ENTITY Order
        ALL FIELDS WITH CORRESPONDING #( keys )
      RESULT DATA(lt_order).

    result = VALUE #(
      FOR ls_order IN lt_order
      ( %tky   = ls_order-%tky
        %param = ls_order ) ).

  ENDMETHOD.

ENDCLASS.
```

이 코드는 짧지만 RAP Behavior Implementation의 핵심 구조를 포함한다.

| 코드 요소 | 의미 |
|---|---|
| `MODIFY ENTITIES` | RAP Entity의 데이터를 변경한다. |
| `IN LOCAL MODE` | 현재 Behavior Implementation 내부의 Transactional Buffer 기준으로 처리한다. |
| `ENTITY Order` | 조작 대상 Entity Alias를 지정한다. |
| `UPDATE FIELDS ( OrderStatus )` | 변경 대상 필드를 명시한다. |
| `WITH VALUE #( ... )` | 변경할 값을 내부 테이블 형태로 전달한다. |
| `%tky` | RAP 인스턴스를 식별하는 Technical Key이다. |
| `FAILED failed` | 실패 정보를 RAP Framework에 전달한다. |
| `REPORTED reported` | 메시지 또는 보고 정보를 전달한다. |
| `READ ENTITIES` | 변경 후 결과를 다시 읽는다. |
| `%param` | Action 결과로 반환할 Entity 데이터를 담는다. |

## 14. `keys`의 의미

Behavior Method에서 `keys`는 현재 동작의 대상 인스턴스 목록이다.

예를 들어 사용자가 UI에서 주문 3건을 선택하고 `set_completed` Action을 실행하면 `keys`에는 3건의 대상 정보가 들어올 수 있다.

```text
keys
 ├─ OrderUUID = A...
 ├─ OrderUUID = B...
 └─ OrderUUID = C...
```

초급자가 기억할 점은 다음이다.

```text
Behavior Method는 단일 건만 처리한다고 가정하면 안 된다.
항상 여러 건이 들어올 수 있다고 생각하고 LOOP 또는 FOR 표현식 기반으로 처리한다.
```

위 예제에서 `FOR key IN keys`를 사용한 이유도 이 때문이다.

## 15. `%tky`의 의미

`%tky`는 RAP Framework가 인스턴스를 식별하기 위해 사용하는 Technical Key이다.

일반적인 업무 Key와 혼동하지 않아야 한다.

| 구분 | 설명 |
|---|---|
| 업무 Key | `OrderID`, `CustomerID`처럼 업무적으로 의미 있는 식별자 |
| `%tky` | RAP 내부에서 현재 Transactional Context의 인스턴스를 식별하는 Technical Key |

Behavior Implementation 내부에서는 `%tky`를 사용하면 Draft, Late Numbering, Composition 등 다양한 RAP 흐름에서 더 안정적으로 인스턴스를 참조할 수 있다.

초급 단계에서는 다음 문장만 기억해도 충분하다.

```text
Behavior Method 내부에서 대상 인스턴스를 다시 수정하거나 읽을 때는 keys의 %tky를 활용하는 패턴이 자주 사용된다.
```

---

## 16. `failed`와 `reported`

Behavior Method의 많은 예제에는 `FAILED failed`와 `REPORTED reported`가 등장한다.

처음 보면 “변수를 선언하지 않았는데 왜 쓰지?”라고 느낄 수 있다. RAP Method Signature에서는 상황에 따라 `failed`와 `reported`가 Framework에 의해 제공되거나 Method 시그니처의 일부로 다뤄진다.

### 16.1 failed

`failed`는 실패한 인스턴스를 Framework에 알리기 위한 구조이다.

예를 들어 특정 주문이 이미 취소 상태라 완료 처리할 수 없다면, 해당 인스턴스를 `failed`에 기록할 수 있다.

초급 단계에서는 다음처럼 이해한다.

```text
failed = 이 요청 중 처리에 실패한 대상 목록
```

### 16.2 reported

`reported`는 사용자 또는 호출자에게 전달할 메시지 정보를 담는 영역이다.

예를 들어 다음과 같은 메시지를 전달할 수 있다.

```text
이미 완료된 주문입니다.
상태값이 유효하지 않습니다.
권한이 없어 변경할 수 없습니다.
```

초급 단계에서는 다음처럼 이해한다.

```text
reported = 처리 중 발생한 메시지 또는 보고 정보
```

> 메시지 클래스 기반의 정교한 오류 메시지 작성은 후속 실무 모듈에서 다루는 것이 적절하다.

---

## 17. `result`의 의미

Action이 `result [1] $self`처럼 선언되어 있으면 Method는 결과를 반환할 수 있다.

예제에서는 상태 변경 후 다시 `READ ENTITIES`를 수행하고, 읽은 데이터를 `result`에 넣었다.

```abap
result = VALUE #(
  FOR ls_order IN lt_order
  ( %tky   = ls_order-%tky
    %param = ls_order ) ).
```

여기서 `%param`은 Action 결과로 반환할 Entity 데이터이다.

초급자는 다음 정도로 이해하면 된다.

```text
Action 실행 후 화면이나 호출자에게 변경된 현재 인스턴스를 돌려주려면 result를 채운다.
```

---

## 18. EML의 역할

EML은 Entity Manipulation Language의 약자로, RAP Entity를 조작하는 ABAP 문법이다.

Behavior Implementation 내부에서는 DB 테이블에 직접 `UPDATE ztjhy_rap_ord`를 쓰는 대신, RAP Entity 기준으로 조작하는 것이 기본 흐름이다.

| 접근 방식 | 권장도 | 이유 |
|---|---|---|
| `MODIFY ENTITIES OF zi_*` | 권장 | RAP Transactional Buffer와 Behavior 흐름을 따른다. |
| `READ ENTITIES OF zi_*` | 권장 | RAP Entity 기준으로 데이터를 읽는다. |
| 직접 `UPDATE ztable` | 신중 | RAP Framework의 상태 관리와 충돌할 수 있다. |
| 직접 `COMMIT WORK` | 비권장 | RAP 트랜잭션 제어를 깨뜨릴 수 있다. |

Behavior Implementation에서는 RAP Framework의 트랜잭션 흐름을 존중해야 한다.

---

## 19. `IN LOCAL MODE`의 감각

`IN LOCAL MODE`는 Behavior Implementation 내부에서 현재 Local Transactional Buffer를 기준으로 Entity를 조작한다는 의미로 이해하면 된다.

초급 단계에서는 다음처럼 설명할 수 있다.

```text
RAP 요청 처리 중 아직 DB Commit까지 끝나지 않은 변경 내용을 포함해,
현재 RAP 처리 흐름 안에서 Entity를 읽고 수정하기 위한 모드
```

이 개념은 Draft, Save Sequence, Late Numbering 등과 연결되므로 깊은 설명은 후속 RAP 심화에서 다룬다.

---

## 20. Behavior Implementation 생성 절차

ADT 기준으로 Behavior Implementation 생성 흐름은 다음과 같다.

```text
1. Behavior Definition을 연다.
2. BDEF에 managed implementation in class ... 구문이 있는지 확인한다.
3. 구현 클래스가 없으면 Quick Fix 또는 생성 기능을 사용한다.
4. Behavior Pool Class를 생성한다.
5. Local Handler Class의 Method Stub을 확인한다.
6. 필요한 Method 내부에 구현 로직을 작성한다.
7. Syntax Check를 수행한다.
8. Activate한다.
```

RAP 개발은 Eclipse ADT에서 진행하는 것이 표준적이다. SAP GUI 800에서는 RAP Behavior Implementation 개발 편의성이 제한적이다.

---

## 21. 구현 시 정상 흐름

정상적인 Behavior Implementation 작업 흐름은 다음과 같다.

```text
BDEF에서 동작 선언
  → Behavior Pool Class 생성
  → Local Handler Method Stub 생성
  → Method 내부 로직 작성
  → Syntax Check
  → Activate
  → Preview 또는 Service Binding 단계에서 동작 확인
```

이번 모듈에서는 Service Binding 테스트는 아직 상세히 다루지 않는다. 다음 모듈에서 Service Definition과 Service Binding을 통해 외부 서비스로 노출하는 흐름을 학습한다.

## 22. 자주 발생하는 오류와 해결

### 22.1 Behavior Pool Class가 존재하지 않음

| 항목 | 내용 |
|---|---|
| 증상 | BDEF에 implementation class가 선언되어 있지만 클래스가 없거나 활성화되지 않음 |
| 원인 | Quick Fix 미수행, 클래스 생성 누락, 활성화 실패 |
| 해결 | ADT에서 Behavior Implementation Class 생성 후 Activate |

### 22.2 Method Stub이 생성되지 않음

| 항목 | 내용 |
|---|---|
| 증상 | BDEF에 Action을 선언했지만 구현 Method가 보이지 않음 |
| 원인 | Quick Fix 미수행, BDEF Syntax 오류, Alias 불일치 |
| 해결 | BDEF Activate 후 Quick Fix를 다시 수행하고 Method Signature 확인 |

### 22.3 Entity Alias 불일치

| 항목 | 내용 |
|---|---|
| 증상 | `Order~set_completed`를 참조할 수 없다는 오류 발생 |
| 원인 | BDEF의 alias와 구현 Method의 Entity 이름이 다름 |
| 해결 | BDEF의 `alias Order`와 Method 시그니처의 Entity 명칭을 일치시킴 |

### 22.4 Field 이름 불일치

| 항목 | 내용 |
|---|---|
| 증상 | `OrderStatus` 필드를 찾을 수 없음 |
| 원인 | CDS View Element 이름과 코드에서 사용한 이름이 다름 |
| 해결 | `ZI_*` Interface View의 Element 이름을 기준으로 코드 수정 |

### 22.5 Direct DB Update 사용

| 항목 | 내용 |
|---|---|
| 증상 | 저장 흐름이 예상과 다르거나 RAP 상태와 충돌 가능 |
| 원인 | Behavior Implementation 내부에서 Persistent Table을 직접 UPDATE |
| 해결 | 가능하면 `MODIFY ENTITIES`를 사용하여 RAP Entity 기준으로 변경 |

### 22.6 COMMIT WORK 사용

| 항목 | 내용 |
|---|---|
| 증상 | RAP 요청 처리 중 트랜잭션 오류 또는 예측 불가 동작 발생 가능 |
| 원인 | Behavior Implementation 내부에서 직접 Commit 수행 |
| 해결 | Commit 제어는 RAP Framework에 맡기고 직접 `COMMIT WORK`를 사용하지 않음 |

## 23. 실무 설계 기준

Behavior Implementation은 단순히 코드가 실행되는 위치가 아니라, RAP Business Object의 업무 규칙이 집중되는 영역이다.

### 23.1 구현 클래스에 넣기 적합한 로직

| 로직 | 예시 |
|---|---|
| 상태 변경 | 주문 완료, 승인, 반려 처리 |
| 자동값 세팅 | 생성자, 생성일시, 변경자, 변경일시 |
| 업무 검증 | 필수값, 상태 전이 가능 여부 |
| 파생값 계산 | 금액 합계, 상태 텍스트, 계산 필드 |
| 권한 판단 | 인스턴스별 변경 가능 여부 |

### 23.2 구현 클래스에 넣을 때 신중해야 하는 로직

| 로직 | 주의 이유 |
|---|---|
| 대량 SELECT 반복 호출 | 성능 저하 가능 |
| 외부 시스템 동기 호출 | 응답 지연과 실패 처리 복잡도 증가 |
| 직접 DB Commit | RAP 트랜잭션 흐름 훼손 가능 |
| UI 전용 판단 | Projection/UI Annotation 계층과 역할 혼동 가능 |
| 과도한 공통 유틸리티 | Behavior Pool이 비대해질 수 있음 |

### 23.3 권장 구조

실무에서는 Behavior Method 안에 모든 코드를 길게 작성하기보다, 필요하면 별도 도메인 서비스 클래스나 유틸리티 클래스로 분리할 수 있다.

```text
Behavior Method
  → RAP 요청/응답, failed/reported/result 처리
  → 핵심 업무 계산은 별도 Class에 위임 가능
```

다만 초급 단계에서는 먼저 Behavior Method의 표준 흐름을 이해하는 것이 우선이다.

## 24. 실습 과제

### 24.1 기본 과제

다음 조건으로 `set_completed` Action 구현을 완성한다.

| 항목 | 값 |
|---|---|
| Interface View | `ZI_JHY_RAP_ORDER` |
| Projection View | `ZC_JHY_RAP_ORDER` |
| Behavior Pool | `ZBP_I_JHY_RAP_ORDER` |
| Action | `set_completed` |
| 변경 필드 | `OrderStatus` |
| 완료 상태값 | `C` |

완성 기준:

```text
1. BDEF에 action set_completed result [1] $self 선언이 있다.
2. Behavior Pool Class에 Method Stub이 있다.
3. Method 내부에서 MODIFY ENTITIES를 사용한다.
4. 변경 후 READ ENTITIES로 결과를 읽는다.
5. result에 %param을 채운다.
6. Syntax Check와 Activate가 성공한다.
```

### 24.2 확장 과제

다음 조건을 추가로 생각해본다.

```text
이미 OrderStatus가 'C'인 주문에 set_completed를 다시 실행하면 어떻게 할 것인가?
취소 상태 'X'인 주문은 완료 처리하면 안 되는가?
상태 변경 메시지를 reported에 어떻게 전달할 것인가?
```

이 확장 과제의 상세 구현은 `Validation / Determination / Action 개요`에서 더 깊게 다룬다.

## 26. 평가 문제

### 26.1 객관식

#### Q1. Behavior Implementation의 가장 적절한 설명은?

A. CDS View의 화면 라벨을 정의하는 객체이다.  
B. BDEF에 선언된 동작 중 개발자 로직이 필요한 부분을 ABAP Class Method로 구현하는 영역이다.  
C. OData 서비스를 외부에 공개하는 Binding 객체이다.  
D. SAP GUI에서 테이블 데이터를 직접 편집하는 도구이다.

정답: B

#### Q2. Managed Scenario에서 표준 CRUD 저장 흐름에 대한 설명으로 가장 적절한 것은?

A. 모든 CRUD는 개발자가 직접 SQL로 구현해야 한다.  
B. Managed Scenario에서는 Framework가 기본 CRUD 흐름을 처리하며, 개발자는 업무 규칙이 필요한 부분을 구현한다.  
C. Managed Scenario에서는 Behavior Implementation이 존재할 수 없다.  
D. Managed Scenario에서는 CDS View가 필요 없다.

정답: B

#### Q3. Behavior Implementation 내부에서 직접 `COMMIT WORK`를 사용하는 것에 대한 설명으로 적절한 것은?

A. 항상 권장된다.  
B. 성능을 위해 필수이다.  
C. RAP Framework의 트랜잭션 제어를 깨뜨릴 수 있으므로 피해야 한다.  
D. Projection View를 자동 생성한다.

정답: C

### 26.2 서술형

#### Q1. BDEF와 Behavior Implementation의 차이를 설명하시오.

모범 답안:  
BDEF는 RAP Business Object가 지원하는 동작을 선언하는 객체이고, Behavior Implementation은 그 선언된 동작 중 개발자 로직이 필요한 부분을 ABAP Class Method로 구현하는 영역이다. BDEF가 계약이라면 Behavior Implementation은 계약의 실행 로직이다.

#### Q2. `keys`와 `%tky`의 역할을 설명하시오.

모범 답안:  
`keys`는 현재 Behavior Method 실행 대상 인스턴스 목록이며, `%tky`는 RAP 내부에서 해당 인스턴스를 안정적으로 식별하기 위한 Technical Key이다. Behavior Method 내부에서 대상 인스턴스를 다시 수정하거나 읽을 때 자주 사용된다.

#### Q3. `MODIFY ENTITIES`를 사용하는 이유를 설명하시오.

모범 답안:  
RAP Entity 기준으로 데이터를 변경하여 RAP Framework의 Transactional Buffer와 Behavior 흐름을 따르기 위해 사용한다. Persistent Table을 직접 UPDATE하면 RAP 상태 관리와 충돌할 수 있으므로 Behavior Implementation에서는 EML 사용이 권장된다.

## 27. 초급자 핵심 요약

```text
Behavior Definition은 동작을 선언한다.
Behavior Implementation은 선언된 동작을 ABAP Class Method로 구현한다.
Managed Scenario에서도 업무 규칙 구현을 위해 Behavior Pool Class가 필요할 수 있다.
Behavior Pool 내부에는 Entity별 Local Handler Class가 생성된다.
Behavior Method는 keys를 입력받아 여러 인스턴스를 처리할 수 있어야 한다.
RAP 내부 인스턴스 식별에는 %tky가 자주 사용된다.
Entity 변경은 가능한 한 MODIFY ENTITIES를 사용한다.
직접 DB UPDATE나 COMMIT WORK는 RAP 트랜잭션 흐름을 깨뜨릴 수 있으므로 피한다.
```
