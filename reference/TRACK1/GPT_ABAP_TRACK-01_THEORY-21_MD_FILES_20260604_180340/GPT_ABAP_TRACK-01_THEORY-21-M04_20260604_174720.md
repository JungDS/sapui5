
이번 모듈에서는 같은 Business Object에 대해 **어떤 행위를 허용할 것인가**를 정의하는 `Behavior Definition`, 즉 **BDEF**를 학습한다.

이번 모듈의 핵심 흐름은 다음과 같다.

```text

→ ZC_* Projection View 확인
→ Behavior Definition의 목적 이해
→ Managed Scenario 기준 Interface BDEF 작성
→ strict(2)의 의미 이해
→ create / update / delete 기본 선언
→ Root-Child Association의 create 허용 방식 확인
→ Projection BDEF에서 use create / use update / use delete 선언
→ Activation 순서와 오류 확인
```

이번 모듈에서는 Behavior Implementation 클래스의 내부 로직, Validation, Determination, Action을 깊게 구현하지 않는다.

## 2. 선수 지식

Behavior Definition은 RAP의 중간 이후 단계에 등장하는 객체이다.  
초급자가 BDEF를 이해하려면 최소한 다음 개념이 필요하다.

| 선수 지식 | 필요한 이유 |
|---|---|
| RAP 아키텍처 | BDEF가 BO의 동작 계층에 위치한다는 점을 이해해야 한다. |
| CDS View Entity | BDEF는 CDS View Entity를 대상으로 작성한다. |
| Interface View `ZI_*` | Interface BDEF의 대상이 되는 내부 모델이다. |
| Projection View `ZC_*` | Projection BDEF의 대상이 되는 소비 모델이다. |
| Root / Child Composition | Root와 Child의 생성·삭제 흐름을 이해해야 한다. |
| ABAP Class 기본 개념 | 후속 Behavior Implementation에서 클래스와 메서드가 사용된다. |

초급자는 다음 문장을 기억하면 된다.

> CDS View는 데이터의 모양을 정의하고, Behavior Definition은 그 데이터에 허용되는 행위를 정의한다.

---

## 3. Behavior Definition이란 무엇인가?

Behavior Definition은 RAP Business Object의 동작을 선언하는 객체이다.

RAP에서 Business Object는 단순히 CDS View만으로 완성되지 않는다.  
CDS View가 “어떤 데이터 구조를 노출할 것인가”를 정의한다면, Behavior Definition은 “그 데이터에 대해 어떤 업무 행위를 허용할 것인가”를 정의한다.

예를 들어 주문 Business Object가 있다고 하자.

```text
Order Header
 ├─ 생성 가능
 ├─ 수정 가능
 ├─ 삭제 가능
 └─ Item 생성 가능

Order Item
 ├─ Header 아래에서 생성 가능
 ├─ 수정 가능
 └─ 삭제 가능
```

이런 동작은 Projection View나 Interface View의 필드 목록만으로는 표현되지 않는다.  
이 동작 계약을 선언하는 객체가 BDEF이다.

---

## 4. RAP BO에서 BDEF의 위치

RAP 기본 계층을 단순화하면 다음과 같다.

```text
Database Table
  ↓
CDS Interface View ZI_*
  ↓
Behavior Definition for ZI_*     ← 이번 모듈의 핵심 1
  ↓
CDS Projection View ZC_*
  ↓
Behavior Projection for ZC_*     ← 이번 모듈의 핵심 2
  ↓
Service Definition / Binding
  ↓
OData V4 / Fiori Elements / 외부 소비자
```

중요한 점은 BDEF가 하나만 있는 것이 아니라는 점이다.

| 구분 | 대상 | 역할 |
|---|---|---|
| Interface BDEF | `ZI_*` | BO 내부 동작의 원천 정의 |
| Projection BDEF | `ZC_*` | 외부 소비 모델에서 사용할 동작 선택 |

초급자는 다음처럼 이해하면 된다.

```text
ZI_* BDEF = Business Object가 실제로 할 수 있는 동작의 정의
ZC_* BDEF = 서비스에 노출할 동작의 선택 또는 투영
```

## 5. 왜 CDS View만으로는 충분하지 않은가?

앞선 모듈에서 `ZI_GPT_Order`, `ZC_GPT_Order` 같은 CDS View를 만들었다고 가정하자.  
이 View들은 데이터 필드와 Association을 정의한다.

예를 들어 `ZC_GPT_Order`가 다음 필드를 노출할 수 있다.

```text
OrderUUID
OrderID
CustomerID
OrderStatus
GrossAmount
CurrencyCode
LastChangedAt
_Item
```

그러나 이것만으로는 다음 질문에 답할 수 없다.

```text
이 Order는 생성 가능한가?
OrderID는 수정 가능한가?
삭제는 허용되는가?
Item은 Header 없이 단독 생성 가능한가?
저장 전에 어떤 검증이 필요한가?
상태 변경 Action은 있는가?
동시 변경 충돌은 어떻게 감지할 것인가?
```

BDEF는 이 질문에 답하기 시작하는 객체이다.

## 6. Managed Scenario와 Unmanaged Scenario

RAP Behavior Definition은 크게 Managed와 Unmanaged 시나리오에서 사용된다.

| 구분 | 설명 | 초급 학습 기준 |
|---|---|---|
| Managed | RAP Framework가 기본 CRUD 저장 흐름을 상당 부분 처리 | 입문 단계 권장 |
| Unmanaged | 개발자가 저장/변경 로직을 더 직접 구현 | 심화 단계 |

이번 모듈은 **Managed Scenario**를 기준으로 설명한다.

Managed Scenario에서는 BDEF에 `managed implementation in class ... unique;` 형태로 선언하고, Persistence Table과 Mapping을 지정한다.  
RAP Framework가 기본 Create/Update/Delete 흐름을 제공하며, 개발자는 필요한 경우 Validation, Determination, Action, Additional Save Logic 등을 구현한다.

> [추정] 실제 프로젝트에서는 기존 레거시 저장 로직, BAPI, Function Module, 특수 DB 구조가 있으면 Unmanaged Scenario를 검토할 수 있다. 그러나 입문 교육에서는 Managed Scenario를 먼저 익히는 것이 적절하다.

## 8. Interface BDEF의 기본 형태

Managed Scenario 기준 Interface BDEF의 기본 형태는 다음과 같다.

```abap
managed implementation in class zbp_i_gpt_order unique;
strict ( 2 );

with draft;

define behavior for ZI_GPT_Order alias Order
persistent table zt_gpt_order
draft table zt_gpt_order_d
lock master
authorization master ( instance )
etag master LastChangedAt
{
  create;
  update;
  delete;

  association _Item { create; with draft; }

  mapping for zt_gpt_order
  {
    OrderUUID     = order_uuid;
    OrderID       = order_id;
    CustomerID    = customer_id;
    OrderStatus   = order_status;
    GrossAmount   = gross_amount;
    CurrencyCode  = currency_code;
    CreatedBy     = created_by;
    CreatedAt     = created_at;
    LastChangedBy = last_changed_by;
    LastChangedAt = last_changed_at;
  }
}

define behavior for ZI_GPT_OrderItem alias Item
persistent table zt_gpt_orderitem
draft table zt_gpt_orderitem_d
lock dependent by _Order
authorization dependent by _Order
etag dependent by _Order
{
  update;
  delete;

  association _Order { with draft; }

  mapping for zt_gpt_orderitem
  {
    OrderUUID     = order_uuid;
    ItemUUID      = item_uuid;
    ItemNo        = item_no;
    ProductID     = product_id;
    Quantity      = quantity;
    Unit          = unit;
    NetAmount     = net_amount;
    CurrencyCode  = currency_code;
    CreatedBy     = created_by;
    CreatedAt     = created_at;
    LastChangedBy = last_changed_by;
    LastChangedAt = last_changed_at;
  }
}
```

위 코드는 RAP 초급 학습을 위한 형태이다.  
실제 시스템에서는 CDS View, Persistent Table, Draft Table, 필드명, Annotation, Behavior 옵션이 프로젝트 기준에 따라 달라질 수 있다.

> [추정] 교육 시스템에서 Draft를 아직 다루지 않는다면 `with draft`, `draft table`, `with draft` 관련 문장을 제외하고 Non-Draft Managed Scenario로 먼저 실습할 수 있다. 다만 최신 Fiori Elements 기반 실무 RAP에서는 Draft가 자주 함께 다뤄지므로 코드 예시에는 Draft 흐름을 함께 보여주었다.

## 9. `managed implementation in class ... unique` 의미

BDEF의 첫 줄은 매우 중요하다.

```abap
managed implementation in class zbp_i_gpt_order unique;
```

이 문장은 다음을 의미한다.

| 부분 | 의미 |
|---|---|
| `managed` | RAP Managed Scenario를 사용한다. |
| `implementation in class` | Behavior Implementation 클래스가 존재한다. |
| `zbp_i_gpt_order` | Behavior Pool 또는 Behavior Implementation Class 이름이다. |
| `unique` | 이 Behavior Definition과 연결되는 구현 클래스가 고유하다는 의미이다. |

초급자는 다음처럼 이해하면 된다.

```text
이 Business Object의 기본 저장 흐름은 RAP Framework가 관리하고,
필요한 추가 동작은 ZBP_I_GPT_ORDER 클래스에서 구현한다.
```

이번 모듈에서는 클래스 내부 구현을 깊게 다루지 않는다.  
그 내용은 다음 모듈 `THEORY-21-M05 — Behavior Implementation 기초`에서 다룬다.

## 10. `strict(2)`의 의미

BDEF에서 자주 보이는 문장이다.

```abap
strict ( 2 );
```

`strict(2)`는 Behavior Definition 작성 시 더 엄격한 문법과 모델링 규칙을 적용하도록 하는 선언이다.

초급 관점에서 중요한 의미는 다음이다.

| 의미 | 설명 |
|---|---|
| 엄격한 모델링 | RAP BO를 더 명확한 규칙에 맞춰 작성하게 한다. |
| 오류 조기 발견 | 느슨한 선언으로 인한 잠재 오류를 활성화 시점에 잡기 쉽다. |
| 최신 RAP 스타일 | ABAP Platform의 현대적 RAP 개발 방식과 잘 맞는다. |
| 학습 효과 | 잘못된 Association, Mapping, Action 선언을 조기에 확인할 수 있다. |

`strict(2)`를 넣으면 처음에는 오류가 더 많이 보일 수 있다.  
그러나 이것은 나쁜 것이 아니다. 오히려 모델 설계 오류를 초기 단계에서 드러내는 효과가 있다.

> 초급자 핵심: `strict(2)`는 불편하게 만드는 옵션이 아니라, 잘못된 RAP 모델을 일찍 발견하게 해주는 안전장치로 이해한다.

## 11. `define behavior for ... alias ...` 의미

Root Entity의 BDEF는 보통 다음처럼 시작한다.

```abap
define behavior for ZI_GPT_Order alias Order
```

| 부분 | 의미 |
|---|---|
| `define behavior for` | 특정 CDS Entity에 대한 동작을 정의한다. |
| `ZI_GPT_Order` | 대상 Interface View Entity이다. |
| `alias Order` | BDEF 내부에서 사용할 짧은 별칭이다. |

Alias를 사용하면 BDEF 내부와 Behavior Implementation에서 Entity를 더 명확하게 다룰 수 있다.

예를 들어 `ZI_GPT_OrderItem`보다 `Item`이라는 Alias가 읽기 쉽다.

```abap
define behavior for ZI_GPT_OrderItem alias Item
```

## 12. Persistent Table과 Mapping

Managed Scenario에서 중요한 설정 중 하나는 Persistent Table이다.

```abap
persistent table zt_gpt_order
```

이 문장은 `ZI_GPT_Order`의 데이터가 실제로 `ZT_GPT_ORDER` 테이블에 저장된다는 것을 나타낸다.

하지만 CDS View의 필드명과 DB Table의 필드명이 항상 같지는 않다.  
그래서 Mapping이 필요하다.

```abap
mapping for zt_gpt_order
{
  OrderUUID     = order_uuid;
  OrderID       = order_id;
  CustomerID    = customer_id;
  OrderStatus   = order_status;
  GrossAmount   = gross_amount;
  CurrencyCode  = currency_code;
}
```

왼쪽은 CDS Entity 필드명, 오른쪽은 Persistent Table 필드명이다.

| 방향 | 예 |
|---|---|
| CDS Field | `OrderUUID` |
| DB Table Field | `order_uuid` |

초급자는 다음을 기억한다.

```text
Managed RAP에서 BDEF Mapping은 CDS 필드와 DB 테이블 필드를 연결하는 계약이다.
```

## 13. CRUD 선언

BDEF에서 가장 직관적인 부분은 CRUD 선언이다.

```abap
create;
update;
delete;
```

이 선언은 해당 Entity에서 어떤 변경 동작을 허용할지 정의한다.

| 선언 | 의미 |
|---|---|
| `create;` | 새 인스턴스 생성 허용 |
| `update;` | 기존 인스턴스 수정 허용 |
| `delete;` | 기존 인스턴스 삭제 허용 |

초급자가 주의할 점은 다음이다.

```text
CDS View에 필드가 있다고 해서 자동으로 생성/수정/삭제가 되는 것은 아니다.
BDEF에 동작이 선언되어야 RAP BO의 변경 가능성이 생긴다.
```

---

## 14. Root Entity와 Child Entity의 CRUD 차이

Root Entity와 Child Entity의 CRUD 선언은 보통 다르게 설계한다.

### 14.1 Root Entity

Root는 Business Object의 시작점이다.  
예제에서는 Order Header가 Root이다.

```abap
define behavior for ZI_GPT_Order alias Order
{
  create;
  update;
  delete;

  association _Item { create; }
}
```

Root에서는 일반적으로 `create`, `update`, `delete`를 선언할 수 있다.

### 14.2 Child Entity

Child는 Root 아래에 종속된다.  
예제에서는 Order Item이 Child이다.

```abap
define behavior for ZI_GPT_OrderItem alias Item
{
  update;
  delete;

  association _Order { }
}
```

Child에 `create;`를 직접 선언하지 않는 경우가 많다.  
대신 Root의 Association에서 다음처럼 Child 생성을 허용한다.

```abap
association _Item { create; }
```

이 의미는 다음과 같다.

```text
Item은 Order와 무관하게 단독 생성되는 것이 아니라,
Order의 _Item Association을 통해 생성된다.
```

이것이 Composition 관계의 핵심이다.

---

## 15. `association _Item { create; }` 의미

Root BDEF 안의 Association 선언을 보자.

```abap
association _Item { create; }
```

이 문장은 Root Entity인 Order에서 Child Entity인 Item을 생성할 수 있음을 의미한다.

| 구성 | 의미 |
|---|---|
| `_Item` | Root View에 정의된 Composition Association |
| `{ create; }` | 해당 Association을 통해 Child 생성 허용 |

초급자는 다음처럼 이해한다.

```text
Order를 만들면서 그 아래 Item을 같이 만들 수 있게 허용한다.
```

RAP에서 Root-Child Composition은 단순 조회 관계가 아니다.  
Lifecycle 관계이다. Root가 삭제되면 Child도 함께 영향을 받을 수 있고, Child는 Root의 소유 관계 안에서 관리된다.

---

## 16. Lock 설정

BDEF에서 Lock 설정은 동시성 제어와 관련된다.

Root Entity에는 보통 다음과 같은 선언이 있다.

```abap
lock master
```

Child Entity에는 다음과 같은 선언이 있을 수 있다.

```abap
lock dependent by _Order
```

초급 관점의 의미는 다음이다.

| 선언 | 의미 |
|---|---|
| `lock master` | Root Entity가 Lock의 기준이 된다. |
| `lock dependent by _Order` | Child Entity는 Parent Association을 통해 Root의 Lock에 종속된다. |

즉, Item을 변경할 때도 결국 Header인 Order의 Lock 기준을 따라간다고 이해할 수 있다.

> Lock Object 자체의 세부 생성과 동시성 제어 심화는 Track 2의 데이터 변경/동시성 제어 영역에서 더 적절하게 다룬다. 이번 모듈에서는 RAP BDEF에서 Lock 선언이 BO 변경 안정성과 연결된다는 점만 이해한다.

---

## 17. Authorization 설정

BDEF에는 Authorization 관련 선언도 등장한다.

Root Entity 예시:

```abap
authorization master ( instance )
```

Child Entity 예시:

```abap
authorization dependent by _Order
```

초급 관점에서는 다음처럼 이해한다.

| 선언 | 의미 |
|---|---|
| `authorization master ( instance )` | Root 인스턴스 기준 권한 점검을 고려한다. |
| `authorization dependent by _Order` | Child 권한은 Parent인 Order 기준에 종속된다. |

이번 모듈에서는 권한 로직을 구현하지 않는다.  
다만 BDEF가 단순 CRUD 선언만이 아니라, 권한과 잠금 같은 엔터프라이즈 동작의 선언 지점이라는 점을 이해해야 한다.

---

## 18. ETag 설정

ETag는 동시 변경 감지와 관련된 중요한 개념이다.

Root Entity에서 다음처럼 선언할 수 있다.

```abap
etag master LastChangedAt
```

이는 `LastChangedAt` 필드를 기준으로 Entity의 변경 상태를 감지한다는 의미로 이해할 수 있다.

| 항목 | 설명 |
|---|---|
| `etag master` | Root Entity의 ETag 기준 지정 |
| `LastChangedAt` | 마지막 변경 시각 필드 |

초급자는 ETag를 다음처럼 이해하면 된다.

```text
두 사용자가 같은 데이터를 동시에 수정할 때,
어느 한쪽이 오래된 데이터를 기반으로 저장하는 상황을 감지하기 위한 기준이다.
```

실무 RAP 서비스에서는 동시성 제어가 매우 중요하다.  
이번 모듈에서는 `LastChangedAt` 같은 변경 시각 필드가 단순 감사 필드가 아니라 RAP 동작 안정성과도 연결될 수 있음을 이해한다.

---

## 19. Draft 관련 선언

RAP에서는 Draft 기능을 통해 사용자가 데이터를 임시 저장하고 나중에 활성화할 수 있다.

Draft를 사용하는 경우 BDEF에 다음과 같은 문장이 포함될 수 있다.

```abap
with draft;
```

Entity별로 Draft Table도 지정할 수 있다.

```abap
draft table zt_gpt_order_d
```

초급자는 Draft를 다음처럼 이해한다.

```text
Fiori 앱에서 사용자가 입력 중인 데이터를 바로 활성 데이터로 저장하지 않고,
초안 상태로 저장해두는 기능이다.
```

다만 Draft는 RAP 초급 학습에서 한 번에 깊게 다루기에는 범위가 넓다.  
따라서 이번 모듈에서는 다음 원칙만 잡는다.

| 구분 | 학습 기준 |
|---|---|
| Non-Draft Managed | 가장 단순한 CRUD 학습에 적합 |
| Draft Managed | Fiori Elements 실무 흐름과 더 가깝지만 설정이 늘어남 |

> [추정] 교육 시간이 제한되어 있다면 먼저 Non-Draft BDEF로 CRUD 흐름을 이해한 뒤, 별도 실습에서 Draft를 추가하는 방식이 좋다.

---

## 20. Projection BDEF의 기본 형태

Projection View `ZC_*`에는 Projection BDEF를 작성한다.

예시:

```abap
projection;
strict ( 2 );

define behavior for ZC_GPT_Order alias Order
{
  use create;
  use update;
  use delete;

  use association _Item { create; }
}

define behavior for ZC_GPT_OrderItem alias Item
{
  use update;
  use delete;

  use association _Order;
}
```

Projection BDEF는 Interface BDEF처럼 Persistent Table을 직접 지정하지 않는다.  
이미 `ZC_*`는 `ZI_*`를 Projection한 객체이고, 실제 동작의 원천은 Interface BDEF에 있기 때문이다.

---

## 21. Interface BDEF와 Projection BDEF 비교

| 구분 | Interface BDEF | Projection BDEF |
|---|---|---|
| 대상 | `ZI_*` | `ZC_*` |
| 역할 | BO 내부 동작 원천 정의 | 소비 모델에서 사용할 동작 선택 |
| Persistent Table | 지정함 | 직접 지정하지 않음 |
| Mapping | 작성함 | 일반적으로 작성하지 않음 |
| CRUD 선언 | `create;`, `update;`, `delete;` | `use create;`, `use update;`, `use delete;` |
| Association 생성 | `association _Item { create; }` | `use association _Item { create; }` |
| 구현 클래스 연결 | 있음 | 보통 없음 |

초급자는 다음 문장을 기억하면 된다.

```text
Interface BDEF는 동작을 정의하고,
Projection BDEF는 정의된 동작 중 외부에 사용할 것을 선택한다.
```

---

## 22. `use create`, `use update`, `use delete` 의미

Projection BDEF에서는 `create`, `update`, `delete` 앞에 `use`가 붙는다.

```abap
use create;
use update;
use delete;
```

이는 “Interface BDEF에서 정의된 동작을 Projection 계층에서도 사용하겠다”는 의미이다.

중요한 점은 Projection BDEF가 Interface BDEF에 없는 동작을 새로 만들어낼 수 없다는 점이다.

예를 들어 Interface BDEF에 `delete;`가 없는데 Projection BDEF에 `use delete;`를 쓰면 오류가 발생할 수 있다.

```text
원천 BDEF에 없는 동작은 Projection에서 사용할 수 없다.
```

## 23. 실습: Interface BDEF 생성 절차

### 23.1 실습 목표

`ZI_GPT_Order`와 `ZI_GPT_OrderItem`을 대상으로 Managed Scenario Interface BDEF를 생성한다.

### 23.2 ADT에서 생성

RAP BDEF는 보통 ADT에서 작성한다.

```text
1. Eclipse ADT 실행
2. Project Explorer에서 패키지 선택
3. New → Other ABAP Repository Object
4. Business Services 또는 Core Data Services 관련 항목에서 Behavior Definition 선택
5. 대상 CDS Entity: ZI_GPT_Order 선택
6. 생성 마법사 진행
7. BDEF 코드 작성
8. Activate
```

시스템 버전과 ADT 플러그인 버전에 따라 메뉴명은 다소 다를 수 있다.  
중요한 것은 BDEF가 ABAP Repository Object이며, 대상 CDS Entity와 연결된다는 점이다.

### 23.3 작성할 최소 Non-Draft 예시

처음 실습에서는 Draft를 제외한 최소 예시가 더 이해하기 쉽다.

```abap
managed implementation in class zbp_i_gpt_order unique;
strict ( 2 );

define behavior for ZI_GPT_Order alias Order
persistent table zt_gpt_order
lock master
authorization master ( instance )
etag master LastChangedAt
{
  create;
  update;
  delete;

  association _Item { create; }

  mapping for zt_gpt_order
  {
    OrderUUID     = order_uuid;
    OrderID       = order_id;
    CustomerID    = customer_id;
    OrderStatus   = order_status;
    GrossAmount   = gross_amount;
    CurrencyCode  = currency_code;
    CreatedBy     = created_by;
    CreatedAt     = created_at;
    LastChangedBy = last_changed_by;
    LastChangedAt = last_changed_at;
  }
}

define behavior for ZI_GPT_OrderItem alias Item
persistent table zt_gpt_orderitem
lock dependent by _Order
authorization dependent by _Order
etag dependent by _Order
{
  update;
  delete;

  association _Order;

  mapping for zt_gpt_orderitem
  {
    OrderUUID     = order_uuid;
    ItemUUID      = item_uuid;
    ItemNo        = item_no;
    ProductID     = product_id;
    Quantity      = quantity;
    Unit          = unit;
    NetAmount     = net_amount;
    CurrencyCode  = currency_code;
    CreatedBy     = created_by;
    CreatedAt     = created_at;
    LastChangedBy = last_changed_by;
    LastChangedAt = last_changed_at;
  }
}
```

### 23.4 실습 중 확인할 항목

| 확인 항목 | 설명 |
|---|---|
| CDS Entity 이름 | `ZI_GPT_Order`, `ZI_GPT_OrderItem`이 정확한가 |
| Persistent Table 이름 | `zt_gpt_order`, `zt_gpt_orderitem`이 실제 존재하는가 |
| Mapping 필드 | CDS 필드와 DB 필드가 모두 매핑되었는가 |
| Association 이름 | CDS View의 Association 이름과 BDEF 선언이 일치하는가 |
| ETag 필드 | `LastChangedAt` 필드가 CDS View에 노출되어 있는가 |
| Lock / Authorization | Root와 Child의 종속 관계가 일관적인가 |
| Activation | 오류 없이 활성화되는가 |

### 24.2 작성할 예시

### 24.3 Projection BDEF 검증 포인트

| 확인 항목 | 설명 |
|---|---|
| `projection;` 선언 | Projection BDEF임을 나타낸다. |
| 대상 Entity | `ZC_*` Projection View를 대상으로 한다. |
| `use` 키워드 | Interface BDEF의 동작을 사용한다. |
| Association 이름 | Projection View에서 Redirection된 Association 이름과 일치해야 한다. |
| 원천 동작 존재 | Interface BDEF에 해당 동작이 먼저 정의되어 있어야 한다. |

## 25. Activation 순서

RAP 객체는 선후수 관계가 강하다.  
활성화 순서를 무시하면 불필요한 오류를 많이 만난다.

권장 활성화 순서는 다음과 같다.

```text
1. Database Table
2. Interface View ZI_* Root / Child
3. Projection View ZC_* Root / Child
4. Interface BDEF for ZI_*
5. Projection BDEF for ZC_*
6. Behavior Implementation Class
7. Service Definition
8. Service Binding
```

다만 실제 ADT에서는 객체 생성 마법사나 Quick Fix가 일부 객체를 자동 생성하기도 한다.  
그래도 초급자는 위 선후수 관계를 이해하고 있어야 오류를 추적할 수 있다.

---

## 26. 자주 발생하는 오류와 해결

### 26.1 CDS Entity 이름 불일치

#### 증상

BDEF 활성화 시 대상 Entity를 찾을 수 없다는 오류가 발생한다.

#### 원인

`ZI_GPT_Order` 대신 `ZI_GPT_ORDER`처럼 실제 객체명과 다른 이름을 입력했을 수 있다.

#### 해결

ADT 또는 Repository Browser에서 정확한 CDS Entity 이름을 확인한다.

---

### 26.2 Persistent Table이 없거나 필드명이 다름

#### 증상

Mapping 관련 오류가 발생한다.

#### 원인

BDEF의 `mapping for zt_gpt_order`에서 지정한 DB 필드명이 실제 테이블 필드와 다르다.

#### 해결

다음 세 가지를 비교한다.

```text
CDS View Field Name
Persistent Table Field Name
BDEF Mapping
```

세 이름이 같은지보다, Mapping이 정확한지가 중요하다.

---

### 26.3 ETag 필드가 CDS View에 없음

#### 증상

`etag master LastChangedAt` 관련 오류가 발생한다.

#### 원인

`LastChangedAt` 필드가 CDS View에 없거나 타입/Annotation이 부적절할 수 있다.

#### 해결

Root Interface View에 변경 시각 필드를 노출하고, Persistent Table에도 대응 필드가 있는지 확인한다.

---

### 26.4 Association 이름 불일치

#### 증상

`association _Item { create; }`에서 `_Item`을 찾을 수 없다는 오류가 발생한다.

#### 원인

CDS View에서 Association 이름이 `_Items`, `_OrderItem`, `_to_Item` 등 다른 이름으로 정의되어 있을 수 있다.

#### 해결

BDEF의 Association 이름은 CDS View의 Association 이름과 정확히 일치해야 한다.

---

### 26.5 Projection BDEF에서 원천에 없는 동작을 사용함

#### 증상

Projection BDEF의 `use delete;`에서 오류가 발생한다.

#### 원인

Interface BDEF에 `delete;`가 선언되어 있지 않을 수 있다.

#### 해결

Projection BDEF에서 `use`할 동작이 Interface BDEF에 먼저 정의되어 있는지 확인한다.

---

### 26.6 Child Entity에 create를 직접 선언함

#### 증상

Composition 관계에서 Child 생성 관련 모델링 오류가 발생한다.

#### 원인

Child를 Root와 무관하게 단독 생성 가능하도록 잘못 선언했을 수 있다.

#### 해결

Composition 구조에서는 Root의 Association을 통해 Child 생성을 허용하는 방식으로 설계한다.

```abap
association _Item { create; }
```

---

## 27. 실무 설계 기준

### 27.1 CRUD를 무조건 모두 열지 않는다

교육용 예제에서는 이해를 위해 `create`, `update`, `delete`를 모두 보여준다.  
하지만 실무에서는 모든 Entity에 모든 변경 동작을 허용하지 않는다.

| 상황 | 판단 |
|---|---|
| 참조성 마스터 조회 | Create/Update/Delete를 막을 수 있음 |
| 사용자가 직접 생성하는 업무 문서 | Create 허용 검토 |
| 승인 완료 문서 | Update/Delete 제한 필요 |
| 감사 로그 | Delete 금지 가능성이 큼 |
| 시스템 생성 데이터 | 사용자 Create 금지 가능 |

초급자는 “BDEF에 선언할 수 있다”와 “실무에서 허용해야 한다”를 구분해야 한다.

### 27.2 Projection BDEF에서 노출 동작을 줄일 수 있다

Interface BDEF에 여러 동작이 있어도 Projection BDEF에서 일부만 노출할 수 있다.

예를 들어 내부적으로는 Delete가 가능하지만 외부 서비스에서는 Delete를 숨길 수 있다.

```abap
projection;
strict ( 2 );

define behavior for ZC_GPT_Order alias Order
{
  use create;
  use update;
  " use delete; 를 선언하지 않음
}
```

이렇게 하면 외부 소비 모델에서 삭제 동작을 노출하지 않는 설계가 가능하다.

### 27.3 Root와 Child Lifecycle을 명확히 한다

Composition 관계에서는 Child가 Root에 종속된다.  
따라서 Child의 생성, 삭제, 잠금, 권한을 Root와 분리해서 생각하면 오류가 생기기 쉽다.

좋은 질문은 다음이다.

```text
이 Item은 Header 없이 존재할 수 있는가?
Header가 삭제되면 Item은 어떻게 되어야 하는가?
Item 변경 권한은 Header 권한을 따라도 되는가?
동시 변경 Lock은 Header 기준으로 충분한가?
```

### 27.4 Mapping은 단순 반복 작업이 아니다

Mapping은 지루해 보이지만, Managed RAP에서 매우 중요하다.

Mapping이 잘못되면 다음 문제가 생길 수 있다.

```text
생성 시 값이 DB에 저장되지 않음
수정 시 엉뚱한 필드가 변경됨
ETag 또는 Audit 필드가 제대로 동작하지 않음
Activation 오류 발생
```

### 27.5 BDEF는 UI 설정이 아니다

BDEF는 Fiori UI 버튼을 직접 그리는 객체가 아니다.  
하지만 BDEF에서 어떤 동작을 허용하느냐에 따라 OData 서비스와 Fiori Elements에서 가능한 동작이 달라진다.

```text
BDEF = BO의 행위 계약
Service Binding / Fiori Elements = 그 계약을 외부 소비자가 사용하는 방식
```

---

## 28. 강사용 설명 포인트

강의에서는 BDEF를 다음 비유로 설명하면 이해가 쉽다.

```text
CDS View = 메뉴판에 보이는 데이터 항목
BDEF = 이 메뉴에 대해 주문, 수정, 취소를 허용할지 정하는 규칙
Behavior Implementation = 실제 주문 처리 시 추가로 수행되는 주방 로직
```

강의 중 다음 질문을 던지면 좋다.

1. CDS View만 만들면 Fiori에서 Create 버튼이 자동으로 안전하게 동작할까요?
2. Item은 Header 없이 단독 생성되어도 될까요?
3. Delete를 허용하면 운영 데이터 관점에서 어떤 문제가 생길 수 있을까요?
4. Projection 계층에서 Delete를 숨기는 이유는 무엇일까요?
5. Mapping이 틀리면 어떤 오류가 날까요?

## 30. 자가 점검 문제

### Q1. Behavior Definition의 목적은 무엇인가?

A. 데이터베이스 테이블의 Technical Settings를 정의한다.  
B. RAP Business Object의 동작 계약을 정의한다.  
C. Fiori 화면 색상을 지정한다.  
D. ABAP Report의 Selection Screen을 만든다.

**정답:** B

---

### Q2. Projection BDEF에서 사용하는 CRUD 키워드 형태는?

A. `create;`, `update;`, `delete;`  
B. `use create;`, `use update;`, `use delete;`  
C. `allow create;`, `allow update;`, `allow delete;`  
D. `enable create;`, `enable update;`, `enable delete;`

**정답:** B

---

### Q3. `association _Item { create; }`의 의미는?

**모범 답안:**  
Root Entity의 `_Item` Association을 통해 Child Entity인 Item 생성을 허용한다는 의미이다. Composition 관계에서는 Child가 Root 아래에서 생성되는 것이 자연스럽기 때문에 Child에 단독 `create;`를 선언하는 대신 Root Association에서 생성 가능성을 선언한다.

---

### Q4. `strict(2)`를 사용하는 이유는?

**모범 답안:**  
Behavior Definition을 더 엄격한 규칙으로 검증하여 모델링 오류를 조기에 발견하기 위해 사용한다. 초급자에게는 오류가 더 많이 보일 수 있지만, 잘못된 Association, Mapping, CRUD 선언을 빠르게 확인할 수 있다는 장점이 있다.

---

### Q5. Interface BDEF와 Projection BDEF의 차이를 설명하시오.

**모범 답안:**  
Interface BDEF는 `ZI_*` Interface View를 대상으로 BO 내부 동작의 원천을 정의한다. Persistent Table, Mapping, Lock, Authorization, ETag, CRUD 등을 선언한다. Projection BDEF는 `ZC_*` Projection View를 대상으로 Interface BDEF에 정의된 동작 중 외부 소비 모델에서 사용할 동작을 `use` 키워드로 선택한다.

## 31. 검증 체크리스트

학습자는 실습 후 다음 항목을 확인한다.

| 체크 | 항목 |
|---|---|
| [ ] | `ZI_*` Interface View가 활성화되어 있다. |
| [ ] | `ZC_*` Projection View가 활성화되어 있다. |
| [ ] | Interface BDEF가 `managed implementation in class ... unique;`로 시작한다. |
| [ ] | `strict(2)`를 선언했다. |
| [ ] | Root Entity에 필요한 CRUD를 선언했다. |
| [ ] | Child 생성은 Root Association을 통해 허용했다. |
| [ ] | Persistent Table 이름이 정확하다. |
| [ ] | Mapping의 좌우 필드가 정확하다. |
| [ ] | Projection BDEF에 `projection;`이 선언되어 있다. |
| [ ] | Projection BDEF에서 `use create`, `use update`, `use delete`를 적절히 선언했다. |
| [ ] | 활성화 오류가 발생하면 CDS, Table, Mapping, Association 순서로 점검할 수 있다. |

## 32. 후속 모듈 연결

이번 모듈에서는 Behavior Definition을 통해 RAP Business Object의 동작 계약을 선언했다.

다음 모듈 `THEORY-21-M05 — Behavior Implementation 기초`에서는 BDEF에서 선언한 동작 중 일부를 실제 ABAP 클래스와 메서드로 구현하는 흐름을 학습한다.

연결 관계는 다음과 같다.

```text
THEORY-21-M04 Behavior Definition 기초
  → 어떤 동작을 허용할지 선언

THEORY-21-M05 Behavior Implementation 기초
  → 선언된 동작에 필요한 ABAP 로직을 구현

THEORY-21-M06 Service Definition / Service Binding
  → BO를 OData V4 서비스로 노출

THEORY-21-M07 Validation / Determination / Action 개요
  → 저장 전 검증, 자동 값 계산, 사용자 액션 구현
```

초급자는 이번 모듈을 마친 뒤 다음 한 문장을 정확히 이해하면 된다.

```text
BDEF는 RAP Business Object가 무엇을 할 수 있는지 정의하는 행위 계약이다.
```

## 33. 핵심 요약

```text
Behavior Definition은 RAP BO의 동작을 정의한다.
CDS View가 데이터 구조라면 BDEF는 행위 계약이다.
Managed Scenario에서는 RAP Framework가 기본 CRUD 저장 흐름을 제공한다.
strict(2)는 더 엄격한 RAP 모델링 검증을 적용한다.
Interface BDEF는 ZI_*를 대상으로 실제 동작 원천을 정의한다.
Projection BDEF는 ZC_*를 대상으로 외부에 사용할 동작을 선택한다.
Root에는 create/update/delete를 선언할 수 있다.
Child 생성은 Composition Association을 통해 허용하는 것이 일반적이다.
Mapping은 CDS 필드와 DB Table 필드를 연결하는 중요한 계약이다.
Projection BDEF의 use 동작은 Interface BDEF에 먼저 존재해야 한다.
```
