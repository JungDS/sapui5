## 3. `CL_GUI_CUSTOM_CONTAINER`란 무엇인가?

`CL_GUI_CUSTOM_CONTAINER`는 SAP GUI 화면의 Custom Control 영역을 ABAP 프로그램의 객체로 다루기 위한 클래스이다.

쉽게 말하면 다음과 같다.

```text
Screen Painter의 Custom Control 영역
        ↓ container_name으로 연결
CL_GUI_CUSTOM_CONTAINER 객체
        ↓ parent로 전달
CL_GUI_ALV_GRID 객체
```

즉, Grid ALV를 화면에 띄우려면 Grid가 붙을 부모 컨테이너가 필요하다.  
그 부모 역할을 하는 대표 클래스가 `CL_GUI_CUSTOM_CONTAINER`이다.

### 3.1 무엇을 하는가?

| 역할 | 설명 |
|---|---|
| 화면 영역 연결 | Dynpro 화면에 만든 Custom Control 영역과 ABAP 객체를 연결한다. |
| Parent Container 제공 | 후속 `CL_GUI_ALV_GRID` 객체 생성 시 parent로 전달된다. |
| Control Framework 기반 제공 | SAP GUI Frontend Control이 화면 안에서 표시될 수 있는 기반을 만든다. |
| 화면 레이아웃 반영 | Screen Painter에서 정한 위치와 크기에 따라 표시 영역이 결정된다. |

### 3.2 무엇을 하지 않는가?

`CL_GUI_CUSTOM_CONTAINER`는 이름 때문에 “ALV를 출력하는 객체”로 오해하기 쉽다.  
하지만 이 클래스는 ALV 데이터 표시를 직접 수행하지 않는다.

| 하지 않는 일 | 실제 담당 객체 |
|---|---|
| Internal Table 데이터를 Grid로 표시 | `CL_GUI_ALV_GRID` |
| Field Catalog 해석 | `CL_GUI_ALV_GRID` |
| Layout 적용 | `CL_GUI_ALV_GRID` |
| Refresh 처리 | `CL_GUI_ALV_GRID` |
| 행/컬럼 색상 표시 | `CL_GUI_ALV_GRID` + Layout/Field Catalog 설정 |

이번 모듈은 Grid ALV의 “자리를 만드는 단계”이다.

## 4. Screen 기반 Grid ALV의 전체 구조

Grid ALV는 단순히 `WRITE`처럼 실행하면 바로 목록이 출력되는 구조가 아니다.  
Classic Dynpro 화면과 Control Framework 객체가 함께 동작한다.

기본 구조는 다음과 같다.

```text
Executable Program 또는 Module Pool
  └─ CALL SCREEN 0100
       └─ Screen 0100
            ├─ Custom Control: CC_ALV
            ├─ PBO: STATUS_0100, CREATE_CONTAINER_0100
            └─ PAI: USER_COMMAND_0100

ABAP Global Data
  ├─ go_container TYPE REF TO cl_gui_custom_container
  └─ go_grid      TYPE REF TO cl_gui_alv_grid   ← 다음 모듈
```

이번 모듈에서는 `go_container` 생성까지만 구현한다.

## 5. Container Name의 의미

### 5.1 `container_name`은 무엇인가?

`container_name`은 ABAP 코드에서 `CL_GUI_CUSTOM_CONTAINER`를 생성할 때 전달하는 이름이다.

예:

```abap
CREATE OBJECT go_container
  EXPORTING
    container_name = 'CC_ALV'.
```

여기서 `'CC_ALV'`는 임의 문자열처럼 보이지만, 실제로는 **Screen Painter에서 만든 Custom Control의 이름**과 일치해야 한다.

### 5.2 Screen Painter 이름과 ABAP 코드 이름의 관계

| 위치 | 이름 |
|---|---|
| Screen Painter의 Custom Control Name | `CC_ALV` |
| ABAP 코드의 `container_name` | `'CC_ALV'` |
| ABAP 참조 변수명 | `go_container` |

이 세 가지는 역할이 다르다.

| 구분 | 설명 |
|---|---|
| `CC_ALV` | 화면에 배치된 Custom Control 영역의 이름 |
| `'CC_ALV'` | 그 화면 영역을 찾기 위해 생성자에 전달하는 문자열 |
| `go_container` | 생성된 컨테이너 객체를 가리키는 ABAP 참조 변수 |

초급자가 가장 자주 하는 실수는 다음이다.

```text
Screen Painter 이름은 CC_ALV인데,
ABAP 코드에는 container_name = 'CONTAINER'라고 입력한다.
```

이 경우 런타임에서 화면 요소를 찾지 못해 컨테이너 생성 오류가 발생할 수 있다.

## 6. 왜 PBO에서 생성하는가?

SAP Dynpro는 화면 표시 전에 PBO(Process Before Output)를 수행한다.  
화면에 표시될 컨트롤을 준비하는 작업은 보통 PBO에서 처리한다.

흐름은 다음과 같다.

```text
CALL SCREEN 0100
  → PBO 실행
     → Custom Container 객체 생성
     → 화면 출력
  → 사용자 입력
  → PAI 실행
```

따라서 컨테이너는 일반적으로 Screen의 PBO Module에서 생성한다.

### 6.1 객체는 매번 생성하면 안 된다

PBO는 화면이 표시될 때마다 반복 실행될 수 있다.  
따라서 PBO 안에서 매번 `CREATE OBJECT`를 수행하면 불필요한 객체 생성 또는 Control Framework 오류를 유발할 수 있다.

권장 패턴은 다음이다.

```abap
IF go_container IS INITIAL.
  CREATE OBJECT go_container
    EXPORTING
      container_name = 'CC_ALV'.
ENDIF.
```

이 패턴은 “컨테이너가 아직 없을 때만 생성”한다는 뜻이다.

## 9. 최소 ABAP 코드

아래 코드는 이번 모듈의 최소 구현 예제이다.  
아직 Grid ALV 객체는 만들지 않고, Custom Container 생성까지만 수행한다.

```abap
REPORT zjhy_alv_container_01.

DATA go_container TYPE REF TO cl_gui_custom_container.
DATA gv_okcode    TYPE sy-ucomm.

START-OF-SELECTION.
  CALL SCREEN 0100.

MODULE status_0100 OUTPUT.
  SET PF-STATUS 'S0100'.
  SET TITLEBAR 'T0100'.
ENDMODULE.

MODULE create_container_0100 OUTPUT.
  IF go_container IS INITIAL.
    CREATE OBJECT go_container
      EXPORTING
        container_name = 'CC_ALV'
      EXCEPTIONS
        cntl_error                  = 1
        cntl_system_error           = 2
        create_error                = 3
        lifetime_error              = 4
        lifetime_dynpro_dynpro_link = 5
        OTHERS                      = 6.

    IF sy-subrc <> 0.
      MESSAGE 'Custom Container 생성 중 오류가 발생했습니다.' TYPE 'E'.
    ENDIF.
  ENDIF.
ENDMODULE.

MODULE user_command_0100 INPUT.
  gv_okcode = sy-ucomm.

  CASE gv_okcode.
    WHEN 'BACK' OR 'EXIT' OR 'CANCEL'.
      IF go_container IS BOUND.
        FREE go_container.
      ENDIF.
      LEAVE TO SCREEN 0.
  ENDCASE.
ENDMODULE.
```

### 9.1 코드 해설

| 코드 | 의미 |
|---|---|
| `DATA go_container TYPE REF TO cl_gui_custom_container` | 컨테이너 객체 참조 변수 선언 |
| `CALL SCREEN 0100` | Screen 0100 호출 |
| `MODULE create_container_0100 OUTPUT` | PBO에서 컨테이너 생성 처리 |
| `IF go_container IS INITIAL` | 중복 생성 방지 |
| `container_name = 'CC_ALV'` | Screen Painter의 Custom Control 이름과 연결 |
| `sy-subrc` 확인 | 생성 오류 발생 여부 확인 |
| `FREE go_container` | 화면 종료 시 컨테이너 참조 해제 |

### 9.2 PF-STATUS 관련 주의

예제에서는 `SET PF-STATUS 'S0100'`를 사용한다.  
실제로 실행하려면 GUI Status `S0100`에 `BACK`, `EXIT`, `CANCEL` 같은 Function Code가 있어야 한다.

초급 실습에서 GUI Status 생성이 부담된다면, 강사가 제공하는 템플릿을 사용하거나 우선 PAI 처리만 단순화할 수 있다.  
다만 Grid ALV 실무 학습에서는 화면 종료 처리를 명확히 하기 위해 PF-STATUS를 생성하는 것이 좋다.

## 10. 정상 실행 흐름

정상 흐름은 다음과 같다.

```text
1. 사용자가 프로그램 실행
2. START-OF-SELECTION에서 CALL SCREEN 0100 수행
3. Screen 0100 PBO 실행
4. STATUS_0100에서 GUI Status와 Title 설정
5. CREATE_CONTAINER_0100에서 GO_CONTAINER가 INITIAL인지 확인
6. GO_CONTAINER가 비어 있으면 CL_GUI_CUSTOM_CONTAINER 생성
7. container_name = 'CC_ALV'로 Screen Custom Control과 연결
8. Screen 0100 표시
9. 사용자가 BACK/EXIT/CANCEL 선택
10. PAI에서 객체 해제 후 이전 화면으로 복귀
```

이 흐름에서 핵심 검증 포인트는 `CREATE OBJECT go_container` 이후 `sy-subrc = 0`인지 확인하는 것이다.

## 11. 오류 흐름과 해결 기준

### 11.1 Screen에 Custom Control이 없음

| 항목 | 내용 |
|---|---|
| 증상 | 컨테이너 생성 오류 또는 화면 출력 오류 |
| 원인 | Screen Layout에 Custom Control 요소를 만들지 않음 |
| 해결 | Screen 0100 Layout에서 Custom Control을 배치한다. |

### 11.2 Custom Control 이름 불일치

| 항목 | 내용 |
|---|---|
| 증상 | `CREATE OBJECT` 시 오류 발생 |
| 원인 | Screen Painter 이름과 `container_name` 문자열이 다름 |
| 잘못된 예 | Screen 이름 `CC_ALV`, 코드 `container_name = 'CONTAINER'` |
| 해결 | 두 이름을 동일하게 맞춘다. |

### 11.3 PBO에서 매번 객체 생성

| 항목 | 내용 |
|---|---|
| 증상 | 화면 이동 또는 Refresh 시 불안정한 동작 |
| 원인 | `IF go_container IS INITIAL` 없이 매번 `CREATE OBJECT` 수행 |
| 해결 | 컨테이너가 없을 때만 생성하는 조건문을 사용한다. |

### 11.4 Screen 번호 불일치

| 항목 | 내용 |
|---|---|
| 증상 | 화면 호출 실패 또는 Custom Control 연결 실패 |
| 원인 | `CALL SCREEN 0100`인데 실제 Screen을 1000 등으로 생성 |
| 해결 | 프로그램의 Screen 번호와 `CALL SCREEN` 번호를 일치시킨다. |

### 11.5 GUI Status 누락

| 항목 | 내용 |
|---|---|
| 증상 | `SET PF-STATUS 'S0100'`에서 오류 발생 |
| 원인 | GUI Status `S0100`을 생성하지 않음 |
| 해결 | SE41 또는 SE80에서 GUI Status를 생성하거나 예제 코드를 조정한다. |

### 11.6 SAP GUI 환경 문제

| 항목 | 내용 |
|---|---|
| 증상 | Control Framework 관련 오류 |
| 원인 | SAP GUI Frontend Control과 관련된 환경 문제 가능 |
| 해결 | SAP GUI 클라이언트, 권한, 프론트엔드 상태, 시스템 메시지를 확인한다. |

## 12. 디버깅 포인트

초급자는 다음 위치에 Breakpoint를 설정하면 흐름을 이해하기 쉽다.

| 위치 | 확인할 내용 |
|---|---|
| `START-OF-SELECTION` | 프로그램 시작 후 Screen 0100으로 이동하는지 확인 |
| `MODULE status_0100 OUTPUT` | PBO가 실행되는지 확인 |
| `MODULE create_container_0100 OUTPUT` | 컨테이너 생성 코드가 실행되는지 확인 |
| `IF go_container IS INITIAL` | 최초 진입과 재진입 시 값이 달라지는지 확인 |
| `CREATE OBJECT go_container` 직후 | `sy-subrc` 값 확인 |
| `MODULE user_command_0100 INPUT` | 사용자의 BACK/EXIT/CANCEL 처리 확인 |

### 12.1 디버깅 중 관찰할 변수

| 변수 | 의미 |
|---|---|
| `GO_CONTAINER` | 컨테이너 객체 참조 상태 |
| `SY-SUBRC` | 생성 결과 코드 |
| `SY-UCOMM` | 사용자가 누른 Function Code |

## 13. 실무 설계 관점

### 13.1 컨테이너 이름은 명확하게 짓는다

나쁜 이름:

```text
C1
CONTAINER
TEST
ABC
```

좋은 이름:

```text
CC_ALV
CC_MAIN_ALV
CC_DETAIL_ALV
CC_LEFT_TREE
CC_RIGHT_GRID
```

화면에 컨트롤이 여러 개 있을 경우 이름이 명확하지 않으면 유지보수가 어려워진다.

### 13.2 전역 참조 변수 사용 기준

Classic Dynpro에서는 PBO와 PAI가 여러 번 호출되므로, 컨테이너 객체 참조는 보통 프로그램 전역 영역에 둔다.

```abap
DATA go_container TYPE REF TO cl_gui_custom_container.
```

로컬 변수로 만들면 PBO가 끝난 뒤 참조를 유지하기 어렵고, 후속 Grid 객체와 연결하기도 불편하다.

### 13.3 객체 생명주기 관리

화면을 빠져나갈 때 컨테이너와 Grid 객체를 정리하는 습관이 중요하다.

이번 모듈에서는 컨테이너만 다루므로 다음 정도를 기억한다.

```abap
IF go_container IS BOUND.
  FREE go_container.
ENDIF.
```

후속 모듈에서 Grid 객체까지 만들면 일반적으로 Grid 객체와 Container 객체의 정리 순서도 고려해야 한다.

### 13.4 화면 로직과 데이터 로직을 분리한다

Container 생성 코드는 화면 준비 로직이다.  
데이터 조회, Internal Table 구성, Field Catalog 구성은 별도 Module 또는 FORM/Method로 분리하는 것이 좋다.

나쁜 구조:

```text
PBO Module 하나에 컨테이너 생성, SELECT, Field Catalog, Grid 생성, Refresh를 모두 작성
```

좋은 구조:

```text
PBO
 ├─ status_0100
 ├─ create_container_0100
 ├─ create_grid_0100
 └─ display_alv_0100
```

이번 모듈에서는 `create_container_0100`까지만 완성한다.

## 15. 자주 하는 질문

### Q1. `CL_GUI_CUSTOM_CONTAINER`와 `CL_GUI_ALV_GRID` 중 무엇을 먼저 만들어야 하는가?

먼저 `CL_GUI_CUSTOM_CONTAINER`를 만든다.  
그 후 `CL_GUI_ALV_GRID`를 만들 때 이 컨테이너를 `i_parent`로 전달한다.

```abap
CREATE OBJECT go_grid
  EXPORTING
    i_parent = go_container.
```

이 코드는 다음 모듈에서 본격적으로 다룬다.

### Q2. `container_name`에는 ABAP 변수명을 넣는가?

아니다.  
`container_name`에는 Screen Painter에서 만든 Custom Control의 이름을 문자열로 넣는다.

```abap
container_name = 'CC_ALV'
```

여기서 `CC_ALV`는 화면 요소 이름이다.

### Q3. Selection Screen 위에도 Grid ALV를 직접 올릴 수 있는가?

일반적인 Grid ALV 기초 학습에서는 Classic Dynpro Screen에 Custom Control을 만들고 그 위에 Grid를 올리는 방식을 먼저 학습한다.  
Selection Screen에 단순 입력 필드를 만드는 것과 Dynpro Custom Control 위에 Grid를 올리는 것은 학습 포인트가 다르다.

### Q4. Container만 만들었는데 화면에 아무것도 안 보이면 실패인가?

반드시 실패는 아니다.  
Container는 “자리”일 뿐이며, 실제 Grid 객체와 데이터 표시를 하지 않으면 빈 영역처럼 보일 수 있다.  
이번 모듈에서는 컨테이너 생성 오류가 없는지, 화면이 정상 표시되는지를 우선 확인한다.

### Q5. 왜 `WRITE`로 출력하지 않고 복잡하게 Screen과 Container를 쓰는가?

`WRITE`는 단순 리스트 출력에는 적합하지만, Grid ALV는 컬럼 조정, 정렬, 필터, Layout Variant 등 업무 리포트에 필요한 상호작용 기능을 제공한다.  
이런 기능을 사용하려면 SAP GUI Control Framework 기반의 Grid ALV 구조를 이해해야 한다.

## 16. 평가 문제

### 16.1 객관식

#### Q1. `CL_GUI_CUSTOM_CONTAINER`의 가장 적절한 역할은 무엇인가?

A. Internal Table 데이터를 직접 정렬한다.  
B. Screen의 Custom Control 영역을 ABAP 객체로 연결한다.  
C. Field Catalog를 자동 생성한다.  
D. Variant를 저장한다.

**정답:** B

#### Q2. `container_name = 'CC_ALV'`에서 `CC_ALV`는 무엇과 일치해야 하는가?

A. 프로그램 이름  
B. GUI Status 이름  
C. Screen Painter의 Custom Control 이름  
D. Internal Table 이름

**정답:** C

#### Q3. PBO에서 컨테이너 생성 시 권장되는 패턴은 무엇인가?

A. PBO가 실행될 때마다 무조건 새로 생성한다.  
B. PAI에서만 생성한다.  
C. `IF go_container IS INITIAL` 조건으로 최초 한 번만 생성한다.  
D. `WRITE` 문으로 생성한다.

**정답:** C

### 16.2 서술형

#### Q1. `CL_GUI_CUSTOM_CONTAINER`와 `CL_GUI_ALV_GRID`의 차이를 설명하시오.

**모범 답안:**  
`CL_GUI_CUSTOM_CONTAINER`는 Dynpro 화면의 Custom Control 영역을 ABAP 객체로 연결하는 컨테이너이다. `CL_GUI_ALV_GRID`는 실제 Internal Table 데이터를 Grid 형태로 표시하는 ALV 컨트롤이다. Grid ALV를 화면에 표시하려면 먼저 Custom Container를 만들고, 그 컨테이너를 Grid의 parent로 전달한다.

#### Q2. Screen Painter에서 Custom Control 이름과 ABAP 코드의 `container_name`이 다르면 어떤 문제가 생길 수 있는가?

**모범 답안:**  
ABAP 런타임이 해당 이름의 화면 Custom Control 영역을 찾지 못해 컨테이너 생성 오류가 발생할 수 있다. 따라서 Screen Painter의 이름과 `container_name` 문자열은 정확히 일치해야 한다.

#### Q3. 컨테이너 객체를 PBO에서 매번 생성하면 안 되는 이유는 무엇인가?

**모범 답안:**  
PBO는 화면 표시 시 반복 실행될 수 있다. 매번 컨테이너를 새로 생성하면 중복 객체 생성, Control Framework 오류, 불필요한 리소스 사용, 화면 동작 불안정이 발생할 수 있다. 따라서 참조 변수가 비어 있을 때만 생성하는 조건이 필요하다.

## 18. 핵심 요약

이번 모듈의 핵심은 다음이다.

```text
CL_GUI_CUSTOM_CONTAINER는 ALV Grid가 표시될 화면 영역을 ABAP 객체로 연결하는 클래스이다.
Screen Painter의 Custom Control 이름과 생성자의 container_name은 반드시 일치해야 한다.
컨테이너는 보통 PBO에서 생성한다.
PBO는 반복 실행될 수 있으므로 컨테이너는 최초 한 번만 생성해야 한다.
이번 모듈은 Grid ALV 자체가 아니라 Grid ALV가 들어갈 부모 컨테이너를 준비하는 단계이다.
```
