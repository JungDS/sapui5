## 1. 모듈 개요

이번 모듈은 Grid ALV를 처음 다루는 학습자가 **Refresh**와 **Stable Refresh**의 차이를 이해하고, 사용자가 보고 있는 ALV 화면을 불필요하게 흔들지 않으면서 Internal Table 변경 내용을 다시 표시하는 방법을 익히기 위한 문서이다.

이전 모듈까지의 흐름은 다음과 같다.

```text
THEORY-15-M01  CL_GUI_CUSTOM_CONTAINER 생성
THEORY-15-M02  CL_GUI_ALV_GRID 생성
THEORY-15-M03  출력용 Internal Table 준비
THEORY-15-M04  Field Catalog 기초
THEORY-15-M05  Layout 기본 설정
THEORY-15-M06  Variant 기본 설정
THEORY-15-M07  SET_TABLE_FOR_FIRST_DISPLAY
THEORY-15-M08  Refresh와 Stable Refresh 기초
THEORY-15-M09  컬럼 색상과 행 색상 기초
```

`SET_TABLE_FOR_FIRST_DISPLAY`는 ALV Grid를 **처음 표시**할 때 사용하는 대표 메서드이다.  
하지만 ALV가 이미 화면에 표시된 이후, Internal Table의 데이터가 바뀔 때마다 이 메서드를 다시 호출하는 것은 바람직하지 않다. 이미 생성된 Grid 인스턴스와 화면 상태를 유지한 채 데이터 표시만 갱신해야 한다.

이때 사용하는 대표 메서드가 다음이다.

```abap
go_grid->refresh_table_display( ).
```

실무에서는 이 메서드를 단순 호출하는 것에서 끝나지 않는다. 사용자가 스크롤을 내렸거나, 특정 행·열을 보고 있거나, 정렬/필터/Variant를 적용한 상태라면 Refresh 후 화면 위치가 바뀌는 것이 불편할 수 있다. 이런 문제를 줄이기 위해 **Stable Refresh** 옵션을 함께 사용한다.

## 4. Refresh가 필요한 이유

Grid ALV는 화면에 Internal Table을 표시한다.  
하지만 화면에 표시된 Grid와 프로그램 내부의 Internal Table은 항상 자동으로 동기화되는 것이 아니다.

예를 들어 다음 상황을 생각해보자.

```text
1. 프로그램이 Internal Table LT_DISPLAY를 ALV로 표시한다.
2. 사용자가 버튼을 눌러 특정 행의 상태를 변경한다.
3. 프로그램이 LT_DISPLAY의 STATUS 값을 변경한다.
4. 그런데 ALV 화면은 이전 값 그대로 보인다.
```

이 경우 Internal Table의 값은 바뀌었지만 Grid 화면은 아직 갱신되지 않은 상태일 수 있다.  
따라서 프로그램은 Grid에게 “현재 Internal Table 기준으로 화면을 다시 그려라”라고 알려야 한다.

이 역할을 하는 메서드가 `REFRESH_TABLE_DISPLAY`이다.

---

## 5. 최초 표시와 Refresh의 역할 분리

초급자가 자주 하는 실수는 데이터가 바뀔 때마다 다음 메서드를 반복 호출하는 것이다.

```abap
go_grid->set_table_for_first_display( ... ).
```

이 메서드는 이름 그대로 “처음 표시”할 때 사용하는 메서드이다.  
이미 Grid가 생성되고 표시된 이후에는 일반적으로 Refresh 메서드를 사용한다.

| 상황 | 권장 메서드 |
|---|---|
| Grid ALV를 처음 표시할 때 | `SET_TABLE_FOR_FIRST_DISPLAY` |
| 표시된 Grid의 데이터만 다시 보여줄 때 | `REFRESH_TABLE_DISPLAY` |
| Field Catalog 자체가 크게 바뀔 때 | 재표시 또는 구조 재검토 필요 |
| 화면 컨테이너/Grid 객체를 다시 만들 때 | 객체 생성 흐름부터 재검토 |

정리하면 다음과 같다.

```text
SET_TABLE_FOR_FIRST_DISPLAY = 최초 바인딩과 최초 표시
REFRESH_TABLE_DISPLAY       = 이미 표시된 Grid의 데이터 갱신
```

---

## 6. `REFRESH_TABLE_DISPLAY` 기본 형태

가장 단순한 호출은 다음과 같다.

```abap
go_grid->refresh_table_display( ).
```

이 호출은 현재 Grid에 바인딩된 출력 Internal Table 기준으로 화면을 다시 표시한다.

그러나 실무에서는 보통 다음과 같이 안정성 옵션을 함께 사용한다.

```abap
DATA ls_stable TYPE lvc_s_stbl.

ls_stable-row = abap_true.
ls_stable-col = abap_true.

go_grid->refresh_table_display(
  EXPORTING
    is_stable = ls_stable
).
```

여기서 `LVC_S_STBL`은 Grid Refresh 후에도 화면 위치를 안정적으로 유지하기 위해 사용하는 구조이다.

---

## 7. Stable Refresh란 무엇인가?

Stable Refresh는 ALV Refresh 후에도 사용자가 보던 위치를 최대한 유지하도록 돕는 방식이다.

예를 들어 사용자가 500행 중 320번째 행을 보고 있는데, 프로그램이 데이터를 갱신한 뒤 화면이 다시 1행으로 돌아가면 불편하다.  
또는 사용자가 오른쪽 컬럼을 보고 있는데 Refresh 후 첫 번째 컬럼으로 돌아가면 역시 불편하다.

Stable Refresh는 이런 화면 흔들림을 줄이기 위한 옵션이다.

```abap
DATA ls_stable TYPE lvc_s_stbl.

ls_stable-row = 'X'.
ls_stable-col = 'X'.
```

| 필드 | 의미 |
|---|---|
| `ROW` | Refresh 후에도 행 위치를 안정적으로 유지하려고 시도한다. |
| `COL` | Refresh 후에도 열 위치를 안정적으로 유지하려고 시도한다. |

ABAP Boolean 표현을 선호하면 다음처럼 작성할 수 있다.

```abap
ls_stable-row = abap_true.
ls_stable-col = abap_true.
```

---

## 8. Stable Refresh가 필요한 대표 상황

Stable Refresh는 다음 상황에서 특히 유용하다.

| 상황 | 설명 |
|---|---|
| ALV 행 상태를 버튼으로 변경 | 특정 행을 선택하고 상태값을 바꾼 뒤 화면 위치를 유지해야 한다. |
| 수량/금액 재계산 | 사용자가 보던 행 주변에서 계산 결과만 갱신한다. |
| 검증 결과 표시 | 오류 메시지나 상태 아이콘만 갱신한다. |
| 주기적 재조회 | 데이터가 주기적으로 갱신되더라도 사용자가 보던 위치를 최대한 유지한다. |
| ALV 편집 후 반영 | 사용자가 수정한 값을 Internal Table에 반영하고 화면을 다시 표시한다. |

초급 실습에서는 “선택한 행의 상태를 변경한 후 Refresh”하는 예제가 가장 이해하기 쉽다.

---

## 9. Refresh가 화면 상태를 모두 보장하지는 않는다

Stable Refresh는 “가능한 범위에서” 행·열 위치를 유지하도록 돕는 기능이다.  
모든 상황에서 사용자의 화면 상태가 완벽히 보존된다고 이해하면 안 된다.

예를 들어 다음 상황에서는 위치 유지가 제한될 수 있다.

| 상황 | 이유 |
|---|---|
| Refresh 전후 데이터 건수가 크게 달라짐 | 기존 행 위치 자체가 사라질 수 있다. |
| 정렬 기준이 바뀜 | 같은 데이터가 다른 위치로 이동할 수 있다. |
| 필터 조건이 바뀜 | 기존 행이 화면에서 제외될 수 있다. |
| Field Catalog가 변경됨 | 열 구조 자체가 달라질 수 있다. |
| Internal Table을 완전히 재구성 | Row Index 기반 안정성이 약해질 수 있다. |

따라서 Stable Refresh는 화면 품질을 높이는 수단이지, 데이터 모델링 문제를 해결하는 수단은 아니다.

## 10. 기본 실습 시나리오

### 10.1 실습 목표

ALV Grid에 사용자 목록을 표시하고, 버튼 또는 PAI 흐름에서 특정 행의 상태를 변경한 뒤 Refresh한다.

### 10.2 예제 데이터 구조

```abap
TYPES: BEGIN OF ty_user,
         user_id   TYPE char10,
         user_name TYPE char40,
         status    TYPE char1,
         message   TYPE char60,
       END OF ty_user.

DATA gt_user TYPE STANDARD TABLE OF ty_user.
DATA gs_user TYPE ty_user.
```

### 10.3 예제 데이터

```abap
gt_user = VALUE #(
  ( user_id = 'U0001' user_name = 'Kim Developer' status = 'A' message = 'Active user' )
  ( user_id = 'U0002' user_name = 'Lee Consultant' status = 'I' message = 'Inactive user' )
  ( user_id = 'U0003' user_name = 'Park Admin' status = 'A' message = 'Active user' )
).
```

이 예제는 DDIC 기반 구조를 사용하지 않고 로컬 타입을 사용한다.  
이유는 이번 모듈의 초점이 DDIC가 아니라 ALV Refresh 동작이기 때문이다.

실무에서는 DDIC Structure 또는 테이블 타입 기반 출력 구조를 사용할 수 있다.

## 11. 전체 예제 흐름

아래 예제는 Refresh 흐름을 이해하기 위한 교육용 골격이다.  
실제 Screen 0100, Custom Control 이름, PF-STATUS는 시스템 실습 환경에 맞게 조정해야 한다.

```abap
REPORT zedu_grid_refresh_basic.

TYPES: BEGIN OF ty_user,
         user_id   TYPE char10,
         user_name TYPE char40,
         status    TYPE char1,
         message   TYPE char60,
       END OF ty_user.

DATA gt_user TYPE STANDARD TABLE OF ty_user.
DATA go_container TYPE REF TO cl_gui_custom_container.
DATA go_grid      TYPE REF TO cl_gui_alv_grid.

START-OF-SELECTION.
  PERFORM set_data.
  CALL SCREEN 0100.

FORM set_data.
  gt_user = VALUE #(
    ( user_id = 'U0001' user_name = 'Kim Developer' status = 'A' message = 'Active user' )
    ( user_id = 'U0002' user_name = 'Lee Consultant' status = 'I' message = 'Inactive user' )
    ( user_id = 'U0003' user_name = 'Park Admin' status = 'A' message = 'Active user' )
  ).
ENDFORM.
```

Screen 0100의 PBO에서 최초 1회 Grid를 표시한다.

```abap
MODULE status_0100 OUTPUT.
  SET PF-STATUS 'S0100'.

  IF go_container IS INITIAL.
    CREATE OBJECT go_container
      EXPORTING
        container_name = 'CC_ALV'.

    CREATE OBJECT go_grid
      EXPORTING
        i_parent = go_container.

    PERFORM display_alv.
  ENDIF.
ENDMODULE.
```

최초 표시 Form은 다음처럼 구성한다.

```abap
FORM display_alv.
  DATA lt_fcat TYPE lvc_t_fcat.
  DATA ls_fcat TYPE lvc_s_fcat.

  CLEAR ls_fcat.
  ls_fcat-fieldname = 'USER_ID'.
  ls_fcat-coltext   = 'User ID'.
  APPEND ls_fcat TO lt_fcat.

  CLEAR ls_fcat.
  ls_fcat-fieldname = 'USER_NAME'.
  ls_fcat-coltext   = 'User Name'.
  APPEND ls_fcat TO lt_fcat.

  CLEAR ls_fcat.
  ls_fcat-fieldname = 'STATUS'.
  ls_fcat-coltext   = 'Status'.
  APPEND ls_fcat TO lt_fcat.

  CLEAR ls_fcat.
  ls_fcat-fieldname = 'MESSAGE'.
  ls_fcat-coltext   = 'Message'.
  APPEND ls_fcat TO lt_fcat.

  go_grid->set_table_for_first_display(
    CHANGING
      it_outtab       = gt_user
      it_fieldcatalog = lt_fcat
  ).
ENDFORM.
```

PAI에서는 사용자의 명령에 따라 데이터를 변경하고 Refresh한다.

```abap
MODULE user_command_0100 INPUT.
  CASE sy-ucomm.
    WHEN 'BACK' OR 'EXIT' OR 'CANC'.
      LEAVE TO SCREEN 0.

    WHEN 'TOGGLE'.
      PERFORM toggle_first_user_status.
      PERFORM refresh_alv_stable.
  ENDCASE.
ENDMODULE.
```

상태 변경 Form은 다음과 같다.

```abap
FORM toggle_first_user_status.
  READ TABLE gt_user ASSIGNING FIELD-SYMBOL(<ls_user>) INDEX 1.
  IF sy-subrc <> 0.
    RETURN.
  ENDIF.

  IF <ls_user>-status = 'A'.
    <ls_user>-status  = 'I'.
    <ls_user>-message = 'Changed to inactive'.
  ELSE.
    <ls_user>-status  = 'A'.
    <ls_user>-message = 'Changed to active'.
  ENDIF.
ENDFORM.
```

Stable Refresh Form은 다음과 같다.

```abap
FORM refresh_alv_stable.
  DATA ls_stable TYPE lvc_s_stbl.

  CHECK go_grid IS BOUND.

  ls_stable-row = abap_true.
  ls_stable-col = abap_true.

  go_grid->refresh_table_display(
    EXPORTING
      is_stable = ls_stable
  ).
ENDFORM.
```

## 12. `IS_STABLE` 없이 Refresh하면 어떻게 되는가?

다음처럼 호출할 수도 있다.

```abap
go_grid->refresh_table_display( ).
```

데이터가 적고 스크롤이 거의 없는 경우에는 차이를 느끼지 못할 수 있다.  
하지만 데이터가 많고 사용자가 특정 위치를 보고 있을 때는 Refresh 후 화면 위치가 바뀌는 현상을 경험할 수 있다.

교육에서는 같은 데이터로 다음 두 가지를 비교하면 좋다.

```text
1. is_stable 없이 Refresh
2. is_stable-row / is_stable-col = abap_true로 Refresh
```

비교 포인트는 다음이다.

| 비교 항목 | 확인 내용 |
|---|---|
| 행 위치 | Refresh 후 같은 행 주변을 보고 있는가 |
| 열 위치 | 오른쪽으로 스크롤한 위치가 유지되는가 |
| 사용자 체감 | 화면이 튀거나 다시 처음으로 돌아가는 느낌이 있는가 |
| 대량 데이터 | 데이터가 많을수록 차이가 체감되는가 |

---

## 13. Refresh 전 데이터 변경 방식

Refresh는 화면을 갱신하는 메서드이다.  
데이터 자체를 변경하는 메서드가 아니다.

즉, 다음 순서가 중요하다.

```text
Internal Table 데이터를 먼저 변경한다.
→ 그 다음 Grid Refresh를 호출한다.
```

잘못된 흐름:

```abap
PERFORM refresh_alv_stable.
MODIFY gt_user FROM gs_user INDEX 1.
```

올바른 흐름:

```abap
MODIFY gt_user FROM gs_user INDEX 1.
PERFORM refresh_alv_stable.
```

Field Symbol을 사용하는 경우에도 동일하다.

```abap
READ TABLE gt_user ASSIGNING FIELD-SYMBOL(<ls_user>) INDEX 1.
IF sy-subrc = 0.
  <ls_user>-status = 'A'.
  PERFORM refresh_alv_stable.
ENDIF.
```

## 14. Refresh와 데이터베이스 Commit은 다르다

초급자가 혼동하기 쉬운 지점이 있다.

```text
REFRESH_TABLE_DISPLAY는 화면 갱신이다.
COMMIT WORK는 데이터베이스 변경 확정이다.
```

ALV 화면의 Internal Table 값을 바꾸고 Refresh했다고 해서 DB에 저장된 것은 아니다.  
반대로 DB에 데이터를 저장했다고 해서 현재 화면이 자동으로 갱신되는 것도 아니다.

| 작업 | 의미 |
|---|---|
| Internal Table 수정 | 프로그램 메모리의 데이터 변경 |
| `REFRESH_TABLE_DISPLAY` | ALV 화면 다시 그리기 |
| `INSERT`, `UPDATE`, `MODIFY dbtab` | DB 변경 요청 |
| `COMMIT WORK` | DB 변경 확정 |
| 재조회 SELECT | DB의 최신 데이터를 다시 Internal Table로 가져오기 |

이번 모듈에서는 Grid 화면 갱신에 집중한다.  
DB 변경과 Commit 처리는 Track 2의 데이터 변경/동시성 제어 영역에서 더 실무적으로 다루는 것이 적절하다.

## 15. Refresh가 필요한 대표 패턴

### 15.1 패턴 1 — ALV 버튼으로 상태 변경

```text
사용자가 행 선택
→ 툴바 버튼 클릭
→ 선택 행 상태 변경
→ ALV Refresh
```

### 15.2 패턴 2 — 계산 결과 갱신

```text
사용자가 조건 입력
→ 금액/수량 재계산
→ Internal Table 값 변경
→ ALV Refresh
```

### 15.3 패턴 3 — 메시지 필드 갱신

```text
데이터 검증 수행
→ 오류 또는 경고 메시지 필드 채움
→ ALV Refresh
```

### 15.4 패턴 4 — 재조회 후 표시

```text
DB 재조회
→ GT_DISPLAY 재구성
→ ALV Refresh
```

단, 재조회 후 데이터 건수와 순서가 많이 바뀌면 Stable Refresh의 효과가 제한될 수 있다.

## 16. 자주 발생하는 오류와 원인

### 16.1 Refresh를 호출했는데 화면이 바뀌지 않음

가능한 원인:

| 원인 | 설명 |
|---|---|
| Internal Table을 실제로 변경하지 않음 | Refresh는 데이터 변경을 대신하지 않는다. |
| 다른 Internal Table을 변경함 | Grid에 바인딩된 테이블이 아니라 별도 테이블을 수정했을 수 있다. |
| `go_grid`가 아직 생성되지 않음 | 객체가 Bound 상태인지 확인해야 한다. |
| PBO/PAI 흐름이 예상과 다름 | Screen Flow Logic과 사용자 명령을 확인해야 한다. |
| Frontend Flush 이슈 | 특수 상황에서 `CL_GUI_CFW=>FLUSH` 확인이 필요할 수 있다. |

### 16.2 Refresh 후 스크롤이 처음으로 돌아감

가능한 원인:

| 원인 | 설명 |
|---|---|
| `IS_STABLE` 미사용 | 기본 Refresh만 수행했다. |
| `ROW`, `COL` 중 일부만 설정 | 행 또는 열 안정성이 빠졌다. |
| 데이터 순서가 크게 변경 | 기존 위치를 유지하기 어렵다. |
| 필터/정렬 상태 변경 | 표시 대상 자체가 달라졌다. |

### 16.3 Dump 또는 객체 참조 오류

가능한 원인:

| 원인 | 설명 |
|---|---|
| `go_grid`가 Initial | Grid 객체 생성 전 Refresh 호출 |
| Screen 종료 후 객체 사용 | 이미 컨테이너가 정리된 뒤 호출 |
| 잘못된 이벤트 타이밍 | PBO/PAI 또는 이벤트 핸들러 흐름 점검 필요 |

방어 코드 예시는 다음과 같다.

```abap
IF go_grid IS BOUND.
  go_grid->refresh_table_display( ).
ENDIF.
```

## 17. `CL_GUI_CFW=>FLUSH`는 언제 언급해야 하는가?

SAP GUI Control Framework는 Frontend Control과 Application Server 간 통신을 사용한다.  
일반적인 초급 ALV Refresh에서는 `REFRESH_TABLE_DISPLAY`만으로 충분한 경우가 많다.

하지만 화면 제어가 복잡하거나, 여러 Control Method를 연속 호출한 뒤 프론트엔드 반영 타이밍을 명시적으로 확인해야 하는 경우 `CL_GUI_CFW=>FLUSH`가 사용될 수 있다.

초급 단계에서는 다음 정도로만 이해한다.

```text
대부분의 기본 Refresh 실습에서는 refresh_table_display를 먼저 사용한다.
Control Framework의 세부 통신 타이밍 문제는 심화 주제로 남긴다.
```

예시:

```abap
CALL METHOD cl_gui_cfw=>flush.
```

[추정] 교육 시스템과 GUI 패치 수준, 화면 제어 방식에 따라 명시적 Flush 필요 여부가 달라질 수 있다. 초급 과정에서는 Dump나 반영 지연 문제가 있을 때 강사 안내에 따라 확인한다.

## 18. Refresh와 `SET_TABLE_FOR_FIRST_DISPLAY` 재호출 비교

| 구분 | `SET_TABLE_FOR_FIRST_DISPLAY` 재호출 | `REFRESH_TABLE_DISPLAY` |
|---|---|---|
| 주 용도 | 최초 표시 | 기존 표시 데이터 갱신 |
| 화면 상태 유지 | 상대적으로 불리 | Stable 옵션 사용 가능 |
| Field Catalog 재설정 | 가능하지만 비용 큼 | 일반적으로 기존 구조 유지 |
| 실무 사용 | 최초 1회 중심 | 데이터 변경 후 반복 사용 |
| 초급 실습 기준 | PBO 최초 진입 시 | PAI 버튼 처리 후 |

실무적으로는 다음 원칙이 좋다.

```text
Grid 객체가 최초 생성될 때만 SET_TABLE_FOR_FIRST_DISPLAY를 호출한다.
그 이후 데이터 변경은 REFRESH_TABLE_DISPLAY로 처리한다.
```

## 19. 실습 과제

### 19.1 기본 과제

다음 요구사항을 만족하는 Grid ALV 프로그램을 구성한다.

```text
1. Screen 0100에 Custom Control CC_ALV를 만든다.
2. GT_USER Internal Table을 ALV로 표시한다.
3. PF-STATUS에 TOGGLE 버튼을 만든다.
4. TOGGLE 버튼을 누르면 첫 번째 행의 STATUS를 A ↔ I로 변경한다.

```

|---|---|---|

| 대량 데이터에서 차이 |  |  |

### 19.3 오류 재현 과제

다음 오류를 일부러 만들어보고 원인을 기록한다.

| 오류 재현 | 기대 관찰 |
|---|---|
| Internal Table 수정 없이 Refresh만 호출 | 화면 변화 없음 |

## 22. 평가 문제

### Q1. `SET_TABLE_FOR_FIRST_DISPLAY`와 `REFRESH_TABLE_DISPLAY`의 차이를 설명하시오.

**모범 답안:**  
`SET_TABLE_FOR_FIRST_DISPLAY`는 Grid ALV를 최초로 표시하고 출력 Internal Table과 Field Catalog 등을 바인딩하는 데 사용한다. `REFRESH_TABLE_DISPLAY`는 이미 표시된 Grid에서 Internal Table 변경 내용을 화면에 다시 반영할 때 사용한다.

### Q2. Stable Refresh에서 `LVC_S_STBL-ROW`와 `LVC_S_STBL-COL`은 각각 무엇을 의미하는가?

**모범 답안:**  
`ROW`는 Refresh 후 행 위치를 최대한 유지하려는 설정이고, `COL`은 열 위치를 최대한 유지하려는 설정이다.

### Q3. Refresh를 호출했는데 화면이 바뀌지 않는 대표 원인을 세 가지 쓰시오.

**모범 답안:**  
Internal Table을 실제로 변경하지 않았거나, Grid에 바인딩된 테이블이 아닌 다른 테이블을 변경했거나, Grid 객체가 아직 생성되지 않았을 수 있다. 또한 PBO/PAI 흐름이 예상과 다르거나 화면 반영 타이밍 문제가 있을 수도 있다.

### Q4. `REFRESH_TABLE_DISPLAY`와 `COMMIT WORK`의 차이를 설명하시오.

**모범 답안:**  
`REFRESH_TABLE_DISPLAY`는 ALV 화면을 다시 그리는 메서드이고, `COMMIT WORK`는 데이터베이스 변경을 확정하는 명령이다. ALV를 Refresh했다고 DB에 저장되는 것은 아니며, DB에 저장했다고 현재 ALV 화면이 자동으로 갱신되는 것도 아니다.

## 23. 핵심 요약

```text
Grid ALV를 처음 표시할 때는 SET_TABLE_FOR_FIRST_DISPLAY를 사용한다.
이미 표시된 ALV의 데이터만 갱신할 때는 REFRESH_TABLE_DISPLAY를 사용한다.
Refresh는 Internal Table 변경 후에 호출해야 의미가 있다.
Stable Refresh는 행과 열 위치를 최대한 유지하기 위해 LVC_S_STBL을 사용한다.
ROW와 COL을 abap_true로 설정하면 사용자가 보던 위치를 더 안정적으로 유지할 수 있다.
Stable Refresh가 모든 화면 상태를 완벽히 보장하는 것은 아니다.
Refresh는 화면 갱신이고, DB Commit은 데이터 저장 확정이다.
```
