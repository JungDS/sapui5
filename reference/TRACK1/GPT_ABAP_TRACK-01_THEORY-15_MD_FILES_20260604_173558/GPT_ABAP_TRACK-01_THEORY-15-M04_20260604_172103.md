## 2. 선행 지식

Field Catalog를 이해하려면 다음 선행 지식이 필요하다.

| 선행 지식 | 필요한 이유 |
|---|---|
| Internal Table | ALV가 표시할 실제 데이터가 Internal Table에 들어 있기 때문이다. |
| Structure / Line Type | Internal Table의 컬럼 구조를 이해해야 Field Catalog를 만들 수 있다. |
| `CL_GUI_CUSTOM_CONTAINER` | Grid ALV가 표시될 화면 컨테이너가 필요하다. |
| `CL_GUI_ALV_GRID` | Field Catalog는 Grid ALV 객체에 전달되는 출력 메타데이터이다. |
| Dynpro PBO/PAI 기본 흐름 | Container와 ALV Grid 생성 위치를 이해하기 위해 필요하다. |

이번 모듈에서는 Screen 생성, Container 생성, Grid 객체 생성 코드를 깊게 반복하지 않는다.  
이미 앞선 모듈에서 준비되어 있다고 가정하고, **Field Catalog 작성 방식**에 집중한다.

## 3. Field Catalog란 무엇인가?

### 3.1 쉬운 정의

Field Catalog는 ALV Grid에 전달하는 컬럼 속성 목록이다.

예를 들어 Output Internal Table이 다음 필드를 가진다고 하자.

```text
CARRID
CONNID
FLDATE
PRICE
CURRENCY
```

Grid ALV는 이 데이터를 화면에 컬럼으로 표시해야 한다.  
하지만 화면에 보여줄 때는 추가 정보가 필요하다.

```text
컬럼 제목을 무엇으로 표시할 것인가?
컬럼 폭은 어느 정도로 둘 것인가?
숫자 필드인지 문자 필드인지 어떻게 해석할 것인가?
숨길 컬럼은 무엇인가?
정렬이나 합계 가능 여부는 어떻게 할 것인가?
색상이나 강조 표시를 할 것인가?
```

이 중 이번 모듈에서는 가장 기초적인 세 가지를 다룬다.

| Field Catalog 필드 | 의미 |
|---|---|
| `FIELDNAME` | Output Internal Table의 필드명 |
| `COLTEXT` | ALV 화면에 표시할 컬럼 제목 |
| `OUTPUTLEN` | 컬럼 출력 폭 |

## 4. `LVC_T_FCAT`과 `LVC_S_FCAT`

Grid ALV에서 Field Catalog는 보통 다음 타입으로 선언한다.

```abap
DATA gt_fcat TYPE lvc_t_fcat.
DATA gs_fcat TYPE lvc_s_fcat.
```

두 타입의 의미는 다음과 같다.

| 타입 | 의미 |
|---|---|
| `LVC_S_FCAT` | Field Catalog 한 줄, 즉 한 컬럼의 속성 |
| `LVC_T_FCAT` | 여러 `LVC_S_FCAT` 행을 담는 Internal Table |

비유하면 다음과 같다.

```text
LVC_S_FCAT = 컬럼 하나의 설정
LVC_T_FCAT = ALV 전체 컬럼 설정표
```

예를 들어 ALV에 5개 컬럼을 보여주려면 `LVC_T_FCAT` 안에 보통 5개의 `LVC_S_FCAT` 행이 들어간다.

## 5. Field Catalog와 Output Internal Table의 관계

Output Internal Table이 다음 구조라고 가정한다.

```abap
TYPES: BEGIN OF ty_flight,
         carrid   TYPE s_carr_id,
         connid   TYPE s_conn_id,
         fldate   TYPE s_date,
         price    TYPE s_price,
         currency TYPE s_currcode,
       END OF ty_flight.

DATA gt_flight TYPE STANDARD TABLE OF ty_flight.
```

Field Catalog의 `FIELDNAME`에는 이 구조의 필드명이 들어가야 한다.

```text
CARRID
CONNID
FLDATE
PRICE
CURRENCY
```

즉, Field Catalog는 Output Internal Table과 이름으로 연결된다.

### 5.1 가장 중요한 규칙

```text
Field Catalog의 FIELDNAME 값은 Output Internal Table의 Component 이름과 일치해야 한다.
```

ABAP 필드명은 보통 대문자로 관리되므로 Field Catalog에서도 대문자로 작성하는 것이 안전하다.

좋은 예:

```abap
gs_fcat-fieldname = 'CARRID'.
```

위험한 예:

```abap
gs_fcat-fieldname = 'carrid'.
gs_fcat-fieldname = 'CARRIER_ID'.
gs_fcat-fieldname = 'CARR_ID'.
```

실제 Component 이름이 `CARRID`인데 Field Catalog에서 다른 이름을 쓰면 ALV가 해당 컬럼을 찾지 못하거나 의도한 속성을 적용하지 못한다.

## 6. 최소 Field Catalog 예제

가장 기본적인 Field Catalog 작성 패턴은 다음과 같다.

```abap
FORM build_field_catalog.

  DATA ls_fcat TYPE lvc_s_fcat.

  CLEAR ls_fcat.
  ls_fcat-fieldname = 'CARRID'.
  ls_fcat-coltext   = '항공사'.
  ls_fcat-outputlen = 10.
  APPEND ls_fcat TO gt_fcat.

  CLEAR ls_fcat.
  ls_fcat-fieldname = 'CONNID'.
  ls_fcat-coltext   = '연결번호'.
  ls_fcat-outputlen = 10.
  APPEND ls_fcat TO gt_fcat.

  CLEAR ls_fcat.
  ls_fcat-fieldname = 'FLDATE'.
  ls_fcat-coltext   = '비행일자'.
  ls_fcat-outputlen = 12.
  APPEND ls_fcat TO gt_fcat.

ENDFORM.
```

위 코드는 다음 뜻이다.

| 코드 | 의미 |
|---|---|
| `CLEAR ls_fcat` | 이전 컬럼 설정값 제거 |
| `FIELDNAME` | 출력 Internal Table의 필드명 지정 |
| `COLTEXT` | 컬럼 제목 지정 |
| `OUTPUTLEN` | 출력 폭 지정 |
| `APPEND` | 완성된 컬럼 설정을 Field Catalog 테이블에 추가 |

---

## 7. `FIELDNAME` 기초

`FIELDNAME`은 Field Catalog에서 가장 중요한 필드이다.

```abap
ls_fcat-fieldname = 'CARRID'.
```

이 값은 Output Internal Table의 Component 이름과 매칭된다.

### 7.1 정상 예

Output Internal Table 구조:

```abap
TYPES: BEGIN OF ty_output,
         carrid TYPE s_carr_id,
         connid TYPE s_conn_id,
       END OF ty_output.
```

Field Catalog:

```abap
ls_fcat-fieldname = 'CARRID'.
```

`CARRID`는 실제 Component 이름과 일치하므로 정상이다.

### 7.2 오류 예

```abap
ls_fcat-fieldname = 'CARRIER'.
```

Output Internal Table에 `CARRIER`라는 Component가 없으면 ALV는 이 필드를 정상적으로 매핑할 수 없다.

### 7.3 실무 점검 포인트

Field Catalog 오류가 의심될 때는 다음을 확인한다.

```text
Output Internal Table의 실제 Component 이름은 무엇인가?
FIELDNAME에 그 이름을 정확히 넣었는가?
오타는 없는가?
대문자로 작성했는가?
필드가 INCLUDE 구조 안에 있는 경우 최종 출력 구조에서 이름이 어떻게 보이는가?
```

## 8. `COLTEXT` 기초

`COLTEXT`는 ALV 컬럼 제목을 지정한다.

```abap
ls_fcat-coltext = '항공사'.
```

### 8.1 왜 필요한가?

Data Element를 참조하는 구조라면 ALV가 DDIC 라벨을 어느 정도 활용할 수 있다.  
하지만 실무에서는 화면 목적에 맞게 컬럼 제목을 직접 지정해야 하는 경우가 많다.

예를 들어 같은 필드라도 리포트 목적에 따라 제목이 달라질 수 있다.

| 필드 | 리포트 A | 리포트 B |
|---|---|---|
| CARRID | 항공사 | Carrier |
| CONNID | 노선번호 | Connection |
| PRICE | 항공권 가격 | 금액 |

Field Catalog의 `COLTEXT`를 사용하면 ALV 화면에서 사용자에게 더 적절한 제목을 제공할 수 있다.

### 8.2 제목 작성 기준

좋은 컬럼 제목은 다음 특징을 가진다.

| 기준 | 설명 |
|---|---|
| 짧고 명확함 | 화면 폭을 낭비하지 않는다. |
| 업무 의미 중심 | 기술명보다 사용자가 이해할 표현을 사용한다. |
| 일관성 | 같은 의미의 필드는 여러 리포트에서 동일 표현을 사용한다. |
| 혼합 언어 지양 | 한 화면 안에서 한글/영문 혼용을 과도하게 하지 않는다. |

나쁜 예:

```text
FIELD1
CARRID
DATA
값
```

좋은 예:

```text
항공사
연결번호
비행일자
항공권 가격
통화
```

## 9. `OUTPUTLEN` 기초

`OUTPUTLEN`은 ALV 컬럼의 출력 폭을 지정한다.

```abap
ls_fcat-outputlen = 12.
```

### 9.1 왜 필요한가?

필드의 실제 길이와 화면에서 필요한 표시 폭은 항상 같지 않다.

예를 들어 `CARRID`는 내부적으로 3자리일 수 있지만, 화면 제목이 “항공사”이고 데이터가 짧다면 8~10 정도가 보기 좋을 수 있다.  
날짜나 금액처럼 표시 형식이 있는 필드는 조금 더 넓게 잡아야 할 수 있다.

### 9.2 예시 기준

| 필드 | 예시 출력 폭 | 설명 |
|---|---:|---|
| CARRID | 8~10 | 항공사 코드 |
| CONNID | 10 | 연결번호 |
| FLDATE | 12 | 날짜 표시 |
| PRICE | 15 | 금액 표시 |
| CURRENCY | 8 | 통화 코드 |

### 9.3 실무 주의

`OUTPUTLEN`을 너무 짧게 주면 값이나 제목이 잘려 보일 수 있다.  
너무 길게 주면 화면 공간이 낭비된다.

초급 단계에서는 `OUTPUTLEN`을 직접 조정하면서 ALV 화면이 어떻게 바뀌는지 확인하는 것이 좋다.

## 10. `CLEAR`의 중요성

Field Catalog를 한 줄씩 작성할 때 `CLEAR`를 빼먹으면 이전 컬럼 설정이 다음 컬럼에 남을 수 있다.

예를 들어 다음 코드는 위험하다.

```abap
ls_fcat-fieldname = 'CARRID'.
ls_fcat-coltext   = '항공사'.
ls_fcat-outputlen = 10.
APPEND ls_fcat TO gt_fcat.

ls_fcat-fieldname = 'CONNID'.
ls_fcat-coltext   = '연결번호'.
APPEND ls_fcat TO gt_fcat.
```

두 번째 컬럼에서 `OUTPUTLEN`을 설정하지 않았지만, 첫 번째 컬럼의 `OUTPUTLEN = 10`이 남아 있을 수 있다.

따라서 다음 패턴을 권장한다.

```abap
CLEAR ls_fcat.
ls_fcat-fieldname = 'CONNID'.
ls_fcat-coltext   = '연결번호'.
ls_fcat-outputlen = 10.
APPEND ls_fcat TO gt_fcat.
```

초급자는 매 컬럼마다 `CLEAR → 값 설정 → APPEND` 패턴을 습관화하는 것이 좋다.

## 11. Field Catalog 생성 위치

Field Catalog는 일반적으로 ALV 최초 표시 전에 한 번 구성한다.

전형적인 Dynpro 기반 Grid ALV 흐름은 다음과 같다.

```text
PBO
  → Container 생성
  → Grid ALV 객체 생성
  → Output Internal Table 준비
  → Field Catalog 구성
  → SET_TABLE_FOR_FIRST_DISPLAY 호출
```

예시:

```abap
MODULE status_0100 OUTPUT.

  IF go_container IS INITIAL.

    CREATE OBJECT go_container
      EXPORTING
        container_name = 'CC_ALV'.

    CREATE OBJECT go_grid
      EXPORTING
        i_parent = go_container.

    PERFORM get_data.
    PERFORM build_field_catalog.
    PERFORM display_alv.

  ENDIF.

ENDMODULE.
```

`build_field_catalog`는 `display_alv`보다 먼저 호출되어야 한다.  
그래야 `SET_TABLE_FOR_FIRST_DISPLAY`에서 `IT_FIELDCATALOG`에 전달할 수 있다.

---

## 12. `SET_TABLE_FOR_FIRST_DISPLAY`와 연결

Field Catalog는 `CL_GUI_ALV_GRID`의 `SET_TABLE_FOR_FIRST_DISPLAY` 메서드에 전달된다.

```abap
CALL METHOD go_grid->set_table_for_first_display
  CHANGING
    it_outtab       = gt_flight
    it_fieldcatalog = gt_fcat.
```

여기서 핵심은 다음 두 개이다.

| 파라미터 | 의미 |
|---|---|
| `IT_OUTTAB` | 실제 출력 데이터 |
| `IT_FIELDCATALOG` | 컬럼 표시 속성 |

즉, 다음 관계를 이해해야 한다.

```text
GT_FLIGHT = 무엇을 보여줄 것인가?
GT_FCAT   = 어떻게 보여줄 것인가?
```

## 13. 전체 최소 예제

아래 예제는 Field Catalog 학습용 최소 구조이다.  
실제 화면 0100과 Custom Control `CC_ALV`가 이미 생성되어 있다고 가정한다.

```abap
REPORT zgpt_alv_fcat_basic.

TYPES: BEGIN OF ty_flight,
         carrid   TYPE s_carr_id,
         connid   TYPE s_conn_id,
         fldate   TYPE s_date,
         price    TYPE s_price,
         currency TYPE s_currcode,
       END OF ty_flight.

DATA: gt_flight    TYPE STANDARD TABLE OF ty_flight,
      gt_fcat      TYPE lvc_t_fcat,
      go_container TYPE REF TO cl_gui_custom_container,
      go_grid      TYPE REF TO cl_gui_alv_grid.

START-OF-SELECTION.
  CALL SCREEN 100.

MODULE status_0100 OUTPUT.

  SET PF-STATUS 'S100'.

  IF go_container IS INITIAL.

    CREATE OBJECT go_container
      EXPORTING
        container_name = 'CC_ALV'.

    CREATE OBJECT go_grid
      EXPORTING
        i_parent = go_container.

    PERFORM get_data.
    PERFORM build_field_catalog.
    PERFORM display_alv.

  ENDIF.

ENDMODULE.

FORM get_data.

  SELECT carrid,
         connid,
         fldate,
         price,
         currency
    FROM sflight
    INTO TABLE @gt_flight
    UP TO 50 ROWS.

ENDFORM.

FORM build_field_catalog.

  DATA ls_fcat TYPE lvc_s_fcat.

  CLEAR gt_fcat.

  CLEAR ls_fcat.
  ls_fcat-fieldname = 'CARRID'.
  ls_fcat-coltext   = '항공사'.
  ls_fcat-outputlen = 10.
  APPEND ls_fcat TO gt_fcat.

  CLEAR ls_fcat.
  ls_fcat-fieldname = 'CONNID'.
  ls_fcat-coltext   = '연결번호'.
  ls_fcat-outputlen = 10.
  APPEND ls_fcat TO gt_fcat.

  CLEAR ls_fcat.
  ls_fcat-fieldname = 'FLDATE'.
  ls_fcat-coltext   = '비행일자'.
  ls_fcat-outputlen = 12.
  APPEND ls_fcat TO gt_fcat.

  CLEAR ls_fcat.
  ls_fcat-fieldname = 'PRICE'.
  ls_fcat-coltext   = '가격'.
  ls_fcat-outputlen = 15.
  APPEND ls_fcat TO gt_fcat.

  CLEAR ls_fcat.
  ls_fcat-fieldname = 'CURRENCY'.
  ls_fcat-coltext   = '통화'.
  ls_fcat-outputlen = 8.
  APPEND ls_fcat TO gt_fcat.

ENDFORM.

FORM display_alv.

  CALL METHOD go_grid->set_table_for_first_display
    CHANGING
      it_outtab       = gt_flight
      it_fieldcatalog = gt_fcat.

ENDFORM.

MODULE user_command_0100 INPUT.

  CASE sy-ucomm.
    WHEN 'BACK' OR 'EXIT' OR 'CANC'.
      LEAVE TO SCREEN 0.
  ENDCASE.

ENDMODULE.
```

> [추정] 실습 시스템에 `SFLIGHT` 데이터가 없거나 권한이 제한된 경우 조회 결과가 비어 있을 수 있다. 이 경우 교육용 Z 테이블 또는 강사가 제공한 샘플 테이블로 대체한다.

## 14. Field Catalog를 수동으로 만드는 이유

Grid ALV는 DDIC 구조를 기반으로 어느 정도 컬럼을 자동 해석할 수 있다.  
그럼에도 수동 Field Catalog를 배우는 이유는 다음과 같다.

| 이유 | 설명 |
|---|---|
| 화면 요구사항 반영 | 컬럼 제목, 폭, 표시 여부를 직접 제어해야 한다. |
| 동적 출력 대응 | 상황에 따라 컬럼 구성이 바뀔 수 있다. |
| 비DDIC 타입 대응 | 로컬 타입이나 계산 필드가 포함될 수 있다. |
| 실무 유지보수 | ALV 리포트에서 컬럼 속성 조정이 자주 발생한다. |
| 심화 기능 기반 | 색상, 합계, 편집 가능 여부, 핫스팟 등의 출발점이 Field Catalog이다. |

초급 단계에서는 자동 생성보다 수동 작성으로 Field Catalog의 구조를 이해하는 것이 중요하다.

## 15. 자주 쓰는 Field Catalog 필드 미리보기

이번 모듈의 핵심은 `FIELDNAME`, `COLTEXT`, `OUTPUTLEN`이다.  
다만 실무에서는 다음 속성도 자주 사용한다.

| 필드 | 의미 | 이번 모듈 범위 |
|---|---|---|
| `FIELDNAME` | Internal Table 필드명 | 학습 |
| `COLTEXT` | 컬럼 제목 | 학습 |
| `OUTPUTLEN` | 출력 폭 | 학습 |
| `SCRTEXT_S` | 짧은 컬럼 텍스트 | 맛보기 |
| `SCRTEXT_M` | 중간 컬럼 텍스트 | 맛보기 |
| `SCRTEXT_L` | 긴 컬럼 텍스트 | 맛보기 |
| `KEY` | Key 컬럼 표시 | 후속/확장 |
| `NO_OUT` | 컬럼 숨김 | 후속/확장 |
| `HOTSPOT` | 클릭 가능한 컬럼 | 후속/확장 |
| `EMPHASIZE` | 컬럼 색상/강조 | 후속 M09 |
| `DO_SUM` | 합계 가능 | 심화 |
| `EDIT` | 셀 편집 가능 | 심화 |

이번 단계에서 너무 많은 속성을 한꺼번에 외우려고 하면 Field Catalog의 본질을 놓칠 수 있다.  
먼저 다음 세 개를 확실히 익힌다.

```text
FIELDNAME
COLTEXT
OUTPUTLEN
```

## 16. 정상 흐름과 오류 흐름

### 16.1 정상 흐름

```text
Output Internal Table 구조 확인
→ Field Catalog Internal Table 선언
→ 각 컬럼별 LVC_S_FCAT 작성
→ FIELDNAME, COLTEXT, OUTPUTLEN 설정
→ APPEND로 LVC_T_FCAT에 추가
→ SET_TABLE_FOR_FIRST_DISPLAY에 전달
→ ALV 화면에서 컬럼 표시 확인
```

### 16.2 오류 흐름 1: `FIELDNAME` 오타

#### 증상

- 특정 컬럼이 보이지 않는다.
- 컬럼 제목이 기대대로 적용되지 않는다.
- ALV 표시 시 오류가 발생할 수 있다.

#### 원인

Field Catalog의 `FIELDNAME`이 Output Internal Table의 Component 이름과 다르다.

#### 해결

```text
1. Output Internal Table의 Line Type 확인
2. 실제 Component 이름 확인
3. FIELDNAME 값을 대문자로 정확히 입력
4. 다시 실행
```

### 16.3 오류 흐름 2: `GT_FCAT` 초기화 누락

#### 증상

- PBO가 여러 번 실행되면서 컬럼이 중복되거나 이상하게 표시된다.
- Refresh 또는 화면 재진입 시 컬럼 설정이 누적된다.

#### 원인

Field Catalog를 다시 만들 때 `CLEAR gt_fcat` 또는 `REFRESH gt_fcat` 처리를 하지 않았다.

#### 해결

Field Catalog 작성 시작 전에 다음을 넣는다.

```abap
CLEAR gt_fcat.
```

### 16.4 오류 흐름 3: `LS_FCAT` 초기화 누락

#### 증상

- 이전 컬럼의 속성이 다음 컬럼에 남는다.
- 어떤 컬럼은 폭, 색상, Key 표시 등이 의도치 않게 적용된다.

#### 원인

각 컬럼 작성 전에 `CLEAR ls_fcat`을 하지 않았다.

#### 해결

각 컬럼마다 다음 패턴을 사용한다.

```abap
CLEAR ls_fcat.
ls_fcat-fieldname = '...'.
ls_fcat-coltext   = '...'.
ls_fcat-outputlen = ...
APPEND ls_fcat TO gt_fcat.
```

### 16.5 오류 흐름 4: Field Catalog 작성 후 전달 누락

#### 증상

- Field Catalog를 작성했는데 ALV에 반영되지 않는다.

#### 원인

`SET_TABLE_FOR_FIRST_DISPLAY` 호출 시 `IT_FIELDCATALOG`를 전달하지 않았다.

#### 해결

```abap
CALL METHOD go_grid->set_table_for_first_display
  CHANGING
    it_outtab       = gt_output
    it_fieldcatalog = gt_fcat.
```

## 17. 디버깅 포인트

Field Catalog 문제가 발생하면 다음 지점에서 디버깅한다.

| 위치 | 확인할 값 |
|---|---|
| `build_field_catalog` 종료 직후 | `GT_FCAT` 행 수 |
| 각 `APPEND` 직후 | `LS_FCAT-FIELDNAME`, `COLTEXT`, `OUTPUTLEN` |
| `display_alv` 진입 전 | `GT_FCAT`이 비어 있지 않은지 |
| `SET_TABLE_FOR_FIRST_DISPLAY` 호출 전 | `GT_OUTPUT`과 `GT_FCAT` 모두 채워져 있는지 |
| ALV 표시 후 | 컬럼 제목과 폭이 의도대로 보이는지 |

디버거에서 `GT_FCAT`을 확인했을 때 다음과 같이 보여야 한다.

| FIELDNAME | COLTEXT | OUTPUTLEN |
|---|---|---:|
| CARRID | 항공사 | 10 |
| CONNID | 연결번호 | 10 |
| FLDATE | 비행일자 | 12 |
| PRICE | 가격 | 15 |
| CURRENCY | 통화 | 8 |

## 18. 성능과 유지보수 관점

Field Catalog 자체는 일반적으로 대량 데이터 처리의 주된 성능 병목은 아니다.  
하지만 ALV 화면을 반복 생성하거나 PBO마다 불필요하게 Field Catalog를 계속 재구성하면 비효율적일 수 있다.

### 18.1 권장 패턴

```abap
IF go_container IS INITIAL.
  PERFORM build_field_catalog.
  PERFORM display_alv.
ENDIF.
```

즉, 최초 화면 생성 시 Field Catalog를 만들고, 이후 단순 데이터 변경은 Refresh로 처리하는 구조가 일반적이다.

### 18.2 유지보수 기준

Field Catalog 작성 시 다음 기준을 지키면 유지보수가 쉬워진다.

| 기준 | 설명 |
|---|---|
| FORM 또는 Method 분리 | Field Catalog 작성 로직을 별도 루틴으로 분리 |
| 컬럼 순서 명확화 | APPEND 순서가 화면 컬럼 순서가 되므로 의도적으로 배치 |
| 상수 활용 검토 | 필드명이 반복되면 오타 방지를 위해 상수화 가능 |
| DDIC 라벨 활용 검토 | 표준 의미가 충분하면 과도한 수동 텍스트 지양 |
| 주석 최소화 | 복잡한 컬럼 의미에만 주석 사용 |

## 19. 실무 안티패턴

### 19.1 모든 컬럼을 무작정 수동 작성

수동 Field Catalog는 제어력이 높지만, 모든 속성을 무작정 수동으로 쓰면 유지보수량이 늘어난다.  
초급 실습에서는 수동 작성이 좋지만, 실무에서는 DDIC 구조와 자동 생성 기능을 함께 고려한다.

### 19.2 필드명 오타를 화면 오류로만 확인

필드명 오타는 화면에서만 확인하면 시간이 오래 걸린다.  
디버거에서 `GT_FCAT`과 Output Internal Table 구조를 직접 비교하는 습관이 필요하다.

### 19.3 컬럼 제목을 기술명 그대로 사용

`CARRID`, `CONNID`, `FLDATE` 같은 기술명만 화면에 보여주면 사용자가 이해하기 어렵다.  
업무 리포트라면 사용자에게 의미 있는 제목을 제공해야 한다.

### 19.4 PBO마다 Field Catalog를 계속 누적

PBO는 화면 처리 중 여러 번 호출될 수 있다.  
초급자가 `IF go_container IS INITIAL` 조건 없이 Field Catalog를 계속 APPEND하면 컬럼 설정이 누적될 수 있다.


| FIELDNAME | COLTEXT | OUTPUTLEN |
|---|---|---:|

| FLDATE | 비행일자 | 12 |
| PRICE | 가격 | 15 |
| CURRENCY | 통화 | 8 |

### 20.3 실습 절차

```text
1. 기존 Grid ALV 프로그램을 연다.
2. 전역 변수 GT_FCAT TYPE LVC_T_FCAT을 선언한다.
3. BUILD_FIELD_CATALOG FORM을 만든다.
4. 각 컬럼별 LVC_S_FCAT을 작성한다.
5. SET_TABLE_FOR_FIRST_DISPLAY에 IT_FIELDCATALOG = GT_FCAT을 전달한다.
6. 프로그램을 실행한다.
7. ALV 컬럼 제목과 폭이 요구사항대로 표시되는지 확인한다.
```

## 21. 평가 문제

### 21.1 객관식

#### Q1. Grid ALV에서 Field Catalog의 주된 역할은 무엇인가?

A. 데이터베이스 테이블을 생성한다.  
B. ALV 컬럼의 표시 속성을 정의한다.  
C. Selection Screen의 입력값을 검증한다.  
D. Screen의 PF-STATUS를 생성한다.

정답: B

#### Q2. `LVC_T_FCAT`에 대한 설명으로 가장 적절한 것은?

A. ALV 한 컬럼의 속성을 담는 구조이다.  
B. 여러 컬럼의 Field Catalog 설정을 담는 Internal Table이다.  
C. ALV 출력 데이터 자체를 담는 Internal Table이다.  
D. Dynpro 화면 번호를 저장하는 변수이다.

정답: B

#### Q3. `FIELDNAME`에는 어떤 값을 넣어야 하는가?

A. 사용자가 보고 싶은 한글 컬럼 제목  
B. Output Internal Table의 실제 Component 이름  
C. 프로그램 이름  
D. Screen 번호

정답: B

#### Q4. `COLTEXT`의 역할은 무엇인가?

A. 컬럼 제목을 지정한다.  
B. 컬럼을 숨긴다.  
C. 컬럼 합계를 계산한다.  
D. 데이터베이스 Key를 설정한다.

정답: A

### 21.2 서술형

#### Q1. `FIELDNAME` 오타가 발생하면 어떤 문제가 생길 수 있는가?

모범 답안:  
Field Catalog의 `FIELDNAME`은 Output Internal Table의 Component 이름과 매칭된다. 오타가 있으면 ALV가 해당 필드를 찾지 못해 컬럼이 표시되지 않거나, 지정한 컬럼 속성이 적용되지 않을 수 있다.

#### Q2. Field Catalog 작성 시 `CLEAR ls_fcat`을 반복해야 하는 이유를 설명하시오.

모범 답안:  
`LVC_S_FCAT` 한 줄을 재사용하여 여러 컬럼 설정을 만들기 때문에, 이전 컬럼의 속성이 다음 컬럼에 남지 않도록 매번 초기화해야 한다.

#### Q3. `GT_FLIGHT`와 `GT_FCAT`의 역할 차이를 설명하시오.

모범 답안:  
`GT_FLIGHT`는 ALV에 출력할 실제 데이터가 들어 있는 Output Internal Table이고, `GT_FCAT`은 그 데이터를 화면에서 어떤 컬럼 제목과 폭으로 보여줄지 정의하는 Field Catalog이다.

## 23. 다음 모듈 연결

다음 모듈은 `THEORY-15-M05 — Layout 기본 설정`이다.

이번 모듈에서 Field Catalog로 **컬럼 단위 표시 속성**을 제어했다면, 다음 모듈에서는 Layout으로 **ALV Grid 전체 표시 속성**을 제어한다.

```text
Field Catalog = 컬럼별 속성
Layout        = ALV 전체 표시 속성
```

예를 들어 다음 속성은 Field Catalog가 아니라 Layout에서 다룬다.

```text
Zebra 표시
Column Width Optimize
행 색상 필드명
선택 모드
```

따라서 `THEORY-15-M04`는 컬럼 설계의 출발점이고, `THEORY-15-M05`는 화면 전체 표시 설계의 출발점이다.

## 24. 핵심 요약

```text
Field Catalog는 Grid ALV 컬럼 표시 방식을 정의하는 메타데이터이다.
LVC_S_FCAT은 한 컬럼의 설정이고, LVC_T_FCAT은 여러 컬럼 설정의 Internal Table이다.
FIELDNAME은 Output Internal Table의 Component 이름과 정확히 일치해야 한다.
COLTEXT는 사용자에게 표시할 컬럼 제목이다.
OUTPUTLEN은 컬럼 폭을 지정한다.
각 컬럼 설정 전 CLEAR ls_fcat을 수행해야 이전 값이 남지 않는다.
SET_TABLE_FOR_FIRST_DISPLAY에서 IT_FIELDCATALOG에 Field Catalog를 전달해야 적용된다.
```
