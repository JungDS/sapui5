```text

2. 화면에 표시할 필드 구조를 설계한다.
3. 출력용 Internal Table을 선언한다.
4. 조회 또는 가공 결과를 출력용 Internal Table에 채운다.
5. Grid ALV에 출력용 Internal Table을 넘긴다.
6. Field Catalog와 Layout으로 표시 방식을 조정한다.
```

이번 모듈은 이 중 2~4단계에 집중한다.

## 3. 출력용 Internal Table이란 무엇인가?

### 3.1 기본 정의

출력용 Internal Table은 Grid ALV에 표시할 데이터를 담는 Internal Table이다.

ABAP 프로그램은 DB 테이블, 계산 결과, 사용자 입력, 다른 함수의 결과 등을 조합하여 화면에 보여줄 데이터를 만든다. 이때 Grid ALV는 일반적으로 다음 메서드 호출에서 출력용 Internal Table을 전달받는다.

```abap
go_grid->set_table_for_first_display(
  CHANGING
    it_outtab       = gt_output
    it_fieldcatalog = gt_fcat ).
```

여기서 `GT_OUTPUT`이 출력용 Internal Table이다.

### 3.2 왜 별도의 출력용 Internal Table을 준비하는가?

원천 DB 테이블을 그대로 ALV에 보여줄 수도 있다. 하지만 실무에서는 출력용 구조를 별도로 만드는 경우가 많다.

이유는 다음과 같다.

| 이유 | 설명 |
|---|---|
| 화면 표시 필드 제한 | DB 테이블의 모든 필드를 보여줄 필요가 없을 수 있다. |
| 필드명 정리 | 화면에 맞는 의미 있는 필드명으로 정리할 수 있다. |
| 계산 필드 추가 | 금액 합계, 상태 텍스트, 표시용 아이콘 등을 추가할 수 있다. |
| 여러 테이블 조합 | JOIN 또는 후처리 결과를 하나의 구조로 표시할 수 있다. |
| ALV 제어 필드 추가 | 행 색상, 셀 색상, 체크박스 등 표시 제어 필드를 추가할 수 있다. |
| 유지보수성 | DB 구조 변경과 화면 출력 구조 변경을 분리할 수 있다. |

즉, 출력용 Internal Table은 단순 데이터 보관용이 아니라 **UI 표시 목적에 맞게 가공된 결과 구조**이다.

## 4. 원천 데이터와 출력 데이터의 차이

### 4.1 원천 데이터

원천 데이터는 DB 테이블이나 CDS View, 함수 호출, 메서드 호출 등에서 가져온 실제 업무 데이터이다.

예:

```text
SFLIGHT
SPFLI
SCARR
ZT_JHY_USER
BAPI 결과 구조
CDS View 결과
```

### 4.2 출력 데이터

출력 데이터는 사용자가 화면에서 이해하기 좋게 정리한 표시용 데이터이다.

예를 들어 `SFLIGHT`에는 항공편 가격, 통화, 날짜, 좌석 정보 등이 있지만, 교육용 ALV에서는 다음 필드만 보여줄 수 있다.

| 출력 필드 | 의미 |
|---|---|
| CARRID | 항공사 코드 |
| CONNID | 연결 번호 |
| FLDATE | 비행일 |
| PRICE | 가격 |
| CURRENCY | 통화 |
| STATUS_TEXT | 표시용 상태 텍스트 |

`STATUS_TEXT`는 원천 테이블에 없을 수 있다. 하지만 ALV 화면에는 표시할 수 있다. 이런 필드는 출력용 Internal Table에 추가한다.

### 4.3 실무 원칙

실무에서는 다음 기준을 권장한다.

```text
DB 테이블 구조 = 저장 목적 중심
ALV 출력 구조 = 사용자 표시 목적 중심
```

두 구조가 항상 같을 필요는 없다.

---

## 5. Grid ALV와 Internal Table의 관계

Grid ALV는 데이터 자체를 영구 저장하지 않는다. 프로그램에서 넘겨준 Internal Table을 기준으로 화면을 구성한다.

흐름은 다음과 같다.

```text
DB 또는 테스트 데이터
  → ABAP Internal Table
  → CL_GUI_ALV_GRID
  → SAP GUI 화면 표시
```

중요한 점은 다음이다.

```text
ALV에 데이터가 안 보인다고 해서 항상 ALV 객체 생성 문제는 아니다.
출력용 Internal Table이 비어 있거나, Field Catalog와 필드명이 맞지 않아도 데이터가 안 보일 수 있다.
```

따라서 Grid ALV 오류를 점검할 때는 객체 생성과 데이터 준비를 분리해서 확인해야 한다.

## 6. 출력용 Line Type 설계

출력용 Internal Table은 한 줄의 구조가 필요하다. 이를 Line Type이라고 한다.

### 6.1 Local TYPES 방식

교육용 예제에서는 프로그램 안에 Local Type을 선언하는 방식이 가장 이해하기 쉽다.

```abap
TYPES: BEGIN OF ty_output,
         carrid      TYPE sflight-carrid,
         connid      TYPE sflight-connid,
         fldate      TYPE sflight-fldate,
         price       TYPE sflight-price,
         currency    TYPE sflight-currency,
         status_text TYPE char20,
       END OF ty_output.

DATA gt_output TYPE STANDARD TABLE OF ty_output.
DATA gs_output TYPE ty_output.
```

이 방식은 특정 프로그램에서만 사용하는 ALV 출력 구조에 적합하다.

### 6.2 DDIC Structure 방식

여러 프로그램에서 같은 출력 구조를 재사용해야 한다면 DDIC Structure를 만들 수도 있다.

예:

```text
ZS_JHY_FLIGHT_ALV
```

그리고 프로그램에서는 다음처럼 사용할 수 있다.

```abap
DATA gt_output TYPE STANDARD TABLE OF zs_jhy_flight_alv.
DATA gs_output TYPE zs_jhy_flight_alv.
```

### 6.3 Local Type과 DDIC Structure 비교

| 구분 | Local Type | DDIC Structure |
|---|---|---|
| 정의 위치 | 프로그램 내부 | ABAP Dictionary |
| 재사용성 | 낮음 | 높음 |
| 생성 속도 | 빠름 | 상대적으로 느림 |
| 화면 라벨 연계 | 제한적 | Data Element 기반 활용 가능 |
| 변경 영향 | 해당 프로그램 중심 | 여러 객체에 영향 가능 |
| 교육용 적합성 | 매우 적합 | DDIC 복습에 적합 |

초급 과정에서는 Local Type으로 시작하고, 재사용 필요성이 생기면 DDIC Structure로 확장하는 흐름이 자연스럽다.

## 7. 출력용 Internal Table 선언 패턴

### 7.1 기본 선언 패턴

```abap
TYPES: BEGIN OF ty_output,
         carrid      TYPE sflight-carrid,
         connid      TYPE sflight-connid,
         fldate      TYPE sflight-fldate,
         price       TYPE sflight-price,
         currency    TYPE sflight-currency,
         status_text TYPE char20,
       END OF ty_output.

DATA gt_output TYPE STANDARD TABLE OF ty_output.
```

이 선언은 다음을 의미한다.

| 코드 | 의미 |
|---|---|
| `TYPES: BEGIN OF ty_output` | 출력 한 줄의 구조를 정의한다. |
| `TYPE sflight-carrid` | 표준 테이블 필드 타입을 참조한다. |
| `status_text TYPE char20` | 화면 표시용 계산 필드를 추가한다. |
| `GT_OUTPUT` | ALV에 넘길 출력용 Internal Table이다. |

### 7.2 Header Line 사용 금지

과거 ABAP 예제에서는 Header Line이 있는 Internal Table을 볼 수 있다.

```abap
DATA gt_output TYPE STANDARD TABLE OF ty_output WITH HEADER LINE.
```

초급 교육에서는 이 방식을 권장하지 않는다. Work Area와 Internal Table이 같은 이름으로 섞여 가독성과 유지보수성이 떨어지기 때문이다.

권장 방식은 다음이다.

```abap
DATA gt_output TYPE STANDARD TABLE OF ty_output.
DATA gs_output TYPE ty_output.
```

또는 최신 문법에서는 필요 시 인라인 선언을 사용할 수 있다.

## 8. 테스트 데이터로 출력용 Internal Table 채우기

DB 조회 전에는 간단한 테스트 데이터를 직접 넣어서 ALV 화면 흐름을 확인할 수 있다.

### 8.1 APPEND VALUE 방식

```abap
APPEND VALUE ty_output(
  carrid      = 'AA'
  connid      = '0017'
  fldate      = sy-datum
  price       = '1000.00'
  currency    = 'USD'
  status_text = 'Test Data 1'
) TO gt_output.

APPEND VALUE ty_output(
  carrid      = 'LH'
  connid      = '0400'
  fldate      = sy-datum + 1
  price       = '1500.00'
  currency    = 'EUR'
  status_text = 'Test Data 2'
) TO gt_output.
```

이 방식은 ALV 컨테이너와 Grid 객체가 정상적으로 표시되는지 빠르게 확인할 때 유용하다.

### 8.2 Work Area 방식

```abap
CLEAR gs_output.
gs_output-carrid      = 'AA'.
gs_output-connid      = '0017'.
gs_output-fldate      = sy-datum.
gs_output-price       = '1000.00'.
gs_output-currency    = 'USD'.
gs_output-status_text = 'Test Data 1'.
APPEND gs_output TO gt_output.
```

초급자에게는 Work Area 방식이 데이터 이동 과정을 눈으로 이해하기 쉽다. 다만 코드가 길어질 수 있으므로 후속 과정에서는 `VALUE #(...)` 표현도 함께 익히는 것이 좋다.

## 9. SELECT 결과를 출력용 Internal Table에 담기

실제 리포트에서는 DB 데이터를 조회해 출력용 Internal Table에 담는 경우가 많다.

### 9.1 같은 필드 구조로 직접 조회

출력용 Line Type의 필드명이 SELECT 필드명과 일치하면 다음과 같이 조회할 수 있다.

```abap
SELECT carrid,
       connid,
       fldate,
       price,
       currency
  FROM sflight
  INTO CORRESPONDING FIELDS OF TABLE @gt_output
  UP TO 50 ROWS.
```

`INTO CORRESPONDING FIELDS OF TABLE`은 이름이 같은 필드에 값을 매핑한다.

초급자는 다음 차이를 기억해야 한다.

| 방식 | 특징 |
|---|---|
| `INTO TABLE` | SELECT 목록과 대상 구조의 순서와 타입 관계가 중요하다. |
| `INTO CORRESPONDING FIELDS OF TABLE` | 이름이 같은 필드 기준으로 매핑한다. |

### 9.2 조회 후 표시용 필드 채우기

`STATUS_TEXT` 같은 계산 필드는 SELECT 결과에 직접 없을 수 있다. 이 경우 조회 후 LOOP로 값을 보완한다.

```abap
LOOP AT gt_output ASSIGNING FIELD-SYMBOL(<ls_output>).
  IF <ls_output>-price >= 1000.
    <ls_output>-status_text = 'High Price'.
  ELSE.
    <ls_output>-status_text = 'Normal Price'.
  ENDIF.
ENDLOOP.
```

이런 후처리는 ALV 출력에서 매우 자주 사용된다.

## 10. 전체 예제: 출력용 Internal Table 준비

아래 예제는 Screen과 Grid 객체가 이미 준비되어 있다는 전제에서 출력용 Internal Table을 준비하는 부분에 집중한다.

```abap
REPORT zjhy_alv_output_table.

TYPES: BEGIN OF ty_output,
         carrid      TYPE sflight-carrid,
         connid      TYPE sflight-connid,
         fldate      TYPE sflight-fldate,
         price       TYPE sflight-price,
         currency    TYPE sflight-currency,
         status_text TYPE char20,
       END OF ty_output.

DATA gt_output TYPE STANDARD TABLE OF ty_output.

START-OF-SELECTION.

  SELECT carrid,
         connid,
         fldate,
         price,
         currency
    FROM sflight
    INTO CORRESPONDING FIELDS OF TABLE @gt_output
    UP TO 50 ROWS.

  LOOP AT gt_output ASSIGNING FIELD-SYMBOL(<ls_output>).
    IF <ls_output>-price >= 1000.
      <ls_output>-status_text = 'High Price'.
    ELSE.
      <ls_output>-status_text = 'Normal Price'.
    ENDIF.
  ENDLOOP.

  IF gt_output IS INITIAL.
    MESSAGE 'No output data found.' TYPE 'I'.
  ENDIF.
```

이 예제에서 중요한 것은 `GT_OUTPUT`이 ALV 표시의 원천이라는 점이다. 후속 모듈에서 Field Catalog와 `SET_TABLE_FOR_FIRST_DISPLAY`를 연결하면 이 Internal Table이 화면에 표시된다.

## 11. Field Catalog와 출력용 Internal Table의 관계

다음 모듈에서 자세히 다루지만, 이번 모듈에서도 핵심 관계는 이해해야 한다.

Field Catalog의 `FIELDNAME`은 출력용 Internal Table의 Component 이름과 일치해야 한다.

예를 들어 출력용 Internal Table이 다음 필드를 가진다고 하자.

```abap
TYPES: BEGIN OF ty_output,
         carrid      TYPE sflight-carrid,
         connid      TYPE sflight-connid,
         fldate      TYPE sflight-fldate,
         price       TYPE sflight-price,
         currency    TYPE sflight-currency,
         status_text TYPE char20,
       END OF ty_output.
```

Field Catalog에서는 다음처럼 필드명을 사용해야 한다.

```abap
gs_fcat-fieldname = 'CARRID'.
gs_fcat-coltext   = 'Airline'.
APPEND gs_fcat TO gt_fcat.
```

만약 `FIELDNAME`에 `CARRIER_ID`를 입력했는데 출력용 Internal Table에 `CARRIER_ID`라는 Component가 없다면, ALV는 해당 컬럼을 정상적으로 표시할 수 없다.

따라서 초급자가 반드시 확인해야 할 관계는 다음이다.

```text
GT_OUTPUT의 Component 이름 = GT_FCAT-FIELDNAME 값
```

## 12. 출력용 Internal Table 설계 기준

### 12.1 사용자 관점에서 필요한 필드만 포함한다

ALV는 업무 사용자가 데이터를 확인하고 판단하기 위한 화면이다. DB 테이블의 모든 필드를 그대로 보여주는 것이 좋은 설계는 아니다.

좋은 설계:

```text
업무 사용자가 판단에 필요한 필드만 표시한다.
```

나쁜 설계:

```text
DB 테이블의 모든 필드를 아무 기준 없이 출력한다.
```

### 12.2 표시용 계산 필드를 분리한다

예를 들어 가격이 높으면 `High Price`, 낮으면 `Normal Price`를 보여주고 싶다면 원천 데이터에 없는 표시용 필드를 추가할 수 있다.

```abap
status_text TYPE char20
```

이런 필드는 DB 저장 목적이 아니라 ALV 표시 목적이다.

### 12.3 타입은 가능하면 원천 필드를 참조한다

필드 타입을 직접 `CHAR`, `P`, `DATS`로 선언하는 것보다, 표준 테이블 또는 DDIC 필드를 참조하는 것이 안전하다.

권장:

```abap
carrid TYPE sflight-carrid
price  TYPE sflight-price
```

비권장:

```abap
carrid TYPE c LENGTH 3
price  TYPE p DECIMALS 2
```

원천 필드 참조는 길이, 소수점, 통화/수량 관련 타입 일관성을 유지하는 데 도움이 된다.

### 12.4 ALV 제어용 필드는 업무 필드와 구분한다

후속 모듈에서 행 색상, 셀 색상, 체크박스 등을 다룰 수 있다. 이런 제어용 필드는 일반 업무 필드와 구분해서 이름을 정하는 것이 좋다.

예:

```abap
row_color TYPE char4
celltab   TYPE lvc_t_styl
```

이번 모듈에서는 개념만 소개하고, 실제 색상/스타일 구현은 후속 모듈에서 다룬다.

## 13. 데이터 준비 위치

Grid ALV 프로그램에서는 데이터 준비 위치도 중요하다.

일반적인 흐름은 다음과 같다.

```text
START-OF-SELECTION
  → DB 조회 및 GT_OUTPUT 채우기
  → CALL SCREEN 0100

PBO of Screen 0100
  → Container 생성
  → Grid 생성
  → SET_TABLE_FOR_FIRST_DISPLAY 호출
```

간단한 구조 예시는 다음과 같다.

```abap
START-OF-SELECTION.
  PERFORM get_data.
  CALL SCREEN 0100.

FORM get_data.
  SELECT carrid,
         connid,
         fldate,
         price,
         currency
    FROM sflight
    INTO CORRESPONDING FIELDS OF TABLE @gt_output
    UP TO 50 ROWS.
ENDFORM.
```

PBO에서 매번 DB 조회를 수행하면 화면 갱신 때마다 불필요한 조회가 반복될 수 있다. 초급 예제에서는 단순화를 위해 PBO에서 데이터를 준비하는 경우도 있지만, 실무 관점에서는 데이터 조회와 화면 생성 흐름을 분리하는 것이 좋다.

---

## 14. 정상 흐름

출력용 Internal Table 준비의 정상 흐름은 다음과 같다.

```text
1. 출력할 업무 필드를 결정한다.
2. Line Type을 선언한다.
3. 출력용 Internal Table을 선언한다.
4. DB 조회 또는 테스트 데이터로 Internal Table을 채운다.
5. 필요 시 표시용 계산 필드를 보완한다.
6. Internal Table이 비어 있지 않은지 확인한다.
7. 후속 모듈에서 Field Catalog와 연결한다.
8. SET_TABLE_FOR_FIRST_DISPLAY에 IT_OUTTAB으로 전달한다.
```

이 흐름에서 이번 모듈의 핵심 산출물은 `GT_OUTPUT`이다.

## 15. 오류 흐름과 점검 방법

### 15.1 ALV가 비어 보이는 경우

가능한 원인:

| 원인 | 점검 방법 |
|---|---|
| `GT_OUTPUT`이 비어 있음 | `LINES( gt_output )` 또는 디버거로 확인 |
| SELECT 결과 없음 | 조건 제거 후 조회, SE16N에서 원천 테이블 확인 |
| 데이터 준비 전에 ALV 호출 | 호출 순서 확인 |
| Field Catalog 필드명 불일치 | `GT_OUTPUT` Component와 `FIELDNAME` 비교 |
| 화면 객체 생성 문제 | M01/M02 컨테이너와 Grid 생성 흐름 확인 |

### 15.2 Dump가 발생하는 경우

가능한 원인:

| 원인 | 설명 |
|---|---|
| 객체 Reference 초기화 누락 | Grid 객체가 생성되지 않은 상태에서 메서드 호출 |
| 잘못된 필드 심볼 사용 | Assign되지 않은 Field Symbol 접근 |
| 타입 불일치 | SELECT 결과와 대상 구조 타입이 맞지 않음 |
| 화면 호출 순서 오류 | 데이터/객체 준비 전 화면 이벤트에서 접근 |

### 15.3 필드 값이 이상하게 보이는 경우

가능한 원인:

| 원인 | 설명 |
|---|---|
| 통화/수량 필드 참조 누락 | 금액/수량 표시 시 통화·단위 필드 필요 가능 |
| 출력 길이 미설정 | Field Catalog에서 Output Length 조정 필요 |
| 타입 직접 선언 오류 | 원천 필드와 다른 길이/소수점 지정 |
| 계산 필드 후처리 누락 | `STATUS_TEXT` 같은 표시 필드를 채우지 않음 |

## 16. 디버깅 포인트

출력용 Internal Table 문제를 디버깅할 때는 다음 위치에 Breakpoint를 둔다.

| 위치 | 확인 내용 |
|---|---|
| `PERFORM get_data` 시작 | 데이터 조회 루틴이 호출되는가 |
| `SELECT ... INTO TABLE` 직후 | `SY-SUBRC`, `LINES( gt_output )` 확인 |
| 후처리 LOOP 내부 | 계산 필드가 채워지는가 |
| `CALL SCREEN` 직전 | 화면 호출 전에 데이터가 준비되었는가 |
| `SET_TABLE_FOR_FIRST_DISPLAY` 직전 | `GT_OUTPUT`, `GT_FCAT` 상태 확인 |

초급자는 특히 다음 두 값을 확인하는 습관을 들이면 좋다.

```abap
sy-subrc
lines( gt_output )
```

## 17. 실무 성능 관점

### 17.1 필요한 필드만 SELECT한다

나쁜 예:

```abap
SELECT *
  FROM sflight
  INTO TABLE @DATA(lt_sflight).
```

좋은 예:

```abap
SELECT carrid,
       connid,
       fldate,
       price,
       currency
  FROM sflight
  INTO CORRESPONDING FIELDS OF TABLE @gt_output.
```

ALV에 필요한 필드만 조회하면 네트워크 전송량과 메모리 사용량을 줄일 수 있다.

### 17.2 대량 데이터는 제한 조건을 고려한다

Grid ALV는 많은 데이터를 표시할 수 있지만, 무제한 조회가 좋은 설계는 아니다.

실무에서는 다음을 고려해야 한다.

| 기준 | 설명 |
|---|---|
| Selection Screen 조건 | 사용자가 조회 범위를 제한하도록 한다. |
| 최대 조회 건수 | 교육용 예제에서는 `UP TO 50 ROWS` 같은 제한을 둘 수 있다. |
| DB WHERE 조건 | ABAP 메모리에서 필터링하기보다 DB에서 먼저 줄인다. |
| 성능 점검 | 대량 테이블은 ST05, SAT 등 후속 성능 도구와 연결된다. |

이번 Section은 Grid ALV 기초이므로 성능 분석 도구까지 확장하지 않는다. 다만 무제한 조회를 습관화하지 않는 것이 중요하다.

## 18. 권한과 운영 안정성 관점

출력용 Internal Table은 조회 결과를 담는다. 따라서 조회 대상 데이터에 권한이 필요할 수 있다.

초급 실습에서는 표준 교육 테이블인 `SFLIGHT` 계열을 사용하지만, 실무에서는 다음을 고려해야 한다.

| 관점 | 설명 |
|---|---|
| 권한 점검 | 특정 업무 데이터 조회 전 권한 확인이 필요할 수 있다. |
| 개인정보 | 사용자명, 연락처, 금액 등 민감 필드는 출력 제한 필요 가능 |
| 운영 데이터량 | 전체 조회는 시스템 부하를 만들 수 있다. |
| 변경 가능 ALV | 편집 ALV에서는 출력용 Internal Table이 변경 버퍼 역할도 할 수 있다. |

이번 모듈은 조회용 출력 테이블 기준이며, 편집 ALV는 후속 실무/심화 주제에서 다루는 것이 적절하다.

## 19. 미니 실습

### 19.1 실습 목표

`SFLIGHT` 데이터를 기준으로 Grid ALV 출력용 Internal Table을 준비한다.

### 19.2 실습 코드

```abap
REPORT zjhy_alv_prepare_outtab.

TYPES: BEGIN OF ty_output,
         carrid      TYPE sflight-carrid,
         connid      TYPE sflight-connid,
         fldate      TYPE sflight-fldate,
         price       TYPE sflight-price,
         currency    TYPE sflight-currency,
         status_text TYPE char20,
       END OF ty_output.

DATA gt_output TYPE STANDARD TABLE OF ty_output.

START-OF-SELECTION.

  SELECT carrid,
         connid,
         fldate,
         price,
         currency
    FROM sflight
    INTO CORRESPONDING FIELDS OF TABLE @gt_output
    UP TO 50 ROWS.

  LOOP AT gt_output ASSIGNING FIELD-SYMBOL(<ls_output>).
    IF <ls_output>-price >= 1000.
      <ls_output>-status_text = 'High Price'.
    ELSE.
      <ls_output>-status_text = 'Normal Price'.
    ENDIF.
  ENDLOOP.

  WRITE: / 'Output row count:', lines( gt_output ).
```

### 19.3 실습 확인

실행 후 다음을 확인한다.

| 확인 항목 | 설명 |
|---|---|
| Syntax Check 성공 | 타입 선언과 SELECT 구문이 올바른가 |
| Row Count 출력 | `GT_OUTPUT`에 데이터가 채워졌는가 |
| 디버거 확인 | `STATUS_TEXT`가 채워졌는가 |
| 원천 데이터 확인 | `SFLIGHT`에 데이터가 있는가 |

### 19.4 오류 케이스 기록

다음 오류 중 하나를 의도적으로 만들어 기록한다.

| 오류 케이스 | 예상 현상 | 해결 |
|---|---|---|
| SELECT 대상 필드명 오타 | Syntax Error | 필드명 수정 |
| `STATUS_TEXT` 필드 누락 | 후처리 LOOP에서 필드 없음 오류 | Line Type에 필드 추가 |
| 원천 데이터 없음 | Row Count 0 | 조건 완화 또는 테스트 데이터 확인 |
| 타입 직접 선언 오류 | 표시값 길이/소수점 이상 | 원천 필드 타입 참조 사용 |

## 20. 강사용 설명 포인트

강의에서는 다음 메시지를 강조하면 좋다.

1. Grid ALV는 데이터를 만드는 도구가 아니라 표시하는 도구이다.
2. ALV에 표시할 데이터는 반드시 Internal Table에 준비되어야 한다.
3. 출력용 Internal Table은 DB 테이블과 1:1로 같을 필요가 없다.
4. 화면 표시용 계산 필드는 출력 구조에 별도로 추가할 수 있다.
5. Field Catalog의 `FIELDNAME`은 출력용 Internal Table의 Component 이름과 맞아야 한다.
6. 데이터가 보이지 않을 때는 Grid 객체보다 `GT_OUTPUT`이 비어 있는지 먼저 확인한다.

## 21. 자주 하는 실수와 안티패턴

| 안티패턴 | 문제 | 개선 |
|---|---|---|
| `SELECT *`를 그대로 ALV에 출력 | 불필요한 필드와 메모리 증가 | 필요한 필드만 SELECT |
| DB 테이블 구조를 화면 구조로 무조건 사용 | UI 표시 목적과 저장 목적이 섞임 | 출력용 구조 별도 설계 |

| Field Symbol 미할당 접근 | Runtime Error 가능 | LOOP ASSIGNING 범위 안에서만 사용 |

## 24. 후속 모듈 연결

이번 모듈에서는 출력용 Internal Table을 준비했다. 다음 모듈에서는 이 Internal Table의 필드를 ALV가 어떻게 컬럼으로 인식하게 할지 다룬다.

```text
THEORY-15-M03 출력용 Internal Table 준비
  → GT_OUTPUT 준비

THEORY-15-M04 Field Catalog 기초
  → GT_OUTPUT의 Component를 ALV 컬럼 정의로 연결

THEORY-15-M07 SET_TABLE_FOR_FIRST_DISPLAY
  → GT_OUTPUT과 GT_FCAT을 Grid ALV에 전달
```

즉, 이번 모듈의 결과물은 다음 모듈들의 입력값이다.

```text
GT_OUTPUT 없이는 ALV에 표시할 데이터가 없다.
GT_FCAT 없이는 컬럼 표시 제어가 어렵다.
SET_TABLE_FOR_FIRST_DISPLAY 없이는 Grid에 데이터를 최초 표시할 수 없다.
```

---

## 25. 핵심 요약

```text
출력용 Internal Table은 Grid ALV에 표시할 데이터의 원천이다.
DB 테이블 구조와 ALV 출력 구조는 반드시 같을 필요가 없다.
Line Type은 화면 표시 목적에 맞게 설계한다.
필요한 필드만 조회하고, 표시용 계산 필드는 후처리로 채울 수 있다.
Field Catalog의 FIELDNAME은 출력용 Internal Table의 Component 이름과 일치해야 한다.
ALV가 비어 보이면 먼저 GT_OUTPUT이 비어 있는지 확인한다.
```
