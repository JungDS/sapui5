## 3. 세 가지 모듈화 방식 한눈에 보기

ABAP에서 초급자가 먼저 만나는 대표 모듈화 방식은 다음 세 가지이다.

| 방식 | 대표 문법 | 범위 | 전형적 사용 |
|---|---|---|---|
| Subroutine | `FORM ... ENDFORM`, `PERFORM` | 주로 같은 프로그램 내부 | Report 내부 로직 분리 |
| Function Module | `CALL FUNCTION` | Function Group 단위 전역 Repository | 표준 API, RFC, BAPI, 공통 함수 |
| Class Method | `CLASS ... METHOD`, `=>`, `->` | Class 단위 전역 또는 로컬 | 현대 ABAP, OO 설계, 테스트 가능한 로직 |

간단히 말하면 다음과 같다.

```text
FORM        = 같은 프로그램 안에서 코드를 나누는 오래된 절차형 방식
Function    = 시스템 전역에서 호출 가능한 함수 단위
Class       = 객체지향 기반의 현대적 모듈화 방식
```

## 4. 선택 기준 요약

실무에서는 다음 기준으로 선택한다.

| 판단 기준 | FORM | Function Module | Class Method |
|---|---:|---:|---:|
| 같은 Report 내부에서만 사용 | 적합 | 과함 | 가능 |
| 여러 프로그램에서 재사용 | 부적합 | 가능 | 적합 |
| 표준 SAP API 호출 | 해당 없음 | 매우 중요 | Wrapper로 감쌀 수 있음 |
| RFC / BAPI / Update Task | 해당 없음 | 적합 | 직접 대체 어려운 영역 있음 |
| 신규 S/4HANA 커스텀 로직 | 제한적 | 상황별 | 권장 |
| 테스트 가능성 | 낮음 | 중간 | 높음 |
| 캡슐화 | 낮음 | 중간 | 높음 |
| Clean ABAP 관점 | Legacy 이해용 | 기존 자산/API 활용 | 신규 개발 권장 |
| RAP / ABAP Cloud 방향성 | 부적합 | 제한적 | 가장 연결성 높음 |

## 5. Subroutine 선택 기준

### 5.1 Subroutine의 기본 성격

Subroutine은 `FORM ... ENDFORM`으로 정의하고 `PERFORM`으로 호출하는 절차형 모듈화 방식이다.

예시:

```abap
REPORT zedu_mod_choice_form.

DATA gv_amount TYPE p LENGTH 8 DECIMALS 2 VALUE '1000.00'.
DATA gv_rate   TYPE p LENGTH 5 DECIMALS 2 VALUE '10.00'.
DATA gv_tax    TYPE p LENGTH 8 DECIMALS 2.

PERFORM calculate_tax USING gv_amount gv_rate
                      CHANGING gv_tax.

WRITE: / 'Tax:', gv_tax.

FORM calculate_tax USING    iv_amount TYPE p
                            iv_rate   TYPE p
                   CHANGING cv_tax    TYPE p.
  cv_tax = iv_amount * iv_rate / 100.
ENDFORM.
```

### 5.2 Subroutine을 사용해도 되는 경우

Subroutine은 다음 상황에서 아직 의미가 있다.

| 상황 | 설명 |
|---|---|
| 기존 Report 프로그램 유지보수 | 오래된 ABAP Report에는 FORM 기반 구조가 많다. |
| 같은 프로그램 내부에서만 사용하는 짧은 로직 | 전역 재사용 목적이 없고 로컬 분리만 필요할 때 가능하다. |
| 초급 교육에서 모듈화 개념 설명 | 입력/출력/처리 분리를 이해하기 쉽다. |
| Legacy 코드 읽기 | 운영 시스템 분석 시 반드시 이해해야 한다. |

예를 들어 하나의 교육용 Report 안에서 출력 헤더, 입력 검증, 간단 계산을 분리하는 정도라면 FORM을 통해 모듈화의 감각을 익힐 수 있다.

### 5.3 Subroutine을 피하는 것이 좋은 경우

다음 상황에서는 FORM 중심 설계를 피하는 것이 좋다.

| 상황 | 이유 |
|---|---|
| 여러 프로그램에서 공통 재사용 필요 | FORM은 기본적으로 프로그램 내부 로컬 절차에 가깝다. |
| 테스트 자동화가 중요 | ABAP Unit 관점에서 Class Method보다 불리하다. |
| 상태와 책임을 캡슐화해야 함 | 객체지향 설계가 더 적합하다. |
| 신규 S/4HANA 대규모 개발 | 유지보수성과 확장성 측면에서 Class 중심이 적합하다. |
| RAP / ABAP Cloud 방향 학습 | FORM은 현대 ABAP 아키텍처와 거리가 있다. |

### 5.4 Subroutine 판단 문장

```text
FORM은 “기존 Report 내부 로직을 읽고 작은 단위로 정리하는 데 필요한 문법”으로 이해한다.
신규 공통 로직 설계의 기본 선택지는 아니다.
```

## 6. Function Module 선택 기준

### 6.1 Function Module의 기본 성격

Function Module은 Function Group에 포함되는 전역 Repository 함수이다.  
호출은 `CALL FUNCTION`으로 수행한다.

예시:

```abap
CALL FUNCTION 'CONVERSION_EXIT_ALPHA_INPUT'
  EXPORTING
    input  = lv_partner
  IMPORTING
    output = lv_partner.
```

Function Module은 SAP 표준에서 매우 중요한 위치를 가진다.  
특히 BAPI, RFC, Conversion Exit, Update Task 등은 Function Module 기반으로 널리 사용된다.

### 6.2 Function Module을 사용하는 것이 적합한 경우

| 상황 | 설명 |
|---|---|
| SAP 표준 Function Module 호출 | 표준 API 사용 시 필수적으로 이해해야 한다. |
| BAPI 호출 | 많은 BAPI는 Function Module 형태로 제공된다. |
| RFC 통신 | Remote-enabled Function Module이 사용된다. |
| Update Task | `IN UPDATE TASK` 흐름에서 Function Module이 사용된다. |
| 기존 고객사 공통 함수 재사용 | 운영 시스템에는 Z Function Module이 많을 수 있다. |
| Conversion Exit | 입력/출력 변환 로직에서 자주 만난다. |

초급자가 Function Module을 배워야 하는 이유는 “신규 개발의 최선이라서”가 아니라, **SAP 표준과 Legacy 실무에서 여전히 자주 만나기 때문**이다.

### 6.3 Function Module의 장점

| 장점 | 설명 |
|---|---|
| 전역 재사용 가능 | 여러 프로그램에서 호출할 수 있다. |
| 명확한 인터페이스 | Importing, Exporting, Changing, Tables, Exceptions를 가진다. |
| SAP 표준 API와 연결 | BAPI, RFC 등 표준 기능 이해에 필요하다. |
| Function Builder 지원 | SE37에서 테스트와 문서 확인이 가능하다. |

### 6.4 Function Module의 한계

| 한계 | 설명 |
|---|---|
| Function Group 전역 상태 | Global Data 사용 시 의존성이 복잡해질 수 있다. |
| 객체지향 캡슐화 한계 | Class 기반 설계보다 책임 분리가 약할 수 있다. |
| 테스트 구조 한계 | Class Method 대비 ABAP Unit 설계가 불편할 수 있다. |
| 신규 Clean Architecture와 거리 | 현대 ABAP에서는 Class 중심 설계가 더 자연스럽다. |
| TABLES 파라미터 남용 가능 | 오래된 방식의 인터페이스가 유지보수성을 떨어뜨릴 수 있다. |

### 6.5 Function Module 판단 문장

```text
Function Module은 SAP 표준 API, RFC, BAPI, 기존 공통 함수 자산을 다루기 위해 반드시 알아야 한다.
하지만 신규 업무 로직의 기본 설계 단위는 점차 Class Method 중심으로 판단하는 것이 좋다.
```

## 7. Class Method 선택 기준

### 7.1 Class Method의 기본 성격

Class Method는 Class 안에 정의되는 메서드이다.  
Static Method는 `=>`로 호출하고, Instance Method는 객체 참조를 통해 `->`로 호출한다.

예시:

```abap
CLASS zcl_edu_tax DEFINITION.
  PUBLIC SECTION.
    CLASS-METHODS calculate_tax
      IMPORTING
        iv_amount TYPE p
        iv_rate   TYPE p
      RETURNING
        VALUE(rv_tax) TYPE p.
ENDCLASS.

CLASS zcl_edu_tax IMPLEMENTATION.
  METHOD calculate_tax.
    rv_tax = iv_amount * iv_rate / 100.
  ENDMETHOD.
ENDCLASS.

START-OF-SELECTION.
  DATA(lv_tax) = zcl_edu_tax=>calculate_tax(
                   iv_amount = '1000.00'
                   iv_rate   = '10.00' ).

  WRITE: / lv_tax.
```

### 7.2 Class Method를 선택하는 것이 좋은 경우

| 상황 | 설명 |
|---|---|
| 신규 커스텀 로직 | 현대 ABAP에서는 Class 중심 설계가 적합하다. |
| 여러 프로그램에서 재사용 | Public Method로 명확히 재사용 가능하다. |
| 테스트 자동화 필요 | ABAP Unit과 연결하기 좋다. |
| 책임 분리 필요 | Service, Validator, Mapper 등 역할 분리가 가능하다. |
| RAP / ABAP Cloud 학습 연계 | Behavior Implementation, Handler, Saver 등 Class 기반 흐름과 연결된다. |
| Clean ABAP 적용 | 작은 Method, 명확한 이름, 테스트 가능한 구조에 적합하다. |

### 7.3 Class Method의 장점

| 장점 | 설명 |
|---|---|
| 캡슐화 | 데이터와 로직의 책임을 묶을 수 있다. |
| 테스트 가능성 | ABAP Unit 테스트 작성이 상대적으로 쉽다. |
| 확장성 | 상속, 인터페이스, 다형성 등으로 확장 가능하다. |
| 가독성 | 책임 단위로 이름을 붙이면 코드 의도가 명확해진다. |
| 현대 SAP 방향성 | S/4HANA, RAP, ABAP Cloud 흐름과 잘 맞는다. |

### 7.4 Class Method의 주의점

Class가 항상 정답은 아니다.  
초급자가 무리하게 Class를 사용하면 다음 문제가 생길 수 있다.

| 문제 | 설명 |
|---|---|
| 과도한 추상화 | 간단한 Report에 너무 많은 Class를 만들 수 있다. |
| Static Method 남용 | 전역 함수처럼만 쓰면 OO 장점이 줄어든다. |
| 이름만 Class인 절차형 코드 | 책임 분리 없이 긴 Method 하나에 모든 로직을 넣는 경우 |
| 선행 지식 부족 | 객체, 인스턴스, 의존성 개념을 이해하지 못하면 오히려 혼란스럽다. |

초급 단계에서는 Class Method를 “현대 ABAP의 권장 방향”으로 받아들이되, OO 심화 개념은 후속 Section에서 단계적으로 학습하는 것이 좋다.

### 7.5 Class Method 판단 문장

```text
신규 ABAP 업무 로직은 가능한 한 Class Method 중심으로 설계하는 것이 장기적으로 유리하다.
다만 초급 단계에서는 작은 Static Method부터 시작하고, 인스턴스와 인터페이스는 후속 OO ABAP에서 확장한다.
```

## 8. 선택 의사결정 트리

다음 질문 순서로 판단하면 좋다.

```text
1. SAP 표준 BAPI/RFC/Conversion Exit를 호출해야 하는가?
   → 예: Function Module 호출

2. 기존 프로그램 내부의 Legacy FORM 로직을 유지보수하는가?
   → 예: FORM 이해 및 제한적 수정

3. 새로 만드는 업무 로직이고 여러 곳에서 재사용될 가능성이 있는가?
   → 예: Class Method 우선 검토

4. 한 Report 안에서만 쓰는 아주 작은 보조 로직인가?
   → 예: FORM 또는 Local Class Method 검토

5. 자동 테스트, 확장성, Clean ABAP 적용이 중요한가?
   → 예: Class Method 우선

6. 외부 시스템 호출 또는 원격 호출이 필요한가?
   → 예: 표준적으로 RFC Function Module 또는 적절한 API 계층 검토
```

실무적으로 단순화하면 다음과 같다.

```text
Legacy Report 내부 정리       → FORM 이해
SAP 표준 API / RFC / BAPI     → Function Module
신규 커스텀 업무 로직          → Class Method
```

## 9. 같은 로직을 세 방식으로 비교하기

### 9.1 요구사항

| Status | Text |
|---|---|
| A | Active |
| I | Inactive |
| B | Blocked |
| 기타 | Unknown |

### 9.2 FORM 방식

```abap
REPORT zedu_status_form.

DATA gv_status TYPE c LENGTH 1 VALUE 'A'.
DATA gv_text   TYPE string.

PERFORM get_status_text USING gv_status
                        CHANGING gv_text.

WRITE: / gv_text.

FORM get_status_text USING    iv_status TYPE c
                     CHANGING cv_text   TYPE string.
  CASE iv_status.
    WHEN 'A'.
      cv_text = 'Active'.
    WHEN 'I'.
      cv_text = 'Inactive'.
    WHEN 'B'.
      cv_text = 'Blocked'.
    WHEN OTHERS.
      cv_text = 'Unknown'.
  ENDCASE.
ENDFORM.
```

특징:

```text
같은 Report 내부에서는 단순하고 이해하기 쉽다.
다른 프로그램에서 재사용하려면 적합하지 않다.
```

---

### 9.3 Function Module 방식

Function Module을 실제로 만들려면 `SE37`에서 Function Group과 Function Module을 생성해야 한다.

개념적 호출 예시는 다음과 같다.

```abap
CALL FUNCTION 'ZFM_EDU_GET_STATUS_TEXT'
  EXPORTING
    iv_status = gv_status
  IMPORTING
    ev_text   = gv_text
  EXCEPTIONS
    not_found = 1
    OTHERS    = 2.
```

특징:

```text
전역 호출이 가능하다.
SE37에서 단독 테스트가 가능하다.
RFC/BAPI 같은 SAP 표준 패턴을 이해하는 데 필요하다.
하지만 신규 순수 업무 로직은 Class로 설계하는 것이 더 적합한 경우가 많다.
```

---

### 9.4 Class Method 방식

```abap
REPORT zedu_status_class.

CLASS lcl_status_text DEFINITION.
  PUBLIC SECTION.
    CLASS-METHODS get_text
      IMPORTING
        iv_status TYPE c
      RETURNING
        VALUE(rv_text) TYPE string.
ENDCLASS.

CLASS lcl_status_text IMPLEMENTATION.
  METHOD get_text.
    CASE iv_status.
      WHEN 'A'.
        rv_text = 'Active'.
      WHEN 'I'.
        rv_text = 'Inactive'.
      WHEN 'B'.
        rv_text = 'Blocked'.
      WHEN OTHERS.
        rv_text = 'Unknown'.
    ENDCASE.
  ENDMETHOD.
ENDCLASS.

START-OF-SELECTION.
  DATA(lv_text) = lcl_status_text=>get_text( iv_status = 'A' ).
  WRITE: / lv_text.
```

특징:

```text
로직 이름과 책임을 Class/Method로 명확히 표현할 수 있다.
후속 단계에서 전역 Class로 분리하거나 ABAP Unit 테스트를 붙이기 좋다.
현대 ABAP 방향성과 가장 잘 맞는다.
```

## 10. 가독성 관점의 선택

모듈화 방식 선택은 가독성과 직접 연결된다.

### 10.1 나쁜 코드

```abap
START-OF-SELECTION.

  " 입력 검증
  IF p_status IS INITIAL.
    WRITE: / 'Status is required.'.
    RETURN.
  ENDIF.

  " 상태 텍스트 계산
  CASE p_status.
    WHEN 'A'.
      DATA(lv_text) = 'Active'.
    WHEN 'I'.
      lv_text = 'Inactive'.
    WHEN 'B'.
      lv_text = 'Blocked'.
    WHEN OTHERS.
      lv_text = 'Unknown'.
  ENDCASE.

  " 출력
  WRITE: / p_status, lv_text.
```

짧아 보이지만 로직이 늘어나면 읽기 어려워진다.

### 10.2 의도를 나눈 코드

```abap
START-OF-SELECTION.

  IF lcl_validator=>is_status_initial( p_status ) = abap_true.
    WRITE: / 'Status is required.'.
    RETURN.
  ENDIF.

  DATA(lv_text) = lcl_status_text=>get_text( p_status ).

  WRITE: / p_status, lv_text.
```

이 코드는 내부 구현을 보지 않아도 전체 흐름을 읽기 쉽다.

```text
검증한다.
상태 텍스트를 구한다.
출력한다.
```

모듈화의 핵심은 코드 줄 수를 줄이는 것이 아니라, **의도를 읽을 수 있게 만드는 것**이다.

## 11. 재사용성 관점의 선택

### 11.1 재사용 범위별 권장 방식

| 재사용 범위 | 권장 방식 |
|---|---|
| 같은 Report 내부 | FORM 또는 Local Class |
| 같은 Package의 여러 프로그램 | Global Class |
| 여러 Package/팀에서 사용하는 공통 로직 | Released API 성격의 Global Class 또는 표준 Function/API |
| 외부 시스템/RFC 연계 | RFC Function Module 또는 공식 API |
| SAP 표준 기능 호출 | 표준 Function Module, BAPI, Class, CDS API 등 상황별 |

### 11.2 재사용의 함정

초급자가 자주 하는 실수는 “언젠가 재사용할 수도 있다”는 이유로 모든 로직을 전역 객체로 만드는 것이다.

그러나 재사용 가능한 객체는 다음 책임도 함께 가진다.

```text
명확한 인터페이스
문서화
하위 호환성
테스트
권한/예외 처리
변경 영향 관리
```

따라서 재사용성은 단순히 “다른 곳에서 부를 수 있다”가 아니라, **다른 곳에서 안전하게 부를 수 있다**는 의미이다.

## 12. 테스트 가능성 관점의 선택

### 12.1 왜 테스트 가능성이 중요한가?

실무 로직은 시간이 지나면서 계속 변경된다.  
변경할 때마다 사람이 수동으로만 테스트하면 누락이 생긴다.  
따라서 중요한 계산, 검증, 변환 로직은 자동 테스트가 가능해야 한다.

### 12.2 방식별 테스트 용이성

| 방식 | 테스트 관점 |
|---|---|
| FORM | 프로그램 내부에 묶여 있어 독립 테스트가 어렵다. |
| Function Module | SE37 단독 테스트는 가능하지만 ABAP Unit 구조화는 Class보다 불편할 수 있다. |
| Class Method | ABAP Unit과 결합하기 좋고 책임 단위 테스트가 쉽다. |

### 12.3 Class Method와 ABAP Unit 연결 예고

후속 과정에서는 다음과 같은 테스트 코드를 작성할 수 있다.

```abap
CLASS ltcl_status_text DEFINITION FOR TESTING
  DURATION SHORT
  RISK LEVEL HARMLESS.
  PRIVATE SECTION.
    METHODS get_text_active FOR TESTING.
ENDCLASS.

CLASS ltcl_status_text IMPLEMENTATION.
  METHOD get_text_active.
    cl_abap_unit_assert=>assert_equals(
      act = lcl_status_text=>get_text( 'A' )
      exp = 'Active' ).
  ENDMETHOD.
ENDCLASS.
```

현재 모듈에서는 ABAP Unit을 깊게 다루지 않는다.  
중요한 것은 Class Method가 테스트 가능한 구조로 확장되기 쉽다는 점이다.

## 13. 성능 관점의 선택

초급자는 “FORM이 빠른가, Function이 빠른가, Method가 빠른가”를 궁금해할 수 있다.  
대부분의 일반 업무 프로그램에서는 호출 방식의 미세한 성능 차이보다 다음이 훨씬 중요하다.

```text
불필요한 DB SELECT를 줄였는가?
LOOP 안에서 SELECT를 반복하지 않는가?
Internal Table 접근 방식을 적절히 선택했는가?
읽기 쉬운 구조로 오류를 줄였는가?
```

즉, 모듈화 방식 자체보다 **모듈 안의 로직 품질**이 성능에 더 큰 영향을 준다.

다만 극단적으로 짧은 로직을 수백만 번 호출하는 경우에는 호출 오버헤드도 검토할 수 있다.  
하지만 초급 과정에서는 다음 원칙이 더 중요하다.

```text
먼저 가독성과 책임 분리를 확보한다.
성능 문제는 실제 측정 결과를 보고 개선한다.
```

## 14. 권한과 운영 안정성 관점의 선택

모듈화 방식은 권한과 운영 안정성에도 영향을 준다.

| 관점 | FORM | Function Module | Class Method |
|---|---|---|---|
| 호출 범위 통제 | 프로그램 내부 중심 | 전역 호출 가능 | Visibility로 통제 가능 |
| 권한 체크 위치 | 개발자가 직접 설계 | FM 내부 또는 호출 전후 | Method 내부/서비스 계층에서 설계 |
| 운영 변경 영향 | 해당 프로그램 중심 | 호출하는 여러 프로그램 영향 | 사용하는 Class/Interface 영향 |
| 공개 API 관리 | 어려움 | 가능하지만 관리 필요 | 명확한 Public/Protected/Private 구조 가능 |

특히 전역 객체는 변경 영향이 크다.  
Function Module이나 Global Class를 수정할 때는 어디서 호출되는지 반드시 확인해야 한다.

```text
Where-Used List 확인
호출 프로그램 영향 분석
인터페이스 변경 여부 확인
테스트 케이스 실행
운영 반영 절차 준수
```

## 15. 실무 선택 가이드

### 15.1 신규 개발 기준

신규 S/4HANA 커스텀 개발에서는 다음 기준을 권장한다.

| 상황 | 권장 |
|---|---|
| Report 안의 매우 작은 보조 로직 | Local Class Method 또는 제한적 FORM |
| 여러 Report에서 쓰는 공통 검증 | Global Class Method |
| 표준 BAPI 호출 | Function Module 호출 |
| 표준 FM을 직접 곳곳에서 호출 | Wrapper Class 검토 |
| RAP로 확장될 가능성 | Class 기반 설계 |
| 테스트가 필요한 계산/검증 | Class Method |

### 15.2 Legacy 유지보수 기준

기존 운영 프로그램이 FORM 중심이라면 무조건 Class로 바꾸는 것은 위험할 수 있다.

| 상황 | 권장 |
|---|---|
| 작은 버그 수정 | 기존 FORM 구조 안에서 최소 수정 |
| 큰 리팩토링 기회 | 신규 Class로 로직 분리 검토 |
| 표준 기능 호출 | 기존 FM 유지 가능 |
| 신규 기능 추가 | 기존 구조를 해치지 않는 범위에서 Class Method 도입 검토 |

Legacy 시스템에서는 다음 원칙이 중요하다.

```text
동작 보존을 우선한다.
한 번에 전면 개편하지 않는다.
테스트 가능한 작은 단위로 점진적으로 분리한다.
```

## 16. 안티패턴

### 16.1 FORM 만능주의

```text
모든 로직을 FORM으로만 나눈다.
전역 변수에 강하게 의존한다.
FORM 이름이 perform_1, calc_data, process_data처럼 모호하다.
```

문제점:

```text
테스트가 어렵다.
재사용 범위가 불명확하다.
전역 변수 영향으로 오류 추적이 어렵다.
```

### 16.2 Function Module 남발

```text
작은 로컬 로직까지 모두 Z Function Module로 만든다.
Function Group Global Data를 공유한다.
인터페이스 문서 없이 여러 프로그램에서 호출한다.
```

문제점:

```text
Repository 객체가 불필요하게 증가한다.
변경 영향 분석이 어려워진다.
Global Data 의존성이 숨겨진다.
```

### 16.3 Class 이름만 있고 절차형 코드 그대로

```text
ZCL_UTIL=>DO_ALL( )
```

하나의 Method에 조회, 검증, 계산, 저장, 출력이 모두 들어가면 Class를 사용해도 모듈화 효과가 낮다.

문제점:

```text
책임 분리가 되지 않는다.
테스트가 어렵다.
Method 이름만 보고 의도를 알 수 없다.
```

### 16.4 무조건 최신 문법만 사용

최신 문법을 쓰는 것과 좋은 설계는 다르다.

```text
Class를 썼지만 책임이 불명확하면 좋은 설계가 아니다.
FORM을 썼지만 Legacy 유지보수에서 안정적이라면 현실적으로 적절할 수 있다.
```

## 20. 평가 문제

### 20.1 객관식

#### Q1. 신규 S/4HANA 커스텀 업무 로직에서 일반적으로 우선 검토할 모듈화 방식은?

A. 모든 로직을 FORM으로 작성  
B. Class Method 중심 설계  
C. 모든 로직을 Function Module로 생성  
D. INCLUDE만 사용

**정답:** B

#### Q2. Function Module이 특히 중요한 영역으로 적절한 것은?

A. WRITE 문 줄바꿈  
B. RFC, BAPI, SAP 표준 API 호출  
C. 주석 작성  
D. 변수명 변경

**정답:** B

#### Q3. FORM/PERFORM에 대한 설명으로 가장 적절한 것은?

A. 현대 ABAP에서 전역 API 설계의 기본 방식이다.  
B. 같은 프로그램 내부 로직을 나누는 절차형 방식이며 Legacy 코드 이해에 중요하다.  
C. 반드시 RFC 통신에 사용된다.  
D. ABAP Unit 테스트를 위해 가장 권장되는 방식이다.

### 20.2 서술형

#### Q1. Subroutine, Function Module, Class Method의 선택 기준을 간단히 설명하시오.

**모범 답안:**  
Subroutine은 주로 같은 프로그램 내부의 절차형 로직 분리에 사용되며 Legacy Report 유지보수에서 중요하다. Function Module은 SAP 표준 API, BAPI, RFC, 기존 공통 함수 호출에서 중요하다. Class Method는 신규 커스텀 업무 로직, 테스트 가능한 구조, Clean ABAP, RAP/ABAP Cloud 방향성과 잘 맞기 때문에 현대 ABAP에서 우선 검토한다.

#### Q2. Function Module을 신규 로직에 무조건 사용하지 않는 이유는 무엇인가?

**모범 답안:**  
Function Module은 전역 재사용이 가능하지만 Function Group Global Data 의존성, 객체지향 캡슐화 한계, 테스트 구조의 불편함이 있을 수 있다. 신규 로직은 책임 분리와 테스트 가능성을 고려해 Class Method가 더 적합한 경우가 많다.

#### Q3. Class를 사용했는데도 좋은 모듈화가 아닐 수 있는 이유를 설명하시오.

**모범 답안:**  
Class 안의 하나의 Method에 조회, 검증, 계산, 저장, 출력이 모두 들어가 있으면 책임 분리가 되지 않는다. Class 문법을 사용했더라도 Method 이름과 책임이 불명확하면 절차형 코드를 단순히 Class 안으로 옮긴 것에 불과하다.

---

## 21. 강사용 설명 포인트

강의에서는 다음 문장을 기준으로 설명하면 좋다.

```text
모듈화는 문법 선택이 아니라 변경 가능성과 책임 경계를 설계하는 일이다.
```

초급자에게는 처음부터 “FORM은 절대 쓰면 안 된다”라고 말하기보다 다음처럼 단계적으로 설명하는 편이 좋다.

```text
FORM은 읽고 유지보수할 줄 알아야 한다.
Function Module은 SAP 표준과 Legacy 실무 때문에 반드시 알아야 한다.
Class Method는 신규 설계의 중심으로 익혀야 한다.
```

이 구분이 되어야 학습자가 기존 시스템과 현대 ABAP을 동시에 이해할 수 있다.

## 22. 후속 학습 연결

이번 모듈은 다음 학습으로 연결된다.

| 후속 주제 | 연결 방식 |
|---|---|
| Internal Table 응용 | 처리 로직을 별도 Method나 FORM으로 분리 |
| Open SQL | 조회 로직과 가공 로직 분리 |
| SALV | 데이터 조회, 가공, 출력 책임 분리 |
| OO ABAP | Class Method 선택 기준을 본격적으로 확장 |
| ABAP Unit | Class Method 기반 테스트 가능성 학습 |
| Clean ABAP | 이름, 책임, 작은 Method 원칙과 연결 |
| RAP | Handler/Behavior 구현이 Class 중심으로 구성됨 |

## 23. 핵심 요약

```text
FORM은 같은 프로그램 내부의 절차형 로직 분리에 적합하며 Legacy 이해에 중요하다.
Function Module은 SAP 표준 API, BAPI, RFC, 기존 공통 함수 호출에서 중요하다.
Class Method는 신규 커스텀 로직, 테스트 가능성, 유지보수성, 현대 ABAP 방향성에 가장 적합하다.
모듈화 선택은 재사용 범위, 테스트 가능성, 인터페이스 안정성, 운영 영향도를 기준으로 판단한다.
최신 문법을 쓰는 것보다 책임이 명확한 구조를 만드는 것이 더 중요하다.
```
