## 3. Function Module이란 무엇인가?

### 3.1 쉬운 정의

Function Module은 ABAP Repository에 등록된 재사용 가능한 함수형 처리 단위이다.  
여러 프로그램에서 같은 기능을 반복 구현하지 않고, 하나의 Function Module을 호출해 사용할 수 있다.

예를 들어 다음과 같은 처리가 여러 프로그램에서 필요하다고 하자.

```text
날짜 유효성 검사
코드 변환
사용자 확인
팝업 표시
BAPI 호출
표준 업무 함수 실행
```

이런 처리를 Function Module로 제공하면 여러 Report, Module Pool, Class, Enhancement, Interface 프로그램에서 동일하게 호출할 수 있다.

### 3.2 Function Module은 어디에 있는가?

Function Module은 보통 `SE37`에서 조회하고 테스트한다.

```text
T-Code: SE37
이름: Function Builder
```

SE37에서는 다음을 확인할 수 있다.

| 영역 | 설명 |
|---|---|
| Attributes | Function Module의 속성 |
| Import | 외부에서 Function Module로 들어오는 입력 파라미터 |
| Export | Function Module이 호출자에게 돌려주는 출력 파라미터 |
| Changing | 입력과 출력 역할을 모두 하는 파라미터 |
| Tables | Internal Table 전달용 고전적 파라미터 |
| Exceptions | Function Module이 반환할 수 있는 예외 상황 |
| Source Code | Function Module 내부 구현 코드 |

초급 단계에서는 Source Code를 분석하기보다 **Interface 탭을 정확히 읽는 능력**이 더 중요하다.

## 4. FORM / PERFORM과 CALL FUNCTION 비교

`FORM / PERFORM`과 `CALL FUNCTION`은 모두 코드를 모듈화하기 위한 방식이지만 범위와 성격이 다르다.

| 구분 | FORM / PERFORM | CALL FUNCTION |
|---|---|---|
| 정의 위치 | 주로 같은 프로그램 내부 | Function Builder(SE37)의 Repository 객체 |
| 재사용 범위 | 같은 프로그램 중심 | 여러 프로그램에서 호출 가능 |
| 관리 단위 | Report 내부 코드 | Function Group에 속한 Function Module |
| 인터페이스 | USING / CHANGING | IMPORTING / EXPORTING / CHANGING / TABLES |
| 예외 처리 | 직접 구현 | EXCEPTIONS 및 sy-subrc 기반 처리 가능 |
| 실무 위치 | Legacy Report 내부 모듈화 | 표준 API, BAPI, RFC, 기존 업무 함수 호출 |

### 4.1 초급자 관점의 차이

```text
FORM은 내 프로그램 안에 있는 작은 처리 블록이다.
Function Module은 SAP 시스템에 등록된 공용 처리 블록이다.
```

### 4.2 실무 관점

S/4HANA 신규 개발에서는 Local Class, Global Class, RAP Service, CDS 기반 개발이 점점 더 중요해졌다.  
그럼에도 Function Module은 여전히 실무에서 매우 자주 등장한다.

이유는 다음과 같다.

| 이유 | 설명 |
|---|---|
| 표준 Function Module | SAP 표준 기능이 Function Module 형태로 제공되는 경우가 많다. |
| BAPI | 많은 BAPI가 Function Module 기반이다. |
| Legacy 시스템 | 기존 고객 개발 프로그램이 Function Module을 많이 사용한다. |
| RFC | 시스템 간 호출 기능과 연결될 수 있다. |
| 교육 효과 | 인터페이스 기반 호출 구조를 익히기에 좋다. |

따라서 초급자는 Function Module을 “새 개발에서 항상 만들어야 하는 객체”라기보다, **기존 SAP 기능을 호출하고 읽기 위해 반드시 이해해야 하는 객체**로 접근하는 것이 좋다.

## 5. CALL FUNCTION 기본 문법

Function Module 호출의 기본 형태는 다음과 같다.

```abap
CALL FUNCTION 'FUNCTION_MODULE_NAME'
  EXPORTING
    input_parameter  = input_value
  IMPORTING
    output_parameter = output_value
  CHANGING
    changing_param   = changing_value
  TABLES
    table_param      = internal_table
  EXCEPTIONS
    error_case_1     = 1
    error_case_2     = 2
    OTHERS           = 3.
```

모든 영역을 항상 사용하는 것은 아니다.  
Function Module이 어떤 Interface를 가지는지에 따라 필요한 영역만 작성한다.

예를 들어 어떤 Function Module에 Import 파라미터만 있고 Export 파라미터가 없다면 `IMPORTING` 영역을 작성하지 않을 수 있다.

## 6. EXPORTING과 IMPORTING 방향성

초급자가 가장 많이 혼동하는 부분이 `EXPORTING`과 `IMPORTING`이다.

특히 `CALL FUNCTION`에서의 방향성은 호출 프로그램 관점으로 이해해야 한다.

| CALL FUNCTION 구문 | 호출 프로그램 관점 | 의미 |
|---|---|---|
| EXPORTING | 호출 프로그램 → Function Module | 값을 넘겨준다 |
| IMPORTING | Function Module → 호출 프로그램 | 결과를 받아온다 |
| CHANGING | 양방향 | 값을 넘기고 변경 결과를 받는다 |
| TABLES | 양방향 성격의 Internal Table 전달 | 고전적 테이블 파라미터 |

### 6.1 기억 문장

```text
CALL FUNCTION의 EXPORTING은 내가 함수에게 보내는 값이다.
CALL FUNCTION의 IMPORTING은 내가 함수로부터 받아오는 값이다.
```

### 6.2 이름 때문에 생기는 혼동

`EXPORTING`이라는 단어만 보면 “Function Module이 값을 내보낸다”라고 생각하기 쉽다.  
하지만 `CALL FUNCTION` 구문에서는 호출자 관점으로 읽어야 한다.

```abap
CALL FUNCTION 'Z_FM_CALCULATE'
  EXPORTING
    iv_amount = gv_amount
  IMPORTING
    ev_result = gv_result.
```

위 코드의 의미는 다음과 같다.

```text
gv_amount 값을 Function Module의 iv_amount로 보낸다.
Function Module의 ev_result 결과를 gv_result로 받아온다.
```

## 7. SE37에서 Interface 읽는 방법

Function Module을 호출하기 전에 반드시 SE37에서 Interface를 확인해야 한다.

### 7.1 확인 절차

```text
1. SAP GUI 실행
2. T-Code: SE37
3. Function Module 이름 입력
4. Display 선택
5. Import / Export / Changing / Tables / Exceptions 탭 확인
6. 필요 시 Documentation 확인
7. Test/Execute로 단독 실행 가능 여부 확인
```

### 7.2 확인해야 할 항목

| 항목 | 확인 이유 |
|---|---|
| Parameter Name | CALL FUNCTION에서 정확히 입력해야 한다. |
| Typing | 어떤 변수 타입을 넘겨야 하는지 알 수 있다. |
| Optional 여부 | 생략 가능한 파라미터인지 판단한다. |
| Default Value | 기본값이 있는지 확인한다. |
| Pass Value 여부 | 값 전달 방식 이해에 도움 된다. |
| Short Text | 파라미터의 업무 의미를 파악한다. |
| Exceptions | 오류 상황별 `sy-subrc` 처리를 작성한다. |
| Documentation | 사용 전제조건과 주의사항을 확인한다. |

초급자는 “인터페이스를 보지 않고 인터넷 예제 코드만 복사”하는 습관을 피해야 한다.  
시스템 버전, 고객 확장, Function Module 릴리스에 따라 파라미터나 동작이 다를 수 있기 때문이다.

## 8. 실습 예제 1: CONVERSION_EXIT_ALPHA_INPUT 호출

### 8.1 예제 목적

SAP에서는 번호 필드가 내부적으로 앞자리에 0을 채워 저장되는 경우가 많다.  
예를 들어 사용자가 `123`을 입력해도 내부 저장 형식은 `0000000123`일 수 있다.

이런 변환 규칙을 이해하기 위해 표준 Function Module `CONVERSION_EXIT_ALPHA_INPUT`을 호출해볼 수 있다.

> [추정] 대부분의 ABAP 시스템에서 `CONVERSION_EXIT_ALPHA_INPUT`은 사용 가능하지만, 교육 시스템 정책에 따라 직접 실행 권한이 제한될 수 있다.

### 8.2 코드 예제

```abap
REPORT zjhy_call_function_01.

DATA gv_external TYPE c LENGTH 10 VALUE '123'.
DATA gv_internal TYPE c LENGTH 10.

CALL FUNCTION 'CONVERSION_EXIT_ALPHA_INPUT'
  EXPORTING
    input  = gv_external
  IMPORTING
    output = gv_internal.

WRITE: / 'External:', gv_external,
       / 'Internal:', gv_internal.
```

### 8.3 코드 해석

| 코드 | 의미 |
|---|---|
| `gv_external` | 사용자가 입력한 외부 표현값 |
| `gv_internal` | SAP 내부 저장 형식으로 변환된 값 |
| `EXPORTING input = gv_external` | `gv_external` 값을 Function Module에 전달 |
| `IMPORTING output = gv_internal` | 변환 결과를 `gv_internal`로 수신 |

실행 결과는 시스템과 타입 길이에 따라 다음과 비슷할 수 있다.

```text
External: 123
Internal: 0000000123
```

### 8.4 검증 포인트

1. `EXPORTING`에 넘긴 값이 원본 입력값인지 확인한다.
2. `IMPORTING`으로 받은 값이 변경 결과인지 확인한다.
3. `gv_internal`의 길이를 바꾸면 결과가 어떻게 달라지는지 확인한다.
4. 공백 또는 이미 0이 붙은 값 입력 시 결과가 어떻게 달라지는지 관찰한다.

## 9. 실습 예제 2: DATE_CHECK_PLAUSIBILITY 호출

### 9.1 예제 목적

날짜값이 실제로 존재하는 날짜인지 확인하고 싶을 때 Function Module을 사용할 수 있다.  
예를 들어 `20250230`은 형식상 8자리 날짜처럼 보이지만 실제 존재하지 않는 날짜이다.

### 9.2 코드 예제

```abap
REPORT zjhy_call_function_02.

PARAMETERS p_date TYPE d DEFAULT sy-datum.

CALL FUNCTION 'DATE_CHECK_PLAUSIBILITY'
  EXPORTING
    date                      = p_date
  EXCEPTIONS
    plausibility_check_failed = 1
    OTHERS                    = 2.

IF sy-subrc = 0.
  WRITE: / 'Valid date:', p_date.
ELSEIF sy-subrc = 1.
  WRITE: / 'Invalid date:', p_date.
ELSE.
  WRITE: / 'Unexpected error. SY-SUBRC:', sy-subrc.
ENDIF.
```

### 9.3 코드 해석

| 코드 | 의미 |
|---|---|
| `PARAMETERS p_date TYPE d` | Selection Screen에서 날짜 입력을 받는다. |
| `EXPORTING date = p_date` | 입력받은 날짜를 Function Module에 전달한다. |
| `EXCEPTIONS plausibility_check_failed = 1` | 날짜 타당성 실패 시 `sy-subrc = 1`로 매핑한다. |
| `OTHERS = 2` | 기타 예외를 `sy-subrc = 2`로 매핑한다. |
| `IF sy-subrc = 0` | 정상 처리 여부를 확인한다. |

### 9.4 실습 입력값

| 입력값 | 예상 |
|---|---|
| 오늘 날짜 | 정상 |
| 20250228 | 정상 |
| 20250230 | 오류 |
| 99999999 | 오류 가능 |
| 00000000 | 시스템/함수 동작에 따라 확인 필요 |

> [추정] 날짜 초기값이나 특수값에 대한 상세 동작은 시스템 릴리스와 Function Module 구현에 따라 다를 수 있으므로 실습 시스템에서 직접 확인하는 것이 좋다.

## 10. CHANGING 파라미터 이해

`CHANGING`은 호출자가 값을 넘겨주고, Function Module이 그 값을 변경하여 다시 호출자에게 반영하는 파라미터 영역이다.

개념적으로는 이전 모듈에서 학습한 `FORM ... CHANGING`과 유사하다.

```text
호출 프로그램 값
→ Function Module로 전달
→ Function Module 내부에서 변경
→ 변경된 값이 호출 프로그램 변수에 반영
```

### 10.1 개념 예시

```abap
CALL FUNCTION 'Z_FM_NORMALIZE_TEXT'
  CHANGING
    cv_text = gv_text.
```

위 코드는 다음 의미를 가진다.

```text
gv_text를 Function Module에 넘긴다.
Function Module이 cv_text를 수정한다.
수정된 값이 다시 gv_text에 반영된다.
```

### 10.2 사용 시 주의

| 주의점 | 설명 |
|---|---|
| 원본 변경 | CHANGING은 호출자 변수를 변경할 수 있다. |
| 디버깅 필요 | 호출 전후 값을 비교해야 한다. |
| 의미 명확화 | 입력인지 출력인지 애매해질 수 있으므로 문서 확인이 중요하다. |
| 과도한 사용 지양 | 신규 설계에서는 입력과 출력을 명확히 분리하는 방식도 검토한다. |

이번 모듈에서는 CHANGING을 “양방향 값 전달”로 이해하면 충분하다.  
세부 전달 방식, Pass by Value/Reference, 깊은 구조 변경은 후속 고급 주제에서 다루는 것이 적절하다.

## 11. TABLES 파라미터 이해

`TABLES`는 Function Module에서 Internal Table을 주고받기 위해 오래전부터 사용된 고전적 파라미터 영역이다.

```abap
CALL FUNCTION 'Z_FM_PROCESS_ITEMS'
  TABLES
    tt_items = lt_items.
```

### 11.1 TABLES의 의미

| 항목 | 설명 |
|---|---|
| 전달 대상 | Internal Table |
| 방향성 | 역사적으로 입력/출력 양방향 성격 |
| 실무 사용 | 표준/레거시 Function Module에서 여전히 발견 |
| 신규 설계 | 가능하면 명확한 Table Type 파라미터와 IMPORTING/EXPORTING/CHANGING 설계를 검토 |

### 11.2 초급자에게 필요한 이해

초급자는 TABLES 파라미터를 다음처럼 이해하면 된다.

```text
TABLES는 Function Module에서 Internal Table을 전달하기 위한 오래된 방식이다.
표준 Function Module이나 오래된 Z Function Module을 호출할 때 볼 수 있다.
호출 전후 Internal Table이 어떻게 변하는지 확인해야 한다.
```

### 11.3 지나친 확장 금지

이번 단계에서는 Internal Table 자체의 종류, Header Line, Standard/Sorted/Hashed Table, Deep Structure를 깊게 다루지 않는다.  
Internal Table의 본격 학습은 후속 Section에서 진행한다.

## 12. EXCEPTIONS와 sy-subrc

Function Module 호출에서는 `EXCEPTIONS`를 통해 오류 상황을 숫자로 매핑하고, 호출 후 `sy-subrc`를 확인하는 방식이 자주 사용된다.

### 12.1 기본 구조

```abap
CALL FUNCTION 'FUNCTION_NAME'
  EXPORTING
    iv_value = gv_value
  EXCEPTIONS
    not_found = 1
    no_auth   = 2
    OTHERS    = 3.

CASE sy-subrc.
  WHEN 0.
    WRITE: / 'Success'.
  WHEN 1.
    WRITE: / 'Not found'.
  WHEN 2.
    WRITE: / 'No authorization'.
  WHEN OTHERS.
    WRITE: / 'Unexpected error:', sy-subrc.
ENDCASE.
```

### 12.2 실무 기준

Function Module 호출 후 `sy-subrc`를 확인하지 않으면 다음 문제가 생길 수 있다.

| 문제 | 설명 |
|---|---|
| 오류 무시 | Function Module이 실패했는데도 정상처럼 후속 처리 |
| 빈 결과 오해 | 데이터가 없는 것인지 오류인지 구분 불가 |
| Short Dump 위험 | 실패 후 초기값이나 잘못된 값으로 후속 로직 실행 |
| 운영 분석 어려움 | 오류 상황을 메시지나 로그로 남기지 않음 |

초급자는 다음 원칙을 기억한다.

```text
EXCEPTIONS가 있는 CALL FUNCTION 뒤에는 sy-subrc를 확인한다.
```

## 13. CALL FUNCTION 자동 생성 패턴

SE37이나 ABAP Editor에서는 Function Module 호출 템플릿을 자동으로 가져오는 기능을 사용할 수 있다.

시스템과 도구에 따라 방식은 다를 수 있지만, 일반적으로 다음 흐름을 사용한다.

```text
ABAP Editor 또는 SE80/SE38
→ Pattern 또는 Insert Statement 기능
→ CALL FUNCTION 선택
→ Function Module 이름 입력
→ Interface 기반 호출 템플릿 생성
```

ADT에서도 코드 완성, 템플릿, Quick Fix 방식으로 호출 구조를 보조받을 수 있다.

초급자에게 중요한 점은 자동 생성된 코드를 그대로 믿지 않는 것이다.  
자동 생성은 문법 골격을 만들어줄 뿐이고, 어떤 파라미터를 실제로 사용할지, 어떤 예외를 어떻게 처리할지는 개발자가 판단해야 한다.

## 15. 정상 흐름과 오류 흐름

### 15.1 정상 흐름

```text
SE37에서 Function Module 확인
→ Interface 파라미터 확인
→ 호출 프로그램 변수 선언
→ CALL FUNCTION 작성
→ EXPORTING으로 입력 전달
→ IMPORTING으로 결과 수신
→ EXCEPTIONS가 있으면 sy-subrc 확인
→ WRITE로 결과 출력
```

### 15.2 오류 흐름 1: Function Module 이름 오타

#### 상황

```abap
CALL FUNCTION 'CONVERSION_EXIT_ALPA_INPUT'.
```

#### 원인

Function Module 이름에 오타가 있다.

#### 해결

SE37에서 정확한 이름을 복사하거나 Pattern 기능을 사용한다.

---

### 15.3 오류 흐름 2: 파라미터 이름 오타

#### 상황

```abap
CALL FUNCTION 'CONVERSION_EXIT_ALPHA_INPUT'
  EXPORTING
    inpt = gv_external.
```

#### 원인

`input`이 아니라 `inpt`로 잘못 작성했다.

#### 해결

SE37 Interface의 정확한 Parameter Name을 확인한다.

---

### 15.4 오류 흐름 3: EXPORTING / IMPORTING 방향 혼동

#### 상황

입력값을 `IMPORTING`에 작성하거나, 결과값을 `EXPORTING`에 작성한다.

#### 원인

CALL FUNCTION의 방향성을 호출자 관점으로 이해하지 못했다.

#### 해결

다음 문장을 기준으로 다시 작성한다.

```text
EXPORTING = 내가 Function Module에 보내는 값
IMPORTING = 내가 Function Module에서 받는 값
```

---

### 15.5 오류 흐름 4: sy-subrc 미확인

#### 상황

Function Module이 실패했는데도 후속 로직이 정상처럼 실행된다.

#### 원인

EXCEPTIONS가 있는데도 호출 후 `sy-subrc`를 확인하지 않았다.

#### 해결

`IF`, `CASE`를 사용해 `sy-subrc` 값별 처리를 작성한다.

---

### 15.6 오류 흐름 5: 권한 또는 실행 환경 문제

#### 상황

Function Module 자체는 존재하지만 실행 중 권한 오류나 환경 오류가 발생한다.

#### 원인

Function Module이 내부적으로 특정 권한, Customizing, 데이터, GUI 환경, RFC 연결 등을 필요로 할 수 있다.

#### 해결

Documentation, Source Code, Exception, 시스템 메시지를 확인하고 운영 기준에 따라 처리한다.

## 16. 실무 적용 기준

### 16.1 Function Module을 호출하기 전에 확인할 것

| 확인 항목 | 질문 |
|---|---|
| Function Module 목적 | 이 함수가 정확히 무엇을 하는가? |
| 릴리스/사용 적합성 | 업무에서 사용 가능한 공개 API인가? |
| 파라미터 의미 | 각 파라미터의 업무 의미를 이해했는가? |
| 예외 처리 | 실패 시 어떤 예외가 발생하는가? |
| 권한 | 내부적으로 권한 체크가 있는가? |
| 데이터 변경 | DB를 변경하는 함수인가, 조회만 하는 함수인가? |
| Commit 필요성 | 호출 후 `COMMIT WORK`가 필요한 유형인가? |
| 운영 영향 | 대량 호출 시 성능 문제가 없는가? |

### 16.2 조회성 Function Module과 변경성 Function Module

Function Module은 단순 계산이나 변환만 수행할 수도 있고, 실제 업무 데이터를 변경할 수도 있다.

| 유형 | 예시 | 주의 |
|---|---|---|
| 변환/검증 | Alpha 변환, 날짜 검증 | 비교적 안전하지만 결과 확인 필요 |
| 조회 | 마스터 데이터 조회 | 권한과 데이터 존재 여부 확인 |
| 변경 | 생성, 수정, 삭제, 상태 변경 | 트랜잭션 처리와 Commit/Rollback 검토 |
| 원격 호출 | RFC/BAPI | 통신 오류, 시스템 연결, 인증 검토 |

이번 모듈에서는 조회성 또는 변환성 Function Module 위주로 실습한다.  
변경성 Function Module과 BAPI Transaction 처리는 Track 2 실무 영역에서 더 적절하게 다룬다.

### 16.3 신규 개발에서의 위치

새로운 업무 로직을 설계할 때 Function Module이 항상 최선은 아니다.  
S/4HANA 환경에서는 Class 기반 설계, RAP, CDS, Behavior 구현 등 현대적 구조가 더 적절할 수 있다.

하지만 Function Module은 다음 상황에서 여전히 중요하다.

```text
표준 Function Module 또는 BAPI 호출
기존 Z Function Module 유지보수
RFC 기반 연동 분석
Legacy Report 개선
운영 오류 원인 분석
```

따라서 초급 단계에서는 “무조건 새 Function Module을 만들자”가 아니라, “기존 Function Module을 정확히 호출하고 오류를 처리할 수 있자”가 목표이다.

## 17. 안티패턴

### 17.1 SE37 확인 없이 인터넷 예제만 복사

문제:

```text
시스템마다 Function Module의 사용 가능 여부나 파라미터 상세가 다를 수 있다.
```

해결:

```text
항상 SE37에서 현재 시스템의 Interface와 Documentation을 확인한다.
```

### 17.2 sy-subrc를 확인하지 않음

문제:

```text
오류가 발생해도 후속 로직이 계속 실행되어 잘못된 결과를 만든다.
```

해결:

```text
EXCEPTIONS를 작성했다면 호출 직후 sy-subrc를 처리한다.
```

### 17.3 모든 로직을 Function Module에 의존

문제:

```text
간단한 로직도 외부 Function Module 호출로 분산되어 프로그램 이해가 어려워진다.
```

해결:

```text
단순 내부 처리라면 FORM, Method, Local Class 등 적절한 모듈화 방식을 선택한다.
```

### 17.4 변경성 Function Module을 테스트 시스템 감각으로 운영에서 호출

문제:

```text
실제 업무 데이터가 생성, 변경, 삭제될 수 있다.
```

해결:

```text
변경성 Function Module은 Documentation, 권한, 테스트 데이터, Commit/Rollback, 운영 승인 절차를 반드시 확인한다.
```

### 17.5 TABLES 파라미터를 현대적 설계로 오해

문제:

```text
TABLES는 레거시 성격이 강한 파라미터 방식이며 신규 설계에서는 더 명확한 방식이 선호될 수 있다.
```

해결:

```text
기존 Function Module 호출 시 이해는 하되, 신규 설계에서는 Class Method나 명시적 Table Type 파라미터 설계를 검토한다.
```

## 18. 강사용 설명 포인트

강사는 이번 모듈에서 다음 포인트를 강조하면 좋다.

### 18.1 EXPORTING / IMPORTING 방향성을 반복 확인

초급자는 반드시 다음 문장을 말로 설명할 수 있어야 한다.

```text
EXPORTING은 내가 함수에게 보내는 값,
IMPORTING은 내가 함수에게서 받는 값이다.
```

### 18.2 SE37 Interface 읽기 훈련

코드를 먼저 작성하기보다 SE37에서 다음을 먼저 보게 한다.

```text
Import 파라미터가 무엇인가?
Export 파라미터가 무엇인가?
Optional 파라미터는 무엇인가?
Exception은 무엇인가?
```

### 18.3 Function Module은 실무 레거시와 표준 API 이해의 관문

현대 ABAP에서 Class가 중요해졌다고 해서 Function Module을 무시하면 안 된다.  
SAP 표준, BAPI, RFC, 고객 기존 프로그램에서 Function Module은 여전히 자주 등장한다.

### 18.4 신규 설계 기준은 뒤에서 다시 판단

이 모듈에서는 Function Module 호출을 학습하되, 신규 개발 설계에서는 Local Class/Global Class와 비교해야 한다는 예고만 한다.  
구체적인 선택 기준은 `THEORY-05-M06`에서 다시 정리한다.

## 20. 평가 문제

### 20.1 객관식

#### Q1. `CALL FUNCTION`의 `EXPORTING` 영역에 대한 설명으로 가장 적절한 것은?

A. Function Module에서 호출 프로그램으로 결과를 돌려주는 영역이다.  
B. 호출 프로그램에서 Function Module로 입력값을 전달하는 영역이다.  
C. Internal Table만 전달할 수 있는 영역이다.  
D. 예외 상황을 숫자로 매핑하는 영역이다.

**정답:** B

#### Q2. Function Module의 Interface를 확인하는 대표 트랜잭션은?

A. SE11  
B. SE16N  
C. SE37

### 20.2 서술형

#### Q1. `CALL FUNCTION`에서 `EXPORTING`과 `IMPORTING`의 방향성을 설명하시오.

**모범 답안:**  
`EXPORTING`은 호출 프로그램이 Function Module로 입력값을 보내는 영역이다. `IMPORTING`은 Function Module의 처리 결과를 호출 프로그램이 받아오는 영역이다. 두 용어는 호출 프로그램 관점으로 이해해야 한다.

#### Q2. Function Module 호출 전에 SE37에서 확인해야 할 항목을 세 가지 이상 쓰시오.

**모범 답안:**  
Import 파라미터, Export 파라미터, Changing 파라미터, Tables 파라미터, Exceptions, Optional 여부, 파라미터 타입, Documentation, Test 실행 가능 여부 등을 확인해야 한다.

#### Q3. `sy-subrc`를 확인하지 않으면 어떤 문제가 발생할 수 있는가?

**모범 답안:**  
Function Module이 실패했는데도 프로그램이 정상 처리된 것처럼 후속 로직을 실행할 수 있다. 이 경우 잘못된 데이터 출력, 초기값 사용, Short Dump, 운영 오류 분석 어려움이 발생할 수 있다.

## 23. 핵심 요약

이번 모듈의 핵심은 다음이다.

```text
Function Module은 SAP Repository에 등록된 재사용 가능한 처리 블록이다.
CALL FUNCTION은 Function Module을 호출하는 ABAP 구문이다.
EXPORTING은 호출 프로그램에서 Function Module로 값을 보낸다.
IMPORTING은 Function Module에서 호출 프로그램으로 결과를 받아온다.
CHANGING은 값을 주고받으며 변경한다.
TABLES는 Internal Table 전달에 사용되는 고전적 파라미터 방식이다.
EXCEPTIONS가 있으면 sy-subrc를 확인해야 한다.
SE37에서 Interface를 확인한 뒤 호출 코드를 작성해야 한다.
```

## 24. 후속 모듈 연결

이번 모듈에서는 Function Module을 호출하는 기본 구조를 배웠다.  
다음 모듈인 `THEORY-05-M04 — Local Class 정의와 Method 호출`에서는 같은 프로그램 안에서 Class를 정의하고 Method를 호출하는 구조를 학습한다.

연결 관계는 다음과 같다.

```text
THEORY-05-M01 FORM / PERFORM 기본 호출
→ THEORY-05-M02 USING / CHANGING 파라미터
→ THEORY-05-M03 CALL FUNCTION 기본 구조
→ THEORY-05-M04 Local Class 정의와 Method 호출
→ THEORY-05-M05 Global Class 호출 기초
→ THEORY-05-M06 Subroutine / Function / Class 선택 기준
```

이번 단계에서 중요한 연결 포인트는 다음이다.

```text
FORM은 프로그램 내부 Subroutine이다.
Function Module은 Repository에 등록된 재사용 처리 블록이다.
Class Method는 객체지향 기반의 메서드 호출 구조이다.
```

이 세 가지를 비교할 수 있어야 다음 모듈의 Local Class와 Method 호출을 자연스럽게 이해할 수 있다.
