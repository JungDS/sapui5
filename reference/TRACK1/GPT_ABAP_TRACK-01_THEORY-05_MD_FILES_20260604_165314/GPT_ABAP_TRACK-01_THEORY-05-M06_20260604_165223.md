## 3. 세 가지 모듈화 수단의 큰 그림

ABAP에서는 오래전부터 여러 방식으로 코드를 나누어 왔다.  
대표적으로 다음 세 가지가 있다.

| 방식 | 대표 문법 | 주 사용 위치 | 현대 ABAP 관점 |
|---|---|---|---|
| Subroutine | `FORM ... ENDFORM`, `PERFORM` | Classic Report 내부 | 기존 코드 이해와 제한적 유지보수에 필요 |
| Function Module | `CALL FUNCTION` | Function Group, 표준 API, RFC/BAPI | 표준 SAP와 레거시 통합에서 여전히 중요 |
| Class/Method | `CLASS`, `METHODS`, `CALL METHOD` 또는 메서드 호출 | Local/Global Class | 신규 개발과 구조화된 설계의 기본 방향 |

이 셋은 모두 “코드를 나눈다”는 공통점을 가진다.  
하지만 **코드를 나누는 위치**, **재사용 범위**, **테스트 가능성**, **확장성**, **표준 SAP와의 연결 방식**이 다르다.

## 4. 왜 선택 기준이 필요한가?

초급자는 보통 다음 질문을 한다.

```text
FORM도 되고 Function Module도 되고 Class도 되는데, 무엇을 써야 하나요?
```

이 질문에 대한 답은 단순하지 않다.  
기준 없이 선택하면 다음 문제가 발생한다.

| 문제 | 설명 |
|---|---|
| 코드 스타일 혼재 | 같은 프로그램 안에 FORM, Function Module, Class가 무질서하게 섞인다. |
| 테스트 어려움 | 로직이 화면, DB, 전역 변수에 강하게 묶여 Unit Test가 어렵다. |
| 재사용성 저하 | 다른 프로그램에서 사용해야 할 로직이 Report 내부 FORM에 갇힌다. |
| 영향 분석 어려움 | 전역 데이터와 CHANGING 파라미터가 많아져 변경 영향이 커진다. |
| 현대 개발 흐름과 단절 | RAP, ABAP Cloud, Clean Core 방향과 맞지 않는 구조가 될 수 있다. |

따라서 모듈화 수단을 선택할 때는 “익숙한 문법”이 아니라 “로직의 성격”을 기준으로 판단해야 한다.

## 5. Subroutine 선택 기준

### 5.1 Subroutine의 역할

Subroutine은 `FORM ... ENDFORM`으로 정의하고 `PERFORM`으로 호출하는 전통적인 ABAP 모듈화 방식이다.

예시:

```abap
REPORT zgpt_modular_form.

DATA gv_text TYPE string VALUE 'Hello ABAP'.

PERFORM display_text USING gv_text.

FORM display_text USING iv_text TYPE string.
  WRITE: / iv_text.
ENDFORM.
```

Subroutine은 Classic Report에서 코드를 논리적으로 나누는 데 자주 사용되었다.

### 5.2 Subroutine을 사용해도 되는 경우

신규 개발에서 무조건 FORM을 금지한다고 이해하면 곤란하다.  
다만 사용 범위를 좁게 보는 것이 좋다.

| 사용 가능 상황 | 설명 |
|---|---|
| 기존 Report 유지보수 | 이미 FORM 기반으로 작성된 프로그램의 일관성을 유지해야 할 때 |
| 짧은 교육용 예제 | 초급자가 모듈화 개념을 빠르게 체험할 때 |
| 프로그램 내부 전용 로직 | 다른 프로그램에서 재사용할 필요가 거의 없을 때 |
| Legacy 코드 분석 | 표준/고객 기존 코드 이해가 목적일 때 |

### 5.3 Subroutine을 피해야 하는 경우

| 피해야 하는 상황 | 이유 |
|---|---|
| 신규 업무 로직의 핵심 서비스 | 테스트와 재사용성이 떨어질 수 있다. |
| 여러 프로그램에서 재사용할 로직 | Report 내부 FORM은 외부 재사용에 부적합하다. |
| 상태 관리가 필요한 복잡 로직 | Class가 더 적합하다. |
| 예외 처리가 중요한 로직 | Method와 Exception 설계가 더 명확하다. |
| RAP, ABAP Cloud 지향 개발 | Class 기반 설계가 기본 방향이다. |

### 5.4 Subroutine의 핵심 한계

Subroutine의 가장 큰 한계는 “프로그램 내부 절차 조각”이라는 성격이 강하다는 점이다.

```text
FORM은 코드를 나누는 데는 도움이 되지만,
재사용 가능한 설계 단위로는 한계가 있다.
```

특히 다음과 같은 문제가 생기기 쉽다.

- 전역 변수에 의존하는 FORM 증가
- `USING`, `CHANGING`의 의미 혼재
- 호출 순서에 따라 결과가 달라지는 로직
- 테스트 코드 작성 어려움
- 다른 프로그램에서 직접 재사용하기 어려움

## 6. Function Module 선택 기준

### 6.1 Function Module의 역할

Function Module은 Function Group에 포함되는 Repository Object이다.  
SAP 표준 API, BAPI, RFC, 기존 고객 시스템에서 매우 많이 사용된다.

예시:

```abap
DATA lv_result TYPE string.

CALL FUNCTION 'Z_GPT_TEXT_TO_UPPER'
  EXPORTING
    iv_text   = 'hello'
  IMPORTING
    ev_result = lv_result
  EXCEPTIONS
    OTHERS    = 1.

IF sy-subrc = 0.
  WRITE: / lv_result.
ENDIF.
```

### 6.2 Function Module을 사용해야 하는 경우

| 사용 상황 | 설명 |
|---|---|
| SAP 표준 Function Module 호출 | 표준 기능을 사용해야 할 때 |
| BAPI 호출 | 외부 또는 표준 업무 API 사용 시 |
| RFC 통신 | 외부 시스템과 원격 호출이 필요할 때 |
| 기존 고객 Function Module 재사용 | 이미 운영 중인 안정화된 로직을 호출할 때 |
| Function Group 기반 레거시 구조 유지 | 기존 설계 방식과 호환해야 할 때 |

### 6.3 Function Module 신규 작성 시 고려점

Function Module은 여전히 중요하지만, 신규 개발에서 무조건 선호할 대상은 아니다.

| 고려 항목 | 설명 |
|---|---|
| Function Group 의존성 | Function Module은 Function Group에 속한다. |
| 전역 데이터 위험 | Function Group의 Global Data를 과도하게 사용하면 상태 의존성이 커진다. |
| 테스트 가능성 | Class Method보다 Unit Test 구조화가 어려울 수 있다. |
| 현대 개발 방향 | 신규 비즈니스 로직은 Class 중심 설계가 더 적합한 경우가 많다. |
| 원격 호출 필요성 | RFC가 필요하다면 Function Module이 여전히 중요한 선택지다. |

### 6.4 Function Module을 선택하는 실무적 이유

Function Module을 선택하는 가장 강한 이유는 보통 “SAP 표준 또는 기존 시스템과의 접점”이다.

```text
BAPI를 호출해야 한다.
RFC Function Module을 사용해야 한다.
기존 고객 시스템의 Function Module을 그대로 재사용해야 한다.
표준 Function Module이 이미 안정적인 기능을 제공한다.
```

반대로 단순히 “여러 곳에서 쓸 수 있으니까”라는 이유만으로 신규 Function Module을 만드는 것은 신중해야 한다.  
그런 경우에는 Global Class의 Public Method가 더 적합할 수 있다.

## 7. Class / Method 선택 기준

### 7.1 Class/Method의 역할

Class는 데이터와 행위를 하나의 단위로 묶는 객체지향 개발의 기본 단위이다.  
Method는 Class 안에서 실제 동작을 수행하는 절차이다.

예시:

```abap
CLASS lcl_text_helper DEFINITION.
  PUBLIC SECTION.
    METHODS to_upper
      IMPORTING iv_text TYPE string
      RETURNING VALUE(rv_text) TYPE string.
ENDCLASS.

CLASS lcl_text_helper IMPLEMENTATION.
  METHOD to_upper.
    rv_text = to_upper( iv_text ).
  ENDMETHOD.
ENDCLASS.

START-OF-SELECTION.
  DATA(lo_helper) = NEW lcl_text_helper( ).
  DATA(lv_result) = lo_helper->to_upper( 'hello' ).
  WRITE: / lv_result.
```

### 7.2 Class/Method를 우선 고려할 상황

| 상황 | 이유 |
|---|---|
| 신규 업무 로직 개발 | 구조화, 테스트, 재사용에 유리하다. |
| 여러 프로그램에서 재사용할 로직 | Global Class로 공개 가능하다. |
| 상태와 행위를 함께 관리해야 함 | 객체 단위 설계가 적합하다. |
| ABAP Unit 테스트 필요 | Test Class와 결합하기 좋다. |
| RAP/CDS/Service 지향 개발 | Class 기반 설계와 자연스럽게 연결된다. |
| Clean ABAP 지향 | 명확한 책임 분리와 작은 Method 설계에 유리하다. |

### 7.3 Local Class와 Global Class 선택

Class를 쓴다고 해서 항상 Global Class를 만들어야 하는 것은 아니다.

| 구분 | Local Class | Global Class |
|---|---|---|
| 정의 위치 | 특정 프로그램 내부 | Repository Object |
| 재사용 범위 | 해당 프로그램 내부 | 여러 프로그램에서 재사용 가능 |
| 적합 상황 | 프로그램 내부 로직 정리 | 공통 서비스, 유틸리티, 업무 로직 |
| 관리 수준 | 비교적 가벼움 | 패키지, Transport, API 설계 필요 |
| 테스트 | 가능 | 더 체계적으로 관리 가능 |

판단 기준은 다음이다.

```text
해당 프로그램에서만 쓰면 Local Class
여러 곳에서 써야 하면 Global Class
```

### 7.4 Static Method와 Instance Method 선택

Global Class를 사용할 때 초급자가 자주 고민하는 것이 Static Method와 Instance Method이다.

| 구분 | Static Method | Instance Method |
|---|---|---|
| 호출 방식 | `zcl_xxx=>method( )` | `lo_obj->method( )` |
| 객체 생성 | 필요 없음 | 필요함 |
| 상태 보관 | 부적합 | 적합 |
| 적합 예 | 순수 계산, 단순 변환, 유틸리티 | 상태가 있는 서비스, 의존성 주입, 테스트 대상 |
| 주의점 | 남용하면 절차형 유틸리티 모음이 됨 | 설계가 과하면 복잡해질 수 있음 |

초급 단계에서는 다음처럼 판단하면 된다.

```text
입력값만 받아 결과를 돌려주는 단순 유틸리티라면 Static Method 가능
객체의 상태나 의존성이 중요하다면 Instance Method 고려
```

## 8. 세 방식의 비교표

| 기준 | Subroutine | Function Module | Class/Method |
|---|---|---|---|
| 대표 문법 | FORM / PERFORM | CALL FUNCTION | METHOD 호출 |
| 주 사용 맥락 | Classic Report 내부 | 표준 API, BAPI, RFC, 레거시 | 신규 개발, OO 설계 |
| 재사용 범위 | 낮음 | 중간~높음 | 높음 |
| 테스트 가능성 | 낮음 | 중간 | 높음 |
| 전역 상태 위험 | 높음 | Function Group 사용 방식에 따라 높음 | 설계에 따라 낮출 수 있음 |
| 현대 ABAP 적합성 | 낮음 | 통합/표준 호출 측면에서 중요 | 높음 |
| 초급 학습 필요성 | 기존 코드 이해에 필요 | 표준 기능 호출에 필요 | 앞으로의 개발 방향에 필요 |
| 신규 개발 권장도 | 낮음 | 목적이 명확할 때만 | 높음 |

## 9. 선택 의사결정 흐름

다음 질문 순서로 판단하면 실무에서 도움이 된다.

```text
1. SAP 표준 BAPI/RFC/Function Module을 호출해야 하는가?
   → 예: CALL FUNCTION 사용
   → 아니오: 다음 질문

2. 기존 프로그램이 FORM 기반이고, 작은 유지보수인가?
   → 예: 기존 스타일에 맞춰 FORM 유지 가능
   → 아니오: 다음 질문

3. 로직이 해당 프로그램 안에서만 쓰이는가?
   → 예: Local Class 우선 고려
   → 아니오: 다음 질문

4. 여러 프로그램에서 재사용되어야 하는가?
   → 예: Global Class 우선 고려
   → 아니오: Local Class 또는 작은 Method 고려

5. 원격 호출이나 외부 시스템 연계가 필요한가?
   → 예: RFC Function Module 또는 적절한 서비스 방식 검토
   → 아니오: Class/Method 우선 고려
```

이를 더 간단히 줄이면 다음과 같다.

```text
표준 API/BAPI/RFC → Function Module
기존 Report 내부 유지보수 → FORM 이해 및 제한적 사용
신규 로직 / 재사용 / 테스트 / 유지보수 → Class/Method 우선
```

## 10. 같은 요구사항을 세 방식으로 비교하기

### 10.1 요구사항

입력받은 금액에 세율을 적용하여 세액을 계산한다.

```text
입력: 금액 10000, 세율 10%
출력: 세액 1000
```

### 10.2 FORM 방식

```abap
REPORT zgpt_tax_form.

DATA: gv_amount TYPE p LENGTH 10 DECIMALS 2 VALUE '10000.00',
      gv_rate   TYPE p LENGTH 5  DECIMALS 2 VALUE '10.00',
      gv_tax    TYPE p LENGTH 10 DECIMALS 2.

PERFORM calc_tax USING gv_amount gv_rate CHANGING gv_tax.

WRITE: / gv_tax.

FORM calc_tax
  USING    iv_amount TYPE p
           iv_rate   TYPE p
  CHANGING cv_tax    TYPE p.

  cv_tax = iv_amount * iv_rate / 100.

ENDFORM.
```

이 방식은 한 Report 내부에서는 간단하다.  
하지만 여러 프로그램에서 같은 세금 계산 로직을 써야 한다면 적합하지 않다.

### 10.3 Function Module 방식

```abap
CALL FUNCTION 'Z_GPT_CALC_TAX'
  EXPORTING
    iv_amount = lv_amount
    iv_rate   = lv_rate
  IMPORTING
    ev_tax    = lv_tax
  EXCEPTIONS
    OTHERS    = 1.

IF sy-subrc <> 0.
  MESSAGE 'Tax calculation failed' TYPE 'E'.
ENDIF.
```

Function Module은 표준화된 인터페이스와 호출 형태를 제공한다.  
RFC나 기존 Function Group 구조가 필요하다면 적합할 수 있다.  
하지만 단순 신규 로직이라면 Class Method가 더 적절할 수 있다.

### 10.4 Class Method 방식

```abap
CLASS zcl_gpt_tax_calculator DEFINITION PUBLIC CREATE PUBLIC.
  PUBLIC SECTION.
    METHODS calculate_tax
      IMPORTING
        iv_amount     TYPE p
        iv_rate       TYPE p
      RETURNING
        VALUE(rv_tax) TYPE p.
ENDCLASS.

CLASS zcl_gpt_tax_calculator IMPLEMENTATION.
  METHOD calculate_tax.
    rv_tax = iv_amount * iv_rate / 100.
  ENDMETHOD.
ENDCLASS.
```

호출 예시는 다음과 같다.

```abap
DATA(lo_calculator) = NEW zcl_gpt_tax_calculator( ).
DATA(lv_tax) = lo_calculator->calculate_tax(
  iv_amount = lv_amount
  iv_rate   = lv_rate ).
```

Class Method 방식은 로직의 책임을 명확히 분리하고, 후속 ABAP Unit 테스트와 확장에 유리하다.

## 11. 실무 기준: 신규 개발에서는 무엇을 우선할까?

S/4HANA 기준의 신규 개발에서는 일반적으로 Class/Method 중심 설계를 우선 고려하는 것이 좋다.

이유는 다음과 같다.

| 이유 | 설명 |
|---|---|
| 책임 분리 | Class 단위로 역할을 나눌 수 있다. |
| 테스트 가능성 | ABAP Unit과 연결하기 쉽다. |
| 재사용성 | Global Class를 여러 프로그램에서 호출할 수 있다. |
| 유지보수성 | Method 단위로 작은 로직을 관리할 수 있다. |
| 현대 개발 흐름 | RAP, CDS Behavior, Service 구현과 연결된다. |
| Clean ABAP | 작고 명확한 Method 중심 설계와 잘 맞는다. |

하지만 실무에서는 기존 자산을 무시할 수 없다.  
따라서 판단은 다음처럼 균형 있게 해야 한다.

```text
신규 핵심 로직: Class/Method 우선
기존 Report 유지보수: 기존 FORM 구조와 일관성 고려
표준 SAP API 호출: Function Module/BAPI 사용
외부 RFC 연계: Function Module 또는 최신 연계 방식 검토
```

## 12. 유지보수 관점의 선택 기준

### 12.1 기존 FORM 기반 프로그램

기존 프로그램이 수천 줄의 Report이고 FORM이 이미 수십 개 있다면, 작은 수정 하나 때문에 전체를 Class 기반으로 바꾸는 것은 위험할 수 있다.

이때는 다음처럼 접근한다.

```text
작은 결함 수정: 기존 FORM 구조 유지
새로운 큰 기능 추가: 별도 Class로 분리 검토
공통화 가능한 로직 발견: Global Class 추출 검토
장기 리팩토링 계획이 있음: 단계적으로 FORM 의존도 축소
```

### 12.2 기존 Function Module 기반 시스템

Function Module 기반 고객 시스템에서는 이미 많은 프로그램이 특정 Function Module을 호출하고 있을 수 있다.

이 경우 무조건 Class로 대체하면 영향 범위가 커진다.

권장 접근:

```text
기존 호출자가 많다면 Function Module 인터페이스는 유지한다.
내부 구현만 Class로 위임할 수 있다.
신규 호출자는 가능하면 Class를 직접 사용하게 설계한다.
```

예시 구조:

```abap
FUNCTION z_gpt_calculate_tax.
  DATA(lo_calculator) = NEW zcl_gpt_tax_calculator( ).

  ev_tax = lo_calculator->calculate_tax(
    iv_amount = iv_amount
    iv_rate   = iv_rate ).
ENDFUNCTION.
```

이 방식은 레거시 호환성과 신규 구조 개선을 동시에 고려할 수 있다.

## 13. 테스트 가능성 관점

좋은 모듈화는 테스트하기 쉬운 구조를 만든다.

| 방식 | 테스트 관점 |
|---|---|
| FORM | 전역 변수와 Report 흐름에 묶이면 테스트가 어렵다. |
| Function Module | 호출 테스트는 가능하지만 Function Group 상태 의존성에 주의해야 한다. |
| Class/Method | ABAP Unit Test Class와 연결하기 가장 좋다. |

초급자는 아직 ABAP Unit을 깊게 배우지 않았더라도 다음 감각을 가져야 한다.

```text
입력과 출력이 명확한 작은 Method는 테스트하기 쉽다.
전역 변수에 의존하는 큰 FORM은 테스트하기 어렵다.
```

예를 들어 아래 Method는 테스트하기 쉽다.

```abap
METHOD calculate_tax.
  rv_tax = iv_amount * iv_rate / 100.
ENDMETHOD.
```

입력값 `iv_amount`, `iv_rate`만 주면 결과 `rv_tax`를 검증할 수 있기 때문이다.

## 14. 가독성 관점

모듈화 방식은 가독성에도 영향을 준다.

### 14.1 나쁜 구조

```abap
PERFORM process_data.

FORM process_data.
  PERFORM get_data.
  PERFORM modify_data.
  PERFORM display_data.
ENDFORM.
```

이 구조 자체가 항상 나쁜 것은 아니다.  
하지만 각 FORM이 전역 변수에 의존하고 내부에서 여러 부작용을 일으킨다면 읽기 어렵다.

### 14.2 더 나은 구조

```abap
DATA(lo_app) = NEW zcl_gpt_sales_report_app( ).
lo_app->run( ).
```

Class 내부에서 책임을 나누면 프로그램의 진입점이 간결해지고, 각 Method의 역할을 분리하기 쉽다.

예:

```abap
METHOD run.
  DATA(lt_data) = read_data( ).
  DATA(lt_result) = calculate_result( lt_data ).
  display_result( lt_result ).
ENDMETHOD.
```

이 구조는 다음 장점이 있다.

- 입력과 출력의 흐름이 명확하다.
- 전역 데이터 의존을 줄일 수 있다.
- Method 이름으로 의도가 드러난다.
- 후속 테스트와 리팩토링이 쉽다.

## 15. 재사용성 관점

### 15.1 FORM의 재사용성

FORM은 기본적으로 해당 프로그램 내부에서 쓰기 쉽다.  
다른 프로그램에서 재사용하려면 Include를 활용하는 방식이 있었지만, 현대적인 설계 관점에서는 신중해야 한다.

### 15.2 Function Module의 재사용성

Function Module은 Repository Object로 여러 프로그램에서 호출 가능하다.  
또한 RFC-enabled로 만들면 외부 시스템에서도 호출 가능하다.

하지만 재사용성이 높다는 이유만으로 모든 공통 로직을 Function Module로 만들면 Function Group이 비대해질 수 있다.

### 15.3 Class/Method의 재사용성

Global Class는 현대 ABAP에서 재사용 가능한 로직을 담기에 적합하다.

예:

```text
ZCL_GPT_TAX_CALCULATOR
ZCL_GPT_DATE_HELPER
ZCL_GPT_FLIGHT_SERVICE
ZCL_GPT_ALV_BUILDER
```

Class 이름과 Method 이름이 명확하면 어떤 책임을 가진 객체인지 쉽게 알 수 있다.

## 16. 권한과 운영 안정성 관점

모듈화 방식 자체가 권한 검사를 자동으로 해결해주지는 않는다.  
하지만 구조에 따라 권한 검사를 어디에 둘지 결정하기 쉬워질 수 있다.

| 방식 | 권한/운영 관점 |
|---|---|
| FORM | Report 내부 흐름에 섞이기 쉬움 |
| Function Module | API 경계에서 권한 검사를 넣기 쉬움 |
| Class/Method | Service Layer 또는 Application Layer로 역할 분리 가능 |

실무에서는 다음 원칙이 중요하다.

```text
DB 변경, 중요 데이터 조회, 외부 호출 로직은 권한과 오류 처리를 함께 고려해야 한다.
모듈화는 단순 코드 분리가 아니라 책임 경계를 정하는 일이다.
```

## 17. 선택 기준 요약표

| 상황 | 권장 선택 | 이유 |
|---|---|---|
| Classic Report 내부에서 작은 코드 블록 분리 | FORM 또는 Local Method | 기존 코드 스타일과 범위 고려 |
| 기존 FORM 기반 Report 유지보수 | FORM 유지 가능 | 불필요한 대규모 변경 방지 |
| 신규 Report의 주요 로직 | Local Class 또는 Global Class | 구조화와 테스트에 유리 |
| 여러 프로그램에서 재사용할 공통 로직 | Global Class | 책임 분리와 재사용성 |
| SAP 표준 BAPI 호출 | Function Module | 표준 API 형태 |
| RFC 원격 호출 | RFC Function Module 또는 적절한 서비스 방식 | 통신 요구사항 |
| 단순 계산 유틸리티 | Static Method 가능 | 상태가 필요 없을 수 있음 |
| 상태가 있는 업무 서비스 | Instance Method | 객체 상태와 의존성 관리 가능 |
| ABAP Unit 테스트 대상 | Class/Method | 테스트 구조화에 유리 |
| 레거시 Function Module 내부 개선 | FM 유지 + 내부 Class 위임 | 호환성과 구조 개선 동시 달성 |

## 18. 초급자용 판단 공식

다음 공식은 엄밀한 절대 규칙은 아니지만 초급자가 판단할 때 유용하다.

```text
읽어야 하는 기존 코드라면 FORM과 Function Module을 이해한다.
새로 만드는 핵심 로직이라면 Class/Method를 우선 고려한다.
표준 SAP API가 Function Module로 제공되면 CALL FUNCTION을 사용한다.
여러 곳에서 재사용해야 한다면 Global Class를 검토한다.
한 프로그램 내부 정리라면 Local Class 또는 작은 FORM을 검토한다.
```

더 짧게 정리하면 다음과 같다.

```text
Legacy 이해: FORM / Function Module
표준 API 호출: Function Module
신규 설계: Class / Method
```

## 19. 미니 실습: 선택 기준 적용하기

### 19.1 실습 목표

다음 요구사항을 보고 적절한 모듈화 방식을 선택한다.

### 19.2 시나리오 A — 기존 Report의 출력 헤더 정리

요구사항:

```text
기존 Z Report에서 WRITE 출력 전 제목과 실행일자를 출력하는 코드가 반복된다.
해당 프로그램 내부에서만 사용한다.
```

가능한 선택:

```text
FORM 또는 Local Method
```

초급 과정에서는 기존 Report가 FORM 기반이면 FORM으로 정리해도 된다.  
신규 구조라면 Local Class의 Method로 분리할 수도 있다.

### 19.3 시나리오 B — 여러 프로그램에서 사용하는 세금 계산

요구사항:

```text
세금 계산 로직이 여러 Report, Batch Program, ALV 프로그램에서 공통으로 필요하다.
향후 테스트도 필요하다.
```

권장 선택:

```text
Global Class / Instance 또는 Static Method
```

이유:

```text
여러 곳에서 재사용할 수 있고, ABAP Unit 테스트 대상으로 만들기 쉽다.
```

### 19.4 시나리오 C — SAP 표준 BAPI로 판매오더 생성

요구사항:

```text
SAP 표준 BAPI를 호출하여 판매오더를 생성해야 한다.
```

권장 선택:

```text
CALL FUNCTION
```

이유:

```text
BAPI는 Function Module 형태로 제공되는 경우가 많으므로 표준 인터페이스를 따라 호출한다.
```

### 19.5 시나리오 D — 기존 RFC 인터페이스 유지

요구사항:

```text
외부 시스템이 이미 Z RFC Function Module을 호출하고 있다.
내부 로직만 정리하고 싶다.
```

권장 선택:

```text
기존 RFC Function Module 유지 + 내부 구현을 Class로 위임
```

이유:

```text
외부 인터페이스 계약을 깨지 않으면서 내부 구조를 개선할 수 있다.
```

## 20. 자주 하는 실수

### 20.1 모든 것을 FORM으로 만든다

문제:

```text
Report가 수천 줄이 되고 FORM이 계속 늘어난다.
전역 변수 의존성이 커져 변경 영향이 불명확해진다.
```

개선:

```text
신규 핵심 로직은 Class로 분리한다.
전역 변수 대신 명확한 파라미터와 반환값을 사용한다.
```

### 20.2 모든 것을 Function Module로 만든다

문제:

```text
Function Group이 비대해지고, 전역 데이터와 상태 의존성이 커진다.
단순 공통 로직까지 Function Module로 만들어 관리가 복잡해진다.
```

개선:

```text
RFC/BAPI/표준 API 성격이 아니라면 Global Class를 우선 고려한다.
```

### 20.3 모든 Method를 Static으로 만든다

문제:

```text
객체지향 구조를 쓰는 것처럼 보이지만 실제로는 절차형 유틸리티 모음이 된다.
상태, 의존성, 테스트 대역을 다루기 어렵다.
```

개선:

```text
단순 계산은 Static Method도 가능하지만,
업무 서비스나 상태가 필요한 로직은 Instance Method를 고려한다.
```

### 20.4 선택 기준 없이 섞어 쓴다

문제:

```text
같은 프로그램 안에서 FORM, Function Module, Local Class가 기준 없이 섞인다.
읽는 사람이 구조를 예측할 수 없다.
```

개선:

```text
프로그램 내부 정리, 공통 로직, 표준 API 호출, 서비스 로직의 경계를 먼저 정한다.
```

## 21. 강사용 설명 포인트

강의에서는 “무엇이 더 최신인가?”보다 “어떤 상황에 무엇이 적절한가?”를 강조하는 것이 좋다.

추천 설명 흐름:

```text
1. FORM은 기존 Classic Report를 읽기 위해 반드시 알아야 한다.
2. Function Module은 SAP 표준 API와 레거시 통합에서 반드시 등장한다.
3. Class/Method는 신규 개발과 현대 ABAP 설계의 중심이다.
4. 선택 기준은 재사용성, 테스트 가능성, 유지보수성, 인터페이스 요구사항이다.
```

학습자에게 다음 질문을 던지면 좋다.

```text
이 로직은 다른 프로그램에서도 쓸까요?
이 로직은 테스트가 필요할까요?
이 로직은 외부 시스템에서 호출해야 하나요?
이 로직은 기존 Report 내부만 정리하면 되나요?
이 로직의 상태를 객체로 관리해야 하나요?
```

## 22. 평가 문제

### 22.1 객관식

#### Q1. 신규 개발에서 공통 업무 로직을 여러 프로그램에서 재사용하고 테스트 가능성도 높이고 싶을 때 가장 우선 고려할 방식은?

A. Report 내부 FORM  
B. Global Class의 Method  
C. WRITE 문 반복 작성  
D. 무조건 Include 복사  

정답: B

#### Q2. SAP 표준 BAPI를 호출해야 하는 상황에서 일반적으로 사용하는 문법은?

A. PERFORM  
B. CALL FUNCTION  
C. WRITE  
D. SELECT-OPTIONS  

정답: B

#### Q3. FORM 사용이 비교적 적절한 상황은?

A. 외부 시스템에서 원격 호출해야 하는 신규 API  
B. 여러 프로그램에서 재사용해야 하는 공통 업무 서비스  
C. 기존 FORM 기반 Report 내부의 작은 유지보수  
D. RAP Behavior 구현  

정답: C

### 22.2 서술형

#### Q1. Subroutine과 Class Method의 차이를 유지보수 관점에서 설명하시오.

모범 답안:

Subroutine은 주로 Report 내부 코드를 나누는 전통적 방식이며 전역 변수에 의존하기 쉬워 재사용성과 테스트 가능성이 낮아질 수 있다. Class Method는 책임을 Class 단위로 분리하고 입력과 출력을 명확히 설계할 수 있어 신규 개발, 재사용, 테스트, 유지보수에 더 적합하다.

#### Q2. 기존 RFC Function Module을 Class로 완전히 대체하지 않고 내부 구현만 Class로 위임할 수 있는 이유는 무엇인가?

모범 답안:

외부 시스템이 이미 RFC Function Module 인터페이스를 호출하고 있다면 인터페이스를 바꾸는 것은 영향 범위가 크다. 따라서 외부 호출 계약은 유지하고, Function Module 내부에서 Class Method를 호출하도록 변경하면 호환성을 유지하면서 내부 구조를 개선할 수 있다.

#### Q3. Static Method를 남용하면 어떤 문제가 생길 수 있는가?

모범 답안:

모든 로직을 Static Method로 만들면 객체지향 구조를 사용하는 것처럼 보이지만 실제로는 절차형 유틸리티 모음이 될 수 있다. 상태 관리, 의존성 대체, 테스트 구조화가 어려워질 수 있으므로 단순 변환이나 계산에는 적합하지만 복잡한 업무 서비스에는 Instance Method를 고려해야 한다.

## 24. Section 마무리

THEORY-05는 ABAP 모듈화의 기초를 다루었다.

이 Section의 핵심 흐름은 다음과 같다.

```text
FORM으로 코드 분리 개념을 경험한다.
USING / CHANGING으로 파라미터 전달을 이해한다.
CALL FUNCTION으로 표준 API 호출 형태를 익힌다.
Local Class로 프로그램 내부 객체화를 경험한다.
Global Class로 Repository 수준 재사용을 이해한다.
마지막으로 Subroutine / Function / Class 선택 기준을 정리한다.
```

이제 학습자는 단순히 긴 코드를 나누는 것이 아니라, 로직의 책임과 재사용 범위를 기준으로 구조를 선택할 수 있어야 한다.

다음 Section인 `THEORY-06 — Internal Table 기본 처리`에서는 모듈화된 코드 안에서 실제 데이터를 메모리 테이블로 다루는 방법을 학습하게 된다.

## 25. 핵심 요약

```text
FORM은 기존 Classic Report와 내부 코드 정리를 이해하기 위해 필요하다.
Function Module은 표준 SAP API, BAPI, RFC, 레거시 통합에서 중요하다.
Class/Method는 신규 개발, 재사용, 테스트, 유지보수 측면에서 우선 고려할 방식이다.
선택 기준은 최신 문법 여부가 아니라 로직의 성격과 운영 맥락이다.
재사용성과 테스트 가능성이 중요할수록 Class/Method 중심 설계가 적합하다.
기존 인터페이스는 유지하면서 내부 구현을 Class로 위임하는 점진적 개선도 가능하다.
```
