## 2. 왜 모듈화가 필요한가?

초급자가 ABAP을 처음 배울 때는 다음처럼 하나의 Report 안에 모든 코드를 순서대로 작성한다.

```abap
REPORT zgpt_mod_001.

WRITE: / '프로그램 시작'.
WRITE: / '입력값 확인'.
WRITE: / '데이터 조회'.
WRITE: / '결과 출력'.
WRITE: / '프로그램 종료'.
```

처음에는 이 방식도 충분하다. 코드가 짧기 때문이다.  
하지만 업무 프로그램은 금방 길어진다.

예를 들어 실제 Report는 다음 작업을 포함할 수 있다.

```text
입력값 검증
권한 확인
조회 조건 보정
DB 데이터 조회
Internal Table 가공
오류 메시지 처리
ALV 출력
로그 기록
```

이 모든 코드를 한 덩어리로 작성하면 다음 문제가 발생한다.

| 문제 | 설명 |
|---|---|
| 가독성 저하 | 어디서 무엇을 하는지 찾기 어렵다. |
| 중복 증가 | 같은 로직을 여러 곳에 반복 작성하게 된다. |
| 디버깅 어려움 | 오류가 발생한 처리 단위를 분리하기 어렵다. |
| 수정 영향 증가 | 한 부분을 수정하다가 다른 흐름을 깨뜨릴 수 있다. |
| 교육 확장성 저하 | 후속 Internal Table, Open SQL, ALV 학습 시 코드 구조가 복잡해진다. |

모듈화는 이런 문제를 줄이기 위해 코드를 의미 있는 작은 단위로 나누는 방법이다.

## 3. ABAP에서의 대표 모듈화 방식

ABAP에는 여러 가지 모듈화 방식이 있다.

| 방식 | 대표 구문 | 특징 | 학습 시점 |
|---|---|---|---|
| Subroutine | `FORM`, `PERFORM` | Classic Report에서 가장 기초적인 모듈화 방식 | 현재 모듈 |
| Function Module | `CALL FUNCTION` | 전역 재사용 가능, Function Group 기반 | THEORY-05-M03 |
| Local Class | `CLASS ... DEFINITION`, `METHODS` | 프로그램 내부 OO 구조 | THEORY-05-M04 |
| Global Class | SE24, ADT Class | 전역 OO 재사용 구조 | THEORY-05-M05 |
| Method | `CALL METHOD`, `object->method( )` | 최신 ABAP에서 권장되는 구조 | OO ABAP Section에서 심화 |

이번 모듈에서는 가장 기초적인 `FORM / PERFORM`만 다룬다.

> 실무 관점:  
> 신규 개발에서는 OO 방식과 Method 사용이 더 권장되는 경우가 많다. 그러나 SAP 현장에는 여전히 Classic Report, Include, FORM Subroutine 기반의 기존 코드가 많다. 따라서 초급자는 `FORM / PERFORM`을 이해해야 기존 소스 분석과 유지보수를 할 수 있다.

## 4. FORM / PERFORM의 기본 개념

### 4.1 FORM이란?

`FORM`은 ABAP Report 안에서 Subroutine을 정의하는 구문이다.

기본 구조는 다음과 같다.

```abap
FORM subroutine_name.
  " 처리 로직
ENDFORM.
```

예:

```abap
FORM display_header.
  WRITE: / '사용자 목록 출력'.
ENDFORM.
```

이 코드는 `display_header`라는 이름의 Subroutine을 정의한다.

### 4.2 PERFORM이란?

`PERFORM`은 정의된 `FORM` Subroutine을 호출하는 구문이다.

기본 구조는 다음과 같다.

```abap
PERFORM subroutine_name.
```

예:

```abap
PERFORM display_header.
```

이 문장을 만나면 ABAP 런타임은 `FORM display_header.`로 정의된 처리 블록을 실행한다.

### 4.3 한 줄 요약

```text
FORM은 처리 블록을 정의한다.
PERFORM은 그 처리 블록을 호출한다.
```

## 5. 가장 작은 FORM / PERFORM 예제

다음은 가장 기본적인 예제이다.

```abap
REPORT zgpt_form_basic_01.

WRITE: / '프로그램 시작'.

PERFORM display_message.

WRITE: / '프로그램 종료'.

FORM display_message.
  WRITE: / 'FORM 내부에서 출력한 메시지'.
ENDFORM.
```

실행 결과는 다음과 같이 이해할 수 있다.

```text
프로그램 시작
FORM 내부에서 출력한 메시지
프로그램 종료
```

실행 흐름은 다음과 같다.

```text
1. REPORT 시작
2. WRITE '프로그램 시작' 실행
3. PERFORM display_message 호출
4. FORM display_message 내부 로직 실행
5. ENDFORM을 만나 호출 위치로 복귀
6. WRITE '프로그램 종료' 실행
```

---

## 6. 실행 흐름을 그림으로 이해하기

다음 코드를 기준으로 보자.

```abap
REPORT zgpt_form_flow.

WRITE: / 'A'.
PERFORM step_b.
WRITE: / 'C'.

FORM step_b.
  WRITE: / 'B'.
ENDFORM.
```

실행 흐름은 다음과 같다.

```text
A 출력
↓
PERFORM step_b
↓
FORM step_b 실행
↓
B 출력
↓
ENDFORM
↓
PERFORM 다음 줄로 복귀
↓
C 출력
```

결과:

```text
A
B
C
```

초급자가 기억할 핵심은 다음이다.

```text
FORM이 소스 아래쪽에 정의되어 있어도, 자동으로 실행되는 것은 아니다.
PERFORM을 만났을 때만 실행된다.
```

## 7. FORM의 위치

ABAP Report에서는 일반적으로 실행 로직을 위쪽에 두고, FORM 정의를 아래쪽에 두는 스타일을 많이 사용한다.

예:

```abap
REPORT zgpt_form_position.

START-OF-SELECTION.
  PERFORM display_header.
  PERFORM display_body.
  PERFORM display_footer.

FORM display_header.
  WRITE: / '=== Header ==='.
ENDFORM.

FORM display_body.
  WRITE: / 'Body line'.
ENDFORM.

FORM display_footer.
  WRITE: / '=== Footer ==='.
ENDFORM.
```

이 스타일의 장점은 프로그램의 전체 흐름을 위에서 빠르게 볼 수 있다는 점이다.

```text
Header 출력
Body 출력
Footer 출력
```

이처럼 `PERFORM` 목록이 프로그램의 목차처럼 보이면 가독성이 좋아진다.

## 8. START-OF-SELECTION과 FORM

초급 과정에서는 `START-OF-SELECTION` 이벤트를 아직 깊게 다루지 않았을 수 있다.  
하지만 Report에서 가장 일반적으로 실행 로직을 배치하는 이벤트이므로 간단히만 연결한다.

```abap
REPORT zgpt_form_event.

START-OF-SELECTION.
  PERFORM initialize_data.
  PERFORM display_result.

FORM initialize_data.
  WRITE: / '초기 데이터 준비'.
ENDFORM.

FORM display_result.
  WRITE: / '결과 출력'.
ENDFORM.
```

이 예제에서 `START-OF-SELECTION`은 Report의 주 실행 흐름을 나타내고, `FORM`은 그 흐름 안에서 호출되는 세부 처리 단위이다.

> 주의:  
> Report Event의 상세 순서와 `INITIALIZATION`, `AT SELECTION-SCREEN`, `START-OF-SELECTION`, `END-OF-SELECTION`의 전체 흐름은 후속 Section에서 별도로 학습한다. 이번 모듈에서는 `PERFORM`으로 처리 블록을 나누는 감각만 익히면 된다.

## 9. FORM 이름 짓기

Subroutine 이름은 매우 중요하다. 이름만 보고 어떤 일을 하는지 알 수 있어야 한다.

### 9.1 좋은 이름

| 이름 | 의미 |
|---|---|
| `display_header` | 헤더 출력 |
| `validate_input` | 입력값 검증 |
| `select_data` | 데이터 조회 |
| `build_output` | 출력 데이터 구성 |
| `display_result` | 결과 출력 |

### 9.2 좋지 않은 이름

| 이름 | 문제 |
|---|---|
| `form1` | 의미 없음 |
| `process` | 너무 포괄적 |
| `data` | 동작이 아니라 명사만 있음 |
| `test` | 실무 의미 없음 |
| `aaa` | 유지보수 불가능 |

### 9.3 권장 규칙

Subroutine은 보통 동작을 표현하므로 동사로 시작하는 이름이 좋다.

```text
validate_...
select_...
build_...
display_...
calculate_...
clear_...
```

예:

```abap
PERFORM validate_input.
PERFORM select_user_data.
PERFORM display_user_list.
```

이름만 읽어도 프로그램의 흐름이 보이는 것이 좋은 코드이다.

## 10. FORM 내부에서 사용할 수 있는 구문

`FORM` 내부에는 일반 ABAP 처리 구문을 작성할 수 있다.

예를 들어 이전 Section에서 배운 구문을 사용할 수 있다.

| 구문 | 사용 예 |
|---|---|
| `DATA` | FORM 내부 변수 선언 |
| `WRITE` | 출력 |
| `IF / ELSEIF / ELSE` | 조건 분기 |
| `CASE` | 값 기준 분기 |
| `DO / WHILE` | 반복 |
| `SELECT` | DB 조회. 후속 Section에서 심화 |
| `LOOP AT` | Internal Table 반복. 후속 Section에서 심화 |

예:

```abap
REPORT zgpt_form_logic.

DATA gv_status TYPE c LENGTH 1 VALUE 'A'.

START-OF-SELECTION.
  PERFORM display_status_text.

FORM display_status_text.
  IF gv_status = 'A'.
    WRITE: / 'Active'.
  ELSEIF gv_status = 'I'.
    WRITE: / 'Inactive'.
  ELSE.
    WRITE: / 'Unknown'.
  ENDIF.
ENDFORM.
```

이 예제에서는 FORM 내부에서 `IF` 조건문을 사용했다.

## 11. 전역 변수와 FORM

이번 모듈에서는 아직 `USING`, `CHANGING` 파라미터를 다루지 않는다.  
따라서 가장 기본적인 FORM은 프로그램 전역 변수를 직접 참조하는 방식으로 이해할 수 있다.

```abap
REPORT zgpt_form_global.

DATA gv_name TYPE c LENGTH 20 VALUE 'SAP Beginner'.

START-OF-SELECTION.
  PERFORM display_name.

FORM display_name.
  WRITE: / 'Name:', gv_name.
ENDFORM.
```

이 코드는 정상 동작한다.  
`gv_name`은 프로그램 전역 영역에 선언되어 있고, `FORM display_name` 안에서 접근할 수 있다.

하지만 실무적으로는 모든 FORM이 전역 변수에 의존하는 방식이 좋은 설계는 아니다.

### 11.1 전역 변수 의존의 문제

| 문제 | 설명 |
|---|---|
| 흐름 추적 어려움 | FORM이 어떤 데이터를 사용하는지 호출부만 보고 알기 어렵다. |
| 수정 영향 증가 | 전역 변수 값이 어디서 바뀌었는지 추적해야 한다. |
| 재사용성 저하 | 특정 프로그램 상태에 강하게 묶인다. |
| 테스트 어려움 | 입력과 출력이 명확하지 않다. |

이 문제를 해결하기 위해 다음 모듈에서 `USING`, `CHANGING` 파라미터를 학습한다.

이번 모듈에서는 다음 정도만 기억한다.

```text
처음에는 전역 변수로 FORM 동작을 이해한다.
하지만 실무적으로는 FORM이 사용하는 입력과 변경 결과를 명확히 드러내는 것이 좋다.
그 방법은 다음 모듈의 USING / CHANGING에서 배운다.
```

## 12. PERFORM을 여러 번 호출하기

하나의 FORM은 여러 번 호출할 수 있다.

```abap
REPORT zgpt_form_multiple.

START-OF-SELECTION.
  PERFORM display_line.
  PERFORM display_line.
  PERFORM display_line.

FORM display_line.
  WRITE: / '----------------'.
ENDFORM.
```

결과:

```text
----------------
----------------
----------------
```

이처럼 반복되는 출력 또는 공통 처리를 FORM으로 묶으면 중복 코드를 줄일 수 있다.

다만 단순히 한 줄짜리 출력까지 모두 FORM으로 나누는 것이 항상 좋은 것은 아니다.  
모듈화의 목적은 코드 수를 늘리는 것이 아니라, 의미 있는 처리 단위로 나누는 것이다.

## 13. PERFORM 호출 순서

`PERFORM`은 작성된 순서대로 실행된다.

```abap
REPORT zgpt_form_order.

START-OF-SELECTION.
  PERFORM third_step.
  PERFORM first_step.
  PERFORM second_step.

FORM first_step.
  WRITE: / '1단계'.
ENDFORM.

FORM second_step.
  WRITE: / '2단계'.
ENDFORM.

FORM third_step.
  WRITE: / '3단계'.
ENDFORM.
```

출력 결과는 FORM이 정의된 순서가 아니라 `PERFORM` 호출 순서를 따른다.

```text
3단계
1단계
2단계
```

초급자가 자주 오해하는 부분이다.

```text
FORM 정의 순서가 실행 순서를 결정하지 않는다.
PERFORM 호출 순서가 실행 순서를 결정한다.
```

## 14. 실습 1 — 기본 호출 흐름 만들기

### 14.1 실습 목표

`FORM`을 정의하고 `PERFORM`으로 호출하여 프로그램 실행 흐름을 분리한다.

### 14.2 실습 코드

```abap
REPORT zgpt_theory05_m01_01.

START-OF-SELECTION.
  WRITE: / '프로그램 시작'.

  PERFORM display_header.
  PERFORM display_body.
  PERFORM display_footer.

  WRITE: / '프로그램 종료'.

FORM display_header.
  WRITE: / '=== ABAP 모듈화 기초 ==='.
ENDFORM.

FORM display_body.
  WRITE: / 'FORM / PERFORM 기본 호출을 학습합니다.'.
ENDFORM.

FORM display_footer.
  WRITE: / '=== END ==='.
ENDFORM.
```

### 14.3 예상 결과

```text
프로그램 시작
=== ABAP 모듈화 기초 ===
FORM / PERFORM 기본 호출을 학습합니다.
=== END ===
프로그램 종료
```

### 14.4 확인 포인트

| 확인 항목 | 설명 |
|---|---|
| `PERFORM display_header.` | Header FORM을 호출하는가? |
| `FORM display_header.` | 실제 처리 블록이 정의되어 있는가? |
| 호출 순서 | Header → Body → Footer 순서로 출력되는가? |
| `ENDFORM.` | 각 FORM이 정상 종료되는가? |

## 15. 실습 2 — 조건문을 FORM으로 분리하기

### 15.1 실습 목표

조건 분기 로직을 FORM 안으로 분리한다.

### 15.2 실습 코드

```abap
REPORT zgpt_theory05_m01_02.

DATA gv_status TYPE c LENGTH 1 VALUE 'A'.

START-OF-SELECTION.
  PERFORM display_status.

FORM display_status.
  CASE gv_status.
    WHEN 'A'.
      WRITE: / '상태: Active'.
    WHEN 'I'.
      WRITE: / '상태: Inactive'.
    WHEN 'B'.
      WRITE: / '상태: Blocked'.
    WHEN OTHERS.
      WRITE: / '상태: Unknown'.
  ENDCASE.
ENDFORM.
```

### 15.3 변경 실험

`gv_status` 값을 다음처럼 바꿔 실행해본다.

| 값 | 예상 출력 |
|---|---|
| A | 상태: Active |
| I | 상태: Inactive |
| B | 상태: Blocked |
| X | 상태: Unknown |

이 실습은 `CASE` 문법 자체보다 “상태 판단 로직을 FORM으로 분리했다”는 점이 중요하다.

## 16. 실습 3 — 입력값 확인 흐름 만들기

이번 실습은 `PARAMETERS`와 `FORM`을 연결한다.

```abap
REPORT zgpt_theory05_m01_03.

PARAMETERS p_name TYPE c LENGTH 20 DEFAULT 'SAP'.

START-OF-SELECTION.
  PERFORM validate_input.
  PERFORM display_result.

FORM validate_input.
  IF p_name IS INITIAL.
    WRITE: / '이름이 입력되지 않았습니다.'.
  ELSE.
    WRITE: / '입력값 확인 완료'.
  ENDIF.
ENDFORM.

FORM display_result.
  WRITE: / '입력한 이름:', p_name.
ENDFORM.
```

이 예제는 아직 완벽한 검증 구조는 아니다.  
`validate_input`에서 오류가 발생해도 `display_result`가 계속 실행된다.  
이 문제는 후속 모듈에서 파라미터 전달, 메시지 처리, Report Event 심화와 함께 개선할 수 있다.

이번 단계의 핵심은 다음이다.

```text
입력값 확인 로직과 출력 로직을 서로 다른 FORM으로 나눌 수 있다.
```

## 17. 정상 흐름과 오류 흐름

### 17.1 정상 흐름

```text
프로그램 실행
→ START-OF-SELECTION 진입
→ PERFORM validate_input
→ FORM validate_input 실행
→ 호출 위치로 복귀
→ PERFORM display_result
→ FORM display_result 실행
→ 프로그램 종료
```

### 17.2 오류 흐름 1 — FORM 이름 오타

```abap
PERFORM display_heder.

FORM display_header.
  WRITE: / 'Header'.
ENDFORM.
```

`PERFORM`에서 호출한 이름과 실제 `FORM` 이름이 다르다.

문제:

```text
display_heder ≠ display_header
```

해결:

```abap
PERFORM display_header.
```

초급자는 오타를 찾을 때 다음을 확인한다.

| 확인 항목 | 설명 |
|---|---|
| PERFORM 이름 | 호출 이름이 정확한가? |
| FORM 이름 | 정의 이름이 정확한가? |
| 언더스코어 | `_` 위치가 일치하는가? |
| 복수/단수 | `result`와 `results` 차이가 없는가? |

### 17.3 오류 흐름 2 — ENDFORM 누락

```abap
FORM display_header.
  WRITE: / 'Header'.

FORM display_body.
  WRITE: / 'Body'.
ENDFORM.
```

첫 번째 FORM의 `ENDFORM`이 없다.  
이 경우 문법 오류가 발생한다.

올바른 코드:

```abap
FORM display_header.
  WRITE: / 'Header'.
ENDFORM.

FORM display_body.
  WRITE: / 'Body'.
ENDFORM.
```

### 17.4 오류 흐름 3 — FORM 안에 FORM 정의

초급자가 중괄호 구조처럼 생각하여 FORM 안에 다른 FORM을 넣으려는 경우가 있다.

```abap
FORM outer_form.
  WRITE: / 'Outer'.

  FORM inner_form.
    WRITE: / 'Inner'.
  ENDFORM.
ENDFORM.
```

이런 방식은 일반적인 FORM 정의 구조가 아니다.  
FORM은 독립적인 처리 블록으로 정의해야 한다.

권장 구조:

```abap
FORM outer_form.
  WRITE: / 'Outer'.
  PERFORM inner_form.
ENDFORM.

FORM inner_form.
  WRITE: / 'Inner'.
ENDFORM.
```

### 17.5 오류 흐름 4 — 너무 많은 전역 변수 의존

```abap
DATA: gv_a TYPE i,
      gv_b TYPE i,
      gv_c TYPE i,
      gv_d TYPE i.

FORM calculate.
  gv_d = gv_a + gv_b + gv_c.
ENDFORM.
```

이 코드는 동작할 수 있지만, FORM이 어떤 값을 입력으로 사용하고 어떤 값을 변경하는지 호출부에서 명확히 보이지 않는다.

이번 모듈에서는 기본 호출을 이해하기 위해 허용하지만, 다음 모듈에서는 `USING`, `CHANGING`으로 개선한다.

## 18. 디버깅 포인트

FORM / PERFORM을 학습할 때는 디버깅이 매우 중요하다.

### 18.1 추천 디버깅 연습

1. `PERFORM display_header.` 줄에 Breakpoint를 건다.
2. 프로그램을 실행한다.
3. Breakpoint에서 멈추면 Single Step을 수행한다.
4. 실행 위치가 `FORM display_header.` 내부로 이동하는지 확인한다.
5. `ENDFORM.` 이후 호출 위치 다음 줄로 복귀하는지 확인한다.

### 18.2 관찰할 내용

| 관찰 항목 | 설명 |
|---|---|
| Call Stack | 현재 어떤 FORM 안에 들어와 있는지 확인 |
| 전역 변수 값 | FORM 진입 전후 값 변화 확인 |
| 실행 위치 | PERFORM → FORM → ENDFORM → 다음 줄 흐름 확인 |
| 반복 호출 | 같은 FORM이 여러 번 호출될 때 흐름 확인 |

디버깅을 통해 학습자는 `PERFORM`이 단순한 텍스트 치환이 아니라 실행 흐름을 이동시키는 호출 구문임을 이해할 수 있다.

## 19. FORM 사용 시 실무 주의점

### 19.1 FORM은 Classic ABAP에서 많이 사용된다

기존 SAP 시스템에는 FORM Subroutine 기반 Report가 많다.  
따라서 유지보수자는 반드시 FORM을 읽고 이해할 수 있어야 한다.

그러나 신규 개발에서는 Class와 Method 기반 구조가 더 적합한 경우가 많다.  
특히 RAP, ABAP Cloud, Clean Core 방향에서는 전통적인 FORM 중심 개발보다 객체지향 구조와 명확한 인터페이스가 중요하다.

초급 단계에서는 다음 균형이 필요하다.

```text
FORM을 알아야 기존 코드를 읽을 수 있다.
그러나 FORM만으로 모든 신규 개발을 설계하려고 하면 안 된다.
```

### 19.2 너무 긴 FORM은 피한다

FORM으로 나누었다고 해서 항상 좋은 코드가 되는 것은 아니다.  
하나의 FORM이 수백 줄이라면 여전히 읽기 어렵다.

나쁜 예:

```text
FORM process_all.
  입력 검증 50줄
  데이터 조회 100줄
  데이터 가공 200줄
  출력 80줄
ENDFORM.
```

좋은 예:

```text
PERFORM validate_input.
PERFORM select_data.
PERFORM build_output.
PERFORM display_result.
```

### 19.3 너무 잘게 나누는 것도 문제다

반대로 한 줄짜리 로직을 모두 FORM으로 분리하면 흐름을 따라가기 어려워질 수 있다.

```text
PERFORM write_slash.
PERFORM write_title.
PERFORM write_space.
PERFORM write_dot.
```

모듈화 단위는 “의미 있는 업무 처리 단위”여야 한다.

### 19.4 FORM 이름은 처리 목적을 표현한다

좋은 FORM 이름은 주석을 줄여준다.

```abap
PERFORM validate_input.
PERFORM select_sales_orders.
PERFORM build_alv_data.
PERFORM display_alv.
```

이런 구조는 코드를 처음 보는 사람도 전체 흐름을 이해하기 쉽다.

## 20. FORM / PERFORM과 후속 모듈의 경계

이번 모듈에서는 파라미터 없는 기본 호출만 다룬다.

다음 모듈에서는 `USING`, `CHANGING`을 통해 FORM에 값을 넘기고, FORM 안에서 값을 변경하는 방법을 배운다.

| 현재 모듈 | 다음 모듈 |
|---|---|
| `PERFORM display_header.` | `PERFORM calculate_total USING lv_price CHANGING lv_total.` |
| 전역 변수 중심 이해 | 명시적 파라미터 전달 이해 |
| 호출 흐름 중심 | 입력/출력 관계 중심 |
| FORM 구조 이해 | FORM 인터페이스 이해 |

따라서 이번 모듈에서 모든 것을 해결하려고 하지 않는다.  
핵심은 다음이다.

```text
FORM을 정의할 수 있다.
PERFORM으로 호출할 수 있다.
호출 흐름을 설명할 수 있다.
```

## 21. 강사용 설명 포인트

강의 시 다음 순서를 권장한다.

| 단계 | 설명 |
|---|---|
| 1 | 긴 Report 코드의 문제를 보여준다. |
| 2 | FORM으로 Header, Body, Footer를 분리한다. |
| 3 | PERFORM 호출 순서가 실행 순서임을 디버깅으로 확인한다. |
| 4 | FORM 이름을 좋은 이름과 나쁜 이름으로 비교한다. |
| 5 | 전역 변수 의존의 문제를 소개하고 다음 모듈로 연결한다. |

강사가 강조할 핵심 문장:

```text
FORM은 코드를 숨기기 위한 도구가 아니라, 의미 있는 처리 흐름을 드러내기 위한 도구이다.
```

```text
PERFORM 목록이 프로그램의 목차처럼 읽히면 좋은 구조이다.
```

```text
신규 개발에서는 Class와 Method도 중요하지만, 기존 ABAP Report를 읽기 위해 FORM은 반드시 이해해야 한다.
```

### 23.2 서술형

#### Q1. FORM / PERFORM을 사용하는 이유를 설명하시오.

긴 ABAP Report 코드를 의미 있는 처리 단위로 나누어 가독성과 유지보수성을 높이기 위해 사용한다. 반복되는 로직을 재사용할 수 있고, 프로그램의 전체 흐름을 `PERFORM` 목록으로 명확히 표현할 수 있다.

**모범 답안:**

#### Q3. 전역 변수에 의존하는 FORM의 단점을 설명하시오.

**모범 답안:**  
FORM이 어떤 값을 입력으로 사용하고 어떤 값을 변경하는지 호출부에서 명확히 보이지 않는다. 이로 인해 흐름 추적, 디버깅, 재사용, 테스트가 어려워질 수 있다. 이 문제는 후속 모듈의 `USING`, `CHANGING` 파라미터로 개선할 수 있다.

## 25. 후속 학습 연결

이번 모듈에서는 파라미터 없는 기본 Subroutine 호출을 배웠다.

이후 흐름은 다음과 같다.

```text
THEORY-05-M01 FORM / PERFORM 기본 호출
→ THEORY-05-M02 USING / CHANGING 파라미터
→ THEORY-05-M03 CALL FUNCTION 기본 구조
→ THEORY-05-M04 Local Class 정의와 Method 호출
→ THEORY-05-M05 Global Class 호출 기초
→ THEORY-05-M06 Subroutine / Function / Class 선택 기준
```

특히 다음 모듈과의 연결이 중요하다.

```text
M01: FORM을 호출할 수 있다.
M02: FORM에 값을 전달하고 변경 결과를 받을 수 있다.
```

따라서 M01에서 호출 흐름을 정확히 이해하면 M02의 파라미터 전달을 훨씬 쉽게 이해할 수 있다.

## 26. 핵심 요약

```text
FORM은 ABAP Report 안에서 Subroutine을 정의하는 구문이다.
PERFORM은 정의된 FORM을 호출하는 구문이다.
FORM은 자동 실행되지 않고 PERFORM을 만났을 때 실행된다.
FORM 정의 순서보다 PERFORM 호출 순서가 실행 흐름을 결정한다.
FORM 이름은 처리 목적이 드러나도록 작성해야 한다.
처음에는 전역 변수로 이해할 수 있지만, 실무적으로는 파라미터 전달을 통해 입력과 출력을 명확히 하는 것이 좋다.
기존 Classic ABAP Report를 읽기 위해 FORM / PERFORM 이해는 여전히 중요하다.
```
