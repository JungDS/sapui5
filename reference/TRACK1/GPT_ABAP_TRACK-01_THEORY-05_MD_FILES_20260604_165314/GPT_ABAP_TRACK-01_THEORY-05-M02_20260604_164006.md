## 0. 이 문서의 학습 범위

이 문서는 `THEORY-05-M02 — USING / CHANGING 파라미터`만 다룬다.

이번 모듈의 핵심 키워드는 다음 세 가지이다.

| 키워드 | 의미 |
|---|---|
| USING | Subroutine 호출 시 입력값을 전달하는 파라미터 영역 |
| CHANGING | Subroutine에서 값을 변경하여 호출자에게 되돌려주는 파라미터 영역 |
| Parameter Passing | 호출부와 처리부 사이에서 데이터를 주고받는 방식 |

이전 모듈 `THEORY-05-M01`에서는 `FORM / PERFORM`의 가장 단순한 호출 구조를 학습했다.

```abap
PERFORM display_header.

FORM display_header.
  WRITE: / 'User List'.
ENDFORM.
```

하지만 실제 프로그램에서는 Subroutine이 고정된 문장만 출력하지 않는다. 호출한 쪽에서 값을 넘겨주고, Subroutine은 그 값을 기준으로 계산하거나 검증한 뒤 결과를 돌려줘야 한다.

이번 모듈은 바로 그 흐름을 다룬다.

```text
호출부에서 값 준비
→ PERFORM ... USING ... CHANGING ...
→ FORM에서 입력값 수신
→ FORM 내부 처리
→ CHANGING 파라미터로 결과 반영
```

## 2. 왜 파라미터가 필요한가?

이전 모듈의 Subroutine은 외부 값을 받지 않는 단순 처리였다.

```abap
FORM display_message.
  WRITE: / 'Hello ABAP'.
ENDFORM.
```

이 방식은 고정된 메시지를 출력할 때는 충분하다. 하지만 사용자명, 금액, 상태, 계산 결과처럼 실행 시점마다 달라지는 값을 처리하려면 Subroutine 밖에서 안으로 값을 전달해야 한다.

예를 들어 다음 요구사항을 보자.

```text
사용자 ID와 사용자명을 전달받아 한 줄로 출력한다.
점수 두 개를 전달받아 합계를 계산한다.
주문금액을 전달받아 할인금액과 최종금액을 계산한다.
입력 상태코드를 전달받아 표시 텍스트를 만든다.
```

이런 경우 Subroutine은 호출부와 데이터를 주고받아야 한다.

파라미터는 이때 사용하는 연결 통로이다.

```text
호출부 변수  →  FORM 파라미터  →  처리 로직  →  호출부 변수에 결과 반영
```

## 3. USING과 CHANGING의 기본 구분

`FORM / PERFORM`에서 자주 사용하는 파라미터 구분은 `USING`과 `CHANGING`이다.

| 구분 | 목적 | 호출부 관점 | FORM 내부 관점 | 권장 사용 |
|---|---|---|---|---|
| USING | 입력값 전달 | 값을 넘겨준다 | 읽어서 사용한다 | 입력 전용 값 |
| CHANGING | 변경값 전달 | 변수의 변경 결과를 받는다 | 값을 변경한다 | 결과값 또는 갱신 대상 |

초급자는 다음 문장으로 기억하면 된다.

```text
USING은 읽기 위한 입력값이다.
CHANGING은 바뀌어 돌아오는 값이다.
```

## 4. 가장 작은 USING 예제

### 4.1 요구사항

사용자명을 Subroutine에 전달하여 출력한다.

### 4.2 코드

```abap
REPORT zgpt_mod_0201.

DATA gv_name TYPE string VALUE 'Kim Developer'.

PERFORM display_name USING gv_name.

FORM display_name USING iv_name TYPE string.
  WRITE: / 'Name:', iv_name.
ENDFORM.
```

### 4.3 실행 흐름

```text
1. GV_NAME에 'Kim Developer' 저장
2. PERFORM display_name USING gv_name 실행
3. FORM display_name의 IV_NAME으로 값 전달
4. FORM 내부에서 IV_NAME 출력
```

### 4.4 이름 규칙 해석

| 이름 | 의미 |
|---|---|
| `gv_name` | Global Variable 성격의 호출부 변수 |
| `iv_name` | Input Variable 성격의 FORM 입력 파라미터 |

이름 규칙은 시스템 강제 사항은 아니다. 그러나 교육과 실무에서는 의미를 드러내는 접두어를 사용하면 코드 흐름이 훨씬 읽기 쉬워진다.

## 5. 가장 작은 CHANGING 예제

### 5.1 요구사항

숫자 두 개를 입력받아 합계를 계산하고 호출부 변수에 결과를 돌려준다.

### 5.2 코드

```abap
REPORT zgpt_mod_0202.

DATA gv_num1   TYPE i VALUE 10.
DATA gv_num2   TYPE i VALUE 20.
DATA gv_result TYPE i.

PERFORM calculate_sum USING    gv_num1
                               gv_num2
                      CHANGING gv_result.

WRITE: / 'Result:', gv_result.

FORM calculate_sum USING    iv_num1   TYPE i
                            iv_num2   TYPE i
                   CHANGING cv_result TYPE i.
  cv_result = iv_num1 + iv_num2.
ENDFORM.
```

### 5.3 실행 흐름

```text
1. GV_NUM1 = 10
2. GV_NUM2 = 20
3. GV_RESULT는 초기값 0
4. PERFORM calculate_sum 호출
5. IV_NUM1, IV_NUM2에 입력값 전달
6. CV_RESULT에 합계 30 대입
7. 호출부 GV_RESULT 값이 30으로 변경
8. WRITE로 결과 출력
```

### 5.4 핵심 포인트

`CHANGING`에 넘긴 변수는 Subroutine 안에서 바뀔 수 있다. 이 예제에서는 `cv_result`가 바뀌면 호출부의 `gv_result`에도 결과가 반영된다.

## 6. USING과 CHANGING을 함께 사용하는 기본 패턴

실무 프로그램에서는 보통 입력값 여러 개와 결과값 한두 개를 조합한다.

```abap
PERFORM do_something USING    input1
                              input2
                     CHANGING result.
```

이를 설계 관점으로 보면 다음과 같다.

```text
USING    = 처리 판단에 필요한 입력 데이터
CHANGING = 처리 후 외부에 알려야 할 결과 데이터
```

예를 들어 상태 코드로 상태 텍스트를 만드는 Subroutine은 다음처럼 작성할 수 있다.

```abap
REPORT zgpt_mod_0203.

DATA gv_status      TYPE c LENGTH 1 VALUE 'A'.
DATA gv_status_text TYPE string.

PERFORM get_status_text USING    gv_status
                        CHANGING gv_status_text.

WRITE: / 'Status:', gv_status,
       / 'Text  :', gv_status_text.

FORM get_status_text USING    iv_status      TYPE c
                     CHANGING cv_status_text TYPE string.

  CASE iv_status.
    WHEN 'A'.
      cv_status_text = 'Active'.
    WHEN 'I'.
      cv_status_text = 'Inactive'.
    WHEN 'B'.
      cv_status_text = 'Blocked'.
    WHEN OTHERS.
      cv_status_text = 'Unknown'.
  ENDCASE.

ENDFORM.
```

이 예제에서 `gv_status`는 입력값이고, `gv_status_text`는 처리 결과이다.

## 7. 파라미터 순서의 중요성

`FORM / PERFORM`의 파라미터는 이름으로 자동 매핑되지 않는다. 기본적으로 호출 순서와 정의 순서가 맞아야 한다.

### 7.1 정상 예

```abap
PERFORM calculate_sum USING gv_num1 gv_num2 CHANGING gv_result.

FORM calculate_sum USING iv_num1 TYPE i
                         iv_num2 TYPE i
                CHANGING cv_result TYPE i.
  cv_result = iv_num1 + iv_num2.
ENDFORM.
```

호출부와 정의부의 순서가 일치한다.

```text
GV_NUM1 → IV_NUM1
GV_NUM2 → IV_NUM2
GV_RESULT → CV_RESULT
```

### 7.2 위험한 예

```abap
PERFORM calculate_difference USING gv_num2 gv_num1 CHANGING gv_result.

FORM calculate_difference USING iv_num1 TYPE i
                                iv_num2 TYPE i
                       CHANGING cv_result TYPE i.
  cv_result = iv_num1 - iv_num2.
ENDFORM.
```

호출부에서 `gv_num2`, `gv_num1` 순서로 넘겼기 때문에 FORM 내부에서는 기대와 다른 계산이 일어날 수 있다.

### 7.3 실무 기준

파라미터가 많아질수록 순서 오류 가능성이 커진다. 따라서 다음 원칙을 권장한다.

| 기준 | 설명 |
|---|---|
| 파라미터 수를 줄인다 | 너무 많은 파라미터는 Subroutine 책임이 크다는 신호이다. |
| 의미 있는 이름을 사용한다 | `iv_num1`보다 `iv_price`, `iv_quantity`가 더 좋다. |
| 호출부 줄바꿈을 정리한다 | `USING`, `CHANGING`을 구분해 읽기 쉽게 작성한다. |
| 복잡해지면 구조체 사용을 검토한다 | 여러 필드를 하나의 Structure로 묶을 수 있다. |
| 더 복잡해지면 Method 전환을 검토한다 | 후속 OO ABAP에서 더 명확한 인터페이스를 배운다. |

## 8. 명시적 타입 선언의 중요성

Subroutine 파라미터에는 타입을 명시하는 것이 좋다.

```abap
FORM display_name USING iv_name TYPE string.
```

타입을 명시하면 다음 장점이 있다.

| 장점 | 설명 |
|---|---|
| 가독성 | 어떤 데이터가 들어오는지 바로 알 수 있다. |
| 오류 예방 | 잘못된 타입 전달을 조기에 발견할 수 있다. |
| 유지보수 | 나중에 호출부를 읽을 때 의도를 파악하기 쉽다. |
| 교육 효과 | DDIC Type, ABAP Type, Structure 사용 흐름을 연결하기 좋다. |

### 8.1 DDIC 타입 사용 예

앞선 DDIC Section에서 Data Element를 만들었다면 다음처럼 사용할 수 있다.

```abap
DATA gv_user_id TYPE zde_jhy_user_id.

PERFORM display_user USING gv_user_id.

FORM display_user USING iv_user_id TYPE zde_jhy_user_id.
  WRITE: / 'User ID:', iv_user_id.
ENDFORM.
```

이렇게 하면 Subroutine 파라미터도 DDIC의 의미와 기술 속성을 재사용할 수 있다.

### 8.2 Structure 타입 사용 예

앞선 DDIC Section에서 Structure를 만들었다면 다음과 같이 구조 전체를 전달할 수 있다.

```abap
DATA gs_user TYPE zs_jhy_user_info.

gs_user-user_id   = 'U0001'.
gs_user-user_name = 'Kim Developer'.
gs_user-status    = 'A'.

PERFORM display_user_info USING gs_user.

FORM display_user_info USING is_user TYPE zs_jhy_user_info.
  WRITE: / is_user-user_id,
           is_user-user_name,
           is_user-status.
ENDFORM.
```

이 예제는 DDIC와 모듈화가 연결되는 지점을 보여준다.

## 9. USING 파라미터를 변경하지 않는 습관

ABAP Subroutine에서 `USING`으로 받은 파라미터도 기술적으로 변경 가능한 형태로 사용되는 경우가 있다. 그러나 교육과 실무 가독성 관점에서는 `USING`은 입력 전용으로 다루는 습관이 좋다.

### 9.1 나쁜 예

```abap
FORM normalize_name USING iv_name TYPE string.
  iv_name = to_upper( iv_name ).
ENDFORM.
```

위 코드는 이름상 `iv_name`이 입력값처럼 보이는데 내부에서 값을 바꾸고 있다. 호출자가 이 변경을 기대하지 않았다면 혼란이 발생한다.

### 9.2 더 나은 예

```abap
FORM normalize_name USING    iv_name        TYPE string
                    CHANGING cv_upper_name  TYPE string.
  cv_upper_name = to_upper( iv_name ).
ENDFORM.
```

이렇게 작성하면 입력값과 결과값이 명확히 분리된다.

```text
IV_NAME       = 원본 입력
CV_UPPER_NAME = 변환 결과
```

### 9.3 원칙

```text
USING은 읽는다.
CHANGING은 바꾼다.
```

이 단순한 원칙을 지키면 Subroutine의 부작용을 줄일 수 있다.

## 10. CHANGING 남용의 위험

`CHANGING`은 편리하지만 남용하면 프로그램 흐름이 복잡해진다.

### 10.1 나쁜 예

```abap
PERFORM process_user CHANGING gv_user_id
                              gv_user_name
                              gv_status
                              gv_message
                              gv_error_flag
                              gv_count.
```

이런 코드는 호출부만 봐서는 무엇이 어떻게 바뀌는지 알기 어렵다.

문제점은 다음과 같다.

| 문제 | 설명 |
|---|---|
| 데이터 흐름 불명확 | 어떤 값이 입력이고 어떤 값이 결과인지 구분하기 어렵다. |
| 디버깅 어려움 | 여러 변수가 한 번에 바뀌어 원인 추적이 어렵다. |
| 책임 과다 | 하나의 FORM이 너무 많은 일을 한다는 신호이다. |
| 재사용성 저하 | 특정 전역 변수 흐름에 의존하기 쉽다. |

### 10.2 개선 방향

| 개선 방식 | 설명 |
|---|---|
| USING과 CHANGING 분리 | 입력과 결과를 명확히 구분한다. |
| Structure 사용 | 관련 값을 하나의 구조로 묶는다. |
| FORM 분리 | 검증, 계산, 출력 책임을 나눈다. |
| Method 전환 | 후속 OO ABAP에서 더 명확한 인터페이스를 사용한다. |

초급 단계에서는 `CHANGING` 파라미터를 1~2개 정도로 유지하는 예제를 권장한다.

## 11. Pass by Reference와 Pass by Value 기본 감각

Classic ABAP Subroutine에서는 파라미터 전달 방식에 따라 내부 변경이 호출부에 영향을 줄 수 있다.

초급 단계에서는 모든 세부 문법을 암기하기보다 다음 감각을 먼저 잡는 것이 중요하다.

```text
USING / CHANGING은 단순 문법 구분일 뿐 아니라 데이터 흐름의 의도를 표현한다.
CHANGING으로 넘긴 값은 변경되어 돌아오는 것이 자연스럽다.
USING으로 넘긴 값은 입력값으로 읽기만 하는 것이 바람직하다.
```

### 11.1 VALUE 사용 예시

`VALUE(...)`를 사용하면 입력 파라미터를 값으로 전달하는 의도를 표현할 수 있다.

```abap
REPORT zgpt_mod_0204.

DATA gv_text TYPE string VALUE 'original'.

PERFORM change_local USING gv_text.

WRITE: / 'After PERFORM:', gv_text.

FORM change_local USING VALUE(iv_text) TYPE string.
  iv_text = 'changed in form'.
  WRITE: / 'Inside FORM:', iv_text.
ENDFORM.
```

이 예제에서 `iv_text`는 FORM 내부의 로컬 복사본처럼 동작한다. FORM 안에서 `iv_text`를 바꾸더라도 호출부 `gv_text`의 값을 바꾸는 의도로 작성한 코드는 아니다.

> 초급 실무 기준:  
> 처음에는 `USING`은 입력 전용, `CHANGING`은 결과 반영용으로 구분해서 작성한다. `VALUE(...)`의 세부 동작과 성능 영향은 나중에 더 깊게 학습해도 된다.

## 12. Subroutine 파라미터 이름 규칙

강제 규칙은 아니지만 교육 자료에서는 다음 이름 규칙을 사용한다.

| 접두어 | 의미 | 예시 |
|---|---|---|
| `iv_` | Input Variable | `iv_user_id`, `iv_status` |
| `cv_` | Changing Variable | `cv_result`, `cv_message` |
| `ev_` | Exporting Variable | Function/Method에서 주로 사용 |
| `is_` | Input Structure | `is_user` |
| `cs_` | Changing Structure | `cs_user` |
| `it_` | Input Internal Table | `it_user` |
| `ct_` | Changing Internal Table | `ct_user` |

Subroutine에서는 공식적으로 `IMPORTING`, `EXPORTING` 키워드를 사용하는 Function Module이나 Method와 다르지만, 이름 규칙을 통해 의도를 표현할 수 있다.

예:

```abap
FORM build_message USING    iv_user_id TYPE zde_jhy_user_id
                            iv_status  TYPE zde_jhy_status
                   CHANGING cv_message TYPE string.
```

위 선언은 다음처럼 읽힌다.

```text
사용자 ID와 상태를 입력받아 메시지 문자열을 만들어 돌려준다.
```

## 13. 실습 1: 상태 코드 텍스트 변환

### 13.1 요구사항

상태 코드 `A`, `I`, `B`를 전달받아 상태 텍스트를 생성한다.

| Status | Text |
|---|---|
| A | Active |
| I | Inactive |
| B | Blocked |
| 기타 | Unknown |

### 13.2 코드

```abap
REPORT zgpt_mod_0205.

DATA gv_status TYPE c LENGTH 1 VALUE 'A'.
DATA gv_text   TYPE string.

PERFORM get_status_text USING    gv_status
                        CHANGING gv_text.

WRITE: / 'Status Code:', gv_status,
       / 'Status Text:', gv_text.

FORM get_status_text USING    iv_status TYPE c
                     CHANGING cv_text   TYPE string.

  CASE iv_status.
    WHEN 'A'.
      cv_text = 'Active'.
    WHEN 'I'.
      cv_text = 'Inactive'.
    WHEN 'B'.
      cv_text = 'Blocked'.
    WHEN OTHERS.
      cv_text = 'Unknown'.
  ENDCASE.

ENDFORM.
```

### 13.3 검증 포인트

| 확인 항목 | 기대 결과 |
|---|---|
| `gv_status = 'A'` | `gv_text = 'Active'` |
| `gv_status = 'I'` | `gv_text = 'Inactive'` |
| `gv_status = 'B'` | `gv_text = 'Blocked'` |
| `gv_status = 'X'` | `gv_text = 'Unknown'` |

## 14. 실습 2: 금액 계산 구조

### 14.1 요구사항

단가와 수량을 입력받아 총액을 계산한다.

```text
총액 = 단가 × 수량
```

### 14.2 코드

```abap
REPORT zgpt_mod_0206.

TYPES ty_amount TYPE p LENGTH 10 DECIMALS 2.

DATA gv_price    TYPE ty_amount VALUE '1200.50'.
DATA gv_quantity TYPE i        VALUE 3.
DATA gv_total    TYPE ty_amount.

PERFORM calculate_total USING    gv_price
                                 gv_quantity
                        CHANGING gv_total.

WRITE: / 'Price   :', gv_price,
       / 'Quantity:', gv_quantity,
       / 'Total   :', gv_total.

FORM calculate_total USING    iv_price    TYPE ty_amount
                              iv_quantity TYPE i
                     CHANGING cv_total    TYPE ty_amount.

  cv_total = iv_price * iv_quantity.

ENDFORM.
```

### 14.3 학습 포인트

| 포인트 | 설명 |
|---|---|
| `TYPES ty_amount` | 금액성 타입을 프로그램 안에서 정의한다. |
| `USING iv_price` | 단가는 입력값이다. |
| `USING iv_quantity` | 수량도 입력값이다. |
| `CHANGING cv_total` | 계산 결과는 호출부로 돌려준다. |

실무에서는 금액과 통화키, 수량과 단위가 함께 고려되어야 한다. 이번 예제는 파라미터 전달 구조를 익히기 위한 최소 계산 예제이다.

## 15. 실습 3: 메시지 생성 Subroutine

### 15.1 요구사항

사용자 ID와 상태를 입력받아 화면 출력용 메시지를 만든다.

### 15.2 코드

```abap
REPORT zgpt_mod_0207.

DATA gv_user_id TYPE c LENGTH 10 VALUE 'U0001'.
DATA gv_status  TYPE c LENGTH 1  VALUE 'A'.
DATA gv_message TYPE string.

PERFORM build_user_message USING    gv_user_id
                                    gv_status
                           CHANGING gv_message.

WRITE: / gv_message.

FORM build_user_message USING    iv_user_id TYPE c
                                 iv_status  TYPE c
                        CHANGING cv_message TYPE string.

  DATA lv_status_text TYPE string.

  PERFORM get_status_text USING    iv_status
                          CHANGING lv_status_text.

  CONCATENATE 'User'
              iv_user_id
              'is'
              lv_status_text
         INTO cv_message
         SEPARATED BY space.

ENDFORM.

FORM get_status_text USING    iv_status TYPE c
                     CHANGING cv_text   TYPE string.

  CASE iv_status.
    WHEN 'A'.
      cv_text = 'Active'.
    WHEN 'I'.
      cv_text = 'Inactive'.
    WHEN 'B'.
      cv_text = 'Blocked'.
    WHEN OTHERS.
      cv_text = 'Unknown'.
  ENDCASE.

ENDFORM.
```

### 15.3 해설

이 예제는 하나의 FORM이 다른 FORM을 호출하는 구조를 보여준다.

```text
MAIN 처리
→ build_user_message
→ get_status_text
→ 메시지 생성
→ 화면 출력
```

초급자가 주의할 점은 Subroutine 호출 흐름이 깊어지면 디버깅이 어려워질 수 있다는 점이다. 따라서 이름을 명확하게 정하고, 각 FORM의 책임을 작게 유지해야 한다.

## 16. 정상 흐름과 오류 흐름

### 16.1 정상 흐름

```text
1. 호출부에서 입력 변수와 결과 변수를 준비한다.
2. PERFORM 구문에서 USING과 CHANGING을 지정한다.
3. FORM 정의부에서 같은 순서로 파라미터를 선언한다.
4. FORM 내부에서 USING 값은 읽고, CHANGING 값은 필요한 만큼 변경한다.
5. FORM 종료 후 호출부 변수에 결과가 반영된다.
6. 결과를 WRITE 또는 후속 처리에 사용한다.
```

### 16.2 오류 흐름 1: 파라미터 개수 불일치

#### 상황

```abap
PERFORM calculate_sum USING gv_num1 CHANGING gv_result.

FORM calculate_sum USING iv_num1 TYPE i
                         iv_num2 TYPE i
                CHANGING cv_result TYPE i.
  cv_result = iv_num1 + iv_num2.
ENDFORM.
```

호출부에서는 입력값을 하나만 넘겼지만 FORM 정의부에서는 두 개를 기대한다.

#### 해결

호출부와 정의부의 파라미터 개수를 맞춘다.

```abap
PERFORM calculate_sum USING gv_num1 gv_num2 CHANGING gv_result.
```

### 16.3 오류 흐름 2: 파라미터 순서 오류

#### 상황

```abap
PERFORM calculate_total USING gv_quantity gv_price CHANGING gv_total.
```

정의부는 단가, 수량 순서를 기대하는데 호출부에서 수량, 단가 순서로 넘겼다.

#### 해결

호출부 순서를 정의부와 맞춘다.

```abap
PERFORM calculate_total USING gv_price gv_quantity CHANGING gv_total.
```

### 16.4 오류 흐름 3: CHANGING에 상수 전달

#### 상황

`CHANGING`은 변경 결과를 돌려받아야 하므로 변경 가능한 변수를 넘겨야 한다. 리터럴 상수나 변경 불가능한 표현식을 넘기면 문제가 된다.

잘못된 예:

```abap
PERFORM calculate_sum USING 10 20 CHANGING 0.
```

#### 해결

결과를 받을 변수를 선언해서 넘긴다.

```abap
DATA gv_result TYPE i.

PERFORM calculate_sum USING 10 20 CHANGING gv_result.
```

### 16.5 오류 흐름 4: USING 값을 결과처럼 변경

#### 상황

`USING`으로 받은 입력값을 내부에서 바꾸면 호출자가 의도하지 않은 부작용을 경험할 수 있다.

#### 해결

결과는 별도의 `CHANGING` 파라미터로 돌려준다.

## 17. 디버깅 포인트

이 모듈은 디버깅 연습에 매우 좋다. 다음 위치에 Breakpoint를 걸어본다.

| 위치 | 확인할 내용 |
|---|---|
| `PERFORM` 직전 | 호출부 변수 값 확인 |
| `FORM` 첫 줄 | FORM 파라미터에 값이 들어왔는지 확인 |
| 계산 또는 CASE 처리 라인 | 처리 결과가 어떻게 결정되는지 확인 |
| `ENDFORM` 직전 | CHANGING 파라미터 최종값 확인 |
| `PERFORM` 다음 줄 | 호출부 결과 변수에 반영되었는지 확인 |

디버깅 중에는 다음 질문을 던진다.

```text
호출부 변수와 FORM 파라미터 값이 같은가?
FORM 내부에서 결과값이 언제 바뀌는가?
FORM 종료 후 호출부 변수도 바뀌었는가?
USING 값이 의도치 않게 변경되지는 않았는가?
```

## 18. 실무 설계 기준

### 18.1 FORM의 책임은 작게 유지한다

FORM 하나가 너무 많은 일을 하면 파라미터도 많아지고, CHANGING도 많아진다. 그러면 유지보수가 어려워진다.

좋은 책임 분리 예:

```text
validate_input
get_status_text
calculate_total
display_result
```

나쁜 책임 이름 예:

```text
do_all
process_data
main_logic
handle_everything
```

### 18.2 입력과 결과를 명확히 분리한다

좋은 예:

```abap
PERFORM calculate_total USING    gv_price
                                 gv_quantity
                        CHANGING gv_total.
```

나쁜 예:

```abap
PERFORM calculate_total CHANGING gv_price
                                 gv_quantity
                                 gv_total.
```

두 번째 예는 어떤 값이 입력이고 어떤 값이 결과인지 불명확하다.

### 18.3 FORM 기반 신규 개발은 신중히 판단한다

S/4HANA 기준의 신규 개발에서는 OO 방식과 Method 기반 설계가 더 적합한 경우가 많다. 하지만 Classic Report와 기존 운영 소스에는 FORM이 여전히 많이 존재한다.

따라서 초급자는 다음 균형을 가져야 한다.

```text
FORM을 이해해야 기존 ABAP 소스를 읽고 유지보수할 수 있다.
그러나 복잡한 신규 설계에서는 Method 기반 구조를 검토해야 한다.
```

### 18.4 전역 변수 의존을 줄인다

FORM이 전역 변수만 읽고 쓰면 호출부에서 데이터 흐름이 보이지 않는다.

나쁜 예:

```abap
FORM calculate_total.
  gv_total = gv_price * gv_quantity.
ENDFORM.
```

더 나은 예:

```abap
FORM calculate_total USING    iv_price    TYPE ty_amount
                              iv_quantity TYPE i
                     CHANGING cv_total    TYPE ty_amount.
  cv_total = iv_price * iv_quantity.
ENDFORM.
```

파라미터를 사용하면 FORM이 어떤 데이터를 필요로 하고 어떤 결과를 만드는지 더 명확해진다.

## 21. 평가 문제

### 21.1 객관식

#### Q1. `USING` 파라미터의 가장 적절한 설명은?

A. FORM에서 생성한 결과를 반드시 호출부로 돌려주는 파라미터이다.  
B. Subroutine 호출 시 입력값을 전달하는 파라미터이다.  
C. Function Module에서만 사용하는 파라미터이다.  
D. 데이터베이스 테이블의 Key를 지정하는 문법이다.

#### Q2. `CHANGING` 파라미터의 가장 적절한 사용 사례는?

A. 화면 제목처럼 고정 문자열만 출력할 때

C. 계산 결과를 호출부 변수에 반영해야 할 때

#### Q3. `FORM / PERFORM` 파라미터 사용 시 가장 주의해야 할 점은?

A. 파라미터 순서와 개수를 호출부와 정의부에서 맞춰야 한다.  
B. 모든 파라미터는 반드시 전역 변수여야 한다.

D. `CHANGING`에는 숫자 리터럴만 전달해야 한다.

정답: A

### 21.2 서술형

#### Q1. `USING`과 `CHANGING`의 차이를 설명하시오.

모범 답안:  
`USING`은 Subroutine이 처리에 사용할 입력값을 전달하는 영역이고, `CHANGING`은 Subroutine에서 변경한 결과를 호출부 변수에 반영하기 위한 영역이다. 교육 및 실무 가독성 관점에서는 `USING`은 읽기 전용 입력값으로, `CHANGING`은 변경 결과로 구분해서 사용하는 것이 좋다.

#### Q2. 전역 변수에 직접 의존하는 FORM보다 파라미터를 사용하는 FORM이 더 좋은 이유는 무엇인가?

모범 답안:  
파라미터를 사용하면 FORM이 어떤 입력을 필요로 하고 어떤 결과를 만드는지 호출부에서 명확히 드러난다. 전역 변수에 직접 의존하면 데이터 흐름이 숨겨져 디버깅과 유지보수가 어려워진다.

#### Q3. CHANGING 파라미터가 많아질 때 발생할 수 있는 문제를 설명하시오.

모범 답안:  
여러 변수가 한 번에 변경되면 호출부에서 데이터 흐름을 파악하기 어렵고, 디버깅 시 어떤 값이 언제 바뀌었는지 추적하기 어렵다. 또한 하나의 FORM이 너무 많은 책임을 가지고 있다는 신호일 수 있다.

## 22. 강사용 설명 포인트

강의에서는 다음 순서로 설명하면 좋다.

```text
1. FORM / PERFORM만 있으면 고정 로직만 호출할 수 있음을 보여준다.
2. USING으로 입력값을 넘겨 동적인 처리를 만든다.
3. CHANGING으로 계산 결과를 호출부에 되돌린다.
4. 파라미터 순서 오류를 일부러 만들어 디버깅한다.
5. 전역 변수 의존 방식과 파라미터 방식의 차이를 비교한다.
6. 복잡해지면 Function Module과 Method로 확장된다는 연결을 만든다.
```

학습자에게 특히 강조할 문장은 다음이다.

```text
USING과 CHANGING은 단순 문법이 아니라 데이터 흐름을 읽기 쉽게 만드는 약속이다.
```

## 23. 후속 모듈과의 연결

이번 모듈에서는 FORM Subroutine 안팎으로 데이터를 전달하는 방법을 학습했다.

다음 모듈 `THEORY-05-M03 — CALL FUNCTION 기본 구조`에서는 전역 재사용 가능한 Function Module 호출 구조를 학습한다.

연결 관계는 다음과 같다.

```text
THEORY-05-M01 FORM / PERFORM 기본 호출
  → Subroutine을 호출하는 최소 구조

THEORY-05-M02 USING / CHANGING 파라미터
  → Subroutine과 호출부 사이의 데이터 전달

THEORY-05-M03 CALL FUNCTION 기본 구조
  → Function Module의 IMPORTING / EXPORTING / CHANGING / TABLES 구조

THEORY-05-M04 Local Class 정의와 Method 호출
  → 프로그램 내부 OO 모듈화

THEORY-05-M05 Global Class 호출 기초
  → 전역 Class 기반 재사용

THEORY-05-M06 Subroutine / Function / Class 선택 기준
  → 상황별 모듈화 방식 판단
```

## 24. 핵심 요약

```text
USING은 Subroutine으로 입력값을 전달한다.
CHANGING은 Subroutine에서 변경한 값을 호출부로 돌려준다.
호출부 PERFORM의 파라미터 순서와 FORM 정의부의 파라미터 순서는 맞아야 한다.
파라미터에는 가능한 명시적 타입을 부여한다.
USING은 입력 전용, CHANGING은 결과 반영용으로 구분하는 습관이 좋다.
CHANGING 남용은 데이터 흐름을 불명확하게 만들 수 있다.
전역 변수 의존보다 파라미터 전달이 데이터 흐름을 더 명확하게 만든다.
FORM은 기존 Classic ABAP 소스 이해에 중요하지만, 복잡한 신규 설계에서는 Method 기반 구조를 검토해야 한다.
```
