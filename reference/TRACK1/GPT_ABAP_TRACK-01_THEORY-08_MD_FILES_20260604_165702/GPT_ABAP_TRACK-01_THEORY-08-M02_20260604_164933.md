## 0. 이 문서의 학습 범위

이 문서는 `THEORY-08-M02 — FACTORY 메서드로 Internal Table 출력`만 다룬다.

이전 모듈에서는 SALV의 목적과 `CL_SALV_TABLE`의 개요를 학습했다. 이번 모듈에서는 실제로 가장 작은 SALV 프로그램을 작성하여 **Internal Table을 ALV 형태로 출력하는 핵심 흐름**을 익힌다.

이번 모듈의 초점은 다음 세 가지이다.

| 핵심 요소 | 설명 |
|---|---|
| `FACTORY` | `CL_SALV_TABLE` 객체를 생성하는 정적 메서드 |
| Changing Table | SALV가 출력할 Internal Table을 메서드에 전달하는 방식 |
| `DISPLAY` | 생성된 SALV 객체를 화면에 표시하는 실행 메서드 |

이 단계에서는 아직 Function 버튼 확장, Layout Variant, Sort, Filter, Column 최적화, Event, Hotspot, Cell Color 같은 심화 기능을 다루지 않는다.  
목표는 “Internal Table이 있으면 SALV로 표 형태 출력이 가능하다”는 핵심 흐름을 확실히 이해하는 것이다.

## 2. 선수 지식

이번 모듈은 다음 선수 지식 위에 놓인다.

| 선수 지식 | 필요한 이유 |
|---|---|
| Internal Table | SALV의 출력 대상이 Internal Table이기 때문이다. |
| Structure / Line Type | Internal Table의 필드가 ALV 컬럼으로 표시된다. |
| Open SQL `SELECT ... INTO TABLE` | DB 조회 결과를 SALV로 출력하는 기본 패턴을 만들 수 있다. |
| Object Reference | `lo_alv`와 같은 객체 참조 변수를 사용한다. |
| Static Method 호출 | `CL_SALV_TABLE=>FACTORY`는 정적 메서드 호출이다. |
| TRY...CATCH | SALV 객체 생성 오류를 처리하기 위해 필요하다. |

초급자에게 가장 중요한 선수 개념은 Internal Table이다.  
SALV는 DB 테이블을 직접 “자동 출력”하는 도구가 아니다. 보통은 DB에서 데이터를 조회하거나 프로그램에서 데이터를 만들어 Internal Table에 담은 뒤, 그 Internal Table을 SALV에 전달한다.

```text
DB Table 또는 프로그램 데이터
→ Internal Table
→ CL_SALV_TABLE=>FACTORY
→ lo_alv->display( )
→ ALV 화면 출력
```

## 3. FACTORY 메서드를 왜 사용하는가?

`CL_SALV_TABLE` 객체를 직접 `CREATE OBJECT`로 만드는 방식이 아니라, 일반적으로 `FACTORY` 메서드를 통해 생성한다.

초급자 입장에서는 `FACTORY`를 다음처럼 이해하면 된다.

```text
FACTORY = SALV 출력 객체를 만들어 주는 표준 생성 입구
```

개발자는 출력할 Internal Table을 전달하고, `FACTORY`는 그 Internal Table의 Line Type을 기반으로 SALV 객체를 만들어 준다.

가장 기본적인 형태는 다음과 같다.

```abap
DATA lo_alv TYPE REF TO cl_salv_table.

cl_salv_table=>factory(
  IMPORTING
    r_salv_table = lo_alv
  CHANGING
    t_table      = lt_data ).

lo_alv->display( ).
```

이 코드에서 중요한 것은 `FACTORY`가 화면 출력까지 수행하지 않는다는 점이다.  
`FACTORY`는 SALV 객체를 준비하고, 실제 화면 출력은 `DISPLAY`가 수행한다.

## 4. FACTORY 호출 구조 분석

### 4.1 전체 코드 형태

기본 호출 형태는 다음과 같다.

```abap
TRY.
    cl_salv_table=>factory(
      IMPORTING
        r_salv_table = lo_alv
      CHANGING
        t_table      = lt_data ).

    lo_alv->display( ).

  CATCH cx_salv_msg INTO DATA(lx_salv).
    MESSAGE lx_salv->get_text( ) TYPE 'I'.
ENDTRY.
```

이 코드는 세 부분으로 나눌 수 있다.

| 단계 | 코드 | 의미 |
|---|---|---|
| 1 | `cl_salv_table=>factory( ... )` | SALV 객체 생성 |
| 2 | `r_salv_table = lo_alv` | 생성된 SALV 객체 참조를 받음 |
| 3 | `t_table = lt_data` | 출력할 Internal Table을 전달 |
| 4 | `lo_alv->display( )` | SALV 화면 실행 |
| 5 | `CATCH cx_salv_msg` | SALV 생성 관련 예외 처리 |

---

## 5. `r_salv_table`의 의미

`r_salv_table`은 `FACTORY`가 생성한 SALV 객체 참조를 돌려주는 파라미터이다.

```abap
IMPORTING
  r_salv_table = lo_alv
```

여기서 `lo_alv`는 객체 참조 변수이다.

```abap
DATA lo_alv TYPE REF TO cl_salv_table.
```

호출 전에는 `lo_alv`가 비어 있다.  
`FACTORY` 호출이 성공하면 `lo_alv`는 생성된 SALV 객체를 가리키게 된다. 그 다음에는 이 객체를 통해 `DISPLAY` 같은 메서드를 호출한다.

```abap
lo_alv->display( ).
```

초급자 관점에서는 다음처럼 이해하면 된다.

```text
lo_alv = SALV 화면을 제어할 수 있는 리모컨
FACTORY = 리모컨을 만들어 주는 과정
DISPLAY = 리모컨의 실행 버튼
```

---

## 6. `t_table`의 의미

`t_table`은 SALV가 출력할 데이터를 담은 Internal Table이다.

```abap
CHANGING
  t_table = lt_data
```

여기서 `lt_data`는 Internal Table이어야 한다.

예를 들어 다음과 같은 Internal Table이 있다.

```abap
TYPES: BEGIN OF ty_user,
         user_id   TYPE char10,
         user_name TYPE char40,
         status    TYPE char1,
       END OF ty_user.

DATA lt_user TYPE STANDARD TABLE OF ty_user.
```

이 Internal Table을 `t_table`에 넘기면 SALV는 Line Type의 필드를 컬럼으로 해석한다.

| ABAP 필드 | SALV 컬럼 |
|---|---|
| `USER_ID` | USER_ID 컬럼 |
| `USER_NAME` | USER_NAME 컬럼 |
| `STATUS` | STATUS 컬럼 |

### 6.1 왜 `CHANGING`인가?

초급자가 자주 묻는 질문이다.

`FACTORY`에서 `t_table`은 `CHANGING` 파라미터로 정의되어 있다.  
이것은 메서드 시그니처의 표준 설계이다. 개발자는 “SALV가 이 Internal Table을 출력 대상으로 받는다”라고 이해하면 된다.

중요한 실무 감각은 다음이다.

```text
SALV에 넘기는 Internal Table은 화면에 표시할 최종 결과 데이터여야 한다.
```

즉, 데이터를 아직 조회하지 않았거나, 필터링·가공이 끝나지 않은 상태에서 넘기면 원하는 화면이 나오지 않는다.

## 7. 최소 예제 1: 직접 만든 Internal Table 출력

가장 단순한 예제는 프로그램 안에서 직접 Internal Table 데이터를 만들어 SALV로 출력하는 것이다.

```abap
REPORT zsalv_factory_demo_01.

TYPES: BEGIN OF ty_user,
         user_id   TYPE char10,
         user_name TYPE char40,
         status    TYPE char1,
       END OF ty_user.

DATA lt_user TYPE STANDARD TABLE OF ty_user.
DATA lo_alv  TYPE REF TO cl_salv_table.

APPEND VALUE #( user_id   = 'U0001'
                user_name = 'Kim Developer'
                status    = 'A' ) TO lt_user.

APPEND VALUE #( user_id   = 'U0002'
                user_name = 'Lee Consultant'
                status    = 'I' ) TO lt_user.

APPEND VALUE #( user_id   = 'U0003'
                user_name = 'Park Admin'
                status    = 'B' ) TO lt_user.

TRY.
    cl_salv_table=>factory(
      IMPORTING
        r_salv_table = lo_alv
      CHANGING
        t_table      = lt_user ).

    lo_alv->display( ).

  CATCH cx_salv_msg INTO DATA(lx_salv).
    MESSAGE lx_salv->get_text( ) TYPE 'I'.
ENDTRY.
```

### 7.1 실행 결과

실행하면 `USER_ID`, `USER_NAME`, `STATUS` 컬럼을 가진 ALV 화면이 표시된다.

| USER_ID | USER_NAME | STATUS |
|---|---|---|
| U0001 | Kim Developer | A |
| U0002 | Lee Consultant | I |
| U0003 | Park Admin | B |

### 7.2 이 예제에서 봐야 할 것

이 예제의 핵심은 다음이다.

```text
1. Internal Table을 준비한다.
2. FACTORY에 Internal Table을 전달한다.
3. FACTORY가 SALV 객체를 반환한다.
4. DISPLAY로 화면에 출력한다.
```

`WRITE` 구문이 한 줄도 없는데도 표 형태 화면이 출력된다는 점이 중요하다.

## 8. 최소 예제 2: 표준 테이블 조회 결과 출력

실무에 가까운 패턴은 Open SQL로 데이터를 조회한 뒤 SALV로 출력하는 것이다.

다음 예제는 SAP 교육 시스템에서 자주 사용되는 항공 데이터 테이블 `SFLIGHT`를 기준으로 한다.

```abap
REPORT zsalv_factory_demo_02.

DATA lo_alv TYPE REF TO cl_salv_table.

SELECT carrid,
       connid,
       fldate,
       price,
       currency
  FROM sflight
  INTO TABLE @DATA(lt_flight)
  UP TO 50 ROWS.

IF lt_flight IS INITIAL.
  MESSAGE '조회된 항공편 데이터가 없습니다.' TYPE 'I'.
  RETURN.
ENDIF.

TRY.
    cl_salv_table=>factory(
      IMPORTING
        r_salv_table = lo_alv
      CHANGING
        t_table      = lt_flight ).

    lo_alv->display( ).

  CATCH cx_salv_msg INTO DATA(lx_salv).
    MESSAGE lx_salv->get_text( ) TYPE 'I'.
ENDTRY.
```

### 8.1 `UP TO 50 ROWS`를 넣는 이유

초급 실습에서는 불필요하게 많은 데이터를 읽지 않는 것이 좋다.

```abap
UP TO 50 ROWS
```

이 구문은 최대 50건만 조회한다. 교육용 예제에서는 화면 출력과 흐름 이해가 목적이므로 적절하다.

### 8.2 `lt_flight IS INITIAL` 확인

조회 결과가 없으면 SALV 화면을 띄울 수는 있지만, 빈 화면이 표시된다.  
초급 실습에서는 빈 화면을 오류로 오해하기 쉽기 때문에 먼저 데이터를 확인하는 습관이 좋다.

```abap
IF lt_flight IS INITIAL.
  MESSAGE '조회된 항공편 데이터가 없습니다.' TYPE 'I'.
  RETURN.
ENDIF.
```

## 9. FACTORY와 DISPLAY의 역할 분리

초급자는 `FACTORY`와 `DISPLAY`를 하나의 동작으로 생각하기 쉽다. 하지만 두 메서드의 역할은 다르다.

| 메서드 | 역할 |
|---|---|
| `CL_SALV_TABLE=>FACTORY` | SALV 객체 생성 및 출력 대상 테이블 연결 |
| `LO_ALV->DISPLAY( )` | 실제 ALV 화면 표시 |

흐름을 문장으로 표현하면 다음과 같다.

```text
FACTORY로 SALV 객체를 준비하고,
DISPLAY로 화면을 실행한다.
```

이 구분은 후속 모듈에서 중요해진다.  
왜냐하면 `DISPLAY`를 호출하기 전에 Function, Column, Layout 같은 속성을 설정할 수 있기 때문이다.

예를 들어 후속 모듈에서는 다음과 같은 흐름으로 확장된다.

```abap
cl_salv_table=>factory(
  IMPORTING r_salv_table = lo_alv
  CHANGING  t_table      = lt_data ).

lo_alv->get_functions( )->set_all( abap_true ).
lo_alv->display( ).
```

즉, `FACTORY`와 `DISPLAY` 사이가 SALV 설정을 추가하는 위치가 된다.

## 10. 객체 참조 변수 `lo_alv`

`lo_alv`는 SALV 객체를 가리키는 참조 변수이다.

```abap
DATA lo_alv TYPE REF TO cl_salv_table.
```

ABAP 초급 문법에서는 일반 변수만 많이 다루지만, SALV부터는 객체 참조를 사용하게 된다.

| 구분 | 예시 | 설명 |
|---|---|---|
| 일반 변수 | `DATA lv_name TYPE string.` | 값을 직접 담음 |
| Internal Table | `DATA lt_data TYPE TABLE OF ...` | 여러 행을 담음 |
| 객체 참조 | `DATA lo_alv TYPE REF TO cl_salv_table.` | 객체를 가리킴 |

초급자는 객체지향을 모두 이해하지 않아도 다음만 기억하면 된다.

```text
lo_alv는 SALV 객체를 조작하기 위한 변수이다.
FACTORY가 성공하면 lo_alv를 통해 DISPLAY를 호출할 수 있다.
```

## 11. TRY...CATCH와 `CX_SALV_MSG`

`CL_SALV_TABLE=>FACTORY`는 SALV 객체 생성 중 문제가 발생할 수 있으므로 예외 처리를 포함하는 것이 좋다.

기본 구조는 다음과 같다.

```abap
TRY.
    cl_salv_table=>factory(
      IMPORTING
        r_salv_table = lo_alv
      CHANGING
        t_table      = lt_data ).

    lo_alv->display( ).

  CATCH cx_salv_msg INTO DATA(lx_salv).
    MESSAGE lx_salv->get_text( ) TYPE 'I'.
ENDTRY.
```

### 11.1 왜 예외 처리를 하는가?

실습 코드에서는 예외가 잘 발생하지 않을 수 있다.  
하지만 실무 코드에서는 화면 출력, 데이터 구조, 런타임 환경, 호출 위치에 따라 예외 가능성을 고려해야 한다.

예외 처리를 해두면 다음 장점이 있다.

| 장점 | 설명 |
|---|---|
| 오류 원인 확인 | 예외 메시지를 사용자 또는 개발자에게 보여줄 수 있다. |
| 비정상 종료 방지 | 프로그램이 갑자기 중단되는 것을 줄일 수 있다. |
| 유지보수성 향상 | 오류 발생 위치와 처리 흐름이 명확해진다. |

### 11.2 MESSAGE 처리 주의

교육용 예제에서는 다음처럼 간단히 메시지를 보여준다.

```abap
MESSAGE lx_salv->get_text( ) TYPE 'I'.
```

실무에서는 메시지 클래스, 로그, 예외 재전달, 사용자 메시지 정책 등을 고려할 수 있다.  
하지만 이번 모듈에서는 “예외를 무시하지 않는다”는 습관이 핵심이다.

## 12. Internal Table이 비어 있을 때

Internal Table이 비어 있어도 SALV 객체 생성 자체가 항상 오류로 이어지는 것은 아니다.  
다만 화면에는 데이터가 없는 리스트가 표시될 수 있다.

초급자가 혼동하지 않도록 다음 패턴을 권장한다.

```abap
IF lt_data IS INITIAL.
  MESSAGE '출력할 데이터가 없습니다.' TYPE 'I'.
  RETURN.
ENDIF.
```

이 패턴은 SALV 고유 기능이라기보다 리포트 프로그램의 사용자 경험을 개선하는 기본 처리이다.

| 상황 | 권장 처리 |
|---|---|
| 교육용 실습 | 빈 테이블이면 메시지 출력 후 종료 |
| 실무 조회 리포트 | 조회 조건, 권한, 데이터 존재 여부 확인 메시지 제공 |
| 분석용 프로그램 | 빈 결과도 의미가 있다면 빈 ALV 표시 가능 |

## 13. Line Type과 컬럼 생성 원리

SALV는 Internal Table의 Line Type을 보고 컬럼을 만든다.

예를 들어 다음 구조가 있다고 하자.

```abap
TYPES: BEGIN OF ty_flight,
         carrid   TYPE sflight-carrid,
         connid   TYPE sflight-connid,
         fldate   TYPE sflight-fldate,
         price    TYPE sflight-price,
         currency TYPE sflight-currency,
       END OF ty_flight.

DATA lt_flight TYPE STANDARD TABLE OF ty_flight.
```

SALV는 `TY_FLIGHT` 안의 필드를 컬럼으로 표시한다.

| Line Type 필드 | SALV 컬럼 |
|---|---|
| CARRID | CARRID |
| CONNID | CONNID |
| FLDATE | FLDATE |
| PRICE | PRICE |
| CURRENCY | CURRENCY |

만약 Line Type이 DDIC 필드 또는 DDIC Data Element를 참조한다면, 화면에서 컬럼 텍스트나 형식이 더 자연스럽게 표시될 수 있다.

따라서 실무에서는 가능하면 DDIC 타입을 적절히 활용하는 것이 좋다.

```abap
TYPES: BEGIN OF ty_flight,
         carrid   TYPE s_carr_id,
         connid   TYPE s_conn_id,
         fldate   TYPE s_date,
       END OF ty_flight.
```

[추정] 교육 시스템의 SAP_BASIS/SAP_ABA 릴리스와 항공 예제 데이터 설치 여부에 따라 `SFLIGHT`, 관련 Data Element의 존재 여부나 데이터 건수는 다를 수 있다.

## 14. SALV 출력 전 데이터 준비 기준

SALV는 “데이터를 예쁘게 보여주는 도구”이지 “업무 데이터를 대신 판단하는 도구”가 아니다.  
따라서 SALV 호출 전에 데이터가 적절히 준비되어 있어야 한다.

출력 전 점검 기준은 다음과 같다.

| 점검 항목 | 설명 |
|---|---|
| 데이터 존재 여부 | Internal Table이 비어 있지 않은가? |
| 컬럼 수 | 너무 많은 필드를 무작정 출력하지 않았는가? |
| 업무 의미 | 컬럼명이 사용자에게 이해 가능한가? |
| 데이터 양 | 교육용/실무용 기준으로 너무 많은 건수를 한 번에 출력하지 않는가? |
| 정렬 필요성 | 1차 모듈에서는 심화 정렬 전, 기본 조회 순서를 이해한다. |
| 권한 | 실제 업무 데이터 조회 시 권한 검토가 필요한가? |

초급 실습에서는 `UP TO 50 ROWS`처럼 출력량을 제한하는 습관이 좋다.  
실무에서는 조회 조건 없이 대량 테이블을 모두 읽어 SALV로 보여주는 방식은 피해야 한다.

## 15. 실습: FACTORY로 Internal Table 출력

### 15.1 실습 목표

직접 만든 Internal Table을 `CL_SALV_TABLE=>FACTORY`에 전달하고, `DISPLAY`로 출력한다.

### 15.2 실습 프로그램 이름

```text
ZSALV_FACTORY_USER
```

### 15.3 실습 코드

```abap
REPORT zsalv_factory_user.

TYPES: BEGIN OF ty_user,
         user_id   TYPE char10,
         user_name TYPE char40,
         role_name TYPE char20,
         status    TYPE char1,
       END OF ty_user.

DATA lt_user TYPE STANDARD TABLE OF ty_user.
DATA lo_alv  TYPE REF TO cl_salv_table.

lt_user = VALUE #(
  ( user_id = 'U0001' user_name = 'Kim Developer' role_name = 'ABAP' status = 'A' )
  ( user_id = 'U0002' user_name = 'Lee Consultant' role_name = 'MM'   status = 'A' )
  ( user_id = 'U0003' user_name = 'Park Admin'     role_name = 'BC'   status = 'I' )
).

IF lt_user IS INITIAL.
  MESSAGE '출력할 사용자 데이터가 없습니다.' TYPE 'I'.
  RETURN.
ENDIF.

TRY.
    cl_salv_table=>factory(
      IMPORTING
        r_salv_table = lo_alv
      CHANGING
        t_table      = lt_user ).

    lo_alv->display( ).

  CATCH cx_salv_msg INTO DATA(lx_salv).
    MESSAGE lx_salv->get_text( ) TYPE 'I'.
ENDTRY.
```

### 15.4 실습 결과 확인

실행 후 다음 컬럼이 ALV 화면에 표시되어야 한다.

```text
USER_ID
USER_NAME
ROLE_NAME
STATUS
```

데이터는 3건이 표시되어야 한다.

### 15.5 실습 중 기록할 항목

| 기록 항목 | 예시 |
|---|---|
| 프로그램명 | ZSALV_FACTORY_USER |
| Internal Table명 | LT_USER |
| SALV 객체명 | LO_ALV |
| 출력 건수 | 3건 |
| 예외 클래스 | CX_SALV_MSG |
| 오류 발생 여부 | 성공 / 실패 |

## 16. 실습: SELECT 결과를 SALV로 출력

### 16.1 실습 목표

표준 예제 테이블에서 데이터를 조회해 Internal Table에 담고, SALV로 출력한다.

### 16.2 실습 프로그램 이름

```text
ZSALV_FACTORY_FLIGHT
```

### 16.3 실습 코드

```abap
REPORT zsalv_factory_flight.

DATA lo_alv TYPE REF TO cl_salv_table.

SELECT carrid,
       connid,
       fldate,
       price,
       currency
  FROM sflight
  INTO TABLE @DATA(lt_flight)
  UP TO 50 ROWS.

IF lt_flight IS INITIAL.
  MESSAGE '조회된 항공편 데이터가 없습니다.' TYPE 'I'.
  RETURN.
ENDIF.

TRY.
    cl_salv_table=>factory(
      IMPORTING
        r_salv_table = lo_alv
      CHANGING
        t_table      = lt_flight ).

    lo_alv->display( ).

  CATCH cx_salv_msg INTO DATA(lx_salv).
    MESSAGE lx_salv->get_text( ) TYPE 'I'.
ENDTRY.
```

### 16.4 실습 해석

이 코드는 다음 흐름을 가진다.

```text
SFLIGHT에서 데이터 조회
→ LT_FLIGHT Internal Table에 저장
→ FACTORY로 SALV 객체 생성
→ DISPLAY로 결과 출력
```

초급자는 여기서 Open SQL 문법을 깊게 확장하지 않는다.  
Open SQL 심화는 이미 앞선 Section과 후속 Section에서 다루며, 여기서는 SALV 연결 흐름이 핵심이다.

## 17. 오류 상황과 해결

### 17.1 `LO_ALV`가 선언되지 않음

#### 증상

```text
Field "LO_ALV" is unknown.
```

#### 원인

SALV 객체 참조 변수를 선언하지 않았다.

#### 해결

```abap
DATA lo_alv TYPE REF TO cl_salv_table.
```

---

### 17.2 `LT_DATA`가 Internal Table이 아님

#### 증상

`t_table`에 단일 구조 또는 일반 변수를 넘겨 오류가 발생한다.

#### 원인

SALV는 표 형태 출력을 위해 Internal Table을 기대한다.

#### 해결

```abap
DATA lt_data TYPE STANDARD TABLE OF ty_data.
```

단일 구조 `ls_data`가 아니라 `lt_data`를 전달해야 한다.

---

### 17.3 `DISPLAY`를 호출하지 않음

#### 증상

프로그램은 오류 없이 끝났지만 화면에 ALV가 나타나지 않는다.

#### 원인

`FACTORY`만 호출하고 `lo_alv->display( )`를 호출하지 않았다.

#### 해결

```abap
lo_alv->display( ).
```

---

### 17.4 조회 결과가 없음

#### 증상

ALV 화면이 비어 있거나 “조회된 데이터가 없습니다” 메시지가 표시된다.

#### 원인

조회 조건에 맞는 데이터가 없거나, 교육 시스템에 항공 예제 데이터가 없을 수 있다.

#### 해결

1. 조건을 줄인다.
2. `UP TO 50 ROWS`만 두고 WHERE 조건을 제거한다.
3. SE16N 또는 ADT Data Preview에서 `SFLIGHT` 데이터 존재 여부를 확인한다.
4. 교육 시스템의 샘플 데이터 적재 여부를 확인한다.

---

### 17.5 `CX_SALV_MSG` 예외 처리 누락

#### 증상

Syntax Check 또는 ATC에서 예외 처리 관련 메시지를 볼 수 있다.

#### 원인

`FACTORY` 호출에서 발생 가능한 예외를 처리하지 않았다.

#### 해결

`TRY...CATCH cx_salv_msg` 구조를 사용한다.

```abap
TRY.
    cl_salv_table=>factory(
      IMPORTING r_salv_table = lo_alv
      CHANGING  t_table      = lt_data ).
  CATCH cx_salv_msg INTO DATA(lx_salv).
    MESSAGE lx_salv->get_text( ) TYPE 'I'.
ENDTRY.
```

## 18. 실무 적용 기준

### 18.1 SALV FACTORY 패턴이 적합한 경우

| 상황 | 적합성 |
|---|---|
| 조회 결과를 빠르게 표로 확인 | 적합 |
| Internal Table 가공 결과를 단순 출력 | 적합 |
| 교육용/검증용 리포트 | 적합 |
| 복잡한 셀 편집, 이벤트, 커스텀 UI | 제한적 |
| 대화형 대량 데이터 편집 | 부적합 |

SALV는 특히 읽기 전용 리스트 출력에 적합하다.  
셀 단위 편집이나 복잡한 화면 제어가 필요하면 Grid ALV 또는 별도 UI 기술을 검토해야 한다.

### 18.2 데이터 조회와 SALV 출력의 책임 분리

실무 코드에서는 데이터 조회와 화면 출력 책임을 분리하는 것이 좋다.

좋은 사고 흐름은 다음과 같다.

```text
1. 조회 조건을 검증한다.
2. DB에서 필요한 필드만 조회한다.
3. Internal Table을 업무 기준으로 가공한다.
4. 출력 대상 Internal Table을 SALV에 전달한다.
5. DISPLAY 직전 필요한 ALV 설정을 적용한다.
```

SALV는 4~5번 영역에 가깝다.  
즉, SALV 객체에게 업무 데이터 조회 책임까지 떠넘기면 안 된다.

### 18.3 대량 데이터 주의

초급 예제에서는 `SELECT *`와 전체 조회가 편해 보일 수 있다.  
하지만 실무에서는 대량 데이터 조회가 성능 문제를 일으킬 수 있다.

권장 기준은 다음이다.

| 기준 | 설명 |
|---|---|
| 필요한 필드만 조회 | 불필요한 컬럼을 줄인다. |
| 조건을 사용 | 전체 테이블 조회를 피한다. |
| 건수 제한 | 교육용이면 `UP TO n ROWS` 사용 가능 |
| 사용자 입력 활용 | Selection Screen 조건과 연결 |
| 권한 확인 | 민감 데이터 조회 시 권한 검토 |

## 19. 강사용 설명 포인트

강의에서는 다음 순서로 설명하면 초급자가 이해하기 쉽다.

```text
WRITE로는 표 형태 출력이 불편하다.
Internal Table은 이미 표 형태 데이터이다.
SALV는 Internal Table을 화면 표 형태로 보여준다.
FACTORY는 SALV 객체를 만든다.
DISPLAY는 화면을 띄운다.
```

강사가 특히 강조할 문장은 다음이다.

```text
FACTORY는 출력할 데이터를 받는 단계이고,
DISPLAY는 실제 화면을 보여주는 단계입니다.
```

또한 다음 질문으로 학습자의 이해를 점검할 수 있다.

1. `FACTORY`만 호출하고 `DISPLAY`를 호출하지 않으면 어떻게 될까요?
2. `t_table`에 Internal Table이 아니라 Structure를 넘기면 왜 문제가 될까요?
3. SALV가 DB에서 데이터를 직접 가져오는 도구가 아니라는 말은 무슨 뜻일까요?
4. `FACTORY`와 `DISPLAY` 사이에 코드를 넣는 이유는 무엇일까요?

## 20. 평가 문제

### 20.1 객관식

#### Q1. `CL_SALV_TABLE=>FACTORY`의 가장 적절한 역할은 무엇인가?

A. 데이터베이스 테이블을 생성한다.  
B. SALV 출력 객체를 생성하고 Internal Table과 연결한다.  
C. ABAP 프로그램을 활성화한다.  
D. Selection Screen을 생성한다.

**정답:** B

#### Q2. `lo_alv->display( )`의 역할은 무엇인가?

A. Internal Table에 데이터를 추가한다.  
B. SALV 화면을 실제로 표시한다.  
C. DDIC Structure를 생성한다.  
D. SQL 조건을 자동 생성한다.

**정답:** B

#### Q3. `t_table`에 전달해야 하는 것은 무엇인가?

A. 단일 문자 변수  
B. Message Class  
C. Internal Table  
D. Transaction Code

**정답:** C

### 20.2 단답형

#### Q1. `r_salv_table = lo_alv`의 의미를 설명하시오.

**모범 답안:**  
`FACTORY`가 생성한 SALV 객체 참조를 `lo_alv` 변수에 전달받는다는 의미이다. 이후 `lo_alv`를 통해 `display( )` 같은 메서드를 호출할 수 있다.

#### Q2. `FACTORY`와 `DISPLAY`의 차이를 설명하시오.

**모범 답안:**  
`FACTORY`는 SALV 객체를 생성하고 출력할 Internal Table과 연결하는 단계이며, `DISPLAY`는 생성된 SALV 객체를 실제 화면에 표시하는 단계이다.

#### Q3. Internal Table이 비어 있을 때 어떤 처리를 할 수 있는가?

**모범 답안:**  
`IF lt_data IS INITIAL.` 조건으로 먼저 확인하고, 출력할 데이터가 없다는 메시지를 표시한 뒤 `RETURN`으로 종료할 수 있다. 상황에 따라 빈 ALV를 보여줄 수도 있지만 초급 실습에서는 메시지 처리가 이해하기 쉽다.
