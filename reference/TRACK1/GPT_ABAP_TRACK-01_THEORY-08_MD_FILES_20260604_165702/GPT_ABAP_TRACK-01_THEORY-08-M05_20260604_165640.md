## 3. SALV 1차에서 이미 다룬 범위

THEORY-08의 1차 목표는 **Internal Table 결과를 가장 단순한 ALV 형태로 시각화하는 것**이다.

즉, 핵심은 다음이다.

```text
Internal Table을 준비한다.
CL_SALV_TABLE=>FACTORY로 SALV 객체를 생성한다.
필요한 기본 기능을 켠다.
DISPLAY로 화면에 출력한다.
```

가장 기본적인 형태는 다음과 같다.

```abap
REPORT zgpt_salv_basic_scope.

TYPES: BEGIN OF ty_student,
         student_id TYPE c LENGTH 10,
         name       TYPE c LENGTH 30,
         score      TYPE i,
         grade      TYPE c LENGTH 1,
       END OF ty_student.

DATA gt_student TYPE STANDARD TABLE OF ty_student.
DATA go_salv    TYPE REF TO cl_salv_table.

gt_student = VALUE #(
  ( student_id = 'S0001' name = 'Kim Beginner' score = 95 grade = 'A' )
  ( student_id = 'S0002' name = 'Lee Junior'   score = 82 grade = 'B' )
  ( student_id = 'S0003' name = 'Park Trainee' score = 71 grade = 'C' )
).

TRY.
    cl_salv_table=>factory(
      IMPORTING
        r_salv_table = go_salv
      CHANGING
        t_table      = gt_student
    ).

    go_salv->get_functions( )->set_all( abap_true ).
    go_salv->display( ).

  CATCH cx_salv_msg INTO DATA(lx_salv).
    MESSAGE lx_salv->get_text( ) TYPE 'E'.
ENDTRY.
```

이 코드에서 1차 학습의 핵심은 네 가지이다.

| 핵심 | 설명 |
|---|---|
| Internal Table | 출력할 데이터의 원본 |
| `CL_SALV_TABLE=>FACTORY` | Internal Table을 SALV 객체로 감싸는 생성 메서드 |
| `GET_FUNCTIONS( )->SET_ALL( )` | 기본 Toolbar Function 표시 |
| `DISPLAY( )` | SALV 화면 출력 |

초급자는 이 네 가지가 자연스럽게 설명될 때까지 반복해야 한다.

## 4. SALV 1차 범위의 핵심 원칙

### 4.1 1차 목표는 “예쁘게 꾸미기”가 아니다

SALV를 처음 배우는 단계에서 목표는 화면을 멋지게 꾸미는 것이 아니다.  
목표는 **Internal Table 결과를 안정적으로 ALV 화면에 표시하는 것**이다.

따라서 1차에서는 다음 질문에 답할 수 있어야 한다.

```text
내 Internal Table에는 어떤 데이터가 들어 있는가?
그 Internal Table이 SALV에 제대로 전달되는가?
FACTORY 호출은 성공하는가?
DISPLAY가 정상 실행되는가?
조회 결과가 없을 때 어떻게 처리하는가?
오류가 발생하면 어떤 예외를 확인하는가?
```

### 4.2 출력보다 데이터 준비가 먼저다

SALV 화면은 결국 Internal Table의 내용을 보여준다.  
Internal Table이 잘못 준비되어 있으면 SALV 화면도 잘못 나온다.

예를 들어 다음 상황을 생각해보자.

```abap
SELECT carrid,
       connid,
       fldate
  FROM sflight
  INTO TABLE @DATA(lt_flight)
  WHERE carrid = 'XX'.
```

조회 결과가 없으면 SALV는 비어 있는 테이블을 출력할 수 있다.  
이때 문제는 SALV가 아니라 데이터 준비 단계이다.

초급자는 화면 결과만 보고 판단하면 안 된다.

```text
화면이 비어 있다.
→ SALV 오류인가?
→ SELECT 결과가 비어 있는가?
→ WHERE 조건이 너무 좁은가?
→ 테스트 데이터가 존재하는가?
```

이 순서로 점검해야 한다.

### 4.3 SALV는 초급 출력 도구로 적합하다

Classic List의 `WRITE` 출력은 기본 문법 학습에는 좋지만, 실무 리스트 화면으로는 한계가 있다.  
SALV는 초급자가 Internal Table 결과를 표 형태로 확인하기 좋다.

| 출력 방식 | 초급 학습에서의 역할 |
|---|---|
| WRITE | 가장 기본적인 List 출력과 문법 확인 |
| SALV | Internal Table 결과를 표 형태로 빠르게 확인 |
| Grid ALV | 화면 제어, 이벤트, 필드 카탈로그 등 심화 UI 제어 |
| Fiori/RAP List Report | 현대적인 비즈니스 앱 UI |

THEORY-08의 목표는 Grid ALV나 Fiori가 아니라, **가장 단순한 SALV 기반 시각화**이다.

## 5. 이번 Section에서 의도적으로 미루는 항목

이 모듈의 기술 키워드는 다음이다.

```text
Sort Deferred
Layout Deferred
Variant Deferred
```

즉, Sort, Layout, Variant는 중요한 주제이지만 이번 Section의 중심 주제가 아니다.

### 5.1 Sort Deferred

SALV에서 정렬은 매우 유용하다.  
예를 들어 점수 내림차순, 항공사별 정렬, 날짜별 정렬 같은 기능은 실무에서 자주 필요하다.

하지만 초급 단계에서는 정렬을 SALV Method로 처리하기 전에 다음을 먼저 알아야 한다.

```text
Internal Table 자체의 정렬은 무엇인가?
SORT 구문은 어떻게 동작하는가?
정렬 기준 필드는 어떤 타입인가?
정렬을 DB에서 할 것인가, ABAP에서 할 것인가, SALV 화면에서 할 것인가?
```

이 질문에 답하지 못한 상태에서 SALV Sort Method만 외우면 학습이 흔들린다.

따라서 THEORY-08 1차에서는 정렬을 깊게 다루지 않는다.  
정렬 자체는 Internal Table과 Open SQL 학습 이후에 더 자연스럽게 이해할 수 있다.

### 5.2 Layout Deferred

SALV Layout은 사용자가 컬럼 배치, 표시 상태, 폭, 저장된 레이아웃 등을 관리하는 주제와 연결된다.  
이것은 단순 출력보다 한 단계 더 운영적인 주제이다.

Layout을 제대로 이해하려면 다음 개념이 필요하다.

```text
사용자별 화면 설정
공통 Layout과 개인 Layout
Variant 저장 가능 여부
프로그램 ID와 Layout Key
권한과 운영 정책
```

초급자가 아직 REPORT 구조, Internal Table, Function, Selection Screen을 배우는 단계에서 Layout까지 깊게 들어가면 과부하가 크다.

따라서 이번 Section에서는 Layout을 “후속 심화 주제”로 남겨둔다.

### 5.3 Variant Deferred

Variant는 프로그램 실행 조건이나 화면 설정을 저장하는 개념과 연결될 수 있다.  
SALV Layout Variant와 Selection Screen Variant는 서로 다른 맥락도 가지고 있다.

Variant를 설명하려면 다음 주제가 함께 필요하다.

```text
Selection Screen
Report Variant
Layout Variant
사용자별 저장
공통 저장
Transport 가능성
권한
운영 배포 기준
```

이 주제는 초급 SALV 1차에서 다루기에는 범위가 넓다.  
따라서 THEORY-08에서는 Variant를 사용하지 않고, 후속 Section에서 다시 다룬다.

## 6. “미룬다”와 “몰라도 된다”는 다르다

Sort, Layout, Variant를 지금 자세히 다루지 않는다고 해서 중요하지 않은 것은 아니다.  
오히려 실무에서는 매우 중요하다.

다만 학습 순서상 지금은 다음을 우선해야 한다.

| 지금 우선할 것 | 나중에 확장할 것 |
|---|---|
| Internal Table을 SALV로 출력 | Sort / Filter |
| FACTORY 호출 구조 이해 | Column 개별 제어 |
| DISPLAY 실행 흐름 이해 | Layout 저장 |
| 기본 Function 활성화 | Variant 관리 |
| 오류 흐름 이해 | Event, Toolbar 확장 |
| 초급 Report 출력 | Grid ALV 심화 제어 |

초급자의 학습은 기능 수를 많이 외우는 것이 아니라, 가장 중요한 흐름을 안정적으로 반복하는 데서 시작한다.

## 7. SALV 1차 완료 기준

THEORY-08을 완료했다고 판단하려면 다음을 스스로 할 수 있어야 한다.

### 7.1 코드 작성 기준

아무 예제 없이도 다음 골격을 작성할 수 있어야 한다.

```abap
DATA go_salv TYPE REF TO cl_salv_table.

TRY.
    cl_salv_table=>factory(
      IMPORTING
        r_salv_table = go_salv
      CHANGING
        t_table      = gt_data
    ).

    go_salv->get_functions( )->set_all( abap_true ).
    go_salv->display( ).

  CATCH cx_salv_msg INTO DATA(lx_salv).
    MESSAGE lx_salv->get_text( ) TYPE 'E'.
ENDTRY.
```

### 7.2 설명 기준

다음 질문에 답할 수 있어야 한다.

| 질문 | 기대 답변 |
|---|---|
| `GT_DATA`는 무엇인가? | SALV로 출력할 Internal Table이다. |
| `R_SALV_TABLE`은 무엇인가? | 생성된 SALV 객체 참조를 받는 파라미터이다. |
| `T_TABLE`은 무엇인가? | SALV가 출력할 Internal Table을 전달하는 파라미터이다. |
| `DISPLAY`는 언제 호출하는가? | SALV 객체 생성과 기본 설정 후 화면 출력을 위해 호출한다. |
| `CX_SALV_MSG`는 왜 필요한가? | SALV 생성 또는 출력 준비 중 발생 가능한 예외를 처리하기 위해 필요하다. |
| Sort/Layout/Variant는 왜 지금 깊게 다루지 않는가? | Internal Table, Selection Screen, 운영 설정 개념 이후에 다루는 편이 더 적절하기 때문이다. |

### 7.3 실습 기준

다음 조건을 만족하는 미니 리포트를 작성할 수 있어야 한다.

```text
1. Internal Table을 직접 구성하거나 SELECT 결과로 준비한다.
2. CL_SALV_TABLE=>FACTORY를 호출한다.
3. 기본 Function을 활성화한다.
4. DISPLAY를 호출한다.
5. 조회 결과가 없을 때 메시지를 출력한다.
6. CX_SALV_MSG 예외를 처리한다.
```

## 8. 실습: SALV 1차 범위 점검 리포트

### 8.1 실습 목표

앞선 모듈에서 배운 내용을 모두 연결하여, SALV 1차 범위에 맞는 미니 리포트를 작성한다.

### 8.2 실습 코드

```abap
REPORT zgpt_salv_scope_check.

TYPES: BEGIN OF ty_result,
         category TYPE c LENGTH 10,
         item     TYPE c LENGTH 30,
         amount   TYPE p LENGTH 8 DECIMALS 2,
         status   TYPE c LENGTH 1,
       END OF ty_result.

DATA gt_result TYPE STANDARD TABLE OF ty_result.
DATA go_salv   TYPE REF TO cl_salv_table.

gt_result = VALUE #(
  ( category = 'SALES' item = 'Notebook' amount = '1200.00' status = 'A' )
  ( category = 'SALES' item = 'Monitor'  amount = '350.00'  status = 'A' )
  ( category = 'COST'  item = 'License'  amount = '180.00'  status = 'I' )
).

IF gt_result IS INITIAL.
  MESSAGE 'No data to display.' TYPE 'S'.
  RETURN.
ENDIF.

TRY.
    cl_salv_table=>factory(
      IMPORTING
        r_salv_table = go_salv
      CHANGING
        t_table      = gt_result
    ).

    go_salv->get_functions( )->set_all( abap_true ).

    go_salv->display( ).

  CATCH cx_salv_msg INTO DATA(lx_salv).
    MESSAGE lx_salv->get_text( ) TYPE 'E'.
ENDTRY.
```

### 8.3 실습 해설

| 코드 | 의미 |
|---|---|
| `TYPES BEGIN OF ty_result` | 출력용 Row 구조를 정의한다. |
| `GT_RESULT` | SALV로 출력할 Internal Table이다. |
| `VALUE #( ... )` | 테스트 데이터를 직접 구성한다. |
| `IF gt_result IS INITIAL` | 출력할 데이터가 없는 경우를 먼저 처리한다. |
| `CL_SALV_TABLE=>FACTORY` | Internal Table을 SALV 객체로 변환한다. |
| `GET_FUNCTIONS( )->SET_ALL( )` | 기본 Function을 표시한다. |
| `DISPLAY` | SALV 화면을 출력한다. |
| `CATCH CX_SALV_MSG` | SALV 관련 메시지 예외를 처리한다. |

### 8.4 이 실습에서 일부러 하지 않는 것

이 실습에서는 다음을 의도적으로 하지 않는다.

```text
컬럼 텍스트 변경
컬럼 폭 자동 최적화
정렬 추가
필터 추가
Layout 저장
Variant 저장
이벤트 처리
Hotspot 처리
Cell Color 처리
Editable Grid 처리
```

이유는 명확하다.  
THEORY-08의 학습 목표는 “SALV 기본 출력 흐름”이지 “ALV 전체 기능 마스터”가 아니기 때문이다.

| Column Text | 제한적 언급 가능 | O |
| Column Optimize | 제한적 언급 가능 | O |
| Event | 제외 | O |
| Toolbar Customizing | 제외 | O |
| Editable ALV | 제외 | Grid ALV 영역 |
| Cell Color / Style | 제외 | Grid ALV 심화 |
| `CL_GUI_ALV_GRID` | 비교만 가능 | 별도 Section |

---

## 10. SALV와 Grid ALV의 경계

SALV와 Grid ALV는 둘 다 ALV 계열이지만 학습 목적이 다르다.

| 구분 | SALV | Grid ALV |
|---|---|---|
| 대표 클래스 | `CL_SALV_TABLE` | `CL_GUI_ALV_GRID` |
| 초급 사용성 | 매우 간단 | 상대적으로 복잡 |
| 기본 출력 | 쉽다 | 설정이 많다 |
| Field Catalog | 명시적으로 덜 필요 | 중요 |
| 화면 컨테이너 | 기본 List 형태 가능 | Custom Container와 연결되는 경우 많음 |
| 이벤트/편집 제어 | 제한적 | 강력함 |
| Cell Color/Style | 제한적 | 심화 구현 가능 |
| 학습 위치 | Internal Table 응용 직후 | Screen Programming 이후 |

THEORY-08에서는 SALV를 통해 “Internal Table 결과를 빠르게 시각화하는 경험”을 얻는다.  
Grid ALV는 후속 Section에서 Screen Programming과 함께 다루는 것이 더 적절하다.

---

## 11. 실무에서 SALV를 선택하기 좋은 경우

SALV는 다음 경우에 특히 적합하다.

| 상황 | 이유 |
|---|---|
| 간단한 조회 결과를 표로 보여주고 싶을 때 | 구현량이 적다. |
| Internal Table 내용을 빠르게 검증하고 싶을 때 | FACTORY + DISPLAY 패턴이 단순하다. |
| 편집이 필요 없는 리포트 | SALV의 기본 사용 목적과 잘 맞는다. |
| 초급 학습용 리포트 | ALV 개념을 빠르게 체험할 수 있다. |
| 프로토타입 또는 내부 조회 도구 | 개발 속도가 빠르다. |

실무에서 SALV는 “가볍고 빠른 조회형 리스트”에 적합하다.

---

## 12. SALV보다 Grid ALV가 더 적합한 경우

다음 경우에는 SALV보다 Grid ALV 또는 다른 UI 기술을 검토하는 것이 좋다.

| 상황 | 이유 |
|---|---|
| 사용자가 셀을 직접 편집해야 함 | Grid ALV가 더 적합하다. |
| Cell Color, Style, Button 등 세밀한 화면 제어 필요 | Grid ALV 심화 기능이 필요하다. |
| 화면 내 여러 영역을 컨테이너로 제어해야 함 | Screen + Custom Container 이해가 필요하다. |
| 복잡한 이벤트 처리가 필요 | SALV보다 Grid ALV가 적합할 수 있다. |
| Fiori 기반 업무 앱이 목표 | RAP/Fiori Elements를 검토해야 한다. |

초급자는 여기서 “SALV가 나쁘다”라고 이해하면 안 된다.  
도구마다 목적이 다르다.

```text
단순 조회형 리스트 → SALV
복잡한 화면 제어와 편집 → Grid ALV
현대적 업무 앱 → Fiori/RAP
```

## 13. 오류 상황 정리

### 13.1 Internal Table이 비어 있음

#### 상황

SALV 화면이 뜨지만 데이터가 없다.

#### 원인

대부분 SALV 문제가 아니라 Internal Table이 비어 있기 때문이다.

#### 점검

```abap
IF gt_data IS INITIAL.
  MESSAGE 'No data to display.' TYPE 'S'.
  RETURN.
ENDIF.
```

### 13.2 FACTORY 호출 시 타입 문제

#### 상황

`CL_SALV_TABLE=>FACTORY` 호출에서 오류가 발생한다.

#### 가능 원인

- `T_TABLE`에 Internal Table이 아닌 데이터를 넘김
- 선언이 불명확함
- 참조 변수 타입이 맞지 않음
- 구조가 너무 복잡하거나 출력에 적합하지 않음

#### 점검

```abap
DATA go_salv TYPE REF TO cl_salv_table.
DATA gt_data TYPE STANDARD TABLE OF ty_data.
```

### 13.3 DISPLAY를 호출하지 않음

#### 상황

프로그램이 실행되지만 화면에 아무 것도 나타나지 않는다.

#### 원인

SALV 객체를 생성했지만 `DISPLAY`를 호출하지 않았다.

#### 해결

```abap
go_salv->display( ).
```

### 13.4 심화 기능을 복사하다가 오류 발생

#### 상황

인터넷 예제에서 Sort, Column, Layout Method를 복사했는데 구문 오류 또는 런타임 오류가 발생한다.

#### 원인

현재 학습 범위를 넘어선 객체, 메서드, 예외 처리를 함께 사용했기 때문이다.

#### 해결

먼저 1차 기본 패턴으로 되돌아간다.

```text
FACTORY
→ SET_ALL
→ DISPLAY
```

그 후 하나씩 기능을 추가해야 한다.

## 14. 안티패턴

### 14.1 SALV를 배우자마자 모든 기능을 붙이려는 방식

나쁜 학습 방식:

```text
정렬 추가
필터 추가
컬럼명 변경
Layout 저장
Variant 추가
Event 처리
Hotspot 처리
```

문제는 기본 흐름이 불안정한 상태에서 기능만 많아진다는 점이다.

좋은 학습 방식:

```text
1. Internal Table 준비
2. FACTORY 성공
3. DISPLAY 성공
4. 기본 Function 확인
5. 결과 없음 처리
6. 예외 처리
7. 이후 심화 기능 확장
```

### 14.2 SALV를 Grid ALV처럼 쓰려는 방식

SALV는 간단한 리스트 출력에 강점이 있다.  
Grid ALV처럼 세밀한 편집·색상·이벤트 중심 UI로 사용하려 하면 한계에 부딪힌다.

### 14.3 데이터 준비 오류를 SALV 오류로 오해

화면이 비어 있거나 값이 이상하게 보이면 먼저 Internal Table을 확인해야 한다.

```abap
BREAK-POINT.
```

또는 디버거에서 `GT_DATA`의 행 수와 각 필드 값을 확인한다.

### 14.4 예외 처리를 생략

초급 예제에서 TRY-CATCH를 생략할 수도 있지만, 교육용 고품질 예제에서는 예외 처리를 함께 보여주는 것이 좋다.

```abap
CATCH cx_salv_msg INTO DATA(lx_salv).
  MESSAGE lx_salv->get_text( ) TYPE 'E'.
```

## 15. 디버깅 포인트

SALV 출력이 예상대로 되지 않을 때는 다음 지점을 확인한다.

| 지점 | 확인할 내용 |
|---|---|
| SELECT 또는 데이터 구성 직후 | Internal Table에 데이터가 들어왔는가? |
| FACTORY 호출 전 | `GT_DATA`가 Internal Table인가? |
| FACTORY 호출 후 | `GO_SALV`가 Bound 상태인가? |
| SET_ALL 호출 후 | 오류 없이 Function 설정이 되었는가? |
| DISPLAY 직전 | 예외 없이 흐름이 도달했는가? |
| CATCH 블록 | `LX_SALV->GET_TEXT( )` 메시지가 무엇인가? |

디버거에서는 다음 표현을 확인한다.

```text
LINES( GT_DATA )
GO_SALV IS BOUND
LX_SALV->GET_TEXT( )
```

## 17. 평가 문제

### 17.1 객관식

#### Q1. THEORY-08의 SALV 1차 학습 범위로 가장 적절한 것은?

A. Cell Color와 Editable Grid 구현  
B. Internal Table을 `CL_SALV_TABLE`로 간단히 출력  
C. Dynpro Screen에 Custom Container 구성  
D. Fiori Elements List Report 생성  

**정답:** B

#### Q2. Sort, Layout, Variant를 이번 Section에서 깊게 다루지 않는 이유로 가장 적절한 것은?

A. 중요하지 않기 때문이다.  
B. SAP에서 더 이상 사용하지 않기 때문이다.  
C. Internal Table, Selection Screen, 운영 설정 등 선행 개념과 함께 다루는 것이 더 적절하기 때문이다.  
D. ABAP 프로그램에서는 정렬이 불가능하기 때문이다.  

**정답:** C

#### Q3. SALV 화면이 비어 있을 때 가장 먼저 확인해야 할 것은?

A. SAP GUI 색상 테마  
B. Internal Table에 데이터가 들어 있는지 여부  
C. 사용자 비밀번호  
D. 프로그램 제목 길이  

**정답:** B

### 17.2 단답형

#### Q1. `CL_SALV_TABLE=>FACTORY`의 핵심 역할을 설명하시오.

**모범 답안:**  
Internal Table을 기반으로 SALV 출력 객체를 생성하는 역할을 한다. 생성된 객체 참조는 일반적으로 `R_SALV_TABLE`을 통해 받으며, 이후 Function 설정과 `DISPLAY` 호출에 사용한다.

#### Q2. SALV 1차에서 `DISPLAY` 호출이 중요한 이유는 무엇인가?

**모범 답안:**  
SALV 객체를 생성하고 설정하더라도 `DISPLAY`를 호출해야 실제 ALV 화면 출력이 실행되기 때문이다.

#### Q3. SALV와 Grid ALV의 차이를 초급자 관점에서 설명하시오.

**모범 답안:**  
SALV는 Internal Table을 빠르고 간단하게 조회형 리스트로 출력하는 데 적합하다. Grid ALV는 화면 컨테이너, 이벤트, 편집, Cell Style, Field Catalog 등 더 세밀한 UI 제어가 필요한 경우에 적합하며 후속 심화 학습에서 다룬다.

강사는 이 모듈에서 “범위 제한의 이유”를 명확히 설명해야 한다.

하지만 SAP ABAP 교육에서는 선후수가 매우 중요하다.

```text
SALV 1차의 목표는 예쁜 ALV가 아니라, Internal Table 결과를 안정적으로 표 형태로 확인하는 것이다.
```

```text
왜 Layout Variant는 Selection Screen Variant와 함께 혼동될 수 있을까요?
왜 SALV와 Grid ALV를 같은 도구처럼 생각하면 안 될까요?
Internal Table이 비어 있는데 SALV 설정만 고치면 문제가 해결될까요?
```

## 19. 후속 Section과의 연결

THEORY-08 이후에는 더 깊은 데이터 처리와 ALV 응용으로 확장된다.

| 후속 학습 | 연결 포인트 |
|---|---|
| Internal Table 심화 | SALV 출력 전 데이터 가공 기준 |
| Open SQL 기본 조회 | DB 조회 결과를 Internal Table로 받아 SALV 출력 |
| Report Event | 조회와 출력 실행 흐름을 체계화 |
| OO ABAP | SALV 객체와 Method 호출 이해 강화 |
| SALV 심화 | Sort, Filter, Layout, Variant, Column 제어 |
| Screen Programming | Grid ALV 선행 조건 |
| Grid ALV | Field Catalog, Layout, Variant, Event, Cell Style 구현 |
| Modern ABAP | Inline Declaration, VALUE, FILTER, REDUCE 등으로 데이터 준비 개선 |
| CDS/RAP | ALV 리포트에서 앱 기반 리스트로 확장 |

THEORY-08은 단독 주제가 아니라, 이후 학습으로 넘어가기 위한 시각화 연결 고리이다.
