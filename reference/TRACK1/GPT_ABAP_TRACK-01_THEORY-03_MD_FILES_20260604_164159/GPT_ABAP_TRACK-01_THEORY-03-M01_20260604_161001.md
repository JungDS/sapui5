## 3. PARAMETERS란 무엇인가?

`PARAMETERS`는 ABAP Report에서 사용자 입력 필드를 선언하는 문장이다.

가장 단순한 형태는 다음과 같다.

```abap
PARAMETERS p_name TYPE c LENGTH 20.
```

이 한 줄을 작성하면, Report 실행 시 SAP는 Selection Screen에 `P_NAME`이라는 입력 필드를 자동으로 만든다.  
사용자가 화면에 값을 입력하고 실행하면, 프로그램 안에서 `p_name` 변수를 사용할 수 있다.

즉, `PARAMETERS`는 다음 두 가지 역할을 동시에 한다.

| 역할 | 설명 |
|---|---|
| 화면 입력 필드 생성 | Report 실행 전에 입력 필드가 Selection Screen에 표시된다. |
| 프로그램 변수 제공 | 입력값이 ABAP 프로그램 안에서 변수처럼 사용된다. |

초급자는 다음 문장으로 기억하면 된다.

```text
PARAMETERS는 Report 실행 전에 사용자에게 단일 값을 입력받기 위한 선언문이다.
```

## 4. Selection Screen이란 무엇인가?

Selection Screen은 ABAP Report 실행 전에 사용자 입력 조건을 받는 화면이다.

예를 들어 사용자가 이름을 입력하고, 그 이름을 프로그램에서 출력하는 Report를 만든다고 하자.

```abap
REPORT zgpt_param_01.

PARAMETERS p_name TYPE c LENGTH 20.

WRITE: / '입력한 이름:', p_name.
```

이 프로그램을 실행하면 ABAP은 다음 흐름으로 동작한다.

```text
1. 프로그램 실행
2. Selection Screen 표시
3. 사용자가 P_NAME 입력
4. Execute 실행
5. 프로그램 본문 처리
6. WRITE 결과 출력
```

개발자가 별도의 Screen Painter로 화면을 만들지 않아도 `PARAMETERS` 선언만으로 입력 화면이 자동 생성된다.  
이것이 Classic ABAP Report의 강력한 기본 기능 중 하나이다.

## 6. PARAMETERS와 DATA의 차이

`PARAMETERS`와 `DATA`는 둘 다 프로그램 안에서 값을 담는 이름을 만든다.  
그러나 목적이 다르다.

| 구분 | PARAMETERS | DATA |
|---|---|---|
| 목적 | 사용자 입력값을 받기 위한 필드 선언 | 프로그램 내부 변수 선언 |
| 화면 표시 | Selection Screen에 표시됨 | 화면에 자동 표시되지 않음 |
| 실행 시 입력 | 사용자가 값을 입력 가능 | 코드에서 값 대입 |
| 사용 위치 | Report Program의 선언부 | 프로그램 전반 |
| 예시 | `PARAMETERS p_carrid TYPE s_carr_id.` | `DATA gv_carrid TYPE s_carr_id.` |

예를 들어 다음 코드를 보자.

```abap
REPORT zgpt_param_vs_data.

PARAMETERS p_name TYPE c LENGTH 20.
DATA gv_text TYPE string.

gv_text = |Hello, { p_name }|.

WRITE gv_text.
```

`p_name`은 Selection Screen에서 사용자가 입력한다.  
`gv_text`는 프로그램 내부에서 문자열을 만들기 위해 사용하는 일반 변수이다.

## 7. PARAMETERS 기본 문법

### 7.1 기본 형태

```abap
PARAMETERS parameter_name TYPE type.
```

예:

```abap
PARAMETERS p_name TYPE c LENGTH 20.
PARAMETERS p_age  TYPE i.
PARAMETERS p_date TYPE d.
```

### 7.2 이름 규칙

교육용으로는 Parameter 이름에 `p_` Prefix를 사용하는 것을 권장한다.

| Prefix | 의미 | 예시 |
|---|---|---|
| `p_` | Parameter | `p_name`, `p_carrid`, `p_date` |
| `gv_` | Global Variable | `gv_text`, `gv_count` |
| `lv_` | Local Variable | `lv_total`, `lv_index` |
| `lt_` | Internal Table | `lt_flights` |
| `ls_` | Structure / Work Area | `ls_flight` |

ABAP에서는 변수명과 Parameter 이름이 기술적으로 다양한 형태를 가질 수 있지만, 교육과 실무 가독성을 위해 Prefix를 사용하는 것이 좋다.

좋은 예:

```abap
PARAMETERS p_carrid TYPE s_carr_id.
PARAMETERS p_name   TYPE c LENGTH 20.
PARAMETERS p_date   TYPE d.
```

나쁜 예:

```abap
PARAMETERS a TYPE c LENGTH 20.
PARAMETERS x TYPE i.
PARAMETERS test TYPE string.
```

이름만 보고 어떤 입력값인지 알 수 있어야 한다.

## 8. 타입 지정 방식

`PARAMETERS`는 입력값의 타입을 가져야 한다.  
타입 지정은 여러 방식으로 할 수 있다.

### 8.1 Built-in Type 사용

가장 단순한 방식은 ABAP 기본 타입을 직접 사용하는 것이다.

```abap
PARAMETERS p_name TYPE c LENGTH 20.
PARAMETERS p_age  TYPE i.
PARAMETERS p_date TYPE d.
```

| Parameter | 타입 | 의미 |
|---|---|---|
| `p_name` | `c LENGTH 20` | 20자리 문자 |
| `p_age` | `i` | 정수 |
| `p_date` | `d` | 날짜 |

초급 실습에서는 Built-in Type이 이해하기 쉽다.  
하지만 실무에서는 DDIC Data Element를 사용하는 것이 더 좋은 경우가 많다.

### 8.2 DDIC Data Element 사용

DDIC Data Element를 타입으로 지정할 수 있다.

```abap
PARAMETERS p_carrid TYPE s_carr_id.
```

이 방식의 장점은 다음과 같다.

| 장점 | 설명 |
|---|---|
| 의미 재사용 | `s_carr_id`가 항공사 ID라는 의미를 가진다. |
| 기술 속성 재사용 | 길이와 타입을 직접 다시 쓰지 않아도 된다. |
| Field Label 활용 가능 | Selection Screen의 텍스트 관리와 연결할 수 있다. |
| 표준 객체 이해 | SAP 표준 테이블/필드와 연결하기 쉽다. |

예를 들어 Flight Model이 있는 시스템에서는 `S_CARR_ID` 또는 관련 Data Element를 사용할 수 있다.  
시스템마다 교육 데이터 모델이 다를 수 있으므로, 실제 시스템에서 존재하는 Data Element를 확인해야 한다.

### 8.3 Table Field를 기준으로 타입 지정

테이블 필드를 기준으로 타입을 지정할 수도 있다.

```abap
PARAMETERS p_carrid TYPE scarr-carrid.
```

이 방식은 `SCARR` 테이블의 `CARRID` 필드 타입을 그대로 사용한다.

초급자에게는 다음 차이를 알려주는 것이 좋다.

| 방식 | 예시 | 설명 |
|---|---|---|
| Data Element 기준 | `TYPE s_carr_id` | 의미 객체를 직접 참조 |
| Table Field 기준 | `TYPE scarr-carrid` | 특정 테이블 필드 타입을 참조 |
| Built-in Type 기준 | `TYPE c LENGTH 3` | 기술 타입을 직접 지정 |

실무에서는 표준 필드와 동일한 입력값을 받을 때 `TYPE scarr-carrid` 같은 방식이 직관적일 수 있다.  
다만 특정 테이블에 불필요하게 강하게 묶이는 설계가 될 수도 있으므로 상황에 맞게 판단한다.

## 9. PARAMETERS 선언 위치

일반적인 Report Program에서 `PARAMETERS`는 선언부에 둔다.

```abap
REPORT zgpt_param_position.

PARAMETERS p_name TYPE c LENGTH 20.

DATA gv_text TYPE string.

START-OF-SELECTION.
  gv_text = |Hello, { p_name }|.
  WRITE gv_text.
```

아직 Report Event를 깊게 배우지 않은 단계라면 다음처럼 더 단순하게 작성해도 된다.

```abap
REPORT zgpt_param_position_simple.

PARAMETERS p_name TYPE c LENGTH 20.

WRITE: / 'Hello,', p_name.
```

초급 단계에서는 “선언부에 PARAMETERS를 쓰면 실행 전에 Selection Screen이 생긴다”는 흐름을 먼저 이해한다.  
`START-OF-SELECTION` 같은 Report Event는 후속 Section에서 더 정리한다.

## 10. 실행 흐름 상세

다음 코드를 기준으로 실행 흐름을 보자.

```abap
REPORT zgpt_param_flow.

PARAMETERS p_name TYPE c LENGTH 20.

WRITE: / '입력값:', p_name.
```

### 10.1 실행 전

개발자는 프로그램을 작성하고 활성화한다.  
이 시점에는 아직 사용자가 입력한 값이 없다.

### 10.2 프로그램 실행

사용자가 프로그램을 실행하면 ABAP Runtime은 `PARAMETERS` 선언을 보고 Selection Screen을 구성한다.

```text
P_NAME: [____________]
```

### 10.3 사용자 입력

사용자가 `Kim`을 입력하고 실행한다.

```text
P_NAME: Kim
```

### 10.4 프로그램 처리

ABAP 프로그램에서 `p_name`은 사용자가 입력한 값을 가진 변수처럼 동작한다.

```abap
WRITE: / '입력값:', p_name.
```

### 10.5 출력 결과

```text
입력값: Kim
```

초급자가 이해해야 할 핵심은 다음이다.

```text
PARAMETERS는 프로그램 실행 전에 값을 입력받고,
그 입력값은 프로그램 본문에서 변수처럼 사용된다.
```

## 11. 화면 텍스트와 Parameter 이름

처음 `PARAMETERS p_name TYPE c LENGTH 20.`을 작성하면 Selection Screen에 기술 이름 `P_NAME`이 표시될 수 있다.  
실무에서는 사용자에게 기술 이름 그대로 보여주기보다 텍스트를 관리하는 것이 좋다.

### 11.1 Selection Text

SAP GUI에서 Report Program의 Text Elements 또는 Selection Texts를 통해 화면에 표시될 텍스트를 관리할 수 있다.

예:

| Parameter | Selection Text |
|---|---|
| `P_NAME` | 이름 |
| `P_CARRID` | 항공사 |
| `P_DATE` | 기준일 |

이 모듈의 핵심은 `PARAMETERS` 선언이므로 Text Elements 심화는 다루지 않는다.  
하지만 초급자에게 다음 메시지는 중요하다.

```text
프로그램 내부 이름과 사용자 화면 텍스트는 분리해서 관리할 수 있다.
```

## 12. PARAMETERS와 DDIC 의미 연결

앞선 DDIC Section에서 Data Element는 업무 의미와 Field Label을 가진다고 학습했다.  
`PARAMETERS`는 DDIC 객체와 연결될 수 있다.

예:

```abap
PARAMETERS p_carrid TYPE scarr-carrid.
```

또는:

```abap
PARAMETERS p_carrid TYPE s_carr_id.
```

이 경우 Parameter는 단순 `CHAR 3`이 아니라 항공사 ID라는 업무 의미와 연결된다.

### 12.1 왜 DDIC 타입을 사용하는가?

| 이유 | 설명 |
|---|---|
| 일관성 | 표준 테이블 필드와 같은 타입을 사용할 수 있다. |
| 유지보수성 | 길이 변경 등 타입 변경을 중앙에서 반영할 수 있다. |
| 의미 명확성 | Parameter의 업무 의미가 더 분명해진다. |
| 후속 F4 연결 | Search Help, Data Element, Check Table 흐름과 연결 가능하다. |

### 12.2 초급 예제

```abap
REPORT zgpt_param_ddic.

PARAMETERS p_carrid TYPE scarr-carrid.

WRITE: / '항공사 ID:', p_carrid.
```

이 예제는 `SCARR-CARRID` 필드와 같은 타입의 입력값을 받는다.  
Flight Model이 없는 시스템에서는 다른 표준 테이블 필드나 교육용 Z Data Element를 사용할 수 있다.

[추정] 교육 시스템에 따라 `SCARR`, `SPFLI`, `SFLIGHT` 같은 Flight Model 테이블이 없거나 데이터가 비어 있을 수 있다. 이 경우 강사가 지정한 표준 테이블 또는 이전 DDIC 실습에서 만든 Z 테이블 필드를 사용해도 된다.

## 16. 오류 상황과 해결

### 16.1 오류 1: 마침표 누락

#### 잘못된 코드

```abap
PARAMETERS p_name TYPE c LENGTH 20
WRITE p_name.
```

#### 원인

ABAP 문장은 마침표(`.`)로 끝나야 한다.  
첫 번째 문장의 마침표가 누락되어 Syntax Error가 발생한다.

#### 올바른 코드

```abap
PARAMETERS p_name TYPE c LENGTH 20.
WRITE p_name.
```

---

### 16.2 오류 2: Parameter 이름 오타

#### 잘못된 코드

```abap
REPORT zgpt_param_error.

PARAMETERS p_name TYPE c LENGTH 20.

WRITE p_nam.
```

#### 원인

선언한 이름은 `p_name`인데 출력 시 `p_nam`으로 잘못 작성했다.

#### 해결

선언한 이름과 사용하는 이름을 동일하게 맞춘다.

```abap
WRITE p_name.
```

---

### 16.3 오류 3: 존재하지 않는 DDIC 필드 참조

#### 잘못된 코드

```abap
PARAMETERS p_code TYPE znot_exist-field1.
```

#### 원인

`ZNOT_EXIST` 테이블 또는 `FIELD1` 필드가 존재하지 않는다.

#### 해결

SE11에서 실제 존재하는 테이블/필드를 확인한 뒤 사용한다.

```abap
PARAMETERS p_carrid TYPE scarr-carrid.
```

또는 교육용 Data Element를 사용한다.

```abap
PARAMETERS p_user TYPE zde_jhy_user_id.
```

---

### 16.4 오류 4: LENGTH 사용 위치 혼동

#### 잘못된 예

```abap
PARAMETERS p_name TYPE string LENGTH 20.
```

#### 설명

`STRING`은 가변 길이 문자열 타입이므로 `c LENGTH 20`과 같은 방식으로 길이를 지정하는 초급 예제와 성격이 다르다.  
단순 고정 길이 입력 필드는 다음처럼 작성한다.

```abap
PARAMETERS p_name TYPE c LENGTH 20.
```

---

### 16.5 오류 5: Selection Screen이 나오지 않는다고 오해

#### 상황

개발자가 프로그램을 실행했는데 바로 출력 화면이 나오거나, 기대한 입력 화면이 나오지 않는다고 느낀다.

#### 확인 항목

```text
1. PARAMETERS 문장이 실제로 존재하는가?
2. 프로그램이 Report Program으로 생성되었는가?
3. 실행한 프로그램이 수정한 프로그램과 동일한가?
4. Activate 후 실행했는가?
5. 다른 트랜잭션이나 Include를 실행한 것은 아닌가?
```

## 17. 실무 관점 주의사항

### 17.1 PARAMETERS는 단일 입력값 중심이다

`PARAMETERS`는 하나의 단일 값을 입력받는 데 적합하다.

예:

```text
회사코드 1개
기준일 1개
사용자 ID 1개
테스트 모드 여부 1개
```

반면 범위 조건이 필요하면 `SELECT-OPTIONS`가 더 적합하다.  
하지만 `SELECT-OPTIONS`는 커리큘럼상 후속 단계에서 다룬다.

### 17.2 입력 검증은 아직 자동으로 충분하지 않다

`PARAMETERS p_age TYPE i.`라고 선언하면 숫자 타입 입력은 받을 수 있지만, “나이가 0보다 커야 한다” 같은 업무 검증은 별도로 필요하다.

예:

```text
기술 타입 검증: 숫자인가?
업무 검증: 0보다 큰가? 허용 범위인가?
```

업무 검증은 후속 Selection Screen 이벤트에서 다룬다.

### 17.3 사용자 화면 텍스트를 고려해야 한다

기술 이름 `P_CARRID`가 사용자에게 그대로 보이면 친절하지 않을 수 있다.  
실무에서는 Selection Text를 관리하여 사용자가 이해할 수 있는 화면 텍스트를 제공해야 한다.

예:

| 기술 이름 | 사용자 표시 텍스트 |
|---|---|
| P_CARRID | 항공사 |
| P_BUKRS | 회사코드 |
| P_DATE | 기준일 |

### 17.4 너무 많은 PARAMETERS는 화면 품질을 떨어뜨린다

입력 필드가 많아지면 화면을 Block으로 나누거나, 조건의 성격에 따라 정리해야 한다.  
이 내용은 `THEORY-03-M04 Selection Screen Block 기초 맛보기`에서 다룬다.

## 18. 강사용 설명 포인트

강의에서는 다음 메시지를 강조하면 좋다.

```text
PARAMETERS는 ABAP Report에서 Selection Screen을 자동 생성하는 가장 기본적인 입력 선언이다.
```

```text
DATA는 내부 변수이고, PARAMETERS는 사용자 입력을 받는 변수이다.
```

```text
TYPE에 DDIC 필드나 Data Element를 사용하면 입력 필드가 SAP 데이터 모델과 연결된다.
```

초급자는 `PARAMETERS`를 단순 문법으로만 받아들이기 쉽다.  
하지만 실무에서는 입력 필드의 타입, 의미, 화면 텍스트, 검증, F4 Help까지 이어지는 출발점이다.

## 20. 평가 문제

### 20.1 객관식

#### Q1. `PARAMETERS`의 가장 적절한 설명은?

A. Internal Table의 데이터를 정렬하는 구문이다.  
B. Report 실행 전에 단일 입력값을 받기 위한 Selection Screen 필드를 선언하는 구문이다.  
C. Database Table을 생성하는 DDIC 객체이다.  
D. Class Method를 정의하는 구문이다.

**정답:** B

#### Q2. 다음 코드에서 `p_name`의 역할은?

```abap
PARAMETERS p_name TYPE c LENGTH 20.
```

A. 화면 출력 전용 텍스트  
B. 사용자 입력값을 받는 Parameter  
C. 데이터베이스 테이블  
D. ABAP Class

**정답:** B

#### Q3. `PARAMETERS p_carrid TYPE scarr-carrid.`의 의미로 가장 적절한 것은?

A. `SCARR` 테이블의 모든 데이터를 조회한다.  
B. `SCARR-CARRID` 필드의 타입을 기준으로 입력 필드를 만든다.  
C. `SCARR` 테이블을 새로 생성한다.  
D. `CARRID` 값을 자동으로 저장한다.

**정답:** B

### 20.2 서술형

#### Q1. `PARAMETERS`와 `DATA`의 차이를 설명하시오.

**모범 답안:**  
`PARAMETERS`는 Report 실행 전에 Selection Screen에 입력 필드를 만들고, 사용자가 입력한 값을 프로그램에서 사용할 수 있게 한다. `DATA`는 프로그램 내부에서 사용하는 일반 변수 선언이며 Selection Screen에 자동으로 표시되지 않는다.

#### Q2. `PARAMETERS`에 DDIC 타입을 사용하는 장점을 설명하시오.

**모범 답안:**  
DDIC Data Element나 Table Field 타입을 사용하면 SAP 데이터 모델의 타입과 의미를 재사용할 수 있다. 필드 길이와 타입을 직접 반복 정의하지 않아도 되며, 후속 F4 Help나 화면 텍스트 관리와도 연결하기 쉽다.

#### Q3. Selection Screen에서 기술 이름 대신 사용자 친화적인 텍스트가 필요한 이유는 무엇인가?

**모범 답안:**  
기술 이름은 개발자에게는 의미가 있을 수 있지만 최종 사용자에게는 불친절할 수 있다. Selection Text를 관리하면 사용자가 입력 필드의 업무 의미를 쉽게 이해할 수 있다.

## 23. 핵심 요약

이번 모듈의 핵심은 다음이다.

```text
PARAMETERS는 단일 입력값을 받는 Selection Screen 필드를 만든다.
PARAMETERS로 선언한 이름은 프로그램 본문에서 변수처럼 사용할 수 있다.
DATA와 PARAMETERS는 모두 값을 담지만, PARAMETERS는 화면 입력과 연결된다.
TYPE에는 Built-in Type, DDIC Data Element, Table Field 타입을 사용할 수 있다.
초급 단계에서는 PARAMETERS의 기본 선언과 실행 흐름을 먼저 익힌다.
DEFAULT, OBLIGATORY, Block, SELECT-OPTIONS, AT SELECTION-SCREEN은 후속 단계에서 다룬다.
```

## 24. 다음 모듈 연결

다음 모듈은 `THEORY-03-M02 — DEFAULT / OBLIGATORY 사용`이다.

이번 모듈에서 다음과 같은 기본 입력 필드를 만들었다.

```abap
PARAMETERS p_name TYPE c LENGTH 20.
```

다음 모듈에서는 이 입력 필드에 기본값을 주거나, 반드시 입력해야 하는 필드로 만드는 방법을 학습한다.

```abap
PARAMETERS p_name TYPE c LENGTH 20 DEFAULT 'SAP'.
PARAMETERS p_code TYPE c LENGTH 10 OBLIGATORY.
```

따라서 이번 모듈은 Selection Screen 입력 필드의 “기본 생성” 단계이고, 다음 모듈은 입력 필드의 “초기값과 필수 입력” 단계이다.
