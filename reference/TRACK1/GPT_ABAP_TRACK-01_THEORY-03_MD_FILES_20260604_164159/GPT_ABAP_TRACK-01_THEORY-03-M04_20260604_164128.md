## 3. Selection Screen이란 무엇인가?

ABAP Report 프로그램에서 사용자가 프로그램 실행 전에 입력값을 제공하는 화면을 Selection Screen이라고 한다.

가장 단순한 예시는 다음과 같다.

```abap
REPORT zgpt_sel_0304_basic.

PARAMETERS p_name TYPE string.

START-OF-SELECTION.
  WRITE: / '입력한 이름:', p_name.
```

이 프로그램을 실행하면 SAP GUI는 `P_NAME` 입력 필드를 가진 Selection Screen을 먼저 보여준다. 사용자가 값을 입력하고 실행하면 프로그램 본문이 실행된다.

즉, 기본 흐름은 다음과 같다.

```text
Report 실행
→ Selection Screen 표시
→ 사용자가 입력
→ 실행 버튼 선택
→ 프로그램 본문 실행
→ WRITE 결과 출력
```

이번 모듈의 관심사는 입력값 검증이 아니라, Selection Screen의 입력 필드를 **보기 좋게 묶는 방법**이다.

## 4. 왜 Block이 필요한가?

입력 필드가 하나뿐이라면 Block이 없어도 큰 문제가 없다.

```abap
PARAMETERS p_name TYPE c LENGTH 20.
```

하지만 입력 필드가 여러 개로 늘어나면 화면의 의미가 흐려진다.

```abap
PARAMETERS p_carrid TYPE c LENGTH 3.
PARAMETERS p_connid TYPE n LENGTH 4.
PARAMETERS p_date   TYPE d.
PARAMETERS p_user   TYPE syuname.
PARAMETERS p_test   TYPE abap_bool.
```

초급자 입장에서는 이 입력값들이 어떤 목적의 묶음인지 바로 알기 어렵다.  
실무 프로그램에서는 조건이 더 많아진다.

예를 들어 다음처럼 영역이 나뉠 수 있다.

| 입력 영역 | 예시 필드 |
|---|---|
| 조회 조건 | 항공사, 연결번호, 날짜 |
| 실행 옵션 | 테스트 실행 여부, 상세 로그 여부 |
| 출력 옵션 | 요약/상세 출력, 정렬 기준 |

이때 Block을 사용하면 사용자가 화면을 이해하기 쉬워진다.

```text
[조회 조건]
  항공사
  연결번호
  비행일자

[실행 옵션]
  테스트 실행
  상세 로그
```

Block은 “입력 화면의 의미 있는 구획”을 만드는 기능이다.

## 5. Selection Screen Block 기본 문법

기본 구조는 다음과 같다.

```abap
SELECTION-SCREEN BEGIN OF BLOCK b1 WITH FRAME TITLE TEXT-001.

PARAMETERS p_name TYPE c LENGTH 20.

SELECTION-SCREEN END OF BLOCK b1.
```

각 부분의 의미는 다음과 같다.

| 구문 | 의미 |
|---|---|
| `SELECTION-SCREEN BEGIN OF BLOCK b1` | `b1`이라는 이름의 Block 시작 |
| `WITH FRAME` | Block 주변에 테두리 표시 |
| `TITLE TEXT-001` | Block 제목으로 Text Symbol `TEXT-001` 사용 |
| `PARAMETERS` | Block 안에 표시할 입력 필드 |
| `SELECTION-SCREEN END OF BLOCK b1` | `b1` Block 종료 |

초급자에게 가장 중요한 규칙은 이것이다.

```text
BEGIN OF BLOCK으로 시작했으면 반드시 같은 이름으로 END OF BLOCK을 닫는다.
```

---

## 6. Block 이름 규칙

Block 이름은 프로그램 내부에서 사용하는 식별자이다. 화면에 직접 표시되는 제목은 아니다.

예:

```abap
SELECTION-SCREEN BEGIN OF BLOCK b_cond WITH FRAME TITLE TEXT-001.
...
SELECTION-SCREEN END OF BLOCK b_cond.
```

여기서 `b_cond`는 Block의 기술적 이름이고, 사용자가 화면에서 보는 제목은 `TEXT-001`이다.

### 6.1 좋은 Block 이름

| 이름 | 의미 |
|---|---|
| `b_cond` | 조회 조건 영역 |
| `b_opt` | 실행 옵션 영역 |
| `b_out` | 출력 옵션 영역 |
| `b_user` | 사용자 입력 영역 |

### 6.2 좋지 않은 Block 이름

| 이름 | 문제 |
|---|---|
| `b1`, `b2`, `b3` | 실습에서는 가능하지만 의미가 약하다. |
| `block1` | 길지만 의미가 부족하다. |
| `test` | 화면 영역의 목적이 드러나지 않는다. |

실무에서는 이름이 길더라도 의미를 알 수 있는 이름이 좋다.  
다만 초급 실습에서는 `b1`부터 시작해도 무방하다.

## 7. Text Symbol과 Block Title

`TITLE TEXT-001`에서 `TEXT-001`은 Text Symbol을 의미한다.

예를 들어 다음과 같이 작성한다.

```abap
SELECTION-SCREEN BEGIN OF BLOCK b_cond WITH FRAME TITLE TEXT-001.
```

프로그램의 Text Elements에서 `001`에 다음 값을 등록한다.

```text
001 조회 조건
```

그러면 Selection Screen에서는 Block 상단 제목으로 “조회 조건”이 표시된다.

### 7.1 왜 문자열을 직접 쓰지 않는가?

ABAP에서는 화면 텍스트, 메시지, 제목 등을 Text Element로 관리하는 경우가 많다.

장점은 다음과 같다.

| 장점 | 설명 |
|---|---|
| 유지보수성 | 텍스트를 코드와 분리해서 관리할 수 있다. |
| 다국어 지원 | 언어별 텍스트 관리를 고려할 수 있다. |
| 표준 관행 | SAP GUI 기반 Report 개발에서 흔히 사용하는 방식이다. |

초급 단계에서는 다음처럼 이해하면 된다.

```text
코드에는 TEXT-001을 쓰고,
실제 표시 문구는 Text Elements에서 관리한다.
```

## 8. 최소 예제 1: 이름 입력 Block

가장 단순한 예제이다.

```abap
REPORT zgpt_sel_block_01.

SELECTION-SCREEN BEGIN OF BLOCK b_name WITH FRAME TITLE TEXT-001.
PARAMETERS p_name TYPE c LENGTH 20.
SELECTION-SCREEN END OF BLOCK b_name.

START-OF-SELECTION.
  WRITE: / '입력한 이름:', p_name.
```

Text Elements에 다음을 등록한다.

```text
TEXT-001 = 사용자 입력
```

실행 흐름은 다음과 같다.

```text
1. 프로그램 실행
2. Selection Screen 표시
3. "사용자 입력"이라는 Block 제목 확인
4. P_NAME에 값 입력
5. 실행
6. WRITE 결과 확인
```

이 예제에서 Block은 입력값을 바꾸지 않는다.  
입력값의 처리 결과는 M03에서 배운 것과 같다. 달라진 것은 화면 구조이다.

## 9. 최소 예제 2: 조회 조건과 실행 옵션 분리

두 개의 Block을 사용하는 예제이다.

```abap
REPORT zgpt_sel_block_02.

SELECTION-SCREEN BEGIN OF BLOCK b_cond WITH FRAME TITLE TEXT-001.
PARAMETERS p_carrid TYPE c LENGTH 3 DEFAULT 'LH'.
PARAMETERS p_connid TYPE n LENGTH 4.
SELECTION-SCREEN END OF BLOCK b_cond.

SELECTION-SCREEN BEGIN OF BLOCK b_opt WITH FRAME TITLE TEXT-002.
PARAMETERS p_test AS CHECKBOX DEFAULT 'X'.
PARAMETERS p_detail AS CHECKBOX.
SELECTION-SCREEN END OF BLOCK b_opt.

START-OF-SELECTION.
  WRITE: / '항공사:', p_carrid,
         / '연결번호:', p_connid,
         / '테스트 실행:', p_test,
         / '상세 출력:', p_detail.
```

Text Elements는 다음처럼 등록한다.

```text
TEXT-001 = 조회 조건
TEXT-002 = 실행 옵션
```

이 예제에서는 입력 필드를 두 영역으로 구분한다.

| Block | 필드 |
|---|---|
| 조회 조건 | `P_CARRID`, `P_CONNID` |
| 실행 옵션 | `P_TEST`, `P_DETAIL` |

### 9.1 이 예제의 학습 포인트

- `DEFAULT`는 기본값을 제공한다.
- `AS CHECKBOX`는 체크박스 입력 필드를 만든다.
- Block은 화면을 묶는 역할만 한다.
- Block을 여러 개 선언할 수 있다.
- 각 Block은 서로 다른 Text Symbol 제목을 가질 수 있다.

## 10. 최소 예제 3: 필수 입력과 Block

`OBLIGATORY`를 Block 안에서 사용할 수 있다.

```abap
REPORT zgpt_sel_block_03.

SELECTION-SCREEN BEGIN OF BLOCK b_req WITH FRAME TITLE TEXT-001.
PARAMETERS p_user TYPE syuname OBLIGATORY.
PARAMETERS p_date TYPE d DEFAULT sy-datum.
SELECTION-SCREEN END OF BLOCK b_req.

START-OF-SELECTION.
  WRITE: / '사용자:', p_user,
         / '기준일:', p_date.
```

Text Elements:

```text
TEXT-001 = 필수 입력 조건
```

여기서 `OBLIGATORY`는 입력값 필수 여부를 제어한다.  
Block은 그 필드를 시각적으로 묶을 뿐이다.

즉, 역할을 분리해서 이해해야 한다.

| 기능 | 역할 |
|---|---|
| `OBLIGATORY` | 값 입력 필수 여부 |
| `DEFAULT` | 기본값 |
| `WITH FRAME` | 화면 구획 |
| `TITLE TEXT-001` | Block 제목 |

## 11. Block은 검증 로직이 아니다

중요한 점은 Block 자체가 값을 검증하지 않는다는 것이다.

예를 들어 다음처럼 작성했다고 하자.

```abap
SELECTION-SCREEN BEGIN OF BLOCK b_cond WITH FRAME TITLE TEXT-001.
PARAMETERS p_carrid TYPE c LENGTH 3.
SELECTION-SCREEN END OF BLOCK b_cond.
```

이때 `P_CARRID`에 존재하지 않는 항공사 코드를 입력해도 Block이 자동으로 DB 검증을 해주지는 않는다.

검증은 다른 계층에서 다룬다.

| 검증 방식 | 예시 | 학습 시점 |
|---|---|---|
| DDIC 기반 검증 | Data Element, Search Help, Foreign Key | DDIC 2차 |
| Selection Screen 이벤트 | `AT SELECTION-SCREEN` | 후속 Selection Screen 심화 |
| 프로그램 내부 검증 | `IF`, `MESSAGE` | Report Event/입력 검증 단계 |
| DB 조회 결과 검증 | `SELECT`, `SY-SUBRC` | Open SQL 단계 |

이번 모듈은 검증이 아니라 “화면 구조화”가 핵심이다.

## 12. `SELECT-OPTIONS`를 아직 다루지 않는 이유

Selection Screen을 배우면 곧바로 `SELECT-OPTIONS`를 쓰고 싶어질 수 있다.  
하지만 이 커리큘럼에서는 `SELECT-OPTIONS`를 초반에 깊게 다루지 않는다.

이유는 다음과 같다.

| 이유 | 설명 |
|---|---|
| 내부 구조가 Range Table이다 | `SIGN`, `OPTION`, `LOW`, `HIGH` 구조를 이해해야 한다. |
| Internal Table 선행 지식이 필요하다 | 범위 조건은 내부 테이블과 연결된다. |
| Open SQL과 함께 이해해야 한다 | `WHERE field IN so_field` 흐름이 중요하다. |
| 초급 단계에서는 PARAMETERS로 충분하다 | 단일 입력값 흐름을 먼저 익혀야 한다. |

따라서 이번 모듈에서는 다음 구분만 기억한다.

```text
PARAMETERS = 단일 입력값
SELECT-OPTIONS = 범위/복수 조건 입력
```

`SELECT-OPTIONS`는 이후 Internal Table과 Open SQL 기본 조회를 학습한 뒤 다루는 것이 더 자연스럽다.

## 13. `AT SELECTION-SCREEN`을 아직 다루지 않는 이유

`AT SELECTION-SCREEN`은 Selection Screen 입력값을 검증하거나 동적으로 제어할 때 사용하는 이벤트이다.

예시는 다음과 같다.

```abap
AT SELECTION-SCREEN.
  IF p_name IS INITIAL.
    MESSAGE '이름을 입력하세요.' TYPE 'E'.
  ENDIF.
```

하지만 이 구문은 이벤트 기반 Report 처리 흐름을 이해해야 한다.  
아직 초급자는 `START-OF-SELECTION`, `INITIALIZATION`, `AT SELECTION-SCREEN`의 실행 순서를 충분히 배우지 않았다.

그래서 이번 모듈에서는 다음 원칙을 둔다.

```text
이번 단계에서는 AT SELECTION-SCREEN을 사용하지 않는다.
Block은 화면을 묶는 기능으로만 사용한다.
검증 이벤트는 후속 Section에서 별도로 학습한다.
```

## 14. 정상 흐름

Selection Screen Block을 사용하는 정상 흐름은 다음과 같다.

```text
1. REPORT 프로그램 생성
2. PARAMETERS 선언 준비
3. BEGIN OF BLOCK 선언
4. PARAMETERS를 Block 내부에 배치
5. END OF BLOCK으로 닫기
6. Text Element에 Block 제목 등록
7. 프로그램 Activate
8. 실행 후 Selection Screen 화면 확인
9. 입력값 입력
10. 실행 결과 WRITE 출력 확인
```

초급자가 특히 확인해야 할 부분은 다음이다.

| 확인 항목 | 설명 |
|---|---|
| Block 시작/종료 | 같은 Block 이름으로 열고 닫았는가 |
| Text Symbol | `TEXT-001`이 실제 Text Elements에 등록되었는가 |
| 필드 표시 | PARAMETERS가 Block 안에 보이는가 |
| 실행 결과 | 입력값이 정상적으로 WRITE되는가 |

## 15. 오류 흐름과 해결

### 15.1 BEGIN만 있고 END가 없음

#### 잘못된 코드

```abap
SELECTION-SCREEN BEGIN OF BLOCK b1 WITH FRAME TITLE TEXT-001.
PARAMETERS p_name TYPE c LENGTH 20.
```

#### 문제

Block을 시작했지만 닫지 않았다.

#### 해결

```abap
SELECTION-SCREEN END OF BLOCK b1.
```

를 추가한다.

---

### 15.2 BEGIN과 END의 Block 이름이 다름

#### 잘못된 코드

```abap
SELECTION-SCREEN BEGIN OF BLOCK b_cond WITH FRAME TITLE TEXT-001.
PARAMETERS p_name TYPE c LENGTH 20.
SELECTION-SCREEN END OF BLOCK b_opt.
```

#### 문제

`b_cond`로 시작했는데 `b_opt`로 끝냈다.

#### 해결

```abap
SELECTION-SCREEN END OF BLOCK b_cond.
```

로 수정한다.

---

### 15.3 Text Symbol 미등록

#### 코드

```abap
SELECTION-SCREEN BEGIN OF BLOCK b_cond WITH FRAME TITLE TEXT-001.
PARAMETERS p_name TYPE c LENGTH 20.
SELECTION-SCREEN END OF BLOCK b_cond.
```

#### 현상

시스템 또는 설정에 따라 제목이 기대대로 표시되지 않거나 Text Symbol 관련 확인이 필요할 수 있다.

#### 해결

ABAP Editor 또는 ADT에서 Text Elements를 열고 `001`을 등록한다.

```text
001 조회 조건
```

---

### 15.4 Block 안에 아무 필드도 없음

#### 예시

```abap
SELECTION-SCREEN BEGIN OF BLOCK b_empty WITH FRAME TITLE TEXT-001.
SELECTION-SCREEN END OF BLOCK b_empty.
```

#### 문제

문법적으로 가능 여부와 표시 방식은 시스템/상황에 따라 다를 수 있지만, 교육적으로 의미가 없다. 화면에 묶을 입력 필드가 없다면 Block을 만들 이유가 부족하다.

#### 해결

의미 있는 `PARAMETERS`를 Block 안에 배치한다.

---

### 15.5 너무 많은 Block 사용

#### 문제

입력 필드가 적은데 Block을 과도하게 나누면 화면이 오히려 복잡해진다.

#### 해결

다음 기준으로 나눈다.

| 필드 수/의미 | 권장 |
|---|---|
| 입력 필드 1~2개 | Block 없이도 가능 |
| 서로 다른 목적의 필드가 2그룹 이상 | Block 사용 검토 |
| 운영 옵션과 조회 조건이 섞임 | Block 분리 권장 |

---

## 16. 실무 적용 기준

### 16.1 Block을 사용하면 좋은 경우

| 상황 | 이유 |
|---|---|
| 조회 조건과 실행 옵션이 섞여 있음 | 사용자가 입력 목적을 쉽게 구분한다. |
| 필수 입력과 선택 입력이 함께 있음 | 입력 우선순위를 시각적으로 나눌 수 있다. |
| 출력 옵션이 별도 존재함 | 프로그램 실행 방식 선택을 명확히 할 수 있다. |
| 테스트 모드, 로그 옵션 등이 있음 | 운영 실수 방지에 도움을 줄 수 있다. |

### 16.2 Block을 과도하게 사용하지 않아야 하는 경우

| 상황 | 이유 |
|---|---|
| 입력 필드가 하나뿐임 | 화면 복잡도만 증가할 수 있다. |
| 모든 필드가 같은 목적임 | 굳이 여러 Block으로 나눌 필요가 없다. |
| Block 제목이 모호함 | 화면 구조화 효과가 없다. |
| 검증 로직 대체 용도로 사용함 | Block은 검증 기능이 아니다. |

### 16.3 실무 화면 설계 질문

Selection Screen Block을 설계할 때 다음 질문을 던진다.

```text
사용자가 이 입력값들의 목적을 한눈에 이해할 수 있는가?
조회 조건과 실행 옵션이 명확히 분리되어 있는가?
Block 제목이 업무적으로 자연스러운가?
필수 입력 필드가 어느 영역에 있는지 알기 쉬운가?
Block이 너무 많아 화면을 복잡하게 만들지는 않는가?
```

## 21. 평가 문제

### 21.1 객관식

#### Q1. Selection Screen Block의 주된 목적은 무엇인가?

A. DB 데이터를 자동 조회한다.  
B. 입력 필드를 의미 있는 화면 영역으로 묶는다.  
C. 입력값을 자동으로 검증한다.  
D. Open SQL의 성능을 개선한다.

**정답:** B

#### Q2. Block 주변에 테두리를 표시하는 옵션은?

A. `OBLIGATORY`  
B. `DEFAULT`  
C. `WITH FRAME`  
D. `AS CHECKBOX`

**정답:** C

#### Q3. Block 제목으로 `TEXT-001`을 사용했다면 무엇을 추가로 관리해야 하는가?

A. Database Index  
B. Text Symbol 001  
C. Transport Layer만  
D. Internal Table Key

**정답:** B

#### Q4. 이번 모듈에서 `AT SELECTION-SCREEN`을 깊게 다루지 않는 이유로 가장 적절한 것은?

A. Selection Screen에서 사용할 수 없는 구문이기 때문이다.  
B. 이벤트 기반 입력 검증은 후속 주제이며, 이번 모듈은 화면 구획이 핵심이기 때문이다.  
C. `PARAMETERS`와 함께 사용할 수 없기 때문이다.  
D. S/4HANA에서 더 이상 지원되지 않기 때문이다.

**정답:** B

---

### 21.2 단답형

#### Q1. `SELECTION-SCREEN BEGIN OF BLOCK b1 WITH FRAME TITLE TEXT-001.`의 의미를 설명하시오.

**모범 답안:**  
`b1`이라는 Selection Screen Block을 시작하고, 화면에 테두리를 표시하며, Block 제목은 Text Symbol `001`에 등록된 텍스트를 사용하겠다는 의미이다.

#### Q2. Block과 `OBLIGATORY`의 역할 차이를 설명하시오.

**모범 답안:**  
Block은 입력 필드를 화면상에서 묶는 구조화 기능이다. `OBLIGATORY`는 특정 입력 필드가 비어 있으면 실행을 제한하는 필수 입력 속성이다.

#### Q3. `SELECT-OPTIONS`를 이번 단계에서 깊게 다루지 않는 이유를 설명하시오.

**모범 답안:**  
`SELECT-OPTIONS`는 Range Table 구조, Internal Table, Open SQL의 `IN` 조건과 연결되므로, 단일 입력값 중심의 `PARAMETERS`를 먼저 익힌 후 학습하는 것이 적절하다.

## 22. 강사용 설명 포인트

강사는 이번 모듈에서 다음 점을 강조하면 좋다.

### 22.1 Block은 기능보다 UX에 가깝다

Block은 데이터를 읽거나 검증하는 기능이 아니다.  
사용자가 입력 화면을 이해하기 쉽도록 구획을 만드는 선언이다.

### 22.2 초급 단계에서는 단순하게 시작한다

이번 모듈에서 너무 많은 Selection Screen 기능을 소개하면 학습자가 혼란스러워진다.

다음은 의도적으로 미루는 것이 좋다.

```text
SELECT-OPTIONS
AT SELECTION-SCREEN
ON VALUE-REQUEST
LOOP AT SCREEN
MODIF ID
Dynamic Screen Modification
Variant 운영
```

### 22.3 커리큘럼 선후수와 연결한다

이번 Section은 “PARAMETERS 기반 Selection Screen 맛보기”이다.  
정식 Selection Screen 심화가 아니라, 입력값을 받아 프로그램 실행 흐름으로 넘기는 경험을 제공하는 단계이다.

THEORY-03 PARAMETERS 기반 Selection Screen 맛보기
