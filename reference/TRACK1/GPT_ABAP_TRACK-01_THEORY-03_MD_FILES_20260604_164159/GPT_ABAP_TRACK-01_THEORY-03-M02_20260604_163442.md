## 3. `DEFAULT`란 무엇인가?

### 3.1 기본 정의

`DEFAULT`는 Selection Screen이 처음 표시될 때 Parameter 필드에 미리 들어갈 값을 지정하는 옵션이다.

예시:

```abap
PARAMETERS p_name TYPE c LENGTH 20 DEFAULT 'SAP'.
```

이 프로그램을 실행하면 Selection Screen의 `P_NAME` 입력 필드에는 처음부터 `SAP`라는 값이 들어가 있다.

사용자는 그대로 실행할 수도 있고, 값을 다른 값으로 바꾼 뒤 실행할 수도 있다.

### 3.2 `DEFAULT`의 의미

`DEFAULT`는 사용자를 대신해 값을 확정하는 기능이 아니다.  
단지 “일반적으로 자주 쓰는 값” 또는 “학습과 테스트를 쉽게 하기 위한 초기값”을 보여주는 기능이다.

```text
DEFAULT = 추천 초기값 또는 편의용 시작값
```

### 3.3 Selection Screen에서의 동작

`DEFAULT`가 있으면 프로그램 실행 시 다음 흐름이 발생한다.

```text
프로그램 실행
→ Selection Screen 생성
→ Parameter 필드에 DEFAULT 값 표시
→ 사용자가 값 유지 또는 변경
→ Execute
→ 프로그램 본문에서 최종 입력값 사용
```

중요한 점은 사용자가 DEFAULT 값을 변경할 수 있다는 것이다.  
즉, `DEFAULT`는 고정값이 아니다.

## 4. `DEFAULT` 기본 예제

### 4.1 문자 입력 기본값

```abap
REPORT zjhy_param_default_01.

PARAMETERS p_name TYPE c LENGTH 20 DEFAULT 'SAP'.

WRITE: / '입력 이름:', p_name.
```

실행 흐름:

```text
1. 프로그램 실행
2. Selection Screen에 P_NAME 입력 필드 표시
3. 기본값 SAP 표시
4. 사용자가 Execute
5. 결과 화면에 입력 이름 출력
```

사용자가 값을 바꾸지 않으면 결과는 다음처럼 표시된다.

```text
입력 이름: SAP
```

사용자가 `ABAP`으로 바꾸면 결과는 다음처럼 표시된다.

```text
입력 이름: ABAP
```

### 4.2 숫자 입력 기본값

```abap
REPORT zjhy_param_default_02.

PARAMETERS p_count TYPE i DEFAULT 10.

WRITE: / 'Count:', p_count.
```

숫자 타입에는 숫자 형태의 기본값을 줄 수 있다.

### 4.3 날짜 입력 기본값

```abap
REPORT zjhy_param_default_03.

PARAMETERS p_date TYPE d DEFAULT sy-datum.

WRITE: / 'Date:', p_date.
```

이 예제는 현재 날짜를 기본값으로 제시한다.

> 초급 주의: `sy-datum`은 시스템 날짜를 의미한다. 시스템 날짜와 사용자의 현지 날짜가 항상 같은 의미라고 단정하지 않는다. 운영 환경에서는 사용자 Time Zone과 업무 기준일을 별도로 검토해야 할 수 있다.

## 5. `OBLIGATORY`란 무엇인가?

### 5.1 기본 정의

`OBLIGATORY`는 Parameter가 필수 입력값임을 지정하는 옵션이다.

예시:

```abap
PARAMETERS p_name TYPE c LENGTH 20 OBLIGATORY.
```

이렇게 선언하면 사용자가 `P_NAME`을 비워둔 상태로 실행하려고 할 때 Selection Screen 단계에서 입력을 요구한다.

### 5.2 `OBLIGATORY`의 의미

`OBLIGATORY`는 “이 필드는 비어 있으면 안 된다”는 기본 입력 검증이다.

```text
OBLIGATORY = 공백 또는 초기값 상태로 실행하지 못하게 하는 기본 필수 입력 지정
```

### 5.3 Selection Screen에서의 동작

```text
프로그램 실행
→ Selection Screen 표시
→ 사용자가 필수 필드를 비워둠
→ Execute
→ 시스템이 필수 입력 누락 메시지 표시
→ 프로그램 본문은 아직 실행되지 않음
```

여기서 매우 중요한 점은 다음이다.

> `OBLIGATORY` 위반은 프로그램 본문 로직에 들어가기 전에 Selection Screen 단계에서 잡힌다.

즉, 아래와 같은 `WRITE` 문은 필수 입력이 비어 있으면 실행되지 않는다.

```abap
WRITE: / p_name.
```

## 6. `OBLIGATORY` 기본 예제

```abap
REPORT zjhy_param_obligatory_01.

PARAMETERS p_name TYPE c LENGTH 20 OBLIGATORY.

WRITE: / '입력 이름:', p_name.
```

### 6.1 정상 흐름

```text
P_NAME = ABAP
Execute
→ 결과 화면 출력
```

출력:

```text
입력 이름: ABAP
```

### 6.2 오류 흐름

```text
P_NAME = 빈 값
Execute
→ Selection Screen에서 필수 입력 오류
→ 결과 화면으로 넘어가지 않음
```

오류 메시지 문구는 시스템 언어와 버전에 따라 다를 수 있지만, 의미는 “필수 필드에 값을 입력하라”는 것이다.

## 7. `DEFAULT`와 `OBLIGATORY` 함께 사용

`DEFAULT`와 `OBLIGATORY`는 함께 사용할 수 있다.

```abap
REPORT zjhy_param_default_obl.

PARAMETERS p_name TYPE c LENGTH 20 DEFAULT 'SAP' OBLIGATORY.

WRITE: / '입력 이름:', p_name.
```

### 7.1 이 조합의 의미

| 옵션 | 역할 |
|---|---|
| `DEFAULT 'SAP'` | 처음 화면에 `SAP`를 보여준다. |
| `OBLIGATORY` | 사용자가 값을 지우고 빈 값으로 실행하지 못하게 한다. |

실행 흐름은 다음과 같다.

```text
Selection Screen에 SAP가 표시된다.
사용자가 그대로 실행하면 정상 실행된다.
사용자가 값을 다른 값으로 바꾸어 실행하면 정상 실행된다.
사용자가 값을 지우고 실행하면 필수 입력 오류가 발생한다.
```

### 7.2 초급자가 흔히 하는 오해

```text
오해: DEFAULT가 있으면 OBLIGATORY는 필요 없다.
```

아니다. 사용자가 DEFAULT 값을 지울 수 있기 때문에, 빈 값 실행을 막으려면 `OBLIGATORY`가 필요하다.

```text
오해: OBLIGATORY가 있으면 DEFAULT는 필요 없다.
```

항상 그런 것은 아니다. 사용 편의성을 위해 기본값을 보여주고, 동시에 빈 값 실행을 막는 조합이 필요할 수 있다.

## 8. Initial Value와 공백값 이해

### 8.1 Initial Value란?

ABAP에서 변수나 Parameter가 명시적으로 값을 받지 않았을 때 가지는 기본 상태를 Initial Value라고 한다.

타입별 Initial Value는 개념적으로 다음처럼 이해할 수 있다.

| 타입 | Initial Value 예시 |
|---|---|
| `C` | 공백 |
| `STRING` | 빈 문자열 |
| `I` | 0 |
| `D` | `00000000` |
| `T` | `000000` |

초급 단계에서는 다음 정도로 기억하면 충분하다.

```text
문자 필드를 비워두면 공백 상태이다.
숫자 필드를 비워두면 0과 관련된 초기 상태로 처리될 수 있다.
날짜 필드를 비워두면 유효한 업무 날짜가 아닐 수 있다.
```

### 8.2 `OBLIGATORY`와 Initial Value

`OBLIGATORY`는 필드가 비어 있는 상태를 막는 기본 검증이다.

하지만 타입과 화면 처리 방식에 따라 학습자가 느끼는 “빈 값”의 의미가 다를 수 있다. 예를 들어 문자 Parameter는 빈 칸이 직관적이지만, 숫자 Parameter는 0이 업무적으로 유효한 값인지 아닌지를 별도로 판단해야 한다.

예:

```abap
PARAMETERS p_count TYPE i OBLIGATORY.
```

이 경우 화면에서 빈 값 처리가 어떻게 보이는지와 별개로, 업무적으로 `0`을 허용할지 여부는 별도 검증이 필요할 수 있다.

> 핵심: `OBLIGATORY`는 “입력 필수”의 기본 검증이지, “업무적으로 올바른 값”까지 보장하지 않는다.

## 9. 업무 검증과 `OBLIGATORY`의 차이

`OBLIGATORY`는 필수 입력 여부만 검증한다.  
하지만 실무 프로그램에서는 다음과 같은 검증이 필요할 수 있다.

| 검증 요구 | `OBLIGATORY`만으로 가능? | 설명 |
|---|---:|---|
| 빈 값 금지 | 가능 | 필수 입력 기본 검증 |
| 숫자가 1 이상이어야 함 | 불충분 | 별도 조건 검증 필요 |
| 날짜가 오늘 이후여야 함 | 불충분 | 날짜 비교 로직 필요 |
| 코드가 존재하는지 확인 | 불충분 | DB 또는 DDIC 검증 필요 |
| 권한이 있는 값인지 확인 | 불충분 | Authorization Check 필요 |

예를 들어 다음 코드는 필수 입력과 업무 검증을 혼동한 사례이다.

```abap
PARAMETERS p_count TYPE i OBLIGATORY.

WRITE: / p_count.
```

이 코드는 `p_count`가 비어 있는 실행은 어느 정도 막을 수 있지만, `0`이나 음수 같은 업무적으로 부적절한 값까지 막지는 않는다.

업무 검증은 후속 Selection Screen 이벤트나 프로그램 로직에서 다루어야 한다.

이번 모듈에서는 아직 `AT SELECTION-SCREEN`을 깊게 다루지 않으므로, 다음 개념만 기억한다.

```text
OBLIGATORY = 기본 입력 검증
업무 규칙 검증 = 별도 로직 또는 후속 Selection Screen 이벤트에서 처리
```

## 10. 실무에서 `DEFAULT`를 사용할 때의 기준

### 10.1 좋은 DEFAULT 사용 예

`DEFAULT`는 사용자가 자주 입력하는 값을 미리 제안할 때 유용하다.

| 예 | 적절한 이유 |
|---|---|
| 날짜 Parameter에 오늘 날짜 | 테스트와 일일 처리에 편리 |
| 회사코드가 교육 시스템에서 하나로 고정 | 실습 편의성 증가 |
| 상태 코드 기본값 `A` | Active 데이터 중심 조회 시 편리 |
| 언어 기본값 `SY-LANGU` | 로그인 언어와 자연스럽게 연결 |

예:

```abap
PARAMETERS p_date TYPE d DEFAULT sy-datum.
PARAMETERS p_langu TYPE sylangu DEFAULT sy-langu.
```

### 10.2 피해야 할 DEFAULT 사용 예

`DEFAULT`가 오히려 위험한 경우도 있다.

| 예 | 문제 |
|---|---|
| 삭제 프로그램에서 삭제 대상 기본값 제공 | 사용자가 실수로 실행할 위험 |
| 대량 처리 범위를 지나치게 넓게 기본 설정 | 성능 문제 유발 가능 |
| 운영 변경 프로그램에서 민감한 값 기본 제공 | 잘못된 변경 가능성 증가 |
| 특정 고객/회사코드를 하드코딩 | 고객사/운영 환경 변화에 취약 |

특히 운영 데이터 변경 프로그램에서는 DEFAULT 사용이 사용자 실수를 줄이는 방향인지, 오히려 실수를 유도하는지 신중하게 판단해야 한다.

## 11. 실무에서 `OBLIGATORY`를 사용할 때의 기준

### 11.1 OBLIGATORY가 적합한 경우

| 상황 | 이유 |
|---|---|
| 단일 키 값 조회 | 키 없이 실행하면 의미가 없음 |
| 필수 기준일 입력 | 날짜가 없으면 로직 기준이 불명확 |
| 파일 경로 입력 | 경로 없이 파일 처리 불가 |
| 회사코드 입력 | 회사코드별 처리 기준 필요 |

예:

```abap
PARAMETERS p_bukrs TYPE bukrs OBLIGATORY.
PARAMETERS p_date  TYPE d     OBLIGATORY.
```

### 11.2 OBLIGATORY만으로 부족한 경우

다음 상황은 `OBLIGATORY`와 별도 검증을 함께 고려해야 한다.

| 상황 | 추가 검증 예 |
|---|---|
| 날짜 입력 | 과거일/미래일 허용 여부 |
| 금액 입력 | 0 이하 금지 |
| 회사코드 입력 | 존재 여부, 권한 여부 |
| 파일 경로 입력 | 파일 존재 여부, 접근 가능 여부 |

예를 들어 회사코드를 필수로 받는 것은 시작일 뿐이다. 실제 프로그램에서는 해당 회사코드가 존재하는지, 사용자가 해당 회사코드 데이터를 볼 권한이 있는지도 확인해야 한다.

## 12. 문법 위치와 작성 순서

`PARAMETERS` 문은 보통 Report Program 상단 선언부에 작성한다.

권장 기본 구조는 다음과 같다.

```abap
REPORT zjhy_param_default_obl.

PARAMETERS p_name TYPE c LENGTH 20 DEFAULT 'SAP' OBLIGATORY.

WRITE: / '입력 이름:', p_name.
```

초급자가 읽기 쉬운 순서는 다음이다.

```text
REPORT 선언
→ PARAMETERS 선언
→ DATA 선언 또는 처리 로직
→ WRITE 출력
```

프로젝트에 따라 선언부 정렬 규칙은 다를 수 있지만, 초급 단계에서는 “입력값 선언이 프로그램 실행 전 화면을 만든다”는 흐름을 보이도록 상단에 배치하는 것이 이해에 좋다.

## 13. 예제 1 — 이름 기본값과 필수 입력

```abap
REPORT zjhy_p_default_name.

PARAMETERS p_name TYPE c LENGTH 20 DEFAULT 'SAP' OBLIGATORY.

WRITE: / '입력된 이름:', p_name.
```

### 실행 관찰 포인트

| 관찰 | 설명 |
|---|---|
| 최초 화면 | `P_NAME`에 `SAP` 표시 |
| 값 유지 후 실행 | `SAP` 출력 |
| 값 변경 후 실행 | 변경한 값 출력 |
| 값 삭제 후 실행 | 필수 입력 오류 |

### 학습 질문

```text
DEFAULT 값은 사용자가 변경할 수 있는가?
OBLIGATORY는 프로그램 본문 실행 전에 동작하는가?
값을 지웠을 때 WRITE 문이 실행되는가?
```

## 14. 예제 2 — 날짜 기본값

```abap
REPORT zjhy_p_default_date.

PARAMETERS p_date TYPE d DEFAULT sy-datum OBLIGATORY.

WRITE: / '기준일:', p_date.
```

### 설명

이 예제는 실행일의 시스템 날짜를 기본 기준일로 보여준다.

초급자가 확인할 포인트는 다음이다.

```text
프로그램 실행 시점의 SY-DATUM이 화면 기본값으로 들어간다.
사용자는 날짜를 바꿀 수 있다.
날짜를 지우고 실행하면 필수 입력 오류가 발생한다.
```

### 실무 주의

`sy-datum`은 편리하지만 모든 업무의 기준일이 항상 시스템 날짜인 것은 아니다. 예를 들어 재무 전기일, 출고 기준일, 마감 기준일은 별도 업무 규칙을 따를 수 있다.

따라서 실무에서는 다음을 구분해야 한다.

| 날짜 | 의미 |
|---|---|
| 시스템 날짜 | 현재 시스템 기준일 |
| 업무 기준일 | 프로세스에서 의미 있는 처리 기준일 |
| 전기일 | 회계 반영 기준일 |
| 문서일 | 업무 문서의 실제 발생일 |

## 15. 예제 3 — 회사코드 Parameter

```abap
REPORT zjhy_p_bukrs.

PARAMETERS p_bukrs TYPE bukrs DEFAULT '1000' OBLIGATORY.

WRITE: / '회사코드:', p_bukrs.
```

### 설명

이 예제는 DDIC Data Element `BUKRS`를 Parameter 타입으로 사용하는 형태이다.

`TYPE bukrs`를 사용하면 회사코드의 표준 DDIC 의미와 타입 속성을 활용할 수 있다.

### 주의

예제의 `1000`은 교육용 기본값이다.

> [추정] 실제 시스템에는 회사코드 `1000`이 없을 수도 있다. 고객사 시스템에서는 실제 존재하는 회사코드를 사용해야 한다.

또한 회사코드가 존재한다고 해서 사용자가 해당 회사코드의 데이터를 조회하거나 변경할 권한이 있다는 뜻은 아니다. 권한 검사는 후속 실무 단계에서 별도로 다룬다.

## 16. 정상 흐름과 오류 흐름

### 16.1 정상 흐름

```text
1. 프로그램 실행
2. Selection Screen 표시
3. DEFAULT 값 표시
4. 사용자가 값 확인 또는 변경
5. 필수 입력값 존재
6. Execute
7. 프로그램 본문 실행
8. WRITE 결과 출력
```

### 16.2 오류 흐름 — 필수값 삭제

```text
1. 프로그램 실행
2. Selection Screen 표시
3. DEFAULT 값 표시
4. 사용자가 값을 삭제
5. Execute
6. OBLIGATORY 검증 실패
7. Selection Screen에 머무름
8. 프로그램 본문 미실행
```

### 16.3 오류 흐름 — DEFAULT 값의 업무적 부적합

```text
1. DEFAULT '1000' 지정
2. 실제 시스템에 회사코드 1000이 없음
3. 사용자가 그대로 실행
4. OBLIGATORY는 통과
5. 이후 DB 조회 또는 업무 로직에서 데이터 없음 또는 오류 가능
```

이 예시는 `OBLIGATORY`가 업무적 존재 여부 검증이 아니라는 점을 보여준다.

## 17. 디버깅 및 검증 포인트

초급자는 다음 방식으로 동작을 확인할 수 있다.

### 17.1 Selection Screen에서 확인

```text
1. 프로그램 실행
2. DEFAULT 값이 표시되는지 확인
3. 값을 지우고 Execute
4. 필수 입력 오류가 발생하는지 확인
```

### 17.2 프로그램 본문에서 확인

`WRITE`를 사용해 입력값을 확인한다.

```abap
WRITE: / 'P_NAME =', p_name.
```

### 17.3 디버깅으로 확인

디버깅을 사용할 수 있다면 Execute 후 프로그램 본문에 진입했을 때 `p_name`, `p_date`, `p_bukrs` 값이 어떻게 들어와 있는지 확인한다.

관찰 포인트:

| 포인트 | 설명 |
|---|---|
| DEFAULT 값 | 사용자가 변경하지 않으면 그대로 들어온다. |
| 변경값 | 사용자가 수정한 값이 들어온다. |
| 빈 값 | OBLIGATORY면 본문 진입 전 막힌다. |

## 18. 초급자 실수와 안티패턴

### 18.1 DEFAULT를 고정 조건처럼 생각함

나쁜 이해:

```text
DEFAULT 'A'를 줬으니 항상 A로 실행된다.
```

올바른 이해:

```text
DEFAULT는 화면에 처음 표시되는 값일 뿐이며 사용자가 변경할 수 있다.
```

### 18.2 OBLIGATORY를 업무 검증 전체로 착각함

나쁜 이해:

```text
OBLIGATORY를 붙였으니 입력값 검증은 끝났다.
```

올바른 이해:

```text
OBLIGATORY는 빈 값 방지일 뿐, 존재 여부·권한·범위·업무 규칙 검증은 별도이다.
```

### 18.3 위험한 프로그램에 DEFAULT를 둠

예를 들어 삭제 대상이나 대량 변경 조건에 넓은 DEFAULT를 두면 실수로 실행할 위험이 커진다.

```abap
PARAMETERS p_del TYPE c LENGTH 1 DEFAULT 'X'.
```

위와 같은 방식은 교육용 예제로도 신중해야 한다.

### 18.4 숫자 0을 유효 입력으로 착각함

숫자 Parameter에서 0이 업무적으로 유효하지 않을 수 있다.  
`OBLIGATORY`가 있더라도 0 금지 같은 업무 검증은 별도로 필요하다.

## 19. 미니 실습

### 19.1 실습 목표

다음 조건을 만족하는 Report Program을 만든다.

```text
프로그램명: ZJHY_THEORY03_M02
입력값 1: 이름, 기본값 SAP, 필수
입력값 2: 기준일, 기본값 오늘 날짜, 필수
입력값 3: 상태, 기본값 A, 필수
출력: 입력된 세 값을 WRITE로 출력
```

### 19.2 예제 코드

```abap
REPORT zjhy_theory03_m02.

PARAMETERS p_name   TYPE c LENGTH 20 DEFAULT 'SAP' OBLIGATORY.
PARAMETERS p_date   TYPE d DEFAULT sy-datum OBLIGATORY.
PARAMETERS p_status TYPE c LENGTH 1 DEFAULT 'A' OBLIGATORY.

WRITE: / 'Name  :', p_name,
       / 'Date  :', p_date,
       / 'Status:', p_status.
```

### 19.3 실행 테스트

다음 케이스를 각각 확인한다.

| 테스트 | 입력 | 기대 결과 |
|---|---|---|
| 기본값 실행 | 아무 값도 변경하지 않음 | SAP, 오늘 날짜, A 출력 |
| 이름 변경 | `p_name = ABAP` | ABAP 출력 |
| 날짜 삭제 | `p_date` 빈 값 | 필수 입력 오류 |
| 상태 삭제 | `p_status` 빈 값 | 필수 입력 오류 |
| 상태를 Z로 변경 | `p_status = Z` | 출력은 되지만 업무적으로 유효한지는 별도 검증 필요 |

마지막 테스트가 중요하다. `OBLIGATORY`는 `Z`가 올바른 상태값인지 판단하지 않는다.

## 21. 강사용 설명 포인트

강의에서는 다음 메시지를 반복해서 강조하는 것이 좋다.

### 21.1 DEFAULT는 편의 기능이다

`DEFAULT`는 사용자가 자주 입력하는 값을 미리 보여주는 편의 기능이다.  
그러나 사용자가 값을 바꿀 수 있으므로 고정 조건으로 생각하면 안 된다.

### 21.2 OBLIGATORY는 최소 검증이다

`OBLIGATORY`는 빈 값 실행을 막는다.  
하지만 다음은 막지 못한다.

```text
존재하지 않는 회사코드
권한 없는 조직값
업무적으로 허용되지 않는 상태값
0 이하 금액
마감일 이후 날짜
```

### 21.3 이 단계에서는 이벤트 검증을 과도하게 확장하지 않는다

초급자에게 바로 `AT SELECTION-SCREEN`을 많이 설명하면 Selection Screen 흐름 자체보다 이벤트 문법에 집중하게 된다.  
이번 모듈에서는 `DEFAULT`와 `OBLIGATORY`의 표준 동작을 정확히 이해시키는 것이 우선이다.

### 21.4 DDIC와 연결한다

`PARAMETERS p_bukrs TYPE bukrs`처럼 DDIC Data Element를 사용하면, 단순 `TYPE c LENGTH 4`보다 의미 있는 타입 선언이 가능하다.  
이전 DDIC Section과 현재 Selection Screen Section이 연결되는 지점이다.

## 23. 평가 문제

### 23.1 객관식

#### Q1. `DEFAULT`에 대한 설명으로 가장 적절한 것은?

A. 사용자가 절대 변경할 수 없는 고정값이다.  
B. 프로그램 실행 후 결과 화면에만 표시되는 값이다.  
C. Selection Screen에 처음 표시되는 초기값이다.  
D. 데이터베이스에 자동 저장되는 값이다.

**정답:** C

#### Q2. `OBLIGATORY`의 기본 목적은?

A. 필드의 출력 색상을 바꾼다.  
B. 필드를 필수 입력으로 지정한다.  
C. F4 Help를 자동 생성한다.  
D. 입력값을 데이터베이스에 저장한다.

**정답:** B

#### Q3. 다음 코드에서 사용자가 값을 지우고 실행하면 어떤 일이 발생하는가?

```abap
PARAMETERS p_name TYPE c LENGTH 20 DEFAULT 'SAP' OBLIGATORY.
```

A. 프로그램이 무조건 SAP로 실행된다.  
B. 필수 입력 오류가 발생하고 본문 실행 전 Selection Screen에 머문다.  
C. Short Dump가 발생한다.  
D. 데이터베이스에 SAP가 저장된다.

**정답:** B

### 23.2 단답형

#### Q1. `DEFAULT`와 `OBLIGATORY`의 차이를 설명하시오.

**모범 답안:**  
`DEFAULT`는 Selection Screen에 처음 표시되는 기본값을 지정하는 옵션이고, `OBLIGATORY`는 사용자가 값을 비워둔 상태로 실행하지 못하도록 하는 필수 입력 옵션이다.

#### Q2. `OBLIGATORY`가 업무 검증 전체를 대체할 수 없는 이유를 설명하시오.

**모범 답안:**  
`OBLIGATORY`는 값이 비어 있는지만 기본적으로 확인한다. 입력값이 실제로 존재하는지, 권한이 있는지, 업무적으로 허용되는 범위인지 같은 검증은 별도 로직이나 후속 Selection Screen 이벤트에서 처리해야 한다.

#### Q3. `DEFAULT sy-datum` 사용 시 주의할 점을 설명하시오.

**모범 답안:**  
`sy-datum`은 시스템 날짜를 기본값으로 제공하므로 편리하지만, 모든 업무 기준일이 시스템 날짜와 일치하는 것은 아니다. 회계 전기일, 마감 기준일, 문서일 등은 별도 업무 규칙을 따를 수 있으므로 실무에서는 기준일 의미를 확인해야 한다.

| OBLIGATORY만으로 업무 검증이 끝나지 않는다는 점을 설명할 수 있다. |  |
| `sy-datum`, `sy-langu` 같은 시스템 필드를 기본값으로 사용할 때 주의점을 설명할 수 있다. |  |
| DDIC Data Element를 Parameter 타입으로 사용하는 장점을 이해한다. |  |

---

## 25. 핵심 요약

이번 모듈의 핵심은 다음이다.

```text
DEFAULT는 Selection Screen에 표시되는 초기값이다.
DEFAULT 값은 사용자가 변경할 수 있다.
OBLIGATORY는 필수 입력을 지정한다.
OBLIGATORY 위반 시 프로그램 본문 실행 전 Selection Screen 단계에서 막힌다.
DEFAULT와 OBLIGATORY는 함께 사용할 수 있다.
OBLIGATORY는 빈 값 방지일 뿐, 업무 검증 전체를 대체하지 않는다.
```

초급자는 이번 모듈을 통해 단순 `PARAMETERS` 선언이 사용 편의성과 기본 검증을 포함한 Selection Screen 입력 설계로 확장되는 흐름을 이해해야 한다.
