## 2. 선행 지식

```text
        ↓

        ↓
Service Definition / Binding
        ↓
OData V4 / Fiori Elements
```

## 3. RAP Behavior Layer의 역할

RAP에서 CDS View Entity는 데이터의 모양과 의미를 표현한다.  
하지만 실제 비즈니스 객체는 단순 조회 모델이 아니다. 사용자는 데이터를 생성하고, 수정하고, 상태를 변경하고, 저장 전에 오류를 검증한다.

이런 동작은 Behavior Layer에서 정의한다.

| 계층 | 주 책임 |
|---|---|
| CDS View Entity | 데이터 모델, Association, Annotation |
| Behavior Definition | 허용되는 동작과 Hook 선언 |
| Behavior Implementation | ABAP 로직 구현 |
| Service Definition/Binding | 외부 노출 |
| Fiori Elements | UI 소비 |

Behavior Layer는 다음과 같은 질문에 답한다.

```text
이 Entity는 create/update/delete 가능한가?
어떤 필드는 readonly인가?
저장 전에 반드시 검증할 규칙은 무엇인가?
사용자가 입력하지 않아도 자동으로 채워야 할 값은 무엇인가?
업무 상태 변경 버튼은 어떤 Action으로 제공할 것인가?
```

## 4. 세 가지 핵심 개념 한눈에 보기

| 구분 | Validation | Determination | Action |
|---|---|---|---|
| 한국어 감각 | 검증 | 자동 결정/자동 보정 | 명시적 업무 명령 |
| 주 목적 | 잘못된 데이터 저장 방지 | 파생값 자동 계산/입력 | 사용자가 실행하는 업무 동작 |
| 대표 시점 | Save Phase 중심 | Modify 또는 Save 시점 | Action 호출 시점 |
| 데이터 변경 | 일반적으로 하지 않음 | 가능 | 가능 |
| 메시지 반환 | 중요 | 가능 | 가능 |
| 예시 | 종료일이 시작일보다 빠르면 오류 | 상태 기본값을 `N`으로 설정 | 승인, 반려, 취소 |
| UI 노출 | 저장 시 오류 메시지 | 자동 반영 | 버튼 또는 메뉴 |
| 구현 위치 | Behavior Implementation | Behavior Implementation | Behavior Implementation |

초급자는 다음 문장으로 구분하면 좋다.

```text
Validation은 “저장해도 되는가?”를 판단한다.
Determination은 “시스템이 자동으로 채워야 할 것은 무엇인가?”를 처리한다.
Action은 “사용자가 명시적으로 실행하는 업무 명령”을 구현한다.
```

```text
Travel Request를 생성할 수 있다.
```

## 6. 예제 데이터 모델 개요

### 6.1 Interface View Entity `ZI_GPT_TRAVEL`

RAP 예제에서는 Interface View와 Projection View를 분리해서 생각해야 한다.  
Interface View는 Business Object 내부 모델의 중심이다.

```abap
@EndUserText.label: 'Travel Request Interface View'
@AccessControl.authorizationCheck: #NOT_REQUIRED
define root view entity ZI_GPT_TRAVEL
  as select from zgpt_travel
{
  key travel_id       as TravelId,
      description     as Description,
      begin_date      as BeginDate,
      end_date        as EndDate,
      status          as Status,
      created_by      as CreatedBy,
      created_at      as CreatedAt,
      last_changed_by as LastChangedBy,
      last_changed_at as LastChangedAt
}
```

> [추정] 위 예제의 물리 테이블 `zgpt_travel`과 필드명은 교육용 예시이다. 실제 실습 시스템에서는 앞선 모듈에서 생성한 Z 테이블 명명 규칙에 맞춰 조정한다.

### 6.2 Projection View Entity `ZC_GPT_TRAVEL`

Projection View는 서비스 노출용 소비 모델이다.

```abap
@EndUserText.label: 'Travel Request Projection View'
@AccessControl.authorizationCheck: #NOT_REQUIRED
@Metadata.allowExtensions: true
define root view entity ZC_GPT_TRAVEL
  as projection on ZI_GPT_TRAVEL
{
  key TravelId,
      Description,
      BeginDate,
      EndDate,
      Status,
      CreatedBy,
      CreatedAt,
      LastChangedBy,
      LastChangedAt
}
```

RAP 학습에서 `ZI_*`와 `ZC_*`를 분리하는 이유는 다음과 같다.

| View | 역할 |
|---|---|
| `ZI_*` | 내부 비즈니스 객체 모델, Behavior의 중심 |
| `ZC_*` | 외부 서비스 노출 및 UI 소비 모델 |

## 7. Behavior Definition 개요

Behavior Definition은 Entity가 어떤 동작을 지원하는지 선언한다.

예제 BDEF의 전체 감각은 다음과 같다.

```abap
managed implementation in class zbp_i_gpt_travel unique;
strict ( 2 );

define behavior for ZI_GPT_TRAVEL alias Travel
persistent table zgpt_travel
lock master
authorization master ( instance )
etag master LastChangedAt
{
  create;
  update;
  delete;

  field ( readonly ) CreatedBy, CreatedAt, LastChangedBy, LastChangedAt;

  determination setInitialStatus on modify
  { create; }

  validation validateDates on save
  { create; update; field BeginDate, EndDate; }

  action approve result [1] $self;
}
```

위 예제는 세 가지를 모두 포함한다.

| 선언 | 의미 |
|---|---|
| `determination setInitialStatus on modify` | 생성/수정 과정에서 상태 기본값을 자동 결정 |
| `validation validateDates on save` | 저장 시 날짜 관계를 검증 |
| `action approve result [1] $self` | 승인 Action 제공 |

> [추정] ABAP Platform 릴리스와 RAP 시나리오에 따라 BDEF 세부 구문, Managed/Unmanaged 선택, Draft 사용 여부는 달라질 수 있다. 이 문서는 초급 개념 이해를 위한 Managed RAP 예제 흐름으로 설명한다.

## 8. Validation 상세 이해

### 8.1 Validation의 목적

Validation은 데이터 저장 전 업무 규칙을 확인하는 로직이다.

예를 들어 다음 데이터는 올바르지 않다.

| BeginDate | EndDate | 문제 |
|---|---|---|
| 2026-06-10 | 2026-06-05 | 종료일이 시작일보다 빠름 |

이 규칙은 단순한 화면 검증으로만 처리하면 안 된다.  
OData API, Fiori UI, EML, 외부 인터페이스 등 다양한 경로에서 데이터가 들어올 수 있기 때문이다.

따라서 RAP Behavior Layer의 Validation에서 검증하는 것이 중요하다.

### 8.2 Validation에 적합한 규칙

| 규칙 | Validation 적합성 |
|---|---|
| 필수 날짜 누락 | 적합 |
| 시작일/종료일 관계 오류 | 적합 |
| 상태 전이 불가능 | 적합 |
| 존재하지 않는 코드 입력 | 적합 |
| 권한 없는 상태 변경 | 경우에 따라 Authorization 또는 Validation 검토 |
| 단순 표시 형식 | UI Annotation 또는 Data Element 성격 검토 |

### 8.3 Validation 구현 기본 형태

BDEF에서 선언한 Validation은 Behavior Implementation Class에서 구현한다.

```abap
METHOD validateDates.

  READ ENTITIES OF zi_gpt_travel IN LOCAL MODE
    ENTITY Travel
      FIELDS ( TravelId BeginDate EndDate )
      WITH CORRESPONDING #( keys )
    RESULT DATA(lt_travel).

  LOOP AT lt_travel INTO DATA(ls_travel).

    IF ls_travel-BeginDate IS NOT INITIAL
       AND ls_travel-EndDate IS NOT INITIAL
       AND ls_travel-EndDate < ls_travel-BeginDate.

      APPEND VALUE #( %tky = ls_travel-%tky ) TO failed-travel.

      APPEND VALUE #(
        %tky = ls_travel-%tky
        %msg = new_message_with_text(
                 severity = if_abap_behv_message=>severity-error
                 text     = '종료일은 시작일보다 빠를 수 없습니다.' )
        %element-EndDate = if_abap_behv=>mk-on
      ) TO reported-travel.

    ENDIF.

  ENDLOOP.

ENDMETHOD.
```

핵심은 `failed`와 `reported`이다.

| 테이블 | 역할 |
|---|---|
| `failed-*` | 실패한 Entity Key를 RAP Runtime에 알림 |
| `reported-*` | 사용자 또는 소비자에게 전달할 메시지 반환 |

### 8.4 Validation에서 주의할 점

Validation은 검증 로직이다.  
따라서 일반적으로 데이터를 조용히 보정하지 않는 것이 좋다.

나쁜 예:

```text
종료일이 시작일보다 빠르면 시스템이 자동으로 종료일을 시작일과 같게 바꾼다.
```

이 로직은 검증이라기보다 자동 보정에 가깝다.  
업무적으로 자동 보정이 합의되어 있다면 Determination을 검토해야 한다.

좋은 예:

```text
종료일이 시작일보다 빠르면 저장을 막고 명확한 오류 메시지를 반환한다.
```

## 9. Determination 상세 이해

### 9.1 Determination의 목적

Determination은 시스템이 자동으로 값을 결정하거나 보정하는 로직이다.

예를 들어 Travel Request 생성 시 사용자가 상태를 직접 입력하지 않아도 시스템이 자동으로 상태를 `N`으로 설정할 수 있다.

```text
신규 생성 → Status = 'N'
```

이런 로직은 Determination에 적합하다.

### 9.2 Determination에 적합한 규칙

| 규칙 | Determination 적합성 |
|---|---|
| 생성 시 기본 상태 설정 | 적합 |
| 금액 합계 자동 계산 | 적합 |
| 마지막 변경자/변경일시 설정 | 적합 |
| 파생 코드 자동 결정 | 적합 |
| 저장 가능 여부 판단 | Validation이 더 적합 |
| 사용자가 누른 승인 버튼 처리 | Action이 더 적합 |

### 9.3 BDEF 선언 예

```abap
determination setInitialStatus on modify
{ create; }
```

이 선언은 Entity가 생성될 때 Determination을 실행한다는 의미로 이해할 수 있다.

### 9.4 Determination 구현 기본 형태

```abap
METHOD setInitialStatus.

  MODIFY ENTITIES OF zi_gpt_travel IN LOCAL MODE
    ENTITY Travel
      UPDATE FIELDS ( Status )
      WITH VALUE #(
        FOR key IN keys
        ( %tky   = key-%tky
          Status = 'N' )
      )
    REPORTED DATA(lt_reported).

ENDMETHOD.
```

위 코드는 신규 생성된 Travel Request의 상태를 `N`으로 설정하는 개념 예시이다.

### 9.5 Determination에서 주의할 점

Determination은 자동 변경 로직이므로 다음 원칙을 지켜야 한다.

| 원칙 | 설명 |
|---|---|
| 예측 가능성 | 사용자가 예상 가능한 값만 자동 변경한다. |
| 최소 변경 | 필요한 필드만 변경한다. |
| 무한 루프 방지 | Determination이 다시 Determination을 유발하는 구조를 주의한다. |
| 검증과 분리 | 오류 판단은 Validation으로 분리한다. |
| 메시지 명확화 | 자동 보정이 사용자에게 중요한 의미라면 메시지 또는 UI 표시를 검토한다. |

## 10. Action 상세 이해

### 10.1 Action의 목적

Action은 사용자가 명시적으로 실행하는 업무 명령이다.

예를 들어 Travel Request에는 다음과 같은 업무 명령이 있을 수 있다.

| Action | 의미 |
|---|---|
| `approve` | 승인 |
| `reject` | 반려 |
| `cancel` | 취소 |
| `submit` | 제출 |

이런 동작은 단순 Update와 다르다.  
사용자 입장에서는 “상태 필드를 A로 바꾸기”가 아니라 “승인한다”라는 업무 명령이다.

따라서 RAP에서는 이를 Action으로 모델링할 수 있다.

### 10.2 BDEF 선언 예

```abap
action approve result [1] $self;
```

의미는 다음과 같다.

| 구문 | 의미 |
|---|---|
| `action approve` | `approve`라는 Action을 정의 |
| `result [1] $self` | 실행 후 현재 Entity 자신을 결과로 반환 |

### 10.3 Action 구현 기본 형태

```abap
METHOD approve.

  MODIFY ENTITIES OF zi_gpt_travel IN LOCAL MODE
    ENTITY Travel
      UPDATE FIELDS ( Status )
      WITH VALUE #(
        FOR key IN keys
        ( %tky   = key-%tky
          Status = 'A' )
      )
    FAILED failed
    REPORTED reported.

  READ ENTITIES OF zi_gpt_travel IN LOCAL MODE
    ENTITY Travel
      ALL FIELDS
      WITH CORRESPONDING #( keys )
    RESULT DATA(lt_travel).

  result = VALUE #(
    FOR travel IN lt_travel
    ( %tky   = travel-%tky
      %param = travel )
  ).

ENDMETHOD.
```

Action은 상태 변경, 후속 처리, 메시지 반환, 결과 반환을 함께 다룰 수 있다.

### 10.4 Action과 일반 Update의 차이

| 구분 | 일반 Update | Action |
|---|---|
| 의미 | 필드 값을 수정 | 업무 명령 실행 |
| UI 표현 | 필드 편집 | 버튼/메뉴 |
| 예시 | Status = 'A' 입력 | Approve 버튼 |
| 권한 | 필드/Entity 수정 권한 중심 | Action별 권한 검토 가능 |
| 검증 | Save Validation 중심 | Action 내부 검증 + Save Validation 가능 |

## 11. Projection Behavior와 서비스 노출

Interface Behavior에서 Action을 정의했다고 해서 Projection에서 자동으로 모두 노출된다고만 생각하면 안 된다.  
Projection Behavior에서도 어떤 동작을 사용할지 명확히 지정하는 흐름을 이해해야 한다.

예시:

```abap
projection;
strict ( 2 );

define behavior for ZC_GPT_TRAVEL alias Travel
use etag
{
  use create;
  use update;
  use delete;

  use action approve;
}
```

Projection Behavior는 소비 모델에서 허용할 동작을 정한다.

| 위치 | 역할 |
|---|---|
| Interface BDEF | BO 내부 동작의 정의와 구현 연결 |
| Projection BDEF | 외부 소비자에게 노출할 동작 선택 |

Fiori Elements에서 Action은 버튼 형태로 노출될 수 있다.  
다만 실제 버튼 위치, 텍스트, 표시 조건은 UI Annotation, Service Binding, Fiori Elements 템플릿 동작과 함께 검토해야 한다.

## 12. 실행 흐름 비교

### 12.1 생성 시나리오

```text
사용자가 Travel Request 생성
→ 필드 입력
→ RAP Modify 처리
→ Determination setInitialStatus 실행
→ 사용자가 Save
→ Validation validateDates 실행
→ 오류 없으면 저장
→ 오류 있으면 failed/reported 반환
```

### 12.2 승인 시나리오

```text
사용자가 Approve Action 실행
→ Action approve 호출
→ 상태를 A로 변경
→ 필요한 경우 Action 내부 검증
→ Save Phase에서 Validation 실행 가능
→ 결과 Entity 반환
→ UI 또는 OData Consumer가 변경 결과 확인
```

### 12.3 오류 시나리오

```text
사용자가 EndDate를 BeginDate보다 빠르게 입력
→ Save 실행
→ Validation validateDates 실행
→ failed-travel에 해당 Key 추가
→ reported-travel에 오류 메시지 추가
→ 저장 실패
→ UI에 오류 메시지 표시
```

## 13. Validation / Determination / Action 선택 기준

비즈니스 규칙을 구현할 때 다음 기준으로 판단한다.

| 질문 | 적합한 RAP 개념 |
|---|---|
| 저장 전에 오류 여부를 판단하는가? | Validation |
| 시스템이 자동으로 값을 채워야 하는가? | Determination |
| 사용자가 명령을 실행하는가? | Action |
| 명령 실행 후 상태가 바뀌는가? | Action |
| 생성 시 기본값을 넣는가? | Determination |
| 필드 간 관계가 맞는지 확인하는가? | Validation |
| 승인/반려/취소 같은 업무 이벤트인가? | Action |

## 14. 실무 설계 원칙

### 14.1 Validation은 명확하고 예측 가능해야 한다

Validation 메시지는 사용자 또는 API 소비자가 바로 이해할 수 있어야 한다.

나쁜 메시지:

```text
Error occurred.
```

좋은 메시지:

```text
종료일은 시작일보다 빠를 수 없습니다.
```

### 14.2 Determination은 숨은 부작용을 만들지 않아야 한다

Determination은 자동 처리이므로 너무 많은 필드를 조용히 바꾸면 사용자가 결과를 이해하기 어렵다.

권장:

```text
생성 시 기본 상태
합계 금액 계산
변경자/변경일시 설정
```

비권장:

```text
사용자가 입력한 핵심 업무값을 별도 설명 없이 다른 값으로 변경
```

### 14.3 Action은 업무 언어로 이름을 정한다

Action 이름은 기술 구현보다 업무 의미를 드러내야 한다.

좋은 예:

```text
approve
reject
submit
cancel
reopen
```

나쁜 예:

```text
changeStatus
updateField
processData
doAction
```

### 14.4 Clean Core 관점

Clean Core 관점에서는 표준 객체를 직접 수정하기보다 확장 가능한 프레임워크와 명확한 비즈니스 객체 경계를 사용하는 것이 중요하다.  
RAP의 Behavior Layer는 비즈니스 로직을 Entity 중심으로 구조화하여 서비스와 UI, 내부 로직 간 결합도를 낮추는 데 도움을 준다.

```abap
managed implementation in class zbp_i_gpt_travel unique;

define behavior for ZI_GPT_TRAVEL alias Travel
persistent table zgpt_travel
lock master
authorization master ( instance )
etag master LastChangedAt
{
  create;
  update;
  delete;

  {
    create;

  {
    create;
    update;

  action approve result [1] $self;
}
```

```abap
projection;
strict ( 2 );

define behavior for ZC_GPT_TRAVEL alias Travel
use etag
{
  use create;
  use update;
  use delete;

  use action approve;
}
```

### 15.6 Behavior Implementation Class Method 개요

```abap
CLASS lhc_Travel DEFINITION INHERITING FROM cl_abap_behavior_handler.
  PRIVATE SECTION.

    METHODS setInitialStatus FOR DETERMINE ON MODIFY
      IMPORTING keys FOR Travel~setInitialStatus.

    METHODS validateDates FOR VALIDATE ON SAVE
      IMPORTING keys FOR Travel~validateDates.

    METHODS approve FOR MODIFY
      IMPORTING keys FOR ACTION Travel~approve RESULT result.

ENDCLASS.
```

[추정] ADT에서 Quick Fix로 Handler Method를 생성하면 실제 Method Signature는 현재 시스템의 RAP 릴리스와 BDEF 선언에 맞춰 자동 생성된다. 교육 시에는 수동 암기보다 ADT Quick Fix로 생성된 시그니처를 기준으로 설명하는 것이 안전하다.

## 16. 디버깅과 검증 포인트

### 16.1 Validation 디버깅 포인트

| 포인트 | 확인 내용 |
|---|---|
| Method 진입 여부 | Save 시 Validation Method가 호출되는가 |
| `keys` 값 | 검증 대상 Entity Key가 들어오는가 |
| READ ENTITIES 결과 | 검증에 필요한 필드가 읽혔는가 |
| 조건문 | 오류 조건이 정확한가 |
| `failed` | 실패 Key가 채워졌는가 |
| `reported` | 메시지가 채워졌는가 |

### 16.2 Determination 디버깅 포인트

| 포인트 | 확인 내용 |
|---|---|
| 실행 시점 | create 시 Determination이 실행되는가 |
| 변경 대상 | Status만 변경하는가 |
| MODIFY ENTITIES | Local Mode로 정상 업데이트되는가 |
| 반복 실행 | 불필요하게 여러 번 실행되지 않는가 |
| 결과 확인 | 생성 직후 Status 값이 `N`인가 |

### 16.3 Action 디버깅 포인트

| 포인트 | 확인 내용 |
|---|---|
| Action 호출 | UI 또는 EML에서 Action Method가 호출되는가 |
| 권한/상태 | 승인 가능한 상태인지 검토되는가 |
| 상태 변경 | Status가 `A`로 변경되는가 |
| 결과 반환 | `result`에 `$self`가 반환되는가 |
| 메시지 | 성공/오류 메시지가 소비자에게 전달되는가 |

## 17. 오류 상황과 해결

### 17.1 Validation이 실행되지 않음

| 원인 | 해결 |
|---|---|
| BDEF에 validation 선언 누락 | `validation ... on save` 선언 확인 |
| Trigger 필드 누락 | `field BeginDate, EndDate` 등 선언 확인 |
| Entity Alias 불일치 | Method Signature와 BDEF Alias 확인 |
| 저장이 아닌 단순 Modify만 수행 | Save Phase까지 실행되는지 확인 |

### 17.2 Determination이 값을 바꾸지 않음

| 원인 | 해결 |
|---|---|
| `on modify` 트리거 조건 누락 | `create;` 또는 필요한 트리거 확인 |
| MODIFY ENTITIES 대상 필드 누락 | `UPDATE FIELDS ( Status )` 확인 |
| Readonly 필드 변경 시도 | BDEF field control 확인 |
| 같은 값으로만 설정 | 실제 변경 전후 값 비교 |

### 17.3 Action 버튼이 보이지 않음

| 원인 | 해결 |
|---|---|
| Projection Behavior에서 `use action` 누락 | `use action approve;` 추가 |
| Service Binding 미갱신 | Service Binding Publish/Refresh 확인 |
| UI Annotation 부족 | Fiori Elements Annotation 확인 |
| 권한 또는 Feature Control 영향 | Authorization/Feature Control 확인 |

### 17.4 메시지가 UI에 표시되지 않음

| 원인 | 해결 |
|---|---|
| `reported` 미작성 | `reported-travel` 채우기 |
| `%element-*` 누락 | 필드 수준 메시지 표시 필요 시 element marker 설정 |
| Severity 부적절 | Error/Warning/Information 수준 확인 |
| UI 갱신 문제 | Service Binding 및 UI 재실행 확인 |

```abap
MODIFY ENTITIES OF zi_gpt_travel
```

초급자는 이 코드를 완전히 암기하기보다 다음 감각을 잡으면 된다.

```text
Validation 실패는 failed/reported로 관찰한다.

```

## 21. 자가 진단 문제

### Q1. Validation과 Determination의 가장 큰 차이는 무엇인가?

**모범 답안:**  
Validation은 저장 가능한 데이터인지 검증하고 오류가 있으면 저장을 막는 역할이다. Determination은 시스템이 자동으로 파생값이나 기본값을 결정하여 데이터를 변경하는 역할이다.

### Q2. 승인 버튼은 Validation, Determination, Action 중 어디에 구현하는 것이 자연스러운가?

**모범 답안:**  
Action이 자연스럽다. 승인은 사용자가 명시적으로 실행하는 업무 명령이며, 단순 필드 검증이나 자동 보정이 아니기 때문이다.

### Q3. Projection Behavior에서 `use action approve;`를 누락하면 어떤 문제가 생길 수 있는가?

**모범 답안:**  
Interface Behavior에 Action이 있어도 Projection 서비스 소비 모델에서 해당 Action이 노출되지 않아 Fiori Elements나 OData 소비자에서 사용할 수 없을 수 있다.

### Q4. Validation에서 `failed`와 `reported`를 모두 사용하는 이유는 무엇인가?

**모범 답안:**  
`failed`는 어떤 Entity의 처리가 실패했는지 RAP Runtime에 알려주고, `reported`는 사용자나 소비자에게 표시할 메시지를 전달한다.

### Q5. 생성 시 Status 기본값을 설정하는 로직을 Validation에 넣으면 왜 좋지 않은가?

**모범 답안:**  
Validation은 검증 책임을 가진 로직이다. 값을 자동으로 변경하는 책임은 Determination에 두는 것이 역할 분리가 명확하고 유지보수성이 좋다.

## 22. 실무 안티패턴

| 안티패턴 | 문제 | 개선 |
|---|---|---|
| Validation에서 데이터를 몰래 변경 | 검증과 보정 책임 혼합 | Determination으로 분리 |
| Determination에서 오류를 과도하게 판단 | 자동 처리와 검증 책임 혼합 | Validation으로 분리 |
| Action 이름이 기술적임 | UI/업무 의미가 불명확 | 업무 동사 사용 |
| 모든 로직을 Action에 몰아넣음 | Save Validation 누락 가능 | 공통 검증은 Validation으로 분리 |
| Projection Behavior 노출 누락 | UI에서 동작 불가 | `use action` 확인 |
| 메시지를 일반 텍스트만 남김 | 필드 위치 표시 어려움 | `%element-*` 활용 |

## 23. 후속 학습 연결

이 모듈은 RAP 입문의 핵심 전환점이다.  
이후 학습은 다음 방향으로 확장된다.

| 후속 주제 | 연결 |
|---|---|
| Draft RAP | Validation/Determination이 Draft Save 흐름과 결합 |
| Feature Control | 상태에 따라 Action 버튼 활성/비활성 제어 |
| Authorization Control | Action 또는 Modify 권한 제어 |
| Side Effects | Determination 결과를 UI에 즉시 반영 |
| Fiori Elements Annotation | Action 버튼, 메시지, Field Control 표시 |
| RAP Test | Behavior Method와 EML 기반 테스트 |

---

## 24. 핵심 요약

```text
Validation은 저장 가능 여부를 판단한다.
Determination은 시스템이 자동으로 값을 결정한다.
Action은 사용자가 명시적으로 실행하는 업무 명령이다.
세 개는 모두 RAP Behavior Layer에 속하지만 책임이 다르다.
역할을 섞지 않는 것이 유지보수성과 Clean Core 관점에서 중요하다.
RAP 예제에서는 반드시 ZI_* Interface View와 ZC_* Projection View를 함께 고려해야 한다.
```
