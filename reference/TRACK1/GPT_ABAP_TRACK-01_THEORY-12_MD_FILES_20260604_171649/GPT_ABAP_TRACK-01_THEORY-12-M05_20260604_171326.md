## 3. Table Maintenance Generator란 무엇인가?

Table Maintenance Generator, 줄여서 TMG는 ABAP Dictionary 테이블 또는 View에 대해 데이터 유지보수용 화면과 관련 객체를 생성하는 기능이다.

일반적으로 사용자는 테이블 데이터를 직접 SQL로 수정하지 않는다.  
실무에서는 데이터 변경에 다음 요소가 필요하다.

| 필요 요소 | 설명 |
|---|---|
| 화면 | 사용자가 데이터를 입력하고 수정할 수 있는 UI |
| 검증 | Key, Foreign Key, 필수값, 값 범위 등을 확인 |
| 권한 | 누가 데이터를 변경할 수 있는지 통제 |
| 이송 | Customizing 성격 데이터의 변경 이력을 Transport로 관리 |
| 유지보수성 | 운영자가 표준 방식으로 데이터를 관리할 수 있어야 함 |

TMG는 이 중 “표준 유지보수 화면”과 “기본 유지보수 흐름”을 빠르게 생성하는 기능이다.

### 3.1 TMG를 사용하지 않는다면?

개발자가 직접 유지보수 프로그램을 만든다면 다음 작업이 필요하다.

```text
화면 생성
PBO/PAI 로직 작성
입력 검증 작성
데이터 조회/저장 로직 작성
권한 체크 작성
오류 메시지 처리
테이블 변경 처리
이송 처리 고려
```

간단한 설정성 테이블 하나를 관리하기 위해 이 모든 것을 직접 구현하는 것은 비효율적이다.  
이때 TMG를 사용하면 SAP 표준 유지보수 다이얼로그를 생성해 `SM30`에서 사용할 수 있다.

## 4. SM30이란 무엇인가?

`SM30`은 Table View Maintenance 트랜잭션이다.  
사용자는 `SM30`에서 테이블명 또는 View명을 입력하고, 생성된 유지보수 다이얼로그를 통해 데이터를 조회하거나 변경한다.

기본 흐름은 다음과 같다.

```text
SM30 실행
→ Table/View Name 입력
→ Maintain 또는 Display 선택
→ 생성된 Maintenance Dialog 호출
→ 데이터 조회/변경
→ 저장
```

중요한 점은 `SM30`이 모든 테이블을 마음대로 수정하는 만능 도구가 아니라는 것이다.  
대상 테이블 또는 View에 대해 유지보수 설정과 권한이 적절히 준비되어 있어야 한다.

### 4.1 SE16N과 SM30의 차이

| 구분 | SE16N | SM30 |
|---|---|---|
| 기본 목적 | 데이터 조회 | 데이터 유지보수 |
| 변경 관점 | 운영상 직접 변경 도구로 일반화하면 위험 | 유지보수 다이얼로그 기반 변경 |
| 생성 객체 필요 | 별도 TMG 불필요 | TMG 또는 View Maintenance 설정 필요 |
| 권한 통제 | 조회/테이블 권한 중심 | 유지보수 권한, Authorization Group 등 고려 |
| 실무 사용 | 데이터 확인 | Customizing/설정성 데이터 관리 |

초급자가 기억할 기준은 다음이다.

```text
데이터를 확인한다 → SE16N
승인된 설정성 데이터를 관리한다 → SM30
```

## 5. TMG가 적합한 대상

TMG는 모든 테이블에 적합한 것은 아니다.  
특히 대량 트랜잭션 데이터나 업무 전표성 데이터는 일반적으로 SM30 직접 유지보수 대상이 아니다.

### 5.1 적합한 경우

| 대상 | 이유 |
|---|---|
| 작은 코드성 테이블 | 값이 적고 관리 화면이 단순하다. |
| Customizing 성격 테이블 | 설정값을 운영자가 관리할 수 있다. |
| Mapping 테이블 | 외부 코드와 내부 코드 매핑 등 단순 관리에 적합하다. |
| Parameter 테이블 | 프로그램 제어값을 관리할 수 있다. |
| Maintenance View | 관련 테이블을 관계 기반으로 함께 관리할 수 있다. |

예시는 다음과 같다.

```text
ZT_JHY_STATUS_CFG
ZT_JHY_REGION_MAP
ZT_JHY_REPORT_PARAM
```

### 5.2 부적합한 경우

| 대상 | 이유 |
|---|---|
| 판매오더/구매오더 같은 전표성 데이터 | 표준 트랜잭션과 비즈니스 로직을 우회할 위험이 있다. |
| 대량 로그 테이블 | SM30 수동 유지보수에 적합하지 않다. |
| 회계/재고 등 정합성 민감 데이터 | 직접 변경 시 감사·정합성 문제가 발생할 수 있다. |
| RAP/애플리케이션에서 관리해야 할 비즈니스 객체 | 별도 권한, 검증, UI, 트랜잭션 처리가 필요하다. |

핵심 원칙은 다음이다.

```text
TMG는 간단한 설정성 데이터 유지보수에 적합하고,
핵심 업무 트랜잭션 데이터 변경에는 일반적으로 적합하지 않다.
```

## 6. TMG 생성 전 준비사항

TMG를 생성하기 전에 대상 테이블 또는 View가 적절히 설계되어 있어야 한다.

### 6.1 테이블 기준 준비사항

| 점검 항목 | 설명 |
|---|---|
| 테이블 활성화 | DDIC 테이블이 Active 상태여야 한다. |
| Key 설계 | 중복 방지를 위한 적절한 Key가 있어야 한다. |
| Data Element | 화면 라벨과 의미 전달을 위해 적절한 Data Element가 권장된다. |
| Foreign Key | 입력값 검증과 F4 Help 연계를 위해 필요할 수 있다. |
| Delivery Class | Customizing/마스터/트랜잭션 성격을 고려한다. |
| Data Browser/Table View Maintenance 설정 | Display/Maintenance 허용 여부를 확인한다. |
| Technical Settings | 테이블이 정상 활성화되어 있어야 한다. |

### 6.2 View 기준 준비사항

Maintenance View를 대상으로 TMG를 만들려면 관계 설정이 더 중요하다.

| 점검 항목 | 설명 |
|---|---|
| Base Table 관계 | Foreign Key 기반 관계가 적절해야 한다. |
| Join 조건 | Maintenance View의 테이블 관계가 명확해야 한다. |
| 유지보수 필드 | 실제 변경할 필드와 조회만 할 필드를 구분해야 한다. |
| Key 구조 | 헤더/아이템 또는 부모/자식 관계가 명확해야 한다. |

[추정] 교육 환경에서는 단일 Z 테이블 대상으로 TMG를 먼저 생성한 뒤, Maintenance View 기반 TMG는 후속 실습 또는 심화 예제로 다루는 방식이 학습 부담을 줄인다.

## 9. Authorization Group

Authorization Group은 해당 유지보수 객체에 대한 권한 통제와 연결된다.

교육용 실습에서는 `&NC&`를 자주 볼 수 있다.  
`&NC&`는 특정 권한 그룹에 할당하지 않는 의미로 이해할 수 있다.  
하지만 실무에서는 민감한 설정 테이블을 무권한 그룹처럼 방치하면 안 된다.

### 9.1 교육용 판단

| 상황 | 판단 |
|---|---|
| 개인 실습용 Local Object | `&NC&`로 진행 가능 |
| 교육 서버 공용 실습 | 강사 기준을 따른다. |
| 실제 프로젝트 설정 테이블 | 프로젝트 권한 그룹 기준을 따른다. |

### 9.2 실무 주의사항

SM30으로 변경 가능한 테이블은 운영 영향이 있을 수 있다.  
따라서 다음을 반드시 고려해야 한다.

```text
누가 Display 가능한가?
누가 Maintain 가능한가?
운영 Client에서 변경 가능한가?
변경 이력이 필요한가?
Transport로만 반영해야 하는가?
```

## 10. Function Group

TMG는 유지보수 다이얼로그를 생성할 때 Function Group을 사용한다.

Function Group은 관련 Function Module과 Screen을 묶는 Repository 객체이다.  
초급자는 다음 정도로 이해하면 된다.

```text
TMG가 생성한 화면과 처리 로직을 담아둘 컨테이너 역할
```

예를 들어 테이블 `ZT_JHY_STATUS_CFG`에 대한 TMG를 만든다면 다음 Function Group을 사용할 수 있다.

```text
ZFG_JHY_STATUS_CFG
```

### 10.1 Function Group 이름 기준

| 기준 | 예시 |
|---|---|
| Z/Y 네임스페이스 사용 | `ZFG_...` |
| 대상 테이블 의미 포함 | `ZFG_JHY_STATUS_CFG` |
| 너무 일반적인 이름 지양 | `ZFG_TEST`, `ZFG_TEMP` 지양 |

### 10.2 Function Group 관리 주의

TMG가 생성한 Function Group을 개발자가 임의로 수정하면 유지보수성이 떨어질 수 있다.  
필요한 보완 로직은 TMG Event를 통해 처리하는 것이 더 적절하다.

## 11. Maintenance Type: One-step과 Two-step

TMG 생성 시 유지보수 유형을 선택할 수 있다.

| 유형 | 설명 | 초급자 관점 |
|---|---|---|
| One-step | Overview 화면에서 데이터 목록과 변경을 한 화면 중심으로 처리 | 단순 테이블에 적합 |
| Two-step | Overview 화면과 Detail 화면을 분리 | 필드가 많거나 상세 입력이 필요한 경우 적합 |

### 11.1 One-step

One-step은 가장 단순한 방식이다.

```text
SM30 실행
→ 데이터 목록 표시
→ 같은 화면에서 행 추가/수정/삭제
→ 저장
```

작은 코드성 테이블에는 One-step이 적합하다.

### 11.2 Two-step

Two-step은 목록과 상세를 분리한다.

```text
SM30 실행
→ Overview 화면에서 항목 선택
→ Detail 화면에서 상세 필드 수정
→ 저장
```

필드 수가 많거나 한 건의 상세 관리가 중요한 경우 적합하다.

### 11.3 교육용 권장

초급 실습에서는 One-step을 먼저 사용한다.

```text
Maintenance Type: One-step
```

Two-step은 화면 흐름이 조금 더 복잡하므로 One-step을 이해한 뒤 비교하는 것이 좋다.

## 12. Screen Number

TMG는 유지보수 화면을 생성할 때 Screen Number를 사용한다.

초급자는 화면 번호 자체를 외우기보다 다음을 이해하면 된다.

```text
TMG는 실제 화면 객체를 생성하며, 이 화면은 Function Group 안에 포함된다.
```

## 13. Recording Routine

Recording Routine은 SM30에서 데이터를 변경할 때 변경 내용을 Transport Request에 기록할지 여부와 연결된다.

이 항목은 테이블의 데이터 성격과 강하게 연결된다.

| 데이터 성격 | Transport 관점 |
|---|---|
| Customizing 데이터 | 변경 내용을 Transport로 이동하는 경우가 많다. |
| Application 데이터 | 운영에서 직접 생성·변경되는 경우가 많다. |
| 교육용 데이터 | 시스템 정책에 따라 단순화 가능 |

### 13.1 초급자 핵심

SM30에서 데이터를 변경할 때 다음 두 종류를 구분해야 한다.

```text
설정성 데이터: 개발/품질/운영으로 이송될 수 있다.
운영성 데이터: 운영 Client에서 직접 관리될 수 있다.
```

테이블의 Delivery Class와 Recording Routine 판단은 서로 연결된다.

[추정] 교육용 실습에서는 Local Object 또는 교육 Client에서 단순히 데이터 변경 흐름을 확인하는 수준으로 진행해도 되지만, 실제 프로젝트에서는 이송 정책을 반드시 확인해야 한다.

Display 모드로 들어가면 현재 테이블 데이터를 조회할 수 있다.

확인 항목은 다음과 같다.

| 항목 | 확인 내용 |
|---|---|
| Field Label | Data Element 라벨이 화면에 적절히 보이는가 |

### 16.3 데이터 추가

```text
STATUS      = A

ACTIVE      = X
SORT_ORDER  = 10
```

`STATUS_TEXT` 또는 `SORT_ORDER`처럼 Key가 아닌 필드를 수정한다.

예시:

```text
STATUS_TEXT = Active User
```

저장 후 변경 결과를 확인한다.

### 16.5 데이터 삭제

교육용 데이터라면 삭제 테스트도 가능하다.  
다만 실무 운영 데이터에서는 삭제가 업무적으로 허용되는지 반드시 확인해야 한다.

### 17.4 오류 3: 권한 부족

| 항목 | 내용 |
|---|---|

### 17.5 오류 4: Key 중복

| 항목 | 내용 |
|---|---|
| 증상 | 신규 행 저장 시 중복 Key 오류가 발생한다. |
| 원인 | 같은 Client와 Key 값을 가진 데이터가 이미 존재한다. |
| 해결 | 기존 데이터 조회 후 다른 Key를 사용하거나 기존 행을 수정한다. |

### 17.6 오류 5: Foreign Key 검증 실패

| 항목 | 내용 |
|---|---|

### 17.7 오류 6: Transport Request 요구

| 항목 | 내용 |
|---|---|
| 증상 | 저장 시 Transport Request 입력을 요구한다. |
| 원인 | Customizing 데이터로 기록되도록 설정되었거나 Client 설정이 Transport를 요구한다. |
| 해결 | 교육/프로젝트 기준에 맞는 Request를 지정한다. |

## 18. TMG Event 개념 맛보기

TMG는 기본 생성 화면만 제공하는 것이 아니라, Event를 통해 특정 시점에 로직을 추가할 수 있다.

예를 들어 다음과 같은 요구가 있을 수 있다.

```text
저장 전 특정 필드를 자동 대문자 변환한다.
신규 생성 시 CREATED_BY, CREATED_ON을 자동 입력한다.
저장 전 중복 업무 조건을 추가 검증한다.
```

이런 요구는 TMG Event를 통해 보완할 수 있다.

초급 단계에서는 Event를 직접 깊게 구현하지 않고, 다음 정도만 이해한다.

```text
TMG는 자동 생성 화면이지만, 필요한 경우 Event로 보완 로직을 추가할 수 있다.
```

TMG Event의 상세 구현은 Screen Programming, Function Group, Modularization, Enhancement 관점과 연결되므로 심화 학습에서 다루는 것이 적절하다.

## 19. 운영 관점 주의사항

SM30은 편리하지만 위험할 수도 있다.  
운영 시스템에서 직접 설정값을 변경할 수 있기 때문이다.

### 19.1 직접 변경의 위험

| 위험 | 설명 |
|---|---|
| 승인 절차 우회 | 프로그램 또는 표준 트랜잭션의 검증 로직을 거치지 않을 수 있다. |
| 감사 문제 | 누가 어떤 기준으로 변경했는지 추적이 필요할 수 있다. |
| 데이터 정합성 문제 | Foreign Key나 추가 업무 검증이 부족하면 잘못된 설정이 저장될 수 있다. |
| 운영 장애 | 잘못된 설정값이 프로그램 실행 결과에 직접 영향을 줄 수 있다. |

## 20. 강사용 설명 포인트

강의에서는 TMG를 단순히 “자동 화면 생성 기능”으로만 설명하지 않는 것이 좋다.

```text
TMG는 설정성 데이터를 표준 방식으로 유지보수하기 위한 도구이다.
```

1. 모든 Z 테이블에 TMG를 만들어도 될까요?
2. 판매오더 데이터를 SM30으로 바꾸면 왜 위험할까요?
3. `&NC&` 권한 그룹을 운영 테이블에 사용해도 될까요?
4. One-step과 Two-step 중 어떤 경우에 Two-step이 더 적합할까요?
5. 설정값 변경을 Transport로 관리해야 하는 이유는 무엇일까요?

### 22.2 서술형

#### Q1. One-step과 Two-step 유지보수의 차이를 설명하시오.

모범 답안:  
One-step은 Overview 화면 중심으로 데이터 목록과 변경을 한 화면에서 처리하는 방식이며, 작은 단순 테이블에 적합하다. Two-step은 Overview 화면과 Detail 화면을 분리하여 한 건의 상세 필드를 별도 화면에서 관리하는 방식이며, 필드가 많거나 상세 관리가 필요한 경우 적합하다.

#### Q2. 운영 시스템에서 SM30 권한을 신중하게 관리해야 하는 이유를 설명하시오.

모범 답안:  
SM30은 설정성 데이터를 직접 변경할 수 있는 통로이므로 잘못된 권한 부여 시 승인 절차 우회, 데이터 정합성 문제, 운영 장애, 감사 추적 문제를 유발할 수 있다. 따라서 Authorization Group, Transport 정책, 변경 로그, 운영 승인 절차를 함께 고려해야 한다.

#### Q3. TMG 생성 전 대상 테이블에서 확인해야 할 항목을 세 가지 이상 쓰시오.

모범 답안:  
테이블 활성화 상태, Key 설계, Data Element 및 Field Label, Foreign Key/F4 Help 설정, Delivery Class, Data Browser/Table View Maintenance 허용 여부, Technical Settings, 권한 그룹 등을 확인해야 한다.

## 24. 핵심 요약

```text
TMG는 테이블 또는 View 데이터를 유지보수하기 위한 표준 다이얼로그를 생성하는 기능이다.
SM30은 생성된 유지보수 다이얼로그를 실행하는 대표 트랜잭션이다.
TMG는 간단한 설정성 데이터 관리에 적합하다.
Function Group, Screen, Authorization Group, Recording Routine은 TMG의 핵심 요소이다.
운영 시스템에서 SM30 권한과 데이터 변경은 신중하게 통제해야 한다.
```

## 25. 다음 모듈 연결

다음 모듈은 `THEORY-12-M06 — Classic View와 CDS View Entity 비교 준비`이다.
