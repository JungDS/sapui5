## 3. Database View란 무엇인가?

### 3.1 쉬운 정의

Database View는 ABAP Dictionary에서 정의하는 Classic View 객체 중 하나이다.  
여러 테이블의 필드를 조인하여 하나의 조회 대상처럼 사용할 수 있게 만든다.

예를 들어 항공사 테이블 `SCARR`와 항공편 연결 테이블 `SPFLI`를 자주 함께 조회한다고 가정한다.

| 테이블 | 의미 | 주요 필드 |
|---|---|---|
| SCARR | 항공사 마스터 | CARRID, CARRNAME, CURRCODE |
| SPFLI | 항공 연결 정보 | CARRID, CONNID, CITYFROM, CITYTO |

Open SQL에서는 다음처럼 매번 JOIN을 작성할 수 있다.

```abap
SELECT FROM scarr AS c
       INNER JOIN spfli AS p
         ON p~carrid = c~carrid
       FIELDS c~carrid,
              c~carrname,
              p~connid,
              p~cityfrom,
              p~cityto
       INTO TABLE @DATA(lt_result).
```

Database View를 사용하면 이 JOIN 구조를 DDIC 객체로 정의해두고, 프로그램에서는 View를 하나의 조회 대상처럼 사용할 수 있다.

```abap
SELECT carrid,
       carrname,
       connid,
       cityfrom,
       cityto
  FROM zv_jhy_carr_conn
  INTO TABLE @DATA(lt_result).
```

즉, Database View는 다음 목적을 가진다.

```text
반복적으로 사용하는 테이블 조인 구조를 DDIC 객체로 정의해 재사용한다.
```

## 4. Open SQL JOIN과 Database View의 핵심 차이

Open SQL JOIN과 Database View는 모두 여러 테이블의 데이터를 함께 조회할 수 있다.  
하지만 사용 위치와 관리 방식이 다르다.

| 구분 | Open SQL JOIN | DDIC Database View |
|---|---|---|
| 정의 위치 | ABAP 프로그램 코드 내부 | ABAP Dictionary Repository Object |
| 재사용 방식 | 프로그램마다 JOIN 작성 | View 객체를 여러 프로그램에서 조회 |
| 변경 관리 | 코드 변경 필요 | View 정의 변경으로 중앙 관리 가능 |
| 가독성 | JOIN이 코드에 직접 보임 | 조회 대상이 단순해짐 |
| 유연성 | 조건, 필드, 조인을 프로그램별로 조정 가능 | View 정의에 묶임 |
| 학습 관점 | SQL 처리 흐름 이해 | 데이터 모델링 객체 이해 |
| 현대화 관점 | 여전히 중요 | CDS View Entity 학습 전 비교 기준 |

### 4.1 Open SQL JOIN이 적합한 경우

다음 경우에는 Open SQL JOIN이 더 자연스럽다.

```text
프로그램마다 조회 조건이나 조인 필드가 자주 달라진다.
일회성 조회 로직이다.
WHERE 조건, GROUP BY, ORDER BY 등을 프로그램 로직과 밀접하게 조합해야 한다.
읽는 사람이 JOIN 구조를 코드 안에서 바로 보는 것이 더 명확하다.
```

예:

```abap
SELECT FROM sflight AS f
       INNER JOIN scarr AS c
         ON c~carrid = f~carrid
       FIELDS f~carrid,
              c~carrname,
              f~connid,
              f~fldate,
              f~price
       WHERE f~carrid = @p_carrid
       INTO TABLE @DATA(lt_flight).
```

### 4.2 Database View가 적합한 경우

다음 경우에는 Database View가 의미를 가진다.

```text
여러 프로그램에서 같은 조인 결과를 반복적으로 사용한다.
표준화된 조회 구조를 Repository 객체로 관리하고 싶다.
ABAP 프로그램의 SELECT 구문을 단순화하고 싶다.
CDS 학습 전 Classic DDIC View의 역할을 이해하고 싶다.
기존 시스템에 이미 Database View 기반 객체가 존재한다.
```

예:

```abap
SELECT *
  FROM zv_jhy_carr_conn
  INTO TABLE @DATA(lt_conn).
```

## 5. Database View를 배우는 이유

S/4HANA 시대에는 CDS View Entity가 더 현대적인 데이터 모델링 수단으로 사용된다.  
그렇다면 왜 Classic DDIC Database View를 배워야 할까?

이유는 세 가지이다.

### 5.1 기존 시스템 이해

많은 SAP 시스템에는 오랜 기간 만들어진 Classic DDIC View가 존재한다.  
운영 시스템을 분석하다 보면 `SE11`에서 View를 열어 조인 관계와 필드 구성을 확인해야 하는 일이 있다.

### 5.2 CDS 학습의 비교 기준

CDS View Entity를 처음 배우면 다음 질문이 생긴다.

```text
기존 DDIC View와 CDS View는 무엇이 다른가?
왜 CDS가 필요한가?
Classic View로도 JOIN이 되는데 굳이 CDS를 써야 하는가?
```

이 질문에 답하려면 Classic DDIC View를 먼저 경험하는 것이 좋다.

### 5.3 Repository Object 사고방식

Database View는 코드가 아니라 Dictionary 객체이다.  
즉, “조회 로직을 프로그램 내부에만 두지 않고 Repository 객체로 모델링할 수 있다”는 사고방식을 익히는 데 도움이 된다.

## 7. 실습 시나리오 개요

### 7.1 실습 목표

`SCARR`와 `SPFLI`를 조인하는 Classic DDIC Database View를 생성한다.

```text
View Name: ZV_JHY_CARR_CONN
Purpose  : Carrier and Connection Basic View
```

[추정] 교육 시스템에 `SCARR`, `SPFLI` Flight Model 데이터가 없거나 비활성화되어 있다면, 강사가 제공한 Z 테이블 또는 시스템 내 유사한 표준 테이블로 대체한다.

### 7.2 사용할 테이블

| 테이블 | 설명 | 사용 필드 |
|---|---|---|
| SCARR | 항공사 정보 | CARRID, CARRNAME, CURRCODE |
| SPFLI | 항공 연결 정보 | CARRID, CONNID, CITYFROM, CITYTO |

### 7.3 조인 조건

```text
SCARR-CARRID = SPFLI-CARRID
```

ABAP Open SQL로 표현하면 다음과 같다.

```abap
FROM scarr AS c
INNER JOIN spfli AS p
  ON p~carrid = c~carrid
```

DDIC Database View에서는 이 관계를 SE11 화면의 Join Conditions에 설정한다.

## 8. SE11에서 Database View 생성 절차

### 8.1 SE11 실행

SAP GUI에서 다음 트랜잭션을 실행한다.

```text
SE11
```

첫 화면에서 `View`를 선택하고 View 이름을 입력한다.

```text
ZV_JHY_CARR_CONN
```

`Create`를 선택한다.

### 8.2 View Type 선택

View Type 선택 팝업에서 다음을 선택한다.

```text
Database View
```

Classic DDIC View에는 여러 유형이 있다.

| View 유형 | 이번 모듈에서의 위치 |
|---|---|
| Database View | 이번 모듈의 핵심 |
| Projection View | 다음 모듈에서 학습 |
| Help View | Search Help 연결에서 학습 |
| Maintenance View | 유지보수 객체에서 학습 |

이번 모듈에서는 Database View만 다룬다.

### 8.3 Short Description 입력

```text
Carrier and Connection Basic View
```

Short Description은 단순 설명이 아니라 Repository 검색과 유지보수에 영향을 준다.  
`Test`, `View`, `Join`처럼 모호한 설명은 피한다.

### 8.4 Tables 입력

Tables 영역에 기본 테이블을 입력한다.

```text
SCARR
SPFLI
```

일반적으로 기준이 되는 테이블과 조인 대상 테이블을 명확하게 구분해 생각한다.

| 테이블 | 역할 |
|---|---|
| SCARR | 항공사 기준 정보 |
| SPFLI | 항공사별 연결 정보 |

### 8.5 Join Conditions 입력

Join Conditions에 다음 관계를 입력한다.

```text
SCARR-CARRID = SPFLI-CARRID
```

초급자는 이 조인 조건이 잘못되면 결과 건수가 크게 달라진다는 점을 기억해야 한다.

잘못된 조인 예:

```text
SCARR-CURRCODE = SPFLI-CARRID
```

이런 조건은 기술적으로 입력될 수 있어도 업무적으로 의미가 없다.

### 8.6 View Fields 선택

View 결과에 노출할 필드를 선택한다.

| View Field | Source Table | Source Field | 설명 |

| CARRID | SCARR | CARRID | 항공사 코드 |
| CARRNAME | SCARR | CARRNAME | 항공사명 |
| CURRCODE | SCARR | CURRCODE | 통화 코드 |

| CITYFROM | SPFLI | CITYFROM | 출발 도시 |
| CITYTO | SPFLI | CITYTO | 도착 도시 |

View Field는 “프로그램에서 조회할 수 있는 컬럼”이 된다.

## 9. Database View 조회 예제

Database View가 활성화되면 Open SQL에서 테이블처럼 조회할 수 있다.

```abap
REPORT zjhy_read_db_view.

SELECT carrid,
       carrname,
       currcode,
       connid,
       cityfrom,
       cityto
  FROM zv_jhy_carr_conn
  INTO TABLE @DATA(lt_conn).

IF sy-subrc = 0.
  LOOP AT lt_conn INTO DATA(ls_conn).
    WRITE: / ls_conn-carrid,
             ls_conn-carrname,
             ls_conn-connid,
             ls_conn-cityfrom,
             ls_conn-cityto.
  ENDLOOP.
ELSE.
  WRITE: / 'No data found.'.
ENDIF.
```

이 예제에서 중요한 점은 다음이다.

```text
ABAP 프로그램은 복잡한 JOIN 조건을 직접 작성하지 않고 View를 조회한다.
```

하지만 이것이 항상 좋은 것은 아니다.  
View 정의를 열어보지 않으면 실제로 어떤 테이블이 어떻게 조인되는지 코드만으로는 바로 보이지 않을 수 있다.

## 10. Open SQL JOIN과 결과 비교

동일한 결과를 Open SQL JOIN으로 직접 조회하면 다음과 같다.

```abap
REPORT zjhy_read_open_sql_join.

SELECT FROM scarr AS c
       INNER JOIN spfli AS p
         ON p~carrid = c~carrid
       FIELDS c~carrid,
              c~carrname,
              c~currcode,
              p~connid,
              p~cityfrom,
              p~cityto
       INTO TABLE @DATA(lt_conn).

IF sy-subrc = 0.
  LOOP AT lt_conn INTO DATA(ls_conn).
    WRITE: / ls_conn-carrid,
             ls_conn-carrname,
             ls_conn-connid,
             ls_conn-cityfrom,
             ls_conn-cityto.
  ENDLOOP.
ENDIF.
```

두 방식의 개념적 결과는 유사하다.  
하지만 관리 포인트가 다르다.

| 관점 | Open SQL JOIN | Database View |
|---|---|---|
| 조인 조건 확인 | ABAP 코드에서 바로 확인 | SE11 View 정의에서 확인 |
| 재사용 | 복사/반복 작성 가능성 | View 객체 재사용 |
| 변경 시 영향 | 해당 프로그램 중심 | View를 사용하는 모든 프로그램 영향 |
| 성능 판단 | SQL 문장 기준 분석 | View 정의 + 실제 SELECT 기준 분석 |
| 학습 가치 | SQL 작성 능력 | DDIC 모델링 이해 |

## 11. Database View 사용 시 성능 관점

초급자는 Database View를 만들면 자동으로 성능이 좋아진다고 오해할 수 있다.  
하지만 Database View는 성능 개선 도구라기보다 **조회 구조를 모델링하는 객체**에 가깝다.

성능은 다음 요소에 의해 결정된다.

| 요소 | 설명 |
|---|---|
| 기본 테이블 데이터량 | 조인 대상 테이블의 건수가 많으면 비용이 증가한다. |
| Join Condition | 적절한 Key 기반 조인인지가 중요하다. |
| WHERE 조건 | View를 조회할 때 조건을 잘 걸어야 한다. |
| 선택 필드 | 불필요하게 많은 필드를 읽지 않는 것이 좋다. |
| DB 인덱스 | 기본 테이블의 Key/Index 설계가 영향을 준다. |
| 실행 계획 | DB가 실제로 어떤 방식으로 조회하는지에 따라 달라진다. |

따라서 다음과 같은 코드는 주의해야 한다.

```abap
SELECT *
  FROM zv_jhy_carr_conn
  INTO TABLE @DATA(lt_all).
```

학습용으로는 괜찮을 수 있지만, 실무에서는 필요한 필드와 조건을 명확히 지정하는 습관이 중요하다.

권장 예:

```abap
SELECT carrid,
       carrname,
       connid,
       cityfrom,
       cityto
  FROM zv_jhy_carr_conn
  WHERE carrid = @p_carrid
  INTO TABLE @DATA(lt_conn).
```

## 12. 권한과 운영 관점

Database View 자체를 만들고 변경하는 것은 개발 권한과 관련된다.  
또한 View가 참조하는 기본 테이블에 대한 데이터 접근 권한은 시스템 설계와 프로그램 권한 체크 방식에 따라 함께 고려해야 한다.

초급자는 다음 원칙을 기억한다.

```text
DDIC View를 만들 수 있다고 해서 운영 데이터를 자유롭게 조회해도 된다는 뜻은 아니다.
```

실무에서는 다음을 검토해야 한다.

| 검토 항목 | 설명 |
|---|---|
| View 생성 권한 | 개발 시스템에서 Repository Object 생성 권한 필요 |
| Transport | 운영 반영 시 CTS 절차 필요 |
| 데이터 접근 권한 | 프로그램 또는 트랜잭션 권한 체크 필요 |
| 민감 데이터 | 인사, 재무, 개인정보 등은 조회 구조 설계 단계부터 주의 |
| 영향 분석 | View 변경 시 사용하는 프로그램 전체 영향 확인 |

## 13. 자주 발생하는 오류와 해결

### 13.1 View 활성화 오류

| 항목 | 내용 |
|---|---|
| 증상 | Activate 시 오류 발생 |
| 가능한 원인 | Join Condition 누락, 필드 선택 오류, 기본 테이블 비활성, 이름 충돌 |
| 해결 | SE11에서 오류 메시지를 확인하고 Tables, Join Conditions, View Fields를 순서대로 점검 |

### 13.2 결과 건수가 예상보다 많음

| 항목 | 내용 |
|---|---|
| 증상 | View 조회 결과가 너무 많이 나온다. |
| 가능한 원인 | Join Condition이 부족하거나 잘못되었다. |
| 해결 | 기본 테이블의 Key 관계를 확인하고 조인 조건을 보완한다. |

### 13.3 결과가 나오지 않음

| 항목 | 내용 |
|---|---|
| 증상 | SE16N 또는 ABAP SELECT 결과가 비어 있다. |
| 가능한 원인 | 기본 테이블에 조인 조건을 만족하는 데이터가 없다. |
| 해결 | 각 기본 테이블을 개별 조회한 뒤 공통 Key 값이 있는지 확인한다. |

### 13.4 Field 이름 충돌

| 항목 | 내용 |
|---|---|
| 증상 | 서로 다른 테이블에 같은 필드명이 있어 View Field 구성이 혼란스럽다. |
| 가능한 원인 | 여러 테이블에 같은 이름의 필드가 존재한다. |
| 해결 | View Field 선택 시 Source Table과 Source Field를 명확히 확인한다. 필요 시 필드명 설계를 재검토한다. |

### 13.5 View를 테이블처럼 변경하려고 함

| 항목 | 내용 |
|---|---|
| 증상 | View에 데이터를 직접 INSERT/UPDATE하려고 한다. |
| 가능한 원인 | View를 실제 저장 테이블로 오해했다. |
| 해결 | Database View는 기본적으로 조회 구조로 이해한다. 데이터 변경은 기본 테이블 또는 승인된 유지보수 객체를 통해 수행한다. |

## 14. 실무 판단 기준

Database View를 만들지 Open SQL JOIN으로 둘지 고민될 때 다음 기준을 사용한다.

### 14.1 Database View를 검토할 수 있는 경우

```text
같은 조인 구조가 여러 프로그램에서 반복된다.
업무적으로 명확한 조회 모델 이름을 부여하고 싶다.
기존 Classic DDIC 기반 프로젝트의 일관성을 유지해야 한다.
CDS 도입 전 단계의 유지보수성 개선이 필요하다.
```

### 14.2 Open SQL JOIN이 더 나은 경우

```text
조회 조건이 프로그램마다 다르다.
조인 구조가 일회성이다.
코드에서 데이터 흐름을 명확히 드러내는 것이 더 중요하다.
최신 ABAP SQL 기능을 적극 활용해야 한다.
CDS 또는 RAP 모델링으로 갈 계획이 명확하다.
```

### 14.3 무조건 피해야 할 사고방식

```text
JOIN이 길어지니까 무조건 View로 뺀다.
Database View를 만들면 성능이 자동으로 좋아진다.
View를 만들면 권한 문제가 자동으로 해결된다.
Classic View가 CDS와 동일한 역할을 한다.
```

이런 사고방식은 실무에서 유지보수 리스크를 만든다.

## 15. CDS View Entity와의 연결

이 Section의 마지막 모듈에서 Classic View와 CDS View Entity를 비교한다.  
이번 모듈에서는 다음 정도만 이해한다.

| 구분 | Classic DDIC Database View | CDS View Entity |
|---|---|---|
| 정의 방식 | SE11 기반 Dictionary View | DDL Source 기반 코드형 모델 |
| 의미 표현 | 제한적 | Annotation, Association 등 풍부 |
| 현대 SAP 모델링 | 기존 객체 이해에 중요 | S/4HANA 중심 데이터 모델링 핵심 |
| RAP 연결 | 직접적이지 않음 | RAP 모델링의 핵심 기반 |

Classic DDIC Database View는 “여러 테이블을 하나의 조회 구조로 묶는다”는 개념을 익히는 데 유용하다.  
CDS View Entity는 이 개념을 현대적인 방식으로 확장한다.

## 17. 평가 문제

### 17.1 객관식

#### Q1. Database View의 가장 적절한 설명은?

A. ABAP 프로그램 내부에서만 존재하는 로컬 타입이다.  
B. 여러 테이블의 조인 구조를 ABAP Dictionary 객체로 정의한 Classic View이다.  
C. 화면 입력 필드를 그룹화하는 Selection Screen 객체이다.  
D. 데이터를 직접 저장하는 신규 Transparent Table이다.

**정답:** B

#### Q2. Open SQL JOIN과 Database View의 차이로 올바른 것은?

A. Open SQL JOIN은 SE11에서만 작성한다.  
B. Database View는 ABAP 코드 내부에서만 존재한다.  
C. Open SQL JOIN은 프로그램 코드에 작성되고, Database View는 DDIC Repository Object로 관리된다.  
D. Database View는 항상 Open SQL JOIN보다 성능이 좋다.

**정답:** C

#### Q3. Database View 사용 시 주의할 점으로 적절한 것은?

A. View를 만들면 권한 체크가 자동으로 완성된다.  
B. View를 만들면 조인 조건이 틀려도 결과는 항상 정확하다.  
C. View는 조회 구조로 이해하고 기본 테이블 관계와 결과 건수를 검증해야 한다.  
D. View는 모든 CDS View Entity를 완전히 대체한다.

**정답:** C

### 17.2 단답형

#### Q1. Database View를 사용하는 대표적인 이유를 쓰시오.

**모범 답안:**  
여러 프로그램에서 반복적으로 사용하는 테이블 조인 구조를 ABAP Dictionary 객체로 정의하여 재사용하고, 프로그램의 SELECT 구문을 단순화하기 위해 사용한다.

#### Q2. 결과 건수가 예상보다 많이 나올 때 가장 먼저 확인할 항목은 무엇인가?

**모범 답안:**  
Join Condition이 올바르게 정의되었는지 확인해야 한다. 기본 테이블 간 Key 관계가 누락되거나 잘못 연결되면 결과 건수가 비정상적으로 증가할 수 있다.

#### Q3. Database View와 CDS View Entity의 관계를 초급자 관점에서 설명하시오.

**모범 답안:**  
Database View는 Classic DDIC 방식의 조회 모델이고, CDS View Entity는 S/4HANA 시대의 현대적 데이터 모델링 방식이다. Database View를 배우면 여러 테이블을 하나의 조회 구조로 묶는 기본 개념을 이해할 수 있고, 이후 CDS 학습의 비교 기준이 된다.

## 19. 핵심 요약

이번 모듈의 핵심은 다음과 같다.

```text
Database View는 Classic ABAP Dictionary View 객체이다.
Database View는 여러 테이블의 INNER JOIN 기반 조회 구조를 Repository Object로 정의한다.
Open SQL JOIN은 프로그램 코드에 조인을 작성하는 방식이다.
Database View는 반복 조회 구조를 중앙에서 재사용할 수 있게 한다.
Database View가 자동 성능 개선이나 권한 해결을 보장하지는 않는다.
Classic View를 이해하면 CDS View Entity 학습의 비교 기준이 생긴다.
```
