## 3. Projection View란 무엇인가?

Projection View는 ABAP Dictionary에서 정의하는 Classic DDIC View 유형 중 하나이다.  
핵심 목적은 **하나의 기본 테이블에서 필요한 필드만 선택하여 제한된 구조로 노출하는 것**이다.

간단히 말하면 다음과 같다.

```text
Projection View = 하나의 테이블을 대상으로 필드 일부만 보여주는 DDIC View
```

예를 들어 `SCARR` 테이블에 다음 필드가 있다고 가정한다.

| 원본 테이블 | 필드 |
|---|---|
| SCARR | MANDT |
| SCARR | CARRID |
| SCARR | CARRNAME |
| SCARR | CURRCODE |
| SCARR | URL |

학습 목적상 항공사 ID와 항공사명만 보여주고 싶다면 Projection View를 다음처럼 설계할 수 있다.

| Projection View | 포함 필드 |
|---|---|
| ZV_JHY_SCARR_PROJ | MANDT |
| ZV_JHY_SCARR_PROJ | CARRID |
| ZV_JHY_SCARR_PROJ | CARRNAME |

이때 `CURRCODE`, `URL`은 View 결과에 노출하지 않는다.

## 4. Projection의 의미

Projection이라는 말은 데이터 모델링에서 “전체 컬럼 중 일부 컬럼만 선택한다”는 의미로 자주 사용된다.

관계형 데이터 관점에서 Projection은 다음과 같다.

```text
테이블 = 행(Row) + 열(Column)
Projection = 열(Column)을 제한하는 작업
Selection = 행(Row)을 제한하는 작업
```

예를 들어 다음 SQL을 보자.

```abap
SELECT carrid,
       carrname
  FROM scarr
  INTO TABLE @DATA(lt_carrier).
```

이 SQL은 `SCARR` 테이블에서 `CARRID`, `CARRNAME` 필드만 조회한다.  
즉, 프로그램 코드 안에서 Projection을 수행한 것이다.

Projection View는 이 “필드 제한”을 ABAP Dictionary Repository Object로 정의해 재사용할 수 있게 만든 것이다.

---

## 5. Projection View의 핵심 특징

Projection View의 주요 특징은 다음과 같다.

| 특징 | 설명 |
|---|---|
| 단일 테이블 기반 | 일반적으로 하나의 기본 테이블을 대상으로 한다. |
| 필드 제한 | 원본 테이블의 필드 중 일부만 View에 포함한다. |
| Repository Object | SE11에서 생성·활성화되는 DDIC 객체이다. |
| 재사용 가능 | ABAP 프로그램에서 DDIC 객체로 참조할 수 있다. |
| JOIN 목적 아님 | 여러 테이블 결합이 목적이라면 Database View 또는 Open SQL JOIN을 검토해야 한다. |
| 계산/집계 목적 아님 | 복잡한 계산, 집계, 조건 로직은 Projection View의 중심 목적이 아니다. |
| Classic View 유형 | CDS View Entity와는 다른 구식 DDIC View 계열이다. |

초급자는 다음 문장을 기억하면 된다.

```text
Projection View는 테이블을 새로 만드는 것이 아니라, 기존 테이블의 일부 필드만 보여주는 Classic DDIC View이다.
```

## 6. Projection View와 Database View 비교

Projection View는 Database View와 자주 비교된다.

| 구분 | Projection View | Database View |
|---|---|---|
| 대상 테이블 수 | 기본적으로 하나의 테이블 | 하나 이상의 테이블 가능 |
| 주요 목적 | 필드 제한 | 테이블 조인 및 View 정의 |
| JOIN 조건 | 사용하지 않음 | 사용 가능 |
| 필드 선택 | 가능 | 가능 |
| 관계 표현 | 제한적 | Join 조건으로 표현 |
| 학습 포인트 | Field Restriction | Inner Join / DDIC View |
| 현대 대안 | CDS View Entity, Open SQL Field List | CDS View Entity, Open SQL JOIN |

Projection View를 Database View처럼 생각하면 안 된다.  
Projection View의 본질은 “JOIN”이 아니라 “필드 제한”이다.

---

## 7. Projection View와 Open SQL Field List 비교

ABAP 프로그램에서는 Projection View를 만들지 않아도 Open SQL에서 필요한 필드만 조회할 수 있다.

예를 들어 다음 Open SQL은 `SCARR`의 일부 필드만 조회한다.

```abap
SELECT carrid,
       carrname
  FROM scarr
  INTO TABLE @DATA(lt_carrier).
```

이 방식과 Projection View의 차이는 다음과 같다.

| 구분 | Open SQL Field List | Projection View |
|---|---|---|
| 정의 위치 | ABAP 프로그램 내부 | ABAP Dictionary |
| 재사용성 | 프로그램별 반복 가능 | Repository Object로 재사용 가능 |
| 변경 영향 | 해당 프로그램 중심 | 참조 객체 전체에 영향 |
| 필드 제한 가시성 | 코드에서 확인 | DDIC 객체에서 확인 |
| 객체 관리 | 별도 객체 없음 | 활성화/패키지/운송 필요 |
| 현대 개발 권장성 | 일반 조회에는 충분히 실용적 | 필요한 경우에만 신중히 사용 |

실무에서는 단순히 특정 프로그램에서 필드 몇 개만 필요하다는 이유로 Projection View를 만드는 것은 과할 수 있다.  
그럴 때는 Open SQL에서 필요한 필드만 명시하는 편이 더 단순하다.

## 8. Projection View의 장점

Projection View가 완전히 쓸모없는 것은 아니다.  
특정 상황에서는 다음 장점이 있다.

| 장점 | 설명 |
|---|---|
| 필드 노출 제한 | 원본 테이블의 모든 필드를 보여주지 않고 필요한 필드만 노출할 수 있다. |
| 구조 재사용 | 동일한 제한 필드 구조를 여러 프로그램에서 재사용할 수 있다. |
| 의미 있는 View 이름 | 특정 목적의 View로 이름을 부여할 수 있다. |
| Classic DDIC 흐름 학습 | Database View, Help View, Maintenance View와 비교하기 좋다. |
| 기존 시스템 호환 | 오래된 ECC/SAP GUI 기반 시스템의 유지보수에서 만날 수 있다. |

예를 들어 다음과 같은 목적에는 Projection View가 교육적으로 유용하다.

```text
SCARR 전체 필드 중 CARRID, CARRNAME만 학습용으로 노출한다.
Z 테이블의 민감하지 않은 일부 필드만 조회용으로 제한한다.
Classic DDIC View 유형 간 차이를 비교한다.
```

## 9. Projection View의 한계

Projection View는 한계가 명확하다.  
이 한계를 이해하는 것이 이번 모듈의 핵심이다.

## 9.1 단일 테이블 중심

Projection View는 기본적으로 하나의 테이블에서 필드를 제한하는 객체이다.  
여러 테이블을 결합하는 목적에는 맞지 않는다.

여러 테이블을 함께 조회해야 한다면 다음을 검토한다.

| 목적 | 적합한 선택 |
|---|---|
| 단순 ABAP 프로그램 내부 조인 | Open SQL JOIN |
| 재사용 가능한 의미 모델 | CDS View Entity |
| Classic DDIC 비교 학습 | Database View |
| F4 도움말 기반 View | Help View |
| 유지보수 화면 기반 객체 | Maintenance View |

## 9.2 복잡한 로직 표현에 부적합

Projection View는 필드 제한이 핵심이다.  
복잡한 계산, CASE 로직, 집계, 파라미터, Annotation 기반 UI 의미 표현은 중심 기능이 아니다.

현대 S/4HANA 기준으로 이런 요구가 있다면 CDS View Entity가 더 적합할 가능성이 높다.

```text
금액 계산
상태값 변환
권한 관련 의미 모델
Fiori Elements 노출
OData 서비스 기반 조회
Association 기반 모델링
```

이런 요구는 Projection View보다 CDS View Entity/RAP 모델에서 다루는 것이 자연스럽다.

## 9.3 객체 남발 위험

Projection View는 Repository Object이다.  
즉, 하나 만들 때마다 객체명, 패키지, 운송, 활성화, 영향 분석 대상이 생긴다.

단순히 `SELECT carrid, carrname FROM scarr` 정도를 여러 번 쓰기 싫다는 이유만으로 View를 만들면 객체가 불필요하게 늘어난다.

실무에서 피해야 할 패턴은 다음과 같다.

```text
ZV_TABLE_FIELD1
ZV_TABLE_FIELD2
ZV_TABLE_FIELD3
ZV_TABLE_SMALL
ZV_TABLE_TEMP
```

이런 View가 많아지면 어떤 View를 왜 만들었는지 파악하기 어려워진다.

## 9.4 권한 보안 대체 수단으로 오해하면 안 됨

Projection View는 필드 노출을 제한할 수 있지만, 이것만으로 완전한 권한 보안 체계를 대체한다고 보면 안 된다.

예를 들어 민감 필드를 View에서 제외했다고 해도, 사용자가 원본 테이블에 접근할 수 있는 권한을 가지고 있다면 별도 경로로 데이터를 볼 수 있을 수 있다.

보안이 목적이라면 다음을 함께 검토해야 한다.

| 보안 관점 | 검토 대상 |
|---|---|
| 트랜잭션 권한 | T-Code, Authorization Object |
| 테이블 조회 권한 | S_TABU_DIS 등 고객사 권한 정책 |
| 프로그램 권한 체크 | AUTHORITY-CHECK |
| CDS 권한 | DCL, Access Control |
| UI/서비스 권한 | Fiori Catalog, OData 권한 |

Projection View는 보안 모델의 일부 보조 수단은 될 수 있지만, 권한 설계 전체를 대체하지 않는다.

## 12. 필드 선택 기준

Projection View에서 어떤 필드를 포함할지는 매우 중요하다.

## 12.1 포함해야 하는 필드

다음 필드는 일반적으로 포함 여부를 신중히 판단해야 한다.

| 필드 유형 | 판단 기준 |
|---|---|
| Key Field | 원본 데이터 식별이 필요하면 포함하는 것이 안전하다. |
| Client Field | Client-dependent 테이블이면 `MANDT` 의미를 이해해야 한다. |
| 업무 식별 필드 | 조회 결과를 구분하기 위해 필요하다. |
| 설명 필드 | 사용자에게 의미 있는 텍스트를 제공한다. |

예제에서는 `CARRID`, `CARRNAME`이 핵심이다.

## 12.2 제외할 수 있는 필드

| 필드 유형 | 제외 이유 |
|---|---|
| 이번 조회 목적에 필요 없는 필드 | View 목적 단순화 |
| 민감하거나 불필요한 필드 | 노출 최소화 |
| 화면/리포트에서 사용하지 않는 필드 | 구조 간결화 |
| 후속 처리에 필요 없는 기술 필드 | 혼란 감소 |

다만 Key Field를 과도하게 제외하면 조회 결과의 식별성이 약해질 수 있다.  
특히 후속 ABAP 프로그램에서 UPDATE, DELETE, 상세 조회와 연결될 여지가 있다면 Key 필드 제외는 신중해야 한다.

## 13. ABAP Open SQL에서 Projection View 사용

Projection View를 활성화하면 ABAP Open SQL에서 조회 대상으로 사용할 수 있다.

예시:

```abap
REPORT zjhy_projection_view_demo.

SELECT carrid,
       carrname
  FROM zv_jhy_scarr_pj
  INTO TABLE @DATA(lt_carrier).

IF sy-subrc = 0.
  LOOP AT lt_carrier INTO DATA(ls_carrier).
    WRITE: / ls_carrier-carrid,
             ls_carrier-carrname.
  ENDLOOP.
ELSE.
  WRITE: / 'No carrier data found.'.
ENDIF.
```

이 예제에서 중요한 점은 다음이다.

```text
ABAP 프로그램은 Projection View를 테이블처럼 FROM 뒤에 사용할 수 있다.
하지만 Projection View에 없는 필드는 SELECT할 수 없다.
```

예를 들어 `ZV_JHY_SCARR_PJ`에 `URL` 필드를 포함하지 않았다면 다음 코드는 오류가 된다.

```abap
SELECT carrid,
       url
  FROM zv_jhy_scarr_pj
  INTO TABLE @DATA(lt_carrier).
```

`URL`이 View에 존재하지 않기 때문이다.

## 14. 정상 흐름과 오류 흐름

## 14.1 정상 흐름

```text
Projection View 생성
→ Base Table 지정
→ 필요한 필드만 선택
→ 저장
→ 활성화
→ Data Browser 또는 Open SQL로 조회
→ 원본 테이블보다 제한된 필드만 표시됨
```

## 14.2 오류 흐름 1: 여러 테이블을 연결하려고 함

### 상황

Projection View에서 `SCARR`와 `SPFLI`를 함께 연결하려고 한다.

### 문제

Projection View의 목적은 단일 테이블의 필드 제한이다.  
여러 테이블 결합은 Projection View의 중심 사용 목적이 아니다.

### 해결

목적에 따라 다음을 선택한다.

| 요구사항 | 대안 |
|---|---|
| ABAP 프로그램 내부 조인 | Open SQL JOIN |
| Classic DDIC View 비교 학습 | Database View |
| 현대적 재사용 모델 | CDS View Entity |
| 검색 도움말 기반 | Help View |

## 14.3 오류 흐름 2: 필요한 Key 필드를 제외함

### 상황

View에 설명 필드만 포함하고 식별 필드를 제외했다.

예:

```text
CARRNAME만 포함
CARRID 제외
```

### 문제

조회 결과에서 각 행을 안정적으로 구분하기 어렵다.  
후속 처리나 상세 조회 연결도 어려워질 수 있다.

### 해결

최소한의 식별 필드를 포함한다.

```text
CARRID + CARRNAME
```

Client-dependent 테이블의 경우 `MANDT` 처리도 시스템/용도에 맞게 검토한다.

## 14.4 오류 흐름 3: View에 없는 필드를 SELECT함

### 상황

Projection View에는 `CARRID`, `CARRNAME`만 있는데 ABAP에서 `URL`을 SELECT한다.

### 문제

View의 필드 목록에 없는 필드는 조회할 수 없다.

### 해결

다음 중 하나를 선택한다.

```text
Projection View에 해당 필드를 추가한다.
또는 원본 테이블을 직접 조회한다.
또는 별도 View를 설계한다.
```

단, 단순히 필드 하나 추가를 위해 기존 View를 수정하면 해당 View를 참조하는 다른 프로그램에 영향이 있을 수 있으므로 영향 분석이 필요하다.

## 14.5 오류 흐름 4: Projection View를 보안 수단으로만 사용함

### 상황

민감 필드를 숨기기 위해 Projection View를 만들고, 별도 권한 설계를 하지 않는다.

### 문제

View에서 필드를 제외하는 것만으로는 전체 보안 통제가 완성되지 않는다.  
원본 테이블 접근 권한, 프로그램 권한, 트랜잭션 권한, CDS/DCL 권한 등을 함께 고려해야 한다.

### 해결

Projection View는 노출 구조 제한 용도로만 이해하고, 실제 보안은 표준 권한 체계와 함께 설계한다.

## 15. 실무 적용 기준

## 15.1 Projection View를 검토할 수 있는 경우

| 상황 | 판단 |
|---|---|
| 기존 테이블의 일부 필드만 반복적으로 조회해야 함 | 검토 가능 |
| Classic DDIC View 교육/유지보수 목적 | 적합 |
| 오래된 프로그램이 Projection View를 이미 사용함 | 유지보수 이해 필요 |
| 원본 테이블 구조를 단순화해 보여주고 싶음 | 검토 가능 |
| 단일 테이블 기반의 재사용 가능한 제한 구조가 필요함 | 검토 가능 |

## 15.2 Projection View를 피하는 것이 좋은 경우

| 상황 | 이유 |
|---|---|
| 단일 프로그램에서 한 번만 쓰는 조회 | Open SQL Field List가 더 단순 |
| 여러 테이블 조인이 필요 | Open SQL JOIN 또는 CDS가 적합 |
| 계산/집계/CASE 로직이 필요 | CDS View Entity 또는 ABAP SQL 검토 |
| Fiori/OData/RAP 노출 목적 | CDS/RAP 모델이 더 적합 |
| 권한/보안의 핵심 수단으로 사용하려는 경우 | 별도 권한 설계 필요 |
| 객체가 너무 많이 늘어나는 경우 | 유지보수 부담 증가 |

## 16. 현대 S/4HANA 관점에서의 Projection View

S/4HANA 개발에서 데이터 모델링은 CDS View Entity 중심으로 이동했다.  
그렇다고 Classic DDIC View를 몰라도 되는 것은 아니다.

실무에서는 다음 상황에서 Classic Projection View를 만날 수 있다.

```text
기존 ECC 또는 S/4HANA 전환 시스템의 레거시 객체
오래된 Report 또는 Function Module에서 사용 중인 View
SM30/TMG 또는 Search Help와 연결된 Classic View 구조
교육용 DDIC View 비교 학습
```

하지만 신규 개발에서 단순 조회 모델을 만들 때는 다음 순서로 판단하는 것이 좋다.

```text
1. 단순 프로그램 내부 조회인가?
   → Open SQL Field List

2. 재사용 가능한 의미 모델인가?
   → CDS View Entity

3. 오래된 Classic DDIC 객체와 호환해야 하는가?
   → Projection View 검토

4. UI/서비스/RAP/Fiori로 확장될 가능성이 있는가?
   → CDS View Entity 우선 검토
```

## 17. Projection View와 CDS Projection View 혼동 주의

ABAP Dictionary의 Projection View와 RAP/CDS에서 말하는 Projection View는 이름이 비슷하지만 맥락이 다르다.

| 구분 | Classic DDIC Projection View | CDS/RAP Projection View |
|---|---|---|
| 위치 | SE11 Classic DDIC View | ABAP CDS / RAP 모델 |
| 목적 | 단일 테이블 필드 제한 | Interface View를 소비자 관점으로 노출 |
| 문법 | DDIC 화면 기반 | DDL Source |
| 현대 개발 중요도 | 레거시 이해 중심 | RAP/Fiori 모델링에서 중요 |
| 후속 학습 위치 | THEORY-12 | CDS/RAP Section |

이번 모듈에서 다루는 것은 **Classic DDIC Projection View**이다.  
RAP의 `Projection View`는 후속 CDS/RAP 학습에서 별도로 다룬다.

## 18. 실습 과제

## 18.1 기본 실습

다음 조건으로 Projection View를 생성한다.

```text
View Name: ZV_JHY_SCARR_PJ
View Type: Projection View
Base Table: SCARR
Fields:
  MANDT
  CARRID
  CARRNAME
```

생성 후 다음을 확인한다.

```text
1. View가 활성화되었는가?
2. Data Browser에서 조회 가능한가?
3. 원본 SCARR의 CURRCODE, URL이 View에는 보이지 않는가?
4. ABAP Open SQL에서 SELECT 가능한가?
```

## 18.2 비교 실습

다음 두 코드를 비교한다.

### 원본 테이블 직접 조회

```abap
SELECT carrid,
       carrname
  FROM scarr
  INTO TABLE @DATA(lt_from_table).
```

### Projection View 조회

```abap
SELECT carrid,
       carrname
  FROM zv_jhy_scarr_pj
  INTO TABLE @DATA(lt_from_view).
```

비교 질문:

```text
두 결과는 같은가?
Projection View를 만들었을 때 추가로 얻는 이점은 무엇인가?
반대로 불필요하게 복잡해진 점은 무엇인가?
```

## 18.3 오류 실습

Projection View에 포함하지 않은 필드를 SELECT해본다.

```abap
SELECT carrid,
       url
  FROM zv_jhy_scarr_pj
  INTO TABLE @DATA(lt_error).
```

예상 결과:

```text
URL 필드가 View에 없으므로 구문 또는 활성화/실행 단계에서 오류가 발생한다.
```

학습자는 오류 메시지를 기록하고, 해결 방법을 작성한다.

## 19. 강사용 설명 포인트

강사는 이번 모듈에서 다음을 강조하면 좋다.

### 19.1 Projection View는 “JOIN 없는 View”가 아니다

Projection View를 단순히 “JOIN이 없는 View”라고 설명하면 부족하다.  
더 정확한 설명은 다음이다.

```text
Projection View는 단일 테이블의 필드 노출을 제한하는 Classic DDIC View이다.
```

### 19.2 Open SQL로도 필드 제한은 가능하다

Projection View를 만들기 전에 Open SQL의 Field List로 충분한지 판단해야 한다.

```abap
SELECT carrid, carrname FROM scarr ...
```

이 정도 요구라면 별도 Repository Object가 꼭 필요한지 질문해야 한다.

### 19.3 레거시 이해와 현대 개발 판단을 함께 가르친다

Projection View는 오래된 개념이지만, 기존 시스템 유지보수에서는 여전히 만날 수 있다.  
따라서 “쓸모없다”가 아니라 다음 관점이 적절하다.

```text
기존 객체를 이해하기 위해 배운다.
신규 개발에서는 더 나은 대안을 함께 판단한다.
CDS/RAP Projection View와 이름이 같아도 맥락이 다름을 구분한다.
```

## 20. 평가 문제

### 20.1 객관식

#### Q1. Classic DDIC Projection View의 가장 적절한 설명은?

A. 여러 테이블을 조인해 결과를 만드는 View이다.  
B. 하나의 테이블에서 필요한 필드만 제한적으로 노출하는 View이다.  
C. ABAP 프로그램의 Selection Screen을 만드는 객체이다.  
D. CDS Association을 정의하는 객체이다.

**정답:** B

#### Q2. Projection View가 적합하지 않은 요구사항은?

A. 단일 테이블의 일부 필드만 노출  
B. 원본 테이블의 필드 제한  
C. 여러 테이블의 JOIN 결과 재사용  
D. Classic DDIC View 유형 비교 학습

**정답:** C

#### Q3. Projection View에 없는 필드를 ABAP Open SQL에서 SELECT하려 하면 어떻게 되는가?

A. 자동으로 원본 테이블에서 찾아온다.  
B. 빈 값으로 조회된다.  
C. 해당 필드는 조회할 수 없어 오류가 발생한다.  
D. 시스템이 임시 필드를 생성한다.

**정답:** C

### 20.2 단답형

#### Q1. Projection View와 Database View의 차이를 설명하시오.

**모범 답안:**  
Projection View는 하나의 기본 테이블에서 필요한 필드만 제한적으로 노출하는 Classic DDIC View이다. Database View는 여러 테이블을 조인하여 조회 구조를 만들 수 있는 Classic DDIC View이다.

#### Q2. Projection View를 보안 수단으로만 사용하면 안 되는 이유는 무엇인가?

**모범 답안:**  
Projection View는 필드 노출을 제한할 수 있지만 원본 테이블 접근 권한, 트랜잭션 권한, 프로그램 권한, CDS/DCL 권한 등을 대체하지 못한다. 실제 보안은 SAP 권한 체계와 함께 설계해야 한다.

#### Q3. 신규 S/4HANA 개발에서 Projection View 대신 CDS View Entity를 검토해야 하는 경우는?

**모범 답안:**  
재사용 가능한 의미 모델, 계산/집계/CASE 로직, Fiori/OData/RAP 노출, Association 기반 모델링, 권한 모델과의 결합이 필요한 경우 CDS View Entity를 우선 검토하는 것이 적절하다.

## 22. 핵심 요약

이번 모듈의 핵심은 다음이다.

```text
Projection View는 Classic DDIC View 유형 중 하나이다.
Projection View는 하나의 테이블에서 필요한 필드만 제한적으로 노출한다.
Projection View의 핵심은 JOIN이 아니라 Field Restriction이다.
여러 테이블 결합이 필요하면 Database View, Open SQL JOIN, CDS View Entity를 검토한다.
단순 프로그램 조회라면 Open SQL Field List로 충분할 수 있다.
현대 S/4HANA 신규 개발에서는 CDS View Entity와의 비교가 필요하다.
Projection View는 보안 설계 전체를 대체하지 않는다.
Classic DDIC Projection View와 RAP/CDS Projection View는 서로 다른 맥락이다.
```
