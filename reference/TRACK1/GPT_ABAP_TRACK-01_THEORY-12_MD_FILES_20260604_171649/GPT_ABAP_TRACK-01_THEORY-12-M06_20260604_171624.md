## 2. Classic DDIC View 전체 복습

THEORY-12에서 학습한 Classic DDIC View 계열은 다음과 같이 정리할 수 있다.

| 객체 | 대표 목적 | 초급자 이해 방식 |
|---|---|---|
| Database View | 여러 테이블을 JOIN하여 하나의 조회 구조 제공 | 저장된 JOIN 정의 |
| Projection View | 하나의 테이블에서 필요한 필드만 제한 | 필드 축소 View |
| Help View | Search Help의 Selection Method로 사용 | F4 Help용 조회 구조 |
| Maintenance View | 관계 있는 테이블을 함께 유지보수 | SM30 유지보수용 View |

이 객체들은 모두 SE11 중심의 DDIC 객체이다. 즉, SAP GUI에서 정의하고 Repository에 저장하며, ABAP 프로그램이나 화면, Search Help, SM30 같은 Classic 도구와 연결된다.

## 3. Classic View가 해결한 문제

Classic View는 단순히 “옛날 방식”으로만 이해하면 안 된다. Classic View는 오랫동안 SAP 시스템에서 데이터 조회와 유지보수를 구조화하는 중요한 도구였다.

### 3.1 반복 JOIN 정의 감소

여러 프로그램에서 같은 JOIN을 반복해서 작성하면 다음 문제가 생긴다.

```abap
SELECT a~carrid,
       a~carrname,
       b~connid,
       b~cityfrom,
       b~cityto
  FROM scarr AS a
  INNER JOIN spfli AS b
    ON a~carrid = b~carrid
  INTO TABLE @DATA(lt_result).
```

이 JOIN이 여러 프로그램에서 반복된다면 유지보수 부담이 생긴다. Classic Database View는 이 JOIN 구조를 SE11의 DDIC 객체로 저장해 재사용할 수 있게 해준다.

```text
JOIN 로직을 프로그램마다 작성하지 않고,
DDIC View 객체로 중앙 정의한다.
```

### 3.2 F4 Help와 연결

Help View는 Search Help의 Selection Method로 사용될 수 있다. 즉, 사용자가 입력 필드에서 F4를 눌렀을 때 보여줄 후보 데이터를 구조화하는 데 활용된다.

이 흐름은 Classic ABAP 화면, PARAMETERS, Dynpro, Search Help 중심 개발에서 매우 중요하다.

### 3.3 SM30 유지보수와 연결

Maintenance View와 Table Maintenance Generator는 SM30 기반 유지보수 화면을 제공한다. 단순 설정성 데이터나 관계 있는 Customizing성 데이터는 별도 프로그램 없이도 유지보수 화면을 만들 수 있다.

이처럼 Classic View는 조회, 입력 도움말, 유지보수 화면을 DDIC 중심으로 재사용하게 해주는 역할을 했다.

## 4. Classic View의 한계

Classic View는 유용하지만, 현대 S/4HANA 개발 관점에서는 한계도 명확하다.

### 4.1 표현력의 한계

Classic DDIC View는 기본적인 필드 선택과 JOIN에는 적합하지만, 복잡한 의미 모델링에는 한계가 있다.

예를 들어 다음과 같은 요구가 있다고 하자.

```text
필드에 업무 의미를 Annotation으로 부여하고 싶다.
Fiori Elements 화면의 라벨, 검색, 필터, Value Help를 모델에 함께 선언하고 싶다.
Association 기반으로 관련 데이터를 탐색하고 싶다.
RAP Business Object의 Projection 계층과 연결하고 싶다.
```

Classic View만으로는 이러한 현대적 요구를 충분히 표현하기 어렵다.

### 4.2 개발 환경의 한계

Classic View는 주로 SAP GUI의 SE11에서 정의된다. 반면 현대 ABAP 개발은 Eclipse ADT, Git 기반 개발 흐름, 코드 리뷰, ATC, ABAP Cloud, RAP 등과 연결된다.

Classic View는 GUI 기반 설정 객체에 가까우므로, 코드 기반 모델링과 DevOps 친화적 흐름에서는 CDS보다 불리하다.

### 4.3 UI와 서비스 노출 관점의 한계

S/4HANA에서는 데이터 모델이 단순 DB 조회를 넘어 Fiori, OData, Analytics, RAP와 연결된다.

Classic View는 이런 계층과 직접적으로 풍부하게 연결되기 어렵다. 반면 CDS는 Annotation과 Association을 통해 UI, 검색, 권한, OData, RAP 등으로 확장되기 쉽다.

### 4.4 의미 모델링 부족

Classic View는 주로 “어떤 테이블을 어떤 조건으로 JOIN할 것인가”에 초점이 있다. CDS는 여기에 더해 “이 데이터가 업무적으로 무엇을 의미하는가”를 모델 안에 표현할 수 있다.

예를 들어 CDS에서는 다음과 같은 관점을 모델에 담을 수 있다.

```text
이 필드는 화면에서 어떤 라벨로 보일 것인가?
이 필드는 검색 가능한가?
이 값은 어떤 Value Help와 연결되는가?
이 데이터는 어떤 Association으로 다른 모델과 연결되는가?
이 View는 Interface View인가, Consumption View인가?
```

이런 점이 Classic View와 CDS의 가장 큰 차이 중 하나이다.

## 5. CDS View Entity란 무엇인가?

CDS View Entity는 ABAP CDS에서 사용하는 현대적인 View 정의 방식이다.

초급자는 CDS View Entity를 다음처럼 이해하면 된다.

```text
CDS View Entity = SQL View 이상의 의미를 가진, 코드 기반 ABAP 데이터 모델링 객체
```

CDS는 단순한 SELECT 문 저장소가 아니다. CDS는 데이터 모델에 업무 의미, 관계, 노출 의도, UI 힌트, 권한, 확장 가능성을 함께 담을 수 있는 모델링 언어이다.

### 5.1 CDS View Entity의 간단한 예시

아래 코드는 개념 이해를 위한 최소 예시이다.

```abap
@EndUserText.label: 'Carrier Basic View'
define view entity ZI_JHY_Carrier
  as select from scarr
{
  key carrid   as CarrierId,
      carrname as CarrierName,
      currcode as CurrencyCode
}
```

이 예제에서 중요한 점은 다음이다.

| 요소 | 의미 |
|---|---|
| `@EndUserText.label` | View의 설명을 Annotation으로 부여 |
| `define view entity` | CDS View Entity 정의 |
| `as select from scarr` | 데이터 소스 지정 |
| `key carrid` | Key 필드 지정 |
| Alias | 필드명을 의미 있게 재정의 |

이 문법은 이후 CDS Section에서 본격적으로 다룬다.

## 6. Classic View와 CDS View Entity 비교

### 6.1 기본 비교표

| 관점 | Classic DDIC View | CDS View Entity |
|---|---|---|
| 주요 도구 | SE11, SAP GUI | ADT, DDL Source |
| 정의 방식 | 화면 기반 설정 | 코드 기반 정의 |
| 핵심 목적 | 조회 구조, F4, 유지보수 보조 | 의미 기반 데이터 모델링 |
| JOIN 표현 | 제한적·전통적 JOIN 중심 | SELECT, Association, Path Expression 등으로 확장 |
| Annotation | 제한적 | 풍부하게 지원 |
| Fiori/RAP 연결 | 직접 연결 제한적 | 핵심 기반 객체 |
| 현대 개발 적합성 | 낮음~중간 | 높음 |
| 교육상 위치 | CDS 전 비교 기준 | S/4HANA 핵심 모델링 기술 |

### 6.2 개발 방식의 차이

Classic View는 화면에서 필드를 선택하고 JOIN 조건을 설정하는 방식이다. CDS View Entity는 코드로 모델을 선언한다.

Classic View의 사고 방식:

```text
SE11에서 테이블 선택
→ 필드 선택
→ JOIN 조건 설정
→ View 활성화
→ 프로그램이나 Search Help에서 사용
```

CDS의 사고 방식:

```text
DDL Source 생성
→ 데이터 소스 선언
→ 필드와 Key 정의
→ Association과 Annotation 설계
→ Activation
→ Preview, OData, RAP, Fiori로 확장
```

### 6.3 재사용 방식의 차이

Classic View도 재사용이 가능하지만, CDS는 계층형 재사용에 더 적합하다.

대표적인 CDS 계층 구조는 다음과 같이 설명할 수 있다.

```text
Interface View
  → Projection View
  → Consumption View
  → Service / UI / RAP
```

단, 이 모듈에서는 CDS 계층을 깊게 다루지 않는다. 중요한 것은 CDS가 단일 View 하나를 만드는 기술이 아니라, S/4HANA 데이터 모델을 계층적으로 구성하는 기반이라는 점이다.

## 7. 왜 지금 Classic View를 배웠는가?

초급자는 “어차피 CDS가 중요하다면 Classic View를 왜 배우는가?”라고 질문할 수 있다.

답은 세 가지이다.

### 7.1 기존 시스템 이해

많은 SAP 시스템에는 여전히 Classic DDIC View, Search Help, Maintenance View, SM30 유지보수 객체가 존재한다. 실무자는 신규 개발만 하는 것이 아니라 기존 객체를 분석하고 유지보수해야 한다.

따라서 Classic View를 모르면 다음 작업에서 어려움을 겪는다.

```text
기존 Search Help 분석
SM30 유지보수 화면 오류 분석
SE11 View 기반 프로그램 이해
표준 DDIC 객체 구조 파악
기존 Z View의 CDS 전환 검토
```

### 7.2 CDS를 이해하기 위한 비교 기준

CDS를 처음 배우면 Annotation, Association, Projection, Consumption 같은 용어가 갑자기 많아진다. Classic View를 먼저 이해하면 CDS가 왜 필요한지 비교하기 쉽다.

```text
Classic View: 조회 구조 중심
CDS: 의미 모델링 중심
```

이 차이를 알고 CDS를 배우면 문법 암기보다 아키텍처 이해가 쉬워진다.

### 7.3 점진적 Modernization 판단

실무에서는 모든 Classic View를 무조건 CDS로 바꾸지 않는다. 기존 객체의 사용 범위, 변경 리스크, UI/서비스 노출 필요성, 성능, 유지보수 비용을 함께 고려한다.

따라서 초급자도 다음 질문에 익숙해져야 한다.

```text
이 Classic View는 그대로 유지해도 되는가?
신규 개발은 CDS로 설계해야 하는가?
Fiori/RAP 노출이 필요한가?
단순 SM30 유지보수 객체인가?
기존 프로그램 의존성이 큰가?
```

## 8. Modernization 관점

Modernization은 단순히 “옛 기술을 새 기술로 바꾸는 것”이 아니다. SAP 개발에서 Modernization은 보통 다음 방향을 포함한다.

| 방향 | 의미 |
|---|---|
| SAP GUI 중심 → ADT 중심 | 코드 기반 개발과 품질 도구 활용 |
| DDIC View 중심 → CDS 중심 | 의미 기반 데이터 모델링 확장 |
| Report 중심 → Service/RAP 중심 | API와 UI 노출을 고려한 설계 |
| 수동 화면 개발 → Fiori Elements | Annotation 기반 UI 생성 |
| 절차적 구현 중심 → 계층형 모델링 | Interface/Projection/Consumption 계층 분리 |

### 8.1 신규 개발 기준

S/4HANA 신규 개발에서는 다음 원칙을 검토하는 것이 좋다.

```text
단순 DB 조회라도 CDS 모델링 가능성을 먼저 검토한다.
Fiori, OData, RAP로 확장될 수 있으면 CDS 기반을 우선 고려한다.
기존 Classic View를 그대로 복사해 신규 개발하지 않는다.
표준 객체 변경보다 Extension과 Clean Core 관점을 우선한다.
```

### 8.2 기존 객체 기준

기존 Classic View가 이미 운영 중이라면 바로 변경하지 않는다.

다음 순서로 분석한다.

```text
1. Where-Used List 확인
2. 사용 프로그램/화면/Search Help/SM30 확인
3. 데이터 소스와 JOIN 조건 확인
4. 성능 이슈 여부 확인
5. 신규 요구사항이 CDS/RAP/Fiori와 연결되는지 확인
6. 전환 여부 결정
```

## 9. Classic View를 CDS로 전환할 때의 사고 절차

이 모듈에서는 실제 전환 작업을 수행하지 않는다. 다만 후속 CDS 학습을 위한 분석 절차를 미리 익힌다.

### 9.1 분석 단계

```text
Classic View 이름 확인
→ Base Table 확인
→ Join Condition 확인
→ Key Field 확인
→ 필드 Alias와 의미 확인
→ 사용처 확인
→ 전환 필요성 판단
```

### 9.2 설계 단계

CDS로 전환할 때는 단순히 SELECT 문을 복사하지 않는다.

검토할 항목은 다음과 같다.

| 항목 | 질문 |
|---|---|
| View 목적 | Interface View인가 Consumption View인가? |
| 필드명 | 기술명 그대로 둘 것인가, 의미 있는 Alias를 줄 것인가? |
| Key | CDS Key는 무엇인가? |
| Association | 관련 데이터는 Association으로 표현할 것인가? |
| Annotation | 라벨, 검색, Value Help, UI 힌트가 필요한가? |
| 권한 | Access Control이 필요한가? |
| 소비처 | ABAP SQL, OData, Fiori, RAP 중 어디서 사용할 것인가? |

### 9.3 검증 단계

```text
CDS Activation
→ Data Preview
→ 기존 Classic View 결과와 데이터 건수 비교
→ 주요 Key 기준 샘플 비교
→ 성능 확인
→ 소비 프로그램 또는 UI 영향 확인
```

이 절차는 후속 CDS/RAP Section에서 실제 코드와 함께 확장한다.

## 10. 초급자가 지금 외워야 할 최소 개념

이 단계에서 CDS를 깊게 외울 필요는 없다. 다음 네 가지 차이만 명확히 기억하면 충분하다.

### 10.1 Classic View는 DDIC 객체이다

```text
SE11에서 만들고, SAP GUI 기반 도구와 강하게 연결된다.
```

### 10.2 CDS View Entity는 코드 기반 데이터 모델이다

```text
ADT에서 DDL Source로 정의하고, Annotation과 Association으로 의미를 확장한다.
```

### 10.3 CDS는 UI와 서비스로 확장되기 쉽다

```text
Fiori Elements, OData, RAP와 연결되는 현대 ABAP 데이터 모델링의 중심이다.
```

### 10.4 Classic View 지식은 여전히 필요하다

```text
기존 시스템 분석, Search Help, SM30, 유지보수 객체 이해에 필요하다.
```

## 11. 미니 실습: 비교 관점 정리

### 11.1 실습 목표

기존 Classic Database View 하나를 선택하고, CDS View Entity로 전환할 때 검토해야 할 항목을 표로 정리한다.

실제 CDS 생성은 하지 않아도 된다.

### 11.2 실습 대상 예시

[추정] 교육 시스템에 항공 모델 테이블이 있다면 다음 조합을 사용할 수 있다.

```text
SCARR + SPFLI
```

만약 해당 테이블이 없다면 시스템에 존재하는 교육용 Z 테이블 또는 표준 조회용 테이블을 사용한다.

### 11.3 작성 양식

| 검토 항목 | Classic View 기준 | CDS 전환 시 고려 |
|---|---|---|
| View 목적 | Carrier와 Connection 조회 | Interface View로 정의 가능 |
| Base Table | SCARR, SPFLI | select from + association 검토 |
| Join 조건 | CARRID 기준 Inner Join | Association 또는 Join 선택 |
| Key | CARRID, CONNID | CDS key 재검토 |
| 필드명 | 기술명 중심 | Alias와 의미 명확화 |
| 라벨 | 제한적 | `@EndUserText.label` 등 Annotation 검토 |
| 소비처 | ABAP Report, Search Help | ABAP SQL, Fiori, RAP 가능성 검토 |

### 11.4 실습 결과 예시

```text
분석 결과:
기존 Classic View는 단순 조회에는 충분하다.
그러나 Fiori 화면이나 RAP 서비스로 확장할 계획이 있다면 CDS View Entity로 재설계하는 것이 적절하다.
단순히 기존 View를 1:1로 옮기는 것보다 Interface View와 Projection View 계층을 고려해야 한다.
```

## 12. 오류 상황과 주의점

### 12.1 CDS를 “새로운 Database View”로만 이해하는 오류

CDS는 단순히 Classic Database View의 새 버전이 아니다. 물론 조회 구조를 정의한다는 점은 비슷하지만, CDS의 핵심은 의미 모델링과 소비 계층 연결이다.

잘못된 이해:

```text
CDS = SE11 Database View를 코드로 쓰는 것
```

더 적절한 이해:

```text
CDS = 데이터 소스, 필드, 관계, 의미, 소비 의도를 함께 표현하는 현대 ABAP 모델링 방식
```

### 12.2 모든 Classic View를 즉시 CDS로 바꾸려는 오류

운영 중인 객체를 무조건 전환하면 리스크가 크다.

확인해야 할 항목은 다음이다.

```text
Where-Used List
프로그램 의존성
Search Help 연결 여부
SM30 유지보수 연결 여부
권한과 데이터 검증 흐름
운영 테스트 범위
```

### 12.3 CDS 학습 전 Classic View를 무시하는 오류

Classic View를 모르면 기존 SAP 시스템을 읽기 어렵다. 특히 Search Help, SM30, Maintenance View는 여전히 실무 분석에서 만날 수 있다.

### 12.4 CDS에서 모든 것을 한 View에 몰아넣는 오류

CDS는 계층형 설계가 중요하다. 초급 단계에서는 아직 깊게 배우지 않지만, 하나의 거대한 CDS에 모든 JOIN, 계산, UI Annotation, 소비 로직을 몰아넣는 방식은 피해야 한다.

후속 RAP/CDS 학습에서는 Interface View, Projection View, Consumption View 분리를 다룬다.

## 13. 실무 판단 기준

Classic View와 CDS View Entity 중 무엇을 사용할지 판단할 때는 다음 기준을 참고한다.

| 상황 | 권장 판단 |
|---|---|
| 기존 Search Help가 Help View를 사용 중 | 기존 구조를 이해하고 영향 분석 후 유지 또는 개선 |
| SM30 유지보수 객체가 필요 | Maintenance View/TMG 흐름 검토 |
| 신규 조회 모델을 Fiori/RAP로 확장 예정 | CDS View Entity 우선 검토 |
| 단순 기존 Report 유지보수 | 기존 Classic View 유지 가능 |
| 신규 S/4HANA 표준 확장 지향 | CDS/Extension 기반 우선 검토 |
| 교육용 Classic 개념 학습 | SE11 View로 비교 기준 확보 |

## 14. 강사용 설명 포인트

강의에서는 다음 메시지를 명확히 전달하면 좋다.

### 14.1 Classic View는 폐기 지식이 아니다

Classic View는 신규 개발의 중심은 아니더라도 기존 시스템을 읽는 데 필요하다. 실무자는 항상 신규 개발과 기존 유지보수를 동시에 고려해야 한다.

### 14.2 CDS는 문법보다 설계 관점이 중요하다

CDS를 단순 SELECT 문법으로 가르치면 학습자가 Annotation, Association, RAP 연결의 의미를 놓치기 쉽다. 따라서 Classic View와 비교하면서 “왜 CDS가 의미 모델링 도구인지”를 먼저 설명해야 한다.

### 14.3 Modernization은 무조건 전환이 아니다

Modernization은 기존 기능을 무조건 새 기술로 바꾸는 것이 아니라, 리스크와 목적에 맞게 점진적으로 전환하는 판단이다.

## 15. 평가 문제

### 15.1 객관식

#### Q1. Classic DDIC View와 CDS View Entity의 차이로 가장 적절한 것은?

A. Classic View는 코드 기반이고 CDS는 SAP GUI 화면 기반이다.  
B. Classic View는 SE11 중심이고 CDS View Entity는 ADT의 DDL Source 중심이다.  
C. Classic View는 Fiori/RAP의 핵심 기반이고 CDS는 SM30 전용이다.  
D. 두 객체는 이름만 다르고 완전히 동일하다.

**정답:** B

#### Q2. CDS View Entity를 배우는 이유로 가장 적절한 것은?

A. 모든 ABAP 프로그램에서 WRITE를 대체하기 위해서이다.  
B. SAP GUI 화면을 자동으로 비활성화하기 위해서이다.  
C. 의미 기반 데이터 모델링, Fiori, OData, RAP 확장 기반을 이해하기 위해서이다.  
D. SM30 유지보수 화면만 만들기 위해서이다.

**정답:** C

#### Q3. 기존 Classic View를 CDS로 전환하기 전에 가장 먼저 확인해야 할 항목으로 적절한 것은?

A. View 이름을 길게 바꿀지 여부  
B. Where-Used List와 사용처  
C. WRITE 문 개수  
D. 사용자 GUI 테마

**정답:** B

### 15.2 서술형

#### Q1. Classic View를 CDS 학습 전에 배우는 이유를 설명하시오.

**모범 답안:**  
Classic View는 기존 SAP 시스템에 많이 존재하며 Search Help, SM30, Report 조회 등과 연결되어 있다. 또한 CDS가 왜 필요한지 이해하기 위한 비교 기준이 된다. Classic View의 목적과 한계를 알아야 CDS의 의미 모델링, Annotation, Association, RAP/Fiori 연결 필요성을 더 명확히 이해할 수 있다.

#### Q2. CDS View Entity가 Classic View보다 현대 ABAP 개발에 더 적합한 이유를 설명하시오.

**모범 답안:**  
CDS View Entity는 ADT에서 코드 기반으로 정의되며 Annotation, Association, 의미 기반 필드 정의, UI/OData/RAP 확장과 연결될 수 있다. Classic View는 전통적인 DDIC 조회 구조에 강점이 있지만 현대 S/4HANA의 서비스 중심 개발과 UI 자동화, 계층형 데이터 모델링 요구에는 한계가 있다.

#### Q3. 모든 Classic View를 즉시 CDS로 전환하면 안 되는 이유를 설명하시오.

**모범 답안:**  
운영 중인 Classic View는 기존 프로그램, Search Help, SM30 유지보수 객체, 권한, 테스트 범위와 연결되어 있을 수 있다. 사용처와 변경 리스크를 확인하지 않고 전환하면 기존 기능에 장애를 일으킬 수 있으므로 Where-Used List와 소비처를 먼저 분석해야 한다.
