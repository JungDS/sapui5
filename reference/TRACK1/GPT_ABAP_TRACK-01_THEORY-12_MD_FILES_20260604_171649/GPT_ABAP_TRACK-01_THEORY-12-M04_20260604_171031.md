## 3. Maintenance View란 무엇인가?

Maintenance View는 ABAP Dictionary에서 제공하는 Classic View 유형 중 하나로, 서로 관련된 여러 테이블의 데이터를 하나의 유지보수 관점에서 다루기 위해 사용한다.

초급자 관점에서는 다음처럼 이해하면 된다.

```text
Database View = 조회 중심의 테이블 조합
Help View     = F4 Help를 위한 조회 기반
Maintenance View = 관련 테이블 데이터를 유지보수하기 위한 View
```

Maintenance View는 단순 조회용 View가 아니다. 이름 그대로 “유지보수”를 전제로 한다. 즉, Table Maintenance Generator와 연결되어 `SM30`에서 데이터를 입력, 변경, 삭제하는 유지보수 화면을 제공할 때 중요한 역할을 한다.

---

## 4. 왜 Maintenance View가 필요한가?

### 4.1 단일 테이블 유지보수의 한계

하나의 설정 테이블만 관리한다면 단순 Table Maintenance Generator로 충분할 수 있다. 예를 들어 상태 코드 테이블 하나만 관리하는 경우다.

```text
ZT_JHY_STATUS
- MANDT
- STATUS
- STATUS_TEXT
```

하지만 실제 업무 설정은 한 테이블만으로 끝나지 않는 경우가 많다.

예를 들어 다음과 같은 설정 구조를 생각해보자.

```text
ZT_JHY_CARR_CFG      항공사 설정 Header
ZT_JHY_CARR_RULE     항공사별 처리 규칙 Detail
```

Header와 Detail이 Foreign Key로 연결되어 있다면 사용자는 항공사 설정을 관리하면서 관련 규칙도 함께 확인하고 싶을 수 있다. 이런 경우 Maintenance View 또는 View Cluster 같은 유지보수 객체 설계가 필요해진다.

### 4.2 업무 설정 유지보수의 관점

실무에서 Maintenance View는 주로 다음 성격의 데이터에 사용된다.

| 데이터 성격 | 예시 | 적합성 |
|---|---|---|
| Customizing성 설정 데이터 | 코드, 매핑, 제어값 | 적합 |
| 관련 테이블을 함께 유지보수해야 하는 데이터 | Header/Detail 설정 | 검토 가능 |
| 대량 트랜잭션 데이터 | 판매오더, 전표, 로그 | 일반적으로 부적합 |
| 표준 트랜잭션으로 관리해야 하는 업무 데이터 | 고객, 자재, 회계전표 | 직접 유지보수 부적합 |

Maintenance View는 사용자가 직접 유지보수할 수 있는 화면으로 이어질 수 있기 때문에, 데이터 성격을 신중하게 판단해야 한다.

## 5. Maintenance View와 Database View의 차이

Maintenance View와 Database View는 둘 다 여러 테이블을 조합할 수 있기 때문에 초급자가 혼동하기 쉽다. 하지만 목적이 다르다.

| 구분 | Database View | Maintenance View |
|---|---|---|
| 주 목적 | 조회용 View | 유지보수용 View |
| 주요 사용 | Open SQL 조회, 조회 객체 | SM30 유지보수 화면 연결 |
| 테이블 관계 | JOIN 조건 중심 | Foreign Key 관계 중심 |
| 데이터 변경 | 조회 중심 | 유지보수 가능성 고려 |
| 설계 질문 | 어떤 데이터를 읽을 것인가? | 어떤 데이터를 사용자가 유지보수할 것인가? |
| 후속 객체 | Report, 조회 프로그램 | TMG, SM30, View Cluster |

핵심 차이는 다음이다.

```text
Database View는 조회 모델이다.
Maintenance View는 유지보수 모델이다.
```

조회만 필요하면 Database View 또는 Open SQL JOIN이 적합하다. 사용자가 관련 데이터를 관리해야 한다면 Maintenance View와 Table Maintenance Generator를 검토한다.

## 6. Foreign Key 관계가 중요한 이유

Maintenance View는 임의로 테이블을 마구 붙이는 도구가 아니다. 테이블 사이의 의미 있는 관계가 전제되어야 한다. 이 관계를 DDIC에서 표현하는 대표 방법이 Foreign Key이다.

### 6.1 Foreign Key의 기본 의미

Foreign Key는 한 테이블의 필드가 다른 테이블의 Key 값을 참조한다는 관계를 표현한다.

예를 들어 다음과 같은 테이블을 생각해보자.

```text
Check Table: ZT_JHY_CARR
- MANDT
- CARRID
- CARRNAME

Foreign Key Table: ZT_JHY_CONN
- MANDT
- CARRID
- CONNID
- CITYFROM
- CITYTO
```

`ZT_JHY_CONN-CARRID`는 `ZT_JHY_CARR-CARRID`를 참조한다. 즉, 연결 정보는 존재하는 항공사에 대해서만 만들어져야 한다.

```text
ZT_JHY_CARR 1건
  └─ ZT_JHY_CONN 여러 건
```

이 관계가 DDIC Foreign Key로 명확히 정의되어 있으면 Maintenance View는 테이블 관계를 더 명확하게 이해할 수 있다.

### 6.2 Maintenance View에서 Foreign Key가 하는 역할

Maintenance View에서 Foreign Key는 다음 역할을 한다.

| 역할 | 설명 |
|---|---|
| 테이블 관계 명시 | 어떤 테이블이 어떤 필드로 연결되는지 알려준다. |
| 유지보수 구조 안정화 | Header/Detail 또는 Check/Dependent 관계를 명확히 한다. |
| 데이터 정합성 기반 | 존재하지 않는 상위 데이터에 종속 데이터를 만들지 않도록 돕는다. |
| TMG/SM30 연결 준비 | 유지보수 화면 생성 시 관계 정보의 기반이 된다. |

Foreign Key가 없으면 시스템은 두 테이블이 업무적으로 어떤 관계인지 명확히 판단하기 어렵다.

## 7. Primary Table과 Secondary Table

Maintenance View에서는 여러 테이블 중 중심이 되는 테이블과 종속되는 테이블을 구분한다.

### 7.1 Primary Table

Primary Table은 Maintenance View의 중심 테이블이다.

예를 들어 항공사와 연결 정보를 관리한다면 다음 중 무엇을 중심으로 할지 결정해야 한다.

```text
항공사 기준으로 연결 정보를 관리할 것인가?
연결 정보 기준으로 항공사명을 함께 보여줄 것인가?
```

항공사 설정이 중심이라면 `ZT_JHY_CARR`가 Primary Table이 될 수 있다.

### 7.2 Secondary Table

Secondary Table은 Primary Table과 Foreign Key 관계로 연결되는 종속 또는 참조 테이블이다.

예:

```text
Primary Table   : ZT_JHY_CARR
Secondary Table : ZT_JHY_CONN
관계            : ZT_JHY_CONN-CARRID → ZT_JHY_CARR-CARRID
```

### 7.3 설계 판단

Primary Table을 잘못 선택하면 유지보수 화면의 의미가 흔들린다.

| 질문 | 판단 |
|---|---|
| 사용자가 주로 무엇을 기준으로 데이터를 관리하는가? | Primary Table 후보 |
| 어떤 데이터가 종속 정보인가? | Secondary Table 후보 |
| 관계가 1:N인가, 1:1인가? | 유지보수 화면 구조 검토 |
| 변경 주체가 같은가? | 같은 Maintenance View에 묶을지 판단 |

## 8. Cardinality와 유지보수 설계

Foreign Key에서는 관계의 Cardinality를 표현할 수 있다. 초급 단계에서는 Cardinality를 다음처럼 이해하면 된다.

```text
한쪽 데이터 1건에 대해 다른 쪽 데이터가 몇 건 연결될 수 있는가?
```

예시:

| 관계 | 의미 | 예시 |
|---|---|---|
| 1:1 | 한 건이 한 건과 연결 | 회사코드와 단일 확장 설정 |
| 1:N | 한 건이 여러 건과 연결 | 항공사 1개와 연결편 여러 개 |
| N:1 | 여러 건이 한 건을 참조 | 연결편 여러 개가 항공사 1개 참조 |

Maintenance View 설계에서는 1:N 관계를 다룰 때 특히 주의해야 한다. View 한 줄이 어떤 테이블의 어떤 한 건을 의미하는지 불명확하면 유지보수 화면에서 사용자가 혼란을 겪을 수 있다.

## 10. SE11에서 Foreign Key 확인

Maintenance View를 만들기 전에 Foreign Key 관계를 먼저 확인해야 한다.

### 10.1 확인 절차

```text
1. SE11 실행
2. Database Table 선택
3. ZT_JHY_CARR_RULE 입력
4. Display 또는 Change
5. Fields 탭 이동
6. CARRID 필드 선택
7. Foreign Key 버튼 선택
8. Check Table이 ZT_JHY_CARR인지 확인
9. MANDT, CARRID 필드 매핑 확인
```

### 10.2 확인할 항목

| 확인 항목 | 설명 |
|---|---|
| Check Table | 참조 대상 테이블이 올바른가 |
| Field Assignment | MANDT와 CARRID가 올바르게 매핑되었는가 |
| Cardinality | 관계 의미에 맞는가 |
| Key 관계 | 참조 대상이 적절한 Key 구조를 가지는가 |
| Activation | 양쪽 테이블과 Foreign Key가 활성화되어 있는가 |

Foreign Key 관계가 올바르지 않으면 Maintenance View 생성 단계에서 관계 선택이 어렵거나 유지보수 화면의 의미가 불명확해질 수 있다.

## 11. Maintenance View 생성 절차

### 11.1 SE11에서 View 생성

```text
1. SE11 실행
2. View 선택
3. View 이름 입력: ZV_JHY_CARR_MAINT
4. Create 선택
5. View Type에서 Maintenance View 선택
```

### 11.2 Short Description 입력

```text
Carrier Rule Maintenance View
```

설명은 유지보수 목적이 드러나도록 작성한다.

나쁜 예:

```text
Test View
View1
Carrier
```

좋은 예:

```text
Carrier Rule Maintenance View
Maintenance View for Carrier Rule Customizing
```

### 11.3 Tables 탭 구성

테이블을 추가한다.

```text
Primary Table   : ZT_JHY_CARR
Secondary Table : ZT_JHY_CARR_RULE
```

테이블을 추가할 때 시스템은 Foreign Key 관계를 기반으로 연결 가능한 관계를 확인한다. 관계가 명확히 정의되어 있으면 연결 조건을 안정적으로 구성할 수 있다.

### 11.4 Join Conditions 확인

Maintenance View에서는 임의 SQL처럼 자유롭게 복잡한 Join을 작성하는 것이 아니라, DDIC 관계를 기반으로 연결을 확인한다.

확인 예:

```text
ZT_JHY_CARR-MANDT  = ZT_JHY_CARR_RULE-MANDT
ZT_JHY_CARR-CARRID = ZT_JHY_CARR_RULE-CARRID
```

### 11.5 View Fields 선택

유지보수에 필요한 필드를 선택한다.

| Source Table | Field | 포함 여부 | 설명 |
|---|---|---:|---|
| ZT_JHY_CARR | CARRID | X | 항공사 코드 |
| ZT_JHY_CARR | CARRNAME | X | 항공사명 |
| ZT_JHY_CARR | ACTIVE | X | 항공사 사용 여부 |
| ZT_JHY_CARR_RULE | RULE_ID | X | 규칙 ID |
| ZT_JHY_CARR_RULE | RULE_TEXT | X | 규칙 설명 |
| ZT_JHY_CARR_RULE | ACTIVE | X | 규칙 사용 여부 |

`MANDT`는 시스템과 View 설정에 따라 별도 표시 여부가 달라질 수 있다. 초급 단계에서는 Client-dependent 테이블 관계에 `MANDT`가 포함된다는 점을 이해하면 충분하다.

### 11.6 Selection Conditions

필요한 경우 View 수준에서 조건을 줄 수 있다. 예를 들어 활성 데이터만 보여주려는 요구가 있을 수 있다.

```text
ACTIVE = 'X'
```

다만 Maintenance View에서 너무 강한 조건을 걸면 사용자가 비활성 데이터를 관리하지 못하는 문제가 생길 수 있다. 조회용 View와 유지보수용 View의 목적이 다르므로 조건은 신중히 사용한다.

### 11.7 저장 및 활성화

```text
Save
→ Package 또는 $TMP 선택
→ Activate
```

교육용 실습에서는 `$TMP` Local Object를 사용할 수 있다. 실무에서는 패키지, Transport Request, 권한 정책을 따른다.

## 12. Maintenance View의 결과를 어떻게 확인하는가?

Maintenance View 자체는 DDIC View 객체이다. 생성 후에는 다음을 확인한다.

| 확인 항목 | 방법 |
|---|---|
| View 활성화 상태 | SE11에서 View Display 후 상태 확인 |
| 테이블 관계 | Tables / Join Conditions 탭 확인 |
| View Fields | 필요한 필드가 포함되었는지 확인 |
| Data Browser 가능 여부 | View 내용 조회 가능 여부 확인 |
| 유지보수 연결 가능성 | 다음 모듈에서 TMG/SM30 생성 여부 확인 |

다만 Maintenance View의 진짜 목적은 단순 조회보다 유지보수 화면으로 연결되는 데 있다. 따라서 이번 모듈에서는 View 생성과 관계 검증까지를 목표로 하고, 실제 `SM30` 유지보수는 다음 모듈에서 진행한다.

## 13. 정상 흐름과 오류 흐름

### 13.1 정상 흐름

```text
1. Primary Table과 Secondary Table 설계
2. Foreign Key 관계 생성 및 활성화
3. SE11에서 Maintenance View 생성
4. Maintenance View에 테이블 추가
5. Foreign Key 기반 관계 확인
6. View Fields 선택
7. Save
8. Activate
9. 관계와 필드 구성 검증
10. 다음 단계에서 TMG / SM30 연결
```

### 13.2 오류 흐름 1: Foreign Key 관계가 없음

#### 증상

Maintenance View에서 테이블을 연결하려고 할 때 관계가 명확히 잡히지 않거나, 원하는 연결이 되지 않는다.

#### 원인

테이블 사이에 DDIC Foreign Key가 정의되어 있지 않다.

#### 해결

```text
1. Secondary Table에서 Foreign Key 정의 여부 확인
2. Check Table 지정 확인
3. Field Assignment 확인
4. 양쪽 테이블 Activate
5. Maintenance View에서 다시 관계 확인
```

### 13.3 오류 흐름 2: Foreign Key 필드 매핑 오류

#### 증상

View는 생성되지만 결과가 이상하거나 유지보수 대상이 잘못 연결된다.

#### 원인

`MANDT` 또는 업무 Key 필드 매핑이 잘못되었다.

#### 해결

Foreign Key의 Field Assignment를 점검한다.

```text
MANDT  ↔ MANDT
CARRID ↔ CARRID
```

Client-dependent 테이블에서 `MANDT` 관계를 누락하면 Client 혼선이 발생할 수 있다.

### 13.4 오류 흐름 3: Primary Table 선택 오류

#### 증상

View의 중심이 되는 데이터가 사용자의 유지보수 관점과 맞지 않는다.

#### 원인

Primary Table을 업무 기준이 아닌 기술 기준으로 선택했다.

#### 해결

다음 질문으로 다시 판단한다.

```text
사용자는 무엇을 기준으로 데이터를 관리하는가?
상위 데이터는 무엇인가?
하위 데이터는 무엇인가?
사용자가 먼저 선택해야 하는 기준 값은 무엇인가?
```

### 13.5 오류 흐름 4: 너무 많은 필드를 View에 포함

#### 증상

유지보수 화면이 복잡해지고 사용자가 어떤 필드를 변경해야 하는지 알기 어렵다.

#### 원인

조회용으로 필요한 필드와 유지보수용 필드를 구분하지 않았다.

#### 해결

Maintenance View에는 유지보수에 필요한 최소 필드를 포함한다.

```text
조회 편의를 위한 필드 ≠ 유지보수 대상 필드
```

### 13.6 오류 흐름 5: 운영 데이터에 Maintenance View 사용

#### 증상

사용자가 `SM30` 등으로 직접 업무 데이터를 변경하려고 한다.

#### 원인

Maintenance View를 Customizing성 데이터가 아닌 트랜잭션 데이터 유지보수에 잘못 사용했다.

#### 해결

운영 업무 데이터는 표준 트랜잭션, 승인된 프로그램, API, BAPI, RAP Action 등 적절한 업무 프로세스를 통해 변경해야 한다.

## 14. 실무 적용 기준

### 14.1 Maintenance View가 적합한 경우

| 상황 | 설명 |
|---|---|
| 설정성 데이터 유지보수 | 코드, 매핑, 제어값 등 |
| 관련 테이블을 함께 보여줘야 함 | Header/Detail 설정 구조 |
| Foreign Key 관계가 명확함 | Check Table과 Dependent Table 관계가 분명함 |
| 데이터량이 크지 않음 | 관리성 데이터 중심 |
| 표준 트랜잭션이 없는 고객 설정 | Z Customizing 테이블 유지보수 |

### 14.2 Maintenance View가 부적합한 경우

| 상황 | 이유 |
|---|---|
| 대량 트랜잭션 데이터 | 유지보수 화면 성능과 운영 위험 |
| 회계전표, 판매오더 등 핵심 업무 데이터 | 표준 프로세스와 통제 필요 |
| 복잡한 검증 로직이 필요한 데이터 | 단순 유지보수 화면만으로 부족 |
| 권한, 승인, 이력 관리가 중요한 데이터 | 별도 애플리케이션 또는 표준 기능 필요 |
| CDS/RAP 기반 현대적 관리 화면이 필요한 경우 | Classic View보다 RAP/Fiori 검토 |

### 14.3 유지보수 객체 설계 질문

Maintenance View를 만들기 전에 다음 질문에 답해야 한다.

```text
이 데이터는 사용자가 직접 유지보수해도 되는가?
테이블 간 Foreign Key 관계가 명확한가?
Primary Table과 Secondary Table의 역할이 분명한가?
SM30 유지보수로 충분한가?
권한과 변경 이력 요구사항은 충족되는가?
대량 데이터 또는 업무 트랜잭션 데이터는 아닌가?
```

이 질문에 답하지 않고 “화면을 빨리 만들기 위해” Maintenance View를 사용하면 운영 리스크가 커질 수 있다.

## 15. ABAP/SAP 아키텍처 내 위치

Maintenance View는 Classic ABAP Dictionary 기반 유지보수 객체이다.

```text
Transparent Table
  → Foreign Key Relationship
    → Maintenance View
      → Table Maintenance Generator
        → SM30 Maintenance Dialog
```

이 구조는 Classic SAP GUI 중심의 설정 데이터 유지보수에 적합하다. 그러나 최신 S/4HANA 개발에서는 CDS View Entity, Behavior Definition, RAP, Fiori Elements 기반의 유지보수 앱이 함께 검토될 수 있다.

초급 단계에서는 다음 정도로 구분하면 충분하다.

| 방식 | 중심 기술 | 사용 맥락 |
|---|---|---|
| Maintenance View + SM30 | Classic DDIC / SAP GUI | 설정성 데이터 유지보수 |
| CDS View Entity | CDS / SQL View Model | 조회 모델과 의미 모델 |
| RAP BO + Fiori Elements | RAP / OData V4 / Fiori | 현대적 트랜잭션 앱 |

## 19. 평가 문제

### 19.1 객관식

#### Q1. Maintenance View의 가장 적절한 목적은 무엇인가?

A. 단순 ABAP WRITE 출력을 위한 텍스트 객체이다.  
B. 관련 테이블 데이터를 유지보수하기 위한 Classic DDIC View이다.  
C. Fiori Elements 전용 CDS Annotation이다.  
D. ABAP Class의 Method Parameter이다.

정답: B

#### Q2. Maintenance View에서 Foreign Key 관계가 중요한 이유는 무엇인가?

A. 테이블 사이의 유지보수 관계를 명확히 하기 위해서이다.  
B. 모든 필드를 자동으로 Key로 만들기 위해서이다.  
C. WRITE 출력 색상을 결정하기 위해서이다.  
D. Internal Table의 정렬 순서를 고정하기 위해서이다.

정답: A

#### Q3. Maintenance View가 일반적으로 부적합한 경우는?

A. 작은 설정성 코드 테이블 유지보수  
B. Foreign Key 관계가 명확한 Customizing 테이블  
C. 대량 트랜잭션 데이터 직접 변경  
D. SM30 유지보수 화면 준비

정답: C

### 19.2 서술형

#### Q1. Database View와 Maintenance View의 차이를 설명하시오.

모범 답안:  
Database View는 주로 여러 테이블의 데이터를 조회하기 위한 DDIC View이다. Maintenance View는 Foreign Key 관계를 기반으로 관련 테이블 데이터를 유지보수하기 위한 View이며, Table Maintenance Generator와 SM30 유지보수 화면으로 이어질 수 있다.

#### Q2. Maintenance View를 만들기 전에 Foreign Key를 확인해야 하는 이유를 설명하시오.

모범 답안:  
Maintenance View는 임의의 테이블 조합이 아니라 관계가 명확한 테이블을 유지보수 대상으로 삼아야 한다. Foreign Key는 어떤 테이블이 어떤 필드로 연결되는지 DDIC 수준에서 표현하므로, 유지보수 구조의 안정성과 데이터 정합성을 확보하는 기반이 된다.

#### Q3. Primary Table을 잘못 선택하면 어떤 문제가 생길 수 있는가?

모범 답안:  
유지보수 화면의 중심 데이터가 사용자의 업무 관점과 맞지 않게 된다. 그 결과 어떤 데이터를 기준으로 조회하고 변경해야 하는지 불명확해지며, Header/Detail 관계나 Check/Dependent 관계가 잘못 표현될 수 있다.

```text
Maintenance View는 관련 테이블 데이터를 유지보수하기 위한 Classic DDIC View이다.
Database View는 조회 중심이고, Maintenance View는 유지보수 중심이다.
Maintenance View는 Foreign Key 관계를 기반으로 테이블 관계를 이해한다.

대량 업무 데이터나 표준 프로세스가 필요한 데이터에는 부적절할 수 있다.
```

## 21. 강사용 설명 포인트

강의에서는 다음 메시지를 강조한다.

1. **Maintenance View는 빠른 화면 생성 도구가 아니라 유지보수 모델이다.**  
   단순히 `SM30` 화면을 빨리 만들기 위한 수단으로만 설명하면 위험하다.

2. **Foreign Key가 있어야 관계가 설명된다.**  
   테이블 관계를 코드나 구두 설명으로만 관리하지 말고 DDIC에 명시하는 이유를 설명한다.

3. **조회용 View와 유지보수용 View의 설계 기준은 다르다.**  
   조회에 필요한 필드와 유지보수에 필요한 필드는 다를 수 있다.

4. **운영 데이터 직접 변경은 위험하다.**  
   설정성 데이터와 트랜잭션 데이터를 구분하도록 지도한다.

5. **CDS/RAP 이전의 Classic 기준점으로 이해한다.**  
   이후 CDS View Entity, RAP BO, Fiori Elements와 비교하기 위한 기준 지식으로 위치를 잡아준다.
