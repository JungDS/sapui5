## 3. Behavior Definition과 Behavior Implementation의 관계

RAP에서 Behavior는 크게 두 층으로 나누어 이해할 수 있다.

```text
Behavior Definition
  → 무엇을 할 수 있는지 선언한다.

Behavior Implementation
  → 선언된 동작을 실제 ABAP 로직으로 구현한다.
```

### 3.1 Behavior Definition의 역할

Behavior Definition, 즉 BDEF는 RAP Business Object의 동작 계약을 선언한다.

예를 들면 다음과 같은 내용을 정의한다.

| BDEF 선언 | 의미 |
|---|---|
| `create;` | 생성 가능 |
| `update;` | 수정 가능 |
| `delete;` | 삭제 가능 |
| `field ( readonly )` | 특정 필드는 읽기 전용 |
| `validation ... on save` | 저장 시 검증 수행 |
| `determination ... on modify` | 변경 시 자동 값 결정 |
| `action ...` | 사용자가 실행할 수 있는 명시적 동작 |

BDEF는 “이 Business Object가 어떤 동작을 지원하는가”를 선언한다.

### 3.2 Behavior Implementation의 역할

Behavior Implementation은 BDEF에 선언된 일부 동작을 실제 ABAP Method로 구현한다.

예를 들어 BDEF에 다음과 같은 선언이 있다고 하자.

```abap
validation validateStatus on save { field Status; }
```

그러면 구현 Class에는 해당 Validation을 처리하는 Method가 필요하다.

```abap
METHOD validateStatus.
  " Status 검증 로직 구현
ENDMETHOD.
```

즉, BDEF가 계약서라면 Behavior Implementation은 계약서에 적힌 업무 규칙을 실제로 수행하는 구현부이다.

## 4. Managed Scenario에서 Behavior Implementation의 위치

RAP Managed Scenario에서는 기본 CRUD 처리를 RAP Framework가 상당 부분 자동으로 처리한다.  
따라서 개발자가 직접 모든 INSERT, UPDATE, DELETE SQL을 작성하지 않는다.

하지만 다음과 같은 업무 규칙은 구현이 필요하다.

| 구현 대상 | 설명 |
|---|---|
| Validation | 저장 전 데이터가 유효한지 검사 |
| Determination | 특정 값 자동 계산 또는 기본값 설정 |
| Action | 사용자가 명시적으로 실행하는 비즈니스 동작 |
| Authorization | 인스턴스별 권한 판단 |
| Feature Control | 필드/액션 가능 여부 동적 제어 |
| Side Effect | UI 반영이 필요한 후속 영향 관리 |

초급 단계에서는 다음 문장을 기억하면 된다.

```text
Managed Scenario에서 CRUD의 기본 저장 처리는 Framework가 담당하고,
개발자는 업무 규칙 중심의 Method를 Behavior Implementation에 구현한다.
```

## 5. Behavior Pool과 Implementation Class

### 5.1 Behavior Pool이란?

RAP Behavior Implementation은 일반적인 전역 Class처럼 보이지만, RAP에서는 보통 **Behavior Pool**이라는 형태로 관리된다.

예제 이름:

```text
ZBP_I_JHY_TRAVEL
```

이 이름은 보통 Interface View `ZI_JHY_TRAVEL`의 Behavior Implementation Class로 이해할 수 있다.

일반적인 흐름은 다음과 같다.

```text
ZI_JHY_TRAVEL
  → Behavior Definition 생성
  → Behavior Implementation 생성
  → Class ZBP_I_JHY_TRAVEL 생성
  → Local Handler Class에서 Method 구현
```

### 5.2 Local Handler Class

Behavior Pool 내부에는 Entity별 Handler Class가 생성된다.

예를 들어 Root Entity Alias가 `Travel`이라면 다음과 같은 Local Handler Class가 생성될 수 있다.

```abap
CLASS lhc_Travel DEFINITION INHERITING FROM cl_abap_behavior_handler.
  PRIVATE SECTION.
    ...
ENDCLASS.
```

이 Class는 RAP Framework가 호출하는 Method를 담는다.

### 5.3 Handler Class의 특징

| 특징 | 설명 |
|---|---|
| `cl_abap_behavior_handler` 상속 | RAP Behavior Handler 역할 수행 |
| Local Class | Behavior Pool 내부에 존재 |
| Entity별 구성 | Root/Child Entity별 Handler가 나뉠 수 있음 |
| Method Signature 자동 생성 | BDEF 선언에 따라 필요한 Method 형태가 결정됨 |
| 직접 호출 목적 아님 | 일반 애플리케이션 코드에서 직접 호출하는 Class가 아님 |

초급자는 다음 점을 주의해야 한다.

```text
Behavior Handler Method는 일반 ABAP 프로그램에서 CALL METHOD로 직접 호출하는 목적이 아니다.
RAP Runtime이 BO 처리 흐름 중 적절한 시점에 호출한다.
```

## 6. 예제 전제: Interface View와 Projection View

RAP 예제는 항상 Interface View와 Projection View를 함께 둔다.

### 6.1 Interface View 예시

아래는 설명용 최소 예제이다.

```abap
@AccessControl.authorizationCheck: #NOT_REQUIRED
@EndUserText.label: 'Travel Interface View'
define root view entity ZI_JHY_TRAVEL
  as select from zt_jhy_travel
{
  key travel_uuid       as TravelUuid,
      travel_id         as TravelId,
      agency_id         as AgencyId,
      customer_id       as CustomerId,
      begin_date        as BeginDate,
      end_date          as EndDate,
      booking_fee       as BookingFee,
      total_price       as TotalPrice,
      currency_code     as CurrencyCode,
      status            as Status,
      created_by        as CreatedBy,
      created_at        as CreatedAt,
      last_changed_by   as LastChangedBy,
      last_changed_at   as LastChangedAt,
      local_last_changed_at as LocalLastChangedAt
}
```

> [추정] `zt_jhy_travel` 테이블과 필드는 교육용 예시이다. 실제 RAP 실습에서는 이전 모듈에서 만든 Root View와 Persistent Table 이름을 사용한다.

### 6.2 Projection View 예시

```abap
@AccessControl.authorizationCheck: #NOT_REQUIRED
@EndUserText.label: 'Travel Projection View'
@Metadata.allowExtensions: true
define root view entity ZC_JHY_TRAVEL
  as projection on ZI_JHY_TRAVEL
{
  key TravelUuid,
      TravelId,
      AgencyId,
      CustomerId,
      BeginDate,
      EndDate,
      BookingFee,
      TotalPrice,
      CurrencyCode,
      Status,
      CreatedBy,
      CreatedAt,
      LastChangedBy,
      LastChangedAt,
      LocalLastChangedAt
}
```

Interface View는 RAP Business Object의 기본 모델에 가깝고, Projection View는 외부 노출과 UI 소비를 위한 계층이다.

## 7. Behavior Definition 예시

### 7.1 Interface Behavior Definition 예시

```abap
managed implementation in class zbp_i_jhy_travel unique;
strict ( 2 );

define behavior for ZI_JHY_TRAVEL alias Travel
persistent table zt_jhy_travel
lock master
authorization master ( instance )
etag master LocalLastChangedAt
{
  create;
  update;
  delete;

  field ( readonly )
    TravelUuid,
    CreatedBy,
    CreatedAt,
    LastChangedBy,
    LastChangedAt,
    LocalLastChangedAt;

  validation validateStatus on save { field Status; }

  mapping for zt_jhy_travel
  {
    TravelUuid          = travel_uuid;
    TravelId            = travel_id;
    AgencyId            = agency_id;
    CustomerId          = customer_id;
    BeginDate           = begin_date;
    EndDate             = end_date;
    BookingFee          = booking_fee;
    TotalPrice          = total_price;
    CurrencyCode        = currency_code;
    Status              = status;
    CreatedBy           = created_by;
    CreatedAt           = created_at;
    LastChangedBy       = last_changed_by;
    LastChangedAt       = last_changed_at;
    LocalLastChangedAt  = local_last_changed_at;
  }
}
```

이 예제에서 중요한 부분은 다음이다.

```abap
managed implementation in class zbp_i_jhy_travel unique;
```

이 선언이 Behavior Implementation Class와 연결된다.

### 7.2 Projection Behavior Definition 예시

Projection 계층에서도 Behavior Projection을 둔다.

```abap
projection;
strict ( 2 );

define behavior for ZC_JHY_TRAVEL alias Travel
{
  use create;
  use update;
  use delete;
}
```

Projection Behavior는 Interface Behavior에서 선언한 동작 중 외부에 노출할 동작을 선택하는 역할을 한다.

## 8. Behavior Implementation 기본 구조

### 8.1 생성되는 Class 구조 예시

ADT에서 Behavior Implementation을 생성하면 대략 다음과 같은 구조를 볼 수 있다.

```abap
CLASS lhc_Travel DEFINITION INHERITING FROM cl_abap_behavior_handler.
  PRIVATE SECTION.

    METHODS validateStatus FOR VALIDATE ON SAVE
      IMPORTING keys FOR Travel~validateStatus.

ENDCLASS.

CLASS lhc_Travel IMPLEMENTATION.

  METHOD validateStatus.
    " 구현 로직
  ENDMETHOD.

ENDCLASS.
```

이 코드는 일반 Class 문법처럼 보이지만, Method Signature는 RAP BDEF 선언에 의해 결정된다.

### 8.2 Method 선언 해석

```abap
METHODS validateStatus FOR VALIDATE ON SAVE
  IMPORTING keys FOR Travel~validateStatus.
```

각 부분의 의미는 다음과 같다.

| 구문 | 의미 |
|---|---|
| `validateStatus` | Method 이름 |
| `FOR VALIDATE ON SAVE` | 저장 시점 Validation 구현 Method |
| `IMPORTING keys` | 검증 대상 Entity의 Key 정보 |
| `FOR Travel~validateStatus` | Travel Entity의 validateStatus Validation과 연결 |

`keys`에는 현재 처리 대상이 되는 Entity Instance의 Key 정보가 들어온다.  
Method 내부에서는 보통 이 Key를 이용해 현재 데이터를 읽고 검증한다.

## 9. `READ ENTITIES ... IN LOCAL MODE`

Behavior Implementation 내부에서는 DB 테이블을 직접 `SELECT`하기보다 EML(Entity Manipulation Language)을 사용하는 경우가 많다.

대표 예시는 다음이다.

```abap
READ ENTITIES OF ZI_JHY_TRAVEL IN LOCAL MODE
  ENTITY Travel
    FIELDS ( Status )
    WITH CORRESPONDING #( keys )
  RESULT DATA(lt_travel).
```

### 9.1 왜 EML을 사용하는가?

RAP Runtime 안에서는 아직 DB에 최종 저장되지 않은 변경 데이터가 Transactional Buffer에 존재할 수 있다.  
따라서 단순한 SQL `SELECT`만으로는 현재 RAP 트랜잭션의 최신 상태를 정확히 반영하지 못할 수 있다.

`IN LOCAL MODE`는 RAP 내부 처리 흐름에서 현재 트랜잭션 컨텍스트를 기준으로 Entity 데이터를 읽기 위해 사용한다.

초급자는 다음처럼 이해하면 된다.

```text
Behavior Implementation 내부에서 현재 처리 중인 Entity 데이터를 읽을 때는
DB SELECT보다 RAP EML READ ENTITIES를 먼저 고려한다.
```

## 10. `failed`와 `reported`

Validation이나 Action 구현에서 자주 등장하는 두 결과 테이블이 있다.

```text
failed
reported
```

### 10.1 failed

`failed`는 해당 Entity 처리에 실패한 Instance를 RAP Runtime에 알려주는 역할을 한다.

예를 들어 Status가 비어 있으면 저장을 실패 처리할 수 있다.

```abap
APPEND VALUE #( %tky = ls_travel-%tky ) TO failed-travel.
```

### 10.2 reported

`reported`는 UI나 호출자에게 전달할 메시지를 담는다.

```abap
APPEND VALUE #(
  %tky = ls_travel-%tky
  %msg = new_message_with_text(
           severity = if_abap_behv_message=>severity-error
           text     = 'Status is required.' )
  %element-Status = if_abap_behv=>mk-on
) TO reported-travel.
```

### 10.3 둘의 차이

| 구분 | 역할 |
|---|---|
| `failed` | 처리 실패 Instance 지정 |
| `reported` | 사용자 또는 호출자에게 메시지 전달 |
| 함께 사용하는 경우 | 실패한 Instance와 실패 이유를 함께 알려야 할 때 |

초급자는 다음 원칙을 기억하면 된다.

```text
failed만 있으면 무엇이 실패했는지 알 수 있지만 이유가 부족하다.
reported만 있으면 메시지는 보일 수 있지만 실패 처리와 연결이 약할 수 있다.
실무에서는 failed와 reported를 함께 설계하는 경우가 많다.
```

## 11. 최소 구현 예제: Status 필수값 검증

이 예제는 `Status`가 비어 있으면 저장하지 못하게 하는 매우 단순한 Validation이다.  
Validation의 상세 설계는 다음 모듈에서 더 깊게 다룬다. 여기서는 Behavior Implementation Method의 기본 구조를 이해하는 데 집중한다.

```abap
CLASS lhc_Travel DEFINITION INHERITING FROM cl_abap_behavior_handler.
  PRIVATE SECTION.

    METHODS validateStatus FOR VALIDATE ON SAVE
      IMPORTING keys FOR Travel~validateStatus.

ENDCLASS.

CLASS lhc_Travel IMPLEMENTATION.

  METHOD validateStatus.

    READ ENTITIES OF ZI_JHY_TRAVEL IN LOCAL MODE
      ENTITY Travel
        FIELDS ( Status )
        WITH CORRESPONDING #( keys )
      RESULT DATA(lt_travel).

    LOOP AT lt_travel INTO DATA(ls_travel).

      IF ls_travel-Status IS INITIAL.

        APPEND VALUE #( %tky = ls_travel-%tky )
          TO failed-travel.

        APPEND VALUE #(
          %tky = ls_travel-%tky
          %msg = new_message_with_text(
                   severity = if_abap_behv_message=>severity-error
                   text     = 'Status is required.' )
          %element-Status = if_abap_behv=>mk-on
        ) TO reported-travel.

      ENDIF.

    ENDLOOP.

  ENDMETHOD.

ENDCLASS.
```

### 11.1 코드 흐름 해석

| 단계 | 설명 |
|---:|---|
| 1 | RAP Runtime이 저장 시점에 `validateStatus` Method를 호출한다. |
| 2 | `keys`로 현재 검증 대상 Instance의 Key가 전달된다. |
| 3 | `READ ENTITIES ... IN LOCAL MODE`로 현재 Entity 데이터를 읽는다. |
| 4 | 각 Instance의 `Status`를 확인한다. |
| 5 | 비어 있으면 `failed-travel`에 실패 Instance를 추가한다. |
| 6 | `reported-travel`에 오류 메시지를 추가한다. |
| 7 | RAP Runtime은 실패 Instance를 저장하지 않고 메시지를 반환한다. |

### 11.2 이 예제가 보여주는 핵심

이 예제의 목적은 복잡한 Validation 설계가 아니다.  
Behavior Implementation에서 자주 등장하는 패턴을 읽는 것이다.

```text
keys를 받는다.
READ ENTITIES로 현재 데이터를 읽는다.
업무 조건을 검사한다.
failed와 reported에 결과를 기록한다.
```

## 12. Behavior Implementation 생성 절차

### 12.1 ADT 기준 절차

RAP Behavior Implementation은 SAP GUI SE80보다는 Eclipse ADT에서 작성하는 것이 표준적이다.

일반적인 절차는 다음과 같다.

```text
1. Eclipse ADT에서 패키지 선택
2. Interface View Entity ZI_JHY_TRAVEL 확인
3. Behavior Definition 생성 또는 열기
4. BDEF에 managed implementation class 지정
5. Quick Fix 또는 생성 메뉴로 Behavior Implementation Class 생성
6. 생성된 Class ZBP_I_JHY_TRAVEL 열기
7. Local Handler Class의 Method Stub 확인
8. Method 내부에 최소 로직 구현
9. Activate
10. Service Preview 또는 EML 테스트로 동작 확인
```

SAP GUI 800은 여전히 DDIC 테이블 확인, Transport 확인, 일부 Repository 객체 조회에 사용할 수 있지만, RAP 개발 자체는 ADT 중심으로 진행하는 것이 일반적이다.

### 12.2 활성화 순서

권장 활성화 흐름은 다음과 같다.

```text
1. Persistent Table
2. Interface View ZI_*
3. Projection View ZC_*
4. Interface Behavior Definition
5. Behavior Implementation Class
6. Projection Behavior Definition
7. Service Definition
8. Service Binding
```

실제 ADT에서는 의존성에 따라 여러 객체를 함께 Activate할 수 있다.  
다만 오류 분석을 위해 초급 단계에서는 의존성 순서를 이해하고 있는 것이 중요하다.

## 13. 정상 흐름과 오류 흐름

### 13.1 정상 흐름

```text
BDEF에 Validation 또는 Action 선언
→ Behavior Implementation Class 생성
→ Handler Method Stub 확인
→ READ ENTITIES로 대상 데이터 읽기
→ 업무 조건 검사
→ failed/reported 또는 mapped/result 작성
→ Activate
→ Preview 또는 EML 테스트
```

### 13.2 오류 흐름 1: Method Stub이 생성되지 않음

| 항목 | 설명 |
|---|---|
| 증상 | BDEF에는 선언했지만 Implementation Class에 Method가 없음 |
| 원인 | Quick Fix 미실행, BDEF Syntax 오류, Entity Alias 불일치 |
| 해결 | BDEF 활성화 후 Quick Fix로 missing method 생성 |

### 13.3 오류 흐름 2: Entity Alias 불일치

| 항목 | 설명 |
|---|---|
| 증상 | `Travel~validateStatus` 같은 참조가 맞지 않음 |
| 원인 | BDEF의 `alias Travel`과 구현부 Entity 이름이 다름 |
| 해결 | BDEF alias와 Implementation Method Signature를 일치시킴 |

### 13.4 오류 흐름 3: `failed-travel` 또는 `reported-travel` 이름 오류

| 항목 | 설명 |
|---|---|
| 증상 | 컴파일 시 `failed-travel`을 찾을 수 없다는 오류 |
| 원인 | Entity Alias 또는 Method 유형에 따른 generated component 이름이 다름 |
| 해결 | ADT가 생성한 Method Stub과 자동 완성 기준으로 정확한 component 이름 사용 |

### 13.5 오류 흐름 4: 직접 DB SELECT 사용으로 최신 변경값 누락

| 항목 | 설명 |
|---|---|
| 증상 | 방금 변경한 값이 Validation에서 다르게 보임 |
| 원인 | RAP Transactional Buffer를 고려하지 않고 DB만 직접 조회 |
| 해결 | Behavior Implementation 내부에서는 필요한 경우 `READ ENTITIES ... IN LOCAL MODE` 사용 |

### 13.6 오류 흐름 5: 메시지는 보이지만 저장 차단이 안 됨

| 항목 | 설명 |
|---|---|
| 증상 | Error 메시지는 작성했지만 Instance가 실패 처리되지 않음 |
| 원인 | `reported`만 작성하고 `failed`를 작성하지 않음 |
| 해결 | 실패 대상 Instance를 `failed-<entity>`에 함께 추가 |

## 14. 실무 설계 기준

### 14.1 Behavior Implementation에 넣기 좋은 로직

| 로직 | 이유 |
|---|---|
| 저장 전 필수값 검증 | Business Object 일관성 보장 |
| 상태 전이 검증 | 잘못된 업무 상태 변경 방지 |
| 기본값 자동 설정 | 사용자 입력 부담 감소 |
| 파생값 계산 | BO 내부 규칙으로 중앙 관리 |
| Action 처리 | 승인, 취소, 마감 같은 명시적 업무 동작 구현 |

### 14.2 Behavior Implementation에 과도하게 넣지 말아야 할 로직

| 로직 | 주의 이유 |
|---|---|
| 화면 표시 전용 로직 | UI 계층에서 처리하는 것이 적절할 수 있음 |
| 대량 집계 리포트 로직 | RAP BO 저장 흐름과 목적이 다름 |
| 외부 시스템 장시간 호출 | 트랜잭션 지연과 장애 전파 위험 |
| 직접 DB UPDATE 남발 | RAP Transactional Buffer와 충돌 가능 |
| 표준 객체 직접 수정 | Clean Core 원칙 위반 가능 |

### 14.3 Clean Core 관점

RAP / ABAP Cloud에서는 Clean Core 원칙이 중요하다.

실무 기준은 다음과 같다.

```text
표준 SAP 객체를 직접 수정하지 않는다.
Released API와 확장 포인트를 우선 검토한다.
Business Object 내부 규칙은 Behavior 계층에서 명확히 표현한다.
DB 직접 조작보다 RAP Runtime의 트랜잭션 모델을 존중한다.
```

이 모듈은 입문 단계이므로 Released API 전체를 깊게 다루지는 않는다.  
해당 주제는 `THEORY-21-M08 ABAP Cloud와 Released API 원칙`에서 확장한다.

Behavior Implementation은 일반 Report처럼 실행 버튼을 누르는 구조가 아니다.  
RAP Runtime이 호출하므로 테스트 경로를 알아야 한다.

### 15.1 주요 검증 경로

## 17. 평가 문제

### 17.1 객관식

#### Q1. Behavior Implementation의 가장 적절한 설명은?

A. CDS View의 필드 라벨만 정의하는 객체이다.  
B. BDEF에 선언된 동작이나 업무 규칙을 ABAP Class/Method로 구현하는 영역이다.  
C. SAP GUI에서만 실행되는 Report 프로그램이다.  
D. 데이터베이스 테이블의 Technical Settings를 설정하는 화면이다.

**정답:** B

#### Q2. Managed Scenario에서 기본 CRUD 처리는 주로 누가 담당하는가?

A. 개발자가 모든 SQL INSERT/UPDATE/DELETE를 직접 작성한다.  
B. RAP Framework가 상당 부분 담당한다.  
C. SE16N이 자동으로 처리한다.  
D. Transport Organizer가 처리한다.

**정답:** B

#### Q3. Validation Method에서 실패 Instance를 표시하는 데 주로 사용하는 것은?

A. `reported`만 사용한다.  
B. `failed`를 사용한다.  
C. `WRITE`를 사용한다.  
D. `COMMIT WORK`를 직접 실행한다.

**정답:** B

### 17.2 단답형

#### Q1. Behavior Definition과 Behavior Implementation의 차이를 설명하시오.

**모범 답안:**  
Behavior Definition은 Business Object가 지원하는 동작과 규칙을 선언하는 계약이고, Behavior Implementation은 그 선언된 규칙을 ABAP Class와 Method로 실제 구현하는 영역이다.

#### Q2. Behavior Implementation 내부에서 `READ ENTITIES ... IN LOCAL MODE`를 사용하는 이유는 무엇인가?

**모범 답안:**  
RAP 트랜잭션 처리 중 아직 DB에 저장되지 않은 변경 데이터가 Transactional Buffer에 존재할 수 있으므로, 현재 RAP 처리 컨텍스트의 데이터를 읽기 위해 사용한다.

#### Q3. `failed`와 `reported`의 차이를 설명하시오.

**모범 답안:**  
`failed`는 처리 실패 대상 Instance를 RAP Runtime에 알려주고, `reported`는 사용자 또는 호출자에게 전달할 메시지를 담는다. 실패와 메시지를 명확히 전달하려면 둘을 함께 사용하는 경우가 많다.

## 18. 초급자 실수와 안티패턴

| 실수 | 문제 | 개선 |
|---|---|---|
| BDEF 선언만 하고 Implementation Method를 만들지 않음 | 활성화 또는 런타임 오류 가능 | ADT Quick Fix로 Method Stub 생성 |
| `SELECT`로만 현재 데이터를 읽음 | RAP Transactional Buffer 미반영 가능 | `READ ENTITIES ... IN LOCAL MODE` 검토 |
| `reported`만 작성하고 `failed` 누락 | 오류 메시지는 보이나 실패 처리 불명확 | 실패 Instance를 `failed`에 추가 |
| Handler Method를 직접 호출하려고 함 | RAP Runtime 호출 모델 오해 | Service Preview 또는 EML로 테스트 |
| Behavior Implementation에 모든 로직을 몰아넣음 | 유지보수성 저하 | 검증, 결정, 액션, 서비스 계층 역할 분리 |
| 표준 객체를 직접 수정 | Clean Core 위반 가능 | Released API와 확장 포인트 검토 |

## 19. 강사용 설명 포인트

강의에서는 다음 순서로 설명하면 이해가 쉽다.

```text
1. BDEF는 선언이고 BIMP는 구현이라는 관계를 먼저 설명한다.
2. Managed Scenario에서는 CRUD 기본 처리를 Framework가 담당한다는 점을 강조한다.
3. 그래도 업무 규칙은 개발자가 Method로 구현해야 함을 설명한다.
4. 생성된 Handler Class를 열어 Method Signature를 같이 읽는다.
5. READ ENTITIES, failed, reported를 최소 패턴으로 보여준다.
6. Service Preview에서 실제로 Method가 호출되는지 Debugger로 확인한다.
```

```text
Behavior Implementation은 일반 Report처럼 실행하는 프로그램이 아니라,
```
