## 3. SQL Expression이란 무엇인가?

SQL Expression은 SQL 문 안에서 계산되거나 평가되는 표현식이다.

간단한 예를 보자.

```abap
SELECT FROM sflight
  FIELDS carrid,
         connid,
         price,
         CASE
           WHEN price >= 1000 THEN 'HIGH'
           WHEN price >= 500  THEN 'MID'
           ELSE 'LOW'
         END AS price_level
  INTO TABLE @DATA(lt_result).
```

위 SELECT는 단순히 `SFLIGHT`의 필드만 가져오지 않는다.  
`PRICE` 값에 따라 `PRICE_LEVEL`이라는 계산 결과 컬럼을 만들어 함께 가져온다.

즉, SQL Expression은 다음과 같은 역할을 한다.

| 역할 | 예 |
|---|---|
| 조건 분기 | `CASE WHEN ... THEN ... ELSE ... END` |
| 타입 변환 | `CAST( ... AS ... )` |
| NULL 기본값 처리 | `COALESCE( value, default )` |
| 문자열/날짜 계산 | 후속 모듈의 SQL String / Date Function |
| 산술 계산 | 금액, 수량, 비율 계산 |

이번 모듈에서는 `CASE`, `CAST`, `COALESCE` 세 가지에 집중한다.

## 4. 왜 SQL Expression을 사용하는가?

### 4.1 기존 방식: ABAP에서 후처리

Classic ABAP 초급 단계에서는 보통 DB에서 데이터를 가져온 뒤 `LOOP AT` 안에서 값을 가공한다.

```abap
SELECT carrid, connid, price, currency
  FROM sflight
  INTO TABLE @DATA(lt_flight).

LOOP AT lt_flight ASSIGNING FIELD-SYMBOL(<ls_flight>).
  " 가격 등급 계산을 ABAP에서 수행
ENDLOOP.
```

이 방식은 이해하기 쉽다. 하지만 단순 분기나 기본값 보정까지 모두 ABAP에서 처리하면 다음 문제가 생긴다.

| 문제 | 설명 |
|---|---|
| 코드 분산 | 조회 로직과 결과 가공 로직이 분리되어 읽기 어려워진다. |
| 반복 처리 증가 | 가져온 모든 행을 다시 LOOP로 순회해야 한다. |
| 의도 표현 부족 | SELECT 결과에 어떤 의미의 컬럼이 필요한지 SQL 단계에서 드러나지 않는다. |
| 후속 CDS 학습 단절 | CDS는 SELECT 리스트에서 Expression을 적극적으로 사용한다. |

### 4.2 Modern 방식: SELECT 결과에서 바로 의미 있는 컬럼 생성

Modern Open SQL에서는 단순한 결과 가공을 SELECT 리스트에서 표현할 수 있다.

```abap
SELECT FROM sflight
  FIELDS carrid,
         connid,
         price,
         CASE
           WHEN price >= 1000 THEN 'HIGH'
           WHEN price >= 500  THEN 'MID'
           ELSE 'LOW'
         END AS price_level
  INTO TABLE @DATA(lt_flight).
```

이 방식의 장점은 다음과 같다.

| 장점 | 설명 |
|---|---|
| 결과 의미 명확 | SELECT 결과에 `PRICE_LEVEL`이 포함되어 의도가 명확하다. |
| 후처리 감소 | 단순 분기나 기본값 보정을 ABAP LOOP에서 줄일 수 있다. |
| CDS 선행 학습 | CDS의 `case`, `cast`, `coalesce` 이해로 자연스럽게 이어진다. |
| SQL 중심 사고 | 데이터를 가져오는 시점에 필요한 결과 모양을 설계하게 된다. |

단, 모든 로직을 SQL로 밀어 넣는 것이 좋은 것은 아니다. 복잡한 업무 규칙, 권한 검증, 상태 변경 로직은 여전히 ABAP 계층에서 명확히 처리해야 한다.

## 5. CASE Expression

### 5.1 CASE의 목적

`CASE`는 SQL 결과 안에서 조건에 따라 다른 값을 반환하는 표현식이다.

ABAP의 `IF` 또는 `CASE`와 비슷한 목적을 가지지만, 실행 위치와 결과 형태가 다르다.

| 구분 | ABAP IF/CASE | SQL CASE |
|---|---|---|
| 실행 위치 | ABAP Application Server | SQL 조회 처리 영역 |
| 사용 위치 | LOOP, Method, Form 등 | SELECT 리스트, 조건식 등 |
| 결과 | 변수 값 변경 또는 로직 분기 | 결과 컬럼 값 생성 |
| 대표 목적 | 업무 로직 처리 | 조회 결과 분류/표현 |

### 5.2 기본 문법

대표적인 searched CASE 형태는 다음과 같다.

```abap
CASE
  WHEN 조건1 THEN 결과1
  WHEN 조건2 THEN 결과2
  ELSE 기본결과
END AS alias_name
```

예시:

```abap
SELECT FROM sflight
  FIELDS carrid,
         connid,
         price,
         CASE
           WHEN price >= 1000 THEN 'HIGH'
           WHEN price >= 500  THEN 'MID'
           ELSE 'LOW'
         END AS price_level
  INTO TABLE @DATA(lt_result).
```

결과 구조에는 다음 필드가 포함된다.

```text
CARRID
CONNID
PRICE
PRICE_LEVEL
```

### 5.3 업무 예시: 항공권 가격 등급

| PRICE | PRICE_LEVEL |
|---:|---|
| 1200 | HIGH |
| 700 | MID |
| 300 | LOW |

이처럼 조회 결과 자체에 분류값을 포함하면 ALV 출력, API 응답, 후속 Internal Table 처리에서 별도의 분류 로직을 줄일 수 있다.

### 5.4 CASE 사용 시 주의할 점

#### 5.4.1 THEN 결과 타입 일관성

`THEN`과 `ELSE`에서 반환하는 값들은 서로 호환 가능한 타입이어야 한다.

좋은 예:

```abap
CASE
  WHEN price >= 1000 THEN 'HIGH'
  WHEN price >= 500  THEN 'MID'
  ELSE 'LOW'
END AS price_level
```

주의가 필요한 예:

```abap
CASE
  WHEN price >= 1000 THEN 'HIGH'
  ELSE 0
END AS price_level
```

문자열과 숫자가 섞이면 타입 추론 또는 변환에서 문제가 발생할 수 있다. 초급자는 `CASE`의 결과 타입을 가능한 한 명확하고 일관되게 맞추는 습관을 가져야 한다.

#### 5.4.2 ELSE 누락

`ELSE`가 없으면 조건에 해당하지 않는 경우 결과가 NULL 성격으로 처리될 수 있다.  
ABAP 초급자는 NULL 개념에 익숙하지 않은 경우가 많으므로, 처음에는 `ELSE`를 명시하는 방식을 권장한다.

권장:

```abap
CASE
  WHEN status = 'A' THEN 'Active'
  WHEN status = 'I' THEN 'Inactive'
  ELSE 'Unknown'
END AS status_text
```

#### 5.4.3 CASE 남발 금지

`CASE`가 너무 길어지면 SQL이 읽기 어려워진다.

다음 상황에서는 별도 코드 테이블, Customizing Table, Domain Fixed Value, CDS 설계 등을 검토한다.

| 상황 | 검토 방향 |
|---|---|
| 코드값이 수십 개 이상 | 코드 테이블 또는 Text Table |
| 다국어 텍스트 필요 | Text Table 또는 CDS Association |
| 자주 변경되는 분류 기준 | Customizing Table |
| 복잡한 업무 규칙 | ABAP Method 또는 Rule 계층 |

## 6. CAST Expression

### 6.1 CAST의 목적

`CAST`는 SQL Expression의 결과를 명시적인 타입으로 변환한다.

초급자가 이해할 핵심은 다음이다.

```text
CAST는 SQL 결과 컬럼의 타입을 의도적으로 맞추기 위해 사용한다.
```

예를 들어 문자 리터럴이나 계산 결과가 예상보다 짧거나 애매한 타입으로 추론될 수 있다. 이때 `CAST`를 사용해 결과 타입을 명확히 할 수 있다.

### 6.2 기본 문법

```abap
CAST( expression AS dtype ) AS alias_name
```

Open SQL에서 사용 가능한 타입 표기는 ABAP SQL 문법과 릴리스에 따라 제한이 있을 수 있다. 초급 단계에서는 공식 ABAP Keyword Documentation 기준으로 확인하는 습관을 가져야 한다.

### 6.3 예시: CASE 결과 길이 명시

```abap
SELECT FROM sflight
  FIELDS carrid,
         connid,
         CAST(
           CASE
             WHEN price >= 1000 THEN 'HIGH'
             WHEN price >= 500  THEN 'MID'
             ELSE 'LOW'
           END AS CHAR( 4 )
         ) AS price_level
  INTO TABLE @DATA(lt_result).
```

이 예시는 `CASE` 결과를 명시적으로 `CHAR(4)` 성격으로 맞춘다.

> [추정] 실제 시스템 릴리스와 ABAP SQL 문법 지원 범위에 따라 `CAST`의 타입 표기 방식 또는 허용 위치가 다를 수 있다. 교육 환경에서는 사용 중인 S/4HANA 릴리스의 ABAP Keyword Documentation을 기준으로 검증해야 한다.

### 6.4 CAST가 필요한 대표 상황

| 상황 | 설명 |
|---|---|
| CASE 결과 타입을 명확히 하고 싶을 때 | 문자 길이나 숫자 타입 혼선을 줄인다. |
| 계산 결과 타입이 후속 처리에 맞지 않을 때 | 결과 컬럼 타입을 맞춘다. |
| COALESCE 기본값과 원본 타입을 맞출 때 | NULL 보정 결과 타입을 안정화한다. |
| CDS 또는 SQL 함수 학습으로 확장할 때 | 타입 명시 사고를 준비한다. |

### 6.5 CAST 사용 시 주의할 점

#### 6.5.1 무리한 타입 변환 금지

문자처럼 보이는 값이라고 해서 항상 숫자로 안전하게 변환할 수 있는 것은 아니다.

예:

```text
'000123' → 숫자로 변환 가능해 보임
'A00123' → 숫자로 변환 불가
'12-34'  → 숫자로 변환 불가
```

실무에서는 변환 실패 가능성을 고려해야 한다.

#### 6.5.2 의미 없는 CAST 남발 금지

모든 컬럼에 CAST를 붙이면 SQL이 장황해지고 유지보수가 어려워진다.  
필요한 경우에만 사용한다.

#### 6.5.3 ABAP 타입과 SQL 타입 감각 구분

ABAP의 `TYPE c LENGTH 10` 사고와 SQL Expression의 `CAST` 타입 표기는 완전히 같은 화면 조작이 아니다.  
Open SQL 문법의 허용 범위를 확인해야 한다.

## 7. COALESCE Expression

### 7.1 COALESCE의 목적

`COALESCE`는 여러 값 중 NULL이 아닌 첫 번째 값을 반환하는 SQL Expression이다.

가장 많이 사용하는 형태는 다음이다.

```abap
COALESCE( nullable_value, default_value ) AS alias_name
```

즉, 값이 있으면 원래 값을 사용하고, NULL이면 기본값을 사용한다.

### 7.2 ABAP 초급자에게 NULL이 어려운 이유

ABAP 초급자는 보통 `INITIAL`에 익숙하다.

```abap
IF gv_text IS INITIAL.
```

하지만 SQL에서의 `NULL`은 단순한 공백이나 0과 다르다.  
`NULL`은 “값이 없음”을 의미한다.

| 구분 | 의미 |
|---|---|
| `''` | 빈 문자열 또는 공백 성격의 값 |
| `0` | 숫자 0이라는 값 |
| `INITIAL` | ABAP 타입의 초기값 |
| `NULL` | DB/SQL 결과에서 값이 존재하지 않음 |

Outer Join, 일부 SQL Expression, 함수 결과, CDS 등으로 확장하면 NULL 처리가 매우 중요해진다.

### 7.3 기본 예시

항공편 데이터에서 특정 텍스트가 없을 때 기본값을 넣는다고 가정한다.

```abap
SELECT FROM zt_demo_flight
  FIELDS carrid,
         connid,
         COALESCE( remark, 'No remark' ) AS remark_text
  INTO TABLE @DATA(lt_result).
```

`REMARK`가 NULL이면 `REMARK_TEXT`에는 `No remark`가 들어간다.

### 7.4 LEFT OUTER JOIN과 COALESCE

`COALESCE`는 특히 `LEFT OUTER JOIN`과 함께 자주 등장한다.

예를 들어 항공사 마스터는 있지만, 보조 텍스트 테이블에 설명이 없을 수 있다고 가정한다.

```abap
SELECT FROM scarr AS carrier
  LEFT OUTER JOIN zt_carrier_note AS note
    ON note~carrid = carrier~carrid
  FIELDS carrier~carrid,
         carrier~carrname,
         COALESCE( note~note_text, 'No note' ) AS note_text
  INTO TABLE @DATA(lt_carrier).
```

여기서 `note~note_text`가 없으면 NULL이 될 수 있고, 이 값을 `No note`로 보정한다.

초급 단계에서는 다음만 기억하면 된다.

```text
Outer Join으로 없는 쪽의 값은 NULL이 될 수 있다.
COALESCE는 그 NULL을 화면/출력에 적합한 기본값으로 바꾸는 데 유용하다.
```

### 7.5 COALESCE 사용 시 주의할 점

#### 7.5.1 NULL과 INITIAL을 혼동하지 않는다

`COALESCE`는 NULL을 처리하는 표현식이다.  
ABAP의 `INITIAL` 값 전체를 자동으로 처리하는 만능 함수가 아니다.

#### 7.5.2 기본값 타입을 원본과 맞춘다

좋은 예:

```abap
COALESCE( note~note_text, 'No note' ) AS note_text
```

주의 예:

```abap
COALESCE( amount, 'No amount' ) AS amount_text
```

숫자 금액 필드에 문자 기본값을 넣으면 타입 호환 문제가 발생할 수 있다.  
금액을 표시용 텍스트로 바꾸려는 목적이라면 설계를 분리해야 한다.

---

## 8. CASE, CAST, COALESCE를 함께 사용하는 예

다음은 세 가지 Expression을 함께 사용하는 예제이다.

```abap
SELECT FROM sflight
  FIELDS carrid,
         connid,
         fldate,
         price,
         currency,
         CAST(
           CASE
             WHEN price >= 1000 THEN 'HIGH'
             WHEN price >= 500  THEN 'MID'
             ELSE 'LOW'
           END AS CHAR( 4 )
         ) AS price_level,
         COALESCE( planetype, 'N/A' ) AS plane_type_text
  INTO TABLE @DATA(lt_result).
```

이 예제의 의미는 다음과 같다.

| Expression | 역할 |
|---|---|
| `CASE` | 가격을 기준으로 등급을 만든다. |
| `CAST` | 가격 등급 결과의 타입을 명시한다. |
| `COALESCE` | 항공기 타입 값이 없을 경우 기본 텍스트를 제공한다. |
| `AS price_level` | 결과 컬럼의 이름을 정한다. |
| `AS plane_type_text` | NULL 보정 결과 컬럼의 이름을 정한다. |

> [추정] 표준 교육 시스템의 `SFLIGHT` 데이터 구성과 필드 NULL 허용 여부는 시스템 설치 상태에 따라 다를 수 있다. 예제의 핵심은 구문과 사고방식이며, 실제 실습에서는 시스템에 존재하는 테이블과 NULL 가능 필드를 기준으로 조정한다.

## 9. Alias와 Inline Target의 관계

Modern Open SQL에서 SQL Expression을 사용하면 Alias가 매우 중요해진다.

예를 들어 다음 SELECT를 보자.

```abap
SELECT FROM sflight
  FIELDS carrid,
         connid,
         CASE
           WHEN price >= 1000 THEN 'HIGH'
           ELSE 'NORMAL'
         END AS price_level
  INTO TABLE @DATA(lt_result).
```

`@DATA(lt_result)`는 SELECT 결과 구조를 기준으로 Internal Table 타입을 추론한다.

따라서 결과 구조는 대략 다음과 같은 필드를 가진다.

```text
CARRID
CONNID
PRICE_LEVEL
```

`CASE ... END`에 Alias를 명확히 주지 않으면 후속 ABAP 코드에서 해당 결과 컬럼을 다루기 어려워진다.

```abap
LOOP AT lt_result INTO DATA(ls_result).
  WRITE: / ls_result-carrid,
           ls_result-connid,
           ls_result-price_level.
ENDLOOP.
```

초급자는 다음 규칙을 습관화하는 것이 좋다.

```text
SQL Expression을 SELECT 리스트에 넣으면 반드시 의미 있는 Alias를 붙인다.
```

## 10. 실습 시나리오

### 10.1 실습 목표

`SFLIGHT` 또는 교육용 항공편 테이블을 조회하면서 다음 결과를 만든다.

1. 가격 기준 등급 `PRICE_LEVEL`
2. 통화 기준 설명 `CURRENCY_GROUP`
3. NULL 가능 필드의 기본값 보정
4. 결과를 Inline Target으로 받아 WRITE 출력

### 10.2 실습 코드 예시

```abap
REPORT zgpt_sql_expr_case_cast.

SELECT FROM sflight
  FIELDS carrid,
         connid,
         fldate,
         price,
         currency,
         CASE
           WHEN price >= 1000 THEN 'HIGH'
           WHEN price >= 500  THEN 'MID'
           ELSE 'LOW'
         END AS price_level,
         CASE currency
           WHEN 'USD' THEN 'US Dollar'
           WHEN 'EUR' THEN 'Euro'
           ELSE 'Other Currency'
         END AS currency_group
  INTO TABLE @DATA(lt_flight).

LOOP AT lt_flight INTO DATA(ls_flight).
  WRITE: / ls_flight-carrid,
           ls_flight-connid,
           ls_flight-fldate,
           ls_flight-price,
           ls_flight-currency,
           ls_flight-price_level,
           ls_flight-currency_group.
ENDLOOP.
```

### 10.3 실습 변형: WHERE 조건 추가

```abap
PARAMETERS p_carrid TYPE s_carr_id DEFAULT 'AA'.

SELECT FROM sflight
  FIELDS carrid,
         connid,
         fldate,
         price,
         currency,
         CASE
           WHEN price >= 1000 THEN 'HIGH'
           WHEN price >= 500  THEN 'MID'
           ELSE 'LOW'
         END AS price_level
  WHERE carrid = @p_carrid
  INTO TABLE @DATA(lt_flight).
```

이 예제는 `@` Host Variable과 SQL Expression이 함께 쓰이는 구조를 보여준다.

## 11. 정상 흐름과 오류 흐름

### 11.1 정상 흐름

```text
SELECT 대상 테이블 확인
→ 필요한 원본 필드 선정
→ CASE / CAST / COALESCE로 결과 컬럼 설계
→ 각 Expression에 의미 있는 Alias 부여
→ INTO TABLE @DATA(...)로 결과 수신
→ 결과 필드명 확인
→ WRITE 또는 디버거로 값 확인
```

### 11.2 오류 흐름 1: Alias 누락 또는 부적절한 Alias

#### 증상

- Inline Target 구조에서 필드명을 예상대로 사용할 수 없다.
- `ls_result-price_level` 같은 접근이 실패한다.

#### 원인

Expression 결과에 명확한 Alias를 부여하지 않았거나, Alias 이름을 잘못 기억했다.

#### 해결

Expression에는 항상 의미 있는 Alias를 부여한다.

```abap
END AS price_level
```

### 11.3 오류 흐름 2: CASE 결과 타입 불일치

#### 증상

- Syntax Check 또는 Activation 단계에서 타입 관련 오류가 발생한다.
- 결과 값이 예상과 다르게 잘리거나 변환된다.

#### 원인

`THEN`과 `ELSE`의 반환값 타입이 일관되지 않거나, 길이가 애매하게 추론되었다.

#### 해결

- 모든 반환값을 같은 성격으로 맞춘다.
- 필요한 경우 `CAST`로 결과 타입을 명확히 한다.

### 11.4 오류 흐름 3: COALESCE 기본값 타입 불일치

#### 증상

- `COALESCE`에서 타입 오류가 발생한다.

#### 원인

원본 값과 기본값의 타입이 호환되지 않는다.

#### 해결

숫자 필드에는 숫자 기본값, 문자 필드에는 문자 기본값을 사용한다.

```abap
COALESCE( note_text, 'No note' )
COALESCE( amount, 0 )
```

### 11.5 오류 흐름 4: 너무 복잡한 SQL Expression

#### 증상

- SELECT 문이 지나치게 길어져 읽기 어렵다.
- 디버깅과 유지보수가 어려워진다.

#### 원인

ABAP에서 처리해야 할 복잡한 업무 규칙까지 SQL Expression으로 넣었다.

#### 해결

- 단순 분류와 기본값 보정은 SQL Expression으로 처리한다.
- 복잡한 업무 판단은 ABAP Method, CDS View, Customizing Table 등으로 분리한다.

## 12. 디버깅과 검증 포인트

SQL Expression은 ABAP 코드 한 줄씩 디버깅하는 것과 다르게, SELECT 실행 결과로 확인하는 경우가 많다.

### 12.1 검증 방법

| 방법 | 설명 |
|---|---|
| Debugger에서 `lt_result` 확인 | Expression 결과 컬럼 값이 예상대로 들어왔는지 확인 |
| WRITE 출력 | 초급 실습에서 가장 단순한 검증 방식 |
| ADT Data Preview와 비교 | 원본 테이블 값과 Expression 결과를 비교 |
| 조건별 테스트 데이터 준비 | CASE 분기별로 HIGH/MID/LOW가 모두 나오게 확인 |

### 12.2 CASE 검증 체크

```text
HIGH 조건에 해당하는 데이터가 있는가?
MID 조건에 해당하는 데이터가 있는가?
LOW 조건에 해당하는 데이터가 있는가?
ELSE로 떨어지는 경우가 있는가?
```

### 12.3 COALESCE 검증 체크

```text
NULL 값이 실제로 발생하는 데이터 조건인가?
기본값이 원본 타입과 호환되는가?
초기값과 NULL을 혼동하고 있지 않은가?
```

## 13. 성능과 운영 관점

SQL Expression은 단순 후처리를 줄이고 결과의 의미를 SELECT 단계에서 명확히 할 수 있다. 하지만 성능 측면에서는 “SQL로 처리하면 무조건 빠르다”라고 단정해서는 안 된다.

### 13.1 장점

| 장점 | 설명 |
|---|---|
| ABAP 후처리 감소 | 단순 분류와 보정 LOOP를 줄일 수 있다. |
| 결과 구조 명확화 | 필요한 결과 컬럼을 SELECT에서 바로 정의한다. |
| DB Pushdown 사고 준비 | CDS/RAP로 넘어가기 전 SQL 표현식 감각을 익힌다. |

### 13.2 주의점

| 주의점 | 설명 |
|---|---|
| 가독성 | Expression이 길어지면 SELECT 문이 읽기 어려워진다. |
| 타입 안정성 | CASE/COALESCE 결과 타입을 명확히 해야 한다. |
| DB 처리 비용 | 복잡한 Expression을 대량 데이터에 적용하면 비용이 생길 수 있다. |
| 업무 로직 위치 | 모든 비즈니스 규칙을 SQL에 넣으면 유지보수가 어려워질 수 있다. |

### 13.3 실무 판단 기준

SQL Expression으로 처리하기 적합한 경우:

```text
단순 코드 텍스트 변환
단순 등급 분류
NULL 기본값 보정
출력용 계산 컬럼
CDS로 옮겨갈 가능성이 높은 조회 표현
```

ABAP 로직으로 두는 것이 나은 경우:

```text
복잡한 업무 승인 규칙
여러 단계의 예외 처리
권한/상태/이력 변경이 결합된 로직
디버깅과 테스트가 중요한 업무 판단
자주 바뀌는 조건표 기반 규칙
```

## 14. CDS 학습과의 연결

이번 모듈은 후속 CDS View Entity 학습의 매우 중요한 선행 지식이다.

CDS에서도 다음과 같은 표현식을 자주 사용한다.

```sql
case
  when condition then value
  else value
end as FieldName
```

```sql
cast( value as abap.char(4) ) as FieldName
```

```sql
coalesce( value, default ) as FieldName
```

Open SQL에서 이 표현식의 기본 감각을 익히면 CDS에서 다음 개념을 이해하기 쉬워진다.

| 이번 모듈 | CDS에서의 확장 |
|---|---|
| SELECT 리스트 Expression | CDS SELECT list expression |
| CASE | CDS calculated field |
| CAST | CDS type adjustment |
| COALESCE | Association/Outer Join NULL 보정 |
| Alias | CDS element name |

초급자는 다음 연결을 기억하면 된다.

```text
Modern Open SQL의 Expression은 CDS View Entity의 계산 필드와 매우 자연스럽게 연결된다.
```

## 16. 평가 문제

### 16.1 객관식

#### Q1. SQL Expression의 설명으로 가장 적절한 것은?

A. ABAP 프로그램의 주석을 자동 생성하는 기능이다.  
B. SQL 문 안에서 계산, 분기, 변환 등을 수행하는 표현식이다.  
C. SAP GUI 화면의 버튼을 만드는 기능이다.  
D. Transport Request를 생성하는 기능이다.

정답: B

#### Q2. CASE Expression의 주요 목적은?

A. 조건에 따라 결과 컬럼 값을 다르게 반환한다.  
B. Internal Table을 정렬한다.  
C. 데이터베이스 테이블을 생성한다.  
D. Selection Screen을 만든다.

정답: A

#### Q3. COALESCE의 주요 목적은?

A. 모든 데이터를 삭제한다.  
B. NULL 가능 값에 대해 기본값을 반환한다.  
C. ABAP 변수명을 자동 변경한다.  
D. 프로그램을 활성화한다.

정답: B

### 16.2 서술형

#### Q1. SQL CASE와 ABAP IF의 차이를 설명하시오.

모범 답안:  
ABAP IF는 ABAP 프로그램 실행 흐름 안에서 조건에 따라 로직을 분기한다. SQL CASE는 SELECT 문 내부에서 조건에 따라 결과 컬럼 값을 생성한다. 즉, ABAP IF는 프로그램 로직 분기이고, SQL CASE는 조회 결과 표현식이다.

#### Q2. SQL Expression에 Alias가 중요한 이유를 설명하시오.

모범 답안:  
Expression 결과는 원본 테이블 필드명이 없기 때문에 의미 있는 이름을 부여해야 후속 ABAP 코드에서 해당 결과 컬럼을 명확히 참조할 수 있다. 특히 `INTO TABLE @DATA(...)`를 사용할 때 Alias는 Inline Target의 필드명으로 이어진다.

#### Q3. COALESCE 사용 시 NULL과 INITIAL을 혼동하면 안 되는 이유를 설명하시오.

모범 답안:  
COALESCE는 SQL의 NULL 값을 처리하는 표현식이다. ABAP의 INITIAL은 타입별 초기값을 의미하며 NULL과 동일하지 않다. 따라서 빈 문자열, 0, 초기값을 모두 COALESCE가 처리한다고 오해하면 안 된다.
