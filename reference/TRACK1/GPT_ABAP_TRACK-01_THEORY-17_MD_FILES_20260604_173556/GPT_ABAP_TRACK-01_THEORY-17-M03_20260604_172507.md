## 0. 문서 목적

이 문서는 Modern ABAP SQL에서 자주 사용하는 다음 구문을 초급자도 실무 관점으로 이해할 수 있도록 설명한다.

```abap
SELECT ...
  FROM ...
  INTO TABLE @DATA(lt_result).
```

`INTO TABLE @DATA(...)`는 SELECT 결과를 받을 Internal Table을 미리 선언하지 않고, SQL 결과 구조에 맞춰 그 자리에서 선언하는 Inline Target 문법이다. 이 문법은 Modern ABAP의 대표적인 생산성 향상 문법이지만, 무조건 “짧아서 좋은 문법”으로 이해하면 안 된다.

이 모듈의 핵심은 다음이다.

```text
SELECT 결과 구조가 Internal Table 타입을 결정한다.
@DATA(...)는 결과를 받는 변수를 그 자리에서 선언한다.
INTO TABLE @DATA(...)는 빠른 조회·검증·단순 처리에는 매우 유용하다.
하지만 Key, Table Category, 재사용 타입, 인터페이스 안정성이 중요한 경우에는 명시적 타입 선언이 더 적절할 수 있다.
```

## 2. 선수 지식

이 모듈을 이해하려면 다음 개념이 필요하다.

| 선수 개념 | 필요한 이유 |
|---|---|
| Internal Table | `INTO TABLE`의 결과가 Internal Table이기 때문이다. |
| Work Area | 단일 행 조회와 다중 행 조회의 차이를 비교하기 위해 필요하다. |
| SELECT 기본 구조 | FROM, FIELDS, WHERE, INTO의 위치를 이해해야 한다. |
| Host Variable `@` | Modern ABAP SQL에서 ABAP 변수와 SQL 필드를 구분해야 한다. |
| Inline Declaration | `DATA(...)`가 변수 선언이라는 점을 이해해야 한다. |

초급자는 다음 문장을 먼저 기억한다.

```text
INTO TABLE @DATA(lt_result)는 SELECT 결과를 담을 Internal Table을 SELECT 문 안에서 바로 만드는 문법이다.
```

## 3. Classic 방식과 Modern Inline Target 비교

### 3.1 Classic 방식

기존 방식에서는 SELECT 결과를 받을 Internal Table 타입을 먼저 선언한다.

```abap
TYPES: BEGIN OF ty_flight,
         carrid TYPE sflight-carrid,
         connid TYPE sflight-connid,
         fldate TYPE sflight-fldate,
         price  TYPE sflight-price,
       END OF ty_flight.

DATA lt_flight TYPE STANDARD TABLE OF ty_flight.

SELECT carrid
       connid
       fldate
       price
  FROM sflight
  INTO TABLE lt_flight
  WHERE carrid = 'LH'.
```

이 방식은 명시적이다.  
`LT_FLIGHT`가 어떤 구조인지 코드 위쪽에서 바로 확인할 수 있다. 그러나 단순 조회 예제에서는 선언부가 길어질 수 있다.

### 3.2 Modern Inline Target 방식

Modern ABAP SQL에서는 다음처럼 쓸 수 있다.

```abap
SELECT FROM sflight
  FIELDS carrid,
         connid,
         fldate,
         price
  WHERE carrid = 'LH'
  INTO TABLE @DATA(lt_flight).
```

여기서 `lt_flight`는 SELECT 결과 필드에 맞춰 자동으로 선언된다.

```text
SELECT list:
  carrid, connid, fldate, price

자동 추론 결과:
  lt_flight = 해당 필드들로 구성된 Internal Table
```

### 3.3 핵심 차이

| 구분 | Classic 명시 선언 | `INTO TABLE @DATA(...)` |
|---|---|---|
| 선언 위치 | SELECT 이전 | SELECT 문 안 |
| 타입 정의 | 개발자가 명시 | SELECT 결과에서 추론 |
| 코드 길이 | 길어질 수 있음 | 짧고 빠름 |
| 재사용성 | 높음 | 해당 Scope 중심 |
| Table Key 제어 | 명시 가능 | 기본 추론에 의존 |
| 교육 효과 | 타입 구조 이해에 좋음 | Modern SQL 패턴 이해에 좋음 |
| 실무 적합성 | 인터페이스/공용 타입에 적합 | 단순 조회/로컬 처리에 적합 |

## 4. `@DATA(...)`의 정확한 의미

`@DATA(...)`는 단순한 약어가 아니라 Inline Declaration이다.  
즉, 변수를 사용하는 위치에서 동시에 선언한다.

```abap
INTO TABLE @DATA(lt_result)
```

위 구문은 다음 의미를 가진다.

```text
SELECT 결과를 받을 Internal Table lt_result를 이 자리에서 선언한다.
그 타입은 SELECT 결과 필드 목록을 기준으로 컴파일러가 추론한다.
```

여기서 `@`는 ABAP SQL 안에서 ABAP 영역의 선언/변수를 사용한다는 표시이다.  
`DATA(...)`는 ABAP의 Inline Declaration 문법이다.

따라서 `@DATA(...)`는 다음 두 의미가 결합된 형태이다.

| 부분 | 의미 |
|---|---|
| `@` | ABAP SQL 내부에서 ABAP Host 영역을 명시 |
| `DATA(...)` | 변수를 해당 위치에서 선언 |

## 5. 기본 예제: 여러 건 조회

### 5.1 표준 Flight Model 기준 예제

[추정] 교육 시스템에 SAP Flight Model 테이블인 `SCARR`, `SPFLI`, `SFLIGHT`가 존재한다고 가정한다. 시스템에 해당 테이블이 없으면 고객사 교육용 Z 테이블 또는 다른 표준 테이블로 대체한다.

```abap
REPORT zsql_inline_target_01.

SELECT FROM sflight
  FIELDS carrid,
         connid,
         fldate,
         price,
         currency
  WHERE carrid = 'LH'
  INTO TABLE @DATA(lt_flight).

IF sy-subrc = 0.
  WRITE: / '조회 건수:', lines( lt_flight ).

  LOOP AT lt_flight INTO DATA(ls_flight).
    WRITE: / ls_flight-carrid,
             ls_flight-connid,
             ls_flight-fldate,
             ls_flight-price,
             ls_flight-currency.
  ENDLOOP.
ELSE.
  WRITE: / '조회 결과가 없습니다.'.
ENDIF.
```

### 5.2 코드 해설

| 코드 | 의미 |
|---|---|
| `SELECT FROM sflight` | `SFLIGHT` 테이블에서 조회 |
| `FIELDS ...` | 결과에 포함할 필드를 명시 |
| `WHERE carrid = 'LH'` | 항공사 코드가 LH인 데이터만 조회 |
| `INTO TABLE @DATA(lt_flight)` | 결과 Internal Table을 Inline으로 선언 |
| `lines( lt_flight )` | Internal Table 행 수 확인 |
| `LOOP AT lt_flight INTO DATA(ls_flight)` | 결과 테이블을 한 줄씩 처리 |

여기서 `lt_flight`는 SELECT 문 실행 후 사용할 수 있는 Internal Table이다.  
`ls_flight` 역시 LOOP 문 안에서 Inline으로 선언한 Work Area이다.

## 6. Inline Target의 타입 추론

`INTO TABLE @DATA(lt_result)`에서 가장 중요한 개념은 타입 추론이다.

### 6.1 SELECT 필드가 타입을 결정한다

다음 SELECT를 보자.

```abap
SELECT FROM scarr
  FIELDS carrid,
         carrname
  INTO TABLE @DATA(lt_carrier).
```

이때 `lt_carrier`의 한 줄 구조는 다음과 유사하게 추론된다.

```abap
TYPES: BEGIN OF ty_carrier,
         carrid   TYPE scarr-carrid,
         carrname TYPE scarr-carrname,
       END OF ty_carrier.

DATA lt_carrier TYPE STANDARD TABLE OF ty_carrier.
```

실제 코드는 컴파일러가 생성/추론하므로 개발자가 직접 위 선언을 쓰지는 않는다.  
하지만 초급자는 머릿속으로 “SELECT list가 Internal Table의 Line Type이 된다”고 이해하면 된다.

### 6.2 Alias가 필드명을 결정할 수 있다

다음처럼 Alias를 사용할 수 있다.

```abap
SELECT FROM scarr
  FIELDS carrid   AS carrier_id,
         carrname AS carrier_name
  INTO TABLE @DATA(lt_carrier).
```

이 경우 결과 구조의 Component 이름은 `carrier_id`, `carrier_name`이 된다.

```abap
LOOP AT lt_carrier INTO DATA(ls_carrier).
  WRITE: / ls_carrier-carrier_id,
           ls_carrier-carrier_name.
ENDLOOP.
```

Alias는 단순히 보기 좋게 이름을 바꾸는 기능이 아니다.  
후속 코드에서 접근하는 Component 이름이 달라지므로, 명확하고 일관된 이름을 사용해야 한다.

## 7. `SELECT *`와 Inline Target

`@DATA(...)`는 `SELECT *`와도 함께 사용할 수 있다.

```abap
SELECT FROM scarr
  FIELDS *
  INTO TABLE @DATA(lt_scarr).
```

또는 구문 스타일에 따라 다음과 같이 작성할 수도 있다.

```abap
SELECT *
  FROM scarr
  INTO TABLE @DATA(lt_scarr).
```

이 경우 `lt_scarr`의 Line Type은 `SCARR` 테이블의 전체 행 구조와 유사하게 결정된다.

하지만 실무에서는 `SELECT *`를 습관적으로 사용하는 것은 권장되지 않는다.

### 7.1 `SELECT *`를 조심해야 하는 이유

| 이유 | 설명 |
|---|---|
| 불필요한 데이터 전송 | 필요한 필드보다 많은 데이터를 DB에서 가져올 수 있다. |
| 의도 불명확 | 어떤 필드가 필요한지 코드만 보고 파악하기 어렵다. |
| 구조 변경 영향 | 테이블 필드가 추가되면 결과 구조도 바뀔 수 있다. |
| 성능 분석 어려움 | 필요한 Projection이 명확하지 않다. |

초급 교육에서는 `SELECT *`가 이해를 쉽게 할 수 있지만, 실무 코드에서는 필요한 필드를 명시하는 습관이 좋다.

## 8. 단일 행 조회와 `@DATA(...)`

### 8.1 단일 Work Area로 조회

다중 행 조회에서는 `INTO TABLE`을 사용한다.  
단일 행 조회에서는 `INTO @DATA(...)`를 사용할 수 있다.

```abap
SELECT SINGLE FROM scarr
  FIELDS carrid,
         carrname,
         currcode
  WHERE carrid = 'LH'
  INTO @DATA(ls_carrier).
```

이 경우 `ls_carrier`는 Internal Table이 아니라 단일 구조 변수이다.

| 구문 | 결과 변수 |
|---|---|
| `INTO TABLE @DATA(lt_result)` | Internal Table |
| `INTO @DATA(ls_result)` | 단일 Work Area 또는 단일 값 구조 |
| `INTO @DATA(lv_value)` | 단일 컬럼이면 Scalar 변수 |

### 8.2 단일 컬럼 조회

```abap
SELECT SINGLE FROM scarr
  FIELDS carrname
  WHERE carrid = 'LH'
  INTO @DATA(lv_carrname).
```

이 경우 `lv_carrname`은 `SCARR-CARRNAME`에 맞는 단일 변수로 추론된다.

## 9. `INTO TABLE @DATA(...)`와 `APPENDING TABLE`

`INTO TABLE`은 결과 Internal Table을 새로 채우는 방식이다.  
기존 데이터를 유지하면서 뒤에 추가하려면 `APPENDING TABLE`을 사용한다.

```abap
SELECT FROM sflight
  FIELDS carrid,
         connid,
         fldate
  WHERE carrid = 'LH'
  INTO TABLE @DATA(lt_flight).

SELECT FROM sflight
  FIELDS carrid,
         connid,
         fldate
  WHERE carrid = 'AA'
  APPENDING TABLE @lt_flight.
```

주의할 점은 두 번째 SELECT에서 `lt_flight`는 이미 선언된 변수이다.  
따라서 `@DATA(lt_flight)`가 아니라 `@lt_flight`를 사용한다.

```text
첫 번째 SELECT:
  INTO TABLE @DATA(lt_flight)
  → 선언 + 데이터 입력

두 번째 SELECT:
  APPENDING TABLE @lt_flight
  → 기존 변수에 추가
```

단, 실무에서는 같은 구조의 데이터를 여러 번 SELECT로 나눠 가져오기보다, 가능한 경우 WHERE 조건을 정리하여 한 번의 SELECT로 가져오는 것이 더 적절할 수 있다.

예:

```abap
SELECT FROM sflight
  FIELDS carrid,
         connid,
         fldate
  WHERE carrid IN ( 'LH', 'AA' )
  INTO TABLE @DATA(lt_flight).
```

## 10. `ORDER BY`와 Inline Target

Inline Target은 결과를 받는 방식일 뿐이며, 정렬 보장은 별도 문제이다.  
정렬된 결과가 필요하면 SQL에서 `ORDER BY`를 명시해야 한다.

```abap
SELECT FROM sflight
  FIELDS carrid,
         connid,
         fldate,
         price
  WHERE carrid = 'LH'
  ORDER BY connid,
           fldate
  INTO TABLE @DATA(lt_flight).
```

### 10.1 왜 `ORDER BY`가 필요한가?

DB에서 조회한 결과는 명시적인 정렬 조건이 없으면 개발자가 기대하는 순서와 다를 수 있다.  
테스트 시스템에서 우연히 정렬되어 보였다고 해서 운영 시스템에서도 항상 같다고 가정하면 안 된다.

초급자는 다음 원칙을 기억한다.

```text
조회 결과의 순서가 중요하면 ORDER BY를 명시한다.
```

## 11. 중복 제거와 Inline Target

중복 없는 결과가 필요하면 `DISTINCT`를 사용할 수 있다.

```abap
SELECT DISTINCT FROM sflight
  FIELDS carrid
  INTO TABLE @DATA(lt_carrid).
```

이 경우 `lt_carrid`는 `carrid` 한 필드를 가진 Internal Table로 추론된다.

단, `DISTINCT`는 DB에서 중복 제거를 수행하므로 결과의 의미와 성능을 함께 고려해야 한다.  
중복 제거가 필요한 이유가 명확할 때만 사용한다.

## 12. 집계 결과와 Inline Target

Inline Target은 집계 결과에도 사용할 수 있다.

```abap
SELECT FROM sflight
  FIELDS carrid,
         COUNT( * ) AS flight_count,
         SUM( price ) AS total_price
  GROUP BY carrid
  INTO TABLE @DATA(lt_summary).
```

이때 `lt_summary`의 Line Type은 다음과 같은 구조로 추론된다.

```text
carrid
flight_count
total_price
```

집계 함수 결과는 원래 테이블 필드와 타입이 다를 수 있다.  
따라서 후속 코드에서 금액, 수량, 정수, Packed Number 타입을 다룰 때는 타입 추론 결과를 확인하는 습관이 필요하다.

---

## 13. Inline Target의 장점

### 13.1 코드가 짧아진다

명시적 TYPES와 DATA 선언 없이 바로 SELECT 결과를 받을 수 있다.

```abap
SELECT FROM scarr
  FIELDS carrid,
         carrname
  INTO TABLE @DATA(lt_scarr).
```

이것만으로 결과 테이블이 생성된다.

### 13.2 SELECT 결과와 타입이 자연스럽게 맞는다

SELECT list를 변경하면 Inline Target의 타입도 함께 바뀐다.

예를 들어 `currcode`를 추가하면 다음처럼 결과 구조도 확장된다.

```abap
SELECT FROM scarr
  FIELDS carrid,
         carrname,
         currcode
  INTO TABLE @DATA(lt_scarr).
```

### 13.3 테스트와 탐색에 적합하다

초기 개발이나 데이터 확인 단계에서는 매우 빠르게 코드를 작성할 수 있다.

```abap
SELECT FROM mara
  FIELDS matnr,
         mtart,
         matkl
  UP TO 20 ROWS
  INTO TABLE @DATA(lt_material).
```

### 13.4 로컬 처리 흐름이 명확해진다

결과가 해당 SELECT 주변에서만 사용된다면 Inline Target은 오히려 가독성을 높인다.

```abap
SELECT FROM scarr
  FIELDS carrid,
         carrname
  INTO TABLE @DATA(lt_carrier).

LOOP AT lt_carrier INTO DATA(ls_carrier).
  WRITE: / ls_carrier-carrid, ls_carrier-carrname.
ENDLOOP.
```

## 14. Inline Target의 한계

`INTO TABLE @DATA(...)`는 편리하지만 모든 상황에서 최선은 아니다.

### 14.1 Table Category와 Key를 직접 통제하기 어렵다

Inline으로 선언된 Internal Table은 개발자가 `SORTED TABLE`, `HASHED TABLE`, `UNIQUE KEY` 같은 속성을 명시적으로 지정하지 않는다.  
따라서 대량 데이터 조회 후 Key 기반 접근이 중요하다면 명시적 선언이 더 적절할 수 있다.

예를 들어 다음처럼 자주 Key로 읽어야 한다면:

```abap
READ TABLE lt_flight WITH KEY carrid = 'LH' connid = '0400' INTO DATA(ls_flight).
```

대량 데이터에서는 명시적인 Sorted/Hashed Table 설계를 검토해야 한다.

```abap
TYPES tt_flight TYPE SORTED TABLE OF ty_flight
  WITH NON-UNIQUE KEY carrid connid.

DATA lt_flight TYPE tt_flight.
```

### 14.2 공용 인터페이스 타입에는 부적합할 수 있다

Method의 Exporting Parameter, Function Module Interface, Public API, 테스트 더블 등에서는 타입을 명시하는 것이 안정적이다.

```abap
METHODS get_flights
  RETURNING VALUE(rt_flight) TYPE ztt_flight.
```

이런 곳에서는 Inline Target보다 DDIC Table Type 또는 명시적 TYPES가 더 좋다.

### 14.3 타입이 코드 아래쪽에서만 보일 수 있다

Inline Target은 선언이 SELECT 문 안에 있으므로, 큰 메서드에서는 변수가 어디서 선언되었는지 찾기 어려울 수 있다.  
이 문제는 메서드를 짧게 유지하고, 변수 사용 범위를 좁히면 줄일 수 있다.

### 14.4 SELECT list 변경이 후속 코드에 영향을 준다

다음 코드는 정상이다.

```abap
SELECT FROM scarr
  FIELDS carrid,
         carrname
  INTO TABLE @DATA(lt_carrier).

LOOP AT lt_carrier INTO DATA(ls_carrier).
  WRITE: / ls_carrier-carrid,
           ls_carrier-carrname.
ENDLOOP.
```

그런데 SELECT list에서 `carrname`을 제거하면 후속 코드가 오류가 된다.

```abap
SELECT FROM scarr
  FIELDS carrid
  INTO TABLE @DATA(lt_carrier).

LOOP AT lt_carrier INTO DATA(ls_carrier).
  WRITE: / ls_carrier-carrname. " 오류 가능
ENDLOOP.
```

즉, Inline Target은 SELECT list와 후속 코드의 결합이 강하다.  
이것은 장점이면서 동시에 주의점이다.

## 15. 언제 Inline Target을 사용하면 좋은가?

### 15.1 적합한 경우

| 상황 | 이유 |
|---|---|
| 단순 조회 후 바로 처리 | 타입 선언이 불필요하게 길어지는 것을 줄인다. |
| 로컬 메서드 내부 임시 결과 | 변수 Scope가 좁고 의도가 명확하다. |
| 실습·검증·프로토타이핑 | 빠르게 SQL 결과를 확인할 수 있다. |
| SELECT list가 간단함 | 타입 추론 결과를 쉽게 이해할 수 있다. |
| 조회 결과를 다른 공용 인터페이스로 노출하지 않음 | 타입 안정성 문제가 작다. |

### 15.2 명시적 선언이 더 좋은 경우

| 상황 | 이유 |
|---|---|
| 공용 Method/Function Interface | 타입 계약이 명확해야 한다. |
| 대량 데이터 Key 접근 | Sorted/Hashed Table 설계가 필요할 수 있다. |
| 여러 메서드에서 같은 타입 재사용 | DDIC Table Type 또는 TYPES가 적절하다. |
| 테스트 코드와 운영 코드가 같은 타입 계약을 공유 | 명시적 타입이 유지보수에 유리하다. |
| 결과 구조가 복잡함 | Inline 타입 추론만으로는 의도 파악이 어려울 수 있다. |

## 16. 실무 예제: Carrier 조회

### 16.1 요구사항

항공사 마스터에서 항공사 코드와 이름을 조회하여 출력한다.

```text
입력: 없음
처리: SCARR에서 CARRID, CARRNAME, CURRCODE 조회
출력: 항공사 코드, 항공사명, 통화키
오류 케이스: 데이터가 없으면 메시지 출력
```

### 16.2 Modern SQL 예제

```abap
REPORT zsql_inline_target_02.

SELECT FROM scarr
  FIELDS carrid,
         carrname,
         currcode
  ORDER BY carrid
  INTO TABLE @DATA(lt_carrier).

IF lt_carrier IS INITIAL.
  WRITE: / '항공사 데이터가 없습니다.'.
  RETURN.
ENDIF.

LOOP AT lt_carrier INTO DATA(ls_carrier).
  WRITE: / ls_carrier-carrid,
           ls_carrier-carrname,
           ls_carrier-currcode.
ENDLOOP.
```

### 16.3 검증 포인트

| 검증 항목 | 확인 방법 |
|---|---|
| Syntax Check | `@DATA` 위치가 올바른지 확인 |
| 데이터 존재 | `LT_CARRIER IS INITIAL` 확인 |
| 결과 필드 접근 | `LS_CARRIER-CARRID` 등 Component 접근 가능 여부 확인 |

| 출력 | WRITE 리스트에 정상 표시되는지 확인 |

## 17. 실무 예제: WHERE 조건과 Host Variable 결합

`@DATA(...)`는 Host Variable과 함께 자주 사용된다.

```abap
REPORT zsql_inline_target_03.

PARAMETERS p_carrid TYPE scarr-carrid DEFAULT 'LH'.

SELECT FROM sflight
  FIELDS carrid,
         connid,
         fldate,
         price,
         currency
  WHERE carrid = @p_carrid
  ORDER BY connid,
           fldate
  INTO TABLE @DATA(lt_flight).

IF sy-subrc <> 0.
  WRITE: / '조회 결과가 없습니다:', p_carrid.
  RETURN.
ENDIF.

LOOP AT lt_flight INTO DATA(ls_flight).
  WRITE: / ls_flight-carrid,
           ls_flight-connid,
           ls_flight-fldate,
           ls_flight-price,
           ls_flight-currency.
ENDLOOP.
```

여기서 두 가지 `@` 사용이 나온다.

| 구문 | 의미 |
|---|---|
| `@p_carrid` | ABAP Host Variable을 SQL 조건에 전달 |
| `@DATA(lt_flight)` | SELECT 결과를 받을 Internal Table을 Inline 선언 |

초급자는 이 둘을 혼동하지 않아야 한다.

## 18. ADT ClassRun 예제

SAP GUI Report 방식도 교육에 유용하지만, ADT 기반 학습에서는 `IF_OO_ADT_CLASSRUN`을 사용할 수 있다.

```abap
CLASS zcl_sql_inline_target DEFINITION
  PUBLIC
  FINAL
  CREATE PUBLIC.

  PUBLIC SECTION.
    INTERFACES if_oo_adt_classrun.
ENDCLASS.

CLASS zcl_sql_inline_target IMPLEMENTATION.
  METHOD if_oo_adt_classrun~main.

    SELECT FROM scarr
      FIELDS carrid,
             carrname,

  ENDMETHOD.
ENDCLASS.
```

이 예제에서 `out->write( lt_carrier )`는 ADT Console에서 Internal Table 내용을 확인하는 데 유용하다.

> [추정] 교육 시스템의 ADT 버전과 권한에 따라 ClassRun 생성 및 실행 방식은 다를 수 있다. SAP GUI 중심 수업에서는 Report 예제를 우선 사용해도 된다.

## 19. 오류 상황과 해결

### 19.1 `@` 누락

#### 오류 예

```abap
SELECT FROM scarr
  FIELDS carrid,
         carrname
  INTO TABLE DATA(lt_carrier).
```

#### 문제

Modern ABAP SQL에서 ABAP Host 영역의 Inline Declaration을 SQL 문 안에서 사용할 때는 `@DATA(...)` 형태가 필요하다.

#### 해결

```abap
SELECT FROM scarr
  FIELDS carrid,
         carrname
  INTO TABLE @DATA(lt_carrier).
```

### 19.2 같은 Scope에서 같은 이름 재선언

#### 오류 예

```abap
SELECT FROM scarr
  FIELDS carrid
  INTO TABLE @DATA(lt_result).

SELECT FROM spfli
  FIELDS carrid,
         connid
  INTO TABLE @DATA(lt_result).
```

#### 문제

같은 Scope에서 `lt_result`를 두 번 Inline 선언하려고 하면 이름 충돌이 발생할 수 있다.

#### 해결

이름을 다르게 하거나, 두 번째 SELECT는 기존 변수를 사용한다.

```abap
SELECT FROM scarr
  FIELDS carrid
  INTO TABLE @DATA(lt_carrier).

SELECT FROM spfli
  FIELDS carrid,
         connid
  INTO TABLE @DATA(lt_connection).
```

### 19.3 SELECT 결과 필드와 후속 코드 불일치

#### 오류 예

```abap
SELECT FROM scarr
  FIELDS carrid
  INTO TABLE @DATA(lt_carrier).

LOOP AT lt_carrier INTO DATA(ls_carrier).
  WRITE: / ls_carrier-carrname.
ENDLOOP.
```

#### 문제

SELECT list에 `carrname`이 없으므로 결과 구조에도 `carrname` Component가 없다.

#### 해결

필요한 필드를 SELECT list에 포함한다.

```abap
SELECT FROM scarr
  FIELDS carrid,
         carrname
  INTO TABLE @DATA(lt_carrier).
```

### 19.4 Inline Target으로 만들어진 테이블의 Key를 과신

#### 상황

Inline Target으로 만든 Internal Table을 대량 데이터에서 반복적으로 Key 검색한다.

```abap
READ TABLE lt_flight INTO DATA(ls_flight)
  WITH KEY carrid = 'LH'
           connid = '0400'.
```

#### 문제

Inline으로 만든 테이블의 Key 설계를 개발자가 명시하지 않았기 때문에, 대량 데이터의 반복 검색에서 성능상 불리할 수 있다.

#### 해결

대량 데이터에서 Key 기반 접근이 핵심이면 명시적인 Table Type을 정의한다.

```abap
TYPES: BEGIN OF ty_flight,
         carrid TYPE sflight-carrid,
         connid TYPE sflight-connid,
         fldate TYPE sflight-fldate,
       END OF ty_flight.

TYPES tt_flight TYPE SORTED TABLE OF ty_flight
  WITH NON-UNIQUE KEY carrid connid.

DATA lt_flight TYPE tt_flight.

SELECT FROM sflight
  FIELDS carrid,
         connid,
         fldate
  WHERE carrid = 'LH'
  INTO TABLE @lt_flight.
```

## 20. `sy-subrc`와 Inline Target

SELECT 후에는 기존 방식처럼 `sy-subrc`를 확인할 수 있다.

```abap
SELECT FROM scarr
  FIELDS carrid,
         carrname
  WHERE carrid = 'ZZ'
  INTO TABLE @DATA(lt_carrier).

IF sy-subrc <> 0.
  WRITE: / '조회된 데이터가 없습니다.'.
ENDIF.
```

다만 Internal Table 조회에서는 다음 방식도 자주 사용한다.

```abap
IF lt_carrier IS INITIAL.
  WRITE: / '조회된 데이터가 없습니다.'.
ENDIF.
```

### 20.1 어떤 방식을 사용할까?

| 방식 | 장점 | 주의점 |
|---|---|---|
| `sy-subrc` | SELECT 직후 상태 확인에 익숙함 | SELECT 직후가 아니면 값이 바뀔 수 있음 |
| `itab IS INITIAL` | 결과 테이블 자체를 확인 | 테이블이 비어 있는지 여부만 판단 |

실무에서는 SELECT 직후에는 `sy-subrc`를 볼 수 있고, 이후 로직에서는 Internal Table 상태 자체를 확인하는 방식이 더 읽기 쉽다.

## 21. Clean Code 관점

### 21.1 좋은 예

```abap
SELECT FROM scarr
  FIELDS carrid,
         carrname,
         currcode
  ORDER BY carrid
  INTO TABLE @DATA(lt_carrier).

IF lt_carrier IS INITIAL.
  RETURN.
ENDIF.
```

좋은 이유:

- 필요한 필드만 조회한다.
- 결과 이름이 의미 있다.
- 정렬이 필요한 경우 `ORDER BY`를 명시한다.
- 결과 없음 처리를 한다.

### 21.2 나쁜 예

```abap
SELECT *
  FROM scarr
  INTO TABLE @DATA(lt_data).

LOOP AT lt_data INTO DATA(ls_data).
  WRITE: / ls_data-carrid.
ENDLOOP.
```

나쁜 이유:

- `SELECT *`로 불필요한 필드까지 조회할 수 있다.
- `lt_data`, `ls_data`처럼 이름이 모호하다.
- 어떤 목적의 데이터인지 이름만 보고 알기 어렵다.

### 21.3 개선 예

```abap
SELECT FROM scarr
  FIELDS carrid,
         carrname
  ORDER BY carrid
  INTO TABLE @DATA(lt_carrier).

LOOP AT lt_carrier INTO DATA(ls_carrier).
  WRITE: / ls_carrier-carrid,
           ls_carrier-carrname.
ENDLOOP.
```

## 25. 평가 문제

### 25.1 객관식

#### Q1. `INTO TABLE @DATA(lt_carrier)`에 대한 설명으로 가장 적절한 것은?

A. 이미 선언된 Internal Table에만 데이터를 넣는 문법이다.  
B. SELECT 결과를 받을 Internal Table을 해당 위치에서 Inline으로 선언한다.  
C. SELECT 결과를 데이터베이스 테이블로 생성한다.  
D. ABAP SQL에서 Host Variable을 사용할 수 없게 만든다.

**정답:** B

#### Q2. 다음 중 단일 행 결과를 받는 구문으로 더 적절한 것은?

A. `INTO TABLE @DATA(lt_result)`  
B. `INTO @DATA(ls_result)`  
C. `APPENDING TABLE @DATA(lt_result)`  
D. `GROUP BY @DATA(ls_result)`

**정답:** B

#### Q3. Inline Target 사용 시 주의할 점으로 가장 적절한 것은?

A. 무조건 모든 테이블을 Hashed Table로 만든다.  
B. 결과 구조와 Key를 항상 명시적으로 설계할 수 있다.  
C. SELECT list가 바뀌면 결과 구조와 후속 코드도 영향을 받을 수 있다.  
D. 반드시 `SELECT *`와 함께 사용해야 한다.

**정답:** C

### 25.2 단답형

#### Q1. `@DATA(...)`에서 `@`와 `DATA(...)`의 의미를 각각 설명하시오.

**모범 답안:**  
`@`는 ABAP SQL 내부에서 ABAP Host 영역의 변수 또는 선언을 사용한다는 표시이다. `DATA(...)`는 해당 위치에서 변수를 선언하는 Inline Declaration이다.

#### Q2. Inline Target보다 명시적 타입 선언이 더 적절한 경우를 두 가지 쓰시오.

**모범 답안:**  
공용 Method/Function Interface에서 타입 계약이 필요한 경우, 대량 데이터에서 Sorted/Hashed Table Key 설계가 필요한 경우, 여러 프로그램이나 메서드에서 같은 타입을 재사용해야 하는 경우 등이 있다.

#### Q3. `SELECT FROM scarr FIELDS carrid AS carrier_id INTO TABLE @DATA(lt_carrier)` 이후 필드 접근은 어떻게 해야 하는가?

**모범 답안:**  
Alias를 사용했기 때문에 `ls_carrier-carrier_id` 형태로 접근해야 한다. 원래 필드명인 `carrid`가 결과 Component 이름으로 유지된다고 가정하면 안 된다.

## 26. 실무 요약

`INTO TABLE @DATA(...)`는 Modern ABAP SQL에서 매우 유용한 문법이다.  
특히 SELECT 결과를 로컬에서 바로 처리하는 경우 코드가 짧아지고, SELECT list와 결과 구조의 관계가 명확해진다.

그러나 실무에서는 다음 균형이 필요하다.

```text
단순 조회와 로컬 처리:
  INTO TABLE @DATA(...) 사용 적극 권장

공용 타입, 인터페이스, 대량 데이터 Key 접근:
  명시적 TYPES, DDIC Table Type, Sorted/Hashed Table 검토
```

이 모듈의 핵심 문장은 다음이다.

```text
Inline Target은 타입 선언을 없애는 문법이 아니라, SELECT 결과에 맞는 타입 선언을 그 자리에서 추론하게 하는 문법이다.
```

## 27. 다음 모듈 연결

다음 모듈은 `THEORY-17-M04 — SQL Expression: CASE / CAST / COALESCE`이다.

이번 모듈에서 SELECT 결과를 `@DATA(...)`로 받는 방법을 학습했다면, 다음 단계에서는 SELECT list 자체에서 값을 가공하는 방법을 배운다.

```text
THEORY-17-M03:
  SELECT 결과를 어디에 받을 것인가?

THEORY-17-M04:
  SELECT 결과를 만들 때 어떤 SQL Expression으로 가공할 것인가?
```

예를 들어 다음과 같은 흐름으로 확장된다.

```abap
SELECT FROM sflight
  FIELDS carrid,
         connid,
         CASE
           WHEN price > 1000 THEN 'HIGH'
           ELSE 'NORMAL'
         END AS price_level
  INTO TABLE @DATA(lt_result).
```

즉, `@DATA(...)`는 다음 모듈의 SQL Expression 결과를 받아들이는 기본 도구가 된다.
