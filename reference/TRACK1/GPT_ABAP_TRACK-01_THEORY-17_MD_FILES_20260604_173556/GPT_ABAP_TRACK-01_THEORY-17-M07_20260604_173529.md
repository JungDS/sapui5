## 3. Classic Open SQL과 Modern ABAP SQL 요약

### 3.1 Classic Open SQL의 특징

Classic Open SQL은 오랫동안 ABAP에서 데이터베이스를 읽고 쓰는 표준 방식이었다.

```abap
DATA: lt_sflight TYPE TABLE OF sflight.

SELECT *
  FROM sflight
  INTO TABLE lt_sflight
  WHERE carrid = 'AA'.
```

| 항목 | 설명 |
|---|---|
| 변수 선언 | SELECT 전에 별도 선언하는 경우가 많음 |
| Host Variable | `@` 없이 ABAP 변수 사용 |
| 결과 Target | 미리 선언한 Work Area 또는 Internal Table 사용 |
| 표현식 | 최신 문법보다 제한적 |
| 장점 | 기존 시스템과 레거시 코드에서 많이 사용 |
| 한계 | SQL 영역과 ABAP 영역의 경계가 덜 명확함 |

### 3.2 Modern ABAP SQL의 특징

Modern ABAP SQL은 문법적으로 SQL 영역과 ABAP 영역을 더 명확히 구분한다.

```abap
SELECT FROM sflight
       FIELDS carrid,
              connid,
              fldate,
              price,
              currency
       WHERE carrid = @p_carrid
       INTO TABLE @DATA(lt_flight).
```

| 항목 | 설명 |
|---|---|
| `FIELDS` | 조회 필드 목록을 명확히 표현 |
| `@` | Host Variable을 명시 |
| `@DATA(...)` | Inline Target 선언 |
| SQL Expression | `CASE`, `CAST`, `COALESCE` 등 사용 가능 |
| 가독성 | 데이터 소스, 필드, 조건, 결과가 명확함 |
| CDS 연결성 | CDS를 학습하기 위한 SQL 사고 기반 형성 |

### 3.3 핵심 변화

```text
ABAP 프로그램 안의 SQL을 더 명시적이고, 표현력 있고, DB 친화적으로 작성한다.
```

## 4. `@` Host Variable 정리

Modern ABAP SQL에서 `@`는 ABAP 변수 또는 ABAP 표현식을 SQL 문 안에서 사용할 때 붙인다.

```abap
PARAMETERS p_carrid TYPE s_carr_id.

SELECT FROM sflight
       FIELDS carrid,
              connid,
              fldate
       WHERE carrid = @p_carrid
       INTO TABLE @DATA(lt_flight).
```

여기서 `p_carrid`는 ABAP 프로그램의 변수이고, SQL 조건식 안에서 사용되므로 `@p_carrid`로 작성한다.

| 이유 | 설명 |
|---|---|
| 경계 명확화 | SQL 필드인지 ABAP 변수인지 구분한다. |
| 가독성 향상 | 조건식 안에서 외부 입력값이 무엇인지 즉시 보인다. |
| 문법 안정성 | 최신 ABAP SQL 문법에서 명시적 Host Variable 사용을 요구한다. |
| 학습 연결 | CDS, AMDP, SQLScript 등으로 확장될 때 영역 구분 감각을 만든다. |

초급자 오류:

```abap
WHERE carrid = p_carrid
```

올바른 작성:

```abap
WHERE carrid = @p_carrid
```

## 5. Inline Target 정리

Modern ABAP SQL에서는 결과 수신 변수를 SELECT 문 안에서 바로 선언할 수 있다.

```abap
SELECT FROM scarr
       FIELDS carrid,
              carrname,
              currcode
       INTO TABLE @DATA(lt_scarr).
```

| 장점 | 설명 |
|---|---|
| 코드 간결성 | 별도 `DATA lt_scarr ...` 선언이 줄어든다. |
| 타입 추론 | SELECT 결과에 맞는 Internal Table 타입이 추론된다. |
| 지역성 | 결과 변수가 사용 지점 근처에서 생성된다. |
| 유지보수 | 필드 변경 시 선언부와 SELECT 불일치가 줄어든다. |

Inline 선언이 항상 좋은 것은 아니다.

| 상황 | 권장 판단 |
|---|---|
| 결과 타입을 여러 메서드에서 재사용 | 명시적 TYPES 또는 DDIC 타입 고려 |
| 인터페이스 파라미터로 전달 | 구조 타입을 명확히 정의 |
| 교육 초급 단계 | Inline과 명시 선언을 모두 경험 |
| 대규모 프로그램 | 변수 스코프와 가독성 고려 |

## 6. SQL Expression 정리

Modern ABAP SQL은 DB 조회 단계에서 간단한 계산과 변환을 수행할 수 있다.

### 6.1 `CASE`

```abap
SELECT FROM sflight
       FIELDS carrid,
              connid,
              seatsmax,
              seatsocc,
              CASE
                WHEN seatsocc = 0 THEN 'EMPTY'
                WHEN seatsocc < seatsmax THEN 'AVAILABLE'
                ELSE 'FULL'
              END AS seat_status
       INTO TABLE @DATA(lt_result).
```

### 6.2 `CAST`

```abap
SELECT FROM sflight
       FIELDS carrid,
              connid,
              CAST( price AS DEC( 15, 2 ) ) AS price_cast
       INTO TABLE @DATA(lt_result).
```

### 6.3 `COALESCE`

```abap
SELECT FROM zt_demo
       FIELDS key_field,
              COALESCE( optional_text, 'N/A' ) AS display_text
       INTO TABLE @DATA(lt_result).
```

### 6.4 SQL Expression 사용 기준

| 사용해도 좋은 경우 | 주의해야 하는 경우 |
|---|---|
| 단순 분류 | 복잡한 업무 규칙 |
| 단순 형변환 | 의미가 바뀌는 강제 변환 |
| NULL 대체 | 데이터 품질 문제를 숨기는 대체 |
| 조회 결과 표시 보조 | 핵심 비즈니스 로직 대체 |

초급자는 다음 원칙을 기억한다.

```text
SQL Expression은 조회 결과를 단순하게 정리하는 데 적합하다.
복잡한 업무 판단은 별도 계층에서 설계해야 한다.
```

## 7. SQL Function 정리

문자열과 날짜 관련 SQL Function은 데이터 조회 시 표시값 또는 계산 기준을 만들 때 유용하다.

```abap
SELECT FROM scarr
       FIELDS carrid,
              carrname,
              upper( carrname ) AS carrname_upper
       INTO TABLE @DATA(lt_carrier).
```

문자열/날짜 함수 사용 기준은 다음과 같다.

| 사용 목적 | 적합성 |
|---|---|
| 표시용 대소문자 변환 | 적합 |
| 간단한 문자열 결합 | 적합 |
| 조회 조건용 날짜 계산 | 검토 가능 |
| 복잡한 캘린더/공장달력 계산 | 신중 |
| 업무 규칙이 들어간 기간 계산 | 별도 로직 검토 |

시스템별 ABAP 릴리스와 문법 지원 범위에 따라 사용 가능한 함수가 달라질 수 있으므로, 실무에서는 ABAP Keyword Documentation과 Syntax Check를 기준으로 확인한다.

## 8. `SELECT FROM @itab` 정리

`SELECT FROM @itab`은 ABAP Internal Table을 SQL 데이터 소스로 활용하는 문법이다.

```abap
DATA lt_filter TYPE STANDARD TABLE OF s_carr_id WITH EMPTY KEY.

lt_filter = VALUE #( ( 'AA' ) ( 'LH' ) ).

SELECT FROM sflight AS f
       INNER JOIN @lt_filter AS filter
         ON f~carrid = filter~table_line
       FIELDS f~carrid,
              f~connid,
              f~fldate
       INTO TABLE @DATA(lt_result).
```

| 주의점 | 설명 |
|---|---|
| Internal Table 크기 | 너무 큰 itab은 성능 문제를 유발할 수 있다. |
| Key 설계 | 조인 대상 itab 구조와 키를 명확히 한다. |
| DB 전송 비용 | itab 데이터가 SQL 처리에 사용되는 방식의 비용을 고려한다. |
| 대체 가능성 | CDS, 임시 테이블, RANGE 조건 등과 비교한다. |

초급자는 `SELECT FROM @itab`을 “Internal Table도 SQL 소스처럼 쓸 수 있다”로 이해하되, 대량 데이터 처리의 만능 도구로 생각하면 안 된다.

## 9. ABAP SQL과 CDS의 차이

### 9.1 ABAP SQL

ABAP SQL은 ABAP 프로그램 안에서 실행되는 데이터 접근 문장이다.

```abap
SELECT FROM zt_sales
       FIELDS sales_id,
              customer_id,
              amount
       WHERE customer_id = @p_customer
       INTO TABLE @DATA(lt_sales).
```

| 특징 | 설명 |
|---|---|
| 위치 | ABAP 프로그램 내부 |
| 목적 | 현재 프로그램에 필요한 데이터 조회 |
| 재사용성 | 해당 프로그램 중심 |
| 노출성 | 외부 소비 모델로 직접 노출되지는 않음 |
| 변경 영향 | 프로그램 단위로 영향 |
| 강점 | 빠른 구현, 로직과 조회의 밀접한 연결 |

### 9.2 CDS

CDS는 데이터 모델을 Repository 객체로 정의한다.

```abap
define view entity ZI_SalesSummary
  as select from zt_sales
{
  key sales_id,
      customer_id,
      amount
}
```

| 특징 | 설명 |
|---|---|
| 위치 | Repository 객체 |
| 목적 | 재사용 가능한 데이터 모델 정의 |
| 재사용성 | 여러 프로그램, 서비스, 분석, RAP에서 재사용 가능 |
| 노출성 | OData, RAP, Analytics 등과 연결 가능 |
| 변경 영향 | 소비자 전체에 영향 |
| 강점 | 모델 중심 개발, 의미 부여, 확장성 |

핵심 차이는 다음 한 문장으로 정리할 수 있다.

```text
ABAP SQL은 프로그램의 데이터 접근 문장이고,
CDS는 재사용 가능한 데이터 모델이다.
```

## 10. Pushdown Boundary란 무엇인가?

### 10.1 DB Pushdown의 의미

DB Pushdown은 가능한 처리를 ABAP Application Server가 아니라 Database에서 수행하도록 이동하는 사고방식이다.

전통적인 방식:

```text
DB에서 원천 데이터를 많이 읽음
→ ABAP Internal Table에서 LOOP 처리
→ 필터링, 계산, 집계
→ 결과 생성
```

Pushdown 방식:

```text
DB에서 필터링, 조인, 집계, 계산을 최대한 수행
→ ABAP은 필요한 결과만 받음
→ 후속 업무 처리
```

### 10.2 Pushdown이 중요한 이유

| 이유 | 설명 |
|---|---|
| 데이터 이동 감소 | 불필요한 대량 데이터를 Application Server로 가져오지 않는다. |
| DB 최적화 활용 | DB Optimizer와 HANA 처리 능력을 활용한다. |
| 코드 단순화 | ABAP LOOP 후처리가 줄어들 수 있다. |
| 재사용 가능성 | CDS로 모델링하면 여러 소비자가 같은 로직을 사용할 수 있다. |

### 10.3 Pushdown Boundary

Pushdown Boundary는 “어디까지 DB로 밀어넣고, 어디부터 ABAP에서 처리할 것인가”의 경계이다.

| DB/CDS에 적합 | ABAP에 적합 |
|---|---|
| 필터링 | 사용자 인터랙션 처리 |
| 조인 | 복잡한 절차적 예외 처리 |
| 집계 | 외부 API 호출 |
| 단순 계산 | 상태 변경이 많은 업무 절차 |
| CASE 기반 분류 | 메시지 처리와 화면 흐름 |
| 의미 있는 View 모델 | 트랜잭션 제어와 Commit 흐름 |

중요한 것은 “모든 것을 DB로 보내라”가 아니다.

```text
데이터량을 줄이는 처리는 DB/CDS로 보낸다.
업무 절차와 상태 제어는 ABAP 계층에 남긴다.
여러 소비자가 재사용할 데이터 의미는 CDS로 모델링한다.
한 프로그램에서만 필요한 단순 조회는 ABAP SQL로 충분할 수 있다.
```

## 11. ABAP SQL에 남겨도 좋은 것

다음과 같은 경우 ABAP SQL에 남겨도 충분하다.

| 상황 | 이유 |
|---|---|
| 한 프로그램에서만 사용하는 단순 조회 | Repository 모델로 만들 필요가 낮다. |
| 화면 입력값에 따라 임시로 바뀌는 조회 | 프로그램 흐름과 밀접하다. |
| 결과 구조가 재사용되지 않음 | CDS 객체 증가를 피할 수 있다. |
| 간단한 테스트/교육용 조회 | 학습과 검증에 적합하다. |
| 소량 데이터 조회 | 모델링 비용보다 직접 조회가 효율적일 수 있다. |

```abap
SELECT FROM scarr
       FIELDS carrid,
              carrname,
              currcode
       WHERE carrid = @p_carrid
       INTO TABLE @DATA(lt_carrier).
```

이 정도의 단순 조회를 무조건 CDS로 만드는 것은 과할 수 있다.

---

## 12. CDS로 넘기는 것이 좋은 것

다음 경우에는 CDS 모델링을 검토하는 것이 좋다.

| 상황 | 이유 |
|---|---|
| 여러 프로그램에서 같은 조인/계산을 반복 | 재사용 가능한 모델 필요 |
| 업무 의미를 데이터 모델에 부여해야 함 | Annotation, semantic modeling 가능 |
| RAP/Fiori/OData 노출 예정 | CDS가 기본 모델 역할 |
| 분석/집계 모델 필요 | DB Pushdown과 재사용성 확보 |
| 복잡한 Join을 여러 곳에서 사용 | 중복 SQL 제거 |
| 권한/접근 제어와 연결 필요 | CDS Access Control 등 후속 연결 가능 |

예를 들어 여러 리포트에서 같은 “판매오더 헤더 + 고객명 + 금액 합계”를 반복 조회한다면, 각 프로그램마다 SQL을 복사하는 것보다 CDS로 모델링하는 편이 좋다.

## 13. 판단 기준: ABAP SQL vs CDS

| 질문 | Yes라면 |
|---|---|
| 이 조회가 여러 프로그램에서 재사용되는가? | CDS 검토 |
| 이 데이터 모델이 OData/RAP/Fiori로 노출될 가능성이 있는가? | CDS 검토 |
| 단순한 프로그램 내부 조회인가? | ABAP SQL 가능 |
| 조인과 집계가 반복적으로 복사되고 있는가? | CDS 검토 |
| 사용자 입력에 따라 임시 결과만 필요한가? | ABAP SQL 가능 |
| 데이터 의미를 Annotation으로 표현해야 하는가? | CDS 검토 |
| 복잡한 절차적 판단이나 메시지 처리가 필요한가? | ABAP 처리 적합 |

한 문장으로 정리하면 다음이다.

```text
재사용 가능한 데이터 의미는 CDS,
프로그램 내부의 일회성 데이터 접근은 ABAP SQL.
```

## 14. 안티패턴 정리

### 14.1 ABAP 후처리 남발

나쁜 예:

```abap
SELECT FROM zt_sales
       FIELDS *
       INTO TABLE @DATA(lt_sales).

LOOP AT lt_sales INTO DATA(ls_sales).
  IF ls_sales-status <> 'A'.
    DELETE lt_sales.
  ENDIF.
ENDLOOP.
```

문제:

- DB에서 불필요한 데이터를 많이 가져온다.
- ABAP 메모리와 네트워크 비용이 증가한다.
- 필터 조건이 SQL로 표현 가능한데 후처리로 밀렸다.

개선 예:

```abap
SELECT FROM zt_sales
       FIELDS sales_id,
              customer_id,
              amount,
              status
       WHERE status = 'A'
       INTO TABLE @DATA(lt_sales).
```

### 14.2 `SELECT *` 남용

| 문제 | 설명 |
|---|---|
| 불필요한 컬럼 조회 | 네트워크와 메모리 낭비 |
| 구조 변경 영향 | 테이블 필드 추가 시 불필요한 영향 |
| 가독성 저하 | 실제 필요한 필드를 알기 어렵다 |
| 성능 분석 어려움 | 조회 의도가 불명확하다 |

개선:

```abap
SELECT FROM zt_sales
       FIELDS sales_id,
              customer_id,
              amount
       INTO TABLE @DATA(lt_sales).
```

### 14.3 CDS 과잉 모델링

모든 SELECT를 CDS로 바꾸는 것도 좋은 설계가 아니다.

문제:

- Repository 객체가 불필요하게 늘어난다.
- 이름 관리가 어려워진다.
- 한 번만 쓰는 조회를 별도 모델로 만들면 유지보수 비용이 증가한다.
- 학습 초급자에게 모델 계층이 과도하게 복잡해질 수 있다.

기준:

```text
한 프로그램에서만 쓰는 단순 조회는 ABAP SQL로 충분할 수 있다.
반복 조회, 서비스 노출, 의미 모델링이 필요한 경우 CDS를 검토한다.
```

### 14.4 DB Pushdown 만능주의

Pushdown은 중요하지만 모든 로직을 DB로 보내는 것이 정답은 아니다.

DB에 적합하지 않은 예:

- 사용자별 메시지 생성
- 화면 상태 제어
- 외부 시스템 호출
- 복잡한 트랜잭션 단계 제어
- Commit/Rollback이 얽힌 업무 절차
- 디버깅과 예외 처리가 매우 중요한 절차 로직

이런 로직은 ABAP Application Layer에서 명확히 관리하는 편이 좋다.

## 15. 초급자용 의사결정 흐름도

```text
1. 데이터가 필요한가?
   ↓
2. 단일 프로그램 안에서만 쓰는가?
   ├─ Yes → ABAP SQL 우선 검토

   ├─ Yes → CDS 기반 모델링 검토
   └─ No  → ABAP SQL 가능
   ↓
5. 대량 데이터를 ABAP으로 가져와 LOOP 처리하고 있는가?
   ├─ Yes → SQL/CDS Pushdown 검토
   └─ No  → 현재 구조 유지 가능
```

## 16. 실습: ABAP SQL에서 CDS 후보 찾기

### 16.1 실습 목표

기존 ABAP SQL 코드를 보고 CDS로 이동할 후보와 ABAP에 남길 로직을 구분한다.

### 16.2 예제 코드

```abap
SELECT FROM zt_order AS o
       INNER JOIN zt_customer AS c
         ON o~customer_id = c~customer_id
       FIELDS o~order_id,
              o~customer_id,
              c~customer_name,
              o~order_date,
              o~net_amount,
              o~currency,
              CASE
                WHEN o~net_amount >= 1000000 THEN 'HIGH'
                WHEN o~net_amount >= 100000  THEN 'MID'
                ELSE 'LOW'
              END AS amount_level
       WHERE o~order_date BETWEEN @p_date_from AND @p_date_to
       INTO TABLE @DATA(lt_order).
```

### 16.3 분석 질문

| 질문 | 판단 |
|---|---|
| 이 Join이 여러 프로그램에서 반복되는가? | 반복된다면 CDS 후보 |
| `amount_level` 분류가 공통 업무 의미인가? | 공통이면 CDS 후보 |
| 날짜 조건은 화면 입력값인가? | ABAP SQL 또는 CDS Parameter 검토 |
| 결과가 Fiori/RAP로 노출될 가능성이 있는가? | 가능성이 있으면 CDS 후보 |
| 단일 리포트만 사용하는 임시 조회인가? | ABAP SQL 유지 가능 |

### 16.4 가능한 판단

이 조회가 여러 리포트에서 반복되고 Fiori 조회 화면으로도 확장될 가능성이 있다면 다음처럼 분리할 수 있다.

```text
CDS:
- 주문 + 고객 조인
- 금액 등급 amount_level
- 기본 표시 필드

ABAP SQL:
- 사용자 입력 날짜 조건 적용
- 특정 리포트에서만 필요한 추가 필터
- 화면 출력 전 최종 가공
```

## 18. CDS 학습으로 넘어갈 때의 관점 변화

ABAP SQL에서 CDS로 넘어갈 때 가장 큰 변화는 “문장 중심”에서 “모델 중심”으로 사고가 바뀐다는 점이다.

### 18.1 ABAP SQL 사고

```text
이 프로그램에서 어떤 데이터를 읽을까?
어떤 조건으로 조회할까?
조회 결과를 어떤 Internal Table에 담을까?
이 프로그램 안에서 어떻게 출력할까?
```

### 18.2 CDS 사고

```text
이 업무 데이터를 어떤 의미 모델로 정의할까?
어떤 필드가 Key인가?
어떤 Association이 필요한가?
이 View를 누가 소비할 것인가?
RAP/Fiori/Analytics로 확장될 가능성이 있는가?
Annotation으로 어떤 의미를 줄 것인가?
```

| 구분 | ABAP SQL | CDS |
|---|---|---|
| 중심 | 프로그램 | 데이터 모델 |
| 재사용 | 낮거나 프로그램 중심 | 높음 |
| 의미 표현 | 코드와 변수명 중심 | View, Annotation, Association |
| 서비스 확장 | 별도 구현 필요 | RAP/OData 연결 기반 |
| 학습 포인트 | SELECT 문법 | 모델링 구조와 소비 방식 |

## 19. 실무 설계 기준

### 19.1 처음부터 CDS로 만들지 않아도 되는 경우

| 경우 | 설명 |
|---|---|
| 단순 테스트 프로그램 | 학습/검증 목적이라면 ABAP SQL이 빠르다. |
| 단일 리포트 전용 조회 | 재사용 필요가 낮다. |
| 매우 작은 테이블 단건 조회 | 별도 모델링 비용이 더 클 수 있다. |
| 임시 운영 보조 프로그램 | 유지보수 범위가 제한적이다. |

### 19.2 CDS를 적극 검토해야 하는 경우

| 경우 | 설명 |
|---|---|
| 여러 리포트에서 같은 Join 반복 | 중복 제거와 일관성 확보 |
| Fiori Elements 사용 예정 | CDS Annotation 기반 화면 생성 |
| RAP Business Object 예정 | CDS View Entity가 핵심 모델 |
| 분석/집계 모델 | DB Pushdown 효과 |
| 권한 통제 필요 | CDS Access Control 확장 가능 |
| 표준 API 성격 | 소비자에게 안정적 모델 제공 |

## 20. 성능 관점 요약

Modern ABAP SQL과 CDS 모두 성능을 위해 중요한 공통 원칙을 가진다.

| 원칙 | 설명 |
|---|---|
| 필요한 필드만 조회 | `SELECT *` 지양 |
| 가능한 필터는 DB에 전달 | ABAP LOOP 후 필터링 지양 |
| 대량 데이터 후처리 최소화 | Application Server 부하 감소 |
| Join 조건 명확화 | 불필요한 Cartesian 결과 방지 |
| Key/Index 이해 | 테이블 설계와 조회 성능 연결 |
| 측정 기반 판단 | 추측이 아니라 ST05, SQL Monitor 등으로 확인 |

초급 단계에서는 성능 도구를 깊게 다루지 않지만, 다음 태도는 반드시 가져야 한다.

```text
성능 문제는 문법 문제가 아니라 데이터량, 조건, 모델, 실행 계획의 문제이다.
```

## 21. 유지보수 관점 요약

### 21.1 ABAP SQL 유지보수

ABAP SQL은 프로그램 내부에 있으므로 해당 프로그램을 이해하는 개발자에게는 빠르게 접근 가능하다.  
하지만 같은 SQL이 여러 프로그램에 복사되면 유지보수 비용이 증가한다.

위험 신호:

```text
같은 Join이 여러 프로그램에 반복된다.
같은 CASE 분류 로직이 여러 곳에 존재한다.
필드 추가 시 여러 프로그램을 동시에 수정해야 한다.
```

### 21.2 CDS 유지보수

CDS는 중앙 모델이므로 재사용성과 일관성이 좋다.  
그러나 한 CDS를 여러 소비자가 사용하면 변경 영향 범위가 커진다.

위험 신호:

```text
하나의 CDS를 너무 많은 목적에 사용한다.
소비자별 요구사항이 다른데 같은 View에 계속 필드를 추가한다.
계층 구조 없이 모든 Join을 하나의 View에 몰아넣는다.
```

따라서 CDS에서도 계층화가 필요하다.

```text
Interface View
→ Consumption View
→ Service/RAP 소비
```

이 계층화는 CDS/RAP Section에서 본격적으로 학습한다.

## 22. 강사용 설명 포인트

### 22.1 “Modern ABAP SQL을 배웠다고 CDS가 불필요한 것은 아니다”

Modern ABAP SQL은 프로그램 안의 SELECT를 개선한다.  
CDS는 데이터 모델 자체를 개선한다.  
두 기술은 경쟁 관계가 아니라 역할이 다르다.

### 22.2 “Pushdown은 목적이 아니라 수단이다”

Pushdown은 성능과 구조 개선의 수단이다.  
업무적으로 이해하기 어려운 SQL 덩어리를 만들기 위한 명분이 아니다.

### 22.3 “CDS 전환 판단은 재사용성과 소비자 기준으로 한다”

한 번만 쓰는 조회를 CDS로 만들 필요는 낮다.  
하지만 여러 소비자가 같은 데이터 의미를 필요로 하면 CDS가 적합하다.

### 22.4 “ABAP 후처리를 줄이되, ABAP의 역할을 없애지 않는다”

ABAP은 여전히 화면 흐름, 절차적 업무 처리, 메시지, 트랜잭션 제어에서 중요하다.

### 24.2 서술형

#### Q1. ABAP SQL에 남겨도 좋은 로직과 CDS로 이동하면 좋은 로직의 차이를 설명하시오.

**모범 답안:**  
한 프로그램에서만 사용하는 단순 조회나 사용자 입력에 따라 임시로 변하는 조회는 ABAP SQL에 남겨도 된다. 반면 여러 프로그램에서 반복되는 조인, 공통 계산, 서비스나 RAP/Fiori로 노출될 가능성이 있는 데이터 의미는 CDS로 모델링하는 것이 좋다.

#### Q2. Pushdown Boundary를 판단할 때 고려할 기준을 쓰시오.

**모범 답안:**  
데이터량을 줄이는 필터링, 조인, 집계, 단순 계산은 DB/CDS로 보낼 수 있다. 반면 사용자 인터랙션, 메시지 처리, 복잡한 절차적 예외 처리, 트랜잭션 제어는 ABAP 계층에 남기는 것이 적절하다.

#### Q3. `SELECT *` 남용의 문제점을 설명하시오.

**모범 답안:**  
필요하지 않은 컬럼까지 조회하여 네트워크와 메모리 비용을 증가시키고, 조회 의도를 불명확하게 만들며, 테이블 구조 변경 시 불필요한 영향을 받을 수 있다.

## 25. 실습 과제

### 25.1 과제 1: ABAP SQL 코드 분류

다음 코드를 보고 ABAP SQL에 남길 부분과 CDS 후보를 분리한다.

```abap
SELECT FROM zt_invoice AS i
       INNER JOIN zt_customer AS c
         ON i~customer_id = c~customer_id
       FIELDS i~invoice_id,
              i~customer_id,
              c~customer_name,
              i~billing_date,
              i~amount,
              i~currency,
              CASE
                WHEN i~amount >= 1000000 THEN 'A'
                WHEN i~amount >= 500000  THEN 'B'
                ELSE 'C'
              END AS amount_grade
       WHERE i~billing_date BETWEEN @p_from AND @p_to
       INTO TABLE @DATA(lt_invoice).
```

분석 항목:

| 항목 | 판단 |
|---|---|
| Join이 재사용 가능한가? |  |
| Amount Grade가 공통 의미인가? |  |
| 날짜 조건은 사용자 입력인가? |  |
| Fiori/RAP 노출 가능성이 있는가? |  |
| CDS 후보 필드는 무엇인가? |  |

### 25.2 과제 2: 안티패턴 개선

아래 코드를 개선한다.

```abap
SELECT *
  FROM zt_order
  INTO TABLE @DATA(lt_order).

LOOP AT lt_order INTO DATA(ls_order).
  IF ls_order-status <> 'A'.
    CONTINUE.
  ENDIF.

  WRITE: / ls_order-order_id,
           ls_order-customer_id,
           ls_order-amount.
ENDLOOP.
```

개선 방향:

```text
필요한 필드만 SELECT한다.
필터 조건은 WHERE로 이동한다.
LOOP는 출력 또는 후속 처리 중심으로 남긴다.
```

예시 개선:

```abap
SELECT FROM zt_order
       FIELDS order_id,
              customer_id,
              amount
       WHERE status = 'A'
       INTO TABLE @DATA(lt_order).

LOOP AT lt_order INTO DATA(ls_order).
  WRITE: / ls_order-order_id,
           ls_order-customer_id,
           ls_order-amount.
ENDLOOP.
```

## 27. 핵심 요약

```text
Modern ABAP SQL은 프로그램 내부의 SQL을 더 명확하고 표현력 있게 만든다.
@ Host Variable은 ABAP 영역과 SQL 영역의 경계를 명확히 한다.
Inline Target은 간결하지만 재사용 타입이 필요한 경우에는 신중히 사용한다.
CASE, CAST, COALESCE, SQL Function은 단순 변환과 분류에 유용하다.
SELECT FROM @itab은 Internal Table과 SQL 처리를 연결하지만 대량 처리에는 신중해야 한다.
ABAP SQL은 프로그램 내부 조회에 적합하다.
CDS는 재사용 가능한 데이터 모델과 서비스 확장에 적합하다.
Pushdown은 모든 로직을 DB로 보내는 것이 아니라 적절한 경계를 설계하는 것이다.
```
