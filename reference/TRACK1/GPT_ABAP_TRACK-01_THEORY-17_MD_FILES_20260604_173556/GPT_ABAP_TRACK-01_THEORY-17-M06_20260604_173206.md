## 3. 왜 SELECT FROM @itab이 필요한가?

ABAP에서 내부 테이블은 매우 자주 사용된다.  
전통적으로 내부 테이블을 처리할 때는 다음과 같은 문법을 사용했다.

```abap
LOOP AT lt_source INTO DATA(ls_source).
  IF ls_source-status = 'A'.
    APPEND ls_source TO lt_result.
  ENDIF.
ENDLOOP.
```

이 방식은 명확하고 초급자에게 적합하다.  
하지만 데이터 처리 조건이 복잡해질수록 다음 문제가 생길 수 있다.

| 문제 | 설명 |
|---|---|
| 반복 코드 증가 | 조건, 변환, 필터링이 늘수록 LOOP 내부 코드가 길어진다. |
| 선언 코드 증가 | Work Area, Result Table 선언이 많아질 수 있다. |
| SQL 사고 흐름과 단절 | DB에서 가져온 데이터를 다시 ABAP 방식으로만 다룬다. |
| 후속 CDS 전환 감각 부족 | Projection, Filter, Join 중심 사고가 약해질 수 있다. |

Modern ABAP SQL은 내부 테이블도 SQL 데이터 소스로 사용할 수 있게 하여 다음과 같은 표현을 가능하게 한다.

```abap
SELECT *
  FROM @lt_source AS source
  WHERE status = 'A'
  INTO TABLE @DATA(lt_result).
```

위 코드는 내부 테이블 `lt_source`에서 `status = 'A'`인 행만 선택한다.  
즉, 내부 테이블을 대상으로 SQL의 `WHERE`를 적용하는 형태이다.

## 4. 기본 문법

### 4.1 최소 문법

가장 기본적인 형태는 다음과 같다.

```abap
SELECT *
  FROM @lt_source AS source
  INTO TABLE @DATA(lt_result).
```

각 요소의 의미는 다음과 같다.

| 요소 | 의미 |
|---|---|
| `SELECT *` | 모든 컬럼을 선택 |
| `FROM @lt_source` | ABAP 내부 테이블 `lt_source`를 데이터 소스로 사용 |
| `AS source` | SQL 문 안에서 사용할 별칭 |
| `INTO TABLE @DATA(lt_result)` | 결과를 새 내부 테이블로 인라인 선언하여 받음 |

### 4.2 왜 `@`가 필요한가?

Modern ABAP SQL에서 `@`는 ABAP 프로그램 영역의 변수, 즉 Host Variable 또는 Host Expression을 SQL 문 안으로 가져올 때 사용한다.

`lt_source`는 DB 테이블명이 아니라 ABAP 내부 테이블 변수이다.  
따라서 SQL 문장에서 `@lt_source`라고 명시해야 한다.

```abap
FROM @lt_source AS source
```

만약 `@` 없이 작성하면 시스템은 `lt_source`를 Dictionary 또는 DB 데이터 소스 이름처럼 해석하려 할 수 있다.

### 4.3 왜 alias가 필요한가?

내부 테이블을 SQL 데이터 소스로 사용할 때는 별칭을 붙이는 습관이 매우 중요하다.

```abap
FROM @lt_source AS source
```

별칭을 붙이면 다음 장점이 있다.

| 장점 | 설명 |
|---|---|
| 가독성 | 컬럼이 어느 데이터 소스에서 왔는지 명확하다. |
| 확장성 | Join이나 서브쿼리 형태로 확장할 때 충돌을 줄인다. |
| 표준 SQL 감각 | CDS, SQL View, DB SQL 사고 방식과 연결된다. |
| 교육 효과 | 내부 테이블도 데이터 소스라는 개념을 명확히 한다. |

## 5. 실습 데이터 준비

이번 모듈에서는 단순한 내부 테이블을 사용한다.

```abap
TYPES: BEGIN OF ty_user,
         user_id   TYPE c LENGTH 10,
         user_name TYPE c LENGTH 40,
         status    TYPE c LENGTH 1,
         dept      TYPE c LENGTH 10,
         score     TYPE i,
       END OF ty_user.

DATA lt_user TYPE STANDARD TABLE OF ty_user WITH EMPTY KEY.

lt_user = VALUE #(
  ( user_id = 'U0001' user_name = 'Kim Developer'  status = 'A' dept = 'ABAP' score = 90 )
  ( user_id = 'U0002' user_name = 'Lee Consultant' status = 'I' dept = 'FI'   score = 75 )
  ( user_id = 'U0003' user_name = 'Park Admin'     status = 'A' dept = 'ABAP' score = 85 )
  ( user_id = 'U0004' user_name = 'Choi Trainee'   status = 'B' dept = 'MM'   score = 60 )
).
```

이 데이터는 DB 테이블이 아니다.  
프로그램 실행 중 메모리에 존재하는 내부 테이블이다.

## 6. 예제 1: 내부 테이블 전체 조회

```abap
SELECT *
  FROM @lt_user AS user
  INTO TABLE @DATA(lt_all_user).
```

이 예제는 내부 테이블 `lt_user`의 모든 행과 모든 컬럼을 `lt_all_user`로 복사하는 형태이다.

전통적인 ABAP으로는 다음과 비슷하다.

```abap
lt_all_user = lt_user.
```

따라서 단순 복사 목적이라면 `SELECT FROM @itab`을 사용할 이유가 크지 않다.  
이 문법의 가치는 단순 복사보다 필터링, 컬럼 선택, 표현식 적용, Join 흐름에서 더 잘 드러난다.

## 7. 예제 2: WHERE 조건으로 필터링

활성 사용자만 조회한다.

```abap
SELECT user_id,
       user_name,
       status,
       dept,
       score
  FROM @lt_user AS user
  WHERE status = 'A'
  INTO TABLE @DATA(lt_active_user).
```

결과는 다음과 같은 의미이다.

| USER_ID | USER_NAME | STATUS | DEPT | SCORE |
|---|---|---|---|---:|
| U0001 | Kim Developer | A | ABAP | 90 |
| U0003 | Park Admin | A | ABAP | 85 |

전통적인 LOOP 방식은 다음과 같다.

```abap
DATA lt_active_user_loop TYPE STANDARD TABLE OF ty_user WITH EMPTY KEY.

LOOP AT lt_user INTO DATA(ls_user).
  IF ls_user-status = 'A'.
    APPEND ls_user TO lt_active_user_loop.
  ENDIF.
ENDLOOP.
```

두 방식은 모두 가능하다.  
초급자는 다음 기준으로 선택하면 된다.

| 상황 | 권장 방식 |
|---|---|
| 단순 반복 처리와 명령형 로직이 중요 | `LOOP AT` |
| SQL 방식의 필터링 표현이 더 명확 | `SELECT FROM @itab` |
| 디버깅하면서 한 줄씩 처리해야 함 | `LOOP AT` |
| Projection/Filter/Sort를 SQL처럼 표현하고 싶음 | `SELECT FROM @itab` |

## 8. 예제 3: 일부 컬럼만 선택하기

내부 테이블에서 필요한 컬럼만 선택할 수 있다.

```abap
SELECT user_id,
       user_name,
       dept
  FROM @lt_user AS user
  WHERE status = 'A'
  INTO TABLE @DATA(lt_user_brief).
```

이 예제의 핵심은 Projection이다.  
즉, 원본 내부 테이블에는 여러 컬럼이 있지만 결과에는 필요한 컬럼만 담는다.

결과 테이블의 구조는 선택한 컬럼 기준으로 결정된다.

```text
LT_USER_BRIEF
 ├─ USER_ID
 ├─ USER_NAME
 └─ DEPT
```

이 방식은 ALV 출력용 중간 데이터를 만들거나, 후속 처리에 필요한 컬럼만 남길 때 유용하다.

## 9. 예제 4: ORDER BY 사용

점수 기준으로 정렬한다.

```abap
SELECT user_id,
       user_name,
       score
  FROM @lt_user AS user
  ORDER BY score DESCENDING
  INTO TABLE @DATA(lt_ranked_user).
```

전통적인 ABAP 방식은 다음과 유사하다.

```abap
DATA lt_ranked_user_loop TYPE STANDARD TABLE OF ty_user WITH EMPTY KEY.
lt_ranked_user_loop = lt_user.

SORT lt_ranked_user_loop BY score DESCENDING.
```

`SELECT FROM @itab`의 `ORDER BY`는 SQL 사고 흐름으로 정렬을 표현한다.  
단순 정렬만 필요하면 `SORT`도 충분히 명확하다.  
하지만 필터링, 컬럼 선택, 정렬을 한 SQL 문장으로 표현하고 싶다면 `SELECT FROM @itab`이 유용하다.

## 10. 예제 5: CASE 표현식 적용

상태 코드를 설명 텍스트로 변환한다.

```abap
SELECT user_id,
       user_name,
       status,
       CASE status
         WHEN 'A' THEN 'Active'
         WHEN 'I' THEN 'Inactive'
         WHEN 'B' THEN 'Blocked'
         ELSE 'Unknown'
       END AS status_text
  FROM @lt_user AS user
  INTO TABLE @DATA(lt_user_status).
```

이 예제는 이전 모듈의 `CASE` 표현식과 연결된다.

결과 의미는 다음과 같다.

| USER_ID | USER_NAME | STATUS | STATUS_TEXT |
|---|---|---|---|
| U0001 | Kim Developer | A | Active |
| U0002 | Lee Consultant | I | Inactive |
| U0003 | Park Admin | A | Active |
| U0004 | Choi Trainee | B | Blocked |

이 방식은 단순 코드값을 화면 출력용 텍스트로 변환할 때 학습용으로 좋다.  
다만 실무에서는 상태 텍스트가 다국어, Customizing, Domain Fixed Value, Text Table과 연결될 수 있으므로 단순 `CASE`로 고정하기 전에 유지보수성을 검토해야 한다.

## 11. 예제 6: Host Variable과 함께 사용

사용자가 선택한 부서만 조회한다고 가정한다.

```abap
DATA gv_dept TYPE c LENGTH 10 VALUE 'ABAP'.

SELECT user_id,
       user_name,
       dept,
       score
  FROM @lt_user AS user
  WHERE dept = @gv_dept
  INTO TABLE @DATA(lt_dept_user).
```

이 예제에는 `@`가 두 번 등장한다.

| 위치 | 의미 |
|---|---|
| `FROM @lt_user` | 내부 테이블을 SQL 데이터 소스로 사용 |
| `WHERE dept = @gv_dept` | ABAP 변수 `gv_dept`를 SQL 조건값으로 사용 |

즉, 같은 `@`라도 역할이 문맥상 다르다.

```text
FROM 절의 @itab
→ ABAP 내부 테이블을 SQL 데이터 소스로 전달

WHERE 절의 @변수
→ ABAP 변수 값을 SQL 조건값으로 전달
```

## 12. 예제 7: 집계 기초

부서별 평균 점수를 구한다.

```abap
SELECT dept,
       AVG( score ) AS avg_score
  FROM @lt_user AS user
  GROUP BY dept
  INTO TABLE @DATA(lt_dept_score).
```

결과 의미는 다음과 같다.

| DEPT | AVG_SCORE |
|---|---:|
| ABAP | 87.5 |
| FI | 75 |
| MM | 60 |

이 예제는 내부 테이블을 대상으로도 SQL식 집계 사고를 적용할 수 있음을 보여준다.

다만 집계가 단순하거나 데이터량이 작으면 ABAP의 `LOOP AT GROUP BY` 또는 일반 반복 처리도 충분히 좋은 선택일 수 있다.  
무조건 SQL처럼 쓰는 것이 목표가 아니라, 표현 방식의 선택지를 이해하는 것이 중요하다.

## 13. SELECT FROM @itab과 LOOP AT 비교

### 13.1 개념 비교

| 구분 | `LOOP AT` | `SELECT FROM @itab` |
|---|---|---|
| 사고 방식 | 명령형 처리 | 선언형 SQL 처리 |
| 주 사용 대상 | 내부 테이블 반복 처리 | 내부 테이블을 SQL 데이터 소스로 처리 |
| 필터링 | `IF`, `CHECK`, `CONTINUE` | `WHERE` |
| 정렬 | `SORT` | `ORDER BY` |
| 컬럼 선택 | 별도 구조 또는 MOVE-CORRESPONDING | SELECT list |
| 표현식 | ABAP 문법 | SQL Expression |
| 디버깅 | 한 줄씩 추적 쉬움 | SQL 결과 중심 확인 |
| 초급 난이도 | 낮음 | 중간 |

### 13.2 선택 기준

`SELECT FROM @itab`이 더 적합한 경우는 다음과 같다.

```text
내부 테이블을 SQL 방식으로 필터링하고 싶다.
필요한 컬럼만 Projection하고 싶다.
CASE, CAST, COALESCE 같은 SQL 표현식을 함께 쓰고 싶다.
GROUP BY, ORDER BY로 SQL 사고 흐름을 유지하고 싶다.
이후 CDS 학습과 연결되는 SQL 기반 사고를 연습하고 싶다.
```

`LOOP AT`이 더 적합한 경우는 다음과 같다.

```text
행마다 복잡한 ABAP 로직이 필요하다.
외부 메서드 호출, 메시지 처리, 예외 처리 등이 행 단위로 필요하다.
디버깅을 한 줄씩 따라가야 한다.
데이터량이 작고 단순한 처리다.
팀원이 SQL식 내부 테이블 처리를 낯설어한다.
```

실무적으로는 둘 중 하나만 고집하지 않는다.  
문맥에 맞는 표현을 선택한다.

## 14. 내부 테이블 Row Type 제약과 설계 주의

`SELECT FROM @itab`을 사용하려면 내부 테이블의 행 구조가 SQL 데이터 소스로 해석될 수 있어야 한다.

초급 단계에서 권장하는 내부 테이블 형태는 다음과 같다.

```abap
TYPES: BEGIN OF ty_source,
         key1   TYPE c LENGTH 10,
         text1  TYPE c LENGTH 40,
         amount TYPE p LENGTH 8 DECIMALS 2,
       END OF ty_source.

DATA lt_source TYPE STANDARD TABLE OF ty_source WITH EMPTY KEY.
```

피해야 할 형태는 다음과 같다.

| 형태 | 이유 |
|---|---|
| Deep Structure가 포함된 내부 테이블 | SQL 데이터 소스로 해석하기 어렵거나 제약이 생길 수 있다. |
| 중첩 Internal Table 필드 포함 | SQL 컬럼으로 직접 다루기 부적합하다. |
| Reference Type 필드 포함 | SQL 데이터 소스의 컬럼처럼 사용하기 어렵다. |
| Generic Type이 과도한 경우 | 컴파일 시 타입 추론과 SQL 해석이 불명확해질 수 있다. |

초급자는 우선 Flat Structure 기반의 내부 테이블로 연습하는 것이 좋다.

## 15. DB 테이블과 JOIN할 때의 주의

`SELECT FROM @itab`은 내부 테이블만 조회하는 데 그치지 않고, DB 테이블과 함께 사용하는 형태로 확장될 수 있다.

예를 들어 내부 테이블에 조회 대상 고객 목록이 있고, DB 테이블에서 고객 상세를 가져오는 흐름을 생각할 수 있다.

```abap
SELECT db~kunnr,
       db~name1,
       src~reason
  FROM kna1 AS db
  INNER JOIN @lt_customer_key AS src
    ON db~kunnr = src~kunnr
  INTO TABLE @DATA(lt_customer_result).
```

이 문법은 강력하지만 주의해야 한다.

| 주의점 | 설명 |
|---|---|
| 데이터 전송 비용 | 내부 테이블 데이터가 DB 처리 쪽으로 전달될 수 있다. |
| 내부 테이블 크기 | 너무 큰 내부 테이블을 JOIN 소스로 넘기면 성능 문제가 생길 수 있다. |
| 인덱스 활용 | DB 테이블 Key/Index와 Join 조건을 고려해야 한다. |
| DB 기능 의존 | 시스템 릴리스와 DB 기능 지원 여부를 확인해야 할 수 있다. |
| 대체안 검토 | `FOR ALL ENTRIES`, Range 조건, 임시 테이블, CDS 등과 비교해야 한다. |

초급 단계에서는 내부 테이블 단독 `SELECT FROM @itab`을 먼저 익히고, DB 테이블과의 JOIN은 중급 이상의 성능·SQL 설계 주제로 확장하는 것이 좋다.

> [추정] 시스템 릴리스와 DB 플랫폼, ABAP 커널 수준에 따라 내부 테이블을 SQL 데이터 소스로 사용하는 기능의 지원 범위나 Syntax Check 메시지가 다르게 보일 수 있다. 실습 시스템의 오류/경고 메시지를 기준으로 확인한다.

## 16. 성능 관점

`SELECT FROM @itab`은 보기에는 SQL이지만, 항상 DB 테이블을 대상으로 하는 전통적 `SELECT`와 같은 성능 모델로 보면 안 된다.

### 16.1 내부 테이블 단독 처리

내부 테이블만 대상으로 필터링하는 경우, 데이터는 이미 ABAP 메모리에 있다.  
따라서 성능 판단은 다음 요소에 영향을 받는다.

| 요소 | 영향 |
|---|---|
| 내부 테이블 행 수 | 많을수록 처리 비용 증가 |
| WHERE 조건 | 필터링 비용 발생 |
| ORDER BY | 정렬 비용 발생 |
| GROUP BY | 그룹화 비용 발생 |
| 선택 컬럼 수 | 결과 구조와 메모리 사용에 영향 |

단순히 몇 건을 필터링하는 정도라면 `LOOP AT`이 더 직관적일 수 있다.

### 16.2 DB 테이블과 함께 사용하는 경우

DB 테이블과 JOIN하면 성능 판단이 훨씬 중요해진다.

```text
내부 테이블 데이터가 어느 계층에서 처리되는가?
DB 테이블의 Key/Index와 Join 조건이 맞는가?
내부 테이블 건수가 너무 많지는 않은가?
동일 목적을 더 단순한 Open SQL로 처리할 수 없는가?
```

실무에서는 데이터량을 기준으로 판단해야 한다.

| 내부 테이블 크기 | 판단 |
|---:|---|
| 수십 건 | 학습/단순 처리에 적합 |
| 수천 건 | 조건, Join 대상, 성능 측정 필요 |
| 수만 건 이상 | 신중 검토, 대체 설계 고려 |
| 대량 운영 데이터 | 성능 테스트와 아키텍처 판단 필요 |

## 17. 자주 발생하는 오류와 해결

### 17.1 `@` 누락

#### 잘못된 예

```abap
SELECT *
  FROM lt_user AS user
  INTO TABLE @DATA(lt_result).
```

#### 문제

`lt_user`가 ABAP 내부 테이블 변수임을 SQL 문장이 알 수 없다.

#### 해결

```abap
SELECT *
  FROM @lt_user AS user
  INTO TABLE @DATA(lt_result).
```

---

### 17.2 Alias 누락 또는 컬럼 출처 혼동

#### 문제 상황

Join이나 복합 SQL에서 컬럼이 어느 데이터 소스의 것인지 불명확해진다.

#### 해결

항상 별칭을 붙이고, 복잡한 SQL에서는 별칭으로 컬럼 출처를 명시한다.

```abap
SELECT user~user_id,
       user~user_name
  FROM @lt_user AS user
  INTO TABLE @DATA(lt_result).
```

---

### 17.3 내부 테이블 구조가 SQL에 부적합

#### 문제 상황

내부 테이블 행 타입에 중첩 테이블, 참조 필드, 문자열 테이블 등 Deep Component가 포함되어 SQL 데이터 소스로 사용할 수 없다.

#### 해결

Flat Structure 기반의 별도 내부 테이블을 만든 뒤 사용한다.

```abap
TYPES: BEGIN OF ty_user_flat,
         user_id   TYPE c LENGTH 10,
         user_name TYPE c LENGTH 40,
         status    TYPE c LENGTH 1,
       END OF ty_user_flat.

DATA lt_user_flat TYPE STANDARD TABLE OF ty_user_flat WITH EMPTY KEY.
```

---

### 17.4 SELECT 결과 구조 예상 오류

#### 문제 상황

`SELECT user_id, user_name`처럼 일부 컬럼만 선택했는데, 결과를 원본 구조 전체 타입의 테이블에 넣으려고 한다.

#### 해결

인라인 선언을 사용하거나 결과 구조를 명확히 맞춘다.

```abap
SELECT user_id,
       user_name
  FROM @lt_user AS user
  INTO TABLE @DATA(lt_user_brief).
```

---

### 17.5 과도한 사용으로 가독성 저하

#### 문제 상황

단순한 내부 테이블 처리까지 모두 SQL로 작성하여 팀원이 읽기 어려워진다.

#### 해결

단순 행 단위 처리는 `LOOP AT`을 유지하고, SQL식 Projection/Filter/Aggregation이 명확할 때만 `SELECT FROM @itab`을 선택한다.

## 18. 실무 적용 기준

### 18.1 사용할 만한 경우

다음 상황에서는 `SELECT FROM @itab`이 유용할 수 있다.

| 상황 | 이유 |
|---|---|
| 내부 테이블에서 필요한 컬럼만 뽑고 싶음 | SELECT list로 Projection 가능 |
| 조건 필터링을 SQL처럼 표현하고 싶음 | WHERE 사용 |
| 정렬과 그룹화를 SQL 문장 안에서 처리하고 싶음 | ORDER BY, GROUP BY 사용 |
| CASE/COALESCE 등 SQL Expression을 적용하고 싶음 | SQL 표현식 사용 |
| CDS 학습 전 SQL 데이터 소스 사고를 연습하고 싶음 | SQL 기반 선언형 사고 강화 |
| 내부 테이블과 DB 테이블을 조건으로 연결하고 싶음 | Join 소스 확장 가능 |

### 18.2 피하는 것이 좋은 경우

다음 상황에서는 신중해야 한다.

| 상황 | 이유 |
|---|---|
| 단순 복사 | `lt_result = lt_source`가 더 명확 |
| 단순 반복 출력 | `LOOP AT`이 더 직관적 |
| 행마다 복잡한 메서드 호출 필요 | SQL 문장에 넣기 부적합 |
| 대량 내부 테이블과 DB JOIN | 데이터 이동/성능 문제 가능 |
| 팀 표준에서 제한 | 유지보수성 문제 |
| 실습 시스템 릴리스가 낮음 | 문법 지원 여부 문제 |

## 19. 실습 과제

### 19.1 기본 과제

다음 내부 테이블을 준비한다.

```abap
TYPES: BEGIN OF ty_material,
         matnr TYPE c LENGTH 18,
         maktx TYPE c LENGTH 40,
         mtart TYPE c LENGTH 4,
         active TYPE c LENGTH 1,
       END OF ty_material.

DATA lt_material TYPE STANDARD TABLE OF ty_material WITH EMPTY KEY.

lt_material = VALUE #(
  ( matnr = 'MAT-001' maktx = 'Notebook' active = 'A' mtart = 'FERT' )
  ( matnr = 'MAT-002' maktx = 'Keyboard' active = 'A' mtart = 'HALB' )
  ( matnr = 'MAT-003' maktx = 'Old Mouse' active = 'I' mtart = 'ROH' )
).
```

다음 조건을 만족하는 SQL을 작성한다.

```text
1. FROM @lt_material AS mat 사용
2. active = 'A'인 행만 선택
3. matnr, maktx, mtart만 결과에 포함
4. 결과를 @DATA(lt_active_material)로 받음
```

### 19.2 확장 과제

`CASE`를 사용하여 `active_text`를 만든다.

| ACTIVE | ACTIVE_TEXT |
|---|---|
| A | Active |
| I | Inactive |
| 그 외 | Unknown |

예상 SQL 형태는 다음과 같다.

```abap
SELECT matnr,
       maktx,
       active,
       CASE active
         WHEN 'A' THEN 'Active'
         WHEN 'I' THEN 'Inactive'
         ELSE 'Unknown'
       END AS active_text
  FROM @lt_material AS mat
  INTO TABLE @DATA(lt_material_status).
```

### 19.3 비교 과제

같은 기능을 `LOOP AT` 방식으로 구현하고, 두 방식의 가독성을 비교한다.

비교 기준:

```text
코드 길이
의도 명확성
디버깅 편의성
팀원이 이해하기 쉬운 정도
후속 CDS 학습 연결성
```

## 20. 강사용 설명 포인트

강의에서는 다음 순서로 설명하는 것이 좋다.


> `SELECT FROM @itab`은 LOOP를 대체하기 위해 외우는 문법이 아니라, 내부 테이블을 SQL 데이터 소스로 바라보는 Modern ABAP 사고방식이다.

## 22. 평가 문제

### 22.1 객관식

#### Q1. `SELECT FROM @itab`의 설명으로 가장 적절한 것은?

A. DB 테이블을 생성하는 DDIC 문법이다.  
B. 내부 테이블을 ABAP SQL의 데이터 소스로 사용하는 문법이다.  
C. 내부 테이블을 항상 DB에 저장하는 문법이다.  
D. CDS View Entity를 생성하는 문법이다.

**정답:** B

#### Q2. `FROM @lt_user AS user`에서 `@`의 의미는?

A. `lt_user`가 ABAP 프로그램 영역의 내부 테이블임을 SQL 문장에 명시한다.  
B. `lt_user`를 삭제한다.  
C. `lt_user`를 자동으로 DB 테이블로 생성한다.  
D. `lt_user`의 모든 필드를 Key로 만든다.

**정답:** A

#### Q3. `SELECT FROM @itab`보다 `LOOP AT`이 더 적합할 수 있는 경우는?

A. 단순 필터링만 필요한 경우  
B. 행마다 복잡한 메서드 호출과 예외 처리가 필요한 경우  
C. 일부 컬럼만 Projection하려는 경우  
D. SQL의 CASE 표현식을 적용하려는 경우

**정답:** B

### 22.2 서술형

#### Q1. `SELECT FROM @itab`과 `LOOP AT`의 차이를 설명하시오.

**모범 답안:**  
`LOOP AT`은 내부 테이블을 행 단위로 반복하며 ABAP 문법으로 처리하는 명령형 방식이다. `SELECT FROM @itab`은 내부 테이블을 SQL 데이터 소스로 보고 `WHERE`, `ORDER BY`, Projection, SQL Expression 등을 사용해 선언적으로 처리하는 방식이다. 두 문법은 경쟁 관계가 아니라 상황에 따라 선택하는 도구이다.

#### Q2. 내부 테이블과 DB 테이블을 JOIN할 때 주의해야 하는 이유를 설명하시오.

**모범 답안:**  
내부 테이블 데이터가 DB 처리 쪽으로 전달될 수 있고, 내부 테이블 크기와 DB 테이블 인덱스, Join 조건에 따라 성능 문제가 발생할 수 있기 때문이다. 특히 대량 내부 테이블을 DB 테이블과 Join하는 경우 성능 테스트와 대체 설계 검토가 필요하다.

#### Q3. 단순 복사 목적으로 `SELECT FROM @itab`을 사용하는 것이 좋은 설계가 아닐 수 있는 이유를 설명하시오.

**모범 답안:**  
단순 복사는 `lt_result = lt_source`가 더 간결하고 의도가 명확하다. `SELECT FROM @itab`은 SQL식 필터링, 컬럼 선택, 정렬, 표현식 적용 등 SQL 처리의 이점이 있을 때 사용하는 것이 더 적절하다.

## 24. 핵심 요약

```text
SELECT FROM @itab은 내부 테이블을 ABAP SQL의 FROM 데이터 소스로 사용하는 Modern ABAP SQL 문법이다.
@는 내부 테이블이 ABAP 프로그램 영역의 데이터임을 SQL 문장에 명시한다.
AS alias를 붙이면 컬럼 출처가 명확해지고 Join 확장에 유리하다.
단순 복사에는 적합하지 않을 수 있으며, Projection/Filter/Expression/Sort에 가치가 있다.
LOOP AT과 SELECT FROM @itab은 경쟁 관계가 아니라 상황별 선택지이다.
DB 테이블과 함께 사용할 때는 내부 테이블 크기와 데이터 이동 비용을 반드시 고려해야 한다.
```

## 25. 후속 모듈 연결

다음 모듈은 `THEORY-17-M07 — CDS로 넘어가기 전 ABAP SQL 정리`이다.

이번 모듈은 CDS로 넘어가기 직전 다음 감각을 만들어준다.

```text
DB 테이블도 SQL 데이터 소스이다.
내부 테이블도 특정 조건에서 SQL 데이터 소스처럼 다룰 수 있다.
SQL은 단순 SELECT가 아니라 Projection, Filter, Expression, Join을 표현하는 언어이다.
CDS는 이러한 SQL식 데이터 모델링 사고를 Repository 객체와 의미 모델로 확장한다.
```

따라서 `SELECT FROM @itab`은 단순한 신문법이 아니라, ABAP 내부 데이터와 SQL 데이터 처리 모델 사이의 연결 지점으로 이해하는 것이 좋다.
