## 3. Open SQL과 ABAP SQL 용어 정리

전통적으로 ABAP에서는 DB 접근 문법을 “Open SQL”이라고 불렀다.  
최근 문서와 학습 자료에서는 “ABAP SQL”이라는 표현도 자주 사용한다.

초급 학습에서는 다음처럼 이해하면 된다.

| 용어 | 실무적 이해 |
|---|---|
| Open SQL | ABAP에서 데이터베이스에 독립적으로 접근하기 위한 전통적 명칭 |
| ABAP SQL | ABAP 언어 안에서 사용하는 SQL 문법의 현대적 명칭 |
| Native SQL | DB 고유 SQL을 직접 사용하는 방식. 초급 과정에서는 다루지 않는다. |

이 문서에서는 교육 흐름을 위해 `Open SQL`과 `ABAP SQL`을 다음처럼 구분한다.

```text
Classic Open SQL = 전통적인 ABAP SQL 작성 스타일
Modern ABAP SQL = 7.40+ 이후 현대 ABAP 문법과 결합된 작성 스타일
```

> [추정] 실제 프로젝트 문서에서는 회사나 시스템 릴리스에 따라 Open SQL, ABAP SQL이라는 용어를 혼용할 수 있다. 중요한 것은 용어 자체보다 ABAP 런타임이 제공하는 DB 독립적 데이터 접근 문법이라는 본질이다.

## 4. Classic Open SQL 기본 형태

Classic Open SQL은 다음과 같은 형태로 자주 작성되었다.

```abap
DATA: lt_flights TYPE STANDARD TABLE OF sflight.

SELECT carrid
       connid
       fldate
       price
       currency
  FROM sflight
  INTO TABLE lt_flights
  WHERE carrid = 'AA'.
```

이 방식은 오랫동안 사용된 표준적인 스타일이다.  
문법적으로도 이해하기 쉽고, 많은 SAP 표준 예제와 고객사 레거시 코드에서 볼 수 있다.

### 4.1 Classic Open SQL의 특징

| 특징 | 설명 |
|---|---|
| 조회 필드가 `SELECT` 바로 뒤에 위치 | 어떤 필드를 가져오는지 먼저 보인다. |
| 대상 테이블은 `FROM`에서 지정 | DB Table 또는 View를 명시한다. |
| 결과 대상은 `INTO TABLE`에 미리 선언된 변수 사용 | 사전에 `DATA` 선언이 필요하다. |
| ABAP 변수와 SQL 필드의 구분이 약함 | 과거 문법에서는 Host Variable 표시가 명확하지 않았다. |
| 레거시 코드에서 많이 사용 | 유지보수 시 반드시 읽을 줄 알아야 한다. |

### 4.2 Classic 스타일의 장점

Classic Open SQL은 아직도 많은 시스템에서 읽고 유지보수해야 하는 중요한 문법이다.

장점은 다음과 같다.

```text
오래된 시스템과 코드에서 널리 사용된다.
기본 SELECT 구조를 이해하기 쉽다.
초급자가 SQL의 기본 흐름을 배우기에 단순하다.
SAP 표준 레거시 예제에서 자주 발견된다.
```

### 4.3 Classic 스타일의 한계

하지만 시스템과 문법이 발전하면서 Classic 스타일만으로는 아쉬운 점이 생긴다.

| 한계 | 설명 |
|---|---|
| ABAP 변수와 DB 필드 구분이 덜 명확 | SQL 안에서 어떤 것이 ABAP 변수인지 구분이 약하다. |
| 사전 DATA 선언이 많아짐 | 코드 상단에 선언부가 길어질 수 있다. |
| JOIN/Expression 확장 시 가독성 저하 | 복잡한 SELECT에서 필드, 소스, 조건 위치가 길게 흩어진다. |
| SQL과 ABAP 영역의 경계가 불분명 | 유지보수자가 의미를 빠르게 파악하기 어렵다. |

## 5. Modern ABAP SQL 기본 방향

Modern ABAP SQL은 기존 Open SQL을 다음 방향으로 개선한다.

```text
1. SQL 안의 ABAP 변수를 명확히 표시한다.
2. 결과 변수를 필요한 위치에서 선언한다.
3. SQL Expression을 활용해 DB에서 계산 가능한 부분을 표현한다.
4. FIELDS 구문으로 데이터 소스와 필드 목록을 더 구조적으로 표현한다.
5. 코드의 의도와 데이터 흐름을 더 명확히 만든다.
```

Modern ABAP SQL은 단순히 “새 문법을 쓰는 것”이 아니다.  
실무 관점에서는 다음 목적이 더 중요하다.

| 목적 | 설명 |
|---|---|
| 가독성 | SQL의 소스, 필드, 조건, 결과를 명확히 읽게 한다. |
| 유지보수성 | 변수 선언, 타입 추론, 결과 구조 변경을 단순화한다. |
| 명시성 | ABAP 변수와 SQL 필드의 경계를 명확히 한다. |
| 확장성 | CASE, CAST, COALESCE, 함수 등으로 확장하기 쉽다. |
| Clean ABAP 흐름 | 불필요한 선언과 반복을 줄인다. |

## 6. `FIELDS` 구문이란?

`FIELDS`는 Modern ABAP SQL에서 조회할 필드를 명시하는 위치와 방식을 개선하는 구문이다.

Classic 방식:

```abap
SELECT carrid,
       connid,
       fldate
  FROM sflight
  WHERE carrid = @lv_carrid
  INTO TABLE @DATA(lt_flights).
```

`FIELDS` 방식:

```abap
SELECT FROM sflight
  FIELDS carrid,
         connid,
         fldate
  WHERE carrid = @lv_carrid
  INTO TABLE @DATA(lt_flights).
```

두 코드는 같은 성격의 조회를 수행한다.  
하지만 구조적으로 보면 차이가 있다.

```text
Classic 스타일:
SELECT 조회필드
  FROM 데이터소스
  WHERE 조건
  INTO 결과

FIELDS 스타일:
SELECT FROM 데이터소스
  FIELDS 조회필드
  WHERE 조건
  INTO 결과
```

### 6.1 `FIELDS` 구문의 장점

`FIELDS` 구문은 특히 복잡한 SELECT에서 장점이 커진다.

| 장점 | 설명 |
|---|---|
| 데이터 소스가 먼저 보임 | `SELECT FROM ...`으로 어떤 테이블에서 읽는지 먼저 알 수 있다. |
| 필드 목록이 명확한 블록이 됨 | 조회 대상 필드가 `FIELDS` 아래에 모인다. |
| JOIN과 잘 어울림 | 여러 테이블을 먼저 정의하고 필드 목록을 정리하기 쉽다. |
| SQL Expression 확장에 유리 | `CASE`, `CAST`, 함수 사용 시 구조가 읽기 쉬워진다. |
| CDS와 사고 방식 연결 | `FROM` 소스와 Projection 필드 목록을 구분하는 감각을 준다. |

### 6.2 `FIELDS` 사용 시 읽는 순서

초급자는 `FIELDS` 문법을 다음 순서로 읽으면 된다.

```text
SELECT FROM sflight
  → SFLIGHT 테이블에서 읽는다.

FIELDS carrid, connid, fldate
  → CARRID, CONNID, FLDATE 필드를 가져온다.

WHERE carrid = @lv_carrid
  → ABAP 변수 LV_CARRID와 일치하는 항공사만 조회한다.

INTO TABLE @DATA(lt_flights)
  → 결과를 새 Internal Table LT_FLIGHTS에 담는다.
```

## 7. Classic Open SQL과 Modern ABAP SQL 비교

### 7.1 단일 테이블 조회 비교

Classic 방식:

```abap
DATA lt_scarr TYPE STANDARD TABLE OF scarr.

SELECT carrid
       carrname
       currcode
       url
  FROM scarr
  INTO TABLE lt_scarr.
```

Modern 방식:

```abap
SELECT FROM scarr
  FIELDS carrid,
         carrname,
         currcode,
         url
  INTO TABLE @DATA(lt_scarr).
```

비교:

| 관점 | Classic | Modern |
|---|---|---|
| 결과 변수 선언 | 사전 선언 | Inline 선언 가능 |
| 조회 필드 위치 | `SELECT` 뒤 | `FIELDS` 뒤 |
| 테이블 위치 | `FROM` 절 | `SELECT FROM`으로 먼저 표시 |
| ABAP 변수 표시 | 과거 스타일에서는 덜 명확 | `@`로 명확히 표시 |
| 가독성 | 단순 조회에 익숙함 | 복잡한 조회에 유리 |

### 7.2 조건이 있는 조회 비교

Classic 방식:

```abap
DATA lt_flights TYPE STANDARD TABLE OF sflight.
DATA lv_carrid  TYPE s_carr_id VALUE 'AA'.

SELECT carrid
       connid
       fldate
       price
  FROM sflight
  INTO TABLE lt_flights
  WHERE carrid = lv_carrid.
```

Modern 방식:

```abap
DATA lv_carrid TYPE s_carr_id VALUE 'AA'.

SELECT FROM sflight
  FIELDS carrid,
         connid,
         fldate,
         price
  WHERE carrid = @lv_carrid
  INTO TABLE @DATA(lt_flights).
```

Modern 방식에서 중요한 포인트는 `@lv_carrid`이다.  
`@`는 SQL 안에서 ABAP 변수 또는 표현식을 사용한다는 표시이다.  
이 내용은 다음 모듈 `THEORY-17-M02 — @ Host Variable과 Host Expression`에서 자세히 다룬다.

## 8. `INTO` 위치에 대한 실무 감각

Modern ABAP SQL에서는 `INTO` 절을 문장 끝에 배치하는 스타일을 자주 볼 수 있다.

```abap
SELECT FROM scarr
  FIELDS carrid,
         carrname
  WHERE currcode = @lv_currcode
  INTO TABLE @DATA(lt_scarr).
```

이 구조는 다음처럼 읽기 쉽다.

```text
무엇에서 읽는가?   FROM scarr
무엇을 가져오는가? FIELDS carrid, carrname
어떤 조건인가?     WHERE currcode = @lv_currcode
어디에 담는가?     INTO TABLE @DATA(lt_scarr)
```

즉, SQL의 의미를 위에서 아래로 읽는 흐름이 자연스러워진다.

### 8.1 단순 문법 암기가 아니라 구조적 사고

초급자는 “INTO가 뒤로 갔다”는 표면적 변화에만 집중하기 쉽다.  
하지만 중요한 것은 SQL 문장을 **데이터 흐름**으로 읽는 것이다.

```text
Source
→ Projection
→ Filter
→ Target
```

Modern ABAP SQL은 이 흐름을 코드 구조로 더 잘 보여준다.

## 9. `SELECT *`와 필드 명시

Classic이든 Modern이든 실무에서는 `SELECT *`를 습관적으로 사용하는 것을 피해야 한다.

비권장 예:

```abap
SELECT *
  FROM sflight
  INTO TABLE @DATA(lt_flights).
```

권장 예:

```abap
SELECT FROM sflight
  FIELDS carrid,
         connid,
         fldate,
         price,
         currency
  INTO TABLE @DATA(lt_flights).
```

### 9.1 왜 필드를 명시해야 하는가?

| 이유 | 설명 |
|---|---|
| 성능 | 필요한 컬럼만 가져오는 것이 일반적으로 유리하다. |
| 가독성 | 어떤 데이터가 필요한지 코드에서 바로 보인다. |
| 안정성 | 테이블 구조 변경에 덜 민감한 코드를 만들 수 있다. |
| 인터페이스 명확성 | 후속 로직이 사용하는 데이터 범위를 알 수 있다. |
| 유지보수 | 불필요한 필드 의존성을 줄인다. |

`FIELDS` 구문은 필드 명시 습관을 자연스럽게 유도한다.

## 10. JOIN에서 `FIELDS`의 장점

JOIN이 들어가면 Classic 방식의 SELECT는 길어지기 쉽다.

Classic 스타일 예:

```abap
SELECT a~carrid,
       a~carrname,
       b~connid,
       b~cityfrom,
       b~cityto
  FROM scarr AS a
  INNER JOIN spfli AS b
    ON b~carrid = a~carrid
  INTO TABLE @DATA(lt_result)
  WHERE a~carrid = @lv_carrid.
```

Modern `FIELDS` 스타일 예:

```abap
SELECT FROM scarr AS carrier
  INNER JOIN spfli AS connection
    ON connection~carrid = carrier~carrid
  FIELDS carrier~carrid,
         carrier~carrname,
         connection~connid,
         connection~cityfrom,
         connection~cityto
  WHERE carrier~carrid = @lv_carrid
  INTO TABLE @DATA(lt_result).
```

Modern 스타일에서는 먼저 데이터 소스와 조인 관계를 읽고, 그 다음 조회 필드를 읽는다.

```text
SCARR와 SPFLI를 JOIN한다.
→ 어떤 필드를 가져올지 FIELDS에서 확인한다.
→ WHERE 조건을 확인한다.
→ 결과를 Internal Table에 담는다.
```

### 10.1 Alias의 중요성

Modern ABAP SQL에서는 Alias를 의미 있게 작성하면 가독성이 크게 좋아진다.

비교:

```abap
SELECT FROM scarr AS a
  INNER JOIN spfli AS b
    ON b~carrid = a~carrid
  FIELDS a~carrid,
         a~carrname,
         b~connid
  INTO TABLE @DATA(lt_result).
```

개선:

```abap
SELECT FROM scarr AS carrier
  INNER JOIN spfli AS connection
    ON connection~carrid = carrier~carrid
  FIELDS carrier~carrid,
         carrier~carrname,
         connection~connid
  INTO TABLE @DATA(lt_result).
```

의미 있는 Alias는 단순히 예쁜 코드가 아니다.  
조인 대상이 많아질수록 오류를 줄이고 유지보수성을 높이는 중요한 기준이다.

---

## 11. 오류 상황과 해결

### 11.1 `@` 누락

Modern ABAP SQL에서 ABAP 변수를 SQL 조건에 사용할 때 `@`를 누락하면 문법 오류가 발생할 수 있다.

오류 예:

```abap
DATA lv_carrid TYPE s_carr_id VALUE 'AA'.

SELECT FROM sflight
  FIELDS carrid,
         connid,
         fldate
  WHERE carrid = lv_carrid
  INTO TABLE @DATA(lt_flights).
```

수정:

```abap
DATA lv_carrid TYPE s_carr_id VALUE 'AA'.

SELECT FROM sflight
  FIELDS carrid,
         connid,
         fldate
  WHERE carrid = @lv_carrid
  INTO TABLE @DATA(lt_flights).
```

이번 모듈에서는 “Modern ABAP SQL에서는 Host Variable에 `@`가 필요하다”는 수준으로 이해한다.  
상세 내용은 다음 모듈에서 다룬다.

### 11.2 쉼표 누락

`FIELDS` 구문에서는 필드 목록을 쉼표로 구분하는 스타일을 사용한다.

오류 예:

```abap
SELECT FROM scarr
  FIELDS carrid
         carrname
         currcode
  INTO TABLE @DATA(lt_scarr).
```

수정:

```abap
SELECT FROM scarr
  FIELDS carrid,
         carrname,
         currcode
  INTO TABLE @DATA(lt_scarr).
```

### 11.3 필드명 모호성

JOIN에서 동일한 필드명이 여러 테이블에 존재하면 어떤 테이블의 필드인지 모호해질 수 있다.

오류 가능 예:

```abap
SELECT FROM scarr AS carrier
  INNER JOIN spfli AS connection
    ON connection~carrid = carrier~carrid
  FIELDS carrid,
         connid
  INTO TABLE @DATA(lt_result).
```

개선:

```abap
SELECT FROM scarr AS carrier
  INNER JOIN spfli AS connection
    ON connection~carrid = carrier~carrid
  FIELDS carrier~carrid,
         connection~connid
  INTO TABLE @DATA(lt_result).
```

### 11.4 `SELECT *`로 인한 결과 구조 혼란

`SELECT *`는 빠르게 테스트할 때 편하지만, 결과 구조가 커지고 불필요한 필드까지 포함된다.

개선 기준:

```text
실무 코드에서는 필요한 필드만 FIELDS에 명시한다.
테스트 코드라도 후속 학습 자료에는 필드 명시 습관을 남긴다.
```

### 11.5 릴리스 호환성 문제

Modern ABAP SQL 문법은 시스템 릴리스와 ABAP Platform 수준에 따라 사용 가능 범위가 다를 수 있다.

[추정] S/4HANA 기반 교육 시스템에서는 대부분의 Modern ABAP SQL 기본 문법을 사용할 수 있지만, 고객사 시스템이나 구버전 ECC에서는 일부 문법이 지원되지 않을 수 있다.

실무 판단:

```text
코드 리팩토링 전에 대상 시스템의 ABAP 릴리스와 Syntax Check 결과를 확인한다.
구버전 시스템을 함께 운영한다면 최신 문법 사용 범위를 프로젝트 기준으로 정한다.
```

## 12. 디버깅과 검증 포인트

Modern ABAP SQL은 문법이 간결하지만, 검증 포인트는 Classic Open SQL과 동일하게 중요하다.

### 12.1 Syntax Check

먼저 문법 오류를 확인한다.

```text
Ctrl + F2 또는 Check
```

확인 항목:

| 항목 | 확인 내용 |
|---|---|
| `@` 사용 | ABAP 변수 앞에 `@`가 있는가 |
| 필드 구분 | `FIELDS` 목록에 쉼표가 있는가 |
| Alias | JOIN 필드가 명확히 지정되었는가 |
| Target | `INTO TABLE @DATA(...)`가 올바른가 |

### 12.2 실행 결과 확인

실행 후 다음을 확인한다.

| 확인 항목 | 의미 |
|---|---|
| `sy-subrc` | 조회 결과 존재 여부 |
| `lines( lt_result )` | 조회 건수 |
| 결과 필드 값 | 예상한 필드가 들어왔는지 확인 |
| 조건 적용 여부 | `WHERE` 조건이 기대대로 동작했는지 확인 |

### 12.3 SQL Trace와 성능 분석

초급 과정에서는 SQL Trace를 깊게 다루지 않는다.  
다만 실무적으로 성능 문제가 의심되면 다음 도구로 확인할 수 있다는 점은 알아둔다.

| 도구 | 목적 |
|---|---|
| ST05 | SQL Trace |
| SAT | ABAP Runtime Analysis |
| SQL Monitor | SQL 사용 패턴 분석 |
| ATC | 정적 품질 점검 |

이번 모듈에서는 실제 도구 실습보다 “Modern 문법을 썼다고 자동으로 성능이 좋아지는 것은 아니다”라는 점이 중요하다.

## 13. 실무 적용 기준

### 13.1 언제 Modern ABAP SQL로 작성할 것인가?

신규 개발에서는 Modern ABAP SQL 스타일을 우선 적용하는 것이 좋다.

권장 상황:

```text
S/4HANA 신규 개발
ADT 기반 개발
Clean ABAP 스타일 적용 프로젝트
JOIN 또는 Expression이 포함된 조회
Inline Declaration을 적극 사용하는 코드
후속 CDS/RAP 학습과 연결되는 교육 코드
```

### 13.2 언제 Classic 스타일을 유지할 수 있는가?

다음 상황에서는 무조건 리팩토링하지 않아도 된다.

```text
운영 중 안정적으로 동작하는 레거시 코드
구버전 시스템과 호환성이 중요한 코드
수정 범위가 작고 리스크가 큰 경우
프로젝트 코딩 규칙이 Classic 스타일을 유지하는 경우
```

중요한 것은 “새 문법이 있으니 무조건 바꾸자”가 아니다.  
실무에서는 다음을 기준으로 판단해야 한다.

```text
가독성이 실제로 좋아지는가?
테스트 범위가 확보되어 있는가?
릴리스 호환성이 확인되었는가?
기능 의미가 바뀌지 않는가?
팀의 코딩 컨벤션과 맞는가?
```

### 13.3 리팩토링 시 주의점

Classic SQL을 Modern SQL로 바꿀 때는 다음을 확인한다.

| 확인 항목 | 설명 |
|---|---|
| 조회 필드 동일성 | 기존과 같은 필드를 가져오는가 |
| 조건 동일성 | WHERE 조건이 변하지 않았는가 |
| 정렬 동일성 | ORDER BY가 필요한 경우 유지했는가 |
| 결과 타입 | Inline Target의 추론 타입이 후속 로직에 맞는가 |
| 예외/빈 결과 처리 | `sy-subrc`, empty table 처리 방식이 유지되는가 |

## 14. 미니 실습

### 14.1 실습 목표

Classic Open SQL 문장을 Modern ABAP SQL의 `FIELDS` 스타일로 바꿔보고, 결과가 동일한지 확인한다.

### 14.2 실습 대상 테이블

교육 시스템에 Flight Model 데이터가 존재한다고 가정하고 다음 표준 테이블을 사용한다.

| 테이블 | 의미 |
|---|---|
| SCARR | 항공사 |
| SPFLI | 항공편 연결 |
| SFLIGHT | 항공편 운항일자/가격 |

[추정] 일부 S/4HANA 교육 시스템에서는 Flight Model 데이터가 없거나 비활성일 수 있다. 이 경우 시스템에 존재하는 다른 표준 테이블 또는 교육용 Z 테이블로 대체한다.

### 14.3 Step 1 — Classic Open SQL 작성

```abap
REPORT zsql_classic_to_modern_01.

DATA lt_scarr TYPE STANDARD TABLE OF scarr.

SELECT carrid
       carrname
       currcode
  FROM scarr
  INTO TABLE lt_scarr.

WRITE: / 'Classic SQL result count:', lines( lt_scarr ).
```

### 14.4 Step 2 — Modern ABAP SQL로 변경

```abap
REPORT zsql_classic_to_modern_02.

SELECT FROM scarr
  FIELDS carrid,
         carrname,
         currcode
  INTO TABLE @DATA(lt_scarr).

WRITE: / 'Modern SQL result count:', lines( lt_scarr ).
```

### 14.5 Step 3 — 조건 추가

```abap
REPORT zsql_classic_to_modern_03.

DATA lv_currcode TYPE scarr-currcode VALUE 'USD'.

SELECT FROM scarr
  FIELDS carrid,
         carrname,
         currcode
  WHERE currcode = @lv_currcode
  INTO TABLE @DATA(lt_scarr).

WRITE: / 'Filtered result count:', lines( lt_scarr ).
```

### 14.6 Step 4 — JOIN으로 확장

```abap
REPORT zsql_classic_to_modern_04.

DATA lv_carrid TYPE scarr-carrid VALUE 'AA'.

SELECT FROM scarr AS carrier
  INNER JOIN spfli AS connection
    ON connection~carrid = carrier~carrid
  FIELDS carrier~carrid,
         carrier~carrname,
         connection~connid,
         connection~cityfrom,
         connection~cityto
  WHERE carrier~carrid = @lv_carrid
  INTO TABLE @DATA(lt_result).

WRITE: / 'Join result count:', lines( lt_result ).
```

### 14.7 실습 기록

| 항목 | 기록 |
|---|---|
| Classic SQL 실행 여부 |  |
| Modern SQL 실행 여부 |  |
| 조회 건수 동일 여부 |  |
| `@` 누락 시 오류 확인 여부 |  |

## 15. 강사용 설명 포인트

강의에서는 단순히 “이 문법이 새 문법입니다”라고 설명하면 효과가 약하다.  
다음 순서로 설명하는 것이 좋다.

```text
1. Classic Open SQL 예제를 먼저 보여준다.
2. 같은 의미의 Modern ABAP SQL 예제를 보여준다.
3. 문법 차이를 표시한다.
4. 어떤 부분이 가독성을 높이는지 설명한다.
5. Host Variable, Inline Target, Expression이 후속 모듈에서 확장됨을 예고한다.
```

### 15.1 꼭 강조할 메시지

```text
Modern ABAP SQL은 문법을 짧게 쓰기 위한 기능만이 아니다.
SQL과 ABAP의 경계를 명확히 하고,
조회 소스·필드·조건·결과를 구조적으로 읽게 만드는 방향이다.
```

### 15.2 초급자에게 피해야 할 설명

피해야 할 설명:

```text
Classic은 옛날 방식이라 쓰면 안 됩니다.
무조건 최신 문법으로 바꾸세요.
FIELDS를 쓰면 성능이 좋아집니다.
SELECT *는 항상 절대 금지입니다.
```

더 적절한 설명:

```text
Classic 코드는 읽을 줄 알아야 한다.
신규 개발에서는 Modern 스타일을 우선 고려한다.
FIELDS는 주로 가독성과 구조화에 도움을 준다.
SELECT *는 실무 코드에서는 필요한 필드를 명시하는 습관을 들이는 것이 좋다.
```

## 16. 평가 문제

### 16.1 객관식

#### Q1. Modern ABAP SQL의 특징으로 가장 적절한 것은?

A. ABAP 프로그램에서 DB 접근을 완전히 금지한다.  
B. Host Variable, Inline Declaration, FIELDS 등으로 SQL과 ABAP 영역을 더 명확히 표현한다.  
C. 모든 SELECT 문을 Native SQL로 변환한다.  
D. 모든 테이블 조회를 자동으로 CDS View로 변경한다.

**정답:** B

#### Q2. `FIELDS` 구문의 주된 장점은 무엇인가?

A. DB 테이블을 자동 생성한다.  
B. 조회 필드 목록을 구조적으로 명시하고, 복잡한 SELECT에서 가독성을 높인다.  
C. 모든 SQL을 병렬 처리한다.  
D. 권한 검사를 자동으로 제거한다.

**정답:** B

#### Q3. Modern ABAP SQL에서 ABAP 변수를 SQL 조건에 사용할 때 일반적으로 필요한 표시는?

A. `#`  
B. `@`  
C. `&`  
D. `%`

**정답:** B

### 16.2 단답형

#### Q1. Classic Open SQL과 Modern ABAP SQL의 차이를 두 가지 쓰시오.

모범 답안:  
Modern ABAP SQL은 `@`를 사용해 ABAP Host Variable을 명확히 표시하고, `@DATA(...)` Inline Declaration을 통해 결과 변수를 필요한 위치에서 선언할 수 있다. 또한 `FIELDS` 구문을 사용해 데이터 소스와 조회 필드 목록을 구조적으로 분리할 수 있다.

#### Q2. `SELECT *` 대신 필요한 필드를 명시하는 것이 좋은 이유를 설명하시오.

모범 답안:  
필요한 데이터만 가져오므로 성능과 네트워크/메모리 사용 측면에서 유리할 수 있고, 코드에서 어떤 필드가 실제로 필요한지 명확하게 드러나 유지보수성이 좋아진다.

#### Q3. Classic SQL을 Modern SQL로 리팩토링할 때 반드시 확인해야 할 항목은 무엇인가?

모범 답안:  
조회 필드, WHERE 조건, ORDER BY, 결과 타입, 빈 결과 처리, 후속 로직의 필드 접근 방식이 기존과 동일하게 유지되는지 확인해야 한다.
