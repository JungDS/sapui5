## 2. SELECT SINGLE이란 무엇인가?

`SELECT SINGLE`은 ABAP SQL에서 데이터베이스 테이블로부터 **한 건의 Row만 조회**할 때 사용하는 구문이다.

예를 들어 항공사 마스터 테이블 `SCARR`에서 특정 항공사 코드 `CARRID = 'AA'`에 해당하는 한 건을 조회하고 싶다면 다음처럼 작성할 수 있다.

```abap
SELECT SINGLE FROM scarr
  FIELDS carrid, carrname, currcode
  WHERE carrid = @p_carrid
  INTO @DATA(ls_carrier).
```

위 코드에서 핵심은 다음이다.

| 구성요소 | 의미 |
|---|---|
| `SELECT SINGLE` | 조건에 맞는 Row 중 한 건만 읽는다. |
| `FROM scarr` | 조회 대상 테이블은 `SCARR`이다. |
| `FIELDS carrid, carrname, currcode` | 필요한 필드만 조회한다. |
| `WHERE carrid = @p_carrid` | 입력값과 항공사 코드를 비교한다. |
| `INTO @DATA(ls_carrier)` | 조회 결과를 구조 변수에 받는다. |

초급자 관점에서 `SELECT SINGLE`은 “한 건만 필요할 때 사용하는 조회 문장”으로 이해할 수 있다.  
하지만 실무에서는 “한 건만 필요하다”보다 더 중요한 기준이 있다.

```text
정말 조건상 한 건만 나오는가?
```

이 질문에 답하지 못한 채 `SELECT SINGLE`을 사용하면, 우연히 조회된 한 건을 정답처럼 처리하는 위험이 생긴다.

## 3. 단건 조회가 필요한 대표 상황

`SELECT SINGLE`은 다음과 같은 상황에서 자주 사용된다.

| 상황 | 설명 |
|---|---|
| 마스터 데이터 한 건 조회 | 고객번호, 자재번호, 항공사 코드처럼 Key 기준으로 한 건 조회 |
| 존재 여부 확인 | 특정 Key의 데이터가 존재하는지 확인 |
| 설명 텍스트 조회 | 코드에 대한 명칭 또는 설명 한 건 조회 |
| 후속 로직 조건 판단 | 조회된 상태값을 기준으로 분기 처리 |

예를 들어 특정 항공사 코드가 존재하는지 확인하고, 존재하면 이름을 출력하는 로직은 단건 조회에 적합하다.

```abap
PARAMETERS p_carrid TYPE scarr-carrid.

SELECT SINGLE FROM scarr
  FIELDS carrid, carrname
  WHERE carrid = @p_carrid
  INTO @DATA(ls_scarr).

IF sy-subrc = 0.
  WRITE: / '항공사:', ls_scarr-carrid, ls_scarr-carrname.
ELSE.
  WRITE: / '존재하지 않는 항공사 코드입니다:', p_carrid.
ENDIF.
```

이 예제에서 `SCARR-CARRID`가 항공사 마스터의 식별 필드 역할을 하기 때문에 단건 조회 예제로 적절하다.

## 4. SELECT SINGLE의 기본 구조

S/4HANA와 최신 ABAP 문법 기준으로 다음 형태를 권장한다.

```abap
SELECT SINGLE FROM <db_table>
  FIELDS <field1>, <field2>, <field3>
  WHERE <condition>
  INTO @DATA(<structure_variable>).
```

예시:

```abap
SELECT SINGLE FROM scarr
  FIELDS carrid, carrname, url
  WHERE carrid = @p_carrid
  INTO @DATA(ls_scarr).
```

전통적인 형태로는 다음처럼 작성할 수도 있다.

```abap
SELECT SINGLE carrid, carrname, url
  FROM scarr
  WHERE carrid = @p_carrid
  INTO @DATA(ls_scarr).
```

두 방식 모두 현장에서 볼 수 있다.  
교육 과정에서는 `FIELDS`를 명시하는 최신 형태를 기본으로 두되, 기존 시스템 코드를 읽을 수 있도록 전통 문법도 함께 이해하는 것이 좋다.

## 5. SY-SUBRC와 조회 결과 판단

`SELECT SINGLE` 실행 후에는 `SY-SUBRC` 값을 통해 조회 성공 여부를 판단할 수 있다.

| `SY-SUBRC` | 의미 |
|---:|---|
| 0 | 조건에 맞는 데이터가 조회됨 |
| 4 | 조건에 맞는 데이터가 없음 |

가장 기본적인 패턴은 다음이다.

```abap
SELECT SINGLE FROM scarr
  FIELDS carrid, carrname
  WHERE carrid = @p_carrid
  INTO @DATA(ls_scarr).

IF sy-subrc = 0.
  WRITE: / '조회 성공:', ls_scarr-carrname.
ELSE.
  WRITE: / '조회 대상 없음'.
ENDIF.
```

초급자가 반드시 기억해야 할 점은 다음이다.

```text
SELECT SINGLE 후에는 조회 결과가 있다고 가정하지 말고, 항상 SY-SUBRC를 확인한다.
```

물론 현대 ABAP에서는 예외 처리, Optional 처리, Table Expression 등 다양한 방식이 후속 학습에서 등장한다.  
하지만 초급 단계에서는 `SY-SUBRC` 기반의 성공/실패 판단을 먼저 익히는 것이 안전하다.

## 6. 단건 조회와 구조 변수

`SELECT SINGLE`은 한 건의 Row를 조회하므로 결과를 일반적으로 **Structure** 형태로 받는다.

### 6.1 인라인 선언 방식

```abap
SELECT SINGLE FROM scarr
  FIELDS carrid, carrname, currcode
  WHERE carrid = @p_carrid
  INTO @DATA(ls_scarr).
```

이 경우 `ls_scarr`는 조회 필드 구성을 기준으로 자동 선언된다.

장점은 다음과 같다.

| 장점 | 설명 |
|---|---|
| 코드가 짧다 | 별도 DATA 선언이 필요 없다. |
| 필드 구성이 명확하다 | SELECT 목록이 결과 구조를 결정한다. |
| 초급 실습에 편리하다 | 작은 예제에서 집중도가 높다. |

### 6.2 명시적 선언 방식

```abap
DATA ls_scarr TYPE scarr.

SELECT SINGLE FROM scarr
  FIELDS *
  WHERE carrid = @p_carrid
  INTO @ls_scarr.
```

또는 필요한 필드만 직접 선언한 타입에 받을 수도 있다.

```abap
TYPES: BEGIN OF ty_carrier,
         carrid   TYPE scarr-carrid,
         carrname TYPE scarr-carrname,
       END OF ty_carrier.

DATA ls_carrier TYPE ty_carrier.

SELECT SINGLE FROM scarr
  FIELDS carrid, carrname
  WHERE carrid = @p_carrid
  INTO @ls_carrier.
```

명시적 선언 방식은 구조가 여러 위치에서 재사용되거나, 인터페이스 타입을 고정하고 싶을 때 유용하다.

## 7. `FIELDS *`를 조심해야 하는 이유

초급자는 편의상 다음처럼 작성하고 싶을 수 있다.

```abap
SELECT SINGLE FROM scarr
  FIELDS *
  WHERE carrid = @p_carrid
  INTO @DATA(ls_scarr).
```

이 문법 자체가 항상 틀린 것은 아니다.  
하지만 실무에서는 필요한 필드만 명시하는 습관이 더 좋다.

```abap
SELECT SINGLE FROM scarr
  FIELDS carrid, carrname, currcode
  WHERE carrid = @p_carrid
  INTO @DATA(ls_scarr).
```

필드 명시가 좋은 이유는 다음이다.

| 이유 | 설명 |
|---|---|
| 가독성 | 어떤 데이터를 읽는지 코드만 보고 알 수 있다. |
| 성능 감각 | 불필요한 컬럼 전송을 줄이는 습관이 생긴다. |
| 변경 영향 감소 | 테이블 필드가 늘어나도 프로그램 의도가 흔들리지 않는다. |
| 교육 효과 | 데이터 모델과 프로그램 의도를 연결해 이해할 수 있다. |

초급 과정에서는 `FIELDS *`를 절대 금지로 외우기보다는, “예제나 디버깅에는 편하지만 실무 로직에서는 필요한 필드만 읽는 습관이 좋다”고 이해한다.

## 8. WHERE 조건과 단건 보장

`SELECT SINGLE`에서 가장 중요한 부분은 `WHERE` 조건이다.

다음 코드는 좋은 예이다.

```abap
SELECT SINGLE FROM scarr
  FIELDS carrid, carrname
  WHERE carrid = @p_carrid
  INTO @DATA(ls_scarr).
```

`CARRID`가 항공사를 식별하는 Key 역할을 하므로, 조건이 충분히 좁다.

반면 다음 코드는 위험할 수 있다.

```abap
SELECT SINGLE FROM sflight
  FIELDS carrid, connid, fldate, price
  WHERE carrid = @p_carrid
  INTO @DATA(ls_flight).
```

`SFLIGHT`에는 같은 항공사 코드에 여러 항공편과 날짜가 존재할 수 있다.  
이 경우 `CARRID`만으로는 한 건이 보장되지 않는다.  
그럼에도 `SELECT SINGLE`을 사용하면 조건에 맞는 여러 건 중 한 건이 조회될 수 있는데, 그 한 건이 업무적으로 원하는 데이터라고 보장하기 어렵다.

### 8.1 좋은 WHERE 조건의 기준

| 기준 | 설명 |
|---|---|
| Key 기반 | Primary Key 또는 Unique한 식별 조건 사용 |
| 충분히 좁음 | 조건 결과가 업무적으로 한 건임을 설명 가능 |
| 의도 명확 | 왜 한 건만 필요한지 코드에서 드러남 |
| 조회 실패 처리 | 데이터가 없을 때의 로직이 있음 |

### 8.2 나쁜 WHERE 조건의 예

```abap
WHERE carrid = @p_carrid
```

이 조건은 `SCARR`에서는 괜찮을 수 있지만, `SFLIGHT`에서는 너무 넓다.  
테이블마다 Key 구조와 데이터 의미가 다르기 때문이다.

따라서 `SELECT SINGLE`을 쓸 때는 항상 다음 질문을 해야 한다.

```text
이 WHERE 조건으로 정말 한 건만 나오는가?
나온 한 건이 업무적으로 유일한 대상인가?
```

## 9. SELECT SINGLE과 `UP TO 1 ROWS`의 차이

초급 단계에서 두 문장은 비슷해 보일 수 있다.

```abap
SELECT SINGLE FROM sflight
  FIELDS carrid, connid, fldate, price
  WHERE carrid = @p_carrid
  INTO @DATA(ls_flight).
```

```abap
SELECT FROM sflight
  FIELDS carrid, connid, fldate, price
  WHERE carrid = @p_carrid
  ORDER BY fldate
  INTO TABLE @DATA(lt_flight)
  UP TO 1 ROWS.
```

실무 감각으로는 다음처럼 구분할 수 있다.

| 구문 | 적합한 목적 |
|---|---|
| `SELECT SINGLE` | Key 또는 Unique 조건으로 업무상 한 건을 조회 |
| `SELECT ... UP TO 1 ROWS ORDER BY ...` | 여러 건 중 정렬 기준에 따라 첫 번째 한 건을 조회 |

예를 들어 항공사 코드로 `SCARR` 한 건을 읽는 것은 `SELECT SINGLE`이 적절하다.  
반면 특정 항공사의 가장 빠른 항공편일자를 찾는 것은 단순 `SELECT SINGLE`보다 정렬 기준을 명시한 `UP TO 1 ROWS` 방식이 더 명확하다.

초급자는 다음 문장을 기억하면 된다.

```text
업무적으로 유일한 한 건이면 SELECT SINGLE.
여러 건 중 기준에 따라 하나를 고르는 것이라면 ORDER BY + UP TO 1 ROWS를 검토한다.
```

## 10. 존재 여부 확인 패턴

`SELECT SINGLE`은 실제 데이터를 사용하지 않고 존재 여부만 확인할 때도 자주 사용된다.

예를 들어 항공사 코드가 존재하는지만 확인하고 싶다면 다음처럼 필요한 최소 필드만 조회한다.

```abap
SELECT SINGLE FROM scarr
  FIELDS carrid
  WHERE carrid = @p_carrid
  INTO @DATA(lv_carrid).

IF sy-subrc = 0.
  WRITE: / '존재하는 항공사 코드입니다.'.
ELSE.
  WRITE: / '존재하지 않는 항공사 코드입니다.'.
ENDIF.
```

S/4HANA 및 최신 ABAP에서는 존재 여부 확인에 더 현대적인 표현이 사용될 수 있지만, 초급 단계에서는 위 패턴으로 `SY-SUBRC`의 의미를 이해하는 것이 중요하다.

단, 존재 여부 확인에서도 조건은 충분히 좁아야 한다.  
너무 넓은 조건으로 존재 여부를 확인하면 업무적으로 잘못된 판단을 할 수 있다.

## 11. 단건 조회 후 분기 처리

`SELECT SINGLE`은 보통 조회 자체로 끝나지 않는다.  
조회 결과를 기준으로 후속 처리를 분기한다.

예시:

```abap
PARAMETERS p_carrid TYPE scarr-carrid.

SELECT SINGLE FROM scarr
  FIELDS carrid, carrname, currcode
  WHERE carrid = @p_carrid
  INTO @DATA(ls_scarr).

IF sy-subrc <> 0.
  WRITE: / '항공사 코드가 존재하지 않습니다:', p_carrid.
  RETURN.
ENDIF.

WRITE: / '항공사 코드:', ls_scarr-carrid,
       / '항공사명    :', ls_scarr-carrname,
       / '통화        :', ls_scarr-currcode.
```

이 예제의 구조는 실무적으로도 중요하다.

```text
1. 입력값을 받는다.
2. 단건 조회를 수행한다.
3. 조회 실패 시 즉시 종료하거나 오류 메시지를 출력한다.
4. 조회 성공 시 후속 로직을 수행한다.
```

초급자는 `IF sy-subrc <> 0.` 이후 `RETURN.`을 사용하는 흐름을 통해 “실패 케이스를 먼저 처리하고 정상 로직을 아래에 두는 구조”를 익힐 수 있다.

## 12. 조회 실패는 항상 오류인가?

`SELECT SINGLE` 후 `SY-SUBRC = 4`가 나왔다고 해서 항상 프로그램 오류는 아니다.

예를 들어 사용자가 존재하지 않는 항공사 코드를 입력했다면, 이는 시스템 오류가 아니라 정상적인 입력 검증 실패일 수 있다.

| 상황 | 해석 |
|---|---|
| 사용자가 없는 코드 입력 | 정상적인 검증 실패 |
| 반드시 있어야 할 Customizing 누락 | 설정 오류 가능성 |
| 프로그램 내부에서 만든 Key가 틀림 | 로직 오류 가능성 |
| 권한 또는 Client 차이로 조회 불가 | 운영/권한/환경 확인 필요 |

초급자는 `SY-SUBRC = 4`를 단순히 “에러”라고 부르기보다, “조회 조건에 맞는 데이터가 없음”으로 정확히 이해해야 한다.

## 13. Client와 SELECT SINGLE

SAP 테이블에는 `MANDT`라는 Client 필드가 포함되는 경우가 많다.  
일반적인 Client-dependent 테이블 조회에서는 현재 로그인한 Client 기준으로 데이터가 처리된다.

초급 단계에서는 다음 정도만 이해한다.

```text
내가 로그인한 Client와 데이터가 저장된 Client가 다르면 조회 결과가 없을 수 있다.
```

예를 들어 개발자가 `100` Client에서 테스트 데이터를 넣었다고 생각했지만 실제로는 `200` Client에 넣었다면, `100` Client에서 `SELECT SINGLE`을 실행할 때 결과가 없을 수 있다.

따라서 조회 결과가 없을 때는 다음을 확인한다.

| 확인 항목 | 설명 |
|---|---|
| 입력 Key | 오타가 없는가? |
| 테스트 데이터 | 실제로 데이터가 존재하는가? |
| Client | 현재 로그인 Client와 데이터 Client가 일치하는가? |
| WHERE 조건 | 조건이 너무 제한적이지 않은가? |
| 데이터 대소문자 | 코드값의 대소문자가 맞는가? |

## 14. 실습: 항공사 단건 조회 프로그램

### 14.1 실습 목표

사용자가 항공사 코드를 입력하면 `SCARR`에서 해당 항공사 한 건을 조회하고, 존재 여부에 따라 다른 메시지를 출력한다.

### 14.2 실습 코드

```abap
REPORT zjhy_sql_single_01.

PARAMETERS p_carrid TYPE scarr-carrid OBLIGATORY.

SELECT SINGLE FROM scarr
  FIELDS carrid, carrname, currcode, url
  WHERE carrid = @p_carrid
  INTO @DATA(ls_scarr).

IF sy-subrc <> 0.
  WRITE: / '입력한 항공사 코드가 존재하지 않습니다:', p_carrid.
  RETURN.
ENDIF.

WRITE: / '항공사 코드:', ls_scarr-carrid,
       / '항공사명    :', ls_scarr-carrname,
       / '통화 코드   :', ls_scarr-currcode,
       / 'URL         :', ls_scarr-url.
```

### 14.3 실행 예시

| 입력값 | 예상 결과 |
|---|---|
| `AA` | 항공사 정보 출력 |
| `LH` | 항공사 정보 출력 |
| 존재하지 않는 코드 | “존재하지 않습니다” 메시지 출력 |

실습 환경마다 `SCARR` 데이터가 다를 수 있다.  
따라서 특정 코드가 반드시 존재한다고 가정하지 말고, 먼저 `SE16N` 또는 ADT Data Preview로 `SCARR` 데이터를 확인하는 것이 좋다.

## 15. 실습: 잘못된 SELECT SINGLE 체감하기

이번에는 `SFLIGHT`에서 `CARRID`만 조건으로 조회하는 코드를 보자.

```abap
REPORT zjhy_sql_single_bad.

PARAMETERS p_carrid TYPE sflight-carrid OBLIGATORY.

SELECT SINGLE FROM sflight
  FIELDS carrid, connid, fldate, price, currency
  WHERE carrid = @p_carrid
  INTO @DATA(ls_flight).

IF sy-subrc = 0.
  WRITE: / ls_flight-carrid,
           ls_flight-connid,
           ls_flight-fldate,
           ls_flight-price,
           ls_flight-currency.
ELSE.
  WRITE: / 'No flight found.'.
ENDIF.
```

이 코드는 문법적으로는 실행될 수 있다.  
하지만 `SFLIGHT`에서 `CARRID` 하나만으로는 항공편 한 건이 보장되지 않는다.

더 적절한 조건은 다음처럼 Key에 가까운 조건을 사용하는 것이다.

```abap
PARAMETERS: p_carrid TYPE sflight-carrid OBLIGATORY,
            p_connid TYPE sflight-connid OBLIGATORY,
            p_fldate TYPE sflight-fldate OBLIGATORY.

SELECT SINGLE FROM sflight
  FIELDS carrid, connid, fldate, price, currency
  WHERE carrid = @p_carrid
    AND connid = @p_connid
    AND fldate = @p_fldate
  INTO @DATA(ls_flight).
```

핵심은 다음이다.

```text
SELECT SINGLE이 한 건만 읽는다고 해서, WHERE 조건이 한 건을 보장한다는 뜻은 아니다.
```

## 16. 디버깅 포인트

`SELECT SINGLE`을 디버깅할 때는 다음 항목을 확인한다.

| 디버깅 위치 | 확인 내용 |
|---|---|
| SELECT 실행 전 | Host Variable 값이 예상과 일치하는가? |
| SELECT 실행 후 | `SY-SUBRC` 값이 0인가 4인가? |
| SELECT 실행 후 | 결과 구조 변수에 값이 들어왔는가? |
| 실패 시 | WHERE 조건이 실제 데이터와 일치하는가? |
| 실패 시 | 현재 Client가 맞는가? |

초급자가 자주 놓치는 것은 SELECT 실행 전 입력값이다.  
예를 들어 `p_carrid`에 공백이 들어가 있거나, 예상과 다른 값이 들어가 있으면 당연히 조회 결과가 없을 수 있다.

## 17. 자주 발생하는 오류와 해결

### 17.1 Host Variable `@` 누락

#### 잘못된 예

```abap
SELECT SINGLE FROM scarr
  FIELDS carrid, carrname
  WHERE carrid = p_carrid
  INTO @DATA(ls_scarr).
```

#### 문제

최신 ABAP SQL 문법에서는 ABAP 변수와 SQL 필드를 구분하기 위해 Host Variable 앞에 `@`를 붙인다.

#### 올바른 예

```abap
SELECT SINGLE FROM scarr
  FIELDS carrid, carrname
  WHERE carrid = @p_carrid
  INTO @DATA(ls_scarr).
```

### 17.2 결과 없음 처리 누락

#### 잘못된 예

```abap
SELECT SINGLE FROM scarr
  FIELDS carrid, carrname
  WHERE carrid = @p_carrid
  INTO @DATA(ls_scarr).

WRITE: / ls_scarr-carrname.
```

#### 문제

조회 결과가 없으면 `ls_scarr`의 값이 기대와 다를 수 있다.  
따라서 반드시 `SY-SUBRC`를 확인해야 한다.

#### 올바른 예

```abap
IF sy-subrc = 0.
  WRITE: / ls_scarr-carrname.
ELSE.
  WRITE: / 'No data found.'.
ENDIF.
```

### 17.3 너무 넓은 WHERE 조건

#### 잘못된 예

```abap
SELECT SINGLE FROM sflight
  FIELDS carrid, connid, fldate
  WHERE carrid = @p_carrid
  INTO @DATA(ls_flight).
```

#### 문제

`CARRID` 하나만으로는 `SFLIGHT` 한 건이 보장되지 않는다.

#### 해결

업무적으로 한 건을 식별할 수 있는 조건을 추가한다.

```abap
WHERE carrid = @p_carrid
  AND connid = @p_connid
  AND fldate = @p_fldate
```

### 17.4 `SELECT SINGLE`을 반복문 안에서 남발

#### 예

```abap
LOOP AT lt_items INTO DATA(ls_item).
  SELECT SINGLE FROM mara
    FIELDS matnr, mtart
    WHERE matnr = @ls_item-matnr
    INTO @DATA(ls_mara).
ENDLOOP.
```

#### 문제

이 패턴은 데이터 건수가 많아질수록 DB 접근이 반복되어 성능 문제가 발생할 수 있다.  
이번 Section의 마지막 모듈 `THEORY-09-M06`에서 반복 SELECT 안티패턴을 맛보기로 다룬다.

이번 모듈에서는 다음 정도만 기억한다.

```text
SELECT SINGLE은 편리하지만, LOOP 안에서 무분별하게 반복하면 성능 리스크가 커진다.
```

## 18. 실무 설계 기준

### 18.1 SELECT SINGLE 사용 전 질문

실무에서 `SELECT SINGLE`을 작성하기 전에는 다음 질문을 한다.

```text
이 조회는 정말 한 건만 필요한가?
WHERE 조건이 업무적으로 한 건을 보장하는가?
조회 결과가 없을 때 정상 처리 로직이 있는가?
필요한 필드만 읽고 있는가?
반복문 안에서 불필요하게 호출하고 있지는 않은가?
```

### 18.2 좋은 코드의 특징

| 특징 | 설명 |
|---|---|
| Key 기반 조건 | 테이블의 식별 구조를 이해하고 조회한다. |
| 필드 명시 | 필요한 필드만 읽는다. |
| 실패 처리 | `SY-SUBRC`로 결과 없음 처리 로직이 있다. |
| 업무 메시지 | 조회 실패 시 사용자가 이해할 수 있는 메시지를 출력한다. |
| 후속 성능 고려 | 반복 조회 가능성을 미리 점검한다. |

### 18.3 나쁜 코드의 특징

| 특징 | 문제 |
|---|---|
| `WHERE` 조건이 너무 넓음 | 어떤 한 건이 조회되는지 불명확하다. |
| `FIELDS *` 남발 | 불필요한 데이터 조회 가능성이 높다. |
| `SY-SUBRC` 미확인 | 조회 실패 후 잘못된 후속 처리 가능성이 있다. |
| 반복문 안에서 매번 조회 | 성능 문제가 발생할 수 있다. |
| 테이블 Key를 모름 | 데이터 모델 이해 없이 코딩하게 된다. |

## 20. 평가 문제

### 20.1 객관식

#### Q1. `SELECT SINGLE`의 가장 적절한 사용 목적은?

A. 조건에 맞는 모든 데이터를 Internal Table에 담기 위해 사용한다.  
B. 업무적으로 한 건이 식별되는 데이터를 조회하기 위해 사용한다.  
C. Selection Screen을 만들기 위해 사용한다.  
D. ABAP 프로그램을 활성화하기 위해 사용한다.

정답: B

#### Q2. `SELECT SINGLE` 후 조회 결과가 없을 때 일반적으로 `SY-SUBRC` 값은?

A. 0  
B. 1  
C. 4  
D. 8

정답: C

#### Q3. 여러 건 중 가장 빠른 일자의 한 건을 조회하고 싶을 때 더 적절한 접근은?

A. 조건 없이 `SELECT SINGLE`  
B. `SELECT SINGLE`과 임의의 WHERE 조건  
C. `ORDER BY`와 `UP TO 1 ROWS` 검토  
D. `WRITE`만 사용

정답: C

### 20.2 서술형

#### Q1. `SELECT SINGLE`에서 WHERE 조건이 중요한 이유를 설명하시오.

모범 답안:  
`SELECT SINGLE`은 조건에 맞는 Row 중 한 건만 조회한다. WHERE 조건이 업무적으로 한 건을 보장하지 않으면, 여러 건 중 어떤 데이터가 조회되는지 불명확해질 수 있다. 따라서 Key 또는 충분히 좁은 조건을 사용해야 한다.

#### Q2. `SY-SUBRC = 4`가 항상 프로그램 오류가 아닌 이유를 설명하시오.

모범 답안:  
`SY-SUBRC = 4`는 조회 조건에 맞는 데이터가 없다는 뜻이다. 사용자가 존재하지 않는 코드를 입력한 경우처럼 정상적인 입력 검증 실패일 수도 있다. 다만 반드시 있어야 하는 설정 데이터가 없거나, 프로그램이 잘못된 Key를 만든 경우라면 오류로 판단할 수 있다.

#### Q3. `SELECT SINGLE`과 `SELECT ... UP TO 1 ROWS`를 실무적으로 구분하시오.

모범 답안:  
`SELECT SINGLE`은 Key 또는 Unique 조건으로 업무상 유일한 한 건을 조회할 때 적합하다. `SELECT ... UP TO 1 ROWS`는 여러 건 중 정렬 기준에 따라 한 건을 고를 때 적합하다.

## 22. 핵심 요약

이번 모듈의 핵심은 다음이다.

```text
SELECT SINGLE은 한 건만 조회하는 ABAP SQL 구문이다.
하지만 한 건만 가져온다고 해서 WHERE 조건이 한 건을 보장하는 것은 아니다.
단건 조회는 Key 또는 충분히 좁은 조건을 기준으로 사용해야 한다.
SELECT SINGLE 후에는 SY-SUBRC로 조회 성공 여부를 확인한다.
조회 결과가 없을 때는 입력값, 데이터 존재 여부, Client, WHERE 조건을 확인한다.
여러 건 중 기준에 따라 하나를 고르는 경우에는 ORDER BY + UP TO 1 ROWS를 검토한다.
```
