## 3. 반복 SELECT란 무엇인가?

반복 SELECT란 보통 다음처럼 반복문 안에서 DB 조회를 수행하는 코드를 말한다.

```abap
LOOP AT lt_sflight INTO DATA(ls_sflight).

  SELECT SINGLE carrname
    FROM scarr
    WHERE carrid = @ls_sflight-carrid
    INTO @DATA(lv_carrname).

  WRITE: / ls_sflight-carrid,
           lv_carrname,
           ls_sflight-connid,
           ls_sflight-fldate.

ENDLOOP.
```

이 코드는 초급자가 보기에는 자연스럽다.

```text
항공편 한 줄을 읽는다.
그 항공편의 항공사 코드를 가져온다.
항공사 코드로 항공사명을 조회한다.
출력한다.
```

논리적으로는 맞다.  
하지만 성능 관점에서는 위험할 수 있다.

왜냐하면 `lt_sflight`에 10건이 있으면 `SELECT SINGLE`이 10번 실행되고,  
10,000건이 있으면 `SELECT SINGLE`이 10,000번 실행될 수 있기 때문이다.

---

## 4. 왜 문제가 되는가?

### 4.1 DB 접근 횟수 증가

ABAP 프로그램과 데이터베이스는 같은 논리 안에서 동작하지만, 성능 관점에서는 DB 접근이 비용이 큰 작업이다.

다음 두 코드를 비교해보자.

#### 방식 A: 반복문 안에서 계속 조회

```text
항공편 1건 처리 → 항공사명 SELECT 1회
항공편 2건 처리 → 항공사명 SELECT 1회
항공편 3건 처리 → 항공사명 SELECT 1회
...
항공편 10,000건 처리 → 항공사명 SELECT 10,000회
```

#### 방식 B: 필요한 항공사 정보를 한 번에 읽고 메모리에서 매칭

```text
항공편 데이터 SELECT 1회
항공사 데이터 SELECT 1회
Internal Table에서 READ 처리
```

DB 접근 횟수 관점에서 두 방식은 크게 다르다.

| 처리 대상 건수 | 반복 SELECT 방식 | 일괄 조회 방식 |
|---:|---:|---:|
| 10건 | 10회 추가 SELECT | 1회 또는 소수 SELECT |
| 1,000건 | 1,000회 추가 SELECT | 1회 또는 소수 SELECT |
| 100,000건 | 100,000회 추가 SELECT | 1회 또는 소수 SELECT |

실무에서는 이 차이가 응답시간, DB 부하, 배치 처리 시간, 사용자 대기 시간으로 이어질 수 있다.

### 4.2 작은 데이터에서는 문제가 숨어 있다

초급 실습에서는 데이터가 적다.  
예제 테이블에 5건, 10건 정도만 있으면 반복 SELECT도 빠르게 실행된다.

그래서 초급자는 다음과 같이 생각하기 쉽다.

```text
실행되는데요?
속도도 괜찮은데요?
문제가 없어 보이는데요?
```

하지만 운영 데이터는 다르다.

```text
개발 시스템: 10건
품질 시스템: 1,000건
운영 시스템: 1,000,000건
```

작은 데이터에서 드러나지 않던 성능 문제가 운영에서 폭발할 수 있다.

### 4.3 DB와 Application Server 사이의 왕복

반복 SELECT는 단순히 SQL이 여러 번 실행된다는 의미만이 아니다.  
ABAP Application Server와 DB 사이의 요청/응답 왕복이 반복된다는 의미이기도 하다.

```text
ABAP → DB 요청
DB → ABAP 결과 반환
ABAP → DB 요청
DB → ABAP 결과 반환
...
```

이런 왕복이 많아지면 처리 시간이 증가한다.  
특히 네트워크, DB 부하, 동시 사용자 수, 테이블 크기, 인덱스 상태에 따라 영향이 커질 수 있다.

## 5. 전형적인 안티패턴 예제

### 5.1 예제 시나리오

SFLIGHT에서 항공편을 조회한 뒤, 각 항공편의 항공사명을 SCARR에서 조회해 출력한다고 가정한다.

표준 학습용 테이블 기준으로 다음 관계를 생각할 수 있다.

| 테이블 | 역할 |
|---|---|
| SCARR | 항공사 마스터 |
| SFLIGHT | 항공편 데이터 |
| 공통 필드 | CARRID |

### 5.2 나쁜 예: LOOP 안의 SELECT SINGLE

```abap
REPORT zopen_sql_bad_select_loop.

SELECT carrid,
       connid,
       fldate,
       price,
       currency
  FROM sflight
  INTO TABLE @DATA(lt_flight)
  UP TO 100 ROWS.

LOOP AT lt_flight INTO DATA(ls_flight).

  SELECT SINGLE carrname
    FROM scarr
    WHERE carrid = @ls_flight-carrid
    INTO @DATA(lv_carrname).

  IF sy-subrc <> 0.
    lv_carrname = 'Unknown Carrier'.
  ENDIF.

  WRITE: / ls_flight-carrid,
           lv_carrname,
           ls_flight-connid,
           ls_flight-fldate,
           ls_flight-price,
           ls_flight-currency.

ENDLOOP.
```

이 코드는 교육용으로는 이해하기 쉽다.  
하지만 성능 관점에서는 위험 패턴이다.

### 5.3 무엇이 문제인가?

문제는 다음 줄이 반복문 안에 있다는 점이다.

```abap
SELECT SINGLE carrname
  FROM scarr
  WHERE carrid = @ls_flight-carrid
  INTO @DATA(lv_carrname).
```

`lt_flight`가 100건이면 SCARR 조회가 최대 100번 발생한다.  
`lt_flight`가 10,000건이면 SCARR 조회가 최대 10,000번 발생한다.

SCARR처럼 작은 마스터 테이블이라도 이런 습관은 좋지 않다.  
작은 테이블에서 허용된 습관이 큰 테이블에서도 반복되기 때문이다.

## 6. 개선 방향 1: 관련 데이터를 먼저 읽고 메모리에서 찾기

### 6.1 기본 아이디어

개선의 기본 아이디어는 다음이다.

```text
반복문 안에서 DB를 매번 조회하지 않는다.
필요한 참조 데이터를 미리 읽어 Internal Table에 담는다.
반복문 안에서는 Internal Table을 READ한다.
```

초급 단계에서는 JOIN이나 FOR ALL ENTRIES를 깊게 다루기 전이므로, 먼저 작은 참조 테이블을 전체 조회해 메모리에서 읽는 방식으로 감각을 잡을 수 있다.

### 6.2 개선 예제

```abap
REPORT zopen_sql_better_read_table.

SELECT carrid,
       carrname
  FROM scarr
  INTO TABLE @DATA(lt_scarr).

SELECT carrid,
       connid,
       fldate,
       price,
       currency
  FROM sflight
  INTO TABLE @DATA(lt_flight)
  UP TO 100 ROWS.

LOOP AT lt_flight INTO DATA(ls_flight).

  READ TABLE lt_scarr INTO DATA(ls_scarr)
    WITH KEY carrid = ls_flight-carrid.

  IF sy-subrc = 0.
    DATA(lv_carrname) = ls_scarr-carrname.
  ELSE.
    lv_carrname = 'Unknown Carrier'.
  ENDIF.

  WRITE: / ls_flight-carrid,
           lv_carrname,
           ls_flight-connid,
           ls_flight-fldate,
           ls_flight-price,
           ls_flight-currency.

ENDLOOP.
```

이 방식에서는 SCARR 테이블을 한 번 읽는다.  
그 후 반복문 안에서는 DB가 아니라 Internal Table `lt_scarr`를 읽는다.

### 6.3 초급자에게 중요한 포인트

이 코드는 최종 성능 최적화 코드라기보다 학습용 개선 코드이다.  
특히 `READ TABLE ... WITH KEY`는 Internal Table 타입과 정렬/키 설계에 따라 성능이 달라질 수 있다.

하지만 이번 모듈의 핵심은 이것이다.

```text
DB를 반복 호출하는 습관을 줄이고,
가능하면 필요한 데이터를 한 번에 읽어 메모리에서 처리한다.
```

Internal Table의 상세 성능은 후속 Section에서 더 자세히 학습한다.

## 7. 개선 방향 2: JOIN으로 한 번에 읽기

### 7.1 개념 미리보기

Open SQL 심화에서는 JOIN을 사용해 관련 테이블 데이터를 한 번에 조회할 수 있다.

예를 들어 SFLIGHT와 SCARR를 CARRID로 연결하면 항공편 데이터와 항공사명을 함께 읽을 수 있다.

```abap
SELECT f~carrid,
       c~carrname,
       f~connid,
       f~fldate,
       f~price,
       f~currency
  FROM sflight AS f
  INNER JOIN scarr AS c
    ON c~carrid = f~carrid
  INTO TABLE @DATA(lt_result)
  UP TO 100 ROWS.
```

이 방식은 반복문 안에서 SCARR를 계속 조회하지 않는다.  
DB가 테이블 관계를 이용해 필요한 결과를 한 번에 구성한다.

### 7.2 이번 모듈에서 JOIN을 깊게 다루지 않는 이유

JOIN은 매우 중요하지만, 이번 Section은 Open SQL 1차 기본 조회이다.  
JOIN과 집계 조회는 별도 Section에서 다룬다.

따라서 이번 모듈에서는 다음 수준만 이해하면 충분하다.

```text
반복 SELECT를 줄이기 위한 대표 대안 중 하나가 JOIN이다.
하지만 JOIN은 후속 Section에서 정확한 문법과 실무 기준을 별도로 학습한다.
```

## 8. 개선 방향 3: FOR ALL ENTRIES 또는 IN 조건

반복 SELECT를 줄이는 또 다른 방식은 필요한 Key 목록을 먼저 모은 뒤, 해당 Key들에 해당하는 데이터만 한 번에 조회하는 것이다.

예를 들어 항공편 데이터에 등장한 `CARRID` 목록을 모아 SCARR에서 필요한 항공사만 읽을 수 있다.

이 패턴은 후속 Open SQL 심화에서 더 적절하게 다룬다.

이번 단계에서는 다음 정도만 기억한다.

```text
반복문 안에서 한 건씩 SELECT하지 않고,
필요한 Key 목록을 모아 한 번에 조회하는 방식이 있다.
```

단, `FOR ALL ENTRIES`에는 빈 Internal Table 처리, 중복 제거, WHERE 조건 작성 등 주의사항이 있다.  
초급 단계에서 잘못 배우면 오히려 오류를 만들 수 있으므로 이 문서에서는 개념만 소개한다.

## 9. SELECT SINGLE은 항상 나쁜가?

아니다.

`SELECT SINGLE` 자체가 나쁜 것이 아니다.  
문제는 `SELECT SINGLE`을 반복문 안에서 대량으로 호출하는 습관이다.

### 9.1 SELECT SINGLE이 적절한 경우

다음 상황에서는 `SELECT SINGLE`이 적절할 수 있다.

| 상황 | 설명 |
|---|---|
| 화면에서 입력한 특정 Key 한 건을 조회 | 사용자가 입력한 고객번호 1건 조회 |
| 존재 여부 확인 | 특정 코드가 존재하는지 단건 확인 |
| Primary Key 또는 Unique Key 기반 조회 | 한 건만 나오는 것이 명확한 경우 |
| 반복문 밖에서 1회 수행 | 전체 처리 중 단 한 번 필요한 값 조회 |

예시:

```abap
PARAMETERS p_carrid TYPE scarr-carrid.

SELECT SINGLE carrname
  FROM scarr
  WHERE carrid = @p_carrid
  INTO @DATA(lv_carrname).

IF sy-subrc = 0.
  WRITE: / lv_carrname.
ELSE.
  WRITE: / 'Carrier not found.'.
ENDIF.
```

이 코드는 사용자 입력값 기준으로 한 번만 조회하므로 반복 SELECT 문제가 아니다.

### 9.2 SELECT SINGLE이 위험해지는 경우

다음 상황이 위험하다.

```abap
LOOP AT lt_data INTO DATA(ls_data).

  SELECT SINGLE ...
    FROM ...
    WHERE key = @ls_data-key
    INTO ...

ENDLOOP.
```

즉, `SELECT SINGLE`의 문제가 아니라 “반복 구조 안에서 DB를 계속 호출하는 구조”가 문제이다.

## 10. 성능 위험을 판단하는 질문

코드를 작성하거나 리뷰할 때 다음 질문을 사용한다.

```text
이 SELECT는 반복문 안에 있는가?
반복문이 최대 몇 번 실행될 수 있는가?
반복 대상 데이터 건수가 운영에서 얼마나 커질 수 있는가?
같은 Key를 여러 번 조회할 가능성이 있는가?
참조 데이터를 미리 읽어둘 수 있는가?
JOIN으로 한 번에 읽을 수 있는가?
조회 결과를 Internal Table에서 재사용할 수 있는가?
```

위 질문 중 하나라도 위험 신호가 있다면 반복 SELECT를 개선할 수 있는지 검토해야 한다.

## 11. 중복 Key 반복 조회 문제

반복 SELECT의 또 다른 문제는 같은 Key를 여러 번 조회할 수 있다는 점이다.

예를 들어 SFLIGHT에는 같은 `CARRID`가 여러 번 등장한다.

| 행 | CARRID | CONNID |
|---:|---|---|
| 1 | AA | 0017 |
| 2 | AA | 0064 |
| 3 | LH | 0400 |
| 4 | AA | 0100 |
| 5 | LH | 0500 |

반복 SELECT 방식이라면 `AA`에 대한 SCARR 조회가 여러 번 실행될 수 있다.  
하지만 SCARR의 항공사명은 같은 `CARRID`에 대해 한 번만 읽어도 된다.

이때는 다음 전략이 가능하다.

```text
필요한 Key를 모은다.
중복 Key를 제거한다.
참조 데이터를 한 번에 조회한다.
반복문 안에서는 메모리에서 찾는다.
```

초급 단계에서는 이 전략을 완벽히 구현하지 않아도 된다.  
중요한 것은 “같은 데이터를 여러 번 DB에서 읽는 것은 낭비일 수 있다”는 감각이다.

## 12. 실습: 나쁜 코드와 개선 코드 비교

### 12.1 실습 목표

다음 두 프로그램을 비교한다.

| 프로그램 | 목적 |
|---|---|
| `ZSQL_BAD_SELECT_LOOP` | 반복문 내부 SELECT 안티패턴 확인 |
| `ZSQL_BETTER_READ_TABLE` | 참조 데이터를 미리 읽는 개선 방향 확인 |

### 12.2 나쁜 코드

```abap
REPORT zsql_bad_select_loop.

SELECT carrid,
       connid,
       fldate
  FROM sflight
  INTO TABLE @DATA(lt_flight)
  UP TO 50 ROWS.

LOOP AT lt_flight INTO DATA(ls_flight).

  SELECT SINGLE carrname
    FROM scarr
    WHERE carrid = @ls_flight-carrid
    INTO @DATA(lv_carrname).

  WRITE: / ls_flight-carrid,
           lv_carrname,
           ls_flight-connid,
           ls_flight-fldate.

ENDLOOP.
```

### 12.3 개선 코드

```abap
REPORT zsql_better_read_table.

SELECT carrid,
       carrname
  FROM scarr
  INTO TABLE @DATA(lt_scarr).

SELECT carrid,
       connid,
       fldate
  FROM sflight
  INTO TABLE @DATA(lt_flight)
  UP TO 50 ROWS.

LOOP AT lt_flight INTO DATA(ls_flight).

  READ TABLE lt_scarr INTO DATA(ls_scarr)
    WITH KEY carrid = ls_flight-carrid.

  IF sy-subrc = 0.
    DATA(lv_carrname) = ls_scarr-carrname.
  ELSE.
    lv_carrname = 'Unknown Carrier'.
  ENDIF.

  WRITE: / ls_flight-carrid,
           lv_carrname,
           ls_flight-connid,
           ls_flight-fldate.

ENDLOOP.
```

### 12.4 실습 기록

실습자는 다음을 기록한다.

| 기록 항목 | 나쁜 코드 | 개선 코드 |
|---|---|---|
| DB SELECT 위치 | LOOP 안 | LOOP 밖 |
| SCARR 조회 횟수 | 반복 건수만큼 가능 | 1회 |
| 코드 이해 난이도 | 쉬움 | 약간 증가 |
| 성능 위험 | 높음 | 낮음 |
| 후속 개선 가능성 | JOIN, FAE 필요 | Internal Table 키 설계 필요 |

## 13. 디버깅과 확인 포인트

### 13.1 반복 횟수 확인

디버깅 시 다음을 확인한다.

```text
lt_flight에 몇 건이 들어왔는가?
LOOP가 몇 번 반복되는가?
LOOP 안의 SELECT가 몇 번 실행되는가?
```

초급자는 디버거에서 `lt_flight`의 라인 수와 반복 횟수를 직접 확인하는 것이 좋다.

### 13.2 Breakpoint 위치

나쁜 코드에서는 다음 위치에 Breakpoint를 걸어본다.

```abap
SELECT SINGLE carrname
  FROM scarr
  WHERE carrid = @ls_flight-carrid
  INTO @DATA(lv_carrname).
```

프로그램을 실행하면 Breakpoint가 반복해서 걸리는 것을 볼 수 있다.  
이것이 바로 “반복문 안에서 DB 조회가 반복 실행된다”는 증거이다.

### 13.3 SY-SUBRC 확인

`SELECT SINGLE` 후에는 `sy-subrc`를 확인할 수 있다.

| SY-SUBRC | 의미 |
|---:|---|
| 0 | 데이터 조회 성공 |
| 4 | 조건에 맞는 데이터 없음 |

하지만 이번 모듈의 핵심은 `sy-subrc` 값 자체가 아니다.  
핵심은 `sy-subrc`를 확인하는 SELECT가 반복문 안에서 너무 자주 실행될 수 있다는 점이다.

## 16. 실무 예외: 반복 SELECT가 항상 금지인가?

반복 SELECT는 안티패턴으로 취급하는 것이 안전하지만, 모든 상황에서 절대 금지는 아니다.

예외적으로 다음 조건이 모두 만족되면 큰 문제가 아닐 수 있다.

| 조건 | 설명 |
|---|---|
| 반복 횟수가 매우 작음 | 예: 최대 3~5회 |
| 조회 대상이 작고 안정적임 | 작은 설정 테이블 |
| 대안 코드가 과도하게 복잡함 | 가독성과 단순성이 더 중요할 수 있음 |
| 성능 측정 결과 문제가 없음 | 실제 Trace/Runtime 기준 확인 |
| 운영 데이터 증가 가능성이 낮음 | 장기적으로도 데이터량이 제한됨 |

하지만 초급자는 예외부터 배우면 위험하다.  
따라서 기본 원칙은 다음으로 둔다.

```text
반복문 안의 SELECT는 먼저 안티패턴으로 의심한다.
예외는 실무 근거가 있을 때만 인정한다.
```

## 17. Clean Code 관점

반복 SELECT는 성능 문제뿐 아니라 코드 구조 문제이기도 하다.

### 17.1 데이터 수집과 처리의 분리

좋은 구조는 보통 다음처럼 나뉜다.

```text
1. 필요한 DB 데이터 수집
2. Internal Table 형태로 준비
3. 비즈니스 로직 처리
4. 출력 또는 후속 처리
```

나쁜 구조는 다음처럼 섞인다.

```text
LOOP
  DB 조회
  비즈니스 처리
  출력
ENDLOOP
```

DB 조회와 처리 로직이 섞이면 테스트, 디버깅, 성능 분석이 어려워진다.

### 17.2 유지보수성

반복 SELECT가 많은 프로그램은 다음 문제가 생긴다.

| 문제 | 설명 |
|---|---|
| 성능 원인 추적 어려움 | 어떤 SELECT가 병목인지 찾기 어려움 |
| DB 의존 로직 증가 | 테스트와 재사용이 어려움 |
| 중복 조회 증가 | 같은 데이터를 여러 번 읽음 |
| 후속 기능 추가 위험 | 출력 필드 하나 추가할 때 SELECT가 더 늘어날 수 있음 |

초급자는 SQL 성능을 처음부터 완벽히 알 수 없다.

```text
Step 1. SELECT가 LOOP 안에 있는지 찾는다.

Step 4. 먼저 한 번에 읽을 수 있는지 생각한다.
Step 5. JOIN/FAE/IN 조건은 후속 학습 주제로 연결한다.
Step 6. 실무에서는 ST05, SAT, ATC 등으로 검증한다.
```

이 프레임만 있어도 초급 단계에서 상당히 많은 위험 코드를 사전에 발견할 수 있다.

## 19. 후속 Section 연결

이번 모듈에서 반복 SELECT의 위험성을 이해하면 이후 학습이 훨씬 자연스럽다.

| 후속 주제 | 연결 |
|---|---|
| Open SQL JOIN | 반복 조회 대신 DB에서 관계 데이터를 한 번에 결합 |
| 집계 조회 | 반복 계산 대신 DB에서 SUM/COUNT/GROUP BY 처리 |
| Internal Table 심화 | 조회 결과를 메모리에서 효율적으로 검색 |
| Modern ABAP Syntax | Inline Declaration, Table Expression 등으로 코드 간결화 |
| New Open SQL | 더 표현력 있는 SQL 문법으로 조회 최적화 |
| CDS View | 데이터 모델과 조회 로직을 DB에 더 가깝게 정의 |
| RAP | 비즈니스 객체의 데이터 접근 패턴과 성능 고려 |

특히 이후 `JOIN/집계 조회`를 배울 때 다음 질문이 중요해진다.

```text
왜 굳이 JOIN을 배워야 하는가?
```

그 답 중 하나가 바로 이번 모듈이다.

```text
반복 SELECT를 줄이고 필요한 데이터를 한 번에 가져오기 위해서이다.
```

A.

```abap
SELECT carrid FROM scarr INTO TABLE @DATA(lt_scarr).
```

```abap
READ TABLE lt_scarr INTO DATA(ls_scarr) WITH KEY carrid = lv_carrid.
```

A. `SELECT SINGLE` 자체는 항상 금지이다.  
B. 반복문 안에서 대량으로 호출될 때 성능 위험이 커질 수 있다.  
C. `SELECT SINGLE`은 DB에 접근하지 않는다.

**정답:** B

### 20.2 단답형

#### Q1. 반복 SELECT를 발견했을 때 가장 먼저 확인할 것은 무엇인가?

**모범 답안:**  
SELECT가 어떤 반복문 안에 있는지, 해당 반복문이 운영 환경에서 최대 몇 건까지 실행될 수 있는지 확인한다.

#### Q2. 반복 SELECT를 줄이는 기본 방향을 설명하시오.

**모범 답안:**  
필요한 데이터를 반복문 밖에서 한 번에 조회하여 Internal Table에 저장하고, 반복문 안에서는 DB가 아니라 Internal Table을 읽도록 개선한다. 또는 관계가 명확한 경우 JOIN 등으로 한 번에 조회하는 방식을 검토한다.

#### Q3. 개발 시스템에서는 빠른 코드가 운영 시스템에서 느려질 수 있는 이유는?

**모범 답안:**  
개발 시스템은 테스트 데이터가 적지만 운영 시스템은 데이터 건수가 많고 동시 사용자와 DB 부하가 크기 때문이다. 반복 SELECT처럼 데이터 건수에 따라 DB 접근 횟수가 증가하는 코드는 운영에서 성능 문제가 커질 수 있다.

## 22. 강사용 설명 포인트

강사는 이 모듈에서 “반복 SELECT는 왜 초급 때부터 조심해야 하는가?”를 명확히 설명해야 한다.

추천 설명 흐름은 다음이다.

```text
처음에는 작동하는 코드부터 보여준다.
그 코드가 왜 자연스러워 보이는지 인정한다.
하지만 데이터가 많아지면 SELECT 횟수가 폭증한다는 점을 보여준다.
반복문 안 SELECT 위치에 Breakpoint를 걸어 반복 실행을 체감시킨다.
개선 코드는 DB 접근을 줄인다는 관점으로 설명한다.
JOIN/FAE는 다음 단계에서 배운다고 연결한다.
```

강의 중 사용할 질문:

```text
lt_flight가 50건이면 SELECT SINGLE은 몇 번 실행될까요?
lt_flight가 50,000건이면 어떤 일이 생길까요?
SCARR의 같은 CARRID를 여러 번 조회할 필요가 있을까요?
반복문 안에서 DB가 아니라 메모리를 읽게 바꾸면 어떤 장점이 있을까요?
```

---

## 23. 핵심 요약

```text
반복문 안의 SELECT는 성능 위험 패턴이다.
SELECT SINGLE 자체가 나쁜 것이 아니라 반복 호출 구조가 위험하다.
데이터가 적은 개발 시스템에서는 문제가 숨어 있을 수 있다.
운영 데이터가 많아지면 DB 접근 횟수가 폭증할 수 있다.
참조 데이터는 반복문 밖에서 미리 읽고 Internal Table에서 찾는 방식으로 개선할 수 있다.
JOIN, FOR ALL ENTRIES, IN 조건은 반복 SELECT를 줄이는 후속 학습 주제이다.
LOOP 안의 SELECT를 보면 먼저 멈추고 생각해야 한다.
```

## 24. 체크리스트

학습자는 이 모듈을 마친 후 다음 항목을 점검한다.

| 체크 항목 | 완료 |
|---|---|
| 반복 SELECT가 무엇인지 설명할 수 있다. |  |
| `SELECT in LOOP` 안티패턴 코드를 식별할 수 있다. |  |
| 반복 건수와 DB 접근 횟수의 관계를 설명할 수 있다. |  |
| `SELECT SINGLE` 자체와 반복 호출 구조를 구분할 수 있다. |  |
| 참조 데이터를 미리 읽어 Internal Table에서 찾는 기본 개선 방향을 설명할 수 있다. |  |
| JOIN이 반복 SELECT를 줄이는 후속 대안임을 이해한다. |  |
| 실무 코드 리뷰에서 LOOP 안 SELECT를 발견하면 위험 신호로 판단할 수 있다. |  |
