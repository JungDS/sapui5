## 0. 이 문서의 학습 범위

이 문서는 `THEORY-09-M05 — 명시적 Target Table 선언 방식`만 다룬다.

이전 모듈에서는 `SELECT ... INTO TABLE @DATA(lt_result)` 형태로 조회 결과를 **인라인 선언된 Internal Table**에 담는 방식을 학습했다.  
이번 모듈에서는 조회 대상 테이블의 결과 구조를 미리 정의하고, 명시적으로 선언한 Internal Table에 조회 결과를 담는 방식을 학습한다.

이번 모듈의 핵심은 다음 세 가지이다.

| 핵심 키워드 | 의미 |
|---|---|
| `DATA lt_table` | 조회 결과를 받을 Internal Table을 명시적으로 선언하는 방식 |
| Typed Internal Table | Line Type이 명확하게 정의된 Internal Table |
| Target Variable | `SELECT` 결과가 들어갈 대상 변수 또는 대상 테이블 |

초급자는 이번 모듈을 통해 다음 차이를 이해해야 한다.

```abap
" 인라인 선언 방식
SELECT carrid, connid, fldate
  FROM sflight
  INTO TABLE @DATA(lt_flights).

" 명시적 Target Table 선언 방식
TYPES: BEGIN OF ty_flight,
         carrid TYPE sflight-carrid,
         connid TYPE sflight-connid,
         fldate TYPE sflight-fldate,
       END OF ty_flight.

DATA lt_flights TYPE STANDARD TABLE OF ty_flight.

SELECT carrid, connid, fldate
  FROM sflight
  INTO TABLE @lt_flights.
```

두 방식 모두 정상적인 ABAP SQL 패턴이다.  
다만 실무에서는 프로그램이 복잡해질수록 **명시적 타입 선언 방식**이 유지보수성과 인터페이스 안정성 측면에서 더 적합한 경우가 많다.

## 2. 선행 지식

이번 모듈은 `Open SQL 1차: 기본 조회` Section 안에서 다섯 번째 단계이다.  
다음 내용을 이미 알고 있어야 한다.

| 선행 모듈 | 필요한 이유 |
|---|---|
| THEORY-09-M01 SELECT FROM / FIELDS 기본 구조 | SELECT 문의 기본 골격을 알아야 한다. |
| THEORY-09-M02 WHERE 조건과 Host Variable @ 기초 | `@`를 사용한 ABAP 변수 전달 방식을 알아야 한다. |
| THEORY-09-M03 SELECT SINGLE과 단건 조회 | 단건 Target Variable과 다건 Target Table의 차이를 비교할 수 있어야 한다. |
| THEORY-09-M04 INTO TABLE로 Internal Table 적재 | SELECT 결과를 Internal Table에 담는 기본 흐름을 알아야 한다. |
| Internal Table 기본 | Standard Table, Work Area, LOOP AT 개념을 알아야 한다. |

초급자에게 가장 중요한 선행 개념은 다음이다.

```text
SELECT는 DB에서 데이터를 읽는다.
INTO TABLE은 읽은 여러 건을 Internal Table에 담는다.
Target Table은 SELECT 결과를 받을 ABAP 메모리상의 대상이다.
```

## 3. 왜 명시적 Target Table 선언을 배우는가?

ABAP 7.40 이후 문법에서는 `@DATA(...)`를 통해 조회 결과를 매우 간단히 받을 수 있다.

```abap
SELECT carrid, connid, fldate
  FROM sflight
  INTO TABLE @DATA(lt_flights).
```

이 방식은 초급 학습과 간단한 프로그램 작성에 매우 편리하다.  
하지만 모든 상황에서 인라인 선언이 최선은 아니다.

명시적 Target Table 선언이 필요한 대표 이유는 다음과 같다.

| 이유 | 설명 |
|---|---|
| 구조를 미리 문서화할 수 있음 | 조회 결과의 필드 구성을 코드 상단에서 명확히 볼 수 있다. |
| 여러 SELECT에서 같은 타입을 재사용 가능 | 같은 결과 구조를 여러 로직에서 공유할 수 있다. |
| 메서드/FORM/함수 파라미터와 연결하기 쉬움 | 타입이 명확하므로 인터페이스 설계에 유리하다. |
| ALV 출력 구조로 재사용 가능 | 출력 필드 구조를 별도 타입으로 관리할 수 있다. |
| 복잡한 조회 결과를 통제하기 쉬움 | JOIN, 계산 필드, Alias, CASE 결과를 명확히 담을 수 있다. |
| 유지보수자가 구조를 파악하기 쉬움 | `@DATA` 결과 타입을 추론하지 않아도 된다. |

실무에서는 단순 조회에는 인라인 선언을 쓰고, 재사용성과 구조 안정성이 필요한 경우 명시적 타입 선언을 사용하는 식으로 균형 있게 접근한다.

## 4. 인라인 선언 방식 복습

이전 모듈에서 다룬 가장 간단한 다건 조회 패턴은 다음과 같다.

```abap
REPORT zgpt_open_sql_inline.

PARAMETERS p_carrid TYPE sflight-carrid DEFAULT 'AA'.

SELECT carrid,
       connid,
       fldate,
       price,
       currency
  FROM sflight
  WHERE carrid = @p_carrid
  INTO TABLE @DATA(lt_flights).

LOOP AT lt_flights INTO DATA(ls_flight).
  WRITE: / ls_flight-carrid,
           ls_flight-connid,
           ls_flight-fldate,
           ls_flight-price,
           ls_flight-currency.
ENDLOOP.
```

이 코드는 짧고 읽기 쉽다.  
ABAP 컴파일러가 SELECT 필드 목록을 보고 `lt_flights`의 Row Type을 추론한다.

하지만 단점도 있다.

```text
lt_flights의 구조를 코드 상단에서 바로 확인하기 어렵다.
같은 구조를 다른 로직에서 재사용하기 어렵다.
ALV 출력이나 메서드 파라미터로 넘길 때 타입이 드러나지 않을 수 있다.
필드가 많아지거나 JOIN이 들어가면 추론된 구조를 관리하기 어려워진다.
```

따라서 이번 모듈에서는 명시적 선언 방식을 익힌다.

## 5. 명시적 Target Table 선언의 기본 구조

명시적 Target Table 선언 방식은 보통 다음 세 단계로 구성된다.

```text
1. 조회 결과 한 줄의 구조를 TYPES로 정의한다.
2. 그 구조를 Line Type으로 가지는 Internal Table을 DATA로 선언한다.
3. SELECT 결과를 INTO TABLE @lt_table에 담는다.
```

### 5.1 기본 예제

```abap
REPORT zgpt_open_sql_explicit.

PARAMETERS p_carrid TYPE sflight-carrid DEFAULT 'AA'.

TYPES: BEGIN OF ty_flight,
         carrid   TYPE sflight-carrid,
         connid   TYPE sflight-connid,
         fldate   TYPE sflight-fldate,
         price    TYPE sflight-price,
         currency TYPE sflight-currency,
       END OF ty_flight.

DATA lt_flights TYPE STANDARD TABLE OF ty_flight.
DATA ls_flight  TYPE ty_flight.

SELECT carrid,
       connid,
       fldate,
       price,
       currency
  FROM sflight
  WHERE carrid = @p_carrid
  INTO TABLE @lt_flights.

LOOP AT lt_flights INTO ls_flight.
  WRITE: / ls_flight-carrid,
           ls_flight-connid,
           ls_flight-fldate,
           ls_flight-price,
           ls_flight-currency.
ENDLOOP.
```

이 예제에서 핵심은 다음이다.

| 코드 | 의미 |
|---|---|
| `TYPES: BEGIN OF ty_flight` | 조회 결과 한 줄의 구조를 정의한다. |
| `DATA lt_flights TYPE STANDARD TABLE OF ty_flight` | 여러 건을 담을 Internal Table을 선언한다. |
| `DATA ls_flight TYPE ty_flight` | LOOP에서 한 줄씩 받을 Work Area를 선언한다. |
| `INTO TABLE @lt_flights` | SELECT 결과 전체를 명시적 Internal Table에 담는다. |

## 6. Target Table과 Line Type

### 6.1 Target Table이란?

Target Table은 SELECT 결과를 받을 Internal Table이다.

```abap
DATA lt_flights TYPE STANDARD TABLE OF ty_flight.
```

여기서 `lt_flights`가 Target Table이다.

초급자 관점에서 Target Table은 다음과 같이 이해하면 된다.

```text
DB에서 조회한 여러 행을 ABAP 메모리 안에 담아두는 표 형태의 변수
```

### 6.2 Line Type이란?

Internal Table은 여러 줄을 담는 표이고, 각 줄은 같은 구조를 가진다.  
그 한 줄의 구조를 Line Type이라고 한다.

```abap
TYPES: BEGIN OF ty_flight,
         carrid   TYPE sflight-carrid,
         connid   TYPE sflight-connid,
         fldate   TYPE sflight-fldate,
       END OF ty_flight.
```

여기서 `ty_flight`는 Line Type이다.

즉 다음 관계가 성립한다.

```text
ty_flight  = lt_flights의 한 줄 구조
lt_flights = ty_flight 여러 줄을 담는 Internal Table
```

### 6.3 Work Area와의 관계

명시적 방식에서는 Work Area도 같은 Line Type으로 선언하는 경우가 많다.

```abap
DATA ls_flight TYPE ty_flight.

LOOP AT lt_flights INTO ls_flight.
  WRITE: / ls_flight-carrid,
           ls_flight-connid.
ENDLOOP.
```

| 변수 | 역할 |
|---|---|
| `lt_flights` | 여러 건을 담는 Internal Table |
| `ls_flight` | LOOP에서 한 건씩 받는 Work Area |
| `ty_flight` | 한 건의 구조를 정의한 타입 |

## 7. SELECT 필드 목록과 Target 구조의 대응

명시적 Target Table을 사용할 때 가장 중요한 것은 SELECT 필드 목록과 Target 구조의 대응이다.

### 7.1 같은 순서로 맞추는 방식

가장 단순한 방식은 SELECT 필드 순서와 `ty_flight` 필드 순서를 맞추는 것이다.

```abap
TYPES: BEGIN OF ty_flight,
         carrid   TYPE sflight-carrid,
         connid   TYPE sflight-connid,
         fldate   TYPE sflight-fldate,
       END OF ty_flight.

SELECT carrid,
       connid,
       fldate
  FROM sflight
  INTO TABLE @DATA(lt_inline). " 비교용
```

명시적 Target Table에서는 다음처럼 사용한다.

```abap
DATA lt_flights TYPE STANDARD TABLE OF ty_flight.

SELECT carrid,
       connid,
       fldate
  FROM sflight
  INTO TABLE @lt_flights.
```

이때 SELECT 목록과 Target Line Type이 자연스럽게 대응된다.

### 7.2 필드 이름 기반 대응을 고려해야 하는 경우

실무에서는 `INTO CORRESPONDING FIELDS OF TABLE` 패턴을 사용하는 경우도 있다.

```abap
SELECT carrid,
       connid,
       fldate
  FROM sflight
  INTO CORRESPONDING FIELDS OF TABLE @lt_flights.
```

이 방식은 필드 순서보다 이름 기반 대응에 초점을 둔다.  
다만 초급 단계에서는 먼저 기본 `INTO TABLE @lt_table` 방식으로 구조 대응을 이해하는 것이 중요하다.

> 주의: `INTO CORRESPONDING FIELDS OF TABLE`은 편리하지만, 필드명 불일치나 누락 필드를 놓치기 쉬울 수 있다. 구조가 명확한 초급 실습에서는 SELECT 필드와 Target 구조를 의도적으로 맞추는 연습이 좋다.

## 8. `@` Host Variable 표기의 의미 유지

ABAP SQL에서 ABAP 변수나 Internal Table 같은 Host Variable을 사용할 때는 `@`를 붙인다.

```abap
WHERE carrid = @p_carrid
INTO TABLE @lt_flights
```

여기서 `@p_carrid`는 SQL 조건에 전달되는 ABAP 변수이고, `@lt_flights`는 SQL 결과를 받을 ABAP Internal Table이다.

초급자가 자주 하는 실수는 다음과 같다.

```abap
SELECT carrid, connid
  FROM sflight
  WHERE carrid = p_carrid
  INTO TABLE lt_flights.
```

최신 ABAP SQL 문법에서는 Host Variable을 명확히 표시하기 위해 `@`를 사용하는 방식이 중요하다.

올바른 형태는 다음이다.

```abap
SELECT carrid, connid
  FROM sflight
  WHERE carrid = @p_carrid
  INTO TABLE @lt_flights.
```

## 9. 실습 예제 1 — SFLIGHT 기본 조회

### 9.1 실습 목표

항공편 테이블 `SFLIGHT`에서 특정 항공사(`CARRID`)의 항공편 목록을 조회하여 명시적으로 선언한 Internal Table에 담는다.

### 9.2 전체 코드

```abap
REPORT zgpt_sql_target_01.

PARAMETERS p_carrid TYPE sflight-carrid DEFAULT 'AA'.

TYPES: BEGIN OF ty_flight,
         carrid   TYPE sflight-carrid,
         connid   TYPE sflight-connid,
         fldate   TYPE sflight-fldate,
         price    TYPE sflight-price,
         currency TYPE sflight-currency,
       END OF ty_flight.

DATA lt_flights TYPE STANDARD TABLE OF ty_flight.
DATA ls_flight  TYPE ty_flight.

SELECT carrid,
       connid,
       fldate,
       price,
       currency
  FROM sflight
  WHERE carrid = @p_carrid
  INTO TABLE @lt_flights.

IF sy-subrc <> 0.
  WRITE: / '조회된 항공편 데이터가 없습니다.' .
  RETURN.
ENDIF.

WRITE: / '조회 항공사:', p_carrid,
       / '조회 건수:', lines( lt_flights ).

ULINE.

LOOP AT lt_flights INTO ls_flight.
  WRITE: / ls_flight-carrid,
           ls_flight-connid,
           ls_flight-fldate,
           ls_flight-price,
           ls_flight-currency.
ENDLOOP.
```

### 9.3 코드 해설

| 구문 | 설명 |
|---|---|
| `PARAMETERS p_carrid` | 조회 조건으로 사용할 항공사 코드를 입력받는다. |
| `TYPES ... ty_flight` | 조회 결과 한 줄의 구조를 명시적으로 정의한다. |
| `DATA lt_flights` | 조회 결과 전체를 받을 Internal Table을 선언한다. |
| `SELECT ... INTO TABLE @lt_flights` | DB 조회 결과를 Target Table에 담는다. |
| `sy-subrc` | 조회 결과 존재 여부를 확인한다. |
| `lines( lt_flights )` | Internal Table의 행 수를 확인한다. |
| `LOOP AT` | 조회 결과를 한 줄씩 출력한다. |

## 10. 실습 예제 2 — SCARR 기본 조회

`SCARR`는 항공사 마스터 성격의 표준 학습 테이블이다.  
필드 수가 적어 초급자가 Target 구조를 이해하기 좋다.

```abap
REPORT zgpt_sql_target_02.

TYPES: BEGIN OF ty_carrier,
         carrid   TYPE scarr-carrid,
         carrname TYPE scarr-carrname,
         currcode TYPE scarr-currcode,
         url      TYPE scarr-url,
       END OF ty_carrier.

DATA lt_carriers TYPE STANDARD TABLE OF ty_carrier.
DATA ls_carrier  TYPE ty_carrier.

SELECT carrid,
       carrname,
       currcode,
       url
  FROM scarr
  INTO TABLE @lt_carriers.

LOOP AT lt_carriers INTO ls_carrier.
  WRITE: / ls_carrier-carrid,
           ls_carrier-carrname,
           ls_carrier-currcode,
           ls_carrier-url.
ENDLOOP.
```

### 10.1 학습 포인트

이 예제에서 중요한 점은 다음이다.

```text
SELECT 대상 필드와 TYPES 구조가 동일한 의미로 맞춰져 있다.
Internal Table은 명시적으로 선언되어 있다.
Work Area도 같은 Line Type으로 선언되어 있다.
조회 결과를 LOOP AT으로 순회할 수 있다.
```

## 11. 실습 예제 3 — 필요한 필드만 조회하기

실무에서 `SELECT *`를 무조건 사용하는 것은 좋지 않다.  
필요한 필드만 명시적으로 조회하면 데이터 전송량과 코드 가독성 측면에서 유리하다.

```abap
REPORT zgpt_sql_target_03.

PARAMETERS p_carrid TYPE sflight-carrid DEFAULT 'AA'.

TYPES: BEGIN OF ty_flight_key,
         carrid TYPE sflight-carrid,
         connid TYPE sflight-connid,
         fldate TYPE sflight-fldate,
       END OF ty_flight_key.

DATA lt_flight_keys TYPE STANDARD TABLE OF ty_flight_key.

SELECT carrid,
       connid,
       fldate
  FROM sflight
  WHERE carrid = @p_carrid
  INTO TABLE @lt_flight_keys.

WRITE: / '조회 건수:', lines( lt_flight_keys ).
```

이 예제는 항공편의 식별성 필드만 조회한다.  
조회 결과에 가격, 통화, 좌석 정보가 필요 없다면 굳이 가져오지 않는 것이 좋다.

## 12. 오류 상황과 해결 방법

### 12.1 Target Table이 선언되지 않음

#### 잘못된 예

```abap
SELECT carrid, connid
  FROM sflight
  INTO TABLE @lt_flights.
```

#### 문제

`lt_flights`가 사전에 선언되지 않았다면 Syntax Error가 발생한다.

#### 해결

먼저 타입과 Internal Table을 선언한다.

```abap
TYPES: BEGIN OF ty_flight,
         carrid TYPE sflight-carrid,
         connid TYPE sflight-connid,
       END OF ty_flight.

DATA lt_flights TYPE STANDARD TABLE OF ty_flight.
```

---

### 12.2 SELECT 필드와 Target 구조가 맞지 않음

#### 잘못된 예

```abap
TYPES: BEGIN OF ty_flight,
         carrid TYPE sflight-carrid,
         connid TYPE sflight-connid,
       END OF ty_flight.

DATA lt_flights TYPE STANDARD TABLE OF ty_flight.

SELECT carrid,
       connid,
       fldate
  FROM sflight
  INTO TABLE @lt_flights.
```

#### 문제

Target Line Type에는 `carrid`, `connid` 두 필드만 있는데 SELECT는 세 필드를 조회한다.  
이런 구조 불일치는 문법 오류 또는 할당 오류의 원인이 된다.

#### 해결

Target 구조에 `fldate`를 추가하거나 SELECT 필드에서 `fldate`를 제거한다.

```abap
TYPES: BEGIN OF ty_flight,
         carrid TYPE sflight-carrid,
         connid TYPE sflight-connid,
         fldate TYPE sflight-fldate,
       END OF ty_flight.
```

---

### 12.3 Host Variable `@` 누락

#### 잘못된 예

```abap
SELECT carrid, connid
  FROM sflight
  WHERE carrid = p_carrid
  INTO TABLE lt_flights.
```

#### 해결

```abap
SELECT carrid, connid
  FROM sflight
  WHERE carrid = @p_carrid
  INTO TABLE @lt_flights.
```

---

### 12.4 Work Area 타입 불일치

#### 잘못된 예

```abap
DATA ls_scarr TYPE scarr.

LOOP AT lt_flights INTO ls_scarr.
  WRITE: / ls_scarr-carrid.
ENDLOOP.
```

#### 문제

`lt_flights`의 Line Type이 `ty_flight`인데 Work Area가 `scarr` 구조라면 의미와 필드 구성이 맞지 않을 수 있다.

#### 해결

Work Area는 Internal Table의 Line Type과 맞춘다.

```abap
DATA ls_flight TYPE ty_flight.

LOOP AT lt_flights INTO ls_flight.
  WRITE: / ls_flight-carrid.
ENDLOOP.
```

## 13. 인라인 선언과 명시적 선언 비교

| 구분 | 인라인 선언 | 명시적 선언 |
|---|---|---|
| 대표 형태 | `INTO TABLE @DATA(lt_data)` | `DATA lt_data TYPE STANDARD TABLE OF ty_data` |
| 장점 | 코드가 짧고 빠르게 작성 가능 | 구조가 명확하고 재사용 가능 |
| 단점 | 타입 구조가 숨어 보일 수 있음 | 코드가 길어짐 |
| 적합한 상황 | 단순 조회, 짧은 프로그램, 일회성 처리 | 복잡한 프로그램, ALV, 메서드 파라미터, 재사용 구조 |
| 유지보수성 | 작은 코드에서는 좋음 | 큰 코드에서 좋음 |
| 초급 학습 효과 | 결과 타입 추론 경험 | 타입 설계와 데이터 흐름 이해 |

초급자에게 권장되는 학습 순서는 다음이다.

```text
1. 인라인 선언으로 SELECT 흐름을 빠르게 이해한다.
2. 명시적 선언으로 Target 구조와 타입 설계를 이해한다.
3. 실무에서는 코드 규모와 재사용성에 따라 선택한다.
```

## 14. 실무 적용 기준

### 14.1 명시적 선언을 권장하는 경우

| 상황 | 이유 |
|---|---|
| ALV 출력 구조가 필요한 경우 | 출력 필드 구조를 명확히 관리해야 한다. |
| 조회 결과를 여러 FORM/Method에서 재사용하는 경우 | 공통 타입으로 전달하기 쉽다. |
| JOIN 결과를 담는 경우 | 원본 테이블과 다른 결과 구조가 필요하다. |
| 계산 필드나 CASE 결과가 포함되는 경우 | Alias와 Target 필드를 명확히 맞춰야 한다. |
| 교육용으로 타입 이해가 필요한 경우 | Internal Table의 구조를 분명히 볼 수 있다. |

### 14.2 인라인 선언이 충분한 경우

| 상황 | 이유 |
|---|---|
| 짧은 테스트 프로그램 | 빠르게 작성하고 확인할 수 있다. |
| 조회 결과가 바로 한 곳에서만 사용됨 | 별도 타입 재사용 필요성이 낮다. |
| 필드 수가 적고 구조가 단순함 | 코드가 간결해진다. |
| 임시 분석용 코드 | 유지보수 기간이 짧다. |

### 14.3 실무 판단 질문

다음 질문 중 하나라도 “예”라면 명시적 선언을 검토한다.

```text
이 조회 결과를 ALV로 출력할 예정인가?
이 결과 구조를 여러 로직에서 재사용할 예정인가?
이 결과가 메서드나 함수의 파라미터로 전달되는가?
JOIN 또는 계산 필드가 포함되는가?
다른 개발자가 결과 구조를 쉽게 파악해야 하는가?
```

## 15. 성능 관점

명시적 Target Table 선언 자체가 조회 성능을 자동으로 높여주는 것은 아니다.  
성능에 직접적인 영향을 주는 것은 주로 다음 요소이다.

| 성능 요소 | 설명 |
|---|---|
| WHERE 조건 | 조회 범위를 줄이는 핵심 조건 |
| SELECT 필드 목록 | 필요한 필드만 조회하면 데이터 전송량 감소 |
| 인덱스 활용 | Key 조건과 DB 인덱스 활용 여부 |
| SELECT in LOOP 회피 | 반복문 안에서 DB 조회를 반복하지 않음 |
| 패키징/페이징 | 대량 데이터 처리 시 분할 처리 고려 |

명시적 선언은 성능보다 **타입 안정성, 가독성, 유지보수성**과 더 직접적으로 관련된다.

다만 명시적으로 필요한 필드만 가진 Target Type을 정의하면 `SELECT *`를 피하는 습관을 만들 수 있다.  
이 점은 실무 성능과도 간접적으로 연결된다.

## 16. 권한과 운영 안정성 관점

Open SQL 조회는 프로그램 실행 사용자의 권한, 테이블 접근 정책, 애플리케이션 설계와 연결될 수 있다.

초급 단계에서는 다음을 기억한다.

```text
SELECT 문이 문법적으로 맞는 것과 운영에서 안전한 것은 다르다.
운영 프로그램에서는 조회 대상, 조회 조건, 데이터량, 권한 체크를 함께 고려해야 한다.
```

명시적 Target Table 선언은 권한을 직접 해결하지는 않는다.  
하지만 조회 결과 구조가 명확하면 이후 권한 체크 결과, 메시지 처리, ALV 출력 제한 등을 설계하기 쉬워진다.

## 17. 미니 실습

### 17.1 실습 목표

`SFLIGHT`에서 특정 항공사의 항공편 데이터를 조회하고, 명시적으로 선언한 Target Table에 담은 뒤 결과 건수를 출력한다.

### 17.2 실습 코드

```abap
REPORT zgpt_sql_target_lab.

PARAMETERS p_carrid TYPE sflight-carrid DEFAULT 'AA'.

TYPES: BEGIN OF ty_result,
         carrid   TYPE sflight-carrid,
         connid   TYPE sflight-connid,
         fldate   TYPE sflight-fldate,
         price    TYPE sflight-price,
         currency TYPE sflight-currency,
       END OF ty_result.

DATA lt_result TYPE STANDARD TABLE OF ty_result.
DATA ls_result TYPE ty_result.

SELECT carrid,
       connid,
       fldate,
       price,
       currency
  FROM sflight
  WHERE carrid = @p_carrid
  INTO TABLE @lt_result.

WRITE: / '조회 조건 CARRID:', p_carrid,
       / '조회 결과 건수:', lines( lt_result ).

ULINE.

LOOP AT lt_result INTO ls_result.
  WRITE: / ls_result-carrid,
           ls_result-connid,
           ls_result-fldate,
           ls_result-price,
           ls_result-currency.
ENDLOOP.
```

### 17.3 실습 변형 과제

다음 변형을 수행해본다.

1. `price`, `currency`를 Target Type에서 제거하고 SELECT 필드에서도 제거한다.
2. SELECT 필드에는 `fldate`를 남기고 Target Type에서만 제거하여 오류를 확인한다.
3. `INTO TABLE @lt_result`에서 `@`를 제거하고 오류 메시지를 확인한다.
4. `DATA ls_result TYPE ty_result`를 삭제하고 `LOOP AT ... INTO DATA(ls_result_inline)`로 바꿔본다.
5. `SCARR` 테이블을 대상으로 항공사 목록 조회용 타입을 직접 정의해본다.

| 조회 조건 | CARRID |
| Target Type | TY_RESULT |

## 18. 자주 하는 실수 정리

| 실수 | 문제 | 해결 |
|---|---|---|
| `lt_table`을 선언하지 않음 | SELECT Target이 존재하지 않음 | `DATA lt_table TYPE ...` 선언 |
| SELECT 필드와 Target 구조 불일치 | 할당 오류 또는 문법 오류 | 필드 수와 타입을 맞춤 |
| `@` 누락 | Host Variable 인식 오류 | ABAP 변수 앞에 `@` 사용 |
| Work Area 타입 불일치 | LOOP 처리 중 필드 접근 오류 | Line Type과 같은 타입 사용 |
| 무조건 `SELECT *` 사용 | 불필요한 데이터 조회 | 필요한 필드만 명시 |
| 너무 많은 로컬 타입 중복 | 유지보수 어려움 | 공통 구조는 DDIC/전역 타입 검토 |
| 인라인 선언만 남발 | 큰 프로그램에서 구조 파악 어려움 | 명시적 타입 선언 검토 |

## 19. 평가 문제

### 19.1 객관식

#### Q1. 명시적 Target Table 선언 방식의 장점으로 가장 적절한 것은?

A. SELECT 성능이 항상 자동으로 빨라진다.  
B. 조회 결과 구조를 명확히 정의하고 재사용하기 쉽다.  
C. WHERE 조건이 없어도 자동으로 데이터량을 줄인다.  
D. 권한 체크가 자동으로 수행된다.

정답: B

#### Q2. `DATA lt_result TYPE STANDARD TABLE OF ty_result.`에서 `ty_result`의 역할은?

A. DB 테이블 이름  
B. 프로그램 이름  
C. Internal Table의 Line Type  
D. Selection Screen 제목

정답: C

#### Q3. 최신 ABAP SQL에서 ABAP 변수를 SQL 문에 전달할 때 사용하는 표기는?

A. `#`  
B. `&`  
C. `@`  
D. `%`

정답: C

### 19.2 서술형

#### Q1. 인라인 선언과 명시적 선언의 차이를 설명하시오.

모범 답안:  
인라인 선언은 `INTO TABLE @DATA(lt_data)`처럼 SELECT 결과를 받는 Internal Table을 SELECT 문 안에서 즉시 선언하는 방식이다. 명시적 선언은 `TYPES`와 `DATA`를 사용해 조회 결과 구조와 Target Table을 미리 정의한 뒤 `INTO TABLE @lt_data`로 결과를 담는 방식이다. 인라인 선언은 간결하고, 명시적 선언은 구조가 명확하고 재사용에 유리하다.

#### Q2. 명시적 Target Table 선언이 ALV 출력에서 유리한 이유를 설명하시오.

모범 답안:  
ALV는 출력할 필드 구조가 명확해야 유지보수하기 쉽다. 명시적 Target Type을 사용하면 어떤 필드가 출력 대상인지 코드 상단에서 확인할 수 있고, Field Catalog나 SALV 출력 구조와 연결하기 쉽다.

#### Q3. SELECT 필드 목록과 Target 구조가 불일치하면 어떤 문제가 발생할 수 있는가?

모범 답안:  
SELECT 결과를 Target Table의 Line Type에 넣을 때 필드 수, 순서, 타입이 맞지 않으면 문법 오류나 데이터 할당 오류가 발생할 수 있다. 따라서 SELECT 필드 목록과 Target 구조를 의도적으로 맞춰야 한다.

## 20. 강사용 설명 포인트

강의에서는 다음 메시지를 강조한다.

```text
@DATA는 편리한 문법이고, 명시적 선언은 구조를 통제하는 문법이다.
```

초급자는 인라인 선언을 배우면 모든 SELECT를 `@DATA`로 처리하려는 경향이 있다.  
하지만 실무 프로그램은 조회 결과가 여러 로직을 거쳐 ALV, 파일, 인터페이스, 메시지 처리로 이어지는 경우가 많다.

따라서 강사는 다음 질문을 던지면 좋다.

```text
이 조회 결과는 한 번만 쓰이나요?
이 결과 구조를 다른 메서드에도 넘기나요?
이 결과를 ALV로 출력할 계획인가요?
SELECT 필드가 바뀌면 어디까지 영향이 있나요?
```

이 질문을 통해 학습자가 단순 문법을 넘어 Target 구조 설계 관점으로 넘어갈 수 있다.

## 21. 후속 모듈 연결

다음 모듈은 `THEORY-09-M06 — 반복 SELECT 안티패턴 맛보기`이다.

이번 모듈에서 명시적 Target Table을 선언했다면, 다음 모듈에서는 성능 관점에서 다음 문제를 다룬다.

```text
LOOP 안에서 SELECT를 반복하면 왜 위험한가?
DB 접근 횟수가 많아지면 어떤 성능 문제가 생기는가?
먼저 한 번에 조회해 Internal Table에 담는 방식이 왜 중요한가?
```

즉, 이번 모듈의 Target Table 선언은 다음 모듈의 성능 안티패턴 개선과 직접 연결된다.

```text
명시적 Target Table 선언
→ 한 번에 필요한 데이터를 조회
→ Internal Table에서 처리
→ 반복 SELECT 회피
```

## 22. 핵심 요약

이번 모듈의 핵심은 다음이다.

```text
명시적 Target Table 선언은 SELECT 결과 구조를 코드에서 명확히 통제하는 방식이다.
TYPES는 조회 결과 한 줄의 구조를 정의한다.
DATA lt_table TYPE STANDARD TABLE OF ty_line은 여러 건의 결과를 받을 Internal Table을 선언한다.
SELECT ... INTO TABLE @lt_table은 DB 조회 결과를 명시적 Target Table에 담는다.
인라인 선언은 간결하고, 명시적 선언은 재사용성과 유지보수성에 강하다.
SELECT 필드 목록과 Target 구조는 반드시 의도적으로 맞춰야 한다.
```
