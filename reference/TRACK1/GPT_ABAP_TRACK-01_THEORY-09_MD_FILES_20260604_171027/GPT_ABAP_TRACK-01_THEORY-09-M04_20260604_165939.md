## 1. 이 문서의 목적

이 문서는 Open SQL 기본 조회에서 가장 중요한 전환점인 **`INTO TABLE`을 이용한 Internal Table 적재**를 초급자 관점에서 설명한다.

앞선 모듈에서는 다음 흐름을 학습했다.

```text
THEORY-09-M01  SELECT FROM / FIELDS 기본 구조
THEORY-09-M02  WHERE 조건과 Host Variable @ 기초
THEORY-09-M03  SELECT SINGLE과 단건 조회
```

이번 모듈에서는 단건 조회가 아니라 **여러 건의 데이터**, 즉 DB 조회 결과 집합(Result Set)을 ABAP 메모리의 Internal Table에 담는 방법을 학습한다.

실무 ABAP 프로그램에서 조회 결과는 대부분 한 건이 아니라 여러 건이다. 예를 들어 항공편 목록, 판매오더 목록, 고객 목록, 자재 목록, 전표 목록은 모두 여러 행으로 구성된다. 이런 데이터를 화면에 출력하거나 ALV로 보여주거나 후속 로직에서 가공하려면 먼저 Internal Table에 적재해야 한다.

이 모듈의 핵심 문장은 다음이다.

```text
SELECT ... INTO TABLE은 DB의 여러 행 결과를 ABAP Internal Table에 한 번에 담는 기본 패턴이다.
```

## 3. 선행 지식

이 모듈은 다음 지식을 전제로 한다.

| 선행 지식 | 필요한 이유 |
|---|---|
| Transparent Table | `SELECT`의 조회 대상이 DB 테이블이기 때문이다. |
| PARAMETERS | 사용자 입력값을 WHERE 조건으로 사용할 수 있기 때문이다. |
| Host Variable `@` | ABAP 변수 값을 Open SQL 조건에 전달하기 위해 필요하다. |
| SELECT SINGLE | 단건 조회와 다건 조회를 비교하기 위해 필요하다. |
| Internal Table 기초 | 조회 결과가 Internal Table에 적재되기 때문이다. |
| LOOP AT 기초 | 조회 결과를 순회하여 확인하기 위해 필요하다. |

초급자는 이 모듈을 통해 DB 세계와 ABAP 메모리 세계가 어떻게 연결되는지 감각을 잡아야 한다.

```text
Database Table
  → SELECT
  → Result Set
  → Internal Table
  → LOOP / ALV / 후속 처리
```

## 4. Result Set이란 무엇인가?

`SELECT` 문을 실행하면 DB에서 조건에 맞는 행들이 조회된다. 이때 조회된 결과 집합을 일반적으로 Result Set이라고 이해할 수 있다.

예를 들어 `SFLIGHT` 테이블에서 항공사 코드가 `AA`인 데이터를 조회한다고 가정한다.

```abap
SELECT FROM sflight
  FIELDS carrid, connid, fldate, price, currency
  WHERE carrid = 'AA'
  INTO TABLE @DATA(lt_flights).
```

이 조회 결과가 1건일 수도 있고, 10건일 수도 있고, 수천 건일 수도 있다. 이처럼 조건에 맞는 여러 행의 묶음이 Result Set이다.

ABAP 프로그램은 이 Result Set을 바로 화면에 자동 출력하지 않는다. 보통 Internal Table이라는 메모리 테이블에 담아 후속 처리한다.

---

## 5. Internal Table이란 무엇인가?

Internal Table은 ABAP 프로그램 실행 중 메모리에 존재하는 테이블 형태의 데이터 객체이다.

초급자에게는 다음과 같은 비유가 가장 쉽다.

```text
DB Table        = 실제 창고에 저장된 원본 데이터
SELECT Result   = 창고에서 꺼내온 데이터 묶음
Internal Table  = 프로그램 안에서 임시로 들고 있는 작업용 표
```

Internal Table은 프로그램 실행 중에만 존재한다. 프로그램이 끝나면 Internal Table에 담긴 데이터도 사라진다. 반면 DB Table의 데이터는 저장소에 남아 있다.

| 구분 | DB Table | Internal Table |
|---|---|---|
| 위치 | 데이터베이스 | ABAP Application Server 메모리 |
| 지속성 | 프로그램 종료 후에도 남음 | 프로그램 종료 시 사라짐 |
| 생성 방식 | DDIC Transparent Table 등 | ABAP 변수 선언 |
| 사용 목적 | 업무 데이터 저장 | 조회 결과 처리, 계산, 출력, ALV |
| 대표 접근 | Open SQL | LOOP, READ TABLE, MODIFY, DELETE 등 |

이번 모듈에서는 Internal Table 심화 조작을 깊게 다루지는 않는다. 핵심은 `SELECT` 결과를 Internal Table에 담는 기본 패턴이다.

## 6. `INTO TABLE`의 역할

`INTO TABLE`은 조회 결과 여러 행을 Internal Table에 적재하겠다는 의미이다.

기본 형태는 다음과 같다.

```abap
SELECT FROM db_table
  FIELDS field1, field2, field3
  WHERE condition
  INTO TABLE @DATA(lt_result).
```

여기서 각 부분의 의미는 다음과 같다.

| 구문 | 의미 |
|---|---|
| `SELECT FROM db_table` | 어떤 DB 테이블에서 조회할지 지정 |
| `FIELDS field1, field2` | 어떤 컬럼을 가져올지 지정 |
| `WHERE condition` | 어떤 조건의 행만 가져올지 지정 |
| `INTO TABLE` | 결과 여러 건을 Internal Table에 담음 |
| `@DATA(lt_result)` | 조회 결과 구조에 맞는 Internal Table을 Inline으로 선언 |

`INTO TABLE`은 단건을 담는 `INTO @DATA(ls_data)`와 구분해야 한다.

| 패턴 | 목적 | 결과 변수 성격 |
|---|---|---|
| `SELECT SINGLE ... INTO @DATA(ls_row)` | 한 건 조회 | Structure / Work Area |
| `SELECT ... INTO TABLE @DATA(lt_rows)` | 여러 건 조회 | Internal Table |

## 7. 기본 예제: SFLIGHT 여러 건 조회

교육 시스템에서 자주 사용하는 표준 항공 예제 테이블을 기준으로 설명한다.

```abap
REPORT zopen_sql_into_table_01.

SELECT FROM sflight
  FIELDS carrid,
         connid,
         fldate,
         price,
         currency
  WHERE carrid = 'AA'
  INTO TABLE @DATA(lt_flights).

WRITE: / '조회 건수:', lines( lt_flights ).

LOOP AT lt_flights INTO DATA(ls_flight).
  WRITE: / ls_flight-carrid,
           ls_flight-connid,
           ls_flight-fldate,
           ls_flight-price,
           ls_flight-currency.
ENDLOOP.
```

### 7.1 코드 해설

| 코드 | 설명 |
|---|---|
| `SELECT FROM sflight` | `SFLIGHT` 테이블에서 데이터를 조회한다. |
| `FIELDS carrid, connid, ...` | 필요한 필드만 조회한다. |
| `WHERE carrid = 'AA'` | 항공사 코드가 `AA`인 행만 조회한다. |
| `INTO TABLE @DATA(lt_flights)` | 결과를 Internal Table `LT_FLIGHTS`에 담는다. |
| `lines( lt_flights )` | Internal Table의 행 수를 반환한다. |
| `LOOP AT lt_flights` | 조회 결과를 한 줄씩 순회한다. |

### 7.2 실행 결과의 의미

실행 결과는 시스템의 샘플 데이터 상태에 따라 달라질 수 있다.

예상 형태는 다음과 같다.

```text
조회 건수: 10
AA 0017 2026.01.01  422.94 USD
AA 0017 2026.01.15  422.94 USD
...
```

[추정] 교육 시스템에 따라 `SFLIGHT` 샘플 데이터가 없거나 일부 항공사 코드가 다를 수 있다. 조회 결과가 없으면 `CARRID` 값을 `LH`, `AZ`, `UA` 등 시스템에 존재하는 값으로 바꿔 테스트한다.

## 8. `sy-subrc`와 조회 결과 없음

`SELECT ... INTO TABLE` 후에는 `sy-subrc`를 통해 조회 성공 여부를 확인할 수 있다.

```abap
SELECT FROM sflight
  FIELDS carrid, connid, fldate
  WHERE carrid = 'ZZ'
  INTO TABLE @DATA(lt_flights).

IF sy-subrc = 0.
  WRITE: / '조회 성공:', lines( lt_flights ), '건'.
ELSE.
  WRITE: / '조회된 데이터가 없습니다.'.
ENDIF.
```

일반적으로 결과가 한 건 이상 있으면 `sy-subrc = 0`, 결과가 없으면 `sy-subrc = 4`로 이해할 수 있다.

다만 실무에서는 `sy-subrc`만 보지 말고 Internal Table 자체도 확인하는 습관이 좋다.

```abap
IF lt_flights IS INITIAL.
  WRITE: / '조회된 데이터가 없습니다.'.
ELSE.
  WRITE: / '조회 건수:', lines( lt_flights ).
ENDIF.
```

### 8.1 초급자에게 권장하는 확인 방식

초급 단계에서는 다음처럼 두 가지를 함께 이해한다.

| 확인 방식 | 의미 |
|---|---|
| `sy-subrc` | 직전 SQL 실행의 성공/실패 상태 |
| `lt_table IS INITIAL` | 실제 Internal Table에 데이터가 있는지 여부 |
| `lines( lt_table )` | 조회된 행 수 |

실무에서는 코드 가독성과 의도에 따라 적절한 방식을 선택한다.

## 9. `SELECT SINGLE`과 `INTO TABLE` 비교

앞선 모듈의 `SELECT SINGLE`과 이번 모듈의 `SELECT ... INTO TABLE`은 목적이 다르다.

| 구분 | `SELECT SINGLE` | `SELECT ... INTO TABLE` |
|---|---|---|
| 조회 의도 | 한 건만 필요 | 여러 건 필요 |
| Target | Work Area 또는 Structure | Internal Table |
| 대표 변수명 | `ls_*`, `lv_*` | `lt_*` |
| 사용 예 | 사용자 ID 1건 조회 | 항공편 목록 조회 |
| 후속 처리 | 바로 필드 사용 | LOOP, READ TABLE, ALV 등 |

예를 들어 사용자 한 명의 이름만 필요하면 `SELECT SINGLE`이 적절할 수 있다.

```abap
SELECT SINGLE FROM scarr
  FIELDS carrname
  WHERE carrid = 'AA'
  INTO @DATA(lv_carrname).
```

반면 특정 항공사의 모든 비행 일정 목록이 필요하면 `INTO TABLE`이 적절하다.

```abap
SELECT FROM sflight
  FIELDS carrid, connid, fldate
  WHERE carrid = 'AA'
  INTO TABLE @DATA(lt_flights).
```

## 10. Inline Declaration 방식

Modern ABAP에서는 `@DATA(...)`를 사용하여 조회 결과를 받는 변수를 바로 선언할 수 있다.

```abap
SELECT FROM scarr
  FIELDS carrid, carrname, currcode
  INTO TABLE @DATA(lt_carriers).
```

이 방식의 장점은 다음과 같다.

| 장점 | 설명 |
|---|---|
| 코드가 짧다 | 별도 `DATA lt_carriers ...` 선언이 필요 없다. |
| 구조 추론 | `FIELDS` 목록을 기준으로 결과 타입이 추론된다. |
| 실습 편의 | 초급자가 SELECT 결과 구조를 빠르게 확인할 수 있다. |
| 가독성 | 조회와 결과 변수 선언이 가까이 있어 흐름이 명확하다. |

하지만 Inline Declaration만 항상 정답은 아니다. 후속 모듈인 `THEORY-09-M05`에서는 명시적 Target Table 선언 방식을 다룬다.

초급자는 현재 단계에서 다음 정도로 이해하면 된다.

```text
간단한 조회와 실습에는 @DATA(lt_result)가 편하다.
재사용 타입, 명확한 인터페이스, 복잡한 로직에서는 명시적 타입 선언도 중요하다.
```

## 11. FIELDS 목록과 Internal Table Line Structure

`FIELDS`에 어떤 컬럼을 적느냐에 따라 Internal Table의 한 줄 구조가 결정된다.

예를 들어 다음 조회를 보자.

```abap
SELECT FROM scarr
  FIELDS carrid, carrname
  INTO TABLE @DATA(lt_carriers).
```

이 경우 `LT_CARRIERS`의 각 행은 다음 필드를 가진다.

```text
CARRID
CARRNAME
```

따라서 LOOP 안에서는 다음 필드를 사용할 수 있다.

```abap
LOOP AT lt_carriers INTO DATA(ls_carrier).
  WRITE: / ls_carrier-carrid,
           ls_carrier-carrname.
ENDLOOP.
```

하지만 `currcode`는 조회하지 않았기 때문에 사용할 수 없다.

```abap
" 오류 가능 예시
WRITE: / ls_carrier-currcode.
```

### 11.1 핵심 원칙

```text
FIELDS에 적은 필드만 결과 Internal Table의 Line Structure에 포함된다.
```

초급자는 `SELECT *`에 익숙해지기보다 필요한 필드를 명시하는 습관을 들이는 것이 좋다.

## 12. `SELECT * INTO TABLE`을 조심해야 하는 이유

`SELECT *`는 테이블의 모든 필드를 조회한다.

```abap
SELECT *
  FROM sflight
  INTO TABLE @DATA(lt_flights).
```

초급 실습에서는 간단해 보이지만 실무에서는 조심해야 한다.

| 문제 | 설명 |
|---|---|
| 불필요한 데이터 전송 | 사용하지 않는 컬럼까지 DB에서 Application Server로 가져온다. |
| 가독성 저하 | 어떤 필드를 실제로 사용하는지 코드만 보고 알기 어렵다. |
| 구조 변경 영향 | 테이블 필드가 바뀌면 예기치 않은 영향이 생길 수 있다. |
| 성능 리스크 | 넓은 테이블에서 대량 조회 시 비용이 커진다. |

권장 패턴은 필요한 필드를 명시하는 것이다.

```abap
SELECT FROM sflight
  FIELDS carrid, connid, fldate, price, currency
  WHERE carrid = @p_carrid
  INTO TABLE @DATA(lt_flights).
```

## 13. 조건 없는 대량 조회를 조심해야 한다

다음 코드는 전체 테이블을 모두 읽는다.

```abap
SELECT FROM sflight
  FIELDS carrid, connid, fldate, price, currency
  INTO TABLE @DATA(lt_flights).
```

교육용 샘플 테이블에서는 큰 문제가 없을 수 있다. 하지만 실무 테이블에서 조건 없는 전체 조회는 심각한 성능 문제가 될 수 있다.

예를 들어 판매오더, 전표, 자재문서, 회계전표 같은 테이블은 데이터가 매우 많을 수 있다.

실무에서는 다음 기준을 고려한다.

| 기준 | 설명 |
|---|---|
| WHERE 조건 | 가능한 업무 조건을 사용한다. |
| 필요한 필드만 조회 | `FIELDS`를 명시한다. |
| 건수 제한 | 필요 시 `UP TO n ROWS` 등을 검토한다. |
| Key 조건 | Primary Key 또는 인덱스 활용 가능성을 고려한다. |
| 후속 처리량 | Internal Table에 담은 후 LOOP 비용도 고려한다. |

`UP TO n ROWS`와 정렬, 페이징은 후속 SQL 심화에서 더 자세히 다룬다.

## 14. PARAMETERS와 함께 사용하는 기본 패턴

앞선 Selection Screen 학습과 연결하면 다음처럼 사용자 입력값을 조건으로 사용할 수 있다.

```abap
REPORT zopen_sql_into_table_02.

PARAMETERS p_carrid TYPE sflight-carrid DEFAULT 'AA'.

SELECT FROM sflight
  FIELDS carrid,
         connid,
         fldate,
         price,
         currency
  WHERE carrid = @p_carrid
  INTO TABLE @DATA(lt_flights).

IF lt_flights IS INITIAL.
  WRITE: / '조회된 항공편이 없습니다:', p_carrid.
  RETURN.
ENDIF.

WRITE: / '항공사:', p_carrid,
       / '조회 건수:', lines( lt_flights ).

ULINE.

LOOP AT lt_flights INTO DATA(ls_flight).
  WRITE: / ls_flight-carrid,
           ls_flight-connid,
           ls_flight-fldate,
           ls_flight-price,
           ls_flight-currency.
ENDLOOP.
```

### 14.1 이 예제가 중요한 이유

이 예제는 지금까지의 여러 Section을 연결한다.

| 학습 주제 | 코드 위치 |
|---|---|
| PARAMETERS | `PARAMETERS p_carrid ...` |
| Host Variable | `@p_carrid` |
| Open SQL | `SELECT FROM sflight` |
| INTO TABLE | `INTO TABLE @DATA(lt_flights)` |
| Internal Table | `lt_flights` |
| LOOP | `LOOP AT lt_flights` |
| WRITE | 조회 결과 출력 |

이처럼 `INTO TABLE`은 단순한 SQL 문법이 아니라 ABAP 프로그램 전체 흐름의 중심에 놓인다.

---

## 15. 조회 결과 정렬에 대한 초급 감각

초급자가 자주 묻는 질문은 “조회 결과가 어떤 순서로 나오나요?”이다.

명시적인 정렬 조건이 없다면 결과 순서를 업무적으로 보장한다고 생각하면 안 된다. 화면에서 우연히 같은 순서로 보일 수 있지만, 그것을 로직의 전제로 두면 위험하다.

정렬이 필요하면 `ORDER BY`를 사용한다.

```abap
SELECT FROM sflight
  FIELDS carrid, connid, fldate, price, currency
  WHERE carrid = @p_carrid
  ORDER BY carrid, connid, fldate
  INTO TABLE @DATA(lt_flights).
```

이번 모듈의 핵심은 `INTO TABLE`이므로 `ORDER BY`는 보조적으로만 다룬다. SQL 정렬과 성능 관점은 후속 Open SQL 심화에서 더 자세히 다룬다.

## 16. 조회 후 Internal Table 처리의 기본 흐름

`INTO TABLE`로 데이터를 담은 후에는 보통 다음 처리를 수행한다.

```text
조회 건수 확인
→ 결과 없음 처리
→ LOOP로 순회
→ 조건에 따른 출력/가공
→ ALV 또는 후속 로직으로 전달
```

예시:

```abap
IF lt_flights IS INITIAL.
  MESSAGE '조회된 데이터가 없습니다.' TYPE 'I'.
  RETURN.
ENDIF.

LOOP AT lt_flights INTO DATA(ls_flight).
  IF ls_flight-price > 500.
    WRITE: / 'High price:', ls_flight-carrid,
                         ls_flight-connid,
                         ls_flight-price.
  ENDIF.
ENDLOOP.
```

여기서 중요한 것은 데이터를 DB에서 가져온 뒤에도 ABAP 메모리에서 가공이 이어진다는 점이다.

다만 실무에서는 가능한 처리는 DB에서 먼저 줄이는 것이 좋다. 예를 들어 가격이 500 초과인 데이터만 필요하다면 ABAP LOOP 안에서 걸러내기보다 WHERE 조건에 넣는 것이 더 적절할 수 있다.

```abap
SELECT FROM sflight
  FIELDS carrid, connid, fldate, price, currency
  WHERE carrid = @p_carrid
    AND price  > 500
  INTO TABLE @DATA(lt_flights).
```

이것은 Code Pushdown과 SQL 조건 활용의 기초 감각이다. 심화 내용은 CDS와 Open SQL 심화에서 다룬다.

## 17. 오류 상황과 해결 방법

### 17.1 Host Variable `@` 누락

오류 가능 코드:

```abap
PARAMETERS p_carrid TYPE sflight-carrid.

SELECT FROM sflight
  FIELDS carrid, connid, fldate
  WHERE carrid = p_carrid
  INTO TABLE @DATA(lt_flights).
```

Modern Open SQL 문법에서는 ABAP 변수를 SQL에 전달할 때 `@`를 붙여야 한다.

수정 코드:

```abap
WHERE carrid = @p_carrid
```

### 17.2 조회하지 않은 필드 사용

오류 가능 코드:

```abap
SELECT FROM scarr
  FIELDS carrid, carrname
  INTO TABLE @DATA(lt_carriers).

LOOP AT lt_carriers INTO DATA(ls_carrier).
  WRITE: / ls_carrier-currcode.
ENDLOOP.
```

`FIELDS`에 `currcode`를 포함하지 않았으므로 결과 구조에 해당 필드가 없다.

수정 코드:

```abap
SELECT FROM scarr
  FIELDS carrid, carrname, currcode
  INTO TABLE @DATA(lt_carriers).
```

### 17.3 결과가 없는데 LOOP만 작성

문제 코드:

```abap
SELECT FROM sflight
  FIELDS carrid, connid, fldate
  WHERE carrid = @p_carrid
  INTO TABLE @DATA(lt_flights).

LOOP AT lt_flights INTO DATA(ls_flight).
  WRITE: / ls_flight-carrid, ls_flight-connid.
ENDLOOP.
```

조회 결과가 없으면 아무것도 출력되지 않아 사용자가 프로그램이 정상 실행된 것인지 알기 어렵다.

개선 코드:

```abap
IF lt_flights IS INITIAL.
  WRITE: / '조회된 데이터가 없습니다.'.
  RETURN.
ENDIF.
```

### 17.4 `SELECT SINGLE`을 목록 조회에 사용

문제 상황:

```abap
SELECT SINGLE FROM sflight
  FIELDS carrid, connid, fldate
  WHERE carrid = @p_carrid
  INTO @DATA(ls_flight).
```

항공사별 모든 항공편 목록을 보여줘야 하는데 `SELECT SINGLE`을 사용하면 한 건만 가져온다.

개선:

```abap
SELECT FROM sflight
  FIELDS carrid, connid, fldate
  WHERE carrid = @p_carrid
  INTO TABLE @DATA(lt_flights).
```

### 17.5 조건 없는 대량 조회

문제 코드:

```abap
SELECT FROM bkpf
  FIELDS bukrs, belnr, gjahr, budat
  INTO TABLE @DATA(lt_bkpf).
```

회계전표 헤더 테이블처럼 대량 데이터가 있는 테이블을 조건 없이 조회하면 성능 문제가 발생할 수 있다.

개선 방향:

```abap
PARAMETERS p_bukrs TYPE bukrs.
PARAMETERS p_gjahr TYPE gjahr.

SELECT FROM bkpf
  FIELDS bukrs, belnr, gjahr, budat
  WHERE bukrs = @p_bukrs
    AND gjahr = @p_gjahr
  INTO TABLE @DATA(lt_bkpf).
```

## 18. 실무 적용 기준

### 18.1 `INTO TABLE`은 목록 처리의 기본이다

실무 프로그램에서 목록 조회는 매우 흔하다.

| 업무 예 | 조회 결과 |
|---|---|
| 특정 기간의 판매오더 목록 | 여러 판매오더 행 |
| 특정 고객의 미결 항목 | 여러 전표 행 |
| 특정 자재의 재고 현황 | 여러 플랜트/저장위치 행 |
| 특정 항공사의 항공편 | 여러 항공편 행 |

이런 목록성 조회에서는 `INTO TABLE`이 기본 패턴이다.

### 18.2 DB에서 줄이고 ABAP에서 가공한다

조회 조건을 너무 넓게 잡고 ABAP에서 모두 걸러내는 것은 좋지 않다.

비권장:

```abap
SELECT FROM sflight
  FIELDS carrid, connid, fldate, price
  INTO TABLE @DATA(lt_all).

LOOP AT lt_all INTO DATA(ls_all).
  IF ls_all-carrid = p_carrid.
    " 처리
  ENDIF.
ENDLOOP.
```

권장:

```abap
SELECT FROM sflight
  FIELDS carrid, connid, fldate, price
  WHERE carrid = @p_carrid
  INTO TABLE @DATA(lt_flights).
```

핵심 원칙은 다음이다.

```text
DB가 잘할 수 있는 필터링은 WHERE 조건으로 먼저 수행한다.
ABAP은 가져온 결과를 업무 로직에 맞게 가공한다.
```

### 18.3 필드 목록을 명확히 한다

실무에서는 “필요한 필드만 조회”하는 습관이 중요하다.

| 나쁜 습관 | 좋은 습관 |
|---|---|
| `SELECT *` | `FIELDS field1, field2` |
| 조건 없이 전체 조회 | 업무 조건 기반 조회 |
| 조회 후 무조건 LOOP | 결과 없음 처리 후 LOOP |
| 정렬 순서 가정 | 필요 시 `ORDER BY` 명시 |

## 20. 강사용 설명 포인트

### 20.1 단건과 다건의 사고 차이

강의에서는 `SELECT SINGLE`과 `INTO TABLE`을 반드시 비교해야 한다.

```text
SELECT SINGLE은 한 건을 확인하는 사고방식이다.
INTO TABLE은 목록을 처리하는 사고방식이다.
```

학습자가 이 차이를 이해하면 이후 Internal Table, ALV, Open SQL 심화로 자연스럽게 넘어갈 수 있다.

### 20.2 DB와 ABAP 메모리의 경계

`INTO TABLE`은 DB 데이터를 ABAP 메모리로 가져오는 경계이다.

강의 중 다음 흐름을 그림으로 설명하면 효과적이다.

```text
SFLIGHT(DB)
  ↓ SELECT WHERE
Result Set
  ↓ INTO TABLE
LT_FLIGHTS(ABAP Memory)
  ↓ LOOP
WRITE / ALV
```

### 20.3 `SELECT *`를 처음부터 습관화하지 않는다

초급자는 `SELECT *`가 편하다고 느낀다. 하지만 실무에서는 불필요한 필드 조회가 성능과 유지보수에 불리할 수 있다. 따라서 초급 단계부터 `FIELDS`를 명시하는 습관을 들이는 것이 좋다.

### 20.4 조회 결과 없음 처리를 반드시 넣는다

출력이 없으면 학습자는 프로그램이 실행되지 않았다고 오해한다. 따라서 교육 예제에서는 `IS INITIAL` 체크를 넣어 사용자에게 결과 없음 메시지를 보여주는 것이 좋다.

**정답:** B

### 21.2 단답형

#### Q1. `INTO TABLE @DATA(lt_flights)`에서 `lt_flights`는 어떤 종류의 데이터 객체인가?

## 22. 실무 리뷰 질문

다음 코드를 보고 문제점을 설명하시오.

```abap
SELECT *
  FROM bkpf
  INTO TABLE @DATA(lt_bkpf).

LOOP AT lt_bkpf INTO DATA(ls_bkpf).
  IF ls_bkpf-bukrs = p_bukrs.
    WRITE: / ls_bkpf-belnr.
  ENDIF.
ENDLOOP.
```

### 모범 리뷰

이 코드는 회계전표 헤더 테이블인 `BKPF`를 조건 없이 전체 조회하고, ABAP LOOP 안에서 회사코드를 필터링한다. 실무에서는 매우 위험한 패턴이다. 필요한 회사코드와 회계연도 등의 조건을 `WHERE`에 먼저 넣어 DB에서 결과를 줄인 뒤 Internal Table에 담아야 한다. 또한 `SELECT *` 대신 필요한 필드만 명시하는 것이 좋다.

개선 예시는 다음과 같다.

```abap
SELECT FROM bkpf
  FIELDS bukrs, belnr, gjahr, budat
  WHERE bukrs = @p_bukrs
    AND gjahr = @p_gjahr
  INTO TABLE @DATA(lt_bkpf).
```

## 23. 핵심 요약

```text
INTO TABLE은 SELECT 결과 여러 건을 Internal Table에 담는 구문이다.
SELECT SINGLE은 단건 조회, SELECT ... INTO TABLE은 다건 조회에 적합하다.
FIELDS 목록에 적은 필드만 결과 Internal Table의 한 줄 구조에 포함된다.
조회 결과가 없을 수 있으므로 IS INITIAL 또는 sy-subrc 확인이 필요하다.
실무에서는 SELECT *와 조건 없는 대량 조회를 조심해야 한다.
DB에서 줄일 수 있는 조건은 WHERE에 넣고, ABAP은 가져온 결과를 후속 처리한다.
```

## 24. 다음 모듈 연결

다음 모듈은 `THEORY-09-M05 — 명시적 Target Table 선언 방식`이다.

이번 모듈에서는 Inline Declaration을 중심으로 다음 패턴을 사용했다.

```abap
INTO TABLE @DATA(lt_flights)
```

다음 모듈에서는 실무에서 자주 필요한 명시적 타입 선언과 Target Table 선언 방식을 다룬다.

```abap
TYPES: BEGIN OF ty_flight,
         carrid   TYPE sflight-carrid,
         connid   TYPE sflight-connid,
         fldate   TYPE sflight-fldate,
       END OF ty_flight.

DATA lt_flights TYPE STANDARD TABLE OF ty_flight.

SELECT FROM sflight
  FIELDS carrid, connid, fldate
  INTO TABLE @lt_flights.
```

즉, 이번 모듈이 “조회 결과를 Internal Table에 담는 기본 감각”이라면, 다음 모듈은 “그 Internal Table의 타입을 명확히 설계하는 방식”이다.
