## 0. 이 문서의 학습 범위

이 문서는 `THEORY-06-M02 — Line Type / Work Area / Standard Table 선언`만 다룬다.

이번 모듈의 목적은 초급자가 Internal Table을 사용하기 전에 반드시 알아야 하는 세 가지 선언 단위를 명확히 구분하는 것이다.

| 키워드 | 초급자 관점의 의미 |
|---|---|
| Line Type | Internal Table 한 줄의 구조 또는 타입 |
| Work Area | Internal Table 한 줄을 임시로 담아 작업하는 변수 |
| STANDARD TABLE | ABAP에서 가장 기본적으로 사용하는 Internal Table 종류 |

이번 모듈에서는 데이터를 추가하는 `APPEND`, 원하는 위치에 넣는 `INSERT`, 전체를 읽는 `LOOP AT`, 단건 검색을 수행하는 `READ TABLE`을 깊게 다루지 않는다.  
이후 모듈에서 해당 문장을 다루기 위해, 지금은 **어떤 타입과 변수를 먼저 선언해야 하는지**에 집중한다.

학습 흐름은 다음과 같다.

```text
Line Type을 설계한다.
→ Work Area를 선언한다.
→ STANDARD TABLE을 선언한다.
→ 세 객체의 관계를 그림처럼 이해한다.
→ 간단한 문법 점검 코드를 작성한다.
```

## 1. 학습 목표

학습자는 이 모듈을 마친 뒤 다음을 설명하고 수행할 수 있어야 한다.

1. Line Type이 Internal Table의 한 줄 타입이라는 점을 설명할 수 있다.
2. Work Area가 한 줄 데이터를 임시로 담는 변수라는 점을 설명할 수 있다.
3. STANDARD TABLE이 순차적 내부 테이블이라는 점을 설명할 수 있다.
4. `TYPES ... BEGIN OF ... END OF ...` 문법으로 구조형 Line Type을 선언할 수 있다.
5. `DATA ls_xxx TYPE ty_xxx` 형식으로 Work Area를 선언할 수 있다.
6. `DATA lt_xxx TYPE STANDARD TABLE OF ty_xxx WITH EMPTY KEY` 형식으로 Internal Table을 선언할 수 있다.
7. Dictionary Structure와 Local Line Type의 차이를 설명할 수 있다.
8. `WITH EMPTY KEY`, `WITH DEFAULT KEY`의 기본 차이를 초급 수준에서 설명할 수 있다.
9. Header Line 방식이 현대 ABAP에서 권장되지 않는 이유를 설명할 수 있다.

## 2. 선행 지식

이 모듈은 `THEORY-06-M01 — Internal Table이 필요한 이유` 다음에 위치한다.  
따라서 학습자는 Internal Table이 DB 테이블 자체가 아니라 **ABAP 프로그램 실행 중 Application Server 메모리에 존재하는 내부 데이터 집합**이라는 점을 알고 있어야 한다.

필요한 선행 개념은 다음과 같다.

| 선행 개념 | 필요한 이유 |
|---|---|
| DATA 선언 | Work Area와 Internal Table 변수를 선언하기 위해 필요하다. |
| TYPES 선언 | Local Line Type을 정의하기 위해 필요하다. |
| Structure 개념 | Internal Table 한 줄이 여러 필드로 구성될 수 있기 때문이다. |
| DDIC Structure | Dictionary Structure를 Line Type으로 사용할 수 있기 때문이다. |
| Runtime Memory | Internal Table이 DB가 아니라 실행 중 메모리에 존재한다는 점을 이해하기 위해 필요하다. |

초급자는 다음 문장을 기억하면 된다.

> Internal Table을 쓰려면 먼저 “한 줄의 모양”을 정해야 한다. 그 한 줄의 모양이 Line Type이다.

## 3. Line Type이란 무엇인가?

### 3.1 쉬운 정의

Line Type은 Internal Table의 한 줄이 어떤 필드들로 구성되는지를 정의하는 타입이다.

엑셀을 비유로 들면 다음과 같다.

| 엑셀 개념 | ABAP Internal Table 개념 |
|---|---|
| 한 행의 컬럼 구조 | Line Type |
| 한 행 데이터 | Work Area 또는 Internal Table의 한 Row |
| 여러 행의 집합 | Internal Table |

예를 들어 학생 목록을 Internal Table로 관리하려면 한 줄에는 다음 필드가 필요할 수 있다.

| 필드 | 의미 | 예시 |
|---|---|---|
| STUDENT_ID | 학생 ID | S0001 |
| STUDENT_NAME | 학생명 | Kim Beginner |
| SCORE | 점수 | 90 |
| GRADE | 등급 | A |

이 한 줄의 구조를 ABAP Local Type으로 선언하면 다음과 같다.

```abap
TYPES: BEGIN OF ty_student,
         student_id   TYPE c LENGTH 10,
         student_name TYPE c LENGTH 40,
         score        TYPE i,
         grade        TYPE c LENGTH 1,
       END OF ty_student.
```

여기서 `ty_student`가 Line Type이다.

### 3.2 Line Type은 데이터가 아니다

중요한 점은 `TYPES`로 만든 `ty_student`는 데이터 자체가 아니라 **타입 정의**라는 것이다.

```abap
TYPES: BEGIN OF ty_student,
         student_id   TYPE c LENGTH 10,
         student_name TYPE c LENGTH 40,
         score        TYPE i,
         grade        TYPE c LENGTH 1,
       END OF ty_student.
```

위 코드는 메모리에 학생 데이터를 담는 변수를 만든 것이 아니다.  
단지 “학생 한 줄은 이런 모양이다”라는 설계도를 만든 것이다.

실제 데이터를 담으려면 `DATA`가 필요하다.

```abap
DATA ls_student TYPE ty_student.
```

이제 `ls_student`라는 Work Area가 메모리에 생성된다.

## 4. Work Area란 무엇인가?

### 4.1 쉬운 정의

Work Area는 Internal Table의 한 줄과 같은 구조를 가진 변수이다.  
Internal Table에 데이터를 넣거나, Internal Table에서 한 줄을 꺼내 처리할 때 사용한다.

```abap
DATA ls_student TYPE ty_student.
```

이 선언은 다음 의미를 가진다.

```text
ls_student는 ty_student 모양의 한 줄 데이터를 담는 변수이다.
```

### 4.2 Work Area 이름 관례

ABAP 실무에서는 변수명 Prefix로 용도를 표현하는 경우가 많다.

| Prefix | 의미 | 예시 |
|---|---|---|
| `ls_` | Local Structure 또는 Work Area | `ls_student` |
| `lt_` | Local Internal Table | `lt_student` |
| `lv_` | Local Variable 단일 값 | `lv_score` |
| `ty_` | Local Type | `ty_student` |

교육용 코드에서는 다음 조합을 권장한다.

```abap
TYPES ty_student ...
DATA  ls_student TYPE ty_student.
DATA  lt_student TYPE STANDARD TABLE OF ty_student WITH EMPTY KEY.
```

이름만 보아도 다음을 알 수 있다.

```text
ty_student = 학생 한 줄의 타입
ls_student = 학생 한 명의 데이터를 담는 Work Area
lt_student = 학생 여러 명을 담는 Internal Table
```

### 4.3 Work Area와 단일 변수의 차이

단일 변수는 하나의 값만 담는다.

```abap
DATA lv_score TYPE i.
```

Work Area는 여러 필드를 가진 한 줄 구조를 담는다.

```abap
DATA ls_student TYPE ty_student.

ls_student-student_id   = 'S0001'.
ls_student-student_name = 'Kim Beginner'.
ls_student-score        = 90.
ls_student-grade        = 'A'.
```

`ls_student-student_id`처럼 하이픈(`-`)을 사용해 구조의 Component에 접근한다.

## 5. STANDARD TABLE이란 무엇인가?

### 5.1 쉬운 정의

STANDARD TABLE은 ABAP Internal Table의 가장 기본적인 형태이다.  
데이터가 내부적으로 순차적으로 쌓이며, 초급자가 Internal Table을 배울 때 가장 먼저 사용하는 종류이다.

선언 예시는 다음과 같다.

```abap
DATA lt_student TYPE STANDARD TABLE OF ty_student WITH EMPTY KEY.
```

이 선언의 의미는 다음과 같다.

| 문법 요소 | 의미 |
|---|---|
| `DATA` | 변수를 선언한다. |
| `lt_student` | Internal Table 변수명이다. |
| `TYPE STANDARD TABLE OF` | Standard Internal Table을 선언한다. |
| `ty_student` | 한 줄의 구조, 즉 Line Type이다. |
| `WITH EMPTY KEY` | 명시적인 테이블 키를 두지 않는다. |

### 5.2 STANDARD TABLE의 초급자 이해

STANDARD TABLE은 다음처럼 이해하면 된다.

```text
같은 구조의 여러 줄을 순서대로 담는 메모리 테이블
```

예를 들어 학생 3명을 담으면 내부적으로 다음과 같은 모양이 된다.

| Index | STUDENT_ID | STUDENT_NAME | SCORE | GRADE |
|---:|---|---|---:|---|
| 1 | S0001 | Kim Beginner | 90 | A |
| 2 | S0002 | Lee Junior | 80 | B |
| 3 | S0003 | Park Trainee | 70 | C |

여기서 `Index`는 Internal Table의 행 순서를 이해하기 위한 번호이다.  
STANDARD TABLE은 순서 기반 접근과 반복 처리에 적합한 기본 테이블이다.

### 5.3 STANDARD TABLE, SORTED TABLE, HASHED TABLE의 위치

Internal Table에는 여러 종류가 있다.

| 종류 | 초급자 설명 | 이번 모듈 범위 |
|---|---|---|
| STANDARD TABLE | 기본 내부 테이블. 순차 저장 중심 | 집중 학습 |
| SORTED TABLE | Key 기준으로 정렬 상태를 유지하는 테이블 | 이름만 소개 |
| HASHED TABLE | Hash Key 기반으로 빠른 단건 접근을 제공하는 테이블 | 이름만 소개 |

이번 모듈은 `STANDARD TABLE`만 다룬다.  
`SORTED TABLE`, `HASHED TABLE`, Table Key 성능 차이는 후속 심화에서 다루는 것이 적절하다.

## 6. 세 객체의 관계

Line Type, Work Area, Internal Table의 관계는 다음과 같다.

```text
TYPES ty_student
  → 학생 한 줄의 모양을 정의한다.

DATA ls_student TYPE ty_student
  → 학생 한 명을 담는 Work Area를 만든다.

DATA lt_student TYPE STANDARD TABLE OF ty_student WITH EMPTY KEY
  → 학생 여러 명을 담는 Internal Table을 만든다.
```

그림처럼 보면 다음과 같다.

```text
[Line Type: ty_student]
  STUDENT_ID
  STUDENT_NAME
  SCORE
  GRADE
        ↓ 타입으로 사용
[Work Area: ls_student]
  학생 한 명의 값
        ↓ 같은 Line Type 사용
[Internal Table: lt_student]
  학생 여러 명의 값
```

초급자에게 가장 중요한 구분은 다음이다.

| 구분 | 타입인가? 데이터인가? | 여러 줄인가? |
|---|---|---:|
| `ty_student` | 타입 | 아니오 |
| `ls_student` | 데이터 변수 | 아니오, 한 줄 |
| `lt_student` | 데이터 변수 | 예, 여러 줄 |

## 7. Local Line Type 선언 방식

### 7.1 구조형 Line Type 선언

가장 기본적인 선언 패턴은 다음과 같다.

```abap
TYPES: BEGIN OF ty_student,
         student_id   TYPE c LENGTH 10,
         student_name TYPE c LENGTH 40,
         score        TYPE i,
         grade        TYPE c LENGTH 1,
       END OF ty_student.
```

이 방식은 프로그램 안에서만 사용하는 Local Type을 만든다.

장점은 다음과 같다.

| 장점 | 설명 |
|---|---|
| 빠른 실습 가능 | DDIC 객체를 만들지 않아도 된다. |
| 프로그램 내부에서 명확 | 한 프로그램 안에서만 쓰는 구조에 적합하다. |
| 초급 학습에 적합 | Line Type의 개념을 직접 확인하기 좋다. |

단점도 있다.

| 단점 | 설명 |
|---|---|
| 재사용성 낮음 | 다른 프로그램에서 바로 사용할 수 없다. |
| Field Label 없음 | DDIC Data Element의 라벨을 활용하기 어렵다. |
| 중앙 관리 어려움 | 여러 프로그램에 같은 구조를 복사하면 불일치가 생길 수 있다. |

### 7.2 Dictionary Structure를 Line Type으로 사용

앞선 DDIC Section에서 Structure를 배웠다면, 그 Structure를 Internal Table의 Line Type으로 사용할 수 있다.

예:

```abap
DATA lt_user TYPE STANDARD TABLE OF zs_jhy_user_basic WITH EMPTY KEY.
DATA ls_user TYPE zs_jhy_user_basic.
```

이 경우 `zs_jhy_user_basic`은 ABAP Dictionary에 존재하는 Structure이다.

Dictionary Structure를 사용하면 다음 장점이 있다.

| 장점 | 설명 |
|---|---|
| 여러 프로그램에서 재사용 가능 | 같은 Structure를 중앙에서 참조할 수 있다. |
| DDIC 의미 유지 | Data Element, Field Label, Domain의 의미를 활용할 수 있다. |
| 인터페이스 안정성 | Function Module, Method, ALV 등에서 일관된 구조를 사용할 수 있다. |

### 7.3 언제 Local Type을 쓰고 언제 DDIC Structure를 쓰는가?

초급 실무 판단 기준은 다음과 같다.

| 상황 | 권장 방식 |
|---|---|
| 한 프로그램에서만 임시로 쓰는 구조 | Local `TYPES` |
| 여러 프로그램에서 재사용할 구조 | DDIC Structure |
| ALV 출력 구조가 여러 곳에서 반복됨 | DDIC Structure 검토 |
| 실습 중 빠른 문법 확인 | Local `TYPES` |
| 표준 테이블과 동일한 구조 사용 | `TYPE TABLE OF <표준테이블>` 가능 |

> [추정] 교육 과정에서는 초급자의 이해를 위해 Local `TYPES`부터 시작한 뒤, DDIC Structure를 Line Type으로 사용하는 방식으로 확장하는 것이 자연스럽다.

## 8. 선언 예제 1: Local Type 기반 Standard Table

다음 코드는 이번 모듈의 핵심 패턴이다.

```abap
REPORT zjhy_itab_declare_01.

TYPES: BEGIN OF ty_student,
         student_id   TYPE c LENGTH 10,
         student_name TYPE c LENGTH 40,
         score        TYPE i,
         grade        TYPE c LENGTH 1,
       END OF ty_student.

DATA ls_student TYPE ty_student.
DATA lt_student TYPE STANDARD TABLE OF ty_student WITH EMPTY KEY.

WRITE: / 'Internal table declaration completed.'.
```

이 코드는 아직 Internal Table에 데이터를 넣지 않는다.  
다만 Syntax Check와 Activate가 성공하면 다음을 확인할 수 있다.

```text
Line Type 선언 성공
Work Area 선언 성공
STANDARD TABLE 선언 성공
프로그램 활성화 성공
```

### 8.1 코드 해석

| 코드 | 해석 |
|---|---|
| `REPORT zjhy_itab_declare_01.` | 실행 가능한 Report 프로그램을 정의한다. |
| `TYPES: BEGIN OF ty_student` | 학생 한 줄 구조 타입 선언을 시작한다. |
| `student_id TYPE c LENGTH 10` | 학생 ID 필드를 10자리 문자로 선언한다. |
| `END OF ty_student.` | 구조 타입 선언을 끝낸다. |
| `DATA ls_student TYPE ty_student.` | 한 줄 Work Area를 선언한다. |
| `DATA lt_student TYPE STANDARD TABLE OF ty_student WITH EMPTY KEY.` | 여러 줄을 담을 Standard Internal Table을 선언한다. |

## 9. 선언 예제 2: DDIC Structure 기반 Standard Table

DDIC Structure를 이미 만들었다면 다음처럼 선언할 수 있다.

```abap
REPORT zjhy_itab_declare_02.

DATA ls_user TYPE zs_jhy_user_basic.
DATA lt_user TYPE STANDARD TABLE OF zs_jhy_user_basic WITH EMPTY KEY.

WRITE: / 'DDIC structure based internal table declared.'.
```

여기서 `zs_jhy_user_basic`은 앞선 DDIC 학습에서 만든 Structure라고 가정한다.

[추정] 실제 교육 시스템에서 `ZS_JHY_USER_BASIC`이라는 Structure가 없다면 본인의 실습 구조명으로 바꾸어야 한다.

### 9.1 DDIC 기반 선언의 장점

| 장점 | 설명 |
|---|---|
| 필드 의미 일관성 | DDIC Data Element 기반 의미가 유지된다. |
| 후속 ALV 연결 용이 | Field Label 활용 가능성이 높다. |
| 다른 프로그램 재사용 | 동일 Structure를 여러 프로그램에서 참조할 수 있다. |
| 실무 설계 흐름과 연결 | DDIC → Program → ALV/Open SQL 흐름을 이해하기 좋다. |

## 10. 선언 예제 3: 표준 테이블 타입 직접 사용

ABAP에서는 데이터베이스 테이블 또는 DDIC Table을 기준으로 Internal Table을 선언할 수도 있다.

예:

```abap
REPORT zjhy_itab_declare_03.

DATA lt_spfli TYPE STANDARD TABLE OF spfli WITH EMPTY KEY.
DATA ls_spfli TYPE spfli.

WRITE: / 'SPFLI line type based internal table declared.'.
```

여기서 `SPFLI`는 SAP 교육 환경에서 자주 사용하는 항공편 연결 정보 테이블이다.

> [추정] 일부 S/4HANA 또는 교육 시스템에서는 Flight Model 관련 표준 테이블 데이터가 없거나 비활성일 수 있다. 이 경우 시스템에 존재하는 다른 표준 테이블 또는 교육용 Z 테이블로 대체한다.

이 선언은 다음 의미이다.

```text
SPFLI 테이블의 한 행 구조를 Line Type으로 사용하여
lt_spfli라는 Standard Internal Table을 선언한다.
```

주의할 점은 `lt_spfli`는 DB 테이블 `SPFLI` 자체가 아니라, 프로그램 실행 중 메모리에 존재하는 Internal Table이라는 점이다.

## 11. WITH EMPTY KEY와 WITH DEFAULT KEY

### 11.1 왜 Key를 명시해야 하는가?

Internal Table에도 Table Key 개념이 있다.  
하지만 초급자가 처음 Internal Table을 배울 때는 Key보다 “여러 줄을 담는 메모리 테이블”이라는 개념이 먼저 중요하다.

현대 ABAP에서는 Standard Table을 선언할 때 Key를 명시하는 습관이 좋다.

```abap
DATA lt_student TYPE STANDARD TABLE OF ty_student WITH EMPTY KEY.
```

이렇게 쓰면 의도가 분명하다.

```text
이 테이블은 현재 단계에서 명시적인 키 기반 접근보다 순차 처리와 기본 저장을 목적으로 사용한다.
```

### 11.2 WITH EMPTY KEY

`WITH EMPTY KEY`는 테이블에 명시적인 키를 두지 않는다는 뜻이다.

초급 학습에서는 다음 상황에 적합하다.

| 상황 | 적합성 |
|---|---|
| APPEND로 데이터를 쌓는 실습 | 적합 |
| LOOP AT으로 전체를 순회하는 실습 | 적합 |
| Key 성능을 아직 배우지 않는 단계 | 적합 |
| 중복 허용 목록 | 적합 |

### 11.3 WITH DEFAULT KEY

`WITH DEFAULT KEY`는 ABAP이 Line Type의 일부 문자형/바이트형 필드 등을 기준으로 기본 키를 구성하는 방식이다.  
하지만 초급자는 기본 키가 어떤 필드로 구성되는지 직관적으로 이해하기 어려울 수 있다.

따라서 실습 코드에서는 다음처럼 명확하게 쓰는 편이 좋다.

```abap
DATA lt_student TYPE STANDARD TABLE OF ty_student WITH EMPTY KEY.
```

그리고 Key 기반 검색과 성능은 후속 모듈에서 별도로 다루는 것이 좋다.

### 11.4 명시적 Key는 언제 배우는가?

명시적 Key, Sorted Table, Hashed Table은 Internal Table 심화 주제에 가깝다.  
이번 Section에서는 `READ TABLE WITH KEY`의 기본 동작 정도만 다루고, 성능 중심 Key 설계는 나중에 다룬다.

## 12. Header Line 방식은 왜 피해야 하는가?

과거 ABAP에서는 Internal Table을 Header Line과 함께 선언하는 문법이 널리 사용되었다.

예전 방식의 예:

```abap
DATA lt_student TYPE STANDARD TABLE OF ty_student WITH HEADER LINE.
```

이 방식은 Internal Table과 Work Area가 같은 이름으로 묶여 동작하는 오래된 스타일이다.

현대 ABAP 교육에서는 다음처럼 분리해서 쓰는 방식을 권장한다.

```abap
DATA ls_student TYPE ty_student.
DATA lt_student TYPE STANDARD TABLE OF ty_student WITH EMPTY KEY.
```

### 12.1 Header Line의 문제점

| 문제 | 설명 |
|---|---|
| 역할 혼동 | 같은 이름이 테이블과 한 줄 영역을 동시에 의미할 수 있다. |
| 가독성 저하 | 코드에서 무엇이 테이블이고 무엇이 Work Area인지 분명하지 않다. |
| 유지보수성 저하 | 초급자와 협업자가 오해하기 쉽다. |
| 현대 ABAP 스타일과 거리 | 명시적 Work Area 또는 Field Symbol 사용이 더 선호된다. |

초급자는 다음 원칙을 기억한다.

```text
Internal Table과 Work Area는 이름을 분리해서 선언한다.
```

---

## 13. 표준 네이밍 규칙

Internal Table 학습에서는 이름이 매우 중요하다.  
이름만 보아도 해당 객체가 타입인지, 한 줄 변수인지, 여러 줄 테이블인지 알아야 한다.

| 객체 | 권장 Prefix | 예시 |
|---|---|---|
| Local Type | `ty_` | `ty_student` |
| Work Area / Structure 변수 | `ls_` | `ls_student` |
| Internal Table | `lt_` | `lt_student` |
| 단일 값 변수 | `lv_` | `lv_count` |
| 상수 | `lc_` | `lc_grade_a` |

나쁜 예:

```abap
DATA data1 TYPE ty_student.
DATA table1 TYPE STANDARD TABLE OF ty_student.
```

좋은 예:

```abap
DATA ls_student TYPE ty_student.
DATA lt_student TYPE STANDARD TABLE OF ty_student WITH EMPTY KEY.
```

실무에서는 프로젝트별 Naming Convention이 존재할 수 있으므로 고객사 기준을 우선한다.

## 14. 오류 상황과 해결

### 14.1 Line Type 선언 종료 누락

#### 오류 예

```abap
TYPES: BEGIN OF ty_student,
         student_id TYPE c LENGTH 10,
         score      TYPE i.
```

#### 문제

`BEGIN OF`로 구조 타입 선언을 시작했지만 `END OF ty_student.`가 없다.

#### 해결

```abap
TYPES: BEGIN OF ty_student,
         student_id TYPE c LENGTH 10,
         score      TYPE i,
       END OF ty_student.
```

### 14.2 Component 구분 쉼표 오류

#### 오류 예

```abap
TYPES: BEGIN OF ty_student,
         student_id TYPE c LENGTH 10
         score      TYPE i,
       END OF ty_student.
```

#### 문제

ABAP의 체인 선언에서는 각 항목을 쉼표로 구분해야 한다.

#### 해결

```abap
TYPES: BEGIN OF ty_student,
         student_id TYPE c LENGTH 10,
         score      TYPE i,
       END OF ty_student.
```

### 14.3 Work Area를 타입처럼 사용

#### 오류 예

```abap
DATA ls_student TYPE ty_student.
DATA lt_student TYPE STANDARD TABLE OF ls_student.
```

#### 문제

`ls_student`는 변수이지 타입이 아니다.  
`STANDARD TABLE OF` 뒤에는 Line Type이 와야 한다.

#### 해결

```abap
DATA ls_student TYPE ty_student.
DATA lt_student TYPE STANDARD TABLE OF ty_student WITH EMPTY KEY.
```

### 14.4 Internal Table을 한 줄 구조처럼 사용

#### 오류 예

```abap
DATA lt_student TYPE STANDARD TABLE OF ty_student WITH EMPTY KEY.

lt_student-student_id = 'S0001'.
```

#### 문제

`lt_student`는 여러 줄을 담는 테이블이므로 하이픈으로 직접 Component에 접근할 수 없다.  
Component에 접근하려면 한 줄 구조인 Work Area가 필요하다.

#### 해결

```abap
DATA ls_student TYPE ty_student.
DATA lt_student TYPE STANDARD TABLE OF ty_student WITH EMPTY KEY.

ls_student-student_id = 'S0001'.
```

데이터를 실제로 Internal Table에 넣는 `APPEND`는 다음 모듈에서 다룬다.

### 14.5 DDIC Structure 이름 오타

#### 오류 예

```abap
DATA lt_user TYPE STANDARD TABLE OF zs_jhy_user_baisc WITH EMPTY KEY.
```

#### 문제

`basic`을 `baisc`로 잘못 입력했다.

#### 해결

SE11 또는 ADT에서 정확한 Structure 이름을 확인한 뒤 수정한다.

```abap
DATA lt_user TYPE STANDARD TABLE OF zs_jhy_user_basic WITH EMPTY KEY.
```

## 17. 실무 적용 기준

### 17.1 Local Type을 남발하지 않는다

한 프로그램 안에서만 쓰는 임시 구조라면 Local Type이 적절하다.  
하지만 여러 프로그램, 여러 클래스, 여러 Function Module에서 같은 구조가 반복된다면 DDIC Structure나 전역 타입을 검토해야 한다.

판단 기준은 다음과 같다.

| 질문 | 판단 |
|---|---|
| 이 구조가 한 프로그램에서만 쓰이는가? | Local Type 가능 |
| 여러 프로그램에서 반복되는가? | DDIC Structure 검토 |
| ALV Field Label이 필요한가? | DDIC Data Element/Structure 유리 |
| 인터페이스 파라미터로 공개되는가? | 전역 타입 검토 |

### 17.2 Work Area는 명시적으로 분리한다

현대 ABAP에서는 Header Line에 의존하지 않고 Work Area를 명확히 선언하는 방식이 좋다.

```abap
DATA ls_student TYPE ty_student.
DATA lt_student TYPE STANDARD TABLE OF ty_student WITH EMPTY KEY.
```

이렇게 하면 코드 리뷰 시 다음이 명확하다.

```text
ls_student는 한 줄이다.
lt_student는 여러 줄이다.
```

### 17.3 Key를 모르면 일단 명시적으로 단순하게 둔다

초급 실습에서는 성능 최적화를 목적으로 복잡한 Key를 설계하기보다, 목적을 명확히 하기 위해 `WITH EMPTY KEY`를 사용한다.

하지만 실무에서는 데이터 건수, 조회 패턴, 검색 조건에 따라 Key와 Table 종류를 신중히 선택해야 한다.

## 18. 초급자 오해 정리

### 오해 1. `TYPES`를 쓰면 데이터가 생긴다

아니다. `TYPES`는 타입 정의이다.  
데이터를 담으려면 `DATA`가 필요하다.

### 오해 2. Work Area와 Internal Table은 같은 것이다

아니다. Work Area는 한 줄이고, Internal Table은 여러 줄이다.

### 오해 3. `lt_student-student_id`처럼 Internal Table에 바로 접근할 수 있다

일반적인 구조 변수처럼 직접 접근할 수 없다.  
Internal Table은 여러 줄이므로 특정 한 줄을 지정하거나 Work Area로 꺼내야 한다.

### 오해 4. Header Line이 더 편하니 계속 써도 된다

초급 학습과 현대 ABAP 스타일에서는 명시적인 Work Area 분리를 권장한다.

### 오해 5. 모든 Internal Table은 STANDARD TABLE로 충분하다

학습 초기에는 STANDARD TABLE로 충분하지만, 실무에서는 데이터량과 접근 패턴에 따라 SORTED TABLE, HASHED TABLE이 더 적합할 수 있다.

## 19. 평가 문제

### 19.1 객관식

#### Q1. Internal Table의 한 줄 구조를 정의하는 것은 무엇인가?

A. Work Area  
B. Line Type  
C. Selection Screen  
D. Transaction Code  

정답: B

#### Q2. `ls_student`와 같은 Work Area의 가장 적절한 설명은?

A. 여러 줄 데이터를 저장하는 DB 테이블이다.  
B. Internal Table의 한 줄과 같은 구조를 가진 변수이다.  
C. 프로그램 전체의 실행 결과 목록이다.  
D. SAP GUI 메뉴 항목이다.  

정답: B

#### Q3. 다음 선언의 의미로 가장 적절한 것은?

```abap
DATA lt_student TYPE STANDARD TABLE OF ty_student WITH EMPTY KEY.
```

A. `ty_student` 타입의 한 줄 변수 선언  
B. `ty_student` 라인 타입을 가지는 Standard Internal Table 선언  
C. 데이터베이스 테이블 생성  
D. Selection Screen 입력 필드 생성  

정답: B

### 19.2 서술형

#### Q1. Line Type, Work Area, Internal Table의 차이를 설명하시오.

모범 답안:  
Line Type은 Internal Table 한 줄의 구조를 정의하는 타입이다. Work Area는 그 Line Type을 기준으로 한 줄 데이터를 담는 변수이다. Internal Table은 같은 Line Type을 가진 여러 줄 데이터를 메모리에 담는 테이블 변수이다.

#### Q2. Header Line 방식이 초급 교육에서 권장되지 않는 이유를 설명하시오.

모범 답안:  
Header Line 방식은 Internal Table과 Work Area의 역할을 같은 이름에 섞어 표현하므로 코드 가독성이 떨어지고 초급자가 테이블과 한 줄 변수의 차이를 이해하기 어렵다. 현대 ABAP에서는 명시적인 Work Area와 Internal Table 분리를 권장한다.

#### Q3. Local `TYPES`와 DDIC Structure 사용 기준을 설명하시오.

모범 답안:  
한 프로그램 안에서만 임시로 사용하는 구조라면 Local `TYPES`가 적절하다. 여러 프로그램에서 재사용되거나 Field Label, Data Element 의미, 인터페이스 안정성이 필요하다면 DDIC Structure 사용을 검토한다.

## 20. 미니 과제

다음 요구사항에 맞게 선언 코드를 작성한다.

### 요구사항

```text
주문번호: ORDER_ID, 문자 10자리
고객번호: CUSTOMER_ID, 문자 10자리

통화키: CURRENCY, 문자 5자리
```

## 22. 핵심 요약

이번 모듈의 핵심은 다음이다.

```text
Line Type은 Internal Table 한 줄의 구조이다.
Work Area는 한 줄 데이터를 담는 변수이다.
STANDARD TABLE은 같은 Line Type의 여러 줄을 담는 기본 Internal Table이다.
TYPES는 타입 정의이고 DATA는 실제 변수 선언이다.
Internal Table과 Work Area는 명시적으로 분리해서 선언한다.
초급 실습에서는 STANDARD TABLE OF ... WITH EMPTY KEY 패턴이 이해하기 좋다.
```

초급자는 특히 다음 세 줄을 자연스럽게 읽을 수 있어야 한다.

```abap
TYPES: BEGIN OF ty_student, ... END OF ty_student.
DATA ls_student TYPE ty_student.
DATA lt_student TYPE STANDARD TABLE OF ty_student WITH EMPTY KEY.
```

이 세 줄을 이해하면 이후 `APPEND`, `LOOP AT`, `READ TABLE` 학습의 기반이 만들어진다.

## 23. 다음 모듈 연결

다음 모듈은 `THEORY-06-M03 — APPEND와 INSERT 기초`이다.

이번 모듈에서 다음 객체를 준비했다.

```text
ty_student: 한 줄 타입
ls_student: 한 줄 Work Area
lt_student: 여러 줄 Internal Table
```

다음 모듈에서는 이 선언을 바탕으로 실제 데이터를 Internal Table에 넣는다.

```text
ls_student에 값 입력
→ APPEND ls_student TO lt_student
→ lt_student에 행이 추가됨
```

즉, 이번 모듈이 “담을 그릇을 준비하는 단계”라면 다음 모듈은 “그 그릇에 실제 줄 데이터를 넣는 단계”이다.
