## 3. Internal Table이란 무엇인가?

### 3.1 쉬운 정의

Internal Table은 ABAP 프로그램 내부에서 여러 줄의 데이터를 담아두기 위한 메모리 기반 테이블이다.

엑셀 시트에 비유하면 이해하기 쉽다.

| 엑셀 개념 | Internal Table 개념 |
|---|---|
| 시트 전체 | Internal Table |
| 한 행 | Row / Line |
| 한 행의 구조 | Line Type |
| 현재 작업 중인 한 행 | Work Area |
| 여러 행을 순서대로 읽기 | `LOOP AT` |
| 특정 행 찾기 | `READ TABLE` |

단, Internal Table은 실제 엑셀 파일도 아니고 DB Table도 아니다.  
ABAP 프로그램이 실행되는 동안 Application Server의 메모리에 만들어지는 임시 데이터 저장 공간이다.

### 3.2 기본 이미지

```text
Database Table
  ↓ SELECT
Internal Table
  ↓ LOOP / READ / MODIFY / DELETE
가공 결과
  ↓ WRITE / ALV / UPDATE / Interface
출력 또는 후속 처리
```

즉, Internal Table은 DB에서 가져온 데이터를 프로그램 안에서 처리하기 위한 중간 작업 공간이다.

---

## 4. 왜 Internal Table이 필요한가?

ABAP 프로그램은 대부분 업무 데이터를 여러 건 단위로 처리한다.

예를 들어 다음과 같은 요구사항을 생각해보자.

```text
항공편 목록을 조회한다.
고객 목록을 출력한다.
판매오더 데이터를 조건별로 가공한다.
자재별 재고 수량을 계산한다.
ALV 화면에 여러 행을 표시한다.
엑셀 업로드 데이터를 검증한다.
BAPI 호출 전에 입력 데이터를 모은다.
```

이런 작업은 단일 변수 하나로 처리할 수 없다.  
데이터가 여러 건이기 때문이다.

### 4.1 단일 변수만 있을 때의 한계

단일 변수는 값 하나만 담을 수 있다.

```abap
DATA gv_carrid TYPE scarr-carrid.

gv_carrid = 'AA'.
WRITE gv_carrid.
```

이 코드는 항공사 코드 하나만 저장할 수 있다.

하지만 항공사 10건, 고객 100건, 판매오더 1,000건을 처리하려면 어떻게 해야 할까?  
변수를 1,000개 만들 수는 없다.

```text
GV_USER_001
GV_USER_002
GV_USER_003
...
GV_USER_1000
```

이런 방식은 불가능에 가깝고 유지보수도 할 수 없다.

### 4.2 Internal Table이 해결하는 문제

Internal Table은 같은 구조의 데이터를 여러 건 담을 수 있다.

```text
LT_USERS
 ├─ U0001 / Kim / Active
 ├─ U0002 / Lee / Inactive
 ├─ U0003 / Park / Blocked
 └─ ...
```

덕분에 ABAP 프로그램은 여러 데이터를 하나의 변수처럼 다룰 수 있다.

```abap
LOOP AT lt_users INTO ls_user.
  WRITE: / ls_user-user_id, ls_user-user_name.
ENDLOOP.
```

초급자는 이 단계에서 문법을 완전히 외울 필요는 없다.  
핵심은 다음이다.

```text
Internal Table은 여러 건의 데이터를 하나의 메모리 객체로 묶어 처리할 수 있게 해준다.
```

## 5. Database Table과 Internal Table의 차이

Internal Table을 이해하려면 Database Table과 반드시 비교해야 한다.

| 구분 | Database Table | Internal Table |
|---|---|---|
| 위치 | Database Server | Application Server Runtime Memory |
| 지속성 | 프로그램 종료 후에도 데이터 유지 | 프로그램 종료 시 사라짐 |
| 생성 방식 | DDIC에서 정의 후 DB에 생성 | ABAP 프로그램 실행 중 선언/생성 |
| 데이터 규모 | 대량 데이터 저장 가능 | 메모리 한계 내에서 사용 |
| 접근 방식 | Open SQL, CDS 등 | LOOP, READ, APPEND, INSERT 등 |
| 목적 | 영구 저장 | 임시 처리, 가공, 출력 준비 |
| 예시 | `SFLIGHT`, `MARA`, `VBAK` | `lt_flights`, `lt_materials`, `lt_orders` |

중요한 차이는 **지속성**이다.

Database Table은 실제 DB에 저장되므로 프로그램이 끝나도 데이터가 남는다.  
Internal Table은 프로그램 실행 중 메모리에만 존재하므로 프로그램이 끝나면 사라진다.

---

## 6. Structure와 Internal Table의 차이

앞선 Section에서 Structure를 학습했다면 Internal Table과도 비교해야 한다.

| 구분 | Structure | Internal Table |
|---|---|---|
| 데이터 건수 | 한 건 구조 | 여러 건 구조 |
| 비유 | 한 줄 | 여러 줄 |
| 사용 예 | Work Area, 파라미터 구조 | DB 조회 결과, ALV 출력 데이터 |
| 선언 예 | `DATA ls_user TYPE zs_user.` | `DATA lt_user TYPE TABLE OF zs_user.` |
| 주요 처리 | 필드 값 대입 | APPEND, LOOP, READ |

### 6.1 비유

Structure는 “한 사람의 정보 카드”이다.

```text
USER_ID: U0001
USER_NAME: Kim
STATUS: A
```

Internal Table은 “여러 사람의 정보 카드 묶음”이다.

```text
U0001 / Kim / A
U0002 / Lee / I
U0003 / Park / B
```

후속 모듈에서는 다음 관계를 구체적으로 학습한다.

```text
Line Type  → 한 줄의 구조
Work Area  → 한 줄을 담는 작업 공간
Internal Table → 같은 Line Type을 가진 여러 줄의 묶음
```

## 7. Runtime Memory란 무엇인가?

Runtime Memory는 프로그램이 실행되는 동안 사용하는 메모리 영역이다.

ABAP 프로그램이 실행되면 필요한 변수와 Internal Table이 Application Server의 메모리에 만들어진다.  
프로그램 실행이 끝나면 일반적으로 이 메모리 객체들은 사라진다.

### 7.1 Runtime Memory 관점의 데이터 흐름

```text
프로그램 시작
  ↓
DATA 선언에 따라 변수와 Internal Table 준비
  ↓
SELECT 결과를 Internal Table에 저장
  ↓
Internal Table을 LOOP로 처리
  ↓
결과 출력 또는 후속 처리
  ↓
프로그램 종료
  ↓
Internal Table 메모리 해제
```

### 7.2 중요한 특징

| 특징 | 설명 |
|---|---|
| 임시성 | 프로그램 실행 중에만 유지된다. |
| 빠른 접근 | DB 접근보다 메모리 접근이 빠를 수 있다. |
| 메모리 제한 | 너무 많은 데이터를 담으면 성능 문제가 발생한다. |
| 프로그램 종속 | 다른 프로그램에서 자동으로 공유되지 않는다. |

초급자는 Internal Table을 “영구 저장소”로 생각하면 안 된다.  
Internal Table은 데이터베이스 대체물이 아니라 프로그램 안의 작업 공간이다.

## 8. Application Server와 Database Server

SAP ABAP 프로그램은 일반적으로 Application Server에서 실행된다.  
실제 업무 데이터는 Database Server에 저장된다.

```text
사용자
  ↓
SAP GUI / Fiori
  ↓
Application Server
  - ABAP 프로그램 실행
  - Internal Table 생성
  - Runtime Memory 사용
  ↓
Database Server
  - Transparent Table 저장
  - SQL 조회 수행
```

### 8.1 역할 비교

| 계층 | 역할 |
|---|---|
| Application Server | ABAP 프로그램 실행, Internal Table 처리, 비즈니스 로직 수행 |
| Database Server | 영구 데이터 저장, SQL 처리, 대량 데이터 검색 |

Internal Table은 Application Server 쪽 개념이다.  
Database Table은 Database Server 쪽 개념이다.

이 차이를 이해하면 성능 관점의 중요한 질문을 할 수 있다.

```text
이 처리는 DB에서 하는 것이 좋은가?
아니면 데이터를 가져온 뒤 Internal Table에서 처리하는 것이 좋은가?
```

초급 단계에서는 정답을 모두 알 필요는 없다.  
다만 Internal Table은 편리하지만 DB 처리를 무조건 대체하는 도구가 아니라는 점을 기억해야 한다.

## 9. Internal Table이 자주 사용되는 대표 상황

### 9.1 SELECT 결과 저장

가장 대표적인 사용처는 DB 조회 결과를 담는 것이다.

```abap
SELECT carrid,
       carrname,
       currcode
  FROM scarr
  INTO TABLE @DATA(lt_carriers).
```

이 코드는 `SCARR` 테이블에서 여러 건을 조회해 `LT_CARRIERS`라는 Internal Table에 담는다.

초급자는 다음 흐름을 이해하면 된다.

```text
SCARR = DB Table
LT_CARRIERS = Internal Table
SELECT = DB에서 데이터를 읽어 Internal Table로 가져오는 구문
```

### 9.2 화면 출력 준비

조회한 데이터를 바로 출력할 수도 있지만, 보통은 Internal Table에 담은 뒤 가공하거나 출력한다.

```abap
LOOP AT lt_carriers INTO DATA(ls_carrier).
  WRITE: / ls_carrier-carrid, ls_carrier-carrname.
ENDLOOP.
```

### 9.3 ALV 출력 데이터

ALV는 여러 건의 데이터를 표 형태로 보여주는 SAP의 대표 출력 방식이다.  
ALV에 넘기는 데이터도 일반적으로 Internal Table이다.

```text
Internal Table
  ↓
ALV Display
  ↓
사용자 화면에 리스트 출력
```

### 9.4 엑셀 업로드 데이터 검증

엑셀에서 업로드한 데이터도 보통 Internal Table에 담긴다.

```text
Excel File
  ↓ Upload
Internal Table
  ↓ Validate
Error Table / Success Table
```

### 9.5 BAPI/RFC 호출 전 데이터 준비

BAPI나 RFC는 여러 건의 데이터를 Table Parameter로 받을 수 있다.  
이때 입력 데이터도 Internal Table 형태로 준비하는 경우가 많다.

## 10. Internal Table 사용 전후 사고 흐름

초급자는 코드를 작성하기 전에 다음 순서로 생각하면 좋다.

```text
1. 처리할 데이터가 한 건인가, 여러 건인가?
2. 여러 건이라면 한 줄의 구조는 무엇인가?
3. 그 여러 줄을 어디에 담을 것인가?
4. 데이터를 직접 만들 것인가, DB에서 조회할 것인가?
5. 전체를 순회할 것인가, 특정 한 건을 찾을 것인가?
6. 처리 결과를 어디에 사용할 것인가?
```

이 질문에 대한 답이 Internal Table 설계의 출발점이다.

예를 들어 “사용자 10명의 상태를 출력한다”는 요구사항을 생각해보자.

| 질문 | 답변 |
|---|---|
| 한 건인가 여러 건인가? | 여러 건 |
| 한 줄 구조는? | 사용자 ID, 이름, 상태 |
| 어디에 담을 것인가? | Internal Table |
| 데이터 출처는? | 직접 입력 또는 DB 조회 |
| 처리 방식은? | 전체 순회 |
| 결과는? | WRITE 또는 ALV 출력 |

## 11. 최소 예제: Internal Table의 필요성 맛보기

이번 모듈에서는 세부 문법을 깊게 설명하지 않는다.  
다만 Internal Table이 왜 필요한지 확인하기 위해 아주 짧은 예제를 본다.

```abap
REPORT zgpt_itab_need_01.

TYPES: BEGIN OF ty_user,
         user_id   TYPE c LENGTH 10,
         user_name TYPE c LENGTH 30,
         status    TYPE c LENGTH 1,
       END OF ty_user.

DATA lt_users TYPE STANDARD TABLE OF ty_user.
DATA ls_user  TYPE ty_user.

ls_user-user_id   = 'U0001'.
ls_user-user_name = 'Kim Beginner'.
ls_user-status    = 'A'.
APPEND ls_user TO lt_users.

CLEAR ls_user.
ls_user-user_id   = 'U0002'.
ls_user-user_name = 'Lee Trainee'.
ls_user-status    = 'I'.
APPEND ls_user TO lt_users.

LOOP AT lt_users INTO ls_user.
  WRITE: / ls_user-user_id,
           ls_user-user_name,
           ls_user-status.
ENDLOOP.
```

이 코드는 후속 모듈에서 자세히 분해한다.  
현재 단계에서는 다음만 파악한다.

| 코드 요소 | 현재 모듈에서의 이해 |
|---|---|
| `TYPES` | 한 줄의 구조를 정의한다. |
| `lt_users` | 여러 사용자 데이터를 담는 Internal Table이다. |
| `ls_user` | 한 명의 사용자 데이터를 담는 Work Area이다. |
| `APPEND` | 한 줄을 Internal Table에 추가한다. |
| `LOOP AT` | Internal Table의 여러 줄을 반복해서 읽는다. |

---

## 12. Internal Table을 쓰지 않으면 생기는 문제

### 12.1 반복 코드 증가

Internal Table 없이 여러 건의 데이터를 처리하려면 같은 코드를 반복하게 된다.

```text
첫 번째 사용자 출력
두 번째 사용자 출력
세 번째 사용자 출력
...
```

데이터가 3건이면 가능해 보이지만 1,000건이면 불가능하다.

### 12.2 데이터 건수 변화에 대응 불가

실무 데이터는 건수가 고정되어 있지 않다.

```text
오늘은 판매오더 10건
내일은 판매오더 3,000건
월말에는 판매오더 100,000건
```

Internal Table은 건수가 가변적인 업무 데이터 처리에 적합하다.

### 12.3 ALV나 Interface로 넘기기 어려움

ALV, BAPI, RFC, 파일 처리 등은 여러 건 데이터를 Table 형태로 다루는 경우가 많다.  
Internal Table을 이해하지 못하면 ABAP 실무 개발의 상당 부분을 진행하기 어렵다.

## 13. Internal Table과 성능

Internal Table은 편리하지만 항상 많이 담아도 되는 것은 아니다.

### 13.1 메모리 사용량

Internal Table은 Application Server 메모리를 사용한다.  
따라서 너무 많은 데이터를 한 번에 담으면 메모리 사용량이 커지고, 프로그램 성능이 떨어질 수 있다.

나쁜 예:

```abap
SELECT *
  FROM sflight
  INTO TABLE @DATA(lt_all_flights).
```

이 코드는 조건 없이 모든 데이터를 가져온다.  
교육용 소량 테이블에서는 문제 없어 보일 수 있지만, 실무 대량 테이블에서는 위험할 수 있다.

좋은 방향:

```abap
SELECT carrid,
       connid,
       fldate
  FROM sflight
  WHERE carrid = @p_carrid
  INTO TABLE @DATA(lt_flights).
```

필요한 필드와 필요한 조건을 사용해 조회 범위를 줄인다.

### 13.2 DB에서 할 일과 ABAP에서 할 일 구분

모든 데이터를 Internal Table에 가져와서 ABAP에서 필터링하는 방식은 비효율적일 수 있다.

비권장 사고:

```text
DB에서 전부 가져온다.
Internal Table에서 조건에 맞는 것만 찾는다.
```

권장 사고:

```text
DB에서 가능한 조건으로 먼저 줄인다.
Internal Table에서는 필요한 후처리를 수행한다.
```

### 13.3 초급자에게 필요한 성능 감각

이번 단계에서는 다음 정도만 기억하면 충분하다.

```text
Internal Table은 메모리 기반이라 빠르게 처리할 수 있지만,
너무 많은 데이터를 무조건 담으면 성능과 메모리 문제가 생긴다.
```

## 14. Internal Table과 SY-SUBRC

Internal Table 관련 구문 중 일부는 처리 결과를 `SY-SUBRC`에 반영한다.  
예를 들어 후속 모듈에서 학습할 `READ TABLE`은 검색 성공 여부를 `SY-SUBRC`로 확인한다.

```text
SY-SUBRC = 0  → 찾음
SY-SUBRC <> 0 → 찾지 못함
```

이번 모듈에서는 `SY-SUBRC`를 자세히 다루지 않는다.  
다만 Internal Table은 단순 저장소가 아니라, 검색과 처리 결과를 시스템 필드와 함께 확인하는 흐름이 있다는 점을 기억한다.

## 16. 실무 적용 기준

### 16.1 Internal Table을 사용하면 좋은 경우

| 상황 | 이유 |
|---|---|
| DB 조회 결과를 여러 건 처리 | SELECT 결과를 담아 반복 처리해야 한다. |
| ALV 출력 데이터 준비 | ALV는 일반적으로 Internal Table 데이터를 표시한다. |
| 파일 업로드 데이터 검증 | 업로드된 여러 행을 메모리에서 검증한다. |
| BAPI/RFC 입력 데이터 준비 | 여러 건 입력 파라미터를 구성한다. |
| 임시 계산 결과 보관 | 프로그램 실행 중 중간 결과를 저장한다. |

### 16.2 Internal Table 사용을 조심해야 하는 경우

| 상황 | 주의점 |
|---|---|
| 대량 데이터를 조건 없이 SELECT | 메모리 사용량 증가 위험 |
| DB에서 가능한 집계/필터를 ABAP에서 처리 | 불필요한 데이터 전송과 메모리 부담 |
| 중첩 LOOP 남발 | 성능 저하 가능 |
| Key 설계 없이 반복 검색 | 후속 성능 문제 가능 |

후속 모듈에서는 Standard Table부터 학습하지만, 이후 Sorted Table, Hashed Table, Binary Search 같은 개념이 등장하면 성능 관점이 더 중요해진다.

## 17. 정상 흐름과 오류 흐름

### 17.1 정상 흐름

```text
필요한 데이터 구조를 정한다.
Internal Table을 선언한다.
DB 또는 직접 입력으로 데이터를 채운다.
LOOP로 전체를 처리한다.
READ로 필요한 행을 찾는다.
결과를 WRITE, ALV, UPDATE, Interface 등에 사용한다.
```

### 17.2 오류 흐름 1: 단일 변수로 여러 건을 처리하려 함

문제:

```text
데이터가 여러 건인데 변수 하나만 선언한다.
```

결과:

```text
마지막 값만 남거나, 반복 처리 구조가 복잡해진다.
```

해결:

```text
여러 건 데이터는 Internal Table에 담는다.
```

### 17.3 오류 흐름 2: 무조건 SELECT * 사용

문제:

```text
필요 없는 필드까지 모두 가져온다.
```

결과:

```text
네트워크, 메모리, 처리 시간이 증가한다.
```

해결:

```text
필요한 필드만 SELECT한다.
```

### 17.4 오류 흐름 3: 조건 없이 대량 데이터 조회

문제:

```text
WHERE 조건 없이 큰 테이블 전체를 Internal Table에 담는다.
```

결과:

```text
Application Server 메모리 부담과 실행 시간 증가.
```

해결:

```text
사용자 입력 조건, 날짜 범위, Key 조건 등으로 DB에서 먼저 줄인다.
```

### 17.5 오류 흐름 4: Internal Table을 DB Table처럼 생각

문제:

```text
Internal Table에 넣은 데이터가 프로그램 종료 후에도 남는다고 착각한다.
```

결과:

```text
다음 실행에서 데이터가 없거나, 영구 저장이 필요한 데이터를 잃는다.
```

해결:

```text
영구 저장이 필요하면 Transparent Table에 INSERT/UPDATE해야 한다.
```

## 18. 미니 실습

### 18.1 실습 목표

Internal Table이 필요한 이유를 체감하기 위해 여러 사용자 데이터를 메모리에 담고 출력 흐름을 확인한다.

### 18.2 실습 코드

```abap
REPORT zgpt_theory06_m01.

TYPES: BEGIN OF ty_user,
         user_id   TYPE c LENGTH 10,
         user_name TYPE c LENGTH 30,
         status    TYPE c LENGTH 1,
       END OF ty_user.

DATA lt_users TYPE STANDARD TABLE OF ty_user.
DATA ls_user  TYPE ty_user.

ls_user-user_id   = 'U0001'.
ls_user-user_name = 'Kim Beginner'.
ls_user-status    = 'A'.
APPEND ls_user TO lt_users.

CLEAR ls_user.
ls_user-user_id   = 'U0002'.
ls_user-user_name = 'Lee Trainee'.
ls_user-status    = 'I'.
APPEND ls_user TO lt_users.

CLEAR ls_user.
ls_user-user_id   = 'U0003'.
ls_user-user_name = 'Park Admin'.
ls_user-status    = 'B'.
APPEND ls_user TO lt_users.

WRITE: / 'Internal Table Row List'.
ULINE.

LOOP AT lt_users INTO ls_user.
  WRITE: / ls_user-user_id,
           ls_user-user_name,
           ls_user-status.
ENDLOOP.
```

### 18.3 관찰 포인트

| 관찰 항목 | 질문 |
|---|---|
| `LT_USERS` | 여러 건을 담는 역할을 하는가? |
| `LS_USER` | 한 건씩 작업하는 역할을 하는가? |
| `APPEND` | Internal Table에 행을 추가하는가? |
| `LOOP AT` | 여러 행을 순서대로 읽는가? |
| 프로그램 종료 | 다시 실행하지 않으면 메모리 데이터는 유지되는가? |

## 20. 평가 문제

### 20.1 객관식

#### Q1. Internal Table의 가장 적절한 설명은?

A. SAP GUI 화면의 버튼 배치 정보이다.  
B. ABAP 프로그램 실행 중 여러 건의 데이터를 메모리에 담기 위한 테이블형 자료구조이다.  
C. 데이터베이스에 영구 저장되는 표준 테이블이다.  
D. 사용자 권한을 저장하는 보안 객체이다.

정답: B

#### Q2. Database Table과 Internal Table의 차이로 올바른 것은?

A. Internal Table은 프로그램 종료 후에도 자동으로 DB에 저장된다.  
B. Database Table은 Runtime Memory에만 존재한다.  
C. Database Table은 영구 저장 대상이고 Internal Table은 프로그램 실행 중 메모리 대상이다.  
D. 둘은 완전히 같은 개념이다.

정답: C

#### Q3. Internal Table을 사용할 때 주의할 점으로 가장 적절한 것은?

A. 항상 모든 DB 데이터를 조건 없이 가져와야 한다.  
B. 대량 데이터를 무조건 Internal Table에 담아도 성능 문제는 없다.  
C. 필요한 필드와 조건으로 데이터를 줄여서 가져오는 것이 좋다.  
D. Internal Table은 ALV와 아무 관련이 없다.

정답: C

### 20.2 서술형

#### Q1. Internal Table이 필요한 이유를 설명하시오.

모범 답안:  
ABAP 프로그램은 고객, 자재, 오더, 항공편 등 여러 건의 업무 데이터를 처리하는 경우가 많다. Internal Table은 이런 다건 데이터를 프로그램 실행 중 메모리에 담아 반복, 검색, 가공, 출력할 수 있게 해주는 핵심 자료구조이다.

#### Q2. Structure와 Internal Table의 차이를 설명하시오.

모범 답안:  
Structure는 한 건의 데이터 모양을 정의하거나 담는 데 사용된다. Internal Table은 같은 구조를 가진 여러 건의 데이터를 담기 위한 테이블형 자료구조이다.

#### Q3. Internal Table에 너무 많은 데이터를 담으면 왜 문제가 되는가?

모범 답안:  
Internal Table은 Application Server의 Runtime Memory를 사용한다. 너무 많은 데이터를 담으면 메모리 사용량이 증가하고 프로그램 실행 시간이 길어지며, 다른 사용자나 프로세스에도 영향을 줄 수 있다.

## 22. 핵심 요약

이번 모듈의 핵심은 다음이다.

```text
Internal Table은 ABAP 프로그램 실행 중 Application Server 메모리에 존재하는 다건 데이터 저장 구조이다.
Database Table은 영구 저장소이고, Internal Table은 임시 작업 공간이다.
Structure는 한 건의 모양이고, Internal Table은 여러 건의 묶음이다.
ABAP 실무에서 DB 조회 결과, ALV 출력, 파일 업로드, BAPI 입력 데이터는 대부분 Internal Table과 연결된다.
Internal Table은 편리하지만 대량 데이터를 무조건 담으면 성능 문제가 생길 수 있다.
```
