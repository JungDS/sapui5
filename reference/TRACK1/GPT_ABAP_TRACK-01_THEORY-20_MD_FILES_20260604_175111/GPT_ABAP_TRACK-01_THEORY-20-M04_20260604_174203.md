## 3. Annotation이란 무엇인가?

### 3.1 쉬운 정의

Annotation은 CDS 객체나 CDS Element에 부여하는 메타데이터이다.

초급자는 다음처럼 이해하면 된다.

```text
CDS 본문 = 어떤 데이터를 가져올 것인가
Annotation = 이 데이터가 어떤 의미를 가지며 어떻게 소비되어야 하는가
```

예를 들어 다음 CDS View Entity가 있다고 하자.

```abap
@EndUserText.label: 'Carrier Basic Interface View'
define view entity ZI_JHY_Carrier
  as select from scarr
{
  key carrid   as CarrierId,
      carrname as CarrierName,
      currcode as CurrencyCode
}
```

여기서 `@EndUserText.label`은 데이터 조회 로직을 바꾸지 않는다.  
하지만 이 CDS View가 ADT, Fiori Elements, 서비스 메타데이터, 개발자 문맥에서 어떤 의미로 표시될지 알려준다.

### 3.2 Annotation은 ABAP 주석이 아니다

ABAP 주석은 사람에게만 의미가 있다.

```abap
" This is a comment
```

반면 CDS Annotation은 시스템이 해석할 수 있는 메타데이터이다.

```abap
@EndUserText.label: 'Carrier Basic Interface View'
```

비교하면 다음과 같다.

| 구분 | ABAP 주석 | CDS Annotation |
|---|---|---|
| 목적 | 사람이 읽는 설명 | 시스템이 해석하는 메타데이터 |
| 런타임/프레임워크 영향 | 없음 | 있을 수 있음 |
| 예시 | `" comment` | `@EndUserText.label` |
| UI/서비스 영향 | 없음 | 있을 수 있음 |
| 문법 오류 가능성 | 낮음 | Annotation 문법 오류 가능 |

## 4. Annotation이 필요한 이유

CDS는 단순 SQL View가 아니다.  
S/4HANA에서는 CDS가 데이터 모델, 서비스, UI, 분석, 권한의 기반으로 사용된다.

따라서 CDS에는 단순한 필드 목록만으로는 부족하다.

예를 들어 `currcode`라는 필드가 있다고 하자.

```abap
currcode as CurrencyCode
```

이 필드가 단순 문자열인지, 통화 코드인지, 금액 필드와 연결되는 통화 단위인지 시스템과 소비자에게 알려주려면 의미 부여가 필요하다.

Annotation은 다음 역할을 한다.

| 역할 | 설명 |
|---|---|
| 설명 제공 | View 또는 Field의 사람이 읽을 수 있는 라벨 제공 |
| 의미 부여 | 금액, 통화, 수량, 단위, 날짜 등 의미 명시 |
| UI 힌트 | Fiori Elements 등에서 화면 구성에 활용 가능 |
| 서비스 노출 힌트 | OData Metadata 등에 반영될 수 있음 |
| 권한 연결 힌트 | DCL 적용 여부와 관련된 기준 제공 |
| 소비 계층 구분 | Interface View와 Projection View의 책임 분리 지원 |

## 5. Annotation의 위치

CDS Annotation은 크게 두 위치에 작성할 수 있다.

```text
1. View 레벨
2. Element 레벨
```

### 5.1 View 레벨 Annotation

View 전체에 적용되는 Annotation이다.

예:

```abap
@EndUserText.label: 'Carrier Basic Interface View'
@AccessControl.authorizationCheck: #NOT_REQUIRED
define view entity ZI_JHY_Carrier
  as select from scarr
{
  key carrid   as CarrierId,
      carrname as CarrierName,
      currcode as CurrencyCode
}
```

대표적으로 다음 정보가 View 레벨에 놓인다.

| Annotation | 의미 |
|---|---|
| `@EndUserText.label` | View 전체의 설명 |
| `@AccessControl.authorizationCheck` | DCL 권한 체크 적용 기준 |
| `@Metadata.allowExtensions` | Metadata Extension 허용 여부 |
| `@ObjectModel.usageType.*` | 사용 유형 관련 힌트 |

> `@AccessControl.authorizationCheck`의 상세 의미와 DCL 설계는 다음 모듈 `THEORY-20-M06`에서 다룬다. 이번 모듈에서는 Annotation 형태와 위치만 이해한다.

### 5.2 Element 레벨 Annotation

특정 Field 또는 Association Element에 적용되는 Annotation이다.

예:

```abap
@EndUserText.label: 'Carrier ID'
key carrid as CarrierId,

@EndUserText.label: 'Carrier Name'
carrname as CarrierName,

@Semantics.currencyCode: true
currcode as CurrencyCode
```

Element 레벨 Annotation은 해당 필드의 의미를 더 명확히 한다.

| Annotation | 적용 대상 | 의미 |
|---|---|---|
| `@EndUserText.label` | Field | 필드 라벨 |
| `@Semantics.currencyCode` | Currency Field | 통화 코드 의미 |
| `@Semantics.amount.currencyCode` | Amount Field | 금액과 통화 코드 연결 |
| `@Semantics.quantity.unitOfMeasure` | Quantity Field | 수량과 단위 연결 |
| `@Semantics.unitOfMeasure` | Unit Field | 단위 필드 의미 |

## 6. `@EndUserText.label`

### 6.1 목적

`@EndUserText.label`은 CDS View 또는 Element에 사람이 읽을 수 있는 라벨을 부여한다.

예:

```abap
@EndUserText.label: 'Carrier Basic Interface View'
define view entity ZI_JHY_Carrier
  as select from scarr
{
  @EndUserText.label: 'Carrier ID'
  key carrid as CarrierId,

  @EndUserText.label: 'Carrier Name'
  carrname as CarrierName
}
```

이 Annotation은 초급자가 가장 먼저 익혀야 할 기본 Annotation이다.

### 6.2 왜 필요한가?

CDS 객체명이나 필드명은 기술 이름이다.

```text
ZI_JHY_Carrier
CarrierId
CarrierName
```

이 이름만으로도 어느 정도 의미를 알 수 있지만, 사용자나 프레임워크가 사용할 표시 텍스트가 필요하다.

`@EndUserText.label`은 다음 위치에서 의미를 가진다.

| 위치 | 효과 |
|---|---|
| ADT Outline / Object Display | 객체 의미 파악 |
| OData Metadata | 서비스 소비자가 라벨을 활용 가능 |
| Fiori Elements | 화면 라벨 또는 설명 구성에 활용 가능 |
| 개발자 유지보수 | View 의도 파악 |
| 문서화 | CDS 모델 설명 강화 |

### 6.3 좋은 라벨과 나쁜 라벨

| 나쁜 라벨 | 문제 |
|---|---|
| `Test` | 의미가 없다. |
| `Data` | 어떤 데이터인지 알 수 없다. |
| `Carrier` | View인지 필드인지 모호하다. |
| `JHY` | 작성자 정보일 뿐 업무 의미가 아니다. |

좋은 라벨:

| 좋은 라벨 | 이유 |
|---|---|
| `Carrier Basic Interface View` | View의 목적이 명확하다. |
| `Carrier ID` | 필드 의미가 명확하다. |
| `Currency Code` | 통화 코드 의미가 드러난다. |

## 7. `@Semantics` Annotation

### 7.1 목적

`@Semantics` Annotation은 필드의 업무적·의미적 성격을 시스템에 알려주는 Annotation이다.

CDS에서는 필드가 단순한 타입 이상의 의미를 가질 수 있다.

예:

```text
Price      = 금액
Currency   = 통화 코드
SeatsMax   = 수량
Unit       = 단위
CreatedAt  = 생성 시각
```

이런 의미를 명확히 부여하면 프레임워크, UI, 서비스 소비자가 데이터를 더 정확히 해석할 수 있다.

### 7.2 통화 코드 예시

표준 항공 예제 테이블 `SCARR`에는 `CURRCODE` 필드가 있다. 이를 CDS에서 통화 코드로 명시할 수 있다.

```abap
@Semantics.currencyCode: true
currcode as CurrencyCode
```

이 Annotation은 `CurrencyCode` 필드가 단순 CHAR 필드가 아니라 통화 코드라는 의미를 가진다고 알려준다.

### 7.3 금액과 통화 코드 연결

금액 필드가 있는 경우에는 금액 필드가 어떤 통화 코드 필드를 참조하는지 명시할 수 있다.

예:

```abap
@Semantics.amount.currencyCode: 'CurrencyCode'
price as FlightPrice,

@Semantics.currencyCode: true
currency as CurrencyCode
```

이 구조에서 `FlightPrice`는 `CurrencyCode`와 함께 해석되어야 한다.

초급자는 다음 규칙을 기억한다.

```text
금액 필드에는 통화 코드 필드가 필요하다.
수량 필드에는 단위 필드가 필요하다.
CDS에서는 이 관계를 @Semantics로 표현할 수 있다.
```

### 7.4 수량과 단위 연결

수량 필드에는 단위 필드가 연결될 수 있다.

```abap
@Semantics.quantity.unitOfMeasure: 'UnitOfMeasure'
seatsmax as MaximumSeats,

@Semantics.unitOfMeasure: true
unit as UnitOfMeasure
```

[추정] 실제 교육 시스템의 항공 예제 테이블에는 위와 동일한 `unit` 필드가 없을 수 있다. 이 경우 수량/단위 예시는 개념 설명용으로만 사용하고, 실습은 시스템에 존재하는 필드 기준으로 조정한다.

## 8. Interface View와 Projection View에서 Annotation 배치

`THEORY-20-M02`에서 Interface View와 Projection View를 구분했다.

Annotation도 이 구분에 맞게 배치해야 한다.

### 8.1 Interface View에 적합한 Annotation

Interface View(`ZI_*`)는 안정적인 재사용 기반 모델이다.  
따라서 데이터 자체의 본질적인 의미는 Interface View에 두는 것이 적절하다.

예:

| Annotation | Interface View 적합성 | 이유 |
|---|---|---|
| `@EndUserText.label` | 적합 | View와 Field의 기본 설명 |
| `@Semantics.currencyCode` | 적합 | 필드의 본질적 의미 |
| `@Semantics.amount.currencyCode` | 적합 | 금액과 통화 관계 |
| `@AccessControl.authorizationCheck` | 검토 필요 | 권한 전략과 연결 |
| UI 전용 Annotation | 신중 | 소비 UI에 따라 달라질 수 있음 |

### 8.2 Projection View에 적합한 Annotation

Projection View(`ZC_*`)는 소비자에게 노출되는 모델이다.  
따라서 특정 앱, 서비스, UI 소비에 가까운 Annotation은 Projection View에 두는 것이 자연스럽다.

예:

| Annotation 성격 | Projection View 적합성 |
|---|---|
| 소비자 친화 라벨 | 적합 |
| UI 노출 순서 | 적합 |
| 특정 Fiori Elements 화면 구성 | 적합 |
| Service 노출을 위한 소비 계층 설명 | 적합 |
| 기본 의미 Annotation | Interface View와 중복 여부 검토 |

### 8.3 실무 기준

다음 기준으로 판단한다.

```text
데이터 자체의 본질적 의미인가?
→ Interface View

소비 화면이나 특정 서비스에 가까운 의미인가?
→ Projection View 또는 Metadata Extension

여러 소비자가 공통으로 써야 하는 의미인가?
→ Interface View

특정 앱에서만 필요한 표시 설정인가?
→ Projection View 또는 Metadata Extension
```

## 9. 최소 예제: Interface View에 Annotation 적용

아래 예제는 `SCARR` 기반 Interface View이다.

```abap
@EndUserText.label: 'Carrier Basic Interface View'
@AccessControl.authorizationCheck: #NOT_REQUIRED
define view entity ZI_JHY_Carrier
  as select from scarr
{
  @EndUserText.label: 'Carrier ID'
  key carrid as CarrierId,

  @EndUserText.label: 'Carrier Name'
  carrname as CarrierName,

  @EndUserText.label: 'Currency Code'
  @Semantics.currencyCode: true
  currcode as CurrencyCode,

  @EndUserText.label: 'Carrier URL'
  url as CarrierUrl
}
```

### 9.1 코드 해설

| 코드 | 의미 |
|---|---|
| `@EndUserText.label` | View 또는 Field의 표시 라벨 |
| `@AccessControl.authorizationCheck: #NOT_REQUIRED` | 이 View에서 DCL 권한 체크를 요구하지 않음 |
| `@Semantics.currencyCode: true` | `CurrencyCode`가 통화 코드임을 명시 |
| `key carrid` | Carrier를 식별하는 Key |
| `as CarrierId` | 소비자 친화적인 Element Alias |

> `#NOT_REQUIRED`는 교육용 단순 예제에서 자주 사용된다. 실무에서는 권한 요구사항에 따라 `#CHECK`와 DCL 설계를 검토해야 한다. 자세한 내용은 `THEORY-20-M06`에서 다룬다.

## 10. 최소 예제: Projection View에 Annotation 적용

Projection View에서는 Interface View를 기반으로 소비자에게 보여줄 형태를 조정한다.

```abap
@EndUserText.label: 'Carrier Basic Consumption View'
@AccessControl.authorizationCheck: #NOT_REQUIRED
@Metadata.allowExtensions: true
define view entity ZC_JHY_Carrier
  as projection on ZI_JHY_Carrier
{
  @EndUserText.label: 'Carrier'
  key CarrierId,

  @EndUserText.label: 'Carrier Name'
  CarrierName,

  @EndUserText.label: 'Currency'
  CurrencyCode,

  @EndUserText.label: 'Website'
  CarrierUrl
}
```

### 10.1 왜 `@Metadata.allowExtensions`를 넣는가?

`@Metadata.allowExtensions: true`는 Metadata Extension을 사용할 수 있게 하는 기반 Annotation이다.

이번 모듈에서는 “Projection View에서 UI 관련 Annotation을 외부 Metadata Extension으로 분리할 수 있다”는 연결만 이해한다.  
Metadata Extension의 문법과 실제 UI Annotation 작성은 다음 모듈 `THEORY-20-M05`에서 다룬다.

### 10.2 Interface View와 Projection View의 라벨 차이

Interface View에서는 기술적·업무적 기본 라벨을 둔다.

```text
Carrier Basic Interface View
Currency Code
Carrier URL
```

Projection View에서는 소비자에게 더 친숙한 라벨을 사용할 수 있다.

```text
Carrier Basic Consumption View
Currency
Website
```

이처럼 Annotation은 같은 데이터라도 계층에 따라 표현 목적이 달라질 수 있다.

## 11. 정상 흐름과 오류 흐름

### 11.1 정상 흐름

Annotation을 적용하는 정상 흐름은 다음과 같다.

```text
1. CDS View Entity 기본 구조 작성
2. View 레벨 @EndUserText.label 작성
3. 필요한 경우 @AccessControl.authorizationCheck 작성
4. Field 레벨 @EndUserText.label 작성
5. 금액/통화/수량/단위 의미가 있으면 @Semantics 작성
6. Syntax Check
7. Activate
8. Data Preview 또는 Metadata 확인
```

### 11.2 오류 흐름 1: Annotation 문법 오류

잘못된 예:

```abap
@EndUserText.label 'Carrier View'
define view entity ZI_JHY_Carrier ...
```

문제:

```text
Annotation 이름과 값 사이에 콜론(:)이 필요하다.
```

올바른 예:

```abap
@EndUserText.label: 'Carrier View'
```

### 11.3 오류 흐름 2: 문자열 따옴표 누락

잘못된 예:

```abap
@EndUserText.label: Carrier View
```

올바른 예:

```abap
@EndUserText.label: 'Carrier View'
```

Annotation 값이 문자열이면 작은따옴표를 사용해야 한다.

### 11.4 오류 흐름 3: 존재하지 않는 Element 참조

잘못된 예:

```abap
@Semantics.amount.currencyCode: 'Currency'
price as FlightPrice,

currency as CurrencyCode
```

문제:

```text
Annotation은 Currency라는 Element를 참조하지만 실제 Element Alias는 CurrencyCode이다.
```

올바른 예:

```abap
@Semantics.amount.currencyCode: 'CurrencyCode'
price as FlightPrice,

@Semantics.currencyCode: true
currency as CurrencyCode
```

### 11.5 오류 흐름 4: 의미 Annotation을 잘못된 필드에 적용

잘못된 예:

```abap
@Semantics.currencyCode: true
carrname as CarrierName
```

`CarrierName`은 통화 코드가 아니므로 의미 Annotation이 맞지 않는다.

해결:

```abap
@Semantics.currencyCode: true
currcode as CurrencyCode
```

### 11.6 오류 흐름 5: UI Annotation을 Interface View에 과도하게 작성

Interface View에 특정 앱 화면 전용 UI Annotation을 너무 많이 작성하면 재사용성이 떨어질 수 있다.

문제:

```text
Interface View가 특정 UI 소비자에 종속된다.
다른 Projection View나 Service에서 재사용하기 어려워진다.
```

해결:

```text
본질적 의미 Annotation은 Interface View에 둔다.
소비자별 UI Annotation은 Projection View 또는 Metadata Extension으로 분리한다.
```

## 12. Annotation 검증 방법

### 12.1 ADT Syntax Check

가장 기본 검증은 ADT의 Syntax Check이다.

```text
Ctrl + F2
```

확인할 항목:

| 항목 | 확인 내용 |
|---|---|
| Annotation 이름 | 존재하는 Annotation인지 |
| 값 문법 | 문자열, Boolean, Enum 값이 맞는지 |
| 참조 필드 | `@Semantics.*`가 실제 Element를 참조하는지 |
| 위치 | View 레벨/Element 레벨 위치가 적절한지 |

### 12.2 Activation

Syntax Check가 통과해도 Activation 시점에 추가 문제가 드러날 수 있다.

```text
Ctrl + F3
```

확인할 항목:

```text
View Entity 활성화 성공 여부
참조한 Source View 활성화 여부
Annotation 관련 오류 메시지
권한 체크 관련 경고 또는 오류
```

### 12.3 Data Preview

Annotation 자체가 Data Preview 결과값을 바꾸지는 않는 경우가 많다.  
하지만 데이터 구조, 필드 Alias, 의미 부여 대상 필드가 올바르게 생성되었는지 확인할 수 있다.

```text
Open With
→ Data Preview
```

### 12.4 Metadata 확인

OData 또는 Fiori Elements로 확장될 경우 Annotation은 Metadata에 반영될 수 있다.  
이번 모듈에서는 개념 수준으로만 이해하고, 실제 서비스 노출과 UI 확인은 후속 과정에서 다룬다.

## 13. 실무 설계 기준

### 13.1 Annotation을 “많이” 쓰는 것이 좋은 설계는 아니다

Annotation은 강력하지만 무분별하게 늘리면 유지보수가 어려워진다.

나쁜 예:

```text
모든 필드에 중복 라벨 작성
Interface View에 UI 전용 Annotation 대량 작성
의미가 불명확한 Annotation 복사/붙여넣기
참조 필드명이 바뀌었는데 Annotation은 그대로 둠
```

좋은 기준:

```text
필수 의미를 명확히 표현한다.
계층 책임에 맞게 Annotation을 배치한다.
후속 소비자에게 필요한 정보만 제공한다.
UI 전용 설정은 Metadata Extension 분리를 검토한다.
```

### 13.2 기본 의미는 Interface View에 둔다

다음은 Interface View에 두기 좋은 Annotation이다.

```text
@EndUserText.label
@Semantics.currencyCode
@Semantics.amount.currencyCode
@Semantics.quantity.unitOfMeasure
```

이들은 데이터 자체의 의미와 가깝기 때문이다.

### 13.3 소비자별 표현은 Projection View 또는 Metadata Extension으로 넘긴다

Fiori Elements 화면에서 어떤 필드를 먼저 보여줄지, 어떤 필드를 Identification 영역에 둘지 같은 UI 전용 판단은 특정 소비자와 관련이 깊다.

이런 설정은 다음 계층에 두는 것이 더 적절할 수 있다.

```text
Projection View
Metadata Extension
```

단, 어느 계층에 둘지는 프로젝트 표준과 Clean Core 정책, RAP 설계 기준에 따라 달라질 수 있다.

### 13.4 Annotation도 변경 영향 분석 대상이다

Annotation은 단순 설명이 아니라 프레임워크가 해석할 수 있는 메타데이터이다.  
따라서 변경 시 다음 영향을 검토해야 한다.

| 변경 | 가능한 영향 |
|---|---|
| 라벨 변경 | UI 표시 텍스트 변경 |
| Semantics 변경 | 금액/통화/단위 해석 변경 |
| Metadata Extension 허용 변경 | UI Annotation 분리 구조 영향 |
| Authorization Check 변경 | DCL 적용 여부 영향 |
| Projection Annotation 변경 | 소비 앱 또는 서비스 Metadata 영향 |

## 14. 미니 실습

### 14.1 실습 목표

`ZI_JHY_Carrier`와 `ZC_JHY_Carrier`에 기본 Annotation을 적용하고 활성화한다.

### 14.2 실습 1 — Interface View 작성

```abap
@EndUserText.label: 'Carrier Basic Interface View'
@AccessControl.authorizationCheck: #NOT_REQUIRED
define view entity ZI_JHY_Carrier
  as select from scarr
{
  @EndUserText.label: 'Carrier ID'
  key carrid as CarrierId,

  @EndUserText.label: 'Carrier Name'
  carrname as CarrierName,

  @EndUserText.label: 'Currency Code'
  @Semantics.currencyCode: true
  currcode as CurrencyCode,

  @EndUserText.label: 'Carrier URL'
  url as CarrierUrl
}
```

확인할 항목:

| 확인 항목 | 기대 결과 |
|---|---|
| Syntax Check | 성공 |
| Activation | 성공 |
| Key | `CarrierId` |
| Currency Semantics | `CurrencyCode`에 적용 |
| Data Preview | SCARR 기반 데이터 확인 |

### 14.3 실습 2 — Projection View 작성

```abap
@EndUserText.label: 'Carrier Basic Consumption View'
@AccessControl.authorizationCheck: #NOT_REQUIRED
@Metadata.allowExtensions: true
define view entity ZC_JHY_Carrier
  as projection on ZI_JHY_Carrier
{
  @EndUserText.label: 'Carrier'
  key CarrierId,

  @EndUserText.label: 'Carrier Name'
  CarrierName,

  @EndUserText.label: 'Currency'
  CurrencyCode,

  @EndUserText.label: 'Website'
  CarrierUrl
}
```

확인할 항목:

| 확인 항목 | 기대 결과 |
|---|---|
| Projection Source | `ZI_JHY_Carrier` |
| Activation | 성공 |
| Metadata Extension 허용 | `@Metadata.allowExtensions: true` |
| Data Preview | Interface View와 동일한 데이터 구조 확인 |
| 라벨 차이 | Projection View의 소비자 친화 라벨 확인 |

### 14.4 실습 3 — 오류 케이스 만들기

일부러 다음 오류를 만들어보고 메시지를 기록한다.

```abap
@EndUserText.label 'Carrier Basic Interface View'
```

기록할 내용:

| 항목 | 기록 |
|---|---|
| 오류 유형 | Annotation 문법 오류 |
| 오류 메시지 | 시스템 메시지 원문 기록 |
| 원인 | 콜론 누락 |
| 수정 | `@EndUserText.label: '...'` 형태로 변경 |
| 재활성화 결과 | 성공 여부 기록 |

## 15. 강사용 설명 포인트

### 15.1 Annotation은 “설명”이 아니라 “계약”이다

강의에서는 Annotation을 단순 설명으로 축소하지 않는 것이 중요하다.  
Annotation은 CDS 소비자와의 계약에 가깝다.

```text
이 필드는 통화 코드이다.
이 금액은 이 통화 코드와 함께 해석해야 한다.
이 View는 이런 표시 라벨을 가진다.
이 View는 Metadata Extension을 허용한다.
```

### 15.2 Interface View와 Projection View의 책임을 계속 연결한다

M02에서 배운 Interface/Projection 구분을 M04에서 다시 연결해야 한다.

```text
Interface View = 안정적 의미 기반
Projection View = 소비자 친화 표현 계층
Metadata Extension = UI 메타데이터 분리 계층
```

### 15.3 Annotation 복붙을 경계한다

초급자는 인터넷 예제에서 Annotation을 복사해 붙이는 경우가 많다.  
하지만 Annotation은 의미와 계층에 맞게 사용해야 한다.

강의 질문 예시:

```text
@Semantics.currencyCode를 CarrierName에 붙이면 왜 문제가 될까요?
@Metadata.allowExtensions는 왜 Projection View에 자주 붙일까요?
Interface View에 UI Annotation을 모두 넣으면 어떤 문제가 생길까요?
```

## 16. 자가 진단 문제

### 16.1 객관식

#### Q1. CDS Annotation의 가장 적절한 설명은?

A. ABAP 주석과 동일하며 시스템이 해석하지 않는다.  
B. CDS 객체나 Element에 의미를 부여하는 메타데이터이다.  
C. SQL WHERE 조건을 대체하는 문법이다.  
D. Internal Table의 정렬 기준이다.

정답: B

#### Q2. View 전체 설명을 부여할 때 가장 기본적으로 사용하는 Annotation은?

A. `@EndUserText.label`  
B. `@Semantics.currencyCode`  
C. `@AbapCatalog.compiler.compareFilter`  
D. `@UI.lineItem`

정답: A

#### Q3. 통화 코드 필드에 적합한 Annotation은?

A. `@Semantics.currencyCode: true`  
B. `@Semantics.amount.currencyCode: true`  
C. `@EndUserText.quickInfo: false`  
D. `@Metadata.ignorePropagatedAnnotations: true`

정답: A

### 16.2 서술형

#### Q1. Annotation과 ABAP 주석의 차이를 설명하시오.

모범 답안:  
ABAP 주석은 사람이 읽기 위한 설명이며 시스템이 의미 있게 해석하지 않는다. CDS Annotation은 CDS 객체나 Element에 부여하는 메타데이터로, UI, 서비스, 권한, 의미 해석 등 프레임워크 동작에 영향을 줄 수 있다.

#### Q2. `@Semantics.amount.currencyCode: 'CurrencyCode'`의 의미를 설명하시오.

모범 답안:  
해당 금액 필드가 `CurrencyCode` Element를 통화 코드로 참조한다는 의미이다. 금액은 단독으로 완전한 의미를 가지기 어렵기 때문에 통화 코드와 함께 해석되어야 한다.

#### Q3. Interface View와 Projection View에서 Annotation을 나눠 배치하는 이유를 설명하시오.

모범 답안:  
Interface View는 여러 소비자가 재사용하는 안정적 의미 기반이므로 데이터 자체의 본질적 의미 Annotation을 두는 것이 적절하다. Projection View는 특정 소비자나 앱에 가까운 계층이므로 소비자 친화 라벨이나 UI 노출 관련 Annotation을 두기 적합하다.

## 17. 실무 체크리스트

| 점검 항목 | 완료 |
|---|---|
| View 레벨 Annotation과 Element 레벨 Annotation을 구분할 수 있다. |  |
| `@EndUserText.label`을 View와 Field에 적용할 수 있다. |  |
| 통화 코드 필드에 `@Semantics.currencyCode`를 적용할 수 있다. |  |
| 금액 필드와 통화 코드 필드의 관계를 설명할 수 있다. |  |
| Interface View에 둘 Annotation과 Projection View에 둘 Annotation을 구분할 수 있다. |  |
| `@Metadata.allowExtensions`가 다음 모듈과 연결된다는 점을 이해한다. |  |
| Annotation 문법 오류를 읽고 수정할 수 있다. |  |
| Annotation을 복사/붙여넣기할 때 의미 검토가 필요하다는 점을 알고 있다. |  |

## 18. 핵심 요약

```text
CDS Annotation은 CDS 모델에 의미를 부여하는 메타데이터이다.
@EndUserText.label은 View와 Field의 표시 라벨을 제공한다.
@Semantics는 금액, 통화, 수량, 단위 등 필드의 의미를 명시한다.
Annotation은 View 레벨과 Element 레벨에 작성할 수 있다.
데이터 자체의 본질적 의미는 Interface View에 두는 것이 적절하다.
소비자별 UI 표현은 Projection View 또는 Metadata Extension으로 분리할 수 있다.
Annotation은 단순 설명이 아니라 UI, 서비스, 권한, 의미 해석에 영향을 줄 수 있다.
```
