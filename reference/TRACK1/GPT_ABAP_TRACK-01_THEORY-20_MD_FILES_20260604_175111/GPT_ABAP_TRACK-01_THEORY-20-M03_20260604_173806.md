## 3. Association이란 무엇인가?

### 3.1 쉬운 정의

Association은 CDS View Entity에서 다른 데이터 모델과의 관계를 선언하는 문법이다.

예를 들어 항공 연결 정보 `SPFLI`는 항공사 마스터 `SCARR`와 연결될 수 있다.

```text
SPFLI-CARRID = SCARR-CARRID
```

이 관계를 CDS View Entity 안에서 다음과 같이 선언할 수 있다.

```abap
association [0..1] to scarr as _Carrier
  on spfli.carrid = _Carrier.carrid
```

이 선언은 다음 의미를 가진다.

```text
현재 View의 각 SPFLI 행은
SCARR의 항공사 한 건과 연결될 수 있다.
연결 조건은 CARRID이다.
연결 대상은 _Carrier라는 이름으로 참조한다.
```

### 3.2 Association의 핵심 특징

| 특징 | 설명 |
|---|---|
| 관계 선언 | 현재 CDS와 다른 데이터 소스의 관계를 선언한다. |
| 지연 사용 | Association은 선언만으로 항상 결과 필드에 펼쳐지는 것은 아니다. |
| Path Expression | `_Carrier.CarrierName`처럼 관련 대상의 필드를 참조할 수 있다. |
| 재사용성 | 하위 View에서 선언한 Association을 상위 View에서 재사용하거나 노출할 수 있다. |
| 의미 모델링 | 단순 Join보다 데이터 모델의 관계를 명확하게 표현한다. |

---

## 4. Association과 Join의 차이

초급자는 Association을 단순히 “CDS에서 쓰는 Join”으로 이해하기 쉽다.  
하지만 정확히는 목적과 사용 방식이 다르다.

| 구분 | Association | Join |
|---|---|---|
| 주 목적 | 관계를 선언하고 필요할 때 탐색 | 즉시 결합 결과를 생성 |
| 구문 위치 | `association ... to ... as ... on ...` | `join ... on ...` |
| 사용 방식 | Path Expression으로 필요 시 사용 | SELECT 결과에 조인된 데이터가 직접 반영 |
| 모델링 의미 | 엔티티 간 관계 표현에 적합 | 특정 조회 결과를 즉시 만들 때 적합 |
| 재사용성 | Association을 노출하면 상위 View에서 탐색 가능 | 해당 View 내부 결합에 머무름 |
| 초급 이해 | “관계를 열어두는 문” | “바로 붙여서 조회하는 문” |

Association은 결과에 항상 조인 결과를 강제로 포함하는 방식이 아니다.  
실제로 대상 필드를 Path Expression으로 사용하거나 Association 자체를 노출할 때 관계가 의미를 갖는다.

> 핵심: Association은 Join을 대체하는 단순 문법이 아니라, CDS 데이터 모델의 관계를 표현하는 방식이다.

## 5. Association 기본 구문

기본 구문은 다음과 같다.

```abap
association [cardinality] to target_entity as _AssociationName
  on source_field = _AssociationName.target_field
```

예제:

```abap
association [0..1] to scarr as _Carrier
  on spfli.carrid = _Carrier.carrid
```

각 부분의 의미는 다음과 같다.

| 구문 요소 | 의미 |
|---|---|
| `association` | Association 선언 시작 |
| `[0..1]` | Cardinality. 연결 대상이 없거나 최대 1건이라는 의미 |
| `to scarr` | 연결 대상 데이터 소스 |
| `as _Carrier` | Association Alias |
| `on ...` | 연결 조건 |
| `spfli.carrid` | 현재 데이터 소스의 필드 |
| `_Carrier.carrid` | 대상 데이터 소스의 필드 |

## 6. Association Alias 네이밍

Association Alias는 보통 언더스코어 `_`로 시작하는 이름을 사용한다.

예:

```text
_Carrier
_Connection
_Flights
_Booking
_Customer
```

이 관행은 Association이 일반 필드가 아니라 관계 탐색 대상이라는 점을 시각적으로 구분해준다.

좋은 예:

```abap
association [0..1] to scarr as _Carrier
association [0..*] to sflight as _Flights
```

나쁜 예:

```abap
association [0..1] to scarr as carrier
association [0..*] to sflight as data1
```

실무에서는 Alias만 보아도 어떤 관계인지 읽을 수 있어야 한다.

## 7. Cardinality 기본 이해

Cardinality는 현재 엔티티의 한 행이 대상 엔티티의 몇 행과 연결될 수 있는지를 표현한다.

대표 표현은 다음과 같다.

| Cardinality | 의미 | 예시 |
|---|---|---|
| `[0..1]` | 대상이 없거나 최대 1건 | 항공 연결 → 항공사 마스터 |
| `[1..1]` | 반드시 1건 | 필수 마스터가 항상 존재한다고 보장되는 경우 |
| `[0..*]` | 대상이 없거나 여러 건 | 항공 연결 → 실제 운항 항공편 |
| `[1..*]` | 최소 1건 이상 여러 건 | 반드시 하위 데이터가 있어야 하는 관계 |

초급자는 다음처럼 이해하면 된다.

```text
[0..1] = 없을 수도 있고, 있어도 하나
[1..1] = 반드시 하나
[0..*] = 없을 수도 있고, 여러 개 가능
[1..*] = 하나 이상 여러 개 가능
```

### 7.1 Cardinality는 단순 주석이 아니다

Cardinality는 단순 설명 문구가 아니다.  
CDS 소비자, 쿼리 최적화, path expression 해석, 모델 의미에 영향을 줄 수 있다.

하지만 초급 단계에서는 다음 원칙을 우선한다.

```text
확실하지 않으면 과도하게 강한 Cardinality를 쓰지 않는다.
실제 데이터 관계를 기준으로 Cardinality를 판단한다.
[1..1]은 데이터가 항상 존재한다는 보장이 있을 때만 사용한다.
```

예를 들어 `SPFLI`의 `CARRID`는 보통 `SCARR`와 연결되지만, 교육 시스템 데이터가 불완전할 수 있다면 `[0..1]`로 설명하는 것이 초급 실습에는 더 안전하다.

## 8. 실습 모델 개요

```text
ZI_GPT_CONNECTION → _Carrier → SCARR
ZI_GPT_CONNECTION → _Flights → SFLIGHT
```

## 9. 실습 1: 항공 연결 Interface View에 Association 추가

### 9.1 생성할 CDS View Entity

```text
ZI_GPT_CONNECTION
```

이 View는 `SPFLI`를 기반으로 항공 연결 정보를 제공하고, 항공사 마스터 및 항공편 정보로 이동할 Association을 가진다.

### 9.2 코드 예제

```abap
@EndUserText.label: 'GPT Connection Interface View'
@AccessControl.authorizationCheck: #NOT_REQUIRED
define view entity ZI_GPT_CONNECTION
  as select from spfli
  association [0..1] to scarr   as _Carrier
    on spfli.carrid = _Carrier.carrid
  association [0..*] to sflight as _Flights
    on  spfli.carrid = _Flights.carrid
    and spfli.connid = _Flights.connid
{
  key spfli.carrid   as CarrierId,
  key spfli.connid   as ConnectionId,
      spfli.cityfrom as CityFrom,
      spfli.cityto   as CityTo,
      spfli.airpfrom as AirportFrom,
      spfli.airpto   as AirportTo,

      _Carrier,
      _Flights
}
```

### 9.3 코드 해설

| 코드 | 설명 |
|---|---|
| `association [0..1] to scarr as _Carrier` | 항공사 마스터와의 관계를 선언한다. |
| `association [0..*] to sflight as _Flights` | 하나의 연결에 여러 항공편 일정이 있을 수 있음을 선언한다. |
| `on spfli.carrid = _Carrier.carrid` | 현재 SPFLI의 항공사 ID와 SCARR의 항공사 ID를 연결한다. |
| `_Carrier` | Association을 외부에 노출한다. |
| `_Flights` | Association을 외부에 노출한다. |

마지막 Element List에 `_Carrier`, `_Flights`를 넣는 것은 중요하다.  
이렇게 Association을 노출해야 상위 CDS나 소비자가 해당 Association을 탐색할 수 있다.

## 10. Association을 선언만 한 경우와 노출한 경우

Association은 선언부에만 있다고 해서 항상 외부에서 사용할 수 있는 것은 아니다.

### 10.1 선언만 한 경우

```abap
define view entity ZI_GPT_CONNECTION
  as select from spfli
  association [0..1] to scarr as _Carrier
    on spfli.carrid = _Carrier.carrid
{
  key spfli.carrid as CarrierId,
  key spfli.connid as ConnectionId
}
```

이 경우 내부에서는 `_Carrier`를 사용할 수 있지만, 외부에 노출되지는 않는다.

### 10.2 노출한 경우

```abap
define view entity ZI_GPT_CONNECTION
  as select from spfli
  association [0..1] to scarr as _Carrier
    on spfli.carrid = _Carrier.carrid
{
  key spfli.carrid as CarrierId,
  key spfli.connid as ConnectionId,

      _Carrier
}
```

이 경우 상위 View에서 다음처럼 Path Expression으로 사용할 수 있다.

```abap
_Carrier.carrname
```

초급자는 다음 문장으로 기억하면 된다.

> Association을 다른 View에서 쓰게 하려면 Element List에 Association Alias를 노출해야 한다.

## 11. Path Expression이란 무엇인가?

Path Expression은 Association을 따라 대상 엔티티의 필드에 접근하는 표현식이다.

예를 들어 `ZI_GPT_CONNECTION`에서 `_Carrier` Association을 노출했다면 다음처럼 사용할 수 있다.

```abap
_Carrier.carrname
```

이 표현식은 다음 의미이다.

```text
현재 연결 정보에서 _Carrier Association을 따라가서
대상 SCARR의 CARRNAME 필드를 가져온다.
```

## 12. 실습 2: Projection View에서 Association 필드 사용

### 12.1 생성할 CDS View Entity

```text
ZC_GPT_CONNECTION
```

이 View는 Interface View `ZI_GPT_CONNECTION`을 기반으로 소비자에게 보여줄 필드를 구성한다.

### 12.2 코드 예제

```abap
@EndUserText.label: 'GPT Connection Projection View'
```

### 12.3 코드 해설

| 코드 | 설명 |

| `_Carrier.carrname as CarrierName` | Association Path를 통해 항공사명을 가져온다. |

## 13. To-One Association과 To-Many Association

Association은 연결 대상의 수에 따라 크게 To-One과 To-Many로 나눌 수 있다.

| 유형 | Cardinality | 예시 |
|---|---|---|
| To-One | `[0..1]`, `[1..1]` | 항공 연결 → 항공사 |
| To-Many | `[0..*]`, `[1..*]` | 항공 연결 → 항공편 일정 |

### 13.1 To-One 예시

```abap
association [0..1] to scarr as _Carrier
  on spfli.carrid = _Carrier.carrid
```

한 연결 정보는 하나의 항공사와 연결된다.

### 13.2 To-Many 예시

```abap
association [0..*] to sflight as _Flights
  on  spfli.carrid = _Flights.carrid
  and spfli.connid = _Flights.connid
```

하나의 연결 정보에는 여러 운항일자의 항공편이 존재할 수 있다.

### 13.3 To-Many Path Expression 주의

To-Many Association의 대상 필드를 단순 조회 필드처럼 가져오면 결과 건수가 늘어나거나 모델 의미가 복잡해질 수 있다.

예를 들어 다음과 같은 사용은 초급 단계에서 주의가 필요하다.

```abap
_Flights.fldate as FlightDate
```

왜냐하면 하나의 Connection에 여러 Flight가 있을 수 있기 때문이다.  
이 경우 결과가 Connection 단위인지 Flight 단위인지 불명확해질 수 있다.

초급자는 다음 원칙을 기억한다.

```text
To-One Association의 필드는 비교적 안전하게 Path Expression으로 가져올 수 있다.
To-Many Association은 결과 건수 증가와 중복 가능성을 항상 의식한다.
```

---

## 14. Cardinality 설계 기준

### 14.1 `[0..1]`을 사용하는 경우

대상 데이터가 없을 수도 있고, 있어도 최대 한 건이라고 판단되는 경우 사용한다.

예:

```text
항공 연결 → 항공사 마스터
```

교육 시스템에서는 데이터 누락 가능성을 고려해 `[0..1]`이 안전한 경우가 많다.

### 14.2 `[1..1]`을 사용하는 경우

대상 데이터가 반드시 존재한다고 보장되는 경우 사용한다.

하지만 초급 실습에서는 `[1..1]`을 신중하게 사용해야 한다.  
데이터가 실제로 불완전하면 모델의 의미와 결과 해석이 어긋날 수 있다.

### 14.3 `[0..*]`을 사용하는 경우

대상 데이터가 여러 건일 수 있는 경우 사용한다.

예:

```text
SPFLI 한 건 → SFLIGHT 여러 운항일자
```

### 14.4 Cardinality를 잘못 잡으면 생기는 문제

| 잘못된 설계 | 문제 |
|---|---|
| 실제로 여러 건인데 `[0..1]`로 선언 | 결과 의미가 잘못 전달될 수 있음 |
| 실제로 없을 수 있는데 `[1..1]`로 선언 | 데이터 누락 상황을 무시하게 됨 |
| To-Many를 무심코 Projection 필드로 펼침 | 결과 건수 증가 또는 중복 발생 가능 |
| 모든 관계를 `[0..*]`로 선언 | 모델 의미가 흐려지고 소비자가 관계를 이해하기 어려움 |

## 16. 자주 발생하는 오류와 해결

### 16.1 Association Alias를 노출하지 않음

#### 증상

상위 View에서 `_Carrier`를 찾을 수 없다는 오류가 발생한다.

#### 원인

하위 View에서 Association을 선언했지만 Element List에 `_Carrier`를 포함하지 않았다.

#### 해결

하위 View의 Element List에 Association Alias를 추가한다.

```abap
{
  key spfli.carrid as CarrierId,
  key spfli.connid as ConnectionId,

      _Carrier
}
```

---

### 16.2 ON 조건 필드 오타

#### 증상

Activation 시 필드를 찾을 수 없다는 오류가 발생한다.

#### 원인

Source 또는 Target 필드명을 잘못 입력했다.

#### 예시

```abap
on spfli.carrid = _Carrier.carrier_id
```

`SCARR`에는 일반적으로 `carrier_id`가 아니라 `carrid` 필드가 있다.

#### 해결

ADT의 Content Assist 또는 Data Definition 탐색 기능을 사용해 실제 필드명을 확인한다.

---

### 16.3 Cardinality와 실제 데이터 관계 불일치

#### 증상

결과 건수가 예상과 다르거나, Association 의미가 혼란스럽다.

#### 원인

실제로 여러 건이 연결될 수 있는데 `[0..1]`처럼 To-One으로 선언했다.

#### 해결

실제 관계를 확인하고 `[0..*]` 등 적절한 Cardinality로 수정한다.

---

### 16.4 To-Many Association 필드를 단순 Projection에 사용

#### 증상

Connection 단위 결과를 기대했는데 Flight 단위로 결과가 늘어난다.

#### 원인

`_Flights`는 To-Many Association인데 해당 대상 필드를 결과 필드로 펼쳤다.

#### 해결

To-Many Association은 별도 View로 모델링하거나, 결과 Grain을 명확히 바꾼다.

```text
Connection 단위 View인지
Flight 단위 View인지
먼저 결정해야 한다.
```

---

### 16.5 대상 View가 비활성 상태

#### 증상

Association 대상 View를 찾지 못하거나 활성화 오류 발생.

#### 원인

대상 CDS View Entity가 아직 Activate되지 않았다.

#### 해결

대상 View를 먼저 Activate한 후 현재 View를 다시 Activate한다.

## 17. 실무 적용 기준

### 17.1 Association을 사용하는 것이 좋은 경우

| 상황 | 이유 |
|---|---|
| 엔티티 간 관계를 모델에 명확히 남기고 싶을 때 | 소비자가 관계를 이해하기 쉽다. |
| Fiori Elements나 OData 노출을 고려할 때 | Association이 Navigation 의미와 연결될 수 있다. |
| Projection View에서 필요한 관련 필드를 선택적으로 가져오고 싶을 때 | Path Expression으로 표현 가능하다. |
| Interface View 계층에서 재사용 관계를 정의하고 싶을 때 | 상위 View에서 관계 재사용 가능 |

### 17.2 Join이 더 단순할 수 있는 경우

| 상황 | 이유 |
|---|---|
| 특정 조회 결과에만 필요한 일회성 결합 | Association 노출까지 필요 없을 수 있다. |
| 관계 탐색 의미보다 결과 평탄화가 목적 | Join이 의도를 더 직접적으로 표현한다. |
| To-Many 관계를 바로 펼쳐 결과 Grain을 바꾸는 경우 | 명시적 Join이 결과 건수 변화를 더 분명히 보여준다. |

### 17.3 Interface View와 Association

실무적으로 Association은 Interface View 계층에서 정의하는 경우가 많다.

예:

```text
ZI_GPT_CONNECTION
  ├─ _Carrier
  └─ _Flights
```

그 후 Projection View에서 소비자에게 필요한 Association이나 관련 필드만 노출한다.

예:

```text
ZC_GPT_CONNECTION
  ├─ CarrierId
  ├─ ConnectionId
  ├─ CarrierName
  └─ _Carrier
```

이 방식은 다음 장점이 있다.

| 장점 | 설명 |
|---|---|
| 재사용성 | Interface View에서 관계를 중앙 정의한다. |
| 소비자 제어 | Projection View에서 필요한 필드만 노출한다. |
| 유지보수성 | 관계 변경 지점을 줄일 수 있다. |
| RAP 확장성 | 향후 RAP 모델링에서 관계 구조를 이해하기 쉽다. |

## 19. 평가 문제

### 19.1 객관식

#### Q1. CDS Association의 가장 적절한 설명은?

A. ABAP 프로그램의 반복문이다.  
B. CDS View Entity에서 다른 데이터 소스와의 관계를 선언하는 문법이다.  
C. 테이블 데이터를 직접 수정하는 SQL 명령이다.  
D. Selection Screen 입력 필드이다.

**정답:** B

#### Q2. `[0..1]` Cardinality의 의미는?

A. 반드시 여러 건 존재한다.  
B. 없거나 최대 한 건 존재할 수 있다.  
C. 항상 정확히 10건 존재한다.  
D. 무조건 오류가 발생한다.

**정답:** B

#### Q3. Association을 상위 View에서 사용하려면 무엇을 해야 하는가?

A. 반드시 `WRITE` 문을 사용한다.  
B. Association Alias를 Element List에 노출한다.  
C. 모든 필드를 Key로 지정한다.  
D. `sy-subrc`를 확인한다.

**정답:** B

#### Q4. To-Many Association의 대상 필드를 단순 Projection할 때 주의할 점은?

A. 결과 건수가 늘어나거나 중복이 생길 수 있다.  
B. 모든 데이터가 자동 삭제된다.  
C. CDS View가 ABAP Report로 바뀐다.  
D. Association이 Domain으로 변환된다.

**정답:** A

### 19.2 서술형

#### Q1. Association과 Join의 차이를 초급자 관점에서 설명하시오.

**모범 답안:**  
Association은 CDS View Entity에서 다른 데이터 소스와의 관계를 선언해두고 필요할 때 Path Expression으로 탐색할 수 있게 하는 모델링 문법이다. Join은 특정 조회 결과를 만들기 위해 데이터 소스를 즉시 결합하는 문법이다.

#### Q2. Association Alias를 `_Carrier`처럼 언더스코어로 시작하는 이유를 설명하시오.

**모범 답안:**  
일반 필드와 구분하여 Association, 즉 관계 탐색 대상임을 쉽게 알 수 있게 하기 위해서이다. 실무적으로 `_Carrier`, `_Flights`처럼 의미 있는 Alias를 사용하면 CDS 모델의 가독성이 좋아진다.

#### Q3. Cardinality를 잘못 선언하면 어떤 문제가 생길 수 있는가?

**모범 답안:**  
실제 데이터 관계와 모델 선언이 달라져 결과 의미가 잘못 전달될 수 있다. 예를 들어 실제로 여러 건이 연결될 수 있는데 `[0..1]`로 선언하면 소비자가 To-One 관계로 오해할 수 있고, Path Expression 사용 시 결과 해석이 어려워질 수 있다.

## 21. 핵심 요약

이번 모듈의 핵심은 다음이다.

```text
Association은 CDS View Entity에서 엔티티 간 관계를 선언하는 문법이다.
Association은 단순 Join과 달리 관계 모델링과 탐색 의미를 가진다.
Path Expression은 Association을 따라 대상 필드에 접근하는 표현식이다.
Cardinality는 관계 대상이 몇 건일 수 있는지를 표현한다.
To-One Association은 비교적 안전하게 필드를 가져올 수 있지만,
To-Many Association은 결과 건수와 중복 가능성을 반드시 검토해야 한다.
Interface View에서 Association을 정의하고 Projection View에서 필요한 관계만 노출하는 방식이 실무적으로 유용하다.
```
