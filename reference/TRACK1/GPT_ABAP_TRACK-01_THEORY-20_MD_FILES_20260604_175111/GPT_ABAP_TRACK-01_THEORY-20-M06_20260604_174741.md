## 3. DCL이란 무엇인가?

DCL은 **Data Control Language**의 약어이다. ABAP CDS에서는 CDS View에 대한 접근 제어를 정의하는 객체를 일반적으로 **Access Control** 또는 **DCL 객체**라고 부른다.

CDS는 데이터를 정의한다.

```abap
define view entity ZI_JHY_Flight
  as select from sflight
{
  key carrid,
  key connid,
  key fldate,
      price,
      currency
}
```

DCL은 해당 CDS 데이터를 어떤 조건에서 조회할 수 있는지 정의한다.

```abap
@MappingRole: true
define role ZR_JHY_FLIGHT {
  grant select on ZI_JHY_Flight
    where carrid = 'AA';
}
```

위 예시는 단순 설명용이다. 이 Access Control이 적용되면 해당 View를 조회할 때 `CARRID = 'AA'` 데이터만 보이도록 제한하는 개념을 표현할 수 있다.

> 초급자 핵심: CDS는 “어떤 데이터를 어떤 구조로 보여줄 것인가”를 정의하고, DCL은 “그 데이터 중 무엇을 볼 수 있게 할 것인가”를 정의한다.

## 4. CDS 권한 제어가 필요한 이유

### 4.1 데이터 모델은 재사용된다

CDS View Entity는 단일 ABAP 프로그램에서만 사용되지 않는다. 하나의 CDS View는 다음과 같은 소비자에게 재사용될 수 있다.

| 소비자 | 설명 |
|---|---|
| ABAP Open SQL | ABAP 프로그램에서 CDS View 조회 |
| 다른 CDS View | 재사용 가능한 Interface View로 활용 |
| OData Service | 서비스 노출 계층에서 사용 |
| Fiori Elements | UI 화면의 데이터 소스 |
| RAP Business Object | RAP 모델의 Root/Projection 기반 |
| Analytics | 분석용 CDS 모델의 하위 계층 |

따라서 CDS View에 아무 권한 제어가 없으면, 다양한 소비 경로에서 의도하지 않은 데이터 노출이 발생할 수 있다.

### 4.2 프로그램 권한만으로는 부족할 수 있다

Classic ABAP Report에서는 프로그램 안에서 직접 권한 체크를 작성할 수 있다.

```abap
AUTHORITY-CHECK OBJECT 'S_CARRID'
  ID 'CARRID' FIELD lv_carrid
  ID 'ACTVT'  FIELD '03'.
```

하지만 CDS View가 여러 프로그램, 서비스, UI에서 재사용된다면 각 소비자마다 같은 권한 체크를 반복하는 것은 비효율적이고 위험하다. DCL은 데이터 모델 근처에서 접근 제어 규칙을 정의하여, CDS 기반 접근에서 일관된 데이터 제한을 제공하는 데 목적이 있다.

## 5. `@AccessControl.authorizationCheck`

CDS View Entity에서 DCL 적용 여부를 의식하게 만드는 대표 Annotation은 다음이다.

```abap
@AccessControl.authorizationCheck: #CHECK
```

예시:

```abap
@EndUserText.label: 'Flight Interface View'
@AccessControl.authorizationCheck: #CHECK
define view entity ZI_JHY_Flight
  as select from sflight
{
  key carrid       as CarrierId,
  key connid       as ConnectionId,
  key fldate       as FlightDate,
      price        as Price,
      currency     as Currency
}
```

### 5.1 `#CHECK`

`#CHECK`는 해당 CDS Entity에 대해 Access Control을 확인하겠다는 의도를 나타낸다. 즉, 이 CDS View를 조회할 때 관련 DCL이 있으면 권한 조건이 적용되는 흐름으로 이해할 수 있다.

```text
#CHECK = 이 CDS View는 Access Control 적용 대상으로 본다.
```

### 5.2 `#NOT_REQUIRED`

`#NOT_REQUIRED`는 해당 CDS View에서 별도의 Access Control이 필수적으로 요구되지 않는다는 의미로 이해할 수 있다. 예를 들어 기술적 보조 View, 공개 가능한 코드성 View, 교육용 단순 View에서는 사용될 수 있다.

하지만 실무에서는 아무 생각 없이 `#NOT_REQUIRED`를 붙이는 것이 매우 위험하다.

```text
권한이 필요 없어서 #NOT_REQUIRED인지,
권한 설계를 아직 안 해서 임시로 #NOT_REQUIRED인지 반드시 구분해야 한다.
```

### 5.3 초급자 판단 기준

| 상황 | 권장 판단 |
|---|---|
| 업무 데이터가 포함된다 | 기본적으로 `#CHECK` 검토 |
| 민감한 조직/금액/개인정보가 포함된다 | 반드시 권한 설계 검토 |
| 공개 가능한 코드성 데이터 | `#NOT_REQUIRED` 가능성 검토 |
| 교육용 단순 실습 | 목적에 따라 `#CHECK` 또는 `#NOT_REQUIRED` 선택 |
| RAP/OData/Fiori로 노출 예정 | 권한 설계 우선 검토 |

## 6. Access Control 객체의 기본 구조

ADT에서 Access Control 객체를 생성하면 DCL 문법으로 역할을 정의한다.

기본 구조는 다음과 같다.

```abap
@MappingRole: true
define role ZR_JHY_FLIGHT {
  grant select on ZI_JHY_Flight
    where CarrierId = 'AA';
}
```

각 요소를 나누어 보면 다음과 같다.

| 요소 | 설명 |
|---|---|
| `@MappingRole: true` | DCL Role을 권한 매핑 대상으로 정의하는 Annotation |
| `define role` | Access Control Role 정의 시작 |
| `ZR_JHY_FLIGHT` | DCL Role 객체명 |
| `grant select on` | 특정 CDS Entity에 대한 SELECT 접근 허용 정의 |
| `ZI_JHY_Flight` | 권한 제어 대상 CDS Entity |
| `where` | 데이터 제한 조건 |

### 6.1 이름 규칙

교육용 예제에서는 다음 Naming을 사용할 수 있다.

| 객체 | 예시 |
|---|---|
| Interface View | `ZI_JHY_Flight` |
| Projection View | `ZC_JHY_Flight` |
| DCL Role | `ZR_JHY_FLIGHT` |

실무 프로젝트에서는 고객사 Naming Rule을 우선한다.

## 7. 단순 조건 기반 DCL

초급 학습에서는 먼저 상수 조건 기반 DCL을 이해하는 것이 좋다.

```abap
@MappingRole: true
define role ZR_JHY_FLIGHT_AA {
  grant select on ZI_JHY_Flight
    where CarrierId = 'AA';
}
```

이 예시는 `CarrierId = 'AA'`인 데이터만 허용하는 구조이다.

### 7.1 장점

| 장점 | 설명 |
|---|---|
| 이해가 쉽다 | WHERE 조건과 유사하게 읽을 수 있다. |
| 실습이 단순하다 | PFCG 설정 없이 DCL 개념을 설명하기 좋다. |
| 권한 제한의 효과를 체감할 수 있다 | 조회 결과가 줄어드는 것을 확인할 수 있다. |

### 7.2 한계

| 한계 | 설명 |
|---|---|
| 사용자별 권한 반영이 어렵다 | 모든 사용자에게 같은 조건이 적용될 수 있다. |
| 운영 권한 체계와 분리된다 | PFCG Role과 연결되지 않는다. |
| 실무 확장성이 낮다 | 조직, 회사코드, 플랜트, 영업조직별 권한에는 부족하다. |

따라서 상수 조건 방식은 개념 설명과 실습에는 유용하지만, 실무 권한 모델의 최종 형태로 보기에는 제한이 있다.

## 8. PFCG 권한과 연계하는 DCL 개념

실무에서는 사용자의 PFCG Role과 Authorization Object를 기준으로 CDS 데이터 접근을 제한하는 방식이 중요하다.

개념적 형태는 다음과 같다.

```abap
@MappingRole: true
define role ZR_JHY_FLIGHT_AUTH {
  grant select on ZI_JHY_Flight
    where CarrierId = aspect pfcg_auth(
      S_CARRID,
      CARRID,
      ACTVT = '03'
    );
}
```

> 위 코드는 교육용 개념 예시이다. 실제 Authorization Object, Field 이름, Activity 값은 시스템과 업무 권한 설계에 맞게 결정해야 한다.

### 8.1 `aspect pfcg_auth`의 의미

`aspect pfcg_auth`는 CDS Access Control에서 PFCG 권한 값을 참조하여 데이터 제한 조건을 구성하는 개념으로 이해할 수 있다. 예를 들어 사용자가 특정 항공사 코드에 대한 조회 권한만 가진다면, 해당 항공사 코드 데이터만 보이도록 제한할 수 있다.

### 8.2 초급자가 기억할 구조

```text
PFCG Role
  → Authorization Object
    → Authorization Field
      → 사용자가 허용받은 값
        → CDS DCL 조건으로 반영
```

### 8.3 실무 중요성

PFCG 연계 DCL은 다음 경우에 중요하다.

| 경우 | 예시 |
|---|---|
| 회사코드별 조회 제한 | 사용자는 허용된 BUKRS만 조회 |
| 플랜트별 조회 제한 | 사용자는 허용된 WERKS만 조회 |
| 영업조직별 조회 제한 | 사용자는 허용된 VKORG만 조회 |
| 구매조직별 조회 제한 | 사용자는 허용된 EKORG만 조회 |
| 항공사 예제 | 사용자는 허용된 CARRID만 조회 |

## 9. Interface View와 Projection View 중 어디에 DCL을 둘 것인가?

CDS View Entity 기초에서 매우 중요한 설계 질문이다.

```text
DCL을 ZI_* Interface View에 둘 것인가?
DCL을 ZC_* Projection View에 둘 것인가?
```

정답은 항상 하나로 고정되지 않는다. 하지만 초급자는 다음 기준을 이해하면 된다.

### 9.1 Interface View에 DCL을 두는 경우

Interface View는 재사용 가능한 데이터 모델 계층이다. 여기에 DCL을 두면 해당 Interface View를 사용하는 여러 소비자가 공통 권한 제한의 영향을 받을 수 있다.

| 장점 | 설명 |
|---|---|
| 중앙 통제 | 재사용 계층에서 일관된 데이터 제한 가능 |
| 누락 위험 감소 | 여러 Projection/Service에서 반복하지 않아도 됨 |
| 보안 기본값 강화 | 하위 모델에 접근하는 다양한 소비자를 보호 |

| 주의점 | 설명 |
|---|---|
| 과도한 제한 가능 | 일부 내부 처리나 다른 소비 시나리오에서도 제한될 수 있음 |
| 재사용 시 영향 큼 | Interface View를 사용하는 모든 객체에 파급 가능 |

### 9.2 Projection View에 DCL을 두는 경우

Projection View는 특정 소비 목적에 맞춘 View이다. 여기에 DCL을 두면 특정 UI, 서비스, API 시나리오에 맞는 권한 제한을 둘 수 있다.

| 장점 | 설명 |
|---|---|
| 소비 시나리오별 제어 | Fiori/OData 등 특정 소비 목적에 맞게 제한 가능 |
| 유연성 | 내부 모델과 외부 노출 모델을 분리 가능 |
| UI 정책 반영 | 화면별 권한 정책을 적용하기 좋음 |

| 주의점 | 설명 |
|---|---|
| 누락 위험 | 다른 Projection에서 권한 설정을 빠뜨릴 수 있음 |
| 중복 가능 | 유사한 권한 규칙을 여러 View에 반복할 수 있음 |

### 9.3 초급 권장 기준

교육용으로는 다음 기준을 추천한다.

```text
민감한 기본 업무 데이터 제한은 Interface View에서 먼저 검토한다.
소비 채널별 추가 제한은 Projection View에서 검토한다.
단, 실제 프로젝트에서는 아키텍처 가이드와 보안 정책을 따른다.
```

## 10. 실습 시나리오

### 10.1 실습 목표

`ZI_JHY_Flight` CDS View Entity에 대해 간단한 Access Control을 생성하고, DCL 적용 전후의 조회 결과 차이를 이해한다.

### 10.2 선행 객체

다음 CDS View Entity가 있다고 가정한다.

```abap
@EndUserText.label: 'Flight Interface View'
@AccessControl.authorizationCheck: #CHECK
define view entity ZI_JHY_Flight
  as select from sflight
{
  key carrid   as CarrierId,
  key connid   as ConnectionId,
  key fldate   as FlightDate,
      price    as Price,
      currency as Currency
}
```

### 10.3 DCL Access Control 생성

ADT에서 다음 흐름으로 생성한다.

```text
1. Project Explorer에서 패키지 선택
2. New → Other ABAP Repository Object
3. Core Data Services → Access Control 선택
4. 이름 입력: ZR_JHY_FLIGHT_AA
5. Description 입력: Access Control for Flight AA
6. Finish
```

생성 후 다음과 같은 DCL을 작성한다.

```abap
@MappingRole: true
define role ZR_JHY_FLIGHT_AA {
  grant select on ZI_JHY_Flight
    where CarrierId = 'AA';
}
```

### 10.4 활성화

CDS View Entity와 Access Control을 모두 Activate한다.

권장 활성화 순서:

```text
1. CDS View Entity Activate
2. Access Control Activate
3. Data Preview 또는 ABAP SELECT로 확인
```

### 10.5 조회 결과 확인

ADT Data Preview 또는 ABAP SQL로 `ZI_JHY_Flight`를 조회한다.

예시 ABAP 코드:

```abap
SELECT *
  FROM zi_jhy_flight
  INTO TABLE @DATA(lt_flight).

cl_demo_output=>display( lt_flight ).
```

초급 실습에서는 결과에 `CarrierId = 'AA'`만 보이는지 확인한다.

## 11. DCL 적용 여부 확인 시 주의할 점

DCL 실습에서 “권한이 적용되지 않는 것처럼 보이는” 상황이 발생할 수 있다.

### 11.1 `@AccessControl.authorizationCheck` 확인

CDS View에 다음 Annotation이 있는지 확인한다.

```abap
@AccessControl.authorizationCheck: #CHECK
```

실습 View가 `#NOT_REQUIRED`라면 Access Control이 의도대로 적용되지 않는다고 느낄 수 있다.

### 11.2 Access Control이 Activate되었는지 확인

DCL 객체도 Repository Object이므로 Activate가 필요하다. 저장만 하고 Activate하지 않으면 적용되지 않는다.

### 11.3 테스트 사용자의 권한 상태 확인

PFCG 권한 기반 DCL을 사용할 경우 테스트 사용자에게 실제 권한 값이 부여되어 있어야 한다. 권한이 없으면 데이터가 보이지 않는 것이 정상일 수 있다.

### 11.4 View 이름과 필드 Alias 확인

DCL의 조건에서 사용하는 필드명은 CDS Entity의 노출 필드명과 맞아야 한다. 예를 들어 CDS View에서 `carrid as CarrierId`로 Alias를 지정했다면, DCL 조건도 그 이름을 기준으로 작성해야 할 수 있다.

## 12. 정상 흐름과 오류 흐름

### 12.1 정상 흐름

```text
CDS View Entity 생성
→ @AccessControl.authorizationCheck: #CHECK 선언
→ Access Control 객체 생성
→ grant select on 대상 View 지정
→ 조건 작성
→ CDS View와 DCL Activate
→ Data Preview 또는 ABAP SELECT로 결과 확인
```

### 12.2 오류 흐름 1: DCL 대상 View 이름 오류

#### 증상

Access Control 활성화 중 대상 Entity를 찾을 수 없다는 오류가 발생한다.

#### 원인

`grant select on` 뒤의 View 이름이 잘못되었거나 아직 활성화되지 않았다.

#### 해결

```text
1. 대상 CDS View Entity 이름 확인
2. CDS View Activate 여부 확인
3. DCL에서 View 이름 오타 수정
4. 다시 Activate
```

### 12.3 오류 흐름 2: 조건 필드명 오류

#### 증상

DCL 조건의 필드를 찾을 수 없다는 오류가 발생한다.

#### 원인

CDS View의 원본 필드명과 노출 Alias를 혼동했을 수 있다.

예:

```abap
key carrid as CarrierId
```

이 경우 DCL 조건에서 `carrid`가 아니라 `CarrierId`를 사용해야 하는 상황이 있을 수 있다.

#### 해결

CDS View의 요소 목록을 기준으로 DCL 조건 필드를 작성한다.

### 12.4 오류 흐름 3: 데이터가 모두 보이지 않음

#### 증상

DCL 적용 후 조회 결과가 0건이다.

#### 가능 원인

| 원인 | 설명 |
|---|---|
| 조건이 너무 좁음 | 예: `CarrierId = 'ZZ'` 데이터 없음 |
| PFCG 권한 없음 | 테스트 사용자에게 해당 권한 값 미부여 |
| Client 차이 | 현재 Client에 해당 데이터 없음 |
| View 자체 데이터 없음 | 원본 테이블에 데이터 없음 |

#### 해결

```text
1. DCL 조건을 단순화하여 확인
2. 원본 CDS View 데이터를 먼저 확인
3. 테스트 사용자 권한 확인
4. 현재 Client 확인
```

### 12.5 오류 흐름 4: 데이터가 너무 많이 보임

#### 증상

권한 제한을 기대했지만 전체 데이터가 보인다.

#### 가능 원인

| 원인 | 설명 |
|---|---|
| `#NOT_REQUIRED` 사용 | Access Control 필수 확인을 하지 않음 |
| DCL 미활성화 | Access Control이 활성화되지 않음 |
| 다른 View 조회 | DCL 대상이 아닌 View를 조회 |
| Privileged Access 사용 | 권한 제한을 우회하는 특수 접근 사용 가능성 |
| 조건이 항상 참 | DCL WHERE 조건이 제한 효과가 없음 |

#### 해결

```text
1. 조회 대상 CDS View 확인
2. @AccessControl.authorizationCheck 확인
3. DCL Activate 상태 확인
4. WHERE 조건 검토
5. 테스트 코드에 우회 접근이 없는지 확인
```

## 13. 실무 적용 기준

### 13.1 업무 데이터는 기본적으로 권한 관점을 가져야 한다

CDS View가 다음 데이터를 포함한다면 권한 검토가 필요하다.

| 데이터 | 권한 검토 필요성 |
|---|---|
| 회사코드 | 조직별 데이터 제한 필요 |
| 플랜트 | 생산/물류 조직별 제한 가능 |
| 구매조직 | 구매 담당 범위 제한 가능 |
| 영업조직 | 영업 담당 범위 제한 가능 |
| 금액 | 민감 데이터 가능 |
| 인사/개인정보 | 강한 권한 통제 필요 |
| 고객/공급업체 | 업무 범위별 제한 가능 |

### 13.2 DCL은 보안의 전부가 아니다

DCL은 CDS 기반 데이터 접근 제어에서 중요한 역할을 하지만, 전체 보안 체계의 일부일 뿐이다.

실무 보안은 다음과 함께 검토되어야 한다.

| 계층 | 예 |
|---|---|
| 사용자 권한 | PFCG Role, Authorization Object |
| 프로그램 권한 | `AUTHORITY-CHECK` |
| CDS 권한 | DCL Access Control |
| 서비스 권한 | OData Service, ICF, Gateway 권한 |
| UI 권한 | Fiori Catalog, Space/Page, Role |
| 운영 통제 | 감사, 로그, 승인 절차 |

초급자는 “DCL만 만들면 모든 보안이 끝난다”라고 이해하면 안 된다.

### 13.3 `#NOT_REQUIRED` 남발 금지

개발 중 오류를 피하기 위해 `#NOT_REQUIRED`를 사용하는 경우가 있다. 하지만 이것이 운영까지 그대로 남으면 권한 누락으로 이어질 수 있다.

권장 체크 질문:

```text
이 View는 정말 권한이 필요 없는가?
업무 데이터가 포함되어 있는가?
OData나 Fiori로 노출되는가?
민감한 필드가 포함되어 있는가?
다른 View에서 재사용되는가?
```

### 13.4 권한 테스트는 반드시 역할별로 수행한다

DCL은 개발자 한 명의 권한으로만 테스트하면 안 된다.

최소한 다음 관점의 테스트가 필요하다.

| 테스트 사용자 | 기대 결과 |
|---|---|
| 전체 권한 사용자 | 모든 허용 데이터 조회 |
| 제한 권한 사용자 | 허용 범위 데이터만 조회 |
| 권한 없는 사용자 | 데이터 미조회 또는 접근 제한 |
| 다른 조직 사용자 | 본인 조직 데이터만 조회 |

## 14. ABAP SQL과 DCL의 관계

CDS View에 DCL이 설정되어 있으면 ABAP SQL로 해당 CDS View를 조회할 때 권한 조건이 적용되는 흐름을 이해해야 한다.

예:

```abap
SELECT *
  FROM zi_jhy_flight
  INTO TABLE @DATA(lt_flight).
```

이 SELECT 문에는 `WHERE CarrierId = 'AA'`가 직접 쓰여 있지 않다. 하지만 CDS View에 DCL이 적용되어 있다면 권한 조건에 따라 조회 결과가 제한될 수 있다.

초급자가 기억할 핵심은 다음이다.

```text
ABAP SQL의 WHERE 조건은 개발자가 작성한 조회 조건이다.
DCL 조건은 CDS Access Control이 적용하는 권한 조건이다.
둘은 서로 다른 목적을 가진다.
```

## 15. DCL과 Fiori / RAP 연결

CDS View Entity는 Fiori Elements와 RAP의 기반이 된다. 따라서 CDS 권한 제어는 단순한 개발 편의 기능이 아니라 서비스와 UI 노출의 안전성과 연결된다.

### 15.1 Fiori Elements

Fiori Elements는 CDS Annotation과 OData 서비스를 기반으로 화면을 생성한다. 만약 CDS View에 권한 제한이 없다면, Fiori 화면에서도 사용자가 볼 수 없어야 할 데이터가 표시될 수 있다.

### 15.2 RAP

RAP에서는 CDS 기반 Business Object가 OData V4 서비스로 노출될 수 있다. 이때 Entity 권한, Behavior 권한, DCL, 서비스 권한이 함께 고려되어야 한다.

이번 모듈에서는 RAP 권한 구현을 깊게 다루지 않는다. 다만 다음 연결은 기억해야 한다.

```text
CDS DCL 기초 이해
→ RAP Projection / Service 노출 시 데이터 접근 제어 이해
→ Fiori Elements 화면에서 데이터 보안 검토
```

## 18. 자주 하는 오해

### 18.1 DCL은 ABAP 프로그램 전체 실행 권한이다

아니다. DCL은 CDS 데이터 접근 제어와 관련된다. 프로그램 실행 권한, 트랜잭션 권한, 서비스 권한은 별도 계층에서 검토해야 한다.

### 18.2 `#CHECK`만 쓰면 권한이 자동으로 완성된다

아니다. `#CHECK`는 Access Control을 확인하겠다는 의도를 나타내는 Annotation이다. 실제 제한 조건은 DCL Access Control 객체에서 정의해야 한다.

### 18.3 `#NOT_REQUIRED`는 개발 편의를 위한 기본값이다

아니다. 권한이 정말 필요 없는 View인지 판단한 뒤 사용해야 한다. 운영 View에서 무분별하게 사용하면 데이터 노출 위험이 생긴다.

### 18.4 DCL이 있으면 PFCG 권한 설계가 필요 없다

아니다. 실무의 사용자 권한은 여전히 PFCG Role과 Authorization Object 기반으로 설계된다. DCL은 그 권한 값을 CDS 데이터 제한에 반영하는 계층으로 이해해야 한다.

### 18.5 DCL 테스트는 개발자 계정으로만 하면 충분하다

아니다. 개발자는 보통 넓은 권한을 가지고 있어 권한 제한 효과가 제대로 검증되지 않을 수 있다. 역할별 테스트 사용자를 통해 확인해야 한다.

## 19. 평가 문제

### 19.1 객관식

#### Q1. CDS DCL의 주 목적은 무엇인가?

A. CDS View의 필드 라벨을 정의한다.  
B. CDS View에 대한 데이터 접근 제어를 정의한다.  
C. CDS View의 SQL JOIN 성능을 자동 최적화한다.  
D. CDS View의 UI 배치를 정의한다.

**정답:** B

#### Q2. `@AccessControl.authorizationCheck: #CHECK`의 의미로 가장 적절한 것은?

A. 해당 View는 Access Control 적용 대상으로 본다.  
B. 해당 View는 권한이 절대 필요 없다.  
C. 해당 View는 테이블 버퍼링을 사용한다.  
D. 해당 View는 Metadata Extension을 사용하지 않는다.

**정답:** A

#### Q3. DCL 테스트 시 개발자 계정만으로 검증하면 위험한 이유는?

A. 개발자 계정은 CDS View를 열 수 없기 때문이다.  
B. 개발자 계정은 보통 넓은 권한을 가지고 있어 제한 효과를 확인하기 어렵기 때문이다.  
C. 개발자 계정은 ABAP SQL을 사용할 수 없기 때문이다.  
D. 개발자 계정은 Fiori 화면을 실행할 수 없기 때문이다.

**정답:** B

### 19.2 단답형

#### Q1. CDS View와 DCL의 역할 차이를 설명하시오.

**모범 답안:**  
CDS View는 어떤 데이터를 어떤 구조로 제공할지 정의한다. DCL은 해당 CDS View의 데이터 중 어떤 사용자가 어떤 조건의 데이터를 볼 수 있는지 접근 제어 규칙을 정의한다.

#### Q2. `#NOT_REQUIRED`를 무분별하게 사용하면 어떤 문제가 생길 수 있는가?

**모범 답안:**  
업무 데이터가 포함된 View에서 권한 검토 없이 `#NOT_REQUIRED`를 사용하면, OData, Fiori, ABAP SQL 등 다양한 소비 경로에서 사용자가 볼 수 없어야 할 데이터가 노출될 수 있다.

#### Q3. PFCG 권한과 DCL은 어떤 관계를 가질 수 있는가?

**모범 답안:**  
PFCG Role의 Authorization Object와 Authorization Field 값이 CDS DCL 조건에 반영되어, 사용자가 허용받은 조직, 회사코드, 플랜트 등의 데이터만 조회되도록 제한할 수 있다.

| 전체 권한 사용자와 제한 권한 사용자로 모두 테스트했는가? |  |
| OData/Fiori/RAP 노출 시나리오에서 권한 영향이 검토되었는가? |  |
| 권한 우회 접근이 코드나 테스트에 포함되어 있지 않은가? |  |

## 21. Section 마무리 요약

`THEORY-20 — CDS View Entity 기초` Section에서는 다음 흐름을 학습했다.

```text
CDS View Entity 기본 구조
→ Interface View와 Projection View 구분
→ Association 기초
→ Annotation과 의미 부여
→ Metadata Extension 기초
→ DCL / Authorization 개요
```

이 흐름은 이후 RAP와 Fiori Elements 학습의 핵심 기반이 된다.

초급자는 이 Section을 마친 뒤 다음을 이해해야 한다.

```text
CDS는 단순 SELECT 문이 아니라 재사용 가능한 의미 기반 데이터 모델이다.
Interface View와 Projection View를 구분하면 모델 재사용성과 소비 계층 설계가 명확해진다.
Association은 관계를 표현한다.
Annotation은 의미와 소비 정보를 부여한다.
Metadata Extension은 UI Annotation을 분리 관리할 수 있게 한다.
DCL은 CDS 데이터 접근 제어를 담당한다.
```
