## 3. 왜 CDS View를 계층화하는가?

CDS를 처음 배울 때는 하나의 View Entity만 만들어도 조회가 가능하다.

예를 들어 다음처럼 만들 수 있다.

```abap
@EndUserText.label: 'User Basic View'
define view entity ZI_JHY_User
  as select from zt_jhy_user
{
  key user_id   as UserId,
      user_name as UserName,
      status    as Status
}
```

이 View는 기본 조회에는 충분하다.  
그러나 실무에서는 하나의 View에 모든 목적을 몰아넣으면 문제가 생긴다.

### 3.1 하나의 View에 모든 목적을 넣을 때의 문제

| 문제 | 설명 |
|---|---|
| 재사용성 저하 | 다른 화면이나 API에서 필요한 필드 구성이 다를 수 있다. |
| 변경 영향 확대 | 특정 UI 요구 때문에 View를 바꾸면 다른 소비처도 영향을 받는다. |
| 보안/노출 범위 혼선 | 내부용 필드와 외부 노출 필드가 뒤섞일 수 있다. |
| 의미 계층 부재 | 어떤 View가 핵심 모델이고 어떤 View가 소비 모델인지 구분하기 어렵다. |
| RAP 확장 어려움 | 후속 Behavior, Service Projection, UI Annotation과 연결할 때 구조가 흐트러진다. |

그래서 CDS 모델은 보통 계층을 나눈다.

```text
Database Table
  ↓
Interface View  (ZI_*)
  ↓
Projection View (ZC_*)
  ↓
Service / UI / Report / API
```

## 4. Interface View란 무엇인가?

### 4.1 정의

Interface View는 기본 데이터 소스 위에 재사용 가능한 핵심 데이터 모델을 만드는 CDS View이다.

교육용 Prefix로는 보통 `ZI_*`를 사용한다.

```text
ZI = Z Interface
```

예:

```text
ZI_JHY_User
ZI_JHY_Flight
ZI_JHY_Booking
ZI_JHY_SalesOrder
```

Interface View는 특정 화면 하나만을 위한 View가 아니다.  
여러 소비자가 안정적으로 사용할 수 있는 **내부 표준 데이터 모델**에 가깝다.

### 4.2 Interface View의 역할

| 역할 | 설명 |
|---|---|
| 핵심 데이터 모델 | DB Table 또는 기본 View 위에 비즈니스 의미를 부여한다. |
| 재사용 계층 | 여러 Projection View, Query, Service에서 공통으로 참조할 수 있다. |
| 필드 정규화 | DB 필드명을 소비하기 좋은 Element 이름으로 정리한다. |
| 기본 계산/파생 | 재사용 가능한 간단한 계산 필드를 둘 수 있다. |
| 관계 모델의 기반 | 후속 Association 계층의 기반이 될 수 있다. |

### 4.3 Interface View에 넣기 좋은 것

Interface View에는 다음과 같은 내용을 넣는 것이 적절하다.

| 항목 | 예시 |
|---|---|
| 안정적인 Key | `UserId`, `CarrierId`, `ConnectionId` |
| 핵심 업무 필드 | 사용자명, 상태, 생성일, 금액, 수량 등 |
| 재사용 가능한 의미 변환 | 상태 설명, 금액 계산, 기본 파생 필드 |
| 공통 Association 기반 | Header → Item, Carrier → Connection 등 |
| 데이터 소스 표준화 | 테이블 필드명을 의미 있는 CDS Element로 Alias 처리 |

### 4.4 Interface View에 과도하게 넣지 말아야 할 것

| 피해야 할 내용 | 이유 |
|---|---|
| 특정 UI 화면만을 위한 필드 순서 | Interface View는 화면 전용 계층이 아니다. |
| 특정 앱에서만 필요한 임시 계산 | 다른 소비처에 불필요한 결합을 만든다. |
| UI Annotation 대량 작성 | Metadata Extension 또는 Projection 계층에서 분리하는 편이 낫다. |
| 외부 노출 전용 이름 정책 | 내부 재사용 모델과 외부 API 모델이 뒤섞인다. |

## 5. Projection View란 무엇인가?

### 5.1 정의

Projection View는 Interface View를 기반으로 특정 소비 목적에 맞게 필드를 노출하거나 제한하는 CDS View이다.

교육용 Prefix로는 보통 `ZC_*`를 사용한다.

```text
ZC = Z Consumption 또는 Z Projection/Consumption 계층
```

예:

```text
ZC_JHY_User
ZC_JHY_UserList
ZC_JHY_UserVH
ZC_JHY_Flight
```

Projection View는 Interface View를 그대로 외부에 노출하지 않고, 목적에 맞게 정리한 공개 계층으로 이해할 수 있다.

### 5.2 Projection View의 역할

| 역할 | 설명 |
|---|---|
| 소비 목적별 필드 선택 | 필요한 필드만 외부 또는 화면에 노출한다. |
| 노출 이름 정리 | 소비자에게 적합한 Element 이름을 제공한다. |
| UI/API 경계 설정 | 내부 모델과 외부 소비 모델을 분리한다. |
| RAP Projection 기반 | RAP에서 Projection Layer로 확장될 수 있다. |
| 앱별 모델 분리 | 목록 화면, 상세 화면, Value Help 등을 각각 다르게 구성할 수 있다. |

### 5.3 Projection View에 넣기 좋은 것

| 항목 | 예시 |
|---|---|
| 소비 목적에 맞는 필드 제한 | 목록 화면에는 핵심 필드만 노출 |
| 외부 노출 이름 정리 | `UserId`, `UserName`, `StatusText` |
| UI에서 필요한 표시 필드 | 상태명, 통화, 단위, 텍스트 필드 |
| 앱별 필드 구성 | List, Detail, Value Help용 View 분리 |
| Annotation 연결 준비 | 후속 UI Annotation, Metadata Extension의 대상 |

### 5.4 Projection View에 넣지 않는 것이 좋은 것

| 피해야 할 내용 | 이유 |
|---|---|
| 원천 테이블 직접 접근 | Interface View 계층을 우회하게 된다. |
| 핵심 비즈니스 의미의 중복 구현 | 여러 Projection View에서 로직 중복이 발생한다. |
| DB 구조에 강하게 결합된 필드명 | 소비 계층이 DB 변경에 직접 영향을 받는다. |
| 모든 필드 무조건 노출 | Projection View의 의미가 약해진다. |

## 6. Interface View와 Projection View 비교

| 구분 | Interface View (`ZI_*`) | Projection View (`ZC_*`) |
|---|---|---|
| 주 목적 | 재사용 가능한 핵심 데이터 모델 | 소비 목적에 맞춘 노출 모델 |
| 주 사용처 | 다른 CDS, Projection, Query, RAP Interface Layer | UI, OData, 앱, Report, RAP Projection Layer |
| 데이터 소스 | DB Table 또는 다른 기본 View | 주로 Interface View |
| 변경 기준 | 핵심 업무 모델 변경 시 | 소비 요구사항 변경 시 |
| 필드 구성 | 상대적으로 넓고 안정적 | 목적에 맞게 제한적 |
| 이름 정책 | 내부 표준 모델 중심 | 소비자 이해 중심 |
| Prefix 예시 | `ZI_JHY_User` | `ZC_JHY_User` |
| 후속 연결 | Association, Behavior 기반 | Service Definition, UI Annotation, Metadata Extension |

핵심은 다음이다.

```text
ZI_*는 내부 표준 모델이다.
ZC_*는 소비 목적 모델이다.
```

## 8. Interface View 예제: `ZI_JHY_User`

### 8.1 생성 목적

`ZI_JHY_User`는 사용자 테이블 위에 재사용 가능한 핵심 사용자 모델을 제공한다.

### 8.2 예제 코드

```abap
@EndUserText.label: 'Interface View for User'
define view entity ZI_JHY_User
  as select from zt_jhy_user
{
  key user_id    as UserId,
      user_name  as UserName,
      status     as Status,
      created_by as CreatedBy,
      created_on as CreatedOn
}
```

### 8.3 코드 설명

| 코드 | 의미 |
|---|---|
| `@EndUserText.label` | View 설명 라벨 |
| `define view entity ZI_JHY_User` | CDS View Entity 정의 |
| `as select from zt_jhy_user` | 원천 테이블 지정 |
| `key user_id as UserId` | CDS Element Key와 Alias 지정 |
| `created_on as CreatedOn` | DB 필드명을 CDS Element 이름으로 정리 |

### 8.4 왜 Alias를 사용하는가?

DB Table 필드는 보통 ABAP Dictionary 관행에 따라 대문자 또는 언더스코어 중심으로 설계된다.
CDS Element는 서비스, UI, API에서 노출될 수 있으므로 보다 의미 있는 이름으로 정리하는 것이 좋다.

예:

| DB Field | CDS Element |
|---|---|
| USER_ID | UserId |
| USER_NAME | UserName |
| CREATED_BY | CreatedBy |
| CREATED_ON | CreatedOn |

초급자는 Alias를 단순한 이름 변경이 아니라 **모델 경계에서 의미를 정리하는 행위**로 이해해야 한다.

## 9. Projection View 예제: `ZC_JHY_User`

### 9.1 생성 목적

`ZC_JHY_User`는 `ZI_JHY_User`를 기반으로 소비자에게 필요한 사용자 정보를 노출한다.

### 9.2 예제 코드

```abap
@EndUserText.label: 'Projection View for User'
define view entity ZC_JHY_User
  as projection on ZI_JHY_User
{
  key UserId,
      UserName,
      Status
}
```

### 9.3 코드 설명

| 코드 | 의미 |
|---|---|
| `define view entity ZC_JHY_User` | Projection View Entity 정의 |
| `as projection on ZI_JHY_User` | Interface View를 기반으로 Projection 생성 |
| `key UserId` | Interface View의 Key를 Projection에서도 노출 |
| `UserName`, `Status` | 소비 목적에 맞게 필요한 필드만 선택 |

이 예제에서는 `CreatedBy`, `CreatedOn`을 Projection View에서 제외했다.  
즉, 내부 모델에는 존재하지만 소비 모델에서는 감춘 것이다.

이것이 Projection View의 중요한 역할이다.

```text
내부 모델의 모든 필드를 외부에 그대로 보여줄 필요는 없다.
```

## 10. 여러 Projection View로 나누는 예

하나의 Interface View에서 여러 Projection View를 만들 수 있다.

```text
ZI_JHY_User
  ├─ ZC_JHY_UserList
  ├─ ZC_JHY_UserDetail
  └─ ZC_JHY_UserVH
```

### 10.1 목록용 Projection

```abap
@EndUserText.label: 'User List Projection'
define view entity ZC_JHY_UserList
  as projection on ZI_JHY_User
{
  key UserId,
      UserName,
      Status
}
```

### 10.2 상세용 Projection

```abap
@EndUserText.label: 'User Detail Projection'
define view entity ZC_JHY_UserDetail
  as projection on ZI_JHY_User
{
  key UserId,
      UserName,
      Status,
      CreatedBy,
      CreatedOn
}
```

### 10.3 Value Help용 Projection

```abap
@EndUserText.label: 'User Value Help Projection'
define view entity ZC_JHY_UserVH
  as projection on ZI_JHY_User
{
  key UserId,
      UserName
}
```

이 구조의 장점은 명확하다.

| Projection | 목적 | 노출 필드 |
|---|---|---|
| `ZC_JHY_UserList` | 목록 표시 | UserId, UserName, Status |
| `ZC_JHY_UserDetail` | 상세 표시 | UserId, UserName, Status, CreatedBy, CreatedOn |
| `ZC_JHY_UserVH` | 입력 도움말 | UserId, UserName |

동일한 핵심 모델을 재사용하면서 소비 목적별로 노출 범위를 다르게 할 수 있다.

## 11. ADT에서 생성하는 절차

CDS View Entity는 일반적으로 ADT(Eclipse)에서 생성한다.

### 11.1 Interface View 생성 절차

```text
1. ADT에서 ABAP Package 선택
2. New → Other ABAP Repository Object
3. Core Data Services → Data Definition 선택
4. Name 입력: ZI_JHY_User
5. Description 입력: Interface View for User
6. Template 선택 또는 빈 소스 생성
7. define view entity 코드 작성
8. Syntax Check
9. Activate
10. Data Preview로 확인
```

### 11.2 Projection View 생성 절차

```text
1. 같은 Package에서 Data Definition 생성
2. Name 입력: ZC_JHY_User
3. Description 입력: Projection View for User
4. as projection on ZI_JHY_User 코드 작성
5. Syntax Check
6. Activate
7. Data Preview로 확인
```

### 11.3 활성화 순서

Projection View는 Interface View를 참조한다.  
따라서 활성화 순서는 다음과 같다.

```text
1. 원천 테이블 또는 원천 View 활성화
2. ZI_* Interface View 활성화
3. ZC_* Projection View 활성화
```

순서를 거꾸로 하면 Projection View가 참조 대상을 찾지 못해 활성화 오류가 발생할 수 있다.

## 12. 정상 흐름과 오류 흐름

### 12.1 정상 흐름

```text
원천 테이블 확인
→ ZI_* Interface View 생성
→ ZI_* 활성화
→ Data Preview 확인
→ ZC_* Projection View 생성
→ ZC_* 활성화
→ Data Preview 확인
```

### 12.2 오류 흐름 1: Interface View가 활성화되지 않음

#### 현상

```text
ZC_JHY_User 활성화 시 ZI_JHY_User를 찾을 수 없거나 사용할 수 없다는 오류 발생
```

#### 원인

- `ZI_JHY_User`가 아직 생성되지 않음
- `ZI_JHY_User`가 비활성 상태
- 이름 오타
- 다른 Package 또는 시스템에만 존재하는 객체를 참조

#### 해결

```text
1. ZI_JHY_User 존재 여부 확인
2. ZI_JHY_User Syntax Check
3. ZI_JHY_User Activate
4. ZC_JHY_User 재활성화
```

### 12.3 오류 흐름 2: `as projection on` 대신 `as select from`을 사용함

#### 현상

Projection View를 만들려 했는데 원천 테이블을 직접 바라보는 일반 View가 만들어진다.

#### 문제

Projection 계층이 Interface 계층을 우회하게 된다.

#### 해결

Projection View 목적이라면 다음처럼 Interface View를 기반으로 작성한다.

```abap
define view entity ZC_JHY_User
  as projection on ZI_JHY_User
{
  key UserId,
      UserName,
      Status
}
```

### 12.4 오류 흐름 3: Projection View에 모든 필드를 그대로 노출

#### 현상

`ZC_*` View가 `ZI_*` View와 거의 동일한 필드 목록을 가진다.

#### 문제

Projection View의 목적이 약해진다.  
소비 목적에 맞게 제한하거나 정리하지 않았다면 계층을 나눈 실익이 줄어든다.

#### 해결

소비 목적을 먼저 정의한다.

```text
목록용인가?
상세용인가?
Value Help용인가?
API 노출용인가?
RAP UI용인가?
```

목적에 따라 필드를 선택한다.

### 12.5 오류 흐름 4: 핵심 로직을 Projection마다 중복 구현

#### 현상

상태 텍스트, 금액 계산, 기본 파생 로직을 여러 `ZC_*` View에 반복 작성한다.

#### 문제

로직 중복이 생기고, 변경 시 여러 View를 수정해야 한다.

#### 해결

여러 소비처에서 재사용할 로직은 `ZI_*` 계층으로 올리는 것을 검토한다.

## 13. 실무 설계 기준

### 13.1 Interface View 설계 기준

Interface View는 재사용 가능한 안정 계층이다.

설계 시 다음 질문을 한다.

```text
이 필드는 여러 소비처에서 공통으로 필요한가?
이 계산은 여러 앱에서 같은 의미로 사용되는가?
이 이름은 내부 개발자들이 공통으로 이해할 수 있는가?
이 View는 후속 Association이나 RAP Entity의 기반이 될 수 있는가?
```

### 13.2 Projection View 설계 기준

Projection View는 소비 목적 계층이다.

설계 시 다음 질문을 한다.

```text
이 View는 어떤 소비자를 위한 것인가?
목록 화면인가, 상세 화면인가, Value Help인가?
외부에 노출하면 안 되는 필드는 없는가?
UI 또는 API에서 필요한 이름은 무엇인가?
추후 Metadata Extension이나 Service Definition의 대상인가?
```

### 13.3 Prefix는 단순 취향이 아니다

`ZI_*`, `ZC_*` Prefix는 단순 이름 규칙이 아니라 계층 의도를 드러낸다.

| Prefix | 의도 |
|---|---|
| `ZI_*` | 재사용 가능한 Interface View |
| `ZC_*` | 소비 목적 Projection / Consumption View |

프로젝트마다 Prefix는 다를 수 있다.  
하지만 중요한 것은 **이름만 보고 계층과 용도를 알 수 있어야 한다**는 점이다.

[추정] 실제 고객사 프로젝트에서는 `ZI_`, `ZC_` 대신 프로젝트 Prefix나 Namespace를 사용할 수 있다. 이 경우에도 Interface 계층과 Consumption 계층의 구분 원칙은 유지하는 것이 좋다.

## 14. RAP와의 연결

이 모듈은 RAP 전체를 설명하는 문서가 아니다.  
하지만 Interface View와 Projection View 구분은 RAP 학습의 선행 개념이다.

RAP에서는 일반적으로 다음과 같은 계층적 흐름을 접하게 된다.

```text
Database Table
  ↓
Interface View Entity (ZI_*)
  ↓
Projection View Entity (ZC_*)
  ↓
Behavior Definition / Projection Behavior
  ↓
Service Definition
  ↓
Service Binding
  ↓
Fiori Elements / OData V4
```

초급 단계에서는 다음만 기억한다.

```text
RAP에서 ZI_*는 비즈니스 객체의 핵심 데이터 모델에 가깝고,
ZC_*는 서비스를 통해 소비되는 노출 모델에 가깝다.
```

Behavior Definition, EML, Draft, Service Binding은 후속 RAP Section에서 다루는 것이 적절하다.

### 15.2 실습 1 — Interface View 생성

| Key Element가 존재하는가? |  |
| Alias가 의미 있게 지정되었는가? |  |

### 15.3 실습 2 — Projection View 생성

다음 CDS Data Definition을 생성한다.

```abap
@EndUserText.label: 'Projection View for User'

  as projection on ZI_JHY_User

  key UserId,
      UserName,
      Status
```

확인할 항목은 다음과 같다.

| 확인 항목 | 완료 여부 |

## 17. 평가 문제

### 17.1 객관식

#### Q1. Interface View의 주된 목적은 무엇인가?

A. 특정 화면의 색상을 지정한다.  
B. 재사용 가능한 핵심 데이터 모델을 제공한다.  
C. 사용자 권한을 직접 부여한다.  
D. SAP GUI 메뉴를 생성한다.

정답: B

#### Q2. Projection View에 대한 설명으로 가장 적절한 것은?

A. 반드시 원천 DB Table을 직접 조회해야 한다.  
B. Interface View를 기반으로 소비 목적에 맞는 필드를 노출하는 계층이다.  
C. Domain Fixed Value를 정의하는 객체이다.  
D. ABAP 프로그램의 Selection Screen을 정의한다.

정답: B

#### Q3. 다음 중 일반적인 교육용 Prefix 연결이 올바른 것은?

A. `ZI_*` = Projection View, `ZC_*` = Domain  
B. `ZI_*` = Interface View, `ZC_*` = Projection / Consumption View  
C. `ZI_*` = Internal Table, `ZC_*` = Check Table  
D. `ZI_*` = Transaction Code, `ZC_*` = Class

정답: B

### 17.2 서술형

#### Q1. Interface View와 Projection View를 분리하는 이유를 설명하시오.

모범 답안:  
Interface View는 재사용 가능한 핵심 데이터 모델을 안정적으로 제공하고, Projection View는 특정 UI, API, Report, RAP 서비스 등 소비 목적에 맞게 필드와 노출 범위를 정리한다. 이 둘을 분리하면 내부 모델 변경과 소비 요구 변경을 분리할 수 있어 유지보수성과 확장성이 좋아진다.

#### Q2. `ZC_*` View가 원천 테이블을 직접 조회하지 않고 `ZI_*` View를 기반으로 해야 하는 이유를 설명하시오.

모범 답안:  
Projection View가 원천 테이블을 직접 조회하면 Interface 계층의 재사용 모델을 우회하게 된다. 이 경우 여러 소비 View가 DB 구조에 직접 결합되고, 공통 의미나 계산 로직이 중복될 수 있다. `ZC_*`는 `ZI_*`를 기반으로 하여 내부 모델과 소비 모델을 분리하는 것이 좋다.

#### Q3. 하나의 `ZI_JHY_User`에서 `ZC_JHY_UserList`와 `ZC_JHY_UserVH`를 따로 만들 수 있는 이유는 무엇인가?

모범 답안:  
Interface View는 핵심 사용자 모델을 제공하고, Projection View는 소비 목적별로 필요한 필드만 노출할 수 있기 때문이다. 목록 화면은 상태까지 필요할 수 있고, Value Help는 사용자 ID와 이름만 필요할 수 있으므로 같은 Interface View를 기반으로 여러 Projection View를 만들 수 있다.

## 18. 초급자 실수와 예방

| 실수 | 문제 | 예방 |
|---|---|---|
| `ZI_*`와 `ZC_*`를 이름만 다르게 만들고 내용은 동일하게 둔다 | 계층 분리의 의미가 약해진다 | 소비 목적을 먼저 정의한다 |
| Projection View가 DB Table을 직접 조회한다 | Interface 계층을 우회한다 | `as projection on ZI_*` 구조를 사용한다 |
| Interface View에 UI 전용 Annotation을 과도하게 넣는다 | 핵심 모델이 UI에 종속된다 | Annotation 분리와 Projection 계층 활용을 검토한다 |
| 여러 Projection View에 같은 계산 로직을 반복한다 | 변경 시 중복 수정 필요 | 공통 로직은 Interface View로 올린다 |
| Prefix만 맞추고 역할을 이해하지 못한다 | 유지보수 시 혼란 발생 | Prefix보다 계층의 책임을 먼저 이해한다 |

## 19. 핵심 요약

이번 모듈의 핵심은 다음과 같다.

```text
Interface View는 재사용 가능한 핵심 데이터 모델이다.
Projection View는 소비 목적에 맞게 Interface View를 노출하는 계층이다.
교육용 Prefix로 Interface View는 ZI_*, Projection View는 ZC_*를 사용한다.
ZC_*는 원칙적으로 ZI_*를 기반으로 작성하여 내부 모델과 소비 모델을 분리한다.
같은 ZI_*에서 목적이 다른 여러 ZC_* View를 만들 수 있다.
이 계층 구분은 RAP, Fiori Elements, OData 노출 학습의 중요한 선행 개념이다.
```
