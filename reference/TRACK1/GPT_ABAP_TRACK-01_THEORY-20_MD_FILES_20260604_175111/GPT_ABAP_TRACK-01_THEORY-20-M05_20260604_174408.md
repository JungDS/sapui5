## 3. Metadata Extension이란 무엇인가?

Metadata Extension은 CDS Entity에 대한 Annotation을 별도의 개발 객체로 분리하여 작성하는 기능이다.

예를 들어 `ZC_JHY_Flight`라는 Projection View가 있다고 가정한다. 이 View는 항공편 데이터를 어떤 필드로 조회할지 정의한다.

```abap
@EndUserText.label: 'Flight Consumption View'
@Metadata.allowExtensions: true
define view entity ZC_JHY_Flight
  as projection on ZI_JHY_Flight
{
  key CarrierId,
  key ConnectionId,
  key FlightDate,
      Price,
      CurrencyCode
}
```

이 View 본문 안에 `@UI.lineItem`, `@UI.selectionField`, `@UI.identification` 같은 UI Annotation을 모두 넣을 수도 있다. 하지만 UI 표시 관련 Annotation이 많아지면 View 본문이 길어지고, 데이터 모델의 본질과 화면 표현이 섞인다.

Metadata Extension을 사용하면 UI 관련 Annotation을 별도 파일로 분리할 수 있다.

```abap
@Metadata.layer: #CUSTOMER
annotate entity ZC_JHY_Flight with
{
  @UI.lineItem: [{ position: 10, label: 'Carrier' }]
  CarrierId;

  @UI.lineItem: [{ position: 20, label: 'Connection' }]
  ConnectionId;

  @UI.selectionField: [{ position: 10 }]
  FlightDate;
}
```

> [추정] 시스템 릴리스와 ADT 템플릿에 따라 `annotate entity` 또는 유사한 Metadata Extension 문법 표시가 다를 수 있다. 실제 작성 시에는 ADT의 Metadata Extension 생성 템플릿과 시스템 문법 검사를 우선한다.

핵심은 문법 자체보다 **분리 목적**이다.

```text
CDS 본문: 데이터 구조와 관계를 정의
Metadata Extension: 표시, UI, 소비 계층 Annotation을 분리
```

## 4. 왜 Metadata Extension이 필요한가?

### 4.1 데이터 모델과 UI 표현의 분리

CDS View Entity는 원래 데이터 모델을 정의하는 객체이다. 여기에 UI Annotation을 모두 직접 작성하면 다음 문제가 생긴다.

```text
데이터 필드 정의
Association 정의
Semantics Annotation
UI LineItem
UI SelectionField
UI Facet
UI Identification
Search 관련 Annotation
```

이 모든 정보가 한 파일에 섞이면 초급자는 물론 실무자도 유지보수가 어려워진다.

Metadata Extension은 다음처럼 역할을 나누게 해준다.

| 영역 | 권장 위치 |
|---|---|
| 데이터 구조 | CDS View Entity 본문 |
| Key, Field, Association | CDS View Entity 본문 |
| 기본 의미 Annotation | CDS View Entity 본문 또는 상황별 분리 |
| UI 표시 Annotation | Metadata Extension |
| Fiori Elements 표시 제어 | Metadata Extension |
| 권한 제어 | DCL, Access Control |

### 4.2 유지보수성 향상

UI 요구사항은 데이터 모델보다 자주 바뀔 수 있다. 예를 들어 리스트 화면에서 표시 순서를 바꾸거나, Selection Field를 추가하거나, Identification 영역에 필드를 배치하는 요구가 생길 수 있다.

이때 UI Annotation이 Metadata Extension에 분리되어 있으면 데이터 모델 본문을 직접 수정하지 않고 UI 메타데이터를 조정할 수 있다.

### 4.3 Clean Core 관점

S/4HANA와 ABAP Cloud 흐름에서는 핵심 데이터 모델과 소비/UI 계층을 명확히 분리하는 설계가 중요하다. Metadata Extension은 이러한 분리 설계를 돕는 도구 중 하나이다.

단, Metadata Extension을 사용한다고 해서 무조건 Clean Core가 보장되는 것은 아니다. 표준 확장 방식, released API 사용 여부, 네임스페이스, 권한, Transport 정책까지 함께 고려해야 한다.

## 5. `@Metadata.allowExtensions: true`

Metadata Extension을 적용하려면 대상 CDS Entity가 Metadata Extension을 허용해야 한다.

대상 View Entity에는 일반적으로 다음 Annotation을 둔다.

```abap
@Metadata.allowExtensions: true
```

예시:

```abap
@EndUserText.label: 'Flight Consumption View'
@AccessControl.authorizationCheck: #NOT_REQUIRED
@Metadata.allowExtensions: true
define view entity ZC_JHY_Flight
  as projection on ZI_JHY_Flight
{
  key CarrierId,
  key ConnectionId,
  key FlightDate,
      Price,
      CurrencyCode
}
```

### 5.1 의미

`@Metadata.allowExtensions: true`는 이 CDS Entity가 별도의 Metadata Extension 객체에 의해 Annotation 보강을 받을 수 있음을 나타낸다.

초급자에게는 다음처럼 설명할 수 있다.

```text
이 View는 별도 Metadata Extension 파일에서 UI Annotation을 추가해도 됩니다.
```

### 5.2 누락 시 문제

이 Annotation이 없으면 Metadata Extension을 작성했더라도 대상 View에 정상 적용되지 않거나 활성화/검증 과정에서 문제가 발생할 수 있다.

점검 순서는 다음과 같다.

```text
1. 대상 CDS View Entity에 @Metadata.allowExtensions: true가 있는가?
2. Metadata Extension이 올바른 Entity를 annotate하고 있는가?
3. Field 이름이 실제 View Element와 일치하는가?
4. Metadata Extension 객체가 활성화되어 있는가?
5. ADT Problems View에 오류가 없는가?
```

## 6. `@Metadata.layer`

Metadata Extension 객체에는 일반적으로 `@Metadata.layer` Annotation이 사용된다.

예시:

```abap
@Metadata.layer: #CUSTOMER
annotate entity ZC_JHY_Flight with
{
  @UI.lineItem: [{ position: 10 }]
  CarrierId;
}
```

### 6.1 Layer의 목적

Layer는 Metadata Extension이 어느 계층의 Annotation인지 구분하는 역할을 한다.

초급자 관점에서는 다음 정도로 이해하면 된다.

| Layer 개념 | 초급자 설명 |
|---|---|
| CORE | 핵심 또는 기본 제공 메타데이터 계층 |
| INDUSTRY | 산업별 확장 계층 |
| PARTNER | 파트너 확장 계층 |
| CUSTOMER | 고객 확장 계층 |

고객 프로젝트에서 직접 작성하는 Z Metadata Extension은 일반적으로 Customer Layer 관점으로 이해하면 된다.

> [추정] 사용 가능한 Layer 값과 적용 정책은 시스템 릴리스 및 개발 가이드에 따라 달라질 수 있으므로, 실제 프로젝트에서는 ADT 자동완성, 구문 검사, 고객사 개발 표준을 우선한다.

### 6.2 왜 Layer가 필요한가?

Annotation은 여러 위치와 계층에서 제공될 수 있다. Layer는 Annotation 충돌이나 우선순위 관리와 관련된 기반 정보를 제공한다.

초급자는 “여러 주체가 Annotation을 보강할 수 있으므로 어느 계층의 확장인지 표시한다” 정도로 이해하면 충분하다.

## 7. UI Annotation을 Metadata Extension으로 분리하기

### 7.1 대상 Projection View 예시

이번 실습에서는 다음 View가 이미 존재한다고 가정한다.

```abap
@EndUserText.label: 'Flight Consumption View'
@AccessControl.authorizationCheck: #NOT_REQUIRED
@Metadata.allowExtensions: true
define view entity ZC_JHY_Flight
  as projection on ZI_JHY_Flight
{
  key CarrierId,
  key ConnectionId,
  key FlightDate,
      Price,
      CurrencyCode
}
```

이 View는 화면 소비 계층에서 사용될 가능성이 있는 Projection View이다. 따라서 UI 관련 Annotation을 Metadata Extension으로 분리하기에 적합하다.

### 7.2 Metadata Extension 예시

```abap
@Metadata.layer: #CUSTOMER
annotate entity ZC_JHY_Flight with
{
  @UI.lineItem: [{ position: 10, label: 'Carrier' }]
  @UI.selectionField: [{ position: 10 }]
  CarrierId;

  @UI.lineItem: [{ position: 20, label: 'Connection' }]
  ConnectionId;

  @UI.lineItem: [{ position: 30, label: 'Flight Date' }]
  @UI.selectionField: [{ position: 20 }]
  FlightDate;

  @UI.lineItem: [{ position: 40, label: 'Price' }]
  Price;

  @UI.lineItem: [{ position: 50, label: 'Currency' }]
  CurrencyCode;
}
```

이 예시는 다음을 보여준다.

| Annotation | 역할 |
|---|---|
| `@UI.lineItem` | 리스트 화면에 필드를 표시하기 위한 정보 |
| `@UI.selectionField` | 검색/필터 영역에 필드를 표시하기 위한 정보 |
| `position` | 표시 순서 |
| `label` | 표시 라벨 |

실무에서는 `@UI.identification`, `@UI.facet`, `@Search`, `@Consumption` 등 다양한 Annotation이 함께 사용될 수 있다. 하지만 이번 모듈에서는 `lineItem`과 `selectionField` 중심으로 이해한다.

## 8. ADT에서 Metadata Extension 생성 절차

Metadata Extension은 Eclipse ADT에서 생성하는 것이 일반적이다.

### 8.1 생성 흐름

```text
1. Eclipse ADT 실행
2. ABAP Project 접속
3. Package 선택
4. New → Other ABAP Repository Object
5. 검색창에 Metadata Extension 또는 DDLX 검색
6. Metadata Extension 선택
7. 객체명 입력
8. 대상 CDS Entity 지정
9. 템플릿 기반으로 기본 코드 생성
10. UI Annotation 작성
11. Save
12. Activate
```

### 8.2 객체명 예시

Metadata Extension 객체명은 프로젝트 네이밍 규칙을 따른다.

예시:

```text
ZC_JHY_FLIGHT_MDE
ZME_JHY_FLIGHT
ZMX_JHY_FLIGHT_UI
```

초급 교육용으로는 대상 View와 연결이 잘 드러나는 이름을 권장한다.

```text
ZC_JHY_FLIGHT_MDE
```

### 8.3 Package와 Transport

교육용 로컬 실습이면 `$TMP`를 사용할 수 있다.  
실무 프로젝트에서는 반드시 지정된 Package와 Transport Request를 사용해야 한다.

## 9. 생성 후 검증 방법

Metadata Extension은 단순히 활성화했다고 끝나는 것이 아니다. 실제로 대상 View에 Annotation이 반영되는지 확인해야 한다.

### 9.1 ADT Problems View 확인

가장 먼저 ADT의 Problems View를 확인한다.

| 오류 유형 | 확인 내용 |
|---|---|
| Syntax Error | 문법 오류 여부 |
| Unknown Element | 대상 View에 없는 필드를 Annotation했는지 여부 |
| Unknown Annotation | 시스템에서 지원하지 않는 Annotation인지 여부 |
| Metadata Extension not allowed | 대상 View에 `@Metadata.allowExtensions`가 없는지 여부 |

### 9.2 대상 View Element 이름 확인

Metadata Extension은 대상 CDS Entity의 Element 이름을 정확히 참조해야 한다.

예를 들어 대상 View에 `CarrierId`가 있는데 Extension에서 `Carrid`라고 작성하면 오류가 발생할 수 있다.

```text
대상 View: CarrierId
잘못된 Extension: Carrid
올바른 Extension: CarrierId
```

### 9.3 Annotation Preview 또는 소비 화면 확인

시스템과 개발 환경에 따라 다음 방식으로 확인할 수 있다.

| 확인 방법 | 설명 |
|---|---|
| ADT Annotation 정보 확인 | 대상 CDS Entity의 Annotation 정보 확인 |
| Fiori Elements Preview | UI Annotation이 화면 구성에 반영되는지 확인 |
| OData Service Metadata | 메타데이터에 UI Annotation이 반영되는지 확인 |
| ADT Data Preview | 데이터 자체 확인. UI Annotation 전체 검증에는 제한적 |

초급자는 먼저 “문법 오류 없이 활성화되는가”와 “대상 필드명이 정확한가”를 확인하고, Fiori/RAP Section에서 화면 반영을 더 자세히 다루면 된다.

## 10. 정상 흐름과 오류 흐름

### 10.1 정상 흐름

```text
Projection View 준비
→ @Metadata.allowExtensions: true 확인
→ Metadata Extension 생성
→ @Metadata.layer 지정
→ 대상 Entity annotate
→ UI Annotation 작성
→ Activate
→ Problems View 확인
→ 소비 화면 또는 메타데이터 확인
```

### 10.2 오류 흐름 1: 대상 View에 Extension 허용 누락

증상:

```text
Metadata Extension을 만들었지만 적용되지 않거나 활성화 오류가 발생한다.
```

점검:

```text
대상 CDS View Entity에 @Metadata.allowExtensions: true가 있는가?
```

해결:

```abap
@Metadata.allowExtensions: true
define view entity ZC_JHY_Flight
  as projection on ZI_JHY_Flight
{
  ...
}
```

### 10.3 오류 흐름 2: Field 이름 불일치

증상:

```text
Unknown element 또는 대상 Element를 찾을 수 없다는 오류가 발생한다.
```

원인:

```text
Metadata Extension에서 작성한 필드명이 대상 View의 Element 이름과 다르다.
```

해결:

대상 View를 열고 Element 이름을 복사하여 Metadata Extension에 정확히 사용한다.

### 10.4 오류 흐름 3: Annotation Scope 오류

증상:

```text
Annotation cannot be used at this position
```

원인:

Annotation이 View 수준에 써야 하는데 Element 수준에 썼거나, 반대로 Element 수준 Annotation을 View 수준에 작성했을 수 있다.

해결:

Annotation의 사용 위치를 확인한다.

| 위치 | 예시 |
|---|---|
| View 수준 | `@UI.headerInfo` |
| Element 수준 | `@UI.lineItem`, `@UI.selectionField` |
| Association 또는 Field 수준 | 상황별 Annotation Scope 확인 필요 |

### 10.5 오류 흐름 4: Layer 누락 또는 부적절

증상:

```text
Metadata layer 관련 오류 또는 경고 발생
```

해결:

ADT 템플릿에서 제안하는 `@Metadata.layer`를 사용하고, 고객 개발에서는 일반적으로 `#CUSTOMER` 계층을 검토한다.

### 10.6 오류 흐름 5: UI Annotation을 Interface View에 과도하게 배치

증상:

```text
Interface View가 데이터 모델과 UI 표현을 동시에 떠안아 재사용성이 떨어진다.
```

해결:

가능하면 Interface View는 안정적인 의미 모델 중심으로 유지하고, Projection/Consumption 성격의 View와 Metadata Extension에서 UI 표시 요구를 처리한다.

## 11. Interface View와 Projection View 관점의 배치 기준

이 Section의 M02에서 Interface View와 Projection View의 구분을 학습했다. Metadata Extension은 이 구분과 밀접하게 연결된다.

### 11.1 Interface View

Interface View는 재사용 가능한 핵심 데이터 모델이다.

예시:

```text
ZI_JHY_Flight
```

권장 관점:

| 항목 | 배치 판단 |
|---|---|
| Key, Field, Association | Interface View 본문 |
| Semantics Annotation | 필요한 경우 본문 |
| UI LineItem | 보통 지양 |
| SelectionField | 보통 소비 계층으로 이동 |
| Facet | 보통 소비 계층으로 이동 |

### 11.2 Projection View

Projection View는 소비 목적에 맞게 노출 형태를 조정한다.

예시:

```text
ZC_JHY_Flight
```

권장 관점:

| 항목 | 배치 판단 |
|---|---|
| 노출 필드 선택 | Projection View 본문 |
| Alias 조정 | Projection View 본문 |
| UI Annotation | Metadata Extension으로 분리 가능 |
| 화면 표시 순서 | Metadata Extension |
| 필터 필드 | Metadata Extension |

### 11.3 초급자 원칙

초급자는 다음 원칙을 따르면 된다.

```text
ZI_*는 재사용 가능한 데이터 의미 모델에 집중한다.
ZC_*는 소비 계층에 집중한다.
UI Annotation은 가능하면 ZC_*의 Metadata Extension에 둔다.
```

## 12. 실무 설계 기준

### 12.1 Metadata Extension을 사용하는 것이 좋은 경우

| 상황 | 이유 |
|---|---|
| UI Annotation이 많아 View 본문이 길어질 때 | 가독성 향상 |
| 데이터 모델과 화면 표시 요구를 분리하고 싶을 때 | 유지보수성 향상 |
| Projection View를 Fiori Elements 소비에 사용하려 할 때 | UI 메타데이터 관리 용이 |
| 같은 데이터 모델에 소비 목적별 Annotation을 달리하고 싶을 때 | 계층 분리 가능 |
| 고객 확장 계층 Annotation을 별도로 관리하고 싶을 때 | 확장 관리 용이 |

### 12.2 Metadata Extension을 남발하면 안 되는 경우

| 상황 | 문제 |
|---|---|
| Annotation이 1~2개뿐인 매우 단순 View | 오히려 파일 수 증가 |
| 데이터 의미 Annotation까지 무조건 분리 | 모델 이해가 어려워질 수 있음 |
| 팀 기준 없이 객체명만 늘어남 | Repository 관리 부담 |
| 어떤 Annotation이 어디에 있는지 정리되지 않음 | 디버깅과 유지보수 어려움 |

Metadata Extension은 분리의 수단이지 목적이 아니다.  
팀이 합의한 기준 없이 무조건 분리하면 오히려 학습자와 실무자 모두 혼란스러워진다.

## 13. 미니 실습

### 13.1 실습 목표

`ZC_JHY_Flight` Projection View에 대해 Metadata Extension을 생성하고, 리스트 표시용 UI Annotation을 작성한다.

### 13.2 선행 조건

다음 객체가 존재한다고 가정한다.

```text
ZI_JHY_Flight
ZC_JHY_Flight
```

`ZC_JHY_Flight`에는 다음 Annotation이 있어야 한다.

```abap
@Metadata.allowExtensions: true
```

### 13.3 실습 단계

```text
1. ADT에서 ZC_JHY_Flight 열기
2. @Metadata.allowExtensions: true 존재 여부 확인
3. Package에서 Metadata Extension 생성
4. 객체명 ZC_JHY_FLIGHT_MDE 입력
5. 대상 Entity를 ZC_JHY_Flight로 지정
6. @Metadata.layer: #CUSTOMER 확인
7. CarrierId, ConnectionId, FlightDate, Price, CurrencyCode에 UI Annotation 작성
8. Activate
9. Problems View 확인
10. 가능하면 Fiori Elements Preview 또는 메타데이터 확인
```

### 13.4 실습 예시 코드

```abap
@Metadata.layer: #CUSTOMER
annotate entity ZC_JHY_Flight with
{
  @UI.lineItem: [{ position: 10, label: 'Carrier' }]
  @UI.selectionField: [{ position: 10 }]
  CarrierId;

  @UI.lineItem: [{ position: 20, label: 'Connection' }]
  ConnectionId;

  @UI.lineItem: [{ position: 30, label: 'Flight Date' }]
  @UI.selectionField: [{ position: 20 }]
  FlightDate;

  @UI.lineItem: [{ position: 40, label: 'Price' }]
  Price;

  @UI.lineItem: [{ position: 50, label: 'Currency' }]
  CurrencyCode;
}
```

> [추정] 실습 시스템에서 `SCARR`, `SPFLI`, `SFLIGHT` 기반 View를 사용한다면 필드명은 위 예시와 다를 수 있다. Metadata Extension의 Element 이름은 반드시 대상 View Entity의 Element 이름과 일치해야 한다.

## 15. Metadata Extension과 DCL의 차이

다음 모듈에서 DCL을 다루므로, 여기서는 간단히 차이만 정리한다.

| 구분 | Metadata Extension | DCL / Access Control |
|---|---|---|
| 목적 | Annotation 보강, 특히 UI 표시 메타데이터 분리 | 데이터 접근 권한 제어 |
| 객체 성격 | Metadata 보조 객체 | 권한 제어 객체 |
| 대표 키워드 | `@Metadata.layer`, `annotate entity` | `define role`, `grant select on` |
| 결과 영향 | 화면 표시, 메타데이터 소비 | 조회 가능한 데이터 범위 |
| 학습 위치 | 현재 모듈 | 다음 모듈 |

초급자는 다음 문장으로 구분하면 된다.

```text
Metadata Extension은 어떻게 보일지를 보강한다.
DCL은 누가 어떤 데이터를 볼 수 있는지를 제한한다.
```

## 16. 자가 점검 문제

### Q1. Metadata Extension의 주된 목적은 무엇인가?

A. 테이블 데이터를 직접 저장하기 위해 사용한다.  
B. CDS Entity의 Annotation을 별도 객체로 분리해 관리하기 위해 사용한다.  
C. ABAP 프로그램의 Exception을 처리하기 위해 사용한다.  
D. 사용자 권한을 직접 부여하기 위해 사용한다.

정답: B

### Q2. Metadata Extension을 허용하기 위해 대상 View에 필요한 대표 Annotation은?

A. `@AbapCatalog.sqlViewName`  
B. `@Metadata.allowExtensions: true`  
C. `@ObjectModel.transactionalProcessingEnabled`  
D. `@ClientHandling.algorithm`

정답: B

### Q3. UI 표시 순서를 제어하는 데 자주 사용되는 Annotation은?

A. `@UI.lineItem`  
B. `@AccessControl.authorizationCheck`  
C. `@Semantics.amount.currencyCode`  
D. `@ObjectModel.readOnly`

정답: A

### Q4. Metadata Extension과 DCL의 차이를 설명하시오.

모범 답안:  
Metadata Extension은 CDS Entity의 Annotation을 보강하여 UI 표시나 소비 메타데이터를 관리하는 객체이다. DCL은 CDS Entity에 대한 데이터 접근 권한을 제어하는 객체이다. 즉 Metadata Extension은 표시와 메타데이터, DCL은 권한과 접근 범위에 초점이 있다.

## 18. 핵심 요약

```text
Metadata Extension은 CDS Annotation을 별도 객체로 분리하는 기능이다.
대상 View에는 일반적으로 @Metadata.allowExtensions: true가 필요하다.
Metadata Extension에는 @Metadata.layer를 지정한다.
UI Annotation은 Projection/Consumption View의 Metadata Extension에 두는 방식이 실무적으로 유용하다.
Interface View는 재사용 가능한 데이터 의미 모델 중심으로 유지하는 것이 좋다.
Metadata Extension은 표시와 메타데이터 보강이고, DCL은 권한 제어이다.
```
