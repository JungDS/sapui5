이전 모듈에서 학습한 `Foreign Key`, `Value Table`, `Elementary Search Help`, `Collective Search Help`는 모두 사용자가 값을 입력할 때 **어떤 후보값을 보여주고, 어떤 값이 의미적으로 맞는지 안내하는 기반**이었다. 이번 모듈에서는 그 DDIC 기반 정보가 ABAP Report의 Selection Screen 입력 필드인 `PARAMETERS`와 어떻게 연결되는지를 다룬다.

```text
Data Element나 Table Field에 연결된 Search Help가 있으면 F4 Help가 자연스럽게 이어진다.
따라서 F4 Help는 가능하면 프로그램 코드보다 DDIC에서 먼저 설계한다.
```

## 3. PARAMETERS 기본 복습

`PARAMETERS`는 Classic ABAP Report에서 Selection Screen의 단일 입력 필드를 선언하는 구문이다.

가장 단순한 형태는 다음과 같다.

```abap
REPORT zjhy_param_basic.

PARAMETERS p_name TYPE c LENGTH 20.

START-OF-SELECTION.
  WRITE: / '입력값:', p_name.
```

이 예제에서 `P_NAME`은 Selection Screen에 표시되는 단일 입력 필드이다. 사용자가 값을 입력하고 실행하면 프로그램은 그 값을 출력한다.

하지만 이 방식은 DDIC와 연결되어 있지 않다.

```abap
PARAMETERS p_name TYPE c LENGTH 20.
```

위와 같이 Built-in Type을 직접 사용하면 프로그램은 입력 필드의 기술적 길이는 알지만, 이 값이 어떤 업무 의미를 가지는지는 알기 어렵다. 또한 DDIC 기반 Field Label, Search Help, Foreign Key 같은 정보도 자연스럽게 활용하기 어렵다.

## 4. DDIC 타입을 사용하는 PARAMETERS

실무적으로 더 좋은 방식은 DDIC 객체를 타입으로 사용하는 것이다.

예를 들어 항공사 ID를 입력받는 필드를 만든다고 하자.

```abap
REPORT zjhy_param_ddic_01.

PARAMETERS p_carrid TYPE s_carr_id.

START-OF-SELECTION.
  WRITE: / 'Carrier ID:', p_carrid.
```

여기서 `S_CARR_ID`는 SAP 교육용 항공 모델에서 자주 사용되는 항공사 ID 관련 Data Element이다. 시스템에 따라 표준 교육 데이터가 다를 수 있으므로 실제 실습에서는 사용 가능한 Data Element 또는 직접 만든 `ZDE_*` Data Element를 사용한다.

DDIC 타입을 사용하면 다음 이점이 있다.

| 이점 | 설명 |
|---|---|
| 타입 일관성 | 같은 Data Element를 사용하는 다른 필드와 기술 속성을 맞출 수 있다. |
| 의미 일관성 | 항공사 ID, 고객 ID, 자재 번호 같은 업무 의미를 명확히 유지할 수 있다. |
| Field Label 활용 | Selection Screen의 텍스트 관리와 연결할 수 있다. |
| Search Help 연결 | Data Element 또는 Table Field에 연결된 Search Help가 F4 Help로 이어질 수 있다. |
| 유지보수성 | DDIC에서 타입이나 Help를 조정하면 관련 프로그램의 의미 기반도 함께 관리하기 쉽다. |

초급자는 다음 차이를 반드시 구분해야 한다.

```abap
" 기술 타입만 직접 선언
PARAMETERS p_carrid TYPE c LENGTH 3.

" DDIC 의미를 가진 타입 선언
PARAMETERS p_carrid TYPE s_carr_id.
```

두 입력 필드가 화면상으로 비슷해 보일 수 있지만, 유지보수성과 DDIC 연결성은 다르다.

## 5. F4 Help란 무엇인가?

F4 Help는 SAP 화면에서 입력 가능한 후보값을 사용자가 선택할 수 있도록 제공하는 입력 도움말이다.

사용자는 입력 필드에 커서를 두고 `F4` 키를 누르거나, 화면의 Value Help 아이콘을 클릭할 수 있다. 그러면 시스템은 해당 필드에 연결된 후보값 목록을 표시한다.

예를 들어 항공사 ID 입력 필드에 F4 Help가 연결되어 있다면 다음과 같은 후보가 표시될 수 있다.

| Carrier ID | Carrier Name |
|---|---|
| AA | American Airlines |
| LH | Lufthansa |
| SQ | Singapore Airlines |

초급자 입장에서 F4 Help는 “입력 가능한 값을 고르는 팝업”으로 보일 수 있다. 하지만 실무적으로는 단순 팝업이 아니라 다음 의미를 가진다.

| 관점 | 의미 |
|---|---|
| 사용자 편의 | 코드값을 외우지 않아도 선택 가능 |
| 입력 오류 감소 | 존재하지 않는 값 입력 가능성을 낮춤 |
| 업무 의미 제공 | 코드와 설명을 함께 보여줄 수 있음 |
| 표준화 | 여러 프로그램에서 같은 입력 도움말 재사용 가능 |
| 유지보수 | 후보값 조회 로직을 DDIC에 집중시킬 수 있음 |

## 6. PARAMETERS와 F4 Help 연결 방식 개요

`PARAMETERS`에 F4 Help가 연결되는 대표 방식은 다음과 같이 정리할 수 있다.

| 방식 | 예시 | 특징 |
|---|---|---|
| Data Element 기반 | `PARAMETERS p_carrid TYPE zde_jhy_carrid.` | Data Element에 Search Help가 연결되어 있으면 자연스럽게 활용 가능 |
| Table Field 기반 | `PARAMETERS p_carrid TYPE zt_jhy_flight-carrid.` | 해당 Table Field의 DDIC 속성, Foreign Key, Search Help 영향을 받을 수 있음 |
| 명시적 Search Help 지정 | `PARAMETERS p_carrid MATCHCODE OBJECT zsh_jhy_carrid.` | 프로그램 선언에서 특정 Search Help를 직접 지정 |
| 프로그램 이벤트 기반 | `AT SELECTION-SCREEN ON VALUE-REQUEST` | 코드로 직접 F4 처리를 구현. 이번 모듈의 중심은 아님 |

이번 모듈의 권장 학습 순서는 다음이다.

```text
1. Data Element에 Search Help를 연결한다.
2. PARAMETERS에서 해당 Data Element를 TYPE으로 사용한다.
3. Selection Screen에서 F4 Help가 표시되는지 확인한다.
4. F4가 표시되지 않으면 DDIC 설정과 활성화 상태를 점검한다.
5. 필요한 경우에만 MATCHCODE OBJECT 또는 이벤트 기반 처리를 검토한다.
```

## 7. Data Element 기반 자동 F4 Help

### 7.1 구조

Data Element 기반 F4 연결은 가장 기본적이고 재사용성이 좋은 방식이다.

```text
Search Help
  ↑
Data Element
  ↑
PARAMETERS
```

예를 들어 다음 객체를 만든다고 가정한다.

| 객체 | 예시 이름 | 역할 |
|---|---|---|
| Check Table 또는 Selection Method | `ZT_JHY_CARR` | 항공사 코드와 이름을 저장 |
| Elementary Search Help | `ZSH_JHY_CARR` | 항공사 후보값 제공 |
| Data Element | `ZDE_JHY_CARRID` | 항공사 ID 의미 정의 및 Search Help 연결 |
| Report Parameter | `P_CARRID` | 사용자가 항공사 ID를 입력 |

이때 ABAP 코드는 매우 단순해진다.

```abap
REPORT zjhy_param_f4_de.

PARAMETERS p_carrid TYPE zde_jhy_carrid.

START-OF-SELECTION.
  WRITE: / '선택한 항공사:', p_carrid.
```

프로그램에는 F4 팝업 로직이 없다. F4 Help의 중심은 DDIC에 있다.

### 7.2 장점

Data Element 기반 연결의 장점은 다음과 같다.

| 장점 | 설명 |
|---|---|
| 재사용성 | 같은 Data Element를 사용하는 여러 화면과 프로그램에서 동일 Help를 활용 가능 |
| 중앙 관리 | Search Help 변경을 DDIC에서 관리할 수 있음 |
| 코드 단순화 | 프로그램에 F4 처리 로직을 반복 작성하지 않아도 됨 |
| 표준 흐름 | SAP Dictionary 중심 설계와 잘 맞음 |
| 교육 효과 | DDIC와 Selection Screen의 연결을 명확히 보여줌 |

## 8. Table Field 기반 F4 Help

Table Field를 타입으로 참조하는 방식도 실무에서 자주 보인다.

```abap
REPORT zjhy_param_f4_field.

PARAMETERS p_carrid TYPE zt_jhy_flight-carrid.

START-OF-SELECTION.
  WRITE: / '선택한 항공사:', p_carrid.
```

이 선언은 `ZT_JHY_FLIGHT` 테이블의 `CARRID` 필드와 같은 타입을 사용한다는 의미이다.

Table Field에 다음 DDIC 정보가 잘 연결되어 있으면 Selection Screen에서도 관련 입력 도움말을 기대할 수 있다.

| DDIC 요소 | 역할 |
|---|---|
| Field의 Data Element | 업무 의미와 라벨 기반 제공 |
| Field의 Search Help | 명시적 Search Help 연결 가능 |
| Foreign Key | Check Table 기반 후보값과 검증 근거 제공 가능 |
| Domain | 기술 타입과 Value Range 제공 |

다만 초급자는 다음 점을 주의해야 한다.

> Table Field 기반 선언은 편리하지만, 그 필드에 어떤 DDIC 정보가 연결되어 있는지 이해하지 못하면 F4 동작 원인을 추적하기 어렵다.

따라서 교육 초기에는 Data Element 기반과 Table Field 기반을 모두 보여주되, 먼저 Data Element 기반 구조를 이해시키는 것이 좋다.

## 9. MATCHCODE OBJECT를 사용한 명시적 연결

`PARAMETERS`에는 `MATCHCODE OBJECT`를 사용해 특정 Search Help를 직접 지정할 수 있다.

예시는 다음과 같다.

```abap
REPORT zjhy_param_matchcode.

PARAMETERS p_carrid TYPE zde_jhy_carrid
                    MATCHCODE OBJECT zsh_jhy_carr.

START-OF-SELECTION.
  WRITE: / '선택한 항공사:', p_carrid.
```

이 방식은 프로그램 코드에서 Search Help를 명시한다.

### 9.1 언제 유용한가?

| 상황 | 설명 |
|---|---|
| 특정 프로그램에서만 다른 Help가 필요 | 공통 Data Element의 Search Help와 다른 후보값을 보여줘야 할 때 |
| 임시 실습에서 빠르게 연결 확인 | DDIC 객체 연결 전체를 구성하기 전 간단히 검증할 때 |
| 동일 Data Element라도 문맥별 Help가 다름 | 업무 화면별로 후보값 범위가 다를 때 |

### 9.2 주의점

`MATCHCODE OBJECT`를 남발하면 같은 Data Element를 사용하더라도 프로그램마다 다른 F4 Help가 붙어 일관성이 깨질 수 있다.

따라서 기본 원칙은 다음과 같다.

```text
공통 의미의 입력 도움말은 DDIC에서 먼저 설계한다.
프로그램별 예외가 명확할 때만 MATCHCODE OBJECT를 검토한다.
```

## 10. 프로그램 이벤트 기반 F4와의 차이

ABAP Report에서는 다음 이벤트를 사용해 F4 Help를 직접 구현할 수 있다.

```abap
AT SELECTION-SCREEN ON VALUE-REQUEST FOR p_carrid.
```

이 이벤트 안에서 Function Module이나 Class를 사용해 후보값 목록을 직접 구성할 수 있다. 하지만 이번 모듈에서는 이 방식을 중심으로 다루지 않는다.

구분은 다음과 같다.

| 구분 | DDIC 기반 F4 | 프로그램 이벤트 기반 F4 |
|---|---|---|
| 구현 위치 | Data Element, Search Help, Table Field | ABAP Report 코드 |
| 재사용성 | 높음 | 프로그램별 구현 성격이 강함 |
| 유지보수 | DDIC 중심 | 코드 중심 |
| 초급 학습 적합성 | 높음 | 중급 이후 적합 |
| 사용 상황 | 표준 후보값, 공통 입력 도움말 | 복잡한 동적 후보값, 화면 문맥 기반 후보값 |

초급자에게는 다음 원칙을 먼저 가르치는 것이 좋다.

```text
F4 Help가 필요하면 먼저 DDIC에서 해결 가능한지 확인한다.
DDIC로 충분하지 않을 때 프로그램 이벤트 기반 F4를 검토한다.
```

## 11. 실습 시나리오

### 11.1 업무 가정

교육용 항공사 선택 프로그램을 만든다. 사용자는 Selection Screen에서 항공사 ID를 입력한다. 이때 직접 코드를 외워 입력하는 것이 아니라 F4 Help를 통해 항공사 목록에서 선택할 수 있어야 한다.

업무 요구사항은 다음과 같다.

```text
사용자는 항공사 ID를 입력한다.
항공사 ID 입력 필드에서 F4 Help를 사용할 수 있어야 한다.
F4 Help에는 항공사 ID와 항공사명이 표시되어야 한다.
선택한 항공사 ID는 프로그램 실행 시 출력된다.
가능하면 F4 Help 로직은 ABAP 코드에 직접 작성하지 않는다.
```

### 11.2 실습 객체 예시

| 객체 유형 | 예시 이름 | 설명 |
|---|---|---|
| Check Table | `ZT_JHY_CARR` | 항공사 마스터 역할 |
| Search Help | `ZSH_JHY_CARR` | 항공사 F4 Help |
| Data Element | `ZDE_JHY_CARRID` | 항공사 ID 의미 정의 |
| Report Program | `ZJHY_PARAM_F4_CARR` | Selection Screen 테스트 프로그램 |

[추정] 실제 실습 시스템에 이미 `SCARR`, `SPFLI`, `SFLIGHT` 같은 SAP 교육용 표준 테이블이 존재한다면 Z 테이블 대신 표준 교육 테이블을 조회 대상으로 사용할 수 있다. 다만 고객 개발 실습에서는 표준 테이블을 수정하지 않고, 조회 또는 참조 용도로만 사용한다.

## 12. DDIC 준비 절차

### 12.1 Check Table 또는 Selection Method 확인

Elementary Search Help는 후보값을 가져올 Selection Method가 필요하다. 예를 들어 `ZT_JHY_CARR` 테이블이 다음 필드를 가진다고 가정한다.

| Field | Key | Data Element | 설명 |
|---|---:|---|---|
| MANDT | X | MANDT | Client |
| CARRID | X | ZDE_JHY_CARRID | 항공사 ID |
| CARRNAME |  | ZDE_JHY_CARRNAME | 항공사명 |

### 12.2 Elementary Search Help 생성 확인

`ZSH_JHY_CARR`는 다음처럼 구성할 수 있다.

| 항목 | 값 |
|---|---|
| Search Help | ZSH_JHY_CARR |
| Selection Method | ZT_JHY_CARR |
| Dialog Type | Display values immediately 또는 시스템 기본값 |

Search Help Parameter 예시는 다음과 같다.

| Parameter | Import | Export | LPos | SPos | 설명 |
|---|---:|---:|---:|---:|---|
| CARRID | X | X | 1 | 1 | 항공사 ID |
| CARRNAME |  |  | 2 | 2 | 항공사명 |

여기서 `CARRID`가 Export Parameter여야 사용자가 선택한 값이 `PARAMETERS p_carrid`로 돌아올 수 있다.

### 12.3 Data Element에 Search Help 연결

`ZDE_JHY_CARRID` Data Element에 `ZSH_JHY_CARR` Search Help를 연결한다.

```text

→ Data Type
```

## 13. ABAP Report 실습

### 13.1 Data Element 기반 F4 테스트

가장 권장되는 기본 실습 코드는 다음이다.

```abap
REPORT zjhy_param_f4_carr.

PARAMETERS p_carrid TYPE zde_jhy_carrid.

START-OF-SELECTION.
  WRITE: / 'Carrier ID:', p_carrid.
```

실행 절차는 다음과 같다.

```text
1. SE38 또는 ADT에서 프로그램 생성
2. 위 코드 입력
3. Activate
4. Execute
5. Selection Screen에서 P_CARRID 필드에 커서 위치
6. F4 키 입력
7. 항공사 목록 표시 여부 확인
8. 항공사 선택
9. 선택값이 P_CARRID 필드에 반영되는지 확인
10. Execute 후 WRITE 출력 확인
```

### 13.2 Table Field 기반 F4 테스트

다음 예제는 Table Field 참조 방식이다.

```abap
REPORT zjhy_param_f4_field.

PARAMETERS p_carrid TYPE zt_jhy_carr-carrid.

START-OF-SELECTION.
  WRITE: / 'Carrier ID:', p_carrid.
```

이 방식은 `ZT_JHY_CARR-CARRID` 필드에 연결된 DDIC 정보를 활용한다. 해당 필드의 Data Element와 Search Help, Foreign Key 설정을 함께 점검해야 한다.

### 13.3 명시적 Search Help 연결 테스트

다음은 `MATCHCODE OBJECT`를 사용한 예제이다.

```abap
REPORT zjhy_param_f4_match.

PARAMETERS p_carrid TYPE zde_jhy_carrid
                    MATCHCODE OBJECT zsh_jhy_carr.

START-OF-SELECTION.
  WRITE: / 'Carrier ID:', p_carrid.
```

이 예제는 Search Help 연결 여부를 코드 수준에서 명확히 확인할 수 있다. 하지만 공통 F4 Help를 매 프로그램에 반복 지정하는 방식은 유지보수 측면에서 바람직하지 않을 수 있다.

## 14. 정상 흐름과 오류 흐름

### 14.1 정상 흐름

정상적인 DDIC 기반 F4 연결 흐름은 다음과 같다.

```text
1. 후보값을 제공할 테이블 또는 뷰를 준비한다.
2. Elementary Search Help를 생성한다.
3. Search Help Parameter의 Import/Export를 올바르게 지정한다.
4. Data Element에 Search Help를 연결한다.
5. Data Element를 Activate한다.
6. PARAMETERS에서 해당 Data Element를 TYPE으로 사용한다.
7. 프로그램을 Activate하고 실행한다.
8. Selection Screen에서 F4 Help를 확인한다.
```

### 14.2 오류 흐름 1: F4 아이콘이 보이지 않음

#### 가능한 원인

| 원인 | 설명 |
|---|---|
| Built-in Type으로 선언 | `TYPE c LENGTH 3`처럼 DDIC 연결이 없을 수 있다. |
| Data Element에 Search Help 없음 | DDIC에서 Search Help가 연결되지 않았다. |
| Table Field에 Foreign Key 또는 Help 연결 없음 | 참조 필드에 입력 도움말 근거가 부족하다. |
| 객체 미활성화 | Search Help, Data Element, Table이 Active 상태가 아니다. |
| 프로그램 미활성화 | 최신 DDIC 변경 후 Report가 갱신되지 않았을 수 있다. |

#### 해결 순서

```text
1. PARAMETERS 선언이 DDIC 타입을 참조하는지 확인한다.
2. Data Element에 Search Help가 연결되어 있는지 확인한다.
3. Search Help가 Active 상태인지 확인한다.
4. Search Help Parameter의 Export 설정을 확인한다.
5. Report를 다시 Activate한다.
6. SAP GUI 화면을 새로 실행하여 확인한다.
```

### 14.3 오류 흐름 2: F4 팝업은 뜨지만 선택값이 필드로 돌아오지 않음

#### 가능한 원인

Search Help Parameter에서 Export가 제대로 설정되지 않았을 가능성이 있다.

#### 확인 포인트

| 항목 | 확인 내용 |
|---|---|
| Export Parameter | 선택값으로 돌려보낼 필드에 Export가 체크되어 있는가? |
| Parameter 이름 | Data Element 또는 필드와 매핑 가능한 이름인가? |
| Selection Method | 후보값 테이블에 해당 필드가 존재하는가? |
| Search Help 활성화 | 변경 후 Activate했는가? |

### 14.4 오류 흐름 3: 후보값 목록이 비어 있음

#### 가능한 원인

| 원인 | 설명 |
|---|---|
| Selection Method 테이블에 데이터 없음 | 후보값을 제공할 테이블에 데이터가 없다. |
| Client 불일치 | 현재 Client에 데이터가 없을 수 있다. |
| Search Help Parameter 조건 문제 | Import Parameter나 조건에 의해 값이 제한되었을 수 있다. |
| 권한 문제 | 조회 권한이 부족할 수 있다. |

#### 해결

```text
1. SE16N에서 Selection Method 테이블을 직접 조회한다.
2. 현재 Client의 데이터 존재 여부를 확인한다.
3. Search Help Parameter의 Import 조건을 임시로 단순화한다.
4. 필요한 경우 테스트 데이터를 입력한다.
```

### 14.5 오류 흐름 4: 엉뚱한 후보값이 표시됨

#### 가능한 원인

Data Element에 의도하지 않은 Search Help가 연결되어 있거나, `MATCHCODE OBJECT`로 다른 Search Help가 지정되어 있을 수 있다.

#### 해결

```text
1. PARAMETERS 선언에 MATCHCODE OBJECT가 있는지 확인한다.
2. Data Element의 Search Help를 확인한다.
3. Table Field의 Search Help 또는 Foreign Key 설정을 확인한다.
4. Collective Search Help라면 포함된 Elementary Search Help 목록을 확인한다.
```

## 15. DDIC F4 Help와 입력 검증의 차이

F4 Help와 입력 검증은 비슷해 보이지만 같은 개념이 아니다.

| 구분 | F4 Help | 입력 검증 |
|---|---|---|
| 목적 | 사용자가 값을 선택하도록 도움 | 입력값이 허용되는지 판단 |
| 시점 | 사용자가 F4를 누를 때 | 입력 후 실행 또는 화면 처리 시점 |
| 구현 기반 | Search Help, Foreign Key, Value Help | Foreign Key, Check Logic, Program Validation |
| 사용자 경험 | 후보값 목록 표시 | 오류 메시지 또는 진행 허용/차단 |

중요한 점은 다음이다.

```text
F4 Help가 있다고 해서 모든 잘못된 입력이 자동으로 막히는 것은 아니다.
입력 후보 제공과 입력값 검증은 역할이 다르다.
```

예를 들어 사용자가 F4 Help에서 값을 선택하지 않고 직접 값을 입력할 수도 있다. 이때 실제 검증은 DDIC Foreign Key, Selection Screen 이벤트, 프로그램 로직, 비즈니스 로직 등과 함께 고려해야 한다.

이 주제는 다음 모듈 `THEORY-04-M06 — DDIC 검증과 프로그램 검증의 역할 분리`에서 이어진다.

## 16. 실무 적용 기준

### 16.1 우선순위 원칙

실무에서 Selection Screen 입력 필드에 F4 Help가 필요할 때는 다음 순서로 검토한다.

```text
1. 표준 Data Element 또는 Table Field에 이미 Search Help가 있는가?
2. 기존 DDIC Search Help를 재사용할 수 있는가?
3. 공통 업무 의미라면 Data Element에 Search Help를 연결할 수 있는가?
4. 특정 프로그램만 다른 후보값이 필요한가?
5. 그래도 부족하면 프로그램 이벤트 기반 F4가 필요한가?
```

### 16.2 좋은 설계

좋은 설계는 다음과 같다.

```abap
PARAMETERS p_carrid TYPE zde_jhy_carrid.
```

그리고 `ZDE_JHY_CARRID`에 적절한 Search Help가 연결되어 있다.

장점은 다음이다.

| 장점 | 설명 |
|---|---|
| 코드가 단순하다 | F4 로직이 프로그램에 반복되지 않는다. |
| 의미가 명확하다 | Parameter의 업무 의미가 Data Element에 있다. |
| 재사용이 쉽다 | 같은 Data Element를 쓰는 다른 곳에서도 활용 가능하다. |
| 유지보수가 쉽다 | 후보값 구조 변경 시 DDIC 중심으로 조정 가능하다. |

### 16.3 피해야 할 설계

다음과 같은 설계는 피하는 것이 좋다.

```abap
PARAMETERS p_carrid TYPE c LENGTH 3.
```

그리고 프로그램마다 별도 F4 로직을 직접 작성한다.

문제는 다음과 같다.

| 문제 | 설명 |
|---|---|
| 의미 약화 | 이 값이 항공사 ID인지 알기 어렵다. |
| 중복 로직 | 프로그램마다 후보값 조회 로직이 반복된다. |
| 유지보수 부담 | 후보값 구조 변경 시 여러 프로그램을 수정해야 한다. |
| 표준성 저하 | DDIC 중심 설계 장점을 활용하지 못한다. |

## 18. 강사용 설명 포인트

### 18.1 “코드 없이 F4가 뜨는 이유”를 보여준다

초급자는 F4 팝업이 프로그램 코드 안에 있을 것이라고 생각하기 쉽다. 이번 모듈에서는 일부러 Report 코드를 매우 짧게 유지한다.

```abap
PARAMETERS p_carrid TYPE zde_jhy_carrid.
```

그리고 F4 Help가 뜨는 것을 보여주면, 학습자는 DDIC가 화면 동작에 영향을 준다는 점을 체감할 수 있다.

### 18.2 Data Element의 중요성을 다시 연결한다

Data Element는 단순 Field Label 객체가 아니다. Selection Screen의 입력 필드에서도 업무 의미와 Help 연결을 제공할 수 있다.

### 18.3 Search Help Parameter의 Export를 강조한다

F4 팝업이 보이는데 값이 돌아오지 않는 오류는 초급자에게 좋은 학습 사례이다. 원인은 대부분 Export Parameter 설정과 관련된다.

### 18.4 다음 모듈과 연결한다

이번 모듈에서는 F4 Help 제공을 다루었다. 다음 모듈에서는 사용자가 직접 입력한 값이 실제로 유효한지 검증하는 역할 분리를 다룬다.

```text
THEORY-04-M05: 입력 후보값을 보여준다.
THEORY-04-M06: 입력값이 유효한지 검증한다.
```

## 19. 평가 문제

### 19.1 객관식

#### Q1. `PARAMETERS p_carrid TYPE zde_jhy_carrid.`의 장점으로 가장 적절한 것은?

A. 모든 F4 Help 로직이 자동으로 ABAP 코드에 생성된다.  
B. DDIC Data Element의 타입과 의미, Search Help 연결을 활용할 수 있다.  
C. Selection Screen이 생성되지 않는다.  
D. 프로그램이 데이터베이스 테이블을 자동 생성한다.

정답: B

#### Q2. F4 팝업은 뜨지만 선택값이 입력 필드로 돌아오지 않을 때 우선 확인할 항목은?

A. Report 이름 길이  
B. Search Help Parameter의 Export 설정  
C. WRITE 문장의 위치  
D. 주석 처리 여부

정답: B

#### Q3. DDIC 기반 F4 Help와 프로그램 이벤트 기반 F4의 차이로 올바른 것은?

A. DDIC 기반 F4는 Search Help와 Data Element 중심이고, 이벤트 기반 F4는 ABAP 코드 중심이다.  
B. 둘은 완전히 같은 기능이며 차이가 없다.  
C. 이벤트 기반 F4는 SE11에서만 작성한다.  
D. DDIC 기반 F4는 Selection Screen에서 사용할 수 없다.

정답: A

### 19.2 단답형

#### Q1. `MATCHCODE OBJECT`는 어떤 목적으로 사용하는가?

모범 답안:  
`PARAMETERS` 선언에서 특정 Search Help를 명시적으로 지정하기 위해 사용한다. 공통 Data Element의 기본 Search Help와 다른 Help를 특정 프로그램에서 사용해야 할 때 활용할 수 있다.

#### Q2. F4 Help와 입력 검증의 차이를 설명하시오.

모범 답안:  
F4 Help는 사용자가 입력 가능한 후보값을 선택하도록 돕는 기능이고, 입력 검증은 사용자가 입력한 값이 실제로 허용되는지 판단하는 기능이다. F4 Help가 있다고 해서 모든 잘못된 직접 입력이 자동으로 차단되는 것은 아니다.

#### Q3. F4 Help가 보이지 않을 때 확인할 DDIC 요소를 세 가지 쓰시오.

모범 답안:  
Data Element에 Search Help가 연결되어 있는지, Search Help가 Active 상태인지, Search Help Parameter의 Import/Export 설정이 올바른지, Table Field의 Foreign Key 또는 Search Help가 설정되어 있는지 확인한다.

## 20. 실습 과제

### 20.1 기본 과제

다음 조건을 만족하는 Report를 작성한다.

```text
Program: ZJHY_PARAM_F4_CARR
Parameter: P_CARRID
Type: ZDE_JHY_CARRID
기능: F4 Help로 항공사 ID를 선택하고 실행 시 선택값을 출력한다.
```

예제 코드:

```abap
REPORT zjhy_param_f4_carr.

PARAMETERS p_carrid TYPE zde_jhy_carrid.

START-OF-SELECTION.
  WRITE: / 'Carrier ID:', p_carrid.
```

| 후보값 목록이 표시되는가? |  |

## 22. 핵심 요약

이번 모듈의 핵심은 다음이다.

```text
PARAMETERS는 Selection Screen 입력 필드를 만든다.
DDIC Data Element를 TYPE으로 사용하면 타입, 의미, 라벨, F4 Help 연결성을 얻을 수 있다.
Search Help는 가능하면 DDIC에 연결하여 재사용성을 높인다.
MATCHCODE OBJECT는 특정 프로그램에서 Search Help를 명시적으로 지정할 때 사용할 수 있다.
F4 Help는 입력 후보를 보여주는 기능이고, 입력 검증은 별도의 책임이다.
```

초급자가 반드시 가져가야 할 실무 감각은 다음이다.

```text
입력 필드에 F4 Help가 필요하다고 해서 바로 ABAP 코드부터 작성하지 않는다.
먼저 Data Element, Table Field, Foreign Key, Search Help 등 DDIC 기반으로 해결 가능한지 확인한다.
```
