## 3. 핵심 용어 정리

| 용어 | 초급자 설명 | 정의 위치 |
|---|---|---|
| Domain | 데이터의 기술적 속성과 값 범위의 기반 | SE11 Domain |
| Value Table | Domain에 연결해 둘 수 있는 대표 값 테이블 | Domain 속성 |

```text

Foreign Key → Table Field에 설정
```

이 차이를 이해하지 못하면 “Domain에 Value Table을 넣었으니 자동 검증이 되겠지”라고 오해하기 쉽다.

## 4. Value Table이란 무엇인가?

Value Table은 Domain에 지정할 수 있는 테이블 참조 정보이다.

예를 들어 항공사 코드 Domain이 있다고 하자.

```text
Domain: ZD_JHY_CARRID
Data Type: CHAR
Length: 3
Value Table: SCARR 또는 ZT_JHY_CARRIER
```

이 설정은 “이 Domain을 사용하는 필드의 값은 보통 항공사 마스터 테이블을 기준으로 삼을 수 있다”는 정보를 제공한다.

하지만 초급자가 반드시 주의해야 할 점이 있다.

```text
Value Table을 Domain에 지정했다고 해서
그 Domain을 사용하는 모든 필드에 자동으로 Foreign Key 검증이 완성되는 것은 아니다.
```

Value Table은 Foreign Key를 만들 때 시스템이 Check Table 후보를 제안하는 데 도움을 줄 수 있다. 그러나 실제 관계와 검증은 Table Field에 Foreign Key를 정의해야 명확해진다.

---

## 5. Foreign Key란 무엇인가?

Foreign Key는 특정 테이블 필드가 다른 테이블의 유효한 값 집합을 참조하도록 정의하는 DDIC 관계이다.

예를 들어 `ZT_JHY_FLIGHT-CARRID`가 항공사 코드를 저장한다고 하자. 이 필드에는 실제 존재하는 항공사 코드만 들어가야 한다.

```text
입력 테이블: ZT_JHY_FLIGHT
입력 필드:   CARRID
Check Table: ZT_JHY_CARRIER
Check Field: CARRID
```

이 관계를 Table Field에 정의하면 다음 의미가 된다.

```text
ZT_JHY_FLIGHT-CARRID에 입력되는 값은
ZT_JHY_CARRIER-CARRID에 존재하는 값이어야 한다.
```

이것이 Foreign Key 관계이다.

## 6. Value Table과 Foreign Key의 한 줄 차이

초급자는 다음 문장을 반드시 기억해야 한다.

```text
Value Table은 Domain이 알고 있는 대표 값 테이블이고,
Foreign Key는 특정 Table Field가 실제로 참조하는 관계이다.
```

표로 비교하면 다음과 같다.

| 구분 | Value Table | Foreign Key |
|---|---|---|
| 정의 위치 | Domain | Table Field |
| 목적 | 대표 값 테이블 제안 | 실제 관계와 검증 정의 |
| Check Table 역할 | 후보 또는 참조 정보 | 실제 Check Table로 사용 |
| 자동 검증 | 이것만으로는 충분하지 않음 | 관계 기반 검증에 사용 |
| 필드별 차등 적용 | 어려움 | 가능 |
| Cardinality 설정 | 없음 | 있음 |
| 관계 의미 | 약함 | 강함 |
| 실무 중요도 | 보조 정보 | 핵심 설계 요소 |

## 7. 왜 Value Table만으로 충분하지 않은가?

### 7.1 같은 Domain을 여러 필드가 사용할 수 있다

하나의 Domain은 여러 Data Element와 여러 Table Field에서 재사용될 수 있다.

예를 들어 `ZD_JHY_ORG_CODE`라는 Domain이 있다고 하자.

| 사용 필드 | 업무 의미 | 참조해야 할 테이블 |
|---|---|---|
| SALES_ORG | 영업조직 | TVKO 또는 ZT_SALES_ORG |
| PURCH_ORG | 구매조직 | T024E 또는 ZT_PURCH_ORG |
| PLANT | 플랜트 | T001W 또는 ZT_PLANT |

기술적으로 모두 `CHAR 4`일 수 있지만 업무 의미와 참조 테이블은 다를 수 있다.

따라서 Domain에 Value Table 하나를 넣는 것만으로 모든 필드의 관계를 정확히 표현하기 어렵다. 실제로 어떤 필드가 어떤 테이블을 참조하는지는 Table Field의 Foreign Key에서 정의해야 한다.

### 7.2 필드별 관계가 다를 수 있다

같은 항공사 코드처럼 보이는 필드라도 업무상 관계가 다를 수 있다.

| 필드 | 의미 | 관계 설계 |
|---|---|---|
| DEFAULT_CARRID | 기본 항공사 | 항공사 마스터 참조 가능 |
| PARTNER_CARRID | 제휴 항공사 | 제휴 항공사 테이블 참조 가능 |
| DISPLAY_CARRID | 출력용 코드 | 검증이 필요 없을 수 있음 |

이처럼 필드별 관계가 다르면 Value Table 하나로는 부족하다.

### 7.3 Foreign Key에는 Cardinality와 관계 의미가 있다

Foreign Key는 단순한 테이블명 연결이 아니다. 관계의 성격을 표현할 수 있다.

예를 들어 다음과 같이 설명할 수 있다.

```text
하나의 항공사 마스터는 여러 항공편 데이터를 가질 수 있다.
하나의 항공편 데이터는 하나의 항공사 코드를 참조한다.
```

이 관계는 Foreign Key 설정에서 Cardinality와 함께 이해한다. Value Table에는 이런 관계 의미가 없다.

## 8. 구조적 위치로 이해하기

DDIC 객체 계층 안에서 Value Table과 Foreign Key의 위치는 다르다.

```text
Domain
  ├─ Data Type
  ├─ Length
  ├─ Fixed Value
  └─ Value Table      ← Domain 수준의 참조 정보

Data Element
  └─ Domain 참조

Transparent Table
  └─ Field
      ├─ Data Element
      └─ Foreign Key  ← Field 수준의 실제 관계 정의
```

이 구조를 보면 다음이 명확해진다.

```text
Value Table은 Domain 쪽에 있다.
Foreign Key는 Table Field 쪽에 있다.
```

즉, Value Table과 Foreign Key는 서로 대체 관계가 아니라 위치와 역할이 다른 설정이다.

## 9. 표준 예제로 이해하기: 항공사와 항공편

SAP 교육 시스템에서는 전통적으로 항공 예제 테이블이 자주 사용된다.

| 테이블 | 의미 |
|---|---|
| SCARR | 항공사 마스터 |
| SPFLI | 항공 연결 정보 |
| SFLIGHT | 항공편 정보 |

예를 들어 `SPFLI-CARRID`는 항공사 코드를 저장한다. 이 값은 `SCARR-CARRID`에 존재하는 값이어야 자연스럽다.

관계는 다음과 같이 이해할 수 있다.

```text
SCARR-CARRID       = 항공사 마스터의 Key
SPFLI-CARRID       = 연결 정보가 참조하는 항공사 코드
SPFLI-CARRID → SCARR-CARRID
```

여기서 `SCARR`는 Check Table 역할을 할 수 있고, `SPFLI-CARRID`에는 Foreign Key 관계가 정의될 수 있다.

이때 Domain에 Value Table이 있더라도 초급자가 확인해야 할 것은 다음이다.

```text
실제 필드 SPFLI-CARRID에 Foreign Key가 설정되어 있는가?
Check Table이 SCARR로 되어 있는가?
Field Assignment가 올바른가?
```

## 11. Domain에 Value Table 설정하기

### 11.1 실습 목적

Domain `ZD_JHY_CARRID`에 Value Table을 설정해본다.

```text
Domain: ZD_JHY_CARRID
Value Table: ZT_JHY_CARRIER
```

이 설정은 이후 Foreign Key를 만들 때 Check Table 후보로 활용될 수 있다.

### 11.2 SE11 절차

SAP GUI 800 기준 흐름은 다음과 같다.

```text
1. SE11 실행
2. Domain 선택
3. ZD_JHY_CARRID 입력
4. Change 모드 진입
5. Definition 또는 Value Range 관련 영역 확인
6. Value Table에 ZT_JHY_CARRIER 입력
7. Save
8. Activate
```

화면 구성은 시스템 릴리스와 언어 설정에 따라 조금씩 다를 수 있다. 핵심은 Domain의 Value Table 속성에 대표 테이블을 입력하는 것이다.

### 11.3 여기서 끝내면 안 되는 이유

Value Table을 입력했다고 해서 `ZT_JHY_FLIGHT-CARRID`의 실제 관계가 자동 완성되었다고 판단하면 안 된다.

반드시 `ZT_JHY_FLIGHT` 테이블의 `CARRID` 필드에서 Foreign Key 관계를 별도로 확인하거나 생성해야 한다.

---

## 12. Table Field에 Foreign Key 설정하기

### 12.1 실습 목적

`ZT_JHY_FLIGHT-CARRID`가 `ZT_JHY_CARRIER-CARRID`를 참조하도록 Foreign Key를 정의한다.

```text
Foreign Key Field: ZT_JHY_FLIGHT-CARRID
Check Table:       ZT_JHY_CARRIER
Check Field:       CARRID
```

### 12.2 SE11 절차

```text
1. SE11 실행
2. Database Table 선택
3. ZT_JHY_FLIGHT 입력
4. Change 모드 진입
5. Fields 탭에서 CARRID 필드 선택
6. Foreign Key 버튼 또는 메뉴 실행
7. Check Table에 ZT_JHY_CARRIER 입력
8. Field Assignment 확인
9. Cardinality 확인
10. Save
11. Activate
```

### 12.3 Field Assignment 확인

Foreign Key 설정에서 가장 중요한 화면 중 하나가 Field Assignment이다.

예를 들어 다음과 같이 매핑되어야 한다.

| Foreign Key Table | Foreign Key Field | Check Table | Check Field |
|---|---|---|---|
| ZT_JHY_FLIGHT | MANDT | ZT_JHY_CARRIER | MANDT |
| ZT_JHY_FLIGHT | CARRID | ZT_JHY_CARRIER | CARRID |

Client-dependent 테이블에서는 `MANDT` 매핑도 함께 고려해야 한다.

초급자는 `CARRID`만 보고 끝내지 말고, `MANDT`가 있는 경우 Client 필드 매핑이 어떻게 되는지도 확인해야 한다.

## 13. Value Table이 Foreign Key 생성에 주는 도움

Value Table은 완전한 관계가 아니지만 쓸모가 없는 것은 아니다.

Domain에 Value Table이 설정되어 있으면, 해당 Domain을 사용하는 필드에 Foreign Key를 만들 때 시스템이 그 테이블을 Check Table 후보로 제안할 수 있다.

예를 들어 다음 흐름을 생각할 수 있다.

```text
ZD_JHY_CARRID Domain에 Value Table = ZT_JHY_CARRIER 설정
↓
ZDE_JHY_CARRID Data Element가 ZD_JHY_CARRID 참조
↓
ZT_JHY_FLIGHT-CARRID가 ZDE_JHY_CARRID 사용
↓
Foreign Key 생성 시 ZT_JHY_CARRIER가 Check Table 후보로 제안될 수 있음
```

하지만 이것은 어디까지나 생성 편의와 설계 힌트에 가깝다. 실제 관계는 Foreign Key 화면에서 정의하고 활성화해야 한다.

## 14. Fixed Value, Value Table, Foreign Key 비교

초급자는 Domain의 Fixed Value와 Value Table도 혼동하기 쉽다. 세 개를 함께 비교해보자.

| 구분 | Fixed Value | Value Table | Foreign Key |
|---|---|---|---|
| 위치 | Domain | Domain | Table Field |
| 대상 | 작은 고정 코드 목록 | 대표 값 테이블 | 실제 참조 관계 |
| 예시 | A/I/B, Y/N | SCARR, ZT_JHY_CARRIER | ZT_JHY_FLIGHT-CARRID → ZT_JHY_CARRIER-CARRID |
| 값 변경 방식 | Domain 수정 | 참조 테이블 데이터 관리 | Check Table 데이터 관리 |
| 적합한 경우 | 값이 매우 적고 거의 변하지 않음 | Domain의 대표 값 테이블을 알려주고 싶을 때 | 입력값 검증과 관계 모델링이 필요할 때 |
| Cardinality | 없음 | 없음 | 있음 |
| 실무 검증력 | 단순 값 제한 | 약함 | 강함 |

### 14.1 Fixed Value가 적합한 예

```text
Y / N
A / I / B
1 / 2 / 3
```

값이 매우 적고 안정적이면 Fixed Value가 적합할 수 있다.

### 14.2 Value Table이 적합한 예

```text
Domain이 대표적으로 어떤 마스터 테이블과 연결되는지 힌트를 주고 싶을 때
Foreign Key 생성 시 Check Table 제안을 받고 싶을 때
```

### 14.3 Foreign Key가 필요한 예

```text
테이블 필드의 값이 실제 마스터 테이블에 존재해야 할 때
F4 Help와 입력 검증을 DDIC 관계 기반으로 구성하고 싶을 때
테이블 관계를 Repository에 명시하고 싶을 때
```

## 15. 실무 판단 기준

### 15.1 Value Table만 설정해도 되는 경우

Value Table만으로 충분하다고 말하기보다는, “외부 관계 검증까지는 필요 없고 Domain 차원의 힌트만 필요한 경우”라고 이해하는 편이 안전하다.

예를 들어 다음과 같은 경우다.

| 상황 | 판단 |
|---|---|
| 교육용으로 Domain과 대표 테이블 연결을 보여주는 경우 | Value Table 설정 의미 있음 |
| 향후 Foreign Key 생성 편의를 위해 후보를 지정하는 경우 | Value Table 의미 있음 |
| 실제 입력 검증이 필요 없는 출력 전용 필드 | Foreign Key가 불필요할 수 있음 |

### 15.2 Foreign Key를 정의해야 하는 경우

다음 경우에는 Foreign Key를 적극적으로 검토한다.

| 상황 | 이유 |
|---|---|
| 입력값이 마스터 테이블에 존재해야 함 | 데이터 정합성 필요 |
| 테이블 관계를 명확히 문서화해야 함 | 유지보수와 영향 분석 필요 |
| F4 Help가 Check Table 기반으로 자연스럽게 동작하기를 원함 | 사용자 입력 지원 |
| Table Maintenance에서 유효값 검증이 필요함 | 운영 오류 예방 |
| 후속 개발자가 관계를 쉽게 이해해야 함 | Repository 기반 설명 가능 |

### 15.3 Foreign Key를 무조건 만들면 안 되는 경우

Foreign Key도 무조건 많이 만들면 좋은 것은 아니다.

| 상황 | 주의점 |
|---|---|
| 대량 처리 성능이 민감한 테이블 | 검증 흐름과 성능 영향 검토 필요 |
| 임시/스냅샷 데이터 | 과거 값 보존 때문에 현재 마스터와 불일치할 수 있음 |
| 외부 시스템 코드 저장 | SAP 내부 Check Table과 직접 매핑이 어려울 수 있음 |
| 자유 입력이 필요한 필드 | Check Table 기반 제한이 부적합할 수 있음 |

[추정] 실제 프로젝트에서는 Foreign Key 정의 여부를 데이터 정합성, 입력 화면, 인터페이스, 성능, 운영 유지보수 기준으로 함께 판단해야 한다.

## 16. 정상 흐름

이번 모듈에서 권장하는 정상 흐름은 다음과 같다.

```text
1. Check Table 후보를 설계한다.
2. Check Table의 Key 구조를 확인한다.
3. Domain에 Value Table을 선택적으로 지정한다.
4. 실제 Foreign Key가 필요한 Table Field를 찾는다.
5. Table Field에서 Foreign Key를 생성한다.
6. Field Assignment를 확인한다.
7. Cardinality를 확인한다.
8. 테이블을 저장하고 활성화한다.
9. F4 Help 또는 입력 검증 흐름을 테스트한다.
```

핵심은 “Value Table 입력 후 끝”이 아니라 “Foreign Key 생성과 검증까지 확인”하는 것이다.

## 17. 오류 흐름과 해결 방법

### 17.1 Value Table을 넣었는데 검증이 되지 않음

| 항목 | 내용 |
|---|---|
| 현상 | Domain에 Value Table을 넣었지만 테이블 필드 입력 시 검증이 기대대로 되지 않음 |
| 원인 | Value Table만 있고 Table Field에 Foreign Key가 정의되지 않음 |
| 해결 | 실제 입력 필드 또는 테이블 필드에서 Foreign Key 관계를 생성한다. |

### 17.2 Foreign Key 생성 시 Check Table이 제안되지 않음

| 항목 | 내용 |
|---|---|
| 현상 | Foreign Key 생성 화면에서 원하는 Check Table이 자동 제안되지 않음 |
| 원인 | Domain에 Value Table이 없거나, 필드가 해당 Domain을 직접/간접 참조하지 않음 |
| 해결 | Check Table을 수동 입력하거나 Domain/Data Element 연결을 확인한다. |

### 17.3 Field Assignment가 맞지 않음

| 항목 | 내용 |
|---|---|
| 현상 | Foreign Key 생성 중 필드 매핑이 불완전하거나 오류 발생 |
| 원인 | Check Table Key와 Foreign Key Table 필드 구성이 맞지 않음 |
| 해결 | Check Table의 Key 필드와 타입을 확인하고, 필요한 필드를 Foreign Key Table에 추가하거나 관계를 재설계한다. |

### 17.4 Client Field 매핑 오류

| 항목 | 내용 |
|---|---|
| 현상 | `MANDT`가 있는 테이블끼리 관계를 만들 때 매핑이 혼란스러움 |
| 원인 | Client-dependent 테이블 구조 이해 부족 |
| 해결 | 두 테이블의 `MANDT` 필드와 Key 구조를 확인하고, Client 필드가 올바르게 매핑되는지 점검한다. |

### 17.5 Value Table과 Check Table을 같은 것으로 오해

| 항목 | 내용 |
|---|---|
| 현상 | “Value Table을 설정했으니 Check Table도 설정된 것”이라고 판단 |
| 원인 | 정의 위치와 역할 차이를 이해하지 못함 |
| 해결 | Domain 수준의 Value Table과 Table Field 수준의 Foreign Key를 분리하여 확인한다. |

## 19. ABAP/화면 흐름에서의 영향

### 19.1 PARAMETERS와 연결될 때

```abap
PARAMETERS p_carrid TYPE zde_jhy_carrid.
```

따라서 Foreign Key를 잘 정의하면 사용자가 존재하지 않는 코드를 입력하는 실수를 줄이는 데 도움이 된다.

## 20. 실무 안티패턴

### 20.1 Domain Value Table만 넣고 관계 설계를 끝내는 경우

```text
문제: 실제 필드 관계가 Repository에 명확히 남지 않는다.
결과: 입력 검증, F4 Help, 영향 분석에서 기대와 다르게 동작할 수 있다.
```

### 20.2 모든 같은 Domain 필드에 동일한 Check Table을 강제하는 경우

```text
문제: 기술 타입은 같지만 업무 의미가 다른 필드가 있을 수 있다.
결과: 잘못된 참조 관계가 생긴다.
```

### 20.3 Check Table의 Key 구조를 확인하지 않는 경우

```text
문제: Field Assignment가 맞지 않거나 Client 필드 매핑이 누락될 수 있다.
결과: Foreign Key 활성화 오류 또는 잘못된 관계가 발생한다.
```

### 20.4 F4 Help를 Foreign Key만으로 해결하려는 경우

```text
문제: 사용자가 원하는 검색 조건, 표시 필드, 다중 검색 경로를 제공하기 어렵다.
결과: 별도 Search Help가 필요한 상황을 놓칠 수 있다.
```

Foreign Key는 기본 관계와 검증에 강점이 있고, Search Help는 사용자 입력 도움말 UX에 강점이 있다.

## 23. 평가 문제

### 23.1 객관식

#### Q1. Value Table의 정의 위치로 가장 적절한 것은?

A. ABAP Report Event  
B. Domain  
C. Function Module  
D. Selection Text  

**정답:** B

#### Q2. Foreign Key의 정의 위치로 가장 적절한 것은?

A. Table Field  
B. Program Include  
C. Package  
D. Transport Request  

**정답:** A

#### Q3. Value Table과 Foreign Key의 차이로 올바른 것은?

A. Value Table은 실제 관계이고 Foreign Key는 주석이다.  
B. Value Table과 Foreign Key는 완전히 같은 기능이다.  
C. Value Table은 Domain 수준의 참조 정보이고 Foreign Key는 Table Field 수준의 관계 정의이다.  
D. Foreign Key는 Domain에만 설정할 수 있다.  

**정답:** C

#### Q4. Foreign Key 생성 시 반드시 확인해야 할 항목으로 가장 적절한 것은?

A. 화면 배경색  
B. Field Assignment  
C. 프로그램 제목  
D. 사용자 즐겨찾기  

**정답:** B

### 23.2 서술형

#### Q1. Value Table만으로 입력 검증이 완성되지 않는 이유를 설명하시오.

**모범 답안:**  
Value Table은 Domain에 설정되는 대표 값 테이블 정보로, 실제 개별 Table Field가 어떤 Check Table을 참조하는지 정의하는 관계가 아니다. 입력 검증과 관계 모델링을 명확히 하려면 해당 Table Field에 Foreign Key를 정의하고 Field Assignment를 확인해야 한다.

#### Q2. Foreign Key가 Value Table보다 실무적으로 더 강한 관계 정의인 이유를 설명하시오.

**모범 답안:**  
Foreign Key는 특정 Table Field가 어떤 Check Table의 어떤 필드를 참조하는지 명시하며, Field Assignment와 Cardinality를 통해 실제 관계를 표현한다. 따라서 입력값 검증, F4 Help, 유지보수, 영향 분석에서 Value Table보다 직접적인 의미를 가진다.

#### Q3. 같은 Domain을 사용하는 필드라도 서로 다른 Foreign Key를 가질 수 있는 이유를 설명하시오.

**모범 답안:**  
Domain은 주로 기술적 속성의 재사용 단위이고, 실제 업무 의미와 관계는 필드마다 다를 수 있다. 같은 CHAR 길이와 Domain을 사용하더라도 어떤 필드는 항공사 마스터를 참조하고, 다른 필드는 별도 제휴사 테이블을 참조할 수 있으므로 Field 수준에서 Foreign Key를 다르게 정의할 수 있다.

| 다음 모듈인 Elementary Search Help와의 연결을 설명할 수 있다. |  |

---

## 25. 핵심 요약

이번 모듈의 핵심은 다음이다.

```text
Value Table은 Domain 수준의 대표 값 테이블 정보이다.
Foreign Key는 Table Field 수준의 실제 관계 정의이다.
Value Table만으로 입력 검증이 완성되었다고 판단하면 안 된다.
Foreign Key를 만들 때는 Check Table, Field Assignment, Cardinality를 확인해야 한다.
Fixed Value, Value Table, Foreign Key는 각각 역할과 적용 위치가 다르다.
```

초급자는 특히 다음 문장을 암기해도 좋다.

```text
Domain의 Value Table은 힌트이고, Table Field의 Foreign Key는 관계이다.
```

## 26. 다음 모듈 연결

다음 모듈은 `THEORY-04-M03 — Elementary Search Help`이다.

이번 모듈에서 Value Table과 Foreign Key의 차이를 구분했다면, 다음 모듈에서는 사용자가 F4를 눌렀을 때 어떤 값 목록을 어떻게 보여줄지 더 직접적으로 설계하는 Search Help를 배운다.

연결 흐름은 다음과 같다.

```text
THEORY-04-M01 Foreign Key와 Check Table
→ THEORY-04-M02 Value Table과 Foreign Key의 차이
→ THEORY-04-M03 Elementary Search Help
→ THEORY-04-M04 Collective Search Help 기초
→ THEORY-04-M05 PARAMETERS와 DDIC F4 Help 연결
→ THEORY-04-M06 DDIC 검증과 프로그램 검증의 역할 분리
```

Foreign Key는 관계와 기본 검증의 기반이고, Search Help는 사용자 입력 도움말의 UX를 더 풍부하게 만드는 도구이다.
