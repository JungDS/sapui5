## 3. 왜 Foreign Key가 필요한가?

### 3.1 문제 상황

다음과 같은 부서 마스터 테이블이 있다고 가정하자.

```text
ZT_JHY_DEPT
```

| MANDT | DEPT_ID | DEPT_NAME |
|---|---|---|
| 100 | D001 | Sales |
| 100 | D002 | Finance |
| 100 | D003 | IT |

그리고 사용자 테이블이 있다.

```text
ZT_JHY_USER
```

| MANDT | USER_ID | USER_NAME | DEPT_ID |
|---|---|---|---|
| 100 | U001 | Kim | D001 |
| 100 | U002 | Lee | D002 |

여기서 `ZT_JHY_USER-DEPT_ID`에는 반드시 `ZT_JHY_DEPT-DEPT_ID`에 존재하는 값만 들어가야 한다.  
그런데 사용자가 실수로 `D999`를 입력하면 어떻게 될까?

| MANDT | USER_ID | USER_NAME | DEPT_ID |
|---|---|---|---|
| 100 | U003 | Park | D999 |

`D999`는 부서 마스터에 존재하지 않는다.  
이런 데이터는 업무적으로 잘못된 데이터이다. 사용자를 부서별로 집계하거나 부서명을 조인해서 보여줄 때 문제가 발생한다.

### 3.2 Foreign Key의 목적

Foreign Key는 이런 잘못된 값을 줄이기 위해 DDIC에서 테이블 간 관계를 정의하는 기능이다.

초급자용 정의는 다음과 같다.

```text
Foreign Key는 한 테이블의 필드 값이 다른 기준 테이블에 존재하는 값이어야 한다는 관계를 DDIC에 정의하는 것이다.
```

여기서 기준 테이블이 Check Table이다.

```text
사용자 테이블 ZT_JHY_USER의 DEPT_ID
  → 부서 마스터 테이블 ZT_JHY_DEPT의 DEPT_ID를 참조
```

## 4. Check Table이란 무엇인가?

Check Table은 입력값 검증의 기준이 되는 테이블이다.

예를 들어 `ZT_JHY_DEPT`가 부서 마스터라면, 사용자 테이블의 부서 필드는 `ZT_JHY_DEPT`에 존재하는 부서 코드만 허용해야 한다.

```text
Check Table: ZT_JHY_DEPT
Checked Field: ZT_JHY_USER-DEPT_ID
```

### 4.1 Check Table의 특징

| 특징 | 설명 |
|---|---|
| 기준 데이터 보유 | 허용 가능한 값을 보유한다. |
| 보통 마스터/코드 테이블 | 부서, 상태, 회사코드, 플랜트, 항공사 등 |
| Key 기반 관계 | 일반적으로 Check Table의 Key 필드를 기준으로 관계를 정의한다. |
| 입력 검증과 연결 | 화면 입력, 테이블 유지보수, 일부 DDIC 기반 처리에서 값 검증에 활용될 수 있다. |
| F4 Help와 연결 가능 | 가능한 값 목록을 사용자에게 보여주는 기반이 될 수 있다. |

### 4.2 Check Table과 일반 테이블의 차이

기술적으로 Check Table도 Transparent Table일 수 있다.  
차이는 "그 테이블을 어떤 관계에서 기준 테이블로 사용하느냐"이다.

| 구분 | 설명 |
|---|---|
| 일반 Transparent Table | 데이터를 저장하는 테이블 |
| Check Table | 다른 필드의 입력값 검증 기준으로 사용되는 테이블 |

즉, 어떤 테이블이 Check Table이라는 것은 그 테이블의 고유한 객체 유형이 다르다는 뜻이 아니라, Foreign Key 관계 안에서 기준 역할을 한다는 의미이다.

## 5. Foreign Key와 Check Table의 관계

Foreign Key와 Check Table은 함께 이해해야 한다.

```text
Foreign Key = 관계 정의
Check Table = 관계에서 참조되는 기준 테이블
```

예시:

```text
Dependent Table: ZT_JHY_USER
Foreign Key Field: DEPT_ID
Check Table: ZT_JHY_DEPT
Check Field: DEPT_ID
```

관계를 그림으로 표현하면 다음과 같다.

```text
ZT_JHY_DEPT                       ZT_JHY_USER
-----------                       -----------
MANDT      <--------------------  MANDT
DEPT_ID    <--------------------  DEPT_ID
DEPT_NAME                         USER_ID
                                  USER_NAME
```

`ZT_JHY_USER`는 사용자 데이터이다.  
`ZT_JHY_DEPT`는 부서 코드 기준 데이터이다.  
사용자 데이터의 `DEPT_ID`는 부서 마스터에 존재하는 값이어야 한다.

## 6. 부모 테이블과 자식 테이블

Foreign Key 관계에서는 보통 다음 용어를 사용할 수 있다.

| 용어 | 의미 | 예시 |
|---|---|---|
| Check Table | 기준값을 가진 테이블 | ZT_JHY_DEPT |
| Foreign Key Table | 기준값을 참조하는 테이블 | ZT_JHY_USER |
| Parent Table | 부모 역할의 기준 테이블 | 부서 마스터 |
| Child Table | 부모를 참조하는 자식 테이블 | 사용자 테이블 |

다만 SAP DDIC 화면에서는 `Check Table`, `Foreign Key Table`, `Foreign Key Fields` 같은 용어가 중요하다.

초급자는 다음 문장을 기억하면 된다.

```text
Check Table은 기준값을 가진 테이블이고,
Foreign Key Table은 그 기준값을 참조하는 테이블이다.
```

## 7. Cardinality란 무엇인가?

Cardinality는 테이블 간 관계 수를 표현한다.

예를 들어 부서와 사용자 관계를 생각해보자.

```text
하나의 부서에는 여러 사용자가 속할 수 있다.
한 사용자는 하나의 부서에 속한다.
```

이를 관계로 표현하면 다음과 같다.

```text
ZT_JHY_DEPT 1건
  → ZT_JHY_USER 여러 건
```

즉, 부서 1건에 사용자 N건이 연결될 수 있다.

### 7.1 초급자용 Cardinality 해석

| 관계 | 설명 | 예시 |
|---|---|---|
| 1:1 | 부모 1건에 자식 1건 | 사용자와 사용자 상세 설정 |
| 1:N | 부모 1건에 자식 여러 건 | 부서 1개에 사용자 여러 명 |
| N:1 | 자식 여러 건이 부모 1건을 참조 | 여러 사용자가 한 부서를 참조 |
| N:M | 여러 건과 여러 건의 관계 | 학생과 과목 관계. 중간 테이블 필요 |

DDIC Foreign Key 설정에서는 관계의 의미를 표현하기 위해 Cardinality를 선택하거나 확인할 수 있다.

### 7.2 Cardinality가 중요한 이유

Cardinality는 단순한 문서용 값이 아니다.  
테이블 관계를 이해하고, 입력 도움말과 데이터 모델의 의미를 설명하는 데 도움을 준다.

| 이유 | 설명 |
|---|---|
| 데이터 모델 이해 | 부모와 자식의 관계 수를 명확히 한다. |
| 개발자 커뮤니케이션 | 테이블 관계를 빠르게 설명할 수 있다. |
| 검증 의도 표현 | 어떤 값이 기준값을 참조해야 하는지 명확해진다. |
| 후속 CDS/RAP 학습 기반 | Association, Composition 이해의 선행 감각이 된다. |

## 8. Foreign Key는 DB 제약조건과 같은가?

초급자가 가장 주의해야 할 부분이다.

SAP DDIC의 Foreign Key는 ABAP Dictionary 수준의 관계 정의이다.  
이 관계는 화면 입력 검증, F4 Help, Table Maintenance, Dynpro, Dictionary 기반 처리에서 중요한 의미를 가진다.

하지만 모든 상황에서 물리 DB의 Foreign Key Constraint처럼 항상 데이터베이스가 직접 강제한다고 단정하면 안 된다.

실무적으로는 다음처럼 이해하는 것이 안전하다.

```text
DDIC Foreign Key는 SAP Dictionary에서 필드 간 관계와 값 검증 의도를 정의하는 표준 메타데이터이다.
그러나 모든 데이터 변경 경로에서 자동으로 업무 검증이 완성되는 것은 아니다.
프로그램 로직, BAPI, RAP, OData, 직접 DB 변경, 마이그레이션 등에서는 별도 검증 책임을 함께 고려해야 한다.
```

따라서 Foreign Key를 만들었다고 해서 프로그램 검증을 모두 생략해도 되는 것은 아니다.  
이 주제는 `THEORY-04-M06 DDIC 검증과 프로그램 검증의 역할 분리`에서 더 자세히 다룬다.

## 12. SE11에서 Foreign Key 관계 정의하기

### 12.1 사용자 테이블에 DEPT_ID 필드 추가

`ZT_JHY_USER` 테이블에 다음 필드를 추가한다.

| Field | Key | Data Element | 설명 |
|---|---:|---|---|
| DEPT_ID |  | ZDE_JHY_DEPT_ID | 부서 ID |

이 필드는 Key가 아니다.  
사용자 한 건을 식별하는 Key는 일반적으로 `MANDT + USER_ID`이다.  
부서는 사용자 속성에 해당하므로 일반 필드로 둔다.

### 12.2 Foreign Key 설정 진입

SE11에서 `ZT_JHY_USER`를 Change 모드로 연다.

```text
SE11
→ Database Table: ZT_JHY_USER
→ Change
→ Fields 탭
→ DEPT_ID 필드 선택
→ Foreign Key 버튼
```

### 12.3 Check Table 입력

Foreign Key 화면에서 Check Table로 다음을 입력한다.

```text
Check Table: ZT_JHY_DEPT
```

시스템은 필드 이름과 Data Element를 기준으로 제안 매핑을 보여줄 수 있다.

예상 매핑은 다음과 같다.

| Foreign Key Table Field | Check Table Field |
|---|---|
| MANDT | MANDT |
| DEPT_ID | DEPT_ID |

`MANDT`도 함께 매핑되는 이유는 Client별 데이터 분리를 고려해야 하기 때문이다.

### 12.4 Cardinality 설정

부서와 사용자 관계는 일반적으로 다음과 같이 이해할 수 있다.

```text
하나의 부서에는 여러 사용자가 속할 수 있다.
한 사용자는 하나의 부서에 속한다.
```

따라서 개념적으로는 다음 관계이다.

```text
ZT_JHY_DEPT 1건 : ZT_JHY_USER N건
```

SE11 화면에서는 Cardinality 선택 방식이 시스템에 따라 다르게 보일 수 있다.  
초급 실습에서는 강사가 지정한 값을 사용하되, 관계 의미가 “부서 1건을 여러 사용자 건이 참조한다”는 점을 이해하는 것이 더 중요하다.

### 12.5 저장 및 활성화

Foreign Key 관계를 저장한 뒤 `ZT_JHY_USER` 테이블을 다시 Activate한다.

정상적으로 활성화되면 DDIC 관계가 정의된 것이다.

## 13. 정상 흐름 정리

Foreign Key 정의의 정상 흐름은 다음과 같다.

```text
1. Check Table 후보를 결정한다.
2. Check Table의 Key와 데이터 의미를 확인한다.
3. Foreign Key Table에 참조 필드를 둔다.
4. 참조 필드와 Check Table 필드의 타입/의미를 맞춘다.
5. SE11에서 Foreign Key 설정으로 들어간다.
6. Check Table을 입력한다.
7. 필드 매핑을 확인한다.
8. Cardinality를 설정 또는 확인한다.
9. 저장한다.
10. 테이블을 Activate한다.
11. 입력값 검증 또는 F4 Help 연결 가능성을 확인한다.
```

## 14. 오류 상황과 해결 방법

### 14.1 Check Table이 활성화되어 있지 않음

| 항목 | 내용 |
|---|---|
| 증상 | Foreign Key 설정 또는 테이블 활성화 중 오류 발생 |
| 원인 | `ZT_JHY_DEPT`가 아직 Activate되지 않음 |
| 해결 | Check Table을 먼저 Activate한 뒤 Foreign Key Table을 활성화 |

권장 활성화 순서는 다음이다.

```text
Domain
→ Data Element
→ Check Table
→ Foreign Key Table
```

### 14.2 필드 타입이 일치하지 않음

| 항목 | 내용 |
|---|---|
| 증상 | Foreign Key 필드와 Check Table 필드 매핑 오류 |
| 원인 | `DEPT_ID`의 Data Element 또는 Domain이 서로 다름 |
| 해결 | 같은 의미의 Data Element를 사용하거나 기술 타입을 일치시킴 |

예를 들어 Check Table의 `DEPT_ID`가 CHAR4인데 Foreign Key Table의 `DEPT_ID`가 CHAR10이면 부적절하다.

### 14.3 Client Field 매핑 누락

| 항목 | 내용 |
|---|---|
| 증상 | Client-dependent 테이블 관계에서 MANDT 매핑 관련 오류 또는 혼란 |
| 원인 | 두 테이블 모두 Client-dependent인데 MANDT 관계를 고려하지 않음 |
| 해결 | `MANDT` 필드를 첫 번째 Key로 두고 Foreign Key 매핑에 포함되는지 확인 |

### 14.4 Check Table의 Key를 잘못 설계함

| 항목 | 내용 |
|---|---|
| 증상 | 관계 설정이 복잡하거나 식별 기준이 불명확 |
| 원인 | Check Table의 Key가 업무 식별 기준과 맞지 않음 |
| 해결 | Check Table의 Key 설계를 먼저 정리 |

Check Table이 잘못 설계되어 있으면 Foreign Key도 자연스럽게 잘못된다.  
관계 정의 전에 기준 테이블의 Key가 명확해야 한다.

### 14.5 존재하지 않는 값 입력

| 항목 | 내용 |
|---|---|
| 증상 | 사용자가 `D999` 같은 존재하지 않는 부서 코드를 입력 |
| 원인 | Check Table에 해당 값이 없음 |
| 해결 | 올바른 값을 입력하거나 Check Table에 기준 데이터를 먼저 생성 |

## 15. Foreign Key와 F4 Help의 관계

Foreign Key는 입력 도움말과도 연결될 수 있다.  
사용자가 `DEPT_ID` 필드에서 F4를 누르면 시스템은 가능한 값 목록을 제안할 수 있다.

초급자는 다음 관계를 기억하면 된다.

```text
Check Table에 유효값이 있다.
Foreign Key로 필드 관계를 정의한다.
입력 필드에서 가능한 값 목록을 제공할 수 있다.
```

다만 F4 Help가 항상 Foreign Key만으로 충분한 것은 아니다.  
복잡한 조회 조건, 여러 필드 표시, 사용자 친화적인 검색 조건이 필요하면 Search Help를 별도로 설계한다.

이 내용은 `THEORY-04-M03 Elementary Search Help`에서 자세히 다룬다.

## 16. Foreign Key와 Value Table의 차이 예고

초급자가 자주 혼동하는 개념이 Value Table이다.

간단히만 예고하면 다음과 같다.

```text
Value Table은 Domain에 제안된 기본 값 테이블 성격이다.
Foreign Key는 실제 필드와 Check Table 사이의 관계 정의이다.
```

Value Table을 Domain에 지정했다고 해서 모든 필드에 자동으로 입력 검증이 완성되는 것은 아니다.  
실제 입력 검증 관계를 위해서는 해당 필드에서 Foreign Key를 정의해야 한다.

## 17. DDIC 검증과 프로그램 검증의 경계

Foreign Key는 DDIC 수준의 중요한 검증 장치이다.  
하지만 실무에서는 다음 상황을 별도로 고려해야 한다.

| 상황 | 고려사항 |
|---|---|
| ABAP 프로그램에서 INSERT/UPDATE | 프로그램 로직이 어떤 검증을 수행하는지 확인 |
| BAPI/RFC/OData 입력 | 서비스 계층의 검증 책임 확인 |
| 대량 업로드 | 업로드 전후 데이터 검증 필요 |
| Migration | 소스 데이터와 기준 테이블 정합성 확인 |
| 운영 중 기준 데이터 삭제 | 참조 중인 자식 데이터 영향 확인 |

즉, Foreign Key는 설계의 시작점이지 모든 업무 검증의 끝이 아니다.

## 18. 실무 설계 기준

### 18.1 Check Table로 적합한 테이블

Check Table로 적합한 테이블은 다음 특징을 가진다.

| 기준 | 설명 |
|---|---|
| 기준값을 보유 | 입력 가능한 값 목록을 가진다. |
| Key가 명확 | 참조할 필드가 명확한 Key 구조를 가진다. |
| 데이터 의미가 안정적 | 값 체계가 자주 바뀌지 않는다. |
| 참조 목적이 명확 | 다른 테이블에서 실제로 참조할 의미가 있다. |
| Client 구조가 일관적 | 참조하는 테이블과 Client 처리 방식이 맞다. |

### 18.2 Foreign Key 설계 시 질문

관계를 만들기 전에 다음 질문을 던진다.

```text
이 필드는 실제로 기준 테이블의 값만 허용해야 하는가?
기준 테이블의 Key는 무엇인가?
두 필드의 Data Element 또는 Domain은 의미상 일치하는가?
Client-dependent 관계인가?
부모 데이터 삭제 시 자식 데이터는 어떻게 되는가?
F4 Help가 필요한가?
프로그램 검증도 추가로 필요한가?
```

### 18.3 피해야 할 설계

| 안티패턴 | 문제 |
|---|---|
| 이름만 같은 필드를 무조건 연결 | 실제 의미가 다를 수 있음 |
| Check Table Key가 불명확 | 관계 의미가 불안정 |
| Client 처리 무시 | 다른 Client 데이터와 혼동 가능 |
| Foreign Key만 믿고 프로그램 검증 생략 | 입력 경로에 따라 검증 누락 가능 |
| 모든 코드값을 Fixed Value로만 처리 | 값이 늘어나는 경우 유지보수 어려움 |
| 모든 코드값을 Check Table로만 처리 | 너무 단순한 값에는 과도한 설계일 수 있음 |

## 20. ABAP 코드와의 연결

Foreign Key 자체는 DDIC 설정이지만, ABAP 프로그램에서도 이 관계를 의식해야 한다.

예를 들어 사용자 데이터를 저장하기 전에 부서 코드가 존재하는지 확인하는 코드를 작성할 수 있다.

```abap
PARAMETERS p_dept TYPE zde_jhy_dept_id.

SELECT SINGLE dept_id
  FROM zt_jhy_dept
  WHERE dept_id = @p_dept
  INTO @DATA(lv_dept_id).

IF sy-subrc <> 0.
  MESSAGE '존재하지 않는 부서 코드입니다.' TYPE 'E'.
ENDIF.
```

이 코드는 DDIC Foreign Key가 있음에도 프로그램 검증이 필요할 수 있다는 점을 보여주기 위한 예시이다.

초급자는 여기서 다음을 이해하면 된다.

```text
DDIC 관계는 설계와 기본 검증을 돕는다.
ABAP 프로그램은 업무 흐름에 맞는 추가 검증을 수행할 수 있다.
두 역할은 경쟁 관계가 아니라 보완 관계이다.
```

## 21. 강사용 설명 포인트

강사는 이번 모듈에서 다음 메시지를 강조하면 좋다.

### 21.1 Foreign Key는 “연결선”이 아니라 “검증 의도”이다

테이블 다이어그램에서 선 하나를 긋는 것이 목적이 아니다.  
중요한 것은 “이 필드에는 어떤 기준값만 들어와야 하는가?”라는 검증 의도이다.

### 21.2 Check Table은 부모 데이터의 기준이다

Check Table은 단순 참조 대상이 아니라 입력 가능한 값의 기준 데이터이다.  
Check Table의 데이터 품질이 낮으면 Foreign Key 관계도 의미가 약해진다.

### 21.3 Cardinality는 후속 CDS/RAP로 이어진다

초급 DDIC에서 Cardinality를 어렵게 느낄 수 있지만, 나중에 CDS Association, RAP Composition을 이해할 때 매우 중요해진다.

### 21.4 Foreign Key만으로 끝나지 않는다

실무에서는 DDIC 검증, 프로그램 검증, UI 검증, 서비스 검증이 함께 고려된다.  
이번 모듈에서는 DDIC 관계의 목적을 이해하고, 역할 경계는 뒤에서 확장한다.

### 23.2 서술형

#### Q1. Foreign Key와 Check Table의 차이를 설명하시오.

**모범 답안:**  
Foreign Key는 한 테이블의 필드가 다른 기준 테이블의 값과 관계를 가진다는 DDIC 관계 정의이다. Check Table은 그 관계에서 허용 가능한 기준값을 보유하는 테이블이다.

#### Q2. `ZT_JHY_USER-DEPT_ID`가 `ZT_JHY_DEPT-DEPT_ID`를 참조하도록 Foreign Key를 정의하는 이유를 설명하시오.

**모범 답안:**  
사용자 테이블의 부서 ID에 실제 존재하는 부서 코드만 입력되도록 하기 위해서이다. 이를 통해 잘못된 부서 코드 입력을 줄이고, 사용자와 부서 마스터 간 관계를 명확히 할 수 있다.

#### Q3. Foreign Key가 있어도 프로그램 검증이 필요한 이유를 설명하시오.

**모범 답안:**  
Foreign Key는 DDIC 수준의 관계와 기본 검증 의도를 정의하지만, 모든 데이터 변경 경로에서 모든 업무 검증을 자동으로 보장하는 것은 아니다. ABAP 프로그램, BAPI, OData, 대량 업로드 등에서는 업무 흐름에 맞는 추가 검증이 필요할 수 있다.

## 25. 핵심 요약

```text
Check Table은 입력 가능한 기준값을 가진 테이블이다.
Foreign Key는 한 테이블의 필드가 Check Table의 값과 관계를 가지도록 정의하는 DDIC 관계이다.
Cardinality는 부모와 자식 데이터의 관계 수를 표현한다.
Foreign Key는 F4 Help와 입력 검증의 기반이 될 수 있다.
Foreign Key는 모든 프로그램 검증을 대체하지 않는다.
Client-dependent 관계에서는 MANDT 매핑을 반드시 고려해야 한다.
```
