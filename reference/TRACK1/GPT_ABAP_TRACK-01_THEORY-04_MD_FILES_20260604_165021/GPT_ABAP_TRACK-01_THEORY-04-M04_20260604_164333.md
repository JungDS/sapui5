이 문서는 `THEORY-04-M04 — Collective Search Help 기초`만 다룬다.

| 키워드 | 의미 |
|---|---|

| Search Help Parameter | Search Help의 입력값, 출력값, 필드 매핑, 화면 표시 위치를 결정하는 파라미터 |

초급자는 이번 모듈에서 다음 차이를 이해해야 한다.

```text
Elementary Search Help = 하나의 검색 방법
Collective Search Help = 여러 검색 방법을 하나로 묶은 검색 도움말
```

예를 들어 항공사 코드를 찾을 때 사용자는 다음처럼 여러 방식으로 검색하고 싶을 수 있다.

```text

항공사 이름으로 검색
통화 코드로 검색
```

이 각각을 Elementary Search Help로 만들고, 이들을 하나의 Collective Search Help에 포함하면 사용자는 F4 Help 화면에서 여러 검색 방식을 선택할 수 있다.

## 3. Collective Search Help란 무엇인가?

### 3.1 쉬운 정의

Collective Search Help는 여러 개의 Elementary Search Help를 하나로 묶은 DDIC 객체이다.

사용자는 하나의 F4 Help를 호출하지만, 내부적으로는 여러 검색 방법 중 하나를 선택해 값을 찾을 수 있다.

```text
Collective Search Help
 ├─ Elementary Search Help 1
 ├─ Elementary Search Help 2
 └─ Elementary Search Help 3
```

### 3.2 사용자 관점

사용자 입장에서는 다음과 같은 차이가 있다.

| Search Help 유형 | 사용자 경험 |
|---|---|
| Elementary Search Help | 하나의 검색 조건 화면 또는 하나의 결과 리스트를 사용한다. |
| Collective Search Help | 여러 검색 방법 중 하나를 선택할 수 있다. |

예를 들어 고객 번호를 찾는 F4 Help가 있다고 하자.  
사용자는 고객 번호를 직접 모르더라도 고객명, 사업자번호, 도시, 국가 등 다양한 기준으로 찾고 싶을 수 있다.

이때 각 검색 기준을 별도 Elementary Search Help로 만들고, 이를 Collective Search Help로 묶으면 사용자 경험이 좋아진다.

### 3.3 개발자 관점

개발자 입장에서 Collective Search Help는 다음 목적을 가진다.

| 목적 | 설명 |
|---|---|
| 검색 경로 통합 | 여러 Elementary Search Help를 하나의 대표 Search Help로 제공한다. |
| 재사용성 향상 | 개별 Elementary Search Help를 다른 Collective Search Help에서도 재사용할 수 있다. |
| 사용자 편의성 향상 | 사용자가 상황에 맞는 검색 방법을 선택할 수 있다. |
| 인터페이스 통일 | 여러 검색 방법이 동일한 결과값을 반환하도록 Parameter를 맞출 수 있다. |

## 4. Elementary Search Help와 Collective Search Help의 차이

### 4.1 비교표

| 구분 | Elementary Search Help | Collective Search Help |
|---|---|---|
| 역할 | 하나의 검색 방법 정의 | 여러 검색 방법 묶음 |
| Selection Method | 직접 지정 | 보통 직접 지정하지 않음 |
| Search Help Parameter | 직접 정의 | 대표 인터페이스 역할로 정의 |
| Included Search Help | 없음 | 여러 Elementary Search Help 포함 |
| 사용자 화면 | 단일 검색 경로 | 여러 검색 경로 선택 가능 |
| 실습 난이도 | 낮음 | 중하 |

### 4.2 핵심 차이

Elementary Search Help는 실제로 어떤 테이블이나 View를 기준으로 값을 찾을지 정의한다.

```text
Selection Method: SCARR
Parameter: CARRID, CARRNAME, CURRCODE
```

Collective Search Help는 그 검색 방법들을 묶는다.

```text
Collective: ZSH_JHY_CARR
Included:
  ZSH_JHY_CARR_BY_ID
  ZSH_JHY_CARR_BY_NAME
  ZSH_JHY_CARR_BY_CURR
```

따라서 Collective Search Help의 핵심은 다음이다.

```text
여러 Elementary Search Help를 포함한다.
각 Search Help의 Parameter를 대표 Parameter에 맞게 연결한다.
```

## 5. 언제 Collective Search Help를 사용하는가?

### 5.1 적합한 경우

Collective Search Help는 하나의 필드 값에 대해 여러 검색 경로가 필요한 경우 적합하다.

| 상황 | 예시 |
|---|---|
| 같은 값을 여러 기준으로 찾고 싶음 | 고객번호를 고객명, 도시, 사업자번호로 검색 |
| 사용자 그룹별 검색 습관이 다름 | 영업은 고객명, 회계는 사업자번호로 검색 |
| 하나의 대표 F4 Help 아래 여러 업무 View를 제공 | 자재를 자재번호, 자재명, 자재그룹 기준으로 검색 |
| 표준 Search Help를 확장하거나 조합 | 표준 포함 Search Help를 참고해 고객 전용 검색 경로 추가 |

### 5.2 부적합한 경우

다음 경우에는 Collective Search Help가 과도한 설계가 될 수 있다.

| 상황 | 이유 |
|---|---|
| 검색 방법이 하나뿐임 | Elementary Search Help로 충분하다. |
| 단순 코드값 몇 개만 제공 | Domain Fixed Value 또는 Check Table 기반 F4가 더 단순할 수 있다. |
| 검색 기준이 거의 동일함 | 사용자에게 중복 탭만 늘어난다. |
| 값 검증이 목적임 | Search Help는 검증 객체가 아니다. |
| 데이터 건수가 매우 작고 변경 가능성이 낮음 | 단순한 방법이 유지보수에 유리하다. |

초급자는 다음 원칙을 기억하면 된다.

```text
검색 방법이 하나면 Elementary Search Help.
검색 방법이 여러 개이고 모두 같은 결과값을 반환해야 한다면 Collective Search Help.
```

## 6. 실습 시나리오 개요

### 6.1 실습 목표

항공사 코드 `CARRID`를 찾기 위한 Collective Search Help를 생성한다.

### 6.2 실습 객체

이번 실습에서는 다음 객체를 사용한다.

| 객체 | 역할 |
|---|---|
| `ZSH_JHY_CARR_BY_ID` | 항공사 코드 기준 Elementary Search Help |
| `ZSH_JHY_CARR_BY_NAME` | 항공사 이름 기준 Elementary Search Help |
| `ZSH_JHY_CARR` | 두 Search Help를 묶는 Collective Search Help |

[추정] 교육용 SAP 시스템에 Flight Model 테이블 `SCARR`가 존재한다고 가정한다. 시스템에 `SCARR`가 없거나 데이터가 없다면, 교육용 Z 테이블 또는 시스템에 존재하는 다른 마스터성 테이블로 대체할 수 있다.

### 6.3 대표 필드

| 필드 | 의미 |
|---|---|
| `CARRID` | 항공사 코드 |
| `CARRNAME` | 항공사명 |
| `CURRCODE` | 통화 코드 |

### 6.4 예상 사용자 흐름

사용자가 `CARRID` 필드에서 F4를 누르면 다음 검색 방법을 선택할 수 있다.

```text
1. 항공사 코드로 검색
2. 항공사 이름으로 검색
```

어떤 검색 방법을 사용하든 최종적으로 입력 필드에는 `CARRID` 값이 반환되어야 한다.

## 7. 사전 준비: Elementary Search Help

Collective Search Help를 만들기 전에 포함할 Elementary Search Help가 먼저 존재해야 한다.

### 7.1 Elementary Search Help 1 — 코드 기준 검색

```text
Search Help: ZSH_JHY_CARR_BY_ID
Short Description: Carrier Search by ID
Selection Method: SCARR
```

| Parameter | IMP | EXP | LPos | SPos | 의미 |
|---|---:|---:|---:|---:|---|
| CARRID | X | X | 1 | 1 | 항공사 코드 |
| CARRNAME |  |  | 2 | 2 | 항공사명 |
| CURRCODE |  |  | 3 | 3 | 통화 코드 |

### 7.2 Elementary Search Help 2 — 이름 기준 검색

```text
Search Help: ZSH_JHY_CARR_BY_NAME
Short Description: Carrier Search by Name
Selection Method: SCARR
```

| Parameter | IMP | EXP | LPos | SPos | 의미 |
|---|---:|---:|---:|---:|---|
| CARRID |  | X | 1 | 2 | 항공사 코드 |
| CARRNAME | X |  | 2 | 1 | 항공사명 |
| CURRCODE |  |  | 3 | 3 | 통화 코드 |

### 7.3 왜 두 Search Help 모두 `CARRID`를 EXP로 두는가?

Collective Search Help의 최종 목적은 항공사 코드를 입력 필드로 반환하는 것이다.  
따라서 내부 검색 방법이 코드 기준이든 이름 기준이든 최종 Export Parameter는 `CARRID`여야 한다.

```text
검색 기준은 다를 수 있다.
하지만 반환값은 같아야 한다.
```

이 원칙을 놓치면 사용자가 F4 Help에서 값을 선택해도 입력 필드에 기대한 값이 돌아오지 않을 수 있다.

## 8. Collective Search Help의 구조

Collective Search Help는 보통 다음 구조로 이해한다.

```text
Collective Search Help: ZSH_JHY_CARR

대표 Parameter:
  CARRID
  CARRNAME
  CURRCODE

Included Search Helps:
  ZSH_JHY_CARR_BY_ID
  ZSH_JHY_CARR_BY_NAME

Parameter Assignment:
  Collective CARRID   ↔ Included CARRID
  Collective CARRNAME ↔ Included CARRNAME
  Collective CURRCODE ↔ Included CURRCODE
```

여기서 중요한 것은 **대표 Parameter**와 **포함된 Search Help의 Parameter**를 연결하는 것이다.

## 9. Search Help Parameter의 의미

Collective Search Help에서도 Search Help Parameter는 중요하다.  
다만 Elementary Search Help와 역할이 약간 다르다.

### 9.1 Elementary Search Help의 Parameter

Elementary Search Help의 Parameter는 실제 검색 화면과 결과 리스트를 구성한다.

| 속성 | 의미 |
|---|---|
| IMP | 입력값으로 사용 가능 |
| EXP | 선택 결과로 반환 가능 |
| LPos | 결과 리스트 표시 순서 |
| SPos | 검색 조건 화면 표시 순서 |

### 9.2 Collective Search Help의 Parameter

Collective Search Help의 Parameter는 여러 포함 Search Help를 연결하는 공통 인터페이스 역할을 한다.

| 역할 | 설명 |
|---|---|
| 대표 입력값 | 외부 필드에서 들어온 값을 내부 Elementary Search Help로 전달 |
| 대표 출력값 | 내부 Elementary Search Help의 결과를 외부 필드로 반환 |
| 매핑 기준 | 포함 Search Help의 Parameter와 연결되는 기준 |
| 일관성 유지 | 여러 검색 방법이 같은 결과값을 반환하도록 맞춤 |

초급자는 Collective Search Help의 Parameter를 다음처럼 이해하면 쉽다.

```text
Collective Search Help Parameter = 여러 검색 방법을 하나로 연결하는 공통 단자
```

## 10. SE11에서 Collective Search Help 생성 절차

### 10.1 SE11 실행

SAP GUI에서 다음 트랜잭션을 실행한다.

```text
SE11
```

### 10.2 Search Help 선택

SE11 첫 화면에서 `Search Help`를 선택하고 이름을 입력한다.

```text
ZSH_JHY_CARR
```

이후 `Create`를 선택한다.

### 10.3 Collective Search Help 선택

생성 팝업에서 다음 유형을 선택한다.

```text
Collective Search Help
```

### 10.4 Short Description 입력

```text
Carrier Collective Search Help
```

Short Description은 나중에 Search Help를 찾거나 유지보수할 때 매우 중요하다.

### 10.5 Definition 탭의 대표 Parameter 입력

Collective Search Help의 대표 Parameter를 입력한다.

| Parameter | IMP | EXP | 설명 |
|---|---:|---:|---|
| CARRID | X | X | 항공사 코드 |
| CARRNAME | X |  | 항공사명 |
| CURRCODE | X |  | 통화 코드 |

설계 의도는 다음과 같다.

```text
CARRID는 외부에서 입력값으로 들어올 수도 있고 결과값으로 반환될 수도 있다.
CARRNAME은 이름 기준 검색에 입력값으로 사용할 수 있다.
CURRCODE는 통화 기준 검색 확장 가능성을 위해 입력값으로 둘 수 있다.
```

교육용 최소 예제에서는 `CARRID`만 EXP로 설정해도 충분하다.

### 10.6 Included Search Helps 입력

Included Search Helps 또는 Inclusions 영역에서 포함할 Elementary Search Help를 입력한다.

| Included Search Help | 설명 |
|---|---|
| ZSH_JHY_CARR_BY_ID | 항공사 코드 기준 검색 |
| ZSH_JHY_CARR_BY_NAME | 항공사 이름 기준 검색 |

시스템 화면에서는 “Included search helps”, “Inclusion”, “Search help inclusion” 등으로 표시될 수 있다.

[추정] SAP GUI 언어와 릴리스에 따라 탭/버튼 명칭이 약간 다르게 보일 수 있다.

### 10.7 Parameter Assignment 수행

각 Included Search Help에 대해 Parameter Assignment를 설정한다.

예시:

| Collective Parameter | Included Search Help Parameter |
|---|---|
| CARRID | CARRID |
| CARRNAME | CARRNAME |
| CURRCODE | CURRCODE |

이 매핑이 제대로 되어야 내부 Search Help의 결과가 Collective Search Help 외부로 전달된다.

### 10.8 저장

교육용 시스템에서는 `$TMP` Local Object로 저장할 수 있다.  
실무 프로젝트에서는 반드시 지정된 Package와 Transport Request를 사용한다.

### 10.9 활성화

Collective Search Help와 포함된 Elementary Search Help가 모두 활성화되어야 정상 테스트가 가능하다.

활성화 순서는 다음처럼 이해하면 된다.

```text
1. Elementary Search Help 활성화
2. Collective Search Help 활성화
3. Data Element 또는 필드 연결
4. F4 Help 테스트
```

## 11. Collective Search Help 테스트

### 11.1 SE11에서 직접 테스트

SE11에서 Collective Search Help를 Display 또는 Change 모드로 연 뒤 테스트 기능을 실행한다.

테스트 시 확인할 내용은 다음이다.

| 확인 항목 | 설명 |
|---|---|
| 포함 Search Help 목록 | 사용자가 여러 검색 방법을 볼 수 있는가 |
| 검색 조건 화면 | 선택한 검색 방법에 맞는 조건 필드가 표시되는가 |
| 결과 리스트 | 기대한 필드가 표시되는가 |
| 값 반환 | 최종적으로 CARRID가 반환되는가 |
| 데이터 건수 | SCARR 또는 Selection Method에 테스트 데이터가 있는가 |

### 11.2 사용자 화면에서의 예상 동작

사용자가 `CARRID` 필드에서 F4를 누르면 다음과 같은 흐름을 기대한다.

```text
1. F4 Help 호출
2. 검색 방법 선택
3. 검색 조건 입력
4. 결과 리스트 표시
5. 항공사 선택
6. CARRID가 입력 필드로 반환
```

### 11.3 결과가 예상과 다를 때

다음 항목을 확인한다.

| 현상 | 확인할 것 |
|---|---|
| 포함 Search Help가 보이지 않음 | Included Search Help 입력 여부, 활성화 여부 |
| 결과값이 반환되지 않음 | EXP Parameter, Parameter Assignment |
| 검색 조건이 비어 있음 | SPos 설정, IMP 설정 |
| 결과 리스트 컬럼이 부족함 | LPos 설정 |
| 데이터가 없음 | Selection Method 데이터 존재 여부 |
| 엉뚱한 값이 반환됨 | Collective Parameter와 Included Parameter 매핑 오류 |

## 12. Parameter Assignment 상세 이해

Collective Search Help에서 초급자가 가장 많이 실수하는 부분은 Parameter Assignment이다.

### 12.1 왜 매핑이 필요한가?

Collective Search Help는 내부의 여러 Elementary Search Help를 호출한다.  
각 Elementary Search Help는 자기 Parameter를 가지고 있다.  
Collective Search Help 역시 외부와 연결되는 대표 Parameter를 가진다.

따라서 시스템은 다음을 알아야 한다.

```text
Collective의 CARRID는 Included Search Help의 어떤 Parameter와 연결되는가?
Collective의 CARRNAME은 Included Search Help의 어떤 Parameter와 연결되는가?
Included Search Help에서 선택된 값은 Collective의 어떤 Parameter로 돌아와야 하는가?
```

이 연결이 Parameter Assignment이다.

### 12.2 매핑 예시

```text
Collective Search Help: ZSH_JHY_CARR
Included Search Help: ZSH_JHY_CARR_BY_NAME

Assignment:
  ZSH_JHY_CARR-CARRID   = ZSH_JHY_CARR_BY_NAME-CARRID
  ZSH_JHY_CARR-CARRNAME = ZSH_JHY_CARR_BY_NAME-CARRNAME
  ZSH_JHY_CARR-CURRCODE = ZSH_JHY_CARR_BY_NAME-CURRCODE
```

### 12.3 매핑을 잘못하면 생기는 문제

| 잘못된 매핑 | 결과 |
|---|---|
| CARRID를 CARRNAME에 매핑 | 이름이 코드 필드로 반환될 수 있다. |
| EXP Parameter가 매핑되지 않음 | 값을 선택해도 입력 필드에 반환되지 않을 수 있다. |
| 일부 Included Search Help만 매핑 | 검색 방법에 따라 동작이 다르게 보일 수 있다. |
| 타입이 다른 필드끼리 매핑 | 활성화 오류 또는 런타임 동작 오류 가능성이 있다. |

## 13. Data Element에 Collective Search Help 연결

Collective Search Help는 단독으로 테스트할 수 있지만, 실제 사용자는 보통 필드에서 F4를 눌러 Search Help를 호출한다.

대표적인 연결 위치는 다음과 같다.

| 연결 위치 | 설명 |
|---|---|
| Data Element | 해당 Data Element를 사용하는 필드에 Search Help 제공 |
| Table Field | 특정 테이블 필드에 직접 연결 |
| Screen Field | 화면 필드에 연결 또는 프로그램에서 제어 |
| PARAMETERS | Data Element 타입을 통해 F4 Help 연결 가능 |

초급 학습에서는 Data Element에 연결하는 흐름을 우선 이해하는 것이 좋다.

```text
Domain
 → Data Element
 → Data Element에 Search Help 연결
 → Table Field 또는 PARAMETERS가 Data Element 사용
 → F4 Help 제공
```

다음 모듈 `THEORY-04-M05`에서는 이 연결을 `PARAMETERS`와 함께 더 구체적으로 다룬다.

## 14. PARAMETERS와의 연결 예고

다음 모듈에서는 다음과 같은 프로그램 흐름을 다룬다.

```abap
REPORT zjhy_demo_f4_collective.

PARAMETERS p_carrid TYPE zde_jhy_carrid.

START-OF-SELECTION.
  WRITE: / 'Carrier ID:', p_carrid.
```

여기서 `ZDE_JHY_CARRID` Data Element에 `ZSH_JHY_CARR` Collective Search Help가 연결되어 있으면, 사용자는 `P_CARRID`에서 F4를 눌러 여러 검색 방법 중 하나를 사용할 수 있다.

이번 모듈에서는 프로그램 구현을 깊게 다루지 않는다.  
핵심은 다음이다.

```text
Collective Search Help는 최종적으로 Data Element나 필드에 연결되어 사용자 입력을 보조한다.
```

## 15. 정상 흐름과 오류 흐름

### 15.1 정상 흐름

```text
1. Elementary Search Help 생성 및 활성화
2. Collective Search Help 생성
3. 대표 Parameter 정의
4. Included Search Help 추가
5. Parameter Assignment 설정
6. Collective Search Help 저장 및 활성화
7. SE11 테스트
8. Data Element 또는 필드 연결
9. 실제 F4 Help 확인
```

### 15.2 오류 흐름 1: 포함 Search Help 미활성화

| 항목 | 내용 |
|---|---|
| 현상 | Collective Search Help 활성화 또는 테스트 시 오류 발생 |
| 원인 | 포함한 Elementary Search Help가 비활성 상태 |
| 해결 | Elementary Search Help를 먼저 활성화한 뒤 Collective Search Help를 다시 활성화한다. |

### 15.3 오류 흐름 2: 대표 Parameter 누락

| 항목 | 내용 |
|---|---|
| 현상 | 결과값이 외부 필드로 반환되지 않음 |
| 원인 | Collective Search Help에 반환용 대표 Parameter가 없음 |
| 해결 | `CARRID` 같은 반환 Parameter를 정의하고 EXP를 설정한다. |

### 15.4 오류 흐름 3: Parameter Assignment 누락

| 항목 | 내용 |
|---|---|
| 현상 | 특정 검색 방법을 선택했을 때 값이 반환되지 않음 |
| 원인 | Included Search Help Parameter와 Collective Parameter가 매핑되지 않음 |
| 해결 | 각 Included Search Help별 Parameter Assignment를 점검한다. |

### 15.5 오류 흐름 4: IMP와 EXP 의미 혼동

| 항목 | 내용 |
|---|---|
| 현상 | 검색 조건 또는 반환값이 기대와 다름 |
| 원인 | IMP는 입력값 전달, EXP는 결과값 반환이라는 역할을 혼동함 |
| 해결 | 최종 입력 필드에 돌아가야 하는 값에 EXP를 설정한다. |

### 15.6 오류 흐름 5: 검색 경로가 너무 많음

| 항목 | 내용 |
|---|---|
| 현상 | F4 Help 화면이 복잡하고 사용자가 어떤 검색 방법을 골라야 할지 모름 |
| 원인 | 유사하거나 중복된 Elementary Search Help를 과도하게 포함함 |
| 해결 | 실제 사용 빈도가 높은 검색 경로만 남긴다. |

### 15.7 오류 흐름 6: 데이터 검증으로 오해

| 항목 | 내용 |
|---|---|
| 현상 | F4 Help에는 값이 보이지만 잘못된 값 직접 입력이 막히지 않음 |
| 원인 | Search Help를 검증 객체로 오해함 |
| 해결 | 값 검증은 Foreign Key, Check Table, 프로그램 검증, 도메인 Fixed Value 등과 구분한다. |

## 16. 실무 설계 기준

### 16.1 Collective Search Help 설계 전 질문

Collective Search Help를 만들기 전에 다음을 확인한다.

```text
검색 방법이 실제로 둘 이상 필요한가?
각 검색 방법이 같은 최종 값을 반환하는가?
사용자에게 검색 방법을 선택하게 하는 것이 편리한가?
기존 표준 Search Help를 재사용할 수 있는가?
검색 대상 데이터의 권한과 성능 이슈는 없는가?
검색 방법이 중복되거나 과도하게 세분화되어 있지는 않은가?
```

### 16.2 좋은 설계

좋은 Collective Search Help는 다음 특징을 가진다.

| 특징 | 설명 |
|---|---|
| 목적이 명확함 | 하나의 대표 필드값을 찾기 위한 검색 경로를 제공한다. |
| 검색 방법이 구분됨 | 코드 기준, 이름 기준, 조직 기준 등 차이가 분명하다. |
| 반환값이 일관됨 | 어떤 검색 방법을 쓰든 최종 반환값이 같다. |
| Parameter 매핑이 명확함 | 대표 Parameter와 Included Parameter가 올바르게 연결된다. |
| 사용자 화면이 단순함 | 불필요한 검색 방법이 없다. |

### 16.3 나쁜 설계

| 나쁜 설계 | 문제 |
|---|---|
| 검색 방법이 하나인데 Collective 생성 | Elementary Search Help로 충분하다. |
| 거의 같은 Search Help를 여러 개 포함 | 사용자 혼란과 유지보수 증가 |
| 서로 다른 의미의 결과값을 반환 | 입력 필드에 잘못된 값이 들어갈 수 있다. |
| Parameter 이름만 보고 대충 매핑 | 타입/의미 불일치 가능 |
| 대량 테이블을 조건 없이 검색 | 성능 문제와 사용자 불편 발생 |

## 17. 성능 관점 주의사항

Search Help는 사용자 편의를 위한 기능이지만, 내부적으로는 테이블이나 View를 조회한다.  
따라서 Collective Search Help에 포함된 각 Elementary Search Help의 성능도 중요하다.

### 17.1 성능 문제를 만들 수 있는 설계

```text
대량 테이블을 Selection Method로 사용한다.
검색 조건이 거의 없다.
LPos에 많은 필드를 표시한다.
권한/조직 조건 없이 전체 데이터를 보여준다.
중복되는 Included Search Help가 많다.
```

### 17.2 권장 설계

| 기준 | 설명 |
|---|---|
| 적절한 Selection Method | 가능하면 검색 목적에 맞는 테이블 또는 View 사용 |
| 필요한 필드만 표시 | 결과 리스트가 불필요하게 넓어지지 않도록 조정 |
| 검색 조건 제공 | 사용자가 값을 좁힐 수 있도록 SPos 설정 |
| 포함 Search Help 최소화 | 실제 필요한 검색 방법만 포함 |
| 표준 객체 재사용 | 가능하면 SAP 표준 Search Help 또는 표준 View를 검토 |

> [추정] 교육 시스템에서는 데이터량이 적어 성능 문제가 잘 보이지 않을 수 있다. 그러나 운영 시스템에서는 Search Help 하나도 사용 빈도가 높으면 성능 이슈가 될 수 있다.

## 18. 권한과 운영 관점

Search Help는 단순히 값을 보여주는 기능처럼 보이지만, 실제로는 사용자에게 데이터 목록을 노출한다.  
따라서 운영 관점에서는 다음을 고려해야 한다.

| 관점 | 설명 |
|---|---|
| 데이터 노출 | F4 Help 결과에 보여도 되는 데이터인지 검토한다. |
| 권한 | 사용자 권한에 따라 조회 가능 범위가 달라야 할 수 있다. |
| 조직 범위 | 회사코드, 플랜트, 영업조직 등 조건이 필요할 수 있다. |
| 유지보수 | 포함 Search Help 변경 시 영향 범위를 확인해야 한다. |
| 표준 변경 영향 | 표준 Search Help를 포함하거나 참조할 경우 업그레이드 영향을 고려한다. |

초급 단계에서는 모든 권한 로직을 구현하지 않는다.  
하지만 실무에서는 “F4 Help에 보이는 데이터도 업무 데이터 노출”이라는 관점을 가져야 한다.

## 21. 초급자 오해 정리

### 21.1 “Collective Search Help는 Search Help를 자동으로 만들어준다”

아니다.  
Collective Search Help는 기존 Elementary Search Help를 묶는 객체이다.  
검색 로직이 되는 Elementary Search Help는 별도로 만들어야 한다.

### 21.2 “Collective Search Help에는 Selection Method를 직접 넣는다”

일반적으로 Collective Search Help는 직접 Selection Method를 지정하는 것이 핵심이 아니다.  
Selection Method는 포함된 Elementary Search Help에서 정의된다.

### 21.3 “포함만 하면 Parameter 매핑은 자동으로 완벽하게 된다”

아니다.  
시스템이 일부 제안을 할 수는 있어도, 개발자는 대표 Parameter와 Included Parameter가 의미적으로 맞게 연결되었는지 검토해야 한다.

### 21.4 “Search Help는 값 검증까지 책임진다”

아니다.  
Search Help는 입력 후보를 제공하는 기능이다.  
직접 입력한 값의 검증은 Foreign Key, Domain Fixed Value, 프로그램 검증 등과 구분해야 한다.

### 21.5 “검색 방법은 많을수록 좋다”

아니다.  
검색 방법이 너무 많으면 사용자가 더 혼란스러워진다.  
실제 사용 빈도가 높고 서로 구분되는 검색 방법만 포함하는 것이 좋다.

## 22. 강사용 설명 포인트

```text
1. Elementary Search Help는 하나의 검색 방법이다.

3. 이때 여러 Elementary Search Help를 묶는 객체가 Collective Search Help이다.
4. 포함만 중요한 것이 아니라 Parameter Assignment가 핵심이다.
```

## 24. 평가 문제

### 24.1 객관식

#### Q1. Collective Search Help의 가장 적절한 설명은?

A. 하나의 테이블에 데이터를 저장하는 객체이다.  
B. 여러 Elementary Search Help를 하나로 묶어 제공하는 Search Help이다.  
C. Foreign Key를 자동으로 생성하는 기능이다.  
D. ABAP 프로그램에서 MESSAGE를 출력하는 기능이다.

**정답:** B

#### Q2. Collective Search Help에서 Parameter Assignment가 필요한 이유는?

A. ABAP 프로그램을 자동 생성하기 위해서  
B. Included Search Help와 Collective Search Help의 Parameter를 연결하기 위해서  
C. DB 테이블의 Primary Key를 변경하기 위해서  
D. Domain Fixed Value를 자동 입력하기 위해서

**정답:** B

#### Q3. 검색 방법이 하나뿐인 경우 일반적으로 가장 적절한 선택은?

A. Collective Search Help  
B. Elementary Search Help  
C. Lock Object  
D. Maintenance View

**정답:** B

#### Q4. Search Help에 대한 설명으로 올바른 것은?

A. Search Help는 항상 값 검증까지 보장한다.  
B. Search Help는 입력 후보를 제공하는 기능이며 검증과는 구분해야 한다.  
C. Collective Search Help는 Selection Method만 지정하면 완성된다.  
D. EXP Parameter는 검색 조건 화면 위치를 의미한다.

**정답:** B

### 24.2 서술형

#### Q1. Elementary Search Help와 Collective Search Help의 차이를 설명하시오.

**모범 답안:**  
Elementary Search Help는 하나의 Selection Method와 Parameter를 기준으로 하나의 검색 방법을 정의한다. Collective Search Help는 여러 Elementary Search Help를 포함하여 사용자가 여러 검색 방법 중 하나를 선택할 수 있게 하는 상위 Search Help이다.

#### Q2. Collective Search Help에서 최종 반환값이 일관되어야 하는 이유를 설명하시오.

**모범 답안:**  
Collective Search Help는 여러 검색 방법을 제공하지만 최종적으로는 하나의 입력 필드에 값을 반환한다. 검색 방법에 따라 서로 다른 의미의 값이 반환되면 입력 필드에 잘못된 값이 들어갈 수 있으므로, 모든 Included Search Help는 같은 의미의 대표 Export Parameter로 값을 반환해야 한다.

#### Q3. F4 Help에서 값을 선택했는데 입력 필드에 값이 들어오지 않을 때 확인할 항목을 설명하시오.

**모범 답안:**  
대표 Export Parameter가 정의되어 있는지, Included Search Help의 Export Parameter가 올바르게 설정되어 있는지, Collective Parameter와 Included Parameter의 Assignment가 누락되거나 잘못되지 않았는지 확인한다. 또한 해당 Search Help와 연결된 Data Element 또는 Field 설정도 확인해야 한다.

## 26. 핵심 요약

이번 모듈의 핵심은 다음이다.

```text
Collective Search Help는 여러 Elementary Search Help를 하나로 묶는 DDIC Search Help이다.
Elementary Search Help는 실제 검색 방법이고, Collective Search Help는 검색 방법의 묶음이다.
Collective Search Help의 핵심은 Included Search Help와 Parameter Assignment이다.
어떤 검색 방법을 사용하더라도 최종 반환값은 일관되어야 한다.
Search Help는 입력 후보를 제공하는 기능이며 데이터 검증과는 구분해야 한다.
검색 방법은 많을수록 좋은 것이 아니라 사용자가 이해할 수 있을 만큼 명확해야 한다.
```
