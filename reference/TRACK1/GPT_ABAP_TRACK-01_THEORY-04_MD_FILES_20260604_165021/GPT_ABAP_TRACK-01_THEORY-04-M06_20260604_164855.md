## 3. 검증이라는 말의 두 가지 의미

SAP 개발에서 “검증”이라는 말은 매우 넓게 사용된다. 초급자가 혼동하지 않기 위해서는 크게 두 가지로 나누어 이해해야 한다.

| 구분 | 설명 | 예시 |
|---|---|---|
| DDIC 검증 | 데이터 모델에 정의된 공통 규칙 기반 검증 | Foreign Key, Check Table, Domain Fixed Value |
| 프로그램 검증 | 특정 프로그램 실행 흐름에서 수행하는 조건 검증 | `AT SELECTION-SCREEN`, `IF`, `MESSAGE` |

두 검증은 모두 중요하지만 목적이 다르다.

### 3.1 DDIC 검증의 성격

DDIC 검증은 데이터 모델 중심이다. 즉, 이 필드는 어떤 테이블의 어떤 값만 허용해야 하는지, 어떤 후보값을 제시할 수 있는지 같은 **구조적·공통적 규칙**을 정의한다.

예를 들어 항공사 코드 `CARRID`가 `SCARR-CARRID`에 존재해야 한다는 규칙은 여러 프로그램에서 공통으로 적용될 수 있다. 이런 규칙은 특정 프로그램 안에 하드코딩하기보다 DDIC 관계로 표현하는 것이 더 적절하다.

### 3.2 프로그램 검증의 성격

프로그램 검증은 실행 상황 중심이다. 같은 항공사 코드라도 어떤 프로그램에서는 모든 항공사를 허용하고, 다른 프로그램에서는 현재 사용자의 권한이 있는 항공사만 허용할 수 있다.

또한 특정 기간, 특정 상태, 특정 업무 단계에 따라 입력 허용 여부가 달라질 수 있다. 이런 규칙은 DDIC만으로 표현하기 어렵고, 프로그램 로직에서 처리하는 것이 적합하다.

## 4. DDIC 검증이 담당하는 영역

DDIC 검증은 다음처럼 데이터 구조에 가까운 영역을 담당한다.

| 검증 영역 | DDIC 객체 또는 설정 | 설명 |
|---|---|---|
| 값 존재 여부 | Foreign Key / Check Table | 입력값이 기준 테이블에 존재하는지 확인하는 기반 |
| 코드값 제한 | Domain Fixed Value | 값이 정해진 목록 안에 있는지 제한 |
| 입력 후보 제공 | Search Help | 사용자가 F4로 후보값을 찾을 수 있도록 지원 |
| 필드 의미 제공 | Data Element | 라벨, 문서화, 의미 일관성 제공 |
| 기술 타입 제한 | Domain | 타입, 길이, 소수점, 대소문자 처리 등 기술 속성 정의 |

### 4.1 Domain Fixed Value

Domain Fixed Value는 값의 종류가 작고 자주 변하지 않는 경우에 적합하다.

예를 들어 상태 코드가 `A`, `I`, `B` 세 가지라면 Domain에서 Fixed Value로 관리할 수 있다.

| Fixed Value | 의미 |
|---|---|
| A | Active |
| I | Inactive |
| B | Blocked |

이런 값은 여러 프로그램에서 동일하게 사용될 가능성이 높으므로 DDIC에 두는 것이 좋다.

### 4.2 Foreign Key와 Check Table

Foreign Key는 한 테이블 필드가 다른 테이블의 Key 또는 후보값과 관계를 가진다는 것을 DDIC에 정의하는 방식이다.

예를 들어 주문 테이블에 `CARRID` 필드가 있고, 이 값은 항공사 마스터 테이블 `SCARR`에 존재해야 한다고 가정할 수 있다.

```text
주문 테이블 ZT_JHY_BOOKING-CARRID
→ Check Table SCARR-CARRID
```

이 관계는 단순 F4 Help 이상의 의미를 가진다. 데이터 모델 차원에서 “이 필드는 이 기준 테이블과 관계가 있다”는 의미를 표현한다.

### 4.3 Search Help

Search Help는 사용자가 값을 찾을 수 있도록 후보값 검색 기능을 제공한다. Search Help는 검증 자체라기보다는 **입력 지원**의 성격이 강하다.

초급자가 자주 하는 오해는 다음이다.

```text
F4 Help가 있으면 잘못된 값은 절대 입력할 수 없다.
```

이것은 정확하지 않다. F4 Help는 값을 선택하도록 돕지만, 사용자가 직접 입력하거나 프로그램이 값을 넣는 경우까지 모두 막는 절대 검증은 아니다. 따라서 필요한 경우 Foreign Key, Domain Fixed Value, 프로그램 검증을 함께 고려해야 한다.

## 5. 프로그램 검증이 담당하는 영역

프로그램 검증은 특정 실행 흐름이나 업무 조건을 처리한다.

| 검증 영역 | ABAP 구현 위치 | 설명 |
|---|---|---|
| 필수 입력 조건 | `PARAMETERS ... OBLIGATORY`, `AT SELECTION-SCREEN` | 화면 입력 단계에서 필수값 확인 |
| 동적 업무 조건 | `IF`, `CASE`, Custom Logic | 현재 날짜, 권한, 상태 등에 따라 판단 |
| 사용자 메시지 | `MESSAGE` | 오류, 경고, 정보 메시지 제공 |
| 복합 조건 검증 | `AT SELECTION-SCREEN`, `START-OF-SELECTION` | 여러 필드 간 조합 검증 |
| DB 존재 여부 확인 | `SELECT SINGLE`, `SELECT ... UP TO 1 ROWS` | DDIC 관계만으로 부족할 때 직접 확인 |

### 5.1 `MESSAGE`의 역할

`MESSAGE`는 사용자에게 오류, 경고, 정보, 성공 메시지를 전달하는 ABAP 문장이다.

예시:

```abap
MESSAGE '항공사 코드를 입력하세요.' TYPE 'E'.
```

초급 단계에서는 메시지 타입을 다음 수준으로 이해하면 된다.

| Type | 의미 | 일반적 효과 |
|---|---|---|
| S | Success | 성공 메시지 |
| I | Information | 정보 팝업 또는 정보성 메시지 |
| W | Warning | 경고 메시지 |
| E | Error | 오류 메시지, 입력 처리 중단 가능 |
| A | Abort | 비정상 종료 성격, 초급 실습에서는 사용 지양 |
| X | Exit/Short Dump | 런타임 오류 유발, 일반 업무 검증에는 사용하지 않음 |

실무에서는 Message Class를 만들어 `MESSAGE e001(zmsg)`와 같이 관리하는 방식이 일반적이다. 하지만 초급 실습에서는 문자열 메시지로 먼저 흐름을 이해해도 된다.

### 5.2 `AT SELECTION-SCREEN` 검증

Selection Screen에서 입력값을 검증할 때 대표적으로 사용하는 이벤트가 `AT SELECTION-SCREEN`이다.

예시:

```abap
REPORT zjhy_validate_screen.

PARAMETERS p_carrid TYPE s_carr_id.

AT SELECTION-SCREEN.
  IF p_carrid IS INITIAL.
    MESSAGE '항공사 코드를 입력하세요.' TYPE 'E'.
  ENDIF.

START-OF-SELECTION.
  WRITE: / 'Carrier:', p_carrid.
```

이 검증은 프로그램 실행 전에 Selection Screen 단계에서 수행된다. 사용자가 잘못된 값을 입력하면 실행 단계로 넘어가기 전에 오류 메시지를 보여줄 수 있다.

## 6. DDIC 검증과 프로그램 검증의 핵심 차이

두 검증을 비교하면 다음과 같다.

| 구분 | DDIC 검증 | 프로그램 검증 |
|---|---|---|
| 위치 | ABAP Dictionary | ABAP Program |
| 기준 | 데이터 모델 | 실행 흐름과 업무 조건 |
| 재사용성 | 높음 | 프로그램별 차이 큼 |
| 예시 | Foreign Key, Check Table, Fixed Value | `IF`, `MESSAGE`, `AT SELECTION-SCREEN` |
| 변경 영향 | 여러 객체에 공통 영향 | 해당 프로그램 중심 영향 |
| 적합한 규칙 | 공통적이고 안정적인 규칙 | 동적이고 상황 의존적인 규칙 |

### 6.1 DDIC에 두어야 하는 검증

다음과 같은 검증은 가능하면 DDIC에 두는 것이 좋다.

```text
값의 후보가 표준 또는 공통 기준 테이블에 존재해야 한다.
값의 종류가 고정되어 있고 여러 프로그램에서 동일하게 쓰인다.
필드의 업무 의미와 기술 속성이 여러 객체에서 재사용된다.
입력 도움말이 여러 화면이나 프로그램에서 공통으로 필요하다.
```

예시:

| 규칙 | 적합한 위치 |
|---|---|
| 항공사 코드는 SCARR에 존재해야 한다 | DDIC Foreign Key / Search Help |
| 상태값은 A/I/B 중 하나이다 | Domain Fixed Value 또는 코드 테이블 |
| 고객 번호는 고객 마스터에서 선택한다 | DDIC 관계 또는 Search Help |

### 6.2 프로그램에 두어야 하는 검증

다음과 같은 검증은 프로그램에서 처리하는 것이 적합하다.

```text
오늘 날짜 이후만 허용한다.
입력 기간의 From 값이 To 값보다 작아야 한다.
로그인 사용자의 권한에 따라 허용값이 달라진다.
특정 업무 상태에서는 변경을 막아야 한다.
두 개 이상의 입력 필드 조합을 확인해야 한다.
```

예시:

| 규칙 | 적합한 위치 |
|---|---|
| 조회 시작일은 종료일보다 작거나 같아야 한다 | Program Validation |
| 상태가 Closed인 문서는 변경할 수 없다 | Program Validation |
| 특정 사용자 그룹만 특정 회사코드를 조회할 수 있다 | Authorization + Program Validation |
| 오늘 이전 날짜는 입력할 수 없다 | Program Validation |

## 7. 예제 시나리오: 항공사 코드 검증

교육용 항공 모델을 기준으로 `CARRID`를 입력받는 프로그램을 생각해보자.

### 7.1 Built-in Type만 사용한 나쁜 예

```abap
REPORT zjhy_bad_validation.

PARAMETERS p_carrid TYPE c LENGTH 3.

AT SELECTION-SCREEN.
  IF p_carrid <> 'AA' AND p_carrid <> 'LH'.
    MESSAGE '허용되지 않는 항공사입니다.' TYPE 'E'.
  ENDIF.
```

이 코드는 초급 실습에서는 동작할 수 있지만 실무적으로 좋지 않다.

문제점은 다음과 같다.

| 문제 | 설명 |
|---|---|
| 하드코딩 | `AA`, `LH`가 프로그램에 직접 박혀 있다. |
| 확장성 부족 | 항공사가 추가될 때마다 프로그램을 수정해야 한다. |
| DDIC 의미 부재 | `P_CARRID`가 항공사 코드라는 의미가 약하다. |
| 공통 규칙 분산 | 다른 프로그램에서도 같은 검증을 반복해야 한다. |

### 7.2 DDIC 타입을 사용한 개선 예

```abap
REPORT zjhy_ddic_validation.

PARAMETERS p_carrid TYPE s_carr_id.

AT SELECTION-SCREEN.
  IF p_carrid IS INITIAL.
    MESSAGE '항공사 코드를 입력하세요.' TYPE 'E'.
  ENDIF.

START-OF-SELECTION.
  WRITE: / 'Carrier:', p_carrid.
```

여기서는 항공사 코드의 기술적 속성과 의미를 DDIC Data Element에 맡긴다. F4 Help나 Field Label도 DDIC 설정을 통해 연결될 수 있다.

단, 이 예제만으로 실제 존재 여부 검증이 반드시 완료된다고 단정하면 안 된다. 실제 검증 방식은 해당 Data Element, Table Field, Search Help, Foreign Key 연결, Selection Screen 선언 방식에 따라 달라질 수 있다.

### 7.3 프로그램에서 DB 존재 여부를 보강하는 예

특정 프로그램에서 반드시 항공사 마스터 존재 여부를 직접 확인해야 한다면 다음처럼 보강할 수 있다.

```abap
REPORT zjhy_check_carrier.

PARAMETERS p_carrid TYPE s_carr_id OBLIGATORY.

AT SELECTION-SCREEN.
  SELECT SINGLE carrid
    FROM scarr
    WHERE carrid = @p_carrid
    INTO @DATA(lv_carrid).

  IF sy-subrc <> 0.
    MESSAGE '존재하지 않는 항공사 코드입니다.' TYPE 'E'.
  ENDIF.

START-OF-SELECTION.
  WRITE: / 'Carrier:', p_carrid.
```

이 방식은 명확하지만, 모든 프로그램마다 반복하면 중복이 생긴다. 따라서 공통 검증은 DDIC 관계와 재사용 가능한 로직으로 정리하고, 프로그램에서는 해당 화면에 필요한 동적 조건만 추가하는 것이 좋다.

## 8. 예제 시나리오: 날짜 범위 검증

날짜 범위는 DDIC보다 프로그램 검증이 적합한 대표 사례이다.

```abap
REPORT zjhy_date_range_check.

PARAMETERS: p_from TYPE d OBLIGATORY,
            p_to   TYPE d OBLIGATORY.

AT SELECTION-SCREEN.
  IF p_from > p_to.
    MESSAGE '시작일은 종료일보다 클 수 없습니다.' TYPE 'E'.
  ENDIF.

START-OF-SELECTION.
  WRITE: / 'From:', p_from,
         / 'To  :', p_to.
```

이 검증은 특정 화면의 두 입력값 조합에 대한 규칙이다. `DATS` 타입 자체는 날짜 형식을 의미하지만, “시작일이 종료일보다 작거나 같아야 한다”는 규칙은 특정 프로그램의 업무 흐름에서 판단하는 것이 적합하다.

즉, 다음처럼 역할을 나눌 수 있다.

| 검증 | 위치 |
|---|---|
| 날짜 형식 | DDIC / ABAP 타입 |
| From <= To 관계 | Program Validation |

## 9. 예제 시나리오: 상태값 검증

상태값은 DDIC 검증과 프로그램 검증이 함께 쓰이는 좋은 예이다.

상태 Domain이 다음 Fixed Value를 가진다고 가정하자.

| 값 | 의미 |
|---|---|
| A | Active |
| I | Inactive |
| B | Blocked |

DDIC는 “상태값은 A/I/B 중 하나”라는 공통 규칙을 표현할 수 있다.

하지만 특정 프로그램에서는 다음과 같은 추가 규칙이 있을 수 있다.

```text
신규 등록 화면에서는 A 또는 I만 허용한다.
관리자 화면에서는 B도 허용한다.
일반 사용자는 Blocked 상태로 변경할 수 없다.
```

이런 규칙은 프로그램 검증 또는 권한 검증과 결합되어야 한다.

```abap
REPORT zjhy_status_check.

PARAMETERS p_stat TYPE zde_jhy_status OBLIGATORY.

AT SELECTION-SCREEN.
  IF p_stat = 'B' AND sy-uname <> 'ADMIN'.
    MESSAGE 'Blocked 상태는 관리자만 입력할 수 있습니다.' TYPE 'E'.
  ENDIF.

START-OF-SELECTION.
  WRITE: / 'Status:', p_stat.
```

[추정] 위 예제의 `sy-uname <> 'ADMIN'`은 교육용 단순화 예시이다. 실제 프로젝트에서는 사용자 ID 하드코딩이 아니라 권한 객체, Role, Authorization Check, 조직 권한 등을 기준으로 판단해야 한다.

## 10. F4 Help와 검증의 차이

F4 Help는 입력값을 고르는 데 도움을 주는 기능이다. 검증은 입력값이 업무적으로 허용되는지 판단하는 기능이다.

| 구분 | F4 Help | Validation |
|---|---|---|
| 목적 | 후보값 검색과 선택 지원 | 입력값의 허용 여부 판단 |
| 실행 시점 | 사용자가 F4를 누를 때 | 입력 후 또는 실행 전후 |
| 대표 구현 | Search Help, Foreign Key 기반 도움말 | DDIC Check, Program Logic, MESSAGE |
| 직접 입력 차단 여부 | 보장하지 않음 | 오류 처리 가능 |
| 사용자 경험 | 편의성 향상 | 데이터 품질 보장 |

초급자는 반드시 다음 문장을 기억해야 한다.

> F4 Help는 사용자를 돕는 기능이고, 검증은 데이터를 지키는 기능이다.

둘은 함께 설계해야 한다.

## 11. Selection Screen에서의 검증 위치

Classic ABAP Report에서 Selection Screen 입력 검증은 보통 다음 위치에서 다룬다.

| 위치 | 용도 |
|---|---|
| `PARAMETERS ... OBLIGATORY` | 단순 필수 입력 |
| `AT SELECTION-SCREEN ON p_field` | 특정 필드에 대한 검증 |
| `AT SELECTION-SCREEN` | 여러 필드 조합 검증 |
| `START-OF-SELECTION` | 실제 처리 시작 전후의 업무 검증 |

### 11.1 단일 필드 검증

```abap
PARAMETERS p_carrid TYPE s_carr_id.

AT SELECTION-SCREEN ON p_carrid.
  IF p_carrid IS INITIAL.
    MESSAGE '항공사 코드를 입력하세요.' TYPE 'E'.
  ENDIF.
```

이 방식은 특정 필드에 대한 검증을 명확히 분리할 수 있다.

### 11.2 여러 필드 조합 검증

```abap
PARAMETERS: p_from TYPE d,
            p_to   TYPE d.

AT SELECTION-SCREEN.
  IF p_from IS NOT INITIAL
     AND p_to IS NOT INITIAL
     AND p_from > p_to.
    MESSAGE '시작일은 종료일보다 클 수 없습니다.' TYPE 'E'.
  ENDIF.
```

두 개 이상의 입력 필드 관계를 확인할 때는 전체 Selection Screen 이벤트에서 검증하는 것이 자연스럽다.

## 12. 실무 설계 기준

### 12.1 DDIC로 우선 설계할 것

다음은 DDIC에 먼저 반영하는 것이 좋다.

| 대상 | 이유 |
|---|---|
| 공통 코드값 | 여러 프로그램에서 동일하게 사용되므로 Domain 또는 코드 테이블이 적합 |
| 기준 테이블 존재 여부 | Foreign Key/Check Table로 의미 관계 표현 가능 |
| 공통 F4 Help | Data Element/Search Help에 연결하면 여러 화면에서 재사용 가능 |
| 필드 라벨과 의미 | Data Element에서 관리하면 UI/ALV/Selection Screen에서 활용 가능 |

### 12.2 프로그램에서 처리할 것

다음은 프로그램에서 처리하는 것이 적합하다.

| 대상 | 이유 |
|---|---|
| 기간 From-To 관계 | 두 입력값의 조합 규칙이므로 프로그램 검증 |
| 사용자 권한별 허용값 | 실행 사용자와 권한에 따라 달라짐 |
| 문서 상태별 변경 가능 여부 | 업무 흐름과 상태 전이에 따라 달라짐 |
| 실시간 재고/잔액 확인 | 실행 시점의 동적 데이터 필요 |
| 외부 시스템 응답 기반 검증 | DDIC만으로 판단 불가 |

### 12.3 중복 검증은 피하되, 보완 검증은 허용한다

DDIC와 프로그램에 같은 검증이 중복되면 유지보수가 어려워진다. 하지만 보완 관계라면 함께 사용할 수 있다.

예를 들어:

```text
DDIC: 항공사 코드는 SCARR에 존재해야 한다.
Program: 현재 사용자에게 허용된 항공사만 조회 가능하다.
```

이 두 검증은 중복이 아니라 역할이 다르다.

반대로 다음은 좋지 않다.

```text
DDIC: 상태값은 A/I/B이다.
Program A: 상태값은 A/I/B이다.
Program B: 상태값은 A/I/B이다.
Program C: 상태값은 A/I/B이다.
```

이런 경우 상태값이 추가되면 여러 프로그램을 모두 수정해야 한다.

## 13. 안티패턴 정리

### 13.1 코드값 하드코딩 남발

```abap
IF p_status <> 'A' AND p_status <> 'I' AND p_status <> 'B'.
  MESSAGE 'Invalid status' TYPE 'E'.
ENDIF.
```

이 방식은 상태값이 변경될 때 프로그램 수정이 필요하다. 공통 상태값이라면 Domain Fixed Value 또는 코드 테이블을 검토해야 한다.

### 13.2 F4 Help만 믿고 검증하지 않음

F4 Help가 있어도 사용자가 직접 값을 입력하거나, 배치 프로그램·인터페이스·외부 호출이 값을 넣을 수 있다. 따라서 중요한 값은 적절한 검증이 필요하다.

### 13.3 프로그램마다 다른 기준 사용

프로그램 A는 `SCARR`를 기준으로 검증하고, 프로그램 B는 하드코딩 목록을 기준으로 검증하면 데이터 품질이 흔들린다. 공통 기준은 중앙화해야 한다.

### 13.4 모든 검증을 DDIC에 넣으려 함

DDIC는 공통적이고 안정적인 데이터 규칙에 적합하다. 실행 사용자, 날짜, 상태, 권한, 외부 시스템 응답처럼 동적인 조건은 프로그램 로직이 필요하다.

### 13.5 메시지를 너무 늦게 보여줌

입력 오류를 `START-OF-SELECTION` 이후 깊은 처리 단계에서 발견하면 사용자 경험이 나빠진다. Selection Screen에서 잡을 수 있는 오류는 가능한 한 입력 단계에서 안내하는 것이 좋다.

## 14. 실습 시나리오

### 14.1 실습 목표

항공사 코드와 날짜 범위를 입력받는 Selection Screen을 만들고, DDIC 검증과 프로그램 검증을 분리한다.

### 14.2 실습 요구사항

```text
1. 항공사 코드는 DDIC 타입을 사용한다.
2. 항공사 코드는 필수 입력이다.
3. 시작일과 종료일을 입력받는다.
4. 시작일이 종료일보다 크면 오류 메시지를 출력한다.
5. 항공사 코드 존재 여부는 필요 시 SCARR에서 확인한다.
6. F4 Help와 프로그램 검증의 역할을 주석으로 구분한다.
```

### 14.3 예제 코드

```abap
REPORT zjhy_ddic_program_check.

PARAMETERS: p_carrid TYPE s_carr_id OBLIGATORY,
            p_from   TYPE d         OBLIGATORY,
            p_to     TYPE d         OBLIGATORY.

AT SELECTION-SCREEN ON p_carrid.
  " Program validation: 존재 여부를 명시적으로 확인해야 하는 경우
  SELECT SINGLE carrid
    FROM scarr
    WHERE carrid = @p_carrid
    INTO @DATA(lv_carrid).

  IF sy-subrc <> 0.
    MESSAGE '존재하지 않는 항공사 코드입니다.' TYPE 'E'.
  ENDIF.

AT SELECTION-SCREEN.
  " Program validation: 여러 입력값의 조합 검증
  IF p_from > p_to.
    MESSAGE '시작일은 종료일보다 클 수 없습니다.' TYPE 'E'.
  ENDIF.

START-OF-SELECTION.
  WRITE: / 'Carrier:', p_carrid,
         / 'From   :', p_from,
         / 'To     :', p_to.
```

### 14.4 코드 해설

| 코드 영역 | 역할 |
|---|---|
| `PARAMETERS p_carrid TYPE s_carr_id` | DDIC 타입을 통해 필드 의미와 기술 속성 연결 |
| `OBLIGATORY` | 단순 필수 입력 검증 |
| `AT SELECTION-SCREEN ON p_carrid` | 항공사 코드 필드 단위 검증 |
| `SELECT SINGLE FROM scarr` | 기준 테이블 존재 여부 확인 |
| `AT SELECTION-SCREEN` | 날짜 From-To 조합 검증 |
| `MESSAGE ... TYPE 'E'` | 사용자에게 오류를 알리고 실행을 막음 |

## 16. 오류 상황과 해결

### 16.1 F4 Help는 보이지만 잘못된 직접 입력이 가능함

| 항목 | 내용 |
|---|---|
| 원인 | F4 Help는 후보 선택 지원이지 모든 직접 입력 차단 기능이 아님 |
| 해결 | 중요한 값은 Foreign Key, Domain Fixed Value, Program Validation을 함께 검토 |

### 16.2 `MESSAGE TYPE 'E'` 후 화면이 다시 돌아감

| 항목 | 내용 |
|---|---|
| 원인 | Selection Screen 검증 단계에서 오류 메시지가 발생했기 때문 |
| 정상 여부 | 정상 동작 |
| 확인 | 오류 메시지 후 해당 입력값 수정 가능 여부 확인 |

### 16.3 `SELECT SINGLE`에서 데이터가 없다고 나옴

| 항목 | 내용 |
|---|---|
| 가능 원인 | 입력값 오타, 현재 Client의 데이터 없음, 기준 테이블 데이터 미존재 |
| 해결 | SE16N에서 기준 테이블 확인, 입력값과 Client 확인 |

### 16.4 DDIC 타입이 없다는 Syntax Error

| 항목 | 내용 |
|---|---|
| 가능 원인 | Data Element 이름 오타 또는 시스템에 해당 객체 없음 |
| 해결 | SE11에서 Data Element 존재 여부 확인, 교육 시스템에 맞는 표준 필드로 대체 |

### 16.5 메시지가 너무 자주 발생함

| 항목 | 내용 |
|---|---|
| 가능 원인 | Selection Screen 이벤트에서 과도한 DB 조회 또는 불필요한 검증 수행 |
| 해결 | 필수 검증만 입력 단계에서 수행하고, 대량/복잡 검증은 실행 단계로 분리 검토 |

## 17. 강사용 설명 포인트

강의에서는 다음 순서로 설명하면 초급자가 이해하기 쉽다.

```text
1. F4 Help와 검증은 다르다.
2. DDIC는 공통 규칙을 담당한다.
3. 프로그램은 실행 상황의 동적 규칙을 담당한다.
4. MESSAGE는 사용자에게 즉시 피드백을 주는 수단이다.
5. 좋은 설계는 DDIC와 프로그램 검증을 중복시키지 않고 분리한다.
```

특히 다음 질문을 던지면 학습자의 사고가 확장된다.

```text

F4 Help가 있으면 MESSAGE 검증은 필요 없을까요?
프로그램마다 상태값 검증을 하드코딩하면 어떤 문제가 생길까요?
```

## 18. 평가 문제

### 18.1 객관식

#### Q1. DDIC 검증에 가장 적합한 것은?

A. 시작일이 종료일보다 작아야 한다.  
B. 로그인 사용자의 권한에 따라 입력값이 달라진다.  
C. 상태값은 A/I/B 중 하나이다.  
D. 현재 시간이 업무 마감 시간 이후인지 확인한다.

**정답:** C

#### Q2. 프로그램 검증에 가장 적합한 것은?

A. Domain의 Data Type 정의  
B. Data Element의 Field Label 정의  
C. Search Help의 Selection Method 설정  
D. From 날짜가 To 날짜보다 크지 않은지 확인

**정답:** D

#### Q3. F4 Help에 대한 설명으로 가장 적절한 것은?

A. F4 Help가 있으면 모든 직접 입력 오류가 자동으로 막힌다.  
B. F4 Help는 입력 후보를 찾고 선택하도록 돕는 기능이다.  
C. F4 Help는 항상 ABAP 프로그램에서만 구현해야 한다.  
D. F4 Help는 `MESSAGE`와 같은 기능이다.

**정답:** B

### 18.2 서술형

#### Q1. DDIC 검증과 프로그램 검증의 차이를 설명하시오.

**모범 답안:**  
DDIC 검증은 데이터 모델에 정의되는 공통 규칙으로, Domain Fixed Value, Foreign Key, Check Table, Search Help와 연결된다. 프로그램 검증은 특정 프로그램의 실행 조건에 따라 수행되는 동적 검증으로, Selection Screen 이벤트, IF 조건, MESSAGE 등을 통해 구현한다.

#### Q2. 날짜 From-To 검증을 DDIC가 아니라 프로그램에서 처리하는 이유는 무엇인가?

**모범 답안:**  
날짜 타입 자체는 DDIC에서 정의할 수 있지만, 시작일과 종료일의 관계는 특정 프로그램의 입력값 조합에 따른 업무 규칙이다. 따라서 두 필드 간 관계를 판단하는 검증은 프로그램에서 처리하는 것이 적절하다.

#### Q3. F4 Help와 검증을 혼동하면 어떤 문제가 생기는가?

**모범 답안:**  
F4 Help는 사용자가 값을 쉽게 선택하도록 돕는 기능일 뿐, 모든 잘못된 직접 입력이나 외부 입력을 막는 검증은 아니다. F4 Help만 믿고 검증을 생략하면 잘못된 값이 프로그램이나 데이터베이스로 들어갈 수 있다.

## 20. 핵심 요약

```text
DDIC 검증은 데이터 모델의 공통 규칙을 담당한다.
프로그램 검증은 실행 상황과 업무 조건에 따른 동적 규칙을 담당한다.
F4 Help는 입력 후보를 찾는 기능이고, 검증은 입력값을 판단하는 기능이다.
MESSAGE는 사용자에게 오류, 경고, 정보, 성공 메시지를 전달하는 수단이다.
AT SELECTION-SCREEN은 Selection Screen 입력 검증의 대표 이벤트이다.
좋은 설계는 DDIC와 프로그램 검증을 중복시키지 않고 역할을 분리한다.
```

## 21. THEORY-04 전체 마무리

이번 모듈을 끝으로 `THEORY-04 — DDIC 2차: 관계와 입력 도움말` Section이 완료된다.

이 Section에서 학습한 흐름은 다음과 같다.

```text
Foreign Key와 Check Table로 데이터 관계를 이해한다.
Value Table과 Foreign Key를 구분한다.
Elementary Search Help로 기본 F4 Help를 설계한다.
Collective Search Help로 여러 검색 경로를 묶는다.
PARAMETERS와 DDIC F4 Help를 연결한다.
DDIC 검증과 프로그램 검증의 역할을 분리한다.
```

후속 Section에서는 Classic View와 Maintenance View 등 DDIC의 추가 객체와 유지보수 흐름으로 확장된다. 특히 DDIC 관계와 입력 도움말을 이해한 상태에서 View와 Table Maintenance를 학습하면, 단순 조회 객체가 아니라 **업무 데이터 관리 흐름** 관점에서 DDIC를 바라볼 수 있다.
