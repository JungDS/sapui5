## 3. Search Help란 무엇인가?

### 3.1 쉬운 정의

Search Help는 사용자가 입력 필드에서 가능한 값을 쉽게 찾을 수 있도록 도와주는 ABAP Dictionary 객체이다.

SAP GUI에서 입력 필드 옆에 있는 작은 버튼을 누르거나 키보드의 `F4`를 누르면 가능한 값 목록이 나타나는 경우가 많다. 이 입력 도움말을 SAP에서는 흔히 `F4 Help`, `Input Help`, `Search Help`라는 말로 설명한다.

초급자 관점에서는 다음처럼 이해하면 된다.

```text
Search Help = 입력 가능한 후보 값을 찾고 선택할 수 있게 해주는 DDIC 객체
F4 Help = 사용자가 화면에서 경험하는 입력 도움말 동작
```

Search Help는 사용자가 값을 직접 외워서 입력하지 않아도 되게 만든다.  
예를 들어 항공사 코드를 입력해야 하는 필드가 있다고 하자.

| CARRID | CARRNAME |
|---|---|
| AA | American Airlines |
| LH | Lufthansa |
| SQ | Singapore Airlines |

사용자가 `AA`, `LH`, `SQ` 같은 코드를 모두 외우기는 어렵다.  
이때 F4 Help를 제공하면 사용자는 항공사명이나 코드 목록을 보고 값을 선택할 수 있다.

### 3.2 Search Help의 역할

Search Help의 역할은 다음과 같다.

| 역할 | 설명 |
|---|---|
| 후보 값 제공 | 입력 가능한 값을 목록으로 보여준다. |
| 검색 조건 제공 | 사용자가 후보 값을 좁혀 찾을 수 있게 한다. |
| 선택값 반환 | 선택한 값을 입력 필드로 돌려준다. |
| 사용자 편의성 향상 | 코드값을 외우지 않아도 되게 한다. |
| 입력 오류 감소 | 잘못된 값을 직접 입력할 가능성을 줄인다. |

단, 중요한 점이 있다.

```text
Search Help는 입력 편의 기능이지, 그 자체로 데이터 무결성을 보장하는 검증 로직은 아니다.
```

데이터 검증은 Foreign Key, Domain Fixed Value, Application Logic, Selection Screen Validation 등과 함께 판단해야 한다.

## 4. F4 Help와 Search Help의 관계

### 4.1 F4 Help는 사용자가 보는 동작

사용자 입장에서 보이는 것은 F4 Help이다.

```text
입력 필드에 커서를 둔다.
→ F4 키를 누른다.
→ 후보 값 목록이 뜬다.
→ 값을 선택한다.
→ 선택한 값이 입력 필드에 들어간다.
```

### 4.2 Search Help는 그 동작을 정의하는 DDIC 객체

개발자 입장에서는 Search Help가 중요하다.

```text
어떤 테이블에서 후보 값을 가져올 것인가?
어떤 필드를 검색 조건으로 사용할 것인가?
어떤 필드를 결과 리스트에 보여줄 것인가?
어떤 필드 값을 입력 필드로 반환할 것인가?
```

즉, F4 Help는 사용자 경험이고, Search Help는 그 사용자 경험을 구현하기 위한 DDIC 설계 객체라고 볼 수 있다.

## 5. Elementary Search Help란 무엇인가?

### 5.1 정의

Elementary Search Help는 하나의 Selection Method를 기준으로 후보 값을 제공하는 Search Help이다.

여기서 Selection Method는 보통 다음 중 하나이다.

| Selection Method 유형 | 설명 |
|---|---|
| Transparent Table | 실제 DB 테이블에서 후보 값을 읽는다. |
| Database View | 여러 테이블을 조인한 View에서 후보 값을 읽는다. |
| Help View | 입력 도움말 용도로 설계된 View를 사용한다. |
| CDS View / View Entity | 시스템과 릴리스, 개발 방식에 따라 입력 도움말 소스로 활용될 수 있다. |

초급 단계에서는 가장 단순하게 Transparent Table 또는 View를 Selection Method로 사용하는 Elementary Search Help를 학습한다.

### 5.2 Elementary Search Help의 구조

Elementary Search Help는 보통 다음 요소로 구성된다.

| 구성 요소 | 의미 |
|---|---|
| Search Help Name | Search Help 객체명 |
| Short Description | 객체 설명 |
| Selection Method | 후보 값을 읽어올 테이블 또는 뷰 |
| Search Help Parameters | 검색 조건, 결과 리스트, 반환값에 사용할 필드 |
| Import Parameter | 외부 입력값을 Search Help로 전달 |
| Export Parameter | 선택 결과를 호출 필드로 반환 |
| LPos | 결과 리스트에서 표시될 순서 |
| SPos | 검색 조건 화면에서 표시될 순서 |

초급자가 처음에는 `LPos`, `SPos`, `Import`, `Export`를 어렵게 느낄 수 있다.  
간단히 말하면 다음과 같다.

```text
LPos = 결과 목록에 보여줄 필드 순서
SPos = 검색 조건 화면에 보여줄 필드 순서
Export = 선택한 값을 입력 필드로 돌려줄 필드
Import = 현재 화면의 값을 검색 도움말 조건으로 넘길 수 있는 필드
```

## 6. Search Help와 데이터 검증의 차이

Search Help는 후보 값을 보여준다.  
하지만 후보 값을 보여준다고 해서 사용자가 반드시 그 값만 입력한다는 뜻은 아니다.

예를 들어 `CARRID` 입력 필드에 F4 Help가 붙어 있어도 사용자가 직접 `ZZ`를 입력할 수 있는 상황이 있을 수 있다.  
그 값이 실제로 허용되는지 검증하려면 별도의 검증 기준이 필요하다.

| 기능 | 주요 목적 |
|---|---|
| Search Help | 값을 쉽게 찾게 한다. |
| Domain Fixed Value | 허용 가능한 고정 값을 정의한다. |
| Foreign Key | 참조 테이블에 존재하는 값인지 검증한다. |
| Selection Screen Validation | 프로그램 입력 단계에서 추가 검증한다. |
| Application Logic | 업무 규칙에 따른 최종 검증을 수행한다. |

초급자는 다음 문장을 반드시 기억해야 한다.

```text
F4 Help는 사용자를 도와주는 기능이고, 검증은 별도로 설계해야 한다.
```

이 점을 혼동하면 “F4 목록에 있으니 검증도 되겠지”라는 잘못된 설계로 이어질 수 있다.

## 7. 실습 시나리오 개요

이번 모듈에서는 항공사 코드를 찾는 Elementary Search Help를 생성한다.

### 7.1 실습 목표

사용자가 항공사 코드 필드에서 F4를 눌렀을 때 항공사 코드와 항공사명을 보고 값을 선택할 수 있게 한다.

### 7.2 실습 객체

```text
Search Help: ZSH_JHY_CARRID
Description: Search Help for Carrier ID
Selection Method: SCARR
```

`SCARR`는 SAP 교육 환경에서 자주 사용하는 항공사 마스터성 테이블이다.

> [추정] 일부 S/4HANA 교육 시스템에서는 Flight Model 데이터가 없거나 비활성화되어 있을 수 있다. 이 경우 앞선 실습에서 만든 `ZT_JHY_CARRIER` 같은 교육용 테이블을 Selection Method로 대체해도 된다.

### 7.3 실습 필드

| Search Help Parameter | Selection Method Field | 역할 |
|---|---|---|
| CARRID | SCARR-CARRID | 항공사 코드, 반환값 |
| CARRNAME | SCARR-CARRNAME | 항공사명, 검색/표시용 |
| CURRCODE | SCARR-CURRCODE | 통화코드, 표시 보조 |
| URL | SCARR-URL | 웹 주소, 표시 보조 |

초급 실습에서는 최소한 `CARRID`, `CARRNAME`만 사용해도 충분하다.

## 8. SE11에서 Elementary Search Help 생성

### 8.1 SE11 실행

SAP GUI에서 다음 트랜잭션을 실행한다.

```text
SE11
```

### 8.2 Search Help 선택

SE11 초기 화면에서 `Search Help`를 선택하고 객체명을 입력한다.

```text
ZSH_JHY_CARRID
```

`Create` 버튼을 누른다.

### 8.3 Elementary Search Help 선택

생성 팝업이 나오면 `Elementary Search Help`를 선택한다.

`Collective Search Help`는 여러 Search Help를 묶는 상위 객체이며, 다음 모듈에서 다룬다.

### 8.4 Short Description 입력

```text
Search Help for Carrier ID
```

설명은 반드시 의미 있게 작성한다.

나쁜 예:

```text
test
help
carrier
```

좋은 예:

```text
Search Help for Carrier ID
Carrier Input Help by Carrier Code and Name
```

### 8.5 Selection Method 입력

Selection Method에 다음을 입력한다.

```text
SCARR
```

Selection Method는 Search Help가 후보 값을 읽어올 데이터 소스이다.

시스템에 `SCARR`가 없거나 사용할 수 없다면 다음처럼 교육용 테이블을 사용할 수 있다.

```text
ZT_JHY_CARRIER
```

단, 이 경우 필드명은 실습 시스템의 테이블 구조에 맞게 조정해야 한다.

## 9. Search Help Parameters 설정

Search Help Parameter 영역에는 Selection Method의 필드들을 입력한다.

### 9.1 기본 설계

| Parameter | Selection Method Field | IMP | EXP | LPos | SPos | 설명 |
|---|---|---:|---:|---:|---:|---|
| CARRID | CARRID |  | X | 1 | 1 | 선택 후 입력 필드로 반환할 항공사 코드 |
| CARRNAME | CARRNAME |  |  | 2 | 2 | 검색 조건과 결과 리스트에 표시할 항공사명 |
| CURRCODE | CURRCODE |  |  | 3 |  | 결과 리스트 보조 표시 |
| URL | URL |  |  | 4 |  | 결과 리스트 보조 표시 |

실습을 단순화하려면 다음 두 필드만 사용해도 된다.

| Parameter | EXP | LPos | SPos |
|---|---:|---:|---:|
| CARRID | X | 1 | 1 |
| CARRNAME |  | 2 | 2 |

### 9.2 Export Parameter의 의미

`EXP`는 사용자가 F4 목록에서 값을 선택했을 때 호출 필드로 돌려줄 값을 의미한다.

예를 들어 `CARRID`에 `EXP`를 체크하면, 사용자가 Lufthansa 행을 선택했을 때 `LH` 값이 입력 필드로 반환된다.

```text
선택한 행: LH / Lufthansa
반환 필드: CARRID
입력 필드 값: LH
```

### 9.3 Import Parameter의 의미

`IMP`는 외부 화면의 현재 값을 Search Help 조건으로 넘기는 기능과 관련된다.

초급 실습에서는 Import Parameter를 반드시 사용하지 않아도 된다.  
다만 후속 모듈에서 여러 입력 필드가 서로 영향을 주는 상황을 다룰 수 있으므로 개념만 알아둔다.

예를 들어 회사코드가 이미 입력되어 있고, 그 회사코드에 해당하는 플랜트만 보여주고 싶다면 회사코드를 Search Help로 전달하는 방식이 필요할 수 있다.

### 9.4 LPos의 의미

`LPos`는 결과 리스트에서 필드가 표시되는 순서이다.

| LPos | 표시 필드 |
|---:|---|
| 1 | CARRID |
| 2 | CARRNAME |
| 3 | CURRCODE |

`LPos`가 비어 있으면 결과 목록에 표시되지 않을 수 있다.

### 9.5 SPos의 의미

`SPos`는 검색 조건 화면에서 필드가 표시되는 순서이다.

| SPos | 검색 조건 필드 |
|---:|---|
| 1 | CARRID |
| 2 | CARRNAME |

사용자가 항공사명으로 검색할 수 있게 하려면 `CARRNAME`에도 SPos를 부여하는 것이 좋다.

## 10. 저장과 활성화

Search Help Parameter를 입력한 뒤 저장한다.

교육용 실습에서는 Local Object로 저장할 수 있다.

```text
Package: $TMP
```

실무 프로젝트에서는 반드시 프로젝트 Package와 Transport Request 기준을 따른다.

저장 후 Activate를 수행한다.

```text
Ctrl + F3
또는 Activate 버튼
```

활성화가 성공해야 다른 DDIC 객체나 프로그램에서 Search Help를 안정적으로 참조할 수 있다.

## 11. Search Help 테스트

### 11.1 SE11에서 테스트

Search Help를 활성화한 뒤 SE11에서 직접 테스트할 수 있다.

```text
→ Test 또는 Execute 기능 실행
→ 검색 조건 입력
→ 결과 리스트 확인
→ 값 선택
```

SAP GUI 화면 구성은 시스템 버전과 권한에 따라 약간 다를 수 있다.  
중요한 것은 결과 리스트에 의도한 필드가 나타나는지 확인하는 것이다.

### 11.2 테스트 시 확인할 항목

| 확인 항목 | 설명 |
|---|---|
| 검색 조건 화면 | CARRID, CARRNAME이 검색 조건으로 보이는가 |
| 결과 리스트 | CARRID, CARRNAME이 리스트에 보이는가 |
| 반환값 | CARRID가 선택 결과로 반환되는가 |
| 데이터 건수 | Selection Method에 실제 데이터가 있는가 |
| 성능 | 너무 많은 데이터가 무조건 조회되지 않는가 |

### 11.3 결과가 비어 있을 때

결과가 비어 있으면 다음을 확인한다.

```text
Selection Method 테이블에 데이터가 있는가?
검색 조건을 너무 좁게 입력하지 않았는가?
현재 Client에 데이터가 존재하는가?
Selection Method가 Client-dependent 테이블인가?
권한 문제로 데이터 조회가 제한되는가?
```

## 12. Search Help를 어디에 연결하는가?

Search Help는 단독으로 생성할 수도 있지만, 실제 사용하려면 일반적으로 다음 위치에 연결한다.

| 연결 위치 | 설명 |
|---|---|
| Data Element | 해당 Data Element를 사용하는 필드에 입력 도움말 제공 |
| Table Field | 특정 테이블 필드에 직접 입력 도움말 제공 |
| Screen Field | Dynpro 화면 필드에 입력 도움말 제공 |
| Selection Screen Parameter | PARAMETERS 입력 필드에 입력 도움말 제공 |
| 프로그램 로직 | `AT SELECTION-SCREEN ON VALUE-REQUEST` 등으로 직접 구현 |

이번 모듈에서는 Search Help 객체 자체를 생성하고 테스트하는 데 집중한다.  
`PARAMETERS`와 DDIC F4 Help 연결은 `THEORY-04-M05`에서 다룬다.

---

## 13. Data Element에 Search Help를 연결하는 개념

Search Help는 Data Element에 연결될 수 있다.

예를 들어 `ZDE_JHY_CARRID`라는 Data Element에 `ZSH_JHY_CARRID`를 연결하면, 해당 Data Element를 참조하는 여러 필드에서 F4 Help를 재사용할 수 있다.

```text
ZDE_JHY_CARRID
  → Search Help: ZSH_JHY_CARRID
```

이 방식의 장점은 다음과 같다.

| 장점 | 설명 |
|---|---|
| 재사용성 | 같은 Data Element를 쓰는 여러 필드에서 동일한 F4 Help 사용 |
| 일관성 | 입력 도움말 결과와 반환 방식이 통일됨 |
| 유지보수성 | Search Help를 수정하면 관련 필드에 일관되게 반영 가능 |
| 의미 중심 설계 | 업무 의미 단위로 입력 도움말을 붙일 수 있음 |

다만 모든 상황에서 Data Element 연결이 최선은 아니다.  
특정 화면에서만 다른 검색 조건이 필요하거나, 프로그램 문맥에 따라 동적 조건이 필요하면 별도 Search Help 또는 프로그램 로직이 필요할 수 있다.

## 14. Elementary Search Help와 Foreign Key 기반 F4 Help의 차이

Foreign Key를 정의하면 특정 화면이나 DDIC 기반 입력에서 F4 Help가 제공될 수 있다.  
그렇다면 Search Help는 왜 필요한가?

| 구분 | Foreign Key 기반 F4 | Elementary Search Help |
|---|---|---|
| 주 목적 | 참조 관계와 입력 검증 | 입력 후보 검색과 사용자 편의 |
| 데이터 소스 | Check Table | Selection Method |
| 검색 조건 화면 | 제한적일 수 있음 | 설계자가 Parameter로 구성 |
| 결과 리스트 구성 | 표준 관계 기반 | LPos 등으로 표시 필드 설계 |
| 반환 필드 | 관계 필드 중심 | Export Parameter로 명시 |
| 재사용 방식 | DDIC 관계 기반 | Data Element, Field, Program 등과 연결 |
| 복잡한 검색 | 제한적 | 더 명시적으로 설계 가능 |

핵심은 다음이다.

```text
Foreign Key는 관계와 검증의 성격이 강하고,
Search Help는 검색과 선택의 사용자 경험 설계 성격이 강하다.
```

둘은 경쟁 관계라기보다 보완 관계이다.

## 15. Search Help 설계 절차

실무에서 Search Help를 만들 때는 바로 SE11에 들어가기보다 다음 질문을 먼저 해야 한다.

```text
1. 사용자가 어떤 값을 찾으려 하는가?
2. 후보 값은 어느 테이블 또는 뷰에서 가져올 것인가?
3. 어떤 필드를 검색 조건으로 제공할 것인가?
4. 어떤 필드를 결과 리스트에 보여줄 것인가?
5. 최종적으로 어떤 값을 입력 필드로 반환할 것인가?
6. 데이터 건수가 많을 때 성능 문제는 없는가?
7. 권한에 따라 후보 값이 제한되어야 하는가?
8. 이 Search Help를 여러 필드에서 재사용할 것인가?
```

### 15.1 설계 예시

항공사 코드 Search Help의 설계는 다음과 같다.

| 질문 | 답변 |
|---|---|
| 사용자가 찾는 값 | 항공사 코드 |
| 후보 값 소스 | SCARR |
| 검색 조건 | 항공사 코드, 항공사명 |
| 결과 리스트 | 코드, 이름, 통화, URL |
| 반환값 | CARRID |
| 성능 이슈 | 교육용 소량 데이터로 낮음 |
| 권한 이슈 | 교육용에서는 낮음 |
| 재사용성 | `ZDE_JHY_CARRID`에 연결 가능 |

## 16. 오류 상황과 해결 방법

### 16.1 Selection Method가 존재하지 않음

| 항목 | 내용 |
|---|---|
| 증상 | Search Help 활성화 또는 테스트 시 Selection Method 관련 오류 |
| 원인 | 테이블/뷰 이름 오타, 객체 미존재, 객체 비활성 |
| 해결 | SE11에서 Selection Method 객체 존재와 활성화 상태 확인 |

### 16.2 Selection Method에 데이터가 없음

| 항목 | 내용 |
|---|---|
| 증상 | F4 결과 리스트가 비어 있음 |
| 원인 | 테이블에 데이터가 없거나 검색 조건이 과도하게 제한됨 |
| 해결 | SE16N으로 Selection Method 데이터 확인, 검색 조건 제거 후 테스트 |

### 16.3 Export Parameter를 지정하지 않음

| 항목 | 내용 |
|---|---|
| 증상 | 결과를 선택해도 입력 필드에 기대한 값이 돌아오지 않음 |
| 원인 | 반환할 필드에 EXP가 체크되지 않음 |
| 해결 | 반환 대상 필드에 EXP 체크 |

### 16.4 LPos를 지정하지 않음

| 항목 | 내용 |
|---|---|
| 증상 | 결과 리스트에 필요한 필드가 보이지 않음 |
| 원인 | 결과 리스트 표시 순서가 지정되지 않음 |
| 해결 | 표시할 필드에 LPos 입력 |

### 16.5 SPos를 지정하지 않음

| 항목 | 내용 |
|---|---|
| 증상 | 검색 조건 화면에 원하는 필드가 나오지 않음 |
| 원인 | 검색 조건 표시 순서가 지정되지 않음 |
| 해결 | 검색 조건으로 사용할 필드에 SPos 입력 |

### 16.6 타입 불일치

| 항목 | 내용 |
|---|---|
| 증상 | Search Help 연결 후 값 반환 또는 필드 연결에서 오류 발생 |
| 원인 | Export Parameter 타입과 호출 필드 타입이 맞지 않음 |
| 해결 | Data Element, Domain, Selection Method 필드 타입 일관성 확인 |

### 16.7 결과가 너무 많이 나옴

| 항목 | 내용 |
|---|---|
| 증상 | F4 실행 시 결과가 너무 많거나 느림 |
| 원인 | Selection Method가 대량 테이블인데 필터 조건이 부족함 |
| 해결 | SPos 조건 필드 제공, 적절한 View 사용, 필요한 필드만 표시, 권한/조직 조건 검토 |

## 17. 성능 관점 주의사항

Search Help는 사용자 편의 기능이지만, 내부적으로는 데이터를 조회한다.  
따라서 Selection Method가 대량 테이블이면 성능 문제가 발생할 수 있다.

### 17.1 피해야 할 설계

```text
대량 트랜잭션 테이블을 그대로 Selection Method로 사용
검색 조건 없이 모든 데이터를 조회
결과 리스트에 불필요한 필드를 많이 표시
권한 또는 조직 조건을 고려하지 않음
```

### 17.2 권장 설계

```text
마스터성 테이블 또는 전용 View 사용
사용자가 검색 조건을 입력할 수 있도록 SPos 제공
결과 리스트에는 필요한 필드만 표시
가능하면 Text 필드와 Code 필드를 함께 표시
대량 데이터는 성능 기준과 인덱스, 권한 조건을 함께 검토
```

초급 실습에서는 작은 테이블을 사용하므로 성능 문제가 잘 드러나지 않는다.  
하지만 실무에서는 Search Help 하나가 사용자의 화면 응답 속도에 직접 영향을 줄 수 있다.

## 18. 권한과 운영 관점

Search Help는 사용자가 후보 값을 볼 수 있게 한다.  
따라서 단순히 “값을 찾게 해준다”는 관점만으로 설계하면 안 된다.

예를 들어 사용자가 조회 권한이 없는 조직, 플랜트, 고객, 자재 목록이 F4 Help에 노출되면 보안 문제가 될 수 있다.

실무에서는 다음 질문이 필요하다.

```text
사용자가 이 후보 값을 볼 권한이 있는가?
조직별로 후보 값을 제한해야 하는가?
회사코드, 플랜트, 영업조직 같은 문맥 조건이 필요한가?
민감한 설명 필드를 결과 리스트에 표시해도 되는가?
```

초급 과정에서는 권한 제어를 깊게 구현하지 않지만, Search Help가 데이터 노출 지점이 될 수 있다는 감각은 반드시 가져야 한다.

## 19. 유지보수 관점

Search Help는 여러 화면과 프로그램에서 재사용될 수 있다.  
따라서 처음 설계할 때 유지보수성을 고려해야 한다.

나쁜 이름 예시:

```text
ZSH_TEST
ZSH_F4
ZHELP1
```

좋은 이름 예시:

```text
ZSH_JHY_CARRID
ZSH_JHY_DEPT_ID
ZSH_JHY_USER_ID
```

## 21. ABAP 프로그램과의 연결 예고

Search Help는 DDIC 객체이므로 Data Element나 Screen Field에 연결할 수 있다.  
후속 모듈에서는 `PARAMETERS`와 연결해 다음과 같은 흐름을 만든다.

```abap
PARAMETERS p_carrid TYPE zde_jhy_carrid.
```

`ZDE_JHY_CARRID`에 Search Help가 연결되어 있으면, 사용자는 Selection Screen에서 `P_CARRID` 입력 필드에 대해 F4 Help를 사용할 수 있다.

또는 프로그램에서 직접 F4 처리를 구현할 수도 있다.

```abap
AT SELECTION-SCREEN ON VALUE-REQUEST FOR p_carrid.
  "후속 과정에서 직접 구현 방식 학습 가능
```

이번 모듈에서는 직접 프로그램 이벤트를 구현하지 않는다.  
Search Help 객체 자체의 목적과 구성 요소를 이해하는 것이 우선이다.

## 22. 초급자 오해 정리

### 22.1 “Search Help가 있으면 검증도 자동으로 된다”

항상 그렇지 않다.  
Search Help는 입력 후보를 보여주는 기능이다. 검증은 Foreign Key, Domain, 프로그램 로직 등과 함께 설계해야 한다.

### 22.2 “Foreign Key와 Search Help는 같은 것이다”

다르다.  
Foreign Key는 참조 관계와 검증 성격이 강하고, Search Help는 후보값 검색과 선택 UI 성격이 강하다.

### 22.3 “Selection Method는 아무 테이블이나 사용해도 된다”

아니다.  
대량 테이블, 민감 데이터 테이블, 권한 제한이 필요한 테이블을 무분별하게 Selection Method로 쓰면 성능과 보안 문제가 생길 수 있다.

### 22.4 “EXP는 결과 리스트 표시 여부다”

아니다.  
EXP는 선택 결과를 호출 필드로 반환할지 결정하는 속성이다. 결과 리스트 표시 여부는 LPos와 관련된다.

### 22.5 “LPos와 SPos는 중요하지 않다”

아니다.  
LPos는 결과 리스트 표시, SPos는 검색 조건 화면 표시와 관련되므로 사용자 경험에 직접 영향을 준다.

## 23. 강사용 설명 포인트

강의에서는 다음 순서로 설명하면 초급자가 이해하기 쉽다.

```text
1. 사용자가 코드값을 외우기 어렵다는 문제 제기
2. F4 Help라는 사용자 경험 설명
3. Search Help가 그 경험을 정의하는 DDIC 객체임을 설명
4. Selection Method가 후보값의 데이터 소스임을 설명
5. EXP, LPos, SPos를 화면 동작과 연결해 설명
6. Search Help와 검증 로직의 차이를 강조
7. 후속 모듈에서 Data Element와 PARAMETERS 연결로 확장됨을 예고
```

특히 `EXP`, `LPos`, `SPos`는 표만으로 설명하면 추상적이다.  
반드시 F4 Help 실행 화면과 연결해서 설명하는 것이 좋다.

## 25. 평가 문제

### 25.1 객관식

#### Q1. Elementary Search Help의 가장 적절한 설명은?

A. 여러 Search Help를 묶는 상위 Search Help이다.  
B. 하나의 Selection Method를 기준으로 입력 후보 값을 제공하는 Search Help이다.  
C. 데이터베이스 테이블의 Primary Key를 정의하는 객체이다.  
D. ABAP 프로그램의 반복문을 자동 생성하는 도구이다.

**정답:** B

#### Q2. Search Help에서 Selection Method의 의미는?

A. 사용자가 누를 수 있는 버튼 이름  
B. 후보 값을 읽어올 테이블 또는 뷰  
C. 결과 화면의 색상 설정  
D. 프로그램 실행 이벤트

**정답:** B

#### Q3. Export Parameter의 역할은?

A. 검색 조건 화면에 필드를 표시한다.  
B. 결과 리스트에서 필드 순서를 정한다.  
C. 선택된 값을 호출 필드로 반환한다.  
D. 데이터를 데이터베이스에 저장한다.

**정답:** C

#### Q4. LPos와 SPos에 대한 설명으로 올바른 것은?

A. LPos는 결과 리스트 표시 순서, SPos는 검색 조건 화면 표시 순서이다.  
B. LPos는 데이터 저장 순서, SPos는 테이블 Key 순서이다.  
C. 둘 다 ABAP 반복문 인덱스이다.  
D. 둘 다 Foreign Key Cardinality 설정이다.

**정답:** A

### 25.2 서술형

#### Q1. Search Help와 Foreign Key의 차이를 설명하시오.

**모범 답안:**  
Search Help는 사용자가 입력 가능한 후보 값을 쉽게 찾고 선택하도록 도와주는 입력 도움말 객체이다. Foreign Key는 테이블 필드 간 참조 관계를 정의하고 입력값이 Check Table에 존재하는지 검증하는 성격이 강하다. Search Help는 사용자 편의와 검색 UI 설계에 가깝고, Foreign Key는 데이터 관계와 무결성에 가깝다.

#### Q2. Search Help가 검증을 완전히 대체할 수 없는 이유를 설명하시오.

**모범 답안:**  
Search Help는 F4 목록을 통해 후보 값을 보여주지만 사용자가 직접 값을 입력할 수도 있고, 화면이나 프로그램 문맥에 따라 검증이 별도로 필요할 수 있다. 따라서 허용 값 검증은 Foreign Key, Domain Fixed Value, Selection Screen Validation, Application Logic 등과 함께 설계해야 한다.

#### Q3. 대량 테이블을 Selection Method로 사용할 때 주의해야 할 점을 설명하시오.

**모범 답안:**  
대량 테이블을 조건 없이 조회하면 F4 Help 실행 시 성능 문제가 발생할 수 있다. 검색 조건 필드 제공, 적절한 View 사용, 필요한 필드만 결과 리스트에 표시, 조직/권한 조건 반영, 인덱스 및 데이터량 검토가 필요하다.

## 26. 핵심 요약

이번 모듈의 핵심은 다음과 같다.

```text
Search Help는 사용자가 입력 후보 값을 쉽게 찾도록 도와주는 DDIC 객체이다.
F4 Help는 사용자가 보는 입력 도움말 경험이고, Search Help는 그 경험을 설계하는 객체이다.
Elementary Search Help는 하나의 Selection Method를 기준으로 후보 값을 제공한다.
Selection Method는 후보 값을 읽어올 테이블 또는 뷰이다.
Export Parameter는 선택한 값을 호출 필드로 반환하는 역할을 한다.
LPos는 결과 리스트 표시 순서이고, SPos는 검색 조건 화면 표시 순서이다.
Search Help는 검증 로직을 완전히 대체하지 않는다.
실무에서는 성능, 권한, 유지보수성을 함께 고려해야 한다.
```
