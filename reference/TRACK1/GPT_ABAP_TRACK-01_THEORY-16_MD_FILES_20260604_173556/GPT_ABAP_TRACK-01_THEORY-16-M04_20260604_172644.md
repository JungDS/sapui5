## 0. 이 문서의 학습 범위

이 문서는 `THEORY-16-M04 — Table Expression`만 다룬다.

이번 모듈의 중심 주제는 Modern ABAP의 **Table Expression**이다.  
Table Expression은 내부 테이블에서 특정 행을 읽을 때 `READ TABLE` 문을 더 짧고 표현식 중심으로 작성할 수 있게 해주는 문법이다.

초급자가 가장 먼저 기억해야 할 문장은 다음이다.

```text
Table Expression은 내부 테이블의 한 줄을 표현식처럼 읽는 문법이다.
찾는 행이 없으면 기본적으로 예외가 발생한다.
없을 수도 있는 데이터는 OPTIONAL, DEFAULT, line_exists 또는 ASSIGN 패턴으로 안전하게 처리한다.
```

이전 모듈 `THEORY-16-M01~M03`에서 Inline Declaration, VALUE Constructor Expression, CORRESPONDING을 배웠다면, 이번 모듈에서는 **내부 테이블 조회 로직을 더 간결하게 표현하는 방법**을 학습한다.

## 1. 왜 Table Expression을 배우는가?

ABAP 프로그램에서 내부 테이블은 거의 모든 데이터 처리의 중심이다.

대표적인 흐름은 다음과 같다.

```text
DB에서 SELECT로 여러 건 조회
→ Internal Table에 저장
→ 특정 Key에 해당하는 한 줄 찾기
→ 찾은 행의 값으로 계산 또는 출력
```

전통적인 ABAP에서는 특정 행을 찾을 때 보통 `READ TABLE`을 사용했다.

```abap
READ TABLE lt_flights INTO ls_flight
  WITH KEY carrid = 'LH'
           connid = '0400'.

IF sy-subrc = 0.
  WRITE ls_flight-price.
ENDIF.
```

Modern ABAP에서는 같은 의도를 다음처럼 표현할 수 있다.

```abap
DATA(ls_flight) = lt_flights[ carrid = 'LH' connid = '0400' ].
WRITE ls_flight-price.
```

이 문법은 짧고 읽기 쉽다.  
하지만 중요한 차이가 있다.

```text
READ TABLE은 실패 여부를 sy-subrc로 확인한다.
Table Expression은 찾지 못하면 기본적으로 예외가 발생한다.
```

따라서 Table Expression은 단순히 `READ TABLE`의 짧은 버전으로만 보면 안 된다.  
**존재가 보장되는 데이터**와 **존재하지 않을 수도 있는 데이터**를 구분해서 사용해야 한다.

## 2. 선행 지식

Table Expression을 이해하려면 다음 내용을 이미 알고 있어야 한다.

| 선행 지식 | 필요한 이유 |
|---|---|
| Internal Table | Table Expression은 내부 테이블을 대상으로 한다. |
| Work Area | 읽은 한 줄을 구조체로 다루는 감각이 필요하다. |
| Key | `itab[ key = value ]` 조건의 의미를 이해해야 한다. |
| READ TABLE | 기존 문법과 비교해야 Table Expression의 장단점이 보인다. |
| Inline Declaration | `DATA(row) = ...` 형태와 자주 함께 사용된다. |
| VALUE Constructor Expression | `OPTIONAL`, `DEFAULT`와 함께 사용할 때 필요하다. |
| Exception | 찾는 행이 없을 때 `CX_SY_ITAB_LINE_NOT_FOUND`가 발생할 수 있다. |

## 3. Table Expression의 기본 개념

### 3.1 기본 형태

Table Expression의 기본 형태는 다음과 같다.

```abap
itab[ ... ]
```

여기서 `itab`은 내부 테이블이고, 대괄호 안에는 찾을 행을 지정하는 조건이 들어간다.

대표 형태는 다음과 같다.

| 형태 | 의미 |
|---|---|
| `itab[ 1 ]` | 인덱스 1번 행을 읽는다. |
| `itab[ key = value ]` | 기본 Key 또는 조건 기준으로 행을 찾는다. |
| `itab[ comp1 = v1 comp2 = v2 ]` | 여러 Component 조건으로 행을 찾는다. |
| `itab[ KEY keyname COMPONENTS comp = value ]` | 명시적 테이블 Key를 사용해 행을 찾는다. |
| `itab[ key = value ]-field` | 찾은 행의 특정 필드만 바로 읽는다. |

### 3.2 가장 단순한 예

```abap
TYPES: BEGIN OF ty_carrier,
         carrid   TYPE scarr-carrid,
         carrname TYPE scarr-carrname,
       END OF ty_carrier.

DATA lt_carriers TYPE STANDARD TABLE OF ty_carrier WITH EMPTY KEY.

lt_carriers = VALUE #(
  ( carrid = 'LH' carrname = 'Lufthansa' )
  ( carrid = 'AA' carrname = 'American Airlines' )
  ( carrid = 'JL' carrname = 'Japan Airlines' )
).

DATA(ls_lh) = lt_carriers[ carrid = 'LH' ].
WRITE: / ls_lh-carrid, ls_lh-carrname.
```

위 코드는 `CARRID = 'LH'`인 행을 찾아 `LS_LH`에 담는다.

### 3.3 필드만 바로 읽기

한 줄 전체가 아니라 특정 필드만 필요하다면 다음처럼 쓸 수 있다.

```abap
DATA(lv_name) = lt_carriers[ carrid = 'LH' ]-carrname.
WRITE lv_name.
```

이 코드는 다음 의미이다.

```text
lt_carriers에서 carrid = 'LH'인 행을 찾고,
그 행의 carrname 필드만 lv_name에 담는다.
```

## 4. READ TABLE과 Table Expression 비교

### 4.1 기존 READ TABLE 방식

```abap
READ TABLE lt_carriers INTO DATA(ls_carrier)
  WITH KEY carrid = 'LH'.

IF sy-subrc = 0.
  WRITE ls_carrier-carrname.
ELSE.
  WRITE 'Carrier not found'.
ENDIF.
```

이 방식은 초급자에게 명시적이다.  
찾기 실패 여부를 `sy-subrc`로 확인한다.

### 4.2 Table Expression 방식

```abap
DATA(ls_carrier) = lt_carriers[ carrid = 'LH' ].
WRITE ls_carrier-carrname.
```

코드는 짧아졌다.  
하지만 `CARRID = 'LH'`인 행이 없다면 런타임 예외가 발생할 수 있다.

### 4.3 비교표

| 구분 | READ TABLE | Table Expression |
|---|---|---|
| 문법 스타일 | Statement 중심 | Expression 중심 |
| 실패 처리 | `sy-subrc` | 기본적으로 예외 |
| 코드 길이 | 길어질 수 있음 | 짧고 간결 |
| Inline과 조합 | 가능하지만 상대적으로 길다 | 매우 자연스럽다 |
| 필드 직접 접근 | 별도 Work Area 필요 | `itab[ ... ]-field` 가능 |
| 존재 여부 확인 | `sy-subrc` | `line_exists( )`, `OPTIONAL`, `DEFAULT` 등 사용 |

핵심은 다음이다.

```text
읽을 행이 반드시 있다고 확신하면 Table Expression이 간결하다.
읽을 행이 없을 수 있다면 안전 처리 패턴을 반드시 사용한다.
```

## 5. 찾는 행이 없을 때의 동작

Table Expression의 가장 중요한 주의점은 “행이 없을 때”이다.

다음 코드를 보자.

```abap
DATA(ls_unknown) = lt_carriers[ carrid = 'ZZ' ].
```

`CARRID = 'ZZ'`인 행이 없다면 기본적으로 `CX_SY_ITAB_LINE_NOT_FOUND` 예외가 발생할 수 있다.  
따라서 이 코드는 “항상 존재하는 행”에만 안전하다.

초급자가 자주 하는 실수는 다음이다.

```abap
" 위험한 코드 예시
DATA(lv_name) = lt_carriers[ carrid = p_carrid ]-carrname.
WRITE lv_name.
```

사용자가 입력한 `P_CARRID`가 내부 테이블에 없으면 오류가 발생할 수 있다.  
입력값이나 외부 데이터는 항상 존재를 보장할 수 없으므로 안전 처리해야 한다.

---

## 6. 안전 처리 1: line_exists

### 6.1 line_exists의 목적

`line_exists( )`는 Table Expression 조건에 해당하는 행이 있는지 확인하는 내장 함수이다.

```abap
IF line_exists( lt_carriers[ carrid = 'LH' ] ).
  WRITE 'LH exists'.
ENDIF.
```

이 코드는 행이 존재하는지 여부만 확인한다.

### 6.2 line_exists와 실제 읽기

```abap
IF line_exists( lt_carriers[ carrid = 'LH' ] ).
  DATA(ls_carrier) = lt_carriers[ carrid = 'LH' ].
  WRITE ls_carrier-carrname.
ELSE.
  WRITE 'Carrier not found'.
ENDIF.
```

이 패턴은 이해하기 쉽지만, 같은 조건으로 두 번 접근한다는 점을 고려해야 한다.

```text
첫 번째 접근: 존재 여부 확인
두 번째 접근: 실제 데이터 읽기
```

교육용으로는 명확해서 좋지만, 실무에서는 성능과 가독성을 함께 판단한다.

### 6.3 언제 적합한가?

| 상황 | 적합성 |
|---|---|
| 단순 존재 여부만 확인 | 매우 적합 |
| 존재하면 별도 로직 수행 | 적합 |
| 같은 행의 여러 필드를 읽어야 함 | 다른 패턴 검토 가능 |
| 대량 반복 안에서 자주 호출 | 테이블 종류와 Key를 반드시 고려 |

---

## 7. 안전 처리 2: OPTIONAL

### 7.1 OPTIONAL의 목적

`OPTIONAL`은 찾는 행이 없을 때 예외를 발생시키지 않고, 결과 타입의 초기값을 반환하도록 돕는다.

대표 문법은 다음과 같다.

```abap
DATA(ls_carrier) = VALUE ty_carrier( lt_carriers[ carrid = 'ZZ' ] OPTIONAL ).
```

또는 문맥상 타입 추론이 가능한 경우 다음처럼 쓸 수 있다.

```abap
DATA(ls_carrier) = VALUE #( lt_carriers[ carrid = 'ZZ' ] OPTIONAL ).
```

찾는 행이 있으면 그 행을 반환하고, 없으면 초기값 구조가 반환된다.

### 7.2 예제

```abap
DATA(ls_carrier) = VALUE ty_carrier(
  lt_carriers[ carrid = 'ZZ' ] OPTIONAL
).

IF ls_carrier IS INITIAL.
  WRITE 'Carrier not found'.
ELSE.
  WRITE ls_carrier-carrname.
ENDIF.
```

다만 구조 전체가 초기값인지로 존재 여부를 판단할 때는 주의가 필요하다.  
실제 데이터가 초기값과 구분되지 않는 경우에는 별도의 존재 여부 플래그나 `line_exists`가 더 명확할 수 있다.

### 7.3 OPTIONAL 사용 기준

| 상황 | 판단 |
|---|---|
| 없으면 빈 구조로 처리해도 됨 | 적합 |
| 없으면 0, 공백, 초기값으로 계산해도 됨 | 적합 가능 |
| 없으면 사용자에게 명확한 오류 메시지가 필요 | `line_exists`, `ASSIGN`, 예외 처리 검토 |
| 초기값과 실제 값의 구분이 중요 | 신중 사용 |

---

## 8. 안전 처리 3: DEFAULT

### 8.1 DEFAULT의 목적

`DEFAULT`는 찾는 행이 없을 때 사용할 대체 값을 명시한다.

```abap
DATA(ls_carrier) = VALUE ty_carrier(
  lt_carriers[ carrid = 'ZZ' ]
  DEFAULT VALUE #( carrid = 'ZZ' carrname = 'Unknown Carrier' )
).
```

이 코드는 다음 의미이다.

```text
lt_carriers에서 carrid = 'ZZ'인 행을 찾는다.
있으면 해당 행을 사용한다.
없으면 carrid = 'ZZ', carrname = 'Unknown Carrier'인 기본 구조를 사용한다.
```

### 8.2 OPTIONAL과 DEFAULT의 차이

| 구분 | OPTIONAL | DEFAULT |
|---|---|---|
| 없을 때 결과 | 초기값 | 지정한 대체 값 |
| 의도 표현 | 없어도 괜찮다 | 없으면 이 값을 사용한다 |
| 코드 의미 | 다소 암시적 | 더 명시적 |
| 업무 메시지 | 별도 처리 필요 | 기본 설명값 제공 가능 |

### 8.3 예제: 출력용 기본값

```abap
DATA(ls_carrier) = VALUE ty_carrier(
  lt_carriers[ carrid = p_carrid ]
  DEFAULT VALUE #( carrid = p_carrid carrname = 'Unknown Carrier' )
).

WRITE: / ls_carrier-carrid, ls_carrier-carrname.
```

이 코드는 조회 결과가 없더라도 출력이 가능하다.  
하지만 실무에서는 기본값 출력이 업무적으로 맞는지 반드시 판단해야 한다.

예를 들어 마스터 데이터가 반드시 존재해야 하는 프로세스라면 `Unknown Carrier`로 넘어가는 것이 오히려 문제를 숨길 수 있다.

## 9. 안전 처리 4: ASSIGN Table Expression

Table Expression을 `ASSIGN`과 함께 사용하면 Field Symbol에 행을 할당할 수 있다.

```abap
ASSIGN lt_carriers[ carrid = p_carrid ] TO FIELD-SYMBOL(<ls_carrier>).

IF sy-subrc = 0.
  WRITE <ls_carrier>-carrname.
ELSE.
  WRITE 'Carrier not found'.
ENDIF.
```

이 패턴은 실무에서 자주 유용하다.

장점은 다음과 같다.

| 장점 | 설명 |
|---|---|
| 복사 최소화 | Work Area로 복사하지 않고 행을 참조할 수 있다. |
| 실패 처리 명확 | `sy-subrc`로 분기할 수 있다. |
| 여러 필드 접근 편리 | `<ls_carrier>-field` 형태로 여러 필드를 읽기 쉽다. |
| 기존 READ TABLE ASSIGNING과 유사 | Legacy 개발자도 이해하기 쉽다. |

주의할 점도 있다.

```text
Field Symbol은 내부 테이블의 실제 행을 가리킬 수 있다.
값을 변경하면 내부 테이블 데이터가 변경될 수 있으므로 READ ONLY 의도라면 수정하지 않도록 주의한다.
```

## 10. line_index

`line_index( )`는 조건에 맞는 행의 인덱스를 반환한다.

```abap
DATA(lv_index) = line_index( lt_carriers[ carrid = 'LH' ] ).
```

초급자는 다음 정도로 이해하면 된다.

| 결과 | 의미 |
|---|---|
| 양수 인덱스 | 해당 행이 존재하며 그 위치를 반환 |
| 0 또는 특수 값 | 테이블 종류와 Key 상황에 따라 “인덱스 없음”을 의미할 수 있음 |

실무에서는 단순 존재 여부만 필요하면 `line_exists`가 더 명확하다.  
인덱스가 실제로 필요한 경우에만 `line_index`를 사용한다.

예를 들어 Standard Table에서 특정 행 위치가 필요할 때 사용할 수 있다.

```abap
DATA(lv_index) = line_index( lt_carriers[ carrid = 'AA' ] ).

IF lv_index > 0.
  WRITE: / 'Found at index:', lv_index.
ENDIF.
```

## 11. 인덱스 기반 Table Expression

Table Expression은 인덱스로도 접근할 수 있다.

```abap
DATA(ls_first) = lt_carriers[ 1 ].
```

이 코드는 내부 테이블의 첫 번째 행을 읽는다.

하지만 인덱스 접근은 주의해야 한다.

```abap
DATA(ls_tenth) = lt_carriers[ 10 ].
```

내부 테이블에 10번째 행이 없으면 예외가 발생할 수 있다.

안전하게 처리하려면 다음처럼 작성한다.

```abap
DATA(ls_tenth) = VALUE ty_carrier( lt_carriers[ 10 ] OPTIONAL ).
```

또는 행 수를 먼저 확인한다.

```abap
IF lines( lt_carriers ) >= 10.
  DATA(ls_tenth) = lt_carriers[ 10 ].
ENDIF.
```

### 11.1 인덱스 접근 사용 기준

| 상황 | 판단 |
|---|---|
| 첫 번째/마지막 행을 명확히 읽는 경우 | 가능 |
| 정렬 순서가 보장된 테이블 | 가능 |
| 업무 Key로 찾아야 하는 경우 | Key 조건 접근 권장 |
| 행 순서가 의미 없는 테이블 | 인덱스 접근 지양 |

## 12. Key 기반 Table Expression

### 12.1 기본 Key 조건

```abap
DATA(ls_carrier) = lt_carriers[ carrid = 'LH' ].
```

이 문법은 `CARRID = 'LH'`인 행을 찾는다.

조건이 여러 개인 경우 다음처럼 쓴다.

```abap
DATA(ls_flight) = lt_flights[
  carrid = 'LH'
  connid = '0400'
  fldate = '20260604'
].
```

### 12.2 명시적 Key 사용

내부 테이블에 명시적 Key가 정의되어 있다면 다음처럼 Key 이름을 지정할 수 있다.

```abap
TYPES ty_flights TYPE SORTED TABLE OF sflight
  WITH UNIQUE KEY carrid connid fldate.

DATA lt_flights TYPE ty_flights.

DATA(ls_flight) = lt_flights[
  KEY primary_key
  COMPONENTS carrid = 'LH'
             connid = '0400'
             fldate = '20260604'
].
```

[추정] 실제 문법 세부 형태와 Key 이름은 시스템 릴리스와 테이블 타입 정의에 따라 다르게 작성될 수 있으므로, 교육 시스템의 문법 검사 결과를 기준으로 확인한다.

초급 단계에서 중요한 것은 다음이다.

```text
Table Expression도 테이블 Key 설계와 무관하지 않다.
Standard Table을 무작정 조건 검색하면 선형 검색이 될 수 있다.
Sorted/Hashed Table 또는 Secondary Key를 고려하면 조회 성능이 달라진다.
```

---

## 13. Standard / Sorted / Hashed Table과 성능 감각

Table Expression은 문법을 짧게 만들어주지만, 내부 테이블 종류에 따른 성능 특성을 없애주지는 않는다.

| 테이블 종류 | 기본 특징 | Table Expression 사용 시 감각 |
|---|---|---|
| Standard Table | 입력 순서 중심 | Key 조건 검색이 선형 검색이 될 수 있음 |
| Sorted Table | Key 기준 정렬 | Key 조건 검색에 유리 |
| Hashed Table | Hash Key 기반 | Unique Key 조건 조회에 매우 유리 |

### 13.1 잘못된 감각

```text
Table Expression을 쓰면 무조건 빠르다.
```

이 말은 틀렸다.  
Table Expression은 문법 형태일 뿐이며, 성능은 내부 테이블 종류와 Key 설계에 영향을 받는다.

### 13.2 올바른 감각

```text
Table Expression은 코드를 간결하게 만든다.
조회 성능은 Standard/Sorted/Hashed Table과 Key 설계가 결정한다.
```

### 13.3 반복문 안에서의 주의

다음 코드는 간결하지만 주의가 필요하다.

```abap
LOOP AT lt_items INTO DATA(ls_item).
  DATA(ls_master) = lt_master[ matnr = ls_item-matnr ].
  " ...
ENDLOOP.
```

`LT_MASTER`가 Standard Table이고 데이터가 많다면, 반복마다 선형 검색이 발생할 수 있다.  
이 경우 Sorted Table, Hashed Table, Secondary Key, 또는 사전 정렬/조회 전략을 검토해야 한다.

## 14. 실무 패턴 1: 존재 보장 데이터 읽기

사용자가 이미 앞 단계에서 존재 여부를 검증했거나, 시스템 설계상 반드시 존재하는 데이터라면 Table Expression을 간결하게 사용할 수 있다.

```abap
IF line_exists( lt_carriers[ carrid = p_carrid ] ).
  DATA(lv_name) = lt_carriers[ carrid = p_carrid ]-carrname.
  WRITE lv_name.
ENDIF.
```

또는 별도 검증 로직이 이미 있다면 다음처럼 간결하게 작성할 수 있다.

```abap
DATA(ls_carrier) = lt_carriers[ carrid = p_carrid ].
```

다만 코드만 보는 사람에게 “왜 반드시 존재하는지”가 명확하지 않다면 주석이나 선행 검증 흐름이 필요하다.

---

## 15. 실무 패턴 2: 없으면 기본값 사용

조회 결과가 없을 때 기본값을 사용해도 되는 출력성 로직에서는 `DEFAULT`가 유용하다.

```abap
DATA(ls_carrier) = VALUE ty_carrier(
  lt_carriers[ carrid = p_carrid ]
  DEFAULT VALUE #( carrid = p_carrid carrname = 'N/A' )
).

WRITE: / ls_carrier-carrid, ls_carrier-carrname.
```

이 패턴은 다음 상황에 적합하다.

| 상황 | 설명 |
|---|---|
| 조회 실패가 업무 오류가 아님 | 없어도 기본 표시 가능 |
| 출력용 텍스트 대체 | `N/A`, `Unknown` 등 사용 가능 |
| 집계/리포트 보조값 | 빈 값을 기본값으로 치환 가능 |

하지만 다음 상황에서는 부적합할 수 있다.

| 상황 | 이유 |
|---|---|
| 마스터 데이터가 반드시 존재해야 함 | 기본값이 오류를 숨길 수 있음 |
| 후속 저장 로직이 있음 | 잘못된 기본값이 DB에 저장될 수 있음 |
| 권한 또는 데이터 누락을 구분해야 함 | 기본값으로 원인이 감춰질 수 있음 |

---

## 16. 실무 패턴 3: ASSIGN으로 안전하게 읽기

여러 필드를 읽거나, 읽은 행을 조건부로 처리해야 할 때는 `ASSIGN` 패턴이 실무적으로 좋다.

```abap
ASSIGN lt_carriers[ carrid = p_carrid ] TO FIELD-SYMBOL(<ls_carrier>).

IF sy-subrc <> 0.
  MESSAGE 'Carrier not found' TYPE 'I'.
  RETURN.
ENDIF.

WRITE: / <ls_carrier>-carrid,
         <ls_carrier>-carrname.
```

장점은 다음이다.

```text
조회 성공/실패가 명확하다.
예외 없이 흐름을 제어할 수 있다.
읽은 행의 여러 필드를 반복 접근하기 좋다.
```

---

## 17. 실무 패턴 4: TRY...CATCH로 명시적 예외 처리

Table Expression의 실패를 예외로 처리할 수도 있다.

```abap
TRY.
    DATA(ls_carrier) = lt_carriers[ carrid = p_carrid ].
    WRITE ls_carrier-carrname.
  CATCH cx_sy_itab_line_not_found.
    WRITE 'Carrier not found'.
ENDTRY.
```

이 방식은 “찾지 못하는 상황을 예외로 보는 경우”에 적합하다.

다만 초급 실무에서는 단순 조회 실패를 모두 예외 처리로 작성하기보다, 상황에 따라 `line_exists`, `OPTIONAL`, `DEFAULT`, `ASSIGN`을 선택하는 감각이 더 중요하다.

## 18. 안티패턴

### 18.1 존재하지 않을 수 있는 데이터를 바로 읽기

```abap
DATA(lv_name) = lt_carriers[ carrid = p_carrid ]-carrname.
```

사용자 입력값 `P_CARRID`가 테이블에 없을 수 있다면 위험하다.

개선 예:

```abap
DATA(lv_name) = VALUE scarr-carrname(
  lt_carriers[ carrid = p_carrid ]-carrname OPTIONAL
).
```

또는:

```abap
ASSIGN lt_carriers[ carrid = p_carrid ] TO FIELD-SYMBOL(<ls_carrier>).
IF sy-subrc = 0.
  DATA(lv_name) = <ls_carrier>-carrname.
ENDIF.
```

### 18.2 Table Expression을 반복문 안에서 무분별하게 사용

```abap
LOOP AT lt_items INTO DATA(ls_item).
  DATA(lv_name) = lt_materials[ matnr = ls_item-matnr ]-maktx.
ENDLOOP.
```

데이터가 적으면 문제가 없어 보일 수 있다.  
하지만 `LT_ITEMS`와 `LT_MATERIALS`가 모두 크면 성능 문제가 생길 수 있다.

개선 방향:

```text
LT_MATERIALS를 Hashed Table로 구성한다.
적절한 Key를 정의한다.
DB 조회 단계에서 JOIN 또는 FOR ALL ENTRIES/IN 조건 전략을 검토한다.
반복문 내부 조회 횟수를 줄인다.
```

### 18.3 OPTIONAL로 업무 오류를 숨기기

```abap
DATA(ls_customer) = VALUE ty_customer(
  lt_customers[ kunnr = p_kunnr ] OPTIONAL
).
```

고객이 반드시 존재해야 하는 프로세스라면 이 코드는 오류를 숨길 수 있다.  
이 경우에는 명확한 메시지를 제공하는 것이 좋다.

```abap
IF NOT line_exists( lt_customers[ kunnr = p_kunnr ] ).
  MESSAGE 'Customer does not exist' TYPE 'E'.
ENDIF.
```

## 19. 디버깅 관점

Table Expression을 디버깅할 때는 다음을 확인한다.

| 확인 항목 | 설명 |
|---|---|
| 내부 테이블 건수 | `LINES( itab )` 또는 디버거에서 확인 |
| Key 필드 값 | 찾으려는 값이 실제 존재하는지 확인 |
| 조건 필드 타입 | CHAR/NUMC 길이, 앞자리 0 여부 확인 |
| 대소문자 | 코드성 필드는 대문자 여부 확인 |
| Client/조직 조건 | 조회 결과가 예상 범위에 있는지 확인 |
| 예외 발생 위치 | 어떤 Table Expression에서 실패했는지 확인 |

초급자가 자주 놓치는 부분은 `NUMC`와 앞자리 0이다.

예를 들어 `CONNID`가 `NUMC4` 성격이면 화면에서는 `400`처럼 보더라도 내부 값은 `0400`일 수 있다.

```abap
DATA(ls_flight) = lt_flights[ connid = '0400' ].
```

이런 차이는 DDIC 타입과 화면 표시를 함께 이해해야 정확히 잡을 수 있다.

## 20. 미니 실습

### 20.1 실습 목표

항공사 내부 테이블을 만들고 Table Expression으로 특정 항공사를 조회한다.  
존재하는 Key와 존재하지 않는 Key를 모두 테스트한다.

### 20.2 실습 코드

```abap
REPORT zgpt_table_expression.

TYPES: BEGIN OF ty_carrier,
         carrid   TYPE scarr-carrid,
         carrname TYPE scarr-carrname,
         currcode TYPE scarr-currcode,
       END OF ty_carrier.

DATA lt_carriers TYPE STANDARD TABLE OF ty_carrier WITH EMPTY KEY.

lt_carriers = VALUE #(
  ( carrid = 'LH' carrname = 'Lufthansa'         currcode = 'EUR' )
  ( carrid = 'AA' carrname = 'American Airlines' currcode = 'USD' )
  ( carrid = 'JL' carrname = 'Japan Airlines'    currcode = 'JPY' )
).

" 1. 존재가 보장되는 값 읽기
DATA(ls_lh) = lt_carriers[ carrid = 'LH' ].
WRITE: / 'LH:', ls_lh-carrname.

" 2. 존재 여부 확인
IF line_exists( lt_carriers[ carrid = 'AA' ] ).
  WRITE: / 'AA exists'.
ENDIF.

" 3. OPTIONAL 사용
DATA(ls_unknown_optional) = VALUE ty_carrier(
  lt_carriers[ carrid = 'ZZ' ] OPTIONAL
).

IF ls_unknown_optional IS INITIAL.
  WRITE: / 'ZZ not found - OPTIONAL returned initial value'.
ENDIF.

" 4. DEFAULT 사용
DATA(ls_unknown_default) = VALUE ty_carrier(
  lt_carriers[ carrid = 'ZZ' ]
  DEFAULT VALUE #( carrid = 'ZZ' carrname = 'Unknown Carrier' currcode = 'N/A' )
).

WRITE: / 'DEFAULT:', ls_unknown_default-carrid, ls_unknown_default-carrname.

" 5. ASSIGN 패턴
ASSIGN lt_carriers[ carrid = 'JL' ] TO FIELD-SYMBOL(<ls_carrier>).
IF sy-subrc = 0.
  WRITE: / 'ASSIGN:', <ls_carrier>-carrid, <ls_carrier>-carrname.
ENDIF.
```

### 20.3 실습 결과 확인

실행 후 다음을 확인한다.

| 확인 항목 | 기대 결과 |
|---|---|
| `LH` 조회 | Lufthansa 출력 |
| `line_exists` | AA 존재 메시지 출력 |
| `OPTIONAL` | ZZ 없음 → 초기값 반환 |
| `DEFAULT` | ZZ 없음 → Unknown Carrier 반환 |
| `ASSIGN` | JL 조회 성공 |

### 20.4 오류 케이스 실험

다음 코드를 일부러 실행해본다.

```abap
DATA(ls_error) = lt_carriers[ carrid = 'XX' ].
```

`XX`가 없으면 예외가 발생할 수 있다.  
그 뒤 `OPTIONAL`, `DEFAULT`, `line_exists`, `ASSIGN` 중 하나로 안전하게 고쳐본다.

## 21. 실무 판단 기준

Table Expression을 사용할지 판단할 때 다음 질문을 던진다.

```text
이 행은 반드시 존재하는가?
없을 수도 있다면 어떤 처리가 맞는가?
초기값으로 넘어가도 되는가?
기본값을 주는 것이 업무적으로 맞는가?
명시적 오류 메시지가 필요한가?
반복문 안에서 성능 문제가 생기지 않는가?
테이블 종류와 Key 설계가 조회 패턴에 맞는가?
```

판단 기준을 표로 정리하면 다음과 같다.

| 상황 | 추천 패턴 |
|---|---|
| 존재가 보장되는 행 | `itab[ key = value ]` |
| 존재 여부만 필요 | `line_exists( itab[ ... ] )` |
| 없으면 초기값 허용 | `VALUE #( itab[ ... ] OPTIONAL )` |
| 없으면 대체값 필요 | `VALUE #( itab[ ... ] DEFAULT ... )` |
| 성공/실패 분기가 명확해야 함 | `ASSIGN itab[ ... ] TO <fs>` |
| 못 찾는 것이 비정상 상황 | `TRY...CATCH cx_sy_itab_line_not_found` |
| 반복문 내 대량 조회 | Sorted/Hashed/Secondary Key 검토 |

## 22. Clean ABAP 관점

Table Expression은 Modern ABAP답게 코드를 짧게 만든다.  
하지만 짧은 코드가 항상 좋은 코드는 아니다.

좋은 코드의 기준은 다음이다.

```text
의도가 명확하다.
실패 상황이 안전하게 처리된다.
성능 특성을 숨기지 않는다.
읽는 사람이 예외 가능성을 이해할 수 있다.
```

### 22.1 좋은 예

```abap
DATA(ls_carrier) = VALUE ty_carrier(
  lt_carriers[ carrid = p_carrid ]
  DEFAULT VALUE #( carrid = p_carrid carrname = 'Unknown Carrier' )
).
```

이 코드는 “없으면 기본 항공사명을 사용한다”는 의도가 드러난다.

### 22.2 나쁜 예

```abap
DATA(lv_name) = lt_carriers[ carrid = p_carrid ]-carrname.
```

입력값이 외부에서 온다면 찾지 못할 가능성이 있는데, 그 가능성이 코드에 드러나지 않는다.

### 22.3 지나친 한 줄 코드 경계

다음처럼 너무 많은 로직을 한 줄에 넣으면 오히려 읽기 어렵다.

```abap
DATA(lv_text) = |Carrier: { lt_carriers[ carrid = p_carrid ]-carrname }|.
```

해당 항공사가 없으면 문자열 템플릿 생성 중 예외가 발생할 수 있다.  
명확한 처리가 필요하다.

개선 예:

```abap
DATA(ls_carrier) = VALUE ty_carrier(
  lt_carriers[ carrid = p_carrid ]
  DEFAULT VALUE #( carrid = p_carrid carrname = 'Unknown Carrier' )
).

DATA(lv_text) = |Carrier: { ls_carrier-carrname }|.
```

## 23. 후속 모듈 연결

이번 모듈에서 Table Expression을 배웠다면 다음 모듈 `THEORY-16-M05 — String Template과 내장 함수`와 자연스럽게 연결된다.

예를 들어 다음 코드는 Table Expression과 String Template이 결합된 형태이다.

```abap
DATA(lv_message) = |Carrier name: { lt_carriers[ carrid = 'LH' ]-carrname }|.
```

하지만 위 코드는 `LH`가 없으면 예외 가능성이 있다.  
따라서 다음 모듈에서는 문자열 템플릿 자체뿐 아니라, 값 생성 전에 데이터를 안전하게 준비하는 감각도 함께 필요하다.

또한 `THEORY-16-M06`에서는 Legacy 코드를 Modern ABAP으로 리팩터링하면서 다음 비교가 중요해진다.

```text
READ TABLE + sy-subrc
→ Table Expression + line_exists/OPTIONAL/DEFAULT/ASSIGN
```

### 24.2 단답형

#### Q1. Table Expression과 READ TABLE의 실패 처리 차이를 설명하시오.

모범 답안:  
`READ TABLE`은 행을 찾지 못하면 일반적으로 `sy-subrc`를 통해 실패 여부를 확인한다. 반면 Table Expression은 행을 찾지 못하면 기본적으로 예외가 발생할 수 있으므로 `line_exists`, `OPTIONAL`, `DEFAULT`, `ASSIGN`, 예외 처리 등을 상황에 맞게 사용해야 한다.

#### Q2. `OPTIONAL`과 `DEFAULT`의 차이를 설명하시오.

모범 답안:  
`OPTIONAL`은 행을 찾지 못할 때 결과 타입의 초기값을 반환한다. `DEFAULT`는 행을 찾지 못할 때 개발자가 지정한 대체 값을 반환한다.

#### Q3. 반복문 안에서 Table Expression을 사용할 때 주의할 점은 무엇인가?

모범 답안:  
반복문 안에서 Standard Table을 조건 검색하면 반복마다 선형 검색이 발생할 수 있다. 데이터가 많으면 성능 문제가 생길 수 있으므로 Sorted Table, Hashed Table, Secondary Key 또는 조회 전략을 검토해야 한다.

## 26. 핵심 요약

```text
Table Expression은 내부 테이블의 한 줄을 표현식처럼 읽는 Modern ABAP 문법이다.
문법은 간결하지만, 행이 없을 때 기본적으로 예외가 발생할 수 있다.
없을 수 있는 데이터는 line_exists, OPTIONAL, DEFAULT, ASSIGN, TRY...CATCH로 안전하게 처리한다.
OPTIONAL은 초기값, DEFAULT는 지정한 대체값을 반환한다.
성능은 Table Expression 자체가 아니라 내부 테이블 종류와 Key 설계에 좌우된다.
```
