## 2. 선수 지식

| 선수 지식 | 필요한 이유 |

## 3. Inline Declaration이란 무엇인가?

Inline Declaration은 변수를 미리 선언하지 않고, 변수가 사용되는 위치에서 바로 선언하는 Modern ABAP 문법이다.

전통적인 ABAP에서는 보통 프로그램 상단에 변수를 먼저 선언했다.

```abap
DATA lt_scarr TYPE TABLE OF scarr.

SELECT *
  FROM scarr
  INTO TABLE lt_scarr.
```

Modern ABAP에서는 다음처럼 결과를 받는 위치에서 바로 선언할 수 있다.

```abap
SELECT *
  FROM scarr
  INTO TABLE @DATA(lt_scarr).
```

두 코드는 비슷한 일을 한다.  
하지만 두 번째 코드는 `lt_scarr`가 어디서 처음 만들어지는지 바로 보인다.

### 3.1 핵심 개념

Inline Declaration은 “타입을 모른 채 아무 변수나 만드는 기능”이 아니다.  
ABAP 컴파일러가 해당 위치의 문맥을 보고 타입을 결정할 수 있을 때만 가능하다.

예를 들어 `SELECT * FROM scarr INTO TABLE @DATA(lt_scarr)`에서는 `SCARR` 테이블의 라인 구조를 컴파일러가 알 수 있다. 그래서 `LT_SCARR`의 타입을 추론할 수 있다.

```text
SELECT 대상: SCARR
결과 형태: Internal Table
추론 결과: LT_SCARR = SCARR 구조의 Internal Table
```

## 4. 전통 선언 방식과 Inline Declaration 비교

### 4.1 전통 방식

```abap
DATA lt_flights TYPE STANDARD TABLE OF sflight.
DATA ls_flight  TYPE sflight.

SELECT *
  FROM sflight
  INTO TABLE lt_flights
  UP TO 10 ROWS.

LOOP AT lt_flights INTO ls_flight.
  WRITE: / ls_flight-carrid, ls_flight-connid, ls_flight-fldate.
ENDLOOP.
```

장점은 명확하다.

- 변수 타입이 상단에 모여 있다.
- 초급자가 타입을 눈으로 확인하기 쉽다.
- 오래된 코드와 호환성이 높다.

하지만 단점도 있다.

- 변수가 어디에서 처음 사용되는지 찾기 어렵다.
- 긴 프로그램에서는 상단 선언부가 비대해진다.
- 실제로 한 번만 쓰는 임시 변수도 전역처럼 보인다.

### 4.2 Inline 방식

```abap
SELECT *
  FROM sflight
  INTO TABLE @DATA(lt_flights)
  UP TO 10 ROWS.

LOOP AT lt_flights INTO DATA(ls_flight).
  WRITE: / ls_flight-carrid, ls_flight-connid, ls_flight-fldate.
ENDLOOP.
```

장점은 다음과 같다.

- 변수가 필요한 위치에서 바로 보인다.
- 일회성 변수의 목적이 명확하다.
- 선언부가 과도하게 길어지지 않는다.
- Open SQL, LOOP, READ TABLE, Method Call과 자연스럽게 결합된다.

주의할 점도 있다.

- 타입이 문맥에서 추론되므로 초급자는 실제 타입을 놓치기 쉽다.
- 너무 긴 표현식 안에 Inline 변수를 남발하면 오히려 읽기 어려워진다.
- 변수의 유효 범위와 재사용 가능성을 고려해야 한다.

## 5. `DATA(...)` 기본 문법

Inline Declaration에서 가장 많이 사용하는 형태는 `DATA(...)`이다.

```abap
DATA(variable_name)
```

단독으로 쓰는 것이 아니라, 타입을 추론할 수 있는 위치에서 사용한다.

대표 예시는 다음과 같다.

```abap
SELECT SINGLE carrid, carrname
  FROM scarr
  INTO @DATA(ls_carrier)
  WHERE carrid = 'AA'.
```

```abap
SELECT carrid, connid, cityfrom, cityto
  FROM spfli
  INTO TABLE @DATA(lt_connection)
  WHERE carrid = 'LH'.
```

```abap
LOOP AT lt_connection INTO DATA(ls_connection).
  WRITE: / ls_connection-carrid, ls_connection-connid.
ENDLOOP.
```

```abap
READ TABLE lt_connection INTO DATA(ls_first_connection) INDEX 1.
```

여기서 `DATA(...)`는 새로운 변수를 선언한다.  
이미 선언되어 있는 변수에 값을 넣는 문법이 아니다.

## 6. `FIELD-SYMBOL(...)` 기본 문법

Field Symbol은 데이터를 복사하지 않고 기존 데이터 객체를 참조하듯 접근할 때 사용한다.  
전통적으로는 다음처럼 미리 선언했다.

```abap
FIELD-SYMBOLS <ls_connection> TYPE spfli.

LOOP AT lt_connection ASSIGNING <ls_connection>.
  <ls_connection>-cityto = 'SEOUL'.
ENDLOOP.
```

Inline 방식에서는 다음처럼 사용할 수 있다.

```abap
LOOP AT lt_connection ASSIGNING FIELD-SYMBOL(<ls_connection>).
  <ls_connection>-cityto = 'SEOUL'.
ENDLOOP.
```

또는 `READ TABLE`에서 사용할 수 있다.

```abap
READ TABLE lt_connection
  ASSIGNING FIELD-SYMBOL(<ls_connection>)
  WITH KEY carrid = 'LH'
           connid = '0400'.

IF sy-subrc = 0.
  <ls_connection>-cityto = 'SEOUL'.
ENDIF.
```

### 6.1 `DATA(...)`와 `FIELD-SYMBOL(...)`의 감각 차이

| 구분 | `DATA(...)` | `FIELD-SYMBOL(...)` |
|---|---|---|
| 성격 | 값을 받을 변수 선언 | 기존 데이터 객체를 참조하는 Field Symbol 선언 |
| 대표 사용 | `INTO DATA(...)` | `ASSIGNING FIELD-SYMBOL(...)` |
| 데이터 복사 | 일반적으로 복사 발생 가능 | 복사하지 않고 참조 접근 |
| 수정 영향 | 원본과 별도 변수일 수 있음 | 원본 Internal Table 라인에 직접 영향 |
| 초급자 주의 | 타입 추론 확인 | 원본 변경 여부 확인 |

초급자는 다음 문장을 기억하면 된다.

```text
INTO DATA(...)는 값을 받아오는 느낌이고,
ASSIGNING FIELD-SYMBOL(...)은 원본 줄을 직접 잡는 느낌이다.
```

## 7. Inline Declaration이 가능한 대표 위치

Inline Declaration은 아무 곳에서나 가능한 것이 아니라, 선언 위치가 문법적으로 허용되고 타입이 추론 가능한 위치에서 가능하다.

초급 단계에서 반드시 알아야 할 대표 위치는 다음과 같다.

| 위치 | 예시 |
|---|---|
| Open SQL 결과 수신 | `INTO TABLE @DATA(lt_result)` |
| 단건 SELECT 결과 수신 | `INTO @DATA(ls_result)` |
| LOOP Work Area | `LOOP AT itab INTO DATA(ls_line)` |
| LOOP Field Symbol | `LOOP AT itab ASSIGNING FIELD-SYMBOL(<ls_line>)` |
| READ TABLE 결과 | `READ TABLE itab INTO DATA(ls_line)` |
| READ TABLE Field Symbol | `READ TABLE itab ASSIGNING FIELD-SYMBOL(<ls_line>)` |
| ASSIGN 결과 | `ASSIGN component TO FIELD-SYMBOL(<lv_value>)` |
| Method 결과 수신 | `DATA(result) = object->method( )` |
| TRY-CATCH 예외 객체 | `CATCH cx_root INTO DATA(lx_error)` |

모든 예시를 한 번에 외울 필요는 없다.  
실무에서 가장 자주 보는 것은 `SELECT`, `LOOP`, `READ TABLE`, `CATCH`이다.

## 8. Open SQL에서 Inline Declaration 사용

### 8.1 테이블 전체 조회 결과 받기

전통 방식:

```abap
DATA lt_scarr TYPE STANDARD TABLE OF scarr.

SELECT *
  FROM scarr
  INTO TABLE lt_scarr.
```

Modern 방식:

```abap
SELECT *
  FROM scarr
  INTO TABLE @DATA(lt_scarr).
```

S/4HANA 기준의 Modern Open SQL에서는 ABAP 변수와 SQL 표현을 구분하기 위해 Host Variable 앞에 `@`를 사용한다.  
`@DATA(lt_scarr)`는 SQL 결과를 받을 ABAP 변수를 Inline으로 선언한다는 의미이다.

### 8.2 필요한 필드만 조회하기

```abap
SELECT carrid,
       carrname,
       currcode
  FROM scarr
  INTO TABLE @DATA(lt_carrier).
```

이 경우 `LT_CARRIER`는 `SCARR` 전체 구조가 아니라, 선택한 필드로 구성된 Internal Table이 된다.

즉, 다음과 같은 구조를 가진 결과라고 이해할 수 있다.

```text
CARRID
CARRNAME
CURRCODE
```

초급자가 자주 하는 오해는 `SELECT carrid, carrname`처럼 일부 필드만 가져와도 결과가 항상 `SCARR` 타입이라고 생각하는 것이다.  
실제로는 선택한 필드 목록에 맞는 결과 구조가 만들어진다.

### 8.3 단건 조회

```abap
SELECT SINGLE carrid,
              carrname,
              currcode
  FROM scarr
  INTO @DATA(ls_carrier)
  WHERE carrid = 'AA'.

IF sy-subrc = 0.
  WRITE: / ls_carrier-carrid, ls_carrier-carrname.
ENDIF.
```

이 예제에서 `LS_CARRIER`는 단일 구조 변수이다.  
`INTO TABLE`이 아니므로 Internal Table이 아니다.

## 9. LOOP에서 Inline Declaration 사용

### 9.1 Work Area를 Inline으로 선언

```abap
SELECT carrid,
       connid,
       cityfrom,
       cityto
  FROM spfli
  INTO TABLE @DATA(lt_connection)
  WHERE carrid = 'LH'.

LOOP AT lt_connection INTO DATA(ls_connection).
  WRITE: / ls_connection-carrid,
           ls_connection-connid,
           ls_connection-cityfrom,
           ls_connection-cityto.
ENDLOOP.
```

`LS_CONNECTION`은 `LOOP AT`에서 현재 라인을 담는 Work Area이다.  
Inline Declaration을 사용하면 Work Area가 Loop 바로 옆에서 선언되므로 읽기 쉽다.

### 9.2 Field Symbol을 Inline으로 선언

```abap
LOOP AT lt_connection ASSIGNING FIELD-SYMBOL(<ls_connection>).
  WRITE: / <ls_connection>-carrid,
           <ls_connection>-connid,
           <ls_connection>-cityfrom,
           <ls_connection>-cityto.
ENDLOOP.
```

Field Symbol 방식은 원본 Internal Table 라인을 직접 참조한다.  
단순 출력만 할 때는 `INTO DATA(...)`와 `ASSIGNING FIELD-SYMBOL(...)` 모두 가능하지만, 원본 라인을 직접 변경하려면 Field Symbol 방식이 자주 사용된다.

### 9.3 수정 예시

```abap
LOOP AT lt_connection ASSIGNING FIELD-SYMBOL(<ls_connection>).
  IF <ls_connection>-cityto = 'FRANKFURT'.
    <ls_connection>-cityto = 'SEOUL'.
  ENDIF.
ENDLOOP.
```

이 코드는 `LT_CONNECTION` 안의 라인을 직접 변경한다.  
따라서 초급자는 Field Symbol을 사용할 때 “원본이 바뀌는가?”를 반드시 의식해야 한다.

## 10. READ TABLE에서 Inline Declaration 사용

### 10.1 INTO DATA

```abap
READ TABLE lt_connection
  INTO DATA(ls_connection)
  WITH KEY carrid = 'LH'
           connid = '0400'.

IF sy-subrc = 0.
  WRITE: / ls_connection-cityfrom, ls_connection-cityto.
ENDIF.
```

이 경우 `LS_CONNECTION`은 찾은 라인의 값을 복사해서 담는 Work Area이다.

### 10.2 ASSIGNING FIELD-SYMBOL

```abap
READ TABLE lt_connection
  ASSIGNING FIELD-SYMBOL(<ls_connection>)
  WITH KEY carrid = 'LH'
           connid = '0400'.

IF sy-subrc = 0.
  <ls_connection>-cityto = 'SEOUL'.
ENDIF.
```

이 경우 `<LS_CONNECTION>`은 찾은 라인을 직접 가리킨다.  
따라서 값을 변경하면 Internal Table의 해당 라인이 변경된다.

### 10.3 `sy-subrc` 확인

`READ TABLE`은 실패할 수 있다.  
Inline으로 선언했다고 해서 실패 처리가 없어지는 것은 아니다.

```abap
READ TABLE lt_connection
  INTO DATA(ls_connection)
  WITH KEY carrid = 'XX'.

IF sy-subrc <> 0.
  WRITE: / 'No matching row found.'.
  RETURN.
ENDIF.

WRITE: / ls_connection-carrid, ls_connection-connid.
```

Modern ABAP 문법을 사용하더라도 오류 가능성과 검증 포인트는 그대로 남는다.  
문법이 짧아졌다고 예외 상황까지 사라지는 것은 아니다.

## 11. Method Call에서 Inline Declaration 사용

OO ABAP에서는 Method의 반환값이나 Exporting 값을 받을 때 Inline Declaration을 자주 사용한다.

예를 들어 Factory Method가 객체 참조를 반환한다고 가정한다.

```abap
DATA(lo_service) = zcl_demo_service=>create( ).
```

이 경우 `LO_SERVICE`의 타입은 `CREATE` 메서드의 반환 타입에서 추론된다.

### 11.1 결과가 명확한 경우

Inline Declaration이 좋은 경우는 반환 타입과 변수 목적이 명확한 경우이다.

```abap
DATA(lv_today) = sy-datum.
DATA(lv_user)  = sy-uname.
```

또는 Method 이름이 충분히 명확한 경우이다.

```abap
DATA(lt_customer) = lo_repository->get_customer_list( ).
```

### 11.2 타입이 중요할 때는 명시 선언도 고려

다음처럼 결과 타입이 중요한 경우에는 Inline만으로는 학습자나 유지보수자가 헷갈릴 수 있다.

```abap
DATA(result) = lo_service->execute( ).
```

`RESULT`가 구조인지, 테이블인지, 객체 참조인지, 문자열인지 이름만 보고 알기 어렵다.  
이럴 때는 변수명을 더 명확히 하거나 명시 타입 선언을 고려한다.

좋은 예:

```abap
DATA(lt_sales_order) = lo_service->get_sales_orders( ).
DATA(ls_summary)     = lo_service->calculate_summary( ).
DATA(lv_message)     = lo_service->build_message( ).
```

## 12. CATCH에서 Inline Declaration 사용

예외 처리를 할 때도 Inline Declaration을 자주 사용한다.

```abap
TRY.
    DATA(lv_result) = 10 / 0.
  CATCH cx_sy_zerodivide INTO DATA(lx_zero_divide).
    WRITE: / lx_zero_divide->get_text( ).
ENDTRY.
```

또는 상위 예외 타입으로 받을 수 있다.

```abap
TRY.
    " risky logic
  CATCH cx_root INTO DATA(lx_root).
    WRITE: / lx_root->get_text( ).
ENDTRY.
```

초급자는 다음을 기억하면 된다.

```text
CATCH ... INTO DATA(lx_error)는 예외 객체를 그 위치에서 바로 선언하는 패턴이다.
```

## 13. Scope와 Lifetime 이해

Inline Declaration을 사용하면 “변수가 그 줄 안에서만 존재하는가?”라고 오해할 수 있다.  
ABAP의 Inline Declaration 변수는 선언된 처리 블록 안에서 사용할 수 있다.

예를 들어 다음 코드는 일반적으로 같은 처리 블록 안에서 `LT_SCARR`를 계속 사용할 수 있다.

```abap
SELECT *
  FROM scarr
  INTO TABLE @DATA(lt_scarr).

WRITE: / lines( lt_scarr ).
```

`LT_SCARR`는 SELECT 문 한 줄에서만 존재하는 것이 아니다.  
선언된 위치 이후 같은 유효 범위 안에서 사용할 수 있다.

다만 초급자가 주의해야 할 점은 다음이다.

| 주의점 | 설명 |
|---|---|
| 너무 멀리 재사용하지 않기 | Inline 변수는 가까운 범위에서 쓰일 때 가장 읽기 좋다. |
| 이름 중복 주의 | 같은 Scope 안에서 같은 이름으로 다시 선언할 수 없다. |
| 의도 명확성 | 재사용이 많은 변수라면 상단 명시 선언이 더 나을 수 있다. |

---

## 14. Inline Declaration이 좋은 경우

Inline Declaration은 다음 상황에서 특히 좋다.

| 상황 | 이유 |
|---|---|
| SQL 조회 결과를 바로 받을 때 | 결과 구조가 SQL 문에서 명확하다. |
| LOOP Work Area가 해당 LOOP에서만 필요할 때 | 변수의 사용 범위가 명확하다. |
| READ TABLE 결과가 바로 다음 로직에서만 필요할 때 | 일회성 변수임이 분명하다. |
| Method 결과를 즉시 사용할 때 | 선언과 사용 흐름이 가까워진다. |
| 예외 객체를 CATCH 블록에서만 사용할 때 | 예외 처리 범위가 명확하다. |

예:

```abap
READ TABLE lt_scarr INTO DATA(ls_scarr) WITH KEY carrid = 'AA'.

IF sy-subrc = 0.
  WRITE: / ls_scarr-carrname.
ENDIF.
```

## 15. Inline Declaration을 피하거나 신중히 써야 하는 경우

Inline Declaration이 항상 좋은 것은 아니다.

| 상황 | 이유 |
|---|---|
| 변수가 긴 범위에서 계속 재사용됨 | 선언 위치와 사용 위치가 멀어져 혼란이 생길 수 있다. |
| 타입이 업무적으로 중요함 | 명시 타입이 문서 역할을 할 수 있다. |
| 결과 타입이 추론만으로 불명확함 | 유지보수자가 타입을 즉시 알기 어렵다. |
| 복잡한 표현식 안에 중첩됨 | 한 줄이 과도하게 길어질 수 있다. |
| 교육 초반 타입 설명이 필요한 경우 | 초급자에게는 명시 선언이 더 이해하기 쉬울 수 있다. |

나쁜 예:

```abap
DATA(result) = lo_srv->run( ).
```

개선 예:

```abap
DATA(ls_order_summary) = lo_order_service->calculate_order_summary( ).
```

또는 명시 선언:

```abap
DATA ls_order_summary TYPE zs_order_summary.

ls_order_summary = lo_order_service->calculate_order_summary( ).
```

## 16. Naming Convention

Inline Declaration을 사용하면 변수명이 더 중요해진다.  
타입 선언이 보이지 않는 경우가 많기 때문에, 변수명이 타입과 의미를 어느 정도 드러내야 한다.

| Prefix | 의미 | 예시 |
|---|---|---|
| `LV_` | Local Value, 단일 값 | `lv_count`, `lv_message` |
| `LS_` | Local Structure | `ls_carrier`, `ls_connection` |
| `LT_` | Local Table | `lt_carrier`, `lt_connection` |
| `LO_` | Local Object Reference | `lo_service`, `lo_alv` |
| `LX_` | Local Exception | `lx_error`, `lx_root` |
| `<LS_...>` | Field Symbol Structure | `<ls_connection>` |

예:

```abap
SELECT *
  FROM scarr
  INTO TABLE @DATA(lt_carrier).

LOOP AT lt_carrier INTO DATA(ls_carrier).
  WRITE: / ls_carrier-carrid, ls_carrier-carrname.
ENDLOOP.
```

`LT_`, `LS_` Prefix를 사용하면 Inline 선언에서도 변수 성격이 즉시 보인다.

## 17. 실습 1 — SELECT 결과 Inline 선언

### 17.1 실습 목표

`SCARR` 테이블을 조회하여 결과 Internal Table을 Inline으로 선언한다.

### 17.2 예제 코드

```abap
REPORT zedu_m16_inline_01.

SELECT carrid,
       carrname,
       currcode
  FROM scarr
  INTO TABLE @DATA(lt_carrier).

IF sy-subrc <> 0.
  WRITE: / 'No carrier data found.'.
  RETURN.
ENDIF.

WRITE: / 'Carrier count:', lines( lt_carrier ).

LOOP AT lt_carrier INTO DATA(ls_carrier).
  WRITE: / ls_carrier-carrid,
           ls_carrier-carrname,
           ls_carrier-currcode.
ENDLOOP.
```

### 17.3 확인 포인트

| 확인 항목 | 설명 |
|---|---|
| `LT_CARRIER` 선언 위치 | `INTO TABLE @DATA(lt_carrier)`에서 선언됨 |
| `LS_CARRIER` 선언 위치 | `LOOP AT ... INTO DATA(ls_carrier)`에서 선언됨 |
| `sy-subrc` 확인 | SELECT 결과 존재 여부 확인 |
| `lines( )` 사용 | Internal Table 건수 확인 |

## 18. 실습 2 — READ TABLE 결과 Inline 선언

### 18.1 실습 목표

Internal Table에서 특정 항공사를 읽고, 성공 여부를 확인한다.

### 18.2 예제 코드

```abap
REPORT zedu_m16_inline_02.

SELECT carrid,
       carrname,
       currcode
  FROM scarr
  INTO TABLE @DATA(lt_carrier).

ELSE.

ENDIF.
```

| 항목 | 기대 결과 |
|---|---|
| `sy-subrc` | 0이 아님 |
| 출력 | `Carrier not found.` |

## 19. 실습 3 — Field Symbol Inline 선언

### 19.1 실습 목표

Internal Table 라인을 Field Symbol로 접근하고, 원본 값 변경 가능성을 이해한다.

### 19.2 예제 코드

```abap
REPORT zedu_m16_inline_03.

SELECT carrid,
       connid,
       cityfrom,
       cityto
  FROM spfli
  INTO TABLE @DATA(lt_connection)
  UP TO 10 ROWS.

LOOP AT lt_connection ASSIGNING FIELD-SYMBOL(<ls_connection>).
  IF <ls_connection>-cityto IS INITIAL.
    <ls_connection>-cityto = 'UNKNOWN'.
  ENDIF.
ENDLOOP.

LOOP AT lt_connection INTO DATA(ls_connection).
  WRITE: / ls_connection-carrid,
           ls_connection-connid,
           ls_connection-cityfrom,
           ls_connection-cityto.
ENDLOOP.
```

### 19.3 확인 포인트

| 확인 항목 | 설명 |
|---|---|
| `<LS_CONNECTION>` | Field Symbol로 Inline 선언됨 |
| 원본 변경 | `ASSIGNING`으로 접근한 라인을 직접 변경 |
| 출력 Loop | 변경 결과가 Internal Table에 반영되었는지 확인 |

## 21. 자주 발생하는 오류

### 21.1 `@` 누락

Modern Open SQL에서 Host Variable을 사용할 때 `@`를 누락하면 Syntax Error가 발생할 수 있다.

잘못된 예:

```abap
SELECT *
  FROM scarr
  INTO TABLE DATA(lt_scarr).
```

개선 예:

```abap
SELECT *
  FROM scarr
  INTO TABLE @DATA(lt_scarr).
```

### 21.2 같은 이름 재선언

같은 Scope 안에서 같은 이름을 다시 Inline 선언하면 오류가 발생한다.

```abap
SELECT *
  FROM scarr
  INTO TABLE @DATA(lt_scarr).

SELECT *
  FROM spfli
  INTO TABLE @DATA(lt_scarr). " 같은 이름 재선언 문제
```

개선 예:

```abap
SELECT *
  FROM scarr
  INTO TABLE @DATA(lt_carrier).

SELECT *
  FROM spfli
  INTO TABLE @DATA(lt_connection).
```

### 21.3 결과 타입 오해

일부 필드만 조회했는데 전체 테이블 구조라고 착각하는 경우가 있다.

```abap
SELECT carrid,
       carrname
  FROM scarr
  INTO TABLE @DATA(lt_carrier).
```

이 결과는 `SCARR` 전체 구조가 아니다.  
선택한 필드 중심의 결과 구조로 이해해야 한다.

### 21.4 Field Symbol 원본 변경 오해

```abap
LOOP AT lt_data ASSIGNING FIELD-SYMBOL(<ls_data>).
  <ls_data>-status = 'X'.
ENDLOOP.
```

이 코드는 원본 Internal Table의 `STATUS` 값을 바꿀 수 있다.  
단순 조회 목적이라면 `INTO DATA(...)`가 더 안전하고 직관적일 수 있다.

## 22. 실무 적용 기준

### 22.1 적극 사용해도 좋은 패턴

| 패턴 | 예시 |
|---|---|
| SELECT 결과 테이블 | `INTO TABLE @DATA(lt_result)` |
| LOOP 일회성 Work Area | `LOOP AT itab INTO DATA(ls_line)` |

| CATCH 예외 객체 | `CATCH cx_root INTO DATA(lx_root)` |

| 재사용 범위가 넓은 변수 | 선언 위치가 오히려 혼란 |
| 타입이 업무적으로 중요한 변수 | 명시 타입이 문서 역할을 함 |

## 23. Clean Code 관점

Inline Declaration은 Modern ABAP의 핵심 문법 중 하나이지만, 단순히 “짧은 코드”를 만드는 도구로만 사용하면 안 된다.

좋은 코드는 다음 조건을 만족해야 한다.

| 조건 | 설명 |
|---|---|
| 의도 명확성 | 변수명이 역할을 설명한다. |
| 범위 최소화 | 변수가 필요한 위치 가까이에서 선언된다. |
| 타입 추론 가능성 | 문맥상 타입이 자연스럽게 드러난다. |
| 예외 처리 유지 | 짧아져도 실패 처리는 생략하지 않는다. |
| 일관성 | 프로젝트 스타일과 팀 규칙을 따른다. |

나쁜 Modernization은 코드만 짧게 만든다.  
좋은 Modernization은 코드의 의도를 더 빠르게 읽게 만든다.

## 24. 초급자 핵심 요약

```text
Inline Declaration은 변수를 사용하는 위치에서 바로 선언하는 Modern ABAP 문법이다.
DATA(...)는 일반 변수 선언에 사용한다.
FIELD-SYMBOL(...)은 Field Symbol 선언에 사용한다.
Open SQL에서는 @DATA(...) 형태를 자주 사용한다.
LOOP, READ TABLE, CATCH에서도 Inline Declaration을 자주 사용한다.
타입은 문맥에서 추론되므로 변수명을 더 명확히 써야 한다.
짧은 코드가 항상 좋은 코드는 아니다.
```

## 25. 평가 문제

### 25.1 객관식

#### Q1. Inline Declaration의 설명으로 가장 적절한 것은?

A. ABAP에서 변수를 아예 만들지 않는 기능이다.  
B. 변수가 필요한 위치에서 타입 추론을 통해 선언하는 문법이다.  
C. 모든 전역 변수를 자동으로 삭제하는 기능이다.  
D. DB 테이블을 자동 생성하는 DDIC 기능이다.

**정답:** B

#### Q2. Open SQL에서 Inline Declaration을 사용할 때 올바른 구문은?

A. `INTO TABLE DATA(lt_scarr)`  
B. `INTO TABLE @DATA(lt_scarr)`  
C. `INTO TABLE FIELD-SYMBOL(lt_scarr)`  
D. `DATA INTO TABLE lt_scarr`

**정답:** B

#### Q3. 원본 Internal Table 라인을 직접 변경할 가능성이 큰 구문은?

A. `LOOP AT itab INTO DATA(ls_line)`  
B. `LOOP AT itab ASSIGNING FIELD-SYMBOL(<ls_line>)`  
C. `WRITE ls_line`  
D. `DATA(lv_text) = 'ABC'`

**정답:** B

### 25.2 단답형

#### Q1. `DATA(...)`와 `FIELD-SYMBOL(...)`의 차이를 설명하시오.

**모범 답안:**  
`DATA(...)`는 값을 받을 일반 변수를 Inline으로 선언하는 문법이고, `FIELD-SYMBOL(...)`은 기존 데이터 객체를 참조하는 Field Symbol을 Inline으로 선언하는 문법이다. `ASSIGNING FIELD-SYMBOL(...)`을 사용하면 Internal Table의 원본 라인을 직접 변경할 수 있다.

#### Q2. Inline Declaration을 남발하면 안 되는 이유를 설명하시오.

**모범 답안:**  
타입이 문맥에서 추론되기 때문에 변수명과 사용 위치가 명확하지 않으면 오히려 읽기 어려워질 수 있다. 또한 긴 범위에서 재사용되는 변수나 타입이 중요한 변수는 명시 선언이 더 적합할 수 있다.

#### Q3. `SELECT carrid, carrname FROM scarr INTO TABLE @DATA(lt_result)`에서 `LT_RESULT`가 항상 `SCARR` 전체 구조라고 볼 수 없는 이유는?

**모범 답안:**  
SELECT 문에서 `CARRID`, `CARRNAME` 두 필드만 조회했기 때문에 결과 구조는 선택한 필드 목록을 기준으로 구성된다. `SCARR` 테이블의 모든 필드를 포함하는 전체 구조라고 볼 수 없다.

예를 들어 다음과 같은 Modern ABAP 패턴은 두 문법이 함께 사용된다.

```abap
DATA(ls_carrier) = VALUE scarr(
  carrid   = 'ZZ'
  carrname = 'Demo Carrier'
  currcode = 'KRW'
).
```

이번 모듈에서 `DATA(...)`로 변수 선언 위치를 간소화하는 방법을 배웠다면, 다음 모듈에서는 `VALUE`로 구조와 Internal Table 값을 더 간결하게 생성하는 방법을 배운다.
