## 0. 이 문서의 학습 범위

이 문서는 `THEORY-16-M03 — CORRESPONDING과 구조 매핑`만 다룬다.

이번 모듈의 중심 주제는 Modern ABAP의 `CORRESPONDING` Constructor Operator이다.  
`CORRESPONDING`은 **같은 이름의 Component를 기준으로 구조체 또는 내부 테이블 데이터를 매핑**할 때 사용하는 표현식 기반 문법이다.

초급자가 가장 먼저 기억해야 할 문장은 다음이다.

```text
CORRESPONDING은 “이름이 같은 필드끼리 값을 옮기는” 구조 매핑 문법이다.
MAPPING은 이름이 다른 필드 간의 명시적 연결이다.
EXCEPT는 매핑 대상에서 제외할 필드를 지정하는 안전장치이다.
```

이전 모듈 `THEORY-16-M02`에서 `VALUE` Constructor Expression으로 구조체와 내부 테이블을 만드는 방법을 배웠다면, 이번 모듈에서는 **이미 존재하는 구조체 또는 내부 테이블의 값을 다른 타입으로 옮기는 방법**을 학습한다.

## 1. 왜 CORRESPONDING을 배우는가?

실무 ABAP에서는 같은 업무 데이터를 서로 다른 구조로 옮기는 일이 매우 많다.

예를 들어 다음 상황을 생각해볼 수 있다.

```text
DB 조회 결과 → ALV 출력 구조
BAPI 반환 구조 → 화면 출력 구조
Legacy 구조 → 신규 구조
Function Module 파라미터 → Class Method 파라미터
CDS 조회 결과 → Report 출력 구조
```

이때 필드를 하나씩 옮기면 코드가 길어지고 실수 가능성이 커진다.

전통적인 코드는 다음처럼 작성되는 경우가 많다.

```abap
ls_output-carrid   = ls_source-carrid.
ls_output-connid   = ls_source-connid.
ls_output-fldate   = ls_source-fldate.
ls_output-price    = ls_source-price.
ls_output-currency = ls_source-currency.
```

필드가 5개라면 괜찮아 보이지만, 30개 또는 50개가 되면 유지보수가 어려워진다.  
또한 필드가 추가되었을 때 누락되기 쉽고, 이름이 비슷한 필드를 잘못 연결할 위험도 있다.

`CORRESPONDING`을 사용하면 같은 이름의 필드는 한 번에 매핑할 수 있다.

```abap
ls_output = CORRESPONDING #( ls_source ).
```

이 한 줄은 다음 의미를 가진다.

```text
ls_source와 ls_output에서 이름이 같은 Component를 찾아 값을 옮긴다.
```

## 3. CORRESPONDING의 기본 개념

### 3.1 기본 문법

가장 단순한 형태는 다음과 같다.

```abap
DATA(ls_target) = CORRESPONDING ty_target( ls_source ).
```

또는 대상 변수의 타입이 이미 정해져 있다면 다음처럼 사용할 수 있다.

```abap
ls_target = CORRESPONDING #( ls_source ).
```

여기서 `#`는 컴파일러가 문맥을 기준으로 결과 타입을 추론하라는 의미이다.

| 요소 | 의미 |
|---|---|
| `CORRESPONDING` | 이름 기준 구조 매핑 Constructor Operator |
| `ty_target` | 생성할 결과 구조 타입 |
| `ls_source` | 원본 구조체 |
| `#` | 문맥 기반 타입 추론 |

### 3.2 기본 동작

`CORRESPONDING`은 기본적으로 다음 규칙을 따른다.

| 규칙 | 설명 |
|---|---|
| 같은 이름 | Source와 Target에 같은 이름의 Component가 있으면 값을 옮긴다. |
| Target에만 있는 필드 | Source에 같은 이름이 없으면 초기값이 유지되거나 생성 시 초기값이 된다. |
| Source에만 있는 필드 | Target에 없으면 무시된다. |
| 이름이 다른 필드 | 자동으로 매핑되지 않는다. |
| 타입 변환 | 가능한 경우 ABAP 표준 변환 규칙에 따라 처리된다. 단, 의미 검증은 하지 않는다. |

## 4. Legacy MOVE-CORRESPONDING과 Modern CORRESPONDING

### 4.1 전통 문법: MOVE-CORRESPONDING

기존 ABAP에서는 다음처럼 작성했다.

```abap
MOVE-CORRESPONDING ls_source TO ls_target.
```

이 문법도 같은 이름의 Component를 찾아 값을 옮긴다.  
그러나 Modern ABAP에서는 표현식 기반 코드를 위해 `CORRESPONDING` Constructor Operator를 더 자주 사용한다.

### 4.2 Modern 문법: CORRESPONDING

```abap
ls_target = CORRESPONDING #( ls_source ).
```

또는 새 변수를 즉시 만들 수 있다.

```abap
DATA(ls_target) = CORRESPONDING ty_target( ls_source ).
```

### 4.3 비교표

| 구분 | MOVE-CORRESPONDING | CORRESPONDING Constructor |
|---|---|---|
| 문법 성격 | 명령문 중심 | 표현식 중심 |
| Inline Declaration | 직접 결합하기 어려움 | 자연스럽게 결합 가능 |
| BASE 조합 | 제한적 | 가능 |
| MAPPING/EXCEPT | Modern 방식으로 명시 가능 | 가능 |
| Modern ABAP 가독성 | 상대적으로 낮음 | 높음 |
| 기존 코드 호환성 | 높음 | 최신 문법 기준 적합 |

실무에서는 기존 코드에 `MOVE-CORRESPONDING`이 많이 남아 있을 수 있다.  
그러나 신규 코드나 리팩터링 대상 코드에서는 `CORRESPONDING #( ... )`이 더 의도가 명확한 경우가 많다.

## 5. 기본 예제: 같은 이름 필드 매핑

### 5.1 타입 정의

```abap
TYPES: BEGIN OF ty_flight_source,
         carrid   TYPE s_carr_id,
         connid   TYPE s_conn_id,
         fldate   TYPE s_date,
         price    TYPE s_price,
         currency TYPE s_currcode,
       END OF ty_flight_source.

TYPES: BEGIN OF ty_flight_output,
         carrid   TYPE s_carr_id,
         connid   TYPE s_conn_id,
         fldate   TYPE s_date,
         price    TYPE s_price,
         currency TYPE s_currcode,
         status   TYPE c LENGTH 1,
       END OF ty_flight_output.
```

Source에는 `STATUS`가 없고 Target에는 `STATUS`가 있다.

### 5.2 데이터 준비

```abap
DATA(ls_source) = VALUE ty_flight_source(
  carrid   = 'AA'
  connid   = '0017'
  fldate   = sy-datum
  price    = '1200.50'
  currency = 'USD'
).
```

### 5.3 CORRESPONDING 사용

```abap
DATA(ls_output) = CORRESPONDING ty_flight_output( ls_source ).
```

결과는 다음과 같다.

| Target Field | 값 | 이유 |
|---|---|---|
| CARRID | AA | Source에 같은 이름 존재 |
| CONNID | 0017 | Source에 같은 이름 존재 |
| FLDATE | 오늘 날짜 | Source에 같은 이름 존재 |
| PRICE | 1200.50 | Source에 같은 이름 존재 |
| CURRENCY | USD | Source에 같은 이름 존재 |
| STATUS | Initial | Source에 같은 이름 없음 |

핵심은 `STATUS`가 자동으로 채워지지 않는다는 점이다.  
`CORRESPONDING`은 이름 기준 매핑이지, 업무 의미를 추론하는 기능이 아니다.

## 6. MAPPING: 이름이 다른 필드 연결

### 6.1 왜 MAPPING이 필요한가?

실무에서는 같은 의미인데 필드명이 다른 경우가 많다.

예를 들어 Source 구조는 SAP 표준 필드명을 사용하고, Target 구조는 ALV 출력용 의미 중심 필드명을 사용할 수 있다.

| Source Field | Target Field | 의미 |
|---|---|---|
| CARRID | CARRIER_ID | 항공사 |
| CONNID | CONNECTION_ID | 연결번호 |
| PRICE | AMOUNT | 금액 |
| CURRENCY | CURRENCY_CODE | 통화 |

이 경우 기본 `CORRESPONDING`만 사용하면 매핑되지 않는다.  
필드 이름이 다르기 때문이다.

### 6.2 MAPPING 문법

```abap
DATA(ls_output) = CORRESPONDING ty_flight_alv(
  ls_source
  MAPPING carrier_id    = carrid
          connection_id = connid
          amount        = price
          currency_code = currency
).
```

여기서 중요한 방향은 다음이다.

```text
MAPPING target_component = source_component
```

즉, 왼쪽은 Target 필드, 오른쪽은 Source 필드이다.

### 6.3 MAPPING 방향을 잘못 이해했을 때

다음은 초급자가 자주 헷갈리는 부분이다.

```abap
"잘못 이해한 예: source = target 방향으로 생각
MAPPING carrid = carrier_id
```

이렇게 작성하면 Target에 `CARRID`라는 Component가 있어야 한다는 의미가 된다.  
Target 구조에 `CARRID`가 없다면 문법 오류가 발생한다.

항상 다음 문장으로 기억한다.

```text
CORRESPONDING의 MAPPING은 “Target 필드 = Source 필드” 방향이다.
```

## 7. EXCEPT: 특정 필드 제외

### 7.1 왜 EXCEPT가 필요한가?

같은 이름의 필드가 있더라도 일부 필드는 옮기면 안 되는 경우가 있다.

예를 들어 다음 필드는 Source에 값이 있더라도 Target에 그대로 옮기면 안 될 수 있다.

| 필드 | 제외 이유 |
|---|---|
| CREATED_BY | 신규 생성 시 현재 사용자로 다시 채워야 함 |
| CREATED_ON | 신규 생성 시 현재 날짜로 다시 채워야 함 |
| CHANGED_BY | 변경 처리에서 별도 설정 필요 |
| CHANGED_ON | 변경 처리에서 별도 설정 필요 |
| STATUS | 업무 규칙에 따라 기본값 재설정 필요 |

### 7.2 EXCEPT 문법

```abap
DATA(ls_target) = CORRESPONDING ty_user_target(
  ls_source
  EXCEPT created_by created_on
).
```

의미는 다음과 같다.

```text
이름이 같은 필드를 매핑하되, CREATED_BY와 CREATED_ON은 제외한다.
```

### 7.3 실무에서 EXCEPT를 권장하는 경우

`CORRESPONDING`은 편리하지만 너무 넓게 사용하면 의도하지 않은 필드까지 옮길 수 있다.  
특히 감사 필드, 상태 필드, 계산 필드에는 주의가 필요하다.

| 필드 유형 | EXCEPT 검토 필요성 |
|---|---|
| 생성자/생성일 | 높음 |
| 변경자/변경일 | 높음 |
| 승인 상태 | 높음 |
| 삭제 플래그 | 높음 |
| 계산 결과 필드 | 중간 |
| 단순 설명 필드 | 낮음 |

## 8. BASE: 기존 값 유지 후 덮어쓰기

### 8.1 BASE의 목적

`BASE`는 기존 Target 값을 유지하면서 Source에서 가져온 값을 덮어쓸 때 사용한다.

예를 들어 Target에 기본 상태값과 생성자 정보를 먼저 넣고, Source에서 이름이 같은 필드만 덮어쓰고 싶을 수 있다.

```abap
DATA(ls_target) = CORRESPONDING ty_user_target(
  BASE ( VALUE ty_user_target(
           status     = 'N'
           created_by = sy-uname
           created_on = sy-datum ) )
  ls_source
  EXCEPT created_by created_on
).
```

이 코드는 다음 의미를 가진다.

```text
1. ty_user_target 기본 구조를 만든다.
2. STATUS, CREATED_BY, CREATED_ON을 기본값으로 채운다.
3. ls_source에서 같은 이름의 필드를 옮긴다.
4. 단, CREATED_BY와 CREATED_ON은 Source에서 가져오지 않는다.
```

### 8.2 BASE를 사용하지 않았을 때

`BASE` 없이 새 구조를 생성하면 Source에 없는 Target 필드는 초기값이 된다.

```abap
DATA(ls_target) = CORRESPONDING ty_user_target( ls_source ).
```

이 경우 `STATUS`, `CREATED_BY`, `CREATED_ON` 같은 필드가 Source에 없으면 초기값이 된다.

### 8.3 BASE를 사용하면 좋은 경우

| 상황 | 설명 |
|---|---|
| 기본값을 먼저 세팅해야 함 | 상태, 생성자, 생성일 등 |
| 일부 필드는 기존 Target 값을 유지해야 함 | 화면 입력값 유지 |
| Source 값으로 전체 덮어쓰기를 피해야 함 | 감사 필드 보호 |
| 리팩터링 중 기존 로직을 보존해야 함 | Legacy 코드 안정화 |

## 9. 내부 테이블 간 CORRESPONDING

`CORRESPONDING`은 단일 구조체뿐 아니라 내부 테이블에도 사용할 수 있다.

### 9.1 타입 정의

```abap
TYPES tt_flight_source TYPE STANDARD TABLE OF ty_flight_source WITH EMPTY KEY.
TYPES tt_flight_alv    TYPE STANDARD TABLE OF ty_flight_alv WITH EMPTY KEY.
```

### 9.2 내부 테이블 매핑

```abap
DATA(lt_alv) = CORRESPONDING tt_flight_alv(
  lt_source
  MAPPING carrier_id    = carrid
          connection_id = connid
          amount        = price
          currency_code = currency
).
```

의미는 다음과 같다.

```text
lt_source의 각 라인을 ty_flight_alv 라인 구조로 변환하여 lt_alv를 만든다.
```

### 9.3 주의할 점

내부 테이블 매핑에서는 다음을 주의해야 한다.

| 주의점 | 설명 |
|---|---|
| 라인 수 | Source 라인 수만큼 Target 라인이 생성된다. |
| Target Table Type | Standard/Sorted/Hashed Table의 Key 조건을 고려해야 한다. |
| 중복 Key | Unique Key가 있는 Target에서는 중복 데이터가 문제가 될 수 있다. |
| 성능 | 대량 데이터에서는 불필요한 전체 변환을 피해야 한다. |
| 의미 | 이름이 같다고 항상 같은 의미는 아니다. |

초급 단계에서는 Standard Table 기준으로 먼저 익히고, Sorted/Hashed Table과 Key 이슈는 Internal Table 심화에서 연결해 이해하는 것이 좋다.

## 10. CORRESPONDING은 의미 검증 도구가 아니다

`CORRESPONDING`은 필드명을 기준으로 값을 이동한다.  
하지만 필드명이 같다고 해서 반드시 업무 의미가 같은 것은 아니다.

예를 들어 두 구조에 모두 `STATUS`라는 필드가 있다고 하자.

| 구조 | STATUS 의미 |
|---|---|
| 주문 구조 | 주문 상태 |
| 사용자 구조 | 계정 상태 |
| 결재 구조 | 승인 상태 |

이 필드들은 이름은 같지만 의미가 다를 수 있다.  
`CORRESPONDING`은 이런 의미 차이를 판단하지 않는다.

따라서 실무에서는 다음 질문을 반드시 해야 한다.

```text
이름이 같은 필드가 정말 같은 업무 의미인가?
자동 매핑되면 안 되는 필드는 없는가?
감사 필드나 상태 필드가 의도치 않게 덮어써지지 않는가?
MAPPING으로 명시해야 하는 필드는 없는가?
EXCEPT로 제외해야 하는 필드는 없는가?
```

## 11. 실무 패턴 1: DB 조회 결과를 ALV 출력 구조로 변환

### 11.1 시나리오

표준 테이블 `SFLIGHT`에서 조회한 결과를 ALV 출력용 구조로 변환한다.

Source 구조는 DB 필드명 중심이다.  
Target 구조는 ALV 출력 의미 중심이다.

```abap
TYPES: BEGIN OF ty_sflight_src,
         carrid   TYPE sflight-carrid,
         connid   TYPE sflight-connid,
         fldate   TYPE sflight-fldate,
         price    TYPE sflight-price,
         currency TYPE sflight-currency,
       END OF ty_sflight_src.

TYPES: BEGIN OF ty_sflight_alv,
         carrier_id    TYPE sflight-carrid,
         connection_id TYPE sflight-connid,
         flight_date   TYPE sflight-fldate,
         amount        TYPE sflight-price,
         currency_code TYPE sflight-currency,
       END OF ty_sflight_alv.
```

### 11.2 조회 및 변환

```abap
SELECT carrid,
       connid,
       fldate,
       price,
       currency
  FROM sflight
  INTO TABLE @DATA(lt_source)
  UP TO 20 ROWS.

DATA(lt_alv) = CORRESPONDING STANDARD TABLE OF ty_sflight_alv(
  lt_source
  MAPPING carrier_id    = carrid
          connection_id = connid
          flight_date   = fldate
          amount        = price
          currency_code = currency
).
```

이 예제에서 `MAPPING`을 사용한 이유는 Source와 Target의 필드명이 다르기 때문이다.

> [추정] 교육 시스템에 `SFLIGHT` 데이터가 없거나 비어 있을 수 있다. 이 경우 같은 구조의 로컬 테스트 데이터를 `VALUE`로 만들어 실습할 수 있다.

## 12. 실무 패턴 2: 감사 필드 보호

### 12.1 시나리오

기존 데이터를 복사해 신규 데이터를 만들되, 생성자와 생성일은 현재 사용자와 현재 날짜로 다시 세팅해야 한다.

```abap
TYPES: BEGIN OF ty_doc,
         doc_id     TYPE c LENGTH 10,
         item_no    TYPE n LENGTH 6,
         amount     TYPE p LENGTH 10 DECIMALS 2,
         status     TYPE c LENGTH 1,
         created_by TYPE syuname,
         created_on TYPE d,
       END OF ty_doc.
```

### 12.2 안전한 변환

```abap
DATA(ls_new_doc) = CORRESPONDING ty_doc(
  BASE ( VALUE ty_doc(
           status     = 'N'
           created_by = sy-uname
           created_on = sy-datum ) )
  ls_old_doc
  EXCEPT doc_id status created_by created_on
).
```

의도는 다음과 같다.

| 필드 | 처리 |
|---|---|
| DOC_ID | 신규 문서번호이므로 제외 |
| STATUS | 신규 상태값 `N` 유지 |
| CREATED_BY | 현재 사용자 유지 |
| CREATED_ON | 현재 날짜 유지 |
| AMOUNT | Source에서 복사 |
| ITEM_NO | Source에서 복사 |

이처럼 `BASE`와 `EXCEPT`를 함께 사용하면 “복사할 필드”와 “복사하지 않을 필드”가 명확해진다.

## 13. 실무 패턴 3: Legacy 수동 매핑 리팩터링

### 13.1 Legacy 코드

```abap
CLEAR ls_output.

ls_output-carrid   = ls_source-carrid.
ls_output-connid   = ls_source-connid.
ls_output-fldate   = ls_source-fldate.
ls_output-price    = ls_source-price.
ls_output-currency = ls_source-currency.
ls_output-status   = 'A'.
```

### 13.2 Modern ABAP 코드

```abap
ls_output = CORRESPONDING #(
  BASE ( VALUE #( status = 'A' ) )
  ls_source
).
```

### 13.3 비교

| 관점 | Legacy 수동 매핑 | CORRESPONDING |
|---|---|---|
| 코드 길이 | 길다 | 짧다 |
| 누락 가능성 | 높다 | 낮다 |
| 필드 추가 대응 | 수동 수정 필요 | 이름이 같으면 자동 매핑 |
| 의도 표현 | 분산됨 | 한 표현식에 집중 |
| 위험 | 잘못된 필드 대입 | 자동 매핑 과다 가능성 |

`CORRESPONDING`이 항상 더 좋은 것은 아니다.  
필드 수가 적고 변환 로직이 복잡하다면 수동 매핑이 더 명확할 수도 있다.

## 14. 오류 상황과 검증 포인트

### 14.1 Target 필드명을 잘못 쓴 경우

```abap
DATA(ls_output) = CORRESPONDING ty_flight_alv(
  ls_source
  MAPPING carrid = carrier_id
).
```

문제는 `MAPPING`의 왼쪽이 Target Component라는 점이다.  
Target 구조에 `CARRID`가 없다면 문법 오류가 발생한다.

해결:

```abap
DATA(ls_output) = CORRESPONDING ty_flight_alv(
  ls_source
  MAPPING carrier_id = carrid
).
```

### 14.2 자동 매핑이 너무 넓은 경우

```abap
ls_target = CORRESPONDING #( ls_source ).
```

이 코드는 간단하지만, 모든 같은 이름 필드를 옮긴다.  
감사 필드나 상태 필드가 덮어써질 수 있다.

해결:

```abap
ls_target = CORRESPONDING #(
  ls_source
  EXCEPT created_by created_on changed_by changed_on status
).
```

### 14.3 Source에 없는 필드를 기대하는 경우

Target에 `STATUS`가 있는데 Source에 `STATUS`가 없다면 기본 `CORRESPONDING`은 값을 채우지 않는다.  
이 경우 `BASE` 또는 후속 대입이 필요하다.

```abap
DATA(ls_target) = CORRESPONDING ty_target(
  BASE ( VALUE ty_target( status = 'A' ) )
  ls_source
).
```

### 14.4 의미가 다른 같은 이름 필드

필드명이 같더라도 의미가 다르면 자동 매핑하면 안 된다.

예:

```text
Source STATUS = 결재 상태
Target STATUS = 계정 상태
```

해결:

```abap
DATA(ls_target) = CORRESPONDING ty_target(
  ls_source
  EXCEPT status
).
```

그리고 별도 업무 로직으로 `STATUS`를 결정한다.

## 15. 디버깅 방법

`CORRESPONDING`은 한 줄로 많은 필드를 매핑하므로 디버깅 시 결과를 반드시 확인해야 한다.

### 15.1 기본 디버깅 절차

```text
1. CORRESPONDING 실행 직전 Breakpoint 설정
2. Source 구조체 값 확인
3. Step Over로 CORRESPONDING 실행
4. Target 구조체 전체 펼쳐보기
5. 의도한 필드가 채워졌는지 확인
6. 제외해야 할 필드가 덮어써지지 않았는지 확인
```

### 15.2 Watchpoint 또는 변수 비교

필드가 많으면 다음 필드를 우선 확인한다.

| 필드 유형 | 확인 이유 |
|---|---|
| Key Field | 잘못 옮기면 데이터 식별 오류 |
| Status Field | 업무 상태 왜곡 가능 |
| Amount/Quantity | 수치 오류 영향 큼 |
| Currency/Unit | 단위 불일치 위험 |
| Audit Field | 생성/변경 이력 훼손 가능 |

## 16. 성능 관점

`CORRESPONDING` 자체는 구조 매핑을 간결하게 표현하는 문법이다.  
그러나 대량 데이터에서 내부 테이블 전체를 변환하면 메모리와 CPU 사용량이 증가할 수 있다.

### 16.1 대량 데이터에서 주의할 점

| 상황 | 주의 |
|---|---|
| 수십만 건 내부 테이블 전체 변환 | 불필요한 전체 복사를 피한다. |
| Target 필드가 매우 많음 | 필요한 필드만 SELECT하거나 변환한다. |
| 변환 후 일부만 사용 | 변환 전 필터링을 검토한다. |
| 반복문 안에서 반복 변환 | 루프 밖에서 한 번에 처리 가능한지 검토한다. |

### 16.2 실무 판단

다음과 같은 경우에는 `CORRESPONDING`을 사용해도 좋다.

```text
필드 수가 많고 대부분 이름이 일치한다.
ALV 출력 구조로 단순 변환한다.
인터페이스 DTO로 필드명을 정리한다.
기존 수동 매핑 코드가 장황하다.
```

다음과 같은 경우에는 신중해야 한다.

```text
매핑마다 복잡한 계산이 필요하다.
같은 이름이지만 의미가 다른 필드가 많다.
대량 데이터에서 일부 필드만 필요하다.
감사 필드나 상태 필드를 엄격히 보호해야 한다.
```

## 17. Clean ABAP 관점

Modern ABAP의 목적은 단순히 문법을 짧게 쓰는 것이 아니다.  
읽는 사람이 코드를 보고 “무엇을 하려는지” 빠르게 이해할 수 있어야 한다.

`CORRESPONDING`은 다음 조건에서 Clean Code에 도움이 된다.

| 조건 | 이유 |
|---|---|
| 구조 간 매핑 의도가 명확함 | `CORRESPONDING` 이름 자체가 매핑 의도를 표현 |
| MAPPING을 명시적으로 사용함 | 필드명 차이를 한 곳에 모아 보여줌 |
| EXCEPT로 위험 필드를 제외함 | 의도하지 않은 덮어쓰기 방지 |
| BASE로 기본값을 명시함 | 초기값 세팅 의도가 분명함 |

반대로 다음 코드는 좋지 않다.

```abap
ls_target = CORRESPONDING #( ls_source ).
```

이 한 줄이 항상 나쁘다는 뜻은 아니다.  
하지만 Source와 Target이 매우 크고 같은 이름 필드가 많다면, “무엇이 옮겨지는지”가 오히려 불명확해질 수 있다.

실무에서는 다음 기준을 추천한다.

```text
작고 명확한 구조 → 기본 CORRESPONDING 가능
업무적으로 중요한 구조 → MAPPING/EXCEPT를 적극 사용
감사 필드 포함 구조 → EXCEPT 검토 필수
```

### 18.1 목표

`ty_source`와 `ty_target`에서 같은 이름 필드를 `CORRESPONDING`으로 매핑한다.

### 18.2 실습 코드


## 20. 실습 3: BASE와 EXCEPT 사용

### 20.1 목표

기본값을 유지하면서 일부 필드를 제외하고 매핑한다.

### 20.2 실습 코드

```abap
REPORT zgpt_corresponding_03.

TYPES: BEGIN OF ty_user,
         user_id    TYPE c LENGTH 10,
         user_name  TYPE c LENGTH 40,
         status     TYPE c LENGTH 1,
         created_by TYPE syuname,
         created_on TYPE d,

         ls_new_user-user_name,
         ls_new_user-status,
         ls_new_user-created_by,
         ls_new_user-created_on.
```

| USER_NAME | Kim Developer |

| CREATED_ON | 오늘 날짜 |

## 21. 실습 4: 내부 테이블 변환

### 21.1 목표

내부 테이블 전체를 ALV 출력 구조로 변환한다.

### 21.2 실습 코드

```abap
REPORT zgpt_corresponding_04.

TYPES: BEGIN OF ty_source,
         carrid   TYPE s_carr_id,
         connid   TYPE s_conn_id,
         fldate   TYPE s_date,
         price    TYPE s_price,
         currency TYPE s_currcode,
       END OF ty_source.

TYPES: BEGIN OF ty_alv,
         carrier_id    TYPE s_carr_id,
         connection_id TYPE s_conn_id,
         flight_date   TYPE s_date,
         amount        TYPE s_price,
         currency_code TYPE s_currcode,
       END OF ty_alv.

TYPES tt_source TYPE STANDARD TABLE OF ty_source WITH EMPTY KEY.
TYPES tt_alv    TYPE STANDARD TABLE OF ty_alv    WITH EMPTY KEY.

DATA(lt_source) = VALUE tt_source(
  ( carrid = 'AA' connid = '0017' fldate = sy-datum price = '1200.50' currency = 'USD' )
  ( carrid = 'LH' connid = '0400' fldate = sy-datum price = '850.00'  currency = 'EUR' )
).

  lt_source
  MAPPING carrier_id    = carrid
          connection_id = connid
          flight_date   = fldate
          amount        = price
          currency_code = currency
).

LOOP AT lt_alv INTO DATA(ls_alv).
  WRITE: / ls_alv-carrier_id,
           ls_alv-connection_id,
           ls_alv-flight_date,
           ls_alv-amount,
           ls_alv-currency_code.
ENDLOOP.
```

## 22. 자주 하는 실수

### 22.1 MAPPING 방향 오류

잘못된 이해:

```text
source = target
```

올바른 이해:

```text
target = source
```

### 22.2 필드명이 같으면 의미도 같다고 착각

`STATUS`, `TYPE`, `CODE`, `TEXT` 같은 필드는 이름만으로 의미를 확정하기 어렵다.  
이런 필드는 자동 매핑 전에 반드시 업무 의미를 확인해야 한다.

### 22.3 감사 필드 제외 누락

`CREATED_BY`, `CREATED_ON`, `CHANGED_BY`, `CHANGED_ON`은 무심코 복사하면 운영 데이터 이력이 왜곡될 수 있다.

### 22.4 너무 복잡한 매핑을 한 줄에 몰아넣기

`CORRESPONDING`은 간결하지만, 지나치게 복잡한 `MAPPING`, `EXCEPT`, `BASE`를 한 줄에 몰아넣으면 오히려 읽기 어려워진다.

권장:

```abap
DATA(ls_base) = VALUE ty_target(
  status     = 'N'
  created_by = sy-uname
  created_on = sy-datum
).

DATA(ls_target) = CORRESPONDING ty_target(
  BASE ( ls_base )
  ls_source
  EXCEPT created_by created_on
).
```

## 23. 실무 리뷰 체크리스트

코드 리뷰에서 `CORRESPONDING`을 발견하면 다음을 확인한다.

| 체크 항목 | 질문 |
|---|---|
| Source/Target 의미 | 두 구조가 같은 업무 맥락인가? |
| 자동 매핑 범위 | 같은 이름 필드가 모두 옮겨져도 되는가? |
| MAPPING 방향 | `target = source`로 작성되었는가? |
| EXCEPT 필요성 | 제외해야 할 필드가 빠지지 않았는가? |
| BASE 필요성 | 기본값 또는 기존 값 유지가 필요한가? |
| 대량 데이터 | 내부 테이블 전체 복사가 필요한가? |
| 가독성 | 수동 매핑보다 명확한가? |

## 24. 평가 문제

### 24.1 객관식

#### Q1. `CORRESPONDING #( ls_source )`의 기본 동작은?

A. 모든 필드를 순서대로 복사한다.  
B. 이름이 같은 Component를 기준으로 값을 매핑한다.  
C. 타입이 같은 필드를 자동으로 찾아 매핑한다.  
D. 업무 의미가 같은 필드를 자동으로 판단해 매핑한다.

**정답:** B

#### Q2. `MAPPING carrier_id = carrid`의 의미는?

A. Source의 `carrier_id` 값을 Target의 `carrid`로 옮긴다.  
B. Target의 `carrier_id`에 Source의 `carrid` 값을 옮긴다.  
C. 두 필드를 모두 초기화한다.  
D. 두 필드를 매핑 대상에서 제외한다.

**정답:** B

#### Q3. `EXCEPT created_by created_on`의 목적은?

A. 해당 필드만 매핑한다.  
B. 해당 필드를 정렬 기준으로 삼는다.  
C. 해당 필드를 매핑 대상에서 제외한다.  
D. 해당 필드를 Key로 지정한다.

**정답:** C

### 24.2 서술형

#### Q1. `CORRESPONDING`과 `MOVE-CORRESPONDING`의 차이를 설명하시오.

**모범 답안:**  
`MOVE-CORRESPONDING`은 전통적인 명령문 방식으로 같은 이름의 Component를 대상 구조로 옮긴다. `CORRESPONDING` Constructor Operator는 표현식 기반 문법으로 Inline Declaration, BASE, MAPPING, EXCEPT 등과 조합하여 더 선언적이고 간결하게 구조 매핑을 작성할 수 있다.

#### Q2. `CORRESPONDING`을 사용할 때 감사 필드를 조심해야 하는 이유를 설명하시오.

**모범 답안:**  
`CREATED_BY`, `CREATED_ON`, `CHANGED_BY`, `CHANGED_ON` 같은 감사 필드는 데이터 생성·변경 이력과 연결된다. Source 값을 그대로 복사하면 신규 데이터의 생성자나 생성일이 잘못 기록될 수 있으므로 `EXCEPT` 또는 별도 세팅을 검토해야 한다.

#### Q3. `CORRESPONDING`이 의미 검증 도구가 아닌 이유를 설명하시오.

**모범 답안:**  
`CORRESPONDING`은 필드명을 기준으로 값을 옮길 뿐, 필드의 업무 의미가 같은지 판단하지 않는다. 따라서 이름이 같은 `STATUS`라도 주문 상태, 사용자 상태, 승인 상태처럼 의미가 다를 수 있으므로 개발자가 직접 의미를 검토해야 한다.

## 25. 핵심 요약

```text
CORRESPONDING은 이름이 같은 Component를 기준으로 구조체 또는 내부 테이블을 매핑한다.
MAPPING은 이름이 다른 Target 필드와 Source 필드를 연결한다.
MAPPING 방향은 target = source이다.
EXCEPT는 자동 매핑에서 제외할 Target Component를 지정한다.
BASE는 기존 값 또는 기본값을 유지하면서 Source 값을 덮어쓸 때 사용한다.
CORRESPONDING은 의미 검증 도구가 아니므로 업무 의미 검토가 필요하다.
감사 필드, 상태 필드, Key 필드는 자동 매핑 전에 반드시 확인한다.
```
