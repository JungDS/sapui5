## 3. 리팩터링이란 무엇인가?

리팩터링은 **외부 동작은 유지하면서 내부 구조를 개선하는 작업**이다.

예를 들어 다음 두 코드는 출력 결과가 같을 수 있다.

### Legacy 스타일

```abap
DATA lv_text TYPE string.

CONCATENATE 'Carrier:' p_carrid INTO lv_text SEPARATED BY space.
WRITE: / lv_text.
```

### Modern 스타일

```abap
DATA(lv_text) = |Carrier: { p_carrid }|.
WRITE: / lv_text.
```

출력 결과가 같다면 기능은 동일하다.  
하지만 두 번째 코드는 문자열 조립 의도가 더 직접적으로 보인다.

리팩터링에서 중요한 것은 다음이다.

```text
기능을 바꾸지 않는다.
동작 결과를 유지한다.
코드의 의도와 구조를 개선한다.
테스트 또는 검증으로 결과 동일성을 확인한다.
```

## 4. Modern ABAP 리팩터링의 기본 원칙

### 4.1 최신 문법 자체가 목적은 아니다

Modern ABAP 문법은 강력하지만, 무조건 사용하는 것이 정답은 아니다.

나쁜 리팩터링의 예:

```abap
DATA(result) = VALUE string( COND #( WHEN line_exists( lt_data[ id = iv_id ] )
                                    THEN |{ lt_data[ id = iv_id ]-name }:{ lt_data[ id = iv_id ]-status }|
                                    ELSE || ) ).
```

이 코드는 최신 문법을 많이 사용했지만, 같은 Table Expression을 여러 번 반복하고 가독성이 떨어진다.

더 나은 방식:

```abap
DATA(ls_data) = VALUE ty_data( lt_data[ id = iv_id ] OPTIONAL ).

IF ls_data IS INITIAL.
  RETURN.
ENDIF.

DATA(lv_result) = |{ ls_data-name }:{ ls_data-status }|.
```

짧은 한 줄보다 읽히는 코드가 중요하다.

---

### 4.2 리팩터링은 작은 단위로 한다

한 번에 모든 문법을 바꾸면 검증이 어려워진다.

권장 순서:

```text
1. 변수 선언 위치 개선
2. 문자열 조립 개선
3. Internal Table 생성 코드 개선
4. 구조 매핑 개선
5. READ TABLE 패턴 개선
6. 중복 로직 분리
7. 결과 검증
```

각 단계는 작은 커밋 또는 작은 변경 단위로 나누는 것이 좋다.

---

### 4.3 릴리스 호환성을 확인한다

Modern ABAP Syntax는 ABAP Platform 릴리스에 따라 지원 범위가 다를 수 있다.  
S/4HANA 환경이라고 해서 모든 시스템에서 모든 최신 문법이 동일하게 사용 가능한 것은 아니다.

> [추정] SAP GUI 800은 프론트엔드 클라이언트 버전이며, 실제 ABAP 문법 지원 범위는 백엔드 ABAP Platform/SAP_BASIS 릴리스에 의해 결정된다.

따라서 프로젝트에서는 다음을 확인한다.

| 확인 항목 | 설명 |
|---|---|
| SAP_BASIS 릴리스 | Modern syntax 지원 범위 판단 |
| ATC 규칙 | 고객사 코드 품질 기준 확인 |
| Clean ABAP 적용 여부 | 팀 스타일 가이드 확인 |
| ABAP Cloud 여부 | 사용 가능한 문법과 API 제한 확인 |
| 운영 시스템 제약 | 다운포트 또는 이중 유지보수 여부 확인 |

## 5. 리팩터링 후보 찾기

Legacy ABAP에서 자주 보이는 리팩터링 후보는 다음과 같다.

| Legacy 패턴 | Modern 후보 | 주의점 |
|---|---|---|
| 상단에 모든 `DATA` 선언 | Inline Declaration | 변수 범위가 명확할 때만 |
| Work Area + `APPEND` 반복 | `VALUE #( )` | 데이터가 많거나 조건이 복잡하면 분리 |
| `MOVE-CORRESPONDING` | `CORRESPONDING #( )` | 필드명과 제외 필드 확인 |
| `READ TABLE ... sy-subrc` | Table Expression, `line_exists` | 미존재 시 예외/초기값 처리 주의 |
| `CONCATENATE` | String Template | 복잡한 포맷은 분리 |
| `WRITE ... TO` 문자열 변환 | String Template / formatting | Locale, 날짜, 금액 포맷 확인 |
| 중복된 `CLEAR` | 지역 변수, 작은 Scope | 의도 없는 값 유지 방지 |
| 긴 루프 내부 처리 | Method Extract | OO 학습 이후 본격 적용 |
| `SELECT *` 남용 | 필요한 필드만 SELECT | DB 성능과 네트워크 부하 고려 |
| 중첩 IF 과다 | Guard Clause, CASE, Method 분리 | 기존 흐름 유지 검증 필요 |

## 6. 예제 1: DATA 선언 위치 개선

### 6.1 Legacy 코드

```abap
DATA lv_carrid TYPE s_carr_id.
DATA lv_text   TYPE string.
DATA ls_scarr  TYPE scarr.

lv_carrid = 'AA'.

SELECT SINGLE *
  FROM scarr
  INTO ls_scarr
  WHERE carrid = lv_carrid.

IF sy-subrc = 0.
  CONCATENATE 'Carrier:' ls_scarr-carrname INTO lv_text SEPARATED BY space.
  WRITE: / lv_text.
ENDIF.
```

이 코드는 정상 동작할 수 있지만, 변수 선언이 모두 위에 몰려 있다.  
초급자는 이렇게 선언해도 되지만, 코드가 길어지면 변수가 실제로 어디에서 쓰이는지 파악하기 어려워진다.

### 6.2 Modern 리팩터링

```abap
DATA(lv_carrid) = 'AA'.

SELECT SINGLE *
  FROM scarr
  WHERE carrid = @lv_carrid
  INTO @DATA(ls_scarr).

IF sy-subrc = 0.
  DATA(lv_text) = |Carrier: { ls_scarr-carrname }|.
  WRITE: / lv_text.
ENDIF.
```

### 6.3 개선 포인트

| 개선 | 설명 |
|---|---|
| `DATA(lv_carrid)` | 값이 처음 필요한 위치에서 선언한다. |
| `INTO @DATA(ls_scarr)` | 조회 결과 구조를 사용 지점에서 선언한다. |
| `DATA(lv_text)` | 문자열 변수도 필요한 블록 안에서 선언한다. |
| String Template | 문자열 조립 의도가 명확해졌다. |

### 6.4 주의점

Inline Declaration은 변수 범위를 줄이는 데 유용하지만, 같은 변수를 여러 블록에서 반복 사용해야 하는 경우에는 명시적 선언이 더 적절할 수 있다.

## 7. 예제 2: Work Area + APPEND 개선

### 7.1 Legacy 코드

```abap
TYPES: BEGIN OF ty_status,
         status TYPE c LENGTH 1,
         text   TYPE string,
       END OF ty_status.

DATA lt_status TYPE STANDARD TABLE OF ty_status.
DATA ls_status TYPE ty_status.

CLEAR ls_status.
ls_status-status = 'A'.
ls_status-text   = 'Active'.
APPEND ls_status TO lt_status.

CLEAR ls_status.
ls_status-status = 'I'.
ls_status-text   = 'Inactive'.
APPEND ls_status TO lt_status.

CLEAR ls_status.
ls_status-status = 'B'.
ls_status-text   = 'Blocked'.
APPEND ls_status TO lt_status.
```

이 코드는 초급자가 이해하기 쉽지만, 반복이 많다.  
특히 `CLEAR`, 필드 대입, `APPEND`가 반복된다.

### 7.2 Modern 리팩터링

```abap
TYPES: BEGIN OF ty_status,
         status TYPE c LENGTH 1,
         text   TYPE string,
       END OF ty_status.

DATA(lt_status) = VALUE STANDARD TABLE OF ty_status(
  ( status = 'A' text = 'Active' )
  ( status = 'I' text = 'Inactive' )
  ( status = 'B' text = 'Blocked' )
).
```

### 7.3 개선 포인트

| 개선 | 설명 |
|---|---|
| `VALUE STANDARD TABLE OF` | Internal Table 초기 데이터를 한 번에 구성한다. |
| Work Area 제거 | 불필요한 중간 변수를 줄인다. |
| `CLEAR` 제거 | 값 초기화 누락 위험이 줄어든다. |
| 데이터 의도 명확화 | 상태 코드 목록이라는 구조가 한눈에 보인다. |

### 7.4 과도한 사용 주의

테스트 데이터 몇 건이나 코드성 데이터 구성에는 `VALUE #( )`가 적합하다.  
하지만 수십 줄 이상의 복잡한 데이터 생성, 조건별 분기, DB 조회 후 가공이 섞인 경우에는 별도 로직으로 분리하는 것이 더 읽기 쉽다.

## 8. 예제 3: MOVE-CORRESPONDING 개선

### 8.1 Legacy 코드

```abap
TYPES: BEGIN OF ty_source,
         carrid   TYPE s_carr_id,
         carrname TYPE s_carrname,
         currcode TYPE s_currcode,
       END OF ty_source.

TYPES: BEGIN OF ty_target,
         carrid   TYPE s_carr_id,
         carrname TYPE s_carrname,
       END OF ty_target.

DATA ls_source TYPE ty_source.
DATA ls_target TYPE ty_target.

ls_source-carrid   = 'AA'.
ls_source-carrname = 'American Airlines'.
ls_source-currcode = 'USD'.

MOVE-CORRESPONDING ls_source TO ls_target.
```

### 8.2 Modern 리팩터링

```abap
DATA(ls_source) = VALUE ty_source(
  carrid   = 'AA'
  carrname = 'American Airlines'
  currcode = 'USD'
).

DATA(ls_target) = CORRESPONDING ty_target( ls_source ).
```

### 8.3 개선 포인트

| 개선 | 설명 |
|---|---|
| `VALUE ty_source( )` | Source 구조 생성이 명확하다. |
| `CORRESPONDING ty_target( )` | Target 구조로의 매핑 의도가 명확하다. |
| 중간 `CLEAR` 불필요 | 새 변수 생성으로 초기화 상태가 분명하다. |

### 8.4 필드 제외 예시

Target에 같은 이름의 필드가 있지만 의도적으로 제외해야 할 수 있다.

```abap
DATA(ls_target) = CORRESPONDING ty_target(
  ls_source
  EXCEPT carrname
).
```

필드 제외는 단순히 문법을 쓰는 것이 아니라 “왜 이 필드는 매핑하지 않는가?”를 코드 리뷰에서 설명할 수 있어야 한다.

## 9. 예제 4: READ TABLE 패턴 개선

### 9.1 Legacy 코드

```abap
DATA ls_status TYPE ty_status.

READ TABLE lt_status INTO ls_status WITH KEY status = 'A'.

IF sy-subrc = 0.
  WRITE: / ls_status-text.
ELSE.
  WRITE: / 'Status not found'.
ENDIF.
```

### 9.2 Modern 리팩터링 1: `VALUE #( ... OPTIONAL )`

```abap
DATA(ls_status) = VALUE ty_status(
  lt_status[ status = 'A' ] OPTIONAL
).

IF ls_status IS INITIAL.
  WRITE: / 'Status not found'.
ELSE.
  WRITE: / ls_status-text.
ENDIF.
```

이 방식은 항목이 없을 때 예외를 발생시키지 않고 초기값을 반환한다.  
하지만 `ls_status IS INITIAL` 판단이 업무적으로 항상 안전한지는 확인해야 한다. 실제 데이터가 초기값을 가질 수 있다면 별도 존재 여부 판단이 필요하다.

### 9.3 Modern 리팩터링 2: `line_exists`

```abap
IF line_exists( lt_status[ status = 'A' ] ).
  DATA(ls_status) = lt_status[ status = 'A' ].
  WRITE: / ls_status-text.
ELSE.
  WRITE: / 'Status not found'.
ENDIF.
```

이 방식은 존재 여부가 명확하다.  
다만 같은 Table Expression을 두 번 수행하므로 데이터량과 테이블 종류에 따라 효율을 검토할 필요가 있다.

### 9.4 Modern 리팩터링 3: `DEFAULT`

```abap
DATA(ls_status) = VALUE ty_status(
  lt_status[ status = 'A' ]
  DEFAULT VALUE #( status = 'A' text = 'Status not found' )
).

WRITE: / ls_status-text.
```

이 방식은 기본값을 코드에 명시할 수 있어 읽기 좋다.  
단, 기본값이 실제 데이터와 혼동되지 않도록 주의해야 한다.

## 10. 예제 5: CONCATENATE 개선

### 10.1 Legacy 코드

```abap
DATA lv_text TYPE string.

CONCATENATE 'Carrier'
            ls_scarr-carrid
            ls_scarr-carrname
       INTO lv_text
       SEPARATED BY space.

WRITE: / lv_text.
```

### 10.2 Modern 리팩터링

```abap
DATA(lv_text) = |Carrier { ls_scarr-carrid } { ls_scarr-carrname }|.

WRITE: / lv_text.
```

### 10.3 더 명확한 출력

```abap
DATA(lv_text) = |Carrier { ls_scarr-carrid } - { ls_scarr-carrname }|.

WRITE: / lv_text.
```

String Template은 문자열 조립의 결과 형태가 코드에 그대로 보인다는 장점이 있다.  
하지만 문자열 내부 표현식이 길어지면 오히려 읽기 어려워진다.

나쁜 예:

```abap
DATA(lv_text) = |Result: { condense( replace( val = to_upper( lv_raw ) sub = '-' with = '_' ) ) }|.
```

더 나은 예:

```abap
DATA(lv_upper) = to_upper( lv_raw ).
DATA(lv_replaced) = replace( val = lv_upper sub = '-' with = '_' ).
DATA(lv_text) = |Result: { condense( lv_replaced ) }|.
```

## 11. 예제 6: Open SQL 코드 개선

### 11.1 Legacy 코드

```abap
DATA lt_scarr TYPE STANDARD TABLE OF scarr.
DATA ls_scarr TYPE scarr.

SELECT *
  FROM scarr
  INTO TABLE lt_scarr.

LOOP AT lt_scarr INTO ls_scarr.
  WRITE: / ls_scarr-carrid, ls_scarr-carrname.
ENDLOOP.
```

### 11.2 Modern 리팩터링

```abap
SELECT carrid,
       carrname,
       currcode
  FROM scarr
  INTO TABLE @DATA(lt_scarr).

LOOP AT lt_scarr INTO DATA(ls_scarr).
  WRITE: / ls_scarr-carrid, ls_scarr-carrname.
ENDLOOP.
```

### 11.3 개선 포인트

| 개선 | 설명 |
|---|---|
| 필요한 필드만 SELECT | `SELECT *`보다 의도가 분명하다. |
| `@DATA(lt_scarr)` | 조회 결과 테이블을 사용 위치에서 선언한다. |
| `INTO DATA(ls_scarr)` | 루프용 Work Area를 루프 안에서 선언한다. |
| Host Variable `@` | New Open SQL 문법과 연결된다. |

이번 모듈은 Open SQL 심화가 아니므로 세부 성능 튜닝은 다루지 않는다.  
다만 리팩터링 시 `SELECT *`를 그대로 두는 것보다 필요한 컬럼을 명시하는 습관이 좋다.

## 12. 예제 7: LOOP와 FIELD-SYMBOL 개선

### 12.1 Legacy 코드

```abap
FIELD-SYMBOLS <ls_status> TYPE ty_status.

LOOP AT lt_status ASSIGNING <ls_status>.
  IF <ls_status>-status = 'A'.
    <ls_status>-text = 'Active User'.
  ENDIF.
ENDLOOP.
```

### 12.2 Modern 리팩터링

```abap
LOOP AT lt_status ASSIGNING FIELD-SYMBOL(<ls_status>).
  IF <ls_status>-status = 'A'.
    <ls_status>-text = 'Active User'.
  ENDIF.
ENDLOOP.
```

이 리팩터링은 기능적으로 크지 않지만, Field Symbol의 사용 범위를 루프 근처로 좁힌다.  
코드가 길어질수록 선언 위치가 사용 위치에 가까운 것은 유지보수에 도움이 된다.

### 12.3 주의점

`ASSIGNING FIELD-SYMBOL`은 Internal Table 행을 직접 변경할 때 유용하다.  
읽기만 한다면 `INTO DATA(...)`가 더 안전하고 명확할 수 있다.

```abap
LOOP AT lt_status INTO DATA(ls_status).
  WRITE: / ls_status-status, ls_status-text.
ENDLOOP.
```

변경 의도가 없는데 `ASSIGNING`을 사용하는 것은 코드 리뷰에서 의도를 혼동시킬 수 있다.

## 13. 종합 리팩터링 예제

### 13.1 Legacy 코드

```abap
REPORT zlegacy_modern_refactor.

TYPES: BEGIN OF ty_output,
         carrid   TYPE s_carr_id,
         carrname TYPE s_carrname,
         text     TYPE string,
       END OF ty_output.

DATA lt_scarr  TYPE STANDARD TABLE OF scarr.
DATA ls_scarr  TYPE scarr.
DATA lt_output TYPE STANDARD TABLE OF ty_output.
DATA ls_output TYPE ty_output.
DATA lv_text   TYPE string.

SELECT *
  FROM scarr
  INTO TABLE lt_scarr.

LOOP AT lt_scarr INTO ls_scarr.
  CLEAR ls_output.

  ls_output-carrid   = ls_scarr-carrid.
  ls_output-carrname = ls_scarr-carrname.

  CONCATENATE ls_scarr-carrid ls_scarr-carrname
         INTO lv_text
         SEPARATED BY space.

  ls_output-text = lv_text.

  APPEND ls_output TO lt_output.
ENDLOOP.

LOOP AT lt_output INTO ls_output.
  WRITE: / ls_output-carrid, ls_output-carrname, ls_output-text.
ENDLOOP.
```

### 13.2 리팩터링 1단계: SELECT 필드와 Inline Declaration

```abap
SELECT carrid,
       carrname,
       currcode
  FROM scarr
  INTO TABLE @DATA(lt_scarr).
```

### 13.3 리팩터링 2단계: LOOP Inline Declaration

```abap
LOOP AT lt_scarr INTO DATA(ls_scarr).
  "...
ENDLOOP.
```

### 13.4 리팩터링 3단계: VALUE와 String Template

```abap
APPEND VALUE ty_output(
  carrid   = ls_scarr-carrid
  carrname = ls_scarr-carrname
  text     = |{ ls_scarr-carrid } { ls_scarr-carrname }|
) TO lt_output.
```

### 13.5 리팩터링 후 코드

```abap
REPORT zmodern_refactor_result.

TYPES: BEGIN OF ty_output,
         carrid   TYPE s_carr_id,
         carrname TYPE s_carrname,
         text     TYPE string,
       END OF ty_output.

SELECT carrid,
       carrname,
       currcode
  FROM scarr
  INTO TABLE @DATA(lt_scarr).

DATA lt_output TYPE STANDARD TABLE OF ty_output.

LOOP AT lt_scarr INTO DATA(ls_scarr).
  APPEND VALUE ty_output(
    carrid   = ls_scarr-carrid
    carrname = ls_scarr-carrname
    text     = |{ ls_scarr-carrid } { ls_scarr-carrname }|
  ) TO lt_output.
ENDLOOP.

LOOP AT lt_output INTO DATA(ls_output).
  WRITE: / ls_output-carrid, ls_output-carrname, ls_output-text.
ENDLOOP.
```

### 13.6 추가 개선 가능성

위 코드는 이미 많이 개선되었지만, `lt_output`을 만드는 과정도 더 줄일 수 있다.  
다만 초급 과정에서는 지나치게 압축하기보다 의도를 읽을 수 있는 수준을 유지하는 것이 좋다.

[추정] 고급 Modern ABAP에서는 `VALUE #( FOR ... IN ... )` 패턴으로 변환할 수 있지만, 이 문서는 초급자가 안전하게 읽고 유지보수할 수 있는 수준을 우선한다.

## 14. 좋은 리팩터링과 나쁜 리팩터링

### 14.1 좋은 리팩터링

좋은 리팩터링은 다음 특징을 가진다.

| 기준 | 설명 |
|---|---|
| 결과 동일 | 기존 기능과 결과가 유지된다. |
| 의도 명확 | 코드가 무엇을 하려는지 더 잘 보인다. |
| 범위 축소 | 변수와 임시 데이터의 Scope가 줄어든다. |
| 중복 감소 | 반복 대입, 반복 문자열 조립이 줄어든다. |
| 검증 가능 | 변경 전후 테스트가 가능하다. |
| 팀 합의 | 프로젝트 코딩 스타일과 맞는다. |

### 14.2 나쁜 리팩터링

나쁜 리팩터링은 다음 특징을 가진다.

| 문제 | 설명 |
|---|---|
| 기능 변경 | 리팩터링 중 의도치 않게 결과가 바뀐다. |
| 과도한 압축 | 한 줄에 너무 많은 의미가 들어간다. |
| 예외 처리 누락 | Table Expression 미존재 예외를 고려하지 않는다. |
| 릴리스 미확인 | 운영 시스템에서 지원하지 않는 문법을 사용한다. |
| 성능 악화 | 같은 Table Expression을 반복 실행한다. |
| 리뷰 어려움 | 팀원이 이해하기 어려운 문법을 무리하게 사용한다. |

## 15. 실무 리팩터링 절차

실무에서 Legacy 코드를 Modern ABAP으로 바꿀 때는 다음 순서를 권장한다.

```text
1. 기존 코드의 목적을 이해한다.
2. 입력과 출력, DB 변경 여부를 확인한다.
3. 리팩터링 대상 범위를 작게 정한다.
4. 결과 비교 기준을 만든다.
5. 단순 선언 개선부터 시작한다.
6. 문자열, 구조 매핑, Table Read 패턴을 개선한다.
7. Syntax Check와 ATC를 실행한다.
8. 테스트 데이터를 기준으로 결과를 비교한다.
9. 코드 리뷰에서 의도를 설명한다.
10. 필요하면 과도한 Modern 문법을 다시 풀어쓴다.
```

### 15.1 리팩터링 전 확인 질문

```text
이 코드는 DB를 변경하는가?
이 코드는 외부 인터페이스와 연결되는가?
이 코드는 배치에서 대량으로 실행되는가?
이 코드는 고객사 Enhancement나 User Exit에 포함되는가?
이 코드의 결과를 테스트할 기준 데이터가 있는가?
```

DB 변경, 인터페이스, 배치, Exit/BAdI 코드는 리팩터링 리스크가 크므로 더 신중해야 한다.

## 16. 검증 기준

리팩터링 후에는 “문법 오류가 없다”만으로는 부족하다.  
다음 항목을 확인해야 한다.

| 검증 항목 | 확인 방법 |
|---|---|
| Syntax Check | 활성화 전 문법 오류 확인 |
| 실행 결과 | 변경 전후 출력 비교 |
| `sy-subrc` 의존 로직 | 기존 분기와 동일하게 동작하는지 확인 |
| 예외 상황 | 데이터 없음, 초기값, 중복 데이터 처리 확인 |
| 성능 영향 | 대량 데이터에서 반복 Table Expression 여부 확인 |
| ATC/Code Inspector | 프로젝트 품질 기준 확인 |
| 코드 리뷰 | 팀원이 의도를 이해할 수 있는지 확인 |

### 16.1 테스트 케이스 예시

| 케이스 | 설명 |
|---|---|
| 정상 데이터 존재 | 조회 결과가 있는 경우 |

| 중복 키 가능성 | Internal Table Key가 유일하지 않은 경우 |
| 대량 데이터 | 반복 조회 또는 중첩 루프 성능 확인 |

## 17. Modern ABAP 적용 판단표

| 상황 | 추천 방식 |
|---|---|
| 변수가 한 블록 안에서만 쓰임 | Inline Declaration |
| 테스트 데이터 몇 건 생성 | `VALUE #( )` |
| 같은 이름 필드 구조 매핑 | `CORRESPONDING #( )` |
| 단일 행 존재 여부 확인 | `line_exists` |
| 단일 행 값을 가져오되 없으면 초기값 허용 | `VALUE #( itab[ ... ] OPTIONAL )` |
| 없을 때 기본값이 명확함 | `DEFAULT` |
| 단순 문자열 조립 | String Template |
| 복잡한 변환이 포함된 문자열 | 중간 변수로 분리 후 String Template |
| 대량 루프에서 반복 Table Expression | 성능 검토 후 READ TABLE 또는 적절한 Key 사용 |
| 팀이 Modern 문법에 익숙하지 않음 | 단계적 적용 |

### 18.1 기본 실습

다음 Legacy 코드를 Modern ABAP 스타일로 리팩터링한다.

```abap
DATA lv_name TYPE string.
DATA lv_msg  TYPE string.

lv_name = 'ABAP'.

CONCATENATE 'Hello' lv_name INTO lv_msg SEPARATED BY space.

WRITE: / lv_msg.
```

예상 개선 예:

```abap
DATA(lv_name) = `ABAP`.
DATA(lv_msg) = |Hello { lv_name }|.

WRITE: / lv_msg.
```

### 18.2 Internal Table 실습

다음 코드를 `VALUE #( )`를 사용해 개선한다.

```abap
DATA lt_status TYPE STANDARD TABLE OF ty_status.
DATA ls_status TYPE ty_status.

ls_status-status = 'A'.
ls_status-text = 'Active'.
APPEND ls_status TO lt_status.

CLEAR ls_status.
ls_status-status = 'I'.
ls_status-text = 'Inactive'.
APPEND ls_status TO lt_status.
```

예상 개선 예:

```abap
DATA(lt_status) = VALUE STANDARD TABLE OF ty_status(
  ( status = 'A' text = 'Active' )
  ( status = 'I' text = 'Inactive' )
).
```

### 18.3 READ TABLE 실습

다음 코드를 Table Expression 또는 `line_exists`를 사용해 개선한다.

```abap
READ TABLE lt_status INTO ls_status WITH KEY status = 'A'.

IF sy-subrc = 0.
  WRITE: / ls_status-text.
ENDIF.
```

예상 개선 예:

```abap
IF line_exists( lt_status[ status = 'A' ] ).
  DATA(ls_status) = lt_status[ status = 'A' ].
  WRITE: / ls_status-text.
ENDIF.
```

## 20. 자가 진단 문제

### Q1. 리팩터링과 기능 변경의 차이는 무엇인가?

**모범 답안:**  
리팩터링은 외부 동작과 결과를 유지하면서 내부 코드 구조를 개선하는 작업이다. 기능 변경은 사용자에게 보이는 동작이나 결과 자체를 바꾸는 작업이다.

### Q2. Inline Declaration을 사용할 때의 장점은 무엇인가?

**모범 답안:**  
변수를 실제 사용 위치에 가깝게 선언하여 Scope를 줄이고, 코드의 의도를 명확하게 만들 수 있다.

### Q3. Table Expression 사용 시 주의할 점은 무엇인가?

**모범 답안:**  
조건에 맞는 행이 없을 때 예외가 발생할 수 있으므로 `OPTIONAL`, `DEFAULT`, `line_exists` 등으로 미존재 상황을 명확히 처리해야 한다.

### Q4. Modern ABAP 문법을 과도하게 쓰면 어떤 문제가 생길 수 있는가?

**모범 답안:**  
코드가 지나치게 압축되어 의도를 읽기 어려워질 수 있고, 팀원이 이해하기 어려운 코드가 될 수 있다. 또한 릴리스 호환성이나 성능 문제가 생길 수 있다.

### Q5. Clean ABAP 관점에서 좋은 리팩터링의 핵심은 무엇인가?

**모범 답안:**  
짧은 코드보다 의도가 분명하고, 테스트 가능하며, 유지보수하기 좋은 코드를 만드는 것이다.

## 21. 강사용 설명 포인트

강의에서는 다음 메시지를 강조한다.

### 21.1 Modern 문법은 도구이다

Modern ABAP은 목적이 아니라 도구이다.  
교육생이 최신 문법을 외우는 데 그치지 않고, 언제 쓰고 언제 쓰지 않을지 판단하게 해야 한다.

### 21.2 한 번에 다 바꾸지 않는다

Legacy 코드를 한 번에 최신 문법으로 전환하면 오류를 찾기 어렵다.  
작은 단위로 바꾸고 매번 결과를 확인하는 습관을 강조한다.

### 21.3 `sy-subrc`를 무시하지 않는다

Modern ABAP이 `sy-subrc`를 없애는 것이 아니다.  
일부 패턴에서 `sy-subrc` 의존을 줄일 수 있지만, 기존 로직이 `sy-subrc`에 의존하고 있다면 대체 흐름을 명확히 설계해야 한다.

### 21.4 릴리스와 팀 규칙을 확인한다

현장에서는 최신 문법을 알고 있어도 고객사 규칙이나 릴리스 제약 때문에 사용하지 못할 수 있다.  
따라서 리팩터링은 기술 지식뿐 아니라 운영 기준과 팀 합의가 함께 필요하다.

## 22. 후속 학습 연결

이 모듈을 끝으로 `THEORY-16 — Modern ABAP Syntax` Section이 마무리된다.  
다음 학습에서는 Modern ABAP 문법을 기반으로 New Open SQL, OO ABAP, CDS, RAP 등 더 큰 구조의 코드 품질을 다루게 된다.

연결 흐름은 다음과 같다.

```text
Modern ABAP Syntax
→ New Open SQL
→ OO ABAP
→ CDS View Entity
→ RAP
```

특히 리팩터링 관점은 이후 모든 주제에 영향을 준다.

| 후속 주제 | 연결 방식 |
|---|---|
| New Open SQL | `@DATA`, host variable, 명시적 필드 조회와 연결 |
| OO ABAP | Method Extract, 책임 분리, Clean Code와 연결 |
| CDS | SQL Pushdown과 ABAP 로직 분리 판단 |
| RAP | Behavior 구현체의 가독성과 유지보수성 |
| ATC | 코드 품질 점검과 리팩터링 근거 제공 |
| ABAP Unit | 리팩터링 안전망 제공 |

---

## 23. 핵심 요약

이번 모듈의 핵심은 다음이다.

```text
리팩터링은 기능을 바꾸지 않고 내부 구조를 개선하는 작업이다.
Modern ABAP 문법은 리팩터링을 돕는 도구이다.
Inline Declaration은 변수 Scope를 줄인다.
VALUE는 데이터 생성 의도를 명확히 한다.
CORRESPONDING은 구조 매핑 의도를 명확히 한다.
Table Expression은 READ TABLE 패턴을 개선할 수 있지만 미존재 상황을 조심해야 한다.
String Template은 문자열 조립 가독성을 높인다.
짧은 코드보다 의도가 분명한 코드가 더 좋은 코드이다.
리팩터링 후에는 반드시 결과 동일성과 예외 상황을 검증해야 한다.
```
