## 0. 이 문서의 학습 범위

이 문서는 `THEORY-16-M02 — VALUE Constructor Expression`만 다룬다.

이번 모듈의 중심 주제는 ABAP의 `VALUE` Constructor Expression이다.  
`VALUE`는 구조체, 내부 테이블, Elementary 값 등을 **표현식 방식으로 생성**할 수 있게 해주는 Modern ABAP의 핵심 문법이다.

기존 ABAP에서는 데이터를 만들기 위해 다음과 같은 절차형 코드가 자주 사용되었다.

```abap
CLEAR ls_item.
ls_item-carrid = 'AA'.
ls_item-connid = '0017'.
APPEND ls_item TO lt_item.
```

Modern ABAP에서는 같은 의도를 다음처럼 더 짧고 명확하게 표현할 수 있다.

```abap
lt_item = VALUE #( ( carrid = 'AA' connid = '0017' ) ).
```

이 모듈에서는 다음을 학습한다.

```text
VALUE의 목적
→ Constructor Expression의 개념
→ VALUE #( ... )와 VALUE type( ... )의 차이
→ 구조체 생성
→ 내부 테이블 생성
→ BASE를 사용한 기존 값 확장
→ VALUE 사용 시 흔한 오류
→ 실무 적용 기준
```

단, `FOR`, `LET`, `REDUCE` 같은 더 복합적인 Constructor Expression 패턴은 이 모듈에서 깊게 다루지 않는다.  
이 문서는 초급자가 `VALUE`를 안전하게 읽고 작성할 수 있도록 만드는 데 집중한다.

## 3. Constructor Expression이란 무엇인가?

### 3.1 쉬운 정의

Constructor Expression은 값을 “단계별 명령”으로 만드는 대신, **표현식 하나로 생성**하는 문법이다.

기존 ABAP 방식은 다음과 같다.

```text
1. 변수를 선언한다.
2. 변수를 초기화한다.
3. 각 필드에 값을 넣는다.
4. 필요하면 내부 테이블에 APPEND한다.
```

Modern ABAP의 Constructor Expression은 다음처럼 표현한다.

```text
이 타입의 값을 이런 구성으로 만들어라.
```

ABAP에서 대표적인 Constructor Expression에는 다음이 있다.

| Constructor Expression | 목적 |
|---|---|
| `VALUE` | 값, 구조체, 내부 테이블 생성 |
| `NEW` | 객체 또는 데이터 참조 생성 |
| `CORRESPONDING` | 이름이 같은 필드 중심 구조 매핑 |
| `CONV` | 타입 변환 |
| `EXACT` | 손실 없는 타입 변환 |
| `REDUCE` | 반복 계산 결과 생성 |
| `COND` | 조건 기반 값 생성 |
| `SWITCH` | 값 분기 기반 결과 생성 |

이 모듈에서는 `VALUE`만 다룬다.

## 4. VALUE의 기본 개념

`VALUE`는 지정된 타입의 값을 생성하는 Constructor Expression이다.

기본 형태는 다음과 같다.

```abap
VALUE type( ... )
```

또는 타입 추론을 사용하는 형태는 다음과 같다.

```abap
VALUE #( ... )
```

여기서 `#`는 “문맥상 알 수 있는 타입을 사용하라”는 의미이다.

예를 들어 왼쪽 변수의 타입이 이미 정해져 있으면, 오른쪽의 `VALUE #( ... )`는 그 타입을 따라간다.

```abap
DATA ls_spfli TYPE spfli.

ls_spfli = VALUE #( carrid = 'AA'
                    connid = '0017' ).
```

위 코드에서 `ls_spfli`의 타입은 `SPFLI`이다.  
따라서 `VALUE #( ... )`의 `#`는 `SPFLI`로 추론된다.

---

## 5. VALUE type( ... )와 VALUE #( ... )의 차이

`VALUE`는 두 가지 방식으로 자주 사용된다.

| 방식 | 의미 | 사용 예 |
|---|---|---|
| `VALUE type( ... )` | 타입을 명시한다. | `VALUE spfli( carrid = 'AA' )` |
| `VALUE #( ... )` | 문맥에서 타입을 추론한다. | `ls_spfli = VALUE #( carrid = 'AA' )` |

### 5.1 타입 명시 방식

```abap
DATA(ls_spfli) = VALUE spfli(
  carrid = 'AA'
  connid = '0017'
).
```

이 방식은 오른쪽에서 직접 `SPFLI` 타입을 지정한다.  
왼쪽 변수는 Inline Declaration으로 선언되어도 오른쪽 타입을 기준으로 결정된다.

### 5.2 타입 추론 방식

```abap
DATA ls_spfli TYPE spfli.

ls_spfli = VALUE #(
  carrid = 'AA'
  connid = '0017'
).
```

이 방식은 왼쪽의 `ls_spfli TYPE spfli`를 기준으로 오른쪽 타입이 추론된다.

### 5.3 실무 판단 기준

| 상황 | 권장 방식 |
|---|---|
| 왼쪽 타입이 명확함 | `VALUE #( ... )` |
| Inline Declaration과 함께 타입을 직접 만들고 싶음 | `VALUE type( ... )` |
| 코드 리뷰자가 타입을 바로 알아야 함 | 타입 명시 고려 |
| 복잡한 중첩 구조 | 타입 명시가 더 읽기 쉬울 수 있음 |
| 간단한 구조체 대입 | `VALUE #( ... )`가 간결함 |

초급 단계에서는 둘 다 읽을 수 있어야 한다.  
작성 시에는 “타입이 문맥상 명확한가?”를 기준으로 선택한다.

## 6. 구조체 생성

### 6.1 기존 방식

예를 들어 항공 연결 정보 구조체를 만든다고 하자.

```abap
DATA ls_spfli TYPE spfli.

CLEAR ls_spfli.
ls_spfli-carrid   = 'AA'.
ls_spfli-connid   = '0017'.
ls_spfli-cityfrom = 'NEW YORK'.
ls_spfli-cityto   = 'SAN FRANCISCO'.
```

이 코드는 이해하기는 쉽지만 반복이 많다.

### 6.2 VALUE 방식

```abap
DATA ls_spfli TYPE spfli.

ls_spfli = VALUE #(
  carrid   = 'AA'
  connid   = '0017'
  cityfrom = 'NEW YORK'
  cityto   = 'SAN FRANCISCO'
).
```

또는 타입을 명시할 수도 있다.

```abap
DATA(ls_spfli) = VALUE spfli(
  carrid   = 'AA'
  connid   = '0017'
  cityfrom = 'NEW YORK'
  cityto   = 'SAN FRANCISCO'
).
```

### 6.3 구조체 VALUE의 장점

| 장점 | 설명 |
|---|---|
| 초기화와 대입이 한 번에 보임 | 어떤 필드가 어떤 값으로 채워지는지 한눈에 보인다. |
| 불필요한 `CLEAR` 감소 | 새 값을 생성하는 표현이므로 초기화 의도가 명확하다. |
| Inline Declaration과 잘 맞음 | `DATA(ls_data) = VALUE type( ... )` 패턴이 자연스럽다. |
| 테스트 데이터 작성에 유리 | ABAP Unit, 샘플 데이터 구성에 적합하다. |

## 7. 내부 테이블 생성

`VALUE`는 내부 테이블 초기 데이터를 만드는 데 특히 유용하다.

### 7.1 기존 방식

```abap
TYPES: BEGIN OF ty_status,
         status TYPE c LENGTH 1,
         text   TYPE string,
       END OF ty_status.

DATA lt_status TYPE STANDARD TABLE OF ty_status WITH EMPTY KEY.
DATA ls_status TYPE ty_status.

CLEAR ls_status.
ls_status-status = 'A'.
ls_status-text   = 'Active'.
APPEND ls_status TO lt_status.

CLEAR ls_status.
ls_status-status = 'I'.
ls_status-text   = 'Inactive'.
APPEND ls_status TO lt_status.

CLEAR ls_status.
ls_status-status = 'B'.
ls_status-text   = 'Blocked'.
APPEND ls_status TO lt_status.
```

### 7.2 VALUE 방식

```abap
TYPES: BEGIN OF ty_status,
         status TYPE c LENGTH 1,
         text   TYPE string,
       END OF ty_status.

DATA lt_status TYPE STANDARD TABLE OF ty_status WITH EMPTY KEY.

lt_status = VALUE #(
  ( status = 'A' text = 'Active'   )
  ( status = 'I' text = 'Inactive' )
  ( status = 'B' text = 'Blocked'  )
).
```

`VALUE`를 사용하면 내부 테이블의 여러 행을 한 번에 선언적으로 생성할 수 있다.

### 7.3 Inline Declaration과 함께 사용

```abap
TYPES: BEGIN OF ty_status,
         status TYPE c LENGTH 1,
         text   TYPE string,
       END OF ty_status,
       tt_status TYPE STANDARD TABLE OF ty_status WITH EMPTY KEY.

DATA(lt_status) = VALUE tt_status(
  ( status = 'A' text = 'Active'   )
  ( status = 'I' text = 'Inactive' )
  ( status = 'B' text = 'Blocked'  )
).
```

이 패턴은 테스트 데이터나 작은 코드 테이블 성격의 예제를 만들 때 매우 유용하다.

---

## 8. 내부 테이블 VALUE 문법 읽는 법

다음 코드를 기준으로 읽어보자.

```abap
DATA(lt_status) = VALUE tt_status(
  ( status = 'A' text = 'Active'   )
  ( status = 'I' text = 'Inactive' )
  ( status = 'B' text = 'Blocked'  )
).
```

구성 요소는 다음과 같다.

| 코드 | 의미 |
|---|---|
| `DATA(lt_status)` | Inline Declaration으로 변수 선언 |
| `VALUE tt_status` | `tt_status` 타입의 값을 생성 |
| 첫 번째 `( ... )` | 내부 테이블의 첫 번째 행 |
| `status = 'A'` | 행의 `STATUS` 필드 값 |
| `text = 'Active'` | 행의 `TEXT` 필드 값 |

내부 테이블을 `VALUE`로 생성할 때는 **바깥 괄호는 테이블 전체**, **안쪽 괄호는 각 행**으로 이해하면 된다.

```text
VALUE table_type(
  ( row 1 )
  ( row 2 )
  ( row 3 )
)
```

## 9. DEFAULT Component 값 사용

내부 테이블에서 여러 행이 같은 값을 공유할 때는 공통 Component 값을 바깥에 둘 수 있다.

예를 들어 모든 행의 `carrid`가 `AA`라고 하자.

```abap
TYPES: BEGIN OF ty_conn,
         carrid TYPE s_carr_id,
         connid TYPE s_conn_id,
         cityto TYPE s_to_cit,
       END OF ty_conn,
       tt_conn TYPE STANDARD TABLE OF ty_conn WITH EMPTY KEY.

DATA(lt_conn) = VALUE tt_conn(
  carrid = 'AA'
  ( connid = '0017' cityto = 'SAN FRANCISCO' )
  ( connid = '0064' cityto = 'NEW YORK'      )
).
```

위 코드에서 `carrid = 'AA'`는 이후 행들에 적용되는 공통 값처럼 읽을 수 있다.

초급자에게는 이 문법이 처음에 낯설 수 있으므로, 다음처럼 해석하면 된다.

```text
이 테이블의 각 행은 기본적으로 carrid = 'AA'를 가진다.
각 행에서는 connid와 cityto만 다르게 지정한다.
```

다만 실무 코드에서는 공통값을 바깥에 두는 방식이 항상 더 읽기 쉬운 것은 아니다.  
행마다 값을 명시하는 편이 리뷰에 더 적합한 경우도 있다.

## 10. BASE를 사용한 값 확장

`BASE`는 기존 값을 바탕으로 새로운 값을 만들 때 사용한다.

### 10.1 구조체 BASE

```abap
DATA(ls_base) = VALUE spfli(
  carrid = 'AA'
  connid = '0017'
).

DATA(ls_new) = VALUE spfli(
  BASE ls_base
  cityfrom = 'NEW YORK'
  cityto   = 'SAN FRANCISCO'
).
```

이 코드는 다음 의미이다.

```text
LS_BASE의 값을 기본으로 가져온다.
그 위에 CITYFROM, CITYTO 값을 추가 또는 덮어쓴다.
```

### 10.2 내부 테이블 BASE

```abap
DATA lt_status TYPE STANDARD TABLE OF ty_status WITH EMPTY KEY.

lt_status = VALUE #(
  ( status = 'A' text = 'Active' )
).

lt_status = VALUE #(
  BASE lt_status
  ( status = 'I' text = 'Inactive' )
  ( status = 'B' text = 'Blocked'  )
).
```

이 코드는 기존 `lt_status` 내용을 유지하면서 두 행을 추가한 새 내부 테이블 값을 만든다.

### 10.3 BASE 사용 시 주의점

`BASE`는 편리하지만, 남용하면 데이터 흐름을 추적하기 어려워질 수 있다.

| 상황 | 판단 |
|---|---|
| 기존 구조체 일부 필드만 바꿔 새 구조체 생성 | 적합 |
| 기존 내부 테이블에 소량의 초기 행 추가 | 적합 |
| 반복문 안에서 대량 데이터를 계속 `BASE`로 누적 | 성능과 가독성 검토 필요 |
| 변경 의도를 명확히 보여야 하는 업무 코드 | 일반 `APPEND`가 더 명확할 수 있음 |

특히 대량 데이터를 반복적으로 누적하는 경우 `VALUE #( BASE ... )`가 매번 새 값을 구성하는 형태로 읽힐 수 있으므로, 단순한 `APPEND`, `INSERT`, `COLLECT` 등이 더 적합한지 검토해야 한다.

## 11. VALUE와 초기값

`VALUE`는 지정하지 않은 Component를 해당 타입의 초기값으로 둔다.

```abap
DATA(ls_spfli) = VALUE spfli(
  carrid = 'AA'
  connid = '0017'
).
```

위 코드에서 `cityfrom`, `cityto` 등 지정하지 않은 필드는 초기값을 가진다.

초기값 예시는 다음과 같다.

| 타입 | 초기값 감각 |
|---|---|
| Character | 공백 |
| Numeric | 0 |
| Date | `00000000` |
| Time | `000000` |
| String | 빈 문자열 |
| Internal Table | 빈 테이블 |

실무에서 이 특성은 장점이 될 수도 있고 위험이 될 수도 있다.

### 11.1 장점

```text
필요한 필드만 명시하여 간결한 테스트 데이터를 만들 수 있다.
```

### 11.2 위험

```text
실수로 필드를 누락해도 문법 오류가 아니라 초기값으로 들어갈 수 있다.
```

예를 들어 필수적으로 채워야 하는 `currency`, `unit`, `status` 같은 필드가 빠지면 런타임상 데이터 의미가 잘못될 수 있다.

## 12. VALUE와 DDIC 타입

`VALUE`는 로컬 타입뿐 아니라 DDIC 타입에도 사용할 수 있다.

예를 들어 표준 Dictionary Structure인 `SPFLI`를 기준으로 값을 만들 수 있다.

```abap
DATA(ls_spfli) = VALUE spfli(
  carrid = 'AA'
  connid = '0017'
).
```

또는 직접 만든 DDIC Structure를 사용할 수 있다.

```abap
DATA(ls_user) = VALUE zs_jhy_user_info(
  user_id   = 'U0001'
  user_name = 'Kim Developer'
  status    = 'A'
).
```

이 방식은 DDIC와 Modern ABAP Syntax가 만나는 지점이다.

```text
DDIC에서 타입을 정의한다.
ABAP 프로그램에서 VALUE로 해당 타입의 값을 만든다.
```

## 13. VALUE와 Range Table

`VALUE`는 Range Table을 만들 때도 자주 사용된다.  
다만 Range Table은 `THEORY-10 SELECT-OPTIONS와 Range Table`에서 이미 학습한 주제이므로 여기서는 연결 예제로만 다룬다.

```abap
DATA lr_carrid TYPE RANGE OF s_carr_id.

lr_carrid = VALUE #(
  ( sign = 'I' option = 'EQ' low = 'AA' )
  ( sign = 'I' option = 'EQ' low = 'LH' )
).
```

이 코드는 `CARRID`가 `AA` 또는 `LH`인 조건을 표현하는 Range Table을 만든다.

Modern ABAP에서는 다음과 같이 Inline Declaration과 함께 쓸 수도 있다.

```abap
DATA(lr_carrid) = VALUE RANGE OF s_carr_id(
  ( sign = 'I' option = 'EQ' low = 'AA' )
  ( sign = 'I' option = 'EQ' low = 'LH' )
).
```

실무에서는 조회 조건을 코드 안에서 구성할 때 이 패턴이 자주 사용된다.

## 14. VALUE와 SELECT 결과는 다르다

초급자가 혼동할 수 있는 점이 있다.

`VALUE`는 데이터를 생성하는 표현식이지, DB에서 데이터를 조회하는 문법이 아니다.

| 구분 | 역할 |
|---|---|
| `VALUE` | 메모리 안에서 값 또는 내부 테이블을 생성 |
| `SELECT` | 데이터베이스에서 데이터를 조회 |
| `APPEND` | 내부 테이블에 한 행 추가 |
| `MODIFY` | 내부 테이블 또는 DB 데이터 변경 |

예를 들어 다음은 내부 테이블에 값을 직접 만든 것이다.

```abap
DATA(lt_status) = VALUE tt_status(
  ( status = 'A' text = 'Active' )
  ( status = 'I' text = 'Inactive' )
).
```

반면 다음은 DB에서 데이터를 조회하는 것이다.

```abap
SELECT carrid,
       connid
  FROM spfli
  INTO TABLE @DATA(lt_spfli).
```

`VALUE`는 SELECT를 대체하지 않는다.  
다만 SELECT 조건용 Range Table을 만들거나, 조회 결과를 가공할 때 보조적으로 사용할 수 있다.

## 15. Legacy 코드와 Modern 코드 비교

### 15.1 구조체 생성 비교

Legacy 방식:

```abap
DATA ls_user TYPE zs_jhy_user_info.

CLEAR ls_user.
ls_user-user_id   = 'U0001'.
ls_user-user_name = 'Kim Developer'.
ls_user-status    = 'A'.
```

Modern 방식:

```abap
DATA(ls_user) = VALUE zs_jhy_user_info(
  user_id   = 'U0001'
  user_name = 'Kim Developer'
  status    = 'A'
).
```

### 15.2 내부 테이블 생성 비교

Legacy 방식:

```abap
DATA lt_user TYPE STANDARD TABLE OF zs_jhy_user_info.
DATA ls_user TYPE zs_jhy_user_info.

CLEAR ls_user.
ls_user-user_id   = 'U0001'.
ls_user-user_name = 'Kim Developer'.
ls_user-status    = 'A'.
APPEND ls_user TO lt_user.

CLEAR ls_user.
ls_user-user_id   = 'U0002'.
ls_user-user_name = 'Lee Consultant'.
ls_user-status    = 'I'.
APPEND ls_user TO lt_user.
```

Modern 방식:

```abap
DATA(lt_user) = VALUE ztt_jhy_user_info(
  ( user_id = 'U0001' user_name = 'Kim Developer'  status = 'A' )
  ( user_id = 'U0002' user_name = 'Lee Consultant' status = 'I' )
).
```

### 15.3 무조건 Modern 방식이 좋은가?

아니다.  
Modern ABAP은 간결하지만, 지나치게 긴 `VALUE` 표현식은 오히려 읽기 어렵다.

다음 기준이 중요하다.

```text
짧고 명확한 데이터 생성 → VALUE 적합
복잡한 분기와 예외 처리가 섞인 로직 → 절차형 코드가 더 명확할 수 있음
대량 데이터 반복 누적 → 성능과 가독성 검토 필요
테스트 데이터 준비 → VALUE 매우 적합
```

## 16. 정상 흐름과 오류 흐름

### 16.1 정상 흐름

```text
타입을 준비한다.
→ VALUE type( ... ) 또는 VALUE #( ... )를 작성한다.
→ 필드 이름을 정확히 입력한다.
→ 필요한 값만 명시한다.
→ Syntax Check를 수행한다.
→ Debugger에서 생성된 구조체 또는 내부 테이블 값을 확인한다.
```

### 16.2 오류 흐름 1: 타입 추론 실패

#### 예시

```abap
DATA(ls_data) = VALUE #( carrid = 'AA' ).
```

#### 문제

왼쪽 `DATA(ls_data)`도 타입을 모르고, 오른쪽 `VALUE #( ... )`도 `#`로 타입을 추론하려 한다.  
문맥상 타입이 명확하지 않으면 컴파일 오류가 발생한다.

#### 해결

타입을 명시한다.

```abap
DATA(ls_data) = VALUE spfli( carrid = 'AA' ).
```

또는 왼쪽 변수 타입을 먼저 선언한다.

```abap
DATA ls_data TYPE spfli.
ls_data = VALUE #( carrid = 'AA' ).
```

---

### 16.3 오류 흐름 2: 존재하지 않는 Component 사용

#### 예시

```abap
DATA(ls_spfli) = VALUE spfli(
  carrier_id = 'AA'
).
```

#### 문제

`SPFLI`에 `CARRIER_ID`라는 Component가 없다면 Syntax Check 오류가 발생한다.

#### 해결

DDIC Structure 또는 로컬 타입의 실제 Component 이름을 확인한다.

```abap
DATA(ls_spfli) = VALUE spfli(
  carrid = 'AA'
).
```

---

### 16.4 오류 흐름 3: 내부 테이블 행 괄호 누락

#### 잘못된 예

```abap
DATA(lt_status) = VALUE tt_status(
  status = 'A' text = 'Active'
  status = 'I' text = 'Inactive'
).
```

#### 문제

내부 테이블의 각 행은 괄호로 감싸야 한다.

#### 올바른 예

```abap
DATA(lt_status) = VALUE tt_status(
  ( status = 'A' text = 'Active'   )
  ( status = 'I' text = 'Inactive' )
).
```

---

### 16.5 오류 흐름 4: 필수 업무값 누락

문법적으로는 맞지만 업무적으로 잘못된 코드도 있다.

```abap
DATA(ls_user) = VALUE zs_jhy_user_info(
  user_id = 'U0001'
).
```

`USER_NAME`, `STATUS`가 업무적으로 필수라면 이 코드는 위험하다.  
ABAP 문법은 누락된 필드를 초기값으로 둘 수 있지만, 업무적으로는 불완전한 데이터가 된다.

해결은 코드 리뷰 기준을 두는 것이다.

```text
VALUE로 객체를 만들 때 업무상 필수 필드를 빠뜨리지 않았는지 확인한다.
```

## 17. Debugger에서 확인할 포인트

`VALUE`는 한 줄로 값을 만들기 때문에 초급자는 디버깅이 어렵다고 느낄 수 있다.  
하지만 생성 후 변수 값을 보면 된다.

확인 포인트는 다음과 같다.

| 확인 대상 | 확인 내용 |
|---|---|
| 구조체 변수 | Component 값이 의도대로 들어갔는가 |
| 내부 테이블 | 행 수가 맞는가 |
| 내부 테이블 각 행 | 각 Component 값이 맞는가 |
| 누락 필드 | 초기값으로 들어간 필드가 없는가 |
| BASE 결과 | 기존 값이 유지되고 새 값이 추가되었는가 |

예를 들어 다음 코드 실행 후 `LT_STATUS`를 확인한다.

```abap
DATA(lt_status) = VALUE tt_status(
  ( status = 'A' text = 'Active'   )
  ( status = 'I' text = 'Inactive' )
  ( status = 'B' text = 'Blocked'  )
).
```

Debugger에서 확인할 내용:

```text
LT_STATUS 행 수 = 3
1행 STATUS = A, TEXT = Active
2행 STATUS = I, TEXT = Inactive
3행 STATUS = B, TEXT = Blocked
```

## 18. 실무 적용 기준

### 18.1 VALUE를 적극 추천하는 경우

| 상황 | 이유 |
|---|---|
| 작은 구조체 초기화 | 필드 대입을 한눈에 볼 수 있다. |
| 테스트 데이터 생성 | ABAP Unit Given 데이터 작성에 유리하다. |
| 작은 내부 테이블 상수성 데이터 생성 | `APPEND` 반복보다 간결하다. |
| Range Table 생성 | 조회 조건을 명확히 표현할 수 있다. |
| Inline Declaration과 함께 타입 생성 | Modern ABAP 스타일과 잘 맞는다. |

### 18.2 신중하게 써야 하는 경우

| 상황 | 이유 |
|---|---|
| 행이 너무 많은 내부 테이블 생성 | 코드가 길어져 가독성이 떨어질 수 있다. |
| 복잡한 조건 분기 포함 | `COND`, `SWITCH`, `FOR`가 섞이면 초급자에게 어렵다. |
| 대량 데이터 반복 누적 | 성능과 메모리 사용을 검토해야 한다. |
| 업무상 필수 필드가 많은 구조 | 필드 누락 위험이 있다. |
| 팀의 ABAP 버전이 낮음 | 시스템 Release와 문법 지원 여부 확인 필요 |

### 18.3 코드 리뷰 기준

`VALUE` 사용 코드를 리뷰할 때는 다음 질문을 한다.

```text
타입이 명확한가?
필드 이름이 실제 Component와 일치하는가?
필수 업무값이 누락되지 않았는가?
한 줄에 너무 많은 정보를 넣지 않았는가?
BASE 사용이 데이터 흐름을 더 명확하게 만드는가?
Legacy 방식보다 실제로 읽기 쉬워졌는가?
```

## 19. Clean ABAP 관점

Modern ABAP 문법은 Clean Code를 자동으로 보장하지 않는다.  
`VALUE`를 썼다고 해서 무조건 좋은 코드가 되는 것은 아니다.

좋은 사용 예:

```abap
DATA(ls_message) = VALUE ty_message(
  type = 'S'
  text = 'Process completed successfully.'
).
```

가독성이 떨어지는 예:

```abap
DATA(lt_data) = VALUE tt_data( ( a = '1' b = '2' c = '3' d = '4' e = '5' f = '6' ) ( a = '7' b = '8' c = '9' d = '10' e = '11' f = '12' ) ).
```

위 코드는 문법적으로 가능하더라도 읽기 어렵다.  
필드 수가 많거나 행 수가 많으면 줄바꿈과 정렬이 중요하다.

권장 포맷:

```abap
DATA(lt_data) = VALUE tt_data(
  ( a = '1'
    b = '2'
    c = '3'
    d = '4'
    e = '5'
    f = '6' )
  ( a = '7'
    b = '8'
    c = '9'
    d = '10'
    e = '11'
    f = '12' )
).
```

## 20. 미니 실습

### 20.1 실습 목표

`VALUE`를 사용하여 상태 코드 내부 테이블과 항공 연결 구조체를 생성한다.

### 20.2 실습 코드

```abap
REPORT zjhy_value_expr_basic.

TYPES: BEGIN OF ty_status,
         status TYPE c LENGTH 1,
         text   TYPE string,
       END OF ty_status,
       tt_status TYPE STANDARD TABLE OF ty_status WITH EMPTY KEY.

DATA(lt_status) = VALUE tt_status(
  ( status = 'A' text = 'Active'   )
  ( status = 'I' text = 'Inactive' )
  ( status = 'B' text = 'Blocked'  )
).

DATA(ls_spfli) = VALUE spfli(
  carrid   = 'AA'
  connid   = '0017'
  cityfrom = 'NEW YORK'
  cityto   = 'SAN FRANCISCO'
).

WRITE: / 'Status count:', lines( lt_status ).
WRITE: / 'Carrier:', ls_spfli-carrid,
       / 'Connection:', ls_spfli-connid,
       / 'From:', ls_spfli-cityfrom,
       / 'To:', ls_spfli-cityto.
```

### 20.3 실습 확인 항목

| 확인 항목 | 기대 결과 |
|---|---|
| Syntax Check | 오류 없음 |
| `LT_STATUS` 행 수 | 3 |
| `LS_SPFLI-CARRID` | `AA` |
| `LS_SPFLI-CONNID` | `0017` |
| 출력 결과 | 상태 개수와 항공 연결 정보 표시 |

### 20.4 오류 케이스 실습

다음 코드를 일부러 작성해본다.

```abap
DATA(ls_data) = VALUE #( carrid = 'AA' ).
```

예상 결과:

```text
타입 추론에 필요한 문맥이 부족하여 Syntax Check 오류가 발생할 수 있다.
```

수정:

```abap
DATA(ls_data) = VALUE spfli( carrid = 'AA' ).
```

## 21. 강사용 설명 포인트

강의에서는 다음 메시지를 강조한다.

### 21.1 VALUE는 “줄이기”가 아니라 “의도 표현”이다

단순히 코드 줄 수를 줄이는 목적이 아니다.  
데이터 생성 의도를 더 명확히 표현하는 것이 핵심이다.

### 21.2 #은 마법이 아니다

`#`는 타입을 자동으로 아무렇게나 찾아주는 기능이 아니다.  
왼쪽 변수, 메서드 파라미터, 타입 문맥 등에서 추론 가능한 경우에만 사용할 수 있다.

### 21.3 구조체와 내부 테이블 괄호를 구분시킨다

초급자는 내부 테이블 행 괄호를 자주 놓친다.

```abap
VALUE table_type(
  ( row 1 )
  ( row 2 )
)
```

이 형태를 반복해서 익히게 한다.

### 21.4 Modern ABAP도 팀 기준이 필요하다

현업에서는 팀원들의 ABAP 숙련도, 시스템 Release, 코드 리뷰 기준을 고려해야 한다.  
새 문법을 쓰더라도 유지보수자가 읽을 수 있어야 한다.

## 22. 평가 문제

### 22.1 객관식

#### Q1. `VALUE` Constructor Expression의 주된 목적은 무엇인가?

A. 데이터베이스에서 데이터를 조회한다.  
B. 지정된 타입의 값을 표현식으로 생성한다.  
C. 프로그램을 백그라운드로 실행한다.  
D. Screen Painter에서 화면을 생성한다.

**정답:** B

#### Q2. `VALUE #( ... )`에서 `#`의 의미로 가장 적절한 것은?

A. 항상 문자열 타입을 의미한다.  
B. 타입을 문맥에서 추론하라는 의미이다.  
C. 내부 테이블만 생성하라는 의미이다.  
D. 오류를 무시하라는 의미이다.

**정답:** B

#### Q3. 내부 테이블을 `VALUE`로 만들 때 각 행은 어떻게 표현하는가?

A. 쉼표로만 구분한다.  
B. 각 행을 괄호 `( ... )`로 감싼다.  
C. `APPEND`를 반드시 사용한다.  
D. `CLEAR`를 먼저 사용해야 한다.

**정답:** B

---

### 22.2 단답형

#### Q1. `VALUE spfli( carrid = 'AA' )`와 `VALUE #( carrid = 'AA' )`의 차이를 설명하시오.

**모범 답안:**  
`VALUE spfli( ... )`는 생성할 타입을 `SPFLI`로 명시한 방식이다. `VALUE #( ... )`는 문맥에서 타입을 추론하는 방식이다. 왼쪽 변수 타입이나 파라미터 타입 등 추론 가능한 문맥이 있어야 한다.

#### Q2. `BASE`의 목적을 설명하시오.

**모범 답안:**  
`BASE`는 기존 구조체나 내부 테이블 값을 기반으로 새 값을 생성할 때 사용한다. 기존 값을 유지하면서 일부 필드를 덮어쓰거나 내부 테이블 행을 추가하는 식으로 사용할 수 있다.

#### Q3. `VALUE` 사용 시 업무적으로 주의해야 할 점은 무엇인가?

**모범 답안:**  
지정하지 않은 Component는 초기값이 되므로, 업무상 필수 필드를 누락하지 않았는지 확인해야 한다. 또한 너무 복잡한 `VALUE` 표현식은 가독성을 해칠 수 있으므로 코드 리뷰 기준이 필요하다.

## 24. 후속 모듈 연결

이번 모듈에서는 `VALUE`를 통해 값을 생성하는 방법을 배웠다.  
다음 모듈인 `THEORY-16-M03 CORRESPONDING과 구조 매핑`에서는 구조체 사이에서 이름이 같은 필드를 기준으로 값을 매핑하는 방법을 다룬다.

연결 관계는 다음과 같다.

```text
THEORY-16-M01 Inline Declaration
  → 타입 추론과 선언 위치 단축

THEORY-16-M02 VALUE Constructor Expression
  → 값과 내부 테이블 생성

THEORY-16-M03 CORRESPONDING과 구조 매핑
  → 구조체/내부 테이블 간 필드 매핑

THEORY-16-M04 Table Expression
  → 내부 테이블 한 줄 접근
```

즉, `VALUE`는 Modern ABAP에서 데이터를 “만드는” 문법이고, `CORRESPONDING`은 데이터를 “옮기고 맞추는” 문법으로 이해하면 좋다.

## 25. 핵심 요약

```text
VALUE는 지정된 타입의 값을 생성하는 Constructor Expression이다.
VALUE type( ... )는 타입을 명시하고, VALUE #( ... )는 문맥에서 타입을 추론한다.
구조체는 field = value 형태로 생성한다.
내부 테이블은 각 행을 ( ... )로 감싸서 생성한다.
BASE는 기존 값을 바탕으로 새 값을 만들 때 사용한다.
지정하지 않은 Component는 초기값이 되므로 필수 필드 누락에 주의해야 한다.
VALUE는 코드 줄 수를 줄이는 문법이 아니라 데이터 생성 의도를 명확히 표현하는 문법이다.
```
