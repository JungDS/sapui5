## 3. 조건 분기가 필요한 이유

프로그램은 입력값, 데이터 상태, 업무 조건에 따라 다른 처리를 해야 한다.

예를 들어 사용자 상태가 다음과 같다고 하자.

| 상태값 | 의미 |
|---|---|
| A | Active |
| I | Inactive |
| B | Blocked |

상태가 `A`이면 “사용 가능”을 출력하고, `I`이면 “비활성 사용자”를 출력하고, `B`이면 “차단 사용자”를 출력해야 한다.

조건 분기가 없다면 모든 메시지를 무조건 출력하게 된다.

```abap
WRITE: / '사용 가능'.
WRITE: / '비활성 사용자'.
WRITE: / '차단 사용자'.
```

이 코드는 업무적으로 맞지 않다.  
상태값에 따라 하나의 메시지만 선택해야 한다.

그래서 조건 분기가 필요하다.

```abap
IF gv_status = 'A'.
  WRITE: / '사용 가능'.
ELSEIF gv_status = 'I'.
  WRITE: / '비활성 사용자'.
ELSEIF gv_status = 'B'.
  WRITE: / '차단 사용자'.
ELSE.
  WRITE: / '알 수 없는 상태'.
ENDIF.
```

## 4. IF 기본 구조

### 4.1 기본 문법

ABAP의 가장 기본적인 조건문은 `IF`이다.

```abap
IF 조건식.
  "조건식이 참일 때 실행할 문장
ENDIF.
```

예제:

```abap
REPORT zgpt_if_basic_01.

DATA gv_score TYPE i VALUE 80.

IF gv_score >= 60.
  WRITE: / '합격입니다.'.
ENDIF.
```

`GV_SCORE`가 60 이상이면 메시지가 출력된다.  
60 미만이면 `IF` 블록 내부의 문장은 실행되지 않는다.

### 4.2 조건식의 의미

조건식은 참 또는 거짓으로 평가되는 표현식이다.

예:

```abap
gv_score >= 60
gv_status = 'A'
gv_count <> 0
gv_name IS INITIAL
```

조건식이 참이면 `IF` 내부가 실행된다.  
조건식이 거짓이면 건너뛴다.

## 5. ELSE

`ELSE`는 `IF` 조건이 거짓일 때 실행되는 대체 흐름이다.

```abap
IF 조건식.
  "조건식이 참일 때
ELSE.
  "조건식이 거짓일 때
ENDIF.
```

예제:

```abap
REPORT zgpt_if_else_01.

DATA gv_score TYPE i VALUE 45.

IF gv_score >= 60.
  WRITE: / '합격입니다.'.
ELSE.
  WRITE: / '불합격입니다.'.
ENDIF.
```

이 프로그램에서는 점수가 45이므로 `ELSE` 블록이 실행된다.

### 5.1 ELSE의 실무 의미

`ELSE`는 “위 조건에 해당하지 않는 나머지 모든 경우”를 의미한다.

따라서 `ELSE`에 들어가는 로직은 신중해야 한다.

나쁜 예:

```abap
IF gv_status = 'A'.
  WRITE: / 'Active'.
ELSE.
  WRITE: / 'Inactive'.
ENDIF.
```

이 코드는 `A`가 아닌 모든 값을 `Inactive`로 처리한다.  
그런데 실제로는 `B`, `D`, 공백, 잘못된 값도 모두 `Inactive`가 된다.

더 안전한 예:

```abap
IF gv_status = 'A'.
  WRITE: / 'Active'.
ELSEIF gv_status = 'I'.
  WRITE: / 'Inactive'.
ELSE.
  WRITE: / 'Unknown status'.
ENDIF.
```

초급자는 `ELSE`를 “나머지는 대충 처리”가 아니라 “명시된 조건에 해당하지 않는 모든 예외 흐름”으로 이해해야 한다.

## 6. ELSEIF

`ELSEIF`는 여러 조건을 순차적으로 판단할 때 사용한다.

```abap
IF 조건1.
  "조건1이 참일 때
ELSEIF 조건2.
  "조건1은 거짓이고 조건2가 참일 때
ELSEIF 조건3.
  "조건1, 조건2는 거짓이고 조건3이 참일 때
ELSE.
  "어느 조건도 참이 아닐 때
ENDIF.
```

예제:

```abap
REPORT zgpt_elseif_01.

DATA gv_score TYPE i VALUE 85.

IF gv_score >= 90.
  WRITE: / 'A Grade'.
ELSEIF gv_score >= 80.
  WRITE: / 'B Grade'.
ELSEIF gv_score >= 70.
  WRITE: / 'C Grade'.
ELSEIF gv_score >= 60.
  WRITE: / 'D Grade'.
ELSE.
  WRITE: / 'F Grade'.
ENDIF.
```

`GV_SCORE`가 85이면 첫 번째 조건 `>= 90`은 거짓이다.  
두 번째 조건 `>= 80`은 참이므로 `B Grade`가 출력된다.  
그 이후 조건은 더 이상 검사하지 않는다.

### 6.1 조건 순서가 중요한 이유

다음 코드는 잘못된 예이다.

```abap
IF gv_score >= 60.
  WRITE: / 'D Grade'.
ELSEIF gv_score >= 70.
  WRITE: / 'C Grade'.
ELSEIF gv_score >= 80.
  WRITE: / 'B Grade'.
ELSEIF gv_score >= 90.
  WRITE: / 'A Grade'.
ENDIF.
```

점수가 95여도 첫 번째 조건 `>= 60`에서 이미 참이므로 `D Grade`가 출력된다.  
조건문은 위에서 아래로 평가되기 때문에, 범위 조건은 좁은 조건 또는 높은 우선순위 조건을 먼저 작성해야 한다.

정상 예:

```abap
IF gv_score >= 90.
  WRITE: / 'A Grade'.
ELSEIF gv_score >= 80.
  WRITE: / 'B Grade'.
ELSEIF gv_score >= 70.
  WRITE: / 'C Grade'.
ELSEIF gv_score >= 60.
  WRITE: / 'D Grade'.
ELSE.
  WRITE: / 'F Grade'.
ENDIF.
```

## 7. 비교 연산자

조건식에서 자주 사용하는 비교 연산자는 다음과 같다.

| 연산자 | 의미 | 예 |
|---|---|---|
| `=` | 같다 | `gv_status = 'A'` |
| `<>` | 같지 않다 | `gv_status <> 'A'` |
| `<` | 작다 | `gv_count < 10` |
| `<=` | 작거나 같다 | `gv_count <= 10` |
| `>` | 크다 | `gv_score > 90` |
| `>=` | 크거나 같다 | `gv_score >= 60` |
| `IS INITIAL` | 초기값이다 | `gv_name IS INITIAL` |
| `IS NOT INITIAL` | 초기값이 아니다 | `gv_name IS NOT INITIAL` |

### 7.1 문자 비교

```abap
DATA gv_status TYPE c LENGTH 1 VALUE 'A'.

IF gv_status = 'A'.
  WRITE: / 'Active'.
ENDIF.
```

문자 비교에서는 값의 대소문자와 공백에 주의해야 한다.  
`CHAR` 타입은 고정 길이이며, 오른쪽 공백을 포함한 내부 표현과 화면 표시가 다르게 느껴질 수 있다.

### 7.2 숫자 비교

```abap
DATA gv_amount TYPE i VALUE 100.

IF gv_amount > 0.
  WRITE: / 'Positive amount'.
ENDIF.
```

숫자 비교에서는 데이터 타입이 중요하다.  
문자 타입에 숫자를 담아 비교하는 방식은 혼란을 만들 수 있다.

### 7.3 초기값 검사

ABAP에서는 변수가 값이 없는 상태인지 확인할 때 `IS INITIAL`을 자주 사용한다.

```abap
DATA gv_name TYPE string.

IF gv_name IS INITIAL.
  WRITE: / 'Name is empty.'.
ENDIF.
```

초급자는 다음처럼 직접 공백만 비교하는 방식보다 `IS INITIAL`을 우선적으로 이해하는 것이 좋다.

```abap
IF gv_name = ''.
  WRITE: / 'Name is empty.'.
ENDIF.
```

문자열, 고정 길이 문자, 숫자, 날짜 등 타입에 따라 초기값의 의미가 다르므로 `IS INITIAL`은 실무에서 매우 중요하다.

## 8. 논리 연산자 AND / OR / NOT

여러 조건을 조합할 때 논리 연산자를 사용한다.

| 연산자 | 의미 |
|---|---|
| `AND` | 양쪽 조건이 모두 참일 때 참 |
| `OR` | 둘 중 하나 이상이 참일 때 참 |
| `NOT` | 조건 결과를 반대로 뒤집음 |

### 8.1 AND

```abap
DATA gv_score TYPE i VALUE 85.
DATA gv_attend TYPE i VALUE 90.

IF gv_score >= 60 AND gv_attend >= 80.
  WRITE: / 'Pass'.
ELSE.
  WRITE: / 'Fail'.
ENDIF.
```

점수와 출석률이 모두 기준을 만족해야 합격이다.

### 8.2 OR

```abap
DATA gv_role TYPE c LENGTH 5 VALUE 'ADMIN'.

IF gv_role = 'ADMIN' OR gv_role = 'SUPER'.
  WRITE: / '관리자 권한입니다.'.
ELSE.
  WRITE: / '일반 사용자입니다.'.
ENDIF.
```

둘 중 하나만 맞아도 조건은 참이다.

### 8.3 NOT

```abap
DATA gv_name TYPE string.

IF NOT gv_name IS INITIAL.
  WRITE: / 'Name exists.'.
ENDIF.
```

다만 초급 단계에서는 `NOT`을 과도하게 중첩하지 않는 것이 좋다.

읽기 어려운 예:

```abap
IF NOT gv_status <> 'A'.
  WRITE: / 'Active'.
ENDIF.
```

더 읽기 좋은 예:

```abap
IF gv_status = 'A'.
  WRITE: / 'Active'.
ENDIF.
```

## 9. CASE 기본 구조

`CASE`는 하나의 기준 값이 여러 경우 중 어디에 해당하는지 판단할 때 적합하다.

```abap
CASE 변수.
  WHEN 값1.
    "값1일 때 실행
  WHEN 값2.
    "값2일 때 실행
  WHEN 값3.
    "값3일 때 실행
  WHEN OTHERS.
    "어느 값에도 해당하지 않을 때 실행
ENDCASE.
```

예제:

```abap
REPORT zgpt_case_basic_01.

DATA gv_status TYPE c LENGTH 1 VALUE 'A'.

CASE gv_status.
  WHEN 'A'.
    WRITE: / 'Active'.
  WHEN 'I'.
    WRITE: / 'Inactive'.
  WHEN 'B'.
    WRITE: / 'Blocked'.
  WHEN OTHERS.
    WRITE: / 'Unknown status'.
ENDCASE.
```

이 프로그램은 `GV_STATUS` 값이 무엇인지에 따라 서로 다른 메시지를 출력한다.

## 10. IF와 CASE의 선택 기준

`IF`와 `CASE`는 모두 조건 분기 문법이다.  
하지만 적합한 상황이 다르다.

| 상황 | 권장 문법 | 이유 |
|---|---|---|
| 하나의 변수 값이 여러 고정 값 중 하나인지 판단 | CASE | 가독성이 좋다 |
| 범위 조건을 판단 | IF | `>=`, `<`, `BETWEEN` 성격 판단에 적합 |
| 여러 변수를 조합 | IF | `AND`, `OR` 조합이 자연스럽다 |
| 복잡한 업무 조건 | IF | 다양한 조건식을 작성하기 쉽다 |
| 상태 코드별 처리 | CASE | 값 중심 분기에 적합 |

### 10.1 CASE가 더 좋은 예

```abap
CASE gv_status.
  WHEN 'A'.
    WRITE: / 'Active'.
  WHEN 'I'.
    WRITE: / 'Inactive'.
  WHEN 'B'.
    WRITE: / 'Blocked'.
  WHEN OTHERS.
    WRITE: / 'Unknown'.
ENDCASE.
```

같은 로직을 `IF`로도 작성할 수 있다.

```abap
IF gv_status = 'A'.
  WRITE: / 'Active'.
ELSEIF gv_status = 'I'.
  WRITE: / 'Inactive'.
ELSEIF gv_status = 'B'.
  WRITE: / 'Blocked'.
ELSE.
  WRITE: / 'Unknown'.
ENDIF.
```

둘 다 동작하지만, 상태 코드처럼 하나의 값에 대한 분기는 `CASE`가 더 읽기 쉽다.

### 10.2 IF가 더 좋은 예

```abap
IF gv_score >= 90.
  WRITE: / 'A Grade'.
ELSEIF gv_score >= 80.
  WRITE: / 'B Grade'.
ELSEIF gv_score >= 70.
  WRITE: / 'C Grade'.
ELSEIF gv_score >= 60.
  WRITE: / 'D Grade'.
ELSE.
  WRITE: / 'F Grade'.
ENDIF.
```

점수 범위를 판단하는 로직은 `CASE`보다 `IF`가 자연스럽다.

## 11. WHEN OTHERS의 의미

`CASE`에서 `WHEN OTHERS`는 어느 `WHEN`에도 해당하지 않는 값을 처리한다.

```abap
CASE gv_status.
  WHEN 'A'.
    WRITE: / 'Active'.
  WHEN 'I'.
    WRITE: / 'Inactive'.
  WHEN OTHERS.
    WRITE: / 'Unknown status'.
ENDCASE.
```

### 11.1 왜 필요한가?

상태값이 항상 정상이라고 가정하면 문제가 생긴다.  
실무에서는 다음과 같은 값이 들어올 수 있다.

```text
공백
소문자
예상하지 못한 코드
Legacy 데이터
인터페이스 오류 데이터
테스트 데이터
```

`WHEN OTHERS`를 두면 예상하지 못한 값에 대한 안전 장치가 된다.

### 11.2 WHEN OTHERS에 아무 처리도 하지 않는 경우

다음 코드는 피하는 것이 좋다.

```abap
CASE gv_status.
  WHEN 'A'.
    WRITE: / 'Active'.
  WHEN 'I'.
    WRITE: / 'Inactive'.
  WHEN OTHERS.
ENDCASE.
```

예외 값을 조용히 무시하기 때문에 오류를 발견하기 어렵다.  
교육용 코드에서는 최소한 메시지를 출력하도록 작성한다.

```abap
WHEN OTHERS.
  WRITE: / 'Unknown status:', gv_status.
```

## 12. 중첩 IF

`IF` 안에 또 다른 `IF`를 작성할 수 있다.

```abap
IF gv_status = 'A'.
  IF gv_amount > 0.
    WRITE: / 'Active user with positive amount'.
  ENDIF.
ENDIF.
```

하지만 중첩이 깊어지면 코드가 읽기 어려워진다.

### 12.1 나쁜 예

```abap
IF gv_status = 'A'.
  IF gv_amount > 0.
    IF gv_approved = 'X'.
      WRITE: / 'Process allowed'.
    ENDIF.
  ENDIF.
ENDIF.
```

### 12.2 개선 예

```abap
IF gv_status = 'A'
   AND gv_amount > 0
   AND gv_approved = 'X'.
  WRITE: / 'Process allowed'.
ENDIF.
```

또는 예외를 먼저 처리하는 방식도 가능하다.

```abap
IF gv_status <> 'A'.
  WRITE: / 'Status is not active.'.
  RETURN.
ENDIF.

IF gv_amount <= 0.
  WRITE: / 'Amount is not positive.'.
  RETURN.
ENDIF.

IF gv_approved <> 'X'.
  WRITE: / 'Not approved.'.
  RETURN.
ENDIF.

WRITE: / 'Process allowed'.
```

단, `RETURN`은 Report 프로그램의 처리 흐름을 즉시 빠져나가는 의미를 가지므로 초급 단계에서는 사용 위치를 분명히 이해한 뒤 사용한다.

## 13. 조건문과 업무 코드값

실무 ABAP에서는 상태 코드, 문서 유형, 처리 구분 같은 코드값을 자주 판단한다.

나쁜 예:

```abap
IF gv_status = 'A'.
  WRITE: / 'Active'.
ENDIF.
```

이 자체가 잘못은 아니지만, 코드값이 여러 곳에서 반복되면 유지보수가 어려워진다.

더 좋은 예:

```abap
CONSTANTS gc_status_active TYPE c LENGTH 1 VALUE 'A'.

IF gv_status = gc_status_active.
  WRITE: / 'Active'.
ENDIF.
```

상수를 사용하면 값의 의미가 명확해진다.

더 확장된 예:

```abap
CONSTANTS:
  gc_status_active   TYPE c LENGTH 1 VALUE 'A',
  gc_status_inactive TYPE c LENGTH 1 VALUE 'I',
  gc_status_blocked  TYPE c LENGTH 1 VALUE 'B'.

CASE gv_status.
  WHEN gc_status_active.
    WRITE: / 'Active'.
  WHEN gc_status_inactive.
    WRITE: / 'Inactive'.
  WHEN gc_status_blocked.
    WRITE: / 'Blocked'.
  WHEN OTHERS.
    WRITE: / 'Unknown status:', gv_status.
ENDCASE.
```

이 방식은 다음 장점이 있다.

| 장점 | 설명 |
|---|---|
| 의미 명확 | `'A'`보다 `gc_status_active`가 읽기 쉽다. |
| 변경 용이 | 코드값 변경 시 상수 정의부를 중심으로 확인 가능하다. |
| 오타 감소 | 여러 곳에 Literal을 반복하지 않는다. |
| 실무 코드와 유사 | 상태값/구분값은 상수로 관리하는 경우가 많다. |

## 14. 전체 실습 예제

### 14.1 요구사항

다음 조건을 만족하는 Report 프로그램을 작성한다.

```text
1. 점수와 상태값을 변수로 선언한다.
2. 점수가 90 이상이면 A Grade, 80 이상이면 B Grade, 70 이상이면 C Grade, 60 이상이면 D Grade, 그 외는 F Grade를 출력한다.
3. 상태값이 A이면 Active, I이면 Inactive, B이면 Blocked, 그 외는 Unknown을 출력한다.
4. IF와 CASE를 모두 사용한다.
```

### 14.2 예제 코드

```abap
REPORT zgpt_cond_branch_01.

CONSTANTS:
  gc_status_active   TYPE c LENGTH 1 VALUE 'A',
  gc_status_inactive TYPE c LENGTH 1 VALUE 'I',
  gc_status_blocked  TYPE c LENGTH 1 VALUE 'B'.

DATA:
  gv_score  TYPE i VALUE 85,
  gv_status TYPE c LENGTH 1 VALUE 'A'.

WRITE: / '=== IF / CASE Condition Branch Demo ===',
       / 'Score :', gv_score,
       / 'Status:', gv_status,
       /.

IF gv_score >= 90.
  WRITE: / 'Grade : A'.
ELSEIF gv_score >= 80.
  WRITE: / 'Grade : B'.
ELSEIF gv_score >= 70.
  WRITE: / 'Grade : C'.
ELSEIF gv_score >= 60.
  WRITE: / 'Grade : D'.
ELSE.
  WRITE: / 'Grade : F'.
ENDIF.

CASE gv_status.
  WHEN gc_status_active.
    WRITE: / 'Status Text: Active'.
  WHEN gc_status_inactive.
    WRITE: / 'Status Text: Inactive'.
  WHEN gc_status_blocked.
    WRITE: / 'Status Text: Blocked'.
  WHEN OTHERS.
    WRITE: / 'Status Text: Unknown'.
ENDCASE.
```

### 14.3 예상 출력

```text
=== IF / CASE Condition Branch Demo ===
Score : 85
Status: A

Grade : B
Status Text: Active
```

### 16.1 확인할 항목

디버깅 시 다음을 확인한다.

| 항목 | 확인 내용 |
|---|---|
| 조건문 진입 여부 | `IF` 또는 `CASE` 라인에서 조건 평가 확인 |
| 변수 값 | `GV_SCORE`, `GV_STATUS` 값 확인 |
| 실행 블록 | 어떤 `ELSEIF` 또는 `WHEN`으로 들어가는지 확인 |
| 건너뛰는 블록 | 조건이 거짓일 때 어떤 라인이 실행되지 않는지 확인 |
| 최종 출력 | 조건 결과가 WRITE 출력과 일치하는지 확인 |

### 16.2 학습 포인트

디버깅하면서 다음을 관찰한다.

```text
IF 조건은 위에서 아래로 순차 평가된다.
참인 조건을 만나면 해당 블록을 실행하고 나머지 ELSEIF는 건너뛴다.
CASE는 기준 값과 일치하는 WHEN 블록 하나를 실행한다.
WHEN OTHERS는 어느 WHEN에도 해당하지 않을 때 실행된다.
```

## 17. 자주 발생하는 오류와 해결

### 17.1 ENDIF 누락

#### 현상

```text
Syntax error near end of program
ENDIF missing
```

#### 원인

`IF`를 시작했지만 `ENDIF.`로 닫지 않았다.

#### 해결

모든 `IF`에는 대응되는 `ENDIF.`가 있어야 한다.

```abap
IF gv_score >= 60.
  WRITE: / 'Pass'.
ENDIF.
```

### 17.2 ENDCASE 누락

#### 현상

`CASE` 블록 종료 관련 Syntax Error가 발생한다.

#### 원인

`CASE`를 시작했지만 `ENDCASE.`를 누락했다.

#### 해결

모든 `CASE`에는 대응되는 `ENDCASE.`가 있어야 한다.

```abap
CASE gv_status.
  WHEN 'A'.
    WRITE: / 'Active'.
ENDCASE.
```

### 17.3 조건 순서 오류

#### 현상

점수가 95인데도 A가 아니라 D가 출력된다.

#### 원인

범위 조건을 낮은 기준부터 작성했다.

#### 해결

높은 기준 또는 더 구체적인 조건부터 작성한다.

```abap
IF gv_score >= 90.
  WRITE: / 'A'.
ELSEIF gv_score >= 80.
  WRITE: / 'B'.
ENDIF.
```

### 17.4 Literal 오타

#### 현상

상태값 비교가 기대와 다르게 동작한다.

#### 원인

`'A'`, `'I'`, `'B'` 같은 Literal을 여러 곳에 직접 반복하면서 오타가 발생했다.

#### 해결

상수를 사용한다.

```abap
CONSTANTS gc_status_active TYPE c LENGTH 1 VALUE 'A'.
```

### 17.5 ELSE 남용

#### 현상

알 수 없는 값이 정상 값처럼 처리된다.

#### 원인

`ELSE`에서 모든 나머지를 특정 업무 상태로 처리했다.

#### 해결

알 수 없는 값은 별도로 출력하거나 오류 메시지를 남긴다.

## 18. 실무 적용 기준

### 18.1 IF가 좋은 경우

다음 상황에서는 `IF`가 적합하다.

```text
여러 변수를 함께 판단해야 한다.
범위 조건을 판단해야 한다.
초기값 여부를 검사해야 한다.
복잡한 업무 조건을 표현해야 한다.
예외 조건을 먼저 걸러야 한다.
```

예:

```abap
IF gv_status = gc_status_active
   AND gv_amount > 0
   AND gv_approved = 'X'.
  WRITE: / 'Process allowed'.
ENDIF.
```

### 18.2 CASE가 좋은 경우

다음 상황에서는 `CASE`가 적합하다.

```text
하나의 변수 값에 따라 처리 경로가 나뉜다.
상태 코드별 메시지를 출력한다.
문서 유형별 처리를 나눈다.
처리 구분값별 로직을 나눈다.
```

예:

```abap
CASE gv_doc_type.
  WHEN 'OR'.
    WRITE: / 'Sales Order'.
  WHEN 'RE'.
    WRITE: / 'Return Order'.
  WHEN OTHERS.
    WRITE: / 'Unknown document type'.
ENDCASE.
```

### 18.3 조건문을 작성할 때의 실무 습관

| 습관 | 이유 |
|---|---|
| Literal 대신 상수 사용 | 의미 명확화, 오타 방지 |
| 범위 조건은 순서 주의 | 먼저 참이 되는 조건만 실행됨 |
| 예외값 처리 | 예상하지 못한 데이터 발견 |
| 중첩 줄이기 | 가독성과 유지보수성 향상 |
| 조건문 주변에 간단한 주석 사용 | 업무 규칙 설명 |
| 너무 긴 조건은 분리 검토 | 읽기 어려운 조건 방지 |

## 19. Clean ABAP 관점의 기본 감각

초급 단계에서 Clean ABAP을 깊게 다루지는 않지만, 조건문 작성 시 다음 감각은 중요하다.

### 19.1 읽기 쉬운 조건을 작성한다

나쁜 예:

```abap
IF NOT gv_status <> 'A'.
  WRITE: / 'Active'.
ENDIF.
```

좋은 예:

```abap
IF gv_status = 'A'.
  WRITE: / 'Active'.
ENDIF.
```

### 19.2 의미 있는 이름을 사용한다

나쁜 예:

```abap
DATA gv_x TYPE c LENGTH 1 VALUE 'A'.
```

좋은 예:

```abap
DATA gv_status TYPE c LENGTH 1 VALUE 'A'.
```

### 19.3 매직 리터럴을 줄인다

나쁜 예:

```abap
IF gv_status = 'A'.
```

좋은 예:

```abap
IF gv_status = gc_status_active.
```

이런 습관은 이후 OO ABAP, RAP, Clean Core 학습에서도 계속 중요해진다.

## 20. 강사용 설명 포인트

강의 시 다음 순서로 설명하면 초급자가 이해하기 쉽다.

1. 프로그램은 기본적으로 위에서 아래로 실행된다고 설명한다.
2. 실제 업무에서는 항상 같은 처리를 하지 않으므로 조건 분기가 필요하다고 연결한다.
3. `IF`는 조건식 중심, `CASE`는 값 중심이라고 구분한다.
4. 점수 등급 예제는 `IF`, 상태 코드 예제는 `CASE`로 보여준다.
5. 조건 순서 오류를 일부러 보여주면 학습 효과가 크다.
6. `WHEN OTHERS` 또는 `ELSE`를 통해 예외값을 처리하는 습관을 강조한다.
7. Literal 대신 `CONSTANTS`를 쓰는 이유를 함께 설명한다.

## 21. 평가 문제

### 21.1 객관식

#### Q1. ABAP에서 기본 조건문을 닫는 키워드는 무엇인가?

A. `ENDLOOP.`  
B. `ENDIF.`  
C. `ENDSELECT.`  
D. `ENDCASE.`

정답: B

#### Q2. `CASE` 문에서 예상하지 못한 나머지 값을 처리하는 구문은 무엇인가?

A. `WHEN DEFAULT.`  
B. `WHEN ANY.`  
C. `WHEN OTHERS.`  
D. `ELSEIF.`

정답: C

#### Q3. 점수 구간처럼 범위 조건을 판단할 때 일반적으로 더 적합한 문법은 무엇인가?

A. `IF`  
B. `CASE`  
C. `WRITE`  
D. `REPORT`

정답: A

### 21.2 서술형

#### Q1. `ELSEIF`와 `ELSE`의 차이를 설명하시오.

모범 답안:  
`ELSEIF`는 앞 조건이 거짓일 때 추가 조건을 다시 평가하는 구문이다. 반면 `ELSE`는 앞의 모든 조건이 거짓일 때 실행되는 나머지 처리 블록이며 별도의 조건식을 가지지 않는다.

#### Q2. 상태 코드 판단에서 `CASE`가 적합한 이유를 설명하시오.

모범 답안:  
상태 코드 판단은 하나의 변수 값이 여러 고정 값 중 어느 것인지 확인하는 구조이므로 `CASE`를 사용하면 각 값별 처리 흐름을 읽기 쉽게 표현할 수 있다.

#### Q3. 조건 순서가 중요한 이유를 설명하시오.

모범 답안:  
`IF ... ELSEIF` 구조는 위에서 아래로 조건을 평가하며, 참인 조건을 만나면 해당 블록을 실행하고 나머지 조건은 검사하지 않는다. 따라서 범위 조건을 잘못된 순서로 작성하면 더 구체적인 조건이 실행되지 않을 수 있다.

## 23. 핵심 요약

이번 모듈의 핵심은 다음이다.

```text
IF는 조건식이 참인지 판단하여 실행 흐름을 나눈다.
ELSEIF는 추가 조건을 순차적으로 평가한다.
ELSE는 앞 조건에 해당하지 않는 모든 나머지 경우를 처리한다.
CASE는 하나의 기준 값에 대해 여러 WHEN 분기를 구성한다.
범위 조건은 IF가 적합하고, 상태값 분기는 CASE가 적합한 경우가 많다.
조건 순서는 결과에 직접 영향을 준다.
Literal 반복보다 CONSTANTS 사용이 유지보수에 유리하다.
예상하지 못한 값은 ELSE 또는 WHEN OTHERS에서 명시적으로 처리하는 습관이 필요하다.
```

조건 분기는 “어떤 경로를 선택할 것인가”를 다루고, 반복 처리는 “같은 처리를 몇 번 또는 언제까지 반복할 것인가”를 다룬다.

연결 관계는 다음과 같다.

```text
THEORY-02-M04 IF / CASE 조건 분기
  → 조건에 따라 처리 경로 선택

THEORY-02-M05 DO / WHILE 반복 처리
  → 조건 또는 횟수에 따라 처리 반복
```

다음 모듈에서는 `DO`, `WHILE`, `EXIT`, `CONTINUE`를 통해 반복 제어의 기본 구조를 학습한다.
