```text
  → Screen Number와 PBO/PAI 중심
  → Transaction Code로 화면을 호출
  → 사용자의 화면 입력과 버튼 이벤트를 처리
```

## 3. Module Pool 프로그램이란?

### 3.1 쉬운 정의

Module Pool 프로그램은 SAP GUI 화면, 즉 Dynpro Screen을 구동하기 위한 ABAP 프로그램이다.

Report 프로그램이 주로 “데이터를 조회하고 리스트를 출력하는 실행 단위”라면, Module Pool 프로그램은 “화면을 만들고, 화면 입력과 버튼 이벤트를 처리하는 실행 단위”에 가깝다.

초급자는 다음처럼 이해하면 된다.

```text
Report = 실행하면 결과 리스트를 보여주는 프로그램
Module Pool = 사용자가 조작할 화면을 제공하는 프로그램
```

### 3.2 왜 Module Pool이 필요한가?

Selection Screen은 간단한 입력 조건을 받기에 좋다.  
하지만 다음과 같은 복잡한 화면을 만들기에는 한계가 있다.

| 요구사항 | Selection Screen | Module Pool |
|---|---|---|
| 여러 입력 필드 배치 | 가능하지만 제한적 | 가능 |
| Push Button 배치 | 제한적 | 가능 |
| 화면 전환 | 제한적 | 가능 |
| Tabstrip / Subscreen | 제한적 | 가능 |
| Custom Control / ALV Container | 부적합 | 가능 |
| PBO/PAI 기반 화면 제어 | 제한적 | 핵심 구조 |
| 사용자 이벤트 세밀 제어 | 제한적 | 가능 |

Module Pool은 SAP GUI 기반 업무 화면을 직접 구성할 때 사용된다.  
특히 Classic SAP GUI 개발에서는 여전히 중요한 기초 지식이다.

## 4. Program Type M

### 4.1 Program Type의 의미

ABAP 프로그램은 생성 목적에 따라 여러 유형을 가진다.  
Module Pool 프로그램은 일반적으로 **Program Type M**으로 생성된다.

| Program Type | 의미 | 대표 사용 |
|---|---|---|
| 1 | Executable Program | Report Program |
| M | Module Pool | Dynpro / Screen Programming |
| F | Function Group | Function Module |
| K | Class Pool | Global Class |
| I | Include Program | Include Source |

이번 모듈의 대상은 `M`, 즉 Module Pool이다.

### 4.2 Program Type M의 특징

Program Type M은 다음 특징을 가진다.

| 특징 | 설명 |
|---|---|
| 직접 실행 목적이 아님 | 일반 Report처럼 F8로 바로 비즈니스 처리가 시작되는 구조가 아니다. |
| Screen과 연결됨 | Dynpro Screen과 Flow Logic을 통해 화면 처리 흐름이 시작된다. |
| Transaction Code 필요 | 일반적으로 T-Code를 만들어 특정 Screen을 호출한다. |
| PBO/PAI MODULE 사용 | 화면 출력 전후 처리를 MODULE 단위로 구현한다. |
| Include 구조 활용 | TOP, PBO, PAI, FORM 등을 Include로 분리한다. |

초급자가 가장 많이 혼동하는 지점은 다음이다.

```text
Module Pool 프로그램을 만들었다고 해서 곧바로 실행 화면이 나오는 것은 아니다.
Screen과 Transaction Code가 연결되어야 사용자가 실행할 수 있다.
```

## 5. Module Pool과 Report의 차이

### 5.1 실행 방식 비교

| 구분 | Report Program | Module Pool Program |
|---|---|---|
| 대표 생성 트랜잭션 | SE38, SE80, ADT | SE80 중심, SE38에서도 Program 생성 가능 |
| Program Type | Executable Program | Module Pool |
| 실행 방식 | 직접 실행 가능 | 보통 T-Code로 Screen 호출 |
| 주요 이벤트 | START-OF-SELECTION 등 | PBO / PAI |
| 화면 구성 | Selection Screen 중심 | Screen Painter / Dynpro 중심 |
| 출력 방식 | WRITE List, ALV 등 | 화면 필드, 버튼, Custom Control 등 |
| 용도 | 조회, 배치성 처리, 리스트 출력 | 대화형 업무 화면 |

### 5.2 코드 구조 비교

Report는 보통 다음처럼 시작한다.

```abap
REPORT zrep_sample.

START-OF-SELECTION.
  WRITE: / 'Hello Report'.
```

Module Pool은 일반적으로 다음처럼 시작한다.

```abap
PROGRAM zmp_sample.

INCLUDE zmp_sample_top.
INCLUDE zmp_sample_o01.
INCLUDE zmp_sample_i01.
INCLUDE zmp_sample_f01.
```

여기서 핵심은 `REPORT`가 아니라 `PROGRAM`을 사용한다는 점이다.

## 6. Module Pool의 기본 구성

초급 Module Pool은 보통 다음 구성으로 이해한다.

```text
Module Pool Program
 ├─ Main Program
 ├─ TOP Include
 ├─ PBO Include
 ├─ PAI Include
 ├─ FORM Include
 ├─ Screen
 └─ Transaction Code
```

각 구성요소의 역할은 다음과 같다.

| 구성요소 | 예시 | 역할 |
|---|---|---|
| Main Program | `SAPMZMP_USER` 또는 `ZMP_USER` | 전체 Module Pool의 메인 프로그램 |
| TOP Include | `ZMP_USER_TOP` | 전역 DATA, TYPES, TABLES 선언 |
| PBO Include | `ZMP_USER_O01` | 화면 출력 전 처리 MODULE 구현 |
| PAI Include | `ZMP_USER_I01` | 사용자 입력 후 처리 MODULE 구현 |
| FORM Include | `ZMP_USER_F01` | 보조 FORM 루틴 구현 |
| Screen | `0100` | 실제 Dynpro 화면 |
| Transaction Code | `ZMP_USER` | 사용자가 실행하는 진입점 |

> 네이밍은 프로젝트와 회사 규칙에 따라 달라질 수 있다.  
> 이 문서의 예시는 교육용이며, 실무에서는 고객사 Naming Rule을 우선한다.

## 7. Main Program

### 7.1 Main Program의 역할

Main Program은 Module Pool의 최상위 소스이다.  
직접 많은 로직을 작성하기보다는 Include를 모으는 역할을 한다.

교육용 예시:

```abap
PROGRAM zmp_jhy_user.

INCLUDE zmp_jhy_user_top.  " Global Data
INCLUDE zmp_jhy_user_o01.  " PBO Modules
INCLUDE zmp_jhy_user_i01.  " PAI Modules
INCLUDE zmp_jhy_user_f01.  " FORM Routines
```

### 7.2 왜 Include로 나누는가?

Module Pool은 화면 이벤트가 많아질수록 소스가 길어진다.  
모든 로직을 Main Program에 몰아넣으면 유지보수가 어려워진다.

Include 분리는 다음 장점이 있다.

| 장점 | 설명 |
|---|---|
| 역할 분리 | 전역 선언, PBO, PAI, 보조 로직을 구분한다. |
| 가독성 향상 | 화면 출력 로직과 입력 처리 로직을 분리한다. |
| 유지보수성 | 오류 발생 위치를 빠르게 찾을 수 있다. |
| 교육 효과 | Dynpro 처리 흐름을 구조적으로 이해하기 쉽다. |

## 8. TOP Include

### 8.1 TOP Include의 목적

TOP Include는 Module Pool 전체에서 사용하는 전역 선언을 모아두는 Include이다.

일반적으로 다음 내용을 둔다.

| 선언 | 예시 |
|---|---|
| TABLES 선언 | `TABLES: zt_jhy_user.` |
| DATA 선언 | `DATA gv_ok_code TYPE sy-ucomm.` |
| TYPES 선언 | 화면/내부 처리용 타입 |
| CONSTANTS 선언 | Function Code 상수 |
| Internal Table 선언 | 조회 결과 저장용 테이블 |
| Work Area 선언 | 화면 또는 처리용 구조 |

### 8.2 OK Code 변수

Dynpro에서 버튼이나 메뉴를 누르면 Function Code가 발생한다.  
이 값을 받기 위해 일반적으로 OK Code 변수를 둔다.

```abap
DATA: gv_ok_code TYPE sy-ucomm,
      gv_save_ok TYPE sy-ucomm.
```

`GV_OK_CODE`는 화면의 OK Code 필드와 연결된다.  
`GV_SAVE_OK`는 PAI 처리 중 OK Code 값을 보존하고 초기화하기 위해 사용되는 경우가 많다.

자세한 Function Code와 PF-STATUS는 `THEORY-14-M06`에서 다룬다.  
이번 모듈에서는 “Module Pool에는 사용자 이벤트 코드를 받을 전역 변수가 필요하다” 정도를 이해하면 된다.

### 8.3 TOP Include 예시

```abap
*&---------------------------------------------------------------------*
*& Include          ZMP_JHY_USER_TOP
*&---------------------------------------------------------------------*

TABLES: zt_jhy_user.

DATA: gv_ok_code TYPE sy-ucomm,
      gv_save_ok TYPE sy-ucomm.

DATA: gs_user TYPE zt_jhy_user,
      gt_user TYPE STANDARD TABLE OF zt_jhy_user.
```

초급자는 `TABLES` 구문을 볼 때 주의해야 한다.  
현대 ABAP에서는 무분별한 `TABLES` 사용을 줄이는 방향이지만, Dynpro 화면 필드와 DDIC 테이블/구조를 연결하는 전통적인 Screen Programming에서는 여전히 학습할 가치가 있다.

> [추정] 교육 시스템이나 코딩 규칙에 따라 `TABLES` 사용을 제한하고 별도 Work Area를 선호할 수 있다. 이 문서는 SAP GUI 기반 Classic Dynpro 기초를 설명하기 위해 전통적인 예시를 함께 제시한다.

## 9. PBO Include

### 9.1 PBO의 의미

PBO는 `Process Before Output`의 약자이다.  
화면이 사용자에게 표시되기 전에 실행되는 처리 흐름이다.

PBO Include에는 일반적으로 다음 MODULE을 둔다.

```abap
MODULE status_0100 OUTPUT.
  SET PF-STATUS 'STATUS_0100'.
  SET TITLEBAR 'TITLE_0100'.
ENDMODULE.
```

이번 M01에서는 PBO의 구조적 위치만 이해한다.  
상세한 PBO 처리 흐름은 `THEORY-14-M04`에서 다룬다.

### 9.2 PBO Include 예시

```abap
*&---------------------------------------------------------------------*
*& Include          ZMP_JHY_USER_O01
*&---------------------------------------------------------------------*

MODULE status_0100 OUTPUT.
  " 화면 표시 전 상태 설정
ENDMODULE.
```

Include 이름에 `_O01`을 붙이는 관행은 `OUTPUT` 처리 모듈을 담는다는 의미로 사용되는 경우가 많다.

## 10. PAI Include

### 10.1 PAI의 의미

PAI는 `Process After Input`의 약자이다.  
사용자가 화면에서 값을 입력하거나 버튼을 누른 뒤 서버로 제어가 넘어왔을 때 실행되는 처리 흐름이다.

PAI Include에는 일반적으로 다음 MODULE을 둔다.

```abap
MODULE user_command_0100 INPUT.
  gv_save_ok = gv_ok_code.
  CLEAR gv_ok_code.

  CASE gv_save_ok.
    WHEN 'BACK' OR 'EXIT' OR 'CANC'.
      LEAVE PROGRAM.
    WHEN 'SAVE'.
      " 저장 처리
  ENDCASE.
ENDMODULE.
```

이번 M01에서는 PAI의 구조적 위치만 이해한다.  
상세한 PAI 처리 흐름과 Function Code 처리는 `THEORY-14-M05`, `THEORY-14-M06`에서 다룬다.

### 10.2 PAI Include 예시

```abap
*&---------------------------------------------------------------------*
*& Include          ZMP_JHY_USER_I01
*&---------------------------------------------------------------------*

MODULE user_command_0100 INPUT.
  " 사용자 명령 처리
ENDMODULE.
```

Include 이름에 `_I01`을 붙이는 관행은 `INPUT` 처리 모듈을 담는다는 의미로 사용되는 경우가 많다.

## 11. FORM Include

### 11.1 FORM Include의 목적

FORM Include는 보조 로직을 분리하기 위한 Include이다.

예를 들어 다음과 같은 처리를 분리할 수 있다.

| 처리 | 예시 |
|---|---|
| 데이터 조회 | `FORM select_user.` |
| 입력값 검증 | `FORM validate_input.` |
| 데이터 저장 | `FORM save_user.` |
| 메시지 처리 | `FORM show_message.` |
| 공통 초기화 | `FORM initialize.` |

초급 Module Pool에서는 처음부터 복잡한 FORM을 많이 만들 필요는 없다.  
다만 화면 이벤트 MODULE 안에 모든 코드를 몰아넣지 않기 위해 FORM Include 구조를 이해해두는 것이 좋다.

### 11.2 FORM Include 예시

```abap
*&---------------------------------------------------------------------*
*& Include          ZMP_JHY_USER_F01
*&---------------------------------------------------------------------*

FORM select_user.
  SELECT *
    FROM zt_jhy_user
    INTO TABLE gt_user
    UP TO 100 ROWS.
ENDFORM.
```

Open SQL의 상세 성능과 문법은 후속 Section에서 이미 다뤘거나 별도 심화에서 다룰 수 있다.  
이번 모듈에서는 “보조 로직은 FORM Include로 분리할 수 있다”는 구조만 이해한다.

## 12. Screen Flow Logic과 ABAP MODULE의 연결

Module Pool을 이해하려면 Screen Flow Logic과 ABAP Include의 연결을 알아야 한다.

Screen Flow Logic에는 다음과 같은 구조가 있다.

```abap
PROCESS BEFORE OUTPUT.
  MODULE status_0100.

PROCESS AFTER INPUT.
  MODULE user_command_0100.
```

이 Flow Logic에서 호출한 `MODULE status_0100`은 PBO Include에 구현되어야 한다.

```abap
MODULE status_0100 OUTPUT.
  " PBO 처리
ENDMODULE.
```

그리고 `MODULE user_command_0100`은 PAI Include에 구현되어야 한다.

```abap
MODULE user_command_0100 INPUT.
  " PAI 처리
ENDMODULE.
```

여기서 주의할 점은 `OUTPUT`과 `INPUT`이다.

| Flow Logic 위치 | ABAP MODULE 구현 |
|---|---|
| PROCESS BEFORE OUTPUT | `MODULE ... OUTPUT.` |
| PROCESS AFTER INPUT | `MODULE ... INPUT.` |

초급자 오류 중 하나는 Flow Logic에는 MODULE을 적었는데 ABAP 소스에 해당 MODULE을 구현하지 않는 것이다.  
반대로 ABAP 소스에 MODULE을 구현했지만 Flow Logic에서 호출하지 않으면 해당 MODULE은 화면 처리 흐름에서 실행되지 않는다.

## 13. Transaction Code와 Module Pool

### 13.1 왜 T-Code가 필요한가?

Report 프로그램은 SE38에서 직접 실행하거나 T-Code로 연결할 수 있다.  
Module Pool은 보통 T-Code를 통해 특정 Program과 Screen Number를 연결해 실행한다.

예를 들어 다음과 같이 연결한다.

| 항목 | 예시 |
|---|---|
| Transaction Code | `ZJHY_USER` |
| Program | `ZMP_JHY_USER` |
| Screen Number | `0100` |

사용자가 `ZJHY_USER`를 실행하면 SAP는 `ZMP_JHY_USER` 프로그램의 `0100` 화면을 호출한다.

### 13.2 생성 도구

T-Code는 일반적으로 `SE93`에서 생성한다.

```text
SE93
→ Transaction Code 입력
→ Create
→ Program and Screen 선택
→ Program: ZMP_JHY_USER
→ Screen: 0100
→ Save
```

이번 M01에서는 T-Code 연결의 필요성만 이해한다.  
Screen Number와 Screen Painter는 `THEORY-14-M02`에서 다룬다.

## 14. 최소 Module Pool 골격 예시

아래는 교육용으로 가장 단순화한 Module Pool 골격이다.

### 14.1 Main Program

```abap
PROGRAM zmp_jhy_user.

INCLUDE zmp_jhy_user_top.
INCLUDE zmp_jhy_user_o01.
INCLUDE zmp_jhy_user_i01.
INCLUDE zmp_jhy_user_f01.
```

### 14.2 TOP Include

```abap
DATA: gv_ok_code TYPE sy-ucomm,
      gv_save_ok TYPE sy-ucomm.
```

### 14.3 PBO Include

```abap
MODULE status_0100 OUTPUT.
  " PF-STATUS와 TITLEBAR는 후속 모듈에서 상세 학습
ENDMODULE.
```

### 14.4 PAI Include

```abap
MODULE user_command_0100 INPUT.
  gv_save_ok = gv_ok_code.
  CLEAR gv_ok_code.

  CASE gv_save_ok.
    WHEN 'BACK' OR 'EXIT' OR 'CANC'.
      LEAVE PROGRAM.
  ENDCASE.
ENDMODULE.
```

### 14.5 Screen Flow Logic

```abap
PROCESS BEFORE OUTPUT.
  MODULE status_0100.

PROCESS AFTER INPUT.
  MODULE user_command_0100.
```

이 예시는 완전한 실무 화면은 아니지만, Module Pool의 핵심 골격을 이해하는 데 충분하다.

## 15. 생성 절차 개요

SAP GUI 800 기준으로 초급자가 이해해야 할 생성 흐름은 다음과 같다.

```text
1. SE80 또는 SE38에서 Module Pool Program 생성
2. Program Type을 Module Pool로 지정
3. Main Program에 Include 선언
4. TOP Include 생성
5. PBO Include 생성
6. PAI Include 생성
7. FORM Include 생성
8. Screen 0100 생성
9. Screen Flow Logic에 PBO/PAI MODULE 연결
10. SE93에서 Transaction Code 생성
11. Program + Screen Number 연결
12. Activate
13. Transaction Code 실행
```

이번 M01의 핵심은 1~7번의 프로그램 구조이다.  
8번 이후는 후속 모듈에서 단계적으로 구체화한다.

## 16. 정상 흐름과 오류 흐름

### 16.1 정상 흐름

정상적인 구조는 다음과 같다.

```text
Main Program 생성
→ Include 구조 생성
→ TOP/PBO/PAI/FORM 역할 분리
→ Screen Flow Logic에서 MODULE 호출
→ ABAP 소스에 MODULE 구현
→ T-Code가 Program + Screen을 호출
```

### 16.2 오류 흐름 1: Program Type을 잘못 선택

#### 상황

Module Pool을 만들어야 하는데 Executable Program으로 생성했다.

#### 결과

Screen Programming 구조와 맞지 않거나, T-Code 연결 및 Dynpro 개발 흐름에서 혼란이 생긴다.

#### 해결

교육용 Module Pool은 Program Type M으로 생성한다.  
이미 잘못 만들었다면 새 Module Pool 프로그램을 올바른 타입으로 생성하는 것이 안전하다.

### 16.3 오류 흐름 2: Include를 만들지 않고 Main Program에 모든 코드 작성

#### 상황

PBO, PAI, 전역 선언, 보조 로직을 모두 Main Program에 작성한다.

#### 문제

초기에는 실행될 수 있지만 화면이 늘어나면 유지보수가 급격히 어려워진다.

#### 해결

다음처럼 역할별 Include를 분리한다.

```text
_TOP  전역 선언
_O01  PBO OUTPUT Module
_I01  PAI INPUT Module
_F01  FORM Routine
```

### 16.4 오류 흐름 3: Flow Logic의 MODULE과 ABAP MODULE 이름 불일치

#### 상황

Screen Flow Logic에는 다음처럼 작성했다.

```abap
MODULE status_0100.
```

하지만 ABAP에는 다음처럼 구현했다.

```abap
MODULE set_status_0100 OUTPUT.
ENDMODULE.
```

#### 문제

Flow Logic에서 호출하는 이름과 ABAP MODULE 이름이 달라 활성화 오류가 발생하거나 화면 흐름이 연결되지 않는다.

#### 해결

이름을 정확히 맞춘다.

```abap
PROCESS BEFORE OUTPUT.
  MODULE status_0100.
```

```abap
MODULE status_0100 OUTPUT.
ENDMODULE.
```

### 16.5 오류 흐름 4: OUTPUT / INPUT 방향 불일치

#### 상황

PBO에서 호출하는 MODULE을 ABAP에서 `INPUT`으로 구현했다.

#### 문제

PBO/PAI 처리 방향이 맞지 않는다.

#### 해결

| Flow Logic | ABAP MODULE |
|---|---|
| PROCESS BEFORE OUTPUT | `MODULE ... OUTPUT.` |
| PROCESS AFTER INPUT | `MODULE ... INPUT.` |

### 16.6 오류 흐름 5: T-Code에 Screen Number를 연결하지 않음

#### 상황

Module Pool 프로그램과 Screen을 만들었지만 T-Code를 만들지 않았거나, T-Code에 Screen Number를 잘못 지정했다.

#### 결과

사용자가 업무 화면으로 진입할 수 없다.

#### 해결

SE93에서 Transaction Code를 생성하고 Program + Screen Number를 정확히 연결한다.

## 17. 실무 설계 기준

### 17.1 Module Pool을 사용할지 먼저 판단한다

현대 SAP 개발에서는 SAP GUI Dynpro 화면만이 유일한 UI 선택지가 아니다.  
Fiori, RAP, UI5, Web Dynpro, ALV Report 등 여러 선택지가 있다.

Module Pool이 적합한 경우는 다음과 같다.

| 상황 | 판단 |
|---|---|
| 기존 SAP GUI 업무 화면 유지보수 | 적합 |
| Classic Dynpro 기반 고객 화면 추가 | 가능 |
| 간단한 조회 리스트 | Report/ALV가 더 적합할 수 있음 |
| 신규 S/4HANA 확장 UI | Fiori/RAP 검토 필요 |
| 복잡한 화면 제어와 Custom Control 필요 | Module Pool 또는 Control Framework 검토 |

> [추정] 신규 프로젝트에서는 Clean Core와 Fiori 우선 전략을 고려하는 경우가 많지만, 기존 SAP GUI 기반 운영 환경에서는 Module Pool 유지보수 역량이 여전히 필요하다.

### 17.2 Include 구조를 일관되게 유지한다

프로젝트마다 Naming Rule이 다를 수 있지만, 중요한 것은 일관성이다.

교육용 권장 구조:

```text
ZMP_JHY_USER
ZMP_JHY_USER_TOP
ZMP_JHY_USER_O01
ZMP_JHY_USER_I01
ZMP_JHY_USER_F01
```

실무에서는 팀 규칙에 따라 다음처럼 다를 수 있다.

```text
LZFGROUPTOP
LZFGROUPO01
LZFGROUPI01
LZFGROUPF01
```

중요한 것은 이름 자체보다 역할이 명확해야 한다는 점이다.

### 17.3 전역 변수 남발을 피한다

Module Pool은 화면과 전역 데이터가 밀접하게 연결되므로 전역 변수가 늘어나기 쉽다.  
하지만 무분별한 전역 변수는 유지보수를 어렵게 한다.

권장 기준:

| 기준 | 설명 |
|---|---|
| 화면 필드와 직접 연결되는 값 | 전역 선언 가능 |
| 여러 MODULE에서 공유하는 상태 | 전역 선언 가능 |
| 특정 처리 안에서만 쓰는 임시 값 | 로컬 변수 권장 |
| 복잡한 비즈니스 로직 | FORM, 메서드, 별도 클래스 분리 검토 |

### 17.4 화면 로직과 비즈니스 로직을 분리한다

PBO/PAI MODULE 안에 모든 업무 로직을 몰아넣으면 유지보수가 어렵다.

좋은 구조는 다음이다.

```text
PAI MODULE
  → Function Code 판단
  → 필요한 FORM 또는 Method 호출
  → 메시지 처리
```

나쁜 구조는 다음이다.

```text
PAI MODULE 안에 SELECT, UPDATE, 검증, 메시지, 화면 제어를 모두 직접 작성
```

초급 단계에서는 FORM Include로 분리하는 연습을 하고, 후속 OO ABAP 학습 후에는 클래스로 분리하는 구조까지 확장할 수 있다.

## 19. 자가 점검 문제

### Q1. Module Pool 프로그램의 Program Type은 무엇인가?

정답: `M`

### Q2. Module Pool은 Report처럼 직접 실행하는 것이 일반적인가?

모범 답안:  
아니다. Module Pool은 일반적으로 Transaction Code가 Program과 Screen Number를 호출하는 방식으로 실행된다.

### Q3. TOP Include에는 주로 무엇을 작성하는가?

모범 답안:  
전역 DATA, TYPES, CONSTANTS, TABLES 선언 및 화면 처리에 필요한 공통 변수를 작성한다.

### Q4. PBO Include와 PAI Include의 차이는 무엇인가?

모범 답안:  
PBO Include에는 화면 출력 전 처리인 `MODULE ... OUTPUT`을 구현하고, PAI Include에는 사용자 입력 후 처리인 `MODULE ... INPUT`을 구현한다.

### Q5. Screen Flow Logic의 `MODULE status_0100.`과 ABAP 소스의 `MODULE status_0100 OUTPUT.`은 어떤 관계인가?

모범 답안:  
Screen Flow Logic은 화면 처리 시 호출할 MODULE 이름을 선언하고, ABAP 소스의 MODULE 구현은 실제 실행될 로직을 제공한다. PBO에서 호출하면 ABAP MODULE은 `OUTPUT`으로 구현해야 한다.

## 20. 강사용 설명 포인트

강의 시에는 다음 순서로 설명하는 것이 효과적이다.

1. Report와 Module Pool을 비교한다.
2. Module Pool이 화면 중심 프로그램임을 설명한다.
3. Program Type M을 강조한다.
4. Main Program은 Include를 모으는 구조임을 보여준다.
5. TOP/O01/I01/F01의 역할을 그림으로 설명한다.
6. Screen Flow Logic의 MODULE 호출과 ABAP MODULE 구현을 연결한다.
7. T-Code가 Program + Screen을 호출한다는 실행 구조를 보여준다.
8. PBO/PAI 상세는 후속 모듈에서 다룬다고 범위를 제한한다.

초급자가 가장 빨리 이해하는 비유는 다음이다.

```text
Main Program = 폴더의 목차
TOP Include = 공통 준비물
PBO Include = 화면 보여주기 전 준비
PAI Include = 사용자가 누른 뒤 처리
FORM Include = 반복되는 보조 작업
Screen = 실제 화면
T-Code = 사용자가 들어오는 입구
```
