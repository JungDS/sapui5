## 3. Dynpro 화면 요소의 기본 구조

Dynpro 화면은 일반적으로 다음 세 영역이 함께 동작한다.

```text
ABAP Program
  ↕
Screen Field
  ↕
사용자가 보는 GUI 화면
```

예를 들어 화면에 `GV_CARRID`라는 Input Field를 배치했다고 하자.  
이 필드가 프로그램의 전역 변수 `GV_CARRID`와 이름이 맞으면, 화면과 프로그램 사이에서 값이 전달될 수 있다.

```abap
DATA gv_carrid TYPE scarr-carrid.
```

화면 Layout에는 다음과 같은 필드가 있을 수 있다.

```text
Field Name: GV_CARRID
```

이때 초급자가 이해해야 할 핵심은 다음이다.

```text
화면에 보이는 Input Field 이름과 ABAP 프로그램의 필드 이름은 연결 기준이 된다.
```

물론 실제 값 전달 시점은 PBO와 PAI의 흐름에 의해 결정된다.  
이 모듈에서는 연결 개념만 잡고, 값이 언제 이동하는지는 후속 모듈에서 다룬다.

## 4. Text Field

### 4.1 Text Field란 무엇인가?

Text Field는 화면에 고정 텍스트를 표시하는 요소이다.  
사용자가 입력하는 필드가 아니라, 화면을 이해하기 쉽게 만드는 라벨이나 설명이다.

예시:

```text
Carrier ID
Carrier Name
조회 조건
사용자 정보
```

화면에서 Text Field는 보통 Input Field의 왼쪽에 배치되어 “이 입력칸에 무엇을 입력해야 하는가”를 안내한다.

### 4.2 Text Field의 주요 속성

| 속성 | 의미 |
|---|---|
| Text | 화면에 표시될 문구 |
| Position | 화면상의 행/열 위치 |
| Length | 표시 길이 |
| Visible | 표시 여부 |
| Output Only 성격 | 사용자가 직접 값을 입력하지 않음 |

초급 실습에서는 Text Field의 기술 속성을 모두 외우기보다, 다음 원칙을 지키는 것이 중요하다.

```text
입력 필드만 던져두지 말고, 사용자가 이해할 수 있는 Text Field를 함께 배치한다.
```

### 4.3 좋은 Text Field 설계

나쁜 예:

```text
ID
Name
Code
```

조금 더 좋은 예:

```text
Airline Code
Airline Name
조회할 항공사
```

실무에서는 화면 라벨이 지나치게 짧으면 사용자 혼란이 생긴다.  
반대로 너무 길면 화면이 복잡해진다.  
따라서 업무 용어와 화면 공간을 균형 있게 고려해야 한다.

### 4.4 Text Field와 Data Element Label의 관계

ABAP Dictionary의 Data Element에는 Field Label이 존재한다.  
하지만 Dynpro 화면에서 항상 자동으로 적절한 라벨이 배치되는 것은 아니다.  
화면 설계자는 화면 문맥에 맞는 텍스트를 고려해야 한다.

예를 들어 같은 `CARRID`라도 화면에 따라 라벨은 달라질 수 있다.

| 화면 문맥 | 적절한 라벨 |
|---|---|
| 단순 조회 조건 | Airline Code |
| 상세 화면 | Carrier |
| 교육용 화면 | 항공사 코드 |

즉, Text Field는 단순 장식이 아니라 사용자와 프로그램 사이의 의미 전달 장치이다.

## 5. Input Field

### 5.1 Input Field란 무엇인가?

Input Field는 사용자가 값을 입력하거나 프로그램이 값을 표시하는 화면 필드이다.

예시:

```text
항공사 코드 입력칸
사용자 ID 입력칸
금액 입력칸
날짜 입력칸
```

Dynpro에서 Input Field는 가장 중요한 화면 요소 중 하나이다.  
입력값은 후속 PAI 처리에서 프로그램으로 전달되고, 프로그램에서 처리된 값은 PBO 처리에서 화면에 다시 표시될 수 있다.

### 5.2 Input Field의 주요 속성

| 속성 | 의미 |
|---|---|
| Name | 화면 필드명. ABAP 필드명 또는 DDIC 필드명과 연결될 수 있다. |
| Text / Label | 직접 라벨이 아니라 Text Field와 함께 구성하는 경우가 많다. |
| Length | 입력/표시 길이 |
| Input | 사용자가 입력 가능한지 여부 |
| Output | 화면 출력 필드로 사용할지 여부 |
| Required | 필수 입력 성격을 가질 수 있음 |
| Dictionary Reference | DDIC 필드를 참조하여 타입과 속성을 가져올 수 있음 |

초급자는 특히 `Name`을 중요하게 봐야 한다.  
화면 필드 이름이 ABAP 프로그램의 전역 변수와 맞지 않으면 값 전달이 기대대로 되지 않을 수 있다.

### 5.3 프로그램 필드와 화면 필드 연결

예를 들어 Module Pool 프로그램에 다음 전역 변수를 선언했다고 하자.

```abap
DATA gv_carrid TYPE scarr-carrid.
DATA gv_carrname TYPE scarr-carrname.
```

Screen Painter에서 Input Field를 다음 이름으로 만든다.

| 화면 필드명 | ABAP 변수 |
|---|---|
| GV_CARRID | `gv_carrid` |
| GV_CARRNAME | `gv_carrname` |

ABAP은 대소문자 구분보다 이름 자체의 일치가 중요하므로, 실무에서는 대문자 기준으로 화면 필드명을 맞추는 것이 일반적이다.

### 5.4 Dictionary Field를 이용한 Input Field

Input Field는 DDIC 필드 참조를 통해 만들 수도 있다.  
예를 들어 `SCARR-CARRID`를 참조하면 필드 길이와 기술 속성을 Dictionary에서 가져올 수 있다.

교육용으로는 다음 두 방식을 모두 이해하는 것이 좋다.

| 방식 | 설명 | 장점 |
|---|---|---|
| Program Field 방식 | `GV_CARRID` 같은 프로그램 전역 변수와 연결 | Module Pool 데이터 흐름 이해에 좋음 |
| Dictionary Field 방식 | `SCARR-CARRID` 같은 DDIC 필드 참조 | 표준 필드 속성 재사용 가능 |

초급 실습에서는 먼저 Program Field 방식을 권장한다.  
이 방식이 화면 필드와 ABAP 변수의 연결을 가장 직관적으로 보여주기 때문이다.

## 6. Push Button

### 6.1 Push Button이란 무엇인가?

Push Button은 사용자가 클릭할 수 있는 버튼이다.  
버튼을 누르면 Function Code가 발생하고, 이후 PAI 흐름에서 이 Function Code를 기준으로 처리를 분기할 수 있다.

예시 버튼:

```text
조회
초기화
저장
뒤로
종료
```

### 6.2 Push Button의 핵심 속성

| 속성 | 의미 |
|---|---|
| Text | 버튼에 표시되는 문구 |
| Function Code | 버튼 클릭 시 발생하는 명령 코드 |
| Position | 버튼 위치 |
| Length | 버튼 표시 길이 |
| Visible / Active | 표시 및 사용 가능 여부 |

Push Button에서 가장 중요한 것은 Function Code이다.

예를 들어 버튼 속성을 다음과 같이 설정할 수 있다.

| Button Text | Function Code |
|---|---|
| 조회 | DISP |
| 초기화 | CLEAR |
| 종료 | EXIT |

버튼을 누르면 Function Code가 발생한다.  
후속 PAI 모듈에서는 이 Function Code를 읽어 어떤 작업을 할지 판단한다.

### 6.3 OK_CODE와 Function Code

Module Pool 프로그램에서는 보통 Function Code를 담기 위한 전역 변수를 선언한다.

```abap
DATA ok_code TYPE sy-ucomm.
DATA save_ok TYPE sy-ucomm.
```

Screen의 OK Code 필드에 `OK_CODE`를 지정하면, 사용자가 누른 버튼이나 GUI Status 명령의 Function Code가 `OK_CODE`에 들어온다.

이번 모듈에서는 버튼이 Function Code를 발생시킨다는 개념까지만 다룬다.  
Function Code를 PAI에서 처리하는 상세 구조는 `THEORY-14-M05`에서 다룬다.

예시:

## 9. 화면 필드 이름 설계 기준

화면 필드 이름은 단순 입력값이 아니다.  
프로그램과 화면을 연결하는 약속이다.

### 9.1 권장 이름

| 목적 | 권장 예 |
|---|---|
| 항공사 코드 | GV_CARRID |
| 항공사명 | GV_CARRNAME |
| 사용자 ID | GV_USER_ID |
| 상태 | GV_STATUS |
| 금액 | GV_AMOUNT |

### 9.2 피해야 할 이름

```text
FIELD1
FIELD2
INPUT1
TEXT1
AAA
BBB
```

이런 이름은 처음 만들 때는 편해 보이지만, 유지보수 시 의미 파악이 어렵다.  
Dynpro는 화면, Flow Logic, ABAP 프로그램, GUI Status가 서로 연결되므로 이름의 의미가 특히 중요하다.

### 9.3 Screen Element와 ABAP 변수 이름 일치

화면 필드명이 `GV_CARRID`인데 프로그램 변수는 `GV_CARRIER`라면 연결이 기대대로 되지 않을 수 있다.

```text
화면 필드: GV_CARRID
프로그램 변수: GV_CARRIER
```

이 경우 이름을 맞춰야 한다.

```text
화면 필드: GV_CARRID
프로그램 변수: GV_CARRID
```

## 10. Input / Output 속성의 이해

Dynpro Input Field는 상황에 따라 입력 필드가 될 수도 있고 출력 전용 필드처럼 사용될 수도 있다.

| 속성 | 의미 |
|---|---|
| Input 가능 | 사용자가 값을 입력하거나 수정 가능 |
| Output 전용 | 프로그램 값만 표시하고 사용자는 수정하지 않음 |
| Invisible | 화면에서 보이지 않게 처리 |
| Required | 필수 입력처럼 동작하도록 설정 가능 |

초급 실습에서는 다음 기준으로 구성한다.

| 필드 | 권장 속성 |
|---|---|
| GV_CARRID | Input 가능 |
| GV_CARRNAME | 처음에는 Output 성격 또는 Input 가능 실습용 |
| 버튼 | Active |

실무에서는 필드 속성을 PBO에서 동적으로 제어하기도 한다.  
예를 들어 특정 조건에서는 `GV_CARRNAME`을 입력 불가로 바꾸고, 다른 조건에서는 입력 가능하게 만들 수 있다.  
이 주제는 후속 Dynpro 또는 Screen 제어 심화에서 다룬다.

## 11. Function Code 설계 기준

Push Button의 Function Code는 짧고 명확하게 작성한다.

### 11.1 좋은 Function Code

```text
DISP
SAVE
CLEAR
BACK
EXIT
CANC
```

### 11.2 피해야 할 Function Code

```text
BUTTON1
BTN2
AAA
TEST
DOIT
```

Function Code는 PAI에서 분기 기준으로 사용된다.

예를 들어 후속 모듈에서는 다음과 같은 구조를 학습한다.

```abap
CASE ok_code.
  WHEN 'DISP'.
    "조회 처리
  WHEN 'CLEAR'.
    "초기화 처리
  WHEN 'EXIT'.
    "종료 처리
ENDCASE.
```

따라서 버튼 이름을 기능 중심으로 짓는 습관이 중요하다.

## 12. 정상 흐름과 오류 흐름

### 12.1 정상 흐름

```text
1. Module Pool 프로그램에 전역 변수 선언
2. Screen 0100 Layout 진입
3. Text Field 배치
4. Input Field 배치
5. Input Field 이름을 전역 변수와 일치시킴
6. Push Button 배치
7. Function Code 입력
8. Screen 저장
9. Screen 활성화
10. 프로그램 활성화
```

### 12.2 오류 흐름 1: 화면 필드와 프로그램 필드 이름 불일치

| 구분 | 내용 |
|---|---|
| 증상 | 화면에서 입력한 값이 프로그램에서 기대대로 처리되지 않음 |
| 원인 | Screen Field Name과 ABAP 전역 변수명이 다름 |
| 해결 | Screen Painter의 필드명과 ABAP 선언명을 일치시킴 |

### 12.3 오류 흐름 2: Push Button에 Function Code 없음

| 구분 | 내용 |
|---|---|
| 증상 | 버튼을 눌러도 PAI에서 어떤 버튼인지 판단하기 어려움 |
| 원인 | 버튼의 Function Code가 비어 있거나 의미 없음 |
| 해결 | `DISP`, `CLEAR`, `EXIT`처럼 명확한 Function Code 입력 |

### 12.4 오류 흐름 3: OK Code 필드 미설정

| 구분 | 내용 |
|---|---|
| 증상 | 버튼 Function Code가 프로그램 변수에 전달되지 않음 |
| 원인 | Screen의 OK Code 필드에 `OK_CODE`가 지정되지 않음 |
| 해결 | Screen 속성 또는 Element List에서 OK Code Field를 확인 |

### 12.5 오류 흐름 4: 화면 요소만 만들고 Screen Flow Logic이 없음

| 구분 | 내용 |
|---|---|
| 증상 | 화면이 표시되거나 입력되더라도 실제 처리가 연결되지 않음 |
| 원인 | PBO/PAI Module이 아직 구현되지 않음 |
| 해결 | 후속 모듈에서 PBO, PAI 모듈을 추가하여 처리 흐름 연결 |

현재 모듈에서는 화면 요소 배치가 목적이므로 PBO/PAI 구현이 완전하지 않아도 된다.  
다만 화면 요소는 Flow Logic과 연결되어야 실제 애플리케이션이 된다는 점은 기억해야 한다.

## 13. 실무 적용 기준

### 13.1 화면 요소는 사용자 업무 흐름 기준으로 배치한다

Dynpro 화면은 기술자 입장에서는 필드와 버튼의 집합이지만, 사용자 입장에서는 업무를 수행하는 화면이다.

따라서 화면 설계 시 다음을 고려한다.

| 관점 | 질문 |
|---|---|
| 업무 흐름 | 사용자가 어떤 순서로 입력하는가? |
| 필수값 | 반드시 입력해야 하는 값은 무엇인가? |
| 가독성 | 라벨과 입력칸이 명확한가? |
| 버튼 위치 | 주요 버튼이 사용자가 찾기 쉬운 위치에 있는가? |
| 오류 예방 | 잘못 입력하기 쉬운 필드는 안내가 충분한가? |

### 13.2 화면에 너무 많은 필드를 넣지 않는다

초급 실습에서는 많은 필드를 넣는 것보다 적은 필드로 명확한 흐름을 만드는 것이 좋다.

나쁜 예:

```text
한 화면에 30개 필드를 무작위 배치
```

좋은 예:

```text
조회 조건 1~2개
결과 표시 1~2개
기본 버튼 2~3개
```

### 13.3 버튼은 기능 기준으로 제한한다

버튼이 많을수록 사용자는 혼란스러워진다.  
처음에는 다음 세 가지 정도가 적절하다.

```text
Display
Clear
Exit
```

Save, Delete, Change 같은 버튼은 데이터 변경과 권한, Lock, Commit 처리와 연결되므로 후속 실무 영역에서 다루는 것이 적절하다.

### 13.4 표준 SAP 화면 관행을 관찰한다

실무에서는 직접 만든 Z 화면만 보지 말고, SAP 표준 트랜잭션의 화면 배치를 관찰하는 것이 좋다.

관찰 포인트:

```text
라벨은 어떻게 배치되어 있는가?
필수 입력값은 어떻게 표시되는가?
버튼은 어디에 위치하는가?
조회, 저장, 뒤로, 종료 같은 기능은 어떤 방식으로 제공되는가?
```

초급자는 표준 화면을 따라 보는 것만으로도 화면 설계 감각을 빠르게 익힐 수 있다.

## 16. 평가 문제

### 16.1 객관식

#### Q1. Text Field의 가장 적절한 설명은?

A. 사용자가 값을 입력하는 필드이다.  
B. 버튼 클릭 시 Function Code를 발생시키는 요소이다.  
C. 화면에 고정 설명이나 라벨을 표시하는 요소이다.  
D. 데이터베이스 테이블을 생성하는 객체이다.

**정답:** C

#### Q2. Input Field의 이름을 ABAP 전역 변수와 맞추는 이유는?

A. 화면 색상을 자동으로 바꾸기 위해서이다.  
B. 화면과 프로그램 사이의 값 전달 연결을 명확히 하기 위해서이다.  
C. Function Code를 생성하기 위해서이다.  
D. Screen Number를 자동 생성하기 위해서이다.

**정답:** B

#### Q3. Push Button에서 가장 중요한 속성 중 하나는?

A. Data Class  
B. Size Category  
C. Function Code  
D. Enhancement Category

**정답:** C

### 16.2 서술형

#### Q1. Push Button의 Function Code가 필요한 이유를 설명하시오.

**모범 답안:**  
Push Button을 클릭했을 때 프로그램이 어떤 버튼이 눌렸는지 판단하기 위한 명령 코드가 필요하다. Function Code는 PAI 처리에서 분기 기준으로 사용되며, 예를 들어 `DISP`, `CLEAR`, `EXIT` 같은 값으로 기능을 구분할 수 있다.

#### Q2. Text Field와 Input Field의 차이를 설명하시오.

**모범 답안:**  
Text Field는 화면에 고정된 설명이나 라벨을 표시하는 요소이고, Input Field는 사용자가 값을 입력하거나 프로그램 값이 표시되는 화면 필드이다. Text Field는 의미를 안내하고, Input Field는 데이터 입출력에 사용된다.

#### Q3. 화면 필드명을 `FIELD1`, `FIELD2`처럼 만들면 어떤 문제가 생기는가?

**모범 답안:**  
필드의 업무 의미를 파악하기 어렵고, ABAP 전역 변수나 Flow Logic과 연결할 때 유지보수성이 떨어진다. 화면, 프로그램, 버튼 처리 로직이 서로 연결되는 Dynpro에서는 의미 있는 이름을 사용하는 것이 중요하다.
