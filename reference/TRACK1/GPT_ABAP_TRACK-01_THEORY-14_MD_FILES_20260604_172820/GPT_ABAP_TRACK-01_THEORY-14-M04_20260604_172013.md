## 3. PBO란 무엇인가?

PBO는 **Process Before Output**의 약어이다. 이름 그대로 화면이 사용자에게 출력되기 전에 실행되는 처리 흐름이다.

초급자는 PBO를 다음처럼 이해하면 된다.

```text
PBO = 화면을 보여주기 전에 화면 상태를 준비하는 단계
```

예를 들어 사용자가 어떤 화면을 열었을 때 다음 작업이 필요하다고 하자.

- 화면 제목 표시
- 상단 Toolbar 버튼 세팅
- 특정 Input Field에 기본값 입력
- 조회 모드에서는 입력 필드 비활성화
- 신규 생성 모드에서는 입력 필드 활성화
- 화면에 보여줄 안내 텍스트 세팅

이런 작업은 대체로 화면이 보이기 전에 준비되어야 한다. 그래서 PBO에서 처리한다.

---

## 4. Dynpro 처리 사이클에서 PBO의 위치

Dynpro 화면은 한 번만 실행되고 끝나는 구조가 아니다. 화면이 열리고, 사용자가 값을 입력하고, 버튼을 누르고, 다시 화면이 표시되는 사이클을 반복한다.

기본 흐름은 다음과 같다.

```text
CALL SCREEN 0100
  ↓
PBO 실행
  ↓
화면 표시
  ↓
사용자 입력 / 버튼 클릭
  ↓
PAI 실행
  ↓
다음 화면 결정 또는 같은 화면 재표시
  ↓
다시 PBO 실행
```

즉 PBO는 화면을 처음 열 때만 실행되는 것이 아니다. 같은 화면으로 다시 돌아오거나, PAI 이후 같은 Screen이 다시 표시될 때도 반복 실행될 수 있다.

이 점은 매우 중요하다. 초급자가 PBO에 누적성 로직을 잘못 넣으면 화면이 다시 표시될 때마다 값이 계속 초기화되거나, 의도치 않게 화면 상태가 반복 변경될 수 있다.

## 5. Screen Flow Logic에서의 PBO

Screen Painter에서 Screen을 만들면 해당 Screen에는 Flow Logic이 있다. Flow Logic에는 대표적으로 다음 두 영역이 있다.

```abap
PROCESS BEFORE OUTPUT.
  MODULE status_0100.

PROCESS AFTER INPUT.
  MODULE user_command_0100.
```

여기서 `PROCESS BEFORE OUTPUT` 아래의 Module들이 PBO 시점에 실행된다.

### 5.1 기본 형태

```abap
PROCESS BEFORE OUTPUT.
  MODULE status_0100.
```

이 구문은 다음 의미이다.

```text
Screen 0100을 사용자에게 출력하기 전에
ABAP 프로그램의 STATUS_0100 OUTPUT Module을 실행하라.
```

### 5.2 ABAP Module 구현 형태

Flow Logic에서 호출한 Module은 ABAP 코드에 다음처럼 구현한다.

```abap
MODULE status_0100 OUTPUT.
  SET PF-STATUS 'STATUS_0100'.
  SET TITLEBAR  'TITLE_0100'.
ENDMODULE.
```

여기서 중요한 점은 `OUTPUT` 키워드이다.

| Flow Logic 위치 | ABAP Module 형태 |
|---|---|
| PROCESS BEFORE OUTPUT | `MODULE module_name OUTPUT.` |
| PROCESS AFTER INPUT | `MODULE module_name INPUT.` |

PBO Module은 반드시 `OUTPUT` Module로 구현해야 한다.

## 6. PBO에서 주로 처리하는 작업

PBO에서는 일반적으로 화면 출력 준비와 관련된 작업을 수행한다.

| 작업 | 설명 |
|---|---|
| GUI Status 설정 | 화면 상단 버튼, 메뉴, Function Key 제어 |
| Titlebar 설정 | 화면 제목 표시 |
| 화면 필드 기본값 설정 | 최초 진입 시 기본값 제공 |
| 화면 필드 속성 제어 | 입력 가능/불가능, 표시/숨김, 강조 등 |
| 출력용 데이터 준비 | 화면에 보여줄 텍스트나 요약 값 계산 |
| Subscreen/Custom Control 준비 | 컨테이너나 화면 구성 요소 준비 |

초급 단계에서는 다음 세 가지를 가장 먼저 익히면 된다.

```text
1. SET PF-STATUS
2. SET TITLEBAR
3. 화면 필드 기본값 또는 속성 제어
```

`SET PF-STATUS`와 `SET TITLEBAR`는 별도 모듈인 `THEORY-14-M06`에서 더 자세히 다룬다. 이번 모듈에서는 PBO에서 호출되는 대표 작업이라는 관점으로만 다룬다.

## 7. PBO 최소 예제 구조

이번 실습에서는 간단한 Module Pool 프로그램을 기준으로 한다.

### 7.1 프로그램 구성 예시

```text
Program: SAPMZJHY_DYNPRO
Screen : 0100
Includes:
  MZJHY_DYNPRO_TOP  - Global Data
  MZJHY_DYNPRO_O01  - PBO Modules
  MZJHY_DYNPRO_I01  - PAI Modules
```

[추정] 실제 교육 시스템에서는 Include 이름이 시스템 규칙이나 생성 방식에 따라 다를 수 있다. 중요한 것은 TOP Include에는 Global Data, O01 Include에는 PBO Module, I01 Include에는 PAI Module을 둔다는 구조적 원칙이다.

### 7.2 TOP Include 예시

```abap
PROGRAM sapmzjhy_dynpro.

DATA: gv_user_id   TYPE char10,
      gv_user_name TYPE char40,
      gv_message   TYPE char80,
      gv_mode      TYPE c LENGTH 1,
      ok_code      TYPE sy-ucomm.
```

화면의 Input Field 이름을 `GV_USER_ID`, `GV_USER_NAME`, `GV_MESSAGE`와 동일하게 만들면, 화면 필드와 ABAP Global Data가 연결되는 기본 흐름을 확인할 수 있다.

### 7.3 Screen 0100 Flow Logic 예시

```abap
PROCESS BEFORE OUTPUT.
  MODULE status_0100.
  MODULE init_screen_0100.

PROCESS AFTER INPUT.
  MODULE user_command_0100.
```

이번 모듈에서는 PBO 영역의 두 Module을 중심으로 본다.

```text
STATUS_0100
INIT_SCREEN_0100
```

## 8. PBO Module 예제 1: Status와 Title 설정

가장 대표적인 PBO Module은 화면 상태와 제목을 세팅하는 Module이다.

```abap
MODULE status_0100 OUTPUT.
  SET PF-STATUS 'STATUS_0100'.
  SET TITLEBAR  'TITLE_0100'.
ENDMODULE.
```

### 8.1 왜 PBO에서 설정하는가?

GUI Status와 Titlebar는 화면이 사용자에게 보이기 전에 준비되어야 한다. 사용자가 화면을 본 뒤에 제목이나 버튼이 세팅되면 화면 표시 흐름과 맞지 않는다.

따라서 PBO에서 다음을 설정한다.

| 구문 | 목적 |
|---|---|
| `SET PF-STATUS` | Toolbar, Menu, Function Key 구성 |
| `SET TITLEBAR` | 화면 제목 구성 |

### 8.2 초급자 주의점

`STATUS_0100`과 `TITLE_0100`은 문자열만 적는다고 자동으로 생성되는 것이 아니다. GUI Status와 Titlebar는 별도 객체로 생성되어 있어야 한다.

PBO Module에 다음 코드를 썼는데 오류가 발생한다면, 실제 GUI Status 또는 Titlebar가 존재하는지 확인해야 한다.

```abap
SET PF-STATUS 'STATUS_0100'.
SET TITLEBAR  'TITLE_0100'.
```

이 주제는 M06에서 더 자세히 다루므로, 이번 모듈에서는 “PBO에서 세팅한다”는 위치를 기억한다.

## 9. PBO Module 예제 2: 화면 기본값 설정

화면이 처음 열릴 때 기본 안내 문구를 보여주고 싶다면 PBO에서 값을 설정할 수 있다.

```abap
MODULE init_screen_0100 OUTPUT.
  IF gv_message IS INITIAL.
    gv_message = '사용자 정보를 입력하세요.'.
  ENDIF.
ENDMODULE.
```

이 코드는 `GV_MESSAGE`가 비어 있을 때만 기본 문구를 세팅한다.

### 9.1 왜 `IS INITIAL`을 확인하는가?

PBO는 한 번만 실행되지 않는다. PAI 이후 같은 화면이 다시 표시될 때도 PBO가 실행될 수 있다. 따라서 매번 무조건 값을 넣으면 사용자가 입력했거나 프로그램에서 변경한 값이 의도치 않게 초기화될 수 있다.

나쁜 예:

```abap
MODULE init_screen_0100 OUTPUT.
  gv_user_name = 'Default Name'.
ENDMODULE.
```

위 코드는 화면이 다시 표시될 때마다 `GV_USER_NAME`을 `Default Name`으로 덮어쓸 수 있다.

더 안전한 예:

```abap
MODULE init_screen_0100 OUTPUT.
  IF gv_user_name IS INITIAL.
    gv_user_name = 'Default Name'.
  ENDIF.
ENDMODULE.
```

초급 단계에서는 PBO 초기값 세팅 시 다음 기준을 사용한다.

```text
정말 매번 다시 세팅해야 하는 값인가?
최초 진입 시에만 세팅해야 하는 값인가?
사용자 입력값을 덮어쓰면 안 되는 값인가?
```

## 10. PBO Module 예제 3: 화면 필드 속성 제어

PBO에서는 화면 필드의 입력 가능 여부나 표시 여부를 제어할 수 있다. 대표적으로 `SCREEN` Internal Table을 사용한다.

예를 들어 조회 모드일 때 `GV_USER_ID`를 입력 불가능하게 만들 수 있다.

```abap
MODULE control_fields_0100 OUTPUT.
  LOOP AT SCREEN.
    IF screen-name = 'GV_USER_ID' AND gv_mode = 'D'.
      screen-input = 0.
      MODIFY SCREEN.
    ENDIF.
  ENDLOOP.
ENDMODULE.
```

### 10.1 SCREEN Internal Table의 의미

`SCREEN`은 현재 Screen의 필드 속성을 담고 있는 시스템 제공 구조이다. PBO 시점에 `LOOP AT SCREEN`으로 각 화면 요소를 순회하면서 속성을 조정할 수 있다.

초급자가 처음 알아야 할 대표 속성은 다음과 같다.

| 속성 | 의미 |
|---|---|
| `screen-name` | 화면 요소 이름 |
| `screen-input` | 입력 가능 여부 |
| `screen-active` | 활성 여부 |
| `screen-invisible` | 숨김 여부 |
| `screen-required` | 필수 입력 표시 여부 |

### 10.2 입력 비활성화 예시

```abap
IF screen-name = 'GV_USER_ID'.
  screen-input = 0.
  MODIFY SCREEN.
ENDIF.
```

### 10.3 숨김 처리 예시

```abap
IF screen-name = 'GV_MESSAGE'.
  screen-invisible = 1.
  MODIFY SCREEN.
ENDIF.
```

### 10.4 주의점

`MODIFY SCREEN`을 호출하지 않으면 변경한 속성이 적용되지 않는다.

나쁜 예:

```abap
LOOP AT SCREEN.
  IF screen-name = 'GV_USER_ID'.
    screen-input = 0.
  ENDIF.
ENDLOOP.
```

좋은 예:

```abap
LOOP AT SCREEN.
  IF screen-name = 'GV_USER_ID'.
    screen-input = 0.
    MODIFY SCREEN.
  ENDIF.
ENDLOOP.
```

## 11. PBO에서 피해야 할 작업

PBO는 화면 출력 전 준비 단계이다. 따라서 모든 로직을 PBO에 넣는 것은 좋지 않다.

### 11.1 사용자 입력 검증을 PBO에서 하지 않는다

사용자가 입력한 값에 대한 검증은 일반적으로 PAI에서 수행한다. PBO는 화면을 보여주기 전 단계이므로, 입력 검증의 주된 위치가 아니다.

나쁜 흐름:

```text
PBO에서 사용자 입력값 검증
```

권장 흐름:

```text
PAI에서 사용자 입력값 검증
PBO에서 검증 결과를 화면에 표시할 준비
```

### 11.2 DB 변경 작업을 PBO에 넣지 않는다

PBO는 화면이 표시될 때마다 반복될 수 있다. 여기에 INSERT, UPDATE, DELETE 같은 DB 변경 작업을 넣으면 화면이 다시 표시될 때마다 데이터가 중복 생성되거나 원치 않게 변경될 수 있다.

나쁜 예:

```abap
MODULE init_screen_0100 OUTPUT.
  INSERT zt_jhy_user FROM ls_user.
ENDMODULE.
```

DB 변경은 사용자의 명확한 액션 이후 PAI 또는 별도 처리 흐름에서 수행해야 한다.

### 11.3 무거운 SELECT를 반복 실행하지 않는다

PBO에 조회 로직을 둘 수는 있지만, 화면이 표시될 때마다 반복 실행된다는 점을 고려해야 한다. 대량 SELECT를 매 PBO마다 실행하면 성능 문제가 생길 수 있다.

초급 단계에서는 다음 원칙을 둔다.

```text
작고 단순한 표시용 값 준비는 가능하다.
대량 조회나 비용이 큰 로직은 실행 조건을 명확히 둔다.
```

---

## 12. PBO와 Global Data의 관계

Dynpro 화면 필드는 ABAP 프로그램의 Global Data와 연결되는 경우가 많다.

예를 들어 Screen Painter에서 Input Field 이름을 `GV_USER_ID`로 만들고, TOP Include에 다음 변수가 있으면 화면 필드와 프로그램 필드가 연결된다.

```abap
DATA gv_user_id TYPE char10.
```

PBO에서 다음처럼 값을 넣으면 화면에 표시될 수 있다.

```abap
MODULE init_screen_0100 OUTPUT.
  gv_user_id = 'U0001'.
ENDMODULE.
```

초급자가 기억할 핵심은 다음이다.

```text
Screen Field 이름과 ABAP Global Data 이름이 연결된다.
PBO에서 Global Data를 준비하면 화면에 출력될 값에 영향을 준다.
PAI에서는 사용자가 입력한 값이 Global Data로 전달되어 처리된다.
```

정확한 데이터 전달 타이밍은 Screen 처리 단계와 Field 속성, Flow Logic 구성에 따라 세부적으로 설명할 수 있지만, 초급 단계에서는 “PBO는 출력 준비, PAI는 입력 처리”라는 큰 구조를 먼저 잡는 것이 중요하다.

## 13. 전체 예제: PBO 중심 Module Pool 흐름

아래 예제는 이번 모듈에서 다루는 PBO 흐름을 한 번에 확인하기 위한 최소 구조이다.

### 13.1 TOP Include

```abap
PROGRAM sapmzjhy_dynpro.

DATA: gv_user_id   TYPE char10,
      gv_user_name TYPE char40,
      gv_message   TYPE char80,
      gv_mode      TYPE c LENGTH 1 VALUE 'C',
      ok_code      TYPE sy-ucomm.
```

### 13.2 Screen 0100 Flow Logic

```abap
PROCESS BEFORE OUTPUT.
  MODULE status_0100.
  MODULE init_screen_0100.
  MODULE control_fields_0100.

PROCESS AFTER INPUT.
  MODULE user_command_0100.
```

### 13.3 PBO Include

```abap
MODULE status_0100 OUTPUT.
  SET PF-STATUS 'STATUS_0100'.
  SET TITLEBAR  'TITLE_0100'.
ENDMODULE.

MODULE init_screen_0100 OUTPUT.
  IF gv_message IS INITIAL.
    gv_message = '사용자 정보를 입력하세요.'.
  ENDIF.
ENDMODULE.

MODULE control_fields_0100 OUTPUT.
  LOOP AT SCREEN.
    IF screen-name = 'GV_USER_ID' AND gv_mode = 'D'.
      screen-input = 0.
      MODIFY SCREEN.
    ENDIF.
  ENDLOOP.
ENDMODULE.
```

### 13.4 PAI Include 예고

PAI Module은 다음 모듈에서 자세히 다룬다. 여기서는 화면이 정상 활성화되도록 최소 형태만 둔다.

```abap
MODULE user_command_0100 INPUT.
  ok_code = sy-ucomm.

  CASE ok_code.
    WHEN 'BACK' OR 'EXIT' OR 'CANC'.
      LEAVE PROGRAM.
  ENDCASE.
ENDMODULE.
```

이 예제에서 이번 모듈의 핵심은 PAI가 아니라 PBO이다. `STATUS_0100`, `INIT_SCREEN_0100`, `CONTROL_FIELDS_0100`이 화면 표시 전에 어떤 준비를 하는지 관찰한다.

## 14. 실습: PBO 실행 확인

### 14.1 실습 목표

Screen 0100이 표시되기 전에 PBO Module이 실행되는 것을 확인한다.

### 14.2 실습 준비

다음 객체가 준비되어 있다고 가정한다.

| 객체 | 예시 |
|---|---|
| Module Pool Program | `SAPMZJHY_DYNPRO` |
| Screen | `0100` |
| Input Field | `GV_USER_ID`, `GV_USER_NAME` |
| Text 또는 Output Field | `GV_MESSAGE` |
| Push Button | BACK 또는 CANCEL 역할 |

### 14.3 실습 절차

```text
1. SE80 또는 Object Navigator에서 Module Pool 프로그램을 연다.
2. Screen 0100의 Flow Logic을 연다.
3. PROCESS BEFORE OUTPUT에 MODULE status_0100, init_screen_0100을 작성한다.
4. ABAP Include에 MODULE ... OUTPUT 구현을 작성한다.
5. 프로그램과 Screen을 Activate한다.
6. Screen 0100을 실행한다.
7. GV_MESSAGE에 기본 문구가 표시되는지 확인한다.
8. PBO Module에 Breakpoint를 설정하고 다시 실행한다.
9. 화면 표시 전에 Breakpoint가 걸리는지 확인한다.
```

### 14.4 검증 포인트

| 검증 항목 | 기대 결과 |
|---|---|
| `STATUS_0100` 실행 | 화면 표시 전에 Breakpoint 도달 |
| `INIT_SCREEN_0100` 실행 | `GV_MESSAGE` 기본값 세팅 |
| 화면 표시 | 기본 문구가 화면에 보임 |
| PAI 후 재표시 | 같은 화면으로 돌아오면 PBO 재실행 |
| `IS INITIAL` 조건 | 기존 값이 있을 때 불필요한 덮어쓰기 방지 |

## 15. 디버깅 관점

PBO 흐름을 이해하려면 Breakpoint가 매우 유용하다.

### 15.1 Breakpoint 위치

다음 위치에 Breakpoint를 설정한다.

```abap
MODULE status_0100 OUTPUT.
```

또는

```abap
MODULE init_screen_0100 OUTPUT.
```

화면을 실행하면 사용자에게 화면이 보이기 전에 Debugger가 먼저 열리는 것을 확인할 수 있다.

### 15.2 확인할 값

Debugger에서 다음을 확인한다.

| 항목 | 확인 내용 |
|---|---|
| `GV_USER_ID` | PBO 전에 값이 있는지 |
| `GV_MESSAGE` | PBO에서 기본값이 들어가는지 |
| `GV_MODE` | 화면 제어 조건으로 사용할 값 |
| `SCREEN-NAME` | LOOP AT SCREEN에서 현재 처리 중인 화면 요소 |
| `SCREEN-INPUT` | 입력 가능 여부가 바뀌는지 |

### 15.3 반복 실행 확인

한 번 화면이 표시된 뒤 버튼을 눌러 같은 화면으로 돌아오면 PBO가 다시 실행되는지 확인한다. 이 실습은 “PBO는 최초 1회가 아니라 화면 출력 전마다 실행된다”는 사실을 이해하는 데 중요하다.

## 16. 자주 발생하는 오류와 해결

### 16.1 Flow Logic의 Module 이름과 ABAP Module 이름이 다름

#### 증상

화면 활성화 또는 실행 시 Module 관련 오류가 발생한다.

#### 원인

Flow Logic에는 다음처럼 작성했지만:

```abap
MODULE status_0100.
```

ABAP 코드에는 다른 이름으로 구현한 경우이다.

```abap
MODULE stat_0100 OUTPUT.
```

#### 해결

Flow Logic의 Module 이름과 ABAP Module 이름을 일치시킨다.

```abap
PROCESS BEFORE OUTPUT.
  MODULE status_0100.
```

```abap
MODULE status_0100 OUTPUT.
  SET PF-STATUS 'STATUS_0100'.
ENDMODULE.
```

---

### 16.2 PBO Module을 INPUT으로 구현함

#### 증상

PBO에서 호출하는 Module인데 ABAP 코드가 맞지 않아 오류가 발생한다.

#### 원인

`PROCESS BEFORE OUTPUT` 영역에서 호출하는 Module은 `OUTPUT` Module이어야 한다.

잘못된 예:

```abap
MODULE status_0100 INPUT.
  SET PF-STATUS 'STATUS_0100'.
ENDMODULE.
```

#### 해결

```abap
MODULE status_0100 OUTPUT.
  SET PF-STATUS 'STATUS_0100'.
ENDMODULE.
```

---

### 16.3 PBO에서 값을 매번 덮어씀

#### 증상

사용자가 입력한 값이 화면 재표시 후 사라지거나 기본값으로 돌아간다.

#### 원인

PBO는 반복 실행될 수 있는데, 매번 기본값을 무조건 세팅했기 때문이다.

#### 해결

최초 세팅이 필요한 값은 조건을 둔다.

```abap
IF gv_user_name IS INITIAL.
  gv_user_name = 'Default Name'.
ENDIF.
```

---

### 16.4 LOOP AT SCREEN 후 MODIFY SCREEN 누락

#### 증상

`screen-input = 0` 같은 코드를 작성했지만 화면 속성이 바뀌지 않는다.

#### 원인

`SCREEN` 구조 값을 변경한 뒤 `MODIFY SCREEN`을 호출하지 않았다.

#### 해결

```abap
LOOP AT SCREEN.
  IF screen-name = 'GV_USER_ID'.
    screen-input = 0.
    MODIFY SCREEN.
  ENDIF.
ENDLOOP.
```

---

### 16.5 GUI Status가 존재하지 않음

#### 증상

`SET PF-STATUS 'STATUS_0100'` 실행 시 Status 관련 오류가 발생한다.

#### 원인

`STATUS_0100`이라는 GUI Status가 실제로 생성되어 있지 않다.

#### 해결

Menu Painter에서 GUI Status를 생성하거나, 임시로 해당 구문을 주석 처리한 뒤 PBO 기본 흐름만 먼저 확인한다. 이후 M06에서 GUI Status를 정식으로 학습한다.

## 17. 실무 적용 기준

### 17.1 PBO에 적합한 로직

| 로직 | 적합성 | 이유 |
|---|---|---|
| `SET PF-STATUS` | 적합 | 화면 출력 전 Toolbar 준비 |
| `SET TITLEBAR` | 적합 | 화면 제목 준비 |
| 필드 입력 가능 여부 제어 | 적합 | 화면 표시 전 속성 결정 |
| 기본 안내 문구 세팅 | 적합 | 사용자에게 보일 출력값 준비 |
| 소규모 표시 데이터 준비 | 조건부 적합 | 반복 실행 비용 고려 필요 |

### 17.2 PBO에 부적합한 로직

| 로직 | 부적합 이유 |
|---|---|
| 사용자 입력값 검증 | PAI가 더 적절 |
| DB INSERT/UPDATE/DELETE | 화면 재표시마다 반복될 위험 |
| 무거운 대량 SELECT | 성능 문제 가능 |
| 권한 변경성 로직 남발 | 화면 표시마다 반복되어 복잡도 증가 |
| 사용자 액션 처리 | PAI의 OK_CODE 처리 위치가 적절 |

### 17.3 실무 설계 원칙

PBO Module은 화면 출력 준비 책임을 가진다. 따라서 Module 이름도 그 책임이 드러나게 작성하는 것이 좋다.

좋은 예:

```text
STATUS_0100
INIT_SCREEN_0100
CONTROL_FIELDS_0100
SET_DEFAULTS_0100
```

나쁜 예:

```text
MODULE_0100
PROCESS_0100
ABC
TEST
```

이름만 보고도 해당 Module이 화면 상태 설정인지, 기본값 세팅인지, 필드 제어인지 추측할 수 있어야 한다.

## 18. 초급자 오해 정리

### 오해 1. PBO는 화면을 처음 열 때만 실행된다

아니다. PBO는 화면이 사용자에게 출력되기 전마다 실행될 수 있다. 같은 화면으로 돌아오면 다시 실행될 수 있다.

### 오해 2. PBO에서 사용자 입력값 검증을 하면 된다

일반적으로 사용자 입력값 검증은 PAI에서 수행한다. PBO는 출력 준비 단계이다.

### 오해 3. PBO에 SELECT를 넣으면 항상 문제다

항상 문제는 아니다. 다만 PBO가 반복 실행될 수 있으므로 조회 비용과 실행 조건을 고려해야 한다.

### 오해 4. MODULE 이름은 아무렇게나 해도 된다

동작만 보면 가능할 수 있지만 유지보수성이 떨어진다. Screen Number와 책임이 드러나는 이름을 사용하는 것이 좋다.

### 오해 5. `SCREEN` 속성을 바꾸면 자동 반영된다

`LOOP AT SCREEN`에서 속성을 바꾼 뒤에는 일반적으로 `MODIFY SCREEN`을 호출해야 한다.

## 19. 강사용 설명 포인트

강의 시에는 다음 흐름을 칠판 또는 슬라이드에 반복적으로 보여주는 것이 좋다.

```text
PBO → 화면 표시 → 사용자 입력 → PAI → 화면 재표시 → PBO
```

특히 초급자는 “PBO는 before output”이라는 용어는 외우지만, 실제로 무엇을 해야 하는지 감을 잡지 못하는 경우가 많다. 따라서 다음 식으로 설명하면 효과적이다.

```text
PBO는 식당으로 비유하면 손님이 오기 전 테이블을 세팅하는 단계입니다.
PAI는 손님이 주문한 뒤 주문 내용을 처리하는 단계입니다.
```

다만 비유 후에는 반드시 실제 ABAP 용어로 되돌려야 한다.

```text
PBO = 화면 출력 전 준비
PAI = 사용자 입력 후 처리
```

또한 PBO에 Breakpoint를 걸고 화면이 표시되기 전에 Debugger가 멈추는 장면을 보여주면 학습 효과가 높다.

## 20. 평가 문제

### 20.1 객관식

#### Q1. PBO의 의미로 가장 적절한 것은?

A. 사용자가 버튼을 누른 후 실행되는 입력 처리 단계  
B. 화면이 사용자에게 출력되기 전에 실행되는 처리 단계  
C. DB Commit 이후 실행되는 후처리 단계  
D. 프로그램이 종료될 때 실행되는 이벤트  

**정답:** B

#### Q2. `PROCESS BEFORE OUTPUT`에서 호출하는 ABAP Module의 올바른 형태는?

A. `MODULE status_0100 INPUT.`  
B. `MODULE status_0100 OUTPUT.`  
C. `FORM status_0100.`  
D. `METHOD status_0100.`  

**정답:** B

#### Q3. PBO에서 일반적으로 처리하기 적절한 작업은?

A. 사용자가 입력한 값의 최종 저장  
B. DB UPDATE 반복 실행  
C. 화면 제목과 GUI Status 설정  
D. 사용자의 버튼 Function Code 처리  

**정답:** C

#### Q4. `LOOP AT SCREEN`에서 필드 속성을 변경한 후 일반적으로 필요한 구문은?

A. `COMMIT WORK`  
B. `MODIFY SCREEN`  
C. `LEAVE SCREEN`  
D. `CALL SCREEN`  

**정답:** B

### 20.2 단답형

#### Q1. PBO가 반복 실행될 수 있다는 사실이 중요한 이유를 설명하시오.

**모범 답안:**  
PBO는 화면이 표시되기 전마다 실행될 수 있으므로, 기본값 세팅이나 DB 조회 같은 로직이 반복 실행될 수 있다. 따라서 사용자 입력값을 무조건 덮어쓰거나 비용이 큰 로직을 매번 실행하지 않도록 조건을 두어야 한다.

#### Q2. PBO와 PAI의 역할 차이를 설명하시오.

**모범 답안:**  
PBO는 화면 출력 전 준비 단계로 GUI Status, Titlebar, 화면 필드 기본값, 화면 속성 제어 등을 수행한다. PAI는 사용자가 입력하거나 버튼을 누른 뒤 실행되는 입력 처리 단계로, OK_CODE 처리와 입력값 검증 등이 중심이다.

#### Q3. `MODULE status_0100 OUTPUT.`에서 `OUTPUT`의 의미를 설명하시오.

**모범 답안:**  
해당 Module이 PBO, 즉 화면 출력 전 처리 단계에서 실행되는 Module임을 나타낸다. `PROCESS BEFORE OUTPUT`에서 호출되는 Module은 `OUTPUT` Module로 구현해야 한다.

### 20.3 실습 리뷰 문제

다음 코드의 문제점을 설명하시오.

```abap
MODULE init_screen_0100 OUTPUT.
  gv_user_name = 'Default User'.
ENDMODULE.
```

**모범 답안:**  
PBO는 화면이 표시될 때마다 반복 실행될 수 있으므로, 이 코드는 화면이 다시 표시될 때마다 `GV_USER_NAME`을 `Default User`로 덮어쓸 수 있다. 최초 진입 시에만 기본값을 세팅하려면 `IF gv_user_name IS INITIAL.` 같은 조건을 두는 것이 안전하다.

| 화면 기본값 세팅 시 무조건 덮어쓰기의 위험을 설명할 수 있다. |  |
| `LOOP AT SCREEN`과 `MODIFY SCREEN`의 기본 용도를 설명할 수 있다. |  |
| PBO와 PAI의 큰 역할 차이를 설명할 수 있다. |  |

---

## 22. 핵심 요약

```text
PBO는 Process Before Output의 약어이다.
PBO는 화면이 사용자에게 표시되기 전에 실행된다.
Screen Flow Logic에서는 PROCESS BEFORE OUTPUT 영역에 PBO Module을 작성한다.
PBO Module은 ABAP 코드에서 MODULE ... OUTPUT 형태로 구현한다.
PBO에서는 GUI Status, Titlebar, 기본값, 화면 속성 제어 같은 출력 준비 작업을 수행한다.
PBO는 화면이 다시 표시될 때마다 반복 실행될 수 있다.
사용자 입력 검증과 버튼 처리의 중심은 PAI이다.
```

## 23. 후속 모듈 연결

이번 모듈에서는 화면이 표시되기 전의 준비 단계인 PBO를 학습했다. 다음 모듈은 `THEORY-14-M05 — PAI 처리 흐름`이다.

연결 관계는 다음과 같다.

```text
THEORY-14-M04 PBO 처리 흐름
  → 화면 출력 전 준비
  → 기본값, 상태, 제목, 필드 속성 제어

THEORY-14-M05 PAI 처리 흐름
  → 사용자 입력 후 처리
  → OK_CODE, 버튼 처리, 입력값 검증
```

Dynpro 학습에서 가장 중요한 구조는 다음 한 줄이다.

```text
PBO는 보여주기 전, PAI는 입력받은 후.
```

이 구조를 이해해야 이후 PF-STATUS, TITLEBAR, Function Code, Custom Control, Grid ALV 연결 흐름을 안정적으로 따라갈 수 있다.
