## 3. PF-STATUS란 무엇인가?

### 3.1 쉬운 정의

`PF-STATUS`는 Classic Dynpro 화면에서 사용할 **GUI Status**를 지정하는 기능이다.

GUI Status에는 다음 요소가 포함될 수 있다.

| 요소 | 설명 |
|---|---|
| Standard Toolbar | 저장, 뒤로가기, 종료, 취소 등 상단 표준 툴바 영역 |
| Application Toolbar | 개발자가 추가하는 업무 버튼 영역 |
| Menu Bar | 화면 상단 메뉴 구성 |
| Function Keys | F1, F2, F3 등 기능키와 Function Code 연결 |
| Function Code | 버튼이나 메뉴 선택 시 PAI로 전달되는 코드 |

즉, PF-STATUS는 단순히 버튼 하나를 만드는 설정이 아니라, 화면에서 사용자가 실행할 수 있는 **명령 집합**을 정의하는 객체이다.

### 3.2 왜 필요한가?

Dynpro 화면은 단순 입력 필드만으로 완성되지 않는다.  
사용자는 화면에서 저장, 조회, 뒤로가기, 취소, 삭제, 신규 생성 같은 액션을 실행해야 한다.

PF-STATUS가 없으면 다음 문제가 생긴다.

```text
사용자가 어떤 버튼을 누를 수 있는지 명확하지 않다.
PAI에서 어떤 Function Code가 들어올지 설계하기 어렵다.
화면별 툴바와 메뉴가 일관되지 않는다.
저장/뒤로가기/취소 같은 기본 흐름을 표준적으로 처리하기 어렵다.
```

PF-STATUS는 화면의 사용자 액션을 명시적으로 정의하고, 그 액션을 PAI 로직과 연결하는 역할을 한다.

## 4. TITLEBAR란 무엇인가?

### 4.1 쉬운 정의

`TITLEBAR`는 Dynpro 화면 상단에 표시되는 제목 영역이다.

예를 들어 사용자 유지보수 화면이라면 다음과 같은 제목을 표시할 수 있다.

```text
사용자 기본정보 유지보수
User Master Maintenance
주문 상세 조회
```

ABAP에서는 PBO에서 다음처럼 설정한다.

```abap
SET TITLEBAR 'T100'.
```

여기서 `T100`은 Menu Painter 또는 관련 화면에서 정의한 Titlebar 이름이다.

### 4.2 TITLEBAR가 중요한 이유

초급자는 제목을 단순 장식으로 생각하기 쉽다.  
하지만 실무 화면에서는 제목이 현재 화면의 목적과 모드를 설명하는 중요한 정보이다.

| 제목 예시 | 사용자가 이해하는 의미 |
|---|---|
| 사용자 생성 | 신규 데이터를 입력하는 화면 |
| 사용자 변경 | 기존 데이터를 수정하는 화면 |
| 사용자 조회 | 변경 없이 확인하는 화면 |
| 주문 상세 조회 | 특정 주문의 상세 정보를 보는 화면 |

제목이 명확하지 않으면 사용자는 현재 화면이 조회인지 변경인지, 생성인지 승인인지 혼동할 수 있다.

## 5. Function Code란 무엇인가?

### 5.1 쉬운 정의

Function Code는 사용자가 화면에서 어떤 액션을 실행했는지 나타내는 코드이다.

예를 들어 다음처럼 정의할 수 있다.

| 사용자 액션 | Function Code 예시 |
|---|---|
| 저장 버튼 클릭 | SAVE |
| 뒤로가기 | BACK |
| 종료 | EXIT |
| 취소 | CANC |
| 조회 | DISP |
| 신규 생성 | NEW |
| 삭제 | DEL |

사용자가 버튼을 누르면 해당 Function Code가 OK Code 필드에 전달되고, PAI에서 그 값을 읽어 분기한다.

### 5.2 OK_CODE와 Function Code의 관계

화면에는 OK Code를 받을 필드가 필요하다. 보통 전역 변수로 다음처럼 선언한다.

```abap
DATA ok_code TYPE sy-ucomm.
DATA save_ok TYPE sy-ucomm.
```

PAI에서는 OK Code 값을 복사하고 초기화하는 패턴을 자주 사용한다.

```abap
MODULE user_command_0100 INPUT.
  save_ok = ok_code.
  CLEAR ok_code.

  CASE save_ok.
    WHEN 'SAVE'.
      PERFORM save_data.
    WHEN 'BACK' OR 'EXIT' OR 'CANC'.
      LEAVE TO SCREEN 0.
  ENDCASE.
ENDMODULE.
```

`SAVE_OK`로 복사하는 이유는 후속 처리 중 `OK_CODE`가 바뀌거나 다시 사용될 수 있기 때문이다.  
초급 단계에서는 “PAI 시작 시 OK Code를 별도 변수에 보관하고 원본을 초기화하는 패턴”으로 기억하면 된다.

## 6. SET PF-STATUS의 기본 사용 위치

`SET PF-STATUS`는 일반적으로 PBO 모듈에서 실행한다.

Screen Flow Logic 예시는 다음과 같다.

```abap
PROCESS BEFORE OUTPUT.
  MODULE status_0100.

PROCESS AFTER INPUT.
  MODULE user_command_0100.
```

PBO 모듈 구현 예시는 다음과 같다.

```abap
MODULE status_0100 OUTPUT.
  SET PF-STATUS 'S100'.
  SET TITLEBAR 'T100'.
ENDMODULE.
```

이 흐름의 의미는 다음이다.

```text
화면이 사용자에게 표시되기 전에
→ 어떤 버튼과 메뉴를 보여줄지 설정하고
→ 어떤 제목을 보여줄지 설정한다.
```

따라서 `SET PF-STATUS`와 `SET TITLEBAR`는 PAI가 아니라 PBO에서 설정하는 것이 일반적인 흐름이다.

## 7. Menu Painter와 GUI Status

### 7.1 Menu Painter란?

Menu Painter는 SAP GUI에서 GUI Status, Menu Bar, Application Toolbar, Function Key, Titlebar 등을 정의하는 도구이다.

대표 트랜잭션은 다음과 같다.

```text
SE41
```

또는 SE80/Object Navigator에서 프로그램 객체 아래의 GUI Status와 Title을 관리할 수 있다.

### 7.2 GUI Status 생성 흐름

기본 생성 흐름은 다음과 같다.

```text
1. SE80 또는 SE41 실행
2. Program 이름 입력
3. GUI Status 생성
4. Status 이름 입력: S100
5. Short Text 입력
6. Function Code 정의
7. Application Toolbar 또는 Function Key에 버튼 연결
8. 저장 및 활성화
```

교육용 화면에서는 다음 GUI Status를 예시로 사용할 수 있다.

```text
Program: SAPMZJHY_DYNPRO_DEMO
GUI Status: S100
Titlebar: T100
```

### 7.3 기본 Function Code 설계 예시

| Function Code | 용도 | 권장 처리 위치 |
|---|---|---|
| SAVE | 저장 | PAI의 `CASE save_ok` |
| BACK | 이전 화면으로 복귀 | PAI |
| EXIT | 프로그램 종료 또는 상위 화면 복귀 | PAI |
| CANC | 취소 | PAI |
| DISP | 조회 | PAI 또는 별도 처리 모듈 |
| CHNG | 변경 모드 전환 | PAI |

Function Code는 단순 문자값처럼 보이지만, 사용자 액션과 프로그램 로직을 연결하는 계약이다.  
따라서 이름을 일관되게 설계해야 한다.

## 9. PF-STATUS의 동적 제어

### 9.1 왜 동적 제어가 필요한가?

화면의 모드에 따라 버튼을 다르게 보여줘야 하는 경우가 있다.

예를 들어 다음과 같은 상황을 생각할 수 있다.

| 화면 모드 | 필요한 버튼 |
|---|---|
| 조회 모드 | BACK, EXIT, CHNG |
| 변경 모드 | SAVE, BACK, CANC |
| 생성 모드 | SAVE, CANC |

모든 모드에서 모든 버튼을 보여주면 사용자가 잘못된 액션을 수행할 수 있다.

### 9.2 Excluding 방식의 기본 감각

ABAP에서는 `SET PF-STATUS`에서 특정 Function Code를 제외하는 방식으로 버튼을 숨기거나 비활성화할 수 있다.

개념 예시는 다음과 같다.

```abap
DATA lt_exclude TYPE TABLE OF sy-ucomm.

APPEND 'SAVE' TO lt_exclude.

SET PF-STATUS 'S100' EXCLUDING lt_exclude.
```

이 예시는 조회 모드에서는 `SAVE` 버튼을 제외하는 식으로 사용할 수 있다.

초급 단계에서는 동적 버튼 제어를 깊게 구현하기보다 다음 원칙만 기억하면 된다.

```text
PF-STATUS는 고정적으로만 쓰는 것이 아니라,
화면 모드에 따라 일부 Function Code를 제외하여 다르게 보이게 할 수 있다.
```

## 10. TITLEBAR의 동적 문구

Titlebar는 고정 제목뿐 아니라 파라미터를 이용해 일부 값을 동적으로 표시할 수 있다.

예를 들어 사용자 ID를 제목에 표시하고 싶을 수 있다.

```abap
SET TITLEBAR 'T100' WITH gv_user_id.
```

Titlebar 정의에서 `&1` 같은 자리표시자를 사용하면 `WITH` 값이 제목에 반영될 수 있다.

예시 제목 정의:

```text
사용자 &1 상세 화면
```

실행 시:

```text
사용자 U0001 상세 화면
```

이 기능은 조회 화면이나 상세 화면에서 현재 대상 데이터를 사용자에게 명확히 알려줄 때 유용하다.

## 11. 정상 흐름과 오류 흐름

### 11.1 정상 흐름

```text
1. GUI Status S100 생성
2. Titlebar T100 생성
3. Screen 0100의 PBO에서 SET PF-STATUS 'S100' 호출
4. PBO에서 SET TITLEBAR 'T100' 호출
5. 화면에 버튼과 제목이 표시됨
6. 사용자가 버튼 클릭
7. Function Code가 OK_CODE에 전달됨
8. PAI에서 CASE 문으로 Function Code 처리
9. 필요한 화면 이동 또는 메시지 처리 수행
```

### 11.2 오류 흐름 1: GUI Status가 존재하지 않음

#### 현상

화면 실행 시 PF-STATUS 관련 오류가 발생하거나 버튼이 기대대로 표시되지 않는다.

#### 원인

`SET PF-STATUS 'S100'`라고 작성했지만 실제 프로그램에 `S100` GUI Status가 생성되어 있지 않다.

#### 해결

```text
1. SE41 또는 SE80에서 해당 Program의 GUI Status 확인
2. Status 이름 철자 확인
3. GUI Status 생성 및 활성화
4. 프로그램 재실행
```

### 11.3 오류 흐름 2: Function Code와 PAI 분기값 불일치

#### 현상

버튼을 눌러도 원하는 처리가 실행되지 않는다.

#### 원인

GUI Status에는 Function Code가 `SAVE`인데, PAI에서는 `SAV` 또는 `OK_SAVE`로 분기하고 있을 수 있다.

#### 해결

GUI Status에 정의된 Function Code와 PAI의 `CASE` 값을 일치시킨다.

```abap
CASE save_ok.
  WHEN 'SAVE'.
    PERFORM save_data.
ENDCASE.
```

### 11.4 오류 흐름 3: OK_CODE 필드 누락

#### 현상

버튼 클릭 후 Function Code가 프로그램 변수에 제대로 전달되지 않는다.

#### 원인

Screen 속성에서 OK Code 필드가 지정되지 않았거나, 프로그램 전역 변수와 이름이 맞지 않을 수 있다.

#### 해결

Screen Painter에서 OK Code 필드가 `OK_CODE` 같은 전역 변수와 연결되어 있는지 확인한다.

### 11.5 오류 흐름 4: PBO가 아니라 PAI에서 SET PF-STATUS를 호출함

#### 현상

화면 버튼 구성이 기대한 시점에 반영되지 않거나, 흐름 이해가 어려워진다.

#### 원인

화면 표시 전에 적용되어야 할 GUI Status를 사용자 액션 이후의 PAI에서 설정했다.

#### 해결

`SET PF-STATUS`와 `SET TITLEBAR`는 일반적으로 PBO 모듈에 둔다.

```abap
MODULE status_0100 OUTPUT.
  SET PF-STATUS 'S100'.
  SET TITLEBAR 'T100'.
ENDMODULE.
```

### 11.6 오류 흐름 5: Function Code 초기화 누락

#### 현상

이전 버튼 액션이 다음 처리에 영향을 주는 것처럼 보인다.

#### 원인

`OK_CODE` 값을 처리 후 초기화하지 않았다.

#### 해결

PAI 초기에 값을 복사한 뒤 `OK_CODE`를 초기화한다.

```abap
save_ok = ok_code.
CLEAR ok_code.
```

## 12. 실무 적용 기준

### 12.1 GUI Status 이름 설계

교육용으로는 `S100`, `S200`처럼 Screen Number에 맞춘 이름을 사용할 수 있다.

| Screen | GUI Status | Titlebar |
|---|---|---|
| 0100 | S100 | T100 |
| 0200 | S200 | T200 |
| 0300 | S300 | T300 |

실무에서는 프로젝트 규칙에 따라 더 의미 있는 이름을 사용할 수 있다.

```text
STATUS_MAIN
STATUS_DISPLAY
STATUS_CHANGE
TITLE_MAIN
TITLE_DETAIL
```

단, 이름이 너무 길거나 일관성이 없으면 유지보수가 어려워진다.

### 12.2 Function Code 설계 원칙

Function Code는 화면 로직의 핵심 계약이므로 일관성이 중요하다.

| 원칙 | 설명 |
|---|---|
| 짧고 명확하게 | `SAVE`, `BACK`, `DISP`, `DELE` 등 |
| 화면별 중복 의미 주의 | 같은 코드가 화면마다 다른 의미를 가지지 않도록 한다. |
| PAI 분기와 일치 | GUI Status의 Function Code와 ABAP CASE 값이 같아야 한다. |
| 표준 흐름 존중 | BACK, EXIT, CANCEL 등 기본 흐름은 일관되게 처리한다. |

### 12.3 화면별 PF-STATUS 복제 남발 주의

초급자는 화면마다 GUI Status를 복사해 여러 개 만들기 쉽다.  
하지만 거의 같은 버튼 구성을 가진 Status가 여러 개로 복제되면 유지보수가 어려워진다.

나쁜 예:

```text
S100_DISPLAY
S101_DISPLAY
S102_DISPLAY
S103_DISPLAY
```

버튼 하나를 바꾸려면 여러 Status를 모두 수정해야 할 수 있다.

개선 방향:

```text
공통 Status를 재사용하고,
필요한 버튼만 EXCLUDING으로 제어한다.
```

### 12.4 PAI에 업무 로직을 과도하게 넣지 않는다

PF-STATUS와 Function Code를 배우면 PAI에서 모든 업무 처리를 직접 구현하고 싶어질 수 있다.  
하지만 실무에서는 PAI는 사용자 액션을 받아 적절한 처리 루틴으로 넘기는 역할에 가깝게 유지하는 것이 좋다.

권장 구조:

```abap
MODULE user_command_0100 INPUT.
  save_ok = ok_code.
  CLEAR ok_code.

  CASE save_ok.
    WHEN 'SAVE'.
      PERFORM save_data.
    WHEN 'BACK' OR 'EXIT' OR 'CANC'.
      PERFORM leave_screen.
  ENDCASE.
ENDMODULE.
```

이렇게 하면 PAI 모듈이 너무 길어지지 않고, 기능별 유지보수가 쉬워진다.

## 13. 미니 실습

### 13.1 실습 목표

Screen 0100에 GUI Status와 Titlebar를 적용하고, 버튼 클릭 시 Function Code를 PAI에서 처리한다.

### 13.2 실습 대상

```text
Program: SAPMZJHY_DYNPRO_DEMO
Screen: 0100
GUI Status: S100
Titlebar: T100
OK Code Field: OK_CODE
```

[추정] 실제 교육 시스템에서 프로그램명은 네이밍 규칙에 따라 다를 수 있다. 본인의 실습 프로그램명으로 대체한다.

### 13.3 실습 절차

```text
1. SE80 또는 SE41에서 Module Pool 프로그램을 연다.
2. GUI Status S100을 생성한다.
3. Application Toolbar에 SAVE 버튼을 추가한다.
4. Standard Toolbar 또는 Function Key에 BACK, EXIT, CANC를 연결한다.
5. 각 버튼에 Function Code를 지정한다.
6. Titlebar T100을 생성한다.
7. Screen 0100의 Flow Logic에 PBO/PAI 모듈이 있는지 확인한다.
8. PBO 모듈에서 SET PF-STATUS 'S100'을 호출한다.
9. PBO 모듈에서 SET TITLEBAR 'T100'을 호출한다.
10. PAI 모듈에서 OK_CODE를 CASE로 분기한다.
11. 화면을 실행하여 버튼이 정상 표시되는지 확인한다.
12. 버튼 클릭 시 기대한 메시지 또는 화면 이동이 수행되는지 확인한다.
```

### 13.4 실습 코드 예시

```abap
MODULE status_0100 OUTPUT.
  SET PF-STATUS 'S100'.
  SET TITLEBAR 'T100'.
ENDMODULE.

MODULE user_command_0100 INPUT.
  save_ok = ok_code.
  CLEAR ok_code.

  CASE save_ok.
    WHEN 'SAVE'.
      MESSAGE 'SAVE 버튼이 선택되었습니다.' TYPE 'S'.

    WHEN 'BACK' OR 'EXIT' OR 'CANC'.
      LEAVE TO SCREEN 0.

    WHEN OTHERS.
      MESSAGE '처리되지 않은 Function Code입니다.' TYPE 'I'.
  ENDCASE.
ENDMODULE.
```

## 15. 평가 문제

### 15.1 객관식

#### Q1. `SET PF-STATUS`의 주된 목적은 무엇인가?

A. 화면 필드 값을 DB에 저장한다.  
B. 화면의 GUI Status, 즉 버튼·메뉴·기능키 구성을 적용한다.  
C. 프로그램을 활성화한다.  
D. Internal Table을 정렬한다.

정답: B

#### Q2. `SET TITLEBAR`는 일반적으로 어디에서 호출하는가?

A. PBO 모듈  
B. PAI 모듈의 마지막 줄  
C. DDIC Domain 정의  
D. SE16N 조회 조건

정답: A

#### Q3. 사용자가 버튼을 눌렀을 때 PAI에서 분기 기준으로 사용하는 값은 무엇인가?

A. Data Element  
B. Function Code  
C. Package  
D. Size Category

정답: B

### 15.2 단답형

#### Q1. PF-STATUS와 TITLEBAR의 차이를 설명하시오.

모범 답안:  
PF-STATUS는 화면에서 사용할 버튼, 메뉴, 기능키와 Function Code 구성을 적용하는 것이고, TITLEBAR는 화면 상단 제목을 설정하는 것이다.

#### Q2. OK_CODE 값을 `SAVE_OK` 같은 별도 변수에 복사한 뒤 초기화하는 이유는 무엇인가?

모범 답안:  
사용자가 실행한 Function Code를 안정적으로 보관하고, 후속 처리에서 이전 OK_CODE 값이 남아 다음 처리에 영향을 주는 것을 방지하기 위해서이다.

#### Q3. 버튼을 눌렀는데 PAI 분기가 실행되지 않을 때 확인할 항목을 쓰시오.

모범 답안:  
GUI Status의 Function Code와 PAI CASE 값이 일치하는지, Screen의 OK Code 필드가 올바르게 지정되어 있는지, PAI Flow Logic에 해당 MODULE이 연결되어 있는지 확인한다.

## 16. 초급자 핵심 요약

## 17. 후속 학습 연결

다음 모듈 `THEORY-14-M07 — Custom Control과 Container 개념`에서는 Dynpro 화면 안에 ALV Grid 같은 Control을 배치하기 위한 기본 개념을 다룬다.

이번 모듈과 다음 모듈의 연결은 다음과 같다.

```text
PF-STATUS / TITLEBAR
→ 화면의 명령과 제목 구성

Custom Control / Container
→ 화면 안에 복합 UI 요소 배치
```

이후 Grid ALV 학습에서는 다음 흐름이 중요해진다.

```text
Screen 0100 생성
→ Custom Control 배치
→ PBO에서 Container와 ALV 객체 생성
→ PF-STATUS로 사용자 버튼 제공
→ PAI에서 Function Code 처리
```

즉, PF-STATUS와 TITLEBAR는 단독 기능이 아니라, Dynpro 기반 UI 프로그램의 사용자 액션 제어 기반이다.
