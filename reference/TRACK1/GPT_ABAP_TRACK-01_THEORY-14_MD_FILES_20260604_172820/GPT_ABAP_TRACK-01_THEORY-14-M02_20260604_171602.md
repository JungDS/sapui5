## 2. Screen Number란 무엇인가?

### 2.1 기본 정의

Screen Number는 Module Pool 프로그램 안에서 하나의 Dynpro 화면을 식별하는 번호이다.

예를 들어 프로그램 `SAPMZJHY_DEMO` 안에 다음 화면들이 있을 수 있다.

| Screen Number | 용도 |
|---:|---|
| 0100 | 메인 화면 |
| 0200 | 상세 화면 |
| 0300 | 팝업 또는 보조 화면 |

이때 `0100`, `0200`, `0300`이 Screen Number이다.

ABAP 코드에서 특정 화면을 호출할 때는 다음과 같이 사용한다.

```abap
CALL SCREEN 0100.
```

이 코드는 현재 프로그램 컨텍스트에서 Screen 0100을 호출하라는 의미이다.  
단, 이번 모듈에서는 `CALL SCREEN`의 세부 실행 흐름보다 Screen Number와 Screen Painter의 구조를 이해하는 데 집중한다.

---

## 3. Screen Number가 중요한 이유

Screen Number는 단순한 숫자가 아니다.  
Dynpro 개발에서 화면 흐름과 유지보수성을 결정하는 중요한 식별자이다.

| 이유 | 설명 |
|---|---|
| 화면 식별 | 하나의 Module Pool 프로그램 안에서 여러 화면을 구분한다. |
| 화면 전환 | `CALL SCREEN`, Next Screen, `LEAVE TO SCREEN` 등과 연결된다. |
| PBO/PAI 연결 | 특정 Screen의 Flow Logic에 PBO/PAI Module이 연결된다. |
| 유지보수 | 개발자들이 화면 흐름을 번호 체계로 파악한다. |
| Grid ALV 선행지식 | Custom Control과 Container를 배치할 화면이 필요하다. |

실무에서는 보통 다음처럼 번호에 의미를 부여한다.

```text
0100: Main Screen
0200: Detail Screen
0300: Popup / Sub Screen 후보
9000: Test 또는 임시 화면
```

단, 번호 체계는 프로젝트마다 다를 수 있으므로 고객사 개발 표준을 따른다.

## 4. Screen Number와 Program의 관계

Screen Number는 독립적으로 존재하지 않는다.  
항상 어떤 프로그램에 소속되어 있다.

```text
Program: SAPMZJHY_DEMO
  ├─ Screen 0100
  ├─ Screen 0200
  └─ Screen 0300
```

같은 `0100`이라는 Screen Number라도 프로그램이 다르면 다른 화면이다.

```text
SAPMZJHY_DEMO 0100
SAPMZORDER_UI 0100
SAPMZCARR_ALV 0100
```

따라서 Screen을 말할 때는 실무적으로 다음 정보를 함께 확인해야 한다.

```text
Program Name + Screen Number
```

예:

```text
SAPMZJHY_DEMO / Screen 0100
```

## 5. Screen Painter란 무엇인가?

Screen Painter는 SAP GUI에서 Dynpro 화면을 설계하는 도구이다.

Screen Painter에서 개발자는 다음을 수행한다.

| 작업 | 설명 |
|---|---|
| Screen 생성 | 특정 Program에 Screen Number를 생성한다. |
| Screen Attribute 설정 | Screen Type, Next Screen, Description 등을 설정한다. |
| Layout 설계 | Text, Input Field, Push Button, Custom Control 등을 배치한다. |
| Element List 관리 | 화면 요소의 이름과 속성을 확인한다. |
| Flow Logic 편집 | PBO/PAI 흐름과 Module을 연결한다. |
| Activate | Screen을 활성화하여 런타임에서 사용할 수 있게 한다. |

Screen Painter는 단순한 “화면 그리기 도구”가 아니다.  
화면의 시각적 배치, 화면 필드, Flow Logic, 프로그램 Module 연결이 함께 관리되는 Classic UI 개발 도구이다.

## 6. Screen Painter 접근 방법

### 6.1 SE51 직접 접근

Screen Painter를 직접 실행하는 대표 트랜잭션은 `SE51`이다.

```text
Transaction Code: SE51
```

일반 흐름은 다음과 같다.

```text
SE51 실행
→ Program 입력
→ Screen Number 입력
→ Create 또는 Change
```

예:

```text
Program: SAPMZJHY_DEMO
Screen Number: 0100
```

### 6.2 SE80 Object Navigator 접근

실무에서는 `SE80` Object Navigator에서 Module Pool 프로그램을 열고 Screen을 생성하는 방식도 많이 사용한다.

```text
SE80
→ Program 선택
→ SAPMZJHY_DEMO 입력
→ Screens 노드
→ Create
```

### 6.3 접근 방식 비교

| 접근 방식 | 장점 | 사용 상황 |
|---|---|---|
| SE51 | Screen Painter에 직접 진입 | Screen만 빠르게 확인하거나 수정할 때 |
| SE80 | 프로그램 구조와 Screen을 함께 확인 | Module Pool 전체 구조를 관리할 때 |
| ADT | 최신 개발 환경과 연계 | Classic Dynpro는 SAP GUI 기능 의존도가 여전히 큼 |

SAP GUI 800 기준으로 Screen Painter 실습은 `SE51` 또는 `SE80`이 가장 직관적이다.

## 8. Screen Attribute 이해

Screen을 생성하면 Attribute 화면에서 여러 속성을 입력하거나 확인한다.  
초급 단계에서는 다음 항목을 중심으로 이해한다.

| Attribute | 의미 |
|---|---|
| Short Description | Screen의 목적을 설명하는 짧은 텍스트 |
| Screen Type | Normal, Subscreen 등 화면 유형 |
| Next Screen | 현재 Screen 처리 후 이어질 Screen |
| Cursor Position | 기본 커서 위치 관련 설정 |
| Hold Data | 화면 데이터 유지 관련 설정 |
| Own GUI Status | Screen별 GUI Status 사용 여부와 연결될 수 있음 |

### 8.1 Short Description

좋은 설명은 화면의 목적을 바로 이해하게 한다.

좋은 예:

```text
Main Screen for Dynpro Demo
Flight List Main Screen
Carrier Detail Screen
```

나쁜 예:

```text
test
screen
abc
```

### 8.2 Screen Type

초급 실습에서는 일반적으로 `Normal` Screen을 사용한다.

| Screen Type | 초급 설명 |
|---|---|
| Normal | 일반 Dynpro 화면 |
| Subscreen | 다른 Screen 안에 포함될 수 있는 보조 화면 |
| Modal Dialog Box | 팝업성 화면 |

이번 모듈에서는 `Normal`만 다룬다.  
Subscreen과 Dialog Box는 Screen Programming 심화에서 다루는 것이 적절하다.

### 8.3 Next Screen

Next Screen은 현재 Screen이 끝난 뒤 이어질 Screen을 의미한다.

예:

| 설정 | 의미 |
|---|---|
| 0100 | 현재 화면으로 다시 돌아오는 흐름 |
| 0200 | 다음 상세 화면으로 이동 |
| 0 | 화면 체인 종료 성격으로 이해 가능 |

초급자는 Next Screen을 무심코 설정하면 화면이 의도치 않게 반복되거나 종료되지 않는 상황이 생길 수 있음을 기억해야 한다.

## 9. Layout Editor의 역할

Layout Editor는 Screen Painter에서 실제 화면 요소를 배치하는 영역이다.

여기서 개발자는 다음 요소를 배치할 수 있다.

| 요소 | 설명 | 자세한 학습 |
|---|---|---|
| Text Field | 고정 텍스트 표시 | M03 |
| Input Field | 사용자 입력 필드 | M03 |
| Push Button | 버튼과 Function Code 연결 | M03, M05 |
| Frame | 화면 영역 구분 | M03 |
| Custom Control | ALV/Grid Control 배치 영역 | M07 |

이번 모듈에서는 Layout Editor의 위치와 역할만 이해하고, 개별 요소의 상세 속성은 다음 모듈에서 다룬다.

### 9.1 Layout Editor에서 중요한 감각

Layout Editor는 “보기 좋게 배치하는 도구”이기도 하지만, ABAP 프로그램과 연결되는 Screen Field를 관리하는 도구이기도 하다.

예를 들어 Input Field를 `GV_CARRID`라는 이름으로 만들면, 같은 이름의 ABAP 전역 변수가 필요할 수 있다.

```abap
DATA gv_carrid TYPE s_carr_id.
```

즉, Layout의 필드 이름은 ABAP 프로그램의 전역 데이터와 연결될 수 있다.

이번 모듈에서는 이 연결 감각만 이해하고, 실제 입력 필드 상세는 다음 모듈에서 다룬다.

## 10. Element List

Element List에서 확인할 수 있는 대표 정보는 다음과 같다.

| 정보 | 설명 |
|---|---|

| Text | 화면에 보이는 텍스트 |

## 11. Flow Logic과 Screen Painter의 관계

Screen Painter는 Layout만 관리하지 않는다.  
각 Screen에는 Flow Logic이 있다.

가장 기본적인 Flow Logic 구조는 다음과 같다.

```abap
PROCESS BEFORE OUTPUT.
  MODULE status_0100.

PROCESS AFTER INPUT.
  MODULE user_command_0100.
```

이 구조는 다음 의미를 가진다.

| 구문 | 의미 |
|---|---|
| PROCESS BEFORE OUTPUT | 화면이 사용자에게 표시되기 전에 실행 |
| MODULE status_0100 | PBO 시점에 실행할 ABAP Module |
| PROCESS AFTER INPUT | 사용자가 입력하거나 버튼을 누른 뒤 실행 |
| MODULE user_command_0100 | PAI 시점에 실행할 ABAP Module |

PBO와 PAI의 상세 처리는 `THEORY-14-M04`, `THEORY-14-M05`에서 각각 다룬다.  
이번 모듈에서는 “Screen은 Layout과 Flow Logic을 함께 가진다”는 점이 핵심이다.

## 12. Screen Number와 Flow Logic Module 네이밍

실무에서는 Screen Number와 Module 이름을 맞춰 읽기 쉽게 만드는 경우가 많다.

예:

| Screen | PBO Module | PAI Module |
|---:|---|---|
| 0100 | `status_0100` | `user_command_0100` |
| 0200 | `status_0200` | `user_command_0200` |

이런 네이밍은 필수 문법은 아니지만 유지보수에 도움이 된다.

```abap
MODULE status_0100 OUTPUT.
  SET PF-STATUS 'S0100'.
  SET TITLEBAR 'T0100'.
ENDMODULE.

MODULE user_command_0100 INPUT.
  CASE sy-ucomm.
    WHEN 'BACK' OR 'EXIT' OR 'CANC'.
      LEAVE PROGRAM.
  ENDCASE.
ENDMODULE.
```

위 코드는 전체 동작을 이해하기 위한 예고 수준이다.  
`SET PF-STATUS`, `SET TITLEBAR`, `SY-UCOMM`은 후속 모듈에서 더 자세히 다룬다.

## 14. 활성화와 Generate

Screen을 저장한 뒤에는 활성화해야 한다.

활성화 과정에서는 다음 대상이 함께 영향을 받을 수 있다.

| 대상 | 설명 |
|---|---|
| Screen Definition | Screen Attribute와 Layout |
| Flow Logic | PBO/PAI 구문 |
| ABAP Module | Flow Logic에서 참조하는 Module |
| Program | Module Pool 프로그램 전체 활성 상태 |

초급자가 자주 겪는 오류는 다음이다.

```text
Flow Logic에 MODULE status_0100을 썼지만,
ABAP 코드에 MODULE status_0100 OUTPUT이 없다.
```

이 경우 Screen 활성화 또는 프로그램 활성화 과정에서 오류가 발생할 수 있다.

해결 방향은 다음이다.

```abap
MODULE status_0100 OUTPUT.
ENDMODULE.

MODULE user_command_0100 INPUT.
ENDMODULE.
```

처음에는 빈 Module로 만들어도 된다.  
이후 M04/M05에서 실제 로직을 채운다.

---

## 15. Screen을 만들었는데 실행되지 않는 이유

초급자가 흔히 하는 질문은 다음이다.

```text
Screen 0100을 만들고 활성화했는데 왜 실행이 안 되나요?
```

이유는 간단하다.  
Screen은 화면 정의일 뿐이고, 실행 진입점이 필요하다.

대표적인 실행 방식은 다음과 같다.

| 방식 | 설명 |
|---|---|
| Transaction Code | Module Pool 프로그램과 Screen을 연결해 실행 |
| CALL SCREEN | ABAP 코드에서 특정 Screen 호출 |
| Dialog Transaction | 프로그램과 Screen Number를 연결하는 트랜잭션 |

이번 모듈에서는 Screen Painter 생성이 핵심이므로 트랜잭션 생성은 깊게 다루지 않는다.  
하지만 실무적으로는 Screen을 만들었다고 자동 실행되는 것이 아니라는 점을 반드시 이해해야 한다.

## 16. 오류 상황과 해결

### 16.1 Screen Number 중복

| 항목 | 내용 |
|---|---|
| 현상 | Screen 생성 시 이미 존재한다는 메시지 |
| 원인 | 같은 Program에 동일 Screen Number가 이미 있음 |
| 해결 | 기존 Screen을 Display/Change하거나 다른 번호 사용 |

### 16.2 Program Type 오류

| 항목 | 내용 |
|---|---|
| 현상 | Screen 생성 또는 실행 흐름이 예상과 다름 |
| 원인 | Module Pool이 아닌 프로그램에 잘못 생성하려고 함 |
| 해결 | Program Type M의 Module Pool 프로그램을 기준으로 생성 |

### 16.3 Layout 저장 누락

| 항목 | 내용 |
|---|---|
| 현상 | Layout에 배치한 요소가 사라짐 |
| 원인 | Layout Editor에서 Save하지 않았거나 Screen 전체 Save 누락 |
| 해결 | Layout 저장 후 Screen 저장, 이후 Activate 수행 |

### 16.4 Flow Logic Module 미정의

| 항목 | 내용 |
|---|---|
| 현상 | `MODULE ...` 관련 오류 발생 |
| 원인 | Flow Logic에 작성한 Module이 ABAP 코드에 없음 |
| 해결 | `MODULE name OUTPUT/INPUT.` 구문으로 Module 구현 |

### 16.5 Next Screen 설정 오류

| 항목 | 내용 |
|---|---|
| 현상 | 화면이 계속 반복되거나 종료되지 않음 |
| 원인 | Next Screen 또는 PAI 종료 로직이 부적절함 |
| 해결 | Next Screen, `LEAVE SCREEN`, `LEAVE PROGRAM` 흐름을 함께 점검 |

### 16.6 Screen Field와 ABAP 변수 이름 불일치

| 항목 | 내용 |
|---|---|
| 현상 | 화면 입력값이 프로그램 변수와 연결되지 않음 |
| 원인 | Screen Field 이름과 ABAP 전역 데이터 이름이 다름 |
| 해결 | 화면 필드명과 ABAP 전역 변수명을 일치시키거나 Dictionary 참조 사용 |

이 항목은 다음 모듈에서 Input Field를 다룰 때 더 자세히 학습한다.

## 17. 실무 설계 기준

### 17.1 Screen Number 체계

프로젝트에서 화면 번호를 임의로 만들면 유지보수가 어려워진다.  
가능하면 화면 흐름과 번호가 어느 정도 대응되도록 설계한다.

예:

| 번호대 | 용도 예시 |
|---:|---|
| 0100 | Main Screen |
| 0200 | Detail Screen |
| 0300 | Create/Change Screen |
| 0400 | Popup성 보조 화면 |
| 9000 | 테스트 또는 임시 화면 |

[추정] 실제 프로젝트에서는 고객사 개발 표준에 따라 번호 체계가 다를 수 있다.

### 17.2 Layout은 미리 복잡하게 만들지 않는다

초급 또는 초기 설계 단계에서 화면 요소를 너무 많이 배치하면 PBO/PAI 로직이 빠르게 복잡해진다.

권장 흐름은 다음이다.

```text
1. Screen 생성
2. 최소 Text 배치
3. PBO/PAI 빈 Module 연결
4. 실행 흐름 확인
5. Input Field 추가
6. Button 추가
7. PF-STATUS와 Function Code 연결
8. Custom Control 또는 Grid ALV 확장
```

### 17.3 화면 이름과 요소 이름을 명확히 한다

나쁜 예:

```text
SCREEN 100
FIELD1
FIELD2
BTN1
```

좋은 예:

```text
SCREEN 0100 — Main Flight Selection Screen
GV_CARRID
GV_CONNID
BTN_SEARCH
```

### 17.4 화면 설계와 비즈니스 로직을 분리한다

Dynpro 개발에서는 화면 이벤트와 업무 로직이 쉽게 섞인다.  
초급 단계부터 다음 원칙을 의식해야 한다.

```text
PBO/PAI Module은 화면 흐름을 제어한다.
복잡한 업무 로직은 FORM, Function Module, Class Method 등으로 분리한다.
```

OO ABAP을 학습한 뒤에는 화면 이벤트에서 Service Class를 호출하는 방식으로 구조화할 수 있다.

## 18. Grid ALV와의 연결

THEORY-14는 Grid ALV의 선행 Section이다.

Grid ALV를 화면에 표시하려면 보통 다음이 필요하다.

| 구성 | 역할 |
|---|---|
| Screen Number | ALV를 표시할 Dynpro 화면 |
| Custom Control | ALV가 들어갈 화면 영역 |
| `CL_GUI_CUSTOM_CONTAINER` | Custom Control과 ABAP 객체 연결 |
| `CL_GUI_ALV_GRID` | Grid ALV 객체 |
| PBO Module | ALV 초기 생성 또는 Refresh |
| PAI Module | 사용자 명령 처리 |

이번 모듈의 Screen Number와 Screen Painter는 그 첫 단계이다.

```text
Screen 0100 생성
→ Layout에 Custom Control 배치
→ PBO에서 Container 생성
→ ALV Grid 생성
→ SET_TABLE_FOR_FIRST_DISPLAY 호출
```

Custom Control은 M07에서, Grid ALV는 다음 Section에서 다룬다.

## 20. 평가 문제

### 20.1 객관식

#### Q1. Screen Number에 대한 설명으로 가장 적절한 것은?

A. SAP Client를 식별하는 번호이다.  
B. Module Pool 프로그램 안의 Dynpro 화면을 식별하는 번호이다.  
C. ABAP 변수의 길이를 나타내는 번호이다.  
D. Transport Request 번호이다.

**정답:** B

#### Q2. Screen Painter의 주요 역할이 아닌 것은?

A. Layout 설계  
B. Screen Attribute 설정  
C. Flow Logic 관리  
D. Open SQL 성능 튜닝

**정답:** D

#### Q3. Screen을 생성하고 활성화했지만 실행되지 않는 가장 기본적인 이유는?

A. Screen은 실행 진입점이 아니기 때문이다.  
B. Screen Number는 항상 9999여야 하기 때문이다.  
C. Module Pool은 화면을 가질 수 없기 때문이다.  
D. Screen Painter는 SE11에서만 실행되기 때문이다.

**정답:** A

### 20.2 서술형

#### Q1. Program Name과 Screen Number를 함께 확인해야 하는 이유를 설명하시오.

**모범 답안:**  
Screen Number는 특정 프로그램 안에서 화면을 식별하는 번호이다. 같은 0100이라도 프로그램이 다르면 서로 다른 화면이므로, 실무에서는 Program Name과 Screen Number를 함께 확인해야 정확한 화면을 식별할 수 있다.

#### Q2. Layout Editor와 Element List의 차이를 설명하시오.

**모범 답안:**  
Layout Editor는 화면 요소를 시각적으로 배치하는 영역이고, Element List는 배치된 요소의 이름, 타입, 길이, 입력 가능 여부, Function Code 등 속성을 표 형태로 확인하고 관리하는 영역이다.

#### Q3. Next Screen 설정을 주의해야 하는 이유를 설명하시오.

**모범 답안:**  
Next Screen은 현재 화면 처리 후 이어질 화면을 결정하므로 잘못 설정하면 화면이 의도치 않게 반복되거나 종료되지 않을 수 있다. PAI의 화면 종료 로직과 함께 점검해야 한다.

## 21. 강사용 설명 포인트

강의에서는 다음 메시지를 강조한다.

```text
Screen Painter는 화면을 그리는 도구이지만,
실제로는 Layout, Element List, Flow Logic, ABAP Module 연결을 함께 관리하는 도구이다.
```

초급자가 가장 많이 놓치는 지점은 다음이다.

| 오해 | 교정 |
|---|---|
| Screen Number는 아무 숫자나 쓰면 된다. | 번호 체계는 유지보수성과 화면 흐름 이해에 중요하다. |
| Layout만 만들면 실행된다. | 실행하려면 Transaction 또는 CALL SCREEN 같은 진입점이 필요하다. |
| Flow Logic은 나중에 봐도 된다. | 최소 PBO/PAI 구조는 Screen 생성 시 함께 이해해야 한다. |
| Screen Field 이름은 대충 지어도 된다. | ABAP 전역 데이터와 연결될 수 있으므로 명확해야 한다. |

## 22. 후속 모듈 연결

이번 모듈에서는 화면의 식별자와 설계 도구를 다루었다.

다음 모듈에서는 실제 화면 요소를 하나씩 배치한다.

```text
THEORY-14-M02 Screen Number와 Screen Painter
→ THEORY-14-M03 Input Field / Text Field / Push Button
→ THEORY-14-M04 PBO 처리 흐름
→ THEORY-14-M05 PAI 처리 흐름
→ THEORY-14-M06 PF-STATUS와 TITLEBAR
→ THEORY-14-M07 Custom Control과 Container 개념
```

특히 M07의 Custom Control은 Grid ALV로 넘어가기 위한 핵심 선행 지식이다.  
따라서 M02에서 만든 Screen 0100은 이후 화면 요소와 Custom Control을 배치하는 기본 무대가 된다.

## 23. 핵심 요약

```text
Screen Number는 Module Pool 프로그램 안의 Dynpro 화면을 식별하는 번호이다.
Screen은 Program Name과 Screen Number의 조합으로 식별하는 것이 안전하다.
Screen Painter는 Screen Attribute, Layout, Element List, Flow Logic을 관리한다.
Layout Editor는 화면 요소를 배치하고, Element List는 요소 속성을 관리한다.
Screen을 만들고 활성화해도 실행 진입점이 없으면 바로 실행되지 않는다.
Screen 0100은 이후 Input Field, Button, PBO/PAI, Custom Control 학습의 기준 화면이 된다.
```
