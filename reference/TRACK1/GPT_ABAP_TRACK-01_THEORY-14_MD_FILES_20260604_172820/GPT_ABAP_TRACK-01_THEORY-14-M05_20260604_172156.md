## 0. 이 문서의 학습 범위

이 문서는 `THEORY-14-M05 — PAI 처리 흐름`만 다룬다.

이번 모듈은 Module Pool / Dynpro 학습에서 **사용자 입력 이후의 처리 흐름**을 이해하는 단계이다.  
이전 모듈 `THEORY-14-M04`에서는 화면이 표시되기 전에 수행되는 **PBO(Process Before Output)** 흐름을 다루었다.  
이번 모듈에서는 사용자가 화면에서 값을 입력하거나 버튼을 누른 뒤, ABAP 프로그램이 그 입력을 어떻게 받아 처리하는지 다룬다.

핵심 흐름은 다음과 같다.

```text
사용자가 화면에 값 입력 또는 버튼 클릭
→ SAP GUI가 Function Code와 화면 필드 값을 서버로 전달
→ Dynpro Runtime이 PAI 이벤트 시작
→ PROCESS AFTER INPUT 블록 실행
→ MODULE ... INPUT 모듈 실행
→ 입력값 검증, Function Code 분기, 다음 화면 결정
```

이 문서에서는 `PF-STATUS`, `TITLEBAR`, `Custom Control`은 깊게 다루지 않는다.  
해당 내용은 후속 모듈인 `THEORY-14-M06`, `THEORY-14-M07`에서 다룬다.

## 3. PAI란 무엇인가?

PAI는 **Process After Input**의 약어이다.  
말 그대로 사용자의 입력 이후에 처리되는 Dynpro 이벤트이다.

사용자가 화면에서 다음과 같은 동작을 수행하면 PAI가 실행된다.

| 사용자 동작 | PAI 실행 여부 |
|---|---|
| Enter 입력 | 실행 |
| Push Button 클릭 | 실행 |
| Toolbar 버튼 클릭 | 실행 |
| Back / Exit / Cancel 같은 Function 선택 | 실행 |
| 화면 필드에 값 입력 후 Enter | 실행 |
| 단순히 화면이 처음 표시되는 순간 | 실행 아님. 이때는 PBO |

PAI는 사용자가 화면과 상호작용한 뒤 프로그램이 반응하는 지점이다.

예를 들어 사용자 관리 화면에서 사용자가 `SAVE` 버튼을 누르면 PAI에서 다음을 수행할 수 있다.

```text
1. 사용자가 입력한 USER_ID, USER_NAME, STATUS 값을 받는다.
2. 필수값이 비어 있는지 검증한다.
3. STATUS가 허용 값인지 확인한다.
4. SAVE Function Code에 따라 저장 로직을 호출한다.
5. 성공 메시지를 출력하거나 다음 화면으로 이동한다.
```

---

## 4. PBO와 PAI의 차이

PBO와 PAI는 Dynpro 처리 흐름의 양쪽 축이다.

| 구분 | PBO | PAI |
|---|---|---|
| 전체 이름 | Process Before Output | Process After Input |
| 실행 시점 | 화면이 표시되기 전 | 사용자가 입력/버튼 동작 후 |
| 주요 목적 | 화면 출력 준비 | 입력 처리와 액션 처리 |
| 대표 구문 | `PROCESS BEFORE OUTPUT` | `PROCESS AFTER INPUT` |
| 대표 모듈 | `MODULE ... OUTPUT` | `MODULE ... INPUT` |
| 예시 작업 | 필드 속성 제어, 기본값 설정, 제목/상태 설정 | 입력 검증, OK_CODE 분기, 저장/조회/화면 이동 |
| 학습 모듈 | THEORY-14-M04 | THEORY-14-M05 |

흐름을 그림으로 표현하면 다음과 같다.

```text
CALL SCREEN 0100
      ↓
PBO
      ↓
Screen Display
      ↓
User Input / Button
      ↓
PAI
      ↓
Next Screen or Same Screen
```

Dynpro는 이 사이클을 반복한다.  
따라서 화면이 한 번 표시되고 끝나는 것이 아니라, 사용자의 액션에 따라 PBO와 PAI가 계속 왕복될 수 있다.

## 5. PROCESS AFTER INPUT 블록

Screen Flow Logic에는 보통 다음과 같은 두 블록이 있다.

```abap
PROCESS BEFORE OUTPUT.
  MODULE status_0100.

PROCESS AFTER INPUT.
  MODULE user_command_0100.
```

여기서 `PROCESS AFTER INPUT` 아래에 정의된 모듈들이 PAI 시점에 실행된다.

### 5.1 기본 구조

```abap
PROCESS AFTER INPUT.
  MODULE user_command_0100.
```

이 구문은 다음 의미를 가진다.

```text
사용자가 화면에서 입력 또는 버튼 동작을 수행한 뒤
ABAP 프로그램의 user_command_0100 INPUT 모듈을 실행한다.
```

### 5.2 ABAP 프로그램 쪽 구현

Flow Logic에서 `MODULE user_command_0100.`를 선언하면 ABAP Include 또는 Main Program 안에 다음 모듈이 있어야 한다.

```abap
MODULE user_command_0100 INPUT.
  " 사용자 입력 이후 처리
ENDMODULE.
```

`INPUT` 키워드가 중요하다.  
PBO 모듈은 `OUTPUT`, PAI 모듈은 `INPUT`으로 구현한다.

---

## 6. MODULE ... INPUT

`MODULE ... INPUT`은 PAI에서 실행되는 ABAP 처리 블록이다.

예시는 다음과 같다.

```abap
MODULE user_command_0100 INPUT.

  CASE gv_ok_code.
    WHEN 'BACK' OR 'EXIT' OR 'CANC'.
      LEAVE PROGRAM.

    WHEN 'SAVE'.
      PERFORM save_data.

    WHEN 'DISP'.
      PERFORM display_data.

    WHEN OTHERS.
      MESSAGE '알 수 없는 기능입니다.' TYPE 'I'.
  ENDCASE.

ENDMODULE.
```

이 모듈은 일반적으로 다음 책임을 가진다.

| 책임 | 설명 |
|---|---|
| Function Code 확인 | 사용자가 어떤 버튼을 눌렀는지 판별 |
| 입력값 검증 | 필수값, 형식, 업무 규칙 검증 |
| 처리 로직 호출 | 저장, 조회, 삭제, 계산 등의 하위 로직 호출 |
| 화면 이동 | 다음 화면, 이전 화면, 프로그램 종료 결정 |
| 메시지 처리 | 성공, 오류, 경고, 정보 메시지 출력 |

## 7. Function Code와 OK_CODE

### 7.1 Function Code란?

Function Code는 사용자가 어떤 기능을 요청했는지 나타내는 코드이다.

예를 들어 화면 버튼에 다음 Function Code를 부여할 수 있다.

| 버튼 | Function Code |
|---|---|
| 저장 | SAVE |
| 조회 | DISP |
| 뒤로 | BACK |
| 취소 | CANC |
| 종료 | EXIT |

사용자가 버튼을 누르면 해당 Function Code가 OK Code 필드에 전달된다.

### 7.2 OK_CODE 필드

Screen Painter에서 OK Code 필드를 전역 변수와 연결한다.  
일반적으로 다음과 같은 변수를 사용한다.

```abap
DATA gv_ok_code TYPE sy-ucomm.
DATA gv_save_ok TYPE sy-ucomm.
```

PAI에서는 보통 OK Code를 별도 변수에 복사한 뒤 초기화한다.

```abap
MODULE user_command_0100 INPUT.

  gv_save_ok = gv_ok_code.
  CLEAR gv_ok_code.

  CASE gv_save_ok.
    WHEN 'SAVE'.
      PERFORM save_data.
    WHEN 'BACK'.
      LEAVE TO SCREEN 0.
  ENDCASE.

ENDMODULE.
```

### 7.3 왜 OK_CODE를 복사하고 초기화하는가?

초급자는 다음 코드를 번거롭게 느낄 수 있다.

```abap
gv_save_ok = gv_ok_code.
CLEAR gv_ok_code.
```

하지만 이 패턴은 실무에서 자주 사용된다.

이유는 다음과 같다.

| 이유 | 설명 |
|---|---|
| 이전 Function Code 잔존 방지 | 이전 버튼 코드가 다음 PAI에 영향을 주는 상황을 줄인다. |
| 처리 안정성 | 현재 PAI에서 처리할 코드를 별도로 보관한다. |
| 디버깅 편의 | 현재 액션과 화면 필드 상태를 분리해 확인하기 쉽다. |
| 유지보수성 | 후속 로직에서 `gv_save_ok`를 기준으로 명확히 분기할 수 있다. |

## 8. 화면 필드 값 전달 흐름

Dynpro에서 화면 필드와 ABAP 변수는 이름 기반으로 연결되는 경우가 많다.

예를 들어 Screen Painter에 다음 필드가 있다고 하자.

```text
GV_USER_ID
GV_USER_NAME
GV_STATUS
```

ABAP 프로그램에도 동일한 이름의 전역 변수가 있어야 한다.

```abap
DATA gv_user_id   TYPE zde_jhy_user_id.
DATA gv_user_name TYPE zde_jhy_user_name.
DATA gv_status    TYPE zde_jhy_status.
```

사용자가 화면에 값을 입력하고 Enter 또는 버튼을 누르면 PAI 시점에 화면 값이 ABAP 변수로 전달된다.

흐름은 다음과 같다.

```text
화면 Input Field
→ 사용자 입력
→ Enter 또는 버튼
→ PAI 시작
→ 화면 필드 값이 ABAP 전역 변수에 반영
→ MODULE ... INPUT 실행
```

따라서 PAI 모듈 안에서는 사용자가 입력한 값을 ABAP 변수로 읽을 수 있다.

```abap
MODULE user_command_0100 INPUT.

  IF gv_user_id IS INITIAL.
    MESSAGE '사용자 ID를 입력하세요.' TYPE 'E'.
  ENDIF.

ENDMODULE.
```

## 9. 입력 검증 기본 흐름

PAI에서 가장 중요한 작업 중 하나는 입력 검증이다.

### 9.1 필수값 검증

예를 들어 사용자 ID가 필수라면 다음처럼 확인할 수 있다.

```abap
MODULE check_input_0100 INPUT.

  IF gv_user_id IS INITIAL.
    MESSAGE '사용자 ID는 필수입니다.' TYPE 'E'.
  ENDIF.

ENDMODULE.
```

Flow Logic에서는 다음처럼 분리할 수 있다.

```abap
PROCESS AFTER INPUT.
  MODULE check_input_0100.
  MODULE user_command_0100.
```

이렇게 하면 먼저 입력값을 검증하고, 그 다음 Function Code를 처리한다.

### 9.2 상태값 검증

상태값이 `A`, `I`, `B` 중 하나여야 한다면 다음처럼 검증할 수 있다.

```abap
MODULE check_status_0100 INPUT.

  IF gv_status <> 'A'
 AND gv_status <> 'I'
 AND gv_status <> 'B'.
    MESSAGE '상태는 A, I, B 중 하나여야 합니다.' TYPE 'E'.
  ENDIF.

ENDMODULE.
```

다만 상태값 검증은 앞선 DDIC 학습에서 Domain Fixed Value, Foreign Key, Search Help 등으로 일부 보완할 수 있다.  
실무에서는 DDIC 검증과 프로그램 검증의 역할을 구분해야 한다.

## 10. MESSAGE TYPE E와 PAI

PAI에서 `MESSAGE ... TYPE 'E'`를 사용하면 일반적으로 오류 메시지를 출력하고 사용자가 현재 화면에서 값을 수정할 수 있도록 한다.

예시:

```abap
IF gv_user_id IS INITIAL.
  MESSAGE '사용자 ID를 입력하세요.' TYPE 'E'.
ENDIF.
```

초급자 관점에서 중요한 점은 다음이다.

```text
PAI에서 오류 메시지를 발생시키면
사용자는 같은 화면에서 입력값을 수정하는 흐름으로 돌아간다.
```

단, 메시지 타입과 화면 필드 처리 방식은 Dynpro Flow Logic, CHAIN/ENDCHAIN, FIELD 구문 사용 여부에 따라 더 세밀하게 달라질 수 있다.  
이 문서에서는 기본 `MODULE ... INPUT` 수준의 검증만 다룬다.

---

## 11. CHAIN / ENDCHAIN은 언제 쓰는가?

PAI에서는 특정 필드 그룹을 묶어 검증하기 위해 `CHAIN ... ENDCHAIN`을 사용할 수 있다.

예시는 다음과 같다.

```abap
PROCESS AFTER INPUT.
  CHAIN.
    FIELD gv_user_id.
    FIELD gv_status.
    MODULE check_required_fields_0100.
  ENDCHAIN.

  MODULE user_command_0100.
```

이 구문은 특정 필드들과 검증 모듈을 연결한다.  
초급 단계에서는 다음 정도로 이해하면 충분하다.

| 구문 | 초급자 설명 |
|---|---|
| FIELD | 어떤 화면 필드와 관련된 검증인지 지정 |
| CHAIN | 여러 필드를 하나의 검증 그룹으로 묶음 |
| MODULE | 해당 필드 또는 그룹에 대한 검증 로직 실행 |
| ENDCHAIN | 검증 그룹 종료 |

이 주제는 Dynpro 입력 검증을 정밀하게 다룰 때 더 깊어진다.  
이번 모듈에서는 “PAI에서 입력 검증을 구조화할 수 있는 표준 구문이 있다”는 정도만 기억한다.

## 12. 기본 예제: PAI Function Code 처리

### 12.1 Screen Flow Logic

Screen `0100`의 Flow Logic을 다음처럼 구성한다.

```abap
PROCESS BEFORE OUTPUT.
  MODULE status_0100.

PROCESS AFTER INPUT.
  MODULE check_input_0100.
  MODULE user_command_0100.
```

### 12.2 ABAP 전역 데이터

```abap
PROGRAM sapmzjhy_dynpro.

DATA gv_user_id   TYPE zde_jhy_user_id.
DATA gv_user_name TYPE zde_jhy_user_name.
DATA gv_status    TYPE zde_jhy_status.
DATA gv_ok_code   TYPE sy-ucomm.
DATA gv_save_ok   TYPE sy-ucomm.
```

### 12.3 PBO 모듈

PBO는 이전 모듈의 영역이므로 최소 형태만 둔다.

```abap
MODULE status_0100 OUTPUT.
  " 후속 M06에서 PF-STATUS와 TITLEBAR를 자세히 다룬다.
ENDMODULE.
```

### 12.4 PAI 검증 모듈

```abap
MODULE check_input_0100 INPUT.

  IF gv_user_id IS INITIAL.
    MESSAGE '사용자 ID를 입력하세요.' TYPE 'E'.
  ENDIF.

  IF gv_status IS INITIAL.
    MESSAGE '상태를 입력하세요.' TYPE 'E'.
  ENDIF.

ENDMODULE.
```

### 12.5 PAI 명령 처리 모듈

```abap
MODULE user_command_0100 INPUT.

  gv_save_ok = gv_ok_code.
  CLEAR gv_ok_code.

  CASE gv_save_ok.
    WHEN 'SAVE'.
      MESSAGE '저장 기능이 요청되었습니다.' TYPE 'S'.

    WHEN 'DISP'.
      MESSAGE '조회 기능이 요청되었습니다.' TYPE 'I'.

    WHEN 'BACK'.
      LEAVE TO SCREEN 0.

    WHEN 'EXIT' OR 'CANC'.
      LEAVE PROGRAM.

    WHEN OTHERS.
      MESSAGE '지원하지 않는 기능입니다.' TYPE 'I'.
  ENDCASE.

ENDMODULE.
```

이 예제의 목적은 실제 저장 로직 완성이 아니라 PAI의 기본 흐름을 이해하는 것이다.

## 13. 화면 이동과 PAI

PAI에서는 사용자의 액션에 따라 다음 화면을 결정할 수 있다.

대표 구문은 다음과 같다.

| 구문 | 의미 |
|---|---|
| `LEAVE TO SCREEN 0` | 이전 화면 또는 호출한 화면으로 돌아가는 흐름 |
| `LEAVE PROGRAM` | 프로그램 종료 |
| `SET SCREEN nnnn` | 다음 화면 번호 지정 |
| `LEAVE SCREEN` | 현재 PAI 후 지정된 다음 화면으로 이동 |

초급자는 처음부터 모든 화면 이동 구문을 세밀하게 구분하려고 하기보다, 다음 두 가지를 먼저 익히면 된다.

```abap
LEAVE TO SCREEN 0.
LEAVE PROGRAM.
```

예시:

```abap
CASE gv_save_ok.
  WHEN 'BACK'.
    LEAVE TO SCREEN 0.
  WHEN 'EXIT' OR 'CANC'.
    LEAVE PROGRAM.
ENDCASE.
```

## 14. 실무적으로 PAI에 무엇을 넣어야 하는가?

PAI는 사용자의 입력에 반응하는 지점이지만, 모든 업무 로직을 PAI 모듈 안에 길게 작성하는 것은 좋지 않다.

### 14.1 PAI에 직접 두기 좋은 로직

| 로직 | 설명 |
|---|---|
| OK_CODE 복사 및 초기화 | 현재 사용자 액션 식별 |
| 단순 입력 검증 호출 | 필수값, 형식 검증 |
| Function Code 분기 | SAVE, BACK, EXIT 등 |
| 하위 FORM 또는 Method 호출 | 실제 업무 로직 위임 |
| 화면 이동 결정 | 다음 화면, 종료 흐름 |

### 14.2 PAI에 길게 넣지 않는 것이 좋은 로직

| 로직 | 이유 |
|---|---|
| 긴 DB 처리 | 화면 이벤트와 업무 로직이 강하게 결합됨 |
| 복잡한 계산 로직 | 테스트와 재사용이 어려워짐 |
| 대량 데이터 처리 | 화면 응답성이 나빠질 수 있음 |
| 여러 화면 공통 로직 | 중복 발생 가능 |
| 하드코딩된 메시지/코드 | 유지보수성 저하 |

권장 구조는 다음과 같다.

```abap
MODULE user_command_0100 INPUT.

  gv_save_ok = gv_ok_code.
  CLEAR gv_ok_code.

  CASE gv_save_ok.
    WHEN 'SAVE'.
      PERFORM validate_input.
      PERFORM save_data.
    WHEN 'BACK'.
      LEAVE TO SCREEN 0.
  ENDCASE.

ENDMODULE.
```

더 현대적인 코드 구조에서는 FORM 대신 Class Method를 호출할 수도 있다.  
다만 이번 Section은 Classic Dynpro 기초이므로 FORM 기반 예제도 학습 목적상 충분하다.

## 15. 정상 흐름과 오류 흐름

### 15.1 정상 흐름

```text
1. 화면 0100이 표시된다.
2. 사용자가 USER_ID, USER_NAME, STATUS를 입력한다.
3. 사용자가 SAVE 버튼을 누른다.
4. OK_CODE에 SAVE가 전달된다.
5. PAI가 실행된다.
6. check_input_0100에서 필수값을 확인한다.
7. user_command_0100에서 SAVE 분기로 이동한다.
8. 저장 처리 또는 저장 메시지를 수행한다.
9. 필요 시 같은 화면을 다시 표시하거나 다음 화면으로 이동한다.
```

### 15.2 오류 흐름: 필수값 누락

```text
1. 사용자가 USER_ID를 비워둔다.
2. SAVE 버튼을 누른다.
3. PAI가 실행된다.
4. check_input_0100에서 USER_ID가 INITIAL인지 확인한다.
5. MESSAGE TYPE E가 발생한다.
6. 사용자는 같은 화면에서 USER_ID를 다시 입력한다.
```

### 15.3 오류 흐름: 알 수 없는 Function Code

```text
1. 버튼의 Function Code가 ABAP CASE문에 정의되어 있지 않다.
2. PAI에서 WHEN OTHERS로 이동한다.
3. 정보 메시지를 출력하거나 무시된다.
```

이 경우 Screen Painter에서 버튼의 Function Code와 ABAP 코드의 `CASE` 분기값을 함께 확인해야 한다.

## 16. 디버깅 포인트

PAI를 디버깅할 때는 다음 지점을 확인한다.

| 확인 지점 | 확인 내용 |
|---|---|
| Flow Logic | `PROCESS AFTER INPUT`에 모듈이 등록되어 있는가 |
| Breakpoint | `MODULE ... INPUT` 안에 Breakpoint를 걸었는가 |
| OK_CODE | 버튼 클릭 후 Function Code가 들어오는가 |
| 화면 필드 변수 | 사용자 입력값이 전역 변수에 반영되었는가 |
| MESSAGE 처리 | 오류 메시지 이후 화면 흐름이 의도대로 돌아가는가 |
| CLEAR OK_CODE | 이전 Function Code가 남아 있지 않은가 |

초급자가 특히 자주 놓치는 것은 `OK_CODE` 필드 자체가 Screen Painter에서 제대로 지정되지 않은 경우이다.  
버튼 Function Code는 있어도 OK Code 필드 연결이 잘못되어 있으면 ABAP 변수에 기대한 값이 들어오지 않을 수 있다.

## 17. 자주 발생하는 오류와 해결

### 17.1 MODULE 이름 불일치

#### 현상

Flow Logic에는 다음처럼 되어 있다.

```abap
MODULE user_command_0100.
```

하지만 ABAP에는 다음 모듈이 없다.

```abap
MODULE user_commnad_0100 INPUT.
```

#### 원인

모듈 이름 오타 또는 Include 누락이다.

#### 해결

Flow Logic의 MODULE 이름과 ABAP `MODULE ... INPUT` 이름을 정확히 맞춘다.

---

### 17.2 INPUT/OUTPUT 키워드 혼동

#### 현상

PAI에서 호출할 모듈을 `OUTPUT`으로 구현했다.

```abap
MODULE user_command_0100 OUTPUT.
ENDMODULE.
```

#### 문제

PAI 모듈은 `INPUT`으로 구현해야 한다.

#### 해결

```abap
MODULE user_command_0100 INPUT.
ENDMODULE.
```

---

### 17.3 OK_CODE가 비어 있음

#### 현상

버튼을 눌러도 `gv_ok_code`가 INITIAL이다.

#### 가능한 원인

| 원인 | 설명 |
|---|---|
| Screen의 OK Code 필드가 지정되지 않음 | 화면 속성에서 OK Code 필드 연결 누락 |
| 버튼 Function Code 미입력 | Push Button 속성에서 Function Code 누락 |
| 변수명 불일치 | ABAP 변수와 Screen OK Code 필드명이 다름 |

#### 해결

Screen Painter에서 다음을 확인한다.

```text
1. 화면의 OK Code 필드 이름
2. Push Button의 Function Code
3. ABAP 프로그램의 전역 변수 선언
```

---

### 17.4 MESSAGE TYPE E 이후 진행이 막힘

#### 현상

오류 메시지가 발생한 뒤 계속 같은 화면에서 벗어나지 못한다.

#### 원인

필수값 검증 조건이 계속 참이거나, 사용자가 수정할 수 없는 필드를 검증하고 있을 수 있다.

#### 해결

검증 조건과 화면 필드 입력 가능 여부를 함께 확인한다.  
필요한 경우 PBO에서 해당 필드가 비활성화되지 않았는지도 확인한다.

---

### 17.5 Function Code 잔존

#### 현상

한 번 누른 버튼의 동작이 다음 PAI에서도 반복되는 것처럼 보인다.

#### 원인

OK Code를 처리한 뒤 초기화하지 않았을 가능성이 있다.

#### 해결

PAI 초반에 다음 패턴을 적용한다.

```abap
gv_save_ok = gv_ok_code.
CLEAR gv_ok_code.
```

## 18. 실습 과제

### 18.1 기본 실습

Screen `0100`에 다음 필드를 배치한다.

| 화면 요소 | 이름 / Function Code |
|---|---|
| Input Field | GV_USER_ID |
| Input Field | GV_USER_NAME |
| Input Field | GV_STATUS |
| Push Button | SAVE |
| Push Button | BACK |

Flow Logic은 다음처럼 작성한다.

```abap
PROCESS BEFORE OUTPUT.
  MODULE status_0100.

PROCESS AFTER INPUT.
  MODULE check_input_0100.
  MODULE user_command_0100.
```

ABAP 프로그램에는 다음 PAI 모듈을 작성한다.

```abap
MODULE check_input_0100 INPUT.

  IF gv_user_id IS INITIAL.
    MESSAGE '사용자 ID를 입력하세요.' TYPE 'E'.
  ENDIF.

ENDMODULE.

MODULE user_command_0100 INPUT.

  gv_save_ok = gv_ok_code.
  CLEAR gv_ok_code.

  CASE gv_save_ok.
    WHEN 'SAVE'.
      MESSAGE '저장 요청이 처리되었습니다.' TYPE 'S'.

    WHEN 'BACK'.
      LEAVE TO SCREEN 0.

    WHEN OTHERS.
      MESSAGE '지원하지 않는 기능입니다.' TYPE 'I'.
  ENDCASE.

ENDMODULE.
```

다음 오류를 일부러 만들어보고 원인을 기록한다.

## 19. 평가 문제

### 19.1 객관식

#### Q1. PAI가 실행되는 시점으로 가장 적절한 것은?

A. 화면이 사용자에게 표시되기 전  
B. 사용자가 화면에서 입력하거나 버튼을 누른 뒤  
C. 프로그램이 최초 로드되기 전  
D. ABAP Dictionary 객체가 활성화될 때  

**정답:** B

#### Q2. PAI 모듈 구현에 사용하는 키워드는?

A. `MODULE ... OUTPUT`  
B. `MODULE ... INPUT`  
C. `FORM ... OUTPUT`  
D. `SCREEN ... INPUT`  

**정답:** B

#### Q3. OK_CODE를 처리한 뒤 초기화하는 주된 이유는?

A. 화면 필드를 모두 삭제하기 위해  
B. 이전 Function Code가 다음 처리에 남아 영향을 주는 것을 줄이기 위해  
C. DB 테이블을 자동 저장하기 위해  
D. PBO를 비활성화하기 위해  

**정답:** B

### 19.2 단답형

#### Q1. PBO와 PAI의 차이를 설명하시오.

**모범 답안:**  
PBO는 화면이 표시되기 전에 실행되어 화면 출력 준비를 담당하고, PAI는 사용자가 화면에서 값을 입력하거나 버튼을 누른 뒤 실행되어 입력 검증과 Function Code 처리를 담당한다.

#### Q2. `PROCESS AFTER INPUT` 블록의 역할은 무엇인가?

**모범 답안:**  
사용자 입력 이후 실행할 PAI 모듈을 정의하는 Screen Flow Logic 영역이다. 이 블록에 등록된 `MODULE ... INPUT` 모듈이 PAI 시점에 실행된다.

#### Q3. Function Code가 들어오지 않을 때 확인해야 할 항목은 무엇인가?

**모범 답안:**  
Screen의 OK Code 필드가 지정되어 있는지, Push Button에 Function Code가 설정되어 있는지, ABAP 전역 변수명이 화면 속성과 일치하는지 확인해야 한다.

## 20. 실무 관점 정리

PAI는 Dynpro에서 사용자의 입력을 실제 프로그램 로직으로 연결하는 핵심 지점이다.  
하지만 PAI 자체에 모든 비즈니스 로직을 길게 작성하면 프로그램이 빠르게 복잡해진다.

실무적으로는 다음 구조가 바람직하다.

```text
PAI
→ OK_CODE 확인
→ 입력 검증 호출
→ 업무 처리 FORM 또는 Method 호출
→ 메시지와 화면 이동 처리
```

즉, PAI는 “모든 일을 직접 하는 곳”이 아니라 “사용자 액션을 받아 적절한 처리 단위로 연결하는 Controller 역할”에 가깝다.

## 22. 핵심 요약

```text
PAI는 Process After Input의 약어이다.
PAI는 사용자가 화면에서 입력하거나 버튼을 누른 뒤 실행된다.
Screen Flow Logic의 PROCESS AFTER INPUT 블록에 PAI 모듈을 등록한다.
PAI 모듈은 MODULE ... INPUT으로 구현한다.
OK_CODE는 사용자가 어떤 기능을 선택했는지 알려준다.
OK_CODE는 처리 후 복사·초기화하는 패턴이 자주 사용된다.
PAI에서는 입력 검증, Function Code 분기, 화면 이동 처리를 수행한다.
PAI에 모든 업무 로직을 길게 넣기보다 별도 FORM 또는 Method로 분리하는 것이 좋다.
```
