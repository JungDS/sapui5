## 0. 이 문서의 학습 범위

이 문서는 `THEORY-21-M06 — Service Definition / Service Binding`만 다룬다.

이번 모듈의 핵심 키워드는 다음 세 가지이다.

| 키워드 | 의미 |
|---|---|
| Service Definition | RAP/CDS 기반 데이터 모델 중 외부 서비스로 노출할 Projection View를 선언하는 개발 객체 |
| Service Binding | Service Definition을 특정 프로토콜과 소비 시나리오에 연결하고, 실제 서비스 엔드포인트를 활성화하는 객체 |
| OData V4 | RAP 서비스에서 현대적인 UI/API 소비를 위해 주로 사용하는 OData 프로토콜 버전 |

이번 모듈은 이전 모듈에서 만든 RAP 구성 요소를 외부 소비 가능한 서비스로 공개하는 단계이다.

```text
ZI_* Interface View
  → ZC_* Projection View
  → Behavior Definition / Behavior Implementation
  → Service Definition
  → Service Binding
  → OData V4 Preview / Fiori Elements / API Consumer
```

중요한 점은 Service Definition과 Service Binding이 “데이터 모델을 새로 만드는 단계”가 아니라는 것이다.  
이 단계는 이미 설계된 RAP Business Object를 **어떤 범위로, 어떤 방식으로, 어떤 소비자에게 노출할 것인가**를 결정하는 서비스 공개 단계이다.

## 3. RAP 서비스 노출의 전체 구조

RAP에서 OData 서비스를 만들 때 객체의 계층은 일반적으로 다음과 같이 나뉜다.

```text
Database Table
  ↓
Interface View Entity: ZI_*
  ↓
Projection View Entity: ZC_*
  ↓
Behavior Definition / Behavior Projection
  ↓
Service Definition
  ↓
Service Binding
  ↓
OData V4 Endpoint
```

각 계층의 책임은 다르다.

| 계층 | 대표 객체 | 책임 |
|---|---|---|
| Persistence | `ZT_*` | 실제 데이터 저장 |
| Interface View | `ZI_*` | Business Object의 기본 데이터 모델 |
| Projection View | `ZC_*` | 소비자에게 보여줄 필드와 의미 조정 |
| Behavior | `BDEF`, `BIMP` | CRUD 및 비즈니스 행위 정의/구현 |
| Service Definition | `ZUI_*` 또는 `ZSD_*` | 외부로 노출할 Entity 집합 선언 |
| Service Binding | `ZUI_*_O4` 등 | OData V4 등 특정 프로토콜과 연결 |

> [추정] 객체 Prefix는 프로젝트 규칙에 따라 달라질 수 있다. 이 문서에서는 교육용 예시로 `ZI_*`, `ZC_*`, `ZUI_*`를 사용한다.

## 4. Service Definition이란 무엇인가?

Service Definition은 RAP/CDS에서 **어떤 Projection View를 서비스로 노출할 것인지** 선언하는 객체이다.

예를 들어 `ZC_JHY_TRAVEL` Projection View를 외부 서비스로 공개하려면 Service Definition에서 다음과 같이 선언할 수 있다.

```abap
@EndUserText.label: 'Travel Service Definition'
define service ZUI_JHY_TRAVEL {
  expose ZC_JHY_TRAVEL as Travel;
}
```

이 코드는 다음 의미를 가진다.

| 코드 요소 | 의미 |
|---|---|
| `define service` | Service Definition 객체를 정의한다. |
| `ZUI_JHY_TRAVEL` | 서비스 정의 객체 이름이다. |
| `expose ZC_JHY_TRAVEL` | Projection View를 서비스에 노출한다. |
| `as Travel` | 외부 서비스에서 사용할 Entity Set 이름을 지정한다. |

Service Definition은 실제 HTTP Endpoint를 직접 만들지는 않는다.  
Endpoint는 Service Binding에서 만들어지고 활성화된다.

---

## 5. Service Binding이란 무엇인가?

Service Binding은 Service Definition을 실제 소비 가능한 서비스로 연결하는 객체이다.

Service Definition이 “무엇을 노출할 것인가”라면, Service Binding은 다음 질문에 답한다.

```text
어떤 프로토콜로 노출할 것인가?
어떤 소비 시나리오로 사용할 것인가?
서비스를 활성화했는가?
Preview 또는 Metadata 확인이 가능한가?
```

ADT에서 Service Binding을 생성할 때 일반적으로 Binding Type을 선택한다.  
RAP 입문 과정에서는 다음 두 가지를 많이 접한다.

| Binding Type | 용도 |
|---|---|
| OData V4 - UI | Fiori Elements UI Preview, UI 기반 소비에 적합 |
| OData V4 - Web API | 외부 API 소비 또는 시스템 간 호출 시나리오에 적합 |

> [추정] 사용 가능한 Binding Type의 명칭과 선택지는 SAP S/4HANA 릴리스, ABAP Platform 버전, SAP BTP ABAP Environment 여부, 시스템 설정에 따라 달라질 수 있다.

## 6. Service Definition과 Service Binding의 차이

두 객체는 이름이 비슷해서 초급자가 자주 혼동한다.

| 구분 | Service Definition | Service Binding |
|---|---|---|
| 핵심 질문 | 무엇을 노출할 것인가? | 어떻게 노출할 것인가? |
| 주요 대상 | Projection View Entity | Service Definition |
| 대표 문법/작업 | `define service ... expose ...` | ADT에서 Binding 생성/Activate/Publish |
| 프로토콜 결정 | 하지 않음 | OData V4 등 Binding Type 선택 |
| Endpoint 생성 | 직접 생성하지 않음 | 실제 서비스 접근 지점 생성 |
| Preview | 직접 Preview 중심은 아님 | Preview/Metadata 확인 가능 |

쉽게 말하면 다음과 같다.

```text
Service Definition = 서비스 목록 설계도
Service Binding    = 서비스 실행/공개 설정
```

## 7. 최소 예제 시나리오

이번 모듈에서는 교육용 Travel Business Object를 예시로 사용한다.

> [추정] 아래 예제는 이전 모듈에서 `ZI_JHY_TRAVEL`, `ZC_JHY_TRAVEL`, Behavior Definition이 이미 생성되어 활성화되어 있다고 가정한다.

### 7.1 전제 객체

| 객체 | 예시 이름 | 역할 |
|---|---|---|
| Database Table | `ZTJHY_TRAVEL` | Travel 데이터 저장 |
| Interface View | `ZI_JHY_TRAVEL` | Root Business Object 모델 |
| Projection View | `ZC_JHY_TRAVEL` | 외부 소비용 Projection |
| Behavior Definition | `ZI_JHY_TRAVEL` / `ZC_JHY_TRAVEL` 관련 BDEF | CRUD 및 동작 정의 |
| Service Definition | `ZUI_JHY_TRAVEL` | 노출 Entity 선언 |
| Service Binding | `ZUI_JHY_TRAVEL_O4` | OData V4 서비스 공개 |

### 7.2 예시 Interface View `ZI_*`

Service Definition 문서의 핵심은 아니지만, 전체 흐름 이해를 위해 최소 전제 View를 확인한다.

```abap
@EndUserText.label: 'Travel Interface View'
define root view entity ZI_JHY_TRAVEL
  as select from ztjhy_travel
{
  key travel_id      as TravelID,
      agency_id      as AgencyID,
      customer_id    as CustomerID,
      begin_date     as BeginDate,
      end_date       as EndDate,
      booking_fee    as BookingFee,
      currency_code  as CurrencyCode,
      overall_status as OverallStatus
}
```

Interface View는 Business Object 내부 모델에 가깝다.  
이 View는 DB Table을 기반으로 하고, 후속 Projection View에서 소비자 친화적인 노출 계층으로 정리된다.

### 7.3 예시 Projection View `ZC_*`

```abap
@EndUserText.label: 'Travel Projection View'
@AccessControl.authorizationCheck: #NOT_REQUIRED
@Metadata.allowExtensions: true
define root view entity ZC_JHY_TRAVEL
  as projection on ZI_JHY_TRAVEL
{
  key TravelID,
      AgencyID,
      CustomerID,
      BeginDate,
      EndDate,
      BookingFee,
      CurrencyCode,
      OverallStatus
}
```

Projection View는 Service Definition에 노출하기 적합한 계층이다.  
외부 소비자에게 보여줄 필드, UI Annotation 확장 가능성, Consumption 관점의 이름을 정리할 수 있다.

> 주의: 실제 RAP 서비스에서는 Projection Behavior Definition도 함께 고려해야 한다. 이 문서에서는 Service Definition / Service Binding 학습 범위를 벗어나지 않도록 최소 연결 관점만 다룬다.

## 8. Service Definition 생성

### 8.1 ADT 생성 절차

ADT 기준 일반 절차는 다음과 같다.

```text
1. ABAP Package 선택
2. New → Other ABAP Repository Object
3. Business Services 또는 Service Definition 검색
4. Service Definition 선택
5. 이름 입력: ZUI_JHY_TRAVEL
6. Description 입력: Travel Service Definition
7. 생성 완료 후 CDS Service Definition 코드 작성
8. Activate
```

### 8.2 Service Definition 코드

```abap
@EndUserText.label: 'Travel Service Definition'
define service ZUI_JHY_TRAVEL {
  expose ZC_JHY_TRAVEL as Travel;
}
```

### 8.3 여러 Entity 노출 예시

Root와 Child Entity가 있는 Composition 모델에서는 여러 Projection View를 함께 노출할 수 있다.

```abap
@EndUserText.label: 'Travel Service Definition'
define service ZUI_JHY_TRAVEL {
  expose ZC_JHY_TRAVEL        as Travel;
  expose ZC_JHY_BOOKING       as Booking;
  expose ZC_JHY_BOOKING_SUPPL as BookingSupplement;
}
```

단, 초급 실습에서는 Root Entity 하나부터 노출하는 것을 권장한다.  
Composition, Navigation, Draft, Fiori Elements Object Page는 후속 심화에서 확장하는 편이 좋다.

## 9. Service Binding 생성

### 9.1 ADT 생성 절차

Service Definition이 활성화되면 Service Binding을 생성한다.

```text
1. Package 선택
2. New → Other ABAP Repository Object
3. Business Services 또는 Service Binding 검색
4. Service Binding 선택
5. 이름 입력: ZUI_JHY_TRAVEL_O4
6. Description 입력: Travel OData V4 UI Binding
7. Service Definition 선택: ZUI_JHY_TRAVEL
8. Binding Type 선택: OData V4 - UI 또는 OData V4 - Web API
9. Finish
10. Activate
11. Publish 또는 Service 활성화
12. Preview 실행
```

### 9.2 Binding 이름 설계

권장 이름은 프로젝트 규칙에 따라 달라질 수 있지만, 교육용으로는 다음과 같은 규칙을 사용할 수 있다.

| 객체 | 예시 | 설명 |
|---|---|---|
| Service Definition | `ZUI_JHY_TRAVEL` | UI/API 노출용 Service Definition |
| OData V4 UI Binding | `ZUI_JHY_TRAVEL_O4` | OData V4 Binding임을 표현 |
| Web API Binding | `ZAPI_JHY_TRAVEL_O4` | API 성격을 분리하고 싶을 때 사용 |

> [추정] 실제 프로젝트에서는 `ZUI_*`, `ZSD_*`, `ZAPI_*` 등 Prefix 규칙이 고객사마다 다를 수 있다. 중요한 것은 Service Definition과 Binding의 관계를 이름만 보고 추적할 수 있게 만드는 것이다.

## 10. OData V4 UI Binding과 Web API Binding

RAP에서 OData V4 Service Binding을 만들 때 UI와 Web API의 목적을 구분해야 한다.

| 구분 | OData V4 - UI | OData V4 - Web API |
|---|---|---|
| 주요 목적 | Fiori Elements 기반 UI 소비 | 시스템 간 API 소비 |
| 주요 소비자 | Fiori Elements Preview, UI5/Fiori 앱 | 외부 시스템, API Client |
| Annotation 활용 | UI Annotation 중요 | API 계약과 Payload 중요 |
| 설계 관점 | 화면 구성, Object Page, List Report | 안정적인 API Contract |
| 변경 관리 | UI 영향 중심 | 외부 연동 영향 중심 |

초급 단계에서는 다음처럼 이해하면 된다.

```text
화면으로 확인하고 Fiori Elements Preview를 보고 싶다면 OData V4 - UI
외부 API처럼 소비할 목적이라면 OData V4 - Web API
```

단, 실제 프로젝트에서는 보안, 릴리스 정책, API 안정성, 인증 방식, 소비자 범위까지 함께 검토해야 한다.

## 11. Preview와 Metadata 확인

Service Binding을 활성화하고 Publish하면 ADT에서 Preview를 실행할 수 있다.

### 11.1 Preview 확인 항목

| 확인 항목 | 설명 |
|---|---|
| Service Binding 상태 | Active인지 확인 |
| Published 여부 | 서비스가 공개 상태인지 확인 |
| Entity 목록 | Service Definition에서 expose한 Entity가 보이는지 확인 |
| Metadata | OData Metadata가 정상 생성되는지 확인 |
| Preview 실행 | List Report 또는 Entity Preview가 열리는지 확인 |
| CRUD 가능 여부 | Behavior 설정에 따라 Create/Update/Delete 가능 여부 확인 |

### 11.2 Metadata에서 확인할 내용

OData Metadata는 서비스의 구조와 계약을 나타낸다.

초급자는 다음 정도를 확인한다.

```text
EntitySet 이름이 의도한 이름인가?
Key 필드가 제대로 노출되는가?
필드 타입이 예상과 맞는가?
Navigation Property가 있다면 의도대로 보이는가?
Action이나 Function이 있다면 노출되는가?
```

Metadata는 UI와 외부 소비자가 서비스를 이해하는 기준이므로, 단순히 Preview 화면만 보고 끝내지 않는 것이 좋다.

## 13. 오류 흐름과 해결 방법

### 13.1 Projection View가 활성화되지 않은 상태

#### 증상

Service Definition에서 `expose ZC_JHY_TRAVEL`을 작성했는데 활성화 오류가 발생한다.

#### 원인

`ZC_JHY_TRAVEL` Projection View가 존재하지 않거나 활성화되지 않았을 수 있다.

#### 해결

```text
1. ADT에서 ZC_JHY_TRAVEL 존재 여부 확인
2. Syntax Check 수행
3. Projection View Activate
4. Service Definition 재활성화
```

---

### 13.2 Interface View와 Projection View 관계 오류

#### 증상

Projection View는 존재하지만, 내부 Interface View 변경으로 인해 Projection View 활성화가 깨진다.

#### 원인

`ZI_*`의 필드명이 바뀌었거나 삭제되었는데 `ZC_*`가 여전히 이전 필드를 참조할 수 있다.

#### 해결

```text
1. ZI_* 필드 변경 이력 확인
2. ZC_* Projection 필드 목록 수정
3. Projection Behavior가 있다면 함께 확인
4. Service Definition 재활성화
```

---

### 13.3 Entity Alias 충돌

#### 증상

Service Definition에서 여러 Entity를 expose할 때 동일 Alias를 사용한다.

```abap
define service ZUI_JHY_TRAVEL {
  expose ZC_JHY_TRAVEL  as Travel;
  expose ZC_JHY_BOOKING as Travel;
}
```

#### 문제

서비스 내 Entity 이름은 소비자에게 보이는 계약이므로 중복되면 안 된다.

#### 해결

각 Entity에 명확한 Alias를 지정한다.

```abap
define service ZUI_JHY_TRAVEL {
  expose ZC_JHY_TRAVEL  as Travel;
  expose ZC_JHY_BOOKING as Booking;
}
```

---

### 13.4 Service Binding Publish 누락

#### 증상

Service Binding은 생성했지만 Preview 또는 접근이 되지 않는다.

#### 원인

Binding을 Activate만 하고 Publish하지 않았을 수 있다.

#### 해결

ADT의 Service Binding 화면에서 Publish 또는 관련 활성화 상태를 확인한다.

```text
Activate 완료 여부 확인
Publish 상태 확인
Service URL 또는 Preview 버튼 확인
```

---

### 13.5 권한 또는 인증 문제

#### 증상

Preview 또는 서비스 호출 시 권한 오류가 발생한다.

#### 원인

사용자 권한, 서비스 접근 권한, CDS Access Control, 시스템 설정이 영향을 줄 수 있다.

#### 해결

```text
1. 같은 사용자로 ADT Preview 가능한지 확인
2. 권한 오류 메시지 원문 기록
3. SU53 또는 시스템 권한 추적 확인
4. DCL/Authorization 설정 여부 확인
5. 운영 시스템에서는 보안 담당자 또는 Basis 기준에 따라 처리
```

> 주의: 교육용으로 `@AccessControl.authorizationCheck: #NOT_REQUIRED`를 사용할 수 있지만, 실무 서비스에서 권한 검증을 생략하는 것은 매우 위험할 수 있다.

---

### 13.6 UI Preview는 되지만 CRUD 버튼이 기대와 다름

#### 증상

Preview 화면은 열리지만 Create, Edit, Delete 기능이 보이지 않거나 동작하지 않는다.

#### 원인

Behavior Definition 또는 Projection Behavior에서 CRUD 권한이 정의되지 않았거나, Annotation/Capabilities가 기대와 다를 수 있다.

#### 해결

```text
1. Interface Behavior Definition에서 create/update/delete 확인
2. Projection Behavior Definition에서 use create/update/delete 확인
3. Service Binding 재활성화
4. Preview 재실행
```

이 내용은 Behavior 심화와 Fiori Elements Annotation에서 더 자세히 다룬다.

## 16. 실무 설계 기준

### 16.1 노출 범위를 최소화한다

Service Definition은 외부 소비자에게 공개되는 계약의 시작점이다.  
따라서 내부적으로 존재하는 모든 View를 그대로 노출하면 안 된다.

나쁜 예:

```text
개발 편의를 위해 모든 ZC_* View를 한 Service Definition에 노출한다.
```

좋은 예:

```text
특정 UI 또는 API 소비 시나리오에 필요한 Entity만 노출한다.
```

### 16.2 Interface View를 직접 노출하지 않는다

일반적으로 외부 소비에는 Projection View `ZC_*`를 사용하는 것이 바람직하다.

```text
ZI_* = 내부 모델 중심
ZC_* = 소비 계층 중심
```

Interface View를 직접 노출하면 내부 모델 변경이 외부 계약에 직접 영향을 줄 수 있다.

### 16.3 UI 서비스와 API 서비스를 분리한다

UI와 API는 변경 이유가 다르다.

| 구분 | 변경 이유 |
|---|---|
| UI 서비스 | 화면 요구사항, 필드 표시, Annotation 변경 |
| API 서비스 | 외부 연동 계약, Payload 안정성, 버전 관리 |

따라서 실무에서는 UI Binding과 API Binding을 분리하는 설계를 검토할 수 있다.

### 16.4 Metadata는 계약이다

OData Metadata는 단순한 기술 산출물이 아니라 소비자와의 계약이다.  
Entity 이름, Key, 필드명, 타입, Navigation, Action 등이 바뀌면 소비자 영향이 발생할 수 있다.

### 16.5 Publish 전 검토가 필요하다

운영 반영 전에는 다음을 검토해야 한다.

```text
노출 Entity가 적절한가?
민감 필드가 포함되어 있지 않은가?
권한 검증이 적용되어 있는가?
OData Metadata가 의도와 맞는가?
UI/API 소비자가 기대하는 이름과 구조인가?
```

## 17. Clean Core 관점

Clean Core에서는 표준 객체를 직접 수정하기보다, 공개된 확장 포인트와 안정적인 API, RAP 기반 확장 모델을 사용하는 것이 중요하다.

Service Definition / Binding 단계에서 Clean Core 관점은 다음과 같다.

| 관점 | 설명 |
|---|---|
| 표준 보호 | SAP 표준 객체를 직접 수정하지 않는다. |
| 확장 분리 | 고객 확장 모델을 Z/Y 네임스페이스로 명확히 분리한다. |
| API 안정성 | 외부 소비 서비스는 변경 영향이 크므로 계약처럼 관리한다. |
| 권한 준수 | 서비스 노출은 항상 권한과 보안 정책을 고려한다. |
| Released API 원칙 | ABAP Cloud 환경에서는 사용 가능한 API와 객체 범위를 준수한다. |

ABAP Cloud 원칙과 Released API는 다음 모듈 `THEORY-21-M08`에서 더 자세히 다룬다.  
이번 모듈에서는 Service를 공개하는 순간 외부 계약이 생긴다는 점에 집중한다.

## 18. 성능과 운영 관점

Service Binding으로 OData 서비스를 노출하면 UI 또는 외부 시스템이 해당 서비스를 호출할 수 있다.  
따라서 단순 Preview 성공만으로는 충분하지 않다.

### 18.1 성능 확인 포인트

| 포인트 | 설명 |
|---|---|
| Entity 필드 수 | 불필요한 필드를 과도하게 노출하지 않는다. |
| Association/Navigation | 과도한 Navigation은 성능 영향을 줄 수 있다. |
| 데이터량 | List Report에서 대량 데이터 조회 가능성을 고려한다. |
| Filter 가능성 | 주요 조회 조건을 고려해 모델과 UI를 설계한다. |
| 권한 필터 | DCL 또는 권한 조건이 성능에 미치는 영향도 확인한다. |

### 18.2 운영 확인 포인트

| 포인트 | 설명 |
|---|---|
| 서비스 활성 상태 | Binding이 Active/Published인지 확인한다. |
| Transport | Service Definition과 Binding이 같은 변경 흐름에 포함되는지 확인한다. |
| 권한 | 사용자 또는 역할에 서비스 접근 권한이 있는지 확인한다. |
| 장애 분석 | 오류 메시지, HTTP Status, Gateway/ICF 관련 로그를 확인할 수 있어야 한다. |
| 버전 관리 | 외부 API 소비자가 있는 경우 변경 정책을 별도로 관리한다. |

### 21.2 서술형

#### Q1. Service Definition과 Service Binding의 차이를 설명하시오.

**모범 답안:**  
Service Definition은 어떤 Projection View Entity를 외부 서비스로 노출할지 선언하는 객체이다. Service Binding은 해당 Service Definition을 OData V4와 같은 특정 프로토콜 및 소비 시나리오에 연결하고, 실제 서비스 활성화와 Preview/Metadata 확인을 가능하게 하는 객체이다.

#### Q2. `ZI_*`가 아니라 `ZC_*`를 Service Definition에 노출하는 이유를 설명하시오.

**모범 답안:**  
`ZI_*`는 Business Object 내부 모델에 가까우며, 내부 구조와 구현 세부사항을 포함할 수 있다. `ZC_*`는 소비 계층 Projection View로 외부 소비자에게 필요한 필드와 의미를 조정하는 계층이다. 따라서 외부 서비스 계약을 안정적으로 관리하려면 일반적으로 `ZC_*`를 노출하는 것이 적절하다.

#### Q3. Service Binding Preview는 성공했지만 Create 버튼이 보이지 않을 때 확인할 항목을 쓰시오.

**모범 답안:**  
Interface Behavior Definition에서 `create`가 허용되어 있는지, Projection Behavior에서 `use create`가 선언되어 있는지, 서비스가 재활성화되었는지, UI 관련 Annotation 또는 Capability가 기대와 맞는지 확인한다.

## 22. 실습 리뷰 체크리스트

강사는 학습자의 실습 결과를 다음 기준으로 검토한다.

| 검토 항목 | 적합 기준 |
|---|---|
| Service Definition 이름 | 프로젝트/교육용 Naming Rule을 따른다. |
| expose 대상 | `ZC_*` Projection View를 노출한다. |
| Entity Alias | 소비자가 이해하기 쉬운 이름이다. |
| Binding Type | UI/API 목적에 맞게 선택했다. |
| Activate 상태 | Service Definition과 Binding이 모두 Active이다. |
| Publish 상태 | Service Binding이 Published 상태이다. |
| Preview | Entity가 정상 표시된다. |
| 오류 기록 | 오류 메시지와 해결 과정을 기록했다. |
| 보안 고려 | 권한 검사를 무시하지 않고 실무 기준을 설명할 수 있다. |

## 23. 핵심 요약

이번 모듈에서 반드시 기억할 내용은 다음이다.

```text
Service Definition은 무엇을 노출할지 정한다.
Service Binding은 어떻게 노출할지 정한다.
RAP 서비스 노출은 일반적으로 ZC_* Projection View를 기준으로 한다.
OData V4 - UI는 Fiori Elements 소비에 적합하다.
OData V4 - Web API는 외부 API 소비 시나리오에 적합하다.
Preview 성공뿐 아니라 Metadata, 권한, 노출 범위까지 확인해야 한다.
서비스 노출은 Clean Core와 API 계약 관점에서 신중하게 관리해야 한다.
```

## 24. 후속 모듈 연결

다음 모듈은 `THEORY-21-M07 — Validation / Determination / Action 개요`이다.

이번 모듈에서 서비스 노출 흐름을 만들었다면, 다음 단계에서는 RAP Business Object가 단순 CRUD를 넘어 비즈니스 규칙과 행위를 어떻게 가지는지 학습한다.

```text
THEORY-21-M06 Service Definition / Service Binding
  → OData V4 서비스 노출

THEORY-21-M07 Validation / Determination / Action 개요
  → 입력 검증, 자동 계산, 사용자 정의 행위 개요
```

이 연결을 통해 학습자는 다음 사실을 이해하게 된다.

```text
서비스로 노출된 RAP Business Object는 단순 테이블 CRUD가 아니라,
검증·자동화·액션을 포함하는 현대식 비즈니스 객체로 확장된다.
```
