## 3. SALV 표시 제어의 큰 흐름

기본 SALV 출력은 보통 다음 흐름으로 작성한다.

```abap
DATA lo_alv TYPE REF TO cl_salv_table.

cl_salv_table=>factory(
  IMPORTING
    r_salv_table = lo_alv
  CHANGING
    t_table      = lt_data ).

lo_alv->display( ).
```

이번 모듈에서는 `display( )`를 호출하기 전에 SALV 객체의 하위 제어 객체를 가져와 설정한다.

```text
CL_SALV_TABLE 객체 생성
  → get_functions( )로 Toolbar 기능 제어
  → get_sorts( )로 정렬 제어
  → get_filters( )로 필터 제어
  → display( ) 호출
```

즉, 핵심은 다음 구조를 이해하는 것이다.

```text
lo_alv
 ├─ get_functions( ) → lo_functions
 ├─ get_sorts( )     → lo_sorts
 ├─ get_filters( )   → lo_filters
 ├─ get_columns( )   → lo_columns
 └─ display( )
```

이번 모듈에서는 `get_columns( )` 심화는 최소화하고, Sort / Filter / Function 제어에 집중한다.

## 4. 실습 데이터 모델

실습에서는 DB 테이블 의존성을 줄이기 위해 Internal Table 샘플 데이터를 직접 만든다.

### 4.1 데이터 구조

```abap
TYPES: BEGIN OF ty_flight_demo,
         carrid   TYPE c LENGTH 3,
         connid   TYPE n LENGTH 4,
         cityfrom TYPE c LENGTH 20,
         cityto   TYPE c LENGTH 20,
         seatsmax TYPE i,
         seatsocc TYPE i,
         status   TYPE c LENGTH 1,
       END OF ty_flight_demo.

DATA lt_flight TYPE STANDARD TABLE OF ty_flight_demo.
```

### 4.2 필드 의미

| 필드 | 의미 | 표시 제어 활용 |
|---|---|---|
| CARRID | 항공사 코드 | Sort / Filter 대상 |
| CONNID | 연결 번호 | Sort 대상 |
| CITYFROM | 출발 도시 | Filter 대상 |
| CITYTO | 도착 도시 | Filter 대상 |
| SEATSMAX | 총 좌석 | 표시 대상 |
| SEATSOCC | 예약 좌석 | 표시 대상 |
| STATUS | 상태 코드 | Filter 대상 |

이 구조는 실제 `SFLIGHT`와 완전히 동일한 표준 구조가 아니다. 교육용으로 정렬과 필터 실습을 쉽게 하기 위해 단순화한 구조이다.

## 6. Function 제어: `get_functions( )`

### 6.1 목적

`get_functions( )`는 SALV Toolbar에 표시되는 표준 기능 버튼을 제어하기 위해 사용한다.

기본적으로 SALV 화면에는 정렬, 필터, 합계, 내보내기, 레이아웃 등 여러 표준 기능이 제공될 수 있다. 시스템 설정과 ALV 표시 방식에 따라 보이는 버튼은 달라질 수 있지만, 개발자는 Function 객체를 통해 표준 기능을 활성화하거나 일부 기능을 조정할 수 있다.

### 6.2 기본 사용법

```abap
DATA lo_functions TYPE REF TO cl_salv_functions_list.

lo_functions = lo_alv->get_functions( ).
lo_functions->set_all( abap_true ).
```

핵심은 다음이다.

```text
lo_alv->get_functions( )로 Function 제어 객체를 얻는다.
set_all( abap_true )로 표준 기능을 활성화한다.
```

### 6.3 전체 예제 중 삽입 위치

```abap
cl_salv_table=>factory(
  IMPORTING
    r_salv_table = lo_alv
  CHANGING
    t_table      = lt_flight ).

DATA(lo_functions) = lo_alv->get_functions( ).
lo_functions->set_all( abap_true ).

lo_alv->display( ).
```

### 6.4 실무 의미

SALV를 교육용 또는 간단한 조회 리포트에 사용할 때 `set_all( abap_true )`는 자주 사용된다.

장점은 다음과 같다.

| 장점 | 설명 |
|---|---|
| 빠른 구현 | 표준 Toolbar 기능을 쉽게 활성화할 수 있다. |
| 사용자 편의 | 정렬, 필터, 내보내기 등 기본 기능을 제공할 수 있다. |
| 유지보수 단순성 | Grid ALV의 PF-STATUS 수동 제어보다 코드가 단순하다. |

주의점도 있다.

| 주의점 | 설명 |
|---|---|
| 기능 세부 제어 한계 | 복잡한 Toolbar 커스터마이징은 Grid ALV가 더 적합하다. |
| 화면 정책 | 운영 시스템에서 내보내기, 인쇄 기능 허용 여부는 보안 정책과 관련될 수 있다. |
| 사용자 혼란 | 필요 없는 기능을 모두 활성화하면 사용자가 혼란스러울 수 있다. |

## 7. Sort 제어: `get_sorts( )`

### 7.1 목적

Sort 제어는 ALV가 처음 표시될 때 기본 정렬 기준을 부여하는 기능이다.

예를 들어 항공사 코드별로 묶고, 연결 번호 순서로 정렬하려면 다음 순서로 설정할 수 있다.

```text
1차 정렬: CARRID 오름차순
2차 정렬: CONNID 오름차순
```

### 7.2 기본 사용법

```abap
DATA lo_sorts TYPE REF TO cl_salv_sorts.

lo_sorts = lo_alv->get_sorts( ).

lo_sorts->add_sort(
  columnname = 'CARRID'
  sequence   = if_salv_c_sort=>sort_up ).

lo_sorts->add_sort(
  columnname = 'CONNID'
  sequence   = if_salv_c_sort=>sort_up ).
```

### 7.3 컬럼명 대문자 주의

SALV의 `columnname`에는 Internal Table 구조의 필드명을 사용한다.

```text
좋은 예: CARRID
나쁜 예: carrid
나쁜 예: Airline
나쁜 예: CARRIER_ID
```

ABAP Dictionary 기반 구조나 로컬 TYPES 기반 구조 모두 실제 필드명과 일치해야 한다.

### 7.4 정렬 방향

대표적인 정렬 방향은 다음과 같이 이해한다.

| 정렬 방향 | 의미 |
|---|---|
| `if_salv_c_sort=>sort_up` | 오름차순 |
| `if_salv_c_sort=>sort_down` | 내림차순 |

예를 들어 좌석 점유가 높은 항목부터 보고 싶다면 다음과 같이 설정할 수 있다.

```abap
lo_sorts->add_sort(
  columnname = 'SEATSOCC'
  sequence   = if_salv_c_sort=>sort_down ).
```

### 7.5 다중 정렬

Sort를 여러 번 추가하면 추가 순서가 정렬 우선순위가 된다.

```abap
lo_sorts->add_sort( columnname = 'CARRID' sequence = if_salv_c_sort=>sort_up ).
lo_sorts->add_sort( columnname = 'STATUS' sequence = if_salv_c_sort=>sort_up ).
lo_sorts->add_sort( columnname = 'CONNID' sequence = if_salv_c_sort=>sort_up ).
```

이 경우 논리적으로는 다음과 같이 이해할 수 있다.

```text
CARRID 기준으로 먼저 정렬한다.
같은 CARRID 안에서 STATUS 기준으로 정렬한다.
같은 CARRID와 STATUS 안에서 CONNID 기준으로 정렬한다.
```

## 8. Filter 제어: `get_filters( )`

### 8.1 목적

Filter 제어는 ALV 표시 대상 데이터를 조건에 따라 제한하는 기능이다.

예를 들어 상태가 `A`인 항목만 표시하고 싶다면 `STATUS = 'A'` 조건을 적용할 수 있다.

### 8.2 기본 사용법

```abap
DATA lo_filters TYPE REF TO cl_salv_filters.

lo_filters = lo_alv->get_filters( ).

lo_filters->add_filter(
  columnname = 'STATUS'
  sign       = 'I'
  option     = 'EQ'
  low        = 'A' ).
```

여기서 각 파라미터의 의미는 다음과 같다.

| 파라미터 | 의미 | 예 |
|---|---|---|
| `columnname` | 필터 대상 컬럼명 | `STATUS` |
| `sign` | 포함/제외 | `I` = Include, `E` = Exclude |
| `option` | 비교 방식 | `EQ`, `NE`, `BT`, `CP` 등 |
| `low` | 비교 값 또는 시작 값 | `A` |
| `high` | 범위의 끝 값 | `Z` |

### 8.3 Include 조건

상태가 `A`인 행만 표시하는 예이다.

```abap
lo_filters->add_filter(
  columnname = 'STATUS'
  sign       = 'I'
  option     = 'EQ'
  low        = 'A' ).
```

### 8.4 Exclude 조건

상태가 `F`인 행을 제외하려면 다음과 같이 설정할 수 있다.

```abap
lo_filters->add_filter(
  columnname = 'STATUS'
  sign       = 'E'
  option     = 'EQ'
  low        = 'F' ).
```

### 8.5 범위 조건

연결 번호가 `0001`부터 `0500` 사이인 항목을 표시하려면 다음과 같은 형태를 사용할 수 있다.

```abap
lo_filters->add_filter(
  columnname = 'CONNID'
  sign       = 'I'
  option     = 'BT'
  low        = '0001'
  high       = '0500' ).
```

### 8.6 패턴 조건

도시명이 `S`로 시작하는 항목을 필터링하는 예시이다.

```abap
lo_filters->add_filter(
  columnname = 'CITYFROM'
  sign       = 'I'
  option     = 'CP'
  low        = 'S*' ).
```

단, 패턴 비교는 필드 타입, 사용자 기대, 데이터 형식에 따라 오해가 생기기 쉽다. 초급 단계에서는 `EQ`, `BT`를 먼저 안정적으로 익히는 것이 좋다.

## 9. Sort와 Filter를 함께 적용한 완성 예제

다음 예제는 표준 기능을 활성화하고, 상태가 `A`인 항목만 표시한 뒤, 항공사 코드와 연결 번호 기준으로 정렬한다.

```abap
REPORT ztl19_m01_salv_sort_filter.

TYPES: BEGIN OF ty_flight_demo,
         carrid   TYPE c LENGTH 3,
         connid   TYPE n LENGTH 4,
         cityfrom TYPE c LENGTH 20,
         cityto   TYPE c LENGTH 20,
         seatsmax TYPE i,
         seatsocc TYPE i,
         status   TYPE c LENGTH 1,
       END OF ty_flight_demo.

DATA lt_flight TYPE STANDARD TABLE OF ty_flight_demo.
DATA lo_alv    TYPE REF TO cl_salv_table.

lt_flight = VALUE #(
  ( carrid = 'LH' connid = '0400' cityfrom = 'Frankfurt' cityto = 'New York' seatsmax = 300 seatsocc = 220 status = 'A' )
  ( carrid = 'LH' connid = '0401' cityfrom = 'Frankfurt' cityto = 'Seoul'    seatsmax = 280 seatsocc = 280 status = 'F' )
  ( carrid = 'AA' connid = '0017' cityfrom = 'New York'  cityto = 'Boston'   seatsmax = 180 seatsocc = 120 status = 'A' )
  ( carrid = 'AA' connid = '0020' cityfrom = 'Boston'    cityto = 'Chicago'  seatsmax = 160 seatsocc = 150 status = 'A' )
  ( carrid = 'KE' connid = '0901' cityfrom = 'Seoul'     cityto = 'Tokyo'    seatsmax = 250 seatsocc = 230 status = 'A' )
  ( carrid = 'KE' connid = '0902' cityfrom = 'Seoul'     cityto = 'Paris'    seatsmax = 260 seatsocc = 260 status = 'F' ) ).

TRY.
    cl_salv_table=>factory(
      IMPORTING
        r_salv_table = lo_alv
      CHANGING
        t_table      = lt_flight ).

    DATA(lo_functions) = lo_alv->get_functions( ).
    lo_functions->set_all( abap_true ).

    DATA(lo_filters) = lo_alv->get_filters( ).
    lo_filters->add_filter(
      columnname = 'STATUS'
      sign       = 'I'
      option     = 'EQ'
      low        = 'A' ).

    DATA(lo_sorts) = lo_alv->get_sorts( ).
    lo_sorts->add_sort(
      columnname = 'CARRID'
      sequence   = if_salv_c_sort=>sort_up ).
    lo_sorts->add_sort(
      columnname = 'CONNID'
      sequence   = if_salv_c_sort=>sort_up ).

    lo_alv->display( ).

  CATCH cx_salv_msg INTO DATA(lx_msg).
    MESSAGE lx_msg->get_text( ) TYPE 'E'.
  CATCH cx_salv_not_found INTO DATA(lx_not_found).
    MESSAGE lx_not_found->get_text( ) TYPE 'E'.
  CATCH cx_salv_data_error INTO DATA(lx_data_error).
    MESSAGE lx_data_error->get_text( ) TYPE 'E'.
  CATCH cx_salv_existing INTO DATA(lx_existing).
    MESSAGE lx_existing->get_text( ) TYPE 'E'.
ENDTRY.
```

[추정] 시스템 릴리스와 SALV 클래스 메서드 시그니처에 따라 일부 예외 클래스 또는 메서드 파라미터 표시가 다르게 보일 수 있다. 실습 시스템에서 구문 오류가 발생하면 ADT 또는 SE38의 자동완성, F2 도움말, 클래스 메서드 시그니처를 기준으로 조정한다.

## 10. 적용 순서의 실무적 의미

코드에서는 보통 다음 순서를 권장한다.

```text
1. SALV 객체 생성
2. Function 활성화
3. Filter 설정
4. Sort 설정
5. Column / Display 설정
6. display( ) 호출
```

실제 화면 표시 결과 관점에서는 필터가 적용되어 표시 대상이 제한되고, 그 결과가 정렬되어 보인다고 이해할 수 있다. 코드 상으로 Sort와 Filter 설정 순서를 바꾸어도 최종 표시 결과가 같을 수 있지만, 읽는 사람의 이해를 위해 “표시 대상 제한 → 표시 순서 지정” 흐름으로 작성하는 것이 좋다.

```abap
DATA(lo_filters) = lo_alv->get_filters( ).
" 먼저 표시할 데이터 범위를 제한

DATA(lo_sorts) = lo_alv->get_sorts( ).
" 그 다음 표시 순서를 지정
```

## 11. SALV Function 제어의 실무 주의점

### 11.1 `set_all( abap_true )`의 장점과 위험

`set_all( abap_true )`는 교육용 예제에서 편리하다. 그러나 실무에서는 모든 기능을 무조건 열어주는 것이 항상 좋지는 않다.

| 관점 | 설명 |
|---|---|
| 보안 | Excel 내보내기 기능이 민감 데이터 유출 경로가 될 수 있다. |
| 업무 통제 | 사용자가 임의 필터와 정렬로 기준 보고서와 다른 결과를 볼 수 있다. |
| UI 단순성 | 불필요한 버튼이 많으면 초급 사용자가 혼란스러워질 수 있다. |
| 감사 | 출력·다운로드 행위가 통제 대상일 수 있다. |

따라서 실무 보고서에서는 “전체 기능 활성화”보다 “업무에 필요한 기능만 제공”하는 설계가 더 적절할 수 있다.

### 11.2 SALV는 편하지만 만능은 아니다

SALV는 빠르게 조회성 리스트를 만들기에 좋다. 하지만 복잡한 편집, 셀 단위 색상, 셀 스타일, 이벤트 기반 인터랙션, 정교한 Toolbar 제어가 필요하다면 `CL_GUI_ALV_GRID` 기반 Grid ALV가 더 적합하다.

이번 Section의 뒤쪽 모듈에서는 Grid ALV의 Cell Color, Cell Style, Stable Refresh를 다룬다.

## 12. Sort 설계의 실무 기준

Sort는 단순한 화면 편의 기능처럼 보이지만, 보고서의 해석 방식에 영향을 준다.

### 12.1 기본 정렬 기준은 업무 우선순위를 반영해야 한다

나쁜 예:

```text
개발자가 보기 편하다는 이유로 CREATED_ON만 내림차순 정렬
```

좋은 예:

```text
회사코드 → 플랜트 → 자재번호 → 생성일 순으로 정렬
```

즉, 사용자가 데이터를 분석하는 기준과 같은 순서로 정렬해야 한다.

### 12.2 정렬 기준이 너무 많으면 오히려 혼란스럽다

초급 개발자는 많은 컬럼을 정렬에 추가하면 더 친절하다고 생각할 수 있다. 하지만 정렬 기준이 많아지면 데이터가 어떤 기준으로 배열되었는지 이해하기 어렵다.

권장 기준은 다음이다.

```text
1차: 업무 그룹 기준
2차: 업무 식별 기준
3차: 날짜 또는 상태 기준
```

### 12.3 필터와 정렬은 보고서 요구사항에 포함되어야 한다

정렬과 필터를 개발자가 임의로 정하면 운영 사용자가 기대하는 결과와 달라질 수 있다. 따라서 요구사항 단계에서 다음을 확인해야 한다.

```text
처음 화면에 어떤 데이터만 보여야 하는가?
기본 정렬 기준은 무엇인가?
사용자가 Toolbar에서 정렬/필터를 바꿔도 되는가?
특정 상태 데이터는 기본적으로 제외해야 하는가?
```

## 13. Filter 설계의 실무 기준

Filter는 표시 결과 자체를 줄인다. 따라서 정렬보다 업무 영향이 더 클 수 있다.

### 13.1 숨겨진 필터를 조심한다

코드에서 기본 필터를 적용하면 사용자는 전체 데이터가 아니라 필터링된 데이터만 보게 된다.

예를 들어 `STATUS = 'A'`만 보여주면 마감, 비활성, 오류 상태 데이터는 처음 화면에서 보이지 않는다.

이런 경우 화면 제목이나 Selection Screen, 안내 문구에서 필터 조건을 명확히 알려야 한다.

```text
보고서 제목: Active Flight List
기본 조건: STATUS = A
```

### 13.2 필터는 DB 조회 조건과 역할을 구분해야 한다

SALV Filter는 표시 제어이다. 대량 데이터 성능을 개선하려면 DB 조회 단계의 `WHERE` 조건이 우선이다.

나쁜 예:

```abap
SELECT * FROM zlarge_table INTO TABLE @lt_data.
" 수십만 건을 가져온 뒤 SALV Filter로 일부만 표시
```

좋은 예:

```abap
SELECT *
  FROM zlarge_table
  WHERE status = 'A'
  INTO TABLE @lt_data.
" DB 단계에서 먼저 줄이고, SALV에서는 사용자 표시 편의 필터를 보조적으로 사용
```

이번 모듈은 SALV 표시 제어를 다루지만, 실무에서는 성능을 위해 DB 조회 조건과 SALV Filter를 함께 설계해야 한다.

### 13.3 필터 컬럼은 화면에 보이는 것이 좋다

기본 필터가 적용된 컬럼이 화면에서 숨겨져 있으면 사용자가 왜 일부 데이터만 보이는지 이해하기 어렵다. 따라서 기본 필터에 사용한 컬럼은 가급적 화면에 표시하거나, 최소한 보고서 설명에 명시한다.

## 14. 오류 상황과 해결 방법

### 14.1 컬럼명을 잘못 입력한 경우

상황:

```abap
lo_sorts->add_sort( columnname = 'CARRIER' ).
```

하지만 실제 필드명은 `CARRID`이다.

증상:

```text
Column not found 또는 SALV 관련 예외 발생
```

해결:

```text
Internal Table 구조의 실제 필드명을 확인한다.
SE11 또는 TYPES 정의에서 필드명을 확인한다.
columnname에는 필드명을 대문자로 입력한다.
```

### 14.2 중복 Sort를 추가한 경우

상황:

```abap
lo_sorts->add_sort( columnname = 'CARRID' ).
lo_sorts->add_sort( columnname = 'CARRID' ).
```

증상:

```text
Existing sort 관련 예외 가능
```

해결:

```text
같은 컬럼을 중복으로 Sort에 추가하지 않는다.
기존 Sort를 확인하거나 설계상 한 번만 추가한다.
```

### 14.3 Filter 값 타입이 맞지 않는 경우

상황:

```abap
lo_filters->add_filter(
  columnname = 'SEATSOCC'
  sign       = 'I'
  option     = 'EQ'
  low        = 'ABC' ).
```

`SEATSOCC`는 정수 필드인데 문자 값을 비교하려고 한다.

증상:

```text
Data error 또는 필터 결과가 예상과 다름
```

해결:

```text
필터 대상 필드의 타입을 확인한다.
숫자 필드에는 숫자형으로 해석 가능한 값을 사용한다.
날짜 필드에는 내부 날짜 형식 YYYYMMDD를 사용한다.
```

### 14.4 `display( )` 후 설정을 변경한 경우

상황:

```abap
lo_alv->display( ).
lo_alv->get_sorts( )->add_sort( columnname = 'CARRID' ).
```

문제:

```text
화면 표시 이후에 설정해도 초기 표시에는 반영되지 않는다.
```

해결:

```text
Function, Sort, Filter, Column 설정은 display( ) 호출 전에 수행한다.
```

### 14.5 대량 데이터를 SALV Filter에만 의존한 경우

상황:

```abap
전체 데이터를 SELECT한 뒤 SALV Filter로만 일부 데이터 표시
```

문제:

```text
DB에서 불필요하게 많은 데이터를 읽어 성능 저하 발생
```

해결:

```text
DB WHERE 조건으로 먼저 데이터량을 줄인다.
SALV Filter는 화면 표시 편의 기능으로 사용한다.
```

## 15. 디버깅과 검증 포인트

SALV Sort / Filter / Function 제어가 예상대로 작동하지 않을 때는 다음 순서로 확인한다.

| 순서 | 확인 항목 | 확인 방법 |
|---:|---|---|
| 1 | Internal Table에 데이터가 있는가? | `LINES( lt_data )`, 디버거 확인 |
| 2 | 컬럼명이 정확한가? | TYPES 또는 DDIC Structure 확인 |
| 3 | SALV 객체가 생성되었는가? | `lo_alv IS BOUND` 확인 |
| 4 | 설정이 `display( )` 전에 실행되는가? | 코드 순서 확인 |
| 5 | Filter 조건이 너무 강하지 않은가? | 필터 제거 후 표시 확인 |
| 6 | Sort 중복이 있는가? | 동일 컬럼 중복 설정 확인 |
| 7 | 예외가 발생했는가? | TRY...CATCH에서 메시지 확인 |

실무에서는 다음 두 테스트를 반드시 수행하는 것이 좋다.

```text
1. 필터 조건 없이 전체 데이터 표시 테스트
2. 필터 적용 후 예상 건수와 표시 건수 비교
```

## 18. SALV와 Grid ALV 전환 기준

SALV는 빠르고 단순한 조회성 리스트에 적합하다.

### 18.1 SALV가 적합한 경우

| 상황 | 이유 |
|---|---|
| 단순 조회 리포트 | 구현이 빠르고 코드가 간결하다. |
| 편집이 필요 없는 리스트 | SALV는 표시 중심에 적합하다. |
| 기본 정렬/필터/내보내기 정도만 필요 | 표준 기능으로 충분하다. |
| 개발 생산성이 중요한 경우 | Grid ALV보다 초기 구현이 쉽다. |

### 18.2 Grid ALV가 더 적합한 경우

| 상황 | 이유 |
|---|---|
| 셀 단위 색상 제어 필요 | `LVC_T_SCOL` 등 Grid ALV 기능 필요 |
| 셀 스타일 또는 편집 제어 필요 | `LVC_T_STYL` 등 심화 제어 필요 |
| 복잡한 Toolbar 이벤트 필요 | Custom Toolbar와 Event Handling 필요 |
| Stable Refresh 필요 | 화면 상태 보존 제어 필요 |
| 사용자 입력 및 데이터 변경 필요 | SALV보다 Grid ALV가 적합 |

이번 모듈은 SALV에서 가능한 표시 제어의 범위를 익히는 단계이다. 이후 모듈에서는 Grid ALV의 세밀한 표시 제어로 확장한다.

D. `display( )` 후 `add_sort( )`  

**정답:** A

#### Q3. 대량 데이터 보고서에서 성능을 위해 우선해야 하는 것은?

A. 모든 데이터를 SELECT한 후 SALV Filter로 줄인다.  
B. DB 조회 단계에서 `WHERE` 조건으로 먼저 줄인다.  
C. ALV Toolbar에서 사용자가 직접 필터하게 한다.  
D. 정렬을 많이 추가한다.  

**정답:** B

### 20.2 서술형

#### Q1. SALV Filter와 Open SQL WHERE 조건의 차이를 설명하시오.

**모범 답안:**  
Open SQL `WHERE` 조건은 데이터베이스에서 데이터를 읽어오는 단계에서 대상 데이터를 줄인다. 반면 SALV Filter는 이미 Internal Table에 존재하는 데이터를 화면 표시 관점에서 제한한다. 따라서 대량 데이터 성능은 DB 조회 조건을 우선 적용하고, SALV Filter는 사용자 표시 편의 기능으로 사용하는 것이 좋다.

#### Q2. `set_all( abap_true )`를 실무에서 무조건 사용하면 안 되는 이유를 설명하시오.

**모범 답안:**  
표준 Toolbar 기능이 모두 활성화되면 사용자가 내보내기, 필터, 정렬, 인쇄 등 다양한 기능을 사용할 수 있다. 이는 편리하지만 민감 데이터 다운로드, 기준 보고서와 다른 화면 조작, 불필요한 버튼 증가 등 보안·업무 통제·사용성 문제가 생길 수 있다. 따라서 업무에 필요한 기능만 제공하는 것이 더 적절할 수 있다.

#### Q3. SALV에서 컬럼명을 잘못 지정했을 때 점검할 항목을 설명하시오.

**모범 답안:**  
Internal Table 구조의 실제 필드명을 확인해야 한다. `TYPES` 정의 또는 DDIC Structure에서 필드명을 확인하고, `columnname`에 대문자 필드명을 정확히 입력한다. 또한 설정이 `display( )` 전에 실행되는지, 예외 처리가 되어 있는지도 함께 확인한다.

## 21. 핵심 요약

이번 모듈의 핵심은 다음과 같다.

```text
SALV는 CL_SALV_TABLE 객체를 중심으로 하위 제어 객체를 가져와 표시 동작을 설정한다.
get_functions( )는 Toolbar 표준 기능 제어에 사용한다.
get_sorts( )와 add_sort( )는 기본 정렬 조건 제어에 사용한다.
get_filters( )와 add_filter( )는 기본 표시 필터 조건 제어에 사용한다.
모든 설정은 display( ) 호출 전에 수행해야 한다.
대량 데이터 성능은 SALV Filter보다 DB WHERE 조건이 우선이다.
복잡한 셀 색상, 스타일, 이벤트, 편집 제어가 필요하면 Grid ALV를 검토한다.
```
