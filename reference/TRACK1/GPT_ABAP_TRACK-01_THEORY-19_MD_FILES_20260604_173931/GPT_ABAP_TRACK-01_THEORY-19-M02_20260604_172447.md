## 3. Layout과 Variant의 개념

### 3.1 Layout이란?

SALV에서 Layout은 ALV 화면이 데이터를 어떻게 보여줄지를 나타내는 표시 설정이다.

예를 들어 같은 Internal Table을 출력하더라도 사용자는 다음과 같은 설정을 바꿀 수 있다.

| Layout 요소 | 예시 |
|---|---|
| 컬럼 순서 | CARRID, CONNID, FLDATE 순서로 표시 |
| 컬럼 숨김 | 내부 관리용 필드 숨김 |
| 컬럼 너비 | 항공사명 컬럼을 넓게 표시 |
| 정렬 | 항공사 코드, 항공편 번호 기준 정렬 |
| 필터 | 특정 항공사만 표시 |
| 합계 | 금액 컬럼 합계 표시 |
| 소계 | 항공사별 소계 표시 |
| 출력 형식 | 특정 컬럼 강조 또는 표시 방식 조정 |

즉 Layout은 사용자가 보는 화면 배치와 표시 조건을 의미한다.

### 3.2 Variant란?

Variant는 특정 Layout 설정을 이름으로 저장한 것이다.

예를 들어 사용자가 항공편 리스트에서 다음과 같은 두 가지 화면을 자주 본다고 가정한다.

| Variant 이름 | 목적 |
|---|---|
| `BASIC` | 기본 컬럼만 간단히 표시 |
| `PRICE` | 가격, 통화, 날짜 중심으로 표시 |
| `ADMIN` | 운영 확인용 전체 컬럼 표시 |

이렇게 저장해두면 매번 컬럼을 숨기고 정렬하는 작업을 반복하지 않아도 된다.

초급자는 다음 문장을 기억하면 된다.

> Layout은 화면 배치이고, Variant는 그 배치를 저장한 이름 있는 설정이다.

## 4. 왜 Layout / Variant가 중요한가?

### 4.1 사용자는 같은 데이터를 다르게 본다

개발자는 보통 하나의 ALV 리스트를 만든다. 하지만 사용자는 부서나 업무 목적에 따라 다른 방식으로 데이터를 보고 싶어 한다.

예를 들어 판매오더 리스트를 생각해보자.

| 사용자 | 보고 싶은 정보 |
|---|---|
| 영업 담당자 | 고객, 주문일, 납기일, 상태 |
| 회계 담당자 | 금액, 통화, 청구 상태 |
| 운영 관리자 | 생성자, 변경일, 처리 상태, 오류 메시지 |
| 품질 담당자 | 반품 여부, 클레임 상태 |

이 요구사항을 모두 별도 프로그램으로 만들면 비효율적이다. 하나의 ALV 프로그램에서 Layout Variant를 허용하면 사용자가 자기 업무에 맞는 화면을 저장할 수 있다.

### 4.2 개발자 유지보수 부담을 줄인다

Variant를 허용하면 다음 요청을 매번 개발 변경으로 처리하지 않아도 된다.

```text
이 컬럼을 앞으로 앞으로 옮겨주세요.
이 필드는 기본에서 숨겨주세요.
이 조건으로 자주 보고 싶습니다.
정렬 기준을 저장해두고 싶습니다.
```

물론 모든 요구를 Variant로 해결할 수는 없다. 하지만 단순 표시 방식 변경은 Layout Variant로 흡수할 수 있다.

### 4.3 운영 표준화에 도움을 준다

공용 Variant를 운영하면 부서 단위로 표준 보기 방식을 제공할 수 있다.

예시:

```text
/DEFAULT_SALES
/DEFAULT_FI
/ADMIN_CHECK
```

단, 공용 Variant를 무분별하게 허용하면 사용자가 너무 많은 Variant를 만들고 관리가 어려워질 수 있다. 따라서 실무에서는 저장 권한과 명명 규칙이 필요하다.

## 5. SALV Layout 제어의 기본 구조

SALV에서 Layout 제어는 `CL_SALV_LAYOUT` 객체를 통해 수행한다.

기본 흐름은 다음과 같다.

```abap
DATA lo_alv    TYPE REF TO cl_salv_table.
DATA lo_layout TYPE REF TO cl_salv_layout.
DATA ls_key    TYPE salv_s_layout_key.

cl_salv_table=>factory(
  IMPORTING
    r_salv_table = lo_alv
  CHANGING
    t_table      = lt_flight ).

lo_layout = lo_alv->get_layout( ).

ls_key-report = sy-repid.
lo_layout->set_key( ls_key ).
lo_layout->set_save_restriction( if_salv_c_layout=>restrict_none ).
lo_layout->set_default( abap_true ).

lo_alv->display( ).
```

이 코드에서 중요한 부분은 다음이다.

| 코드 | 의미 |
|---|---|
| `get_layout( )` | SALV Layout 제어 객체를 가져온다. |
| `salv_s_layout_key` | Variant 저장 기준이 되는 Key 구조이다. |
| `set_key( )` | 이 ALV의 Variant 저장 기준을 지정한다. |
| `set_save_restriction( )` | Variant 저장 허용 범위를 지정한다. |
| `set_default( )` | 기본 Variant 사용 가능 여부를 지정한다. |

---

## 6. `get_layout( )`의 역할

`get_layout( )`은 SALV 객체에서 Layout 제어 객체를 반환한다.

```abap
lo_layout = lo_alv->get_layout( ).
```

SALV의 기능은 여러 전용 객체로 나누어져 있다.

| 목적 | 접근 메서드 | 반환 객체 예시 |
|---|---|---|
| Function 버튼 제어 | `get_functions( )` | `CL_SALV_FUNCTIONS_LIST` |
| Column 제어 | `get_columns( )` | `CL_SALV_COLUMNS_TABLE` |
| Sort 제어 | `get_sorts( )` | `CL_SALV_SORTS` |
| Filter 제어 | `get_filters( )` | `CL_SALV_FILTERS` |
| Layout 제어 | `get_layout( )` | `CL_SALV_LAYOUT` |

즉 `get_layout( )`은 ALV 화면의 저장 가능한 표시 설정을 제어하기 위한 출입구이다.

## 7. Layout Key

### 7.1 Layout Key가 필요한 이유

SALV Variant는 단순히 이름만으로 저장되지 않는다. 시스템은 어떤 프로그램의 어떤 ALV에 대한 Variant인지 알아야 한다.

이때 사용하는 기준이 Layout Key이다.

대표적인 Key 요소는 다음이다.

| 요소 | 의미 |
|---|---|
| `REPORT` | 프로그램 이름 |
| `HANDLE` | 같은 프로그램 안의 여러 ALV를 구분하는 식별자 |

가장 기본적인 방식은 현재 프로그램명을 Key로 설정하는 것이다.

```abap
DATA ls_key TYPE salv_s_layout_key.

ls_key-report = sy-repid.
lo_layout->set_key( ls_key ).
```

### 7.2 같은 프로그램에 ALV가 하나만 있는 경우

ALV가 하나만 있다면 `REPORT = SY-REPID`만으로 충분한 경우가 많다.

```abap
ls_key-report = sy-repid.
lo_layout->set_key( ls_key ).
```

### 7.3 같은 프로그램에 ALV가 여러 개 있는 경우

같은 프로그램에서 Header ALV와 Item ALV를 각각 출력한다면 Variant가 섞이면 안 된다.

이 경우 Handle을 구분하는 것이 좋다.

```abap
DATA ls_key TYPE salv_s_layout_key.

ls_key-report = sy-repid.
ls_key-handle = 'HDR'.
lo_layout_header->set_key( ls_key ).

CLEAR ls_key.
ls_key-report = sy-repid.
ls_key-handle = 'ITM'.
lo_layout_item->set_key( ls_key ).
```

> [추정] 실제 프로젝트에서는 Handle 값에 화면 번호, ALV 목적, 컨테이너 ID 등을 반영해 더 명확하게 설계할 수 있다.

### 7.4 Key를 설정하지 않았을 때의 문제

Layout Key를 설정하지 않으면 다음 문제가 발생할 수 있다.

| 문제 | 설명 |
|---|---|
| Variant 저장 버튼이 기대대로 동작하지 않음 | 저장 기준이 명확하지 않다. |
| 기본 Variant가 적용되지 않음 | 시스템이 어떤 ALV의 Variant인지 판단하기 어렵다. |
| 프로그램 변경 후 Variant 관리 혼선 | 안정적인 식별 기준이 부족하다. |
| 여러 ALV 간 Variant 충돌 | 같은 프로그램 안에서 화면 목적이 섞일 수 있다. |

따라서 실무에서는 Layout을 쓸 때 `set_key( )`를 거의 필수 설정처럼 생각하는 것이 좋다.

## 8. Variant 저장 제한

### 8.1 저장 제한이란?

Variant 저장 제한은 사용자가 Layout Variant를 저장할 수 있는 범위를 지정하는 설정이다.

대표적으로 다음과 같은 선택지가 있다.

| 설정 | 의미 |
|---|---|
| 저장 불가 | 사용자가 Variant를 저장하지 못함 |
| 사용자별 저장 허용 | 개인 Variant 중심으로 저장 |
| 공용 저장 허용 | 여러 사용자가 공유 가능한 Variant 허용 |
| 제한 없음 | 개인/공용 저장을 모두 허용 |

SALV에서는 일반적으로 다음 상수를 사용한다.

```abap
if_salv_c_layout=>restrict_none
if_salv_c_layout=>restrict_user_dependant
if_salv_c_layout=>restrict_user_independant
```

> 참고: 일부 상수명에는 SAP 표준 객체에서 사용하는 영문 표기가 그대로 반영되어 있다. 시스템 릴리스나 개발 환경에 따라 자동완성으로 정확한 상수명을 확인하는 것이 안전하다.

### 8.2 제한 없음

```abap
lo_layout->set_save_restriction( if_salv_c_layout=>restrict_none ).
```

교육용 실습에서는 이 설정을 사용하면 Layout 저장 기능을 쉽게 확인할 수 있다.

장점:

- 개인 Variant와 공용 Variant를 실습하기 쉽다.
- Layout 저장 버튼이 기대대로 보인다.
- 교육자가 기능을 설명하기 좋다.

주의:

- 실무 운영 프로그램에서 무조건 허용하면 Variant 관리가 난잡해질 수 있다.
- 공용 Variant 생성 권한과 명명 규칙이 필요할 수 있다.

### 8.3 사용자별 저장만 허용

사용자별 Variant만 허용하면 각 사용자는 자기 화면 설정을 저장할 수 있지만, 다른 사용자에게 영향을 주지 않는다.

적합한 상황:

| 상황 | 이유 |
|---|---|
| 사용자별 업무 스타일이 다름 | 개인 설정이 유리하다. |
| 공용 Variant 관리 기준이 없음 | 개인 Variant로 제한하는 편이 안전하다. |
| 운영 혼선을 줄이고 싶음 | 공용 Variant 난립을 방지한다. |

### 8.4 공용 Variant 제한

일부 프로그램에서는 공용 Variant만 운영하고 개인 Variant를 제한하려는 경우도 있다. 하지만 대부분의 초급 실습에서는 공용/개인 차이를 이해하는 수준이면 충분하다.

실무에서 중요한 것은 다음이다.

```text
Variant 저장은 단순 UI 편의 기능이지만, 운영 관점에서는 표준 화면 형태를 누가 관리할 것인지의 문제와 연결된다.
```

## 9. 기본 Variant

### 9.1 기본 Variant란?

기본 Variant는 사용자가 프로그램을 실행했을 때 자동으로 적용되기를 기대하는 Layout Variant이다.

예를 들어 영업 부서에서 대부분의 사용자가 `SALES_DEFAULT` 레이아웃을 본다면, 이 Variant를 기본으로 지정할 수 있다.

SALV 코드에서는 기본 Variant 사용을 허용하기 위해 다음 메서드를 사용할 수 있다.

```abap
lo_layout->set_default( abap_true ).
```

이 설정은 Layout Variant 기능에서 기본 Variant 선택을 가능하게 하는 데 사용된다.

### 9.2 기본 Variant가 필요한 경우

| 상황 | 설명 |
|---|---|
| 기본 컬럼 구성이 복잡함 | 사용자가 매번 컬럼을 조정하지 않아도 된다. |
| 부서 표준 보기 방식이 있음 | 공통 화면 기준을 제공할 수 있다. |
| 운영자가 표준 점검 화면을 정의함 | 오류 확인, 정산 확인 등 고정된 Layout이 필요하다. |

### 9.3 기본 Variant 사용 시 주의점

기본 Variant는 편리하지만, 너무 강하게 의존하면 다음 문제가 생길 수 있다.

| 문제 | 설명 |
|---|---|
| 프로그램 변경 시 Variant 불일치 | 컬럼명이 바뀌거나 삭제되면 기존 Variant가 깨질 수 있다. |
| 사용자 혼란 | 기본 화면과 사용자 개인 화면이 다를 수 있다. |
| 운영 기준 불명확 | 누가 기본 Variant를 관리하는지 불분명할 수 있다. |

따라서 실무에서는 기본 Variant의 명명 규칙과 관리자를 정하는 것이 좋다.

## 10. 초기 Layout Variant 지정

### 10.1 Selection Screen에서 Variant 입력 받기

사용자가 실행 시점에 Layout Variant를 선택하도록 만들 수도 있다.

예시:

```abap
PARAMETERS p_layo TYPE disvariant-variant.
```

이 파라미터는 사용자가 저장된 Layout Variant 이름을 입력하는 용도로 사용할 수 있다.

### 10.2 SALV에 초기 Layout 연결

사용자가 `P_LAYO`에 값을 입력했다면 SALV Layout에 초기 Variant로 전달할 수 있다.

```abap
IF p_layo IS NOT INITIAL.
  lo_layout->set_initial_layout( p_layo ).
ENDIF.
```

이렇게 하면 사용자가 실행 시점에 지정한 Layout을 적용해 ALV를 열 수 있다.

> [추정] 시스템 릴리스 또는 SAP GUI 설정에 따라 Variant 선택 도움말, 저장 화면, 초기 Layout 적용 동작이 약간 다르게 보일 수 있다. 메서드 시그니처는 ADT 또는 SE80의 Class Builder에서 확인한다.

## 11. 전체 예제 프로그램

다음 예제는 `SFLIGHT` 데이터를 SALV로 출력하면서 Layout Variant 저장을 허용하는 최소 예제이다.

```abap
REPORT zgpt_salv_layout_variant.

PARAMETERS p_layo TYPE disvariant-variant.

START-OF-SELECTION.

  SELECT carrid,
         connid,
         fldate,
         price,
         currency,
         seatsmax,
         seatsocc
    FROM sflight
    INTO TABLE @DATA(lt_sflight)
    UP TO 100 ROWS.

  IF lt_sflight IS INITIAL.
    MESSAGE '조회된 항공편 데이터가 없습니다.' TYPE 'S' DISPLAY LIKE 'E'.
    RETURN.
  ENDIF.

  TRY.
      cl_salv_table=>factory(
        IMPORTING
          r_salv_table = DATA(lo_alv)
        CHANGING
          t_table      = lt_sflight ).

      DATA(lo_functions) = lo_alv->get_functions( ).
      lo_functions->set_all( abap_true ).

      DATA(lo_layout) = lo_alv->get_layout( ).
      DATA(ls_key)    = VALUE salv_s_layout_key( report = sy-repid ).

      lo_layout->set_key( ls_key ).
      lo_layout->set_save_restriction( if_salv_c_layout=>restrict_none ).
      lo_layout->set_default( abap_true ).

      IF p_layo IS NOT INITIAL.
        lo_layout->set_initial_layout( p_layo ).
      ENDIF.

      DATA(lo_columns) = lo_alv->get_columns( ).
      lo_columns->set_optimize( abap_true ).

      lo_alv->display( ).

    CATCH cx_salv_msg INTO DATA(lx_msg).
      MESSAGE lx_msg->get_text( ) TYPE 'S' DISPLAY LIKE 'E'.
  ENDTRY.
```

### 11.1 예제 코드 해설

| 코드 | 설명 |
|---|---|
| `PARAMETERS p_layo` | 실행 시 적용할 Layout Variant 이름을 입력받는다. |
| `SELECT ... FROM sflight` | ALV 출력 데이터를 준비한다. |
| `cl_salv_table=>factory` | SALV 객체를 생성한다. |
| `get_functions( )->set_all` | Layout 저장 등 사용자가 쓸 수 있는 기능 버튼을 활성화한다. |
| `get_layout( )` | Layout 제어 객체를 가져온다. |
| `set_key( )` | Variant 저장 기준을 프로그램명으로 설정한다. |
| `set_save_restriction( )` | Variant 저장을 허용한다. |
| `set_default( )` | 기본 Variant 기능 사용을 허용한다. |
| `set_initial_layout( )` | 입력받은 Variant를 초기 Layout으로 적용한다. |
| `set_optimize( )` | 컬럼 너비를 자동 최적화한다. |

## 13. 자주 발생하는 오류와 해결

### 13.1 Layout 저장 버튼이 보이지 않음

| 구분 | 내용 |
|---|---|
| 증상 | ALV 화면에서 Layout 저장 또는 변경 관련 버튼이 보이지 않는다. |
| 원인 | Function 활성화 누락, Layout 설정 누락, SALV 표시 모드 제약 가능성 |
| 해결 | `get_functions( )->set_all( abap_true )`, `get_layout( )`, `set_key( )`, 저장 제한 설정을 확인한다. |

### 13.2 Variant가 저장되지 않음

| 구분 | 내용 |
|---|---|
| 증상 | 사용자가 Layout을 저장하려 하지만 저장이 되지 않는다. |
| 원인 | Save Restriction 설정, 권한 부족, Layout Key 누락 가능성 |
| 해결 | `set_save_restriction( )` 값과 사용자 권한, Layout Key를 확인한다. |

### 13.3 저장한 Variant가 다시 적용되지 않음

| 구분 | 내용 |
|---|---|
| 증상 | Variant를 저장했지만 다음 실행에서 적용되지 않는다. |
| 원인 | 기본 Variant 미설정, 초기 Layout 미전달, 다른 Layout Key 사용 |
| 해결 | `set_default( )`, `set_initial_layout( )`, `set_key( )` 값을 확인한다. |

### 13.4 프로그램명을 바꾸자 기존 Variant가 보이지 않음

| 구분 | 내용 |
|---|---|
| 증상 | 복사한 프로그램에서 기존 Variant가 보이지 않는다. |
| 원인 | Layout Key의 `REPORT` 값이 프로그램명 기준이기 때문이다. |
| 해결 | 새 프로그램에서는 새 Variant를 저장하거나, 실무 정책에 따라 Variant 이관을 검토한다. |

### 13.5 여러 ALV의 Variant가 섞임

| 구분 | 내용 |
|---|---|
| 증상 | Header ALV와 Item ALV에서 Variant가 구분되지 않는다. |
| 원인 | 같은 프로그램 내 여러 ALV에 동일한 Layout Key를 사용했다. |
| 해결 | `HANDLE`을 사용해 ALV별 Key를 분리한다. |

### 13.6 컬럼 변경 후 기존 Variant가 깨짐

| 구분 | 내용 |
|---|---|
| 증상 | 프로그램 변경 후 저장된 Variant 적용 시 일부 컬럼이 누락되거나 이상하게 보인다. |
| 원인 | 저장된 Variant가 이전 컬럼 구조를 기준으로 하기 때문이다. |
| 해결 | 기존 Variant 재저장, 신규 Variant 생성, 사용자 안내, 배포 전 영향 확인을 수행한다. |

## 14. 실무 운영 기준

### 14.1 개인 Variant와 공용 Variant

| 구분 | 개인 Variant | 공용 Variant |
|---|---|---|
| 적용 범위 | 특정 사용자 | 여러 사용자 |
| 장점 | 사용자 맞춤 화면 제공 | 부서 표준 화면 제공 |
| 단점 | 사용자별 관리 어려움 | 변경 시 영향 범위 큼 |
| 권장 운영 | 자유롭게 허용 가능 | 관리자 또는 Key User 중심 관리 권장 |

### 14.2 명명 규칙

공용 Variant는 이름만 보고 목적을 알 수 있어야 한다.

좋은 예:

```text
/SALES_BASIC
/FI_AMOUNT
/ADMIN_CHECK
/DAILY_MON
```

나쁜 예:

```text
/TEST
/A
/TEMP
/123
```

개인 Variant도 너무 무분별하게 만들면 사용자 본인이 관리하기 어려워진다. 교육 시에는 Variant 이름에 목적을 반영하도록 지도하는 것이 좋다.

### 14.3 개발 변경 시 Variant 영향 점검

ALV 프로그램에서 컬럼명이 바뀌거나 필드가 삭제되면 기존 Variant에 영향이 생길 수 있다.

변경 전 점검 질문:

```text
기존 사용자가 저장한 Layout Variant가 있는가?
삭제하려는 컬럼이 Variant에 포함되어 있는가?
공용 Variant가 운영 기준으로 사용 중인가?
기본 Variant가 깨질 가능성이 있는가?
사용자 안내가 필요한가?
```

### 14.4 권한과 운영 책임

Layout Variant는 기술적으로는 화면 설정이지만, 운영 관점에서는 사용자 경험과 표준 업무 화면을 좌우한다.

따라서 다음 책임 구분이 필요하다.

| 역할 | 책임 |
|---|---|
| 개발자 | Layout 기능이 정상 작동하도록 Key와 저장 정책 설정 |
| Key User | 공용 Variant 명명, 표준 Variant 관리 |
| 일반 사용자 | 개인 Variant 생성 및 사용 |
| 운영자 | 권한, 장애, Variant 관리 정책 지원 |

## 15. SALV Layout과 Grid ALV Layout 비교

SALV와 Grid ALV 모두 Layout Variant를 제공하지만 제어 수준은 다르다.

| 구분 | SALV | Grid ALV |
|---|---|---|
| 기본 목적 | 빠른 표시 중심 | 정교한 화면 제어 중심 |
| 구현 난이도 | 낮음 | 상대적으로 높음 |
| Layout 접근 | `get_layout( )` | `IS_VARIANT`, `I_SAVE`, `IS_LAYOUT` 등 |
| 컬럼 제어 | 비교적 단순 | Field Catalog 기반 상세 제어 |
| 색상/스타일 | 제한적 | Cell Color, Cell Style 가능 |
| 편집 | 일반적으로 제한 | Editable ALV 가능 |
| 실무 사용 | 단순 조회 리스트 | 복잡한 표시/편집 화면 |

이번 모듈은 SALV Layout을 다루며, Grid ALV의 상세 Layout과 Variant 제어는 후속 Grid ALV 심화 또는 표시 제어 심화 주제와 연결된다.

## 17. 실습 과제

### 17.1 기본 과제

`SFLIGHT` 데이터를 출력하는 SALV 프로그램을 만들고 다음을 수행한다.

1. Layout Key를 `SY-REPID` 기준으로 설정한다.
2. Variant 저장을 허용한다.
3. 기본 Variant 사용을 허용한다.
4. ALV 화면에서 컬럼 순서를 변경한다.
5. Layout Variant를 저장한다.
6. 프로그램을 다시 실행해 Variant 적용을 확인한다.

### 17.2 확장 과제

같은 프로그램에서 두 개의 ALV를 출력한다고 가정하고 다음을 설계한다.

| ALV | Handle | 목적 |
|---|---|---|
| Header ALV | HDR | Header 데이터 표시 |
| Item ALV | ITM | Item 데이터 표시 |

각 ALV가 서로 다른 Variant를 가지도록 Layout Key를 어떻게 설정할지 코드로 작성한다.

예시:

```abap
DATA ls_key TYPE salv_s_layout_key.

ls_key-report = sy-repid.
ls_key-handle = 'HDR'.
lo_layout_header->set_key( ls_key ).

CLEAR ls_key.
ls_key-report = sy-repid.
ls_key-handle = 'ITM'.
lo_layout_item->set_key( ls_key ).
```

### 17.3 실무 검토 과제

공용 Variant를 허용하는 프로그램에 대해 다음 운영 기준을 작성한다.

```text
공용 Variant 명명 규칙
공용 Variant 생성 가능 사용자
기본 Variant 변경 승인 절차
프로그램 변경 시 Variant 영향 점검 방식
사용자 안내 방식
```

## 18. 평가 문제

### 18.1 객관식

#### Q1. SALV에서 Layout 제어 객체를 얻는 메서드는?

A. `get_functions( )`  
B. `get_columns( )`  
C. `get_layout( )`  
D. `get_sorts( )`

정답: C

#### Q2. Layout Key를 설정하는 가장 중요한 이유는?

A. 데이터베이스 인덱스를 생성하기 위해  
B. Variant가 어떤 프로그램 또는 ALV에 속하는지 식별하기 위해  
C. Internal Table을 정렬하기 위해  
D. SELECT 문 성능을 높이기 위해

정답: B

#### Q3. 공용 Variant 운영 시 가장 중요한 주의점은?

A. 모든 사용자가 아무 이름으로 저장하도록 허용한다.  
B. 공용 Variant는 운영 영향이 있으므로 명명 규칙과 관리 책임을 정한다.  
C. 공용 Variant는 항상 금지해야 한다.  
D. 공용 Variant는 ABAP 코드와 무관하므로 관리하지 않아도 된다.

정답: B

### 18.2 단답형

#### Q1. Layout과 Variant의 차이를 설명하시오.

모범 답안:  
Layout은 ALV 화면의 컬럼 순서, 숨김, 정렬, 필터 등 표시 설정이고, Variant는 이러한 Layout 설정을 이름으로 저장한 재사용 단위이다.

#### Q2. 같은 프로그램에서 두 개의 ALV를 사용할 때 Handle을 사용하는 이유는?

모범 답안:  
같은 프로그램명만으로 Layout Key를 설정하면 두 ALV의 Variant가 섞일 수 있으므로, Header와 Item처럼 목적이 다른 ALV를 구분하기 위해 Handle을 사용한다.

#### Q3. 기존 Layout Variant가 프로그램 변경 후 깨질 수 있는 이유는?

모범 답안:  
Variant는 기존 ALV 컬럼 구조를 기준으로 저장되어 있는데, 프로그램 변경으로 컬럼명이 바뀌거나 필드가 삭제되면 저장된 설정이 더 이상 맞지 않을 수 있기 때문이다.

```text
SALV Layout은 ALV 화면의 표시 설정이다.
Variant는 Layout을 이름으로 저장한 재사용 단위이다.
SALV에서는 get_layout( )으로 Layout 제어 객체를 가져온다.
Variant 저장을 안정적으로 사용하려면 set_key( )가 중요하다.
Save Restriction은 개인/공용 Variant 저장 가능 범위를 제어한다.
기본 Variant는 편리하지만 운영 책임과 영향 점검이 필요하다.
같은 프로그램의 여러 ALV는 Handle로 Variant를 분리하는 것이 좋다.
```
