
이런 화면은 기능적으로는 동작하지만 사용자 경험은 나쁘다.  
Stable Refresh는 이런 문제를 줄이기 위해 사용한다.

## 3. Refresh가 필요한 상황

ALV는 처음 한 번 표시하고 끝나는 경우도 있지만, 실무 프로그램에서는 사용자의 액션에 따라 데이터를 갱신해야 하는 경우가 많다.

대표 상황은 다음과 같다.

| 상황 | 예시 |
|---|---|
| 데이터 재조회 | 사용자가 조건을 바꾸고 다시 조회 |
| 상태 변경 | 선택 행의 승인/반려/잠금 상태 변경 |
| 색상 재계산 | 오류 행, 경고 행, 성공 행 색상 갱신 |
| 스타일 재계산 | 특정 셀을 입력 가능/불가능 상태로 변경 |
| 계산 결과 변경 | 수량, 금액, 차이값 재계산 |
| 외부 처리 결과 반영 | BAPI 호출 후 처리 상태를 ALV에 반영 |

이때 프로그램은 보통 다음 흐름을 수행한다.

```text
사용자 액션 발생
→ Internal Table 데이터 변경
→ 색상/스타일/필드 상태 재계산
→ ALV Refresh
```

문제는 Refresh 후 사용자가 보고 있던 위치가 사라지거나, 스크롤이 맨 위로 돌아갈 수 있다는 점이다.

---

## 4. 일반 Refresh의 문제

일반 Refresh는 ALV 데이터를 다시 화면에 그리는 기본 동작이다.

예를 들어 다음처럼 호출할 수 있다.

```abap
go_grid->refresh_table_display( ).
```

이 호출은 간단하지만 다음 문제가 발생할 수 있다.

| 문제 | 설명 |
|---|---|
| 세로 스크롤 위치 손실 | 사용자가 보던 행 위치가 유지되지 않을 수 있다. |
| 가로 스크롤 위치 손실 | 오른쪽 열을 보고 있었는데 왼쪽 첫 열로 돌아갈 수 있다. |
| 선택 위치 혼란 | 사용자가 처리하던 행이 화면에서 사라진 것처럼 보일 수 있다. |
| 작업 흐름 방해 | 반복 처리, 검토, 승인 업무에서 사용성이 떨어진다. |

사용자는 “데이터는 맞는데 화면이 자꾸 튄다”고 느낀다.  
이는 기능 오류가 아니라 표시 상태 보존을 고려하지 않은 구현 문제이다.

---

## 5. Stable Refresh란 무엇인가?

Stable Refresh는 ALV Refresh 시 **현재 행 위치와 열 위치를 최대한 유지하도록 요청하는 방식**이다.

Grid ALV에서는 `CL_GUI_ALV_GRID->REFRESH_TABLE_DISPLAY` 메서드의 `IS_STABLE` 파라미터를 사용한다.

핵심 구조는 다음과 같다.

```abap
DATA ls_stable TYPE lvc_s_stbl.

ls_stable-row = abap_true.
ls_stable-col = abap_true.

go_grid->refresh_table_display(
  EXPORTING
    is_stable = ls_stable ).
```

`LVC_S_STBL` 구조의 대표 필드는 다음과 같다.

| 필드 | 의미 |
|---|---|
| ROW | 행 위치 안정성 보존 요청 |
| COL | 열 위치 안정성 보존 요청 |

초급자는 이렇게 기억하면 된다.

```text
ROW = 세로 스크롤 위치 보존
COL = 가로 스크롤 위치 보존
```

정확히 말하면 ALV Grid가 현재 표시 상태를 기준으로 행/열 위치를 최대한 유지하도록 요청하는 것이다.  
단, 내부 테이블의 데이터 순서가 크게 바뀌거나 Sort/Filter 상태가 바뀌면 사용자가 기대한 위치와 완전히 일치하지 않을 수 있다.

---

## 6. Stable Refresh의 최소 코드

### 6.1 기본 형태

```abap
DATA ls_stable TYPE lvc_s_stbl.

ls_stable-row = 'X'.
ls_stable-col = 'X'.

go_grid->refresh_table_display(
  EXPORTING
    is_stable = ls_stable ).
```

S/4HANA 환경의 현대 ABAP 스타일에서는 다음처럼 작성할 수도 있다.

```abap
go_grid->refresh_table_display(
  EXPORTING
    is_stable = VALUE lvc_s_stbl(
                  row = abap_true
                  col = abap_true ) ).
```

두 코드는 실무적으로 같은 목적을 가진다.  
강의에서는 초급자에게 구조 변수를 먼저 보여준 뒤, 후속 단계에서 `VALUE #( )` 스타일을 소개하는 것이 좋다.

## 7. `I_SOFT_REFRESH`의 의미

`REFRESH_TABLE_DISPLAY`에는 `I_SOFT_REFRESH` 파라미터도 자주 함께 등장한다.

예:

```abap
go_grid->refresh_table_display(
  EXPORTING
    is_stable      = VALUE lvc_s_stbl( row = abap_true col = abap_true )
    i_soft_refresh = abap_true ).
```

초급 단계에서는 다음 정도로 이해하면 충분하다.

| 파라미터 | 목적 |
|---|---|
| `IS_STABLE` | 행/열 표시 위치 보존 요청 |
| `I_SOFT_REFRESH` | 전체 표시 구조를 크게 흔들지 않고 데이터 중심으로 부드럽게 갱신하려는 의도 |

`I_SOFT_REFRESH`는 상황에 따라 유용하지만, 모든 변경에 항상 적합한 것은 아니다.  
예를 들어 Field Catalog나 Layout 자체가 크게 바뀌는 경우에는 단순 Soft Refresh만으로 기대한 결과가 나오지 않을 수 있다.

> 실무 기준:  
> 데이터 값만 바뀌는 경우에는 `IS_STABLE`과 `I_SOFT_REFRESH` 조합을 우선 검토한다.  
> 컬럼 구성, Field Catalog, Layout, 색상 필드 구조가 크게 바뀌는 경우에는 전체 표시 흐름을 다시 점검한다.

## 8. Stable Refresh 실습 시나리오

### 8.1 업무 상황

사용자가 ALV에서 여러 사용자 데이터를 검토하고 있다.  
선택 행에 대해 상태를 `A`에서 `I`로 변경하면 ALV의 STATUS 값과 Cell Color가 바뀌어야 한다.  
하지만 사용자가 보고 있던 위치는 유지되어야 한다.

요구사항은 다음과 같다.

```text
1. ALV에 사용자 목록을 표시한다.
2. 선택한 행의 STATUS 값을 변경한다.
3. 변경된 STATUS에 따라 색상을 다시 계산한다.
4. ALV를 Refresh한다.
5. Refresh 후 행/열 위치가 최대한 유지되어야 한다.
```

앞선 모듈에서 학습한 `CTAB_FNAME`과 연결될 수 있다.


## 10. 데이터 변경 후 Refresh 예제

다음 예제는 선택 행을 변경한 뒤 Stable Refresh를 수행하는 핵심 흐름이다.

```abap
FORM change_status_and_refresh.

  DATA lt_rows TYPE lvc_t_row.
  DATA ls_row  TYPE lvc_s_row.

  go_grid->get_selected_rows(
    IMPORTING
      et_index_rows = lt_rows ).

  READ TABLE lt_rows INTO ls_row INDEX 1.
  IF sy-subrc <> 0.
    MESSAGE '변경할 행을 선택하세요.' TYPE 'S' DISPLAY LIKE 'E'.
    RETURN.
  ENDIF.

  READ TABLE gt_user ASSIGNING FIELD-SYMBOL(<ls_user>) INDEX ls_row-index.
  IF sy-subrc <> 0.
    MESSAGE '선택한 행을 내부 테이블에서 찾을 수 없습니다.' TYPE 'S' DISPLAY LIKE 'E'.
    RETURN.
  ENDIF.

  IF <ls_user>-status = 'A'.
    <ls_user>-status  = 'I'.
    <ls_user>-message = 'Inactive 상태로 변경되었습니다.'.
  ELSE.
    <ls_user>-status  = 'A'.
    <ls_user>-message = 'Active 상태로 변경되었습니다.'.
  ENDIF.

  PERFORM set_cell_color CHANGING <ls_user>.

  go_grid->refresh_table_display(
    EXPORTING
      is_stable      = VALUE lvc_s_stbl(
                         row = abap_true
                         col = abap_true )
      i_soft_refresh = abap_true ).

ENDFORM.
```

이 예제의 핵심은 다음 세 줄이다.

```abap
is_stable = VALUE lvc_s_stbl(
              row = abap_true
              col = abap_true )
```

그리고 데이터 값만 바꾸는 경우에는 다음 파라미터를 함께 고려할 수 있다.

```abap
i_soft_refresh = abap_true
```

## 11. 색상 재계산 예제

Stable Refresh는 위치 보존을 담당한다.  
하지만 Cell Color 자체는 프로그램이 다시 계산해야 한다.

```abap
FORM set_cell_color
  CHANGING cs_user TYPE ty_user.

  DATA ls_color TYPE lvc_s_scol.

  CLEAR cs_user-cellcolor.

  CLEAR ls_color.
  ls_color-fname     = 'STATUS'.
  ls_color-color-col = COND #( WHEN cs_user-status = 'A' THEN 5
                               WHEN cs_user-status = 'I' THEN 6
                               ELSE 3 ).
  ls_color-color-int = 1.
  ls_color-color-inv = 0.

  APPEND ls_color TO cs_user-cellcolor.

ENDFORM.
```

중요한 점은 Refresh 전에 Internal Table의 표시 관련 필드가 이미 최신 상태여야 한다는 것이다.

```text
잘못된 순서:
ALV Refresh
→ 색상 재계산

올바른 순서:
데이터 변경
→ 색상 재계산
→ ALV Refresh
```

## 12. Stable Refresh와 Sort/Filter의 관계

Stable Refresh는 현재 표시 상태를 보존하려는 요청이지만, Sort나 Filter 상태와 함께 사용될 때는 주의가 필요하다.

### 12.1 Sort가 적용된 경우

ALV가 특정 컬럼으로 정렬되어 있을 때 데이터 값이 바뀌면, 해당 행의 정렬 위치가 달라질 수 있다.

예:

```text
STATUS 기준 정렬 중
A → I 로 상태 변경
Refresh 후 해당 행 위치가 정렬 기준에 따라 이동 가능
```

이 경우 Stable Refresh를 사용해도 사용자가 보던 행이 같은 화면 위치에 남지 않을 수 있다.  
이는 Stable Refresh 실패라기보다, 데이터 정렬 기준이 달라졌기 때문에 발생하는 자연스러운 결과이다.

### 12.2 Filter가 적용된 경우

Filter가 적용된 상태에서 데이터가 변경되면 행이 필터 조건에서 제외될 수 있다.

예:

```text
STATUS = A 필터 적용 중
선택 행을 A → I 로 변경
Refresh 후 해당 행은 필터 조건에서 사라질 수 있음
```

이때 사용자는 “행이 사라졌다”고 느낄 수 있다.  
하지만 실제로는 필터 조건 때문에 표시 대상에서 제외된 것이다.

### 12.3 Layout/Variant와의 관계

Layout Variant는 컬럼 순서, 숨김, 폭, 정렬, 필터 등 다양한 표시 상태와 연결될 수 있다.  
Stable Refresh는 Variant 자체를 저장하거나 관리하는 기능이 아니다.

즉, 역할을 구분해야 한다.

| 기능 | 역할 |
|---|---|
| Layout / Variant | 사용자의 표시 레이아웃을 저장하거나 복원 |
| Sort / Filter | 데이터 표시 순서와 표시 대상 제어 |
| Cell Color / Style | 개별 셀의 시각적/입력 상태 제어 |
| Stable Refresh | Refresh 후 화면 위치 흔들림 최소화 |

## 13. 스크롤 위치 보존의 한계

Stable Refresh를 사용해도 모든 상황에서 완벽한 표시 상태 보존이 보장되는 것은 아니다.

대표 한계는 다음과 같다.

| 한계 상황 | 설명 |
|---|---|
| Internal Table 전체 재생성 | 기존 행 인덱스와 새 행 인덱스가 달라질 수 있다. |
| Sort 기준 변경 | 행의 표시 위치가 변경될 수 있다. |
| Filter 조건 변경 | 행이 표시 대상에서 제외될 수 있다. |
| Field Catalog 변경 | 컬럼 구조가 바뀌면 열 위치 보존이 어려울 수 있다. |
| Layout 변경 | 사용자가 저장한 Variant 적용 상태와 충돌할 수 있다. |
| 화면 전체 재생성 | Container/Grid 객체를 새로 만들면 기존 상태가 사라질 수 있다. |

따라서 Stable Refresh는 “사용자 위치를 무조건 고정한다”가 아니라, “가능한 범위에서 기존 표시 위치를 안정적으로 유지하도록 요청한다”로 이해해야 한다.

---

## 14. Grid 객체를 다시 만들지 않는 원칙

ALV 화면이 흔들리는 가장 흔한 원인 중 하나는 매번 Grid 객체를 새로 생성하는 것이다.

나쁜 흐름:

```text
사용자 버튼 클릭
→ 기존 Container/Grid 무시
→ 다시 CREATE OBJECT
→ SET_TABLE_FOR_FIRST_DISPLAY 재호출
→ 화면 상태 초기화
```

좋은 흐름:

```text
최초 표시 시에만 CREATE OBJECT
최초 표시 시에만 SET_TABLE_FOR_FIRST_DISPLAY
이후 데이터 변경 시 REFRESH_TABLE_DISPLAY
```

실무적으로 다음 패턴을 자주 사용한다.

```abap
IF go_grid IS INITIAL.
  CREATE OBJECT go_container
    EXPORTING
      container_name = 'CC_ALV'.

  CREATE OBJECT go_grid
    EXPORTING
      i_parent = go_container.

  go_grid->set_table_for_first_display(
    EXPORTING
      is_layout       = gs_layout
    CHANGING
      it_outtab       = gt_user
      it_fieldcatalog = gt_fcat ).
ELSE.
  go_grid->refresh_table_display(
    EXPORTING
      is_stable      = VALUE lvc_s_stbl( row = abap_true col = abap_true )
      i_soft_refresh = abap_true ).
ENDIF.
```

이 패턴은 ALV 실무에서 매우 중요하다.

## 15. 사용자 입력 보호와 Refresh

Editable Grid ALV에서는 Refresh 전에 사용자가 입력 중인 값을 Internal Table에 반영해야 할 수 있다.

대표적으로 다음 메서드가 함께 사용된다.

```abap
go_grid->check_changed_data( ).
```

흐름 예시는 다음과 같다.

```abap
go_grid->check_changed_data( ).

PERFORM validate_input.
PERFORM recalculate_display_status.

go_grid->refresh_table_display(
  EXPORTING
    is_stable      = VALUE lvc_s_stbl( row = abap_true col = abap_true )
    i_soft_refresh = abap_true ).
```

만약 `CHECK_CHANGED_DATA` 없이 Refresh를 먼저 수행하면, 사용자가 화면에 입력한 값이 내부 테이블에 반영되지 않았거나 검증 흐름이 꼬일 수 있다.

> 실무 기준:  
> Editable ALV에서는 Refresh 전에 화면 입력값 반영과 검증이 먼저인지 반드시 확인한다.

## 16. 성능 관점의 주의점

Refresh는 화면을 다시 그리는 작업이다.  
데이터 건수가 많거나 색상/스타일 계산이 복잡하면 사용자가 지연을 느낄 수 있다.

### 16.1 피해야 할 방식

```text
LOOP 한 건마다 REFRESH_TABLE_DISPLAY 호출
사용자 입력 한 글자마다 전체 ALV Refresh
대량 데이터에서 모든 Cell Color/Style을 매번 전체 재계산
DB를 다시 조회한 뒤 즉시 전체 화면 재생성
```

### 16.2 권장 방식

```text
여러 변경을 Internal Table에 모아 반영
필요한 색상/스타일만 재계산
마지막에 한 번만 Stable Refresh
데이터 재조회가 필요한 경우와 화면만 갱신할 경우를 분리
```

예:

```abap
LOOP AT gt_user ASSIGNING FIELD-SYMBOL(<ls_user>) WHERE status = 'E'.
  <ls_user>-message = '오류 상태 확인 필요'.
  PERFORM set_cell_color CHANGING <ls_user>.
ENDLOOP.

go_grid->refresh_table_display(
  EXPORTING
    is_stable      = VALUE lvc_s_stbl( row = abap_true col = abap_true )
    i_soft_refresh = abap_true ).
```

## 17. 정상 흐름과 오류 흐름

### 17.1 정상 흐름

```text
1. 사용자가 ALV에서 작업한다.
2. 프로그램이 변경 이벤트를 받는다.
3. 필요한 경우 CHECK_CHANGED_DATA를 수행한다.
4. Internal Table 데이터를 변경한다.
5. 색상/스타일/메시지를 재계산한다.
6. IS_STABLE을 설정한다.
7. REFRESH_TABLE_DISPLAY를 호출한다.
8. 사용자는 기존 위치와 유사한 위치에서 변경 결과를 확인한다.
```

### 17.2 오류 흐름 1: Refresh 후 화면이 맨 위로 이동

| 항목 | 내용 |
|---|---|
| 증상 | Refresh 후 사용자가 보던 행이 사라지고 맨 위로 이동 |
| 원인 | `IS_STABLE` 미사용 또는 Grid 재생성 |
| 해결 | `IS_STABLE-ROW`, `IS_STABLE-COL` 설정 후 `REFRESH_TABLE_DISPLAY` 사용 |

### 17.3 오류 흐름 2: 색상이 바뀌지 않음

| 항목 | 내용 |
|---|---|
| 증상 | 데이터는 바뀌었지만 Cell Color가 그대로임 |
| 원인 | Refresh 전에 색상 필드를 재계산하지 않음 |
| 해결 | Internal Table의 `LVC_T_SCOL` 필드를 먼저 갱신한 뒤 Refresh |

### 17.4 오류 흐름 3: 선택 행이 사라짐

| 항목 | 내용 |
|---|---|
| 증상 | 변경 후 선택한 행이 화면에서 사라짐 |
| 원인 | Filter 조건에서 제외되었거나 Sort 기준에 의해 위치 이동 |
| 해결 | 현재 Filter/Sort 상태를 확인하고 사용자 메시지로 안내 |

### 17.5 오류 흐름 4: 사용자가 입력한 값이 반영되지 않음

| 항목 | 내용 |
|---|---|
| 증상 | Editable ALV에서 입력 후 Refresh했는데 값이 사라짐 |
| 원인 | `CHECK_CHANGED_DATA` 호출 전 Refresh 수행 |
| 해결 | Refresh 전에 `CHECK_CHANGED_DATA`와 입력 검증 수행 |

## 18. 실무 적용 기준

### 18.1 Stable Refresh를 사용해야 하는 경우

| 상황 | 판단 |
|---|---|
| ALV 데이터 값만 갱신 | 사용 권장 |
| 색상/스타일만 재계산 | 사용 권장 |
| 상태 버튼 처리 후 결과 표시 | 사용 권장 |
| 사용자 검토 위치 유지 필요 | 사용 권장 |
| Editable Grid에서 검증 후 재표시 | `CHECK_CHANGED_DATA`와 함께 사용 |

### 18.2 Stable Refresh만으로 부족한 경우

| 상황 | 추가 고려 |
|---|---|
| Field Catalog 자체 변경 | `SET_TABLE_FOR_FIRST_DISPLAY` 재호출 또는 구조 재설계 검토 |
| 컬럼 구성이 바뀜 | Layout/Variant 영향 검토 |
| 데이터 전체 재조회와 정렬 변경 | 사용자 위치 보존 한계 안내 |
| Container/Grid 재생성 | 객체 생명주기 설계 수정 |
| 대량 데이터 재계산 | 성능 최적화 필요 |

## 20. 평가 문제

### 20.1 객관식

#### Q1. `IS_STABLE-ROW`의 목적에 가장 가까운 것은?

A. 행 색상을 지정한다.  
B. 행 높이를 변경한다.  
C. Refresh 후 행 위치 안정성을 보존하도록 요청한다.  
D. 선택 행을 삭제한다.

정답: C

#### Q2. Stable Refresh를 사용해도 행이 사라질 수 있는 대표 상황은?

A. Filter 조건에서 제외되는 값으로 데이터가 변경된 경우  
B. `WRITE` 문을 사용한 경우  
C. 변수명을 대문자로 작성한 경우  
D. 프로그램에 주석이 많은 경우

정답: A

#### Q3. Editable Grid에서 Refresh 전에 고려해야 하는 메서드는?

A. `CHECK_CHANGED_DATA`  
B. `WRITE`  
C. `APPEND`  
D. `MESSAGE`

정답: A

### 20.2 서술형

#### Q1. Stable Refresh가 필요한 이유를 설명하시오.

모범 답안:  
ALV 데이터를 갱신할 때 사용자가 보고 있던 행/열 위치가 초기화되면 작업 흐름이 끊긴다. Stable Refresh는 Refresh 후에도 행과 열 위치를 최대한 유지하도록 요청하여 사용자 경험을 개선한다.

#### Q2. `IS_STABLE-ROW`와 `IS_STABLE-COL`의 차이를 설명하시오.

모범 답안:  
`ROW`는 세로 방향 행 위치의 안정성 보존과 관련되고, `COL`은 가로 방향 열 위치의 안정성 보존과 관련된다. 둘을 함께 설정하면 Refresh 후 행/열 위치 흔들림을 줄일 수 있다.

#### Q3. Stable Refresh가 모든 표시 상태를 완벽히 보존하지 못하는 이유를 설명하시오.

모범 답안:  
Refresh 전에 Internal Table의 순서가 바뀌거나 Sort/Filter 조건이 변경되면 원래 행이 다른 위치로 이동하거나 표시 대상에서 제외될 수 있다. Field Catalog나 Layout 자체가 변경되는 경우에도 기존 표시 상태를 그대로 유지하기 어렵다.

## 21. 강사용 설명 포인트

강의에서는 Stable Refresh를 단순 메서드 옵션으로만 설명하지 말고 “사용자가 작업 중인 화면 맥락을 보존하는 기술”로 설명하는 것이 좋다.

추천 설명 흐름은 다음이다.

```text
일반 Refresh 시 화면이 흔들리는 문제 시연
→ IS_STABLE 없이 Refresh
→ IS_STABLE 사용 후 차이 확인
→ Sort/Filter 적용 상태에서 한계 확인
→ Editable Grid에서 CHECK_CHANGED_DATA 필요성 설명
```

```text
Editable ALV에서 화면 입력값을 Internal Table에 반영하지 않고 Refresh하면 어떤 문제가 생길까요?
```

## 22. 후속 학습 연결

이 모듈은 Track 1의 ALV 표시 제어 심화 Section을 마무리하는 주제이다.  
Stable Refresh를 이해하면 이후 OO ABAP, 이벤트 처리, 사용자 인터랙션, 실무 데이터 변경 프로그램에서 ALV 화면을 안정적으로 다룰 수 있다.

후속 연결은 다음과 같다.

| 후속 주제 | 연결 방식 |
|---|---|
| OO ABAP | Grid 객체 생명주기와 이벤트 핸들러 구조화 |
| ALV Event | 버튼 클릭, 더블클릭, 데이터 변경 이벤트 후 Refresh |
| Editable ALV | 입력 검증 후 안정적인 화면 갱신 |
| Lock Object | 데이터 변경 중 동시성 제어 후 Refresh |
| BAPI / Transaction 처리 | 처리 결과를 ALV에 반영 |
| RAP/Fiori | 화면 상태 보존과 사용자 경험 개념 확장 |

## 23. 핵심 요약

```text
Stable Refresh는 ALV Refresh 후 행/열 위치 흔들림을 줄이기 위한 Grid ALV 표시 제어 기법이다.
CL_GUI_ALV_GRID->REFRESH_TABLE_DISPLAY의 IS_STABLE 파라미터를 사용한다.
IS_STABLE-ROW는 행 위치, IS_STABLE-COL은 열 위치 보존 요청에 해당한다.
데이터 값만 바뀌는 경우 I_SOFT_REFRESH와 함께 검토할 수 있다.
색상/스타일은 Refresh 전에 Internal Table에서 먼저 재계산해야 한다.
Sort/Filter/Layout 변경이 있으면 Stable Refresh에도 한계가 있다.
Editable Grid에서는 Refresh 전에 CHECK_CHANGED_DATA 호출 여부를 반드시 고려한다.
Grid 객체를 매번 새로 생성하지 말고, 최초 표시와 Refresh 흐름을 분리해야 한다.
```
