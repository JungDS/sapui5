## 3. ABAP Cloud란 무엇인가?

### 3.1 초급자용 정의

ABAP Cloud는 클라우드 환경과 지속적인 업그레이드에 적합하도록 설계된 ABAP 개발 모델이다. 핵심은 ABAP 개발자가 사용할 수 있는 언어 요소, Repository Object, API, 확장 방식을 제한하고 표준화하여 업그레이드 안정성을 높이는 데 있다.

Classic ABAP에서는 개발자가 많은 표준 테이블, Function Module, 클래스, Enhancement 지점에 접근할 수 있었다. 이러한 자유도는 강력하지만, 동시에 다음 리스크를 만든다.

```text
SAP 표준 내부 구조에 직접 의존
→ 업그레이드 시 내부 구조 변경
→ 커스텀 프로그램 오류
→ 회귀 테스트 증가
→ 유지보수 비용 증가
```

ABAP Cloud는 이러한 위험을 줄이기 위해 “사용해도 되는 것”과 “사용하면 안 되는 것”을 더 명확히 나눈다.

### 3.2 ABAP Cloud의 핵심 원칙

| 원칙 | 설명 |
|---|---|
| Released API 사용 | 공개적으로 사용 허용된 API만 직접 참조한다. |
| Cloud-ready language subset | ABAP Cloud에서 허용되는 언어 요소와 객체 유형을 사용한다. |
| RAP 중심 개발 | 비즈니스 객체와 OData V4 서비스를 RAP 방식으로 모델링한다. |
| Clean Core 유지 | SAP 표준 객체의 직접 수정과 내부 의존성을 줄인다. |
| ADT 중심 개발 | Eclipse ADT를 기준으로 최신 ABAP 개발 흐름을 사용한다. |
| 엄격한 정적 검사 | Syntax Check, ATC, ABAP language version check를 통해 위반을 조기에 발견한다. |

### 3.3 SAP GUI 800과 ADT의 역할 구분

사용자 환경 기준으로 SAP GUI 800을 전제로 설명하되, ABAP Cloud와 RAP 개발은 실무적으로 Eclipse ADT 중심이다.

| 도구 | 역할 |
|---|---|
| SAP GUI 800 | 전통적 트랜잭션, 테이블 조회, 일부 관리 업무, 기존 객체 확인 |
| Eclipse ADT | CDS View Entity, RAP Behavior, Service Definition/Binding, ABAP Cloud 개발 중심 |
| ATC / Custom Code Check | 사용 금지 객체, unreleased API, 클라우드 호환성 위반 점검 |
| SAP Fiori / OData Client | RAP 서비스 소비 및 테스트 |

> 주의: ABAP Cloud 개발을 SAP GUI 중심으로만 이해하면 한계가 있다. RAP와 ABAP Cloud는 ADT에서 객체 생성, 활성화, 체크, 서비스 바인딩까지 이어지는 흐름으로 익혀야 한다.

## 4. Released API란 무엇인가?

### 4.1 초급자용 정의

Released API는 SAP 또는 API 소유자가 외부 사용을 허용한다고 명시한 API이다. 여기서 API는 단순히 REST API만 의미하지 않는다. ABAP Cloud 관점에서는 CDS View, Behavior Definition, Class, Interface, Functionality, Service 등도 API 사용 범위에 포함될 수 있다.

간단히 말하면 다음과 같다.

```text
Released API = 사용해도 된다고 공개적으로 약속된 안정적 접근 지점
Unreleased Object = 내부 구현용이거나 외부 사용 안정성이 보장되지 않은 객체
```

### 4.2 왜 Released API가 필요한가?

SAP 표준 시스템에는 수많은 테이블, 클래스, Function Module, View가 있다. 그러나 그중 일부는 SAP 내부 구현을 위한 객체이다. 이런 내부 객체를 고객 개발에서 직접 참조하면 현재는 동작하더라도 향후 릴리스에서 변경될 수 있다.

Released API를 사용하는 이유는 다음과 같다.

| 이유 | 설명 |
|---|---|
| 업그레이드 안정성 | 릴리스 간 변경 리스크를 줄인다. |
| Clean Core 유지 | 표준 코어 내부 구현에 직접 의존하지 않는다. |
| 클라우드 호환성 | Public Cloud 또는 Cloud-ready 확장 모델에 맞춘다. |
| 영향 분석 용이성 | 허용된 API 경계를 기준으로 의존성을 관리할 수 있다. |
| 유지보수성 | 내부 테이블/클래스 변경에 덜 민감한 설계를 만들 수 있다. |

### 4.3 Released API 판단 기준

초급자가 실습에서 확인해야 하는 판단 흐름은 다음이다.

```text
1. 내가 사용하려는 표준 객체가 무엇인가?
2. 이 객체가 외부 사용용으로 release되어 있는가?
3. ABAP language version check에서 허용되는가?
4. 대체 Released API가 있는가?
5. 없으면 직접 참조 대신 wrapper 또는 side-by-side 확장을 검토해야 하는가?
```

## 5. Clean Core란 무엇인가?

### 5.1 초급자용 정의

Clean Core는 SAP 표준 코어를 가능한 깨끗하게 유지하면서, 필요한 확장은 공개된 확장 포인트와 안정적인 API를 통해 구현하는 접근 방식이다.

초급자에게는 다음 비유가 유용하다.

```text
SAP 표준 코어 = 건물의 주요 구조물
커스텀 개발 = 내부 인테리어와 확장 공간
Clean Core = 기둥과 배관을 무단 변경하지 않고, 허용된 방식으로 확장하는 원칙
```

### 5.2 Clean Core가 중요한 이유

| 관점 | 의미 |
|---|---|
| 업그레이드 | 표준 변경 시 커스텀 영향이 줄어든다. |
| 운영 안정성 | SAP 내부 구현 변경에 덜 민감해진다. |
| 클라우드 전환 | S/4HANA Cloud 또는 ABAP Cloud 모델에 가까워진다. |
| 품질 관리 | ATC, API release check로 위반을 조기에 발견할 수 있다. |
| 장기 유지보수 | 개발자가 바뀌어도 구조와 의존성 기준이 명확하다. |

### 5.3 Clean Core를 깨는 대표 사례

| 사례 | 문제점 |
|---|---|
| SAP 표준 테이블 직접 UPDATE | 데이터 정합성, 권한, 비즈니스 로직 우회 위험 |
| Unreleased Function Module 직접 호출 | 릴리스 변경 시 시그니처/동작 변경 가능 |
| 표준 프로그램 Include 수정 | 업그레이드 충돌 가능성 매우 높음 |
| 내부 클래스 직접 사용 | 공개 계약이 아니므로 변경 리스크 큼 |
| 복사 개발 후 방치 | 표준 개선과 보안 패치를 따라가기 어려움 |
| 직접 DB 접근으로 비즈니스 로직 우회 | Validation, Authorization, Determination 누락 가능 |

## 6. Classic ABAP과 ABAP Cloud의 사고방식 차이

| 구분 | Classic ABAP 사고 | ABAP Cloud / Clean Core 사고 |
|---|---|---|
| 표준 객체 접근 | 접근 가능하면 사용 | Release 여부 확인 후 사용 |
| 데이터 변경 | 테이블 직접 변경 가능성을 검토 | Business Object/API를 통해 변경 |
| Enhancement | User Exit, BAdI, implicit enhancement 등 다양 | 공개된 extension point 중심 |
| 서비스 | Gateway OData V2, SEGW, RFC 등 혼재 | RAP + OData V4 중심 |
| 개발 도구 | SAP GUI 중심 | ADT 중심 |
| 품질 체크 | 사후 테스트 중심 | 정적 검사와 release check 선행 |
| 업그레이드 대응 | 영향 발생 후 수정 | 영향 가능성을 설계 단계에서 줄임 |

이 차이는 “기존 방식이 모두 틀렸다”는 뜻이 아니다. On-premise 환경에서는 여전히 Classic ABAP 자산이 많고, 실무에서는 공존이 필요하다. 다만 새 개발과 전략적 확장에서는 Clean Core와 ABAP Cloud 원칙을 기준으로 판단하는 것이 중요하다.

## 7. RAP 개발에서 Released API 원칙이 놓이는 위치

RAP 개발 흐름을 단순화하면 다음과 같다.

```text
Database Table
  ↓
Interface View Entity (ZI_*)
  ↓
Projection View Entity (ZC_*)
  ↓
Behavior Definition / Implementation
  ↓
Service Definition
  ↓
Service Binding
  ↓
OData V4 Service
```

ABAP Cloud와 Released API 원칙은 이 전체 흐름에 걸쳐 적용된다.

| RAP 계층 | Clean Core 관점의 질문 |
|---|---|
| DB Table | 표준 테이블을 직접 변경하지 않는가? |
| ZI_* Interface View | 내부 데이터 모델과 공개 범위가 분리되어 있는가? |
| ZC_* Projection View | 소비자에게 필요한 필드와 액션만 노출하는가? |
| Behavior Definition | 데이터 변경을 직접 SQL이 아니라 BO 동작으로 제어하는가? |
| Behavior Implementation | 사용 API가 released 상태인가? |
| Service Definition | 외부 공개 범위가 명확한가? |
| Service Binding | OData V4 서비스가 의도한 시나리오에 맞게 노출되는가? |

사용자 교육 규칙에 따라 RAP 예제에서는 항상 Interface View `ZI_*`와 Projection View `ZC_*`를 함께 제공해야 한다.

## 8. 최소 예제: Clean Core 관점의 RAP 객체 흐름

이번 모듈은 전체 RAP 구현 실습이 아니라 ABAP Cloud와 Released API 판단 원칙을 다루는 모듈이다. 따라서 예제는 최소 흐름과 판단 기준 중심으로 제공한다.

### 8.1 예제 시나리오

교육용 주문 요청 객체를 만든다고 가정한다.

```text
업무 요구사항:
- 주문 요청 번호, 고객 ID, 상태, 생성일자를 관리한다.
- 외부 소비자는 Projection View를 통해 필요한 필드만 조회한다.
- 데이터 변경은 RAP Behavior를 통해 수행한다.
- 표준 SAP 내부 테이블을 직접 UPDATE하지 않는다.
- 외부 API 또는 표준 객체 사용 시 Released API 여부를 확인한다.
```

### 8.2 Interface View 예시: `ZI_JHY_OrderRequest`

```abap
@EndUserText.label: 'Order Request Interface View'
@AccessControl.authorizationCheck: #CHECK
define root view entity ZI_JHY_OrderRequest
  as select from zjhy_ord_req
{
  key order_uuid      as OrderUUID,
      order_id        as OrderID,
      customer_id     as CustomerID,
      status          as Status,
      created_by      as CreatedBy,
      created_at      as CreatedAt,
      last_changed_at as LastChangedAt
}
```

이 Interface View는 내부 데이터 모델에 가깝다. 핵심은 `ZI_*`가 후속 Projection View와 Behavior Definition의 기반이 된다는 점이다.

### 8.3 Projection View 예시: `ZC_JHY_OrderRequest`

```abap
@EndUserText.label: 'Order Request Projection View'
@AccessControl.authorizationCheck: #CHECK
@Metadata.allowExtensions: true
define root view entity ZC_JHY_OrderRequest
  as projection on ZI_JHY_OrderRequest
{
  key OrderUUID,
      OrderID,
      CustomerID,
      Status,
      CreatedAt
}
```

Projection View는 소비자에게 공개할 모델이다. Clean Core 관점에서는 내부 구현 필드나 민감한 필드를 무분별하게 노출하지 않는 것이 중요하다.

### 8.4 Service Definition 예시

```abap
@EndUserText.label: 'Order Request Service Definition'
define service ZUI_JHY_ORDER_REQUEST {
  expose ZC_JHY_OrderRequest as OrderRequest;
}
```

### 8.5 Released API 판단 포인트

위 예제가 표준 객체를 참조하지 않는 단순 Z 객체라면 Released API 문제가 크게 드러나지 않을 수 있다. 하지만 실제 프로젝트에서는 다음 상황이 자주 발생한다.

```text
고객명 조회를 위해 표준 고객 테이블을 직접 읽고 싶다.
회사코드 텍스트를 표준 테이블에서 직접 가져오고 싶다.
판매오더 상태를 표준 내부 테이블에서 직접 참조하고 싶다.
표준 Function Module을 호출해 값을 계산하고 싶다.
```

이때 바로 표준 테이블이나 Function Module을 사용하지 말고, 다음 순서로 판단한다.

```text
1. 해당 업무 의미에 맞는 Released CDS View 또는 API가 있는가?
2. SAP Business Accelerator Hub 또는 ADT API 정보에서 released 여부를 확인했는가?
3. ABAP Cloud language version check에서 허용되는가?
4. Released API가 없으면 custom wrapper 또는 side-by-side extension이 가능한가?
5. 불가피하게 예외가 필요하다면 아키텍처 리뷰와 보류 기준을 문서화했는가?
```

## 9. ADT에서 확인해야 할 기본 포인트

ABAP Cloud와 Released API 원칙은 머릿속 규칙이 아니라 도구로 검증해야 한다.

### 9.1 ABAP Language Version

ADT에서 ABAP 객체 또는 패키지는 language version과 관련된 제약을 가질 수 있다.

초급자는 다음 식으로 이해하면 된다.

```text
Standard ABAP
  → 기존 ABAP 개발과 호환성이 넓은 방식
ABAP for Cloud Development
  → ABAP Cloud 원칙에 맞는 제한된 개발 방식
```

[추정] 실제 메뉴 위치와 명칭은 시스템 릴리스, ADT 버전, 권한, 패키지 설정에 따라 다를 수 있다. 교육 환경에서는 강사가 지정한 패키지와 객체 유형을 기준으로 확인한다.

### 9.2 Syntax Check와 ATC 메시지

ABAP Cloud 제약을 위반하면 다음과 유사한 메시지를 만날 수 있다.

```text
The use of object ... is not permitted in ABAP for Cloud Development.
Object ... is not released for use.
Statement ... is not allowed in this ABAP language version.
API ... is not released.
```

초급자는 오류 메시지를 “귀찮은 제한”으로 보지 말고, Clean Core 위반 가능성을 알려주는 설계 피드백으로 이해해야 한다.

### 9.3 API State 확인

Released API 여부를 확인할 때는 다음 정보를 확인한다.

| 확인 항목 | 의미 |
|---|---|
| API State | Released 여부 또는 사용 가능 상태 |
| Visibility | 외부 사용 가능 범위 |
| Package | 객체가 속한 소프트웨어 컴포넌트/패키지 |
| Release Contract | 어떤 소비자에게 어떤 방식으로 사용이 허용되는지 |
| Deprecation 여부 | 향후 사용 중단 예정인지 |

## 10. 오류 상황과 해결 흐름

### 10.1 오류 1: Unreleased API 사용

#### 상황

개발자가 표준 클래스를 호출했는데 ATC 또는 Syntax Check에서 사용 불가 메시지가 발생한다.

```abap
DATA(lo_obj) = cl_some_sap_internal_class=>get_instance( ).
```

#### 원인

해당 클래스가 SAP 내부 구현용이며 외부 사용용으로 release되지 않았을 수 있다.

#### 해결 흐름

```text
1. 해당 기능을 제공하는 Released API가 있는지 검색한다.
2. Released CDS View, released class/interface, business service를 우선 검토한다.
3. 대체 API가 없으면 요구사항을 재검토한다.
4. 불가피한 경우 아키텍처 리뷰에서 예외 여부를 판단한다.
5. 예외 사용은 문서화하고 업그레이드 리스크를 명시한다.
```

### 10.2 오류 2: 허용되지 않는 ABAP 문 사용

#### 상황

ABAP Cloud language version에서 특정 문법 또는 객체 사용이 제한된다.

#### 원인

해당 문법이 클라우드 개발 모델에서 허용되지 않거나 안정적 운영을 저해할 수 있다.

#### 해결 흐름

```text
1. 메시지의 금지 대상 statement를 확인한다.
2. ABAP Cloud에서 허용되는 대체 문법을 찾는다.
3. Local object 직접 접근보다 released API나 RAP BO 동작을 사용한다.
4. 필요 시 설계를 분리한다.
```

### 10.3 오류 3: 표준 테이블 직접 변경

#### 상황

커스텀 프로그램에서 SAP 표준 테이블에 직접 `UPDATE`, `INSERT`, `DELETE`를 수행하려고 한다.

#### 문제

표준 비즈니스 로직, 권한, Lock, Validation, Change Document, Event 처리를 우회할 수 있다.

#### 해결 흐름

```text
1. 해당 업무 객체의 표준 API 또는 RAP BO가 있는지 확인한다.
2. BAPI, released class, released CDS/action, business service를 검토한다.
3. 직접 DB 변경은 원칙적으로 금지 또는 예외 승인 대상으로 둔다.
4. 변경 이력과 권한 처리를 포함한 표준 경로를 사용한다.
```

### 10.4 오류 4: Projection View에 내부 필드 과다 노출

#### 상황

`ZC_*` Projection View에 내부 관리 필드, 기술 필드, 민감 필드가 모두 노출된다.

#### 문제

서비스 소비자에게 불필요한 내부 구현이 드러나고, API 변경 비용이 커진다.

#### 해결 흐름

```text
1. 소비자가 실제로 필요한 필드만 Projection에 남긴다.
2. 내부 필드는 Interface View 또는 Behavior 내부에서만 사용한다.
3. 노출 필드는 API 계약이라는 관점으로 검토한다.
4. 권한과 개인정보/민감정보 노출 여부를 확인한다.
```

## 11. Released API가 없을 때의 대안

실무에서는 원하는 기능에 딱 맞는 Released API가 없는 경우가 있다. 이때 바로 unreleased object를 사용하기보다 다음 대안을 검토한다.

| 대안 | 설명 | 적합한 상황 |
|---|---|---|
| 요구사항 조정 | 표준 API가 제공하는 범위에 맞게 기능을 단순화 | 초기 설계 단계 |
| Custom Wrapper | 내부 커스텀 로직을 안정적 인터페이스로 감싸기 | Z 객체 간 경계 정리 |
| Released CDS View 사용 | 직접 테이블 접근 대신 공개된 CDS API 사용 | 조회 중심 요구사항 |
| RAP BO Action 사용 | 데이터 변경을 BO 동작으로 노출 | 트랜잭션 처리 요구사항 |
| Side-by-side Extension | SAP BTP 등 외부 확장으로 분리 | Core 영향 최소화 필요 |
| 아키텍처 예외 승인 | 리스크를 문서화하고 제한적으로 허용 | 대체 수단이 없는 긴급/특수 상황 |

> 핵심: Released API가 없다는 이유만으로 unreleased object를 바로 사용하는 것은 Clean Core 관점에서 위험하다.

## 14. 강사용 설명 포인트

이 주제는 문법보다 설계 판단이 중요하다. 강의 시 다음 포인트를 강조한다.

### 14.1 “동작한다”와 “사용해도 된다”는 다르다

Classic ABAP 경험이 있는 학습자는 “Syntax Check가 통과하면 괜찮다”고 생각하기 쉽다. ABAP Cloud와 Clean Core에서는 현재 동작 여부보다 API 사용 계약이 중요하다.

```text
현재 접근 가능하다 ≠ 외부 사용이 허용되었다
현재 동작한다 ≠ 업그레이드 후에도 안전하다
```

### 14.2 Released API는 개발 제약이 아니라 유지보수 계약이다

제약이 많아 보이지만, 장기적으로는 업그레이드와 클라우드 전환 리스크를 줄이기 위한 계약이다.

### 14.3 RAP 객체는 API 계약으로 봐야 한다

특히 `ZC_*` Projection View와 Service Definition은 외부 소비자에게 공개되는 계약에 가깝다. 한 번 공개한 필드와 동작은 변경 비용이 크므로 신중해야 한다.

### 14.4 예외는 가능하지만 문서화되어야 한다

실무에서는 완벽한 Clean Core만으로 모든 요구사항을 해결하기 어려운 경우도 있다. 중요한 것은 예외를 무의식적으로 만드는 것이 아니라, 영향과 대안을 검토한 뒤 문서화하는 것이다.

## 15. 성능, 권한, 운영 안정성 관점

### 15.1 성능

Released API를 사용한다고 해서 자동으로 성능이 보장되는 것은 아니다. Projection View에서 불필요한 필드를 과다 노출하거나, Behavior Implementation에서 반복 호출을 남발하면 성능 문제가 생길 수 있다.

체크 포인트:

```text
필요한 필드만 조회하는가?
반복문 안에서 API를 과도하게 호출하지 않는가?
Projection View가 과도하게 넓지 않은가?
필요한 필터 조건을 서비스 소비 단계에서 제공하는가?
```

### 15.2 권한

RAP와 OData 서비스는 외부 소비 가능성이 높다. 따라서 다음을 반드시 확인한다.

```text
@AccessControl.authorizationCheck 설정이 적절한가?
DCL이 필요한가?
Behavior Authorization이 필요한가?
Service Binding 노출 대상이 통제되는가?
Projection View에 민감 필드가 포함되어 있지 않은가?
```

### 15.3 운영 안정성

운영 안정성은 다음과 연결된다.

| 항목 | 설명 |
|---|---|
| 업그레이드 영향 | Unreleased object 사용이 많을수록 영향 증가 |
| 장애 분석 | 공개 API 경계를 지키면 원인 분석이 쉬워짐 |
| 변경 관리 | API 계약이 명확해야 변경 범위 통제 가능 |
| 보안 | 직접 DB 변경과 내부 API 사용은 우회 위험 증가 |

## 16. 자가 진단 문제

### 16.1 객관식

#### Q1. Released API의 가장 적절한 설명은?

A. 개발자가 접근 가능한 모든 SAP 객체  
B. SAP 또는 API 소유자가 외부 사용을 허용한 안정적 API  
C. 성능이 가장 빠른 내부 테이블  
D. SAP GUI에서 조회 가능한 모든 Function Module  

**정답:** B

#### Q2. Clean Core 관점에서 가장 위험한 개발 방식은?

A. Projection View에서 필요한 필드만 노출한다.  
B. Service Definition에서 소비 대상 엔티티만 expose한다.  
C. 표준 SAP 테이블을 직접 UPDATE한다.  
D. ATC 메시지를 확인하고 대체 API를 찾는다.  

**정답:** C

#### Q3. RAP 개발에서 `ZC_*` Projection View의 주요 역할은?

A. 데이터베이스 테이블을 직접 생성한다.  
B. 외부 소비자에게 공개할 소비 계층을 정의한다.  
C. ABAP Package를 Transport한다.  
D. 시스템 Client를 변경한다.  

**정답:** B

### 16.2 단답형

#### Q1. “현재 접근 가능하다”와 “Released API이다”의 차이를 설명하시오.

**모범 답안:**  
현재 접근 가능하다는 것은 기술적으로 참조가 가능하다는 뜻일 뿐이다. Released API는 SAP 또는 API 소유자가 외부 사용을 허용하고 안정적 사용 계약을 제공한다는 의미이다. Clean Core 관점에서는 접근 가능 여부보다 release 여부가 중요하다.

#### Q2. ABAP Cloud에서 unreleased object 사용을 피해야 하는 이유를 설명하시오.

**모범 답안:**  
Unreleased object는 내부 구현용일 수 있으며 향후 릴리스에서 변경되거나 제거될 수 있다. 이를 직접 참조하면 업그레이드 시 커스텀 프로그램 오류와 유지보수 비용이 커질 수 있다.

#### Q3. Released API가 없을 때 바로 내부 객체를 쓰지 않고 검토해야 하는 대안을 세 가지 쓰시오.

**모범 답안:**  
요구사항 조정, Released CDS/API 검색, Custom Wrapper 설계, RAP BO Action 사용, Side-by-side Extension, 아키텍처 예외 승인 등을 검토할 수 있다.

## 17. 실무 리뷰 시나리오

다음 코드를 리뷰한다고 가정한다.

```abap
METHOD validate_order.
  SELECT SINGLE *
    FROM some_sap_internal_table
    WHERE key_field = @iv_key
    INTO @DATA(ls_internal).

  IF sy-subrc <> 0.
    reported-order = VALUE #( ( %msg = new_message_with_text(
                                  severity = if_abap_behv_message=>severity-error
                                  text     = 'Invalid order' ) ) ).
  ENDIF.
ENDMETHOD.
```

### 17.1 리뷰 질문

```text
1. some_sap_internal_table은 released API인가?
2. 직접 SELECT가 Clean Core 관점에서 허용 가능한가?
3. 동일 의미의 released CDS View 또는 BO API가 있는가?
4. Projection 또는 Service 계층에서 이 검증을 처리하는 것이 적절한가?
5. 해당 검증은 Validation, Determination, Action 중 어디에 두어야 하는가?
```

### 17.2 개선 방향 예

```text
1. 내부 테이블 직접 접근을 중단한다.
2. Released CDS View 또는 released business service를 검색한다.
3. 없으면 요구사항을 재검토하거나 custom validation table을 별도로 둔다.
4. 검증 로직은 RAP Validation에 위치시킨다.
5. 예외가 필요하면 아키텍처 리뷰 기록을 남긴다.
```

## 18. 핵심 요약

이번 모듈의 핵심은 다음과 같다.

```text
ABAP Cloud는 클라우드 준비형 ABAP 개발 모델이다.
Released API는 외부 사용이 허용된 안정적 API이다.
Clean Core는 SAP 표준 코어를 직접 오염시키지 않고 안정적인 확장 지점을 사용하는 원칙이다.
Classic ABAP에서 접근 가능했던 모든 객체가 ABAP Cloud에서 허용되는 것은 아니다.
RAP 개발에서도 ZI_*와 ZC_* 계층을 API 계약 관점으로 설계해야 한다.
Unreleased object 사용은 업그레이드와 운영 안정성 리스크를 만든다.
ATC, Syntax Check, API State 확인은 설계 품질을 높이는 도구이다.
```
