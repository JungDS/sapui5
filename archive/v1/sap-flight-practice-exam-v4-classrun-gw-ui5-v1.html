SAP Flight 통합 실습 시험 패키지 v4

요청 반영 요약

  • ClassRun 과제에서는 Report(Selection Screen) 완전 제외 (ADT에서 클래스 단독 실행 기준으로 재구성)
  • Gateway(OData V2): Flight 모델 기반으로 CRUD(생성/수정/삭제/조회)가 자연스러운 비즈니스 시나리오로 재설계
  • UI5 연동: 화면 구성/동작/바인딩/라우팅/검증/에러처리까지 “시험 중 오해가 없도록” 상세 스펙 제공
  • 문서 톤은 해설본/답안지 수준

0. 공통 전제(시험 환경 가정)

  • S/4HANA 기반, OData V2(Gateway/SEGW), SAPUI5(Fiori 스타일)
  • Flight 표준 테이블을 데이터 소스로 사용: SCARR, SPFLI, SFLIGHT, SBOOK, SCUSTOM, STRAVELAG
  • 교육/시험 환경에서 표준 데이터 변경이 허용된다고 가정하되, 실무 관점에서는 표준 테이블 직접 변경이 위험하다는 점을 “설계 해설”에 포함

1. D75AW/S4D400 – ClassRun 단독 “Flight KPI Analyzer” (정답지 수준, 단계형)

산출물: 실행 클래스 1개(예: ZCL_FLT_KPI_ANALYZER, IF_OO_ADT_CLASSRUN 구현)

핵심 정정: 본 과제는 Report를 만들지 않습니다. 입력은 Class 내부 “시나리오 파라미터(상수/로컬 변수)”로 제어합니다.

1-1. 요구 시나리오(입력값이 없는 ClassRun의 현실적 처리)

운영팀 요청: “최근 30일 기준” 또는 “지정한 CARRID/기간”으로 KPI를 콘솔(out)로 분석해달라.

정답 원칙: ClassRun에서 외부 입력 UI가 없으므로, 다음 중 1개를 채택하고 문서화합니다.

  1. Option A(권장, 시험 표준): main( ) 내부에 테스트용 입력을 로컬 상수로 정의하고, 핵심 로직은 run( is_sel )로 분리
  2. Option B: 클래스의 PUBLIC 메소드 set_selection( )으로 입력을 설정 가능하게 하고, main( )은 기본값으로 실행

채점 포인트: “입력은 테스트용”으로 제한하되, 로직이 재사용 가능하도록 API 계약(run)을 갖추는지.

1-2. 데이터 계약(정답 설계)

ty_selection(입력 구조) 최소 필드:

  • so_carr (range of SCARR-CARRID) – 비어있으면 전체 또는 특정 기본값
  • date_from, date_to (SFLIGHT-FLDATE) – 비어있으면 최근 30일
  • mode (SUMMARY/DETAIL)
  • page, size (DETAIL에서만 사용; default page=1 size=50)

ty_kpi_carrier(항공사 KPI) 최소 필드:

  • carrid, carrname
  • flights_cnt
  • seatsmax_sum, seatsocc_sum
  • occupancy_pct (소수 1자리 반올림 규칙 명시)
  • status(HIGH/MID/LOW)

ty_exception(이상치): reason_code, severity, carrid, connid, fldate, details

1-3. 문제(단계형) – 구현 순서 그대로 따라가면 완성되는 구성

문제 1. 클래스/메소드 뼈대(정답 구조)

  1. ZCL_FLT_KPI_ANALYZER 생성
  2. IF_OO_ADT_CLASSRUN 구현(메소드 main)
  3. PUBLIC 메소드 run( IMPORTING is_sel EXPORTING et_carrier et_ex et_detail ) 정의
  4. PRIVATE 메소드 분리: select_flight_raw( ), build_carrier_kpi( ), build_exceptions( ), render_out( )

문제 2. main( )의 “테스트용 입력” 표준 작성(정답 템플릿)

정답 템플릿(설계 설명)

  • 기본 실행: date_to=sy-datum, date_from=sy-datum-30
  • 특정 항공사 분석 시나리오: so_carr에 'LH' 등 1~2개 carrid
  • mode 기본 SUMMARY
  • DETAIL은 page/size 지정(예: 1/50)

중요: “입력 UI가 없다”는 사실을 코드 주석/문서에 명시하고, 학습자가 오해하지 않게 합니다.

문제 3. Flight Raw 조회(정답 패턴: JOIN + 최소 컬럼 + 필터)

  1. FROM SFLIGHT
  2. JOIN SCARR(항공사명), JOIN SPFLI(노선 도시)
  3. WHERE carrid IN so_carr(선택), fldate BETWEEN date_from AND date_to
  4. SELECT 컬럼 최소화: carrid, connid, fldate, seatsmax, seatsocc, carrname, cityfrom, cityto

문제 4. Carrier KPI 집계(정답: DB 집계 우선)

정답 선택지

  • 정답 A(권장): Open SQL GROUP BY carrid로 flights_cnt, seats sums를 DB에서 집계 → ABAP에서 occupancy/status 계산
  • 정답 B: ABAP에서 group/reduce로 집계(단, 대량 데이터에서 불리하므로 감점 가능)

occupancy 계산 정답: seatsmax_sum=0이면 occupancy=0 처리 + Exception 기록.

문제 5. Status(CASE)와 반올림 규칙(정답)

  • status: occupancy_pct >=85 HIGH, 50~84 MID, else LOW
  • 반올림: 소수 1자리(예: round(…, 1))로 통일

문제 6. Exception 생성(정답 최소 4개 규칙)

  • SEATSMAX=0
  • SEATSOCC > SEATSMAX
  • 결과 0건(조건 과도) – 정보성 warning
  • DETAIL 모드에서 page 범위 초과 – 사용자 입력 오류로 처리

문제 7. DETAIL 모드 페이징(정답 설계)

  • 정렬 기준 고정: carrid, connid, fldate
  • offset=(page-1)*size, up to size
  • OFFSET 미지원/제약 가정 시: 상위 N 조회 후 슬라이스(단, 비효율 경고 주석 필수)

문제 8. out 출력(정답: 블록 구조로 명확히)

  • Block 1: 입력 파라미터 요약(기간, carrid, mode)
  • Block 2: Carrier KPI Top N(예: revenue가 없으므로 occupancy desc 또는 flights_cnt desc)
  • Block 3: Exception 목록
  • DETAIL이면 Block 4: Flight Detail 페이지

문제 9. S4D400 리팩토링(정답 제출물)

  • 집계는 DB로, SELECT 컬럼 최소화, 중복 SELECT 제거
  • 개선 전/후 비교(호출 수/후처리량) 1페이지 텍스트로 제출

문제 10. 회귀 테스트 8개(정답 표)

입력/기대 결과/검증 방법을 표로 작성(예: 기간 기본값, 특정 carrid, 0건, seatmax=0 포함 시 exception 등).

2. GW100 – Gateway OData V2 CRUD 시나리오(Flight Booking Management) + UI5 연동

목표: Flight 모델에서 CRUD가 가장 자연스러운 대상은 “예약(Booking)”입니다. 따라서 SBOOK(예약)을 중심으로 서비스/화면을 설계합니다.

2-1. 비즈니스 시나리오(정답 수준 설명)

여행사 상담원이 고객 요청에 따라 예약을 생성/수정/취소(삭제)하고, 조회 화면(UI5)에서 필터/정렬/상세를 확인해야 합니다.

  • Create: 고객(Customer) + 항공편(Flight)을 선택하여 예약 생성
  • Read: 기간/항공사/고객 기준으로 예약 조회
  • Update: 예약의 클래스(좌석등급), 인원수, 메모(설명) 등 수정
  • Delete: 예약 취소(교육 환경에서는 Delete로 처리. 실무라면 Cancel 플래그가 더 안전)

2-2. 데이터 모델(정답 기준)

핵심 엔티티

  • BookingSet (주 엔티티, CRUD)
  • CustomerSet (SCUSTOM, 읽기 전용 – Value Help)
  • FlightSet (SFLIGHT(+SPFLI/SCARR 조인), 읽기 전용 – Value Help)

2-3. BookingSet Key 설계(정답 가이드)

SBOOK의 키 필드 조합은 시스템/버전에 따라 다를 수 있으므로, 시험에서는 아래 2가지 중 하나를 선택해 설계 근거를 명시합니다.

  1. 정답 A(권장): SBOOK의 실제 키 필드 조합을 그대로 사용 (예: CARRID/CONNID/FLDATE/BOOKID 등)
  2. 정답 B(교육용 단순화): BookingId를 단일 키처럼 취급(단, 실제 저장은 복합키로 매핑) – 단순화 이유 문서화

중요: “키가 불명확한 상태로 구현”은 오해를 낳으므로, 설계 문서에 반드시 키 필드를 명시하도록 문제에 포함합니다.

3. GW100 실습 문제(단계형 12문항, 정답지 수준)

문제 1. SEGW 프로젝트 생성 + 네이밍(정답)

  • Project: ZGW_FLT_BOOKING
  • Namespace: Z
  • Model Version: 1

문제 2. EntityType 정의(정답: 최소 필드)

Booking

  • Key: (선택한 키 설계에 따라) carrid, connid, fldate, bookid(또는 booking_id)

Customer(SCUSTOM)

  • Key: id

Flight(SFLIGHT 기반 View)

  • Key: carrid, connid, fldate
  • Fields: carrname, cityfrom, cityto, seatsmax, seatsocc

문제 3. Association/Navigation(정답)

  • Booking → Customer (1:1)
  • Booking → Flight (1:1)

해설: UI5에서 Value Help 및 Object Page 표시 시 Navigation이 있으면 구현이 단순해집니다(확장 시 $expand 활용).

문제 4. Service Generation + Runtime Artifacts 생성(정답 절차)

  1. Generate Runtime Objects
  2. DPC_EXT / MPC_EXT 생성 확인
  3. /IWFND/MAINT_SERVICE에서 등록 및 테스트 호출

문제 5. GET_ENTITYSET (BookingSet 조회) – 필터/정렬/페이징(정답)

필수 지원 Query Option: $filter, $orderby, $top, $skip, $count/inlinecount

정답 구현 기준:

  • $filter: carrid, customerid, fldate 범위(또는 created_at) 지원
  • $orderby: fldate desc, carrid asc 등 기본 정렬 지원
  • $top/$skip: DB 페이징 적용 (최대 top 제한 정책 예: 200)
  • $count: 동일 필터 조건으로 count 계산 (조건 불일치 금지)

문제 6. GET_ENTITY (Booking 단건 조회)(정답)

  • Key predicate로 단건 조회
  • 존재하지 않으면 404 성격의 오류 메시지(비즈니스 메시지 포함 가능)

문제 7. CREATE_ENTITY (예약 생성)(정답: 검증 포함)

필수 검증(정답 기준):

  • customerid 필수
  • carrid/connid/fldate(항공편 키) 필수
  • 해당 Flight가 존재하는지 확인(미존재 시 오류)
  • 중복 예약 방지(키 중복 시 오류)

정답 DB 처리: INSERT SBOOK (교육 환경 가정). 성공 시 생성된 키를 응답에 포함.

문제 8. UPDATE_ENTITY (예약 수정)(정답: ETag 선택)

  • 수정 가능 필드만 허용(예: class, amount, memo 등) – 키 변경 금지
  • ETag는 선택(가산점): If-Match 검증을 적용하고 충돌 시 오류

문제 9. DELETE_ENTITY (예약 취소)(정답)

  • 교육: DELETE SBOOK
  • 실무 해설: 상태 플래그(CANCELLED)로 논리 삭제가 더 안전하다는 코멘트 포함

문제 10. CustomerSet/FlightSet (Value Help용 읽기 전용)(정답)

  • CustomerSet: 검색($filter name/city) + top 제한
  • FlightSet: 기간 필터 필수(대량 방지), carrid/route 필터 지원

문제 11 (추가). 오류/메시지 설계(정답 제출물)

  • DB 실패는 “시스템 오류”로 분리
  • 메시지 클래스/코드 체계를 문서화(예: ZGW_BOOKING 001~050)

문제 12 (추가). 서비스 테스트 스크립트(정답)

4. SAPUI5 연동 과제(정답지 수준 스펙) – “Booking Management App”

목표: 위에서 만든 OData V2 서비스(ZGW_FLT_BOOKING)를 UI5 앱과 연동하여 CRUD를 수행합니다.

4-1. 앱 구조(정답)

  • App Type: SAPUI5 (Fiori 스타일)
  • OData Model: sap.ui.model.odata.v2.ODataModel (manifest.json에 dataSources 설정)
  • Routing: Master-Detail (or List-Detail) 패턴
  • View 2개 + Fragment 2개 권장:
    • View1: BookingList.view.xml
    • View2: BookingDetail.view.xml
    • Fragment: BookingCreateEditDialog.fragment.xml
    • Fragment: ValueHelpCustomer.fragment.xml / ValueHelpFlight.fragment.xml

4-2. 화면 1: Booking List (정답 스펙)

목적: 예약 목록 조회 + 필터 + 정렬 + 생성/삭제 진입

4-2-1. 상단 Filter Bar(또는 Simple Filter 영역) 구성

  • 항공사(CARRID) – 입력 또는 Select
  • 고객(CustomerId) – Value Help 버튼
  • 기간(Date From/To) – DateRangeSelection
  • 검색 버튼(Search) / 초기화 버튼(Reset)

4-2-2. 리스트 테이블(필수 컬럼)

  • Booking Key(표시용: carrid/connid/fldate/bookid)
  • CustomerName
  • Route(cityfrom-cityto)
  • Class
  • Amount + Currency
  • Status(있다면) 또는 created_at

4-2-3. UX 동작(정답 기준)

  • 행 클릭 → Detail 라우팅 (key로 route)
  • 테이블은 Growing(페이징) 사용: growing=true, threshold=20 (서버 $top/$skip 사용)
  • 상단 버튼:
    • Create → Create/Edit Dialog 열기
    • Delete → 선택 행 삭제(Confirmation 필수)
    • Refresh → 재조회
  • BusyIndicator: 조회/저장 중 화면 Busy 표시

4-3. 화면 2: Booking Detail (정답 스펙)

목적: 단건 상세 조회 + 수정 + 저장

4-3-1. Object Header(또는 Simple Header)

  • Title: Booking {carrid}/{connid} {fldate}
  • Subtitle: Customer {customerName}

4-3-2. Form 섹션(필수 필드)

  • Flight 정보: carrid, connid, fldate (읽기 전용)
  • Customer: customerid + customername (customerid는 Value Help 가능, 수정 허용 여부는 설계로 결정)
  • Class: Select(예: Y/C/F 또는 시스템 값)
  • Amount: Input + CurrencyText
  • 메모(있다면): TextArea

4-3-3. 버튼/동작(정답 기준)

  • Edit → 입력 가능 상태로 전환
  • Save → OData update (submitChanges 또는 update)
  • Cancel → 변경 취소(model resetChanges)
  • Delete → 단건 삭제 후 목록으로 이동

4-4. Create/Edit Dialog (정답 스펙)

생성 시 필수 흐름:

  1. Customer Value Help로 고객 선택(필수)
  2. Flight Value Help로 항공편 선택(필수: carrid/connid/fldate 세트)
  3. Class/Amount 입력
  4. Save → OData CREATE_ENTITY 호출

Value Help 요구:

  • Customer VH: 검색창(이름/도시), 결과 리스트(고객ID/이름/도시)
  • Flight VH: 기간 필터 필수, 결과 리스트(carrid/connid/fldate/route/좌석현황)

4-5. 오류/메시지 처리(정답 기준)

  • MessageManager 연동: OData 오류 응답을 메시지 팝업/MessageStrip로 표시
  • 사용자 입력 오류(검증 실패)는 필드 ValueState로 표시 + 메시지 텍스트 제공
  • 저장 실패 시 변경 유지 여부 정책 명시(기본: 유지, 사용자가 수정 후 재시도)

4-6. 시험 채점 체크리스트(정답)

  • 목록 조회(필터/정렬/페이징) 동작
  • 생성(Create) – Value Help 포함
  • 수정(Update) – 저장/취소 동작
  • 삭제(Delete) – 확인창 포함
  • 에러 메시지 표시(서버 검증 오류 포함)
  • 라우팅/바인딩 깨짐 없이 안정 동작

5. 출제자용 보완 메모(오해 방지)

  • ClassRun은 “UI 입력이 없다”는 점을 문제 서두에 명확히 고지합니다.
  • Gateway CRUD에서 표준 테이블(SBOOK)을 수정하는 것은 실무에서 권장되지 않으나, 교육 환경에서는 허용된다는 가정을 문제에 명시합니다.
  • 키 설계는 시스템마다 차이가 있을 수 있으므로, “실제 키 확인 후 설계서에 명시”를 문제의 필수 제출물로 둡니다.
