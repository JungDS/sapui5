SAP 실습 시험 문제 세트 (하루 종일 푸는 통합형)

대상 과목: D75AW, GW100, S4D400, S4D401, S4D437

핵심 컨셉: 단위문제 나열이 아니라 “하나의 시나리오”를 기반으로, 과목별 산출물이 연결되도록 구성합니다.

0. 공통 배경 시나리오 (Flight Model 기반)

당신은 항공사/여행사 통합 운영팀의 개발 담당입니다. 현업 요구는 다음 3가지입니다.

  1. 운항 현황을 빠르게 조회하고(대시보드),
  2. 예약/좌석/매출을 집계해서 KPI를 보고하며,
  3. 외부 채널(UI 또는 API)로 데이터를 안정적으로 제공해야 합니다.

데이터는 SAP 표준 Flight 모델 테이블을 사용합니다: SCARR, SPFLI, SFLIGHT, SBOOK, SAIRPLANE, SCUSTOM, STRAVELAG

모든 과제는 S/4HANA 기준으로 작성합니다.

공통 요구(전체 과제 공통)

  • 가능한 경우 Code Pushdown(CDS/Open SQL) 우선
  • “조회-가공-노출”을 분리(레이어 분리)하여 확장/유지보수 가능하게 설계
  • 결과 검증을 위해 테스트 데이터/검증 포인트를 과제 내에 포함
  • 성능: 불필요한 SELECT 반복/LOOP inside SELECT 금지

1. D75AW (ABAP Workbench) - “운항 KPI 리포트 클래스”

목표: ABAP 기본기 + New Syntax + ITAB 설계/성능 + OO 구조화

산출물: 실행 가능한 클래스 1개(권장: IF_OO_ADT_CLASSRUN) 또는 리포트 1개

1-1. 프로그램/클래스 요구사항

클래스명(예): ZCL_FLT_KPI_REPORT

실행 시 다음을 콘솔(out) 또는 ALV로 출력합니다.

  1. Carrier KPI 요약 (항공사별)
  2. Route KPI 요약 (노선별)
  3. Exception 목록 (비정상/주의 데이터)

1-2. 선택화면(SSCR) 요구사항

  • CARRID (다중 선택 가능)
  • CONNID (선택)
  • Flight Date 범위 (SFLIGHT-FLDATE)
  • 출력 모드: SUMMARY/DETAIL (라디오버튼)
  • 페이징: 페이지 번호, 페이지 크기(기본 50)

1-3. 조회/집계 규칙

  • 좌석 점유율(%) = (SUM(SEATSOCC) / SUM(SEATSMAX)) * 100
  • 매출(예시) = SBOOK의 (LOCCURAM) 합계를 노선/항공사별 집계
  • 노선(Route)은 SPFLI(CARRID, CONNID) 기준
  • 가능하면 집계는 SQL/GROUP BY로 처리

1-4. 구현 단계(필수)

  1. 데이터 모델 정의: 결과 구조(ABAP TYPES) 설계 (Deep/Flat 구분)
  2. 조회 메소드 분리: get_flight_raw( ), get_booking_raw( ), get_kpi( ) 등
  3. Internal Table 타입 선택:
    • KPI 결과는 KEY로 빠르게 찾을 수 있도록 적절한 테이블 타입(SORTED/HASHED) 선택
    • 선택 이유를 주석으로 명시
  4. New Syntax 사용:
    • DATA(...), VALUE, CORRESPONDING, REDUCE 또는 GROUPING 활용
  5. 페이징 구현:
    • OFFSET + UP TO(또는 ABAP SQL의 페이징 지원 방식)를 사용
    • 지원이 어려운 경우 “대안 페이징”을 제시하고 구현(정렬/상위 N개/삭제 방식 등)
  6. Exception 목록:
    • SEATSMAX=0 인 항목, 날짜 범위 밖 데이터 등 “이상치”를 별도 표로 출력

1-5. 평가 포인트(채점 기준 예시)

  • 레이어 분리(조회/가공/출력) 및 가독성
  • 집계의 SQL 처리 비율
  • ITAB 타입 선택의 합리성
  • 페이징 정확성
  • 예외/엣지 케이스 처리

2. GW100 (SAP Gateway) - “Flight KPI OData V2 서비스”

목표: SEGW 모델링 + DPC_EXT 구현 + Query Option + $count/inlinecount + ETag 기초

산출물: OData V2 서비스 1개(프로젝트 1개)

2-1. 서비스 시나리오

외부 채널(예: Fiori/UI5, 외부 파트너)이 KPI와 상세 데이터를 조회할 수 있어야 합니다.

2-2. 모델 설계(권장 엔티티)

  • CarrierKpiSet: 항공사 KPI (CARRID 기준)
  • RouteKpiSet: 노선 KPI (CARRID+CONNID 기준)
  • FlightDetailSet: 항공편 상세 (CARRID+CONNID+FLDATE+FLIGHTNO 등 키 구성은 설계)

2-3. 기능 요구사항(필수)

  1. GET_ENTITYSET:
    • $filter: CARRID, CONNID, 날짜(FLDATE) 지원
    • $orderby: KPI 값(매출/점유율) 정렬 지원
    • $top/$skip: 페이징 지원
    • $select: 성능 고려(가능한 범위에서)
  2. $count / inlinecount:
    • UI에서 전체 건수를 표시할 수 있도록 지원
    • 정확한 구현이 어려우면 구현 불가 사유 + 대안 설계 제시
  3. ETag(선택/가산점):
    • FlightDetail 업데이트 시 동시성 제어 개념 적용(If-Match 활용)
    • 실제 업데이트 대상이 표준 테이블이면 “읽기 전용”으로 제한하고 설계로 대체

2-4. 구현 단계(필수)

  1. SEGW 프로젝트 생성 → EntityType/Set 정의
  2. 모델-백엔드 매핑 전략 정의 (CDS/뷰/직접조회 중 선택)
  3. DPC_EXT에서 Query Option 파싱 및 적용
  4. 성능 점검: SELECT 반복 제거, 필요한 필드만 조회

2-5. 검증 시나리오(테스트 케이스 예시)

  • CARRID='LH' AND FLDATE between A and B → top 20 orderby Revenue desc
  • skip=20 top=20 → 2페이지 데이터 일관성
  • $count 호출 시 동일 필터 조건 반영

3. S4D400 (ABAP in S/4HANA) - “Pushdown 리팩토링 과제”

목표: HANA 친화적 설계 + New Open SQL + Code Pushdown 리팩토링

산출물: 1번(D75AW) KPI 리포트를 성능 개선한 버전(동일 클래스 내 리팩토링 또는 V2 클래스)

3-1. 리팩토링 미션

현재 KPI 리포트가 “LOOP 안 SELECT”, “중복 SELECT”, “ABAP 측 집계”로 느립니다. 아래를 수행하시오.

3-2. 요구사항(필수)

  1. 집계 Pushdown:
    • 매출/점유율 집계를 Open SQL GROUP BY 또는 CDS로 이동
    • ABAP LOOP 집계는 금지(예외 시 이유와 최소화 전략 명시)
  2. 페이징 최적화:
    • OFFSET 지원 가능 시 DB 페이징 사용
    • 미지원/제약 시 “정렬+키 기반 Seek 방식” 대안 설계 제시
  3. 필드 최소 조회:
    • SELECT * 제거, 필요한 컬럼만
    • JOIN 컬럼/조건 최적화
  4. 성능 비교 리포트:
    • 개선 전/후 예상 병목(정성)과 개선 근거를 문서화(주석/README 형식)

3-3. 가산점

  • UNION/CASE/CAST 등을 활용한 “단일 SQL로 처리”
  • 대량 데이터에서의 ITAB 타입/키 설계로 후처리 최소화

4. S4D401 (CDS Advanced) - “CDS + UI Annotation 패키지”

목표: CDS 레이어링(Interface/Projection) + Annotation + Metadata Extension

산출물: CDS 뷰 2개(ZI_*, ZC_*) + Metadata Extension 1개

4-1. CDS 설계 목표

OData/UI에서 소비 가능한 “Flight KPI” 데이터모델을 CDS로 표준적으로 설계하시오.

4-2. 필수 구성

  • ZI_FlightKpi (Interface View):
    • SCARR/SPFLI/SFLIGHT/SBOOK 기반
    • JOIN + 집계 + CASE + 산술식 포함
    • 금액/통화 Annotation 적용
    • 가능하면 파라미터(날짜 범위 또는 기준통화 등) 적용
  • ZC_FlightKpi (Projection View):
    • UI/Consumption 중심 Annotation을 Projection에 배치
    • 검색(Search) 필드 지정
    • List Report/ Object Page를 의도한 FieldGroup/Facet 구성
  • Metadata Extension:
    • Section 3개로 분리(Facet)
    • Key+Description / 주요 KPI / 감사필드(ChangedAt/ChangedBy 등) 분리

4-3. UI 요구(예시)

  • Header: 항공사명 + KPI 요약(매출/점유율)
  • Identification: 핵심 키/기간
  • Facets:
    • Section 1: Key + Description
    • Section 2: Customer/Date/Status 성격의 필드(예: 기간, 상태, 카운트)
    • Section 3: 기타(감사/추가 KPI)

4-4. 검증 포인트

  • ZI와 ZC의 역할 분리가 명확한가
  • Annotation이 올바른 레이어에 배치되었는가
  • 집계/계산 필드가 DB에서 처리되는가

5. S4D437 (RAP & Extensibility) - “Flight Alert 관리 BO”

목표: RAP Managed BO 설계 + Behavior + Validation/Determination + Clean Core 사고

산출물: RAP BO 1세트(Interface/Projection/Behavior/Service Definition/Binding)

5-1. 시나리오

KPI 분석 결과, 특정 항공사/노선에 대해 “주의(Alert)”를 등록/해제하고 추적하려 합니다.

표준 테이블을 직접 수정하는 것이 아니라, 확장 테이블(고객 테이블)에 Alert를 저장하는 방식으로 설계합니다(Clean Core).

5-2. 데이터 모델(권장)

커스텀 테이블(예): ZFLT_ALERT

  • Key: AlertId (UUID 권장) 또는 (CARRID, CONNID, FLDATE) 조합
  • Fields:
    • CARRID, CONNID, FLDATE(또는 기간), Severity(LOW/MED/HIGH), Reason
    • Status(OPEN/CLOSED), Owner, CreatedAt/By, ChangedAt/By
    • Reference KPI Snapshot(매출/점유율 등 일부 저장)

5-3. RAP 요구사항(필수)

  1. Managed Scenario로 BO 생성
  2. Behavior:
    • Create/Update/Delete 허용
    • Action: CloseAlert (Status를 CLOSED로 전환)
    • Validation:
      • Severity는 지정된 값만
      • OPEN 상태에서만 Close 가능
    • Determination:
      • Create 시 CreatedAt/By 자동 세팅
      • Update 시 ChangedAt/By 자동 세팅
  3. Projection Layer 분리(ZI_*/ZC_* + projection behavior)
  4. Service Definition/Binding으로 OData 노출

5-4. Clean Core 체크(필수 서술형)

  • 왜 표준 Flight 테이블을 직접 업데이트하면 안 되는지
  • 확장 테이블/Side-by-side/Released API 관점에서의 대안
  • 운영/업그레이드 안정성 관점의 설명

6. “하루 종일 풀 수 있는” 추천 진행 순서

  1. D75AW: KPI 리포트 기본 구현(조회/집계/출력/페이징)
  2. S4D400: 성능 리팩토링(Pushdown/필드최소화/페이징 개선)
  3. S4D401: 동일 KPI를 CDS로 표준 레이어링(ZI/ZC + UI Annotation)
  4. GW100: KPI/상세 조회용 OData V2 구현(Query Option, count)
  5. S4D437: Alert BO를 RAP로 구축(운영/확장 아키텍처까지 설명)

7. 제출물 체크리스트

  • ABAP 클래스/리포트(소스 + 실행 스크린샷 또는 out 결과)
  • CDS 정의서(ZI/ZC + Metadata Extension)
  • Gateway 프로젝트(엔티티 설계, DPC_EXT 핵심 구현 설명)
  • RAP BO(Behavior/Service Binding, Action/Validation/Determination)
  • 성능/아키텍처 설명 문서(간단한 Markdown/주석)
