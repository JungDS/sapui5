Gateway / OData V2 CRUD 입문

SEGW 기반 OData V2 서비스에서 EntitySet, MPC/DPC, CRUD 메서드, Gateway Client 테스트와 오류 처리 흐름을 초급자 기준으로 정리한다.

P0 Gateway OData V2 예상 50~60분
01 · 큰 그림

Gateway는 SAP 데이터를 HTTP API로 노출하는 관문이다

Gateway OData V2 개발은 SAP 내부의 데이터와 로직을 외부 소비자가 호출할 수 있는 HTTP API로 만드는 작업이다. 초급자는 처음부터 모든 클래스와 메서드를 외우기보다, 요청이 들어와 EntitySet과 DPC_EXT 메서드를 거쳐 응답으로 돌아가는 흐름을 먼저 이해해야 한다.

1
Model 정의

SEGW에서 Entity Type, Entity Set, Key, Property를 정의한다.

2
Runtime Artifact 생성

MPC, DPC, MPC_EXT, DPC_EXT 클래스를 생성한다.

3
DPC_EXT 구현

GET_ENTITYSET, GET_ENTITY, CREATE_ENTITY 같은 CRUD 메서드에 로직을 작성한다.

4
서비스 등록

/IWFND/MAINT_SERVICE에서 서비스를 등록하고 활성화한다.

5
Gateway Client 테스트

$metadata, EntitySet, CRUD 요청을 순서대로 테스트한다.

04 · GET_ENTITYSET

목록 조회는 필터와 반환 테이블을 중심으로 구현한다

GET_ENTITYSET은 여러 건을 조회해 EntitySet으로 반환하는 메서드다. 실무에서는 $filter, $top, $skip, 정렬, 페이징 등을 고려하지만 초급 단계에서는 먼저 조회 조건과 반환 구조를 명확히 한다.

METHOD flightset_get_entityset.

  SELECT carrid,
         connid,
         fldate,
         price,
         currency
    FROM sflight
    INTO CORRESPONDING FIELDS OF TABLE @et_entityset
    UP TO 100 ROWS.

ENDMETHOD.
실습 기준 처음에는 단순 SELECT로 응답 구조를 확인하고, 이후 $filter 처리와 페이징을 추가한다. API는 화면보다 먼저 단독 테스트되어야 한다.
05 · GET_ENTITY

단건 조회는 Key 값을 정확히 읽는 것이 핵심이다

GET_ENTITY는 URL에 포함된 Key를 기준으로 한 건을 조회한다. 초급자가 자주 놓치는 부분은 Key 이름과 Entity Property 이름이 일치하는지, 타입 변환이 필요한지 확인하는 것이다.

METHOD flightset_get_entity.

  DATA lv_carrid TYPE sflight-carrid.
  DATA lv_connid TYPE sflight-connid.
  DATA lv_fldate TYPE sflight-fldate.

  READ TABLE it_key_tab INTO DATA(ls_key) WITH KEY name = 'Carrid'.
  IF sy-subrc = 0.
    lv_carrid = ls_key-value.
  ENDIF.

  SELECT SINGLE carrid,
                connid,
                fldate,
                price,
                currency
    FROM sflight
    WHERE carrid = @lv_carrid
      AND connid = @lv_connid
      AND fldate = @lv_fldate
    INTO CORRESPONDING FIELDS OF @er_entity.

ENDMETHOD.
06 · CUD 구현 관점

생성, 수정, 삭제는 요청 Body와 Key 처리 기준이 다르다

CREATE_ENTITY

요청 Body를 읽어 신규 데이터를 만든다. Key가 서버에서 채번되는지, 클라이언트가 보내는지 먼저 결정한다.

UPDATE_ENTITY

URL Key로 대상 데이터를 찾고, Body의 변경 값을 반영한다. 전체 변경과 부분 변경의 기준을 확인한다.

DELETE_ENTITY

URL Key 기준으로 삭제한다. 실제 삭제인지 삭제 플래그 처리인지 업무 기준을 먼저 정한다.

METHOD flightset_create_entity.

  DATA ls_input TYPE zcl_zflight_mpc=>ts_flight.

  io_data_provider->read_entry_data(
    IMPORTING
      es_data = ls_input ).

  er_entity = ls_input.

ENDMETHOD.
07 · Gateway Client 테스트

테스트는 $metadata → EntitySet → CRUD 순서로 진행한다

  1. /IWFND/MAINT_SERVICE에서 서비스가 등록되어 있는지 확인한다.
  2. Gateway Client에서 /$metadata를 호출해 EntityType과 EntitySet을 확인한다.
  3. 목록 조회 URL로 EntitySet이 응답하는지 확인한다.
  4. 단건 조회 URL에서 Key Predicate가 정상 동작하는지 확인한다.
  5. POST 요청으로 CREATE_ENTITY가 호출되는지 확인한다.
  6. PUT 또는 MERGE 요청으로 UPDATE_ENTITY가 호출되는지 확인한다.
  7. DELETE 요청으로 DELETE_ENTITY가 호출되는지 확인한다.
  8. 오류가 발생하면 HTTP Status, 응답 Body, SAP Message, Error Log를 함께 확인한다.
08 · 오류 처리

Gateway 오류는 HTTP 상태와 SAP 메시지를 함께 봐야 한다

증상가능한 원인확인 위치
404 Not Found서비스 등록 누락, EntitySet 이름 오류, URL 오류/IWFND/MAINT_SERVICE, $metadata
405 Method Not Allowed해당 EntitySet에 Method 구현 또는 허용이 맞지 않음DPC_EXT 메서드, Gateway Client Method
500 Internal Server ErrorABAP 예외, SELECT 오류, 타입 변환 오류/IWFND/ERROR_LOG, ST22, ABAP Debugger
응답은 200이지만 데이터가 비어 있음조회 조건 오류, 원천 데이터 없음, 필드 매핑 불일치DPC_EXT Debugging, SQL Console, 응답 Body
초급자 주의 HTTP 200만 보고 성공으로 판단하면 안 된다. 응답 Body, Entity Key, Error Message, 반환 필드명이 화면 Binding과 맞는지까지 확인한다.
09 · 학습 완료 체크

다음 단계로 넘어가기 전에 확인한다

  1. Entity Type과 Entity Set의 차이를 설명한다.
  2. MPC_EXT와 DPC_EXT의 역할 차이를 설명한다.
  3. GET_ENTITYSET과 GET_ENTITY의 차이를 설명한다.
  4. CREATE_ENTITY에서 요청 Body를 읽는 위치를 설명한다.
  5. Gateway Client에서 $metadata와 EntitySet을 순서대로 테스트한다.
  6. HTTP 404, 405, 500 오류의 대표 원인과 확인 위치를 구분한다.
  7. UI5 오류를 보기 전에 Gateway 서비스 단독 테스트를 수행한다.
