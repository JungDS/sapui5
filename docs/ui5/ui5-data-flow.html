SAPUI5 데이터 흐름과 Messaging 아키텍처

앱의 데이터 흐름은 화면, 모델, 서버, 메시지 계층을 함께 봐야 안정적으로 이해된다. 이 문서는 입력값과 서버 응답이 화면 메시지로 이어지는 구조를 참고자료 형식으로 정리한다.

Stage 7 Docs Data Flow Architecture
01 · 계층

데이터 흐름은 화면, 모델, 서버 세 층으로 봅니다

화면 컨트롤은 사용자의 입력과 표시를 담당하고, 모델은 화면과 데이터 소스를 연결한다. 서버는 업무 데이터와 검증 결과를 제공한다. 메시지는 이 세 층에서 발생한 오류나 안내를 사용자가 이해할 수 있는 형태로 연결하는 별도 흐름이다.

1
View

Input, Table, Form 같은 컨트롤이 값을 표시하고 입력을 받는다.

2
Model

또는 이 View와 데이터 구조를 연결한다.

3
Service

또는 RAP 서비스가 조회, 저장, 검증 결과를 반환한다.

4
Message

오류와 안내가 MessageModel, MessagePopover, 필드 상태로 표현된다.

02 · 이벤트

바인딩과 이벤트는 서로 다른 책임을 가집니다

은 데이터와 화면을 연결하는 선언이고, 이벤트는 사용자의 행동에 반응하는 함수다. 초급자는 이벤트 함수 안에서 모든 값을 직접 읽고 쓰려 하기 쉽지만, 화면 표시 자체는 바인딩에 맡기는 편이 안정적이다.

구분책임예시
데이터를 화면에 표시하고 변경을 반영한다.items="{/SalesOrderSet}"
Event사용자 행동에 반응해 라우팅, 저장, 필터를 실행한다.press=".onSave"
Message검증 결과와 서버 응답을 사용자에게 전달한다.MessagePopover
03 · 메시지 유형

Messaging은 오류를 사용자가 이해할 수 있게 연결합니다

메시지는 단순 알림이 아니라 사용자의 다음 행동을 안내해야 한다. Error는 저장을 막는 문제, Warning은 확인이 필요한 문제, Success는 작업 완료, Information은 참고 안내로 구분한다.

  • Error: 필수값 누락, 형식 오류, 서버 업무 규칙 위반
  • Warning: 저장은 가능하지만 사용자가 확인해야 하는 상태
  • Success: 생성, 저장, 삭제 완료
  • Information: 작업 조건이나 후속 안내
04 · 주의점

메시지 흐름을 놓치면 저장 오류가 사용자에게 숨겨집니다

  • 서버 오류를 콘솔에만 남기지 않는다.
  • 필드 오류는 가능한 해당 필드와 연결한다.
  • Batch 요청에서는 여러 메시지가 한 번에 돌아올 수 있음을 고려한다.
  • 성공 메시지는 실제 서버 저장이 완료된 뒤 표시한다.
05 · 완료 체크

데이터 흐름을 다음 항목으로 확인합니다

  1. View, Model, Service, Message의 역할을 구분한다.
  2. Binding과 Event의 책임 차이를 설명한다.
  3. 서버 오류를 UI 메시지로 연결해야 하는 이유를 설명한다.
