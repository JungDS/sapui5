CDS View에서 OData 노출까지

Interface View, Projection View, Association, Service Definition, Service Binding의 연결 구조를 초급 개발자 관점에서 정리한다.

Stage 7ABAP 개발CDS / OData배포자: 정훈영
01 · 아키텍처

CDS는 데이터 모델이고 OData는 외부 소비를 위한 서비스 계층입니다

CDS View는 SAP HANA와 ABAP Dictionary 위에서 의미 있는 데이터 모델을 정의한다. OData는 그 모델을 UI5, Fiori Elements, 외부 시스템이 호출할 수 있는 HTTP 기반 서비스로 노출한다. 실무에서는 데이터 모델과 서비스 노출 책임을 분리하는 것이 중요하다.

표준 의도 Interface View는 재사용 가능한 안정 계층, Projection View는 소비 목적에 맞춘 노출 계층으로 보는 것이 좋다.
02 · 계층

ZI_*와 ZC_*를 분리하면 변경 영향도를 줄일 수 있습니다

Interface View · ZI_*

테이블 또는 표준 View를 기반으로 핵심 필드, Association, Semantics를 정의한다. 여러 소비 View가 재사용할 수 있는 기반이다.

Projection View · ZC_*

화면, API, 분석 등 특정 소비 목적에 맞춰 필드와 Association을 노출한다. UI Annotation도 이 계층에 두는 편이 관리하기 쉽다.

Service Definition

어떤 Entity를 서비스에 포함할지 선언한다. 외부에 보여줄 모델의 경계를 정하는 단계다.

Service Binding

OData V2/V4 등 프로토콜과 런타임 노출 방식을 결정하고 publish한다.

03 · 예제

Flight 모델은 CDS와 OData 흐름을 설명하기 좋은 예제입니다

@EndUserText.label: 'Interface View 항공사'
define view entity ZI_JHY_Carrier
  as select from scarr
{
  key carrid   as Carrid,
      carrname as Carrname,
      currcode as Currcode,
      url      as Url
}

@EndUserText.label: 'Projection View 항공사'
define view entity ZC_JHY_Carrier
  as projection on ZI_JHY_Carrier
{
  key Carrid,
      Carrname,
      Currcode,
      Url
}

교육에서는 반드시 Interface View와 Projection View를 함께 보여주는 편이 좋다. 학생들이 처음부터 소비 계층과 재사용 계층의 차이를 이해할 수 있기 때문이다.

04 · 주의점

OData 노출은 CDS 생성의 마지막 단계일 뿐입니다

  • 키 필드가 안정적이지 않으면 OData Entity 식별이 흔들린다.
  • 수량과 금액 필드는 Unit, Currency Semantics를 함께 지정한다.
  • Association Cardinality를 실제 데이터 관계와 맞춘다.
  • 권한 체크가 필요한 경우 Access Control과 서비스 노출 범위를 함께 검토한다.
05 · 완료 체크

다음 단계로 가기 전 확인합니다

  1. Interface View와 Projection View의 역할 차이를 설명할 수 있다.
  2. Association이 OData Navigation으로 연결되는 흐름을 설명할 수 있다.
  3. Service Definition과 Service Binding의 역할을 구분할 수 있다.
  4. Gateway Client 또는 Browser에서 Metadata와 EntitySet을 확인할 수 있다.
