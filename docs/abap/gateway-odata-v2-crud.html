Gateway / OData V2 CRUD 입문

SEGW 기반 OData V2 서비스에서 EntitySet, MPC/DPC, DPC_EXT CRUD 메서드, Gateway Client 테스트 흐름을 초급자 관점에서 이해한다.

Stage 7 Pilot ABAP 개발 Gateway 배포자: 정훈영
01 · 역할

Gateway는 SAP 데이터를 HTTP API로 열어주는 관문입니다

개발에서는 SAP 내부의 테이블, BAPI, 클래스, CDS 결과 등을 외부에서 호출 가능한 OData V2 서비스로 노출한다. 초급자는 먼저 Entity, EntitySet, Service Document, Metadata, DPC_EXT의 역할을 구분해야 한다.

핵심 관점 Gateway는 단순한 URL 생성기가 아니다. URI로 들어온 요청을 ABAP 로직으로 연결하고, 그 결과를 OData 응답 구조로 변환하는 런타임 계층이다.
02 · 구조

MPC는 모델, DPC는 데이터 처리를 담당합니다

MPC / MPC_EXT

Model Provider Class는 Entity Type, EntitySet, Association 같은 서비스 메타데이터 구조를 담당한다. 일반적으로 SEGW가 기본 클래스를 생성하고, 필요 시 MPC_EXT에서 메타데이터 보강을 한다.

DPC / DPC_EXT

Data Provider Class는 실제 조회, 생성, 수정, 삭제 로직을 담당한다. 실무에서는 DPC_EXT의 GET_ENTITYSET, GET_ENTITY, CREATE_ENTITY, UPDATE_ENTITY, DELETE_ENTITY를 재정의한다.

1
HTTP Request

브라우저, UI5, Postman, Gateway Client에서 OData URL을 호출한다.

2
Gateway Runtime

요청 URI와 HTTP Method를 분석해 적절한 DPC_EXT 메서드로 라우팅한다.

3
ABAP Logic

SELECT, BAPI, 클래스 호출 등으로 데이터를 읽거나 변경한다.

4
OData Response

ABAP 구조와 Internal Table이 OData 응답으로 직렬화되어 반환된다.

03 · CRUD 매핑

HTTP Method와 DPC_EXT 메서드를 함께 이해합니다

업무 동작 HTTP Method DPC_EXT 메서드 초급자 확인 포인트
목록 조회 GET *_GET_ENTITYSET 필터, 정렬, 페이징 처리를 고려한다.
단건 조회 GET *_GET_ENTITY Key Predicate에서 키 값을 읽는다.
생성 POST *_CREATE_ENTITY 요청 Payload를 읽고 신규 데이터를 만든다.
수정 PUT / PATCH *_UPDATE_ENTITY 전체 수정과 부분 수정의 차이를 구분한다.
삭제 DELETE *_DELETE_ENTITY 삭제 전 권한과 참조 데이터를 확인한다.
04 · 실습 흐름

SEGW 개발은 모델 정의 후 런타임 클래스를 확장하는 순서로 진행합니다

  1. 1
    Project 생성

    SEGW에서 Gateway Project를 만들고 패키지, 설명, 담당자를 정리한다.

  2. 2
    Entity Type / EntitySet 정의

    노출할 데이터 구조와 Key 필드를 정의한다. EntitySet 이름은 UI5에서 호출할 목록 리소스 이름이 된다.

  3. 3
    Runtime Object 생성

    MPC, DPC, MPC_EXT, DPC_EXT 클래스를 생성한다.

  4. 4
    DPC_EXT 메서드 재정의

    조회와 변경 로직을 DPC_EXT에 구현한다. 표준 생성 클래스는 직접 수정하지 않는다.

  5. 5
    Service 등록 및 테스트

    /IWFND/MAINT_SERVICE에서 서비스를 등록하고 /IWFND/GW_CLIENT에서 호출을 검증한다.

05 · 코드 감각

GET_ENTITYSET에서는 결과 Internal Table을 채우는 흐름을 먼저 봅니다

DPC_EXT 예시 · 목록 조회
METHOD carrier_get_entityset.

  SELECT carrid,
         carrname,
         currcode,
         url
    FROM scarr
    INTO CORRESPONDING FIELDS OF TABLE @et_entityset.

ENDMETHOD.

실제 프로젝트에서는 필터, 권한, 예외 메시지, 페이징 처리를 함께 고려해야 한다. 하지만 초급 단계에서는 먼저 “요청이 DPC_EXT 메서드로 들어오고, et_entityset에 결과를 채운다”는 구조를 이해하는 것이 중요하다.

06 · 주의사항

Generated Class와 Extension Class를 구분하지 못하면 유지보수가 어려워집니다

주의 SEGW가 생성한 기본 MPC/DPC 클래스에 직접 로직을 넣는 방식은 피한다. 재생성 시 변경이 손실될 수 있으므로, 실무 로직은 MPC_EXT/DPC_EXT에 작성하는 것이 기본 원칙이다.
체크리스트
  • EntitySet 이름과 UI5 호출 경로가 일치하는가?
  • Key 필드가 Metadata에 정확히 정의되어 있는가?
  • DPC_EXT 메서드가 올바른 EntitySet에 매핑되어 있는가?
  • 오류 발생 시 Gateway Client에서 메시지를 확인했는가?
  • 서비스 등록 후 metadata cache를 갱신했는가?
07 · 정리

Gateway CRUD는 URL, HTTP Method, DPC_EXT 메서드의 대응 관계를 이해하는 것이 출발점입니다

Gateway OData V2 개발은 처음에는 SEGW 화면과 클래스가 많아 복잡해 보인다. 그러나 구조를 나누면 모델은 MPC, 데이터 처리는 DPC, 실무 확장은 EXT 클래스, 테스트는 Gateway Client라는 흐름으로 정리할 수 있다.
