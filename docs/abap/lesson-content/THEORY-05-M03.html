학습 목표

지난 Lesson에서 FORM에 값을 전달했습니다. 이번에는 SAP 시스템에 등록된 재사용 기능인 Function Module을 CALL FUNCTION으로 호출하는 기본 구조를 배웁니다. Importing, Exporting, Changing, Tables 파라미터의 방향 감각을 잡습니다.

1. 지난 시간 연결: 내 프로그램 밖의 기능을 빌려 쓰기 🧰

FORM은 같은 프로그램 안에서 코드를 나누는 방법입니다. 그런데 여러 프로그램이 함께 써야 하는 기능이라면 한 프로그램 안의 FORM만으로는 부족합니다. SAP에는 시스템 전체에서 호출할 수 있는 재사용 기능 단위가 있습니다. 그것이 Function Module입니다.

Function Module은 Function Group 안에 저장되는 전통적인 ABAP 재사용 단위입니다. 표준 SAP도 많은 Function Module을 제공하고, 고객사도 필요한 경우 커스텀 Function Module을 만들 수 있습니다.

Function Module은 “시스템 공용 도구함에 들어 있는 기능 버튼”처럼 생각하면 됩니다.

REPORT zcall_function_basic.

DATA gv_week TYPE scal-week.

CALL FUNCTION 'DATE_GET_WEEK'
  EXPORTING
    date = sy-datum
  IMPORTING
    week = gv_week
  EXCEPTIONS
    date_invalid = 1
    OTHERS       = 2.

IF sy-subrc = 0.
  WRITE: / '현재 주차:', gv_week.
ELSE.
  WRITE: / '주차 계산 실패'.
ENDIF.

위 예제는 표준 Function Module DATE_GET_WEEK를 호출해 현재 날짜가 몇 번째 주인지 계산합니다. 날짜를 Function Module로 보내고, 결과 주차를 받아 출력합니다.

3. EXPORTING과 IMPORTING 방향 헷갈리지 않기 🔄

CALL FUNCTION을 처음 보면 EXPORTING과 IMPORTING 이름이 헷갈릴 수 있습니다. 호출하는 프로그램 입장에서 생각하면 아래처럼 기억하세요.

  • EXPORTING: 내 프로그램이 Function Module에게 보내는 값입니다.
  • IMPORTING: Function Module이 계산해서 내 프로그램으로 돌려주는 값입니다.
  • Changing: 값을 보내고, Function Module 안에서 바뀐 값을 다시 받는 경우입니다.
  • Tables: 여러 줄 데이터 테이블을 주고받는 오래된 방식입니다. 현대 ABAP에서는 다른 방식도 많이 사용합니다.
⚠️

방향은 “Function Module 기준 이름”으로 이해하세요

Function Module 정의 화면에서는 Importing이 함수 안으로 들어오는 값, Exporting이 함수 밖으로 나가는 값입니다. 그런데 CALL FUNCTION 문에서는 호출자가 값을 보내는 구역이 EXPORTING으로 보입니다. 처음에는 혼란스럽지만 예제를 여러 번 보면 익숙해집니다.

같은 값이라도 호출자 쪽에서는 EXPORTING(보냄), Function Module 쪽에서는 Importing(받음)으로 불립니다. 이름은 항상 “그 코드를 쓰는 쪽 기준”입니다.

4. EXCEPTIONS와 SY-SUBRC로 결과 확인하기 ✅

Function Module은 실패할 수 있습니다. 그래서 EXCEPTIONS 구역에서 가능한 예외 결과를 숫자로 매핑하고, 호출 후 sy-subrc를 확인합니다.

  • sy-subrc = 0: 보통 정상 성공
  • sy-subrc = 1: 예제에서는 date_invalid에 해당
  • sy-subrc = 2: 그 외 예외

Chapter 2에서 배운 SY-SUBRC가 여기서 다시 등장합니다. 외부 기능을 호출한 뒤에는 성공했는지 바로 확인하는 습관이 중요합니다.

5. 정상 흐름과 오류 흐름으로 확인하기 🔎

  • ✅ 정상 흐름: 필요한 EXPORTING 값을 넘기고, IMPORTING 결과를 받은 뒤 sy-subrc = 0이면 결과를 사용합니다.
  • ❌ 필수 파라미터 누락: Function Module이 요구하는 값을 넘기지 않으면 문법 오류나 실행 오류가 발생할 수 있습니다.
  • ❌ 결과 확인 누락: sy-subrc를 확인하지 않고 결과값을 믿으면 실패 상황을 놓칠 수 있습니다.
  • ❌ 표준 오해: 표준 Function Module이라고 해서 모든 환경에서 사용 권장이라는 뜻은 아닙니다. 릴리스 상태와 대체 API를 확인해야 할 수 있습니다.

미니 실습에서는 DATE_GET_WEEK처럼 입력과 출력이 단순한 Function Module을 호출하고, 성공/실패 메시지를 나눠 출력해보면 좋습니다.

6. 실무에서 조심해야 할 점 🚨

⚠️

Function Module은 강력하지만, 아무거나 호출하면 안 됩니다

표준 Function Module 중에는 오래된 것, 내부 사용 목적, 권장되지 않는 것이 섞여 있을 수 있습니다. 실무에서는 문서, 릴리스 상태, 대체 Class/API, 고객사 사용 기준을 확인해야 합니다. 단순히 “검색해서 나오니까 호출”은 위험합니다.

또한 Tables 파라미터 방식은 오래된 코드에서 자주 보지만, 현대 ABAP에서는 Internal Table을 명확한 타입으로 Importing/Exporting하거나 Class Method를 사용하는 설계도 많습니다. 이번 Lesson은 CALL FUNCTION 구조를 읽기 위한 기초입니다.

예외 처리도 가볍게 보면 안 됩니다. Function Module 내부에서 예외가 발생했는데 호출문의 EXCEPTIONS에 해당 예외도, OTHERS도 매핑되어 있지 않으면 프로그램이 런타임 오류로 강제 종료될 수 있습니다. “조용히 넘어가겠지”가 아니라 정반대입니다.

7. 미니 실습: 표준 기능 빌려 쓰기 🧪

✍️

실습 과제

  1. 예제의 DATE_GET_WEEK 호출 Report를 만들어 실행하고, 현재 주차가 출력되는지 확인합니다.
  2. date = sy-datum 대신 PARAMETERS로 날짜를 입력받아 넘기도록 바꿔봅니다.
  3. 일부러 잘못된 날짜 값을 넘겨 sy-subrc가 어떻게 바뀌는지, 실패 메시지가 출력되는지 확인합니다.
  4. 위 관계도에서 자신이 보낸 값과 받은 값이 어느 구역을 지나는지 손으로 짚어가며 설명합니다.

완료 조건: 성공/실패 두 경우 모두 실행해보고, sy-subrc 값에 따라 다른 메시지가 출력되면 성공입니다.

9. 확인 퀴즈와 정답/해설 ✅

  1. CALL FUNCTION 문에서 EXPORTING 구역에 적는 값은 누가 누구에게 보내는 값인가요?
  2. Function Module 내부에서 예외가 발생했는데 호출문에 EXCEPTIONS 매핑(특히 OTHERS)이 없다면 어떻게 될까요?
  3. Function Module 호출이 성공했는지 확인하는 시스템 필드는 무엇인가요?
정답/해설 보기
  1. 호출자가 Function Module에게 보내는 값입니다. 같은 값이 Function Module 정의 쪽에서는 Importing으로 보입니다.
  2. 처리되지 않은 예외로 간주되어 런타임 오류(강제 종료)가 날 수 있습니다. 조용히 무시되는 것이 아니므로 OTHERS까지 매핑하고 sy-subrc를 확인해야 합니다.
  3. sy-subrc입니다. 0이면 성공, EXCEPTIONS에 매핑한 숫자면 해당 예외가 발생한 것입니다.

10. 한눈에 정리 🏁

📝

오늘의 핵심만 딱 잡기

  • Function Module은 시스템 전체에서 재사용할 수 있는 전통적인 ABAP 기능 단위입니다.
  • CALL FUNCTION은 Function Module을 호출하는 문법입니다.
  • EXPORTING은 호출자가 Function Module로 보내는 값, IMPORTING은 호출자가 돌려받는 값입니다.
  • CHANGING은 값을 보내고 바뀐 값을 다시 받는 방식입니다.
  • 호출 후 SY-SUBRC와 예외 처리를 확인해야 합니다.
