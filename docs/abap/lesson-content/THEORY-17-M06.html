학습 목표

DB 테이블이 아니라 ABAP 메모리의 Internal Table을 SELECT로 조회하는 SELECT FROM @itab을 배웁니다. 이미 들고 있는 데이터를 SQL처럼 가공하는 감각을 익힙니다.

1. 지난 시간 연결: 이미 가진 데이터를 또 가공하고 싶다 🔁

DB에서 데이터를 한 번 가져와 Internal Table에 담았습니다. 그런데 그걸 다시 그룹으로 묶거나 JOIN하고 싶을 때가 있습니다. DB를 또 조회하긴 아깝죠(이미 메모리에 있으니까요).

최신 ABAP은 Internal Table을 SELECT의 대상으로 삼을 수 있게 해줍니다. SELECT ... FROM @itab입니다.

2. Internal Table을 SQL로 조회 ✍️

" gt_flights는 이미 메모리에 있는 Internal Table
SELECT carrid, SUM( price ) AS total
  FROM @gt_flights AS f          "DB가 아니라 메모리 테이블에서
  GROUP BY carrid
  INTO TABLE @DATA(lt_summary).
  • FROM @gt_flights: @가 붙은 ABAP 테이블을 조회 대상으로 삼습니다.
  • GROUP BY·JOIN 등: DB 조회처럼 집계·결합 문법을 그대로 쓸 수 있습니다.
💡

비유: 장바구니를 다시 정리

마트(DB)에 다시 가지 않고, 이미 담아온 장바구니(Internal Table) 안에서 품목별로 다시 분류·합산하는 것과 같아요. DB 왕복을 아낍니다.

3. 언제 유용할까? 🤔

  • ✅ 이미 조회해 둔 데이터를 다시 집계·정렬·필터하고 싶을 때.
  • ✅ DB를 또 때리지 않고 메모리에서 가공해 왕복을 줄이고 싶을 때.
  • ✅ 두 Internal Table을 JOIN하고 싶을 때.

4. 정상 흐름과 오류 흐름 🔍

  • ✅ 정상: 메모리 테이블을 SELECT로 가공해 새 결과 테이블을 얻습니다.
  • ❌ 오류 1 — 착각: "어차피 SQL이니 DB만큼 빠르겠지" → 메모리 테이블이 아주 크면 느릴 수 있습니다. DB의 인덱스 같은 최적화가 없습니다.
  • ❌ 오류 2: 원본이 비어 있는데 결과를 기대 → 빈 결과. 입력 테이블 상태를 확인하세요.

5. 실무에서 조심할 점 🚨

⚠️

"DB 조회"와 "메모리 조회"를 헷갈리지 마세요

SELECT FROM @itab은 문법이 DB 조회와 똑같아서, 진짜 DB를 조회하는 것으로 착각하기 쉽습니다. 이건 이미 가진 데이터를 메모리에서 가공하는 것입니다. 따라서 "DB에 없는 최신 데이터"는 여기서 나오지 않습니다. 또 거대한 메모리 테이블을 복잡하게 가공하면 성능이 나빠질 수 있으니, 정말 메모리 가공이 맞는지 판단하세요.

6. 한눈에 정리 🏁

📝

오늘의 핵심만 딱 잡기

  • SELECT FROM @itab으로 메모리의 Internal Table을 SQL처럼 조회합니다.
  • GROUP BY·JOIN 등 SQL 문법을 그대로 쓸 수 있습니다.
  • DB 왕복을 줄이고 이미 가진 데이터를 재가공할 때 유용합니다.
  • DB 조회가 아니라 메모리 가공임을 잊지 않습니다.
