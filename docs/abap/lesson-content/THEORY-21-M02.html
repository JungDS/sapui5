학습 목표

RAP의 데이터 기반인 Interface View(ZI_)를 RAP 관점에서 설계하는 법을 배웁니다. 트랜잭션(쓰기)을 염두에 둔 키·필드 설계의 포인트를 익힙니다.

1. 지난 시간 연결: 읽기용에서 "쓰기까지" 되는 모델로 ✏️

Chapter 20의 Interface View는 주로 읽기(조회)를 위한 것이었습니다. RAP에서는 같은 ZI_가 생성·수정의 기반(Business Object의 뿌리)이 됩니다. 그래서 설계 시 몇 가지를 더 신경 써야 합니다.

define root view entity ZI_Travel
  as select from ztravel
{
  key travel_id,
      agency_id,
      customer_id,
      begin_date,
      end_date,
      booking_fee,
      @Semantics.amount.currencyCode: 'CurrencyCode'
      total_price,
      currency_code,
      // 관리 필드(생성자/시각 등)
      created_by,
      last_changed_at
}
  • root view entity: RAP Business Object의 최상위(루트) 뷰임을 표시.
  • 키 설계: 트랜잭션의 기준이 되는 키(예: travel_id)를 명확히.
  • 관리 필드: 생성자·변경시각 등은 나중에 Determination으로 자동 채울 수 있게 자리만 둠.
💡

읽기 모델 vs 쓰기 기반의 차이

조회 전용이면 필요한 필드만 골라도 됩니다. 하지만 RAP의 쓰기 기반은 "이 업무 데이터의 한 건"을 온전히 표현해야 해서, 키·필수 필드·관리 필드를 빠짐없이 설계하는 것이 중요합니다.

3. 부모-자식 구조 (Composition 맛보기) 🧩

여행(Travel) 한 건에 여러 예약(Booking)이 딸리는 것처럼, RAP는 부모-자식 구조를 Composition으로 표현합니다. Chapter 20의 Association과 비슷하지만, "자식의 생사가 부모에 묶인다"는 더 강한 관계입니다. 이번 단계에서는 "루트 뷰가 있고 그 아래 자식이 붙는다" 정도만 기억하면 됩니다.

4. 정상 흐름과 오류 흐름 🔍

  • ✅ 정상: root view entity + 명확한 키 + 필요한 필드 → 트랜잭션의 튼튼한 기반.
  • ❌ 오류 1: 키 설계가 모호 → 생성·수정 시 어떤 행인지 특정 못 해 동작이 꼬임.
  • ❌ 오류 2: 읽기 편의로 필드를 과하게 가공해 두면, 쓰기 시 원본 매핑이 어려워짐.

5. 실무에서 조심할 점 🚨

⚠️

데이터 모델이 곧 앱의 뼈대

RAP에서 ZI_(데이터 모델)는 단순 조회 뷰가 아니라 앱 전체의 뼈대입니다. 여기서 키나 구조를 잘못 잡으면 위에 얹는 Behavior·Service·화면이 전부 영향을 받습니다. Chapter 1~4의 DDIC·관계 설계 기본기가 RAP에서 그대로 위력을 발휘하니, 데이터 모델을 탄탄히 잡는 데 시간을 쓰세요.

6. 미니 실습: Root와 Composition 후보 찾기 🧪

이번 실습은 ZI_ View를 단순 조회 View가 아니라 RAP Business Object의 뼈대로 보는 연습입니다.

✍️

실습 과제

  1. 여행 예약 예제를 가정하고 Root가 될 엔티티와 하위 엔티티 후보를 나눕니다.
  2. Root View가 가져야 할 key, 텍스트 필드, 상태 필드 후보를 적습니다.
  3. Composition을 넣어야 하는 관계와 Association만으로 충분한 관계를 구분합니다.

완료 조건: Interface View가 RAP의 재사용 가능한 비즈니스 데이터 기반이라는 점을 설명할 수 있으면 성공입니다.

8. 확인 퀴즈와 정답/해설 ✅

  1. RAP에서 Root View는 어떤 역할을 하나요?
  2. Composition과 Association을 같은 의미로 쓰면 왜 위험한가요?
  3. ZI_에 UI 전용 Annotation을 많이 넣지 않는 이유는 무엇인가요?
정답/해설 보기
  1. Business Object의 중심 노드로, 트랜잭션과 하위 노드 관계의 기준점이 됩니다.
  2. Composition은 소유 관계와 생명주기까지 암시할 수 있지만, Association은 일반 관계 탐색에 가깝습니다.
  3. ZI_는 재사용 가능한 데이터 기반이어야 하기 때문입니다. UI 요구는 ZC_나 Metadata Extension 쪽에서 처리하는 편이 안전합니다.
