학습 목표

이번 Lesson에서는 Domain 위에 업무 의미, Field Label, F1 Help를 얹는 Data Element를 설계합니다. 목표는 “같은 기술 재질이라도 왜 다른 이름표가 필요할 수 있는가?”를 설명하고, SE11에서 Data Element를 직접 생성·활성화하는 흐름을 시뮬레이션하는 것입니다.

1. Data Element는 값에 업무 이름표를 붙인다

지난 Lesson의 Domain은 값의 재질을 정했습니다. 예를 들어 CHAR 3이라는 규격만 있으면 시스템은 세 자리 문자를 저장할 수 있다는 사실은 알지만, 사용자는 그 값이 항공사인지 공항인지 회사 코드인지 알 수 없습니다.

Data Element는 이 빈칸을 채웁니다. 기술 속성은 Domain에서 가져오고, 그 위에 업무 의미, 화면 라벨, F1 설명을 붙여 테이블 필드와 프로그램이 재사용할 수 있는 의미 있는 타입으로 만듭니다.

Domain은 재질, Data Element는 의미입니다. 테이블 필드와 ABAP 변수는 보통 의미가 붙은 Data Element를 통해 타입을 참조합니다.

SAP Learning은 Data Element, Structure, Database Table 같은 Dictionary 객체를 ABAP 코드 타입으로 사용할 수 있지만 Domain은 Data Element의 기반으로만 쓰인다고 설명합니다.

2. Data Element 설계는 세 묶음으로 본다

Data Element 화면은 항목이 많아 보이지만 초급 단계에서는 아래 세 묶음만 잡으면 됩니다. 어떤 기술 타입을 받을지, 화면에 어떤 텍스트를 줄지, 사용자가 F1을 눌렀을 때 무엇을 보여줄지가 핵심입니다.

Data Element 설계 판단표

3. Field Label 4종은 화면 공간별 이름표다

SAP Help의 Data Element 생성 절차는 Field label 탭에서 short, medium, long field label과 title을 관리한다고 설명합니다. 즉 하나의 의미를 화면 공간에 맞게 여러 길이로 준비하는 것입니다.

할인율 Data Element 라벨 예시

라벨 예시 쓰이는 상황
Short 할인 공간이 매우 좁은 입력 필드
Medium 할인율(%) 일반 Selection Screen 필드 라벨
Long 고객 특별 할인율 상세 화면처럼 설명 폭이 충분한 곳
Heading 할인% 리스트, 테이블, ALV 컬럼 제목
⚠️

라벨은 “예쁜 이름”이 아니라 재사용 자산입니다

한 Data Element를 여러 화면과 리포트가 참조할 수 있습니다. 라벨 하나를 대충 쓰면 같은 객체를 쓰는 다른 화면의 사용자 경험까지 같이 나빠질 수 있습니다.

4. SE11에서 Data Element를 만들고 코드 화면을 미리 본다

SAP GUI 상단 명령창에 SE11 또는 /nSE11을 입력합니다. 초기 화면에서 Data Type을 선택하고 Data Element 이름을 입력한 뒤 Create를 누르면 Data Element 유지보수 화면으로 들어갑니다. 아래 sandbox는 이 흐름을 줄인 실습입니다. ABAP TYPE Target에 Domain 이름을 넣어 실패시킨 뒤, Data Element 이름으로 되돌려 활성화해 보세요. 코드에서 직접 타입으로 쓰는 이름은 Domain이 아니라 Data Element입니다.

T-Code: SE11 Data Element
ABAP Dictionary: Data Element Maintenance
버튼을 누르면 Data Element 활성화 결과와 ABAP 코드/화면 라벨 미리보기가 출력됩니다.

5. F1 Help와 F4 Help는 질문이 다르다

F1 Help는 “이 필드가 무슨 뜻인가?”에 답합니다. Data Element 문서와 짧은 설명은 사용자가 필드 의미를 이해하는 데 도움을 줍니다.

F4 Help는 “어떤 값을 고를 수 있는가?”에 답합니다. 값 후보를 찾게 하려면 Search Help, Fixed Value, Foreign Key 같은 값 도움 설계를 따로 봐야 합니다.

사용자 질문으로 구분하기

F1 Help
  • 질문: 이 입력칸은 무엇을 뜻하나요?
  • 내용: 필드 의미, 업무 기준, 입력 시 주의점
  • 위치: Data Element documentation
F4 Help
  • 질문: 어떤 값 중에서 고르면 되나요?
  • 내용: 후보 값 목록, 검색 조건, 텍스트 설명
  • 위치: Search Help 또는 DDIC 값 도움 연결

6. 같은 Domain, 다른 Data Element가 필요한 순간

실무 판단의 핵심은 “기술 규격만 같은가, 의미까지 같은가?”입니다. 기술 규격만 같으면 Domain을 재사용할 수 있지만, 화면 라벨과 업무 설명이 다르면 Data Element는 분리해야 합니다.

재사용 판단 예시

상황 Domain 판단 Data Element 판단
출발 공항과 도착 공항 재사용 가능 둘 다 공항 코드 재질 분리 라벨과 F1 설명이 다릅니다.
여러 테이블의 회사 코드 재사용 표준 코드 규격 표준 우선 의미까지 같으면 표준 Data Element를 찾습니다.
개발자 내부 임시 변수 주의 전역 DDIC 객체가 과할 수 있음 주의 로컬 타입이나 클래스 public type이 더 적합할 수 있습니다.
표준 Data Element의 라벨을 직접 바꿔도 될까?

가볍게 보면 안 됩니다. 같은 Data Element를 쓰는 다른 화면까지 영향을 받을 수 있습니다. 표준 텍스트를 조정해야 하는 상황은 별도 확장·텍스트 보강 절차와 영향 범위를 확인해야 합니다.

8. 확인 퀴즈

  1. Domain과 Data Element를 “재질”과 “의미”로 나눠 설명해보세요.
  2. Field Label 4종은 어떤 화면 문제를 해결하나요?
  3. F1 Help와 F4 Help의 질문 차이는 무엇인가요?
  4. 같은 CHAR 3 규격이면 항상 같은 Data Element를 써야 할까요?
  5. ABAP 코드에서 Domain을 직접 타입으로 쓰는 것이 왜 맞지 않을까요?
정답/해설 보기
  1. Domain은 기술 재질, Data Element는 업무 의미입니다. Domain은 타입과 길이, Data Element는 라벨과 설명을 담당합니다.
  2. 화면 공간별 이름표 문제입니다. 좁은 필드, 일반 입력 화면, 상세 화면, 컬럼 제목에 맞는 텍스트를 중앙에서 제공합니다.
  3. F1은 의미 설명, F4는 값 찾기입니다. 하나는 문서, 하나는 후보 값 탐색입니다.
  4. 아니요. 기술 규격만 같고 업무 의미가 다르면 Data Element는 분리합니다.
  5. Domain은 Data Element의 기반 객체이기 때문입니다. 코드와 필드는 의미가 붙은 Dictionary 타입을 참조합니다.
