학습 목표

Data Element가 Domain 위에 어떻게 의미(Semantic)와 필드 라벨(Field Label)을 입히는지 익힙니다. 왜 테이블 필드가 Domain이 아니라 Data Element를 직접 참조하는지 이해합니다.

1. Data Element는 부품에 붙이는 "이름표" 🏷️

앞에서 만든 Domain은 "3자리 문자"라는 재질만 알려줄 뿐, 그게 무슨 뜻인지는 모릅니다. 같은 CHAR 3 재질이라도 '항공사 코드'일 수도, '통화 코드'일 수도 있죠.

Data Element(데이터 엘리먼트)는 이 재질 위에 의미와 이름표를 붙이는 부품입니다.

🔗

3단 구조를 기억하세요

Domain(재질: CHAR 3) ← Data Element(의미: 항공사 코드 + 라벨) ← Table Field(실제 사용)

밑에서부터 위로 쌓아 올리는 상향식(Bottom-Up) 구조입니다.

2. 필드 라벨(Field Label) — 화면에 뜨는 글자 📋

Data Element에는 길이별로 4종류의 필드 라벨을 등록합니다. 화면 폭에 따라 SAP가 알아서 골라 보여줍니다.

  • Short(짧은): 10자 — 좁은 컬럼 머리글
  • Medium(중간): 20자
  • Long(긴): 40자
  • Heading(제목): 리포트·ALV 컬럼 제목용
이 라벨 하나만 잘 등록해 두면, 이 Data Element를 쓰는 모든 화면·리포트·ALV가 자동으로 같은 한글 제목을 달고 나옵니다. 화면마다 글자를 따로 입력할 필요가 없습니다.

또한 사용자가 입력 필드에서 F1(도움말)을 누르면 Data Element에 연결된 문서(Documentation)가 떠서, 이 필드가 무엇인지 설명해 줍니다.

3. 왜 테이블은 Domain이 아니라 Data Element를 쓸까? 🤔

테이블 필드를 만들 때는 항상 Data Element를 지정합니다. Domain을 직접 쓰지 않습니다. 이유는 분업 때문입니다.

  • ✅ Data Element 재사용: 'BUKRS(회사코드)' Data Element를 100개 테이블이 공유 ➔ 라벨·F1 도움말·검색도움말이 전부 일관됨
  • ✅ Domain 분리의 이점: 재질(길이·타입)은 Domain이, 의미(라벨·뜻)는 Data Element가 따로 관리 ➔ 한쪽만 바꿔도 다른 쪽은 안전

4. 실무에서 주의할 점 🚨

⚠️

"의미가 다르면 Data Element도 따로"

길이·타입이 똑같다고 해서 아무 Data Element나 재사용하면 안 됩니다. '출발 공항'과 '도착 공항'은 같은 CHAR 3여도, 라벨과 의미가 다르므로 보통 별도의 Data Element로 만듭니다. 의미를 기준으로 나눠야 화면·F4 도움말이 헷갈리지 않습니다.

반대로 표준 Data Element(BUKRS, MATNR 등)가 내 의미와 정확히 맞으면, 새로 만들지 말고 그대로 재사용하는 것이 유지보수에 유리합니다.
