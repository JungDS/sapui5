학습 목표

지난 Lesson에서 만든 Domain 위에 Semantic Meaning과 Field Label을 입히는 Data Element를 배웁니다. “왜 그냥 Domain을 바로 테이블에 쓰면 안 되나요?”라는 초보자의 자연스러운 질문에 답할 수 있게 되는 것이 오늘의 목표입니다.

1. 지난 시간 연결: 재질만으로는 부족하다 🏷️

이전 Lesson에서 우리는 Domain을 만들며 “항공사 코드는 CHAR 3이다”처럼 데이터의 재질을 정했습니다. 그런데 여기서 살짝 멈춰볼게요. CHAR 3이라는 정보만 보고 사람이 그 값의 뜻을 바로 알 수 있을까요?

KE가 항공사 코드인지, 국가 코드인지, 내부 부서 코드인지 Domain만 보고는 모릅니다. Data Type과 길이는 기술적으로 중요하지만, 화면을 보는 사용자에게는 “이 칸에 무엇을 입력해야 하는지”가 더 중요합니다.

Domain이 “이 칸은 3자리 문자야”라고 말한다면, Data Element는 “이 칸은 항공사 코드야. 화면에는 항공사 코드라고 보여줘”라고 말합니다.

2. Data Element는 의미와 이름표를 붙이는 단계 💬

Data Element는 Domain 위에 사람이 이해할 수 있는 의미를 붙입니다. SAP 문서에서는 이런 의미를 Semantic Meaning이라고 부릅니다. 어렵게 들리지만, 쉽게 말하면 “이 값이 업무적으로 무엇을 뜻하는가?”입니다.

  • Domain: 기술적 재질입니다. 예: CHAR 3
  • Data Element: 업무적 의미입니다. 예: 항공사 코드
  • Table Field: 실제 테이블의 한 칸입니다. 예: 항공편 테이블의 CARRID
🔗

조립 순서 다시 보기

Domain → Data Element → Table Field 순서로 올라갑니다. 이 구조를 이해하면 DDIC가 갑자기 복잡한 미로가 아니라, 레고처럼 차근차근 쌓는 조립 방식으로 보이기 시작합니다.

3. Field Label 4종: 화면에 자동으로 뜨는 이름표 📋

Data Element에서 초심자가 꼭 봐야 하는 칸이 Field Label입니다. 화면이나 리포트에 필드를 보여줄 때, SAP는 Data Element에 저장된 라벨을 가져와 자동으로 제목을 붙입니다.

  • Short: 아주 좁은 칸에서 쓰는 짧은 라벨입니다. 예: 항공사
  • Medium: 일반 입력 화면에서 자주 쓰는 기본 라벨입니다. 예: 항공사 코드
  • Long: 설명을 조금 더 자세히 보여줄 여유가 있을 때 씁니다. 예: 항공편의 항공사 코드
  • Heading: 리스트나 ALV의 컬럼 제목으로 자주 쓰입니다. 예: 항공사

이 라벨은 작은 기능처럼 보이지만, 실무에서는 엄청난 생산성 차이를 만듭니다. 같은 Data Element를 100개 화면에서 쓰고 있다면, 라벨 하나를 바꾸는 것만으로 100개 화면의 제목이 함께 정리될 수 있습니다. 이것이 DDIC 재사용의 맛입니다.

✨

학습지 포인트

처음에는 Short, Medium, Long, Heading의 차이가 귀찮아 보여도 괜찮습니다. “화면 공간에 따라 SAP가 적당한 이름표를 골라 쓰려고 4종류를 준비해 둔다”라고 기억하면 충분합니다.

4. F1 Help와 문서화: 사용자를 위한 작은 설명서 📖

Data Element는 라벨만 담당하지 않습니다. 사용자가 SAP 화면에서 어떤 필드에 커서를 두고 F1 Help를 누르면, 그 필드의 설명 문서가 나타날 수 있습니다. 이 설명도 Data Element의 Documentation 영역에서 관리합니다.

예를 들어 CARRID 필드에 “항공편을 운항하는 항공사를 식별하는 코드입니다”라고 문서를 달아두면, 개발자뿐 아니라 현업 사용자도 도움말을 통해 의미를 확인할 수 있습니다. 단순히 코드를 짜는 것이 아니라, 사용자가 덜 헤매게 만드는 친절함까지 DDIC에 담는 셈입니다.

  • ✅ 정상 흐름: Data Element에 라벨과 Documentation을 입력합니다. 화면 필드가 자동으로 읽기 쉬운 이름과 도움말을 갖습니다.
  • ❌ 부족한 흐름: 라벨을 비워두거나 너무 짧게 적습니다. 화면에는 애매한 약어가 뜨고, 사용자는 “이 칸이 뭐지?” 하고 멈춥니다.

5. 왜 Domain을 바로 쓰지 않을까? 🤔

이 질문은 아주 좋습니다. 처음 배우는 입장에서는 Domain도 있고 Data Element도 있으니 “왜 굳이 두 번 만들지?”라는 생각이 자연스럽습니다. 답은 분업과 재사용입니다.

  • 재질만 같고 의미가 다른 경우: 출발 공항과 도착 공항은 둘 다 CHAR 3일 수 있습니다. 하지만 화면 라벨과 의미가 다르므로 Data Element는 나누는 것이 좋습니다.
  • 의미까지 같은 경우: 회사 코드처럼 SAP 표준 Data Element가 의미와 라벨까지 딱 맞는다면, 새로 만들지 말고 표준을 재사용하는 것이 좋습니다.
  • 라벨만 바꾸고 싶은 경우: Data Element만 수정하면 됩니다. 굳이 Domain의 기술적 재질을 건드릴 필요가 없습니다.
핵심은 이겁니다. Domain은 기계가 이해할 규칙에 가깝고, Data Element는 사람과 화면이 이해할 설명에 가깝습니다.

6. 실무에서 조심해야 할 점 🚨

⚠️

길이가 같다고 같은 Data Element를 쓰면 안 됩니다

출발 공항과 도착 공항은 둘 다 3자리 문자일 수 있습니다. 하지만 두 필드의 의미는 다릅니다. 같은 Data Element를 쓰면 화면 라벨도 같아지고, 도움말도 같아져서 사용자가 헷갈릴 수 있습니다. 재질이 같아도 업무 의미가 다르면 Data Element를 분리하세요.

반대로, SAP 표준 Data Element의 의미와 라벨이 내가 원하는 것과 정확히 맞는다면 커스텀으로 새로 만들 필요가 없습니다. 표준을 재사용하면 다른 프로그램과 용어가 맞아지고, 나중에 유지보수할 사람도 훨씬 빨리 이해합니다.

7. 한눈에 정리 🏁

📝

오늘의 핵심만 딱 잡기

  • Data Element는 Domain의 재질 위에 업무 의미와 화면 라벨을 붙입니다.
  • Semantic Meaning은 “이 값이 업무적으로 무엇인가?”라는 뜻입니다.
  • Field Label은 Short, Medium, Long, Heading 4종류로 화면 표시를 도와줍니다.
  • F1 Help 문서화를 통해 사용자와 개발자에게 필드 설명을 제공할 수 있습니다.
  • 재질이 같아도 의미가 다르면 Data Element를 분리하고, 의미까지 같으면 표준을 먼저 재사용합니다.

이제 낱개 필드에 재질과 의미를 모두 붙였습니다. 다음 Lesson Structure 기본 생성에서는 이렇게 만든 필드들을 한 줄짜리 데이터 꾸러미로 묶어보겠습니다.
