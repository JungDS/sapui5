학습 목표

지난 Chapter에서 PARAMETERS로 사용자가 값을 입력하는 흐름을 배웠습니다. 이번에는 잘못된 값을 줄이기 위해 DDIC에서 관계를 거는 방법을 봅니다. Foreign Key, Check Table, Cardinality의 역할을 처음부터 차근차근 익힙니다.

1. 지난 Chapter 연결: 입력칸은 만들었는데, 값이 맞는지는 누가 볼까? 🤔

THEORY-03에서 Selection Screen 입력칸을 만들었습니다. 사용자는 항공사 코드나 날짜 같은 값을 직접 입력할 수 있었죠. 그런데 사용자가 KE 대신 XXX를 입력하면 어떻게 될까요?

타입이 CHAR 3이라면 XXX도 기술적으로는 들어갈 수 있습니다. 하지만 업무적으로 실제 항공사 코드가 아니라면 잘못된 값입니다. 이런 상황에서 DDIC 관계가 도움을 줍니다.

Foreign Key는 “이 필드의 값은 저 기준표에 실제로 존재해야 해요”라고 DDIC에 연결선을 긋는 설정입니다.

2. Check Table: 정답 목록을 담은 기준표 📋

Check Table은 입력 가능한 값의 기준 목록을 담은 테이블입니다. 예를 들어 항공사 코드가 유효한지 확인하려면, 항공사 마스터 테이블 같은 기준표에 그 코드가 존재하는지 봐야 합니다.

  • 기준표: 항공사 코드와 항공사 이름을 가진 테이블
  • 검사 대상 필드: 예약 테이블의 항공사 코드 필드
  • 검사 의미: 예약 테이블에 들어가는 항공사 코드는 기준표에 있어야 함

일상으로 치면 학교 출석부가 Check Table입니다. 출석 체크할 때 이름이 출석부에 있어야 진짜 학생으로 인정되는 것처럼, 입력값도 기준표에 있어야 유효한 값으로 볼 수 있습니다.

3. Foreign Key: 필드와 기준표를 연결하는 약속 🔗

Foreign Key는 현재 테이블의 필드가 Check Table의 키 필드를 참조하도록 만드는 관계입니다. 단순히 “비슷한 이름의 필드가 있다”가 아니라, DDIC에 실제 관계로 등록하는 것이 중요합니다.

💡

예시 관계

  • 예약 테이블 ZBOOKING-CARRID: 사용자가 입력하는 항공사 코드
  • 항공사 기준표 ZCARRIER-CARRID: 존재 가능한 항공사 코드 목록
  • Foreign Key 설정: ZBOOKING-CARRID는 ZCARRIER-CARRID에 존재해야 함

이 관계가 있으면 화면 입력이나 테이블 유지보수 상황에서 DDIC 기반 검증과 입력 도움말이 훨씬 자연스럽게 연결됩니다. 프로그램마다 같은 검사를 따로 만드는 부담도 줄어듭니다.

4. Cardinality: 관계의 숫자 감각 잡기 🔢

Cardinality는 두 테이블이 어떤 숫자 관계를 갖는지 표현합니다. 초심자 단계에서는 복잡하게 외우기보다 “한 기준값이 여러 업무 데이터에서 반복될 수 있다”는 감각부터 잡으면 됩니다.

  • 항공사 기준표에는 KE가 한 번만 존재합니다.
  • 예약 테이블에는 KE를 쓰는 예약이 수천 건 있을 수 있습니다.
  • 즉, 기준표 한 줄이 업무 테이블 여러 줄과 연결될 수 있습니다.
Cardinality는 관계의 지도입니다. “하나가 여러 개와 연결되는가?”, “반드시 있어야 하는가?” 같은 설계 의도를 보여줍니다.

5. 정상 흐름과 오류 흐름으로 확인하기 🔎

  • ✅ 정상 흐름: 사용자가 KE를 입력했고 Check Table에 KE가 존재하면 입력이 통과합니다.
  • ❌ 오류 흐름: 사용자가 XXX를 입력했는데 기준표에 없으면 DDIC 기반 검사에서 막힐 수 있습니다.
  • ❌ 관계 누락: 기준표가 있어도 Foreign Key 관계를 걸지 않으면, 시스템은 그 필드가 기준표를 봐야 한다는 사실을 모릅니다.
  • ❌ 키 불일치: Check Table의 키 구조와 현재 필드 매핑이 맞지 않으면 관계 설정이나 검증이 어긋날 수 있습니다.

미니 실습으로는 작은 코드 기준표와 업무 테이블을 상상하고, 업무 테이블의 코드 필드에 Check Table을 연결하는 흐름을 따라가면 충분합니다. 실제 데이터 입력 시 “있는 코드”와 “없는 코드”를 각각 넣어보면 차이가 확실히 보입니다.

6. 실무에서 조심해야 할 점 🚨

⚠️

표준 관계를 무시하고 새로 만들지 마세요

SAP 표준 테이블과 Data Element에는 이미 검증된 관계가 많이 들어 있습니다. 표준 필드와 같은 의미라면 새 관계를 억지로 만들기보다 표준 객체의 의미와 관계를 먼저 확인하세요. 고객사 관행으로 별도 테이블을 만들더라도, 표준 동작과 커스텀 설계를 섞어 외우면 나중에 유지보수가 어려워집니다.

또한 Foreign Key는 입력값의 존재 여부를 도와주지만, 모든 업무 규칙을 대신하지는 않습니다. 예를 들어 “이 사용자가 이 회사 코드를 볼 권한이 있는가?” 같은 판단은 별도 권한과 프로그램 로직이 필요합니다.

7. 한눈에 정리 🏁

📝

오늘의 핵심만 딱 잡기

  • Check Table은 허용 가능한 값의 기준 목록을 담은 테이블입니다.
  • Foreign Key는 현재 필드가 Check Table의 값을 참조하도록 연결하는 관계입니다.
  • Cardinality는 기준표와 업무 테이블 사이의 숫자 관계를 표현합니다.
  • 기준표가 있어도 Foreign Key 관계를 걸지 않으면 자동 검증으로 이어지지 않습니다.
  • Foreign Key는 존재 여부를 돕지만 권한이나 복잡한 업무 규칙을 모두 대신하지는 않습니다.
