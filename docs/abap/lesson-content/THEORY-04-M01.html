학습 목표

지난 Chapter에서 PARAMETERS로 사용자에게 값을 입력받는 화면을 만들어 봤습니다. 그런데 “입력칸”만 있으면 사용자가 아무 값이나 넣을 수 있죠. 이번 Lesson에서는 잘못된 값을 입력 단계에서 걸러내는 DDIC의 관계 장치 — Foreign Key, Check Table, Cardinality — 를 초심자 눈높이로 처음부터 익힙니다.

1. 지난 Chapter 연결: 입력칸은 만들었는데, 값이 진짜인지는 누가 보나? 🤔

Chapter 3에서 Selection Screen 입력칸을 만들었습니다. 사용자는 항공사 코드 같은 값을 직접 타이핑할 수 있었죠. 그런데 항공사 코드 타입이 CHAR 3이라면, 사용자가 KE 대신 XXX를 넣어도 글자 수만 맞으면 기술적으로는 들어갑니다.

문제는 XXX가 업무적으로 존재하지 않는 항공사라는 점입니다. 이런 “타입은 맞지만 실제로는 없는 값”을 입력 단계에서 막아주는 것이 이번 Chapter의 핵심입니다.

Foreign Key는 “이 필드에 들어올 값은 저 기준표에 실제로 존재해야 해요”라고 DDIC에 연결선을 긋는 약속입니다.

2. Check Table: 정답 목록을 담은 기준표 📋

Check Table은 “이 값들만 허용된다”는 기준 목록을 담은 마스터 테이블입니다. SAP 표준 예제로 보면 이해가 빠릅니다. 예약 데이터를 담는 SBOOK 테이블에 항공사 코드(CARRID)를 넣을 때, 그 코드가 진짜인지 확인하려면 항공사 마스터 테이블 SCARR과 대조해야 합니다. 이때 기준이 되는 SCARR이 바로 Check Table입니다.

  • 기준표(Check Table): 항공사 코드와 이름을 가진 마스터 테이블 (SCARR)
  • 검사 대상 필드(Check Field): 예약 테이블의 항공사 코드 필드 (SBOOK-CARRID)
  • 검사 의미: 예약에 들어가는 항공사 코드는 반드시 마스터 목록에 있어야 함

일상으로 치면 학교 출석부가 Check Table입니다. 출석을 부를 때 이름이 출석부에 있어야 진짜 우리 반 학생으로 인정되는 것처럼, 입력값도 기준표에 있어야 유효한 값으로 봅니다.

💡

한 가지 규칙: 검사 대상 필드는 Check Table의 “기본 키”와 연결된다

Foreign Key를 걸 때, 검사 대상 필드(Check Field)는 아무 필드가 아니라 Check Table의 기본 키(Primary Key) 영역에 속한 필드와 매핑됩니다. 그래야 “이 코드 한 개”를 기준표에서 유일하게 찾아 존재 여부를 판단할 수 있기 때문입니다.

3. Foreign Key: 필드와 기준표를 잇는 약속 🔗

Foreign Key는 현재 테이블의 필드가 Check Table의 키를 참조하도록 만드는 논리적 관계입니다. 단순히 “비슷한 이름의 필드가 양쪽에 있다”가 아니라, DDIC에 실제 관계로 등록해야 시스템이 그 연결을 인식합니다.

사용자가 입력한 CARRID는 Check Table의 키 목록과 대조됩니다. 있으면 통과, 없으면 화면 입력 단계에서 막힙니다.

🧲

Domain에 Value Table이 있으면, 시스템이 Check Table을 제안해 준다

검사 대상 필드의 Domain에 Value Table이 미리 지정돼 있으면, Foreign Key를 만들 때 시스템이 그 테이블을 Check Table 후보로 자동 제안합니다. Value Table과 Check Table이 왜 같은 게 아닌지는 다음 Lesson에서 자세히 다룹니다.

4. Cardinality: 관계의 숫자 감각 잡기 🔢

Cardinality(다중성)는 “Check Table의 한 줄이 업무 테이블의 몇 줄과 연결될 수 있는가”를 나타내는 수량 관계입니다. 초심자는 복잡하게 외우기보다 “기준값 하나가 업무 데이터 여러 곳에서 반복될 수 있다”는 감각부터 잡으면 됩니다.

1:N 감각 — 기준표 한 줄, 업무 데이터 여러 줄

Check Table SCARR (1쪽)
CARRIDCARRNAME
KE대한항공
업무 테이블 SBOOK (N쪽)
BOOKIDCARRID
0001KE
0005KE
0042KE

기준표의 KE 한 줄이 예약 여러 줄과 연결됩니다. 왼쪽(1)이 Check Table, 오른쪽(N)이 참조하는 업무 테이블입니다.

Cardinality 표기 — Classic vs Modern

Classic ABAP 표기 (Check : Foreign)
  • 1:1 — 마스터 1개당 종속 데이터 정확히 1개
  • 1:N — 1개당 여러 개 (가장 흔한 1:다)
  • 1:C — 1개당 최대 1개 또는 0개(Conditional)
  • 1:CN — 1개당 0개 또는 여러 개
Modern ABAP 표기 [min..max]
  • [1..1] — 정확히 1개
  • [0..1] — 0개 또는 최대 1개
  • [1..*] — 적어도 1개 이상
  • [0..*] — 0개 이상 어떤 수든

표기법만 다를 뿐 뜻은 짝이 맞습니다. 예: Classic 1:CN ≈ Modern [0..*]. 최신 테이블 문법에서는 with foreign key [0..*,1]처럼 적습니다.

Cardinality는 강제 차단 장치라기보다, 관계 설계를 문서화해 시스템과 동료가 데이터 모델을 이해하도록 돕는 정보에 가깝습니다.

5. 정상 흐름과 오류 흐름을 함께 보기 🔎

ABAP 초반 실력은 거창한 로직보다 “어디서 왜 막혔는지 읽는 습관”에서 자랍니다. 같은 입력을 정상·오류 케이스로 나눠 봅시다.

기준표가 “있다”와 Foreign Key가 “걸렸다”는 다릅니다. 관계를 등록해야 비로소 그 기준표가 Check Table로 동작합니다.

6. 가장 중요한 사실: DDIC Foreign Key는 DB 제약이 아니다 🚨

⚠️

“DDIC에 Foreign Key를 걸면 DB가 막아준다”는 흔한 오해

초심자가 가장 자주 하는 오해입니다. SAP DDIC의 Foreign Key는 데이터베이스(RDBMS) 레벨의 물리적 제약 조건을 만들지 않습니다. DB 계층에서의 자동 일관성 검사도 수행하지 않습니다. 오직 화면(Dynpro) 입력 단계에서의 암묵적 입력 점검과 F4 입력 도움말을 제공하는 용도로 동작합니다.

그래서 개발자가 프로그램 안에서 INSERT/UPDATE 같은 Open SQL로 데이터를 직접 밀어 넣으면, DB는 Foreign Key 설정을 무시하고 잘못된 값도 그대로 저장합니다. 화면을 거치지 않는 배치 인터페이스나 직접 삽입 경로에는 프로그램 차원의 별도 검증이 반드시 필요합니다.

환경별로 Foreign Key를 쓰는 이유가 어떻게 진화했나?
  • Classic ABAP (SAP GUI): 화면에서 오타를 사전 차단하고 필드 옆 F4 도움말을 띄우는 UI 제어의 핵심 기능. 반드시 설정.
  • Modern ABAP (S/4HANA): 직접 삽입으로 뚫릴 수 있음을 전제로, 테이블 간 관계를 시스템에 알려주는 관계 문서화 목적으로 지정.
  • ABAP Cloud (Clean Core · RAP): 전통적 화면 에러 메시지의 의미는 사라지고, 이 관계를 바탕으로 CDS View의 연관(association)을 설계. 실제 강한 검증은 RAP의 Behavior Definition(BDEF) 비즈니스 로직에서 수행.

7. 미니 실습: 기준표 관계 설계 따라가기 🧪

✍️

실습 과제

  1. 항공사 기준표(코드, 이름)와 예약 테이블(예약번호, 항공사 코드)을 종이에 그립니다.
  2. 예약 테이블의 항공사 코드 필드에 Foreign Key를 건다면 Check Table은 무엇이 되는지, 그 필드는 Check Table의 어떤 키와 연결되는지 적습니다.
  3. 기준표에 있는 코드(KE)와 없는 코드(XXX)를 화면에 입력했을 때 각각 어떤 일이 일어나는지 위 흐름을 따라 말로 설명합니다.
  4. 같은 XXX를 프로그램에서 INSERT로 직접 넣으면 어떻게 될지도 한 줄로 적어봅니다.

완료 조건: “Check Table은 기준 목록, Foreign Key는 그 목록을 검사하도록 거는 연결, 단 화면 입력에서만 동작”이라고 자신의 말로 설명할 수 있으면 성공입니다.

8. 실무에서 조심해야 할 점

  • 표준 관계를 무시하고 새로 만들지 않기: SAP 표준 테이블·Data Element에는 이미 검증된 관계가 많습니다. 표준과 같은 의미라면 표준 객체의 관계를 먼저 확인하세요.
  • Foreign Key는 “존재 검사”까지: “이 사용자가 이 코드를 볼 권한이 있는가” 같은 업무 규칙은 별도 권한·로직이 필요합니다.
  • 화면 밖 경로는 직접 검증: 배치·인터페이스·직접 INSERT에는 프로그램 검증을 따로 둡니다.

10. 확인 퀴즈 ✅

  1. 기준표(Check Table 후보)가 존재하기만 하면 입력값 검증이 자동으로 동작할까요?
  2. DDIC Foreign Key는 데이터베이스의 물리적 제약 조건일까요?
  3. Cardinality 1:N에서 “1쪽”과 “N쪽”은 각각 어떤 테이블인가요?
  4. 검사 대상 필드(Check Field)는 Check Table의 어떤 영역과 연결되나요?
정답/해설 보기
  1. 아니요. 기준표가 있어도 업무 테이블 필드에 Foreign Key 관계를 실제로 등록해야 그 기준표가 Check Table로 동작합니다.
  2. 아니요. DDIC Foreign Key는 화면(Dynpro) 입력 단계의 논리적 검증일 뿐, DB 물리 제약이 아닙니다. 직접 INSERT는 우회됩니다.
  3. 1쪽 = 기준표(Check Table), N쪽 = 업무 테이블입니다. 기준표 KE 한 줄이 예약 여러 줄과 연결됩니다.
  4. Check Table의 기본 키(Primary Key)와 연결됩니다. 그래야 값을 유일하게 찾아 존재를 판단합니다.
