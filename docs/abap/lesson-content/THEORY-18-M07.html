학습 목표

기존 클래스를 물려받아 확장하는 상속(Inheritance)과, 물려받은 메서드를 다시 정의하는 재정의(Redefinition)를 맛봅니다. OO ABAP Chapter를 마무리합니다.

1. 지난 시간 연결: 비슷한 클래스를 또 만들기 아깝다 🧬

"일반 직원"과 "관리자" 클래스를 만든다고 해봅시다. 둘 다 이름·사번이 있고 출근하지만, 관리자는 추가로 결재 기능이 있죠. 공통 부분을 매번 다시 적는 건 낭비입니다.

상속은 기존 클래스(부모)의 속성·메서드를 물려받아, 새 클래스(자식)에서 필요한 것만 더하거나 바꾸게 해줍니다.

CLASS zcl_employee DEFINITION PUBLIC.
  PUBLIC SECTION.
    METHODS work.

" 자식 클래스 — 부모를 물려받음

CLASS zcl_manager DEFINITION PUBLIC
  INHERITING FROM zcl_employee.        "상속

  PUBLIC SECTION.
    METHODS approve.                   "관리자만의 새 기능

ENDCLASS.

zcl_manager는 work( )를 따로 안 적어도 부모에게서 물려받아 쓸 수 있고, approve( )만 추가하면 됩니다.

💡

비유: 가업 물려받기

자식이 부모의 가게(공통 기능)를 물려받고, 거기에 자기만의 신메뉴(새 기능)를 추가하는 것과 같아요. 처음부터 가게를 새로 차릴 필요가 없죠.

3. Redefinition — 물려받은 걸 바꾸기 🔧

물려받은 메서드의 동작을 자식에서 다르게 하고 싶으면 재정의(REDEFINITION)합니다.

ABAP

CLASS zcl_manager DEFINITION PUBLIC
  INHERITING FROM zcl_employee.
  PUBLIC SECTION.
    METHODS work REDEFINITION.    "부모의 work를 다르게 구현

ENDCLASS.

재정의 안에서 super->work( )로 부모 동작을 부른 뒤 추가 작업을 더할 수도 있습니다("부모 것 + 내 것").

4. 정상 흐름과 주의 🔍

  • ✅ 정상: 공통은 부모에, 차이는 자식에. 중복 없이 확장.
  • ❌ 오류 — 과한 상속: 상속을 너무 깊게(여러 단계) 쌓으면, 어디서 무엇이 정의됐는지 추적이 어려워집니다.
  • 📌 대안: "is-a"(관리자는 직원이다) 관계가 분명할 때만 상속을, 단순 기능 공유는 인터페이스(M05)나 조합을 고려합니다.

5. 실무에서 조심할 점 🚨

⚠️

상속보다 인터페이스/조합이 안전할 때가 많습니다

상속은 강력하지만, 부모를 바꾸면 모든 자식이 영향을 받아 위험할 수 있습니다("부모 한 번 잘못 고치면 자식 다 깨짐"). 현대 설계에서는 깊은 상속보다 인터페이스(M05)와 조합(필요한 객체를 안에 두고 쓰기)을 더 권장합니다. 지금은 "상속이 무엇이고, 남용하면 위험하다"는 감각만 잡으면 충분합니다. 깊은 설계는 실무에서 패턴과 함께 익힙니다.

THEORY-18 마무리 핵심

  • OO ABAP: 클래스/객체 → 속성·메서드·Visibility → 생성자 → Static/Instance → 인터페이스 → 예외 → 상속.
  • 상속은 부모를 물려받아 확장하고, 재정의로 동작을 바꿉니다.
  • "is-a" 관계가 분명할 때만 상속, 아니면 인터페이스/조합.
  • 캡슐화·다형성·재사용이 OO의 핵심 가치입니다.
