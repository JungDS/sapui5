학습 목표

지난 Lesson에서는 @DATA(lt_countries)처럼 조회 결과 Target을 inline으로 만들었습니다. 이번에는 명시적 Target Table, Typed Internal Table, Target Variable을 직접 선언하는 방식을 배웁니다.

1. Inline 선언은 편하지만 항상 충분하지는 않다 🧭

@DATA(lt_countries)는 빠르고 편합니다. SELECT 결과 모양에 맞춰 ABAP이 Target 변수를 만들어주기 때문입니다. 하지만 실무 코드에서는 Target 타입을 명확하게 선언해두는 편이 더 읽기 좋거나 안전할 때가 많습니다.

예를 들어 여러 Method에서 같은 결과 타입을 공유하거나, SALV 표시 전에 Internal Table을 다른 로직에서도 사용해야 한다면 명시적 타입 선언이 도움이 됩니다.

명시적 Target 선언은 “조회 결과를 어떤 모양의 그릇에 담을지” 코드에 먼저 적어두는 방식입니다.

2. TYPES로 결과 한 줄 모양 정하기 📏

ABAP
1
2
3
4 
TYPES: BEGIN OF ty_country,
         land1 TYPE t005t-land1,
         landx TYPE t005t-landx,
       END OF ty_country.

위 코드는 조회 결과 한 줄이 국가 코드와 국가명 두 필드로 구성된다고 정의합니다. DDIC 필드 타입을 참조하므로 실제 테이블 필드 타입과 맞추기 쉽습니다.

이렇게 한 줄 타입을 먼저 정하면, SELECT 결과와 ABAP 처리 구조가 한눈에 보입니다.

3. DATA lt_table로 Typed Internal Table 선언하기 📦

ABAP
1 
DATA lt_countries TYPE STANDARD TABLE OF ty_country.

Typed Internal Table은 어떤 Line Type을 담는지 명확히 정해진 Internal Table입니다. 여기서는 ty_country 모양의 여러 줄을 담습니다.

ABAP
1
2
3
4 
SELECT FROM t005t
  FIELDS land1, landx
  WHERE spras = @sy-langu
  INTO TABLE @lt_countries.

이제 SELECT 결과는 미리 선언한 lt_countries에 들어갑니다. 이 lt_countries가 Target Variable입니다.

즉석 보관함 vs 미리 만든 보관함

Inline 선언: INTO TABLE @DATA(lt_...)
모양 결정SELECT의 FIELDS 목록이 자동 결정
장점짧고 빠르게 작성
주의FIELDS를 바꾸면 테이블 모양도 같이 바뀜 — 뒤 로직이 조용히 영향받음
명시적 선언: TYPES + DATA lt_...
모양 결정TYPES로 개발자가 먼저 고정
장점여러 곳에서 재사용, 의도가 코드에 드러남
주의FIELDS 목록과 타입 필드가 맞아야 함

짧은 일회성 조회는 inline이 편하지만, 결과를 여러 로직·FORM·Method에서 함께 쓰거나 모양을 안정적으로 유지해야 한다면 명시적 Target이 안전합니다.

REPORT zsql_explicit_target.

TYPES: BEGIN OF ty_country,
         land1 TYPE t005t-land1,
         landx TYPE t005t-landx,
       END OF ty_country.

DATA lt_countries TYPE STANDARD TABLE OF ty_country.
DATA ls_country   TYPE ty_country.

SELECT FROM t005t
  FIELDS land1, landx
  WHERE spras = @sy-langu
  INTO TABLE @lt_countries.

LOOP AT lt_countries INTO ls_country.
  WRITE: / ls_country-land1, ls_country-landx.
ENDLOOP.

이 코드는 inline 선언보다 조금 길지만, 조회 결과 구조가 코드 위쪽에 명확하게 드러납니다. 협업 코드나 긴 Report에서는 이런 명확성이 도움이 됩니다.

5. 정상 흐름과 오류 흐름으로 확인하기 🔎

  • ✅ 정상 흐름: FIELDS 목록과 Target 구조 필드가 맞으면 조회 결과가 명시적 Internal Table에 담깁니다.
  • ✅ 가독성 향상: 결과 구조가 TYPES와 DATA 선언에 드러나 코드 리뷰가 쉬워집니다.
  • ❌ 필드 수/타입 불일치: SELECT한 필드와 Target 구조가 맞지 않으면 문법 또는 실행 문제가 생길 수 있습니다.
  • ❌ 불필요한 장황함: 아주 짧은 일회성 조회에 과도한 타입 선언을 붙이면 코드가 길어질 수 있습니다.

미니 실습으로 ty_country에 spras 필드를 추가하고 SELECT의 FIELDS에도 spras를 추가해보세요. Target 구조와 조회 필드가 함께 움직인다는 점을 확인합니다.

6. 실무에서 조심해야 할 점 🚨

⚠️

Target 타입은 조회 의도를 보여주는 문서이기도 합니다

명시적 Target Table은 단순한 변수 선언이 아닙니다. 이 Report가 어떤 필드를 결과로 다룰지 보여주는 작은 설계 문서 역할을 합니다. 이름과 필드 구성을 대충 만들면 오히려 혼란이 커집니다.

프로젝트에 따라 inline 선언을 선호할 수도 있고, 명시적 TYPES를 선호할 수도 있습니다. 팀 컨벤션과 코드 길이, 재사용 범위를 보고 선택하세요.

7. 미니 실습: 두 가지 보관함 만들어보기 🧪

✍️

실습 과제

  1. 같은 SELECT를 ① inline @DATA(...) 버전과 ② TYPES+DATA 명시적 Target 버전으로 각각 작성합니다.
  2. 두 버전 모두 정상 출력되는지 확인합니다.
  3. ①에서 FIELDS에 필드를 하나 추가했을 때 뒤 LOOP 코드에 어떤 영향이 가는지 관찰합니다.
  4. ②에서 FIELDS와 TYPES 필드가 어긋나면 어떤 문법 메시지가 나는지 확인합니다.

완료 조건: “언제 inline이 편하고 언제 명시적 선언이 안전한가”를 자신의 기준 한 줄로 정리하면 성공입니다.

9. 확인 퀴즈와 정답/해설 ✅

  1. INTO TABLE @DATA(lt_x)에서 lt_x의 모양(필드 구성)은 무엇이 결정하나요?
  2. 조회 결과를 여러 FORM/Method에서 함께 써야 한다면 inline과 명시적 Target 중 무엇이 유리한가요?
  3. 명시적 Target을 쓸 때 FIELDS 목록과 무엇이 맞아야 하나요?
정답/해설 보기
  1. SELECT의 FIELDS 목록입니다. FIELDS를 바꾸면 inline 테이블의 모양도 함께 바뀌므로 뒤 로직에 영향이 갑니다.
  2. 명시적 Target(TYPES+DATA)입니다. 타입 이름으로 여러 곳에서 재사용할 수 있고 모양이 안정적으로 고정됩니다.
  3. Target의 Line Type 필드 구성입니다. 어긋나면 문법 오류나 의도하지 않은 값 매핑이 생깁니다.

10. 한눈에 정리 🏁

📝

명시적 Target 핵심

  • 명시적 Target Table은 조회 결과를 받을 Internal Table을 미리 선언하는 방식입니다.
  • Typed Internal Table은 어떤 Line Type을 담는지 정해진 테이블입니다.
  • Target Variable은 SELECT 결과가 들어가는 ABAP 변수입니다.
  • FIELDS와 Target 구조가 맞아야 안전하게 조회 결과를 받을 수 있습니다.
  • inline 선언과 명시적 선언은 상황과 팀 컨벤션에 맞춰 선택합니다.
