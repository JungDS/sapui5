학습 목표

Chapter 5의 마무리로 Modularization 도구를 선택하는 기준을 정리합니다. Subroutine, Function Module, Class를 언제 고려할지 보고, Reuse와 Readability 관점으로 판단하는 습관을 만듭니다.

1. 지난 시간 연결: 도구를 배웠으면 고르는 기준도 필요하다 🧭

이번 Chapter에서는 FORM/PERFORM, USING/CHANGING, CALL FUNCTION, Local Class, Global Class를 차례로 맛봤습니다. 이제 질문이 생깁니다. “그럼 실무에서는 뭘 써야 하나요?”

정답은 하나가 아닙니다. 기존 코드 구조, 재사용 범위, 팀 기준, 시스템 버전, ABAP Cloud 여부, 유지보수 난이도에 따라 선택이 달라집니다. 그래서 문법을 아는 것만큼 선택 기준을 갖는 것이 중요합니다.

좋은 모듈화는 멋진 문법을 쓰는 것이 아니라, 다음 사람이 빨리 이해하고 안전하게 재사용할 수 있게 만드는 것입니다.

2. Subroutine은 같은 프로그램 안의 작은 정리함 📦

FORM/PERFORM 기반 Subroutine은 같은 Report 안에서 코드를 나누는 데 유용합니다. 특히 오래된 리포트에서 입력 검증, 데이터 조회, 출력 같은 구역을 FORM으로 나눈 코드를 자주 만납니다.

  • 어울리는 경우: 기존 Report 안에서 작은 로직을 정리하거나 유지보수할 때
  • 장점: 구조가 단순하고 오래된 코드에서 익숙하게 보입니다.
  • 주의: 전역 변수 의존이 커지면 값 흐름을 추적하기 어렵습니다.

신규 설계에서 무조건 FORM을 선택하기보다는, 기존 코드 맥락과 팀 기준을 먼저 봐야 합니다.

3. Function Module은 시스템 공용 기능 단위 🧰

Function Module은 여러 프로그램에서 재사용할 수 있는 전통적인 공용 기능 단위입니다. 표준 SAP Function Module도 많고, 고객사에서 만든 Z Function Module도 있을 수 있습니다.

  • 어울리는 경우: 여러 프로그램에서 이미 사용하는 기능을 호출하거나, 기존 Function Module 기반 설계를 유지보수할 때
  • 장점: 시스템에 등록되어 재사용하기 쉽고, 인터페이스가 비교적 명확합니다.
  • 주의: 오래된 구현이나 비권장 표준 객체가 섞여 있을 수 있으므로 사용 가능성을 확인해야 합니다.

특히 Function Module 호출 후에는 예외와 sy-subrc 확인을 습관화해야 합니다. 공용 기능을 부른다는 것은 실패 가능성도 함께 다룬다는 뜻입니다.

4. Class는 현대 ABAP 설계의 중심축 🏛️

Class는 관련 데이터와 기능을 Method로 묶어 구조화하는 방식입니다. Local Class는 한 프로그램 안에서 정리할 때, Global Class는 여러 프로그램에서 재사용할 때 사용할 수 있습니다.

  • 어울리는 경우: 새 기능을 구조적으로 만들거나, 테스트·재사용·확장성을 고려할 때
  • 장점: 책임을 Method와 Class 단위로 나누기 좋고, 현대 ABAP/ABAP Cloud 방향과 잘 맞습니다.
  • 주의: 역할을 나누지 않은 거대한 Class는 읽기 어려운 FORM 덩어리와 다르지 않습니다.

OO ABAP의 깊은 설계 원칙은 Chapter 18에서 다루지만, 지금부터 “새로운 재사용 설계는 Class를 먼저 떠올린다”는 감각을 가져가면 좋습니다.

5. 선택 기준: Reuse와 Readability로 생각하기 🔍

Reuse는 같은 기능을 여러 곳에서 다시 쓸 수 있는지, Readability는 코드를 읽는 사람이 빠르게 이해할 수 있는지를 뜻합니다.

  • 현재 프로그램 안에서만 쓰는 작은 로직: 기존 코드라면 FORM, 새 코드라면 Local Class Method도 고려
  • 여러 프로그램이 공유하는 기존 기능: 이미 있는 Function Module이나 Global Class 재사용 검토
  • 새로 만드는 공용 업무 로직: Global Class와 Method 중심 설계 우선 검토
  • 단순 반복 제거: 문법보다 이름과 책임이 명확한지가 먼저

초심자 판단 문장

“이 로직은 어디서 다시 쓰일까?”, “다음 사람이 이름만 보고 이해할까?”, “값이 어디서 들어오고 어디서 바뀔까?” 이 세 질문만 해도 모듈화 품질이 확 좋아집니다.

지금 배우는 이유 기존 코드 읽기 표준 기능 호출 + 기존 코드 읽기 새 설계의 기본기
Q1. 기존 코드 수정? 예 → 기존 구조(FORM/FM)를 존중하며 유지보수
Q2. 새 로직, 한 프로그램용? 예 → Local Class Method 고려
Q3. 새 로직, 여러 곳 공용? 예 → Global Class Method 우선

신규 개발의 기본값은 Class입니다. OO 문맥과 ABAP Cloud에서는 Subroutine 선언 자체가 허용되지 않으므로, FORM은 “읽기 위해” 배운다고 생각하면 정확합니다.

6. 실무에서 조심해야 할 점 🚨

⚠️

새 문법이 항상 좋은 설계를 보장하지는 않습니다

Class를 쓴다고 자동으로 Clean Code가 되는 것도 아니고, FORM을 쓴다고 무조건 나쁜 코드가 되는 것도 아닙니다. 중요한 것은 책임이 작고 명확한지, 입력과 출력이 드러나는지, 표준과 고객사 기준에 맞는지입니다.

또한 기존 시스템에서는 과거 방식과 현대 방식이 섞여 있습니다. 기존 코드를 존중하며 읽되, 새로 만드는 로직은 팀의 최신 기준과 SAP 권장 방향을 확인해 선택해야 합니다.

7. 미니 실습: 선택 기준 적용해보기 🧪

✍️

실습 과제

  1. 다음 네 가지 상황에 어떤 모듈화 도구를 고를지 위 결정 플로우로 판단해 적어봅니다: ① 오래된 Report의 출력 FORM 버그 수정 ② 새 Report 안에서만 쓰는 검증 로직 ③ 여러 프로그램이 함께 쓸 금액 계산 로직 ④ 외부 시스템이 호출할 인터페이스
  2. 각 선택의 이유를 Reuse(어디서 다시 쓰나)와 Readability(누가 읽나) 관점에서 한 줄씩 적습니다.
  3. 이번 Chapter에서 작성한 FORM 예제 하나를 골라 Local Class Method로 바꾸면 어떤 모양이 될지 시그니처만 적어봅니다.

완료 조건: ①은 기존 구조 유지, ②는 Local Class, ③은 Global Class, ④는 RFC Function Module 방향으로 판단하고 이유를 설명할 수 있으면 성공입니다.

9. 확인 퀴즈와 정답/해설 ✅

  1. S/4HANA 신규 개발에서 FORM/PERFORM 기반 Subroutine을 새로 만드는 것이 권장될까요?
  2. 여러 프로그램에서 함께 쓸 새 업무 로직을 만든다면 무엇을 먼저 고려해야 하나요?
  3. Function Module을 신규로 만드는 것이 여전히 적합한 대표적인 경우는 무엇인가요?
정답/해설 보기
  1. 아니요. Subroutine은 신규 개발에서 더 이상 권장되지 않는(Obsolete) 방식이며, OO 문맥과 ABAP Cloud에서는 선언 자체가 허용되지 않습니다. 기존 코드를 읽기 위해 배웁니다.
  2. Global Class의 Method입니다. 현대 ABAP과 Clean Core 방향에서 재사용 로직의 표준 컨테이너는 Class입니다.
  3. 외부 시스템 연동(RFC)처럼 Function Module이 기술적으로 필요한 경우입니다. 그 외 일반 업무 로직은 Class를 우선 검토합니다.

10. 한눈에 정리 🏁

📝

Chapter 5 마무리 핵심

  • Modularization은 코드를 작고 의미 있는 단위로 나누는 설계 습관입니다.
  • Subroutine은 같은 프로그램 안의 전통적인 코드 묶음입니다.
  • Function Module은 시스템에 등록된 전통적인 공용 기능 단위입니다.
  • Class는 현대 ABAP에서 재사용과 구조화를 위한 중요한 중심축입니다.
  • 도구 선택은 Reuse, Readability, 기존 코드 맥락, 팀 기준, SAP 권장 방향을 함께 보고 결정합니다.
