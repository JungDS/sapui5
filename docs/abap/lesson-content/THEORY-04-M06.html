학습 목표

Chapter 4의 마무리로 DDIC Validation과 프로그램 안의 Input Check 역할을 나눠봅니다. 어디까지는 DDIC가 막아주고, 어디부터는 ABAP 코드와 MESSAGE로 처리해야 하는지 초심자 기준으로 정리합니다.

1. 지난 시간 연결: F4로 골랐는데도 검증이 더 필요할까? 🤔

이전 Lesson에서 PARAMETERS 입력칸이 DDIC Data Element와 Search Help를 통해 F4 Help를 얻을 수 있다고 배웠습니다. 그러면 이제 모든 입력 검증이 끝난 걸까요? 아쉽지만 그렇지는 않습니다.

DDIC는 데이터의 기술적 형태와 기본 관계를 매우 잘 관리합니다. 하지만 “이 사용자가 이 값을 처리할 수 있는가?”, “이 날짜가 회사 마감일 이후인가?”, “이 상태에서는 수정하면 안 되는가?” 같은 업무 판단은 프로그램 로직이 맡아야 할 때가 많습니다.

DDIC는 공통 규칙을 지키는 문지기이고, 프로그램 검증은 상황별 업무 판단을 담당하는 안내자입니다.

2. DDIC Validation이 잘하는 일 🧱

DDIC Validation은 DDIC에 정의된 타입, 고정값, 관계를 바탕으로 입력값의 기본 품질을 높입니다.

  • 타입과 길이: CHAR 3, 날짜, 숫자처럼 기술적으로 맞는 값을 유도합니다.
  • Fixed Value: Y/N처럼 허용된 작은 목록만 받게 할 수 있습니다.
  • Foreign Key: 기준표에 존재하는 값인지 확인하는 데 도움을 줍니다.
  • Search Help: 사용자가 올바른 후보를 쉽게 고르게 도와줍니다.

이런 규칙은 여러 프로그램에서 공통으로 재사용되기 좋습니다. 그래서 DDIC에 둘 수 있는 기본 규칙은 DDIC에 두는 편이 유지보수에 유리합니다.

3. Program Input Check가 필요한 일 🧠

Input Check는 프로그램의 업무 문맥에 맞춰 입력값을 확인하는 로직입니다. 같은 회사 코드라도 프로그램 목적에 따라 허용 여부가 달라질 수 있습니다.

  • 업무 기간: 조회 시작일이 종료일보다 늦으면 안 됩니다.
  • 권한: 사용자가 특정 회사 코드나 조직 데이터를 볼 수 있는지 확인해야 합니다.
  • 상태: 이미 마감된 문서는 수정할 수 없을 수 있습니다.
  • 조합 조건: 항공사 코드와 노선 코드가 서로 맞는 조합인지 확인해야 할 수 있습니다.

이런 규칙은 단순히 Domain이나 Foreign Key만으로 표현하기 어렵습니다. 그래서 ABAP 코드에서 조건문과 메시지를 사용해 확인합니다.

4. MESSAGE로 사용자에게 알려주기 📣

MESSAGE는 사용자에게 오류, 경고, 정보 메시지를 보여주는 ABAP 문법입니다. 여기서는 가장 단순한 감각만 잡습니다.

REPORT zinput_check.

PARAMETERS p_days TYPE i DEFAULT 7.

IF p_days > 30.
  MESSAGE '조회 일수는 30일을 넘길 수 없습니다.' TYPE 'E'.
ENDIF.

WRITE: / '조회 일수:', p_days.

위 예제는 조회 일수가 30보다 크면 오류 메시지를 보여줍니다. 실제 Selection Screen 검증 이벤트인 AT SELECTION-SCREEN은 나중에 더 깊게 다룹니다. 지금은 “업무 조건을 코드로 확인하고 사용자에게 메시지를 줄 수 있다”는 감각만 가져가면 됩니다.

5. 역할 분리 예시: 어디에 둘까? 🔍

  • ✅ DDIC에 두기 좋은 것: 항공사 코드는 3자리 문자, 사용 여부는 Y/N, 회사 코드는 회사 기준표에 있어야 함
  • ✅ 프로그램에 두기 좋은 것: 조회 기간은 최대 30일, 로그인 사용자는 특정 조직만 조회 가능, 마감된 데이터는 수정 금지
  • ❌ 나쁜 흐름: 모든 검증을 프로그램마다 복사해서 만들기. 공통 규칙이 흩어져 유지보수가 어려워집니다.
  • ❌ 반대 흐름: DDIC가 모든 업무 규칙을 해결해줄 것이라 기대하기. 상황별 판단은 코드가 필요합니다.
좋은 설계는 “공통 규칙은 DDIC, 상황별 규칙은 프로그램”으로 책임을 나눕니다.

검증 책임 나누기 — 같은 입력값, 두 개의 관문

1차 관문: DDIC Validation (공통 규칙)
타입/길이CHAR 3, 날짜, 숫자 형태
Fixed ValueY/N만 허용
Foreign Key기준표에 있는 값인가
강점여러 프로그램에서 재사용
2차 관문: Program Input Check (업무 문맥)
기간시작일 ≤ 종료일, 최대 30일
권한이 사용자가 볼 수 있는 조직인가
상태/조합마감 문서 수정 금지, 코드 조합 확인
강점상황별 업무 판단 가능

입력값은 DDIC의 공통 관문을 먼저 지나고, 프로그램의 업무 관문에서 한 번 더 확인됩니다. 한쪽이 다른 쪽을 대신하지 못합니다.

6. 실무에서 조심해야 할 점 🚨

⚠️

DDIC 검증과 프로그램 검증을 서로 대체품처럼 보지 마세요

DDIC 검증을 무시하면 같은 검사를 여러 프로그램에 중복 구현하게 됩니다. 반대로 프로그램 검증을 생략하면 권한, 기간, 상태 같은 업무 규칙을 놓칠 수 있습니다. 둘은 경쟁 관계가 아니라 역할이 다른 협업 관계입니다.

또한 운영 환경에서는 메시지 문구도 사용자 경험의 일부입니다. “오류입니다”처럼 막연한 메시지보다, 무엇을 어떻게 고쳐야 하는지 알려주는 메시지가 훨씬 좋습니다.

그리고 DDIC 기반 검증은 화면 입력 경로에서 동작한다는 점을 기억하세요. 배치 인터페이스나 프로그램 내부의 직접 INSERT처럼 화면을 거치지 않는 경로에서는 DDIC 검증이 자동으로 막아주지 않으므로, 그런 로직에는 프로그램 검증을 반드시 넣어야 합니다.

7. 미니 실습: 검증 배치도 그리기 🧪

✍️

실습 과제

  1. 위 예제 zinput_check를 만들어 실행하고, p_days에 31을 넣었을 때 오류 메시지가 뜨는지 확인합니다.
  2. 기준 일수를 30에서 14로 바꾸고 동작 차이를 확인합니다.
  3. 다음 네 가지 규칙을 DDIC와 프로그램 중 어디에 둘지 분류합니다: ① 통화 코드는 3자리 ② 조회 기간 최대 30일 ③ 사용 여부는 Y/N만 ④ 마감된 전표 수정 금지
  4. 오류 메시지 문구를 “무엇을 어떻게 고쳐야 하는지” 알 수 있게 직접 다듬어봅니다.

완료 조건: ①③은 DDIC, ②④는 프로그램 검증으로 분류하고 그 이유를 설명할 수 있으면 성공입니다.

8. 공식 문서로 더 확인하기 🔗

  • SAP Help Portal: MESSAGE - MESSAGE 문장의 공식 문법과 메시지 타입을 확인합니다.
  • SAP Help Portal: Foreign Key - DDIC가 담당하는 관계 기반 검증의 공식 정의를 확인합니다.
  • SAP Help Portal: PARAMETERS - 입력칸 선언과 검증 흐름의 출발점을 확인합니다.

9. 확인 퀴즈와 정답/해설 ✅

  1. “조회 시작일이 종료일보다 늦으면 안 된다”는 규칙은 DDIC와 프로그램 중 어디에 두는 것이 적합한가요?
  2. DDIC 검증(Foreign Key 등)을 잘 설정했다면 배치 인터페이스 코드에서는 검증을 생략해도 될까요?
  3. MESSAGE '...' TYPE 'E'에서 'E'는 무엇을 의미하나요?
정답/해설 보기
  1. 프로그램 검증입니다. 두 입력값의 조합 조건은 Domain이나 Foreign Key만으로 표현하기 어렵습니다.
  2. 아니요. DDIC 검증은 주로 화면 입력 단계에서 동작하므로, 화면을 거치지 않는 경로에는 프로그램 검증을 별도로 넣어야 합니다.
  3. Error(오류) 타입입니다. 사용자에게 오류로 표시되고 진행이 중단되는 메시지 유형입니다.

10. 한눈에 정리 🏁

📝

Chapter 4 마무리 핵심

  • DDIC Validation은 타입, 길이, 고정값, Foreign Key, Search Help 같은 공통 규칙에 강합니다.
  • Program Input Check는 기간, 권한, 상태, 조합 조건 같은 업무 문맥을 확인합니다.
  • MESSAGE는 사용자에게 오류나 안내를 전달하는 ABAP 문법입니다.
  • 공통 규칙은 DDIC에, 상황별 규칙은 프로그램에 두는 것이 유지보수에 좋습니다.
  • F4 Help와 DDIC 검증이 있어도 최종 업무 검증을 생략하면 안 됩니다.

이제 DDIC 관계와 입력 도움말의 기본 그림을 잡았습니다. 다음 Chapter ABAP 모듈화 기초에서는 프로그램 안의 코드를 더 작고 읽기 좋은 단위로 나누는 방법을 배웁니다.
