학습 목표

Chapter 4 내내 “편의(F4) ≠ 검증”을 반복했습니다. 이번 마지막 Lesson에서는 DDIC 검증이 자동으로 해주는 것과, 프로그램이 직접 해야 하는 검증(MESSAGE, Input Check)을 역할 분리 관점에서 정리합니다. 두 검증을 2단 방어선으로 설계하는 법을 잡습니다.

1. 지난 흐름 정리: 두 종류의 검증이 있다 🛡️

Foreign Key/Check Table, Search Help를 배우며 계속 강조한 사실이 있죠. DDIC가 화면에서 자동으로 막아주는 부분이 있고, 그것만으로는 부족한 부분이 있습니다. 후자는 프로그램이 직접 검증해야 합니다.

DDIC 검증은 “화면 앞단의 1차 문지기”, 프로그램 검증은 “백엔드의 최후 수호자”입니다. 둘은 경쟁이 아니라 역할 분담입니다.

2. DDIC 자동 검증: 무엇을 해주고, 어디서 멈추나 🚧

DDIC가 자동으로 막아주는 것 vs 한계

자동으로 해주는 것
  • 타입/길이: 문자칸에 넘치는 숫자, 날짜칸에 문자 방어
  • Domain 고정값: 정해진 값 외 차단(드롭다운)
  • Foreign Key/Check Table: 마스터에 없는 코드 차단
치명적 한계
  • 오직 화면(Dynpro/Selection Screen) 입력에서만 동작
  • DB 물리 제약이 아님
  • 프로그램 INSERT/UPDATE·인터페이스는 우회

DDIC 검증은 “키보드로 화면에 칠 때”만 방패가 됩니다. 화면을 거치지 않으면 방패가 사라집니다.

3. 프로그램 검증이 반드시 필요한 경우 🧩

DDIC로는 못 막는 3가지

① 화면 밖 경로
Excel 업로드, RFC, BAPI, IDoc
실무 데이터의 다수가 인터페이스 유입
DDIC 방어막 미작동 → 수동 검증
② 복합 업무 규칙
필드 간 교차 검증
예: 등급=VIP일 때만 할인율 20%↑
DDIC는 단일 필드만 봄
③ 권한
이 사용자가 이 회사코드를 바꿀 자격?
AUTHORITY-CHECK
DDIC로 불가 → 프로그램 로직

화면을 거치지 않거나, 여러 필드를 함께 보거나, 권한을 따지는 검증은 모두 프로그램의 몫입니다.

4. MESSAGE 문: 6가지 타입과 흐름 제어 📣

프로그램이 “이 값 잘못됐어요”를 사용자에게 알리고 흐름을 통제하는 수단이 MESSAGE 문입니다. 타입에 따라 프로그램이 멈출지 말지가 달라집니다.

메시지 타입별 동작

타입표시흐름
E 에러빨간 상태바중단 재입력 강제
W 경고노란 상태바엔터 한 번 더 누르면 통과
I 정보팝업확인 후 계속 진행
S 성공다음 화면 상태바방해 없이 진행
A 중단팝업강제 종료
X 덤프런타임 에러Short Dump

절대 뚫리면 안 되는 검증은 E를 씁니다. W는 사용자가 무시하고 진행할 수 있습니다.

5. AT SELECTION-SCREEN: 실행 직전의 입력 검증 ✋

사용자가 PARAMETERS에 값을 넣고 실행(F8)을 누르면, 메인 로직으로 넘어가기 직전에 AT SELECTION-SCREEN 이벤트가 호출됩니다. 여기서 Selection Screen 입력값을 검증하기 좋습니다.

ABAP

2
3
4

6 
PARAMETERS p_date TYPE sy-datum.

AT SELECTION-SCREEN.
  IF p_date < sy-datum.
    MESSAGE e001(zmsg).   " 과거 날짜 → 에러: 선택화면으로 되돌려 재입력 강제
  ENDIF.

E(에러) 메시지를 던지면 메인 로직(START-OF-SELECTION)으로 넘어가지 못하고, 입력 화면으로 되돌아가 사용자가 값을 고치도록 강제합니다. DDIC가 못 막는 “과거 날짜 금지” 같은 업무 규칙을 여기서 처리합니다.

6. 2단 방어선으로 설계하기 🧱

역할 분리 — 상호 보완하는 두 계층

1계층 · DDIC (화면 앞단)
타입/길이, Domain 고정값
단일 마스터 존재 검사(Check Table)
즉각적인 1차 오타 차단
→
2계층 · Program (백엔드)
업무 규칙·교차 검증
권한(AUTHORITY-CHECK)
인터페이스 유입 데이터 검증

1계층이 가벼운 오타를 화면에서 걸러주고, 2계층이 그걸 통과했거나 우회해 들어온 데이터를 정밀 검증합니다.

ABAP Cloud / RAP에서는 이 역할 분리가 어떻게 진화하나?

Clean Core(RAP)에서는 화면을 통제하던 AT SELECTION-SCREEN·Dynpro 로직이 사라집니다. 대신 1계층은 CDS View Entity가 타입·Domain을 OData 메타데이터로 Fiori UI에 넘겨주고, 2계층의 강한 비즈니스 검증은 RAP의 Behavior Definition(BDEF) 안 Validations 로직에 캡슐화됩니다. 화면에서 들어오든 OData API로 꽂히든 백엔드 코어가 동일한 검증을 타도록 통일된 것이 핵심입니다.

7. 자주 하는 오해 🚨

⚠️

오해 1: “Foreign Key 걸었으니 인터페이스 데이터도 안전하겠지”

가장 큰 사고의 원인입니다. Check Table은 DB 무결성 제약이 아니라 화면 검증입니다. BAPI·RFC·업로드로 들어오는 데이터는 화면 방어막을 거치지 않으므로, 프로그램에서 직접 검증(예: BAPI Return 메시지 파싱)해야 합니다.

⚠️

오해 2: “Warning(W)이면 끝까지 막을 수 있다”

W는 사용자가 엔터를 한 번 더 치면 그대로 통과됩니다. 절대 통과시키면 안 되는 검증은 E(에러)를 쓰세요.

⚠️

오해 3: “에러 메시지를 띄우면 잘못된 값이 알아서 지워진다”

메시지를 띄우는 것과 변수를 비우는 것은 별개입니다. 에러를 띄워도 변수에는 잘못된 값이 남아 있을 수 있으니, 재입력·재처리 시 변수 처리에 주의하세요.

8. 미니 실습: 검증 책임 나누기 🧪

✍️

실습 과제

  1. “항공사 코드는 마스터에 있어야 한다 / 출발일은 오늘 이후여야 한다 / 이 사용자가 해당 노선을 변경할 권한이 있어야 한다” 세 규칙을 1계층(DDIC)과 2계층(프로그램)으로 분류합니다.
  2. 출발일 검증을 AT SELECTION-SCREEN에서 처리한다면 메시지 타입은 무엇을 쓸지, 그 이유(흐름 중단)를 적습니다.
  3. 같은 데이터가 화면이 아니라 Excel 업로드로 들어온다면 어떤 검증이 추가로 필요한지 적습니다.

완료 조건: “DDIC=화면 1차, 프로그램=업무·권한·인터페이스 2차”로 책임을 나누고, 필수 차단엔 E를 쓰는 이유를 설명하면 성공입니다.

10. 확인 퀴즈 ✅

  1. DDIC의 Foreign Key 검증은 프로그램의 직접 INSERT에도 동작하나요?
  2. 필드 간 교차 검증(예: 등급에 따른 할인율 제한)은 어디서 해야 하나요?
  3. 반드시 통과시키면 안 되는 검증에는 어떤 MESSAGE 타입을 써야 하나요?
  4. Selection Screen 입력값을 실행 직전에 검증하는 이벤트는 무엇인가요?
정답/해설 보기
  1. 아니요. DDIC 검증은 화면 입력에서만 동작하며 직접 INSERT는 우회됩니다. 프로그램 검증이 필요합니다.
  2. 프로그램(2계층)에서 합니다. DDIC는 단일 필드만 보므로 교차 검증을 못 합니다.
  3. E(에러)입니다. W(경고)는 사용자가 엔터를 다시 치면 통과됩니다.
  4. AT SELECTION-SCREEN 이벤트입니다. 여기서 E를 던지면 선택화면으로 되돌립니다.
