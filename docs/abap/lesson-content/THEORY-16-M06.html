학습 목표

지금까지 배운 최신 문법을 모아, 옛 스타일 코드를 깔끔한 Modern ABAP으로 리팩터링하는 감각을 익힙니다. "왜, 어디까지 바꿀지"의 기준을 세우며 Chapter를 마무리합니다.

1. 지난 시간 연결: 도구를 모으면 무엇이 달라질까 🧰

인라인 선언, VALUE, CORRESPONDING, Table Expression, String Template을 따로 배웠습니다. 이 도구들을 함께 쓰면, 길고 복잡하던 옛 코드가 놀랍도록 짧고 읽기 쉬워집니다. 이렇게 동작은 그대로 두고 코드 구조만 개선하는 것을 리팩터링이라고 합니다.

2. Before → After ✍️

" Before (옛 스타일)
DATA: lt_out  TYPE ty_flights,
      ls_out  TYPE ty_flight,
      lv_text TYPE string.
SELECT carrid connid price FROM sflight INTO TABLE lt_out.
READ TABLE lt_out INTO ls_out WITH KEY carrid = 'LH'.
IF sy-subrc = 0.
  CONCATENATE '요금:' ls_out-price INTO lv_text SEPARATED BY space.
ENDIF.
" After (Modern)
SELECT carrid, connid, price FROM sflight INTO TABLE @DATA(lt_out).
IF line_exists( lt_out[ carrid = 'LH' ] ).
  DATA(lv_text) = |요금: { lt_out[ carrid = 'LH' ]-price NUMBER = USER }|.
ENDIF.
💡

줄었지만 더 명확해졌다

선언이 사라지고(인라인), 검색이 짧아지고(Table Expression), 문자열이 깔끔해졌습니다(String Template). 핵심 로직이 한눈에 들어오죠. 짧아진 게 아니라 의도가 또렷해진 겁니다.

3. 어디까지 바꿀까? — 리팩터링의 선 ✂️

  • ✅ 새로 짜는 코드: 처음부터 Modern으로. 가장 부담 없습니다.
  • ✅ 마침 고치는 김에: 어차피 수정하는 부분을 Modern으로 정리.
  • ⚠️ 잘 도는 옛 코드: 단지 "옛날 스타일"이라는 이유로 멀쩡한 운영 코드를 통째로 바꾸는 건 위험합니다. 바꾸면 테스트도 다시 해야 합니다.
리팩터링의 목적은 "최신 문법 자랑"이 아니라 "읽기 쉽고 고치기 쉬운 코드"입니다. 위험과 이득을 견줘서 결정하세요.

4. 정상 흐름과 오류 흐름 🔍

  • ✅ 정상: 동작(결과)은 그대로 두고 구조만 개선 → 같은 입력에 같은 출력.
  • ❌ 오류 1: Table Expression으로 바꾸며 예외 처리(OPTIONAL)를 빠뜨려, 없던 덤프가 생김(M04 주의).
  • ❌ 오류 2: CORRESPONDING으로 바꾸며 이름 다른 필드가 누락됨(M03 주의).

5. 실무에서 조심할 점 🚨

⚠️

리팩터링 후엔 반드시 테스트

"동작은 똑같겠지"라는 가정이 리팩터링의 가장 큰 함정입니다. 최신 문법으로 바꾸는 과정에서 예외 처리나 필드 매핑이 달라질 수 있습니다. 바꾼 뒤에는 같은 입력으로 같은 결과가 나오는지 반드시 확인하세요. 가능하면 ABAP Unit 테스트(THEORY 이후)로 안전망을 만들어 두면 마음 놓고 개선할 수 있습니다.
