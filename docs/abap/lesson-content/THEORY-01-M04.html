학습 목표

이번 Lesson에서는 낱개 Data Element를 모아 한 줄짜리 데이터 모양을 만드는 Structure를 배웁니다. Structure 안의 Component, 프로그램 메모리의 Work Area, 여러 곳에서 공유하는 Reusable Type을 구분하고, Structure가 Transparent Table과 어떻게 다른지 설명할 수 있게 됩니다.

1. 낱개 필드는 결국 한 줄로 묶인다

지금까지 Domain으로 재질을 정하고, Data Element로 의미와 라벨을 붙였습니다. 하지만 실제 업무 데이터는 낱개 필드 하나만으로 움직이지 않습니다. 항공편 한 건에는 항공사 코드, 편명, 출발일, 출발지, 도착지가 함께 필요합니다.

Structure는 이렇게 함께 움직이는 필드들을 정해진 순서로 묶는 DDIC 타입입니다. SAP Help는 Structure가 Component로 이루어진 structured type이며, Component는 Data Element나 직접 타입, 다른 Structure, Table Type 등을 참조할 수 있다고 설명합니다.

Structure는 “한 줄 데이터가 어떤 칸을 가져야 하는가”를 정의하는 재사용 가능한 타입입니다.

2. Structure 안에는 Component가 들어간다

Structure를 표처럼 생각하면 이해가 쉽습니다. Structure 자체는 한 줄의 모양이고, 그 안의 각 칸이 Component입니다. Component는 보통 의미가 붙은 Data Element를 타입으로 참조합니다.

항공편 한 줄 Structure 예시

Structure
ZSFLIGHT_LINE
항공편 한 줄 모양
DB 저장소 아님
→
Components
CARRID : 항공사 코드
CONNID : 편명

Component Type

Data Element를 쓰면 라벨과 F1/F4 같은 의미 정보까지 함께 따라올 수 있습니다.

3. Structure와 Work Area는 설계도와 실제 변수다

초심자가 가장 자주 헷갈리는 지점은 DDIC Structure와 ABAP 프로그램 안의 Work Area입니다. Structure는 타입이고, Work Area는 그 타입으로 만든 실제 변수입니다.

설계도와 실체 구분

Structure
  • DDIC에 저장되는 타입 정의입니다.
  • 필드 이름, 순서, Component 타입을 정의합니다.
  • 그 자체가 프로그램 실행 중 값을 담는 변수는 아닙니다.
Work Area
  • ABAP 프로그램 메모리에 생기는 실제 데이터 객체입니다.
  • Structure 타입을 사용해 한 줄 값을 담습니다.
  • wa_flight-carrid처럼 하이픈으로 Component에 접근합니다.

DATA wa_flight TYPE zsflight_line.에서 zsflight_line은 타입, wa_flight는 실제 Work Area입니다.

Structure 자체가 메모리를 차지할까?

Structure 정의 자체는 설계도입니다. 프로그램에서 그 타입으로 변수나 파라미터를 선언할 때 실제 데이터 객체가 생깁니다. “타입”과 “변수”를 구분해야 합니다.

4. Structure는 저장소가 아니다

Structure와 Transparent Table은 둘 다 필드 목록처럼 보입니다. 하지만 결정적인 차이는 물리 데이터베이스 저장소를 만드는가입니다.

Structure와 Transparent Table 비교

구분 Structure Transparent Table
정체 한 줄 데이터 타입 데이터베이스 테이블 정의
활성화 결과 Structure 런타임 타입 생성 DB 저장 대상과 연결
데이터 저장 영구 저장 안 함 영구 저장 가능
사용 예 Work Area, 메서드 파라미터, Table Type row SELECT, INSERT 대상
⚠️

SELECT * FROM 구조체는 안 됩니다

Structure는 물리 데이터가 없으므로 조회 대상이 아닙니다. Structure는 데이터를 읽어오는 대상이 아니라, 읽어온 값을 담거나 전달하는 타입으로 사용합니다.

5. Reusable Type으로 쓰는 기준

DDIC Structure를 만들면 시스템 여러 곳에서 같은 이름으로 참조할 수 있습니다. 그래서 반복해서 쓰는 데이터 모양에는 Reusable Type으로 가치가 있습니다.

Structure 사용처 판단

좋은 후보
여러 프로그램에서 같은 한 줄 모양을 씁니다.
화면·함수·메서드 인터페이스에서 공유합니다.

DDIC 라벨이나 확장성이 필요 없습니다.
public type으로 충분할 수 있습니다.
나쁜 후보
데이터 저장소를 기대하고 만듭니다.
테이블 키와 저장 설정이 필요합니다.

DDIC Structure 대신 클래스 public type을 써도 될까?

가능합니다. SAP Learning도 새 Dictionary 객체를 만들기 전에 global class나 interface의 public structure type을 검토하라고 안내합니다. 여러 도구와 화면에서 DDIC 의미 정보가 필요할 때 Dictionary Structure의 가치가 커집니다.

6. Flat, Nested, Include, Deep은 지금 이렇게만 구분한다

Structure에는 더 깊은 주제도 많지만, 지금은 이름만 보고 겁먹지 않을 정도로만 구분하면 충분합니다. 이번 Lesson의 중심은 flat structure입니다.

Structure 형태 구분

형태 초급 설명 지금 할 일
Flat Structure Component가 주로 Data Element 같은 elementary type을 참조합니다. 오늘의 중심
Nested Structure Component가 또 다른 Structure를 참조해 계층이 생깁니다. 개념만
Include Structure 다른 Structure의 Component를 같은 레벨로 펼쳐 넣습니다. 오해 방지
Deep Structure Table Type, string, reference처럼 깊은 Component를 포함합니다. 후속 학습
Include와 Nested는 왜 헷갈릴까?

Include는 다른 Structure의 Component가 같은 레벨로 들어온 것처럼 보입니다. Nested는 하위 Structure 이름 아래로 한 단계 더 들어갑니다. 그래서 접근도 wa-city와 wa-address-city처럼 달라질 수 있습니다.

7. 생성 흐름: Component를 채우고 활성화한다

SAP GUI와 ADT의 화면은 다르지만, 기본 흐름은 같습니다. 이름을 만들고, Component를 채우고, 타입을 지정하고, 활성화합니다.

Structure 생성 흐름

1. Structure 생성ZSFLIGHT_LINE처럼 한 줄 타입 이름을 정한다.
2. 설명 입력나중에 찾기 쉬운 short text를 적는다.
3. Component 추가CARRID, CONNID, FLDATE 등을 순서대로 둔다.
4. Component Type 지정Data Element, 직접 타입, 다른 Structure 등을 선택한다.
5. 활성화검사 통과 후 프로그램과 인터페이스에서 사용할 수 있다.
Component 순서는 중요할까?

중요합니다. 이름 기반 이동을 쓰는 경우도 있지만, 초급 단계에서는 Structure의 Component 이름, 순서, 타입을 업무 의미에 맞게 안정적으로 정하는 습관이 필요합니다.

실습 과제

  1. Structure 이름을 정합니다. 예: ZSFLIGHT_LINE
  2. Component 5개를 정합니다. 예: CARRID, CONNID, FLDATE, FROM_AIRP, TO_AIRP
  3. 각 Component가 참조할 Data Element 또는 직접 타입을 적습니다.
  4. 이 Structure로 Work Area를 만들 때의 선언 문장을 한 줄로 적습니다.
  5. 이 Structure가 DB에 데이터를 저장하지 않는다는 점을 한 문장으로 설명합니다.

완료 조건: Component 목록, 타입 연결, Work Area 선언, “저장소가 아니다” 설명이 모두 있으면 성공입니다.

10. 확인 퀴즈

  1. Structure를 활성화하면 실제 DB 테이블이 자동으로 만들어질까요?
  2. Structure 안의 낱개 필드는 무엇이라고 부르나요?
  3. DATA wa_flight TYPE zsflight_line.에서 타입과 변수는 각각 무엇인가요?
  4. Structure와 Transparent Table의 가장 큰 차이는 무엇인가요?
  5. Flat Structure와 Nested Structure를 한 문장으로 구분해보세요.
정답/해설 보기
  1. 아니요. Structure는 DB 저장소가 아니라 DDIC 타입입니다.
  2. Component입니다. Component마다 Data Element, 직접 타입, 다른 Structure 등을 지정할 수 있습니다.
  3. zsflight_line은 타입, wa_flight는 변수입니다. 변수는 프로그램 메모리에 생기는 Work Area입니다.
  4. 영구 저장 여부입니다. Structure는 한 줄 타입이고, Transparent Table은 DB 저장 대상입니다.
  5. Flat은 Component가 같은 레벨에 있고, Nested는 Component 안에 또 다른 Structure 계층이 있습니다.

11. 한눈에 정리

Structure여러 Component를 묶어 한 줄 데이터 모양을 만드는 DDIC 타입입니다.
ComponentStructure 안의 낱개 필드이며 Data Element나 직접 타입을 참조합니다.
Work AreaStructure 타입으로 만든 실제 ABAP 메모리 변수입니다.
저장소 아님Structure는 DB 테이블이 아닙니다. 영구 저장은 Transparent Table의 역할입니다.
