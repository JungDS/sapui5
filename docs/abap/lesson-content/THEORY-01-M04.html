학습 목표

여러 필드를 하나로 묶는 Structure(구조체)를 만들어 봅니다. 컴포넌트(Component)의 개념과, Structure가 왜 재사용 가능한 타입(Reusable Type)으로 쓰이는지 익힙니다.

1. Structure는 부품을 묶은 "꾸러미" 📦

지금까지 만든 필드 부품(Data Element)은 낱개였습니다. 하지만 실무 데이터는 보통 여러 값이 한 묶음으로 다닙니다. 예를 들어 '항공편 한 건'은 항공사·편명·출발지·도착지·날짜가 한 세트죠.

이렇게 여러 필드를 정해진 순서로 묶은 부품이 Structure(구조체)입니다. 묶음 안의 각 필드를 컴포넌트(Component)라고 부릅니다.

💡

Structure 예시 (ZSFLIGHT)

CARRID(항공사) · CONNID(편명) · FLDATE(날짜) · PRICE(요금)
각 컴포넌트는 앞에서 배운 Data Element를 타입으로 지정합니다.

2. Structure는 그릇일 뿐, 데이터를 저장하지 않는다 🥣

가장 자주 헷갈리는 지점입니다. Structure 자체는 데이터베이스에 데이터를 저장하지 않습니다. 데이터가 잠깐 담겼다 비워지는 그릇(틀)일 뿐입니다.

Structure는 "이런 모양의 데이터를 다룰 거야"라는 설계도입니다. 프로그램이 실행될 때 이 모양대로 메모리에 작업 영역(Work Area)을 잡아 한 줄씩 처리합니다. 실제 영구 저장은 다음 Lesson의 Transparent Table이 맡습니다.

ABAP 프로그램에서는 DATA gs_flight TYPE zsflight. 처럼, 만들어 둔 Structure를 타입으로 그대로 가져다 변수를 선언합니다.

3. 재사용 가능한 타입(Reusable Type) ♻️

DDIC에 한 번 만들어 둔 Structure는 전역(Global) 타입이 되어 어디서든 재사용됩니다.

  • ✅ 변수 타입: Work Area, Internal Table의 한 줄(Line Type)로 사용
  • ✅ 인터페이스: Function Module / Method의 파라미터 타입으로 사용
  • ✅ 일관성: 필드 구성이 바뀌면 Structure 하나만 고쳐도 쓰는 모든 곳에 반영

4. 실무에서 주의할 점 🚨

⚠️

컴포넌트 순서와 타입 일치

Structure의 컴포넌트 순서는 의미가 있습니다. 특히 다른 구조와 값을 통째로 옮기는 MOVE-CORRESPONDING이 아니라 단순 대입(=)을 쓰면 순서·타입이 어긋나 데이터가 엉뚱한 칸에 들어갈 수 있습니다. 가능한 한 이름 기반 매핑을 쓰고, 타입은 Data Element로 정확히 맞추세요.

또한 이 단계에서는 깊은 중첩(Structure 안에 Internal Table을 넣는 Deep Structure)까지 욕심내지 않습니다. 그건 THEORY-07에서 따로 다룹니다.

5. 다음 단계로 🚀

Structure로 데이터의 모양(설계도)을 완성했습니다. 이제 이 모양 그대로 데이터를 영구히 저장할 진짜 테이블을 만들 차례입니다.

다음 Lesson 'Transparent Table 기본 생성'에서 실제 데이터베이스에 행이 쌓이는 투명 테이블을 만들어 봅니다.
