학습 목표

지금까지 만든 낱개 필드들을 하나의 세트로 묶는 Structure를 배웁니다. Structure 안의 한 칸인 Component, 프로그램에서 잠깐 데이터를 담는 Work Area, 여러 곳에서 같은 모양을 재사용하는 Reusable Type 개념을 초심자 눈높이로 연결합니다.

1. 지난 시간 연결: 낱개 필드는 혼자 일하지 않는다 🧺

이전 Lesson까지 우리는 Domain으로 재질을 정하고, Data Element로 의미와 라벨을 붙였습니다. 이제 “항공사 코드”, “편명”, “출발일”, “금액” 같은 낱개 필드 부품을 만들 수 있습니다.

그런데 실제 업무 데이터는 대부분 여러 칸이 한 세트로 움직입니다. 항공편 한 건을 생각해보면 항공사 코드만 덜렁 있으면 부족합니다. 편명, 날짜, 출발지, 도착지, 금액이 함께 있어야 “항공편 한 줄”이 됩니다.

Structure는 낱개 필드 여러 개를 “한 줄짜리 데이터 세트”로 묶어주는 DDIC 타입입니다.

2. Structure와 Component를 천천히 보기 📦

Structure는 여러 필드를 정해진 순서로 묶은 설계도입니다. 그리고 Structure 안에 들어가는 각각의 필드를 Component라고 부릅니다.

💡

예시: 항공편 한 줄 구조 ZSFLIGHT

  • CARRID: 항공사 코드, 타입은 항공사 코드용 Data Element
  • CONNID: 편명, 타입은 편명용 Data Element
  • FLDATE: 출발일, 타입은 날짜용 Data Element
  • PRICE: 요금, 타입은 금액용 Data Element

이렇게 묶어두면 프로그램이나 함수가 “항공편 한 줄 모양”을 같은 기준으로 사용할 수 있습니다.

여기서 중요한 것은 각 Component가 보통 Data Element를 타입으로 가진다는 점입니다. 그러면 Data Element가 가진 의미와 라벨을 그대로 물려받을 수 있습니다. Structure는 낱개 부품을 대충 모아놓은 것이 아니라, 이미 의미가 붙은 필드를 한 줄로 정리하는 과정입니다.

3. 가장 큰 오해: Structure는 데이터를 저장하지 않는다 🥣

초보자가 Structure를 처음 보면 “테이블처럼 생겼으니까 여기에 데이터가 저장되나?”라고 생각하기 쉽습니다. 하지만 꼭 기억해야 합니다. Structure 자체는 데이터베이스에 데이터를 영구 저장하지 않습니다.

Structure는 창고가 아니라 그릇의 모양입니다. “이 그릇은 항공사 칸, 편명 칸, 날짜 칸, 금액 칸이 있어요”라고 알려주는 설계도에 가깝습니다. 실제 데이터는 프로그램 실행 중 메모리에 잠깐 담겼다가, 프로그램이 끝나면 사라집니다.

🧪

DATA gs_flight TYPE zsflight.

gs_flight-carrid = 'KE'.
gs_flight-connid = '0017'.
gs_flight-fldate = sy-datum.

gs_flight는 Work Area입니다. ZSFLIGHT Structure 모양대로 메모리에 생긴 “임시 한 줄 그릇”이라고 보면 됩니다.

4. 정상 흐름과 오류 흐름으로 확인하기 🔎

Structure도 정상 흐름과 실수 흐름을 나눠서 보면 이해가 빠릅니다.

  • ✅ 정상 흐름: Structure를 만들고 Component에 올바른 Data Element를 연결합니다. 프로그램에서 TYPE zsflight로 선언하면 같은 모양의 Work Area를 만들 수 있습니다.
  • ❌ 타입 연결 실수: 금액 필드에 날짜용 Data Element를 연결하면, 화면 라벨과 데이터 타입이 업무 의미와 어긋납니다. 나중에 프로그램에서 값 처리도 꼬입니다.
  • ❌ 저장소 오해: Structure를 만들고 “이제 데이터가 DB에 저장되겠지?”라고 생각하면 안 됩니다. 영구 저장은 다음 Lesson의 Transparent Table이 담당합니다.
Structure는 “한 줄의 모양”을 정의합니다. “여러 줄을 오래 저장하는 창고”는 아닙니다.

5. Reusable Type: 한 번 만든 모양을 계속 쓰기 ♻️

DDIC에 Structure를 만들어두면 시스템 전체에서 이름으로 불러 쓸 수 있는 Reusable Type이 됩니다. 즉, 같은 항공편 한 줄 모양이 필요한 곳마다 매번 필드를 새로 적지 않고 ZSFLIGHT 하나를 가져다 쓸 수 있습니다.

  • 프로그램 변수: DATA gs_flight TYPE zsflight.처럼 한 줄 Work Area를 만들 수 있습니다.
  • Internal Table의 한 줄: 나중에 배울 여러 줄 목록의 라인 타입으로 사용할 수 있습니다.
  • 함수나 메서드 인터페이스: 프로그램끼리 데이터를 주고받을 때 “이 모양으로 주세요”라고 약속할 수 있습니다.

이 재사용성 덕분에 여러 개발자가 같은 데이터 모양을 다르게 정의하는 사고를 줄일 수 있습니다. 한 사람이 만든 Structure를 모두가 같이 쓰면, 이름과 순서와 타입이 맞아 떨어집니다.

6. 실무에서 조심해야 할 점 🚨

⚠️

Component 순서는 생각보다 중요합니다

두 Structure가 비슷하게 생겼다고 해서 무조건 안전하게 복사되는 것은 아닙니다. 단순 대입을 할 때는 순서와 타입이 맞지 않으면 엉뚱한 값이 들어갈 수 있습니다. 이름이 같은 Component끼리 옮기는 MOVE-CORRESPONDING 같은 방식은 나중에 배울 예정이지만, 지금은 “Structure의 순서와 이름은 대충 정하면 안 된다”만 기억하면 됩니다.

또한 Structure 안에 또 다른 Structure나 Internal Table을 넣는 Deep Structure도 만들 수 있습니다. 하지만 지금 단계에서 너무 깊게 들어가면 헷갈립니다. 이번 Lesson에서는 평평한 한 줄 구조만 정확히 잡고, 복잡한 구조는 Chapter 7에서 다시 다룹니다.

7. 한눈에 정리 🏁

📝

오늘의 핵심만 딱 잡기

  • Structure는 여러 필드를 한 줄 데이터 세트로 묶는 DDIC 타입입니다.
  • Component는 Structure 안의 낱개 필드입니다.
  • Structure는 데이터베이스 저장소가 아니라, 프로그램에서 쓰는 한 줄 그릇의 모양입니다.
  • Work Area는 Structure 모양대로 메모리에 생기는 임시 한 줄 변수입니다.
  • Structure는 여러 프로그램과 인터페이스에서 재사용할 수 있는 Reusable Type입니다.

이제 우리는 한 줄 데이터의 모양을 만들 수 있습니다. 다음 Lesson Transparent Table 기본 생성에서는 이 한 줄 모양을 바탕으로 데이터를 실제 데이터베이스에 오래 보관하는 창고를 만들어보겠습니다.
