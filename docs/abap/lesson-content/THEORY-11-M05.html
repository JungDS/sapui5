학습 목표

조회 결과를 원하는 순서로 줄 세우는 ORDER BY를 배웁니다. 오름차순/내림차순(Sort Order)을 지정하는 법과, "정렬을 DB에서 할지 ABAP에서 할지"의 판단 감각을 잡습니다.

1. 지난 시간 연결: 결과가 뒤죽박죽일 때 🔀

SELECT로 데이터를 꺼내면, 특별히 지정하지 않는 한 순서가 보장되지 않습니다. DB가 가장 빠른 방식으로 꺼내 주기 때문에, 우리가 기대한 순서대로 나온다는 보장이 없습니다.

그런데 사람이 보는 리포트는 보통 정렬이 필요합니다. "매출 높은 순으로", "날짜 빠른 순으로"처럼요. 이때 DB에게 "이 기준으로 줄 세워서 줘"라고 하는 것이 ORDER BY입니다.

2. ORDER BY 기본 문법 ✍️

ABAP
1

SELECT carrid, connid, fldate, price
  FROM spfli
  ORDER BY carrid ASCENDING,      "항공사 코드 오름차순,
           price  DESCENDING      "같은 항공사면 요금 내림차순
  INTO TABLE @DATA(lt_sorted).
  • ASCENDING: 오름차순(작은 값 → 큰 값). 기본값이라 생략 가능.
  • DESCENDING: 내림차순(큰 값 → 작은 값).
  • 여러 기준: 콤마로 이어 적으면, 앞 기준이 같을 때 뒤 기준으로 다시 정렬합니다(1차/2차 정렬).
💡

ORDER BY PRIMARY KEY

키 순서대로 정렬하고 싶으면 ORDER BY PRIMARY KEY라고 간단히 쓸 수 있습니다. 테이블의 키 필드 순서대로 정렬됩니다.

3. 정렬은 DB에서? ABAP에서? 🤔

정렬은 두 군데서 할 수 있습니다. DB에서 ORDER BY로 하거나, 데이터를 ABAP 내부 테이블로 받은 뒤 SORT 문으로 하거나요.

  • ✅ DB ORDER BY: 정렬 기준이 인덱스와 맞으면 효율적입니다. 결과를 바로 정렬된 채 받습니다.
  • ✅ ABAP SORT: 이미 메모리에 올라온 데이터를 가볍게 다시 정렬할 때 좋습니다(THEORY-07에서 배운 SORT).
큰 데이터를 DB에서 꺼내며 정렬까지 시키면 DB 부하가 커질 수 있습니다. 반대로 작은 결과를 여러 기준으로 이리저리 정렬한다면 ABAP SORT가 편합니다. 상황에 따라 고릅니다.

4. ORDER BY 전/후 — 정렬 전과 후 비교 🔀

DB ORDER BY vs ABAP SORT 선택 기준

상황DB ORDER BYABAP SORT
조회 시 정렬 보장이 필요✔ 적합
이미 메모리에 올라온 데이터 재정렬✔ 적합
정렬 기준이 자주 바뀜✔ 적합
대량 데이터 + 인덱스 없는 필드 정렬⚠ 느릴 수 있음
ALV 화면에서 사용자가 직접 정렬 가능생략 가능

정훈영이 매출 리포트를 만들 때: DB에서 꺼낼 때 정렬하면 화면이 바로 정돈되고, 이미 받아온 데이터를 기준만 바꿔 보고 싶다면 ABAP SORT가 편합니다.

5. 정상 흐름과 오류 흐름 🔍

  • ✅ 정상: ORDER BY로 명시하면 결과 순서가 보장됩니다.
  • ❌ 흔한 실수: ORDER BY를 안 쓰고 "어차피 키 순으로 나오겠지"라고 가정 → 환경/DB에 따라 순서가 달라져 버그가 됩니다. 순서가 중요하면 반드시 명시하세요.

6. 실무에서 조심할 점 🚨

⚠️

정렬 비용은 공짜가 아닙니다

대량 데이터를 인덱스에 없는 필드로 ORDER BY 하면 DB가 따로 정렬 작업을 하느라 느려질 수 있습니다. "정말 정렬이 필요한가?", "정렬 기준이 인덱스와 맞는가?"를 한 번 생각해보세요. 화면 ALV는 사용자가 클릭으로 정렬할 수 있으니, 굳이 DB 정렬이 필요 없는 경우도 많습니다.

7. 미니 실습: ORDER BY 직접 써보기 🧪

✍️

실습 과제

  1. 예제 코드를 SE38에서 실행하고 lt_sorted의 순서가 carrid 오름차순 → price 내림차순으로 정렬됐는지 디버거로 확인합니다.
  2. ORDER BY carrid ASCENDING에서 ASCENDING을 DESCENDING으로 바꿔 결과 순서가 반전되는지 확인합니다.
  3. 정훈영·홍길동·아이유 3명의 판매 데이터를 임의 순서로 직접 채운 내부 테이블을 SORT 문으로 이름(ASCENDING) → 매출(DESCENDING) 순서로 정렬해봅니다.
  4. ORDER BY 없이 SELECT를 실행한 뒤 같은 SELECT를 다시 실행했을 때 순서가 달라지는지 여러 번 확인해봅니다(환경에 따라 차이가 나타날 수 있음).

완료 조건: "ORDER BY 없으면 순서가 보장되지 않는다", "ASCENDING이 기본값이라 생략 가능하다"를 직접 확인했으면 성공입니다.

8. 공식 문서로 더 확인하기 🔗

  • SAP Help Portal: SORT — 내부 테이블 SORT 문법과 ASCENDING/DESCENDING 옵션을 확인합니다.
  • SAP Help Portal: SELECT 문 개요 — SELECT 전체 절 구조에서 ORDER BY의 위치를 확인합니다.

9. 확인 퀴즈와 정답/해설 ✅

  1. ORDER BY를 쓰지 않으면 SELECT 결과의 순서가 보장되나요?
  2. 정훈영이 이름순(오름차순)으로 정렬된 사원 목록을 받은 뒤, 나중에 급여 내림차순으로 다시 보고 싶다면 DB ORDER BY와 ABAP SORT 중 어느 쪽이 더 효율적인가요?
  3. ORDER BY PRIMARY KEY는 무엇을 기준으로 정렬하나요?
정답/해설 보기
  1. 보장되지 않습니다. DB는 가장 빠른 방법으로 데이터를 꺼내므로 ORDER BY 없이는 실행할 때마다 순서가 달라질 수 있습니다. 순서가 중요하다면 반드시 ORDER BY를 명시해야 합니다.
  2. ABAP SORT가 더 효율적입니다. 데이터는 이미 메모리에 올라와 있으므로 DB에 다시 조회하지 않고 메모리에서 재정렬하면 됩니다. DB ORDER BY는 DB에서 꺼낼 때 한 번 정렬받는 데 적합하고, 이미 받은 데이터를 기준 바꿔 볼 때는 SORT가 빠릅니다.
  3. 테이블의 키 필드 순서대로 정렬합니다. ORDER BY PRIMARY KEY는 테이블에 정의된 키 필드 전체를 오름차순으로 정렬합니다. 명시적으로 필드를 나열하지 않아도 되어 편리하지만, 키가 여러 개인 경우 정렬 순서가 키 정의 순서에 따라 달라집니다.

10. 한눈에 정리 🏁

📝

오늘의 핵심만 딱 잡기

  • SELECT 결과 순서는 ORDER BY가 없으면 보장되지 않습니다.
  • ASCENDING/DESCENDING으로 방향을, 콤마로 여러 정렬 기준을 줍니다.
  • 정렬은 DB(ORDER BY)와 ABAP(SORT) 둘 다 가능하니 상황에 맞게 고릅니다.
  • 대량 데이터 정렬은 성능 비용이 있으니 정말 필요한지 따져봅니다.

여기까지 JOIN과 집계, 정렬을 배웠습니다. 그런데 JOIN 말고 "이미 ABAP에 있는 목록을 기준으로 DB를 조회"하고 싶을 때가 있습니다. 다음 Lesson FOR ALL ENTRIES 사용 기준에서 그 강력하지만 함정 많은 기능을 배웁니다.
