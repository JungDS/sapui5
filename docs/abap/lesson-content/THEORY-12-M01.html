학습 목표

코드 안에서 그때그때 쓰던 JOIN을, DDIC에 미리 만들어 두고 재사용하는 Database View를 배웁니다. 코드로 쓰는 Open SQL JOIN과 무엇이 같고 다른지 비교하는 것이 목표입니다.

1. 지난 시간 연결: 같은 JOIN을 매번 또 쓰는 게 번거롭다 🔁

앞 Chapter에서 우리는 SPFLI와 SCARR를 INNER JOIN으로 연결해 읽었습니다. 그런데 이 "항공편 + 항공사 이름" 조합을 여러 프로그램에서 똑같이 쓴다면, 매번 같은 JOIN 코드를 반복해서 적어야 합니다.

반복은 곧 실수와 유지보수 부담입니다. 그래서 SAP는 자주 쓰는 JOIN을 DDIC에 객체로 미리 정의해 두고, 마치 테이블 하나처럼 꺼내 쓰게 해줍니다. 이것이 Database View입니다.

2. Database View는 "미리 짜둔 JOIN" 🧩

DDIC View 중 가장 기본인 Database View는, 여러 테이블을 INNER JOIN으로 연결한 결과를 하나의 가상 테이블처럼 보여줍니다. 실제 데이터를 따로 저장하지는 않고, 조회할 때 원본 테이블에서 합쳐 보여줍니다.

💡

일상 비유: 자주 쓰는 레시피를 카드로 만들어 두기

매번 재료(테이블)를 어떻게 섞을지 떠올리는 대신, "항공편+항공사 카드"를 한 장 만들어 두는 거예요. 다음부터는 그 카드만 꺼내면 합쳐진 결과가 바로 나옵니다.

한 번 만들어 두면 ABAP에서는 SELECT ... FROM zv_flight_carr처럼 테이블 이름 자리에 View 이름을 넣어 쓰면 끝입니다.

3. Open SQL JOIN과 비교 ✍️

  • Open SQL JOIN: 코드 안에서 그때그때 정의. 상황마다 자유롭게 바꿀 수 있음(유연함).
  • Database View: DDIC에 한 번 정의해 재사용. 여러 프로그램이 같은 정의를 공유(일관성).
ABAP
1
2
3
4 
" View를 테이블처럼 사용
SELECT carrid, connid, carrname
  FROM zv_flight_carr      "← 미리 정의해 둔 Database View
  INTO TABLE @DATA(lt).
"이 JOIN을 여러 곳에서 똑같이 쓴다" → Database View가 어울립니다. "이번만, 이 화면에서만 특수하게 합친다" → 코드 JOIN이 편합니다.

4. SQL JOIN vs Database View 매커니즘 비교 시각화 🗺️

ABAP 프로그램에서 직접 JOIN을 수행할 때와, DB에 미리 만들어진 Database View 객체를 통해 조회할 때의 아키텍처 및 데이터 흐름의 차이를 살펴보겠습니다.

Open SQL JOIN vs Database View 처리 방식 비교

방법 A — Open SQL JOIN (프로그램 내 정의)
ABAP
1
2
3
4 
SELECT a~empid, b~deptname
  FROM zemployee AS a
  INNER JOIN zdept AS b
    ON a~deptid = b~deptid
1. 프로그램 실행쿼리문 내의 JOIN 구조를 런타임에 해석하여 DB로 요청
2. DB 처리두 테이블을 결합 연산하여 결과를 반환
방법 B — Database View (DDIC 사전 정의)
ABAP
1
2 
SELECT empid, deptname
  FROM zv_emp_dept  "← DB View
1. 프로그램 실행가상 테이블인 뷰 ZV_EMP_DEPT에 단순 조회 요청
2. DB 처리이미 정의된 뷰 스키마에 따라 내부적으로 JOIN 처리 후 즉시 반환

Database View는 DB 사전(Dictionary) 레벨에 물리적인 View 객체로 생성되므로, 여러 프로그램이 동일한 JOIN 구조를 재사용할 때 압도적으로 안전하고 일관된 데이터를 보장합니다.

5. 정상 흐름과 한계 🔍

  • ✅ 정상 흐름: 사원 테이블(`ZEMPLOYEE`)과 부서 테이블(`ZDEPARTMENT`)이 부서 코드(`DEPTID`)로 Foreign Key가 맺어져 있다면, 이를 기반으로 Database View를 손쉽게 생성하여 `정훈영(개발팀)`, `홍길동(영업팀)` 같은 짝이 맞는 INNER JOIN 결과 데이터를 테이블 조회하듯 가져올 수 있습니다.
  • ❌ 한계 1 — 읽기 전용 (Read-Only): Database View는 결합 데이터이므로 **수정(INSERT/UPDATE/DELETE)이 원천적으로 불가능**하며 오직 SELECT 조회만 가능합니다.
  • ❌ 한계 2 — INNER JOIN 한정: Classic Database View는 구조적으로 `INNER JOIN` 성격만 지원합니다. 짝이 없는 데이터(예: 부서가 없는 사원)까지 조회 결과에 남겨야 하는 `LEFT OUTER JOIN`과 같은 유연한 처리는 불가능합니다.

6. 실무에서 조심할 점 🚨

⚠️

Database View의 버퍼링 설정을 조심하세요

Database View는 일반 테이블처럼 **버퍼링(Buffering)**을 설정해 성능을 높일 수 있습니다. 하지만 뷰를 구성하는 기본 테이블 중 단 하나라도 데이터가 자주 바뀌거나 버퍼링이 맞지 않게 설계되어 있다면, 뷰 조회 시 최신 데이터가 누락되는 동기화 버그가 발생할 수 있습니다. 성능 최적화가 꼭 필요한 읽기 전용 코드 테이블 뷰에만 신중하게 적용해야 합니다.

7. 미니 실습: Database View 조회 프로그램 작성 🧪

✍️

실습 과제

  1. 표준 테이블인 항공편(`SPFLI`)과 항공사(`SCARR`)를 합친 표준 Database View인 SPFLIV를 탐색기로 확인합니다.
  2. 뷰 SPFLIV를 일반 투명 테이블처럼 사용하여 항공사 이름(`CARRNAME`)과 연결된 데이터를 한 번에 가져오는 SELECT 쿼리문을 작성하고 실행해 봅니다.
  3. 직접 작성한 SELECT 구문이 이전 레슨에서 직접 INNER JOIN을 구현했던 코드와 비교하여 얼마나 더 직관적이고 단순해졌는지 체감해 봅니다.

완료 조건: Database View를 FROM 절에 할당하여 다중 테이블 데이터를 JOIN 없이 단순 조회를 통해 출력할 수 있으면 성공입니다.

9. 확인 퀴즈와 정답/해설 ✅

  1. Database View는 내부적으로 어떤 JOIN 방식(INNER vs OUTER)으로 데이터를 연결하나요?
  2. Database View에 INSERT나 UPDATE 구문을 실행하여 원본 테이블의 데이터를 수정할 수 있나요?
  3. 실무에서 자주 쓰이는 JOIN 쿼리를 Open SQL로 매번 짜는 대신 Database View로 등록했을 때 얻는 가장 큰 설계적 이점은 무엇인가요?
정답/해설 보기
  1. 기본적으로 INNER JOIN으로 동작합니다. 따라서 양쪽 테이블에 매칭되는 키 값이 모두 존재하는 온전한 짝 데이터만 최종 결과로 출력됩니다.
  2. 아니요. 불가능합니다. Database View는 가상의 읽기 전용 객체이므로 원본 데이터를 뷰를 통해 변경할 수 없으며 오직 SELECT 조회만 가능합니다.
  3. 데이터 접근 구조의 '단일 진실 공급원(SSOT)'과 일관성 유지입니다. 한 번 정의된 뷰를 여러 프로그램이 공유하여 사용하므로, JOIN 조건 오타로 인한 버그를 원천 차단하고 중앙 집중식으로 결합 규칙을 편리하게 관리할 수 있습니다.

10. 한눈에 정리 🏁

📝

Database View 핵심 요약

  • Database View는 여러 테이블의 INNER JOIN을 DDIC 상에 뷰 객체로 미리 정의해 두고 테이블처럼 조회하는 가상 구조입니다.
  • 뷰 내부에는 실제 데이터가 저장되지 않으며, 런타임 조회 시점에 실시간으로 결합 처리가 일어납니다.
  • 조회만 가능하고 수정은 불가능하며, 버퍼링 설정 시 기본 테이블들의 버퍼 동기화 특성을 신중하게 따져야 합니다.
  • 최신 S/4HANA 및 ABAP Cloud 환경에서는 더욱 고성능의 CDS View Entity로 진화하여 사용됩니다.

Database View가 "여러 테이블 합치기"였다면, 다음 Lesson Projection View 개념과 한계에서는 "한 테이블에서 필요한 칸만 골라 보여주는" 더 단순한 구조의 뷰를 배웁니다.
