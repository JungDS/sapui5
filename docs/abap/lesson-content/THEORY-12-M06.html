학습 목표

지금까지 배운 Classic View들이 왜 현대의 CDS View Entity로 옮겨가는지(현대화) 큰 그림으로 정리합니다. 다음 Chapter로 넘어가기 전 "고전 → 현대"의 다리를 놓는 것이 목표입니다.

1. 지난 시간 연결: View가 너무 여러 종류였다 🤯

이번 Chapter에서 우리는 Database View(합치기), Projection View(솎기), Help View(F4 목록), Maintenance View(편집)를 배웠습니다. 각각 역할이 다르고, 만드는 화면도 따로였죠.

초보자 입장에서는 "왜 이렇게 종류가 많지?"라는 생각이 듭니다. 사실 SAP도 같은 고민을 했고, 그 답으로 나온 것이 하나의 강력한 모델로 통합한 CDS View Entity입니다.

2. Classic View의 한계 🧱

  • 흩어진 종류: 용도마다 다른 View를 만들어야 합니다.
  • 제한된 표현력: 복잡한 계산·조건·의미 부여가 어렵습니다.
  • GUI 종속: 주로 SAP GUI(SE11) 기반이라, 최신 클라우드·Fiori 흐름과는 결이 다릅니다.
💡

비유: 따로 노는 앱 여러 개 vs 올인원 앱

지도 앱, 길찾기 앱, 맛집 앱을 따로 깔던 시절에서, 하나의 앱이 다 해주는 시대로 바뀐 것과 비슷해요. CDS는 합치기·계산·의미·권한·도움말을 한 곳에서 표현합니다.

3. CDS View Entity가 가져온 변화 ✍️

  • ✅ 코드로 정의: 화면 클릭이 아니라 텍스트(소스 코드)로 View를 정의해, 버전 관리·이관이 쉽습니다.
  • ✅ 풍부한 표현: JOIN·계산·CASE·집계는 물론, Association(관계)과 Annotation(의미 부여)까지 한 곳에서.
  • ✅ 현대 스택 연결: OData·Fiori·RAP로 자연스럽게 이어집니다(THEORY-20·21).
  • ✅ 코드 푸시다운: 계산을 DB(HANA)에서 처리해 성능에 유리합니다.
한 줄 요약: Classic View가 "용도별 도구 모음"이라면, CDS View Entity는 "현대적 통합 데이터 모델 언어"입니다.

4. 그래도 Classic을 배우는 이유 🔍

  • ✅ 유지보수 현장: 운영 중인 수많은 기존 시스템은 여전히 Classic View로 가득합니다. 읽고 고칠 줄 알아야 합니다.
  • ✅ 개념의 뿌리: JOIN·필드 제한·F4·유지보수 같은 개념은 CDS에서도 그대로 쓰입니다. 이름과 도구만 바뀝니다.

5. 실무에서 조심할 점 🚨

⚠️

"무조건 CDS"도, "무조건 Classic"도 아닙니다

신규 개발은 CDS가 기본이지만, 기존 Classic 자산을 무리하게 한꺼번에 갈아엎으면 위험합니다. 시스템 버전(ECC인지 S/4HANA인지), 팀 표준, 영향 범위를 보고 판단합니다. 지금 단계에서는 "둘의 관계와 방향"을 이해하는 것으로 충분합니다.

6. 한눈에 정리 🏁

📝

THEORY-12 마무리 핵심

  • Classic View는 Database(합치기)·Projection(솎기)·Help(F4)·Maintenance(편집)로 용도가 나뉩니다.
  • TMG/SM30으로 유지보수 화면을 자동 생성·관리합니다.
  • 현대 SAP는 이 역할들을 CDS View Entity 하나로 통합·확장합니다.
  • 개념(JOIN·필드 제한·F4·유지보수)은 그대로 이어지므로, Classic 학습은 헛되지 않습니다.

데이터 모델과 View를 충분히 다졌습니다. 다음 Chapter ABAP Report Event와 Selection Screen 심화에서는, 프로그램이 실행될 때 거치는 이벤트 흐름을 배우며 본격적인 리포트 프로그래밍으로 들어갑니다.
