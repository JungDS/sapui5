학습 목표

이번 Lesson에서는 SAP 개발의 첫 입구인 SAP Dictionary가 왜 필요한지, SE11과 ADT에서 무엇을 하는지, 그리고 Repository Object가 어떤 흐름으로 저장·검사·활성화되는지 초심자 기준으로 잡아봅니다.

1. 지난 시간 연결: ABAP 학습은 왜 데이터 설계에서 시작할까? 🧭

ABAP을 처음 배우면 바로 코드를 치고 싶어집니다. 그런데 SAP에서는 코드보다 먼저 "이 시스템에서 데이터가 어떤 모양으로 존재하는가"를 이해해야 합니다. 회사 시스템의 프로그램은 혼자 놀지 않습니다. 구매, 판매, 회계, 생산 화면이 같은 고객 번호, 같은 통화 코드, 같은 전표 번호를 함께 봅니다.

그래서 SAP 개발의 첫 관문은 데이터 정의를 중앙에서 맞추는 일입니다. 이 중앙 창고가 바로 SAP Dictionary, 줄여서 DDIC입니다. 오늘은 세부 부품을 만들기 전에 "왜 DDIC라는 창고를 거쳐야 하는지"를 먼저 이해합니다.

한 줄로 말하면, DDIC는 SAP 시스템 전체가 같은 데이터 규격을 믿고 쓰게 해주는 출발점입니다.

2. 왜 데이터베이스에 바로 테이블을 만들지 않을까? 🤔

일반적인 웹 개발에서는 데이터베이스에 직접 접속해서 DDL 문장, 예를 들어 CREATE TABLE을 실행해 테이블을 만들 수 있습니다. 하지만 SAP에서는 보통 이런 방식으로 업무 테이블을 직접 만들지 않습니다.

SAP는 데이터베이스 위에 ABAP 애플리케이션 서버와 여러 개발 도구가 올라간 구조입니다. 개발자가 DDIC에서 테이블, 구조, 데이터 타입을 정의하고 활성화하면, SAP가 그 정의를 실제 데이터베이스에 맞게 반영합니다. 개발자는 특정 데이터베이스 문법보다 SAP 시스템 안에서 일관되게 쓰이는 데이터 정의에 집중합니다.

  • 중앙 관리: 여러 프로그램이 같은 필드 타입과 라벨을 재사용합니다.
  • 일관성: 테이블, 화면, 리포트, ALV가 같은 의미의 필드를 같은 방식으로 해석합니다.
  • 검증: 활성화 시점에 타입, 참조, 의존 관계 오류를 먼저 잡을 수 있습니다.
  • 운영 안정성: 변경이 실제 DB에 어떤 영향을 주는지 SAP 도구 흐름 안에서 관리합니다.
💡

DDIC는 단순한 설계 화면이 아닙니다

DDIC는 데이터 타입을 적어두는 메모장이 아니라, ABAP 런타임·화면·DB 테이블·입력 도움말이 함께 참고하는 단일 진실 공급원에 가깝습니다. 그래서 첫 Lesson에서 이 감각을 잡아두면 뒤의 Domain, Data Element, Table, Search Help가 훨씬 덜 낯설어집니다.

3. Repository Object는 SAP 안에 저장되는 개발 부품이다 📦

SAP 개발자가 만드는 것은 단순 파일이 아니라 Repository Object입니다. Repository Object는 SAP 시스템 저장소에 등록되는 개발 부품입니다. 프로그램, 클래스, 테이블, 구조, 데이터 엘리먼트, 도메인처럼 이름을 가진 개발 산출물이 여기에 들어갑니다.

처음에는 "부품"이라고 생각하면 쉽습니다. 자동차 공장에 엔진, 바퀴, 나사, 배선 부품이 따로 있고 조립 순서가 있듯이, SAP에도 데이터 타입, 테이블, 프로그램, 클래스가 따로 있고 서로 참조합니다. 한 부품이 잘못되면 그 부품을 가져다 쓰는 다른 부품에도 영향이 갑니다.

🧩

오늘 알아둘 대표 부품

  • Domain: 데이터의 기술적 재질, 예를 들어 문자 3자리 같은 규격입니다.
  • Data Element: Domain 위에 업무 의미와 화면 라벨을 붙인 부품입니다.
  • Structure: 여러 필드를 한 줄 모양으로 묶은 타입입니다.
  • Database Table: 실제 데이터를 영구 저장하는 테이블 정의입니다.
  • Program/Class: 데이터를 읽고 처리하는 실행 로직입니다.

4. SE11과 ADT: 문은 달라도 보는 창고는 같다 🛠️

DDIC 객체를 만들고 확인하는 대표 입구는 두 가지입니다. 전통적인 SAP GUI에서는 SE11을 많이 사용했고, 최신 개발 환경에서는 Eclipse 기반 ADT를 사용합니다.

  • SE11: SAP GUI에서 DDIC 객체를 조회·생성·변경하는 전통적인 화면입니다.
  • ADT: Eclipse 기반의 현대 ABAP 개발 환경입니다. ABAP Cloud, CDS, RAP 학습으로 갈수록 중요해집니다.
  • 공통점: 둘 다 SAP 시스템의 Repository Object를 다룹니다. 화면 모양은 달라도 "객체를 만들고 활성화한다"는 흐름은 같습니다.

실무에서는 회사 시스템 버전과 개발 정책에 따라 둘 다 보게 됩니다. 기존 시스템을 읽을 때는 SE11 화면을 만날 수 있고, 신규 개발이나 ABAP Cloud 흐름에서는 ADT가 중심이 됩니다. 그래서 지금은 도구 이름을 외우기보다, 도구가 DDIC 객체를 다루는 입구라는 관계를 잡아두면 충분합니다.

5. 저장과 활성화는 다르다 🔍

SAP에서 개발 부품을 만들 때 가장 자주 헷갈리는 단어가 저장과 활성화입니다. 저장은 "내가 적은 정의를 보관했다"에 가깝고, 활성화는 "이제 시스템의 다른 객체가 믿고 써도 된다"는 상태로 만드는 검사 과정입니다.

  • ✅ 정상 흐름: 객체 생성 → 필수 정보 입력 → 저장 → 문법/참조 검사 → 활성화 성공 → 다른 프로그램이나 객체에서 사용 가능
  • ❌ 오류 흐름: 참조한 Domain이 없거나, 필수 필드가 비어 있거나, 의존 객체가 깨져 있으면 활성화가 실패합니다.
  • 🧪 확인 포인트: "저장됐으니 끝"이 아니라, 활성화 상태와 오류 메시지를 확인해야 합니다.
초심자 체크: 활성화되지 않은 객체는 이름이 보여도 실제 개발 흐름에서는 아직 믿고 쓰기 어렵습니다. 객체를 만들었다면 마지막에 활성화 상태를 꼭 확인하세요.

6. 미니 실습: DDIC 객체 흐름을 말로 따라가기 ✍️

아직 실제 시스템이 없어도 괜찮습니다. 오늘은 손으로 코드를 치는 대신, DDIC 개발 흐름을 머릿속으로 따라가며 기록하는 실습을 해봅니다. 시스템이 있다면 SE11 또는 ADT에서 같은 흐름을 직접 찾아봐도 좋습니다.

🧪

실습 과제

  1. 새 업무 필드가 필요하다고 가정합니다. 예: 항공사 코드.
  2. 이 필드를 만들 때 바로 테이블부터 만들지 않고, 어떤 DDIC 부품이 먼저 필요할지 적어봅니다.
  3. 각 부품이 저장만 된 상태인지, 활성화까지 된 상태인지 구분해봅니다.
  4. 활성화가 실패할 수 있는 이유를 하나 적어봅니다. 예: 참조한 Domain 이름이 틀림.

완료 조건: "Domain → Data Element → Table Field"처럼 최소 3단계 흐름을 말로 설명하고, 활성화 실패 사례 1개를 적을 수 있으면 성공입니다.

7. 실무에서 주의할 점 🚨

⚠️

표준 객체와 고객사 관행을 구분하세요

SAP에는 이미 통화, 단위, 날짜, 회사 코드처럼 검증된 표준 객체가 많습니다. 필요한 객체를 바로 새로 만들기 전에 표준 객체가 있는지 먼저 확인하세요. 다만 어떤 회사에서는 자체 네이밍과 확장 규칙을 강하게 둘 수 있으니, 표준 SAP 개념과 고객사 로컬 관행을 섞어 외우지 않는 것이 중요합니다.

또 하나 중요한 점은 운영 데이터입니다. 이미 데이터가 많이 쌓인 테이블의 구조를 바꾸면 실제 데이터베이스 조정이 필요할 수 있고, 잘못하면 데이터 손상이나 긴급 장애로 이어질 수 있습니다. 지금은 개념 단계지만, "데이터 구조 변경은 조심스럽게"라는 감각을 초반부터 가져가면 좋습니다.

9. 확인 퀴즈와 정답/해설 ✅

📝

짧게 점검해보기

  1. 문제 1. SAP에서 업무 테이블을 만들 때 DDIC를 거치는 가장 큰 이유는 무엇일까요?
  2. 문제 2. 저장과 활성화 중, 다른 객체가 안정적으로 사용할 수 있는 상태로 만드는 단계는 무엇일까요?
  3. 문제 3. SE11과 ADT의 관계를 가장 잘 설명하는 문장은 무엇일까요?
정답/해설 보기
  1. 정답 1: 데이터 정의를 중앙에서 일관되게 관리하기 위해서입니다. DDIC는 타입, 의미, 참조 관계를 여러 프로그램과 화면이 함께 믿고 쓰게 해줍니다.
  2. 정답 2: 활성화입니다. 저장은 보관에 가깝고, 활성화는 시스템 검사를 통과해 사용할 수 있는 상태로 만드는 과정입니다.
  3. 정답 3: 둘은 서로 다른 개발 도구 입구입니다. SE11은 전통적인 SAP GUI 입구, ADT는 Eclipse 기반 현대 개발 입구이며, 둘 다 SAP Repository Object를 다룹니다.

10. 한눈에 정리 🏁

📌

오늘의 핵심만 딱 잡기

  • DDIC는 SAP 데이터 정의를 중앙에서 관리하는 핵심 창고입니다.
  • Repository Object는 SAP 시스템 저장소에 등록되는 개발 부품입니다.
  • SE11과 ADT는 DDIC와 Repository Object를 다루는 서로 다른 개발 도구 입구입니다.
  • 저장과 활성화는 다릅니다. 사용할 수 있는 상태가 되려면 활성화가 중요합니다.
  • 표준 객체를 먼저 찾고, 운영 데이터가 있는 구조 변경은 신중하게 다뤄야 합니다.

이제 SAP 개발의 데이터 창고가 왜 필요한지 알게 됐습니다. 다음 Lesson Domain 기본 설계에서는 이 창고의 가장 작은 부품인 Domain을 만들고, 데이터의 기술적 재질을 어떻게 정하는지 확인합니다.
