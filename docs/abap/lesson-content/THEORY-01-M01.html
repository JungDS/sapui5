학습 목표

DDIC, SE11 / ADT, Repository Object의 목적과 특징을 살펴보고, ABAP 프로그램이 데이터를 어떻게 다루기 시작하는지 가볍게 훑어봅니다.

1. 왜 SAP는 데이터베이스를 직접 다루지 않을까? 🤔

일반적인 웹이나 앱 개발에서는 오라클(Oracle)이나 MySQL 같은 데이터베이스에 직접 접속해서 DDL 쿼리(CREATE TABLE...)를 날려 테이블을 만듭니다. 하지만 SAP에서는 이런 방식을 쓰지 않습니다. 대신 SAP Dictionary (DDIC)라는 중간 관리 도구를 사용합니다.

DDIC는 시스템 내의 모든 데이터 형태를 중앙에서 똑같이 관리하는 "단일 진실 공급원(SSOT)" 역할을 합니다.

개발자가 DDIC 화면에서 테이블의 모양을 디자인하고 활성화(Activate) 버튼을 누르면, SAP 시스템이 알아서 실제 데이터베이스(SAP HANA 등)의 문법에 맞게 진짜 테이블을 만들어 줍니다. 개발자는 복잡한 데이터베이스 언어를 알 필요가 없는 것이죠!

2. 부품 창고 (Repository Object) 📦

SAP 시스템은 엄청나게 거대한 공장과 같습니다. 이 공장 안에는 수십만 개의 부품(Repository Object)들이 쌓여있습니다. 우리가 만들 테이블, 데이터 엘리먼트, 프로그램 소스 코드 등이 모두 이 부품에 속합니다.

💡

어디서 부품을 만들까요? (SE11 vs ADT)

이런 부품들을 새로 만들거나 열어볼 때, 예전에는 SAP 화면에서 트랜잭션 SE11 이라는 명령어를 치고 들어갔습니다. 하지만 요즘은 화면이 훨씬 세련되고 편리한 이클립스 기반의 ADT 환경을 사용하는 추세(ABAP Cloud)입니다. 모양만 다를 뿐, 부품을 만든다는 본질은 똑같습니다.

3. 성공과 실패의 갈림길 (활성화) 🔍

SAP에서 부품(객체)을 만들 때는 단순히 "저장(Save)"한다고 끝나는 게 아닙니다. 반드시 활성화(Activation)라는 특별한 검사 과정을 거쳐야 합니다.

  • ✅ 성공 흐름: 객체 저장 ➔ 문법 검사 통과 ➔ 활성화 성공 ➔ 이제 다른 프로그램에서 가져다 쓸 수 있음!
  • ❌ 실패 흐름: 활성화를 눌렀는데 빨간 에러가 뜸 (예: 내가 가져다 쓴 다른 부품이 고장나 있음). 활성화되지 않은 부품은 시스템에 존재하지 않는 것과 같습니다.
꿀팁: 무언가를 수정했다면, 관련된 다른 부품들까지 함께 '활성화'가 잘 되었는지 확인하는 습관이 중요합니다.

4. 실무에서 주의할 점 🚨

⚠️

"다시 만들지 말고, 있는 걸 쓰세요!"

SAP 공장 안에는 이미 독일 SAP 본사에서 완벽하게 만들어둔 수십만 개의 표준 부품이 있습니다. (예를 들어, 전 세계 통화 코드를 다루는 WAERS 같은 표준 부품들입니다). 무턱대고 새로운 나만의 부품을 만들기 전에, 이미 쓸만한 표준 부품이 존재하는지 검색해보는 것이 실력자의 기본 자세입니다.

또한, 이미 회사의 진짜 데이터가 잔뜩 쌓여있는 운영 서버에서 테이블의 크기를 줄이거나 모양을 함부로 바꾸면, 데이터베이스가 고장 나거나 소중한 데이터가 날아갈 수 있습니다. 구조 변경은 항상 조심해야 합니다.

5. 다음 단계로 🚀

지금까지 DDIC가 왜 필요한지, 부품(Repository Object)이 무엇인지 가볍게 살펴보았습니다. SAP에서 테이블 하나를 만들기 위해서는 한 번에 뚝딱! 만들어지는 게 아니라, 가장 작은 부품부터 하나씩 조립해서 큰 테이블을 완성하는 상향식(Bottom-Up) 구조를 거칩니다.

그럼 다음 Lesson인 'Domain 기본 설계'에서 데이터의 가장 작은 단위 부품을 어떻게 만드는지 직접 확인해 볼까요?
