학습 목표

이번 Lesson에서는 SAP 개발의 첫 기준점인 SAP Dictionary가 왜 필요한지, SE11과 ADT가 같은 Repository Object를 어떻게 다루는지, 그리고 저장·검사·활성화 흐름이 왜 중요한지 잡습니다.

1. 첫 질문: 왜 코드보다 데이터 정의를 먼저 볼까?

ABAP을 처음 배우면 바로 코드를 실행하고 싶어집니다. 하지만 SAP 업무 시스템에서는 여러 화면, 리포트, 인터페이스가 같은 고객 번호·통화·날짜 규격을 믿고 움직여야 합니다. 각 프로그램이 자기 마음대로 타입을 만들면 같은 필드를 서로 다르게 해석하는 문제가 생깁니다.

그래서 SAP는 데이터 정의를 중앙에서 관리합니다. 이 기준점이 DDIC입니다. DDIC는 테이블만 만드는 곳이 아니라, 데이터베이스 객체, 전역 타입, 입력 도움 같은 주변 서비스를 함께 관리합니다.

오늘의 핵심은 “DDIC는 SAP 시스템 전체가 같은 데이터 정의를 한 번 만들고 계속 재사용하게 하는 기준점”이라는 감각입니다.

2. DDIC가 맡는 세 가지 일

DDIC의 역할을 세 묶음으로 나누면 뒤 Lesson에서 나오는 객체가 덜 헷갈립니다. 지금 내가 만드는 것이 저장 공간인지, 값의 타입인지, 화면을 도와주는 서비스인지 먼저 구분하세요.

3. 작은 부품부터 조립한다: Domain → Data Element → Field

예를 들어 “도서 번호” 필드가 필요하다고 해 봅시다. 바로 테이블 열부터 만들기보다, 먼저 값의 기술 규칙과 업무 의미를 나눠 둡니다.

테이블과 코드에서 재사용

Domain은 “재질”, Data Element는 “의미”입니다. 이 둘을 분리해야 같은 기술 규칙을 여러 업무 필드에서 재사용할 수 있습니다.

Domain만 만들면 프로그램에서 바로 쓸 수 있나요?

대부분의 초급 실습에서는 Data Element까지 만든 뒤 테이블 필드나 프로그램 타입으로 참조합니다. Domain은 재질을 정의하는 밑바닥 부품이고, Data Element가 화면 라벨과 업무 의미를 붙여 사용 지점에 더 가까운 이름표 역할을 합니다. 즉 Domain 자체를 DATA ... TYPE의 최종 타입처럼 외우기보다, Data Element 안에서 간접 사용되는 기술 규칙으로 잡는 편이 안전합니다.

4. 어디로 들어가서 고칠까: SE11, ADT, SE38/SE80

Classic SAP GUI에서는 명령창에 SE11을 입력해 DDIC 객체를 만들고 조회합니다. 최신 개발 환경에서는 Eclipse 기반 ADT의 ABAP Project에서 같은 Repository 객체를 다룹니다. 도구의 화면은 달라도 대상은 SAP 서버의 Repository입니다.

메뉴로 따라간다면 SAP Easy Access → Tools → ABAP Workbench → Development → ABAP Dictionary가 SE11 입구입니다. 초기 화면에서는 Database table, Data type, Domain 같은 객체 유형을 고르고, Z 또는 Y로 시작하는 이름을 넣은 뒤 Display/Create/Change로 들어갑니다.

5. 저장과 활성화는 다르다

초심자가 가장 자주 헷갈리는 지점입니다. 저장은 변경 내용을 보관하는 단계이고, 활성화는 문법·참조·일관성 검사를 통과해 시스템이 사용할 수 있는 기준 버전으로 올리는 단계입니다.

Repository Object가 사용 가능해지는 흐름

1. 생성SE11 또는 ADT에서 객체 이름과 패키지를 정한다.
2. 속성 입력타입, 길이, 라벨, 필드 목록을 채운다.
3. 저장Inactive 변경 내용은 보관됐지만 아직 기준 버전은 아니다.
4. 검사문법, 참조 대상, 일관성을 확인한다.
5. 활성화Active 다른 객체와 런타임이 믿고 참조한다.
⚠️

아래 부품부터 활성화하세요

Data Element가 Domain을 참조한다면 Domain이 먼저 활성화되어 있어야 합니다. 기반 객체가 비활성 상태이면 위에 얹은 테이블이나 프로그램도 활성화 중에 참조 오류를 만날 수 있습니다.

이미 쓰이는 DDIC 객체인지 어디서 확인하나요?

SE11의 Where-Used List로 특정 Domain, Data Element, Table이 시스템 안 어디에서 참조되는지 확인할 수 있습니다. 초급 단계에서는 “활성화된 객체는 다른 객체가 믿고 참조한다”는 감각을 잡는 용도로만 기억해 두세요.

7. 실무에서 조심해야 할 점

처음 DDIC 작업에서 자주 생기는 오해

오해
  • 저장했으니 다른 프로그램이 바로 쓸 수 있다.
  • Domain과 Data Element는 거의 같은 것이다.
  • Structure와 Transparent Table은 둘 다 필드 묶음이니 비슷하다.
기준
  • 활성화가 성공해야 다른 객체가 믿고 참조한다.
  • Domain은 기술 규칙, Data Element는 업무 의미와 라벨이다.
  • Structure는 타입 모양, Transparent Table은 실제 저장 공간과 연결된다.

ABAP Cloud에서는 더 제한적으로 봅니다

Classic SAP GUI 입문에서는 SE11로 DDIC 객체를 직접 다루는 감각이 중요합니다. 하지만 ABAP Cloud와 Clean Core 환경에서는 released object, CDS, RAP, ADT 중심 개발 규칙이 더 중요해집니다. 지금은 Classic 객체의 원리를 배우되, 최신 환경에서는 허용된 API와 확장 지점을 확인해야 한다는 점만 기억하세요.

9. 확인 퀴즈

  1. DDIC가 SAP 시스템에서 필요한 가장 큰 이유는 무엇인가요?
  2. Domain과 Data Element를 “재질”과 “의미”라는 말로 구분해보세요.
  3. 저장과 활성화 중, 다른 객체가 믿고 사용할 수 있는 기준 버전을 만드는 단계는 무엇인가요?
  4. SE11과 ADT는 화면이 다르지만 무엇을 공통으로 다루나요?
정답/해설 보기
  1. 데이터 정의를 중앙에서 일관되게 관리하기 위해서입니다. 여러 프로그램과 화면이 같은 타입과 의미를 참조합니다.
  2. Domain은 기술적 재질, Data Element는 업무 의미입니다. 같은 재질을 재사용하면서 라벨과 설명은 다르게 줄 수 있습니다.
  3. 활성화입니다. 저장은 비활성 버전 보관이고, 활성화는 검사 후 사용 가능한 기준 버전을 만드는 과정입니다.
  4. SAP Repository Object입니다. 도구는 달라도 서버의 Repository에 있는 개발 객체를 열고 수정합니다.
