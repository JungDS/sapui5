학습 목표

이번 Lesson에서는 SAP 개발의 첫 입구인 SAP Dictionary가 왜 필요한지, SE11과 ADT가 같은 저장소를 어떻게 다루는지, 그리고 Repository Object가 저장·검사·활성화되는 흐름을 초심자 기준으로 잡습니다.

1. 첫 Lesson의 질문: 왜 코드보다 데이터 정의가 먼저일까?

ABAP을 처음 배우면 바로 Report를 만들고 WRITE를 실행하고 싶어집니다. 하지만 SAP 업무 시스템에서는 코드보다 먼저 “회사 전체가 같은 데이터 규격을 믿고 쓰는가”를 맞춰야 합니다. 판매 화면, 구매 화면, 회계 전표, ALV 리포트가 모두 같은 고객 번호와 통화 코드와 날짜 규격을 봐야 하기 때문입니다.

이 중앙 규격 창고가 DDIC입니다. DDIC는 테이블만 만드는 화면이 아니라 데이터베이스 객체, 타입 정의, 검색 도움말 같은 서비스 정의를 한곳에서 관리합니다. 그래서 뒤 Lesson의 Domain, Data Element, Structure, Transparent Table을 이해하려면 오늘의 전체 흐름이 먼저 잡혀야 합니다.

DDIC는 “SAP 시스템 전체가 같은 데이터 정의를 한 번 만들고 계속 재사용하게 하는 기준점”입니다.

2. DDIC는 세 가지 일을 한다

SAP 공식 설명에서 DDIC의 역할은 크게 세 묶음으로 나뉩니다. 이 세 묶음을 구분하면 “지금 내가 만드는 것이 저장 공간인지, 타입인지, 도움 기능인지”가 덜 헷갈립니다.

3. 개발 부품의 조립 순서: 재질 → 의미 → 저장 공간

DDIC에서 업무 필드를 만들 때는 보통 작은 부품부터 쌓습니다. 예를 들어 “항공사 코드” 필드가 필요하다면 바로 테이블 열부터 만들기보다, 먼저 기술적 재질과 업무 의미를 나눠 생각합니다.

Domain 하나를 여러 Data Element가 재사용할 수 있습니다. 같은 CHAR 3 재질이어도 “출발 공항”과 “도착 공항”처럼 화면 라벨과 의미는 다르게 둘 수 있습니다.

왜 Domain과 Data Element를 굳이 나눌까?

Domain은 타입·길이·값 범위처럼 기술적 속성을 맡고, Data Element는 라벨·F1 도움말처럼 업무 의미를 맡습니다. 재질과 의미를 나눠두면 같은 기술 규격을 여러 업무 필드에서 재사용하면서도 화면 설명은 각각 다르게 줄 수 있습니다.

4. SE11과 ADT: 문은 달라도 Repository는 같다

SE11은 SAP GUI에서 DDIC 객체를 만들고 조회하는 전통적인 입구입니다. ADT는 Eclipse 기반의 최신 ABAP 개발 환경입니다. 화면은 다르지만 둘 다 SAP 시스템의 Repository Object를 다룹니다.

실무에서는 회사 정책과 시스템 버전에 따라 SE11과 ADT를 모두 볼 수 있습니다. 중요한 것은 “어떤 도구든 SAP Repository Object를 만들고 활성화한다”는 공통 원리입니다.

5. 저장과 활성화는 완전히 다르다

초심자가 가장 자주 헷갈리는 지점은 저장과 활성화입니다. 저장은 “변경 내용을 비활성 버전으로 보관했다”에 가깝습니다. 활성화는 “문법과 참조 관계를 검사했고, 이제 다른 객체가 이 정의를 사용해도 된다”는 상태로 올리는 단계입니다.

DDIC 객체가 사용 가능해지는 5단계

1. 객체 생성이름, 패키지, 설명을 정한다.
2. 속성 입력타입, 길이, 라벨, 필드 목록을 채운다.
3. 저장Inactive 변경 내용은 보관됐지만 아직 기준 버전은 아니다.
4. 활성화문법·참조·의존 관계를 검사한다.
5. 런타임 사용Active 프로그램과 화면이 믿고 참조한다.
⚠️

저장 아이콘만 누르고 끝내면 안 됩니다

저장된 비활성 버전은 작업 중인 초안에 가깝습니다. 실제 실행 기준은 마지막으로 성공한 활성 버전입니다. 객체를 만들거나 고쳤다면 활성화 상태와 오류 메시지를 확인하는 습관을 들이세요.

6. 런타임 오브젝트와 구조 변경 리스크

활성화가 중요한 이유는 단순히 버튼 하나를 더 누르기 위해서가 아닙니다. DDIC 정의가 활성화되면 ABAP 런타임과 데이터베이스가 참조할 수 있는 런타임 기준 정보가 만들어집니다. 테이블 정의라면 SAP가 데이터베이스 수준으로 정의를 반영하고, 프로그램 실행 시점에는 현재 DDIC 상태와 런타임 정보가 맞는지도 중요해집니다.

Structure와 Transparent Table의 생명주기 차이

Structure
  • 필드 묶음의 타입 정의입니다.
  • DB에 데이터를 저장할 물리 공간을 만들지 않습니다.
  • Work Area, 파라미터, 화면 구조 같은 “모양”으로 자주 씁니다.
Transparent Table
  • DDIC 테이블 정의입니다.
  • 활성화 시 실제 데이터베이스의 물리 테이블과 연결됩니다.
  • 운영 데이터가 쌓인 뒤 구조 변경은 변환·조정 리스크가 있습니다.

초반에는 “Structure는 모양, Transparent Table은 저장 공간”으로 기억해도 충분합니다.

실습 과제

  1. 새 필드가 필요하다고 가정합니다. 예: 항공사 코드.
  2. 먼저 Domain에 적을 기술 규격을 씁니다. 예: CHAR 3.
  3. 그다음 Data Element에 붙일 업무 의미와 Field Label을 씁니다. 예: 항공사 코드, Airline Code.
  4. 마지막으로 Table Field 이름을 씁니다. 예: ZFLIGHT-CARRID.
  5. 저장만 한 상태와 활성화까지 끝난 상태를 색으로 구분해 표시합니다.

완료 조건: “Domain → Data Element → Table Field → 저장 → 활성화” 흐름을 자신의 말로 설명하고, 활성화 실패 이유 1개를 말할 수 있으면 성공입니다.

활성화 실패 예시 보기
  • Data Element가 참조하는 Domain 이름을 잘못 적었다.
  • Table Field가 아직 활성화되지 않은 Data Element를 참조한다.
  • 운영 데이터가 있는 테이블의 필드 길이를 줄여 기존 데이터와 충돌한다.

8. 실무에서 조심해야 할 점

🚨

표준 객체와 고객사 관행을 섞어 외우지 마세요

SAP에는 통화, 단위, 날짜, 회사 코드처럼 이미 검증된 표준 DDIC 객체가 많습니다. 새로 만들기 전에 표준 객체가 있는지 먼저 확인하고, 고객사 네이밍 규칙이나 확장 규칙은 별도 관행으로 구분해 기록하세요.

  • 운영 테이블 구조 변경: 데이터가 쌓인 테이블의 길이·키·필드 변경은 변환 작업과 장애 리스크가 있습니다.
  • 고정값 오해: Domain의 고정값은 입력 도움과 기본 검증에 도움을 주지만, 모든 입력 경로의 무결성을 자동 보장한다고 생각하면 안 됩니다.
  • Cloud 제약: ABAP Cloud나 Clean Core 환경에서는 사용 가능한 객체와 확장 방식이 제한될 수 있으므로 릴리스 상태와 확장 가이드를 확인해야 합니다.

10. 확인 퀴즈

  1. DDIC가 SAP 시스템에서 필요한 가장 큰 이유는 무엇인가요?
  2. Domain과 Data Element를 나누는 이유를 “재질”과 “의미”라는 말로 설명해보세요.
  3. 저장과 활성화 중, 다른 객체가 믿고 사용할 수 있는 상태로 만드는 단계는 무엇인가요?
  4. Structure와 Transparent Table의 가장 큰 차이는 무엇인가요?
정답/해설 보기
  1. 데이터 정의를 중앙에서 일관되게 관리하기 위해서입니다. 여러 프로그램과 화면이 같은 타입과 의미를 참조합니다.
  2. Domain은 기술적 재질, Data Element는 업무 의미입니다. 같은 재질을 재사용하면서 라벨과 설명은 다르게 둘 수 있습니다.
  3. 활성화입니다. 저장은 비활성 버전 보관이고, 활성화는 검사 후 사용 가능한 기준 버전을 만드는 과정입니다.
  4. Structure는 저장 공간이 없는 타입 모양이고, Transparent Table은 실제 데이터 저장과 연결되는 테이블 정의입니다.
