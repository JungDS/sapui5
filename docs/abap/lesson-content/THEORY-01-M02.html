학습 목표

이번 Lesson에서는 Domain을 “값의 기술 규격”으로 설계합니다. 수업이 끝나면 Data Type, Length, Output Length, Fixed Value의 역할을 나눠 설명하고, SE11에서 작은 Domain을 저장·검사·활성화하는 흐름을 직접 시뮬레이션할 수 있어야 합니다.

1. Domain은 업무 의미가 아니라 값의 재질을 정한다

지난 Lesson에서 DDIC는 SAP 시스템이 공유하는 데이터 정의의 기준점이라고 봤습니다. Domain은 그 기준점 안에서 가장 아래쪽에 놓이는 부품입니다. “주문 상태”라는 업무 의미보다 먼저 “한 글자 코드인가, 숫자인가, 허용값이 고정되어 있는가”를 정합니다.

Domain은 값의 재질과 허용 범위입니다. 필드 라벨, 업무 설명, F1 도움말처럼 사람이 읽는 의미는 다음 Lesson의 Data Element에서 붙입니다.

Domain이 답하는 질문

Type
질문값의 종류는 무엇인가?
예CHAR, NUMC, DATS, DEC
Size
질문몇 자리까지 저장할 수 있는가?
예상태 코드 CHAR 1, 사번 NUMC 8
Range
질문허용값을 작은 목록으로 잠글 수 있는가?
예N, P, C, X

NotebookLM 보강 기준: Domain은 기술 속성, Data Element는 의미 속성으로 분리해 외워야 이후 테이블 필드 설계가 흔들리지 않습니다.

2. Domain 설계는 네 칸으로 줄여 본다

SAP 공식 학습 자료는 Domain이 Dictionary 타입, 길이, 출력 길이, 값 범위 같은 기술 속성을 제공한다고 설명합니다. 초급 단계에서는 아래 네 칸을 순서대로 채우면 충분합니다.

Domain 속성 판단표

속성 결정 질문 초급 판단 기준
Data Type 계산할 값인가, 코드처럼 보존할 값인가? 계산하지 않는 코드는 숫자처럼 보여도 CHAR 또는 NUMC를 먼저 검토합니다.
Length 저장 가능한 최대 길이는? 운영 데이터가 쌓인 뒤 줄이기 어렵기 때문에 업무 코드 체계를 확인하고 정합니다.
Output Length 화면과 리스트에서 어느 폭으로 보여야 하는가? 저장 길이와 같을 때가 많지만, 표시 형식이 다른 타입에서는 분리해서 봅니다.
Fixed Value 허용값이 작고 거의 변하지 않는가? 사용 여부, 상태 코드처럼 작은 목록이면 Domain에 직접 등록할 수 있습니다.
001은 항상 숫자 타입일까?

아닙니다. 앞의 0이 의미 있는 사번·고객 코드·우편번호는 계산 대상 숫자가 아니라 표현을 보존해야 하는 코드일 수 있습니다. 이때 INT4로 만들면 001이라는 표현 자체가 사라질 수 있습니다.

3. SE11 진입 경로와 최소 생성 흐름

Classic SAP GUI에서는 상단 명령창에 SE11 또는 /nSE11을 입력해 ABAP Dictionary 화면으로 들어갑니다. Domain 라디오 버튼을 선택하고 이름을 입력한 뒤 Create를 누르면 Domain 유지보수 화면으로 이동합니다.

Domain 생성 흐름

1. 진입SAP GUI 명령창 → /nSE11 → Domain 선택
2. 이름고객 객체는 보통 Z 또는 Y 네임스페이스로 시작
3. DefinitionData Type, Length, Output Length 입력
4. Value Range작은 허용값은 Fixed Value로 등록
5. Activate저장 후 검사와 활성화를 통과해야 다른 객체가 참조 가능

5. Fixed Value와 Value Table을 섞지 않는다

Fixed Value는 Domain 안에 작은 허용값 목록을 직접 넣는 방식입니다. SAP Help의 Fixed Values 설명처럼, 입력 값이 Domain의 고정값에 맞지 않으면 Dictionary 기반 검증 지점에서 오류가 날 수 있고 F4 입력 도움에도 활용됩니다.

반대로 Value Table은 “이 Domain을 쓰는 필드가 나중에 어떤 check table을 제안받을 수 있는가”에 가까운 힌트입니다. 실제 테이블 필드 입력 검증은 Foreign Key를 명시적으로 정의해야 합니다. 값을 찾아주는 별도 서비스인 Search Help와도 책임이 다릅니다.

값 목록 설계 판단

Domain에 둔다
  • 값이 작고 안정적입니다.
  • Y/N, 주문 상태처럼 몇 개의 코드로 충분합니다.
  • Domain의 Fixed Value로 입력 도움과 기본 검증을 기대할 수 있습니다.
관계 객체로 분리한다
  • 값이 많거나 운영 중 자주 늘어납니다.
  • 고객, 자재, 국가처럼 마스터 테이블 관리가 필요합니다.
  • Check Table, Foreign Key, Search Help를 후속 설계에서 검토합니다.

“Value Table 입력 = 자동 입력 검증 완성”으로 외우면 안 됩니다. 실제 검증 관계는 테이블 필드에서 다시 정의합니다.

6. 운영 변경 리스크: 줄이는 변경을 가볍게 보지 않는다

Domain은 여러 Data Element와 테이블 필드가 재사용할 수 있는 하위 규격입니다. 그래서 처음 만들 때는 작아 보이는 변경도 나중에는 영향 범위가 커집니다.

변경 전 점검표

변경 위험 초급 점검
Length 축소 기존 데이터가 새 길이에 맞지 않을 수 있습니다. 데이터 분포와 참조 필드를 먼저 확인합니다.
Data Type 변경 입력 형식, 변환, 프로그램 타입 참조가 달라질 수 있습니다. 계산 대상인지 코드 대상인지 다시 검토합니다.
Fixed Value 삭제 기존 저장값이 더 이상 허용 목록에 없을 수 있습니다. 삭제 전 실제 사용 값과 화면 입력 경로를 확인합니다.
Domain을 새로 만들지, 기존 것을 재사용할지 판단하는 기준

기술 속성과 값 범위가 같으면 기존 Domain 재사용을 먼저 검토합니다. 업무 의미만 다르다면 Domain을 새로 늘리기보다 Data Element에서 라벨과 설명을 분리하는 편이 더 자연스럽습니다.

8. 확인 퀴즈

  1. Domain이 주로 정하는 것은 업무 라벨인가요, 기술 속성인가요?
  2. 앞의 0이 중요한 코드 값을 무조건 정수 타입으로 만들면 어떤 문제가 생길 수 있나요?
  3. Fixed Value에 적합한 값 목록의 특징은 무엇인가요?
  4. Value Table만 입력하면 Foreign Key 검증이 자동 완성되나요?
  5. Domain과 Data Element를 “재질”과 “의미”로 나눠 설명해보세요.
정답/해설 보기
  1. 기술 속성입니다. 타입, 길이, 출력 길이, 값 범위가 Domain의 중심입니다.
  2. 표현이 사라질 수 있습니다. 001 같은 앞자리 0이 중요하면 코드 타입으로 봐야 합니다.
  3. 작고 거의 변하지 않는 목록입니다. 상태, 사용 여부, 승인 여부처럼 안정적인 코드가 적합합니다.
  4. 아니요. Value Table은 후보 제안 성격이고 실제 관계와 검증은 Foreign Key 등 후속 설정이 필요합니다.
  5. Domain은 재질, Data Element는 의미입니다. 같은 Domain 위에 서로 다른 라벨과 설명을 얹을 수 있습니다.

9. 한눈에 정리

Domain값의 기술 규격과 작은 허용 범위를 정하는 DDIC 하위 부품입니다.
Data Type과 Length계산할 값인지 보존할 코드인지 먼저 보고 저장 길이를 정합니다.
Fixed Value작고 안정적인 코드 목록에 적합하며 입력 도움과 기본 검증에 쓰입니다.
Value Table자동 검증이 아니라 Foreign Key 후보를 제안하는 성격으로 이해합니다.
