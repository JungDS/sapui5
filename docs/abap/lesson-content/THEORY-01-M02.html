학습 목표

데이터의 가장 기본적이고 작은 부품인 Domain을 직접 만들어 봅니다. 도메인이 무엇인지, 데이터 타입과 길이(Length), 그리고 입력값을 엄격하게 제한하는 고정값(Fixed Value)의 역할을 확실히 이해해 봅니다.

1. 지난 시간 요약 & 왜 이게 필요한가? 🤔

이전 Lesson에서 SAP는 한 번에 커다란 테이블을 뚝딱! 만드는 게 아니라, 가장 작은 부품부터 조립해서 완성하는 상향식(Bottom-Up) 구조를 가진다고 배웠죠?

그렇다면 가장 처음으로 만들어야 할 기초 부품은 무엇일까요? 바로 데이터의 가장 밑바닥, 즉 "이 데이터는 어떤 재질로 만들어졌는가?"를 정의하는 과정이 필요합니다. 이것을 SAP에서는 Domain(도메인)이라고 부릅니다.

2. Domain, 넌 도대체 정체가 뭐니? 🧱

Domain(도메인)은 한마디로 "데이터의 재질 명세서"입니다. 예를 들어 옷을 만들 때 "이 옷감은 면 100%고, 길이는 3미터야"라고 정해두는 것과 똑같아요. 이 옷감으로 치마를 만들지 바지를 만들지(즉, 의미)는 Domain의 관심사가 아닙니다. 오직 기술적인 형태만 책임집니다.

Domain을 만들 때 설정해야 하는 핵심 세 가지는 다음과 같습니다.

  • 데이터 타입(Data Type): 들어갈 값이 문자인지(CHAR), 숫자인지(NUMC, INT4), 날짜인지(DATS) 등을 정합니다.
  • 길이(Length): 그 값을 몇 자리까지 담을 수 있는지 정합니다. (예: 항공사 코드 CHAR 3)
  • 소수 자릿수(Decimals): 만약 금액이나 수량처럼 숫자를 다룬다면, 소수점 이하 몇 번째 자리까지 쓸 것인지 설정합니다.
기억하세요: Domain은 "이 값은 3자리 문자다"까지만 말합니다. 이게 '항공사 코드'인지 '국가 코드'인지 같은 이름표(의미)는 다음 Lesson의 Data Element가 책임진답니다!

3. 어떻게 만들까? 항공사 코드 Domain 예제 ✍️

이클립스 기반의 세련된 ADT(또는 전통적인 SE11 화면)에서 ZCARRID라는 이름의 Domain을 만든다고 상상해 봅시다. 설정은 정말 간단해요!

💡

설정값은 단 세 줄이면 충분합니다

✔️ Data Type: CHAR (문자)
✔️ Length: 3 (3자리)
✔️ Output Length: 3 (화면에 보여줄 길이도 3자리)

이것만 딱 채우고 활성화(Activate) 버튼을 누르면 끝입니다! 이제 SAP 시스템 어디서든 "3자리짜리 항공사 코드 재질"을 원할 때 이 Domain을 계속 가져다 쓸 수 있습니다.

만약 똑같은 재질의 코드를 100군데에서 쓰더라도 Domain은 단 하나만 만들면 됩니다. 나중에 "우리 항공사 코드를 3자리에서 4자리로 늘리자!"라는 지시가 내려오면, 이 Domain 딱 하나만 수정하세요. 그러면 이 Domain을 참조하는 100군데가 마법처럼 한 번에 바뀝니다. 이게 바로 DDIC가 자랑하는 단일 진실 공급원(SSOT)의 엄청난 파워입니다.

4. 고정값(Fixed Value): 엄격한 문지기 역할 🚦

Domain에는 아주 유용하고 강력한 기능이 하나 더 숨어있습니다. 바로 고정값(Fixed Value)이라는 기능입니다. 이것은 해당 칸에 들어올 수 있는 값의 목록을 미리 엄격하게 못 박아 두는 역할을 합니다. 마치 자판기에서 지정된 음료수 버튼만 누를 수 있는 것과 같아요.

  • ✅ 정상 흐름: '성별' Domain에 M(남), F(여)만 고정값으로 등록합니다. 그러면 프로그램이나 입력 화면에서 무조건 이 두 가지만 허용합니다. 사용자가 키보드 F4(입력 도움말)를 누르면 목록에도 예쁘게 M과 F만 표시됩니다.
  • ❌ 오류 흐름: 사용자가 실수로 장난을 쳐서 X나 Z를 입력합니다. 그러면 시스템이 "허용되지 않은 값입니다!"라며 입력을 단호하게 거부합니다. 개발자가 별도로 검사하는 코드를 짤 필요가 없죠!
팁: 고정값은 성별(M/F)이나 승인 여부(Y/N)처럼 "값의 종류가 적고 거의 변하지 않는 것"에 쓰기 딱 좋습니다. 반대로 국가 코드나 통화 코드처럼 값이 수백 개고 종종 추가되는 것들은 고정값 대신 다른 방식(Value Table)을 쓰는 게 좋은데, 이건 나중에 배우게 됩니다.

5. 실무에서 조심해야 할 점 🚨

초보 개발자가 흔히 하는 실수들을 미리 짚어드릴게요.

⚠️

다짜고짜 새로 만들지 말고 표준을 찾아보세요!

금액(WERTV8), 수량(MENG13), 통화 코드(WAERS) 같은 데이터는 전 세계 모든 회사가 씁니다. 당연히 SAP가 이미 완벽하게 만들어 둔 표준 Domain이 산더미처럼 준비되어 있습니다. 냅다 나만의 ZWAERS를 새로 만들기 전에, 이미 있는 걸 재사용할 수 있는지 검색해보는 것이 실력자의 기본기입니다.

또한, 만약 회사 시스템이 운영 중이어서 이미 그 Domain에 수백만 건의 진짜 데이터가 쌓여 있다면? 이때 Domain의 길이를 함부로 줄이거나 데이터 타입을 다른 것으로 바꾸면, 기존 데이터가 잘려나가거나 변환 오류가 발생해서 시스템이 멈출 수 있습니다. 늘리는 건 그나마 안전하지만, 줄이는 건 폭탄 스위치를 누르는 것과 같으니 항상 두 번, 세 번 조심하세요!

6. 한눈에 정리 🏁

오늘 배운 가장 핵심적인 내용을 딱 정리해 드립니다.

📝

오늘의 요약

  • Domain(도메인)은 데이터의 가장 작은 단위 부품으로 "재질(데이터 타입과 길이)"만 책임집니다.
  • 똑같은 재질이라면 하나의 Domain을 만들어 여러 곳에서 재사용(SSOT)하는 것이 SAP의 철학입니다.
  • 고정값(Fixed Value)을 설정하면, 개발자가 따로 코딩하지 않아도 허용된 값 이외의 입력을 시스템이 알아서 튕겨냅니다.
  • 이미 데이터가 쌓여있는 Domain의 길이를 줄이거나 타입을 바꾸는 건 매우 위험하니 주의해야 합니다.

Domain으로 데이터의 "재질"은 완벽하게 정의했습니다. 하지만 아직 끝이 아니죠! 이 재질만으로는 화면에 표시될 이름표가 무엇인지 알 수 없습니다. 다음 Lesson 'Data Element 기본 설계'에서는 이 밋밋한 원단(Domain) 위에 예쁜 의미와 이름표를 달아 진짜 부품으로 완성하는 마법을 부려보겠습니다. 기대해 주세요!
