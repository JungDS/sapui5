학습 목표

이번 Lesson에서는 Domain이 무엇을 책임지는지 명확히 나눕니다. Data Type, Length, Output Length, Fixed Value, Value Table의 역할을 보고, 다음 Lesson의 Data Element와 어디서 갈라지는지 설명할 수 있게 됩니다.

1. Domain은 DDIC의 가장 작은 기술 규격이다

지난 Lesson에서 DDIC는 SAP 데이터 정의를 중앙에서 관리하는 기준점이라고 배웠습니다. Domain은 그 기준점 안에서 가장 아래쪽에 놓이는 기술 규격입니다. SAP Learning의 표현처럼 Domain의 주된 목적은 테이블 필드의 기술 속성을 정하는 것입니다.

예를 들어 “항공사 코드”라는 필드가 필요하다고 해서 곧바로 화면 라벨부터 쓰면 설계가 흐려집니다. 먼저 “이 값은 문자 몇 자리인가?”, “허용값 목록이 있는가?”, “화면에는 어느 폭으로 보일까?”를 결정해야 합니다. 이 질문의 답이 Domain입니다.

Domain은 업무 의미가 아니라 값의 재질과 허용 범위를 정합니다. 의미와 라벨은 Data Element에서 붙입니다.

2. Domain 설계의 네 칸

초급 단계에서는 Domain 화면을 아래 네 칸으로 줄여서 보면 충분합니다. 모든 항목을 외우기보다, 각 항목이 어떤 질문에 답하는지 먼저 잡으세요.

Domain 속성 판단표

Data Type
질문값의 종류는?
예CHAR, NUMC, DATS, CURR
판단계산할 숫자인지, 코드처럼 보이는 문자인지 구분한다.
Length
질문저장 가능한 최대 자릿수는?
예항공사 코드 CHAR 3, 사번 NUMC 8
판단실제 업무 코드 길이를 확인한 뒤 정한다.
Output Length
질문화면·리스트 표시 폭은?
예날짜처럼 내부 길이와 표시 폭이 달라질 수 있다.
판단저장 길이와 같은 값이라고 단정하지 않는다.
Fixed Value
질문허용값이 작고 고정적인가?
예Y/N, A/B/C
판단값이 많거나 자주 늘면 별도 테이블 쪽을 검토한다.

Domain 설계는 “타입 → 길이 → 표시 폭 → 허용값” 순서로 검토하면 초반 실수가 줄어듭니다.

3. 작은 예제로 만들기: 예약 등급 Domain

아래 요구사항을 Domain 관점으로 바꿔봅시다. “예약 등급은 비즈니스석, 이코노미석, 일등석 세 종류만 허용한다. 화면에는 한 글자 코드로 충분하다.” 이 요구사항은 업무 설명처럼 보이지만, Domain에 들어갈 내용은 기술 규격과 허용값입니다.

요구사항을 Domain 속성으로 접기

1. 이름ZBOOK_CLASS처럼 고객 네임스페이스 규칙에 맞춘다.
2. 타입코드 값이므로 CHAR를 우선 검토한다.
3. 길이한 글자 코드면 Length = 1로 둔다.
4. 고정값B Business, E Economy, F First를 등록한다.
5. 활성화저장 후 활성화해야 다른 DDIC 객체가 사용할 수 있다.
✍️

SE11/ADT에서 보는 최소 입력값

  • SE11: Domain 선택 → 이름 입력 → Data Type, Length, Output Length, Value Range 입력 → 활성화.
  • ADT: New ABAP Repository Object에서 Domain 생성 → 같은 기술 속성 입력 → 활성화.
  • 도구는 달라도 Repository에 저장되는 Domain의 책임은 같습니다.

4. Length와 Output Length는 같은 말이 아니다

처음에는 CHAR 3의 저장 길이와 표시 폭이 둘 다 3이라서 둘을 같은 설정처럼 느끼기 쉽습니다. 하지만 역할은 다릅니다. Length는 값이 실제로 담기는 최대 크기이고, Output Length는 사용자 화면이나 리스트에서 차지할 표시 폭입니다.

저장 크기와 표시 폭 비교

Length
  • 데이터 저장 가능 크기를 정합니다.
  • CHAR 3이면 최대 세 자리까지 담을 수 있습니다.
  • 운영 데이터가 쌓인 뒤 줄이면 데이터 변환 리스크가 큽니다.
Output Length
  • 화면과 리스트에서 보여줄 폭을 정합니다.
  • 날짜나 통화처럼 표시 형식 때문에 저장 길이와 다를 수 있습니다.
  • 무리하게 줄이면 값이 잘려 보이거나 사용성이 나빠집니다.

초급 실습에서는 같은 숫자를 자주 쓰더라도, 저장 크기와 표시 폭이라는 역할 차이는 반드시 분리해 기억합니다.

001은 숫자 타입으로 만들면 될까?

항상 그렇지 않습니다. 앞의 0이 업무적으로 의미 있는 코드라면 계산 대상 숫자가 아니라 “숫자처럼 보이는 코드”입니다. 이런 경우 NUMC 또는 CHAR를 검토합니다. INT4로 만들면 001이라는 표현 자체를 잃을 수 있습니다.

5. Fixed Value는 작은 목록에만 강하다

Fixed Value는 Domain에 허용값 목록을 직접 등록하는 기능입니다. 값이 작고 거의 변하지 않을 때 좋습니다. 예를 들어 승인 여부 Y/N, 예약 등급 B/E/F처럼 사용자가 선택할 값이 적으면 F4 입력 도움과 입력 검증에 도움이 됩니다.

Fixed Value 후보 판단

요구사항 Domain Fixed Value 적합도 이유
사용 여부 Y/N 좋음 값이 작고 거의 변하지 않습니다.
예약 등급 B/E/F 좋음 한정된 코드 목록입니다.
국가 코드, 고객 번호, 자재 번호 부적합 값이 많고 운영 중 계속 관리됩니다.
⚠️

Fixed Value를 데이터베이스 제약처럼 과장하지 마세요

Fixed Value는 Dynpro 입력 화면과 DDIC 기반 입력 도움에 영향을 주지만, 모든 프로그램 경로의 데이터 무결성을 자동으로 보장하는 물리 DB 제약은 아닙니다. 중요 업무 규칙은 애플리케이션 검증도 함께 고려해야 합니다.

6. Value Table은 자동 검증이 아니라 제안이다

Domain 화면에는 Value Table 항목도 있습니다. 여기서 초심자가 가장 많이 오해합니다. Value Table에 테이블 이름을 적었다고 해서 모든 입력이 자동으로 그 테이블과 대조되지는 않습니다. SAP 문서와 NotebookLM 교차 확인 기준으로, Value Table은 나중에 Foreign Key를 정의할 때 check table 후보를 제안하는 성격에 가깝습니다.

Fixed Value, Value Table, Foreign Key 구분

Domain 안에서 끝나는 것
  • Fixed Value: 작은 허용값 목록을 Domain에 직접 둡니다.
  • DDIC 기반 화면에서 입력 도움과 기본 검증에 사용됩니다.
  • 값 목록이 거의 변하지 않을 때 적합합니다.
관계 정의가 필요한 것
  • Value Table: check table 후보를 알려주는 힌트입니다.
  • Foreign Key: 테이블 필드에서 명시적으로 관계를 정의해야 합니다.
  • 대량·변동 목록은 별도 테이블과 값 도움 설계를 검토합니다.

“Value Table 입력 = 자동 입력 검증”으로 외우면 이후 테이블 관계 설계에서 크게 헷갈립니다.

Search Help와도 같은 말일까?

아닙니다. Search Help는 사용자가 값을 찾도록 돕는 별도 DDIC 서비스입니다. Fixed Value, Value Table, Foreign Key, Search Help는 모두 F4 경험과 관련될 수 있지만 책임과 설정 위치가 다릅니다.

7. Domain과 Data Element의 경계

SAP의 two-level domain concept를 초급자 말로 풀면 “재질과 의미를 나눈다”입니다. Domain은 타입과 길이, 값 범위 같은 기술 속성을 맡습니다. Data Element는 업무 의미, 필드 라벨, F1 도움말처럼 사용자와 개발자가 이해할 설명을 맡습니다.

같은 Domain, 다른 Data Element

DomainCHAR 3, 항공사 코드와 같은 재질
Data Element A출발 항공사, 화면 라벨과 설명
Data Element B도착 항공사, 다른 화면 라벨과 설명
Table Field각 테이블 필드가 필요한 의미의 Data Element를 참조
💡

판단 문장

“이 값이 몇 자리이고 어떤 타입인가?”는 Domain 질문입니다. “이 필드가 업무적으로 무엇이고 화면에 어떤 라벨로 보일까?”는 Data Element 질문입니다.

8. 초심자 실수 체크리스트

실수 1: 새 필드마다 새 Domain을 만든다

기술 속성과 값 범위가 같은데도 Domain을 계속 새로 만들면 중앙 재사용 장점이 사라집니다. 먼저 SAP 표준 Domain과 기존 커스텀 Domain을 검색하고, 의미만 다르면 Data Element에서 분리할 수 있는지 봅니다.

실수 2: 숫자처럼 보이면 무조건 숫자 타입을 고른다

고객 코드, 사번, 우편번호처럼 앞의 0이 중요하거나 계산하지 않는 값은 숫자 타입이 아닐 수 있습니다. 데이터 타입은 “계산 가능 여부”와 “표현 보존”을 함께 보고 고릅니다.

실수 3: Fixed Value에 운영 마스터 전체를 넣는다

값이 많거나 운영 중 추가·삭제되는 목록은 Domain의 Fixed Value로 관리하기 어렵습니다. 이후 Lesson에서 다룰 테이블 관계, Foreign Key, Search Help로 분리하는 쪽을 검토합니다.

실수 4: Length를 줄이는 변경을 가볍게 본다

이미 데이터가 쌓인 뒤 Domain 길이를 줄이면 기존 값이 새 규격에 맞지 않을 수 있습니다. 운영 반영 전 영향 범위와 변환 작업을 반드시 확인해야 합니다.

11. 확인 퀴즈

  1. Domain이 주로 정하는 것은 업무 라벨인가요, 기술 속성인가요?
  2. 001처럼 앞의 0이 중요한 사번 코드는 무조건 INT4로 잡아도 될까요?
  3. Fixed Value에 적합한 목록의 특징은 무엇인가요?
  4. Value Table에 테이블 이름을 넣으면 자동으로 Foreign Key 검증이 완성되나요?
  5. Domain과 Data Element를 “재질”과 “의미”로 나눠 설명해보세요.
정답/해설 보기
  1. 기술 속성입니다. Data Type, Length, Output Length, 값 범위가 Domain의 핵심입니다.
  2. 아니요. 앞의 0을 보존해야 하는 코드는 NUMC나 CHAR를 검토해야 합니다.
  3. 값이 작고 거의 변하지 않는 목록입니다. 예: 사용 여부, 승인 여부, 예약 등급.
  4. 아니요. Value Table은 후보 제안에 가깝고, 실제 관계와 입력 검증은 Foreign Key 등 별도 설정이 필요합니다.
  5. Domain은 재질, Data Element는 의미입니다. 같은 재질 위에 서로 다른 라벨과 설명을 붙일 수 있습니다.

12. 한눈에 정리

Domain값의 기술 규격과 허용 범위를 정하는 DDIC 하위 부품입니다.
타입과 길이계산할 숫자인지, 보존할 코드인지 보고 Data Type과 Length를 정합니다.
Fixed Value작고 변하지 않는 값 목록에 적합하며 입력 도움과 기본 검증에 도움을 줍니다.
Value Table자동 검증이 아니라 Foreign Key 후보를 제안하는 성격으로 이해합니다.
