학습 목표

지난 Lesson에서 DDIC가 SAP 데이터 정의의 중심 창고라는 것을 봤습니다. 이번에는 그 창고에서 가장 작은 부품인 Domain을 직접 이해합니다. Data Type, Length, Output Length, Fixed Value가 각각 무엇을 막아주고 도와주는지 초심자 기준으로 차근차근 익혀봅니다.

1. 지난 시간 연결: SAP는 왜 작은 부품부터 만들까? 🧩

이전 Lesson에서 SAP는 데이터베이스에 바로 CREATE TABLE을 던지는 방식보다, DDIC에서 부품을 하나씩 정의하고 활성화한 뒤 조립하는 방식을 선호한다고 배웠습니다. 처음 보면 조금 돌아가는 길처럼 느껴질 수 있어요. 하지만 회사 시스템은 한두 명이 쓰는 앱이 아니라, 수백 개 프로그램과 수천 개 화면이 같은 데이터를 바라보는 큰 세계입니다.

그래서 SAP는 가장 작은 규격부터 통일합니다. 예를 들어 “항공사 코드는 3자리 문자다”라는 규칙을 여기저기 흩뿌려두지 않고, 딱 한 곳에 등록해 둡니다. 그 한 곳이 바로 Domain입니다.

Domain은 “이 데이터는 어떤 재질이고, 몇 자리까지 담을 수 있고, 어떤 값만 허용할까?”를 정하는 첫 번째 설계도입니다.

2. Domain은 의미가 아니라 재질을 정한다 🧱

Domain을 처음 배울 때 가장 중요한 포인트는 의미와 재질을 분리해서 생각하는 것입니다. Domain은 “항공사 코드”, “회사 코드”, “성별 코드”처럼 사람이 읽는 의미를 깊게 설명하지 않습니다. 대신 아주 기술적인 질문에 답합니다.

  • 어떤 종류의 값인가? 문자라면 CHAR, 숫자처럼 보이는 코드라면 NUMC, 날짜라면 DATS처럼 Data Type을 고릅니다.
  • 몇 자리까지 담을 수 있는가? 항공사 코드처럼 3자리면 Length = 3, 사번처럼 8자리면 Length = 8처럼 Length를 정합니다.
  • 화면에는 몇 자리로 보여줄까? 내부 저장 길이와 화면 표시 폭을 맞추기 위해 Output Length를 지정합니다.
  • 값을 제한할까? Y/N, M/F처럼 선택지가 적으면 Fixed Value로 허용 목록을 막아둘 수 있습니다.

비유하자면 Domain은 옷 이름이 아니라 원단 규격표입니다. “면 100%, 폭 3cm” 같은 정보는 말하지만, 이 원단이 교복이 될지, 가방끈이 될지는 아직 말하지 않아요. 그 “의미 붙이기”는 다음 Lesson의 Data Element가 맡습니다.

3. 항공사 코드 Domain을 상상하며 만들어보기 ✍️

이제 아주 작은 실습을 머릿속으로 따라가 봅시다. 목표는 ZCARRID라는 Domain을 만드는 것입니다. 이름 앞의 Z는 고객사에서 직접 만든 객체에 자주 붙이는 접두어라고 생각하면 됩니다. 실제 프로젝트에서는 회사 네이밍 규칙을 따릅니다.

💡

최소 설정 예시

  • Domain 이름: ZCARRID
  • Short Description: 항공사 코드 Domain
  • Data Type: CHAR, 글자를 담는 타입
  • Length: 3, 최대 3자리 저장
  • Output Length: 3, 화면에도 3자리 폭으로 표시

SE11에서는 Domain 화면에서 위 값을 채우고 저장한 뒤 활성화합니다. ADT에서는 Dictionary Object를 만들고 같은 값을 입력한 뒤 활성화합니다. 도구 모양은 달라도 핵심은 같습니다.

여기서 CHAR 3은 “세 글자까지 들어가는 문자 칸”이라는 뜻입니다. KE, AA, SQ처럼 2자리 값도 들어갈 수 있고, KOR처럼 3자리 값도 들어갈 수 있습니다. 하지만 KOREA처럼 5자리는 들어갈 수 없습니다. Domain이 저장 가능한 그릇 크기를 정했기 때문입니다.

초심자 체크: Length는 데이터가 실제로 저장될 수 있는 최대 자리수입니다. Output Length는 화면에 보이는 폭입니다. 처음에는 둘을 같은 값으로 두는 예제가 많지만, 둘은 역할이 다릅니다.

4. 정상 흐름과 오류 흐름을 나눠서 보기 🔍

Domain을 만들 때는 “활성화가 됐다”에서 끝내지 말고, 정상 흐름과 오류 흐름을 같이 떠올려야 합니다. 초보 단계에서 이 습관을 들이면 나중에 디버깅할 때 덜 당황합니다.

  • ✅ 정상 흐름: ZCARRID를 CHAR 3으로 만들고 활성화합니다. 이후 Data Element나 Table Field가 이 Domain을 참조하면 “3자리 문자” 규칙을 자동으로 물려받습니다.
  • ❌ 길이 오류: 프로그램이나 화면에서 3자리를 넘는 값을 넣으려 하면, 화면 또는 저장 단계에서 값이 잘리거나 오류가 날 수 있습니다. 그래서 업무 코드의 실제 길이를 먼저 확인해야 합니다.
  • ❌ 타입 선택 오류: 코드가 숫자처럼 보여도 앞에 0이 붙을 수 있으면 INT4가 아니라 NUMC나 CHAR를 고려해야 합니다. 예를 들어 001은 숫자 1이 아니라 코드 001일 수 있습니다.
⚠️

처음부터 너무 작게 잡으면 나중에 아픕니다

운영 데이터가 쌓인 뒤 Domain의 길이를 줄이는 것은 특히 위험합니다. 이미 저장된 값이 새 길이에 맞지 않으면 데이터 변환 오류가 날 수 있습니다. 반대로 무작정 크게 잡으면 화면 폭과 저장 공간, 검증 기준이 흐려집니다. “업무에서 실제로 쓰는 코드 길이”를 확인하고 정해야 합니다.

5. Fixed Value는 작은 목록을 지키는 문지기 🚦

Fixed Value는 Domain에 “이 값들만 허용한다”라고 목록을 박아두는 기능입니다. 예를 들어 승인 여부가 Y 또는 N만 가능하다면, Domain에 두 값을 등록할 수 있습니다.

  • Value: 실제로 저장되는 값입니다. 예: Y, N
  • Short Text: 사용자가 이해할 설명입니다. 예: 승인, 미승인
  • 입력 도움말: 사용자가 F4를 누르면 허용된 값 목록이 보입니다.
  • 검증 효과: 목록에 없는 X를 입력하면 시스템이 거부합니다.

다만 Fixed Value는 작고 거의 변하지 않는 목록에 어울립니다. 성별, 사용 여부, 승인 여부처럼 값이 몇 개 안 되는 경우에는 아주 좋습니다. 하지만 국가 코드, 고객 번호, 자재 번호처럼 값이 많거나 계속 늘어나는 목록은 Fixed Value가 아니라 나중에 배울 Check Table이나 Value Help 쪽으로 가는 것이 맞습니다.

6. 실무 감각: 표준을 먼저 찾고, 커스텀은 신중하게 🚨

실무에서 가장 흔한 초보 실수는 “내가 필요한 Domain을 바로 새로 만드는 것”입니다. SAP에는 이미 통화 코드, 단위, 금액, 날짜, 회사 코드처럼 전 세계 프로젝트에서 검증된 표준 Domain이 많이 있습니다.

⚠️

표준 SAP 동작과 고객사 관행을 섞어 외우지 마세요

어떤 회사에서는 “항상 Z로 새로 만든다” 같은 관행이 있을 수 있지만, 그것이 SAP 표준 철학은 아닙니다. 먼저 표준 객체를 검색하고, 의미와 기술 조건이 정말 맞지 않을 때만 커스텀 Domain을 만드는 쪽이 유지보수에 유리합니다.

Domain은 작아 보이지만, 나중에 수많은 Data Element와 Table Field가 이어지는 출발점입니다. 첫 단추가 삐뚤어지면 뒤의 부품들도 전부 영향을 받습니다. 그래서 “작은 칸 하나”를 만드는 지금부터 신중하게 생각하는 습관이 중요합니다.

7. 미니 실습: Domain 설계 기록지 만들기 🧪

이번 Lesson의 실습은 실제 시스템이 없어도 할 수 있는 설계 기록 실습입니다. 아래 업무 요구사항을 보고 Domain을 어떻게 만들지 스스로 적어보세요.

✍️

요구사항

예약 등급을 저장해야 합니다. 값은 비즈니스석, 이코노미석, 일등석 세 종류만 허용합니다. 화면에는 한 글자 코드로 보이면 충분합니다.

  1. Domain 이름을 정합니다. 예: ZBOOK_CLASS
  2. Data Type과 Length를 정합니다.
  3. Fixed Value 후보를 3개 적고, 각 값의 설명을 붙입니다.
  4. 잘못된 값이 들어오는 오류 케이스를 1개 적습니다. 예: X 입력 시 거부되어야 함

완료 조건: Domain 이름, 타입/길이, 허용값 목록, 오류 케이스가 모두 한 줄씩 적혀 있으면 성공입니다.

NotebookLM의 ABAP Dictionary 자료도 같은 포인트를 강조합니다. Domain은 라벨이나 업무 설명이 아니라 기술 속성과 허용값을 잡는 곳입니다. 그래서 실습 기록에도 “의미 설명”보다 “값의 규격”이 먼저 나와야 합니다.

9. 확인 퀴즈와 정답/해설 ✅

  1. Domain이 주로 정하는 것은 화면 라벨일까요, 데이터의 기술적 규격일까요?
  2. 001처럼 앞의 0이 중요한 코드는 무조건 숫자 타입으로 잡아도 될까요?
  3. 국가 코드처럼 값이 많고 계속 관리되는 목록은 Fixed Value에 전부 넣는 것이 좋을까요?
정답/해설 보기
  1. 데이터의 기술적 규격입니다. 화면 라벨과 업무 의미는 다음 단계인 Data Element가 담당합니다.
  2. 아니요. 앞의 0이 의미 있는 코드는 숫자 계산 대상이 아니라 코드일 수 있으므로 CHAR나 NUMC를 검토해야 합니다.
  3. 아니요. Fixed Value는 작고 거의 변하지 않는 목록에 적합합니다. 값이 많거나 운영 중 늘어나는 목록은 Check Table이나 Value Help 쪽으로 설계하는 것이 보통 더 안전합니다.

10. 한눈에 정리 🏁

📝

오늘의 핵심만 딱 잡기

  • Domain은 데이터의 의미가 아니라 기술적 재질을 정합니다.
  • Data Type은 문자, 숫자, 날짜처럼 값의 종류를 고릅니다.
  • Length는 저장 가능한 자리수, Output Length는 화면 표시 폭입니다.
  • Fixed Value는 작고 고정된 허용값 목록을 시스템 차원에서 막아줍니다.
  • 표준 Domain이 이미 있다면 새로 만들기 전에 재사용 가능성을 먼저 확인합니다.

이제 우리는 데이터의 “재질”을 정할 수 있게 됐습니다. 다음 Lesson Data Element 기본 설계에서는 이 재질 위에 사람이 이해할 수 있는 의미와 화면 라벨을 붙여보겠습니다.
