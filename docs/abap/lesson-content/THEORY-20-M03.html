학습 목표

View끼리 관계를 잇는 Association을 배웁니다. JOIN과 무엇이 다른지, "필요할 때만 따라가는 똑똑한 연결"이라는 개념을 익힙니다.

1. 지난 시간 연결: JOIN인데 더 똑똑한 것 🔗

Chapter 11에서 JOIN으로 테이블을 합쳤습니다. JOIN은 강력하지만, 항상 데이터를 미리 합쳐 읽습니다. CDS의 Association은 "관계를 정의해 두되, 실제로 필요할 때만 따라가는" 더 유연한 연결입니다.

2. Association 정의 ✍️

define view entity ZI_Flight
  as select from sflight
  association [1..1] to ZI_Carrier as _Carrier
    on $projection.carrid = _Carrier.carrid    "연결 조건
{
  key carrid,
  key connid,
      price,
      _Carrier                                  "관계 노출(이름만)
}
  • association [1..1] to ... as _Carrier: "이 뷰는 항공사(_Carrier)와 관계가 있다"고 선언. [1..1]은 카디널리티(1:1).
  • on: 연결 조건(JOIN의 ON과 비슷).
  • _Carrier (필드 목록에): 관계를 밖으로 노출. 쓰는 쪽이 필요하면 따라갈 수 있게.
💡

비유: 전화번호부의 단축번호

Association은 "항공사 정보로 가는 단축번호"를 등록해 두는 거예요. 평소엔 안 걸어도 되고, 필요할 때만 그 번호로 전화(데이터 조회)하면 됩니다. JOIN은 항상 통화 연결, Association은 필요 시 연결인 셈이죠.

3. 관계 따라가기 (Path) 🧭

노출된 Association은 점(.)으로 따라가 다른 뷰의 필드를 가져올 수 있습니다.

ABAP
1
2

define view entity ZC_Flight
  as projection on ZI_Flight
{
  key carrid,
      price,
      _Carrier.carrname as CarrierName   "관계를 따라가 이름을 가져옴
}

필요한 화면에서만 _Carrier.carrname처럼 따라가니, 불필요한 JOIN을 항상 짊어지지 않아도 됩니다.

4. 정상 흐름과 오류 흐름 🔍

  • ✅ 정상: 관계를 한 번 정의 → 여러 곳에서 필요할 때만 path로 따라감.
  • ❌ 오류 1: 카디널리티([1..1] / [0..*])를 실제 데이터와 다르게 적음 → 결과 행 수가 의도와 어긋남.
  • ❌ 오류 2: Association을 노출만 하고 안 쓰면 부담은 없지만, 남용해 path를 깊게 체이닝하면 성능·가독성이 나빠질 수 있음.

5. 실무에서 조심할 점 🚨

⚠️

카디널리티는 "사실"대로 적으세요

Association의 카디널리티(1:1인지 1:N인지)는 단순 표기가 아니라, DB가 최적화와 결과 행 수를 판단하는 근거입니다. 실제 관계와 다르게 적으면 데이터가 중복되거나 누락될 수 있습니다. "이 관계가 정말 1:1인가, 1:N인가?"를 Chapter 4의 Foreign Key 데이터 모델을 떠올리며 정확히 적으세요.

6. 미니 실습: Association 경로 읽기 🧪

이번 실습은 Association을 JOIN 대체 문법처럼 외우지 않고, “관계를 이름으로 노출하고 필요한 순간 따라간다”는 감각을 잡는 데 목적이 있습니다.

✍️

실습 과제

  1. 예제 Association에서 대상 View, 별칭, ON 조건, Cardinality를 각각 표시합니다.
  2. _Carrier.Name 같은 path expression을 보고, 어느 관계를 따라 어떤 필드를 읽는지 말로 풀어씁니다.
  3. 실제 데이터가 1:N인데 1:1처럼 Cardinality를 적으면 어떤 문제가 생길지 적습니다.

완료 조건: Association이 항상 즉시 JOIN되는 것이 아니라, 사용 위치와 경로 표현에 따라 의미가 달라진다는 점을 설명할 수 있으면 성공입니다.

8. 확인 퀴즈와 정답/해설 ✅

  1. Association과 일반 JOIN을 초심자 관점에서 어떻게 구분하면 좋을까요?
  2. Cardinality를 실제 데이터 관계와 다르게 쓰면 왜 위험한가요?
  3. _Carrier.Name 같은 표현에서 밑줄로 시작하는 이름은 보통 무엇을 뜻하나요?
정답/해설 보기
  1. JOIN은 지금 결합해 결과를 만들고, Association은 따라갈 수 있는 관계를 모델에 노출한다고 이해하면 좋습니다.
  2. 문법 검사, 최적화, 결과 해석에 잘못된 힌트를 줄 수 있습니다. Cardinality는 장식이 아니라 관계 계약에 가깝습니다.
  3. Association 별칭입니다. 그 관계를 따라 대상 엔티티의 필드를 path expression으로 읽을 수 있습니다.

9. 한눈에 정리 🏁

📝

오늘의 핵심만 딱 잡기

  • Association은 View 간 관계를 정의하되 필요할 때만 따라가는 똑똑한 연결입니다.
  • association [card] to ... as _Name on ...로 정의하고 필드 목록에 노출합니다.
  • 점(.) path로 관계를 따라가 다른 뷰의 필드를 가져옵니다.
  • 카디널리티는 실제 관계대로 정확히 적습니다.
