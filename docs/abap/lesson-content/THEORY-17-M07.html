학습 목표

지금까지 배운 ABAP SQL을 정리하고, 왜 다음 단계로 CDS View가 필요한지 이해합니다. "조회는 어디에 둘 것인가"라는 관점으로 코드 푸시다운을 다시 짚으며 Chapter를 마무리합니다.

1. 지난 시간 연결: 우리가 익힌 도구들 🧰

이번 Chapter에서 우리는 Modern ABAP SQL을 배웠습니다. 콤마·@·인라인, SQL 표현식(CASE·CAST·COALESCE), 문자/날짜 함수, 메모리 테이블 조회까지. 이제 SELECT 한 번으로 꽤 많은 가공을 DB에서 처리할 수 있습니다.

그런데 한 가지 한계가 남습니다. 이 SELECT들은 특정 프로그램 안에 갇혀 있습니다.

2. ABAP SQL의 한계: 재사용이 어렵다 🔒

  • 한 프로그램 전용: 잘 만든 JOIN·집계 SELECT라도, 다른 프로그램에서 쓰려면 또 적어야 합니다.
  • 의미 부여 부족: 컬럼이 무엇을 뜻하는지, 어떻게 보여줄지 같은 정보를 SELECT는 담지 못합니다.
  • 현대 스택 단절: OData·Fiori·RAP는 SELECT 문이 아니라 모델을 필요로 합니다.
🔗

그래서 CDS

이 한계를 넘으려고 SELECT 로직을 재사용 가능한 모델로 끌어올린 것이 CDS View Entity입니다. ABAP SQL에서 배운 JOIN·CASE·집계가 CDS에서 거의 그대로 쓰이되, 한 번 만들면 여러 곳에서 재사용됩니다.

3. 다시 보는 코드 푸시다운 🏭

코드 푸시다운은 "계산·결합·집계는 가능한 한 DB(HANA)에서 하고, ABAP으로는 결과만 적게 가져온다"는 현대 ABAP의 큰 원칙입니다.

  • ✅ ABAP SQL 표현식 → 1차 푸시다운(SELECT 안에서 가공).
  • ✅ CDS View → 본격 푸시다운(재사용 가능한 모델로).
  • 📌 흐름: 옛 ABAP 루프 가공 → Modern ABAP SQL → CDS View로 점점 DB 쪽으로 내려갑니다.

4. 정상 흐름과 오류 흐름 🔍

  • ✅ 좋은 흐름: 간단·일회성은 ABAP SQL, 재사용·표준 모델이 필요하면 CDS로 올립니다.
  • ❌ 안티패턴: 같은 복잡한 JOIN을 여러 프로그램에 복붙 → 유지보수 지옥. 이런 신호가 보이면 CDS로 모델화할 때입니다.

5. 실무에서 조심할 점 🚨

⚠️

"전부 CDS"가 정답은 아닙니다

CDS가 강력하다고 모든 SELECT를 CDS로 만들 필요는 없습니다. 한 곳에서만 쓰는 단순 조회는 ABAP SQL이 더 간단하고 명확합니다. "여러 곳에서 재사용되는가, 표준 모델로 쓸 가치가 있는가"를 기준으로 판단하세요. 도구는 상황에 맞게 고르는 것이지, 최신이라고 무조건 쓰는 게 아닙니다.

6. 한눈에 정리 🏁

📝

THEORY-17 마무리 핵심

  • Modern ABAP SQL: 콤마·@·인라인 + 표현식(CASE/CAST/COALESCE) + 문자/날짜 함수 + @itab 조회.
  • 한계: SELECT는 프로그램 전용이라 재사용·모델화가 약합니다.
  • 그 한계를 넘는 것이 CDS View이며, ABAP SQL 지식이 거의 그대로 이어집니다.
  • 원칙은 코드 푸시다운: 가공은 DB로, ABAP은 결과만.
