학습 목표

이번 Lesson에서는 지난 시간의 Transparent Table을 실제로 활성화하기 전 확인하는 Technical Settings를 배웁니다. Data Class, Size Category, Buffering을 운영 힌트로 이해하고, Data Browser와 ADT Data Preview로 Test Data를 확인하는 흐름까지 닫습니다.

1. Technical Settings는 필드 뜻을 정하지 않는다

Transparent Table은 필드 목록과 Key만으로 끝나지 않습니다. 실제 데이터베이스에 만들어지는 저장 대상이므로, 시스템은 “이 테이블을 어떤 물리 특성으로 만들고 접근할 것인가?”라는 정보를 더 필요로 합니다. 이 묶음이 Technical Settings입니다.

SAP Learning은 Technical Table Settings를 테이블과 별도로 활성화하고 전송할 수 있는 개발 객체로 설명합니다. 이 설정은 물리 DB 테이블의 속성과 ABAP SQL 접근 방식에 영향을 줍니다. 단, 어떤 설정이 실제 DB에 전달되는지는 사용하는 데이터베이스에 따라 달라집니다.

필드의 업무 의미는 Data Element 쪽에서 잡고, Technical Settings는 저장과 접근의 운영 힌트를 잡습니다.

2. 설정 네 칸을 한 화면에 놓고 보기

초급 단계에서는 모든 옵션을 외우기보다, 각 칸이 어떤 질문에 답하는지 먼저 잡는 편이 낫습니다.

3. Data Class는 데이터의 성격표다

Data Class는 테이블이 담는 데이터의 성격을 나타냅니다. 예전 DB에서는 물리 tablespace 선택에 직접 연결되었고, SAP HANA에서는 SAP Learning 설명처럼 효과가 없지만 여전히 필수 입력값이자 문서 정보로 남습니다.

세 가지 대표 Data Class

값 성격 초급 판단 예
APPL0 Master data 고객, 자재, 직원처럼 기준이 되는 데이터
APPL1 Transaction data 주문, 전표, 재고 이동처럼 업무가 생길 때 계속 쌓이는 데이터
APPL2 Organizational/customizing data 회사 설정, 국가 코드, 조직 기준처럼 상대적으로 드물게 바뀌는 데이터
HANA에서는 의미가 없다면 아무거나 골라도 될까?

아닙니다. 실제 물리 효과가 제한되더라도 설계 문서와 운영 기준으로 남습니다. 프로젝트 표준, Basis 기준, 교육 시스템의 지시값을 우선 따르세요.

4. Size Category는 예상 데이터 양을 말한다

Size Category는 테이블이 앞으로 어느 정도 커질지 알려주는 값입니다. SAP 공식 문서는 Size Category가 초기 저장 공간과 관련되고, 값 도움말에 예상 record 범주가 연결된다고 설명합니다.

크기 판단 예시

테이블 성격 예상 규모 판단 방향
소규모 코드 테이블 수십에서 수백 건 낮은 범주 후보
마스터 테이블 수천에서 수십만 건 값 도움말과 요구사항 확인
거래 이력 테이블 기간이 길수록 계속 증가 작게 찍지 말고 운영 기준 확인

숫자 자체를 암기하지 말고, 값 도움말과 프로젝트 기준으로 예상 row 범주를 고른다는 흐름을 익힙니다.

5. Buffering은 성능과 최신성 사이의 선택이다

Buffering은 테이블 데이터를 애플리케이션 서버의 table buffer에서 읽을 수 있게 하는 설정입니다. SAP Learning은 활성 버퍼링이 있는 테이블을 ABAP SQL로 접근할 때 table buffer가 암묵적으로 사용된다고 설명합니다.

그래서 버퍼링은 “빠르게 읽고 싶으니 항상 켠다”가 아닙니다. 데이터가 자주 바뀌거나 최신성이 중요한 테이블에서는 오히려 위험합니다.

버퍼링 후보 비교

어울리는 후보
  • 작고 자주 읽는 기준 데이터
  • 변경이 드문 customizing성 데이터
  • 잠깐의 반영 지연이 업무 위험을 만들지 않는 데이터
피해야 할 후보
  • 주문, 재고, 전표처럼 자주 바뀌는 transaction data
  • 항상 최신 상태를 읽어야 하는 테이블
  • 변경량이 커서 버퍼 무효화 비용이 큰 데이터
Buffering을 켜면 SELECT 문을 다 바꿔야 할까?

아닙니다. 활성 버퍼링 테이블을 ABAP SQL로 읽을 때는 DB 인터페이스가 table buffer 사용을 처리합니다. 개발자는 “이 테이블이 버퍼링 대상인지”를 설계 단계에서 신중히 판단해야 합니다.

6. 활성화 순서는 별도 객체라는 점 때문에 헷갈린다

ADT 기준으로 Technical Table Settings는 테이블 정의의 부속 화면처럼 보이지만, SAP Learning은 별도로 활성화하고 전송할 수 있는 개발 객체라고 설명합니다. 그래서 실습에서는 테이블 정의와 technical settings를 모두 활성화하는 습관이 필요합니다.

Transparent Table 마무리 흐름

1. Field List필드, Key Field, MANDT 여부를 정한다.
2. Technical SettingsData Class, Size Category, Buffering, 변경 로그를 확인한다.
3. Activate Settingstechnical settings 객체를 먼저 또는 함께 활성화한다.
4. Activate TableActivation 성공 후 ABAP SQL 접근 대상이 된다.
5. Preview DataData Browser나 ADT Data Preview로 테스트 데이터를 확인한다.
⚠️

기본값을 믿고 지나가지 않습니다

새 테이블 생성 시 editor가 흔한 기본값을 제안할 수 있습니다. 그래도 SAP Learning의 권고처럼 기본값이 내 테이블에 맞는지 반드시 확인하고 필요하면 바꿔야 합니다.

7. Data Browser와 ADT Data Preview로 눈으로 확인한다

Data Browser는 ABAP 프로그램을 직접 만들지 않고 테이블 데이터를 확인하는 도구입니다. SAP GUI에서는 전통적으로 SE16, SE16N 같은 트랜잭션을 떠올리고, ADT에서는 테이블이나 view의 Data Preview로 결과를 봅니다.

조회 도구의 역할 구분

도구 초급 사용 목적 주의
SE16 테이블 row 조회 권한과 시스템 정책을 따른다.
SE16N 조회 조건을 넣고 표 형태로 확인 운영 직접 수정 경로로 쓰지 않는다.
ADT Data Preview 개발 객체에서 바로 result set 확인 대량 데이터 탐색 도구처럼 남용하지 않는다.
Client-dependent 테이블에서는 무엇을 먼저 볼까?

Client-dependent 테이블이라면 MANDT 기준으로 현재 로그인 client의 데이터가 보이는지 확인합니다. 다른 client의 데이터와 섞어 이해하면 실습 결과를 잘못 판단할 수 있습니다.

8. Test Data와 운영 데이터의 경계를 긋는다

개발 환경에서 Test Data 한 줄을 넣고 Key 중복 오류를 확인하는 것은 좋은 학습입니다. 하지만 운영 시스템의 실제 데이터를 Data Browser에서 직접 고치는 것은 전혀 다른 문제입니다.

🚫

운영 데이터는 정식 경로로 바꿉니다

Data Browser 직접 수정은 권한 체크, 상태 체크, 후속 문서 생성, 변경 이력, application logic을 우회할 수 있습니다. 운영에서는 승인된 트랜잭션, 프로그램, 마이그레이션 절차를 사용합니다.

허용 범위 감각

상황 판단 이유
교육 client에서 내가 만든 Z 테이블에 테스트 row 입력 학습 범위 테이블 설계와 Key 동작을 확인하기 위한 제한된 데이터입니다.
개발 서버에서 승인된 테스트 프로그램으로 sample data 생성 권장 재현 가능한 방식으로 데이터를 넣고 지울 수 있습니다.
운영 client에서 SE16N으로 업무 테이블 직접 수정 금지 업무 검증과 변경 절차를 우회해 데이터 정합성을 깨뜨릴 수 있습니다.

9. 미니 실습: Technical Settings 결정표 작성

지난 Lesson에서 만든 항공편 일정 테이블을 기준으로 아래 순서대로 판단해 보세요. 실제 시스템이 없어도 설계표를 완성할 수 있습니다.

🧪

실습 과제

  1. 테이블이 master data, transaction data, customizing data 중 어디에 가까운지 적습니다.
  2. 예상 row 수를 낮음, 중간, 높음 중 하나로 잡고 Size Category 값 도움말에서 고를 범위를 적습니다.
  3. Buffering을 허용할지 말지 판단하고, “읽기 빈도”와 “변경 빈도”를 근거로 씁니다.
  4. technical settings와 table definition을 활성화한 뒤 Data Browser 또는 ADT Data Preview로 테스트 row를 확인합니다.
  5. 같은 Key 조합의 row를 다시 넣으면 어떤 오류가 기대되는지 설명합니다.

완료 조건: Data Class, Size Category, Buffering 판단 근거와 테스트 데이터 확인 결과를 각각 한 줄씩 기록하면 성공입니다.

11. 확인 퀴즈

  1. Technical Settings는 필드의 업무 의미를 정하는 설정인가요, 물리 DB 테이블과 접근 특성을 정하는 설정인가요?
  2. SAP HANA에서 Data Class는 물리 tablespace 선택에 강하게 영향을 준다고 말해도 될까요?
  3. Buffering은 주문, 재고, 전표처럼 자주 바뀌는 테이블에 항상 켜는 것이 좋을까요?
  4. 개발 환경의 Test Data 입력과 운영 데이터 직접 수정은 같은 수준의 작업인가요?
정답/해설 보기
  1. 물리 DB 테이블과 접근 특성을 정하는 설정입니다. 필드 의미는 Data Element 쪽에서 다룹니다.
  2. 아니요. SAP Learning은 Data Class가 SAP HANA에서는 효과가 없지만 필수값과 문서 정보로 남는다고 설명합니다.
  3. 아니요. Buffering은 작고 자주 읽으며 변경이 드문 데이터에 신중히 검토합니다.
  4. 아니요. 운영 데이터는 승인된 트랜잭션, 프로그램, 마이그레이션 절차로 변경해야 합니다.
