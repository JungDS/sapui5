학습 목표

여러 테이블을 묶어 한 화면에서 입력·수정할 수 있게 해주는 Maintenance View를 배웁니다. 이때 테이블들을 안전하게 묶어주는 Foreign Key 관계가 왜 중요한지 익힙니다.

1. 지난 시간 연결: 보기만 말고 "고치기"까지 ✏️

지금까지 배운 View들(Database/Projection/Help)은 모두 읽기 전용이었습니다. 데이터를 합치거나 솎아서 보여줄 뿐, 직접 수정하지는 못했죠.

그런데 설정 데이터(코드표, 매핑표 등)는 사용자가 화면에서 직접 추가·수정해야 할 때가 많습니다. 프로그램을 따로 만들지 않고도 표 형태로 데이터를 관리하게 해주는 것이 Maintenance View입니다.

2. Maintenance View는 "편집 가능한 표 화면" 🗂️

Maintenance View는 하나 이상의 테이블을 묶어, 엑셀처럼 줄을 추가·수정·삭제할 수 있는 유지보수 화면을 위한 View입니다. 관리자가 코드값을 직접 손볼 수 있게 해줍니다.

💡

일상 비유: 공유 엑셀 시트

개발자에게 매번 부탁하지 않고도, 담당자가 직접 코드표를 여닫으며 줄을 추가하는 공유 엑셀 같은 거예요. 단, 아무 값이나 못 넣게 규칙(Foreign Key)이 걸려 있죠.

3. Foreign Key가 데이터를 지킨다 🔐

여러 테이블을 묶어 편집하게 하려면, 테이블들 사이의 관계가 분명해야 합니다. 이때 Foreign Key(THEORY-04에서 배운 그 개념)가 테이블 관계를 정의합니다.

  • ✅ 정상: Foreign Key가 "이 코드는 저 마스터 테이블에 있는 값만 허용"이라고 막아줍니다. 잘못된 값 입력이 차단됩니다.
  • ❌ 관계 없음: 관계가 모호하면 Maintenance View를 만들 때 "어떻게 묶을지 모르겠다"는 오류가 나거나, 엉뚱한 데이터가 들어갈 수 있습니다.
그래서 Maintenance View는 Foreign Key 설계가 잘 되어 있을수록 안전하고 편리하게 동작합니다. 데이터 모델(THEORY-01·04)이 탄탄해야 화면도 튼튼한 셈이죠.

4. Maintenance View와 테이블 Foreign Key 결합 시각화 🗺️

부서 기본 마스터 테이블(`ZDEPT`)과 언어별 부서명 설명 테이블(`ZDEPTT`)이 Foreign Key 관계로 결합되어, 사용자가 하나의 화면에서 동시에 데이터를 추가하고 저장하는 구조를 시각화해 보겠습니다.

ZDEPT (부서 키) ↔ ZDEPTT (부서명) Foreign Key 결합 구조

1. 기본 테이블 간의 Foreign Key 관계
ZDEPT (부서 테이블)방향ZDEPTT (설명 테이블)
DEPTID (Key)➔ (Foreign Key)DEPTID (Key)
BUDGETSPRAS (언어 Key)
DEPTNAME

ZDEPTT의 부서 코드는 반드시 ZDEPT에 존재하는 코드만 허용하는 물리 규칙을 가집니다.

2. 결합된 ZV_DEPT_MAINT (유지보수 뷰 화면)
DEPTID (부서코드)DEPTNAME (부서명)BUDGET (예산)비고
D01개발팀50,000,000정훈영 소속 (동시 입력 가능 ✅)
D02영업팀30,000,000홍길동 소속 (동시 입력 가능 ✅)

사용자는 하나의 표 화면에서 데이터를 입력하지만, 저장 시 각각 ZDEPT와 ZDEPTT 테이블에 나누어 안전하게 기록됩니다.

5. 정상 흐름과 특별한 기능 🔍

  • ✅ 복수 테이블 CUD 동시 지원: Database View는 읽기만 가능하지만, Maintenance View는 복수 테이블을 엮어 **추가, 수정, 삭제(CUD)를 모두 동시에 처리**할 수 있는 유일한 고전 뷰입니다.
  • ✅ 일관성 보장: Foreign Key가 뷰 구성의 단단한 중심점이 되어, 기준 테이블에 없는 엉뚱한 상세 정보가 추가되는 논리적 모순을 사전에 완벽히 방단해 줍니다.
  • ❌ N:1 관계 제약: 결합할 테이블들의 관계는 반드시 N:1 구조(상세 테이블이 자식, 마스터 테이블이 부모)여야 하며, 1:N과 같이 복잡한 일대다 관계는 뷰 레벨에서 동시에 수정 화면으로 제공할 수 없습니다.

6. 실무에서 조심할 점 🚨

⚠️

운영 환경에 데이터 전송(Transport) 설정을 설계하세요

Maintenance View를 사용해 편집 화면을 띄우면, 개발자가 프로그램 로직을 짜지 않아도 데이터를 직접 DB에 수정할 수 있어 매우 편합니다. 하지만 운영 환경(PRD)에서 테이블 데이터를 직접 수정하게 방치하면 전체 시스템 정합성이 깨질 수 있으므로, 권한 그룹을 묶고 데이터를 개발 환경(DEV)에서 테스트 환경을 거쳐 운영 환경으로 **전송 요청서(TR)**를 통해 배포(Transport)하도록 뷰 기술 설정 단계에서 제한을 걸어야 합니다.

7. 미니 실습: Maintenance View 생성 및 Foreign Key 확인 🧪

✍️

실습 과제

  1. 표준 테이블 T005(국가 마스터)와 T005T(국가 텍스트)를 엮은 대표적 유지보수 뷰인 V_T005를 조회해 봅니다.
  2. 두 테이블을 유지보수 뷰로 묶기 위해 사용된 Foreign Key 구조가 테이블 결합(Join) 조건 탭에 어떻게 매핑되어 명시되어 있는지 파악합니다.
  3. 이 유지보수 뷰를 통해 데이터를 입력할 때, 국가 설명의 언어 키(`SPRAS`)가 로그인 언어로 자동 바인딩되어 입력되는 구조적 흐름을 관찰합니다.

완료 조건: 복수 테이블을 Maintenance View로 묶을 때 Foreign Key가 정의되어 있어야 하는 이유와 CUD 기능의 장점을 설명할 수 있으면 성공입니다.

8. 공식 문서로 더 확인하기 🔗

  • SAP Help Portal: Maintenance Views - Maintenance View가 데이터를 수정하는 표준 내부 동작 방식 사양을 학습합니다.
  • SAP Help Portal: Foreign Key Relation - 뷰를 설계할 때 핵심이 되는 Foreign Key 정의 규칙과 도메인 검증 기준을 학습합니다.
  • SAP Help Portal: Table Maintenance Dialog - 생성된 유지보수 뷰를 바탕으로 실제 화면 다이얼로그를 빌드하는 과정을 확인합니다.

9. 확인 퀴즈와 정답/해설 ✅

  1. Maintenance View는 Database View와 달리 어떤 SQL 연산(Read 외에)이 가능하여 데이터를 제어하나요?
  2. 복수 테이블을 하나의 Maintenance View로 묶을 때, 각 테이블 사이에 반드시 사전에 DDIC 상에 정의되어야 하는 속성은 무엇인가요?
  3. 실무에서 Maintenance View로 만든 편집 화면을 운영 시스템(PRD)에서 아무나 실행해 직접 고칠 수 없도록 설계할 때 설정하는 보안 대책은 무엇인가요?
정답/해설 보기
  1. 데이터의 삽입, 수정, 삭제(CUD - INSERT/UPDATE/DELETE)가 동시에 가능합니다.
  2. Foreign Key(외래 키) 관계가 맺어져 있어야 합니다. 이를 통해 부모-자식 관계의 데이터 무결성을 검증합니다.
  3. 권한 그룹(Authorization Group)을 뷰에 지정하여 권한이 있는 담당자만 SM30을 통해 실행하게 통제하고, 데이터 변경 시 전송요청서(TR)를 발행하도록 설정합니다.

10. 한눈에 정리 🏁

📝

Maintenance View 핵심 요약

  • Maintenance View는 여러 테이블의 데이터를 한 표 화면에서 입력·수정하도록 제공하는 CUD 지원 뷰 구조입니다.
  • 테이블 간의 Foreign Key 관계가 단단하게 묶여 있어야만 뷰를 설계 및 생성할 수 있습니다.
  • 실제 물리 데이터베이스에 테이블이 생기지 않으며, 데이터는 원본 기본 테이블들에 안전하게 나누어 적재됩니다.
  • 강력한 데이터 변경 기능을 가지므로 권한 그룹 매핑과 Transport 관리 설계가 필수적입니다.
