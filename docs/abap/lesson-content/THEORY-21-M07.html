학습 목표

RAP에서 업무 규칙을 더하는 3대 도구 — 검증 Validation, 자동 계산 Determination, 사용자 동작 Action — 의 역할을 개요로 배웁니다.

1. 지난 시간 연결: 표준 동작을 넘어 "업무 규칙" 📐

create/update/delete 같은 표준 동작과 서비스 노출까지 됐습니다. 하지만 실제 업무에는 "종료일은 시작일 이후여야 한다", "요금은 자동 계산", "승인 버튼" 같은 고유 규칙이 필요합니다. RAP는 이를 세 가지 도구로 표현합니다.

2. 세 도구의 역할 ✍️

  • Validation(검증): 저장 전에 데이터가 규칙에 맞는지 확인. 틀리면 저장 차단. (예: 종료일 ≥ 시작일). M05에서 본 그것.
  • Determination(결정/자동계산): 특정 시점에 값을 자동으로 채움. (예: 생성 시 상태='신규', 변경 시 총액 자동 합산).
  • Action(액션): 표준 CRUD 외의 사용자 동작. (예: '승인', '취소' 버튼). 화면 버튼으로 노출됨.
define behavior for ZI_Travel alias Travel
{
  ...
  validation validateDates on save { field begin_date, end_date; }
  determination setStatus on modify { create; }
  action ( features : instance ) acceptTravel result [1] $self;
}

3. 언제 무엇을? 🧭

💡

한 문장 구분법

  • 막아야 하면 → Validation ("이건 틀렸어, 저장 못 해").
  • 자동으로 채워야 하면 → Determination ("이건 내가 알아서 채울게").
  • 버튼이 필요하면 → Action ("사용자가 누르면 이걸 해").

4. 정상 흐름과 오류 흐름 🔍

  • ✅ 정상: 검증은 Validation, 자동값은 Determination, 특수 동작은 Action — 역할대로 배치.
  • ❌ 오류 1: 자동 계산을 Validation에서 하려다 흐름이 꼬임(검증은 "막기"만, 값 변경은 Determination).
  • ❌ 오류 2: Determination이 무한히 서로를 트리거 → 루프. 트리거 조건을 명확히 설계.

5. 실무에서 조심할 점 🚨

⚠️

역할을 섞으면 디버깅 지옥

Validation·Determination·Action은 실행 시점과 목적이 다릅니다. "검증인데 값을 바꾼다", "결정인데 저장을 막는다"처럼 역할을 섞으면, 나중에 "왜 이 값이 이렇게 됐지?"를 추적하기가 매우 어렵습니다. 각 도구를 본래 역할대로만 쓰는 것이 RAP를 깔끔하게 유지하는 비결입니다. 이 셋의 깊은 구현은 실무·Fiori 트랙에서 단계별로 익힙니다.

6. 한눈에 정리 🏁

📝

오늘의 핵심만 딱 잡기

  • Validation: 저장 전 검증, 틀리면 차단("막기").
  • Determination: 특정 시점 값 자동 채움("자동 채우기").
  • Action: CRUD 외 사용자 동작, 화면 버튼("누르면 실행").
  • 역할을 섞지 말고 본래 목적대로만 사용합니다.

RAP의 핵심 도구를 모두 봤습니다. 마지막 Lesson ABAP Cloud와 Released API 원칙에서, 이 모든 것이 돌아가는 현대 환경의 원칙을 정리하며 Track 1을 완성합니다.
