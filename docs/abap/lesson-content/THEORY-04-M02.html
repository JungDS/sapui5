학습 목표

지난 Lesson에서 Foreign Key와 Check Table로 입력값을 검증하는 법을 배웠습니다. 그런데 DDIC를 보면 Value Table이라는 비슷해 보이는 이름이 또 등장합니다. 이번 Lesson에서는 Value Table이 무엇이고 왜 Check Table과 헷갈리면 안 되는지 — 둘의 역할이 어떻게 다른지를 확실히 정리합니다.

1. 지난 Lesson 연결: 검증은 Check Table이 했는데, Value Table은 뭐지? 🤔

지난 Lesson의 결론은 “기준표(Check Table)가 있어도 Foreign Key를 걸어야 검증이 동작한다”였습니다. 그런데 Domain을 들여다보면 “Value Table”이라는 칸이 있어서, 많은 초심자가 “이게 그 기준표인가?” 하고 헷갈립니다.

결론부터 말하면, Value Table은 “정보”이고 Check Table은 “검증”입니다. 이름은 비슷하지만 시스템에서 가지는 권한이 완전히 다릅니다. 이 차이를 모르면 “Value Table만 적어두고 검증이 될 거라 착각하는” 실수를 하게 됩니다.

Value Table은 “이 값들의 마스터는 저 테이블에 있어요”라고 알려주는 명함이고, Check Table은 실제로 잘못된 값을 막아서는 방패입니다.

2. Value Table: Domain에 적어두는 “값의 본가” 주소 🏠

Value Table은 어떤 Domain이 가질 수 있는 “유효한 값들의 전체 집합(pool)”이 어느 테이블에 저장돼 있는지를 선언해 두는 속성입니다. 중요한 건 지정되는 위치입니다.

  • 지정 위치: Domain 유지보수 화면(SE11)의 Value Range(값 범위) 탭 맨 아래 “Value Table” 칸.
  • 레벨: 테이블 필드가 아니라 Domain 레벨. 즉 데이터의 기술적 뼈대에 붙는 메타데이터입니다.
  • 성격: “마스터 값은 저기 모여 있어요”라는 정보 제공일 뿐, 데이터를 통제할 권한은 없습니다.

어디에 무엇이 붙는가 — 레벨이 다르다

Value Table은 Domain에, Check Table은 테이블 필드의 Foreign Key에 붙습니다. 붙는 위치가 곧 권한의 차이입니다.

3. 결정적 차이: 제안하는 Value Table vs 검증하는 Check Table ⚖️

가장 중요한 사실 하나만 기억하세요. Value Table에 테이블 이름을 적어두는 것만으로는 어떤 입력 검증도 일어나지 않습니다. 실제로 잘못된 값을 막는 건 오직 Foreign Key로 맺어진 Check Table입니다.

Value Table vs Check Table

Value Table (제안·정보용)
  • 위치: Domain 레벨
  • 역할: “마스터 값은 여기 있다”는 선언
  • 권한: 입력 검증 안 함
  • 비유: 이력서 / 명함
Check Table (검증용)
  • 위치: 테이블 필드의 Foreign Key
  • 역할: 입력값이 기준표에 있는지 검사
  • 권한: 화면 입력 검증함
  • 비유: 출입을 막는 방패

둘 다 같은 마스터 테이블을 가리키는 경우가 대부분이지만, “어디에 붙어서 무슨 일을 하느냐”가 다릅니다.

💡

오해 바로잡기: Value Table과 Check Table은 “다른 테이블”이 아니다

둘은 보통 물리적으로 같은 하나의 마스터 테이블(예: SCARR)을 가리킵니다. Domain 밑바닥에서 “값의 본가”로 소개될 때는 Value Table, 테이블 필드 위에서 외래 키 방패로 일할 때는 Check Table이라 부를 뿐입니다. 별개의 테이블 두 개가 아니라, 같은 테이블의 두 역할입니다.

4. 그럼 Value Table은 왜 적어둘까? — 자동 제안 ✨

검증 권한도 없는 Value Table을 굳이 Domain에 적어두는 이유는 개발 생산성 때문입니다. Foreign Key를 만들 때 시스템이 Check Table을 알아서 제안해 주거든요.

Foreign Key 생성 시 Check Table 자동 제안 흐름

1. 외래 키 버튼필드(예: SBOOK-CARRID)에서 Foreign Key 생성 클릭
2. 추적필드 → Data Element → Domain 순서로 스캔
3. 발견Domain에 Value Table(SCARR)이 등록돼 있음
4. 제안“이 SCARR을 Check Table로 쓸까요?” 팝업
5. 격상Yes → 그 이름이 필드의 Check Table로 복사·승격

Value Table은 이 “제안”의 출발점입니다. 개발자가 매번 기준표 이름을 손으로 찾지 않아도 되게 도와줍니다.

5. Value Table만 있고 Foreign Key를 안 걸면? 🚧

설정 상태에 따른 검증 동작

입력사용자가 화면에 XXX 입력

결과검증 기준표에 없으니 화면에서 차단

데이터 무결성을 지키려면 Value Table 등록만으로는 부족합니다. 반드시 Foreign Key 설정이 동반되어야 합니다.

6. 실무에서 조심해야 할 점

⚠️

“Value Table 적었으니 검증되겠지”가 가장 흔한 함정

Domain에 Value Table을 아무리 꼼꼼히 등록해도, 테이블 필드에서 Foreign Key를 맺지 않으면 검증은 0입니다. 검증이 필요한 필드라면 Foreign Key 설정 여부를 반드시 확인하세요.

  • 화면 검증 한계 동일: Check Table 검증도 화면(Dynpro) 입력에서만 동작합니다. 프로그램의 직접 INSERT/UPDATE나 인터페이스(BDC 등)는 우회되므로 별도 검증 로직이 필요합니다.
  • 표준 재사용: 표준 Domain·Data Element에는 이미 Value Table이 지정된 경우가 많습니다. 새로 만들기 전에 표준을 먼저 확인하세요.
Modern ABAP / ABAP Cloud(RAP)에서는?

최신 S/4HANA·ABAP Cloud(RAP)에서도 Domain의 Value Table 속성은 그대로 유지되어 데이터 모델의 기초 메타데이터로 쓰입니다. 다만 DDIC Foreign Key는 화면 에러를 띄우는 역할에서 물러나, CDS View의 연관(association)을 추론·문서화하는 뼈대로 사용됩니다. 실제 강한 유효성 검사는 RAP의 Behavior Definition(BDEF) 안의 validation 로직이 백엔드에서 담당합니다.

7. 미니 실습: 역할 구분해서 말로 설명하기 🧪

✍️

실습 과제

  1. 항공사 코드 Domain에 Value Table로 SCARR을 적었다고 가정합니다. 이 상태에서 예약 화면에 XXX를 넣으면 어떻게 되는지 적습니다.
  2. 이번엔 예약 테이블의 항공사 코드 필드에 Foreign Key를 걸어 SCARR을 Check Table로 만들었습니다. 같은 XXX를 넣으면 어떻게 달라지는지 적습니다.
  3. “Value Table과 Check Table은 보통 같은 테이블인데 역할만 다르다”를 자신의 비유로 한 문장으로 표현해 봅니다.

완료 조건: “Value Table은 Domain의 정보/제안, Check Table은 필드 Foreign Key의 검증”이라고 막힘없이 구분해 말할 수 있으면 성공입니다.

9. 확인 퀴즈 ✅

  1. Value Table은 어느 레벨(Domain / 테이블 필드)에 지정되나요?
  2. Domain에 Value Table만 등록하면 입력 검증이 동작하나요?
  3. Foreign Key를 만들 때 Value Table은 어떤 역할을 하나요?
  4. Value Table과 Check Table은 서로 다른 물리 테이블인가요?
정답/해설 보기
  1. Domain 레벨입니다(Value Range 탭). Check Table은 테이블 필드의 Foreign Key에 붙습니다.
  2. 아니요. Value Table은 정보 제공일 뿐 검증 권한이 없습니다. Foreign Key를 걸어야 검증됩니다.
  3. Check Table 자동 제안의 출발점입니다. 시스템이 Domain의 Value Table을 보고 Check Table로 제안합니다.
  4. 보통 아닙니다. 대개 같은 마스터 테이블을 가리키며, 붙는 위치·역할에 따라 이름만 달라집니다.
