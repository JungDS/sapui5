학습 목표

지난 Lesson에서 Internal Table의 키와 성능 관점을 살펴봤습니다. 이번에는 구조 안에 또 다른 테이블이나 긴 문자열이 들어가는 Deep Structure, Nested Internal Table, String Component 개념을 소개합니다.

1. Structure가 항상 납작한 것은 아니다 🧭

Chapter 1에서 Structure는 여러 필드를 묶은 한 줄 타입이라고 배웠습니다. 처음에는 id, name, score처럼 납작한 필드만 생각하면 됩니다.

하지만 실제 업무 데이터는 더 복잡합니다. 주문 한 건 안에 여러 품목 줄이 들어가거나, 설명 필드가 길이가 자유로운 문자열일 수 있습니다. 이런 경우 구조 안에 Internal Table이나 String 같은 깊은 컴포넌트가 들어갑니다.

Deep Structure는 구조 안에 단순 값만 있는 것이 아니라, 문자열·내부 테이블 같은 깊은 데이터가 포함된 구조입니다.

2. Flat Structure와 Deep Structure 비교 🧱

Flat Structure는 각 컴포넌트가 고정 길이 문자, 숫자, 날짜처럼 단순한 값으로 구성된 구조입니다. 반면 Deep Structure는 컴포넌트 중 하나 이상이 동적 길이 문자열, Internal Table, Reference처럼 내부에 더 깊은 구조를 가질 수 있습니다.

  • Flat Structure: 학생 ID, 이름, 점수처럼 한 줄 안의 단순 칸들
  • Deep Structure: 주문 헤더 안에 품목 목록 테이블이 들어 있는 구조
  • String Component: 길이가 고정되지 않은 설명·메모 필드
  • Nested Internal Table: 구조의 한 필드가 다시 여러 줄 표인 형태

초심자 단계에서는 “구조 안에 또 다른 표나 유동적인 데이터가 들어가면 Deep해진다”라고 기억하면 충분합니다.

REPORT zdeep_structure_basic.

TYPES: BEGIN OF ty_item,
         product TYPE char20,
         amount  TYPE i,
       END OF ty_item.

TYPES tt_items TYPE STANDARD TABLE OF ty_item WITH DEFAULT KEY.

TYPES: BEGIN OF ty_order,
         order_id TYPE char10,
         note     TYPE string,
         items    TYPE tt_items,
       END OF ty_order.

DATA: ls_order TYPE ty_order,
      ls_item  TYPE ty_item.

ls_order-order_id = 'O-100'.
ls_order-note = '첫 주문 메모입니다.'.

ls_item-product = 'BOOK'.
ls_item-amount = 2.
APPEND ls_item TO ls_order-items.

ty_order 구조 안에는 note TYPE string과 items TYPE tt_items가 있습니다. items는 주문 한 건 안에 들어 있는 품목 목록 Internal Table입니다.

Flat Structure는 모든 칸이 단순 값이지만, Deep Structure는 items처럼 칸 하나가 통째로 또 다른 표(또는 string 같은 가변 길이 데이터)입니다. 마트료시카 인형처럼 “열어보면 또 구조가 나오는” 모양입니다.

4. Deep Structure는 왜 필요할까? 📦

실제 업무 화면이나 API 데이터는 “헤더 1건 + 상세 여러 건” 모양이 많습니다. 주문 헤더와 주문 품목, 전표 헤더와 전표 라인, ALV의 행별 스타일 정보처럼 한 데이터 안에 하위 목록이 붙는 경우가 있습니다.

이번 Lesson의 범위

Deep Structure의 개념만 소개합니다. ALV 셀 색상/스타일처럼 복잡한 구현은 Chapter 19에서 더 정확히 다룹니다.

Deep Structure는 데이터를 현실에 가깝게 표현할 수 있지만, 복사·초기화·출력·디버깅이 Flat Structure보다 복잡해질 수 있습니다.

5. 정상 흐름과 오류 흐름으로 확인하기 🔎

  • ✅ 정상 흐름: 구조 안의 Internal Table 컴포넌트에 APPEND로 하위 줄을 추가할 수 있습니다.
  • ✅ 문자열 사용: string 컴포넌트는 길이가 고정되지 않은 설명에 편리합니다.
  • ❌ 단순 WRITE 착각: Deep Structure 전체를 그대로 WRITE하기는 어렵습니다. 필요한 컴포넌트를 꺼내 출력해야 합니다.
  • ❌ 초기화 누락: 구조를 재사용할 때 내부 테이블 컴포넌트까지 비워졌는지 확인해야 합니다.
  • ❌ 과한 중첩: 너무 깊은 구조는 디버깅과 유지보수를 어렵게 만들 수 있습니다.

미니 실습으로 ls_item을 하나 더 만들어 ls_order-items에 APPEND해보세요. 디버거에서 주문 한 건 안에 품목 2줄이 들어 있는지 확인합니다.

6. 실무에서 조심해야 할 점 🚨

⚠️

Deep Structure는 편하지만 무거울 수 있습니다

구조 안에 Internal Table이 들어가면 데이터 표현력은 좋아지지만, 복사 비용과 메모리 사용량도 커질 수 있습니다. 큰 Deep Structure를 반복해서 복사하는 코드는 성능에 영향을 줄 수 있습니다.

Deep Structure는 강력한 모델링 도구입니다. 다만 처음부터 복잡하게 설계하기보다, 실제 업무 데이터의 부모-자식 관계가 분명할 때 사용하는 것이 좋습니다.

7. 미니 실습: 주문 안에 품목 채우기 🧪

✍️

실습 과제

  1. 예제 zdeep_structure_basic을 완성해 주문 O-100에 품목 BOOK 외 2개를 더 APPEND합니다.
  2. LOOP AT ls_order-items INTO ls_item.으로 품목 목록을 출력합니다.
  3. 주문을 여러 건 담는 lt_orders TYPE STANDARD TABLE OF ty_order를 선언하고, 주문 2건(각각 품목 포함)을 담아봅니다.
  4. 바깥 LOOP(주문)와 안쪽 LOOP(품목)를 중첩해 “주문 → 품목들” 형태로 출력합니다.

완료 조건: 중첩 LOOP로 헤더 1건 + 상세 N건 구조를 출력하고, 어느 변수가 어느 계층을 가리키는지 설명할 수 있으면 성공입니다.

9. 확인 퀴즈와 정답/해설 ✅

  1. Flat Structure와 Deep Structure를 가르는 기준은 무엇인가요?
  2. ls_order-items에 품목을 추가하는 문장은 무엇인가요?
  3. Deep Structure가 편리한데도 “복사 비용”을 조심하라는 이유는 무엇인가요?
정답/해설 보기
  1. 구성 요소에 단순 값만 있는지(Flat), 내부 테이블이나 string처럼 가변 길이 데이터가 들어 있는지(Deep)입니다.
  2. APPEND ls_item TO ls_order-items.처럼 구조의 테이블 필드를 경로로 지정해 APPEND합니다.
  3. 한 건을 복사할 때 안에 든 테이블 전체가 함께 복사될 수 있기 때문입니다. 품목이 수천 줄인 주문을 복사하면 보기보다 큰 메모리·시간 비용이 듭니다.

10. 한눈에 정리 🏁

📝

Deep Structure 핵심

  • Deep Structure는 구조 안에 문자열, Internal Table 같은 깊은 컴포넌트가 있는 구조입니다.
  • Nested Internal Table은 구조 필드 안에 들어간 내부 테이블입니다.
  • String Component는 길이가 유동적인 문자열 필드입니다.
  • 헤더-아이템 관계 같은 업무 데이터 표현에 유용합니다.
  • 복사, 초기화, 디버깅, 메모리 사용이 복잡해질 수 있어 주의합니다.
