학습 목표

"이 사용자가 이 데이터를 봐도 되는가"를 확인하는 AUTHORITY-CHECK와, "입력한 값이 실제로 존재하는가"를 확인하는 마스터 존재 검증을 배웁니다. 안전한 리포트의 기본기를 다지며 Chapter를 마무리합니다.

1. 지난 시간 연결: 동작하는 것과 안전한 것은 다르다 🛡️

지금까지 만든 리포트는 잘 동작합니다. 그런데 실무에서는 한 가지가 더 필요합니다. 바로 보안입니다. "이 데이터를 이 사람이 봐도 되나?"를 확인하지 않으면, 권한 없는 사용자가 민감한 데이터를 조회할 수 있습니다.

또 "입력한 회사코드가 진짜 존재하나?" 같은 마스터 존재 검증도 데이터 정합성을 위해 중요합니다.

2. AUTHORITY-CHECK로 권한 확인 ✍️

AUTHORITY-CHECK는 현재 사용자가 특정 작업에 대한 권한을 가졌는지 검사합니다. 보통 검증 단계나 조회 직전에 둡니다.

ABAP
1
2
3
4

7 
AUTHORITY-CHECK OBJECT 'F_BKPF_BUK'
  ID 'BUKRS' FIELD p_bukrs
  ID 'ACTVT' FIELD '03'.        "03 = 조회(Display)

IF sy-subrc <> 0.
  MESSAGE '해당 회사코드를 조회할 권한이 없습니다.' TYPE 'E'.
ENDIF.
  • OBJECT: 검사할 권한 객체(Authorization Object).
  • ID ... FIELD: 검사할 값(여기서는 회사코드와 활동 유형).
  • sy-subrc = 0: 권한 있음. 0이 아니면 권한 없음 → 막습니다.

3. 마스터 존재 검증 🔍

입력값이 형식상 맞아도, 실제 마스터 데이터에 없으면 조회가 헛돕니다. 그래서 조회 전 존재 여부를 확인합니다(Chapter 13의 Lesson 4에서 배운 검증과 같은 맥락).

ABAP
1
2
3
4
5
6 
SELECT SINGLE bukrs FROM t001
  INTO @DATA(lv_dummy)
  WHERE bukrs = @p_bukrs.
IF sy-subrc <> 0.
  MESSAGE '존재하지 않는 회사코드입니다.' TYPE 'E'.
ENDIF.
💡

두 검증의 역할 구분

  • 존재 검증: "그 값이 시스템에 있는가?"
  • 권한 검증: "그 값을 이 사람이 봐도 되는가?"

둘 다 통과해야 안전하게 조회할 수 있습니다.

4. 존재 검증과 권한 검증 시각화 🔐

"값이 있나?"와 "봐도 되나?"는 다른 질문

존재 검증
질문입력한 회사코드가 T001에 있는가?
대표 방식SELECT SINGLE로 기준 마스터 확인
실패 시존재하지 않는 값이므로 입력 수정 요청
권한 검증
질문정훈영 사용자가 이 회사코드를 조회해도 되는가?
대표 방식AUTHORITY-CHECK 후 sy-subrc 확인
실패 시보안상 조회 차단 및 안내

값이 실제로 존재해도 권한이 없으면 막아야 하고, 권한이 있어도 값이 존재하지 않으면 조회할 수 없습니다. 운영 리포트는 두 문을 모두 통과해야 안전합니다.

5. 정상 흐름과 오류 흐름 🔍

  • ✅ 정상: 존재·권한 모두 통과 → 안심하고 조회 진행.
  • ❌ 권한 검증 누락: 동작은 하지만, 보안 감사에서 큰 문제로 지적됩니다. 운영 리포트에서는 거의 필수입니다.
  • ❌ 매번 메시지 'E'만: 너무 빡빡하면 사용성이 떨어질 수 있으니, 상황에 맞는 메시지 타입과 안내를 고릅니다.

6. 실무에서 조심할 점 🚨

⚠️

권한 검사는 "있는지"가 아니라 "통과했는지"로 판단

AUTHORITY-CHECK를 적어두기만 하고 sy-subrc 결과를 확인하지 않으면, 검사한 의미가 없습니다. 반드시 결과를 보고 막아야 합니다. 또 어떤 권한 객체를 써야 하는지는 모듈·테이블마다 다르니, 보안 담당자나 표준 가이드를 참고하는 것이 안전합니다.

7. 미니 실습: 존재와 권한을 둘 다 막기 🧪

✍️

실습 과제

정훈영 사원의 회사코드 조회 리포트에 두 단계 검증을 넣어 보세요. 먼저 SELECT SINGLE로 회사코드 존재 여부를 확인하고, 이어서 AUTHORITY-CHECK로 조회 권한을 확인합니다.

완료 조건: 존재하지 않는 회사코드, 존재하지만 권한 없는 회사코드, 존재하고 권한도 있는 회사코드의 세 케이스를 나누어 어떤 메시지와 흐름이 나와야 하는지 설명할 수 있어야 합니다.

8. 공식 문서로 더 확인하기 🔗

  • SAP Help Portal: AUTHORITY-CHECK OBJECT - 권한 객체와 필드 값을 검사하는 구문을 확인합니다.
  • SAP Help Portal: SELECT SINGLE - 마스터 존재 여부 확인에 쓰는 단건 조회 문법을 확인합니다.
  • SAP Help Portal: MESSAGE - 검증 실패 시 사용자에게 어떤 타입으로 알릴지 판단합니다.

9. 확인 퀴즈와 정답/해설 🧩

  1. 존재 검증과 권한 검증은 각각 어떤 질문에 답하는 단계인가요?
  2. AUTHORITY-CHECK를 실행한 뒤 반드시 확인해야 하는 시스템 필드는 무엇인가요?
  3. 운영 리포트에서 권한 검사를 생략하면 어떤 리스크가 생기나요?
정답/해설 보기
  1. 존재 검증은 "그 값이 시스템에 있는가?", 권한 검증은 "현재 사용자가 그 값을 조회해도 되는가?"를 확인합니다.
  2. sy-subrc입니다. 0이면 권한 통과, 0이 아니면 실패로 보고 적절히 막아야 합니다.
  3. 권한 없는 사용자가 민감 데이터를 볼 수 있고, 보안 감사나 운영 사고로 이어질 수 있습니다. 동작 여부와 보안 적합성은 별개입니다.
