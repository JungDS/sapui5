학습 목표

지난 Lesson에서 SORT로 Internal Table을 정렬했습니다. 이번에는 정렬된 데이터를 전제로 BINARY SEARCH를 사용해 검색하는 흐름을 배웁니다. 핵심은 Sorted Data와 SY-SUBRC 확인입니다.

1. 왜 정렬 다음에 BINARY SEARCH가 나올까? 🧭

READ TABLE은 Internal Table에서 원하는 한 줄을 찾는 문법입니다. 그런데 줄이 많아질수록 처음부터 하나씩 찾는 방식은 느려질 수 있습니다. 그래서 정렬된 데이터에서는 더 효율적인 검색 방식인 BINARY SEARCH를 사용할 수 있습니다.

BINARY SEARCH는 정렬된 목록에서 가운데를 기준으로 범위를 계속 반씩 줄여가며 찾는 방식입니다. 전화번호부가 이름순으로 정렬되어 있을 때 중간쯤을 펴고 앞쪽/뒤쪽을 판단하는 느낌과 비슷합니다.

BINARY SEARCH는 빠를 수 있지만, 정렬이 맞지 않으면 결과를 믿기 어렵습니다.

2. 기본 구조: SORT 후 READ TABLE 🔍

ABAP
1
2
3
4
5 
SORT lt_students BY id.

READ TABLE lt_students INTO ls_student
  WITH KEY id = 'A02'
  BINARY SEARCH.

순서는 반드시 먼저 정렬, 그다음 검색입니다. 여기서는 id 기준으로 찾기 때문에 id 기준으로 정렬해둡니다.

  • SORT lt_students BY id: 검색 기준과 맞는 정렬을 준비합니다.
  • WITH KEY id = 'A02': 찾을 조건을 지정합니다.
  • BINARY SEARCH: 정렬된 상태를 이용해 빠르게 찾습니다.
  • sy-subrc: 검색 성공/실패를 확인합니다.

REPORT zbinary_search_basic.

TYPES: BEGIN OF ty_student,
         id    TYPE char3,
         name  TYPE char20,
         score TYPE i,
       END OF ty_student.

DATA: lt_students TYPE STANDARD TABLE OF ty_student,
      ls_student  TYPE ty_student.

ls_student-id = 'A03'. ls_student-name = 'Sora'. ls_student-score = 95.
APPEND ls_student TO lt_students.

CLEAR ls_student.
ls_student-id = 'A01'. ls_student-name = 'Mina'. ls_student-score = 90.
APPEND ls_student TO lt_students.

CLEAR ls_student.
ls_student-id = 'A02'. ls_student-name = 'Jun'. ls_student-score = 85.
APPEND ls_student TO lt_students.

SORT lt_students BY id.

READ TABLE lt_students INTO ls_student WITH KEY id = 'A02' BINARY SEARCH.
IF sy-subrc = 0.
  WRITE: / '검색 성공:', ls_student-id, ls_student-name.
ELSE.
  WRITE: / '검색 실패'.
ENDIF.

처음 APPEND 순서는 A03, A01, A02입니다. 하지만 검색 전에 SORT lt_students BY id.를 실행했기 때문에 BINARY SEARCH가 기대하는 정렬 상태가 됩니다.

4. 정렬 기준이 틀리면 왜 위험할까? ⚡

BINARY SEARCH는 “이미 올바르게 정렬되어 있다”는 전제 위에서 움직입니다. 그런데 id로 찾으면서 score로 정렬해두면, 검색 알고리즘이 잘못된 방향으로 범위를 줄일 수 있습니다.

ABAP
1
2 
SORT lt_students BY score.
READ TABLE lt_students INTO ls_student WITH KEY id = 'A02' BINARY SEARCH.

위 코드는 문법상 보일 수는 있지만, 검색 기준과 정렬 기준이 맞지 않아 결과를 신뢰하기 어렵습니다. 초심자 단계에서는 “BINARY SEARCH 앞에는 같은 기준의 SORT가 있어야 한다”라고 강하게 기억해두세요.

⚠️

정렬이 안 맞으면 조용히 틀릴 수 있습니다

문법 오류가 나지 않는다고 논리까지 맞는 것은 아닙니다. BINARY SEARCH의 가장 무서운 점은 “실행은 되는데 검색 결과가 틀릴 수 있다”는 점입니다.

5. 정상 흐름과 오류 흐름으로 확인하기 🔎

  • ✅ 정상 흐름: 검색 키 기준으로 정렬한 뒤 BINARY SEARCH를 실행하고 sy-subrc = 0을 확인합니다.
  • ❌ 정렬 누락: SORT 없이 BINARY SEARCH를 쓰면 결과를 믿을 수 없습니다.
  • ❌ 기준 불일치: score로 정렬하고 id로 검색하면 논리 오류가 됩니다.
  • ❌ 검색 실패 미처리: sy-subrc 확인 없이 Work Area를 사용하면 잘못된 출력으로 이어질 수 있습니다.

미니 실습으로 SORT 기준을 일부러 score로 바꿔보고, 다시 id로 돌려보세요. BINARY SEARCH는 정렬 기준과 검색 기준이 한 팀이어야 한다는 감각을 잡는 것이 목표입니다.

6. 실무에서 조심해야 할 점 🚨

최신 ABAP에서는 SORTED TABLE, HASHED TABLE, 명시적 Table Key를 활용해 검색 의도를 더 분명히 표현할 수 있습니다. 기존 코드에서는 READ TABLE ... BINARY SEARCH를 많이 만나므로 읽을 수 있어야 하지만, 새 설계에서는 테이블 종류와 키를 먼저 검토하는 습관이 좋습니다.

특히 정렬 기준과 검색 기준이 코드상 멀리 떨어져 있으면 유지보수자가 실수하기 쉽습니다. BINARY SEARCH를 쓴다면 정렬 위치와 검색 위치를 함께 리뷰해야 합니다.

7. 한눈에 정리 🏁

📝

BINARY SEARCH 핵심

  • BINARY SEARCH는 정렬된 데이터에서 범위를 줄여가며 찾는 방식입니다.
  • 검색 키 기준으로 먼저 SORT한 뒤 사용해야 합니다.
  • 정렬 기준과 검색 기준이 다르면 결과를 신뢰하기 어렵습니다.
  • READ TABLE 뒤에는 SY-SUBRC로 성공/실패를 확인합니다.
  • 새 설계에서는 SORTED/HASHED TABLE이나 명시적 키도 함께 검토합니다.
