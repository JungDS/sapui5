학습 목표

여러 클래스가 같은 "약속"을 공유하게 하는 인터페이스(Interface)를 배웁니다. 인터페이스가 어떻게 다형성(Polymorphism)의 기초가 되는지 익힙니다.

1. 지난 시간 연결: 모양은 같게, 속은 다르게 🎭

"출력하다"라는 기능을 생각해 봅시다. PDF로 출력하는 클래스, 엑셀로 출력하는 클래스가 있다면, 둘 다 print( )라는 메서드를 가지면 좋겠죠. 쓰는 쪽은 "출력해줘"라고만 하고, 실제 방식은 각 클래스가 알아서.

이렇게 "이런 메서드를 반드시 가진다"는 약속(규격)만 정의하는 것이 인터페이스입니다.

2. 인터페이스 = 메서드 약속 ✍️

" 약속 정의 (구현은 없음)
INTERFACE zif_printer PUBLIC.
  METHODS print.
ENDINTERFACE.

" 약속을 지키는 클래스들
CLASS zcl_pdf DEFINITION PUBLIC.
  PUBLIC SECTION.
    INTERFACES zif_printer.        "이 약속을 따른다
ENDCLASS.
CLASS zcl_pdf IMPLEMENTATION.
  METHOD zif_printer~print.
    " PDF 방식으로 출력
  ENDMETHOD.
ENDCLASS.
💡

비유: 충전 단자 규격(USB-C)

인터페이스는 USB-C 규격 같은 거예요. 삼성·애플·LG가 각자 다르게 만들어도, 모두 USB-C 규격을 따르면 같은 충전기로 충전됩니다. "규격을 따른다"는 약속이 핵심이죠.

3. 다형성 — 같은 명령, 다른 동작 🎭

인터페이스 타입으로 객체를 다루면, 쓰는 쪽은 어느 클래스인지 몰라도 같은 메서드를 부를 수 있습니다. 이것이 다형성입니다.

DATA: lo_printer TYPE REF TO zif_printer.

lo_printer = NEW zcl_pdf( ).
lo_printer->print( ).      "PDF로 출력

lo_printer = NEW zcl_excel( ).
lo_printer->print( ).      "엑셀로 출력 (같은 호출, 다른 동작)

쓰는 코드는 print( ) 하나면 끝. 새 출력 방식(클래스)이 늘어도 쓰는 코드는 안 바뀝니다.

4. 정상 흐름과 오류 흐름 🔍

  • ✅ 정상: 여러 클래스가 한 인터페이스를 구현 → 인터페이스 타입으로 일관되게 다룸.
  • ❌ 오류: INTERFACES로 선언만 하고 약속된 메서드(zif_printer~print)를 구현 안 함 → 활성화 오류. 약속은 반드시 지켜야 합니다.

5. 실무에서 조심할 점 🚨

⚠️

인터페이스는 "확장에 강한 설계"의 핵심

인터페이스를 쓰면 새 기능(새 클래스)을 추가해도 기존 코드를 거의 안 고쳐도 됩니다. 이는 RAP·테스트(Mock 객체)·디자인 패턴(THEORY 이후 실무)의 토대가 됩니다. 다만 처음부터 모든 것을 인터페이스로 만들 필요는 없습니다. "여러 구현이 생길 가능성이 있는가?"가 보일 때 도입하면 충분합니다.

6. 한눈에 정리 🏁

📝

오늘의 핵심만 딱 잡기

  • 인터페이스는 "이런 메서드를 가진다"는 약속(규격)만 정의합니다.
  • 여러 클래스가 INTERFACES로 같은 약속을 구현합니다.
  • 같은 호출에 클래스마다 다르게 동작하는 것이 다형성입니다.
  • 새 구현이 늘어도 쓰는 코드는 안 바뀌어 확장에 강합니다.
