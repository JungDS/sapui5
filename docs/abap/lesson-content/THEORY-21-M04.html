학습 목표

데이터 모델에 "무엇을 할 수 있는가"(생성·수정·삭제 등)를 정의하는 Behavior Definition(BDEF)을 배웁니다. 읽기 전용 모델이 트랜잭션 가능한 Business Object로 바뀌는 지점을 익힙니다.

1. 지난 시간 연결: 보기만 하던 모델에 "행동"을 ✍️

지금까지의 CDS(ZI_/ZC_)는 데이터를 보여주기만 했습니다. 이제 "이 데이터를 생성·수정·삭제할 수 있다"는 동작을 정의합니다. 그 정의서가 Behavior Definition(BDEF)입니다.

BDEF를 붙이는 순간, CDS 모델은 트랜잭션 가능한 Business Object가 됩니다.

2. Behavior Definition 기본 ✍️

managed implementation in class zbp_i_travel unique;

define behavior for ZI_Travel alias Travel
persistent table ztravel
lock master
{
  create;          // 생성 가능
  update;          // 수정 가능
  delete;          // 삭제 가능

  field ( readonly ) travel_id;       // 키는 읽기 전용
  field ( mandatory ) agency_id;      // 필수 입력
}
  • managed: 표준 저장 로직(생성·수정·삭제·저장)을 RAP가 자동 처리하는 방식. 초보자에게 가장 쉬움.
  • create/update/delete: 허용할 표준 동작.
  • field ( readonly / mandatory ): 필드별 입력 규칙.
💡

managed vs unmanaged

managed는 저장 로직을 RAP가 알아서 해줘서(자동 운전) 빠릅니다. unmanaged는 기존 저장 로직(레거시 함수 등)에 직접 연결할 때 씁니다(수동 운전). 신규 개발은 보통 managed로 시작합니다.

3. lock과 authorization 한 줄 소개 🔐

  • lock master: 동시에 같은 데이터를 고치지 못하게 잠금(THEORY의 Lock 개념). RAP가 자동 관리.
  • authorization: 누가 이 동작을 할 수 있는지(권한). BDEF에 선언해 둘 수 있습니다.

4. 정상 흐름과 오류 흐름 🔍

  • ✅ 정상: BDEF로 create/update/delete + 필드 규칙 정의 → 트랜잭션 가능한 BO 완성.
  • ❌ 오류 1: 키 필드를 readonly로 안 막음 → 사용자가 키를 바꿔 데이터 정합성 붕괴.
  • ❌ 오류 2: managed인데 표준 흐름과 맞지 않는 특수 저장이 필요 → unmanaged나 추가 구현 검토.

5. 실무에서 조심할 점 🚨

⚠️

"무엇을 허용할지"를 명확히

BDEF는 곧 "이 데이터로 할 수 있는 일의 목록"입니다. 필요 없는 동작(예: 삭제)을 무심코 열어두면 사용자가 데이터를 지울 수 있습니다. 필드 규칙(readonly/mandatory)도 데이터 정합성의 1차 방어선입니다. "이 업무에서 정말 허용해야 하는 동작·입력인가?"를 따져 최소한으로 여세요.

6. 한눈에 정리 🏁

📝

오늘의 핵심만 딱 잡기

  • Behavior Definition(BDEF)이 CDS 모델에 동작을 부여해 Business Object로 만듭니다.
  • managed는 표준 저장을 RAP가 자동 처리(신규 권장).
  • create/update/delete와 field(readonly/mandatory)로 동작·입력을 통제합니다.
  • lock·authorization으로 동시성·권한도 선언합니다.
