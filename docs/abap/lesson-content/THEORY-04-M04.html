학습 목표

지난 Lesson에서 단일 검색 경로를 제공하는 Elementary Search Help를 배웠습니다. 그런데 같은 값을 “여러 방법”으로 찾고 싶을 때가 있죠. 이번 Lesson에서는 여러 Elementary를 하나로 묶어 여러 검색 경로(탭)를 제공하는 Collective Search Help의 기초를 잡습니다.

1. 지난 Lesson 연결: 검색 방법이 하나가 아니라면? 🤔

Elementary Search Help는 “한 가지 길”로만 값을 찾습니다. 하지만 실무에서 항공편 예약을 찾을 때 누군가는 도착지로, 누군가는 여행사로 검색하고 싶어 합니다. 자재·고객·사원처럼 큰 마스터 데이터일수록 “찾는 길”이 다양하죠.

Collective Search Help는 이런 여러 검색 경로를 하나로 묶어 사용자에게 탭으로 제공합니다. 한 필드에서 F4를 누르면 “도착지 기준 / 여행사 기준 …” 탭이 나란히 뜨는 식입니다.

Collective Search Help는 여러 Elementary Search Help를 담는 “컨테이너(폴더)”입니다. 자기 스스로 데이터를 읽지는 않습니다.

2. Collective = 여러 Elementary를 담는 컨테이너 📦

컨테이너와 그 안의 검색 경로들

Collective Search Help (컨테이너)
여러 검색 경로를 묶는 껍데기
Selection Method 없음
스스로 데이터 못 읽음
→
포함된 Elementary들
① 도착지 기준 (View A)
② 여행사 기준 (View B)
각자 Selection Method 있음

데이터를 실제로 읽는 건 안에 든 Elementary들입니다. Collective는 이들을 묶어 “여러 탭”으로 배포하는 역할만 합니다.

3. F4를 누르면? — 탭으로 갈라지는 검색 경로 🗂️

단일 Elementary가 붙은 필드는 검색 창 하나만 뜹니다. Collective가 붙은 필드는 상단에 탭이 여러 개 있는 다이얼로그가 뜨고, 탭을 바꿀 때마다 안의 Elementary가 교체되며 전혀 다른 조건으로 검색합니다.

예: 항공편 예약 찾기 F4 다이얼로그

조건도착 도시 = NEW YORK
경로도착지 기준 Elementary가 조회
결과뉴욕행 예약 목록
조건여행사 = 우리투어
경로여행사 기준 Elementary가 조회
결과그 여행사 예약 목록

같은 “예약 번호”를 찾더라도 접근 방식(탭)이 다릅니다. 위 탭을 눌러 경로가 바뀌는 느낌을 확인해 보세요.

4. Collective의 3계층 구성 🧱

Collective Search Help는 세 개의 논리적 계층으로 짜입니다.

  • ① Shared Interface (공유 인터페이스): 화면 필드와 값을 주고받는 대문(IMPORT/EXPORT 파라미터). Collective 전체의 입출구입니다.
  • ② Search Helps Included (포함된 검색 도움말): 컨테이너 안에 등록하는 여러 Elementary들. SAP 표준에 더해, 소스 수정 없이 고객 전용 경로를 덧붙이는 Append Search Help도 가능합니다.
  • ③ Parameter Mapping (파라미터 매핑): 공유 인터페이스의 파라미터와 각 Elementary의 파라미터를 서로 연결하는 작업.
⚠️

초심자 최대 함정: Parameter Mapping 누락

Collective의 공유 파라미터와 내부 Elementary 파라미터를 매핑하지 않으면, 사용자가 탭에서 값을 골라도 그 값이 화면 필드로 돌아오지 않습니다. “목록은 뜨는데 선택해도 안 채워져요”의 단골 원인이 바로 이 매핑 누락입니다.

5. 언제 Collective, 언제 Elementary? ⚖️

선택 기준

Elementary로 충분
  • 검색 경로가 하나면 충분
  • 예: 국가 코드를 국가명으로 찾기
  • 단순·고정된 조회
Collective가 필요
  • 접근 방식이 여러 가지
  • 예: 자재/고객/사원 (이름·부서·과거번호…)
  • 탭으로 경로 분리가 유용

큰 마스터 데이터일수록 “찾는 길”이 많아 Collective가 유리합니다.

💡

실무 팁: 당장 경로가 하나여도 Collective로 시작

지금은 검색 경로가 하나뿐이라도, Collective를 만들어 필드에 연결하고 그 안에 Elementary 1개만 넣어두는 방식을 권장합니다. 나중에 “검색 탭 하나 더요”라는 요청이 오면, 화면 프로그램 수정 없이 Collective에 Elementary 하나만 추가(Append)하면 되기 때문입니다.

6. 자주 하는 오해와 주의사항 🚨

⚠️

“Collective에 테이블/뷰를 직접 붙이면 알아서 합쳐 보여주겠지?”

불가능합니다. 데이터를 읽어오는 Selection Method 속성은 오직 Elementary에만 있습니다. Collective는 데이터를 직접 못 읽으므로, 반드시 테이블/뷰가 연결된 Elementary들을 포함시켜야 동작합니다.

ABAP Cloud / Clean Core에서는 어떻게 달라지나?

전통적 DDIC 기반 Search Help(Elementary·Collective)는 SAP GUI·Dynpro에 강하게 종속된 객체입니다. ABAP Cloud(Clean Core) 환경에서는 이 클래식 DDIC Search Help 문법이 지원되지 않습니다(obsolete). 대신 CDS 기반 Search Help로 새로 구축합니다. 기존 DDIC/Function Module 검색 도움말을 클라우드에서 재사용하려면 직접 호출하지 말고 Wrapper CDS View나 Custom Entity로 감싸서 제공해야 합니다.

7. 미니 실습: 예약 검색 Collective 설계 🧪

✍️

실습 과제

  1. “예약 번호”를 찾는 두 가지 경로(도착지 기준, 여행사 기준)를 각각 Elementary로 상상하고 이름을 붙입니다.
  2. 이 둘을 묶는 Collective Search Help를 만든다면, 어떤 계층(①공유 인터페이스 ②포함 ③매핑) 작업이 필요한지 순서대로 적습니다.
  3. “선택해도 값이 안 채워진다”면 어느 계층을 의심해야 하는지 한 줄로 답합니다.
  4. 지금 경로가 하나뿐인데도 Collective로 시작하면 좋은 이유를 자신의 말로 적습니다.

완료 조건: “Collective는 컨테이너, 데이터는 Elementary가 읽는다”와 “매핑이 있어야 값이 돌아온다”를 설명할 수 있으면 성공입니다.

9. 확인 퀴즈 ✅

  1. Collective Search Help는 스스로 데이터를 읽을 수 있나요?
  2. F4를 눌렀을 때 Collective는 화면에 무엇을 보여 주나요?
  3. 사용자가 탭에서 값을 골랐는데 화면에 안 채워진다면 무엇을 의심해야 하나요?
  4. 검색 경로가 지금 하나뿐이어도 Collective로 시작하면 좋은 이유는?
정답/해설 보기
  1. 아니요. Selection Method가 없어 직접 못 읽습니다. 안에 포함된 Elementary가 데이터를 읽습니다.
  2. 여러 검색 경로 탭이 있는 다이얼로그를 보여줍니다. 탭마다 다른 Elementary가 동작합니다.
  3. Parameter Mapping 누락을 의심합니다. 매핑이 있어야 선택값이 화면으로 돌아옵니다.
  4. 나중에 화면 수정 없이 Elementary를 추가(Append)해 검색 경로를 늘릴 수 있기 때문입니다.
