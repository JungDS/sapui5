학습 목표

이번 Lesson에서는 데이터를 실제 DB에 오래 저장하는 Transparent Table을 배웁니다. 지난 Lesson의 Structure와 무엇이 다른지, Key Field가 왜 필요한지, MANDT와 Client-Dependent가 SAP 데이터 분리에 어떤 역할을 하는지 잡습니다.

1. 한 줄 모양에서 데이터 창고로 넘어간다

Structure는 한 줄 데이터의 모양을 정의했지만, 데이터를 영구 저장하지는 않았습니다. 프로그램이 끝나면 Work Area의 값도 사라집니다. 반대로 Transparent Table은 ABAP Dictionary에서 정의하고 실제 데이터베이스에 데이터를 저장하는 대상입니다.

SAP Learning은 database table definition이 field list와 additional table properties를 가지고, 활성화 후 ABAP SQL이 접근할 수 있는 DB 테이블로 이어진다고 설명합니다. 그래서 Transparent Table은 단순한 필드 목록이 아니라 운영 데이터의 창고입니다.

Structure는 모양입니다. Transparent Table은 그 모양의 여러 줄을 오래 보관하는 저장소입니다.

2. Structure와 Transparent Table의 결정적 차이

둘 다 필드 목록처럼 보이기 때문에 처음에는 비슷해 보입니다. 하지만 “데이터베이스에 저장 공간을 만드는가?”라는 질문으로 바로 구분할 수 있습니다.

한 줄 타입과 DB 테이블 비교

Structure
  • 한 줄 데이터의 타입입니다.
  • DB에 물리 저장소를 만들지 않습니다.
  • Work Area, 파라미터, Table Type의 row type으로 자주 씁니다.
Transparent Table
  • DB에 저장되는 테이블 정의입니다.
  • 활성화 후 데이터를 읽고 쓸 대상이 됩니다.
  • Key, client dependency, technical settings까지 함께 고려합니다.

SELECT의 대상은 Transparent Table입니다. Structure는 INTO 쪽의 타입으로 쓰일 수는 있지만 FROM 대상이 아닙니다.

3. Field List는 Data Element 중심으로 만든다

Transparent Table의 각 열은 Table Field입니다. SAP Learning은 field list를 편집할 때 Data Element 사용을 권장하며, Domain을 field list에 직접 사용할 수 없다고 설명합니다. Domain은 Data Element 아래의 기술 기반입니다.

테이블 필드가 의미를 받는 흐름

Domain
타입, 길이, 값 범위
직접 테이블 필드 타입으로 쓰지 않음
→
Data Element
업무 의미, 라벨, F1 도움말
테이블 필드 타입으로 사용
→
Table Field
CARRID, CONNID, FLDATE
DB 테이블의 실제 열
직접 타입을 쓰면 항상 나쁠까?

항상 나쁘지는 않습니다. 최신 ADT 기반 테이블 정의에서는 내장 타입을 직접 쓰는 예도 있습니다. 다만 화면 라벨, F1 설명, 재사용 의미가 중요한 업무 필드는 Data Element를 먼저 검토하는 것이 안전합니다.

4. Key Field는 한 줄을 유일하게 찾는 기준이다

Transparent Table에는 각 row를 식별할 수 있는 Primary Key가 필요합니다. 이 Primary Key를 이루는 필드가 Key Field입니다. SAP Learning은 모든 database table에 primary key가 필요하고, key field는 field list의 시작 부분에 모여 있어야 한다고 설명합니다.

항공편 일정 테이블 키 설계

순서 필드 역할 Key?
1 MANDT 클라이언트 구분 Key
2 CARRID 항공사 코드 Key
3 CONNID 편명 Key
4 FLDATE 출발일 Key
5 PRICE 요금 일반 필드

같은 MANDT + CARRID + CONNID + FLDATE 조합은 한 테이블 안에서 두 번 존재할 수 없습니다.

Key Field 사이에 일반 필드를 넣어도 될까?

안 됩니다. SAP Learning 기준으로 key fields는 field list의 시작 부분에 함께 있어야 하며, key field 사이에 non-key field가 들어가면 안 됩니다. 초급 단계에서는 “키 먼저, 일반 필드 나중”으로 기억하세요.

5. MANDT는 클라이언트 칸막이다

SAP 업무 테이블에서 MANDT는 보통 첫 번째 Key Field입니다. 이것은 “이 row가 어느 client의 데이터인가?”를 표시합니다. SAP 공식 자료는 CLNT 타입 key field가 자동으로 client field로 취급되고, 기본 접근은 로그인 client로 제한된다고 설명합니다.

같은 시스템 안의 client 분리

Client 100
MANDT = 100
개발/교육 데이터
100번 로그인 사용자가 기본 조회
Client 200
MANDT = 200
테스트 데이터
200번 로그인 사용자가 기본 조회
Client-Independent
MANDT 없음
모든 client가 공유
초급 단계에서는 매우 신중
⚠️

MANDT는 회사 코드가 아닙니다

MANDT는 SAP client를 구분하는 시스템 필드입니다. 회사 코드 같은 업무 조직 필드와 섞어 외우면 안 됩니다. 대부분의 업무 데이터는 client-dependent를 기본 출발점으로 두고, client-independent는 명확한 공유 이유가 있을 때만 선택합니다.

6. 활성화와 Technical Settings까지 이어진다

Table Field와 Key를 채웠다고 끝이 아닙니다. Transparent Table은 실제 DB 저장 대상이므로 활성화와 Technical Settings가 중요합니다. M06에서 자세히 다루지만, 지금은 연결만 잡아둡니다.

Transparent Table 생성 흐름

1. Table 생성이름, 설명, delivery 성격을 정한다.
2. Field Listclient field, key field, 일반 field를 배치한다.
3. 타입 지정Data Element를 우선 검토하고 필요하면 직접 타입을 쓴다.
4. Technical Settings저장 특성, 크기, 버퍼링 같은 DB 운영 힌트를 확인한다.
5. Activate검사 통과 후 ABAP SQL이 접근할 수 있는 기준이 된다.
저장만 하면 DB 테이블이 생길까?

아닙니다. 저장은 비활성 버전 보관에 가깝습니다. 다른 객체와 프로그램이 믿고 쓰려면 활성화가 성공해야 합니다. 활성화 과정에서 테이블 정의와 관련 설정이 검사됩니다.

7. 운영 테이블 변경은 무겁게 본다

Transparent Table은 실제 데이터가 쌓이는 창고입니다. 그래서 운영 데이터가 들어간 뒤 키나 필드 길이를 바꾸는 것은 단순한 문구 수정이 아닙니다.

변경 위험도 감각

변경 위험도 이유
뒤쪽에 신규 일반 필드 추가 상대적으로 낮음 기존 key와 데이터 식별 기준을 크게 흔들지 않습니다.
필드 길이 줄이기 높음 기존 값이 새 길이에 맞지 않을 수 있습니다.
Key Field 추가/변경 매우 높음 row 유일성 기준과 기존 데이터 중복 여부가 바뀝니다.
버퍼링은 무조건 성능을 올릴까?

아닙니다. 자주 바뀌는 트랜잭션 데이터에 버퍼링을 켜면 최신성 관리와 무효화 비용 때문에 오히려 문제가 될 수 있습니다. 버퍼링은 M06에서 Technical Settings와 함께 따로 판단합니다.

실습 과제

  1. 테이블 이름을 정합니다. 예: ZSFLIGHT_SCHEDULE
  2. MANDT를 첫 번째 key로 둘지 결정하고 이유를 적습니다.
  3. 항공편 한 줄을 유일하게 찾을 key 조합을 적습니다.
  4. 일반 필드 2개를 적습니다. 예: PRICE, CURRENCY
  5. 같은 key 조합으로 두 번 저장하려는 오류 케이스를 설명합니다.

완료 조건: key field와 일반 field가 구분되어 있고, 중복 key 오류가 왜 필요한지 설명할 수 있으면 성공입니다.

10. 확인 퀴즈

  1. Structure와 Transparent Table의 가장 큰 차이는 무엇인가요?
  2. Primary Key를 이루는 필드는 무엇이라고 부르나요?
  3. Key Field는 field list의 어디에 있어야 하나요?
  4. MANDT는 회사 코드와 같은 업무 필드인가요?
  5. 운영 데이터가 쌓인 뒤 key를 바꾸는 일이 왜 위험한가요?
정답/해설 보기
  1. 영구 저장 여부입니다. Structure는 타입이고, Transparent Table은 DB 저장 대상입니다.
  2. Key Field입니다. Key Field 조합은 table row를 유일하게 식별합니다.
  3. Field list의 시작 부분에 모여 있어야 합니다. key 사이에 non-key field를 끼우면 안 됩니다.
  4. 아니요. MANDT는 SAP client를 구분하는 시스템 필드입니다. 회사 코드와 다릅니다.
  5. row 유일성 기준이 바뀌기 때문입니다. 기존 데이터가 새 key 기준에서 중복되거나 변환에 실패할 수 있습니다.
