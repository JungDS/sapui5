학습 목표

빈 그릇이 아니라 데이터를 실제로 영구 보관하는 Transparent Table(투명 테이블)을 직접 설계해 봅니다. 테이블에서 가장 중요한 키 필드(Key Field)의 역할과, 거의 모든 업무 테이블 맨 앞에 철벽처럼 세워지는 클라이언트 필드(MANDT)의 존재 이유를 완벽히 이해합니다.

1. 지난 시간 요약 & 진짜 보관 창고가 필요해! 🤔

이전 Lesson에서 배운 Structure(구조체)는 여러 필드를 하나로 묶어주긴 하지만, 데이터를 잠시 담았다 비우는 '빈 그릇(임시 메모리)'일 뿐 영구적으로 저장하지는 않는다고 배웠죠.

하지만 회사 생활을 생각해 보세요. 어제 가입한 고객 정보, 한 달 전에 팔린 비행기 티켓 기록이 컴퓨터를 껐다 켰다고 날아가면 큰일 나겠죠? 그래서 우리는 드디어 데이터를 진짜 데이터베이스 하드디스크에 영구히 저장해 주는 거대한 창고를 만들 때가 되었습니다!

2. Transparent Table (투명 테이블) 이란? 🏬

데이터를 영구히 보관하는 이 창고를 SAP에서는 Transparent Table(투명 테이블)이라고 부릅니다.

왜 하필 '투명'이라는 독특한 이름을 쓸까요? 개발자가 DDIC(SE11이나 ADT 화면)에서 테이블의 컬럼 모양을 예쁘게 디자인하고 활성화 버튼을 누르면, 시스템 내부적으로 진짜 데이터베이스(Oracle, SAP HANA 등)에 완벽하게 똑같은 모양을 가진 1개의 물리적 테이블을 몰래 만들어줍니다. 즉, DDIC에 그린 설계도와 진짜 DB의 모습이 1:1로 유리창처럼 투명하게 비친다고 해서 붙은 이름입니다!

3. 키 필드(Key Field): 유일함을 증명하라 🔑

테이블을 만들 때 가장 신중하게 설계해야 하는 것이 바로 키 필드(Key Field)입니다. 화면에서 필드 옆에 체크박스(Key)를 콕 찍어주는 순간, 엄청난 마법이 일어납니다.

키 필드의 역할은 "이 테이블의 수만 줄 데이터 중에서, 이 줄(Row)은 세상에 단 하나뿐이야!"라고 구분 짓는 기준점이 되는 것입니다. (마치 학교의 '학번'이나 국가의 '주민등록번호'처럼요!)

💡

키 설계 예시 (항공편 테이블)

만약 MANDT(클라이언트) + CARRID(항공사) + CONNID(편명) + FLDATE(날짜) 이렇게 4개를 키로 묶어 잡았다고 해봅시다.

그러면 시스템은 "대한항공(KE)의 123편, 2026년 12월 25일 출발 데이터"는 이 거대한 창고 안에 절대 두 줄이 생길 수 없도록(중복 불가) 꽉 막아버립니다. 똑같은 데이터를 한 번 더 넣으려 하면 튕겨내버리죠!

키의 위치: 키 필드는 아무 데나 두면 안 됩니다. 항상 테이블 정의의 맨 위쪽(실제 표에서는 가장 왼쪽)에 옹기종기 모여 있어야 합니다. 중간에 일반 필드가 섞여 있으면 에러가 납니다.

4. 클라이언트(MANDT): 한 시스템 지붕 아래 칸막이 🏢

거의 모든 SAP 업무 테이블을 열어보면, 제일 첫 번째 줄에 약속이나 한 듯이 MANDT (클라이언트 필드)가 떡하니 자리 잡고 있습니다. 이건 왜 넣는 걸까요?

아주 큰 건물(하나의 SAP 시스템) 안에 여러 계열사나 테스트 환경이 동시에 입주해 있다고 상상해 보세요 (100번 회사는 삼성전자, 200번 회사는 삼성물산 이런 식). 이때 MANDT 필드를 테이블 맨 앞에 두면, SAP가 알아서 보이지 않는 칸막이를 쳐줍니다!

  • ✅ 자동 필터링의 마법: 개발자가 100번 회사 아이디로 로그인해서 "데이터 다 가져와!"라고 코딩하면, 시스템은 진짜 다 가져오지 않고 조용히 뒤에서 "MANDT가 100인 것만 줘"라고 조건을 알아서 붙여줍니다. 다른 회사 데이터를 볼래야 볼 수가 없게 되죠!

이렇게 MANDT가 맨 앞에 있는 테이블을 우리는 Client-Dependent(클라이언트 종속) 테이블이라고 부릅니다. (아주 드물게 회사 구분 없이 모두가 공유해야 하는 데이터는 MANDT를 뺀 Client-Independent 테이블로 만들기도 합니다.)

5. 실무에서 조심해야 할 점 🚨

⚠️

운영 테이블의 키나 필드 길이를 함부로 바꾸면 지옥이 열립니다

처음 테이블을 만들 때는 마음대로 고쳐도 됩니다. 하지만 이미 실제 서비스에 적용되어(운영 서버) 진짜 데이터가 수백만 건 쌓인 테이블에서 키 필드를 중간에 추가/수정하거나, 필드의 길이를 확 줄여버리면 어떤 일이 벌어질까요?

SAP 시스템이 멘붕에 빠지면서 데이터를 억지로 맞추려다 테이블 변환(Conversion) 에러를 뿜어내고 기존 소중한 데이터를 다 날려버릴 수 있습니다! 운영 테이블은 가능하면 변경하지 말고, 정 필요하다면 맨 밑에 신규 일반 필드를 조심스럽게 추가하는 방식을 선택해야 합니다.

6. 한눈에 정리 🏁

📝

오늘의 요약

  • Transparent Table(투명 테이블)은 Structure와 달리 데이터를 DB에 영구적으로 보관하는 진짜 창고입니다.
  • 키 필드(Key Field)는 데이터가 중복되지 않도록 방어하는 유일한 식별자이며, 반드시 테이블 맨 위에 모여 있어야 합니다.
  • 테이블 맨 앞에 들어가는 MANDT(클라이언트)는 하나의 시스템 안에서 데이터를 회사별/환경별로 완벽하게 격리해 주는 마법의 칸막이입니다.
  • 데이터가 이미 쌓인 운영 테이블의 구조(특히 키나 길이)를 함부로 바꾸는 것은 시스템을 파괴하는 위험한 행동입니다.

자, 이제 우리는 튼튼한 데이터 창고의 설계도(모양과 키)를 완벽하게 그렸습니다.

하지만 앗! 아직 활성화 버튼을 누를 수가 없네요. 이 창고를 데이터베이스의 어느 구역에 지을지, 얼마나 크게 지을지 알려줘야 하거든요. 다음 Lesson 'Technical Settings와 데이터 확인 기초'에서 테이블 설정의 마지막 퍼즐을 맞추고, 직접 창고에 데이터를 집어넣어 보는 꿀잼 실습을 진행해 보겠습니다!
