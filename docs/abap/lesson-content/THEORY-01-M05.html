학습 목표

지난 Lesson의 Structure가 임시 그릇이었다면, 이번에는 데이터를 실제 DB에 오래 저장하는 Transparent Table을 배웁니다. 특히 중복을 막는 Key Field, 클라이언트별 데이터를 나누는 MANDT, 그리고 Client-Dependent 테이블의 감각을 잡습니다.

1. 지난 시간 연결: 그릇에서 창고로 넘어가기 🏬

이전 Lesson에서 Structure는 데이터를 영구 저장하지 않는다고 했습니다. Structure는 “항공편 한 줄은 이런 칸들로 구성됩니다”라고 알려주는 타입, 즉 그릇의 모양입니다. 프로그램이 끝나면 Work Area에 담긴 값도 사라집니다.

그런데 회사 시스템에는 사라지면 안 되는 데이터가 훨씬 많습니다. 고객 주문, 자재 재고, 항공편 예약, 전표 내역은 프로그램이 종료되어도 계속 남아 있어야 합니다. 이때 필요한 것이 바로 Transparent Table입니다.

Transparent Table은 DDIC에서 정의하고, 실제 데이터베이스에도 같은 모양으로 만들어지는 영구 저장 창고입니다.

2. Transparent Table은 왜 “투명”할까? 🔍

SAP에서 Transparent Table은 DDIC 설계도와 실제 DB 테이블이 1:1로 대응되는 테이블입니다. 개발자가 DDIC에서 필드 목록을 정의하고 활성화하면, SAP가 실제 데이터베이스에 그 구조와 맞는 물리 테이블을 생성하거나 조정합니다.

“투명”이라는 말은 개발자가 보는 DDIC 테이블 구조와 DB에 존재하는 구조가 유리창처럼 대응된다는 느낌으로 이해하면 됩니다. 우리는 DBMS별 세부 문법을 직접 다루지 않고도, DDIC를 통해 테이블 구조를 관리할 수 있습니다.

💡

Structure와 Transparent Table의 차이

  • Structure: 한 줄 데이터의 모양만 정의합니다. DB에 저장하지 않습니다.
  • Transparent Table: 한 줄 모양을 바탕으로 여러 줄 데이터를 DB에 영구 저장합니다.

3. Table Field를 설계하는 기본 흐름 ✍️

Transparent Table을 만들 때는 필드 목록을 하나씩 추가합니다. 각 필드는 보통 Data Element를 타입으로 가집니다. 그러면 필드가 Domain의 재질, Data Element의 의미와 라벨을 함께 물려받습니다.

  • MANDT: 클라이언트 필드, 보통 맨 앞에 둡니다.
  • CARRID: 항공사 코드
  • CONNID: 편명
  • FLDATE: 출발일
  • PRICE: 요금

여기까지 보면 Structure와 비슷해 보입니다. 하지만 Transparent Table에는 추가로 아주 중요한 질문이 붙습니다. “수많은 데이터 줄 중에서 각 줄을 어떻게 유일하게 구분할 것인가?” 이 질문의 답이 바로 Key Field입니다.

4. Key Field: 똑같은 줄이 두 번 생기지 않게 막기 🔑

Key Field는 테이블의 한 줄을 유일하게 구분하는 기준입니다. 학교의 학번, 주민등록번호, 주문번호처럼 “이 값 조합이면 딱 한 줄만 찾을 수 있다”는 기준을 세우는 것입니다.

🧪

항공편 테이블 키 예시

MANDT + CARRID + CONNID + FLDATE를 키로 잡으면, 같은 클라이언트 안에서 “대한항공 KE, 0017편, 2026-06-09 출발” 데이터는 딱 한 줄만 존재할 수 있습니다.

  • ✅ 처음 저장: 키 조합이 없으므로 저장됩니다.
  • ❌ 같은 키로 다시 저장: 이미 같은 키가 있으므로 중복 오류가 납니다.

키 필드는 테이블 정의의 맨 앞쪽에 모여 있어야 합니다. 중간에 일반 필드가 끼어 있으면 활성화 오류가 날 수 있습니다. 처음 테이블을 만들 때는 “키 필드 먼저, 일반 필드 나중”이라는 리듬을 기억하세요.

5. MANDT와 Client-Dependent: 한 시스템 안의 칸막이 🏢

SAP 업무 테이블을 보면 맨 앞에 MANDT가 있는 경우가 많습니다. MANDT는 클라이언트 번호를 담는 필드입니다. 여기서 클라이언트는 하나의 SAP 시스템 안에서 데이터를 나누는 논리적 구역이라고 보면 됩니다.

예를 들어 같은 개발 시스템 안에도 100번 클라이언트, 200번 클라이언트가 있을 수 있습니다. 사용자가 100번 클라이언트에 로그인하면, 일반적인 Open SQL 조회는 100번 클라이언트 데이터만 보도록 자동으로 조건이 붙습니다. 그래서 다른 클라이언트 데이터가 섞이지 않습니다.

  • Client-Dependent 테이블: MANDT가 있고, 클라이언트별로 데이터가 분리됩니다.
  • Client-Independent 테이블: MANDT가 없고, 모든 클라이언트가 공유하는 성격의 데이터에 사용됩니다. 초보 단계에서는 훨씬 조심해야 합니다.
대부분의 업무 데이터는 Client-Dependent로 생각하는 것이 출발점입니다. MANDT를 빼는 선택은 “왜 공유해야 하는지”가 명확할 때만 합니다.

6. 운영 테이블 변경은 왜 위험할까? 🚨

Transparent Table은 실제 데이터가 쌓이는 창고입니다. 그래서 이미 운영 중인 테이블의 구조를 바꾸는 것은 단순한 화면 수정과 다릅니다. 특히 Key Field와 길이 변경은 매우 조심해야 합니다.

⚠️

키와 길이는 나중에 고치기 어렵습니다

운영 데이터가 수백만 건 쌓인 뒤 키를 추가하거나 필드 길이를 줄이면, 기존 데이터가 새 구조에 맞지 않아 테이블 변환 오류가 날 수 있습니다. 데이터가 잘리거나 중복 기준이 바뀌면 업무 영향도 큽니다. 새 일반 필드를 뒤에 추가하는 것보다 훨씬 위험합니다.

  • ✅ 개발 초기: 키와 필드 의미를 충분히 고민하고, 테스트 데이터를 넣어 중복 방지가 맞는지 확인합니다.
  • ❌ 운영 이후: “필드 하나만 바꾸면 되겠지”라고 가볍게 생각하지 않습니다. 데이터 변환, 영향 프로그램, 인터페이스까지 확인해야 합니다.

7. 한눈에 정리 🏁

📝

오늘의 핵심만 딱 잡기

  • Transparent Table은 데이터를 실제 DB에 영구 저장하는 DDIC 테이블입니다.
  • Structure는 한 줄 모양이고, Transparent Table은 그 모양의 여러 줄을 저장하는 창고입니다.
  • Key Field는 한 줄을 유일하게 구분하고 중복 저장을 막습니다.
  • MANDT가 있는 테이블은 보통 Client-Dependent로, 클라이언트별 데이터가 자동 분리됩니다.
  • 운영 테이블의 키와 필드 길이 변경은 데이터 변환 위험이 있어 매우 신중해야 합니다.

이제 우리는 데이터 창고의 모양과 키를 설계했습니다. 다음 Lesson Technical Settings와 데이터 확인 기초에서는 이 창고를 실제 DB에 어떻게 배치할지 정하고, Data Browser로 안에 든 데이터를 확인해보겠습니다.
