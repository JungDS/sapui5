학습 목표

이번 Lesson에서는 데이터를 실제 DB에 오래 저장하는 Transparent Table을 만듭니다. 지난 Lesson의 Structure와 무엇이 다른지, Key Field가 왜 필요한지, MANDT가 client-dependent 데이터 분리에 어떤 역할을 하는지 잡습니다.

1. Structure에서 저장소로 넘어간다

지난 Lesson의 Structure는 “데이터 한 줄이 어떤 모양인지”만 정해 둔 것이었습니다. 값을 보관하지는 않으므로, 프로그램이 끝나면 Work Area에 담겼던 값은 모두 사라집니다. 즉 Structure는 그릇의 설계도일 뿐 창고가 아닙니다.

Transparent Table은 ABAP Dictionary에 두는 테이블 정의(설계도)입니다. 이것을 활성화하면 데이터베이스 서버에 같은 이름의 실제 DB Table이 만들어지고, 데이터는 바로 그 DB Table에 저장됩니다. 즉 Transparent Table 자체가 데이터를 담는 게 아니라, 담을 DB Table을 만들기 위한 정의입니다. (이 구분은 바로 아래 §2에서 자세히)

한마디로 — Structure는 “한 줄 모양”, Transparent Table은 “그 줄들을 저장할 DB Table을 만드는 DDIC 설계도”입니다. 실제 저장은 동명 DB Table이 합니다.

한 줄 타입과 DB 저장소 비교

Structure
  • 한 줄 데이터 타입입니다.
  • DB에 물리 저장소를 만들지 않습니다.
  • Work Area, 파라미터, Table Type의 row type으로 씁니다.
Transparent Table
  • DB Table을 만드는 DDIC 정의입니다 (저장소 자체가 아님).
  • 활성화하면 같은 이름의 DB Table이 생기고, 데이터는 그 DB Table에 저장됩니다.
  • 변수 타입으로 쓰면 한 줄짜리 구조 변수가 됩니다.

활성화하면 같은 이름의 실제 DB 테이블이 생겨 데이터를 오래 보관할 수 있습니다. 이 테이블을 실제로 조회·입력하는 구문(ABAP SQL)은 뒤 Chapter에서 배웁니다 — 지금은 “Structure는 모양, Transparent Table은 저장소”만 확실히 기억하면 됩니다.

2. 중요한 오해 바로잡기: Transparent Table은 ‘DB Table’이 아니다

가장 흔한 오해부터 잡고 갑니다. Transparent Table은 데이터를 담는 테이블이 아닙니다. ABAP Dictionary(SE11)에 두는 ‘테이블 정의(설계도)’일 뿐입니다. 활성화하면 SAP가 데이터베이스 서버에 같은 이름의 실제 DB Table을 만들고, 데이터는 그 DB Table에 저장됩니다. (아래 예시는 어느 교육 서버에나 있는 표준 항공사 테이블 SCARR로 봅니다.)

세 개의 층으로 보기

① ABAP Program
DATA gs TYPE scarr.
Transparent Table을 타입으로 쓰면 gs는 테이블이 아니라 한 줄짜리 구조(Structure) 변수가 됩니다.
② ABAP Dictionary (SE11)
Transparent Table SCARR 정의(설계도) — 표준 항공사 테이블
필드 목록 · Key · 속성만 정의. 여기엔 데이터가 없습니다.
③ Database Server
동일 이름의 실제 DB Table SCARR
SAP가 만들어 둔 실제 테이블. 항공사 데이터(코드·이름·통화 등)가 들어 있습니다.

②를 활성화하면 ③이 같은 구조로 만들어집니다. SE11에서 Transparent Table로 데이터를 “조회”해 볼 수도 있지만, 그것은 Transparent Table에 든 데이터가 아니라 동명 DB Table(③)에서 읽어온 것입니다.

⚠️

“타입으로 쓰면 테이블이 아니라 한 줄(구조)”

DATA gs TYPE scarr.처럼 Transparent Table 이름을 변수 타입으로 쓰면, gs는 테이블이 아니라 한 줄짜리 구조(Structure) 변수가 됩니다. 여러 줄을 담는 내부 테이블은 별도의 Table Type으로 만들고, 실제 DB 조회(SELECT)와 함께 뒤 Chapter에서 배웁니다.

3. Field List는 Data Element 중심으로 만든다

Transparent Table의 각 열은 Table Field입니다. SAP Learning은 field list 편집 시 Data Element 사용을 권장하며, Domain은 field list에 직접 사용할 수 없다고 설명합니다. Domain은 Data Element 아래의 기술 기반입니다.

테이블 필드가 의미를 받는 흐름

Domain
타입, 길이, 값 범위
직접 테이블 필드 타입으로 쓰지 않음
→
Data Element
업무 의미, 라벨, F1 설명
테이블 필드 타입으로 사용
→
Table Field
ORDER_ID, CUSTOMER_ID, STATUS
DB 테이블의 실제 열

4. Key Field는 한 줄을 유일하게 찾는 기준이다

Transparent Table에는 각 row를 식별할 수 있는 Primary Key가 필요합니다. 이 Primary Key를 이루는 필드가 Key Field입니다. SAP Learning은 모든 database table에 primary key가 필요하고, key field는 field list의 시작 부분에 모여 있어야 한다고 설명합니다.

주문 테이블 key 설계

Key? 순서 필드 역할
Key 1 MANDT client 구분
Key 2 ORDER_ID 주문 번호
일반 3 CUSTOMER_ID 고객 번호
일반 4 STATUS 주문 상태

같은 MANDT + ORDER_ID 조합은 한 테이블 안에서 두 번 존재할 수 없습니다.

Key Field 사이에 일반 필드를 넣어도 될까?

안 됩니다. Key field는 field list의 시작 부분에 함께 있어야 합니다. 초급 단계에서는 “키 먼저, 일반 필드 나중”으로 기억하세요.

5. MANDT는 client 칸막이다

SAP 업무 테이블에서 MANDT는 보통 첫 번째 Key Field입니다. 이것은 “이 row가 어느 client의 데이터인가?”를 표시합니다. CLNT 타입 key field가 첫 번째에 있으면 client field로 취급되고, 기본 접근은 로그인 client 기준으로 제한됩니다.

같은 시스템 안의 client 분리

Client 100
MANDT = 100
교육 데이터
100번 로그인 사용자가 기본 조회
Client 200
MANDT = 200
테스트 데이터
200번 로그인 사용자가 기본 조회
Client-independent
MANDT 없음
모든 client가 공유
초급 단계에서는 매우 신중
⚠️

MANDT는 회사 코드가 아닙니다

MANDT는 SAP client를 구분하는 시스템 필드입니다. 회사 코드 같은 업무 조직 필드와 섞어 외우면 안 됩니다. 대부분의 업무 데이터는 client-dependent를 기본 출발점으로 둡니다.

SAP GUI 명령창에 SE11(또는 /nSE11)을 입력해 시작합니다. 아래 4단계 — ① 초기 화면 → ② 생성 화면 → ③ Technical Settings → ④ Activate — 를 순서대로 따라가며 만들어 보세요. ① 화면의 Create를 누르면 ②로 이동합니다. (예시 테이블: ZT00_TEST001)

테이블의 기본 속성(설명·생성자·패키지 등)을 보는 탭입니다. 연습에서는 Short Description만 확인하고 넘어갑니다.

필드별 외래키(Foreign Key) · 검색도움말(Search Help)을 연결해 입력값 검증·F4 도움말을 구성하는 탭입니다. (자세히는 Chapter 4)

SAP에서 금액·수량 필드는 단독으로 존재할 수 없습니다. 반드시 “단위” 필드와 짝을 이뤄야 의미가 생기며, 이 탭에서 그 짝을 연결합니다.

데이터 필드타입짝지을 단위 필드단위 타입예시
금액 (Amount)CURR통화 키 (Currency Key)CUKY1,000 + KRW
수량 (Quantity)QUAN수량 단위 (Unit)UNIT5 + EA

예: 금액 NETWR(CURR)는 통화 WAERS(CUKY)와 함께 봐야 “1,000원”인지 “1,000달러”인지 구분됩니다. 만약 CURR/QUAN 필드를 넣었다면 이 탭에서 짝 단위 필드를 지정하지 않으면 활성화가 실패합니다. (이 연습 테이블엔 금액·수량 타입이 없어 비어 있습니다.)

보조 인덱스(Secondary Index)를 정의하는 탭입니다. 다만 SAP S/4HANA(SAP HANA DB)에서는 보조 인덱스를 일반적으로 권장하지 않습니다. HANA는 컬럼 기반 인메모리 저장이라 대부분의 조회를 인덱스 없이도 빠르게 처리하기 때문입니다. 꼭 필요하다고 측정으로 입증된 경우에만 신중히 추가합니다.

활성화 성공 = 진짜 테이블 탄생

활성화가 끝나면 같은 이름의 실제 DB 테이블이 생겨 레코드를 CRUD할 수 있습니다. 저장(Save)만으로는 아직 만들어지지 않는다는 점을 꼭 기억하세요.

테이블 설계에서 가장 흔한 두 실수

❌ 안티패턴
  • MANDT 누락: 첫 필드에 MANDT가 없으면 client-independent가 되어 개발·테스트·운영 데이터가 한 저장소에 뒤섞입니다.
  • Key 비연속 배치: MANDT(Key) → ZNAME(일반) → ZID(Key)처럼 key 사이에 일반 필드를 끼우면 활성화 시 “Key fields must be at the beginning” 오류가 납니다.
✅ 올바른 설계
  • 1번 필드 = MANDT (Data Element도 MANDT, Key 체크).
  • Key는 MANDT → ZID처럼 맨 앞에 연속 배치한 뒤 일반 필드를 둡니다.

규칙: Key 필드는 반드시 테이블 시작 부분에 연속으로 모여 있어야 합니다 (중간에 일반 필드를 끼우면 활성화 시 오류).

7. Technical Settings까지 이어진다

Table Field와 Key를 채웠다고 끝이 아닙니다. Transparent Table은 실제 DB 저장 대상이므로 Technical Settings가 중요합니다. M06에서 자세히 다루지만, 지금은 연결만 잡아둡니다.

저장만 하면 DB 테이블이 생길까?

아닙니다. 저장은 비활성 버전 보관에 가깝습니다. 다른 객체와 프로그램이 믿고 쓰려면 활성화가 성공해야 합니다. 활성화 과정에서 테이블 정의와 관련 설정이 검사됩니다.

9. 확인 퀴즈

  1. Structure와 Transparent Table의 가장 큰 차이는 무엇인가요?
  2. Primary Key를 이루는 필드는 무엇이라고 부르나요?
  3. Key Field는 field list의 어디에 있어야 하나요?
  4. MANDT는 회사 코드와 같은 업무 필드인가요?
  5. 같은 key 조합으로 두 row를 저장하려고 하면 왜 막혀야 할까요?
정답/해설 보기
  1. 영구 저장 여부입니다. Structure는 타입이고, Transparent Table은 DB 저장 대상입니다.
  2. Key Field입니다. Key Field 조합은 table row를 유일하게 식별합니다.
  3. Field list의 시작 부분에 모여 있어야 합니다. key 사이에 non-key field를 끼우면 안 됩니다.
  4. 아니요. MANDT는 SAP client를 구분하는 시스템 필드입니다. 회사 코드와 다릅니다.
  5. row 유일성이 깨지기 때문입니다. 같은 key 조합이 두 개 있으면 어떤 row가 대상인지 구분할 수 없습니다.
