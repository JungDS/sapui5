학습 목표

CDS 데이터를 "누가 볼 수 있는가"를 제어하는 DCL(Data Control Language)과 행 단위 권한(Access Control)을 개요 수준으로 배웁니다. CDS Chapter를 마무리합니다.

1. 지난 시간 연결: 데이터를 잘 만들었는데, 보안은? 🔐

지금까지 CDS로 데이터를 합치고(Association) 의미를 입혔습니다(Annotation). 그런데 한 가지가 남았습니다. "이 데이터를 이 사용자가 봐도 되는가?" THEORY-13에서 리포트에 AUTHORITY-CHECK를 걸었듯, CDS에도 권한 장치가 있습니다.

그것이 DCL로 정의하는 Access Control입니다.

2. DDL은 "구조", DCL은 "권한" 🧱

  • DDL(앞서 배운 것): View의 구조·데이터를 정의.
  • DCL: 그 View를 조회할 때 행 단위로 자동 필터를 거는 권한 규칙.
" CDS View에 권한 검사 켜기 (M01에서 본 헤더)
@AccessControl.authorizationCheck: #CHECK
define view entity ZI_Flight as select from sflight { ... }
" 별도 DCL: 사용자의 권한에 맞는 항공사 데이터만 보이게
@MappingRole: true
define role ZI_Flight_Role {
  grant select on ZI_Flight
    where ( carrid ) = aspect pfcg_auth( S_CARRID, CARRID, ACTVT = '03' );
}
💡

비유: 자동 출입 통제

DCL은 건물의 자동 출입 통제와 같아요. 사용자가 데이터를 조회하면, 그 사람의 출입증(권한)으로 들어갈 수 있는 층(항공사)만 자동으로 보입니다. 개발자가 매번 조건을 안 걸어도 시스템이 알아서 걸러줍니다.

3. 자동으로 걸리는 행 필터 🔍

DCL이 걸린 CDS를 SELECT하면, SAP가 로그인한 사용자의 권한에 맞는 행만 자동으로 돌려줍니다. THEORY-01의 MANDT(클라이언트 자동 분리)와 비슷한 느낌으로, 권한 기준의 자동 필터가 한 겹 더 얹히는 것입니다.

4. 정상 흐름과 오류 흐름 🔍

  • ✅ 정상: authorizationCheck: #CHECK + DCL 정의 → 권한 있는 행만 조회됨.
  • ❌ 오류 1: #NOT_REQUIRED로 열어두고 민감 데이터 노출 → 보안 사고. 운영 데이터는 반드시 검사.
  • ❌ 오류 2: DCL의 권한 객체(S_CARRID 등)를 실제 권한 설계와 다르게 매핑 → 권한자가 못 보거나 비권한자가 봄.

5. 실무에서 조심할 점 🚨

⚠️

권한은 "기본 켜짐"으로 설계하세요

편하다고 authorizationCheck: #NOT_REQUIRED로 두면 누구나 전체 데이터를 봅니다. 학습·기술 뷰가 아니라면 권한 검사를 기본으로 켜고, 어떤 권한 객체로 거를지 보안 담당자와 협의하세요. DCL은 강력하지만 잘못 설계하면 "봐야 할 사람이 못 보거나, 못 볼 사람이 보는" 양방향 사고가 납니다. 권한은 항상 신중하게.

6. 한눈에 정리 🏁

📝

THEORY-20 마무리 핵심

  • CDS: View Entity(DDL) → Interface/Projection 2계층 → Association → Annotation → MDE → DCL.
  • DCL/Access Control은 조회 시 권한에 맞는 행만 자동 필터합니다.
  • authorizationCheck: #CHECK로 검사를 켜고 DCL role로 규칙을 정의합니다.
  • 운영 데이터는 권한 검사를 기본으로 켜고 신중히 설계합니다.
