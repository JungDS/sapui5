학습 목표

CDS 데이터를 "누가 볼 수 있는가"를 제어하는 DCL(Data Control Language)과 행 단위 권한(Access Control)을 개요 수준으로 배웁니다. CDS Chapter를 마무리합니다.

1. 지난 시간 연결: 데이터를 잘 만들었는데, 보안은? 🔐

지금까지 CDS로 데이터를 합치고(Association) 의미를 입혔습니다(Annotation). 그런데 한 가지가 남았습니다. "이 데이터를 이 사용자가 봐도 되는가?" Chapter 13에서 리포트에 AUTHORITY-CHECK를 걸었듯, CDS에도 권한 장치가 있습니다.

그것이 DCL로 정의하는 Access Control입니다.

2. DDL은 "구조", DCL은 "권한" 🧱

  • DDL(앞서 배운 것): View의 구조·데이터를 정의.
  • DCL: 그 View를 조회할 때 행 단위로 자동 필터를 거는 권한 규칙.

💡

비유: 자동 출입 통제

DCL은 건물의 자동 출입 통제와 같아요. 사용자가 데이터를 조회하면, 그 사람의 출입증(권한)으로 들어갈 수 있는 층(항공사)만 자동으로 보입니다. 개발자가 매번 조건을 안 걸어도 시스템이 알아서 걸러줍니다.

3. 자동으로 걸리는 행 필터 🔍

DCL이 걸린 CDS를 SELECT하면, SAP가 로그인한 사용자의 권한에 맞는 행만 자동으로 돌려줍니다. Chapter 1의 MANDT(클라이언트 자동 분리)와 비슷한 느낌으로, 권한 기준의 자동 필터가 한 겹 더 얹히는 것입니다.

4. 정상 흐름과 오류 흐름 🔍

  • ✅ 정상: authorizationCheck: #CHECK + DCL 정의 → 권한 있는 행만 조회됨.
  • ❌ 오류 1: #NOT_REQUIRED로 열어두고 민감 데이터 노출 → 보안 사고. 운영 데이터는 반드시 검사.
  • ❌ 오류 2: DCL의 권한 객체(S_CARRID 등)를 실제 권한 설계와 다르게 매핑 → 권한자가 못 보거나 비권한자가 봄.

5. 실무에서 조심할 점 🚨

⚠️

권한은 "기본 켜짐"으로 설계하세요

편하다고 authorizationCheck: #NOT_REQUIRED로 두면 누구나 전체 데이터를 봅니다. 학습·기술 뷰가 아니라면 권한 검사를 기본으로 켜고, 어떤 권한 객체로 거를지 보안 담당자와 협의하세요. DCL은 강력하지만 잘못 설계하면 "봐야 할 사람이 못 보거나, 못 볼 사람이 보는" 양방향 사고가 납니다. 권한은 항상 신중하게.

6. 미니 실습: DCL 권한 필터 흐름 그리기 🧪

이번 실습은 DCL을 별도 보안 문서처럼 보지 않고, CDS 조회 결과에 행 단위 필터가 어떻게 얹히는지 흐름으로 이해하는 데 목적이 있습니다.

✍️

실습 과제

  1. CDS DDL, DCL Role, 사용자 권한, 최종 조회 결과를 화살표로 연결해봅니다.
  2. @AccessControl.authorizationCheck와 DCL Role의 역할 차이를 한 문장씩 적습니다.
  3. 개발 환경에서 #NOT_REQUIRED를 쓴 예제가 운영 기준으로 그대로 가면 왜 위험한지 적습니다.

완료 조건: DCL이 화면 숨김이 아니라 CDS 조회 결과 자체를 제한하는 권한 계층이라는 점을 설명할 수 있으면 성공입니다.

7. 공식 문서로 더 확인하기 🔗

  • SAP Help Portal: CDS DCL DEFINE ROLE - DCL Role 선언 문법을 확인합니다.
  • SAP Help Portal: DCL Grant Rule - 접근 규칙이 CDS 엔티티에 어떻게 부여되는지 확인합니다.
  • SAP Help Portal: Conditional Access Rule - 조건부 접근 규칙으로 행 제한을 적용하는 방식을 확인합니다.

8. 확인 퀴즈와 정답/해설 ✅

  1. DCL은 CDS의 어떤 측면을 보완하나요?
  2. @AccessControl.authorizationCheck만 있으면 권한 로직이 완성되나요?
  3. 권한 필터를 UI에서만 처리하면 왜 위험한가요?
정답/해설 보기
  1. 데이터 접근 제어를 보완합니다. DDL이 구조와 의미를 정의한다면 DCL은 누가 어떤 행을 볼 수 있는지 제한합니다.
  2. 아닙니다. Annotation은 권한 검사 정책을 명시하는 역할이고, 실제 제한 조건은 DCL Role과 권한 설계에서 구체화됩니다.
  3. 다른 소비 경로에서 우회될 수 있기 때문입니다. CDS/DCL 계층에서 제한하면 여러 소비자에게 일관된 보안 기준을 적용하기 쉽습니다.
