Transport Request / CTS 입문

SAP 시스템에서 작성한 코드, 오브젝트, 딕셔너리를 검증 시스템 및 운영 시스템으로 이송하는 CTS(Change and Transport System)의 개념과 실무 반영 절차를 이해한다.

01 · CTS 개요

SAP의 고유한 소스 배포 관리 체계

SAP는 별도의 파일 업로드나 외부 CI/CD 빌드 없이 자체 DB와 시스템 간 RFC 연결을 사용하여 변경 사항을 동기화합니다. 이를 가능하게 해주는 아키텍처가 바로 CTS와 TR(Transport Request)입니다.

시스템 단계수행 주체역할 및 상태 관리
DEV (개발 시스템)개발자신규 소스 작성 및 Customizing 수행. TR 생성 및 잠금 설정.
QAS (검증 시스템)현업 / QA 담당자DEV에서 이송(Import) 완료된 소스를 테스트하고 실무 정합성 검증.
PRD (운영 시스템)시스템 관리자(Basis)검증 완료된 TR을 일괄 또는 개별 운영 반영하여 실서비스 오픈.
02 · 실무 TR 이송 절차

TR을 이송하기 위한 정형화된 루틴

1단계: TR 생성 및 Task 할당

오브젝트를 처음 저장할 때 TR 팝업이 뜹니다. 하나의 TR 밑에 다수의 작업자 Task가 묶이며, 작업이 진행되는 동안 오브젝트는 다른 사람의 변경이 불가능하도록 Lock 상태가 유지됩니다.

2단계: Task 및 TR 릴리즈 (Release)

개발 완료 후 ADT나 SAP GUI(SE09/SE10)에서 하위 Task를 먼저 Release하고, 최상위 TR을 Release합니다. 이 시점에 소스 오브젝트가 바이너리 파일 형태로 서버 물리 디렉토리에 export됩니다.

3단계: 이송 요청 및 모니터링

Basis 담당자에게 TR 번호를 공유하여 QAS/PRD로 Import를 요청합니다. 이송 성공 여부는 이송 로그(STMS)의 Return Code(정상: 0 또는 4, 오류: 8 또는 12)를 통해 최종 검증합니다.

주의: 이송 순서 누락 (Sequence Issue)

도메인, 데이터 엘리먼트 등 참조 오브젝트가 포함된 TR이 메인 프로그램 TR보다 나중에 이송되면 'Syntax Error'로 시스템이 중단될 수 있습니다. 종속성을 고려한 이송 순서 관리가 생명입니다.

03 · 학습 체크리스트

배포 관리를 마스터하기 위해 확인할 포인트

  1. Workbench Request(소스 코드용)와 Customizing Request(테이블 셋팅용)의 차이를 안다.
  2. T-Code `SE09` 혹은 ADT의 Transport Organizer에서 TR의 구조와 상태를 추적할 수 있다.
  3. 이송 결과인 Return Code 4, 8, 12의 세부 의미와 대처법을 이해한다.
