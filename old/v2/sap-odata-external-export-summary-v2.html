SAP에 저장된 데이터를 외부(인터넷)로 내보내는 방법

핵심: OData 서비스를 만들어 외부 시스템(웹/앱/서드파티)에서 SAP 데이터를 조회·등록·변경·삭제(CRUD)할 수 있도록 제공합니다.

주요 선택지 SEGW(ABAP) · CDS OData Publish · RAP(Service Definition/Binding) 버전 OData V2 / V4 기능 범위 조회(R) · 쓰기(CUD)

1) SAP GUI — SEGW에서 Gateway Project로 서비스 제공

ABAP 중심 · 유연성 높음

SEGW 기반 방식은 서비스 모델(엔티티/관계)을 정의하고, ABAP로 로직을 구현하는 전통적인 Gateway 개발 흐름입니다.

1-1. Data Model을 직접 만들고 ABAP으로 직접 코딩

장점

  • 커스터마이징 자유도가 높습니다.
  • CRUD 구현이 비교적 직관적입니다(요구사항 반영 용이).

단점

  • 난이도가 높습니다(ABAP 개발 역량 필요).

1-2. Data Model을 Import(가져오기)하여 생성

  • (1) DDIC Structure 이용
    • Database Table
    • 각종 View
    • Structure Type
  • (2) RFC / BOR 이용
    • 함수의 Export 또는 Tables 파라미터를 이용해 Entity 생성
  • (3) Search Help 이용
    • Parameter를 이용해 Entity 생성

1-3. 서비스를 구현하는 방법(데이터 소스 매핑)

  • (1) Map to data source → RFC/BOR
  • (2) Map to data source → CDS View (조회 기능만 구현)

1-4. Data Model & 서비스 구현을 “한방에” 구성

  • (1) Reference 이용 → CDS View (조회 기능)
  • BO 기반 managed 방식 (쓰기 기능)
조회는 CDS로 빠르게 구성하고, 쓰기는 BO(Managed)로 표준 패턴을 타는 조합이 실무에서 자주 활용됩니다.

2) Eclipse(ADT) — CDS View에서 OData 서비스를 직접 제공

모던 개발 흐름 · RAP 연계

ADT에서 CDS와 서비스 정의/바인딩을 활용하면, 설계 의도를 더 명확하게 유지하면서 OData를 노출할 수 있습니다.

2-1. @OData.publish: true로 서비스 제공

  • 조회 전용(Read-only) 목적에 적합합니다.
  • OData V2만 서비스가 가능합니다.

2-2. Service Definition & Service Binding 생성

  • 조회(R)는 가능하지만, 쓰기(CUD)는 BO(Behavior)가 필요합니다.
  • OData V2 또는 V4 선택이 가능합니다.
  • RAP에서 핵심적으로 활용합니다.
빠른 판단 기준
- 조회만 필요: @OData.publish: true (단, V2 한정)
- 표준 지향 + 확장성 + 장기 유지보수: Service Definition/Binding + RAP(특히 V4) 방향을 권장합니다.

요약

실무 관점 빠른 비교

SEGW (SAP GUI)

  • ABAP 구현 중심으로 자유도가 높습니다.
  • CRUD 요구가 강하고 기존 Gateway 자산이 많을 때 유리합니다.

ADT (CDS / RAP)

  • 설계(모델) 중심으로 표준화·확장성이 좋습니다.
  • 장기적으로는 RAP + Service Binding이 전략적으로 유리합니다.
